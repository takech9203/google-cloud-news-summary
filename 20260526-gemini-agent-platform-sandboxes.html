🚀 概要

Gemini Enterprise Agent Platform に、AI エージェントの実行環境を大幅に強化する 4 つの新しいサンドボックス機能 が Preview として追加されました。GKE Agent Sandbox をベースに構築され、Kubernetes CRD を活用して AI エージェントが安全に隔離された環境で信頼できないコードやタスクを実行できるようにします。

🔄 Before / After

❌ Before (課題)

  • ブラウザタスク自動化のセキュア環境が未提供
  • カスタム依存関係ワークロードに独自インフラが必要
  • サンドボックスを毎回一から構築、起動に時間がかかる
  • 環境の状態保存・復元の標準的方法が存在しない

✅ After (改善)

  • 隔離 Chrome 環境で API/CDP 経由のブラウザ制御
  • Artifact Registry からカスタムコンテナを持ち込み実行
  • 事前ウォームプールで 1 秒未満の高速起動
  • スナップショットで完全な状態保存・復元が可能

⚡ 主要機能

🖥️ Computer Use

AI エージェントが隔離された Web ブラウザ環境内でブラウザベースのタスクを自動化。API 経由または Chrome DevTools Protocol (CDP) を使用して直接ブラウザを制御します。

  • gVisor によるカーネルレベル分離
  • フォーム入力、Web スクレイピング、UI テスト

📦 Custom Container Sandboxes

BYOC (Bring Your Own Container) により、独自のコンテナをサンドボックスとして実行可能。Artifact Registry にホストされた専用依存関係に対応。

  • Google 提供ベースコンテナ (Standard / Slim)
  • 特殊 ML フレームワーク対応

📄 Sandbox Templates

SandboxTemplate CRD で再利用可能なテンプレートを定義。SandboxWarmPool と連携し、事前ウォームされたインスタンスで即座にプロビジョニング。

  • SandboxClaim による 1 秒未満のプロビジョニング
  • ネットワークポリシー、リソース制限を一元定義

📷 Sandbox Snapshots

サンドボックスの完全な状態 (依存関係、ファイルシステム、プロセス状態) を Cloud Storage に保存。新しいサンドボックスに復元可能。

  • PodSnapshotStorageConfig / PodSnapshotPolicy CRD
  • ウォームプールと組み合わせて instant-on を実現

🛠️ 設定方法

💡 前提条件: GKE クラスタ (v1.35.2-gke.1269000 以降)、Artifact Registry API / Kubernetes Engine API の有効化、roles/container.admin IAM ロール、gVisor 対応ノードプール

Step 1: Agent Sandbox の有効化

Bash クラスタ作成 / 更新 
# Autopilot クラスタの場合
gcloud beta container clusters create-auto ${CLUSTER_NAME} \
  --location=${LOCATION} \
  --cluster-version=${CLUSTER_VERSION} \
  --enable-agent-sandbox

# 既存クラスタの場合
gcloud beta container clusters update ${CLUSTER_NAME} \
  --location=${LOCATION} \
  --enable-agent-sandbox

Step 2: SandboxTemplate と WarmPool の作成

YAML SandboxTemplate 定義例 
apiVersion: extensions.agents.x-k8s.io/v1alpha1
kind: SandboxTemplate
metadata:
  name: python-runtime-template
  namespace: default
spec:
  podTemplate:
    metadata:
      labels:
        sandbox-type: python-runtime
    spec:
      runtimeClassName: gvisor
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
      nodeSelector:
        sandbox.gke.io/runtime: gvisor
      tolerations:
        - key: "sandbox.gke.io/runtime"
          value: "gvisor"
          effect: "NoSchedule"
      containers:
        - name: runtime
          image: registry.k8s.io/agent-sandbox/python-runtime-sandbox:v0.1.0
          ports:
            - containerPort: 8888
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "500m"
              memory: "1Gi"
          securityContext:
            capabilities:
              drop: ["ALL"]
      restartPolicy: OnFailure

Step 3: SandboxClaim の作成

Bash サンドボックスリクエスト 
kubectl apply -f - <<EOF
apiVersion: extensions.agents.x-k8s.io/v1alpha1
kind: SandboxClaim
metadata:
  name: my-sandbox-claim
  namespace: default
spec:
  sandboxTemplateRef:
    name: python-runtime-template
EOF

Step 4: スナップショットの設定 (オプション)

YAML スナップショットストレージ設定 
apiVersion: podsnapshot.gke.io/v1
kind: PodSnapshotStorageConfig
metadata:
  name: snapshot-storage-config
spec:
  snapshotStorageConfig:
    gcs:
      bucket: "${BUCKET_NAME}"
---
apiVersion: podsnapshot.gke.io/v1
kind: PodSnapshotPolicy
metadata:
  name: snapshot-policy
  namespace: default
spec:
  storageConfigName: snapshot-storage-config
  selector:
    matchLabels:
      app: agent-sandbox-workload
  triggerConfig:
    type: manual
    postCheckpoint: resume
  snapshotGroupingRules:
    groupRetentionPolicy:
      maxSnapshotCountPerGroup: 2

🌟 メリット

ビジネス面

🚀開発スピードの向上 - テンプレートとウォームプールにより、プロビジョニングが 1 秒未満で完了。エージェント開発のイテレーションサイクルが大幅短縮。
💰運用コストの削減 - スナップショットにより環境の再構築が不要。インフラの維持管理工数を削減。
🔒セキュリティコンプライアンス - gVisor によるカーネルレベル分離が標準化。信頼できないコードの実行に関するセキュリティ要件を容易に達成。

技術面

⚡サブ秒プロビジョニング - ウォームプールにより通常の Pod スケジューリングよりも大幅に高速な環境提供
📄宣言的 API - Kubernetes ネイティブな CRD ベースの管理。GitOps ワークフローとの統合が容易
💻プログラマティックアクセス - Python SDK を通じて LangChain や Vertex AI Agentic SDK から直接サンドボックスを管理可能
🛡️Default Deny ネットワークポリシー - サンドボックス内コードが不正な内部ネットワークや GKE コントロールプレーンへのアクセスを防止

⚠️ 制約事項・注意点

⚠️ 制限事項:
  • GKE バージョン 1.35.2-gke.1269000 以降が必要
  • Pod スナップショットは E2 マシンタイプをサポートしていない (N2 または C3 を推奨)
  • Preview ステータスであり、本番環境での使用は SLA の対象外
  • Kata Containers を使用する場合、Google のサポートと SLA は適用されない
💡 考慮すべき点:
  • ウォームプールの常時稼働インスタンスはリソースコストが発生する
  • スナップショット保存には Cloud Storage の容量と料金が必要
  • Autopilot クラスタではデフォルトで E2 ノードが使用されるため、スナップショット利用時は ComputeClass の設定が必要
  • Computer use 機能ではブラウザ内のデータがエージェントに公開されるため、機密情報の取り扱いに注意

💡 ユースケース

🌐 AI エージェントによる Web タスクの自動化

シナリオ: カスタマーサポートの AI エージェントが、顧客の依頼に基づき社内ツールの Web UI を操作してチケットを作成・更新する。

Python CDP 経由ブラウザ制御例 
from agentic_sandbox import SandboxClient

# サンドボックスを作成してブラウザを起動
client = SandboxClient()
sandbox = client.create(template="browser-automation-template")

# CDP 経由でブラウザを制御
cdp_session = sandbox.connect_cdp()
cdp_session.navigate("https://internal-tool.example.com")
cdp_session.click("#new-ticket-button")
cdp_session.fill("#description", ticket_description)

効果: セキュアな隔離環境内でブラウザ操作を行い、エージェントが意図しないリソースにアクセスするリスクを排除。

🤖 ML モデルの安全な評価環境

シナリオ: データサイエンスチームが、カスタム依存関係を含む ML モデルの評価パイプラインをサンドボックス内で実行し、評価完了後に環境状態をスナップショットとして保存する。

効果: カスタムコンテナで独自 ML フレームワークを安全に実行。スナップショットで評価環境を任意の時点に復元可能。実験の再現性が向上。

⚡ 開発環境の即時プロビジョニング

シナリオ: プラットフォームチームが開発者に対して、事前構成済みの開発環境をオンデマンドで 1 秒未満で提供する。

効果: ウォームプールとテンプレートの組み合わせにより、環境セットアップの待ち時間なく即座にコーディングを開始可能。スナップショットにより前日の作業状態から再開可能。

💰 料金情報

💡 Agent Sandbox 自体は GKE の追加料金なしで提供されます。 通常の GKE リソース料金 (Compute、Storage、Networking) が適用されます。
リソース 月額料金 (概算)
GKE クラスタ (Autopilot, e2-standard-4 相当) 通常の GKE 料金に準拠
N2 ノード (スナップショット対応) Compute Engine の N2 料金に準拠
Cloud Storage (スナップショット保存) $0.020/GB/月 (Standard)
ウォームプール常時稼働分 Pod リソース使用量に応じた GKE 料金

🌎 利用可能リージョン

GKE Agent Sandbox は GKE が利用可能な全リージョン で使用できます。ただし、Pod スナップショット機能は Preview 段階であり、特定のリージョンでの利用可能性が制限される場合があります。

📍 推奨リージョン: us-central1

📝 まとめ

今回の Agent Platform Sandboxes アップデートは、AI エージェントの実行環境に関する包括的な機能強化であり、セキュリティ、パフォーマンス、柔軟性の全てを向上させます。

特にウォームプールによる 1 秒未満のプロビジョニングとスナップショットによる状態保存・復元は、エージェントの実用化に向けた重要なマイルストーンです。

👉 推奨アクション: AI エージェントの本格的な開発・運用を計画しているチームは、GKE クラスタでの Agent Sandbox 有効化を検討し、Preview 段階での評価を開始することを推奨します。
