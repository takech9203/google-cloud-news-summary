🔐 Confidential GKE Nodes

Autopilot クラスターで AMD SEV-SNP / Intel TDX をクラスターレベルでサポート。ハードウェアベースのメモリ暗号化により全ノードを保護。

📊 L4LBConfig CRD

GKE 1.36.0-gke.2459000 以降で L4 ロードバランサーの Cloud Logging を CRD で宣言的に設定可能。

🔄 Before / After 比較

❌ Before

  • Autopilot で AMD SEV のみサポート (SEV-SNP / TDX 不可)
  • L4 LB のロギング設定はコンソール/CLI で手動設定
  • ロギング設定が Kubernetes マニフェスト管理対象外
  • Infrastructure as Code の一貫性が欠如

✅ After

  • Autopilot で AMD SEV-SNP / Intel TDX をクラスターレベルで有効化可能
  • L4LBConfig CRD で宣言的にロギング設定を管理
  • Service アノテーションで CRD を参照し GitOps 統合
  • CI/CD パイプラインとシームレスに連携

🔐 主要機能 1: Confidential GKE Nodes

Autopilot クラスターレベルでの AMD SEV-SNP / Intel TDX 対応

→クラスター作成時に指定: --confidential-node-type フラグで sev_snp または tdx を選択
→全ノード保護: クラスター内の全ノードが選択した技術で暗号化保護
→不可逆設定: クラスターレベルでの設定は後からの無効化やオーバーライドが不可
→AMD SEV-SNP: Secure Nested Paging により、ハイパーバイザーからのメモリ攻撃に対する追加保護を提供
→Intel TDX: Trust Domain Extensions により、VM 全体を信頼ドメインとして分離

📊 主要機能 2: L4LBConfig CRD

Cloud Logging を Kubernetes ネイティブなリソース定義で宣言的に管理

→宣言的設定: networking.gke.io/v1 API グループの L4LBConfig で設定
→サンプルレート制御: 0 - 1,000,000 (1,000,000 = 100%) でログ収集量を制御
→出力フィールド制御: optionalMode で EXCLUDE_ALL_OPTIONAL / INCLUDE_ALL_OPTIONAL / CUSTOM を選択
→Service アノテーション: networking.gke.io/l4lb-config で CRD リソースを参照
→ステータス監視: LoggingConfigManaged 条件タイプで設定の同期状態を確認可能

L4LBConfig CRD 仕様

項目 詳細
API バージョン networking.gke.io/v1
リソース種別 L4LBConfig
必要 GKE バージョン 1.36.0-gke.2459000 以降
対応 LB (内部) 内部パススルーネットワーク LB (サブセッティング有効)
対応 LB (外部) 外部パススルーネットワーク LB (RBS 有効)
サンプルレート範囲 0 - 1,000,000 (1,000,000 = 100%)
💡 コースト動作: アノテーション削除時は「コースト状態」に移行し、最後の正常な設定が維持されます。CRD を参照しない場合、コントローラーがロギングを無効化し手動設定を上書きします。

⚙️ 設定方法

Confidential GKE Nodes (AMD SEV-SNP)

Bash 
gcloud container clusters create-auto my-confidential-cluster \
    --location=us-central1 \
    --confidential-node-type=sev_snp

Confidential GKE Nodes (Intel TDX)

Bash 
gcloud container clusters create-auto my-tdx-cluster \
    --location=us-central1 \
    --confidential-node-type=tdx

L4LBConfig CRD の作成

YAML 
apiVersion: networking.gke.io/v1
kind: L4LBConfig
metadata:
  name: svc-l4lb-config
  namespace: default
spec:
  logging:
    enabled: true
    sampleRate: 500000
    optionalMode: "INCLUDE_ALL_OPTIONAL"

Service に L4LBConfig を関連付け (内部 LB)

YAML 
apiVersion: v1
kind: Service
metadata:
  name: ilb-svc
  annotations:
    networking.gke.io/load-balancer-type: "Internal"
    networking.gke.io/l4lb-config: "svc-l4lb-config"
spec:
  type: LoadBalancer
  selector:
    app: store
  ports:
    - name: tcp-port
      protocol: TCP
      port: 8080
      targetPort: 8080

ステータス確認

Bash 
kubectl get svc ilb-svc -o yaml
# status.conditions の LoggingConfigManaged タイプが True / Reconciled であることを確認

⚠️ デメリット・制約事項

⚠️ 制限事項:
  • Confidential GKE Nodes のクラスターレベル設定は不可逆 (一度設定すると無効化・技術変更不可)
  • AMD SEV-SNP / Intel TDX は対応マシンタイプとゾーンが限定的
  • L4LBConfig CRD は GKE 1.36.0-gke.2459000 以降のみ
  • 内部 L4 LB のロギングにはサブセッティングの有効化が前提
  • 外部 L4 LB のロギングには RBS の有効化が前提
🚨 考慮すべき点:
  • Confidential Computing の選択は永続的 - ワークロード要件とゾーン可用性を事前に検討すること
  • CRD を参照しない Service にはコントローラーがロギングを無効化 - 既存の手動設定が上書きされる可能性
  • ログサンプルレートを高く設定すると Cloud Logging コストが増加
  • Confidential Computing 有効化でマシンタイプが制限され、一部ワークロードに性能影響の可能性

💡 ユースケース

🏦 ユースケース 1: 金融機関における機密データ処理

シナリオ: PCI DSS やデータ保護規制に準拠が必要な金融機関が、顧客の取引データを GKE 上で処理。

実装: --confidential-node-type=sev_snp で Autopilot クラスターを作成

効果: Autopilot の運用負荷軽減 + AMD SEV-SNP によるハイパーバイザーレベル攻撃からのメモリ保護を両立

📡 ユースケース 2: マイクロサービスのネットワークトラフィック分析

シナリオ: 内部 LB 経由の通信をパフォーマンス問題検知のためにロギングし、GitOps で管理したい。

実装: L4LBConfig CRD で sampleRate: 100000 (10%) + optionalMode: "CUSTOM"

効果: コスト効率良くトラフィック可視化。設定は Git リポジトリで変更履歴追跡可能。

☁️ ユースケース 3: マルチテナント環境での機密ワークロード分離

シナリオ: SaaS プロバイダーが複数テナントのデータをハードウェアレベルで分離したい。

実装: --confidential-node-type=tdx で Intel TDX を有効化

効果: Intel TDX により各 VM が独立した信頼ドメインとして動作し、テナント間データ漏洩リスクをハードウェアレベルで排除。
