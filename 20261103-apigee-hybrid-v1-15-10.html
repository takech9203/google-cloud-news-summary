🔧 Apigee hybrid v1.15.10 パッチリリース

apigee-connect-agent のフォワードプロキシ対応修正 + 侵害ルート証明書の削除 + 広範な CVE 修正
📅 リリース日: 2026-11-03

📌 概要

Google は Apigee hybrid ソフトウェアの更新版 v1.15.10 をリリースしました。 コンテナイメージは Helm チャートに統合されているため、Helm アップグレードのみでイメージも自動更新されます (手動のイメージ変更は通常不要)。

最重要ポイントは、apigee-connect-agent が環境変数 HTTPS_PROXY を無視し、 HTTP フォワードプロキシ必須のクラスタでコントロールプレーンとのテザーを確立できなくなる問題 (Bug ID: 578314600) の修正です。 プロキシ経由でしか外部に出られない閉域ネットワーク環境では必須のアップデートです。

さらに、侵害された emSign ルート証明書とクロス署名用 Comodo AAA Services ルート証明書を 全コンテナのトラストストアから削除する修正 (Bug ID: 576707253) と、多数のコンポーネントにわたる CVE 対応が含まれます。

❌ アップデート前の課題 (v1.15.8 / v1.15.9)

  • overrides.yaml に httpProxy を設定しても、カスタム TCP キープアライブダイヤラーが gRPC 組み込みの HTTP CONNECT プロキシ処理をバイパスし、apigeeconnect.googleapis.com:443 へ直接接続を試行
  • Egress がプロキシに制限されたクラスタでは接続がタイムアウトし、「no connections available from the Apigee connect agent(s)」エラーでデプロイ等が失敗
  • 侵害された emSign / Comodo AAA Services ルート証明書がトラストストアに残存し、不正証明書を信頼するリスク
  • 各コンポーネントのイメージに複数の既知 CVE が未修正

✅ アップデート後の改善 (v1.15.10)

  • apigee-connect-agent が HTTPS_PROXY (プロキシ認証情報を含む) を尊重し、フォワードプロキシ必須のクラスタでもテザーを確立可能に
  • HTTP/2 キープアライブ ping により、サイレント切断の検知が約 2 時間 → 約 80 秒に短縮
  • 侵害された emSign ルートと Comodo AAA Services ルートを全コンテナのシステム / Java トラストストアから削除
  • asm-ingress / istiod / envoy / fluent-bit / cassandra など多数の CVE を修正

⚡ 主要な修正内容

🔌 1. apigee-connect-agent のフォワードプロキシ対応修正 Bug ID: 578314600

→overrides.yaml の httpProxy 設定により pod に設定される HTTPS_PROXY 環境変数を正しく尊重 (プロキシ認証情報も対応)
→根本原因: Bug 513032450 で導入されたカスタム TCP キープアライブダイヤラーが gRPC 組み込みの HTTP CONNECT プロキシ処理をバイパス
→修正後は HTTP/2 キープアライブ ping を使用し、サイレントドロップされた接続を約 80 秒 (従来は約 2 時間) で検知・再確立
→影響バージョン: 1.14.9 / 1.15.8 / 1.15.9 / 1.16.11 / 1.16.12 / 1.17.1 / 1.17.2 ・ 修正版: 1.15.10 / 1.16.13 / 1.17.3 (1.16.12 と 1.17.2 は使用しないこと)

🔐 2. 侵害されたルート証明書のトラストストアからの削除 Bug ID: 576707253

→侵害された emSign ルート証明書群を、全コンテナのシステムトラストストアおよび Java (cacerts) トラストストアから削除
→emSign ルートへのクロス署名に使われる Comodo AAA Services ルート証明書も併せて削除
→API プロキシのターゲット接続等で、これらのルートに連鎖する証明書が信頼されなくなる

🛡️ 3. コンポーネント横断のセキュリティ (CVE) 修正

→サービスメッシュ、ログ収集、データストアなど広範なコンテナイメージの脆弱性を修正 (下の技術仕様の表を参照)

⚙️ フォワードプロキシ設定 (参考)

Apigee hybrid でフォワードプロキシを使用する場合は、overrides.yaml に以下のように設定します。

YAML overrides.yaml 
envs:
  - name: test
    httpProxy:
      scheme: HTTP   # 大文字の HTTP が必須
      host: 10.12.0.47
      port: 3128

🛠️ 設定方法 (アップグレード手順)

✅ 前提条件

✓Apigee hybrid v1.15 系を運用中であること (v1.15 より古い場合は先に v1.15 へのアップグレードが必要)
✓Helm v3.14.2 以降、対応バージョンの kubectl / cert-manager
✓アップグレード前に Helm チャートディレクトリと Cassandra データベースのバックアップを取得
📥 ① Helm チャート取得
→
📜 ② CRD 更新
→
🚀 ③ 各チャートを順にアップグレード

📥 ステップ 1: v1.15.10 の Helm チャートを取得

Bash Google Artifact Registry から v1.15.10 チャート一式を取得 
export CHART_REPO=oci://us-docker.pkg.dev/apigee-release/apigee-hybrid-helm-charts
export CHART_VERSION=1.15.10

helm pull $CHART_REPO/apigee-operator --version $CHART_VERSION --untar
helm pull $CHART_REPO/apigee-datastore --version $CHART_VERSION --untar
helm pull $CHART_REPO/apigee-env --version $CHART_VERSION --untar
helm pull $CHART_REPO/apigee-ingress-manager --version $CHART_VERSION --untar
helm pull $CHART_REPO/apigee-org --version $CHART_VERSION --untar
helm pull $CHART_REPO/apigee-redis --version $CHART_VERSION --untar
helm pull $CHART_REPO/apigee-telemetry --version $CHART_VERSION --untar
helm pull $CHART_REPO/apigee-virtualhost --version $CHART_VERSION --untar

📜 ステップ 2: CRD を更新

Bash dry-run で検証してから適用 
# dry-run で検証
kubectl apply -k apigee-operator/etc/crds/default/ \
  --server-side --force-conflicts --validate=false --dry-run=server

# 問題がなければ適用
kubectl apply -k apigee-operator/etc/crds/default/ \
  --server-side --force-conflicts --validate=false
💡 ヒント: CRD のインストールは kubectl apply -k + --server-side が唯一サポートされる方法です。 namespace が apigee 以外の場合は、事前に apigee-operator/etc/crds/default/kustomization.yaml の namespace を変更します。

🚀 ステップ 3: 各チャートを順番にアップグレード

Bash operator から順にアップグレード 
helm upgrade operator apigee-operator/ \
  --install --namespace apigee --atomic -f overrides.yaml
# 以降、datastore → telemetry → redis → ingress-manager → org → env → virtualhost の順に実行

パッチリリースのため、Helm アップグレードによりコンテナイメージが自動的に v1.15.10 のものへ更新されます。詳細な手順とロールバック方法は公式のアップグレードガイドを参照してください。

💡 メリット

💼 ビジネス面

✓閉域環境での運用安定性: フォワードプロキシ必須のエンタープライズ / 規制業種のネットワーク環境で、管理プレーン操作 (プロキシのデプロイ、構成変更) が失敗するリスクを解消
✓セキュリティコンプライアンス: 侵害されたルート証明書の排除と広範な CVE 修正により、脆弱性監査・コンプライアンス要件への対応が容易に

⚙️ 技術面

✓障害検知の高速化: HTTP/2 キープアライブ ping により、サイレント切断の検知が約 2 時間 → 約 80 秒に短縮され、自動再接続までの時間が大幅に改善
✓運用負荷の軽減: コンテナイメージが Helm チャートに統合されているため、Helm アップグレードのみで完結し、手動のイメージ差し替えが不要
✓プロキシ認証対応: HTTPS_PROXY の認証情報 (ユーザー名 / パスワード) を含めて正しく処理

⚠️ デメリット・制約事項

🚧 制限事項

✗v1.15 系のパッチであり、v1.15 より古いバージョンからはまず v1.15 へのメジャーアップグレードが必要
✗Bug 578314600 の修正を得るには、1.16 系では 1.16.13、1.17 系では 1.17.3 が必要 (1.16.12 と 1.17.2 は使用しないよう公式に案内)

🤔 考慮すべき点

⚠️ 注意: emSign / Comodo AAA Services ルートの削除により、これらのルートに連鎖する証明書を使うターゲットバックエンドとの TLS 接続は失敗するようになります。該当するバックエンドがないか事前に確認してください。
!アップグレード前に Helm チャートディレクトリと Cassandra のバックアップ取得が推奨される
!アップグレード処理中は新しい環境 (environment) を作成しないこと

🎯 ユースケース

🏦 ユースケース 1: フォワードプロキシ必須の閉域クラスタでの管理プレーン接続復旧

シナリオ: 金融機関のオンプレミス Kubernetes クラスタで Apigee hybrid v1.15.9 を運用しており、Egress はすべて社内 HTTP フォワードプロキシ経由に制限されている。 API プロキシのデプロイが「no connections available from the Apigee connect agent(s)」エラーで失敗する。

Bash アップグレード後の connect agent 状態確認 
# v1.15.10 へ Helm アップグレード後、connect agent の状態を確認
kubectl get pods -n apigee | grep apigee-connect-agent
kubectl logs -n apigee -l app=apigee-connect-agent --tail=50

効果: apigee-connect-agent が HTTPS_PROXY 経由でコントロールプレーンへのテザーを確立し、デプロイ等の管理プレーン操作が正常に動作する。

🔍 ユースケース 2: 脆弱性スキャン指摘への一括対応

シナリオ: コンテナ脆弱性スキャナーが Apigee hybrid の Cassandra、Envoy、fluent-bit などのイメージに多数の CVE を検出し、セキュリティチームから対応期限が設定されている。

効果: v1.15.10 への Helm アップグレードのみで、10 コンポーネント以上にわたる CVE 修正と侵害ルート証明書の削除が一括適用され、個別イメージの差し替え作業なしに指摘を解消できる。

💰 料金・利用可能リージョン

💵 料金

Apigee hybrid のソフトウェアアップデート自体に追加料金は発生しません。 Apigee の料金はサブスクリプション (Standard / Enterprise / Enterprise Plus) または従量課金 (Pay-as-you-go) に基づきます。 詳細は Apigee 料金ページ を参照してください。

Apigee hybrid のランタイムはユーザー管理の Kubernetes クラスタ (GKE、他クラウド、オンプレミス) 上で動作するため、ランタイムのリージョン制約はクラスタの配置に依存します。 対応プラットフォームは Supported platforms を参照してください。

📝 まとめ

✅ 要点: Apigee hybrid v1.15.10 は、フォワードプロキシ必須環境での管理プレーン接続断という重大な既知の問題 (578314600) の修正と、 侵害ルート証明書の削除を含む広範なセキュリティ修正をまとめたパッチリリースです。 特に v1.15.8 / v1.15.9 をプロキシ経由の閉域クラスタで運用している場合は接続障害の影響を直接受けるため、速やかな適用を強く推奨します。 それ以外の環境でも CVE 修正の観点から、計画的な Helm アップグレードを検討してください。
