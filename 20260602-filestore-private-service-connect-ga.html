📋 概要

Google Cloud Filestore インスタンスにおける Private Service Connect (PSC) のサポートが一般提供 (GA) になりました。VPC ネットワーク内の単一の内部 IP アドレスをプロビジョニングするだけで、マネージド NFS ストレージにプライベートにアクセスできます。

Before / After 比較

❌ Before (従来の課題)

  • VPC ピアリングやプライベートサービスアクセスで IP 範囲全体を予約する必要
  • マルチテナント環境でのプロジェクト間アクセス構成が煩雑
  • IPv6 のネイティブサポートがなく、モダンネットワーク対応が制限

✅ After (今回の改善)

  • 単一の内部 IP アドレスのプロビジョニングのみでプライベート接続が可能
  • Service Connection Policy で自動エンドポイント作成、大規模管理が効率化
  • IPv4/IPv6 デュアルスタック対応でモダン環境に完全対応

⚡ 主要機能

🔗 Private Service Connect エンドポイント

→VPC 内に単一の内部 IP アドレスとして作成される接続ポイント
→Service Connection Policy による自動プロビジョニング
→Shared VPC 構成ではホストプロジェクトにプロビジョニング可能

📡 デュアルプロトコル (NFSv3 / NFSv4.1)

→NFSv3: 全ティアで利用可能、双方向通信、ステートレス復旧
→NFSv4.1: Kerberos 認証対応、リースベースのロック制御
→PSC 経由でも両プロトコルの機能をフル活用可能

🌐 IPv4 / IPv6 デュアルスタック対応

→サービスアタッチメントごとに IPv4 / IPv6 を選択可能
→IPv6 選択時はアクセス制御を IPv6 CIDR 表記で検証
→モダンなネットワーク環境への完全対応

⚙️ Service Connection Policy

→VPC ネットワークごとに接続ポリシーを定義
→サブネット指定で IP アドレスの自動割り当て
→接続数の制限設定による管理の一元化

🛠️ 設定方法

💡 前提条件: Filestore クォータの確認、Compute Engine API / Network Connectivity API / Service Consumer Management API の有効化、VPC ネットワークとサブネットの準備が必要です。

ステップ 1: Service Connection Policy の作成

Bash 
gcloud network-connectivity service-connection-policies create filestore-psc-policy \
  --network=my-vpc-network \
  --project=my-project \
  --region=us-central1 \
  --service-class=gcp-filestore \
  --subnets=https://www.googleapis.com/compute/v1/projects/my-project/regions/us-central1/subnetworks/psc-subnet \
  --psc-connection-limit=10

ステップ 2: Filestore インスタンスの作成 (PSC 接続モード)

Bash 
gcloud filestore instances create my-filestore-instance \
  --project="my-project" \
  --region=us-central1 \
  --tier=REGIONAL \
  --protocol=NFS_v4_1 \
  --file-share=name="my_share",capacity=1024 \
  --network=name="my-vpc-network",connect-mode=PRIVATE_SERVICE_CONNECT,address-mode=MODE_IPV4

ステップ 3: IPv6 エンドポイントでの作成 (オプション)

Bash 
gcloud filestore instances create my-filestore-ipv6 \
  --project="my-project" \
  --region=us-central1 \
  --tier=REGIONAL \
  --protocol=NFS_v3 \
  --file-share=name="my_share_v6",capacity=2048 \
  --network=name="my-vpc-network",connect-mode=PRIVATE_SERVICE_CONNECT,address-mode=MODE_IPV6

ステップ 4: Shared VPC 環境での作成 (オプション)

Bash 
gcloud filestore instances create my-shared-vpc-instance \
  --project="service-project" \
  --region=us-central1 \
  --tier=REGIONAL \
  --protocol=NFS_v4_1 \
  --file-share=name="shared_vol",capacity=1024 \
  --network=name=projects/host-project/global/networks/shared-vpc,connect-mode=PRIVATE_SERVICE_CONNECT,address-mode=MODE_IPV4,psc-endpoint-project=host-project

✅ メリット

ビジネス面

✓IP アドレス管理の効率化: 単一 IP のプロビジョニングで接続が完了し、IP 計画の複雑さが大幅削減
✓マルチテナント対応の強化: 異なるプロジェクト・組織からのプライベートアクセスが容易に
✓コンプライアンス対応: データがパブリックインターネットを経由しないため、規制要件への適合が容易

技術面

✓セキュリティの強化: VPC 内プライベート IP 経由アクセスで攻撃面を最小化
✓ネットワーク構成の簡素化: VPC ピアリングの制約 (推移的ルーティング不可など) を回避
✓IPv6 対応: デュアルスタック環境でモダンなネットワーク構成をサポート
✓自動化対応: Service Connection Policy で Infrastructure as Code との親和性が高い

⚠️ 制約事項・注意点

制限事項
✗Legacy ティア (Basic HDD / Basic SSD) では PSC 接続は利用不可
✗Service Connection Policy は VPC ネットワーク、リージョン、サービスクラスの組み合わせごとに 1 つのみ
✗Shared VPC 構成では、Service Connection Policy のスコープがホストプロジェクトを許可する必要あり
✗VPC ネットワーク数の上限は 49 (Filestore 全体の制限)
💡 考慮すべき点
→プライベートサービスアクセスから PSC への移行にはインスタンスの再作成が必要な可能性
→Service Connection Policy の更新はサブネットと接続数制限のみ。その他の変更は再作成が必要
→NFSv4.1 + Kerberos 認証には Managed AD の追加構成が必要
→IPv6 エンドポイント使用時は既存ファイアウォールルールの見直しが必要

🎯 ユースケース

🏢 ユースケース 1: マルチプロジェクト環境でのファイル共有

シナリオ: 複数の開発チームが異なる Google Cloud プロジェクトで作業し、共通の Filestore インスタンスにプライベートにアクセスする必要がある。

効果: VPC ピアリングなしで同一の Filestore インスタンスにプライベートアクセスでき、IP アドレス管理の複雑さも削減。

🔐 ユースケース 2: セキュリティ要件が厳しい GKE ワークロード

シナリオ: 金融系ワークロードを GKE 上で実行し、NFS ストレージへのアクセスにデータ暗号化とクライアント認証が必須。

効果: PSC + NFSv4.1 Kerberos (krb5p) でネットワークレベルとプロトコルレベルの両方でセキュリティを確保。

🌐 ユースケース 3: IPv6 対応のモダンインフラストラクチャ

シナリオ: 組織全体で IPv6 への移行を進めており、ファイルストレージサービスも IPv6 ネイティブで接続したい。

効果: IPv6 エンドポイントで IPv4 アドレス枯渇を気にせずスケーラブルな接続を構築。デュアルスタックでの段階的移行もサポート。
