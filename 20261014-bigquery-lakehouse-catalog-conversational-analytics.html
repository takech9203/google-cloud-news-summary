📊 BigQuery GA (一般提供)

🏞️ Lakehouse ランタイムカタログの Hive エンドポイント GA
& Conversational Analytics の機能拡張

リリース日: 2026-10-14

📝 概要

2026 年 10 月 14 日、BigQuery に関する 5 件の機能が GA になりました。 「Lakehouse ランタイムカタログ」「Conversational Analytics」「AI 関数」の 3 領域にわたるアップデートです。

5 件
GA になった機能
3 領域
Lakehouse / Conversational Analytics / AI 関数
3 エンジン
Spark / Hive / BigQuery でメタデータ共有
→Lakehouse ランタイムカタログ: Apache Hive カタログエンドポイントが GA になり、サーバーレスで一元化されたメタデータレイヤーとして利用可能に。Dataproc Metastore からのメタデータ移行 (バックフィル / ドライラン) も GA。
→Conversational Analytics: マルチプロジェクト / データセット単位の会話作成と、エージェントの Gemini Enterprise への公開が GA。
→AI.AGG 関数: output_schema 引数がサポートされ、構造化 (STRUCT) 出力を直接取得可能に。

❌ Before (アップデート前の課題)

  • セルフホスト Hive Metastore や Dataproc Metastore を自前運用する必要があり、メタストア管理の運用負荷が発生
  • Dataproc Metastore から Lakehouse への公式な GA 移行手段がなく、モダナイゼーションの移行パスが限定的
  • Conversational Analytics の会話は限定的なスコープのみで、複数プロジェクト横断の質問が困難
  • データエージェントを Gemini Enterprise で利用する公式な公開手段が GA ではなかった
  • AI.AGG の出力は STRING 値のみで、構造化出力には後処理が必要

✅ After (アップデート後の改善)

  • Hive カタログエンドポイントにより、サーバーレスのフルマネージドメタストアで Spark / Hive / BigQuery 間のデータ共有と統合クエリが可能に
  • ワンタイムバックフィル移行とドライランがコンソール / gcloud CLI / REST API から GA 機能として実行可能に
  • 複数プロジェクトの全データソースやデータセット単位での会話作成が GA になり、横断的なデータ探索が容易に
  • エージェントを Gemini Enterprise に公開でき、ビジネスユーザーが使い慣れた UI からデータに質問可能に
  • AI.AGG の output_schema で STRUCT 形式の構造化出力を直接取得可能に

Dataproc Metastore のメタデータを Lakehouse ランタイムカタログへ移行し、Hive カタログエンドポイントを介して Spark / Hive / BigQuery がメタデータを共有。実データは Cloud Storage に保存されるデータフロー。

⭐ 主要機能

1️⃣ Apache Hive カタログエンドポイント GA

✓サーバーレスの統合メタストアとして機能し、セルフホスト Hive Metastore の管理が不要に
✓Apache Spark の ExternalCatalog 互換に最適化。Spark は標準の IMetastoreClient インターフェース経由で接続 (HMS インターフェースのサブセットをサポート)
✓Hive SerDes / Spark データソースの標準的な Hive / Spark テーブルを管理 (Iceberg テーブルは Iceberg REST カタログエンドポイントを使用)
✓Parquet / ORC / Avro / Delta Lake などのストレージ形式と、Cloud Storage 上のデータに対する CMEK をサポート
✓Managed Service for Apache Spark のランタイムイメージには必要なクライアントライブラリが事前構成済み

2️⃣ Dataproc Metastore から Lakehouse へのメタデータ移行 GA

✓Iceberg REST カタログまたは Hive カタログエンドポイントへの一度限りのバックフィル移行を実行可能
✓実際に書き込まずに移行を検証するドライランモードをサポート
✓コンソール、gcloud CLI (gcloud beta metastore services migrations start)、REST API (startMigration) から実行可能
✓重複エントリのスキップ / 上書きを選択できる競合ポリシー付き
✓移行完了後、summary.json と full_report.json の詳細レポートが Cloud Storage に出力

3️⃣ Conversational Analytics: マルチプロジェクト / データセット会話 GA

✓複数プロジェクト内のすべてのデータソースを対象にした会話を作成可能。BigQuery の Agents ページでプロジェクトを複数選択して横断質問
✓テーブル、ビュー、データセット、プロジェクト、グラフをナレッジソースとして直接会話を開始可能

4️⃣ エージェントの Gemini Enterprise 公開 GA

✓BigQuery で作成したデータエージェントを Gemini Enterprise に公開し、ビジネスユーザーが自然言語でデータをクエリ・分析可能に
✓推奨公開方法は Agent Registry 経由。代替として A2A カード JSON による公開も可能
✓Agent Gateway の構成が必要。データエージェントのストレージリージョン (US / EU / Global) と Agent Registry バインディングのリージョンの一致が必要

5️⃣ AI.AGG 関数の output_schema 引数 GA

✓出力スキーマをカンマ区切りのフィールドリスト (名前、データ型、オプションの説明) で指定可能
✓output_schema 未指定時は STRING 値、指定時はスキーマに準拠した STRUCT 値を返す
✓サポートするデータ型は STRING / INT64 / FLOAT64 / BOOL / ARRAY / STRUCT。フィールドに NOT NULL も指定可能

🤖 AI.AGG の output_schema 指定例

SQL output_schema による構造化出力 
SELECT
  t.by,
  AI.AGG(
    t.text,
    'These are the blog posts of a single user. Tell me what topics the user talks about the most. Keep it concise.',
    output_schema => 'topics ARRAY<STRUCT<name STRING NOT NULL, explanation STRING NOT NULL>>'
  ) AS common_topic
FROM sample_data AS t
GROUP BY t.by;

⚙️ 設定方法

📋 前提条件

✓(メタデータ移行) 移行元となるアクティブな Dataproc Metastore サービスが存在すること
✓(メタデータ移行) 移行先の Hive / Iceberg カタログが存在し、移行元テーブルのデータ / メタデータが置かれている Cloud Storage バケットまたはパスを含むこと
✓(メタデータ移行) 移行開始ユーザーに roles/metastore.editor、カタログ作成に roles/biglake.admin などの IAM ロールが付与されていること
✓(Conversational Analytics) BigQuery、Gemini Data Analytics、Gemini for Google Cloud の各 API が有効で、roles/geminidataanalytics.dataAgentUser などの必要なロールが付与されていること

🚀 ステップ 1: Dataproc Metastore から Lakehouse への移行を開始

Bash gcloud CLI でバックフィル移行を開始 
gcloud beta metastore services migrations start SERVICE_ID \
  --location=REGION \
  --hive-catalog="projects/PROJECT_ID/catalogs/HIVE_CATALOG_ID" \
  --hive-databases="HIVE_DB_1,HIVE_DB_2" \
  --async
💡 ヒント: Hive カタログと Iceberg カタログの両方へ同時に移行することも可能です。--hive-databases に * を指定すると全データベースを移行します。

🔍 ステップ 2: 移行の進行状況を確認

Bash 移行の実行状況を確認 
gcloud beta metastore services migrations describe MIGRATION_EXECUTION_ID \
  --service=SERVICE_ID \
  --location=REGION

移行完了後、指定した Cloud Storage パス (未指定の場合はサービスのアーティファクトバケット) に出力される summary.json / full_report.json で結果を検証します。

💡 メリット

💼 ビジネス面

✓運用コストの削減: セルフホスト Hive Metastore や Dataproc Metastore の運用から解放され、サーバーレスでスケーリングするフルマネージドカタログに移行できる
✓データ活用の民主化: エージェントを Gemini Enterprise に公開することで、SQL を書けないビジネスユーザーも自然言語でデータ分析が可能に
✓ガバナンスの統一: メタデータを単一の信頼できる情報源に集約し、データ検出とポリシー適用を簡素化できる

🛠️ 技術面

✓マルチエンジン相互運用: Spark、Hive、BigQuery がファイルを複製することなく同一テーブルのメタデータを共有できる
✓安全な移行パス: ドライランと詳細レポートにより、本番移行前に移行の妥当性を検証できる
✓構造化 AI 出力: AI.AGG の output_schema により LLM の出力を型付きの STRUCT として直接取得でき、後続処理での文字列パースが不要に

⚠️ デメリット・制約事項

🚫 制限事項

✗Hive カタログエンドポイント経由のテーブルは BigQuery からは読み取り専用 (書き込みは Spark / Hive などの OSS エンジンから)
✗Hive カタログエンドポイントは HMS インターフェースのサブセットをサポート。トランザクション、コンパクション、Kerberos などに依存するワークロードは事前の機能比較確認が必要
✗メタデータ移行は一度限りのバックフィルのみ。移行後に移行元へ加えられた変更は自動伝播せず、同期には移行の再実行が必要
✗Dataproc Metastore のテーブル / データベースに対する権限は移行されない
✗移行先カタログに移行元データの Cloud Storage バケット / パスが含まれていない場合、テーブル移行は失敗する
✗AI.AGG の関数出力はグループあたり 10,000 トークンが上限

🤔 考慮すべき点

→Lakehouse ランタイムカタログのテーブルに対する BigQuery からのクエリ性能は、標準 BigQuery テーブルと比べて低下する可能性がある (概ね Cloud Storage からの読み取りと同等)
→Gemini Enterprise への公開では、データエージェントのストレージリージョンと Agent Gateway の Agent Registry バインディングのリージョンを一致させる必要があり、エージェント保存後はリージョンを変更できない
→Conversational Analytics は自動でクエリを実行するため、大きなテーブル、JOIN、AI 関数の頻繁な呼び出しはクエリコストを増加させる可能性がある
→AI.AGG の output_schema では、LLM が NULL を返すのを避けるため、ほとんどのフィールドに NOT NULL を指定することが推奨される

🎯 ユースケース

🏭 ユースケース 1: オンプレミス Hive ワークロードのサーバーレスモダナイゼーション

シナリオ: Dataproc Metastore を使って Spark / Hive の ETL パイプラインを運用しているデータエンジニアリングチームが、メタストアの運用負荷を削減しつつ BigQuery からの直接分析を実現したい。

Bash 全データベースのバックフィル移行 
# 1. ドライランで移行を検証 (コンソールの「Migrate to Lakehouse」でも可)
# 2. バックフィル移行を実行
gcloud beta metastore services migrations start my-metastore \
  --location=us-central1 \
  --hive-catalog="projects/my-project/catalogs/my-hive-catalog" \
  --hive-databases="*" \
  --async
# 3. 移行レポート (summary.json / full_report.json) を確認

💪 効果: メタストアのインフラ管理が不要になり、Spark で作成したテーブルを BigQuery から直接クエリできる統合レイクハウスが実現する。

💼 ユースケース 2: ビジネスユーザー向けセルフサービス分析

シナリオ: データアナリストが BigQuery で Conversational Analytics エージェント (検証済みクエリ、用語集、エージェント指示を設定済み) を構築し、営業部門のユーザーに Gemini Enterprise 経由で提供する。

📊 ユースケース 3: AI.AGG による構造化サマリーの生成

シナリオ: 大量のユーザーレビューをユーザーごとに集約し、主要トピックとその説明を型付きの構造化データとして BI ダッシュボードに取り込みたい。

SQL レビューの構造化トピックサマリー 
SELECT
  user_id,
  AI.AGG(
    review_text,
    'Summarize the main topics this user writes about.',
    output_schema => 'topics ARRAY<STRUCT<name STRING NOT NULL, explanation STRING NOT NULL>>'
  ) AS topic_summary
FROM reviews
GROUP BY user_id;

💪 効果: LLM の出力を STRUCT として直接取得できるため、文字列パースなどの後処理なしで下流の分析やダッシュボードに利用できる。

→⚡ Managed Service for Apache Spark: ランタイムイメージに Hive カタログエンドポイント用のクライアントライブラリが事前構成されており、Spark ジョブからシームレスに接続できる
→🗄️ Dataproc Metastore: 今回 GA になった移行機能の移行元。既存の HMS ワークロードを Lakehouse へモダナイズする起点となる

✅ まとめ

今回の GA 群は、Lakehouse ランタイムカタログを中核としたオープンレイクハウス戦略 (Hive エンドポイント GA と Dataproc Metastore からの移行パス確立) と、 Conversational Analytics によるデータ活用の民主化 (マルチプロジェクト会話と Gemini Enterprise 公開) の両輪を本番利用可能にする重要なアップデートです。 セルフホストメタストアや Dataproc Metastore を運用中のチームは、ドライラン機能で移行の実現可能性を検証し、 Hive エンドポイントの機能比較と制限事項 (BigQuery からは読み取り専用など) を確認したうえで移行計画を立てることを推奨します。
