Google Distributed Cloud Fixed 脆弱性修正 パッチリリース

🏢 GDC (software only) 1.35.600-gke.140 リリース

VMware 版 / ベアメタル版 — 脆弱性修正 + 複数のバグ修正
📅 リリース日: 2026-10-12

📋 概要

Google Distributed Cloud (software only) の VMware 版およびベアメタル版の両プラットフォームで、パッチリリース 1.35.600-gke.140 がダウンロード可能になりました。両バージョンとも Kubernetes v1.35.8-gke.100 上で動作します。GKE On-Prem API クライアント (コンソール / gcloud CLI / Terraform) での利用はリリース後約 7〜14 日で可能になります。

新機能の追加ではなく、セキュリティ脆弱性の修正とクラスタ運用の安定性に関わるバグ修正が中心のリリースです。audit-proxy の無限リトライ、プリフライトヘルスチェックの名前空間スコープ (アップグレード失敗の原因)、ユーザークラスタのステータスフラッピングなど両プラットフォーム共通の修正に加え、ベアメタル版では containerd の耐性向上、CA ローテーション失敗の修正、BGP フェイルオーバー高速化などの独自修正が含まれます。

❌ アップデート前の課題

  • audit-proxy が恒久的なエラーでも監査ログエクスポートを無限リトライし、過剰なトラフィックが発生 (共通)
  • プリフライトヘルスチェックが管理クラスタの全名前空間をスキャンし、無関係なクラスタの古い reconciling リソースでアップグレードが失敗 (共通)
  • Pod 密度設定が異なると、ユーザークラスタが reconciling / running を繰り返すステータスフラッピング (共通)
  • (ベアメタル) イメージ展開中のノード再起動で containerd の状態が破損する可能性
  • (ベアメタル) アップグレード / ロールバック中に構成ドリフトヘルスチェックが「version not supported」で失敗
  • (ベアメタル) セルフマネージドクラスタの CA ローテーションが最終フェーズで失敗し、クラスタが管理不能になることも
  • (ベアメタル) バンドル型 BGP LB で、コントロールプレーン更新時に最大 20 秒の API サーバー接続断

✅ アップデート後の改善

  • audit-proxy は恒久的なエラーでは無限リトライせず、過剰な監査ログトラフィックが解消
  • プリフライトヘルスチェックは対象クラスタの名前空間のみをスキャンし、無関係なクラスタ起因のアップグレード失敗がなくなる
  • Pod 密度設定が異なる構成でもユーザークラスタのステータスが安定
  • (ベアメタル) イメージ展開中のノード再起動に対する containerd の耐性が向上
  • (ベアメタル) ノードドレイン時に全ホストボリュームのアンマウントと CSI VolumeAttachment のデタッチ完了を検証し、孤立リソースや I/O エラーを防止
  • (ベアメタル) BGP LB 構成でのフェイルオーバーが約 4 秒で完了
💡 対象ユーザー: オンプレミス環境で GDC クラスタを運用している管理者。特に 1.35 系を利用中で、アップグレードやメンテナンスの安定性に課題を抱えていた組織にとって重要なリリースです。

⚙️ サービスアップデートの詳細 (主要機能)

1️⃣ 1.35.600-gke.140 のリリース (両プラットフォーム共通)

  • VMware 版・ベアメタル版ともに Kubernetes v1.35.8-gke.100 上で動作
  • 脆弱性修正一覧に記載されたセキュリティ脆弱性を修正
  • サードパーティストレージベンダー利用時は、認定済みストレージパートナー一覧で対応状況の確認が必要

2️⃣ 両プラットフォーム共通のバグ修正

  • audit-proxy の無限リトライ修正: 恒久的なエラー発生時に監査ログのエクスポートを無限にリトライし、過剰な監査ログトラフィックを生成していた問題を修正
  • プリフライトヘルスチェックのスコープ修正: 管理クラスタの全名前空間をスキャンしていたため、無関係なクラスタの古い reconciling リソースが原因でアップグレードが失敗する問題を修正
  • ユーザークラスタのステータスフラッピング修正: 管理クラスタとユーザークラスタの Pod 密度設定が異なる場合に、reconciling と running の状態を繰り返す問題を修正

3️⃣ ベアメタル版固有の修正

  • containerd の耐性向上: イメージ展開中にノードが再起動した場合の状態破損に対する耐性を改善
  • 構成ドリフトヘルスチェックの修正: アップグレード / ロールバック実行中に「version not supported」エラーで失敗する問題を修正
  • ノードドレインの検証強化: kubelet による全ホストボリュームのアンマウントと CSI VolumeAttachment のデタッチを検証してからドレインを完了
  • CA ローテーションの修正: セルフマネージドクラスタ (admin / hybrid / standalone) の CA ローテーションが最終フェーズで失敗する問題を修正。CA をローテーションする前に 1.35.600-gke.140 へのアップグレードが必須
  • BareMetalMachine ステータスの修正: メンテナンスモード遷移中にノードが早期に ready / available と報告される問題を修正
  • BGP ロードバランシングのフェイルオーバー高速化: コントロールプレーンノード再起動時の API サーバー接続断を最大約 20 秒から約 4 秒に短縮

🎯 ユースケース

📌 ユースケース 1: アップグレード失敗が頻発していたマルチクラスタ環境の安定化

シナリオ: 1 つの管理クラスタで複数のユーザークラスタを運用しており、一部のクラスタに古い reconciling リソースが残っていたため、別のクラスタのアップグレードがプリフライトチェックで失敗していた。

効果: プリフライトヘルスチェックが対象クラスタの名前空間のみをスキャンするようになり、他クラスタの状態に影響されずにアップグレードを完了できる。

📌 ユースケース 2: (ベアメタル) 証明書ライフサイクル管理の実施

シナリオ: セキュリティポリシーに基づき、admin / hybrid / standalone クラスタの CA を定期的にローテーションする必要があるが、ローテーション失敗によるクラスタ管理不能のリスクを懸念していた。

Bash アップグレード後に CA ローテーションを実行 
# 1. まず 1.35.600-gke.140 へアップグレード (必須)
./bmctl upgrade cluster -c CLUSTER_NAME --kubeconfig ADMIN_KUBECONFIG

# 2. その後 CA ローテーションを実行
./bmctl update credentials certificate-authorities rotate -c CLUSTER_NAME \
  --kubeconfig ADMIN_KUBECONFIG

効果: ローテーション最終フェーズでの失敗が修正されており、安全に CA ローテーションを完了できる。

📌 ユースケース 3: (ベアメタル) 高可用性要件のある BGP ロードバランシング環境

シナリオ: バンドル型 BGP ロードバランシングを使用する本番クラスタで、コントロールプレーンのアップグレードのたびに最大 20 秒の API サーバー接続断が発生し、CI/CD パイプラインや運用ツールがタイムアウトしていた。

効果: 正常なコントロールプレーンノードへのフェイルオーバーが約 4 秒で完了するようになり、計画メンテナンス中の接続断が大幅に短縮される。

GDC (software only) 1.35.600-gke.140 は、脆弱性修正に加え、アップグレードの信頼性・監査ログパイプライン・クラスタステータスの安定性に関わる重要なバグ修正を含むパッチリリースです。特にベアメタル版で CA ローテーションを予定している組織は、ローテーション実行前に本バージョンへのアップグレードが必須となるため、早期の適用計画を推奨します。1.35 系を運用中のクラスタは、メンテナンスウィンドウを確保して本パッチへのアップグレードを進めてください。
