📁 HNS バケットのフォルダ再帰削除
folders.deleteRecursive が利用可能に

リリース日: 2026-11-20

📝 概要

階層型名前空間 (Hierarchical Namespace、HNS) が有効な Cloud Storage バケットで、JSON API の新メソッド folders.deleteRecursive により、非空フォルダとその全コンテンツを単一の長時間実行オペレーション (LRO) で削除できるようになりました。

これまで JSON API の folders.delete は空フォルダしか削除できず、非空フォルダの削除にはオブジェクト・サブフォルダの個別削除をボトムアップで行うクライアント実装が必要でした。今回のアップデートで 1 回の API 呼び出しでフォルダツリー全体の削除を開始でき、進行状況は LRO として追跡できます。

HNS バケットを分析基盤 (Hadoop/Spark)、ML データセット管理、ファイルシステム的なデータ整理に利用するユーザーにとって、フォルダのライフサイクル管理が大幅に簡素化されます。

❌ Before (アップデート前の課題)

  • folders.delete は空のフォルダしか削除できなかった
  • 非空フォルダは配下オブジェクトを全削除し、サブフォルダを末端から順に削除する処理をクライアント側で実装する必要があった
  • 再帰削除はコンソールや gcloud CLI (gcloud storage rm --recursive) では可能だったが、JSON API には単一操作がなかった

✅ After (アップデート後の改善)

  • 単一の folders.deleteRecursive リクエストで、非空フォルダと配下の全オブジェクト・サブフォルダを削除
  • 削除処理は LRO として実行され、ステータスを追跡可能
  • フォルダに関連付けられたマネージドフォルダ (associated managed folders) も併せて削除

従来は非空フォルダの削除がエラーになり中身の個別削除が必要でしたが、新しい deleteRecursive メソッドでは 1 回の呼び出しで再帰削除が LRO として開始されます。

⚡ 主要機能

🗑️ 非空フォルダの再帰削除

HNS 有効バケット内の非空フォルダと、その配下のすべてのコンテンツ (オブジェクト、サブフォルダ) を 1 回のリクエストで削除。空フォルダのみ対象だった既存の folders.delete を補完する新メソッド。

⏳ 長時間実行オペレーション (LRO)

メソッドは LRO を返し、削除の完了やエラーを追跡可能。大規模なフォルダツリーの削除でもクライアントが同期的に待つ必要がない。

🔐 関連マネージドフォルダの削除

削除対象フォルダに関連付けられたマネージドフォルダも併せて削除。マネージドフォルダを明示的に削除する場合と同じルール・権限チェックが適用される。

🎯 メタ世代による条件付き削除

ifMetagenerationMatch / ifMetagenerationNotMatch クエリパラメータで、メタ世代 (metageneration) に基づく条件付き削除が可能。

ステップ 1: 非空フォルダの再帰削除リクエストを送信

公式ドキュメント (Delete a folder) に記載されている cURL の例:

Bash 非空フォルダの再帰削除 
curl -X DELETE -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://storage.googleapis.com/storage/v1/b/BUCKET_NAME/folders/FOLDER_NAME/deleteRecursive"
  • BUCKET_NAME: 削除対象フォルダを含むバケット名 (例: my-bucket)
  • FOLDER_NAME: URL エンコードされたフォルダ名 (例: my-folder/ → my-folder%2F)
💡 補足: API リファレンス (Folder: deleteRecursive) では HTTP リクエストは POST .../deleteRecursive と定義されています。

ステップ 2: 長時間実行オペレーションの完了を確認

メソッドは LRO を返すため、オペレーションのステータスと削除完了・エラーを確認します。LRO のステータス・エラーコードの詳細は公式のエラーハンドリングドキュメントを参照してください。

空のフォルダを削除する場合は、従来どおり folders.delete を使用します。

Bash 空フォルダの削除 (従来どおり) 
curl -X DELETE -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://storage.googleapis.com/storage/v1/b/BUCKET_NAME/folders/FOLDER_NAME"

💡 メリット

💼 ビジネス面

✓運用コストの削減: データセットやログの一括クリーンアップをクライアント側の複雑な削除ロジックなしで実現でき、運用スクリプトの開発・保守コストを削減
✓データライフサイクル管理の簡素化: プロジェクト単位・日付単位などフォルダで整理したデータの廃棄を単一操作で実行可能

⚙️ 技術面

✓API 呼び出しの大幅な削減: オブジェクト・サブフォルダごとの個別削除リクエストが不要になり、1 回のリクエストで削除を開始できる
✓非同期処理による信頼性向上: LRO として実行されるため、大規模フォルダツリーの削除でもクライアントのタイムアウトを気にせず進行状況を追跡できる
✓マネージドフォルダとの整合性: 関連マネージドフォルダとその IAM ポリシーも併せて削除され、孤立したアクセス制御設定が残らない

⚠️ デメリット・制約事項

🚧 制限事項

✗階層型名前空間 (HNS) が有効なバケットでのみ利用可能 (フラット名前空間バケットの擬似フォルダは対象外)
✗関連マネージドフォルダの削除には、マネージドフォルダを明示的に削除する場合と同じ権限 (storage.managedFolders.delete) が必要で、権限がない場合は削除リクエストが失敗する

🤔 考慮すべき点

⚠️フォルダとその配下のすべてのオブジェクトが削除される強力な操作のため、誤削除防止の観点から IAM 権限の付与範囲や ifMetagenerationMatch による条件付き削除の活用を検討すべき
⚠️削除リクエストが失敗した場合、関連マネージドフォルダ名がエラーメッセージや Cloud Audit Logs に返されるため、storage.folders.delete 権限を持つユーザーは storage.managedFolders.get/list 権限がなくても関連マネージドフォルダの存在を知り得る点に留意

🎯 ユースケース

📊 ユースケース 1: 分析ワークロードの中間データ一括削除

シナリオ: Hadoop/Spark ワークロードで HNS バケットをファイルシステムのように利用しており、ジョブ完了後に日付別フォルダ配下の中間データ (多数のオブジェクトとサブフォルダ) を廃棄したい。

Bash 実装例 
curl -X DELETE -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://storage.googleapis.com/storage/v1/b/analytics-bucket/folders/tmp%2F2026-11-20%2F/deleteRecursive"

効果: 従来必要だった「オブジェクトの全列挙 → 個別削除 → 末端から順にフォルダ削除」という処理が不要になり、単一の LRO で削除が完了する。

🏢 ユースケース 2: テナント/プロジェクト単位のデータ廃棄

シナリオ: マルチテナント構成でテナントごとにフォルダを割り当てており、契約終了時にテナントフォルダ全体 (関連マネージドフォルダの IAM ポリシー含む) を削除したい。

効果: フォルダ本体・配下オブジェクト・関連マネージドフォルダとその IAM ポリシーが併せて削除されるため、アクセス制御設定の残骸なくテナントデータを廃棄できる。

📌 まとめ

HNS バケットの JSON API に folders.deleteRecursive が追加され、非空フォルダとその全コンテンツを単一の長時間実行オペレーションで削除できるようになりました。

これまでクライアント側で実装していたボトムアップの削除ロジックが不要になるため、HNS バケットを API 経由で管理しているアプリケーションは削除処理の本メソッドへの置き換えを検討することを推奨します。

強力な削除操作であるため、storage.folders.delete 権限の付与範囲の見直しも併せて行ってください。
