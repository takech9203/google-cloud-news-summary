Knowledge Catalog (旧 Dataplex Universal Catalog) Preview
📅 リリース日: 2026-11-03

📌 概要

Knowledge Catalog のガバナンスワークフローがバッチメタデータ変更リクエストに対応 (Preview)。 エントリ (Entry) とエントリリンク (Entry link) に対する作成・更新・削除を最大 250 件まで 1 つの変更リクエストにまとめて提出し、 承認者のレビュー・承認を経てカタログへ一括反映できます。

🤖 エンリッチメントエージェントとの統合: エージェントが生成したメタデータ提案のうち、自動公開 (auto-publishing) ではなく人間のレビューが必要なものは、自動的にバッチ変更リクエストとして登録されます。 承認者は承認前に提案内容を編集 (キュレーション) できるため、AI 生成メタデータを検証・修正してから公開する 「human-in-the-loop」のガバナンスプロセスを構築できます。

❌ Before (アップデート前の課題)

  • 変更リクエストは単一リソース単位。多数のエントリ変更は個別提出が必要で、承認者も 1 件ずつレビュー・承認
  • エンリッチメントエージェントが大量生成するメタデータ提案を、承認フローで効率的にレビューする仕組みがない
  • 単一リソースのリクエストではエントリリンクの更新 (Update) が非サポート

✅ After (アップデート後の改善)

  • 最大 250 件の作成・更新・削除を 1 リクエストにまとめ、1 回の承認で一括適用
  • エージェントの実行結果が自動でバッチ変更リクエストとして登録され、承認者は承認前に提案を編集可能
  • バッチリクエストではエントリリンクの作成・更新・削除すべてをサポート
🎯 対象ユーザー: エントリグループへの直接の書き込み権限を持たないデータ利用者、AI によるメタデータ自動生成を統制の取れた形で導入したいデータスチュワード・プラットフォーム管理者

⚡ 主要機能

📦 1. 最大 250 操作の一括変更リクエスト

  • エントリとエントリリンクに対する作成・更新・削除を最大 250 件まで 1 つの変更リクエストにグループ化
  • entryGroups.requestBatchMetadataChange メソッドを使用して REST API 経由で提出
  • 提出時にリクエストの構文と、参照されるエントリタイプ・アスペクトタイプ・エントリリンクタイプ・親エントリの存在が検証される

🤖 2. エンリッチメントエージェント提案のキュレーション

  • 人間のレビューが必要なメタデータ提案が生成されると、エージェントが自動的にバッチ変更リクエストを作成
  • 承認者は、リクエストが NEW または FAILED 状態の間、承認前にペイロードを編集可能
  • エージェントは信頼度 (confidence) に基づいて自己承認するか、承認者へレビューを依頼するかを選択できる
  • エージェント起点のリクエストには batchChangeMetadataRequest.description.job.name にエンリッチメント実行 ID が含まれる

⚙️ 3. 依存関係を考慮した自動適用

  • 承認されると以下の依存順で操作が自動適用される

🔄 リクエストのステータス遷移

ステータスバッチ変更リクエストでの意味
NEWレビュー待ち。ユーザー提出分は作成者が、エージェント提出分はレビュアーが編集可能
APPLYING承認済みで、バックグラウンドで適用中
APPROVED承認済みで、バッチ内の少なくとも 1 件の変更が成功。項目レベルのエラーはレスポンスに記録
FAILEDバッチ内のすべての変更が適用不可。リクエストを更新すると NEW に戻り再承認が可能
REJECTED承認者が却下。変更は適用されない

🔐 必要な IAM ロール

操作ロール
バッチ変更リクエストの提出Dataplex Catalog Viewer (roles/dataplex.catalogViewer) ※対象エントリグループに付与
リクエストの承認Dataplex Workflow Approver (roles/dataplex.workflowApprover) に加え、提案された変更に必要な書き込み・タイプ使用権限
ワークフローの管理Dataplex Workflow Admin (roles/dataplex.workflowAdmin)
💡 カスタムロールの場合: 対象エントリグループに対する dataplex.entryGroups.get と dataplex.entryGroups.requestChanges 権限が必要です。

📐 バッチ構築時の参照ルール

  • 同一バッチ内で削除するエントリを参照するエントリリンクの作成・更新は不可。削除対象エントリを parentEntry に指定することも不可
  • 新規エントリが同一バッチ内の別エントリを parentEntry として参照する場合、親エントリの作成操作を子より先に列挙する
  • parent フィールドを省略した場合は changePayload.name のエントリグループが使用される。指定する場合は changePayload.name と一致している必要がある
  • justification (変更理由) は最大 1,024 文字

🛠️ 設定方法

✅ 前提条件

✓Dataplex API が有効化されていること
✓提出者に対象エントリグループの Dataplex Catalog Viewer ロール、承認者に Dataplex Workflow Approver ロールと必要な書き込み権限が付与されていること

📤 ステップ 1: バッチ変更リクエストの提出

Bash requestBatchMetadataChange API の呼び出し 
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "projects/PROJECT_ID/locations/LOCATION/entryGroups/ENTRY_GROUP_ID",
    "changePayload": {
      "name": "projects/PROJECT_ID/locations/LOCATION/entryGroups/ENTRY_GROUP_ID",
      "changes": [
        {
          "createEntryRequest": {
            "parent": "projects/PROJECT_ID/locations/LOCATION/entryGroups/ENTRY_GROUP_ID",
            "entryId": "ENTRY_ID",
            "entry": {
              "entryType": "projects/PROJECT_ID/locations/LOCATION/entryTypes/ENTRY_TYPE_ID"
            }
          }
        }
      ]
    },
    "justification": "JUSTIFICATION"
  }' \
  "https://dataplex.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/entryGroups/ENTRY_GROUP_ID:requestBatchMetadataChange"

changes 配列に最大 250 件の操作を列挙できます。レスポンスには作成された変更リクエストのリソース名が返されます。

🔍 ステップ 2: 保留中リクエストの確認

Bash NEW 状態のリクエストを一覧表示 
curl -X GET \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://dataplex.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/changeRequests?filter=state=NEW"

バッチリクエストは changeType が BATCH_CHANGE_METADATA となります。 コンソールでは「Governance Workflows」ページの「Pending Approvals」タブから確認できます。

✅ ステップ 3: リクエストの承認・却下

Bash 変更リクエストの承認 
# 承認
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -d '{}' \
  "https://dataplex.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/changeRequests/CHANGE_REQUEST_ID:approve"

承認後、リクエストは APPLYING 状態となり、バックグラウンドで適用されます。 最終状態 (APPROVED または FAILED) は changeRequests.get をポーリングして確認します。

💡 メリット

💼 ビジネス面

✓ガバナンスの効率化: 大量のメタデータ変更を 1 回のレビュー・承認で処理でき、データスチュワードの承認作業の負担を大幅に削減
✓AI 活用の統制: エンリッチメントエージェントが生成したメタデータを人間が検証・編集してから公開する human-in-the-loop プロセスを標準機能として実現。AI 生成メタデータの品質と説明責任を担保
✓監査性の向上: 変更理由 (justification)、作成者、承認者、ステータスがリクエスト単位で記録され、ワークフロー管理者は全状態の監査証跡を閲覧可能

⚙️ 技術面

✓API 呼び出しの集約: 個別リクエストを多数発行する代わりに、1 回の API 呼び出しで最大 250 操作を提出
✓依存関係の自動解決: 削除 → 作成・更新の依存順で自動適用されるため、適用順序を呼び出し側で制御する必要がない
✓項目レベルのエラー可視化: 一部失敗しても failedRequests で失敗箇所とエラー内容を特定でき、リカバリーが容易

⚠️ デメリット・制約事項

🚫 制限事項

✗Preview 段階であり、Pre-GA Offerings Terms が適用される (サポートが限定される可能性)
✗1 リクエストあたりの操作数は最大 250 件
✗バッチ変更リクエストの提出は REST API (Dataplex API) 経由のみ
✗ガバナンスワークフローは Assured Workloads プロジェクト、CMEK、VPC Service Controls を非サポート
✗トランザクション整合性や自動ロールバックはなく、承認後は各操作が個別に評価・適用される

🤔 考慮すべき点

⚠同時実行は「last writer wins」モデル。最後に承認された変更が以前の更新を上書きする。複数の保留中リクエストが同一リソースに共存できる点に注意
⚠自分自身のリクエストは承認できない (エンリッチメントエージェントは信頼度に基づく自己承認が可能)
⚠リクエストは手動削除、対象リソースの削除、または 90 日の有効期限で完全に削除され、以後の照会は 404 エラーになる
⚠承認時の同期検証で失敗した場合、INVALID_ARGUMENT/NOT_FOUND は FAILED 状態へ、PERMISSION_DENIED は NEW 状態のまま残るという挙動の違いがある

🎯 ユースケース

🤖 ユースケース 1: エンリッチメントエージェント提案のキュレーション

シナリオ: データプラットフォームチームがエンリッチメントタスクを定期実行し、BigQuery テーブルの説明やビジネスコンテキストを AI で自動生成している。 ただし、信頼度が低い提案はそのまま公開せず、データスチュワードのレビューを必須にしたい。

実装例:

  1. エンリッチメントタスクを auto-publishing 無効 (レビュー必須) で構成
  2. エージェント実行後、バッチ変更リクエストが NEW 状態で自動登録される
  3. 承認者が Governance Workflows ページでリクエストを開き、提案内容を編集
  4. 問題のない提案のみに修正したうえで承認 → カタログへ一括反映

効果: AI によるメタデータ生成のスケールメリットを享受しつつ、公開前の人間による検証で品質を担保できる。

👥 ユースケース 2: 権限を持たないチームによる大規模メタデータ登録

シナリオ: データ基盤の移行プロジェクトで、移行チームが数百件のカスタムエントリとエントリリンク (リネージ関係など) をカタログに登録したいが、 エントリグループへの直接の書き込み権限は中央ガバナンスチームのみが保持している。

効果: 移行チームは Catalog Viewer 権限のみで最大 250 操作をまとめた変更リクエストを提出でき、ガバナンスチームは 1 回の承認で一括適用できる。 個別リクエストの往復が不要になり、移行作業のリードタイムを短縮できる。

📝 まとめ

Knowledge Catalog のガバナンスワークフローにバッチメタデータ変更リクエストが追加され、 最大 250 件のエントリ・エントリリンク操作を 1 つのリクエストとして提出・承認できるようになりました。

特にエンリッチメントエージェントの提案を承認前に編集できる点は、AI 生成メタデータを統制の取れた形で大規模導入するうえで重要な基盤となります。

メタデータのキュレーション運用を担うチームは、Preview 段階のうちに requestBatchMetadataChange API と承認フローを検証し、 既存のカタログ運用プロセスへの組み込みを検討することを推奨します。
