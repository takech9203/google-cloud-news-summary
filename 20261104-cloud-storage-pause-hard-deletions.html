⏸️ ソフト削除オブジェクトのハード削除一時停止機能

📅 リリース日: 2026-11-04

📝 概要

Cloud Storage に、バケット単位でソフト削除オブジェクトの完全削除 (ハード削除) を一時停止できる機能が追加されました。 通常、ソフト削除されたオブジェクトは保持期間 (デフォルト 7 日間、最大 90 日間) が経過すると自動的に完全削除されますが、 本機能を使うと保持期間が満了してもオブジェクトは完全削除されず、ハード削除を再開するまでソフト削除状態のまま保持されます。

大規模な誤削除インシデントや悪意ある削除の発生時に、復元作業のための時間を確保することが目的です。 数十億オブジェクト規模の復旧では復元処理が保持期間内に完了しない可能性がありますが、 ハード削除を一時停止すれば「保持期間切れによるデータの恒久的な喪失」というタイムリミットを気にせず、調査・復元・検証を進められます。

💡 誰に嬉しい? ストレージ管理者、データ保護 (バックアップ/DR) 担当者、セキュリティインシデント対応チーム。 ランサムウェアや誤操作によるマスデリーションへの対応手段が強化されます。

❌ Before (アップデート前の課題)

  • ソフト削除されたオブジェクトは保持期間 (最大 90 日間) 満了で自動的に完全削除され、止める手段がなかった
  • 保持期間の変更は変更後に削除されたオブジェクトにのみ適用され、ソフト削除済みオブジェクトの保持期間は延長できなかった
  • 数十億オブジェクト規模の復元や調査に時間がかかる場合、保持期間内に作業が完了せずデータを恒久的に失うリスクがあった

✅ After (アップデート後の改善)

  • バケット単位でハード削除を一時停止でき、ソフト削除済みオブジェクトを保持期間満了後も削除されない状態で保持できる
  • 大規模復元や削除インシデントの調査・復旧検証を時間的制約なく実施できる
  • 一時停止は即時に反映されるため、インシデント検知後すぐにデータ喪失を食い止められる

削除インシデント検知時にハード削除を一時停止すると、保持期間が満了してもオブジェクトはソフト削除状態のまま維持され、 復元・検証完了後に再開するというインシデント対応フローを示しています。

⚙️ 主要機能

1️⃣ ハード削除の一時停止 (Pause)

→ソフト削除ポリシーに hardDeletePause 設定を追加し、enabled: true で有効化
→一時停止中は、保持期間が満了したソフト削除オブジェクトも完全削除されず保持される
→即時に有効化 (キャッシュされた API レスポンスでは反映に数秒かかる場合あり)

2️⃣ ハード削除の再開 (Resume)

→hardDeletePause の enabled を false に設定して再開
→再開時、すでに保持期間を超過していたオブジェクトは即時に完全削除される
→保持期間内のオブジェクトは、通常どおり保持期間満了時に完全削除

3️⃣ 一時停止中の動作

✓オブジェクトの削除操作自体は引き続き可能 (削除されたオブジェクトはソフト削除状態になる)
✓ソフト削除の保持期間の変更は可能
✗ソフト削除の無効化はできない
✗バケット自体を削除できない

🛠️ 設定方法

📋 前提条件

✓対象バケットでソフト削除が有効であること (バケット作成時には一時停止を設定できない)
✓storage.buckets.update 権限を含むロール (例: roles/storage.admin) を持っていること
✓gcloud CLI がインストール・初期化されていること (アクセストークンの取得に使用)
⏸️ ステップ 1
ハード削除を一時停止
→
📦 ステップ 2
復元作業を実施
→
▶️ ステップ 3
ハード削除を再開

1ハード削除を一時停止する

Bash JSON API でハード削除を一時停止 
# 設定ファイルを作成
cat > pause.json << 'EOF'
{
  "softDeletePolicy": {
    "hardDeletePause": {
      "enabled": true
    }
  }
}
EOF

# JSON API でバケットを更新
curl -X PATCH --data-binary @pause.json \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://storage.googleapis.com/storage/v1/b/BUCKET_NAME"

BUCKET_NAME を対象バケット名に置き換えます。これ以降、ソフト削除オブジェクトは保持期間が満了しても完全削除されません。

2復元作業を実施する

Bash ソフト削除されたオブジェクトを一括復元 (例) 
gcloud storage restore "gs://BUCKET_NAME/**" --async

削除範囲の調査、必要なオブジェクトの復元 (個別または一括)、復旧内容の検証を行います。

3ハード削除を再開する

Bash JSON API でハード削除を再開 
# 設定ファイルを作成
cat > resume.json << 'EOF'
{
  "softDeletePolicy": {
    "hardDeletePause": {
      "enabled": false
    }
  }
}
EOF

# JSON API でバケットを更新
curl -X PATCH --data-binary @resume.json \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://storage.googleapis.com/storage/v1/b/BUCKET_NAME"
⚠️ 注意: 再開すると、保持期間をすでに超過していたオブジェクトは即時に完全削除されます。復旧の検証が完了してから再開してください。

👍 メリット

💼 ビジネス面

✓データ喪失リスクの低減: 誤削除やランサムウェア等によるマスデリーション発生時に、保持期間のタイムリミットに追われることなく確実に復旧できる
✓インシデント対応の質の向上: 削除の影響範囲の調査や復旧後の検証を、データ喪失のプレッシャーなく丁寧に実施できる

🔧 技術面

✓大規模復元への対応: 数十億オブジェクト規模のバケットなど、復元処理が保持期間内に完了しないケースでも安全に復旧できる
✓即時性: 一時停止は即時に反映されるため、インシデント検知直後の初動対応として有効
✓既存機能との統合: ソフト削除ポリシーの拡張として提供されるため、既存のバケット設定 (PATCH Bucket) の延長で利用できる

⚠️ デメリット・制約事項

🚫 制限事項
✗一時停止 / 再開の切り替えは 24 時間に 1 回までに制限される
✗ソフト削除が有効なバケットでのみ利用可能 (バケット作成時には設定できない)
✗一時停止中はソフト削除を無効化できず、バケット自体の削除もできない
🤔 考慮すべき点
→一時停止中もソフト削除オブジェクトのストレージ料金は発生し続けるため、長期間の一時停止はコストが大幅に増加する可能性がある。復旧完了後は速やかに再開することが推奨される
→再開した時点で、保持期間を超過していたオブジェクトは即座に完全削除されるため、再開前に復元の完了と検証を必ず済ませておく必要がある
→24 時間に 1 回という切り替え頻度の制限があるため、一時停止 / 再開の操作は計画的に行う必要がある

🎯 ユースケース

📦 ユースケース 1: マスデリーションインシデントからの大規模復旧

シナリオ: 誤って実行されたバッチ処理により、数億オブジェクトを格納する本番バケットの大部分が削除された。ソフト削除の保持期間は 7 日間だが、全オブジェクトの復元と整合性検証には 2 週間以上かかる見込み。

Bash 実装例 
# 1. 即座にハード削除を一時停止
curl -X PATCH --data-binary '{"softDeletePolicy":{"hardDeletePause":{"enabled":true}}}' \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://storage.googleapis.com/storage/v1/b/prod-data-bucket"

# 2. 一括復元を非同期で実行
gcloud storage restore "gs://prod-data-bucket/**" --async

# 3. 検証完了後にハード削除を再開
✅ 効果: 保持期間の 7 日間を超えても復元対象のオブジェクトが完全削除されず、時間をかけて確実に全データを復旧できる。

🔍 ユースケース 2: セキュリティインシデントの調査

シナリオ: 不正アクセスの疑いがあり、バケット内で意図しない削除が行われた形跡がある。削除の影響範囲が特定できておらず、どのオブジェクトを復元すべきか調査が必要。

✅ 効果: 調査が完了するまで証跡 (ソフト削除オブジェクト) が完全削除されることを防ぎ、影響範囲の特定後に必要なオブジェクトだけを確実に復元できる。

💰 料金

ハード削除の一時停止機能自体に追加料金は発生しませんが、 一時停止中もソフト削除状態のオブジェクトにはストレージ料金が継続して課金されます。 保持期間満了後も削除されずに保持され続けるため、一時停止期間が長引くほどストレージコストが増加します。 復旧完了後は速やかにハード削除を再開することが推奨されます。

詳細は Cloud Storage の料金ページ を参照してください。

🔗 関連サービス・機能

  • 🗑️ ソフト削除 (Soft Delete): 本機能の前提となる機能。削除されたオブジェクトを 7〜90 日間保持し、復元を可能にする。本機能はこのソフト削除ポリシーの拡張として提供される
  • 📦 一括復元 (Bulk Restore): ソフト削除オブジェクトの大規模復元に使用する非同期の長時間実行オペレーション。本機能と組み合わせることで大規模復旧を時間制約なく実施できる
  • 🗂️ オブジェクトのバージョニング (Object Versioning): 非現行バージョンの削除時もソフト削除状態になるため、本機能による保護の対象となる
  • 🔒 バケットロック / オブジェクト保持ロック: 削除自体を防止する機能。ソフト削除と本機能は、削除後の復元可能期間を保護する補完的なレイヤーとして機能する
  • 💡 ソフト削除向け Recommender: Cloud Billing のコストと使用状況に基づき、ソフト削除の有効化 / 無効化の推奨事項を提示する

✨ まとめ

ソフト削除の保持期間という「復旧のタイムリミット」を一時的に止められる本機能は、 大規模な誤削除やセキュリティインシデントへの対応力を大きく高めるアップデートです。

📌 推奨アクション
→ソフト削除を利用しているバケットの運用手順書 (ランブック) に、インシデント検知時の初動として「ハード削除の一時停止」を組み込む
→一時停止中はストレージコストが増加するため、復旧完了後に速やかに再開する運用ルールも整備しておく
