Agent Platform Workbench Gemini Enterprise GA (一般提供)

🏛️ Agent Platform Workbench
インスタンス向けカスタム組織ポリシーが GA

📅 リリース日: 2026-10-26

📌 概要

Gemini Enterprise Agent Platform Workbench インスタンスに対するカスタム組織ポリシーのサポートが GA になりました。 組織ポリシー管理者は notebooks.googleapis.com/Instance リソースに対して CEL 条件によるカスタム制約を定義し、 インスタンスの構成に基づいて作成 (CREATE)・更新 (UPDATE) 操作を ALLOW / DENY で制御できます。

「Shielded VM を必須化」「マシンタイプを制限」「外部 IP を禁止」といった組織独自のガバナンス要件を、 組織・フォルダ・プロジェクトの各階層で一元的に適用可能。ドライランモードにより、実際にブロックする前に違反を監査ログで観測して安全に導入できます。

❌ Before (アップデート前の課題)

  • 組み込み制約では、マシンタイプ・Shielded VM・外部 IP などの個別フィールドを制御できない
  • 統制は作成後の監査や運用ルール周知など事後的・手動の手段に依存
  • 非準拠インスタンスの作成を階層的に予防ブロックする仕組みが不足

✅ After (アップデート後の改善)

  • インスタンスのフィールドを参照する CEL 条件で組織独自の制約を定義し、作成・更新時に強制
  • 非準拠リクエストは API レベルで拒否され、ガードレールを予防的に適用
  • ドライランで違反を監査ログ観測し、安全にポリシーを導入可能

管理者が定義したカスタム制約を組織ポリシーとして適用すると、インスタンスの作成・更新リクエストが制約条件で評価され、非準拠のリクエストは拒否されます。 ドライランモードでは拒否せずに違反を監査ログへ記録します。

⚙️ 主要機能

1️⃣ インスタンス構成に基づく作成・更新の制御 GA

  • notebooks.googleapis.com/Instance リソースに対するカスタム制約が一般提供
  • CREATE と UPDATE の両メソッドで制約を強制可能
  • 条件が true の場合に許可する ALLOW、拒否する DENY の 2 種類のアクションタイプ

2️⃣ CEL 条件による柔軟な制約定義

  • resource.gceSetup.machineType.startsWith('n1-standard-') のような CEL 式で条件を記述 (最大 1,000 文字)
  • マシンタイプ、Shielded VM、外部 IP、ディスク暗号化 (CMEK)、ネットワーク、サービスアカウントなど多数のフィールドを参照可能
  • resource.gceSetup.systemMetadata では許可リスト内の Workbench システムメタデータキー (例: idle-timeout-seconds、notebook-disable-downloads) を個別に参照可能

3️⃣ ドライランモードのサポート

  • dryRunSpec を使ってポリシーを適用すると、違反操作をブロックせずに監査ログへ記録
  • ライブポリシー (spec) とドライランポリシー (dryRunSpec) を同一の YAML で併用可能
  • 本番適用前に影響範囲を検証する段階的なロールアウトが可能

4️⃣ リソース階層でのポリシー継承

  • 組織・フォルダ・プロジェクトの各レベルでポリシーを適用可能
  • デフォルトでポリシーは下位リソースに継承 (例: フォルダに適用すると配下の全プロジェクトに適用)

📐 技術仕様

項目詳細
対象リソースnotebooks.googleapis.com/Instance
適用メソッドCREATE、UPDATE
条件記述言語CEL (Common Expression Language)、最大 1,000 文字
アクションタイプALLOW / DENY

📜 カスタム制約の YAML 例 (マシンタイプの制限)

YAML 
name: organizations/ORGANIZATION_ID/customConstraints/custom.restrictWorkbenchMachineType
resourceTypes:
- notebooks.googleapis.com/Instance
methodTypes:
- CREATE
- UPDATE
condition: "resource.gceSetup.machineType.startsWith('n1-standard-')"
actionType: ALLOW
displayName: Restrict Workbench instance machine types
description: Workbench instances must use an n1-standard machine type.

1カスタム制約を作成して適用

カスタム制約を組織に登録し、組織ポリシーで利用可能な状態にします。

2組織ポリシーを作成して適用
YAML 
# policy-restrict-machine-type.yaml
name: projects/PROJECT_ID/policies/custom.restrictWorkbenchMachineType
spec:
  rules:
  - enforce: true
Bash 
gcloud org-policies set-policy ~/policy-restrict-machine-type.yaml

# ポリシーの確認
gcloud org-policies list --project=PROJECT_ID
💡 ポイント: ポリシー適用後、強制が開始されるまで約 2 分かかります。
3(推奨) ドライランモードで事前検証
YAML 
# ライブポリシーは無効のまま、ドライランのみ有効化する例
name: projects/PROJECT_ID/policies/custom.restrictWorkbenchMachineType
spec:
  rules:
  - enforce: false
dryRunSpec:
  rules:
  - enforce: true
Bash 
gcloud org-policies set-policy POLICY_PATH --update-mask=dryRunSpec

ドライランモードでは違反操作はブロックされず、監査ログに違反として記録されます。影響を確認した後にライブポリシーへ昇格します。

💡 メリット

💼 ビジネス面

  • コンプライアンスの予防的担保: セキュリティ基準 (Shielded VM 必須、外部 IP 禁止、CMEK 必須など) を満たさないインスタンスの作成を API レベルでブロックし、事後監査の負担を軽減
  • 一元的なガバナンス: 組織・フォルダ・プロジェクト階層でポリシーを継承させ、組織全体の Workbench 利用を一貫したルールで統制
  • コスト統制: マシンタイプやアクセラレータの制限、アイドルシャットダウンの必須化で、意図しない高コスト構成を防止

🔧 技術面

  • きめ細かなフィールドレベル制御: マネージド制約では対応できない個別フィールド (マシンタイプ、ネットワーク、ディスク暗号化など) を CEL 条件で柔軟に制御
  • ドライランによる安全な導入: 違反をブロックせず監査ログで観測でき、既存ワークフローへの影響を検証してから段階的に強制を開始
  • GA 品質: 一般提供となり、本番環境のガバナンス基盤として利用可能

⚠️ デメリット・制約事項

🚧 制限事項

  • ポリシーは遡及適用されない。既存インスタンスの構成には影響せず、非準拠の構成でも更新されない限り有効なまま
  • 条件 (CEL 式) は最大 1,000 文字、カスタム制約はほとんどのリソースタイプで最大 20 個まで
  • resource.gceSetup.systemMetadata は許可リスト内のシステムメタデータキーのみ参照可能。生の resource.gceSetup.metadata フィールドは参照不可
  • ドライランモードの利用には、プロジェクトで課金が有効になっている必要がある

🤔 考慮すべき点

  • ポリシー適用後、強制が開始されるまで約 2 分程度かかる
  • ALLOW アクションは条件に合致するケース以外をすべてブロックするため、条件の書き方によっては意図以上に広くブロックされる可能性がある。ドライランでの事前検証を推奨
  • UPDATE メソッドに制約を適用した場合、違反状態のリソースへの変更は、違反を解消する変更でない限りブロックされる
  • 制約 ID やエラーメッセージ (displayName / description) は呼び出し元に露出するため、PII や機密情報を含めない

🎯 ユースケース

🔒 1. セキュリティ基準の強制

シナリオ: 金融機関などの規制業種で、Workbench インスタンスに Secure Boot の有効化と外部 IP アドレスの無効化を必須にしたい。

効果: 非準拠インスタンスの作成・更新が API レベルで拒否され、セキュリティ基準からの逸脱を予防。外部 IP 禁止は resource.gceSetup.disablePublicIp == true を条件とする別制約で実現。

💰 2. コスト統制

シナリオ: データサイエンスチームが多数のインスタンスを利用しており、高価なマシンタイプの乱用やアイドル放置によるコスト超過を防ぎたい。

効果: 承認済みマシンタイプのみ利用可能にし、idle-timeout-seconds によるアイドルシャットダウンを必須化して放置コストを抑制。

🧪 3. 段階的なポリシー導入

シナリオ: 既に多数のチームが Workbench を利用している組織で、新しい制約の導入による業務影響を最小化したい。

効果: dryRunSpec で違反を監査ログに記録しながら影響を把握し、問題がないことを確認してからライブポリシーへ昇格する安全なロールアウトが可能。

📜 実装例: Secure Boot 必須化 (ユースケース 1)

YAML 
name: organizations/ORGANIZATION_ID/customConstraints/custom.workbenchRequireSecureBoot
resourceTypes:
- notebooks.googleapis.com/Instance
methodTypes:
- CREATE
- UPDATE
condition: "resource.gceSetup.shieldedInstanceConfig.enableSecureBoot == true"
actionType: ALLOW
displayName: Require Secure Boot on Workbench instances
description: All Workbench instances must have Secure Boot enabled.

📜 実装例: アイドルシャットダウン必須化の CEL 条件 (ユースケース 2)

CEL 
'idle-timeout-seconds' in resource.gceSetup.systemMetadata && int(resource.gceSetup.systemMetadata['idle-timeout-seconds']) > 0

💲 料金

Organization Policy Service のカスタム制約機能自体についての追加料金の記載は、参照したドキュメントには見当たりませんでした。 なお、ドライランモードの利用にはプロジェクトで課金が有効になっている必要があります。 Agent Platform Workbench インスタンス自体には、基盤となるコンピュートリソース等の料金が発生します。

🔗 関連サービス・機能

→Organization Policy Service: 本機能の基盤。マネージド制約とカスタム制約により Google Cloud リソースを一元的に統制
→Policy Simulator: 組織ポリシーの変更による影響を適用前にシミュレーション (ドライランと併用可能)
→Cloud Audit Logs: ドライランモードでの違反はブロックされずに監査ログへ記録されるため、違反の観測に使用
→IAM: カスタム制約の管理には roles/orgpolicy.policyAdmin ロールが必要
→Shielded VM / Confidential Computing / CMEK: カスタム制約で有効化を必須にできる Workbench インスタンスのセキュリティ機能

📝 まとめ

Agent Platform Workbench インスタンスに対するカスタム組織ポリシーが GA となり、 マシンタイプ、Shielded VM、外部 IP、暗号化設定などの構成をフィールドレベルで予防的に統制できるようになりました。 既存インスタンスには遡及適用されないため、まずはドライランモードで現状の違反状況を把握し、 影響を確認した上でライブポリシーへ段階的に昇格させる導入が推奨されます。
