🔒 Identity-Aware Proxy:
Agent Gateway Egress セキュリティ

Identity-Aware Proxy GA Agent Gateway
2026-06-24

📋 概要

Identity-Aware Proxy (IAP) が Agent Gateway における Agent-to-Anywhere エグレストラフィックのセキュリティ保護を正式に GA (一般提供) としてサポートしました。

Gemini Enterprise Agent Platform 上で動作するエージェントが外部のツール、MCP サーバー、API、他のエージェントにアクセスする際のすべてのアウトバウンド通信に対して、IAM ベースのきめ細かなアクセス制御ポリシーを適用できるようになります。

Agent Gateway は Gemini Enterprise Agent Platform のネットワーキング/セキュリティの中核コンポーネントとして機能し、IAP がそのデフォルト認可レイヤーとしてエージェントの SPIFFE ID を検証し、IAM 権限に基づいて呼び出しを許可/拒否します。

✅ Zero Trust の実現: エンタープライズ環境で AI エージェントのエグレストラフィックを本番品質のセキュリティで運用でき、Zero Trust アーキテクチャの原則をエージェント間通信にも適用可能になりました。

🔄 Before / After 比較

❌ アップデート前の課題

  • エージェントから外部サービスへの一元的アクセス制御なし
  • アクセス先の可視性が限定的で不正通信を防止困難
  • VPC Service Controls ではエージェント固有のエグレスポリシーを細かく制御不可
  • エージェントのアイデンティティに基づく認可がなく全エージェントが同一権限

✅ アップデート後の改善

  • IAP が Agent Gateway のデフォルト認可レイヤーとして GA 品質で利用可能
  • roles/iap.egressor でエージェント単位のアクセス制御
  • デフォルト拒否で未許可のエグレスを自動ブロック
  • Dry-run モードで安全にポリシーをテスト
  • Cloud Audit Logs で完全な監査証跡を取得

⚡ 主要機能

🚫 デフォルト拒否ポリシー

Agent Gateway はデフォルトですべてのエグレストラフィックを拒否。roles/iap.egressor が明示的に付与されたエージェントのみがアクセス可能。Registry 未登録ホストへのアクセスは自動ブロック。

🎯 きめ細かな IAM 制御

iap.webServiceVersions.egressViaIAP パーミッションを付与する専用ロール。レジストリ全体または個別リソースレベルでバインディング可能。Organization/Folder/Project レベルの階層管理対応。

🧪 Dry-run モード

DRY_RUN モードではポリシー違反を Cloud Audit Logs に記録するが通信はブロックしない。本番適用前にポリシーの影響を安全に検証。検証完了後に ENFORCE モードへ切り替え。

🛡️ 多層セキュリティ統合

Model Armor: プロンプトインジェクション攻撃や機密データ漏洩からの保護。Semantic Governance: ツールの危険な組み合わせに対する制御。Service Extensions: カスタム認可エンジンへの委任。

⚙️ 設定方法

前提条件

✓ Gemini Enterprise Agent Platform が有効化されたプロジェクト
✓ Agent Registry にエージェント、エンドポイント、MCP サーバーが登録済み
✓ エージェントに Agent Identity が割り当て済み
✓ 適切な IAM 権限 (IAP Policy Admin など)

Step 1: Agent Gateway リソースの作成

YAML 
name: my-agent-gateway-egress
protocols:
  - MCP
googleManaged:
  governedAccessPath: AGENT_TO_ANYWHERE
  registries:
    - //agentregistry.googleapis.com/projects/PROJECT_ID/locations/REGION
Bash 
gcloud network-services agent-gateways import my-agent-gateway-egress \
  --source="my-agent-gateway-egress.yaml" \
  --location=us-central1

Step 2: IAP Authorization Extension (DRY_RUN モード推奨)

YAML 
name: my-iap-request-authz-ext
service: iap.googleapis.com
failOpen: true
timeout: 1s
metadata:
  iamEnforcementMode: "DRY_RUN"
  iapPolicyVersion: "V1"

Step 3: Authorization Policy の作成と適用

YAML 
name: my-iap-request-authz-policy
target:
  resources:
    - "projects/PROJECT_ID/locations/us-central1/agentGateways/my-agent-gateway-egress"
policyProfile: REQUEST_AUTHZ
action: CUSTOM
customProvider:
  authzExtension:
    resources:
      - "projects/PROJECT_ID/locations/us-central1/authzExtensions/my-iap-request-authz-ext"

Step 4: IAP Egressor ロールの付与

Bash 
curl -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  -H "Content-Type: application/json" \
  -d '{
    "policy": {
      "bindings": [{
        "role": "roles/iap.egressor",
        "members": ["principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/subject/AGENT_SPIFFE_ID"]
      }]
    }
  }' \
  -X POST "https://iap.googleapis.com/v1/projects/PROJECT_NUMBER/locations/REGION/iap_web/agentRegistry:setIamPolicy"

Step 5: エージェントを Agent Gateway に関連付け

Bash 
curl -X PATCH \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d '{
    "spec": {
      "deploymentSpec": {
        "agentGatewayConfig": {
          "agentToAnywhereConfig": {
            "agentGateway": "projects/PROJECT_ID/locations/us-central1/agentGateways/my-agent-gateway-egress"
          }
        }
      }
    }
  }' \
  "https://us-central1-aiplatform.googleapis.com/v1beta1/projects/PROJECT_ID/locations/us-central1/reasoningEngines/RESOURCE_ID?updateMask=spec.deploymentSpec.agentGatewayConfig"

Step 6: 本番適用 (DRY_RUN → ENFORCE)

YAML 
# 検証完了後、ENFORCE モードに変更
name: my-iap-request-authz-ext
service: iap.googleapis.com
failOpen: true
timeout: 1s
metadata:
  iamEnforcementMode: "ENFORCE"
  iapPolicyVersion: "V1"

🎯 メリット

ビジネス面

✓ Zero Trust の実現: エージェント間通信にもゼロトラスト原則を適用し、セキュリティコンプライアンス要件を満たせる
✓ 段階的な導入: Dry-run モードで既存ワークロードを中断せずにポリシーを段階的に導入可能
✓ 一元管理: すべてのエージェントエグレスポリシーを IAM で一元的に管理

技術面

✓ きめ細かな制御: エージェント単位、ツール単位でのアクセス許可制御
✓ 完全な監査証跡: Cloud Audit Logs との統合
✓ デフォルト拒否: 未許可トラフィックを全てブロック
✓ Multi-layer セキュリティ: IAP + Model Armor + Semantic Governance

⚠️ 制限事項・考慮点

制限事項:
  • 2026 年 4 月 29 日以前に作成された Runtime Reasoning Engine には Agent Gateway をバインド不可
  • 同一プロジェクト・リージョン内のすべてのエージェントは同一の Agent Gateway インスタンスにバインドが必要
  • VPC Service Controls は Agent Gateway との併用がサポートされていない
  • Client-to-Agent (Ingress) モードでは Agent Runtime の query/streamQuery メソッドのみが統制対象
  • Gemini Enterprise は Agent-to-Anywhere (Egress) モードのみをサポート
考慮すべき点:
  • Agent Registry に登録されていないホストへのアクセスはすべてブロック - Cloud Trace、Cloud Logging、LLM API 等も事前登録が必要
  • mTLS やリージョナルバリアントなど、同一サービスの複数エンドポイントホスト名をすべて登録が必要
  • Organization Policy によるゲートウェイの制限設定が反映されるまでに最大 15 分のラグ

💡 ユースケース

🏢 ユースケース 1: マルチエージェントシステムの権限分離

シナリオ: 顧客対応エージェント、バックオフィスエージェント、データ分析エージェントがそれぞれ異なる外部ツールにアクセスする。

YAML 
# 顧客対応エージェント: CRM API とナレッジベースのみアクセス可能
- role: roles/iap.egressor
  members: ["principal://...customer-agent-identity"]
  resource: "projects/PROJECT/locations/REGION/iap_web/agentRegistry/endpoints/crm-api"

# データ分析エージェント: BigQuery と Cloud Storage のみアクセス可能
- role: roles/iap.egressor
  members: ["principal://...analytics-agent-identity"]
  resource: "projects/PROJECT/locations/REGION/iap_web/agentRegistry/endpoints/bigquery-api"

効果: エージェントごとにアクセス可能なリソースを明確に分離し、1 つのエージェントが侵害された場合の影響範囲を限定。

🔗 ユースケース 2: 外部 MCP サーバーへのセキュアなアクセス制御

シナリオ: AI エージェントがサードパーティの MCP サーバー (コード生成ツール、検索エンジン等) にアクセスする際に、認可されたエージェントのみがアクセスでき、Model Armor でコンテンツの安全性を確保。

効果: エージェントの外部通信に対するセキュリティガードレールを確立し、データ漏洩やプロンプトインジェクション攻撃のリスクを軽減。
