Cloud Composer Apache Airflow GA Beta (dockerconfigjson)

📋 概要

Cloud Composer (Managed Service for Apache Airflow) の新しいリリースが開始されました。Google Cloud タグサポート、dockerconfigjson シークレットタイプ、Airflow UI のログレベルフィルタ修正、および複数の新しい Airflow ビルドが提供されています。

💡 ハイライト: Cloud Composer 環境への Google Cloud タグサポートにより、タグベースの IAM ポリシーで細かなアクセス制御が可能になりました。

Before / After

❌ Before

  • 環境にタグを付与できず、タグベースの IAM 条件付きアクセス制御が利用不可
  • Gen 3 で Opaque タイプのみサポート、Docker レジストリ認証にワークアラウンドが必要
  • Airflow 3 UI の INFO ログフィルタが正しく動作しない
  • 旧バージョンのセキュリティパッチ適用負担が増加

✅ After

  • Google Cloud タグを付与し、IAM 条件付きポリシーで細かなアクセス制御が可能
  • dockerconfigjson シークレットでプライベートレジストリ認証が簡素化
  • Airflow 3 UI の INFO ログフィルタが正常動作
  • Airflow 3.1.7 含む最新ビルドでセキュリティパッチ適用済み

⚡ 主要機能

🏷 Google Cloud タグサポート

Cloud Composer 環境に Google Cloud タグを付与可能に。タグはキーと値のペアで構成され、IAM 条件と組み合わせてアクセス制御ポリシーを設定できます。

➜Gen 2、Gen 3 の両方で利用可能
➜gcloud resource-manager tags bindings create でバインディング作成

🔒 dockerconfigjson シークレット (Gen 3)

Managed Airflow (Gen 3) で kubernetes.io/dockerconfigjson シークレットタイプが利用可能に。beta Cloud Composer API 経由で作成できます。

➜プライベートレジストリ認証を Kubernetes 標準形式で管理
➜従来の Opaque タイプに加えて利用可能

🔧 Airflow 3 UI ログフィルタ修正

Airflow 3 の UI で INFO ログレベルフィルタが正しく動作しない問題が修正されました。INFO レベルのログメッセージが正確に表示されます。

🚀 新ビルド提供

最新の Airflow 3.1.7 ビルドを含む新しいビルドが利用可能に。最新機能とセキュリティパッチが適用されています。

🛠 設定方法

前提条件

✓Google Cloud プロジェクトが作成済み
✓Cloud Composer API が有効化
✓roles/composer.admin + roles/resourcemanager.tagUser ロール付与済み
✓タグキーとタグ値が組織レベルで作成済み

ステップ 1: タグキーとタグ値の作成

Bash 
# タグキーの作成
gcloud resource-manager tags keys create environment-type \
  --parent=organizations/ORGANIZATION_ID \
  --description="Cloud Composer 環境の種別"

# タグ値の作成
gcloud resource-manager tags values create production \
  --parent=tagKeys/TAG_KEY_ID \
  --description="本番環境"

ステップ 2: Cloud Composer 環境にタグを付与

Bash 
# タグバインディングの作成
gcloud resource-manager tags bindings create \
  --tag-value=tagValues/TAG_VALUE_ID \
  --parent="//composer.googleapis.com/projects/PROJECT_ID/locations/LOCATION/environments/ENVIRONMENT_NAME" \
  --location=LOCATION

ステップ 3: dockerconfigjson シークレットの作成 (Gen 3)

Bash 
# beta Cloud Composer API を使用してシークレットを作成
gcloud beta composer environments user-workloads-secrets create \
  --environment=ENVIRONMENT_NAME \
  --location=LOCATION \
  --source=docker-secret.yaml

ステップ 4: DAG での Kubernetes Secret の使用

Python 
from airflow.providers.cncf.kubernetes.operators.kubernetes_pod import KubernetesPodOperator
from kubernetes.client import models as k8s

# dockerconfigjson シークレットを imagePullSecrets として使用
pod_operator = KubernetesPodOperator(
    task_id="pull-from-private-registry",
    name="private-registry-task",
    namespace="composer-user-workloads",
    image="my-private-registry.example.com/my-image:latest",
    image_pull_secrets=[k8s.V1LocalObjectReference(name="my-registry-credentials")],
    startup_timeout_seconds=300,
)

🎯 ユースケース

👥 マルチチーム環境のアクセス制御

大規模組織で複数チームが Cloud Composer を利用しており、各チームが自分の環境のみにアクセスできるよう制限したい場合。

Bash 
# チーム A の環境にタグを付与
gcloud resource-manager tags bindings create \
  --tag-value=tagValues/TEAM_A_VALUE_ID \
  --parent="//composer.googleapis.com/projects/my-project/locations/us-central1/environments/team-a-composer" \
  --location=us-central1

# IAM 条件付きロールバインディングの設定
gcloud projects add-iam-policy-binding my-project \
  --member="group:team-a@example.com" \
  --role="roles/composer.user" \
  --condition='expression=resource.matchTag("ORGANIZATION_ID/team", "team-a"),title=team-a-access'

効果: チームごとに独立したアクセス制御が実現され、誤操作による他チーム環境への影響を防止。

🤖 プライベートレジストリからの ML モデルイメージ取得

ML パイプラインで社内プライベートレジストリのカスタム ML モデルコンテナを KubernetesPodOperator で実行したい場合。

Python 
from airflow.providers.cncf.kubernetes.operators.kubernetes_pod import KubernetesPodOperator
from kubernetes.client import models as k8s

ml_training = KubernetesPodOperator(
    task_id="ml-model-training",
    name="ml-training-pod",
    namespace="composer-user-workloads",
    image="private-registry.example.com/ml-models/training:v2.1",
    image_pull_secrets=[k8s.V1LocalObjectReference(name="my-registry-credentials")],
    resources=k8s.V1ResourceRequirements(
        requests={"memory": "4Gi", "cpu": "2"},
        limits={"memory": "8Gi", "cpu": "4"},
    ),
    startup_timeout_seconds=600,
)

効果: プライベートレジストリへの認証が Kubernetes 標準の仕組みで管理され、セキュアかつ運用しやすい ML パイプラインが構築可能。

🛡 本番/開発環境のポリシー分離

本番環境と開発環境で異なるセキュリティポリシーを適用し、本番環境への変更を限定したメンバーのみに許可したい場合。

効果: タグベースの条件付きポリシーにより、本番環境への書き込みアクセスを SRE チームのみに制限し、開発者は開発環境のみで作業できるようになる。
