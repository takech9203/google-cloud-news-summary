🔁 正規表現 URL リライト (regexRewrite) が GA

Application Load Balancer の URL マップで RE2 正規表現によるパス書き換えが可能に
📅 リリース日: 2026-10-27

📝 概要

Application Load Balancer の URL マップにおいて、ルートルールの正規表現 URL リライト (regexRewrite) が GA (一般提供) になりました。RE2 構文の正規表現 (pathPattern) で受信リクエストパスの一部をキャプチャし、 置換文字列 (pathSubstitution) でキャプチャグループを参照しながら、バックエンド転送前にパスを置換・削除・並べ替え・結合できます。

名前付きキャプチャグループ ((?<name>re)) を \g<name> で参照する方式と、 \1 や \2 のような番号参照の両方に対応。2026 年 10 月 12 日に GA となった正規表現マッチャー (regexMatch) と合わせて、 マッチングからリライトまで正規表現で統一した柔軟なトラフィック制御が可能になりました。

❌ Before (アップデート前の課題)

✗URL リライトは pathPrefixRewrite (プレフィックス置換) と pathTemplateRewrite (パステンプレート) に限られ、正規表現リライトを GA 機能として利用できなかった
✗パス途中のコンポーネントを条件付きで抽出・並べ替え・結合する複雑な変換は、テンプレート構文では表現が難しいケースがあった

✅ After (アップデート後の改善)

✓RE2 正規表現でパスの任意の部分をキャプチャし、置換文字列で自由に再構築 (置換・削除・並べ替え・結合) 可能に
✓名前付きキャプチャグループと番号参照の両方で、可読性の高いリライト定義が可能に
✓GA となり、本番環境のワークロードで利用しやすくなった

⚙️ 主要機能

1️⃣ 正規表現によるパスマッチング (pathPattern)

→pathMatchers[].routeRules[].routeAction.urlRewrite.regexRewrite.pathPattern フィールドに RE2 構文の正規表現を指定
→受信リクエストパスの一部をキャプチャグループ (...) で捕捉
→名前付きキャプチャグループは (?<name>re) または (?P<name>re) の形式で定義

2️⃣ キャプチャグループを使ったパス再構築 (pathSubstitution)

→pathSubstitution フィールドで、バックエンドサービスに送信する前のパスを再構築
→名前付きグループは \g<name>、番号付きグループは \1 や \2 で参照
→名前付きグループ (?<name>re) は番号でも名前でも参照可能

✏️ リライト動作の例

📥 受信リクエストの URL パス/api/users/21334/profile.json
🔍 pathPattern/api/users/(?<id>\d+)/(?<path>[a-z]+\.json)
🔁 pathSubstitution/users/\g<id>/\g<path>
📤 バックエンドに送信されるパス/users/21334/profile.json

📄 URL マップ設定例 (YAML)

/region/us-central1/bucket/my-bucket/stage/dev/object.pdf のようなリクエスト URL を /us-central1/my-bucket-dev/object.pdf にリライトしてからバックエンドサービスにプロキシする、公式ドキュメント記載の設定例です。

YAML URL マップ設定例 (regexRewrite) 
defaultService: projects/example-project/regions/us-central1/backendServices/default-bs
name: regex-rewrite-url-map
pathMatchers:
- name: region-matcher
  defaultService: projects/example-project/regions/us-central1/backendServices/default-bs
  routeRules:
  - matchRules:
    - prefixMatch: /region/
    priority: 1
    service: projects/example-project/regions/us-central1/backendServices/rewrite-bs
    routeAction:
      urlRewrite:
        regexRewrite:
          pathPattern: "/region/(?<reg>[a-z0-9-]+)/bucket/(?<bkt>[a-z0-9-]+)/stage/(?<stg>[a-z0-9-]+)/object\\.pdf"
          pathSubstitution: "/\\g<reg>/\\g<bkt>-\\g<stg>/object.pdf"
  • matchRules.prefixMatch: ルールの適用対象を /region/ で始まるパスに限定
  • pathPattern: 名前付きキャプチャグループでリージョン (reg)、バケット名 (bkt)、ステージ名 (stg) を捕捉
  • pathSubstitution: 捕捉した値を \g<name> で参照し、新しいパスを構築

⚠️ デメリット・制約事項

🚧 制限事項

✗Classic Application Load Balancer は正規表現をサポートしない
✗正規表現は RE2 構文で記述する必要があり、URL マップで許可される演算子には制限がある (RE2 specifications for URL maps を参照)
✗1 つのルートルールに指定できる URL リライトアクションは 1 つのみで、regexRewrite は pathPrefixRewrite や pathTemplateRewrite と併用できない
✗pathSubstitution で参照できるキャプチャグループは最大 8 個
✗pathPattern と pathSubstitution はそれぞれ最大 250 文字

🤔 考慮すべき点

⚠️正規表現の誤りはルーティング不具合に直結するため、パターンとキャプチャグループの動作を事前に十分検証する必要がある
⚠️既に pathPrefixRewrite や pathTemplateRewrite を使用しているルートルールに追加する場合は、排他制約を踏まえてどのリライト方式を使うか設計を見直す必要がある

🎯 ユースケース

🧩 ユースケース 1: API パス構造の変換 (バージョン・階層の付け替え)

シナリオ: 公開 API のパス (/api/users/{id}/profile.json) と、バックエンドの内部パス (/users/{id}/profile.json) の構造が異なる。バックエンドを改修せずにロードバランサーでパスを変換したい。

YAML 実装例 
routeAction:
  urlRewrite:
    regexRewrite:
      pathPattern: "/api/users/(?<id>\\d+)/(?<path>[a-z]+\\.json)"
      pathSubstitution: "/users/\\g<id>/\\g<path>"
✅ 効果: クライアント向けの URL を変えずにバックエンドの内部パス構造へ変換でき、アプリケーション側の改修が不要になる。
