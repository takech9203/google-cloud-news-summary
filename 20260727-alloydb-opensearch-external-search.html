🐘 AlloyDB for PostgreSQL
外部検索 (External Search) が OpenSearch をサポート

AlloyDB for PostgreSQL Preview external_search_fdw
📅 リリース日: 2026-07-27

📝 概要

AlloyDB for PostgreSQL の外部検索機能が、新たに OpenSearch をサポート (Preview)。 external_search_fdw 拡張 (PostgreSQL の Foreign Data Wrapper) を使って OpenSearch クラスタに接続し、 OpenSearch のインデックスを外部テーブルとしてマッピングすることで、データを移動・コピーせずに AlloyDB から直接 SQL で検索・JOIN できます。

標準 SQL (Lucene 構文)、OpenSearch の Query DSL に加え、AlloyDB のベクトル検索と組み合わせた ハイブリッド検索 (ai.hybrid_search 関数、RRF によるランク融合) にも対応。 すでに対応済みの Elasticsearch (2026 年 4 月 Preview)・Solr と合わせて、主要な検索エンジンへの接続が揃いました。

❌ Before: アップデート前の課題

  • AlloyDB と OpenSearch のデータを組み合わせるには、アプリ側で 2 システムに個別クエリ発行 + 結果マージの実装が必要
  • OpenSearch のデータを SQL で分析するには ETL パイプラインでのコピー・同期が必要で、データ重複や鮮度の問題が発生
  • ベクトル検索 + トークン検索のハイブリッド検索を DB 内で完結する手段がなかった

✅ After: アップデート後の改善

  • external_search_fdw で OpenSearch インデックスを外部テーブル化し、AlloyDB から直接 SQL で検索可能に
  • データの移動・コピーなしに OpenSearch インデックスと AlloyDB テーブルを JOIN 可能に
  • ai.hybrid_search でトークン検索とベクトル検索を RRF で融合するハイブリッド検索が DB 内で実行可能に

💡 仕組み: AlloyDB は SQL クエリを OpenSearch の REST API クエリに変換して外部クラスタに送信し、結果を外部テーブルとして返します。認証情報は Secret Manager で安全に管理され、OpenSearch のインデックスと AlloyDB のテーブルをデータ移動なしで JOIN できます。

⚙️ 主要機能

🗂️ 1. OpenSearch インデックスの外部テーブルマッピング

→CREATE SERVER で OpenSearch クラスタを外部データサーバーとして登録し、CREATE FOREIGN TABLE でインデックスのスキーマを外部テーブルにマッピング
→データを移動・コピーすることなく、AlloyDB のリレーショナルテーブルと OpenSearch のインデックスを JOIN 可能
→読み取り専用 (read-only) のシャロー統合として提供

🔍 2. 3 種類のクエリ方式

📄
標準 SQL
Lucene 構文の検索式を ORDER BY metadata <@> 'QUERY' 形式で指定 (例: body:database)
🧩
Query DSL
OpenSearch の JSON 形式 Query DSL をそのまま利用可能 (query / filter / sort 式に対応)
🤝
ハイブリッド検索
ai.hybrid_search でトークン検索とベクトル検索を RRF (Reciprocal Rank Fusion) で融合

🔐 3. Secret Manager による認証情報管理

→OpenSearch の認証情報 (Basic 認証) を Secret Manager に格納し、secret_path オプションで参照
→AlloyDB サービスアカウントに roles/secretmanager.secretAccessor ロールを付与して利用

⚡ 4. クエリプッシュダウンによる効率化

→SELECT フィールド、WHERE フィルタ、ORDER BY ソート、LIMIT を OpenSearch への API 呼び出しに直接プッシュダウンし、転送データ量と処理を最適化

ステップ 1: 拡張機能の有効化と外部サーバーの作成

SQL 外部データサーバーの作成 
CREATE EXTENSION external_search_fdw;

CREATE SERVER opensearch_server
FOREIGN DATA WRAPPER external_search_fdw
OPTIONS (
    server 'OPENSEARCH_SERVER_HOST_PORT',
    search_provider 'opensearch',
    auth_mode 'secret_manager',
    auth_method 'Basic',
    secret_path 'projects/123456789012/secrets/opensearch-credentials/versions/1'
);

ステップ 2: ユーザーマッピングと外部テーブルの作成

SQL OpenSearch インデックスの外部テーブルマッピング 
CREATE USER MAPPING FOR CURRENT_USER SERVER opensearch_server;

CREATE FOREIGN TABLE my_fd_opensearch_table(
    metadata external_search_fdw_schema.OpaqueMetadata,
    id BIGINT,
    body TEXT
)
SERVER opensearch_server
OPTIONS (
    remote_table_name 'my-opensearch-index'
);

ステップ 3: クエリの実行

SQL 標準 SQL + Lucene 構文 / ハイブリッド検索 
-- 標準 SQL + Lucene 構文
SELECT id, body
FROM my_fd_opensearch_table
ORDER BY metadata <@> 'body:database';

-- ハイブリッド検索 (OpenSearch トークン検索 + AlloyDB ベクトル検索)
SELECT *
FROM ai.hybrid_search(
  ARRAY[
    '{"limit": 10,
      "weight": 0.5,
      "table_name": "my_fd_opensearch_table",
      "key_column": "id",
      "query_text_input": "body:\"cloud databases\""}'::jsonb
  ])
ORDER BY score DESC;

⚖️ メリット・制約事項

👍 ビジネス面のメリット

✓データ統合コストの削減: ETL パイプラインやアプリ側マージ処理の構築・維持が不要に
✓既存資産の活用: OpenSearch の検索インデックスをそのまま活用しつつ、AlloyDB のデータと組み合わせた分析・検索が可能

🔧 技術面のメリット

✓データ移動なしの JOIN: データの重複や同期遅延が発生しない
✓ハイブリッド検索: 全文検索とベクトル検索を RRF で融合し、セマンティック検索とキーワード検索の長所を両立
✓クエリプッシュダウン: SELECT / WHERE / ORDER BY / LIMIT を OpenSearch 側で効率的に実行

⚠️ 制限事項

✗Preview 段階の機能 (Pre-GA Offerings Terms が適用され、サポートが限定される可能性あり)
✗読み取り専用の統合であり、AlloyDB から OpenSearch のデータは更新不可
✗OpenSearch クラスタにはパブリックにアクセス可能なエンドポイントが必要
✗認証は Secret Manager 経由の Basic 認証を使用

🤔 考慮すべき点

→AlloyDB インスタンスでアウトバウンド接続の有効化が必要
→プッシュダウンできない要素 (複数フィールド比較式や関数を含む式など) は AlloyDB 側での後処理となり、パフォーマンスに注意
→OpenSearch 側にセキュリティプラグインの有効化と読み取り専用ユーザーの作成が必要

🎯 ユースケース

🛒 ユースケース 1: 運用データと検索インデックスの横断分析

シナリオ: EC サイトで注文・在庫データを AlloyDB に、商品カタログの全文検索インデックスを OpenSearch に保持。商品検索結果に在庫状況や販売実績を組み合わせて表示したい。

SQL 検索インデックスと在庫テーブルの JOIN 
SELECT p.id, p.title, o.stock_count
FROM my_fd_opensearch_table p
JOIN inventory o ON o.product_id = p.id
ORDER BY p.metadata <@> 'title:wireless earphone'
LIMIT 20;

効果: アプリ側での 2 システムへのクエリ発行と結果マージが不要になり、1 つの SQL で検索と在庫参照を完結できる。

🤖 ユースケース 2: RAG 向けハイブリッド検索

シナリオ: 生成 AI アプリケーションの検索拡張生成 (RAG) で、AlloyDB のベクトル検索 (セマンティック検索) と OpenSearch のキーワード検索を組み合わせて検索精度を高めたい。

効果: ai.hybrid_search 関数により、ベクトル検索とトークン検索の結果を RRF で融合した高精度な検索結果をデータベース内で取得でき、RAG パイプラインの構成をシンプルにできる。

📌 まとめ

AlloyDB の外部検索が OpenSearch に対応したことで、Elasticsearch・Solr と合わせて主要な検索エンジンを AlloyDB から SQL で直接検索できる体制が整いました。

運用データベースと検索エンジンを併用している場合、ETL やアプリケーション側の統合処理を削減できる可能性があるため、Preview 段階のうちに接続性 (パブリックエンドポイント、アウトバウンド接続) とクエリプッシュダウンの挙動を検証しておくことをおすすめします。
