🔐 Identity and Access Management (IAM) ✅ GA (一般提供)
📅 リリース日: 2026-10-29

🔑 新しい基本ロール Admin / Writer / Reader が GA

基本ロールでも IAM Conditions による条件付きアクセス制御が可能に。暗黙的な追加権限のない、予測可能な権限セットを実現

📋 概要

Google Cloud IAM の新しい基本ロール (Basic roles) である Admin (roles/admin)、Writer (roles/writer)、Reader (roles/reader) が一般提供 (GA) になりました。基本ロールは、すべての Google Cloud サービスにまたがる数千のパーミッションを含む、非常に広範な権限を付与するロールです。

従来のレガシー基本ロール (Owner / Editor / Viewer) は引き続き利用可能かつ積極的にメンテナンスされますが、Google Cloud は基本ロールを付与する必要がある場合、IAM Conditions (条件付きロールバインディング) をサポートする新しい Admin / Writer / Reader ロールの付与を推奨しています。

🕰️ Before: アップデート前の課題

  • レガシー基本ロール (Owner / Editor / Viewer) には IAM Conditions を追加できず、時間帯・リソース・IP などの属性ベースの条件付きアクセス制御が利用できなかった
  • Cloud Storage の便宜的な値 (convenience values) や BigQuery の特別なグループメンバーシップによる暗黙的な権限も付与され、実効権限の把握が難しかった
  • 条件付きで制御できる基本ロールの選択肢が GA としては存在しなかった

✨ After: アップデート後の改善

  • Admin / Writer / Reader が GA となり、基本ロールに IAM Conditions を適用可能に (例: 営業時間のみ、特定リソースのみ、期間限定のアクセス)
  • 暗黙的な権限付与がなく、権限の範囲がロール定義どおりで予測しやすい
  • Privileged Access Manager (PAM) のエンタイトルメントとして設定し、ジャストインタイムの昇格アクセスにも組み込める
⚠️ ベストプラクティス: 本番環境では基本ロール自体の使用を避け、最小権限の事前定義ロールまたはカスタムロールを使用することが引き続き推奨されます。基本ロールは検証・ステージング環境など、広範な権限を手早く付与したい場合に限定しましょう。

レガシー基本ロールでは条件を付与できず暗黙的な追加権限も発生していましたが、GA となった Admin / Writer / Reader ロールでは IAM Conditions による属性ベースのアクセス制御が可能になり、権限範囲もロール定義どおりに限定されます。

⚙️ 主要機能

1️⃣ 新しい基本ロール 3 種の GA

Reader (読み取り専用) → Writer (状態変更) → Admin (機密操作) の 3 段階の階層構造。上位ロールは下位ロールの全パーミッションを包含します。

👀 Reader
roles/reader
状態を変更しない読み取り専用アクション (既存リソースやデータの閲覧)
＋
✏️ Writer
roles/writer
Reader の全権限 + 状態を変更するアクション (リソースの作成・変更・削除など)。ただし全サービスの全アクションを含むわけではない
＋
👑 Admin
roles/admin
Writer の全権限 + 機密性の高い操作 (タグバインディング管理、IAM 管理、課金設定など)
2️⃣ IAM Conditions のサポート

ロールバインディングに条件 (CEL 式) を追加でき、日時・リソースタイプ・リソース名・タグなどの属性に基づくアクセス制御が可能。レガシー基本ロールでは従来どおり条件付きバインディングは利用不可。

3️⃣ 暗黙的権限の排除

Cloud Storage convenience values や BigQuery 特別グループメンバーシップによる追加権限は付与されません。ロール定義どおりの実効権限で、権限の棚卸しが容易になります。

4️⃣ レガシー基本ロールの継続提供

Owner / Editor / Viewer は廃止されず、引き続き利用可能かつ積極的にメンテナンスされます。プロジェクト作成者への Owner 自動付与など、一部の自動化ワークフローでは引き続き使用されます。

📜 条件付きロールバインディングの例

JSON 営業時間のみ Writer ロールを有効にする条件付きバインディング 
{
  "bindings": [
    {
      "role": "roles/writer",
      "members": [
        "user:dev-user@example.com"
      ],
      "condition": {
        "title": "business-hours-only",
        "description": "営業時間 (ベルリン時間 9-17 時、平日) のみ許可",
        "expression": "request.time.getHours('Europe/Berlin') >= 9 && request.time.getHours('Europe/Berlin') <= 17 && request.time.getDayOfWeek('Europe/Berlin') >= 1 && request.time.getDayOfWeek('Europe/Berlin') <= 5"
      }
    }
  ]
}
💡 Admin ロールの注意点: Admin はすべての権限を含むわけではありません。Cloud Billing の支払い情報の変更や IAM Deny ポリシーの作成権限は含まれません。

🛠️ 設定方法

✅ 前提条件

✓対象リソース (プロジェクトなど) に対する IAM ポリシーの設定権限 (resourcemanager.projects.setIamPolicy など) を持っていること
✓gcloud CLI または IAM API を利用できること (新しい基本ロールは Google Cloud コンソールからは付与できない)

ステップ 1: 新しい基本ロールを付与する

Bash Writer ロールをユーザーに付与 
# Writer ロールをユーザーに付与
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="user:dev-user@example.com" \
  --role="roles/writer"

Google Cloud コンソールでは Reader / Writer / Admin ロールを付与できないため、gcloud CLI または API を使用します。

ステップ 2: IAM Conditions を付けて付与する

Bash 期間限定で Reader ロールを付与 (2026 年末まで) 
# 期間限定で Reader ロールを付与 (2026 年末まで)
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="user:auditor@example.com" \
  --role="roles/reader" \
  --condition='title=expires-end-of-2026,expression=request.time < timestamp("2027-01-01T00:00:00Z")'

条件式は CEL (Common Expression Language) のサブセットで記述します。条件が true と評価された場合のみロールが有効になります。

💪 メリット

💼 ビジネス面

🛡️ ガバナンスの強化

広範な権限に期間・時間帯・リソース範囲などの条件を付けられるため、監査やコンプライアンス要件 (最小権限・期限付きアクセス) への対応が容易に。

🔍 権限の透明性向上

暗黙的な追加権限が付与されないため、「誰が何にアクセスできるか」の棚卸しが正確になり、セキュリティレビューの工数を削減。

🔧 技術面

⏱️ 条件付きアクセス制御

レガシー基本ロールでは不可能だった IAM Conditions を適用でき、一時アクセスやリソース限定アクセスを宣言的に実装可能。

🔗 PAM との統合

Privileged Access Manager のエンタイトルメントとして定義し、ジャストインタイムの権限昇格フローに組み込める。

📐 予測可能な権限セット

Cloud Storage / BigQuery の特別な暗黙的権限が付与されないため、ロール定義に基づいた正確な権限設計が可能。

⚠️ デメリット・制約事項

🚧 制限事項

✗新しい基本ロールは Google Cloud コンソールからは付与できず、API または gcloud CLI (もしくは PAM エンタイトルメント) を使用する必要がある
✗Admin ロールはすべての権限を含むわけではない (例: Cloud Billing の支払い情報の変更、IAM Deny ポリシーの作成は不可)
✗IAM Conditions は allUsers / allAuthenticatedUsers への付与には使用できない
✗条件付きロールバインディングを受け付けないリソースタイプもある (その場合は組織・プロジェクトレベルで付与する)

🤔 考慮すべき点

⚠本番環境では基本ロール自体の使用を避け、最小権限の事前定義ロールまたはカスタムロールを使用することが引き続き推奨 (基本ロールは代替がない場合のみ)
⚠レガシー基本ロールから移行する場合、Storage convenience values や BigQuery 特別グループによる暗黙的権限に依存したアクセスが失われないか事前確認が必要
⚠プロジェクト作成時の Owner 自動付与など、自動化ワークフローでは引き続きレガシー基本ロールが使用される
⚠1 つの許可ポリシーに追加する条件付きロールバインディングは 100 個以下に抑えることがベストプラクティス (ポリシーのサイズ上限超過を防ぐため)

🎯 ユースケース

📌 ユースケース 1: 検証環境での期限付き広範アクセス

シナリオ: 開発チームが検証プロジェクトで短期間の PoC を実施するため、広範な権限を期間限定で付与したい。レガシー Editor ロールでは期限を設定できず、付与後の剥奪を手動管理する必要があった。

Bash PoC 期間限定で Writer ロールを付与 
gcloud projects add-iam-policy-binding poc-project \
  --member="group:poc-team@example.com" \
  --role="roles/writer" \
  --condition='title=poc-period,expression=request.time < timestamp("2026-12-31T23:59:59Z")'
✅ 効果: 期限が切れると自動的にアクセスが無効になり、権限剥奪の運用漏れによるセキュリティリスクを排除できる。
📌 ユースケース 2: レガシー基本ロールからの計画的な移行

シナリオ: 組織内のステージング環境で Editor / Viewer が広く付与されており、暗黙的な Storage / BigQuery 権限を含めた実効権限の把握が困難。セキュリティ監査で条件付きアクセスへの移行を求められている。

✅ 効果: Writer / Reader への置き換えにより、暗黙的権限のない予測可能な権限セットと IAM Conditions による属性ベース制御を実現し、監査要件を満たせる。移行時は Policy Analyzer などで既存アクセスの依存関係を確認してから切り替えることで安全に移行できる。

🧩 関連サービス・機能

⏱️ IAM Conditions

新しい基本ロールで利用可能になった属性ベースのアクセス制御。CEL 式で日時・リソース・タグなどの条件を定義する。

🔐 Privileged Access Manager (PAM)

新しい基本ロールのエンタイトルメントを作成し、ジャストインタイムの権限昇格を実現できる。

🎛️ 事前定義ロール / カスタムロール

本番環境で推奨されるロールタイプ。基本ロールは代替がない場合にのみ使用する。

🗄️ Cloud Storage / BigQuery のアクセス制御

レガシー基本ロールに紐づく convenience values / 特別グループメンバーシップは新しい基本ロールには適用されないため、移行時に確認が必要。

📝 まとめ

IAM の新しい基本ロール Admin / Writer / Reader が GA となり、レガシー基本ロールでは不可能だった IAM Conditions による条件付きアクセス制御を、広範な権限セットに対しても適用できるようになりました。

✓基本ロールを付与する必要がある場合は、今後は Owner / Editor / Viewer ではなく Admin / Writer / Reader を選択することが推奨される
✓本番環境では引き続き最小権限の事前定義ロール・カスタムロールの使用を原則とする
✓既存のレガシー基本ロールの付与箇所は、暗黙的権限への依存を確認したうえで計画的な移行を検討する
