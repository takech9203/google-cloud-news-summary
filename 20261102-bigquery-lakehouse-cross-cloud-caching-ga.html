🔍 BigQuery: Lakehouse クロスクラウドキャッシング
(Intelligent Caching) GA

BigQuery / Lakehouse GA (一般提供) マルチクラウド コスト最適化
📅 リリース日: 2026-11-02

📝 概要

クロスクラウドデータアクセスにおける Lakehouse キャッシング (Intelligent Caching) が一般提供 (GA) になりました。 有効化すると、Amazon S3 や Azure Blob Storage から取得したファイルブロックが、クエリを実行する Google Cloud リージョン内に ローカルキャッシュとして保持されます。同じブロックを参照する後続クエリはリモートクラウドから再取得せずキャッシュから直接読み取るため、 クロスクラウド Egress コストの削減とクエリ性能の向上を同時に実現します。

デフォルトでは無効で、Lakehouse のフェデレーテッドカタログ、または BigQuery のクロスクラウド接続 (cross-cloud connection) の作成時・更新時に オプトインで有効化します。キャッシュの容量・保持期間・エビクションは Google が自動管理し、追加料金なしで利用できます。

❌ Before: アップデート前の課題

  • クエリ実行のたびにリモートクラウド (S3 / Azure Blob Storage) からファイルを読み取り、繰り返しアクセスでも毎回 Egress 料金が発生
  • リモートストレージからの読み取りがクエリのたびに発生し、ネットワーク転送がレイテンシのボトルネックに
  • Egress コスト対策に Google Cloud 側へデータを複製する ETL パイプラインの構築・運用が必要

✅ After: アップデート後の改善

  • キャッシングを有効化するだけで取得済みブロックがクエリ実行リージョン内に自動キャッシュされ、後続クエリ (別クエリも含む) がローカルから読み取り
  • リモート再取得が不要になり、Egress コスト削減と後続クエリ高速化を同時に実現
  • Google が自動管理するため運用負荷ゼロ・追加料金なし
  • objectStorageStats で cacheBytesRead / objectStorageBytesRead を確認でき、削減効果を定量的に把握

💡 キャッシングを有効化すると、リモートストレージから取得したファイルブロックがクエリ実行リージョン内に自動保存され、後続クエリはキャッシュから直接読み取ります。 キャッシュ提供前には毎回リモートソースとメタデータ・アクセス権限を検証するため、古いデータの読み取りや失効済み権限のバイパスは発生しません。

⚡ 主要機能

🧱 1. ブロックレベルのリードスルーキャッシュ

  • Amazon S3 / Azure Blob Storage から取得したファイルブロックを、Google Cloud のクエリ実行リージョン内にローカルキャッシュ
  • 同一ファイルブロックを参照するクエリであれば、異なるクエリでもキャッシュが再利用される
  • キャッシュの容量・保持期間・エビクションは Google が自動管理

🔒 2. 鮮度と権限の自動検証

  • キャッシュからデータを提供する前に、すべてのクエリでリモートストレージソースとメタデータ・アクセス権限を検証
  • 古い (stale な) データの読み取りや、失効済み権限でのキャッシュ読み取りを防止

🎚️ 3. オプトイン方式の有効化

  • クロスクラウドキャッシングはデフォルトで無効
  • Lakehouse フェデレーテッドカタログ、または BigQuery クロスクラウド接続の作成時・更新時に有効/無効を切り替え可能

📊 4. キャッシュ利用状況のモニタリング

  • BigQuery コンソールのジョブ詳細、または JobStatistics2 の objectStorageStats フィールドで確認
  • cloudProvider: アクセス先のクラウドプロバイダ (例: AWS、AZURE)
  • cacheBytesRead: ローカルキャッシュから読み取った合計バイト数 (リモート読み取りを回避した量)
  • objectStorageBytesRead: リモートオブジェクトストレージから直接読み取った合計バイト数

ステップ 1: キャッシングを有効にした AWS クロスクラウド接続を作成する

Bash AWS 接続の作成 (キャッシング有効) 
bq mk --connection \
  --connection_type='AWS' \
  --location=LOCATION \
  --project_id=PROJECT_ID \
  --properties='{"accessRole":{"iamRoleId":"arn:aws:iam::AWS_ACCOUNT_ID:role/ROLE_NAME"},"crossCloudCacheOptions":{"enabled":true}}' \
  CONNECTION_ID

crossCloudCacheOptions.enabled を true に設定するとキャッシングが有効になります (デフォルトは false)。 Google Cloud コンソールでは、接続作成画面の「Cross-cloud caching」で「Enable cross-cloud caching」を選択します。 既存接続は「Connection info」ページの「Edit details」から後で変更することもできます。

ステップ 2: キャッシングを有効にした Azure クロスクラウド接続を作成する (Azure の場合)

Bash Azure 接続の作成 (キャッシング有効) 
bq mk --connection \
  --connection_type='Azure' \
  --tenant_id=TENANT_ID \
  --location=LOCATION \
  --federated_azure=true \
  --federated_app_client_id=APP_ID \
  --project_id=PROJECT_ID \
  --properties='{"crossCloudCacheOptions":{"enabled":true}}' \
  CONNECTION_ID

Azure でも同様に crossCloudCacheOptions でキャッシングを有効化します。 Lakehouse フェデレーテッドカタログを使う場合は、各カタログプロバイダ (Databricks Unity Catalog、AWS Glue など) のセットアップガイドに従ってカタログ作成・更新時に有効化します。

ステップ 3: キャッシュ利用状況と Egress 削減効果を確認する

Bash ジョブ統計の確認 
bq show --format=prettyjson --job=true JOB_ID

出力 JSON の statistics.query.objectStorageStats で、クラウドプロバイダごとの cacheBytesRead (キャッシュから読み取った量) と objectStorageBytesRead (リモートから直接読み取った量) を確認し、キャッシュヒット率と Egress コスト削減効果を測定できます。

💡 メリット

💼 ビジネス面

✓クロスクラウド Egress コストの削減: 繰り返しアクセスされるデータをローカルキャッシュから提供することで、AWS / Azure からのデータ転送料金を削減。追加料金なしのため導入障壁が低い
✓データ複製パイプラインの削減: Egress コスト対策として Google Cloud にデータを複製する ETL パイプラインを構築・運用する必要性が低下

⚙️ 技術面

✓後続クエリの高速化: リモートストレージへのネットワーク往復を回避し、同じファイルブロックを参照するクエリの性能が向上
✓運用レス: キャッシュの容量・保持・エビクションは Google が自動管理するため、チューニングや運用作業が不要
✓一貫性と安全性: 毎クエリでリモートソースのメタデータと権限を検証するため、古いデータの読み取りや失効権限によるアクセスが発生しない
✓効果の可視化: objectStorageStats によりキャッシュヒット量を定量的に監視でき、コスト削減効果を検証できる

⚠️ デメリット・制約事項

🚫 制限事項

✗CMEK (顧客管理の暗号鍵) は非対応。キャッシュデータは Google 所有・Google 管理の鍵で暗号化される
✗組織ポリシー constraints/gcp.restrictNonCmekServices (Restrict Non-CMEK Services) 適用時は、制限対象テーブルへのクエリでキャッシングが自動的に無効化 (クエリ自体はリモートストレージから直接読み取って実行)
✗デフォルトでは無効のため、効果を得るには接続またはカタログごとに明示的な有効化が必要

🤔 考慮すべき点

🌍 データレジデンシー: キャッシング有効時、リモートファイルのキャッシュコピーがクエリ実行先の Google Cloud リージョンに一時保存されます。 別の地理的リージョン・法域にあるデータ (例: EU の S3 / Azure Blob Storage を us-east4 からクエリ) をキャッシュする場合は、 組織のデータレジデンシー・コンプライアンス要件を満たすか事前に確認が必要です。
📉 削減効果はワークロード依存: 実際の Egress 削減効果は、クエリパターン、ソースファイルの更新頻度、対象リージョンでのキャッシュ保持状況に依存します。 頻繁に更新されるデータや一度しか読まないデータでは効果が限定的です。

🎯 ユースケース

📊 ユースケース 1: AWS 上の Iceberg データレイクに対する BI ダッシュボード

シナリオ: Amazon S3 上の Apache Iceberg テーブル (AWS Glue カタログ管理) を BigQuery からフェデレーションし、 Looker などの BI ダッシュボードが同じテーブルを 1 日に何度も参照。毎回 S3 からデータを読み取るため、AWS の Egress コストが膨らんでいる。

SQL AWS Glue データベースのフェデレーション 
-- キャッシング有効のクロスクラウド接続を使って AWS Glue データベースをフェデレーション
CREATE EXTERNAL SCHEMA `my-project.aws_glue_data`
WITH CONNECTION `us-east4.my-aws-connection`
OPTIONS (
  location = 'us-east4',
  external_source = 'aws-glue://arn:aws:glue:us-east-1:123456789:database/sales_db');

-- ダッシュボードのクエリは 2 回目以降ローカルキャッシュから読み取られる
SELECT region, SUM(amount) FROM `my-project.aws_glue_data.orders` GROUP BY region;

効果: 初回クエリで取得したファイルブロックがキャッシュされ、ダッシュボードの繰り返しクエリ (同じブロックを参照する別クエリも含む) がキャッシュヒットし、 S3 からの Egress コスト削減とレスポンス改善を両立できる。

🔗 ユースケース 2: Cross-Cloud Interconnect との組み合わせによる転送コスト最適化

シナリオ: セキュリティポリシー上、AWS との間の通信を Cross-Cloud Interconnect (CCI) 経由のプライベート転送にしており、さらに転送量自体も減らしたい。

効果: 予測可能なプライベートインターコネクトの Egress 料金と、ローカルブロックキャッシングによる転送量削減を組み合わせることで、 繰り返し実行される分析ワークロードのクロスクラウド転送コストを最小化できる (公式ドキュメントでも推奨されている組み合わせ)。

💰 料金

✅ 追加料金なし: クロスクラウドキャッシング自体は追加料金なしで利用できます。 キャッシュヒットによりリモートクラウド (AWS / Azure) 側の Egress 料金を削減できますが、実際の削減額はクエリパターン、ソースファイルの更新頻度、キャッシュ保持状況に依存します。

クエリ自体の料金は通常の BigQuery 料金体系 (クロスクラウド接続では標準のスロット予約・コミットメントを消費) に従います。 詳細は BigQuery の料金ページ を参照してください。

🌏 利用可能リージョン

クロスクラウド接続では、標準の BigQuery ロケーション (例: us-east4) を接続リージョンとして使用します。 対応リージョンと機能の詳細は Supported regions and capabilities を参照してください。

🧩 関連サービス・機能

🔌 BigQuery クロスクラウド接続 (cross-cloud connections)

AWS / Azure / Salesforce Data 360 のデータを BigQuery に取り込んでクエリする接続。本キャッシング機能の有効化対象の 1 つで、標準スロット予約を消費し BigQuery AI やマテリアライズドビューなどの機能も利用できる。

🗂️ Lakehouse クロスクラウドデータアクセス (フェデレーテッドカタログ)

Databricks Unity Catalog、AWS Glue、Snowflake Horizon Catalog などのリモート Iceberg REST カタログをフェデレーションし、ファイル移行や ETL なしでリモートデータをクエリする機能。もう 1 つのキャッシング有効化対象。

🔗 Cross-Cloud Interconnect (CCI)

クロスクラウドのクエリデータ転送とメタデータ更新をプライベート経路でルーティングするネットワークサービス。キャッシングと組み合わせることで転送コストをさらに最適化できる。

🌐 BigQuery Omni

リモートリージョンに計算ワーカーをデプロイしてデータ移動なしでクエリする方式。クロスクラウド接続はその代替アプローチにあたる。

⚡ Managed Service for Apache Spark

BigQuery SQL に加えて、フェデレーションされたリモートデータを Spark で処理できる。

📌 まとめ

Lakehouse キャッシングの GA により、BigQuery から AWS / Azure 上のデータを繰り返しクエリするマルチクラウド分析ワークロードにおいて、 追加料金なしで Egress コスト削減とクエリ高速化を実現できるようになりました。 デフォルトでは無効のため、クロスクラウド接続やフェデレーテッドカタログを利用中の組織は、 データレジデンシー要件と CMEK 制約を確認したうえで有効化し、 objectStorageStats でキャッシュヒット率と削減効果を測定することを推奨します。
