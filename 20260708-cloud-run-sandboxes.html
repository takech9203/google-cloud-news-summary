📋 概要

Cloud Run に新たに「Sandboxes」機能が Preview として追加されました。AI エージェントが生成した信頼できないコードを高速かつセキュアに隔離実行するための環境を提供します。

Cloud Run の既存の二層サンドボックス技術 (ハードウェアベースの x86 仮想化レイヤーとソフトウェアカーネルレイヤー) を活用し、各インスタンスを他のインスタンスから強力に分離します。

🤖 対象ユーザー: AI エージェントを構築するデベロッパー。コード生成・実行を伴う AI アプリケーション、自動化ワークフロー、インタラクティブな開発環境などを Cloud Run 上で安全に運用したい組織に最適です。

🔄 Before / After

❌ Before (アップデート前)

  • 独自のサンドボックス環境を構築・運用する必要があった
  • コンテナベースの分離だけではセキュリティ保証が不十分
  • 環境プロビジョニングに時間がかかりレイテンシが課題

✅ After (アップデート後)

  • マネージドなサンドボックスで追加インフラ不要
  • 二層分離 (HW + SW) で強力なセキュリティ保証を標準提供
  • 高速プロビジョニングで低レイテンシ処理を実現

🏗️ アーキテクチャ図

Cloud Run Sandboxes は二層のサンドボックス技術によりコードを隔離します。AI エージェントが生成したコードは Sandbox Supervisor を経由してセキュアな環境内で実行され、IAM 権限と VPC ファイアウォールによる追加のセキュリティ制御が適用されます。

⚡ 主要機能

🔒 二層サンドボックス

→ハードウェアベース: x86 仮想化レイヤー (個別 VM 相当)
→ソフトウェアカーネル: gVisor (gen1) / Linux microVM (gen2)
→各インスタンスが他全てのインスタンスから保護

🚀 コード実行モード

→同期実行: リクエスト/レスポンス形式 (最大 1 時間)
→非同期実行: Cloud Run ジョブで長時間タスク処理
→コンカレンシー 1 設定でリクエスト単位の隔離

🎛️ Sandbox Launcher

→--sandbox-launcher フラグでスーパーバイザー設定
→サンドボックスの起動・管理を制御するコンテナ指定
→--no-sandbox-launcher で無効化可能

🛠️ 設定方法

以下の 3 ステップで Cloud Run Sandboxes を有効化できます。

1️⃣ サービスデプロイ
--sandbox-launcher
→
2️⃣ IAM 権限制限
最小権限の原則
→
3️⃣ VPC ファイアウォール
Egress 制限

ステップ 1: サンドボックスランチャーを有効にしたサービスのデプロイ

Bash 
gcloud beta run deploy SERVICE_NAME \
  --image=IMAGE_URL \
  --sandbox-launcher \
  --execution-environment=gen2 \
  --concurrency=1 \
  --region=REGION

ステップ 2: IAM 権限の制限

Bash 
# サービスアカウントの権限を最小限に設定
gcloud run services update SERVICE_NAME \
  --service-account=SANDBOX_SERVICE_ACCOUNT@PROJECT_ID.iam.gserviceaccount.com \
  --region=REGION

ステップ 3: VPC ファイアウォールルールの設定

Bash 
# サンドボックスからのインターネットアクセスを制限
gcloud compute firewall-rules create deny-sandbox-egress \
  --direction=EGRESS \
  --priority=1000 \
  --network=VPC_NETWORK \
  --action=DENY \
  --rules=all \
  --target-service-accounts=SANDBOX_SERVICE_ACCOUNT@PROJECT_ID.iam.gserviceaccount.com

🔄柔軟な実行モード: 同期・非同期の両方に対応し最適な実行方式を選択可能
🌐任意言語対応: コンテナベースのため任意のプログラミング言語でコード実行可能

⚠️ デメリット・制約事項

制限事項:
  • Preview ステータスのため、本番環境での SLA が適用されない可能性あり
  • 第1世代環境では一部のシステムコールが非対応 (gVisor の制約)
  • ファイルディスクリプタのハードリミット: 25,000
  • インスタンスはステートレス - 永続化には外部ストレージが必要
💡 考慮すべき点:
  • 信頼できないコード実行時は IAM 権限最小化 + VPC ファイアウォール設定が必須
  • コールドスタートのレイテンシ → 最小インスタンス数の設定で緩和可能
  • コンカレンシー 1 設定時は同時リクエスト増加でインスタンス数・コスト増加

💡 ユースケース

🔍 AI コードレビューエージェント

シナリオ: AI エージェントが Pull Request のコードを解析し、修正提案のコードを生成して実際にテスト実行する。

効果: 生成コードの動作検証をセキュアに実行し、コードレビューの品質と信頼性を向上。

Python 
# AI エージェントからのコード実行リクエスト
import requests

def execute_generated_code(code: str) -> dict:
    response = requests.post(
        "https://sandbox-service-xxx.run.app/execute",
        json={
            "code": code,
            "language": "python",
            "timeout": 30
        }
    )
    return response.json()

📊 インタラクティブなデータ分析エージェント

シナリオ: ユーザーの自然言語クエリに基づき、AI がデータ分析コード (Python/SQL) を生成し、サンドボックス内で実行して結果を返却する。

効果: ユーザーが直接コードを書くことなく、安全な環境でデータ分析を実行可能。悪意あるコードの混入リスクを排除。

🎓 教育・学習プラットフォーム

シナリオ: オンライン学習プラットフォームで、受講者が提出したコードをサンドボックス内で実行し、自動採点を行う。

効果: 受講者のコードによるシステムへの影響を完全に防止しつつ、リアルタイムのフィードバックを提供。
