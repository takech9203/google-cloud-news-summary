📝 概要

AlloyDB for PostgreSQL において、AlloyDB AI およびベクトル検索に関する複数の機能が 一般提供 (GA) になりました。中核は alloydb_scann 拡張が PostgreSQL 17 以降でサポートする 4 レベルツリー (4LT) ScaNN ベクトルインデックスで、 最大 100 億 (10B) 行のベクトルデータを持つテーブルに対するベクトル検索が可能になります。 4LT インデックスは自動インデックスメンテナンスにも対応しました。

あわせて、scann.satisfy_limit = relaxed_order によるストリーミング検索 (フィルタ付き検索のリコール改善)、 宣言的 SQL フレームワーク Vector assist、num_leaves 上限の引き上げ、 Elasticsearch / Solr / OpenSearch へのフェデレーション検索を実現する external_search_fdw 拡張、 高性能全文検索の rum 拡張が同時に GA。さらに 4LT インデックス構築時のメモリ見積もり改善 (OOM 防止) が Preview で提供されます。大規模 RAG やセマンティック検索基盤を運用する組織に重要なアップデートです。

❌ Before (アップデート前の課題)

  • 4LT ScaNN は Preview 段階で、10 億〜100 億行規模を GA 品質で利用できなかった
  • num_leaves 上限は 30,000,000 で、超大規模データのパーティション分割に上限
  • フィルタ付き検索で LIMIT 句を満たせずリコールが低下することがあった
  • 埋め込み生成・インデックスパラメータ・クエリチューニングを手動設計する必要
  • 外部検索クラスタのデータ検索にはデータコピーやアプリ側統合が必要
  • メモリ見積もりが不正確だと OOM でインデックス構築が失敗

✅ After (アップデート後の改善)

  • PG17+ で 4LT ScaNN が GA。最大 100 億ベクトル行 + 自動インデックスメンテナンス対応
  • num_leaves 上限が 104,857,600 に拡大 (PG17+)
  • ストリーミング機能で LIMIT を満たすまでリーフパーティションを追加探索し、リコール向上
  • Vector assist が本番品質のベクトル検索セットアップを宣言的に構築
  • external_search_fdw で Elasticsearch / Solr / OpenSearch に直接クエリ
  • rum 拡張で高速なフレーズ検索・関連度ランキング。メモリ見積もり改善で構築が安定 (Preview)

AlloyDB 内でベクトル検索 (4LT ScaNN)・全文検索 (rum)・外部検索クラスタへのフェデレーション検索 (external_search_fdw) を統合的に実行できる構成です。Vector assist はベクトルワークロードの構成を 推奨 SQL として生成し、自動インデックスメンテナンスがインデックスの品質を維持します。

⚡ 主要機能

1️⃣ 4 レベルツリー (4LT) ScaNN ベクトルインデックス GA

alloydb_scann 拡張が PostgreSQL 17 以降で 4 レベルツリーの ScaNN ベクトルインデックスをサポート。 最大 100 億 (10B) ベクトル行のテーブルに対応し、10 億〜100 億行のテーブルには 4 レベルインデックスが推奨。 作成時に max_num_levels = 3 (セントロイド 3 レベル + リーフレベル) を指定。

2️⃣ 自動インデックスメンテナンス GA

4LT ScaNN インデックスで auto_maintenance オプションが利用可能。データセットの増加に応じて AlloyDB がセントロイドを分析・更新し、大きな外れ値パーティションを分割。QPS と検索結果品質を自動的に改善。

3️⃣ ストリーミング機能 (scann.satisfy_limit = relaxed_order) GA

有効化すると、LIMIT 句を満たす十分な結果が見つかるまでベクトルスキャンが追加のリーフパーティションを探索し続け、 フィルタ条件付き検索のリコールが向上。scann.enable_parallel_satisfy_limit フラグを on にすると並列プロセススキャンにも適用可能。

4️⃣ Vector assist GA

ベクトル検索ワークロードのデプロイと管理のための宣言的 SQL フレームワーク。対象テーブル・テキストカラム・ 目標リコールなどの要件 (vector spec) を vector_assist.define_spec で宣言すると、 自動チューニングアルゴリズムが最適化された SQL 推奨 (説明付き) を生成。埋め込み生成、クエリ最適化、 HNSW などのインデックス作成を含む本番品質のセットアップを支援。

5️⃣ num_leaves 上限の引き上げ

PostgreSQL 17 以降の AlloyDB インスタンスで、ScaNN インデックス構築時の num_leaves 最大サポート値が 30,000,000 → 104,857,600 に増加 (約 3.5 倍)。

6️⃣ external_search_fdw 拡張 GA

外部検索クラスタに接続し、データベースから直接そのデータをクエリ可能。 対応する検索ソース: Elasticsearch / Solr / OpenSearch。

7️⃣ rum 拡張 GA

PostgreSQL 17 以前で高性能な全文検索操作をサポート。標準の GIN インデックスを拡張し、 位置情報をインデックスに直接保存することで、テーブルデータにアクセスせずに高速な フレーズ検索と関連度ランキングを実行可能。

8️⃣ 4LT インデックス構築時のメモリ見積もり改善 Preview

ScaNN 4 レベルツリーインデックス構築時のメモリ使用量見積もりがより正確になり、OOM エラーを防止。 メモリ制限の適用と制約条件下でのメモリ見積もり改善により、インデックス構築の安定性が向上。

⚙️ 主要パラメータ

項目詳細

⚠️ Vector assist の制限事項:
  • PostgreSQL 17 以降のみサポート
  • インデックスタイプは HNSW と IVFFlat のみサポート (ScaNN インデックスタイプは非サポート)
  • 埋め込み自動生成はテキスト埋め込みモデルのみサポート (マルチモーダル埋め込みが必要な場合は google_ml_integration 拡張などで事前に生成)

🛠️ 設定方法

💡 前提条件:
  • PostgreSQL 17 以降の AlloyDB インスタンス (4LT ScaNN / Vector assist / num_leaves 上限拡大の場合)
  • OOM 回避のため maintenance_work_mem と shared_buffers をマシンメモリ合計より小さい値に設定
  • rum 拡張の作成には alloydbsuperuser データベースロールが必要

ステップ 1: 4 レベルツリー ScaNN インデックスの作成

SQL 4LT ScaNN インデックス作成 
CREATE EXTENSION IF NOT EXISTS alloydb_scann;

CREATE INDEX my_scann_index ON my_table
USING scann (embedding_column cosine)
WITH (
  mode = 'MANUAL',
  num_leaves = NUM_LEAVES_VALUE,  -- 例: power(行数, 3/4) を起点に調整
  quantizer = 'SQ8',
  auto_maintenance = ON,           -- 自動インデックスメンテナンスを有効化
  max_num_levels = 3               -- 4 レベルツリー
);

max_num_levels = 3 により 4 レベルツリーインデックスが作成されます。auto_maintenance = ON で自動メンテナンスが有効になります。

ステップ 2: ストリーミング機能の有効化

SQL ストリーミング検索の有効化 
-- セッション単位でストリーミング機能を有効化
SET scann.satisfy_limit = relaxed_order;

-- 並列プロセススキャンにも適用する場合はデータベースフラグを設定
-- scann.enable_parallel_satisfy_limit = on

フィルタ条件付きベクトル検索で、LIMIT 句を満たすまで追加のリーフパーティションを探索するようになります。

ステップ 3: rum 拡張による全文検索インデックスの作成 (任意)

SQL rum インデックス作成 
CREATE EXTENSION IF NOT EXISTS rum;

ALTER TABLE documents ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (to_tsvector('english', content)) STORED;

CREATE INDEX idx_docs_rum ON documents
USING rum (search_vector rum_tsvector_ops);

位置情報がインデックスに保存されるため、テーブルアクセスなしで高速なフレーズ検索・関連度ランキングが可能です。

🔧 技術面

✅リコールの改善: relaxed_order ストリーミングにより、フィルタ付き検索でも LIMIT を満たすまで探索が継続され、検索品質が向上
✅スケーラビリティの向上: num_leaves 上限が約 3.5 倍 (30,000,000 → 104,857,600) に拡大し、超大規模データセットでより細かいパーティション分割が可能

⚠️ デメリット・制約事項

🚧 制限事項

❌4LT ScaNN インデックス、Vector assist、num_leaves 上限拡大 (104,857,600) は PostgreSQL 17 以降が必要 (PG16 以前の上限は 30,000,000)
❌Vector assist は HNSW / IVFFlat インデックスのみ対応し、ScaNN インデックスタイプは非サポート
❌Vector assist の埋め込み自動生成はテキスト埋め込みモデルのみ対応
❌rum 拡張は PostgreSQL 17 以前でのサポートと Release Notes に記載
❌4LT インデックス構築時のメモリ見積もり改善は Preview であり、Pre-GA 利用規約が適用される

🤔 考慮すべき点

  • ScaNN インデックスの auto_maintenance はデフォルト OFF。自動メンテナンスを利用する場合は明示的な有効化が必要
  • scann.satisfy_limit = relaxed_order は追加のリーフパーティションを探索するため、リコールと引き換えに探索コストが増加する可能性がある。チューニングのベストプラクティスを確認のうえ設定すること
  • インデックス構築前に maintenance_work_mem / shared_buffers の適切な設定が引き続き推奨される
  • 行数に応じたツリーレベルと num_leaves の選択 (4 レベルの場合は power(行数, 3/4) が起点) がリコールと構築時間のバランスに影響する

🎯 ユースケース

💡 ユースケース 1: 100 億ベクトル規模のエンタープライズ RAG 基盤

シナリオ: 全社のドキュメント・ナレッジを埋め込みベクトル化して保存し、生成 AI アプリケーションから 低レイテンシで類似検索したい。データ量は数十億〜100 億ベクトル行に達する。

SQL 実装例 
CREATE INDEX kb_scann_idx ON knowledge_base
USING scann (embedding cosine)
WITH (mode='MANUAL', num_leaves = 5623413, -- power(1e10, 3/4) 起点で調整
      quantizer='SQ8', auto_maintenance=ON, max_num_levels=3);

SET scann.satisfy_limit = relaxed_order;
SELECT doc_id, title FROM knowledge_base
WHERE category = 'engineering'
ORDER BY embedding <=> $1 LIMIT 10;

効果: 100 億行規模でも GA 品質のベクトル検索が可能になり、フィルタ条件付きでもストリーミング機能により LIMIT を満たす結果を取得できる。自動メンテナンスによりデータ増加後も検索品質が維持される。

🔌 ユースケース 2: 既存 Elasticsearch 資産とのフェデレーション検索

シナリオ: ログ・商品カタログを Elasticsearch で運用しているが、トランザクションデータは AlloyDB にある。 両者を結合した検索をデータコピーなしで実行したい。

効果: external_search_fdw により Elasticsearch のインデックスを外部テーブルとして SQL から直接クエリでき、AlloyDB のリレーショナルデータと組み合わせた検索がデータ移動なしに実現できる。

🤖 ユースケース 3: Vector assist による検索アプリの迅速なプロトタイピング

シナリオ: セマンティック検索機能を新規アプリに追加したいが、埋め込みモデル選定や インデックスチューニングの知見が少ない。

効果: vector spec (対象テーブル、テキストカラム、目標リコールなど) を SQL で宣言するだけで、 埋め込み生成・インデックス作成・クエリ最適化の推奨 SQL が説明付きで生成され、レビュー・修正しながら 本番品質のセットアップを短期間で構築できる。
