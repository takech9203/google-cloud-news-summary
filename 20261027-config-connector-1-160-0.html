📝 概要

Config Connector は Kubernetes のアドオン (オープンソース) であり、CRD とコントローラを通じて Google Cloud リソースを宣言的に管理できる。 バージョン 1.160.0 では、Direct Reconciler を使用する 21 種類の新しい Alpha リソースが追加され、 Kafka Connect クラスタ、NetApp Volumes、Migration Center、Knowledge Catalog、Agent Search、Service Extensions、Workload Manager などを Kubernetes マニフェストで管理できるようになった。

運用面でも 2 つの重要な機能強化が含まれる。

✓cnrm.cloud.google.com/backoff-max-delay-in-seconds アノテーションで、Direct コントローラの指数バックオフの最大遅延上限とリトライ停止をリソース単位で設定可能に
✓cnrm.cloud.google.com/actuation-mode: Paused の個別リソースで削除操作も停止 (halt) されるようになり、誤削除リスクを低減
✓ComputeNetworkFirewallPolicy や SQLSSLCert など 6 リソースにオプトイン方式の直接 reconciliation サポートを追加
✓AlloyDBCluster の誤検知差分、ComputeRouterNAT の動作不一致など 6 件のバグ修正

GitOps で Google Cloud インフラを管理するプラットフォームチームが主な対象。

❌ Before (アップデート前の課題)

  • Kafka Connect クラスタ、NetApp Volumes の AD 構成、Migration Center、Agent Search のスキーマなどは Config Connector 未対応で、gcloud CLI や Terraform など Kubernetes 外のツールで個別管理が必要
  • Direct コントローラのエラー時バックオフは最大 2 分の固定上限で、リソース単位の調整やリトライ停止ができず、API クォータ消費を制御しにくい
  • actuation-mode: Paused でも削除操作は停止対象外で、Kubernetes オブジェクトの削除が Google Cloud リソースの削除につながる可能性
  • AlloyDBCluster の誤検知差分、ArtifactRegistryRepository の移行差分などが発生

✅ After (アップデート後の改善)

  • 21 種類の新 Alpha リソースで Kafka Connect、NetApp Volumes、Migration Center、Knowledge Catalog、Agent Search などを Kubernetes マニフェストで宣言的に管理
  • backoff-max-delay-in-seconds でバックオフ上限設定・リトライ停止がリソース単位で可能に
  • actuation-mode: Paused のリソースは削除操作も停止され、意図しない削除を防止
  • 6 リソースで API 変更なしのオプトイン直接 reconciliation が利用可能に
  • 動作不一致・誤検知差分の修正で Direct コントローラ移行の安全性が向上

🔧 運用

ConfigDeploymentGroup (Infrastructure Manager)、SaaSServiceMgmtUnit (App Lifecycle Manager)、WorkloadManagerEvaluation (Workload Manager)

2️⃣ 新規フィールド

  • BigtableTable: spec.columnFamily[].type をサポート (カラムファミリーの値型を指定可能に)
  • MemorystoreInstance: spec.gcsSource をサポート (Cloud Storage からのデータインポート構成)
  • MonitoringDashboard: ウィジェットの timeSeriesQuery.opsAnalyticsQuery をサポート (ログ分析クエリをダッシュボードに表示)

3️⃣ バックオフとリトライの制御

  • cnrm.cloud.google.com/backoff-max-delay-in-seconds アノテーションで、Direct コントローラの指数バックオフの最大遅延上限を設定可能
  • 同アノテーションによるリトライの停止 (retry halting) もサポート

4️⃣ Paused リソースの削除停止

  • cnrm.cloud.google.com/actuation-mode: Paused が設定された個別リソースでは削除操作も停止するよう resource actuation を更新
  • リソース単位の actuation 一時停止 (1.158.0 で導入) の保護範囲が削除操作にまで拡大

5️⃣ Reconciliation の改善 (オプトインの直接 reconciliation)

  • ComputeNetworkFirewallPolicy、ComputeProjectMetadata、FirebaseHostingSite、NetworkServicesEdgeCacheService、OSLoginSSHPublicKey、SQLSSLCert の 6 リソースに直接 reconciliation サポートを追加
  • API は変更なし。alpha.cnrm.cloud.google.com/reconciler: direct アノテーションの付与でオプトイン利用

⚙️ 技術仕様

🏷️ 1.160.0 で追加・強化されたアノテーション

アノテーション対象動作
cnrm.cloud.google.com/backoff-max-delay-in-seconds Direct コントローラのリソース 指数バックオフの最大遅延上限を秒単位で設定。リトライの停止 (halting) も可能。従来はエラー時のバックオフ上限が最大 2 分の固定だった
cnrm.cloud.google.com/actuation-mode: Paused 個別リソース 作成・更新に加えて、1.160.0 からは削除操作も停止。リソース単位の actuation 一時停止は 1.158.0 で導入
alpha.cnrm.cloud.google.com/reconciler: direct 直接 reconciliation 対応リソース Terraform / DCL ベースのコントローラから Direct コントローラへオプトインで切り替え。API は不変

🔄 Direct Reconciler (Direct コントローラ) の特徴

新規リソースはすべて Direct コントローラで実装されている。

項目詳細
実装Kubernetes controller-runtime + Google Cloud Go SDK による直接 API 呼び出し
リソース消費Terraform / DCL の変換オーバーヘッドがなく CPU・メモリ消費を削減
レイテンシGoogle Cloud エンドポイントへの直接操作により reconciliation の収束が高速
可観測性cnrm-controller-manager ログに構造化された差分 (structured diff) を出力
状態参照status.observedState に Google Cloud API が返すサーバー側の状態を反映
💡 ポイント: すべての Config Connector リソースは Kubernetes API グループ cnrm.cloud.google.com に属する。

🛠️ 設定方法

📋 前提条件

✓Config Connector がクラスタにインストールされていること (バージョン 1.160.0 へのアップグレードが必要)
✓Config Connector の IAM サービスアカウントに、管理対象リソース (Kafka、NetApp Volumes、Migration Center など) を操作する権限が付与されていること
✓Alpha リソースを使用する場合は、Alpha ステータスであることを理解した上で検証環境から利用すること

ステップ 1: 新しい CRD の確認

Bash Config Connector が管理する CRD の一覧を確認 
# Config Connector が管理する CRD の一覧を確認
kubectl get crds --selector cnrm.cloud.google.com/managed-by-kcc=true

アップグレード後、ManagedKafkaConnectCluster などの新しいリソースタイプが CRD として登録されていることを確認する。

ステップ 2: バックオフ制御・actuation 一時停止アノテーションの設定

YAML アノテーションの設定例 (SQLInstance) 
apiVersion: sql.cnrm.cloud.google.com/v1beta1
kind: SQLInstance
metadata:
  name: my-instance
  annotations:
    # 指数バックオフの最大遅延上限を 600 秒に設定
    cnrm.cloud.google.com/backoff-max-delay-in-seconds: "600"
    # メンテナンス中は actuation (作成・更新・削除) を一時停止
    cnrm.cloud.google.com/actuation-mode: Paused
spec:
  # ...
💡 ヒント: actuation-mode: Paused を設定している間は、Kubernetes オブジェクトを削除しても Google Cloud 側の削除操作が停止される。作業完了後にアノテーションを削除または変更して actuation を再開する。

ステップ 3: 直接 reconciliation のオプトイン (任意)

YAML 直接 reconciliation のオプトイン例 
apiVersion: compute.cnrm.cloud.google.com/v1beta1
kind: ComputeNetworkFirewallPolicy
metadata:
  name: my-firewall-policy
  annotations:
    alpha.cnrm.cloud.google.com/reconciler: direct
spec:
  # ... (API は変更なし)

リソースの status.condition が Ready: True になれば、Google Cloud 側のリソースが作成・同期されている。 各リソースの具体的なフィールド定義は、対応する CRD (kubectl describe crd) または リソースリファレンスで確認できる。

✨ メリット

💼 ビジネス面

✓管理対象の大幅な拡大: 21 種類の新リソースにより、データ基盤 (Knowledge Catalog)、移行 (Migration Center)、AI エージェント (Agent Search、Dialogflow)、ストレージ (NetApp Volumes) まで GitOps での一元管理の範囲が広がり、ツールの分断による運用コストを削減
✓誤削除リスクの低減: actuation-mode: Paused が削除操作にも適用されるため、GitOps パイプラインの誤操作やマニフェストの誤削除が本番リソースの削除につながるリスクを抑制

🔧 技術面

✓リトライ動作の制御性向上: backoff-max-delay-in-seconds によりリソース単位でバックオフ上限とリトライ停止を調整でき、API クォータの消費やエラー時の負荷を細かく制御
✓Direct コントローラ移行の安全性向上: ArtifactRegistryRepository の移行差分や ComputeRouterNAT の動作不一致の修正により、移行時の予期しない差分・動作変化が減少
✓ドリフト誤検知の解消: AlloyDBCluster や MemorystoreInstance の誤検知差分・ドリフト修正により、不要な reconciliation や差分アラートが減り運用ノイズが低減

⚠️ デメリット・制約事項

🚧 制限事項

✗新規追加された 21 リソースはいずれも Alpha ステータスであり、API が変更される可能性があるため本番環境での利用は慎重に判断する必要がある
✗既存リソースの直接 reconciliation (alpha.cnrm.cloud.google.com/reconciler: direct) はオプトインかつ alpha アノテーションであり、挙動の検証を経てから適用することが推奨される

🤔 考慮すべき点

⚠️actuation-mode: Paused 中は Google Cloud 側の実リソースと Kubernetes マニフェストの状態が乖離し得るため、一時停止の運用ルール (期間、解除手順) を定めておく必要がある
⚠️backoff-max-delay-in-seconds でリトライを停止 (halt) した場合、エラーが自動回復しなくなるため、監視 (Events、cnrm-controller-manager ログ) と組み合わせて利用すべき
⚠️Reconciliation は Config Connector の IAM サービスアカウントの権限で実行されるため、新しいリソースタイプを利用する際は対応する権限の付与が必要

🎯 ユースケース

📨 ユースケース 1: Kafka Connect クラスタの GitOps 管理

シナリオ: データプラットフォームチームが、Managed Service for Apache Kafka の Connect クラスタ (BigQuery や外部システムとの連携コネクタの実行基盤) を、Kafka クラスタやアプリケーションと同じ Git リポジトリ・Kubernetes マニフェストで管理したい。ManagedKafkaConnectCluster リソースを Kubernetes マニフェストとして定義し、Config Sync などで Git リポジトリから自動適用する (フィールド定義は kubectl describe crd で確認)。

効果: Kafka 本体と Connect クラスタの構成が Git で一元管理され、環境間の一貫性確保と変更履歴の追跡が容易になる。

🛑 ユースケース 2: メンテナンス時の削除保護

シナリオ: 本番の Cloud SQL インスタンスや AlloyDB クラスタに対する調査・メンテナンス中に、GitOps パイプラインからの意図しない変更や削除を確実に防ぎたい。

効果: 対象リソースに cnrm.cloud.google.com/actuation-mode: Paused を付与するだけで、作成・更新に加えて削除操作も停止されるため、メンテナンスウィンドウ中の安全性が向上する。

⏱️ ユースケース 3: API クォータに配慮したリトライ制御

シナリオ: 大量の Config Connector リソースを管理するクラスタで、一部リソースの継続的なエラーによるリトライが Google Cloud API のクォータを圧迫している。

効果: 該当リソースに backoff-max-delay-in-seconds を設定してバックオフ上限を引き上げる、またはリトライを停止することで、API 呼び出し頻度を制御しクォータ消費を抑制できる。

📌 まとめ

Config Connector 1.160.0 は、21 種類の新しい Alpha リソースによる管理対象の大幅な拡大に加え、 backoff-max-delay-in-seconds によるリトライ制御と actuation-mode: Paused 時の削除停止という、 運用の安全性・制御性を高める実用的な機能強化が中心のリリースである。

GitOps で Google Cloud インフラを管理しているチームは、削除保護とバックオフ制御のアノテーションを運用手順に組み込みつつ、 Direct コントローラ関連のバグ修正 (AlloyDBCluster、ComputeRouterNAT、ArtifactRegistryRepository など) の恩恵を受けるためにアップグレードを計画することを推奨する。
