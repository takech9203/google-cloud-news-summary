🔐 Cloud Build: Secret Manager 権限チェック強化

Security Update Cloud Build GCP-2026-042
2026-06-24

📋 概要

Cloud Build は、GitLab Enterprise Edition (GLE) および Bitbucket Data Center (BBDC) へのリポジトリ接続時に Secret Manager シークレットを使用して認証を行います。今回のセキュリティアップデートにより、接続の作成・更新時に呼び出し元プリンシパルの secretmanager.versions.access 権限も検証されるようになりました。

💡 背景: 従来の実装では、権限のないユーザーがリポジトリ接続のホスト URI を攻撃者制御エンドポイントに向けることで、参照先の Secret Manager シークレットを読み取れる脆弱性が存在していました。

🔄 Before / After 比較

❌ 改善前

  • P4SA (サービスエージェント) の認証情報のみでチェック
  • 呼び出し元ユーザーのシークレットアクセス権限は未検証
  • ホスト URI 変更による不正読み取りが可能

✅ 改善後

  • 呼び出し元プリンシパル + P4SA の両方で権限チェック
  • シークレットアクセス権限のないユーザーは接続不可
  • 最小権限の原則に準拠

⚡ 主要機能

1. デュアル権限チェック (Dual Authorization Check)

→呼び出し元プリンシパルの資格情報 (end-user credentials) で権限を検証
→P4SA (service-PROJECT_NUMBER@gcp-sa-cloudbuild.iam.gserviceaccount.com) の権限も従来通り検証
→両方が secretmanager.versions.access を持つ場合のみアクセス許可

2. 対象範囲の限定

✓GitLab Enterprise Edition (GLE) 接続
✓Bitbucket Data Center (BBDC) 接続
✗GitHub 接続 (対象外)
✗GitLab.com 接続 (対象外)
→既存接続は影響なし、作成・更新操作時のみチェック実行

3. 脆弱性の修正 (GCP-2026-042)

→ホスト URI を攻撃者制御エンドポイントに変更することによるシークレット読み取り攻撃を防止
→重要度: Low

📝 設定方法

⚠️ 前提条件: Cloud Build API と Secret Manager API が有効化されていること。接続を作成・更新するユーザーに roles/cloudbuild.connectionAdmin が付与されていること。

ステップ 1: 呼び出し元ユーザーにシークレットアクセス権限を付与

Bash 
# 特定のシークレットに対してユーザーに Secret Accessor ロールを付与
gcloud secrets add-iam-policy-binding SECRET_NAME \
  --member="user:USER_EMAIL" \
  --role="roles/secretmanager.secretAccessor" \
  --project="PROJECT_ID"

ステップ 2: P4SA にシークレットアクセス権限を確認

Bash 
# P4SA に Secret Accessor ロールが付与されていることを確認
gcloud secrets get-iam-policy SECRET_NAME \
  --project="PROJECT_ID" \
  --format="table(bindings.role,bindings.members)"

# 付与されていない場合は追加
gcloud secrets add-iam-policy-binding SECRET_NAME \
  --member="serviceAccount:service-PROJECT_NUMBER@gcp-sa-cloudbuild.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor" \
  --project="PROJECT_ID"

ステップ 3: Terraform 設定例 (GitLab Enterprise Edition)

HCL 
# 呼び出し元ユーザーにもシークレットへのアクセス権限を付与
resource "google_secret_manager_secret_iam_member" "user-access-api-pat" {
  project   = google_secret_manager_secret.api-pat-secret.project
  secret_id = google_secret_manager_secret.api-pat-secret.secret_id
  role      = "roles/secretmanager.secretAccessor"
  member    = "user:admin@example.com"
}

resource "google_secret_manager_secret_iam_member" "user-access-read-pat" {
  project   = google_secret_manager_secret.read-pat-secret.project
  secret_id = google_secret_manager_secret.read-pat-secret.secret_id
  role      = "roles/secretmanager.secretAccessor"
  member    = "user:admin@example.com"
}

# P4SA にも従来通り権限を付与
data "google_iam_policy" "serviceagent-secretAccessor" {
  binding {
    role    = "roles/secretmanager.secretAccessor"
    members = [
      "serviceAccount:service-PROJECT_NUMBER@gcp-sa-cloudbuild.iam.gserviceaccount.com",
      "user:admin@example.com"
    ]
  }
}

✅ メリット

ビジネス面

✓コンプライアンス強化: 最小権限の原則を徹底し、SOC 2 / ISO 27001 などの監査要件への適合が容易に
✓インシデントリスク低減: シークレット不正アクセス経路を排除、情報漏洩リスク軽減

技術面

✓デュアル認証によるセキュリティ多層化: P4SA のみへの依存から多層的な権限検証へ移行
✓監査証跡の明確化: Cloud Audit Logs でユーザー単位のシークレットアクセス試行を追跡可能
✓既存接続への影響なし: 既存の接続は引き続き動作、新規作成・更新時のみ新チェック適用

⚠️ デメリット・制約事項

制限事項

!GitLab Enterprise Edition (GLE) と Bitbucket Data Center (BBDC) の接続のみが対象
!既存接続の更新時、呼び出し元ユーザーがシークレットアクセス権限を持っていないと操作失敗
⚠️ 考慮すべき点:
  • 接続管理ユーザーやサービスアカウントに roles/secretmanager.secretAccessor の追加付与が必要な場合がある
  • CI/CD パイプラインで接続を自動更新している場合、実行サービスアカウントにもシークレットアクセス権限が必要
  • 組織内の IAM ポリシーを確認し、接続管理者の権限設定を見直す必要がある

💼 ユースケース

📦 ユースケース 1: GitLab Enterprise Edition 接続の新規作成

シナリオ: DevOps チームが社内 GitLab Enterprise Edition を Cloud Build に接続して CI/CD パイプラインを構築

Bash 
# 1. シークレットを作成
echo -n "glpat-xxxxxxxxxxxx" | gcloud secrets create gitlab-api-token \
  --data-file=- --project=my-project

# 2. P4SA に権限を付与
gcloud secrets add-iam-policy-binding gitlab-api-token \
  --member="serviceAccount:service-123456789@gcp-sa-cloudbuild.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor" \
  --project=my-project

# 3. 呼び出し元ユーザーにも権限を付与 (新規要件)
gcloud secrets add-iam-policy-binding gitlab-api-token \
  --member="user:devops-admin@example.com" \
  --role="roles/secretmanager.secretAccessor" \
  --project=my-project

# 4. 接続を作成
gcloud builds connections create gitlab my-gle-connection \
  --region=us-central1 \
  --host-uri="https://gitlab.internal.example.com" \
  --authorizer-token-secret-version="projects/my-project/secrets/gitlab-api-token/versions/latest" \
  --read-authorizer-token-secret-version="projects/my-project/secrets/gitlab-read-token/versions/latest" \
  --webhook-secret-secret-version="projects/my-project/secrets/webhook-secret/versions/latest"

効果: 呼び出し元ユーザーと P4SA の両方がシークレットアクセス権限を持つことが検証され、不正なシークレット読み取りを防止

🛠️ ユースケース 2: 既存接続の更新時のエラー対応

シナリオ: セキュリティアップデート後に接続の更新時に権限エラーが発生した場合の対処

エラーメッセージ:
ERROR: Permission denied. The caller does not have secretmanager.versions.access on the referenced secret(s).
Bash 
# 対処: 呼び出し元ユーザーにシークレットアクセス権限を付与
gcloud secrets add-iam-policy-binding SECRET_NAME \
  --member="user:USER_EMAIL" \
  --role="roles/secretmanager.secretAccessor" \
  --project=PROJECT_ID

効果: 最小限の権限付与で接続の更新操作を再実行可能
