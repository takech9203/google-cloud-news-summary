📅 リリース日: 2026-11-11 | 機能: 不正利用モニタリング向けエンドユーザー safety_identifier リクエストラベル

📝 概要

Gemini の generateContent / streamGenerateContent と Veo の predictLongRunning API 呼び出しで、 リクエストボディの labels フィールドに 匿名化されたユーザーごとの ID (safety_identifier) を渡せる機能が GA になりました。

Google は生成 AI トラフィックを AUP (利用規約) / Prohibited Use Policy の違反検出のためにモニタリングしています。 safety_identifier を付与すると、ポリシー違反を特定のエンドユーザーに帰属 (attribution) させることができ、 Google Cloud プロジェクト全体への強制措置 (enforcement action) の回避に役立ちます。 API リセラー、モデルアグリゲーター、外部ユーザーを抱えるマルチテナントアプリが主な対象です。

❌ Before: アップデート前の課題

  • ポリシー違反の検出・強制措置はプロジェクト単位で扱われ、違反したエンドユーザーを Google に伝える標準手段がなかった
  • マルチテナントアプリや API リセラーでは、一部ユーザーの悪用がプロジェクト全体の利用制限・停止につながるリスク
  • 悪質ユーザーの特定・対処をアプリ側で独自に行う必要があった

✅ After: アップデート後の改善

  • labels の safety_identifier キーで匿名 ID を渡すことが GA サポートされ、違反を個々のユーザーに帰属可能に
  • ターゲットを絞った帰属により、プロジェクト全体への強制措置を防ぐことに役立つ
  • Gemini (グローバル / マルチリージョン / リージョナル) と Veo (リージョナル) の両方で本番利用が可能に
💡 ポイント: 一部の悪質なエンドユーザーの行為でプロジェクト全体、ひいてはサービス全体が停止されるリスクを軽減できるため、 生成 AI を組み込んだ SaaS やコンシューマー向けアプリを運用する事業者にとって重要なアップデートです。

🐍 リクエスト例 (Python / Google Gen AI SDK)

Python GenerateContentConfig で labels を指定 
from google import genai
from google.genai import types

client = genai.Client(
    vertexai=True,
    project="PROJECT_ID",
    location="global",
)

response = client.models.generate_content(
    model="gemini-3.5-flash",
    contents="Summarize the key responsibilities of an API gateway.",
    config=types.GenerateContentConfig(
        labels={"safety_identifier": "user_session_001"},
    ),
)
print(response.text)

🛠️ 設定方法

✅ 前提条件

✓Gemini Enterprise Agent Platform で Gemini または Veo の API を利用していること
✓呼び出し元に aiplatform.endpoints.predict 権限があること (通常の推論権限のみで可)
✓エンドユーザーごとに一意かつ匿名化された ID (PII を含まない) を生成する仕組みがあること
1

エンドユーザー ID の匿名化

Bash SHA-256 ハッシュ化 + 63 文字以下に切り詰め 
# 例: ユーザー ID を SHA-256 でハッシュ化し、小文字 16 進で 63 文字以下に切り詰める
echo -n "user@example.com" | sha256sum | cut -c1-63

メールアドレスなどの PII をそのまま使わず、匿名化したユーザー名またはハッシュの切り詰め値を使用します。

2

API リクエストに labels を付与

Bash curl で generateContent を呼び出し 
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d @request.json \
  "https://aiplatform.googleapis.com/v1/projects/PROJECT_ID/locations/global/publishers/google/models/gemini-3.5-flash:generateContent"

request.json の labels.safety_identifier に、ステップ 1 で生成した匿名 ID を設定します。ローカルテストではユーザー認証情報、本番ではサービスアカウントを接続した Application Default Credentials (ADC) を使用します。

✓ストリーミング・動画生成にも対応: streamGenerateContent や Veo の predictLongRunning もカバーし、主要な生成 AI ワークロードで一貫して利用可能
✓プライバシーに配慮した設計: PII を送らず匿名 ID やハッシュで帰属を行うため、ユーザープライバシーを守りながら不正対策ができる

⚠️ デメリット・制約事項

🚫 制限事項
✗値は 1〜63 文字で、小文字英字・数字・アンダースコア・ハイフンのみ。違反すると HTTP 400 INVALID_ARGUMENT でリクエスト自体が失敗する
✗対応 API は Gemini の generateContent / streamGenerateContent と Veo の predictLongRunning に限られる (Veo はリージョナルエンドポイントのみ)
✗1 ラベルキーに Cloud Billing アカウントあたり 1,000 超のユニーク値が紐付くと、コストレポートからそのキーが除外される場合がある (不正利用の帰属には影響なし)
🤔 考慮すべき点
  • safety_identifier に PII (メールアドレス、氏名など) を含めてはならない。ID 設計の段階で匿名化・ハッシュ化の方針を決めておく
  • ユーザー数が多いサービスでは、ラベルは Cloud Billing のコスト分析用途 (1,000 ユニーク値上限) とは特性が異なる点を理解して運用する
  • 不正利用モニタリング自体の仕組み (自動分類器による検出、疑わしい場合のプロンプトログ保存と人手レビュー) は Google Cloud Platform 利用規約に基づくため、対象範囲を利用規約で確認しておく

📝 ユースケース 1: 生成 AI SaaS でのテナント保護

シナリオ: Gemini を組み込んだ文章生成 SaaS を数万ユーザーに提供。ごく一部のユーザーが Prohibited Use Policy に違反するプロンプトを繰り返し送信しており、プロジェクト全体への強制措置が懸念される。

Python 実装例 
config = types.GenerateContentConfig(
    labels={"safety_identifier": tenant_user.anonymized_id},  # 例: "tenant42-u-9f3a..."

効果: 違反行為が特定のエンドユーザーに帰属されるため、プロジェクト全体ではなく問題のあるユーザーに対象を絞った対応が可能になり、他の健全なユーザーへのサービス提供を継続できる。

🔁 ユースケース 2: API リセラー / モデルアグリゲーターの不正対策

シナリオ: 複数の顧客アプリに対して Gemini / Veo API を再販しており、どの顧客のどのユーザーが問題行動をしているかを Google 側と連携して切り分けたい。

効果: safety_identifier により違反の発生源がユーザー単位で特定され、ポリシーフィードバックがプロジェクト全体ではなく該当ユーザーに向くため、リセラー事業全体の停止リスクを抑えつつ該当ユーザーのみを自社側で措置できる。

🔗 関連サービス・機能

🏷️ API 呼び出しへのラベル付与 (request body labels)

safety_identifier は汎用のリクエストボディラベルの仕組みの上に実装されており、コストセンターや環境名などのラベルと同じ labels フィールドで併用可能 (Google モデルは 1 回の呼び出しで最大 64 ラベル)。

📊 Cloud Billing レポート / 課金データエクスポート

リクエストボディラベルは Cloud Billing にも転送され、ラベル単位でのコスト分析に利用できる。

📋 推論リクエストメタデータログ (Cloud Logging)

ラベルはログエントリの labels フィールドに記録され、Logs Explorer でユーザー単位の利用状況をクエリできる。

🛡️ 不正利用モニタリング (Abuse Monitoring)

Google の自動安全分類器と (必要時の) 人手レビューによる AUP / Prohibited Use Policy 違反検出の仕組み。本機能はこのモニタリングに対するユーザー単位の帰属情報を提供する。

🎁 まとめ

エンドユーザー safety_identifier リクエストラベルの GA により、マルチテナントアプリや API リセラーは、 匿名化されたユーザー ID を 1 行追加するだけでポリシー違反の帰属をユーザー単位に絞り込み、 プロジェクト全体への強制措置リスクを大きく低減できます。

外部ユーザー向けに Gemini / Veo を提供しているサービスでは、PII を含まない ID 設計 (匿名ユーザー名や SHA-256 ハッシュの切り詰め) を定めた上で、 すべての推論リクエストへの safety_identifier 付与を標準実装とすることを推奨します。
