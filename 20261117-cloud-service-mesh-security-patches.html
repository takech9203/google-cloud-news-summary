1.31.3-asm.13 / 1.30.7-asm.13 / 1.29.10-asm.8 — xDS 接続問題の修正 + CVE 対応
📅 リリース日: 2026-11-17

📝 概要

in-cluster Cloud Service Mesh のサポート対象 3 系統すべてに新しいパッチリリースが公開されました。今回のパッチには、直前のパッチで混入した xDS 設定ストリーム切断問題の修正と、プラットフォーム CVE (CVE-2026-118131 / CVE-2026-128085) の修正という 2 つの重要な修正が含まれています。

❌ アップデート前の課題

  • 直前のパッチで pilot-agent の gRPC HTTP/2 フロー制御エラーにより istiod からの xDS 設定ストリームが切断されることがあった
  • xDS ストリーム切断により、サイドカープロキシが設定を受信できずプロキシ Pod が Ready にならない (デプロイ・再起動・スケールアウトが停滞)
  • コントロールプレーン / CNI / プロキシに CVE-2026-118131、CVE-2026-128085 が未修正のまま残存

✅ アップデート後の改善

  • 3 系統すべてで gRPC HTTP/2 フロー制御エラーが修正され、xDS 設定ストリームが安定して維持されるように
  • プロキシ Pod が正常に Ready 状態へ遷移し、デプロイ・スケーリングのブロッキング要因が解消
  • CVE 修正が各コンポーネントイメージ (Control Plane / Proxy / Distroless / CNI) に適用
⚠️ 早期アップグレード推奨: 直前のパッチ (1.31.3-asm.9 / 1.30.7-asm.9 / 1.29.10-asm.4 系) を適用済みの環境では、Pod の起動不良が発生するリスクがあります。in-cluster Cloud Service Mesh を運用しているプラットフォームチーム・SRE は、本パッチへの早期アップグレードを推奨します。

ステップ 1: asmcli でコントロールプレーンをアップグレード

Bash asmcli によるアップグレード 
./asmcli install \
  --project_id PROJECT_ID \
  --cluster_name CLUSTER_NAME \
  --cluster_location CLUSTER_LOCATION \
  --fleet_id FLEET_PROJECT_ID \
  --output_dir DIR_PATH \
  --enable_all \
  --ca mesh_ca

公式の Upgrade Cloud Service Mesh の手順に従い、新しいパッチバージョンのコントロールプレーンをインストールします。--output_dir を指定すると istioctl やサンプルマニフェストの場所を把握しやすくなります。

ステップ 2: ワークロードを再デプロイしてプロキシを更新

Bash データプレーンの更新と確認 
# 新しいリビジョンにネームスペースを切り替えてワークロードを再起動
kubectl rollout restart deployment -n NAMESPACE

# プロキシ Pod が Ready になることを確認
kubectl get pods -n NAMESPACE

データプレーン (サイドカープロキシ) に修正を反映するには、ワークロードの再デプロイが必要です。再起動後、プロキシ Pod が正常に Ready 状態へ遷移することを確認します。

⚖️ メリット・デメリット

👍 メリット

  • セキュリティリスクの低減 (ビジネス面): コントロールプレーン・プロキシ・CNI の CVE が修正され、コンプライアンス要件への対応が容易に
  • サービス可用性の回復 (ビジネス面): Pod が Ready にならない不具合が解消され、デプロイ・スケールアウト停滞による障害リスクを排除
  • xDS ストリームの安定化 (技術面): pilot-agent の gRPC HTTP/2 フロー制御エラー修正で設定配信の信頼性が向上
  • 全系統での同時提供 (技術面): 1.29.x〜1.31.x のどの系統でも、系統内のパッチ適用のみで修正を取り込める (メジャー/マイナーアップグレード不要)

👀 制限事項・考慮すべき点

  • データプレーンへの修正反映にはワークロードの再起動 (プロキシの再注入) が必要
  • GKE 上での ISTIOD コントロールプレーンを使用した in-cluster Cloud Service Mesh は非推奨 (deprecated)。Google Distributed Cloud (ソフトウェアのみ) は引き続きサポート対象。GKE 利用者はマネージド Cloud Service Mesh への移行を検討
  • 直前のパッチ (asm.9 / asm.4 系) 適用済み環境は xDS 切断問題の影響を受ける可能性があるため優先的なアップグレードを推奨
  • CVE の影響コンポーネントは系統ごとに異なるため、リリースノートの表で自環境の確認が必要
  • アップグレード時に CA を変更するとダウンタイムが発生するため、既存と同じ CA 設定を維持すること

🎯 ユースケース

🚑 ユースケース 1: Pod 起動不良が発生している環境の復旧

シナリオ: 直前のパッチを適用後、新規デプロイした Pod のサイドカープロキシが Ready にならず、ローリングアップデートが途中で停止している。

Bash アップグレード後のワークロード再起動 
# 新パッチでコントロールプレーンをアップグレード後、対象ワークロードを再起動
kubectl rollout restart deployment my-app -n production
kubectl rollout status deployment my-app -n production

効果: pilot-agent の修正により xDS ストリームが安定し、プロキシ Pod が正常に Ready となってデプロイが完了する。

📋 ユースケース 2: 脆弱性管理ポリシーに基づく定期パッチ適用

シナリオ: セキュリティチームのポリシーで、メッシュコンポーネントの CVE は検出から一定期間内に修正適用が義務付けられている。

効果: 系統内のパッチ適用 (例: 1.30.7-asm.9 → 1.30.7-asm.13) のみで CVE-2026-118131 等への対応が完了し、互換性リスクを最小限に抑えながら脆弱性管理の SLA を満たせる。

🔗 関連サービス・機能

☸️ GKE (Google Kubernetes Engine)

Cloud Service Mesh が稼働する基盤。GKE 上の in-cluster ISTIOD コントロールプレーンは非推奨のため、マネージド Cloud Service Mesh への移行が推奨される。

🖥️ Google Distributed Cloud (ソフトウェアのみ)

in-cluster コントロールプレーンが引き続きサポートされるプラットフォーム。

📜 Certificate Authority Service / Mesh CA

メッシュ内 mTLS の証明書発行基盤。アップグレード時は既存の CA 設定を維持する必要がある。

🚢 GKE Enterprise / フリート

asmcli によるアップグレードではフリートへのクラスタ登録と Workload Identity の構成が前提となる。
