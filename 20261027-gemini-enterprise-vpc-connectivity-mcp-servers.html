Gemini Enterprise GA (一般提供) ネットワーキング

🔒 カスタム MCP サーバー向け
VPC 接続と静的 IP エグレス

📅 リリース日: 2026-10-27

📝 概要

Gemini Enterprise で、カスタム Model Context Protocol (MCP) サーバー データストア向けの VPC 接続が GA になりました。 Agent Gateway (us-central1 / europe-west1) を経由してアウトバウンドのツールトラフィックをルーティングすることで、 VPC ネットワーク内にプライベートにホストされた MCP サーバーへ安全にアクセスできます。

プライベート ホスティングには Private Service Connect (PSC) ネットワーク アタッチメントと エージェント接続テンプレートを使用。さらに、パブリック MCP サーバーに対しても Cloud NAT の静的外部 IP 経由でトラフィックをルーティングでき、 接続先の厳格な IP 許可リスト運用にも対応できます。

💡 こんな企業向け: 標準コネクタがない社内システムやレガシーシステムを MCP 経由で統合したい企業、 プライベート ネットワーク内のツールや IP 許可リストで保護された外部 SaaS / オンプレミスの MCP サーバーを利用したい企業。

❌ Before (アップデート前の課題)

  • Gemini Enterprise はプライベート ネットワーク内のリソースにアクセス不可
  • パブリック MCP サーバーへのアクセスは Google 管理ネットワーク経由のため送信元 IP が固定されず、IP ベースの許可リストを構成できない
  • オンプレミスやマルチクラウドの MCP サーバーをハイブリッド ネットワーク経由で安全に利用する手段がない

✅ After (アップデート後の改善)

  • PSC ネットワーク アタッチメント + 接続テンプレートで、パブリック IP を持たない VPC 内のプライベート MCP サーバーを利用可能
  • Cloud NAT の静的外部 IPv4 により送信元 IP を固定し、接続先での IP 許可リスト運用が可能
  • ハイブリッド ネットワーク経由でマルチクラウド / オンプレミスの MCP サーバーにも接続可能
  • カスタム TLS トラスト アンカー (tlsConfig) でプライベート CA / 自己署名証明書に対応

Gemini Enterprise のツール呼び出しトラフィックが Agent Gateway と PSC ネットワーク アタッチメント経由で顧客の VPC に注入され、 VPC 内のプライベート MCP サーバーへ直接、または Cloud NAT の静的 IP 経由でパブリック MCP サーバーへルーティングされる構成です。

⭐ 主要機能

🔒 1. プライベート ネットワーク ホスティング

  • パブリック IP を持たない VPC 内のプライベート MCP サーバーに Egress Agent Gateway 経由で接続可能
  • Agent Gateway が PSC ネットワーク アタッチメントを使用して VPC 内に Private Service Connect インターフェースをデプロイ
  • プライベート ドメイン名 (例: mcp.cymbal.internal) は Cloud DNS のプライベート DNS ピアリング (dnsPeeringConfig) で名前解決

🌐 2. パブリック MCP サーバー向け静的 IP エグレス

  • 接続テンプレートで vpcEgress を ALL_TRAFFIC に設定し、インターネット向けリクエストを VPC 経由でルーティング
  • サブネットに Cloud NAT を構成し、予約済み静的外部 IPv4 アドレスで送信元 IP を固定
  • 接続先 MCP サーバー側で IP ベースのファイアウォール許可リストを構成可能

📋 3. 宣言的な接続定義 (エージェント接続テンプレート)

  • ネットワーク アタッチメント、プライベート解決ドメイン、VPC 経由ルーティング対象を宣言的に定義
  • Egress Agent Gateway がテンプレートを参照してカスタム MCP サーバーに到達
  • オプションで Certificate Manager の TrustConfig を参照し、プライベート CA / 自己署名証明書の TLS 検証に対応

🔗 4. ハイブリッド / マルチクラウド接続

  • マルチクラウドやオンプレミス環境のプライベート MCP サーバーのアクションにハイブリッド ネットワーク経由で接続
  • VPC に注入されたトラフィックは VPC ルートテーブル (デフォルト インターネット ゲートウェイ ルート、ネクストホップ ファイアウォール アプライアンスなど) に従う

🔀 VPC エグレス モード

モード動作
PRIVATE_RANGES_ONLY プライベート IP 範囲 (RFC 1918、RFC 6598、クラス E、private/restricted.googleapis.com など) 宛てのみ VPC に注入。インターネット向けは Agent Gateway から直接
ALL_TRAFFIC すべてのアウトバウンド (パブリック インターネット、外部 SaaS API 含む) を VPC 経由でルーティング。静的 IP エグレスと VPC Service Controls に必要

🚧 制限事項

  • トランスポート: 旧来の SSE は非サポート。StreamableHTTP のみ対応
  • TLS 証明書: 公的に信頼された CA の署名が原則必須。Agent Gateway 経由のプライベート MCP サーバーのみ tlsConfig でプライベート CA / 自己署名証明書を利用可
  • アクション数: 同時に有効化するアクションは 100 個まで推奨
  • Agent Gateway バインド: 1 アプリにつきエグレス Agent Gateway は 1 つ (複数アプリでの共有は可能)
  • データストアのスコープ: スタンドアロンのカスタム MCP データストアのリンクは不可。アプリ内「Connected Data Stores」で直接作成が必要
  • プロキシ対象: クエリ時のアウトバウンド ツール実行のみ。モデル推論、RAG 検索、組み込みツール、コネクタ取り込みジョブ、インバウンド トラフィックは対象外
  • テンプレートの変更: Gateway から参照中はインプレース変更不可。networkAttachment は構成後は不変

🛠️ 設定方法

✅ 前提条件

  • カスタム MCP データストア作成をブロックする組織ポリシー制約のオーバーライド
  • MCP サーバー URL・認可 URL・トークン URL の FQDN を allowedEgressFqdns に追加
  • プロジェクト強制 / VPC Service Controls 保護下では許可データソースに custom_mcp を追加
  • アプリの Agent Gateway へのバインドを組織ポリシーで許可
  • データストア作成者に Discovery Engine Editor (roles/discoveryengine.editor) を付与
  • Compute Engine API の有効化と roles/compute.networkAdmin の付与 (Shared VPC の場合はホスト プロジェクトのサブネットに roles/compute.networkUser)
1

PSC ネットワーク アタッチメントの作成

コンソールの「Network attachments」で、要件を満たすサブネット (リージョン一致、/28 以上、Private Google Access 有効) を指定し、「Automatically accept all connections」を選択して作成。リソース URI (projects/PROJECT_ID/regions/LOCATION/networkAttachments/ATTACHMENT_NAME) を控えます。

2

エージェント接続テンプレートの作成

Bash 接続テンプレートのインポート 
gcloud network-services agent-connectivity-templates import CONNECTIVITY_TEMPLATE_NAME \
  --source="agw-connectivity-template.yaml" \
  --location=LOCATION

YAML でネットワーク アタッチメント、DNS ピアリング (dnsPeeringConfig)、VPC エグレス モード (vpcEgress) を定義。静的 IP エグレスの場合は vpcEgress: ALL_TRAFFIC を設定します。

3

Agent Gateway の作成

YAML my-agent-gateway-vpc-egress.yaml 
name: AGENT_GATEWAY_NAME
protocols:
- MCP
googleManaged:
  governedAccessPath: AGENT_TO_ANYWHERE
  agentConnectivityTemplate: projects/AGENT_GATEWAY_PROJECT_NUMBER/locations/LOCATION/agentConnectivityTemplates/CONNECTIVITY_TEMPLATE_NAME
registries:
- AGENT_REGISTRY_PATH
Bash Agent Gateway のインポート 
gcloud network-services agent-gateways import AGENT_GATEWAY_NAME \
  --source="my-agent-gateway-vpc-egress.yaml" \
  --location=LOCATION

エグレスはデフォルトでブロックされるため、ゲートウェイを対象とする認可ポリシーのバインドも必要。静的 IP エグレスの場合は、サブネットに静的外部 IP を割り当てた Cloud NAT を構成します。

4

カスタム MCP サーバー データストアの作成

アプリの「Connected Data Stores」から「Custom MCP Server」を追加し、「Route egress through Agent Gateway」チェックボックスを選択。エンジン リソース名 (projects/PROJECT_NUMBER/locations/LOCATION/collections/default_collection/engines/APP_ID) を入力してエグレス先を指定します。

5

構成の検証

Bash 構成の確認コマンド 
# ゲートウェイが接続テンプレートを参照しているか確認
gcloud network-services agent-gateways describe AGENT_GATEWAY_NAME \
  --location=LOCATION --project=AGENT_GATEWAY_PROJECT_ID

# ネットワーク アタッチメントの接続が ACCEPTED か確認
gcloud compute network-attachments describe ATTACHMENT_NAME \
  --region=LOCATION --project=PROJECT_ID
🔍 トラブルシューティング: HTTP 403 はゲートウェイへの認可ポリシー未バインド、HTTP 503 は DNS ピアリング設定・Private Google Access・ファイアウォール ルールの不備が主な原因です。

💪 メリット

💼 ビジネス面

✓レガシー / 社内システムの AI 統合: 標準コネクタが存在しない社内システムやレガシーシステムを、カスタム MCP サーバー経由で Gemini Enterprise のエージェントから安全に利用できる
✓セキュリティ ポリシーへの準拠: 送信元 IP の固定により、厳格な IP 許可リストを要求する外部パートナーや SaaS のセキュリティ要件を満たしながら AI 活用を進められる

🔧 技術面

✓パブリック公開不要: MCP サーバーにパブリック IP を付与せず VPC 内でプライベートにホストでき、攻撃対象領域を削減できる
✓宣言的なエグレス管理: 接続テンプレートにより DNS ピアリング、エグレス モード、TLS 設定を宣言的に一元管理できる
✓プライベート CA 対応: Agent Gateway 経由であれば、カスタム TLS トラスト アンカーにより社内 CA や自己署名証明書を使った TLS 検証が可能
✓VPC Service Controls 連携: ALL_TRAFFIC モードと restricted.googleapis.com への解決を組み合わせ、サービス境界による保護を適用できる

⚠️ デメリット・制約事項

🚫 制限事項

✗Agent Gateway のサポート リージョンは us-central1 と europe-west1 のみ
✗SSE トランスポート非対応 (StreamableHTTP のみ)
✗1 アプリにつきバインドできるエグレス Agent Gateway は 1 つ
✗接続テンプレートの networkAttachment と tlsConfig.trustConfig は構成後は不変。変更には新しいテンプレート (場合により新しいゲートウェイ) の作成が必要

🤔 考慮すべき点

  • Agent Gateway がプロキシするのはクエリ時のツール実行トラフィックのみ。モデル推論や RAG 検索、コネクタ取り込みは VPC を経由しない点をネットワーク設計で考慮
  • ALL_TRAFFIC モードではすべてのアウトバウンドが VPC に注入されるため、デフォルト ルート (0.0.0.0/0) や Cloud NAT、ファイアウォールなどルーティングとセキュリティの管理責任は利用者側にある
  • Shared VPC では最小権限の観点から、ネットワーク アタッチメントをサービス プロジェクト側に作成する方式を推奨 (ホスト側作成は roles/compute.networkAdmin 相当の高権限が必要)
  • 組織ポリシー (許可エグレス FQDN、許可データソース、ゲートウェイ バインド制限) の事前整備が必要

🎯 ユースケース

🏢 1. VPC 内のプライベート MCP サーバーで社内業務ツールを公開

シナリオ: 社内の在庫管理システムの API を MCP サーバーとして VPC 内 (パブリック IP なし) にデプロイし、Gemini Enterprise のエージェントから在庫照会・更新のアクションを実行させたい。

YAML 接続テンプレート (抜粋): プライベート ドメインの DNS ピアリング 
egressNetworkConfig:
  networkAttachment: projects/PROJECT_ID/regions/us-central1/networkAttachments/mcp-attachment
dnsPeeringConfig:
  domains:
  - corp.internal.   # 末尾のドット必須

効果: MCP サーバーをインターネットに公開せずに、Gemini Enterprise から社内システムのアクションを安全に実行。社内 CA の証明書も TrustConfig 経由で検証可能。

🤝 2. IP 許可リスト必須の外部 SaaS MCP サーバーへの接続

シナリオ: 外部パートナーが提供する MCP サーバーが、セキュリティ要件として接続元の静的 IP アドレスの事前登録を要求している。

効果: vpcEgress: ALL_TRAFFIC と Cloud NAT の静的外部 IPv4 アドレスにより、ツール呼び出しが常に固定 IP から送信され、パートナー側の IP 許可リストに登録するだけで接続を許可できる。

🌍 3. オンプレミス / マルチクラウドの MCP サーバーとのハイブリッド接続

シナリオ: オンプレミスのデータセンターで稼働する業務システムを MCP サーバー化し、Cloud Interconnect / VPN 経由で Gemini Enterprise から利用したい。

効果: VPC に注入されたトラフィックが VPC ルートテーブルに従ってハイブリッド ネットワークへルーティングされるため、オンプレミスや他クラウドの MCP サーバーのアクションもエージェントから実行できる。

📌 まとめ

カスタム MCP サーバーの VPC 接続と静的 IP エグレスの GA により、Gemini Enterprise のエージェントが プライベート ネットワーク内の社内ツールや IP 許可リストで保護された外部 MCP サーバーへ、 エンタープライズのネットワーク セキュリティ要件を満たしながらアクセスできるようになりました。 標準コネクタがない社内システムの AI 統合を検討している場合は、まず組織ポリシー (許可エグレス FQDN、許可データソース) の整備と、 us-central1 / europe-west1 での PSC ネットワーク アタッチメント + Agent Gateway の構成から着手することを推奨します。
