📋 概要

Google Cloud は、内部パススルー ネットワーク ロードバランサ (Internal Passthrough Network Load Balancer) のゾーンアフィニティ機能を一般提供 (GA) としてリリースしました。

ゾーンアフィニティは、ロードバランサのバックエンドサービスに設定することで、クロスゾーントラフィックを制限し、レイテンシを削減し、パフォーマンスを向上させる機能です。マルチゾーンアーキテクチャの利点を維持しながら、クライアントと同じゾーンにあるバックエンドへの接続を優先的にルーティングします。

💡 対象ユーザー: レイテンシに敏感なワークロードを実行している組織、ゾーン間トラフィックのコストを最適化したい組織、内部パススルー ネットワーク ロードバランサでマイクロサービス間の通信を管理しているすべてのユーザー

⚙️ 主要機能 - 3 つのゾーンアフィニティモード

1. ZONAL_AFFINITY_STAY_WITHIN_ZONE

→ゾーンマッチが発生した場合、トラフィックをクライアントのゾーン内に維持
→同一ゾーン内のバックエンドが正常でなくても、ゾーン内バックエンドを使用
→推奨: レイテンシ最適化を最優先するユースケース

2. ZONAL_AFFINITY_SPILL_CROSS_ZONE

→スピルオーバー比率に基づいてトラフィックを制御 (0.0 - 1.0)
→同一ゾーン内の正常バックエンドが比率を下回ると、他ゾーンへスピルオーバー許可
→推奨: 可用性とレイテンシのバランスが必要な場合

3. ZONAL_AFFINITY_DISABLED (デフォルト)

→ゾーンアフィニティが無効な状態 (従来の動作)
→すべての正常なバックエンドから均等に選択
→推奨: デフォルト動作、均等分散が必要な場合

🔧 設定方法

📝 前提条件:
✓Google Cloud プロジェクトが作成済み
✓内部パススルー ネットワーク ロードバランサが構成済み
✓バックエンドが複数ゾーンにデプロイ済み
✓Backend subsetting が無効であること

STAY_WITHIN_ZONE の設定

Bash 
gcloud compute backend-services update BACKEND_SERVICE_NAME \
    --zonal-affinity-spillover=ZONAL_AFFINITY_STAY_WITHIN_ZONE \
    --region=REGION

SPILL_CROSS_ZONE の設定 (スピルオーバー比率付き)

Bash 
gcloud compute backend-services update BACKEND_SERVICE_NAME \
    --zonal-affinity-spillover=ZONAL_AFFINITY_SPILL_CROSS_ZONE \
    --zonal-affinity-spillover-ratio=0.8 \
    --region=REGION

ゾーンアフィニティの無効化

Bash 
gcloud compute backend-services update BACKEND_SERVICE_NAME \
    --zonal-affinity-spillover=ZONAL_AFFINITY_DISABLED \
    --region=REGION

JSON 設定例

JSON 
{
  "name": "backend-service-example",
  "loadBalancingScheme": "INTERNAL",
  "protocol": "TCP",
  "zonalAffinity": {
    "zonalAffinitySpillover": "ZONAL_AFFINITY_SPILL_CROSS_ZONE",
    "zonalAffinitySpilloverRatio": 0.8
  }
}

💼 ビジネス面

✓運用の簡素化: ロードバランサ設定変更のみ、アプリコード変更不要

🔬 技術面

✓レイテンシ削減: 同一ゾーン内通信でネットワークホップ削減、RTT 短縮
✓柔軟な制御: スピルオーバー比率で可用性とローカリティのトレードオフを制御
✓既存接続影響なし: コネクション追跡テーブルの既存接続は影響を受けない
✓フェイルオーバー併用: 高可用性を維持しながらゾーンアフィニティ活用可能

⚠️ デメリット・制約事項

制限事項:
✗Backend subsetting との併用は不可
✗Packet Mirroring のコレクター宛先との併用は不可
✗Network Security Integration との併用はパケットドロップの原因
✗Cloud VPN/Cloud Interconnect 経由クライアントでは動作しない
✗クライアント VM が異なるリージョンにある場合は無効
考慮すべき点:
!STAY_WITHIN_ZONE 使用時、同一ゾーン内バックエンドが不健全でもゾーン内に留まるため可用性リスクあり
!ステートフルアーキテクチャ (ファイアウォール並列構成) でのネクストホップ使用は非推奨
!スピルオーバー比率はワークロード特性に応じたチューニングが必要
!ゾーン間バックエンド数が不均等な場合、特定ゾーンに負荷集中の可能性

💡 ユースケース

🏦 ユースケース 1: レイテンシに敏感なマイクロサービス通信

シナリオ: 金融取引システムにおいて、注文管理サービスから約定処理サービスへのリクエストを最小レイテンシで処理。両サービスは複数ゾーンにデプロイされているが、同一ゾーン内通信を優先したい。

Bash 
gcloud compute backend-services update order-execution-backend \
    --zonal-affinity-spillover=ZONAL_AFFINITY_SPILL_CROSS_ZONE \
    --zonal-affinity-spillover-ratio=0.5 \
    --region=asia-northeast1

効果: 通常時は同一ゾーン内で低レイテンシ通信、バックエンドが 50% 以下になるとクロスゾーンにフォールバックして可用性確保。

💰 ユースケース 2: データ転送コストの最適化

シナリオ: 大量データを処理するバッチ処理システムで、ワーカーノードがデータストア (内部 LB 経由) にアクセスする際のゾーン間データ転送コストを削減したい。

Bash 
gcloud compute backend-services update data-store-backend \
    --zonal-affinity-spillover=ZONAL_AFFINITY_STAY_WITHIN_ZONE \
    --region=us-central1

効果: ワーカーノードと同一ゾーンのデータストアバックエンドにのみ接続され、ゾーン間データ転送料金が発生せず大幅なコスト削減を実現。

🔗 ユースケース 3: Private Service Connect と組み合わせたサービス提供

シナリオ: SaaS プロバイダーが Private Service Connect を使用してサービスを公開しており、エンドポイント経由のトラフィックを効率的に処理したい。

効果: Private Service Connect エンドポイントからのトラフィックが、プロデューサー側の同一ゾーンのバックエンドに優先的にルーティングされ、サービス提供のレイテンシが改善。

💲 料金情報

ゾーンアフィニティ機能自体には追加料金は発生しません。 通常の Cloud Load Balancing の料金体系が適用されます。

💡 コスト削減のポイント: ゾーンアフィニティを有効にすることで、クロスゾーントラフィックが減少し、ゾーン間のエグレス料金を間接的に削減できる可能性があります。

🌍 利用可能リージョン

ゾーンアフィニティは、内部パススルー ネットワーク ロードバランサが利用可能なすべてのリージョンで GA として利用可能です。

📝 注意: ゾーンアフィニティの効果を得るためには、ロードバランサと同じリージョン内の複数ゾーンにバックエンドがデプロイされている必要があります。

🔗 関連サービス・機能

→Internal Passthrough Network Load Balancer: ゾーンアフィニティが設定される対象
→Private Service Connect: 互換性あり、パブリッシュされたサービスのプロデューサーとして使用可能
→Cloud VPN / Cloud Interconnect: これらを経由するクライアントはゾーンアフィニティの対象外
→Connection Tracking Policy: ゾーンアフィニティと併用して接続管理を最適化可能
→Backend Subsetting: ゾーンアフィニティとは非互換、どちらか一方を選択
