☸️ GKE: ストレージ最適化 Z4M マシンシリーズのノードサポート

Google Kubernetes Engine (GKE) Feature (提供開始)
📅 リリース日: 2026-10-19
Google Cloud Release Notes

📌 概要

GKE で、ストレージ最適化 Z4M マシンシリーズからノードをプロビジョニングできるようになりました。 Z4M は第 5 世代 Intel Xeon Scalable プロセッサ (Emerald Rapids)、DDR5 メモリ、Titanium オフロードプロセッサを搭載し、 最大 168,000 GiB のローカル Titanium SSD を提供する Compute Engine のマシンシリーズです (2026 年 10 月 15 日に GA)。 この大容量・高 IOPS のローカルストレージを、GKE 上のコンテナワークロードから利用できるようになります。

❌ Before (アップデート前の課題)

  • Z4M は Compute Engine の VM としては利用可能 (2026-10-15 GA) だったが、GKE ノードとしてはプロビジョニング不可。Kubernetes 上のワークロードから Z4M の大容量 Titanium SSD を利用できなかった
  • GKE のストレージ最適化シリーズは Z3 (最大 72,000 GiB) と Z4D (最大 84,000 GiB、2026-09-28 から GKE 対応) にとどまり、1 ノードあたりのローカルストレージ密度に上限があった

✅ After (アップデート後の改善)

  • GKE Standard クラスタで Z4M ノードプールを手動作成可能に (1.36.3-gke.1767000 以降)
  • コンピュートクラス、クラスタオートスケーラー、ノードプール自動作成、Autopilot でも Z4M を利用でき、宣言的・自動的なプロビジョニングが可能に (1.37.0-gke.4713000 以降)
  • 1 ノードあたり最大 168,000 GiB の Titanium SSD と最大 400 Gbps の帯域を、GKE 上の並列ファイルシステムや DB ワークロードで活用可能に
⚠️ 注意: GKE では現時点で Z4M のベアメタルインスタンス (z4m-highmem-192-metal) はサポートされません。Z4M は AI/ML ワークロードを支える大規模並列ファイルシステムや、データベースなどの I/O 集約型ワークロードに適しています。

GKE クラスタ上で手動またはコンピュートクラス / オートスケーラー経由で Z4M ノードプールを作成し、 ノードに自動付属する Titanium SSD を並列ファイルシステムや I/O 集約型データベースのストレージとして利用する構成です。

⚙️ 主要機能

1️⃣ Z4M ノードプールの手動作成 GKE 1.36.3-gke.1767000 以降

→GKE Standard クラスタのノードプール作成時に Z4M マシンタイプ (z4m-highmem-16 / 32 / 48 / 192) を指定可能
→Titanium SSD はマシンタイプに含まれており、ノード作成時に自動的にアタッチされる

2️⃣ コンピュートクラス・オートスケーラー・Autopilot 対応 GKE 1.37.0-gke.4713000 以降

→カスタムコンピュートクラスの優先順位ルールで Z4M を指定し、ノードプール自動作成と組み合わせた宣言的なプロビジョニングが可能
→クラスタオートスケーラーによる Z4M ノードプールのスケーリングに対応
→Autopilot クラスタでも Z4M を利用可能

3️⃣ ストレージ最適化ワークロード向けのローカルストレージ

→ストレージ最適化マシン (Z3 / Z4D / Z4M) では Local SSD をエフェメラルストレージとして利用する方法が案内されている (GKE Local SSD ドキュメント)
→emptyDir ボリュームやローカル PersistentVolume を通じて Pod から Titanium SSD にアクセスできる

🛠️ 設定方法

✅ 前提条件

✓GKE クラスタが必要バージョン以降であること (手動作成: 1.36.3-gke.1767000 以降、コンピュートクラス / Autopilot など: 1.37.0-gke.4713000 以降)
✓Z4M が利用可能なゾーン・リージョンでクラスタ / ノードプールを作成すること
✓Z4M は Windows OS イメージ非対応のため、Linux ノードイメージを使用すること

ステップ 1: Z4M ノードプールを手動作成する (Standard クラスタ)

Bash gcloud で Z4M ノードプールを作成 
gcloud container node-pools create z4m-pool \
    --cluster=CLUSTER_NAME \
    --location=LOCATION \
    --machine-type=z4m-highmem-16 \
    --ephemeral-storage-local-ssd count=1
💡 ポイント: ストレージ最適化マシンでは、Local SSD (Titanium SSD) をエフェメラルストレージとして構成する方法が推奨されています。Local SSD 構成はノードプール作成後に変更できない点に注意してください。

ステップ 2: コンピュートクラスで Z4M を宣言的に利用する (1.37.0-gke.4713000 以降)

YAML ComputeClass 定義例 
apiVersion: cloud.google.com/v1
kind: ComputeClass
metadata:
  name: storage-optimized
spec:
  priorities:
  - machineFamily: z4m
  nodePoolAutoCreation:
    enabled: true

Pod がこのコンピュートクラスを要求すると、GKE が Z4M のノードプールを自動作成・スケールします。 なお、コンピュートクラスの machineFamily 指定ではベアメタルマシンタイプはプロビジョニングされません (GKE 自体が Z4M ベアメタルを未サポート)。

⚖️ メリットと制約事項

👍 メリット

💼 ビジネス面
  • AI/ML ストレージ基盤の Kubernetes 統合: 並列ファイルシステムなどのストレージ基盤を GKE 上で運用でき、コンテナベースの AI/ML プラットフォームとインフラ運用を統一
  • ノード集約によるコスト効率: 1 ノード最大 168,000 GiB の高ストレージ密度により、少ないノード数で大規模データを扱える
🔧 技術面
  • Compute Engine 最大のローカルストレージを GKE で利用可能: z4m-highmem-192 で読み取り最大 1,560 万 IOPS、75,600 MiBps
  • 自動プロビジョニング対応: コンピュートクラス、クラスタオートスケーラー、ノードプール自動作成、Autopilot に対応
  • 広帯域ネットワーク: z4m-highmem-192 は 2 枚の物理 NIC で最大 400 Gbps。分散ストレージのノード間通信に最適

⚠️ 制約・考慮点

🚫 制限事項
  • Z4M ベアメタル (z4m-highmem-192-metal) は GKE 未サポート
  • コンピュートクラス / オートスケーラー / Autopilot は 1.37.0-gke.4713000 以降が必要 (手動作成より新しいバージョン)
  • 一部ゾーン・リージョンのみ、GPU 利用不可、カスタムマシンタイプ不可、Windows OS イメージ非対応
  • Titanium SSD 48 TiB 超または Cloud RDMA 使用時はライブマイグレーション非対応 (メンテナンス時に終了、SSD データ保持を伴う)
🤔 考慮すべき点
  • Local SSD 上のデータはエフェメラル。永続化が必要なデータは Persistent Disk / Hyperdisk、Filestore、Cloud Storage を併用
  • Local SSD の構成 (エフェメラル / raw ブロック) はノードプール作成後に変更不可。事前にアクセス方式を設計
  • 確実なスケジュールには node affinity やコンピュートクラスによる制御を行う

🎯 ユースケース

🗂️ ユースケース 1: GKE 上の AI/ML 向け並列ファイルシステム

シナリオ: GKE 上の AI/ML トレーニングに学習データを供給する大規模並列ファイルシステムのストレージノード群を、Kubernetes ネイティブに運用したい。

Bash raw ブロックモードでの Z4M ノードプール作成例 
gcloud container node-pools create pfs-pool \
    --cluster=ml-cluster \
    --location=us-central1 \
    --machine-type=z4m-highmem-192 \
    --local-nvme-ssd-block count=12

効果: raw ブロックモードで Titanium SSD を構成し、ZFS などのファイルシステムや RAID を自前で構成することで、1 ノード 168,000 GiB・最大 400 Gbps のストレージノードを GKE 上で運用できる。

🗄️ ユースケース 2: I/O 集約型データベースのホスティング

シナリオ: SQL / NoSQL / ベクトルデータベースなど、低レイテンシかつ高 IOPS のローカルストレージを要求するデータベースを GKE 上で StatefulSet として運用したい。

効果: Titanium SSD の高い IOPS・スループットをローカル PersistentVolume 経由でデータベース Pod から利用でき、ストレージ密度の高いノードにデータを集約できる。データの永続性はデータベース側のレプリケーションと永続ストレージへのバックアップで担保する。

🔁 ユースケース 3: コンピュートクラスによるストレージ最適化ノードの自動管理

シナリオ: ストレージ要件の大きいワークロードが増減する環境で、Z4M ノードプールの作成・スケーリングを自動化したい。

効果: GKE 1.37.0-gke.4713000 以降では、コンピュートクラスとノードプール自動作成により、Pod の要求に応じて GKE が Z4M ノードプールを自動作成・スケール・削除する。手動のキャパシティ管理が不要になる。

💰 料金

GKE で Z4M ノードを使用する場合、GKE のクラスタ管理料金に加えて、 ノードとして使用する Z4M インスタンスの料金 (Titanium SSD を含む) が Compute Engine の料金体系に基づいて課金されます。

💳 割引オプション: Z4M はリソースベース確約利用割引 (CUD)、Flexible CUD、Spot VM (ベアメタルを除く)、予約に対応しています。
  • VM インスタンス料金 (Z4M マシンタイプ)
  • GKE の料金
  • ディスクとイメージの料金

🌍 利用可能リージョン

Z4M は一部のゾーン・リージョンで利用可能です。最新の利用可能ゾーンは リージョンとゾーン を参照するか、以下のコマンドで確認してください。

🗃️ Google Cloud Hyperdisk

Z4M がサポートする高性能ブロックストレージ。永続データは Hyperdisk、ホットデータは Titanium SSD という使い分けができる。
