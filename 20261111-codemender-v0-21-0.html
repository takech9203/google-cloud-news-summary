📝 概要

AI コードセキュリティエージェント CodeMender は、脆弱性のスキャン (cm find)・検証 (cm verify)・修正 (cm fix) を行う自律型エージェント。推論はクラウド側のホスト型エンジン、パッチ適用・ビルド・テストはローカルの OS レベルサンドボックス内で実行する。

v0.21.0 の中心テーマは「サンドボックス境界の徹底」。build.command のサンドボックス内実行、ホストツールチェーンの読み取り専用マウント、キャッシュのセッションスコープ隔離、Git フック無効化・Git 設定分離・__pycache__ 無視を導入。あわせて cm fix のパッチ diff 自動更新と 3 件のバグ修正を含む。同日、前日 (2026-11-10) に GA となったフロンティアモデル Gemini 4 Carbon の Preview サポートも追加された (デフォルトは引き続き Gemini 3.8 Flash)。

❌ Before (v0.20.0 以前)

  • サンドボックス有効時でも build.command の実行はサンドボックス内で完結せず、分離が不十分
  • ビルドがホストのツールチェーン・共有キャッシュへ書き込み、ホスト環境を汚染するリスク
  • リポジトリの Git フック、ホスト Git 設定、stale な __pycache__ が実行に影響し得た
  • ビルド検証後に保存済みパッチ diff が更新されないことがあった
  • 無応答セッションがタイムアウトせず停止したままに
  • PoC エラー時に実行出力が失われ診断が困難
  • 実行途中のサンドボックス障害でパッチ生成が失敗
  • Gemini 4 Carbon が選択肢になかった

✅ After (v0.21.0)

  • cm build / cm fix のビルド検証が build.command をサンドボックス内で実行、エンドツーエンドで境界内に完結
  • ホストツールチェーンは読み取り専用マウント、キャッシュはセッションスコープの一時ディレクトリへリダイレクト
  • Git フック無効化・Git 設定分離・__pycache__ 無視で再現性と安全性が向上
  • cm fix がビルド検証完了後にパッチ diff を自動更新し整合性を保証
  • 30 分タイムアウトで停止セッションをクリーンに復旧
  • PoC エラー時も stdout / stderr を保持
  • サンドボックス障害時は新環境で自動リトライ
  • --model gemini-4-carbon で Preview 利用可能

v0.21.0 では build.command の実行がサンドボックス内に移り、ホストツールチェーンの読み取り専用化・キャッシュの隔離・Git フック無効化によってビルド検証がホスト環境から分離される。検証完了後は保存済みパッチ diff が更新され、ワークスペースに適用される。

⚡ 主要機能

📦 1. サンドボックス内ビルドコマンド実行とパッチ diff 更新

→サンドボックス有効時、cm build / cm fix のビルド検証が設定済みの build.command をサンドボックス内で実行
→cm fix はビルド検証完了後に保存済みパッチ diff を更新 (refresh) し、検証を経た最終状態をパッチに正しく反映

🔒 2. 読み取り専用ホストツールチェーンと隔離キャッシュ

→サンドボックス化された cm build / cm fix / cm verify では、ホストのツールチェーン・パッケージマネージャーディレクトリを読み取り専用でマウント
→コンパイラ・パッケージキャッシュはセッションスコープの一時ディレクトリにリダイレクト
→エージェントのビルドがホストの共有キャッシュやツールチェーンを書き換えず、ホスト環境の完全性を維持

🚫 3. コマンド実行環境の分離

→コマンド・ビルド実行中はリポジトリの Git フックを無効化 (悪意あるフックの実行防止)
→ホストの Git 設定を分離
→Python バイトコードキャッシュ (__pycache__) を無視し、stale なキャッシュによる予期しない挙動を防止

🐛 4. バグ修正 (3 件)

✓無応答のアクティブターンに 30 分のタイムアウトを追加し、停止セッションをクリーンにキャンセル・復旧
✓PoC (reproducer) エラー発生時も stdout / stderr を保持し、ビルド失敗・タイムアウト・セットアップ問題の診断を支援
✓実行途中のサンドボックス障害時は、新しいサンドボックス環境での自動リトライでパッチ生成失敗を解消

🧠 5. Gemini 4 Carbon サポート (Preview)

→cm find / cm verify / cm fix に --model gemini-4-carbon を渡して利用 (デフォルトは Gemini 3.8 Flash のまま)
→Gemini 4 Carbon は 2026-11-10 に GA となったフロンティアモデルで、コーディングやサイバーセキュリティを含む複雑なタスク向け
→組み込みサイバーセーフティによるブロック発生時は Gemini 3.8 Flash Cyber で自動リトライ、アクセスがない場合は Gemini 3.8 Flash へフォールバック

💡 メリット

💼 ビジネス面

✓サプライチェーンリスクの低減: 悪意ある Git フックやビルドスクリプトによるホスト環境 (ツールチェーン、共有キャッシュ、Git 設定) の改変リスクを構造的に遮断。未知のコードベースや外部由来のリポジトリにも安全に実行しやすくなる
✓運用の安定化: 停止セッションの自動タイムアウト・サンドボックス障害時の自動リトライで、長時間実行や CI 組み込み時の「ハングしたまま」「途中失敗でやり直し」が減少
✓モデル選択の柔軟性: 複雑な脆弱性にフロンティアモデル (Gemini 4 Carbon) を選択でき、精度とコストのトレードオフをユースケースごとに最適化

⚙️ 技術面

✓ビルド検証のエンドツーエンド分離: パッチ適用だけでなく build.command によるビルド・テストまでサンドボックス内で完結し、ホストへの副作用 (キャッシュ汚染、ツールチェーン改変) がなくなる
✓再現性の向上: セッションスコープのキャッシュ、Git 設定の分離、__pycache__ の無視により、ホスト固有の状態に依存しないクリーンなビルド検証が可能
✓診断性の向上: PoC エラー時にも stdout / stderr が保持され、ビルド失敗・タイムアウト・セットアップ問題の原因究明が容易に
✓パッチ整合性の保証: ビルド検証後のパッチ diff 自動更新により、「検証したコード」と「適用されるパッチ」の乖離を解消

⚠️ デメリット・制約事項

🚧 制限事項

✗CodeMender は Preview であり、限定された顧客のみ利用可能。Pre-GA Offerings Terms が適用される
✗CodeMender における Gemini 4 Carbon サポートは Preview 段階
✗サンドボックスのネットワーク分離はドメイン単位の許可リストに未対応 (permissive-closed か permissive-open の二択)
✗Gemini 4 Carbon はサイバーセーフティ機能により、エクスプロイト生成・脆弱性検証に関わるリクエストをブロックする場合がある (自動フォールバックあり)。cm verify はサイバーモデル (Fairwind Program 経由) との組み合わせが最適
✗Windows のサンドボックスは Experimental

🤔 考慮すべき点

  • キャッシュがセッションスコープにリダイレクトされるため、ホストの共有ビルドキャッシュ (ccache、ローカル Maven/Go キャッシュなど) の恩恵を受けられず、サンドボックス内ビルドの所要時間が従来より長くなる可能性
  • デフォルトのネットワーク分離下では、ビルド中の外部依存取得 (npm install など) が失敗する。これまでホスト側で動いていたビルドが失敗するケースがあり得るため、依存の事前フェッチやネットワークプロファイルの見直しを行う
  • Git フックに依存したビルド・テストフロー (フックでコード生成など) は、実行中のフック無効化により挙動が変わる可能性
  • 30 分の無応答タイムアウトにより、極端に長いビルド検証を伴うセッションの挙動が変わる可能性があるため、長時間ビルドのプロジェクトでは動作を確認する

🎯 ユースケース

🔍 ユースケース 1: 外部由来リポジトリの安全なスキャンと修正

シナリオ: OSS フォークや買収先のコードベースなど、完全には信頼できないリポジトリに対して脆弱性スキャンと自動修正を実施。悪意ある Git フックやビルドスクリプトからホスト環境を保護したい。

Bashサンドボックス有効のままスキャン → 検証 → 修正
# CLI を v0.21.0 以降に更新
cm update

# サンドボックス有効 (デフォルト) のままスキャン → 検証 → 修正
cm find .
cm verify FINDING_ID
cm fix FINDING_ID

効果: ビルド・テストを含むすべてのコマンド実行がサンドボックス内で完結。Git フックは無効化、ホストツールチェーンは読み取り専用、キャッシュはセッションスコープに隔離され、悪意あるコードがホスト環境へ影響を及ぼす経路が遮断される。

🧠 ユースケース 2: 複雑な脆弱性に対する Gemini 4 Carbon の活用

シナリオ: マルチテナントのセッション検証ロジックなど、コードベースを横断する複雑な脆弱性に対して、デフォルトモデルでは修正パッチの品質が安定しない。

Bashフロンティアモデルで検証・修正
# フロンティアモデルで検証・修正を実行
cm verify FINDING_ID --model gemini-4-carbon -c "Focus analysis on the multi-tenant session validation path"
cm fix FINDING_ID --model gemini-4-carbon

効果: 持続的なエージェントワークフローと複雑な推論に強い Gemini 4 Carbon を適用し、難度の高い脆弱性の検証・修正品質の向上が期待できる。日常のスキャンはデフォルトの Gemini 3.8 Flash、難しい finding のみ Carbon という使い分けでコストも最適化。

🩺 ユースケース 3: ビルド失敗の診断効率化

シナリオ: cm verify の PoC 実行が環境問題 (依存不足、タイムアウト) で失敗するが、従来は出力が失われ原因究明に時間がかかっていた。

効果: v0.21.0 では reproducer エラー時にも stdout / stderr が保持されるため、ビルド失敗・タイムアウト・セットアップ問題を実行ログから直接診断でき、ネットワークプロファイルや依存の事前フェッチといった対処を迅速に判断できる。

📌 まとめ

CodeMender v0.21.0 は、build.command のサンドボックス内実行、ホストツールチェーンの読み取り専用化、キャッシュ・Git 環境の隔離により、ビルド検証を含むエージェント実行全体をホスト環境から分離する、セキュリティ境界の大幅な強化リリース。あわせて Gemini 4 Carbon (Preview) のサポートにより、難度の高い脆弱性にフロンティアモデルを適用する選択肢が加わった。cm update での早期アップデートを推奨するが、ビルドがサンドボックス内実行に移ることでネットワーク依存のビルドやキャッシュ性能に影響が出る可能性があるため、依存の事前フェッチとネットワークプロファイルの確認もあわせて行いたい。
