☁️ Cloud DNS: Outbound Endpoints

Cloud DNS Preview ネットワーキング
リリース日: 2026-10-12
Google Cloud アップデート

📝 概要

Cloud DNS の Outbound Endpoints が Preview として利用可能になりました。 転送ゾーン (forwarding zones) またはサーバーポリシーにアタッチすることで、VPC ネットワークから外部およびオンプレミスの DNS リゾルバーへ、 プライベート IP アドレスを使用して DNS クエリを直接転送できます。

Outbound Endpoint は特定の VPC ネットワーク内に作成されるリージョンリソースで、そのネットワークの プロキシ専用サブネットを送信元 IP アドレスとして使用します。 従来の固定転送プロキシ範囲 35.199.192.0/19 によるルーティング上の制約を克服し、 VPC ネットワークごとに固有のエグレス範囲を割り当てることで、アウトバウンド DNS トラフィックのきめ細かな制御が可能になります。 ハイブリッド/マルチクラウド環境の DNS 名前解決を構成するネットワーク管理者や Solutions Architect にとって重要なアップデートです。

❌ Before: アップデート前の課題

  • アウトバウンド DNS 転送はすべて Google 所有の固定プロキシ範囲 35.199.192.0/19 が送信元となり、オンプレミス側でこの範囲への戻りルートを同一 VPC 経由で構成する必要があるなど、ルーティング上の制約があった
  • すべての VPC が同じ送信元範囲を共有するため、オンプレミスのファイアウォールや DNS リゾルバー側で VPC ごとにトラフィックを識別・分離できなかった
  • Hub-and-Spoke 構成で DNS 転送を集約するには、ネットワーク間の接続構成に依存した設計が必要だった

✅ After: アップデート後の改善

  • VPC ごとに固有のエグレス範囲 (プロキシ専用サブネットの IP 範囲) を割り当て、オンプレミス側で VPC 単位のファイアウォール設定・アクセス制御が可能に
  • ハブ VPC の Outbound Endpoint をスポーク VPC の転送ゾーン/サーバーポリシーから利用でき、ハブ・スポーク間のネットワーク接続なしで DNS 転送を一元化 (Cloud DNS が内部でクエリ転送を処理)
  • Shared VPC に対応し、ホストプロジェクトに集約したエンドポイントをサービスプロジェクトからクロスプロジェクトでバインド可能に
  • GKE クラスタはホスト VPC の Outbound Endpoints を自動継承し、クラスタレベルの変更なしに外部宛てクエリをルーティング

VM からの DNS クエリは転送ゾーン/サーバーポリシーにアタッチされた Outbound Endpoint を経由し、 プロキシ専用サブネットの IP を送信元としてオンプレミスのリゾルバーへ転送されます。 複数リージョンにエンドポイントを配置することで、リージョン障害時の自動フェイルオーバーが可能です。

⚡ 主要機能

1️⃣ VPC ネットワーク固有の送信元 IP によるアウトバウンド DNS 転送

  • Outbound Endpoint は VPC ネットワーク内に作成され、そのネットワークのリージョナルプロキシ専用サブネットを DNS クエリの送信元 IP 範囲として使用
  • 従来の固定範囲 35.199.192.0/19 によるルーティング制約を克服し、ネットワークごとに固有のエグレス範囲を割り当て可能
  • 専用かつ予測可能な送信元 IP 範囲が必要な場合は、DNS 専用のエグレス VPC ネットワークを構築するアーキテクチャも推奨

2️⃣ 自動ランキングとリージョンフェイルオーバー

  • 複数エンドポイントのアタッチ時は、既存のターゲットランキングアルゴリズム (成功応答数、低レイテンシ、地理的近接性) に基づき最適なエンドポイントを自動選択
  • 最上位のエンドポイントが異常な場合は次点へ自動フェイルオーバーし、回復後は再び優先される
  • リージョン障害への保護として、ワークロードを実行する 2 つ以上のリージョンへのエンドポイント構成を推奨

3️⃣ Hub-and-Spoke 構成と Shared VPC のサポート

  • 転送ゾーン/サーバーポリシーから別の集中管理 VPC (ハブ) のエンドポイントを利用可能。ハブ・スポーク間のネットワーク接続は不要 (Cloud DNS が内部で転送を処理)
  • Shared VPC では、エンドポイントとプロキシ専用サブネットをホストプロジェクトに集約し、サービスプロジェクトからクロスプロジェクトでバインド可能 (dns.outboundEndpoints.bindPrivateDNSZone / bindPrivateDNSPolicy 権限が必要)

4️⃣ GKE クラスタの自動継承

  • ホスト VPC が Outbound Endpoints 構成済みの標準グローバル転送ゾーンまたはサーバーポリシーで認可されている場合、VPC DNS 解決を使用する Pod はクラスタレベルの変更なしに外部宛てクエリをリージョナル Outbound Endpoint 経由でルーティング

5️⃣ 地理位置ルーティングポリシーとの連携

  • FQDN を転送ターゲットに指定し、Geolocation ルーティングポリシーを組み合わせることで、クエリ元リージョンに近いオンプレミスリゾルバーへのルーティングが可能

🛠️ 設定方法

✅ 前提条件

✓オンプレミスまたは外部の DNS ネームサーバーへの接続性 (Cloud Interconnect / Cloud VPN など) を持つ VPC ネットワークがあること
✓エンドポイントをデプロイする各リージョンに、通常のサブネットとプロキシ専用サブネットの両方が存在すること
✓オンプレミスネットワークにリージョナルプロキシ専用サブネットの IP 範囲への戻りルートがあること
✓オンプレミスのファイアウォールで、プロキシ専用サブネットの IP 範囲からのインバウンド DNS クエリ (UDP/TCP ポート 53) を許可すること
✓Cloud DNS、Compute Engine、Network Services の各 API が有効化されていること

ステップ 1: Outbound Endpoint を作成する

Bash Outbound Endpoint の作成 
gcloud beta dns outbound-endpoints create ENDPOINT_NAME \
    --project=PROJECT_ID \
    --network=VPC_NETWORK \
    --subnetwork=REGULAR_SUBNET \
    --location=REGION \
    --endpoint-ip=IP_ADDRESS \
    --description="DESCRIPTION"

--endpoint-ip には通常サブネットのプライマリ IPv4 範囲から利用可能な内部 IP アドレスを指定します。 この IP はネットワークスタック上の配置に使用され、実際の DNS クエリのエグレスはプロキシ専用サブネットの IP 範囲から行われます。

ステップ 2: 転送ゾーンにエンドポイントをアタッチする

Bash 転送ゾーンへのアタッチ (複数リージョン推奨) 
gcloud beta dns managed-zones update ZONE_NAME \
    --project=PROJECT_ID \
    --outbound-endpoints=projects/PROJECT_ID/locations/REGION_1/outboundEndpoints/ENDPOINT_NAME_1,projects/PROJECT_ID/locations/REGION_2/outboundEndpoints/ENDPOINT_NAME_2
💡 ポイント: アタッチするエンドポイントはすべて同一の VPC ネットワークに属している必要があります。 高可用性のため、異なるリージョンの 2 つ以上のエンドポイントを指定することが推奨されます。 Google Cloud コンソールの場合は、転送ゾーン作成/編集時に「Forwarding path」で「Outbound Endpoints」を選択します。

🎯 メリット

💼 ビジネス面

✓ハイブリッド/マルチクラウド DNS の制約解消: 固定プロキシ範囲 35.199.192.0/19 のルーティング要件が障壁となっていたユースケースを実現できる
✓セキュリティポリシーの精緻化: オンプレミスのファイアウォールで VPC ネットワークごとに異なる送信元 IP を識別でき、ネットワーク単位のアクセス制御・監査が可能になる
✓運用の一元化: Hub-and-Spoke や Shared VPC により、DNS エグレスをホスト/ハブプロジェクトに集約し、ガバナンスを強化できる

⚙️ 技術面

✓リージョンフェイルオーバー: 複数リージョンへの配置で、リージョン障害時も自動的に正常なエンドポイントへ切り替わる
✓GKE との透過的な統合: クラスタレベルの変更なしに、Pod のアウトバウンドクエリが Outbound Endpoint 経由でルーティングされる
✓ライフサイクル保護: 使用中のプロキシ専用サブネットや VPC ネットワークは削除から保護され、誤操作による DNS 障害を防止できる

⚠️ デメリット・制約事項

🚫 制限事項

✗IPv4 のみ: 送信元 IP は IPv4 のみで、転送先も IPv4 ターゲット (または IPv4 に解決される FQDN) に限定
✗プライベートターゲットのみ: パブリックインターネット宛て DNS トラフィックのエグレスプロキシや固定送信元 IP アンカーとしては使用不可 (パブリック宛てクエリは Google の anycast エッジで直接解決)
✗リージョンリソース: 使用する各リージョンにエンドポイントの作成が必要
✗転送メカニズムの排他性: 同一の転送ゾーン/サーバーポリシーで、デフォルトの 35.199.192.0/19 範囲と Outbound Endpoints の併用は不可
✗クロスプロジェクトのエンドポイント作成は不可: エンドポイントは VPC ネットワーク・サブネットと同一プロジェクトに作成する必要がある (Shared VPC のサービスプロジェクトからホストプロジェクト VPC への作成は不可)
✗プロキシ専用サブネットへの直接ピアリング不可: 外部ネームサーバーへの接続は Cloud Interconnect、Cloud VPN、VPC Network Peering などの標準的な VPC ルーティング経由で確立する必要がある

🤔 考慮すべき点

  • 使用中のプロキシ専用サブネットは直接変更できない。IP 範囲の変更には BACKUP ロールの新サブネット作成 → ACTIVE 化 → ドレイン完了待ち → 旧サブネット削除という移行手順が必要
  • プロキシ専用サブネットは Regional Application Load Balancer など同一リージョンの他のリソースと共有されるため、専用の送信元 IP 範囲が必要な場合は DNS 専用のエグレス VPC ネットワークの構築を検討
  • Preview (Pre-GA) 機能のため、サポートが限定される可能性がある。本番環境への適用は GA を待つか慎重に判断
  • 既存の転送構成からの移行は、公式の移行ガイド (Migrate an existing Cloud DNS forwarding setup to Outbound Endpoints) を参照

💡 ユースケース

🔐 ユースケース 1: VPC ネットワークごとの送信元 IP 分離

シナリオ: 同一リージョンの複数の VPC ネットワーク (本番用・開発用など) からオンプレミスのリゾルバーへクエリを転送し、オンプレミス側で VPC ごとに異なるファイアウォールポリシーを適用したい。

Plan 実装例 
1. 各 VPC ネットワークに Outbound Endpoint を作成
2. 各 VPC に転送ゾーン (またはサーバーポリシー) を作成し、
   その VPC のみを認可、その VPC のエンドポイントのみを使用
3. オンプレミス側では各 VPC のプロキシ専用サブネットの
   送信元 IP 範囲ごとにポリシーを適用

効果: オンプレミスネットワークが VPC ネットワークごとに異なる送信元 IP を識別でき、ネットワーク単位のきめ細かなアクセス制御が実現する。

🌐 ユースケース 2: Hub-and-Spoke による DNS エグレスの一元化

シナリオ: 多数のスポーク VPC からのオンプレミス宛て DNS クエリを、ハイブリッド接続 (Cloud Interconnect) を持つハブ VPC に集約したい。

効果: ハブ VPC に Outbound Endpoint を作成し、スポーク VPC の転送ゾーン/サーバーポリシーからそれを指定するだけで、ハブ・スポーク間のネットワーク接続なしに DNS 転送を一元化できる。冗長なハイブリッド回線のプロビジョニングが不要になり、コストを最小化できる。

🗺️ ユースケース 3: 地理位置ルーティングによるリージョン別オンプレミスリゾルバーへの転送

シナリオ: 米国と欧州にそれぞれオンプレミス DNS リゾルバーがあり、クエリ元リージョンに近いリゾルバーへ転送したい。

効果: Geolocation ルーティングポリシーを適用したプライベートゾーンの FQDN (例: onprem-resolvers.example.com) を転送ターゲットに指定し、各リージョンの Outbound Endpoint をアタッチすることで、欧州のクエリは欧州のリゾルバーへ、米国のクエリは米国のリゾルバーへ 2 段階ルーティングされ、レイテンシを最小化できる。

🔗 関連サービス・機能

📂 Cloud DNS 転送ゾーン (Forwarding Zones)

特定の DNS 名のクエリを別の DNS サーバーへ転送するゾーン。Outbound Endpoints の主要なアタッチ先。

📜 Cloud DNS サーバーポリシー (Server Policies)

VPC ネットワークの名前解決順序を変更し、代替ネームサーバーへ全クエリを転送するアウトバウンドポリシー。Outbound Endpoints のもう 1 つのアタッチ先。

🗺️ Cloud DNS ルーティングポリシー (Geolocation)

FQDN 転送ターゲットと組み合わせて、クエリ元リージョンに応じたリゾルバー選択を実現。

🔗 Cloud Interconnect / Cloud VPN

Outbound Endpoint からオンプレミスリゾルバーへの接続経路を提供するハイブリッド接続サービス。

🏢 Shared VPC

ホストプロジェクトにエンドポイントを集約し、サービスプロジェクトからクロスプロジェクトバインドが可能。

⚓ Google Kubernetes Engine (GKE)

ホスト VPC の Outbound Endpoints 構成を自動的に継承し、Pod の外部宛てクエリをルーティング。

📌 まとめ

Cloud DNS Outbound Endpoints は、長年ハイブリッド DNS 設計の制約となっていた固定転送プロキシ範囲 35.199.192.0/19 への依存を解消し、VPC ネットワークごとの送信元 IP 分離、 Hub-and-Spoke での一元化、Shared VPC 対応を実現する重要なアップデートです。 Preview 期間中はエンドポイントの時間課金が免除されるため、ハイブリッド/マルチクラウド DNS を運用している組織は、 この期間に 2 リージョン以上の冗長構成で検証を開始し、GA (2027 年 1 月予定) に向けた移行計画を立てることを推奨します。
