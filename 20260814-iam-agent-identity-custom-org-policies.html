🛡️ Agent Identity リソースに対する
Organization Policy カスタム制約が GA

Identity and Access Management (IAM) Organization Policy Service GA (一般提供)
対象リソース: agentidentity.googleapis.com/AuthProvider

📌 概要

2026 年 8 月 14 日、Organization Policy Service のカスタム制約 (custom constraints) が Agent Identity リソースに対応し、GA となりました。agentidentity.googleapis.com/AuthProvider リソースの 特定のフィールド単位で、粒度の細かいガバナンスを組織全体に適用できます。

Agent Identity (2026 年 4 月 22 日 GA) は、エージェントをホストするリソースのライフサイクルに紐付いた、 強く証明された暗号学的な ID をエージェントに付与する機能です。その Agent Identity auth manager は 3-legged OAuth・2-legged OAuth・API キーでエージェントをサードパーティサービスへ安全に認証させる仕組みで、 その設定を保持するのが AuthProvider リソースです。今回のアップデートで、この AuthProvider の作成・更新を組織のセキュリティ要件に沿って強制できるようになりました。

🎯 対象ユーザー: AI エージェントを Google Cloud 上で本番運用する組織の 組織のポリシー管理者 (Organization Policy Administrator) およびプラットフォーム/セキュリティチーム。 「3LO では PKCE を必須にする」「2LO プロバイダの作成を禁止する」「説明文を必須にする」といったルールを 組織・フォルダ・プロジェクトのいずれかのレベルで強制できます。

❌ Before: アップデート前の課題

  • AuthProvider はカスタム制約の対象外で、clientId・tokenUrl・enablePkce・allowedScopes などの個別フィールド値を組織として強制する手段がなかった
  • ガードレールは IAM ロール (roles/agentidentity.editor / admin) による「操作できる/できない」の粒度に留まり、「作成は許可するが安全でない設定値は禁止」ができなかった
  • 安全でない設定 (PKCE 無効の 3LO、意図しない認可サーバー URL、過剰なスコープなど) はレビューや監査など予防的でない仕組みに頼るしかなかった

✅ After: アップデート後の改善

  • AuthProvider の 12 フィールドを CEL 条件で参照し、リクエスト時点で DENY / ALLOW を強制できる
  • 認証方式の種別まで踏み込んだガードレールが可能 (例: has(resource.authProviderTypeParams.twoLeggedOauth) で 2LO 作成のみ禁止)
  • 組織のポリシーとしてリソース階層に沿って継承され、新規プロジェクトにも自動適用
  • GA のため、通常の一般提供条件のもとで本番環境に適用できる

組織のポリシー管理者が定義したカスタム制約は、Agent Identity API への CREATE / UPDATE リクエストを Organization Policy Service が CEL 条件で評価する形で強制され、違反するリクエストはリソースが作成される前に拒否されます。

⚙️ 主要機能

1️⃣ AuthProvider のフィールド単位制御

OAuth のクライアント ID、認可エンドポイント、トークンエンドポイント、PKCE の有効/無効、許可・ブロックするスコープなど 12 フィールドを CEL 条件で参照可能。認証方式ごとに authProviderTypeParams.threeLeggedOauth / twoLeggedOauth のサブフィールドが分かれており、 方式別のポリシーを書き分けられます。

2️⃣ CREATE / UPDATE メソッドへの強制

methodTypes には CREATE のみ、または CREATE + UPDATE を指定可能 (UPDATE のみの指定はカスタム制約全体で非サポート)。UPDATE を含めた場合、 制約違反の既存リソースへの変更は、違反を解消するものでない限りブロックされます。

3️⃣ ALLOW / DENY 両方のアクションタイプ

DENY: 条件が true と評価された場合に作成・更新をブロック (例: PKCE 無効の 3LO を拒否)。
ALLOW: 条件が true の場合のみ許可し、それ以外をすべてブロックする許可リスト方式。

4️⃣ ドライラン (dry-run) モードによる事前検証

--update-mask=dryRunSpec で適用すると、実際にはブロックせずに違反を検出できます。 意図どおりの動作を確認した後、--update-mask=spec でライブポリシーへ切り替える運用が可能です。

📄 カスタム制約 YAML の構造

YAML カスタム制約の定義例 (PKCE 必須化) 
name: organizations/ORGANIZATION_ID/customConstraints/custom.requirePkceFor3LO
resourceTypes:
  - agentidentity.googleapis.com/AuthProvider
methodTypes:
  - CREATE
  - UPDATE
condition: "has(resource.authProviderTypeParams.threeLeggedOauth) && resource.authProviderTypeParams.threeLeggedOauth.enablePkce == false"
actionType: DENY
displayName: Require PKCE for 3LO
description: All new 3-legged OAuth authentication providers must have PKCE enabled.

🛠️ 設定方法

📋 前提条件: ① 組織 ID を把握している ② 対象プロジェクトで課金が有効 ③ Google Cloud CLI がインストール・初期化済み (gcloud init) ④ 上表の IAM ロールが付与されている
1カスタム制約を作成する

constraint-require-pkce.yaml を保存し (上記 YAML 参照)、組織に登録します。3LO かつ PKCE 無効の場合に作成・更新を拒否する制約です。

Bash 制約の登録と確認 
gcloud org-policies set-custom-constraint constraint-require-pkce.yaml

# 制約が登録されたことを確認
gcloud org-policies list-custom-constraints --organization=ORGANIZATION_ID
2組織のポリシーで制約を有効化する
YAML policy-require-pkce.yaml 
name: projects/PROJECT_ID/policies/custom.requirePkceFor3LO
spec:
  rules:
    - enforce: true
Bash ドライラン検証からライブ適用へ 
# まずはドライランで検証
gcloud org-policies set-policy policy-require-pkce.yaml --update-mask=dryRunSpec

# 意図どおりであればライブポリシーとして適用
gcloud org-policies set-policy policy-require-pkce.yaml --update-mask=spec

# ポリシーの一覧を確認
gcloud org-policies list --project=PROJECT_ID

ポリシーの反映には最大 15 分かかります。適用後は約 2 分待つと強制が始まります。

💡 メリット

💼 ビジネス面

✓AI エージェントのガバナンスを予防的に実現: 監査による事後検出ではなく、リソース作成時点で組織のセキュリティ要件を強制。エージェントの認証設定に起因するリスクを構造的に低減
✓追加コストなしで適用可能: Organization Policy Service は事前定義の制約もカスタムの組織のポリシーも無償で提供
✓GA によるプロダクション適用: Pre-GA Offerings Terms の制約を受けずに本番組織へ正式に展開できる

🔧 技術面

✓フィールド単位の粒度: IAM ロールでは表現できない「設定値レベル」の制御を CEL 条件で記述できる
✓リソース階層による一元管理: 組織・フォルダ・プロジェクトのいずれかに適用すれば配下に継承。プロジェクトごとの個別設定が不要
✓ドライランによる安全な導入: 既存ワークロードへの影響を事前に把握してから強制モードへ移行できる
✓既存のカスタム制約運用に統合: IAM allow policy、managed workload identity、Workload Identity Federation、Privileged Access Manager などと同じ gcloud org-policies ワークフローで管理できる

⚠️ デメリット・制約事項

🚧 制限事項
  • 対応リソースは現時点で agentidentity.googleapis.com/AuthProvider のみ
  • UPDATE のみを指定したカスタム制約は非サポート (CREATE または CREATE + UPDATE を使用)
  • CEL 条件は最大 1,000 文字、制約 ID は最大 70 文字の長さ制限
  • ほとんどのリソースタイプで 1 タイプあたり最大 20 個のカスタム制約という上限
  • クライアントシークレットに相当するフィールドは参照可能フィールドに含まれず、シークレット値そのものを条件に使えない
🤔 考慮すべき点
  • ポリシー反映に最大 15 分のラグがあるため、CI/CD パイプラインでの検証タイミングに注意
  • ALLOW は条件に明示されないケースをすべてブロックするため、許可リスト方式では条件の網羅性を十分に検証する
  • UPDATE を含む制約の適用前に、既存 AuthProvider の棚卸しを行うことが望ましい (違反状態のリソースは違反解消以外の変更がブロックされる)
  • 表示名・制約 ID・説明はエラーメッセージに露出する可能性があるため、PII や機密情報を含めない
  • Agent Identity auth manager 自体の認証方式 (3LO / 2LO / API キー) は Preview 段階の項目があるため、ポリシー設計時にローンチステージを確認する

🎯 ユースケース

🔐 ユースケース 1: 3-legged OAuth プロバイダで PKCE を必須化する

シナリオ: エージェントがユーザーの権限を借用して外部 SaaS (Jira、GitHub など) にアクセスする 3LO フローを社内標準としているが、認可コード横取り攻撃を防ぐため PKCE を必ず有効にしたい。

YAMLcustom.requirePkceFor3LO
name: organizations/ORGANIZATION_ID/customConstraints/custom.requirePkceFor3LO
resourceTypes:
  - agentidentity.googleapis.com/AuthProvider
methodTypes:
  - CREATE
  - UPDATE
condition: "has(resource.authProviderTypeParams.threeLeggedOauth) && resource.authProviderTypeParams.threeLeggedOauth.enablePkce == false"
actionType: DENY
displayName: Require PKCE for 3LO
description: All new 3-legged OAuth authentication providers must have PKCE enabled.

効果: PKCE 無効の 3LO プロバイダは作成・更新の時点で拒否され、組織全体で PKCE 適用が保証されます。

🚫 ユースケース 2: 2-legged OAuth プロバイダの利用を禁止する

シナリオ: マシン間認証には社内標準の別方式を用いる方針であり、2LO プロバイダの新規作成を組織として禁止したい。

YAMLcustom.disallow2LO
name: organizations/ORGANIZATION_ID/customConstraints/custom.disallow2LO
resourceTypes:
  - agentidentity.googleapis.com/AuthProvider
methodTypes:
  - CREATE
condition: "has(resource.authProviderTypeParams.twoLeggedOauth)"
actionType: DENY
displayName: Disallow 2LO
description: 2-legged OAuth AuthProviders are not allowed.

効果: 2LO の認証プロバイダが新規に作られなくなり、認証方式の標準化を強制できます。

📝 ユースケース 3: すべての AuthProvider に説明文を必須化する

シナリオ: エージェントの認証プロバイダが増えるにつれ用途が不明なリソースが発生しており、運用・監査のために説明文を必ず記載させたい。

YAMLcustom.requireAuthProviderDescription
name: organizations/ORGANIZATION_ID/customConstraints/custom.requireAuthProviderDescription
resourceTypes:
  - agentidentity.googleapis.com/AuthProvider
methodTypes:
  - CREATE
  - UPDATE
condition: "resource.description == ''"
actionType: DENY
displayName: Require description
description: All AuthProviders must have a description.

効果: 説明が空の AuthProvider は作成・更新できなくなり、リソースの棚卸しやインシデント対応時の追跡性が向上します。

💰 料金・利用可能リージョン

💵 料金: Organization Policy Service は、事前定義の制約およびカスタムの組織のポリシーを含めて無償で提供されます。 今回のアップデートによる追加料金は発生しません。 なお、ポリシーの適用対象となる Agent Identity や、エージェントをホストする Google Cloud サービス側の料金は別途発生します。
🌏 利用可能リージョン: Organization Policy はリソース階層 (組織・フォルダ・プロジェクト) に対して適用されるサービスであり、 リージョン単位の指定はありません。適用対象の AuthProvider リソースはロケーションを持ち、 公式ドキュメントの例では --location=global が使用されています。

📝 まとめ

AI エージェントを本番運用する組織にとって、エージェントの認証設定は新たな攻撃面であり、 その設定値を組織レベルで予防的に強制できるようになったことは大きな前進です。
