📋 概要

AlloyDB for PostgreSQL のリードプールインスタンスにおけるオートスケーリング機能に、新たにクールダウン期間（cooldown period）を設定できる機能が追加されました。不必要なスケールイン・スケールアウトの繰り返し（フラッピング）を防止し、コスト効率とパフォーマンスのバランスを最適化できます。

💡 ポイント: クールダウン期間は、AlloyDB がリードプールインスタンスのリソース使用状況をオートスケーリングアルゴリズムに反映するまでの待機時間を秒単位で定義するパラメータです。デフォルト値は 300 秒（5 分）で、--autoscaler-cool-down-period-seconds フラグで変更可能です。

Before / After 比較

❌ Before（アップデート前）

  • クールダウン期間をカスタマイズ不可
  • 短期的な負荷変動で不要なスケーリング発生
  • スケールイン待機時間が固定
  • 周期的トラフィックでフラッピング発生

✅ After（アップデート後）

  • クールダウン期間を自由に設定可能
  • ワークロード特性に合わせた感度調整
  • 不要なスケーリングイベントを削減
  • 安定運用とコスト最適化の両立

⚙️ 主要機能

🕐 1. クールダウン期間の設定

→--autoscaler-cool-down-period-seconds パラメータで秒単位でクールダウン期間を設定可能
→デフォルト値は 300 秒（5 分）
→スケーリング判定前のリソース使用状況の安定化待機時間として機能

⏱️ 2. スケールイン遅延の制御

→スケールイン時: max(10分, クールダウン期間) の待機時間を適用
→CPU 使用率がターゲット値を下回り続けるまで待機
→例: クールダウン 660 秒 = スケールイン前に 11 分間の安定確認が必要

🔗 3. 既存ポリシーとの統合

→CPU 使用率ベースポリシーとの併用が可能
→スケジュールベースポリシーとの併用が可能
→複数ポリシー有効時は、最も多くのノードを推奨するポリシーが選択される

🚀 設定方法

前提条件

✓Google Cloud プロジェクトが作成済みで AlloyDB API が有効化
✓AlloyDB クラスタとプライマリインスタンスが作成済み
✓gcloud CLI がインストールされ認証済み
✓roles/alloydb.admin または同等の IAM ロールが付与済み

ステップ 1: 新規リードプールの作成

Bash 
gcloud beta alloydb instances create my-read-pool \
    --instance-type=READ_POOL \
    --read-pool-node-count=2 \
    --region=us-central1 \
    --cluster=my-cluster \
    --project=my-project \
    --enable-autoscaler \
    --autoscaler-max-node-count=5 \
    --autoscaler-cool-down-period-seconds=600 \
    --autoscaler-target-cpu-usage=0.7 \
    --machine-type=n2-highmem-4

クールダウン期間 600 秒（10 分）、CPU ターゲット 70%、ノード数 2-5 の設定例

ステップ 2: 既存インスタンスの更新

Bash 
gcloud beta alloydb instances update my-read-pool \
    --region=us-central1 \
    --cluster=my-cluster \
    --project=my-project \
    --enable-autoscaler \
    --autoscaler-cool-down-period-seconds=900

クールダウン期間を 900 秒（15 分）に変更する例

ステップ 3: 状態確認

Bash 
gcloud alloydb instances describe my-read-pool \
    --region=us-central1 \
    --cluster=my-cluster \
    --project=my-project \
    --view=FULL \
    --format="yaml(nodes)"

✅ メリット

ビジネス面

📈予測可能な運用コスト: スケーリング頻度を制御し、月次コストの予測精度が向上
🎯SLA 安定化: フラッピングによる接続切断やキャッシュミスを回避

技術面

🛡️フラッピング防止: 短期的な負荷変動に対する過剰反応を抑制
⚡キャッシュ効率向上: ノードの増減が減少し、キャッシュが温まった状態を維持
🔌既存接続への影響最小化: スケーリング頻度低下で長期接続アプリへの影響を低減
🔧柔軟なチューニング: バースト型・周期型・定常型に応じた最適値を設定可能

⚠️ デメリット・制約事項

制限事項
  • プレビュー機能であり「Pre-GA Offerings Terms」の対象。サポートが限定される場合がある
  • gcloud beta コマンドが必要（GA 版では利用不可）
  • クラスタ全体で最大 20 ノードの制限は変更なし
  • クールダウン期間を短く設定しすぎると、フラッピング防止効果が薄れる
💡 考慮すべき点
  • 長いクールダウン設定時、急激な負荷増加に対するスケールアウト反応が遅延する可能性
  • スケールイン待機時間は max(10分, クールダウン期間) のため、10 分未満設定でもスケールイン速度は不変
  • 新ノードのキャッシュウォーミングに数分かかるため、別途考慮が必要
  • 長期接続利用時、新規ノードへの分散には新しいクライアント接続作成が必要

💡 ユースケース

🛒 ユースケース 1: EC サイトのセール期間対応

シナリオ: 定期セール時にトラフィックが急増するが、瞬間的なスパイクでスケールアウトが繰り返されるのを防ぎたい。

Bash 
gcloud beta alloydb instances update ecommerce-read-pool \
    --region=asia-northeast1 \
    --cluster=ecommerce-cluster \
    --project=my-ecommerce-project \
    --enable-autoscaler \
    --autoscaler-max-node-count=10 \
    --autoscaler-cool-down-period-seconds=600 \
    --autoscaler-target-cpu-usage=0.6 \
    --autoscaler-set-schedule=sale-period \
    --autoscaler-schedule-cron-exp="0 9 * * 1-5" \
    --autoscaler-schedule-duration-seconds=36000 \
    --autoscaler-schedule-time-zone=Asia/Tokyo \
    --autoscaler-schedule-min-node-count=5
効果: スケジュールポリシーで最低 5 ノードを確保しつつ、クールダウン 600 秒で瞬間的な負荷変動でのスケーリング頻度を抑制。

📊 ユースケース 2: バッチ処理と OLTP の混在環境

シナリオ: 日中は OLTP、夜間はバッチ処理。バッチ処理開始時の短期的な CPU スパイクによる不要なスケールアウトを防ぎたい。

Bash 
gcloud beta alloydb instances update analytics-read-pool \
    --region=us-central1 \
    --cluster=analytics-cluster \
    --project=my-analytics-project \
    --enable-autoscaler \
    --autoscaler-cool-down-period-seconds=900 \
    --autoscaler-target-cpu-usage=0.7
効果: バッチ処理開始時の一時的なスパイク（数分間）に対してスケールアウトが発動せず、不要なノード追加コストを回避。

💰 料金情報

クールダウン期間の設定自体には追加料金は発生しません。料金はオートスケーリングにより実際に稼働するノード数に基づいて算出されます。

💡 コスト削減のヒント: クールダウン期間を適切に設定することで、不要なノード増加を防ぎ月額コストを削減できます。1-3 年の Committed Use Discount (CUD) も利用可能です。
