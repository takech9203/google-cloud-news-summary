2026-06-23

☁️ 概要

BigQuery パイプラインに、テーブル更新をトリガーとしたイベント駆動型スケジューリングが Preview として追加されました。特定の BigQuery テーブルへの更新を検知して、パイプライン実行を自動トリガーできるようになります。

従来の時間ベースのスケジューリング (cron 形式) に加え、データの変更に応じてリアクティブにパイプラインを実行できるため、データの鮮度を保ちつつ不要な実行を削減できます。BigQuery パイプラインは Dataform を基盤としており、SQL クエリ、ノートブック、データ準備のコードアセットを順序立てて実行するワークフローを構築できます。

❌ Before (従来の課題)

  • 固定スケジュール (時間ベース) でしか設定できない
  • ソーステーブルの更新タイミングとのずれ
  • データ更新がなくても不要なパイプライン実行が発生
  • イベント駆動に外部ツール (Cloud Composer 等) が必要

✅ After (改善後)

  • テーブル更新検知で自動パイプライン実行
  • ALL / ANY 条件で柔軟なトリガー定義
  • 最小実行間隔・最大待機時間で細かく制御
  • BigQuery 内でイベント駆動を完結

⚡ 主要機能

🎯 イベント駆動型パイプライン実行

指定した BigQuery テーブルへの更新を検知して、パイプラインの実行を自動トリガー。固定スケジュールではなくデータ変更に応じたリアクティブな実行が可能。

🔀 柔軟なトリガー条件定義

単一テーブル監視: 1 つのテーブル更新でトリガー
ALL 条件: 全テーブル更新で発火
ANY 条件: いずれかのテーブル更新で発火

⏱️ 実行間隔の制御パラメータ

Min Execution Duration: 最小発火間隔 (3分-24時間)
Max Wait Duration: 強制発火期間 (1秒-7日間)

🔐 認証方式の選択

サービスアカウントによる実行、または Google アカウントのユーザー認証情報 (Preview) による実行が選択可能。

🔧 技術仕様

パラメータ 説明 設定範囲 デフォルト
Trigger Condition トリガー条件 (ALL/ANY) ALL または ANY -

Step 1: パイプラインの選択

Google Cloud コンソール → BigQuery → Explorer からプロジェクトを展開 → Pipelines をクリック → 対象パイプラインを選択

Step 2: トリガーの作成

パイプライン詳細画面 → 「Trigger」クリック → トリガー名入力 → 認証方式を選択 (サービスアカウント or ユーザー認証情報)

Step 3: トリガー条件の設定

Configuration Type → 「Trigger (event-based execution)」選択 → 監視テーブル追加 → Trigger Condition で ALL/ANY を選択

Step 4: オプション設定

(任意) Max Wait Duration / Min Execution Duration を設定 → 「Create schedule」で完了

✅ メリット

💼 ビジネス面

✓ データ鮮度の向上: ソースデータ更新後、最短 3 分でパイプライン実行
✓ コスト最適化: 不要なパイプライン実行を削減し計算コスト抑制
✓ 運用工数削減: 外部オーケストレーションツールの構築・運用が不要

🔧 技術面

✓ イベント駆動の簡素化: BigQuery ネイティブで外部依存を排除
✓ 柔軟な条件設定: ALL/ANY + 実行間隔パラメータで複雑な依存関係を表現
✓ Dataform 基盤の信頼性: ワークフロー管理機能を活用した堅牢な制御

⚠️ デメリット・制約事項

⚠️ Preview 段階: サポートが限定的で SLA の対象外です。本番ワークロードへの適用は慎重に検討してください。
✗ ポーリングベースのため即時性に限界 (約 3 分の遅延)
✗ 監視テーブル数が多い場合、BigQuery API クォータを消費
✗ Google Cloud コンソールからのみ設定可能 (API/CLI 未対応の可能性)
✗ Min Execution Duration のデフォルト 3 分で高頻度更新時にスキップ発生の可能性

💡 ユースケース

🏢 ユースケース 1: データウェアハウスの段階的更新

シナリオ: ETL パイプラインでソーステーブルにデータがロードされた後、派生テーブルやマートテーブルを自動的に更新したい。ソースデータの到着タイミングが不定期。

効果: ソーステーブルの更新検知で自動的に下流の変換処理が実行。データ鮮度向上 + 不要実行コスト削減。

🔗 ユースケース 2: 複数データソースの統合分析

シナリオ: 複数部門から異なるタイミングで BigQuery テーブルにデータ投入。全ソーステーブル更新後に統合レポートを生成したい。

効果: ALL 条件のトリガーで全テーブル更新を確認してから統合処理実行。データ整合性が保証される。

🤖 ユースケース 3: ML モデルの自動再学習

シナリオ: 学習データテーブルに新しいデータが追加された際に、ノートブックによるモデル再学習パイプラインを自動実行したい。

効果: ANY 条件 + Min Execution Duration の組み合わせで、更新頻度に応じた適切な間隔でモデル再学習。

💰 料金情報

✅ トリガーベーススケジューリング自体に追加料金はありません。

ただし、以下のコストが発生します:

→ パイプライン実行時の BigQuery クエリ実行コスト (オンデマンドまたはリザベーション)
→ ノートブック実行時の Colab Enterprise ランタイムコスト
→ ポーリングによる BigQuery API 呼び出し (API クォータに影響)
