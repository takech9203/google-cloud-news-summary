❌ Before (アップデート前の課題)

  • OAuth 2.0 の非厳格なサブリソースマッチングで redirect_uri 検証をバイパス可能。<EnforceStrictCallbackURI> が強制されていなかった
  • <JythonURL> JAR で org.python.core.PyReflected を定義すると無制限の pythonns: 保護ドメインが付与され、サンドボックスをエスケープ可能
  • SSE ストリームの終了理由・送信バイト数を PostClientFlow で判別・ログ記録する手段がなかった
  • LLM トークン Analytics は LLMTokenQuota ポリシーが前提。SSE では <EventFlow> なしに記録されず、Anthropic プロンプトキャッシュも未集計
  • MCP レスポンスが非標準の application/vnd.mcp+json。バックエンドの JSON-RPC エラーが合成エンベロープで上書き
  • Message Processor のメモリ / コネクションカウントリークでオートスケーリング指標が水増しされ、レプリカ最大張り付き・CPU 枯渇の恐れ
  • 120 秒超のストリーミングレスポンスが大きなリクエストボディのバッファ時に切り詰め
  • Envoy ext_proc パスのトレーススパンが受信 W3C / B3 コンテキストを引き継がず新規トレースを開始

✅ After (アップデート後の改善)

  • JavaCallout / Script / JavaScript のサンドボックス強化。OAuth redirect_uri バイパスと Jython エスケープを修正
  • 新フロー変数 response.event.stream.state / response.event.stream.content.length で SSE 終了状態 (COMPLETE / UPSTREAM_ABORT / DOWNSTREAM_ABORT / TIMEOUT) と送信バイト数をログ可能
  • LLM Analytics カノニカルフィールドがポリシー / ストリーミングの有無にかかわらず自動入力。Anthropic プロンプトキャッシュ読み書きトークンも含む
  • MCP レスポンスが仕様準拠の application/json に。バックエンド発の JSON-RPC エラーをそのまま透過
  • Message Processor のリークを修正し、オートスケーリングの異常動作リスクを解消
  • 分散トレーススパンが受信 W3C / B3 トレースコンテキストを継続し、エンドツーエンドのトレースがつながる

🤖 2. SSE / LLM / MCP プロキシ関連の修正

📡 582789138: SSE ストリーム状態のフロー変数を追加

response.event.stream.state と response.event.stream.content.length を追加。PostClientFlow で読み取り可能で、MessageLogging が COMPLETE / UPSTREAM_ABORT / DOWNSTREAM_ABORT / TIMEOUT の終了種別と送信バイト数をログ記録できる。response.event.processed.count と組み合わせてイベント数も取得可能。

📊 571610415: LLM トークン Analytics の自動入力

ai_llm_canonical_cached_prompt_token_count、ai_llm_canonical_response_token_count (thinking トークン含む)、ai_llm_canonical_thinking_token_count、ai_llm_canonical_model_name、ai_llm_canonical_model_provider が LLMTokenQuota ポリシーの有無にかかわらず LLM プロバイダーの応答から入力される。ai_llm_canonical_prompt_token_count には Anthropic のプロンプトキャッシュ読み取り / 書き込みトークンを含むようになった。ストリーミング (SSE) レスポンスでも <EventFlow> なしでトークン使用量の Analytics 列が記録される。

🔌 581734420: MCP プロキシのレスポンス形式を修正

Content-Type が非標準の application/vnd.mcp+json から仕様準拠の application/json に。バックエンド発の JSON-RPC エラー (例: -32020 HeaderMismatch、-32022 UnsupportedProtocolVersion、-32601 Method not found) が Apigee の合成エンベロープで上書きされずそのまま透過。非 MCP (LLM) プロキシの挙動変更はなし。

🛡️ 583643203 / 544820285 / 568062600: Model Armor 連携・セキュリティヘッダー・トレース

SanitizeUserPrompt / SanitizeModelResponse が MA-Client-Correlation-Id ヘッダーを Model Armor に転送。LLM/MCP フォーマッターのゲートウェイレスポンスに X-Content-Type-Options: nosniff を付与。Semantic Governance のトレースがスキップしたリクエストを含め各リクエストの LLM ファミリーとモデルを記録。

🧰 3. 安定性・可観測性・WS-Security の修正

🧠 579213551: Message Processor のメモリリーク修正

プロキシデプロイ・環境リロード時のメモリリークを修正。コンパイル済み OASValidation 仕様がコンテンツハッシュで共有され、置き換えられた / 失敗した環境ロードのリソースが解放される。

📈 583672651: コネクションカウントリーク修正 (オートスケーリング正常化)

管理ポート (例: 8843) のランタイム HTTP サーバーにおけるコネクションカウントリークを修正。オートスケーリング指標の水増しによるレプリカ最大張り付き・クラスタ CPU 枯渇の問題が解消。

⏱️ 576448578: 長時間ストリーミングレスポンスの切り詰め修正

プロキシエンドポイントが大きなリクエストボディをバッファした場合に、受信接続タイムアウト (120 秒) を超えるストリーミングターゲットレスポンスが切り詰められる問題を修正。

🔍 572000222: W3C / B3 トレースコンテキストの継続

Envoy ext_proc パス上の Apigee 分散トレーススパンが、新しいトレースを開始せず呼び出し元の受信 W3C または B3 トレースコンテキストを継続するようになった。

✍️ 582791025 / 582790275: WS-Security 署名の修正

SignatureConfirmation 値が重複・失敗しなくなり、署名付き確認とその他の署名要素が検証可能に。max_lifetime を使った署名検証がすべてのドキュメントを拒否する問題も修正。

🐞 582790249 / 582790971 / 582790557: デバッグ・API パスの修正

メッセージのない例外で失敗したポリシーの Execution エントリがデバッグトレースから欠落する問題、デバッグセッションでマスクされていないペイロード等が表示される問題を修正。Management API のパスが登録済みベースパスとパスセグメント単位でのみマッチするように (例: /optimizer が /o にルーティングされない)。インフラストラクチャとライブラリも更新。

🔧 技術仕様

🔑 OAuth 2.0 redirect_uri 検証の背景

OAuthV2 ポリシーの認可コードグラントでは、デベロッパーアプリに登録された Callback URL とリクエストの redirect_uri の一致検証が行われます。デフォルトは前方一致 (forward match) であり、完全一致を強制するには組織プロパティ features.isStrictOAuthUriValidation = true の設定が必要です。本リリースでは、非厳格なサブリソースマッチング時に検証をバイパスできる問題が修正され、GenerateAuthorizationCode ポリシーで <EnforceStrictCallbackURI> が強制されるようになりました。

📡 新しい SSE ストリームフロー変数

フロー変数内容
response.event.stream.stateストリームの終了状態: COMPLETE / UPSTREAM_ABORT / DOWNSTREAM_ABORT / TIMEOUT
response.event.stream.content.lengthクライアントへ送信されたバイト数
response.event.processed.count (既存)ストリームごとの処理済みイベント数 (上記と組み合わせて使用)

これらは PostClientFlow で読み取り可能で、MessageLogging ポリシーによるストリーム終了ログの記録に使用できます。

📝 PostClientFlow での SSE 終了状態ロギング例

<MessageLogging name="ML-sse-stream-state">
  <CloudLogging>
    <LogName>projects/{organization.name}/logs/sse-stream-log</LogName>
    <Message contentType="application/json">

<!-- PostClientFlow に配置 -->
<PostClientFlow name="PostClientFlow">

    <Step>

    </Step>
  </Response>
</PostClientFlow>

🤔 考慮すべき点 (挙動変更)

⚠️ MCP プロキシの挙動変更: Content-Type が application/vnd.mcp+json から application/json に変わり、バックエンド発の JSON-RPC エラーが透過されるようになる。MCP クライアント側で旧 Content-Type や Apigee の合成エラーエンベロープに依存した処理がある場合は影響を確認すること (非 MCP プロキシへの影響はなし)。
⚠️ OAuth 検証の厳格化: <EnforceStrictCallbackURI> の強制により、これまで非厳格なサブリソースマッチングで通過していた redirect_uri が拒否される可能性がある。認可コードフローを利用するアプリの Callback URL 登録を確認すること。
⚠️ Management API のパスマッチング変更: パスセグメント単位の完全一致になるため、前方一致に依存した API 呼び出し (例: /optimizer が /o にマッチすることを前提とした呼び出し) があれば修正が必要。
⚠️ カスタムコードポリシー: サンドボックス強化により、JavaCallout / Script / JavaScript / Jython でサンドボックスの境界に依存した (本来許可されない) 操作を行っていたカスタムコードは動作しなくなる可能性がある。

🎯 ユースケース

📡 ユースケース 1: LLM ストリーミング API の切断監視

シナリオ: Apigee X を LLM の AI ゲートウェイとして使用し、SSE ストリーミングでレスポンスを配信している。クライアントから「応答が途中で切れる」という報告があるが、タイムアウトなのか上流 / 下流の中断なのか判別できない。

XML 異常終了のみログ記録する条件付きステップ 
<PostClientFlow name="PostClientFlow">
  <Response>
    <Step>
      <Name>ML-sse-stream-state</Name>
      <Condition>response.event.stream.state != "COMPLETE"</Condition>
    </Step>
  </Response>
</PostClientFlow>

効果: response.event.stream.state により TIMEOUT / UPSTREAM_ABORT / DOWNSTREAM_ABORT を区別してログに記録でき、切断の原因切り分け (バックエンド起因かクライアント起因か) が迅速になる。

💰 ユースケース 2: ポリシー設定なしの LLM トークンコスト集計

シナリオ: 複数チームが Apigee X 経由で Gemini / Anthropic などの LLM API を利用しており、チームごとのトークン消費量を集計してコストを配賦したい。これまでは LLMTokenQuota ポリシーの付与が必要で、ストリーミングレスポンスでは集計できないプロキシがあった。

効果: LLMTokenQuota ポリシーや <EventFlow> の有無にかかわらず、ストリーミングを含むすべての LLM プロキシで ai_llm_canonical_* フィールドが自動記録されるため、Analytics のカスタムレポートだけでチーム / アプリ単位のトークン消費 (Anthropic のプロンプトキャッシュ読み書きトークン含む) を正確に集計できる。

🔌 ユースケース 3: MCP サーバーの標準準拠ゲートウェイ

シナリオ: Apigee X を MCP (Model Context Protocol) サーバーのゲートウェイとして公開しており、サードパーティの MCP クライアントから「Content-Type が標準でない」「エラーの詳細が得られない」という互換性問題が報告されていた。

効果: レスポンスが仕様準拠の application/json となり、バックエンドの JSON-RPC エラー (-32020、-32022、-32601 など) がそのまま透過されるため、標準的な MCP クライアントがエラーを正しく解釈でき、相互運用性が向上する。
