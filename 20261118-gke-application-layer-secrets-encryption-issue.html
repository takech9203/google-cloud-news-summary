☁️ Google Kubernetes Engine ⚠️ 既知の問題 (Known Issue)

🔐 GKE アプリケーションレイヤ シークレット暗号化
Secrets のみ暗号化される既知の問題

対象機能: アプリケーションレイヤ シークレット暗号化 (Application-layer Secrets Encryption)
📅 2026-11-18

📌 概要

GKE バージョン 1.35 / 1.36 / 1.37 において、コントロール プレーンがクラスタ状態を Spanner に保存しているクラスタで、新規または既存クラスタに アプリケーションレイヤ シークレット暗号化を有効化した場合、本来であればすべての Kubernetes API オブジェクトが暗号化される (ALL_OBJECTS_ENCRYPTION_ENABLED) はずが、 Kubernetes Secrets のみが暗号化される (ENCRYPTED) 状態になる既知の問題が公表されました。

GKE 1.35 以降では、クラスタ状態のキーバリュー ストアが Spanner の場合、アプリケーションレイヤ シークレット暗号化は すべての Kubernetes API オブジェクトを Cloud KMS 鍵で暗号化する仕様です (etcd の場合は主に Secrets を暗号化)。今回の問題により、新たに暗号化を構成したクラスタではこの 「全オブジェクト暗号化」が適用されず、Secrets のみの暗号化にフォールバックしてしまいます。

GKE 1.37

🚨 この問題による影響
✗GKE 1.35/1.36/1.37 の Spanner ベースのクラスタで新たに暗号化を有効化すると、期待される全オブジェクト暗号化ではなく Secrets のみの暗号化 (ENCRYPTED) になる
✗ENCRYPTED 状態のクラスタでは、Cloud KMS 鍵ローテーション後に Secrets の手動再暗号化が必要 (全オブジェクト暗号化の場合は不要)
✗Secrets 以外の Kubernetes API オブジェクトは CMEK による追加の暗号化レイヤで保護されない (Google Cloud のデフォルトの保存時暗号化は引き続き適用される)
✅ 影響を受けないケース
✓すでに ALL_OBJECTS_ENCRYPTION_ENABLED 状態にあるクラスタは、引き続きすべての Kubernetes API オブジェクトが暗号化される
✓etcd ベースのクラスタは元々 Secrets を主な暗号化対象とする仕様のため、挙動の変化はない

GKE 1.35 以降では、クラスタ状態を保持するキーバリュー ストアによって暗号化対象が異なります。

🗄️Spanner: すべての Kubernetes API オブジェクトを暗号化 (本来の仕様)
📦etcd: 主に Secrets を暗号化
💡 ポイント: 今回の問題は、Spanner ベースのクラスタで新規に暗号化を構成した際に、 etcd 相当の「Secrets のみ」の暗号化スコープになってしまうものです。

🩺 確認方法

💻 暗号化状態の確認 (gcloud)

自クラスタがこの問題の影響を受けているかどうかは、databaseEncryption.state の値で確認できます。

Bash 暗号化状態の確認 
gcloud container clusters describe CLUSTER_NAME \
  --location=CONTROL_PLANE_LOCATION \
  --format='value(databaseEncryption.state)' \
  --project=CLUSTER_PROJECT_ID
出力値意味
ALL_OBJECTS_ENCRYPTION_ENABLED✅ クラスタ状態データベース内のすべての Kubernetes API オブジェクトが暗号化されている (影響なし)
ENCRYPTED⚠️ Secrets のみが暗号化されている (本問題の影響を受けている可能性あり)
DECRYPTED➖ アプリケーションレイヤ シークレット暗号化が無効

🛠️ 対応・運用上の注意

🔄 ENCRYPTED 状態のクラスタで必要な運用

ENCRYPTED 状態 (Secrets のみ暗号化) のクラスタでは、Cloud KMS 鍵のローテーション後、 既存の Secrets は旧バージョンの KEK で暗号化されたままになります。新しい KEK バージョンで保護するには、 Secrets の手動再暗号化が必要です。

Bash Secrets の手動再暗号化 
# 鍵ローテーション後、新バージョンが整合するまで 3 時間以上待機してから実行
kubectl get secrets --namespace=NAMESPACE -o json \
  | kubectl annotate --overwrite -f - encryption-key-rotation-time="TIME"
→NAMESPACE: Secrets を更新する Namespace。Standard クラスタでは --all-namespaces フラグでクラスタ内のすべての Secrets を一括更新可能。Autopilot クラスタでは自分が所有する Namespace のみ更新可能
→TIME: ローテーション時刻を示す文字列 (例: 20261118-090909)
✅ 補足: 全オブジェクト暗号化 (ALL_OBJECTS_ENCRYPTION_ENABLED) のクラスタでは、この手動再暗号化は不要です。

🚫 鍵バージョン破棄時の注意

🚨 重要: クラスタ状態データベース内のオブジェクトの暗号化に使用中の KMS 鍵バージョンを破棄すると、 クラスタが劣化状態になり最終的に動作不能になります。ENCRYPTED 状態のクラスタでは 再暗号化が完了するまで旧 KEK バージョンを破棄しないよう、特に注意が必要です。

💡 考慮すべき点

📋CMEK による全オブジェクト暗号化をコンプライアンス要件として採用している場合、GKE 1.35/1.36/1.37 で新規に構成したクラスタが要件を満たしていない可能性があるため、databaseEncryption.state の確認を推奨
🛡️ENCRYPTED 状態であっても Google Cloud のデフォルトの保存時暗号化は引き続きすべてのデータに適用される (CMEK による追加レイヤが Secrets に限定されるのみ)
🔄新規構成クラスタで全オブジェクト暗号化を復元する修正が進行中のため、修正リリース後に状態を再確認するとよい
⏰Cloud KMS の鍵ローテーションを自動化している場合は、ENCRYPTED 状態の間、ローテーションに合わせた Secrets 再暗号化 (CronJob などによる自動化) の運用を組み込む必要がある

🔗 関連サービス・機能

🔑 Cloud KMS アプリケーションレイヤ シークレット暗号化の KEK を管理。鍵のローテーション (自動/手動)、鍵バージョンの破棄・復元を担う
🔐 Cloud HSM / Cloud EKM Cloud KMS がサポートする保護レベルの鍵も KEK として利用可能 (この場合 Cloud KMS の暗号リクエスト クォータを消費)
🗄️ Spanner GKE コントロール プレーンのクラスタ状態データベースとして利用されるキーバリュー ストア。本問題は Spanner ベースのクラスタが対象

📝 まとめ

GKE 1.35/1.36/1.37 の Spanner ベースのクラスタで新規にアプリケーションレイヤ シークレット暗号化を 有効化すると、全オブジェクト暗号化ではなく Secrets のみの暗号化になる既知の問題です。

→該当バージョンで暗号化を構成したクラスタは gcloud container clusters describe で databaseEncryption.state を確認する
→ENCRYPTED の場合は Cloud KMS 鍵ローテーション後の Secrets 手動再暗号化を運用に組み込む
