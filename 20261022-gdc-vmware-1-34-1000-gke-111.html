バージョン 1.34.1000-gke.111 リリース

Google Distributed Cloud for VMware GA (一般提供) 🔒 脆弱性修正 🔧 CA ローテーション問題の恒久修正
📅 リリース日: 2026-10-22

📝 概要

GDC (software only) for VMware のパッチバージョン 1.34.1000-gke.111 がダウンロード可能になりました。 本バージョンは Kubernetes v1.34.7-gke.200 上で動作します。 オンプレミスの VMware vSphere 環境で GKE クラスタを運用している IT 管理者・オペレーターが対象です (ベアメタル版のアップデートは別レポートで扱います)。

セキュリティ脆弱性の修正に加え、クラスタの認証局 (CA) を過去にローテーションしていた場合に、 アドバンストクラスタへの更新・アップグレード時にコントロールプレーンノードの参加 (join) が失敗する問題が修正されました。 この問題は 1.33 / 1.34 で確認されていた既知の問題で、恒久的な修正は 1.34.1000 以降で利用可能と公式に明記されています。

❌ Before: アップデート前の課題

  • CA ローテーション後、アクティブな CA はバージョン番号付き Secret (cluster-ca-cert-2 など) に格納されるが、gkectl が ca-rotation-stage ConfigMap を確認せず、バージョン番号なしの Secret を参照
  • バージョン番号なしの cluster-ca-cert Secret がない場合 (ユーザークラスタで一般的)、secrets "cluster-ca-cert" not found エラーで失敗
  • 古い CA が残っている場合 (管理クラスタで一般的)、古い公開鍵ハッシュがピン留めされ、ノード参加が none of the public keys ... are pinned エラーで失敗
  • kubeconfig が古い CA で更新されると kubectl が crypto/rsa: verification error で失敗
  • CA Secret の手動同期やブートストラップクラスタ再作成 (--reuse-bootstrap-cluster=false) といった複雑な回避策が必要

✅ After: アップデート後の改善

  • CA ローテーション済みのクラスタでも、アドバンストクラスタへの移行時にコントロールプレーンノードが正しく参加できる (恒久修正)
  • Vulnerability fixes に記載された脆弱性が修正され、セキュリティ態勢が改善
  • Kubernetes v1.34.7-gke.200 ベースへの更新により、最新パッチが適用された状態で運用可能

🐛 修正された CA ローテーション問題の症状 (1.33 / 1.34 で確認されていたもの)

発生シナリオ症状
バージョン番号なしの cluster-ca-cert Secret が存在しない (ユーザークラスタで一般的) クラスタ準備中に failed to get user cluster ca secret from admin client: secrets "cluster-ca-cert" not found で失敗
バージョン番号なしの Secret にローテーション前の CA が残存 (管理クラスタで一般的) 古い CA の公開鍵ハッシュが kubeadm join 構成にピン留めされ、ノード参加が none of the public keys ... are pinned で失敗
gkectl が kubeconfig を古い CA で更新 kubectl コマンドが crypto/rsa: verification error で失敗

🛠️ 設定方法

✅ 前提条件

✓アップグレード前に管理クラスタとユーザークラスタの最新バックアップを取得しておく (アップグレードのベストプラクティスを参照)
✓アップグレードの概要でサポートされるバージョンスキューとバージョンルールを確認する
✓非アドバンストクラスタからアドバンストクラスタへのアップグレードでは、gkectl のバージョンをアップグレード先のターゲットバージョンと一致させる (この厳密なバージョン要件はアドバンストクラスタへのアップグレード時のみ適用)
✓非アドバンストクラスタからのアップグレードでは、コントロールプレーンとすべてのノードプールを同時に同じターゲットバージョンへアップグレードする (バージョンスキュー不可)

📦 ステップ 1: 管理ワークステーションとバンドルの準備

ダウンロードページから 1.34.1000-gke.111 を取得し、管理ワークステーションをアップグレードします。

🚀 ステップ 2: クラスタのアップグレード

Bash gkectl によるクラスタアップグレード 
# ユーザークラスタのアップグレード
gkectl upgrade cluster --kubeconfig ADMIN_KUBECONFIG --config USER_CLUSTER_CONFIG

# 管理クラスタのアップグレード
gkectl upgrade admin --kubeconfig ADMIN_KUBECONFIG --config ADMIN_CLUSTER_CONFIG
💡 ヒント: コントロールプレーンとノードプールを別々にアップグレードする方法を含む詳細な手順は、公式ドキュメント「クラスタのアップグレード」を参照してください。

✓最新 Kubernetes パッチの適用: Kubernetes v1.34.7-gke.200 ベースで運用できる

⚠️ 考慮すべき点

!GKE On-Prem API クライアント (Google Cloud コンソール、gcloud CLI、Terraform) でこのバージョンが利用可能になるまで、リリース後約 7〜14 日かかる
!サードパーティストレージベンダー利用時は、このリリースに対する認定状況をストレージパートナー一覧で確認する必要がある
!非アドバンストクラスタを 1.33 から 1.34 にアップグレードすると、クラスタは必ずアドバンストクラスタに変換される (非アドバンストのまま維持できるのは 1.32 → 1.33 のみ)
!アドバンストクラスタへの移行時、バンドルされた cert-manager が既存の cert-manager を自動的に上書きするため、カスタム構成がある場合は事前確認が必要

🎯 ユースケース

📌 ユースケース 1: CA ローテーション実施済みクラスタのアドバンストクラスタへのアップグレード

シナリオ: セキュリティポリシーに従い gkectl update credentials certificate-authorities rotate で CA ローテーションを実施済みの 1.33 クラスタを、アドバンストクラスタ (1.34) へアップグレードしたい。 これまでは既知の問題によりコントロールプレーンノードの参加が失敗し、手動での CA Secret 同期が必要だった。

✅ 効果: 1.34.1000-gke.111 には恒久修正が含まれるため、手動回避策なしでアップグレードを完了できる。

📌 ユースケース 2: 脆弱性対応としての定期パッチ適用

シナリオ: オンプレミスの VMware 環境で稼働する GDC クラスタに対し、 セキュリティ運用の一環として最新パッチを適用する。

✅ 効果: Vulnerability fixes に記載された脆弱性が解消され、セキュリティ態勢を維持できる。

💡 まとめ

GDC (software only) for VMware 1.34.1000-gke.111 は、脆弱性修正に加えて、 CA ローテーション済みクラスタのアドバンストクラスタ移行を妨げていた既知の問題の恒久修正を含む重要なパッチリリースです。

特に 1.33 / 1.34 で CA ローテーションを実施済みの環境では、本バージョンへのアップグレードにより 手動回避策なしで安全にアドバンストクラスタへ移行できるため、早期の適用を推奨します。 適用前にはバックアップの取得とストレージパートナーの認定状況の確認を忘れずに行ってください。
