📋 概要

Google Cloud は、Gemini Enterprise Agent Platform の Agent Gateway に対する Model Armor 統合を一般提供 (GA) として発表した。 Agent Gateway を通過するプロンプトとレスポンスに対して、組織のコンテンツセキュリティガードレールをインフラストラクチャレベルで一元的に適用できる。

🤖 ポイント: エージェント内部にフィルタリングロジックを実装することなく、ゲートウェイ層でプロンプトインジェクション、ジェイルブレイク攻撃、機密情報漏洩、有害コンテンツ生成を防止する。

⚡ 主要機能

🔄 双方向トラフィック保護

→Ingress: クライアント → エージェント間のリクエスト/レスポンス検査
→Egress: エージェント → 外部 LLM / MCP / A2A 通信を検査
→各方向に個別テンプレート適用可能

🚫 コンテンツセキュリティフィルター

→プロンプトインジェクション検知 (最大 10,000 トークン)
→ジェイルブレイク検知
→責任ある AI フィルター (ヘイトスピーチ、ハラスメント等)
→機密データ保護 (PII リダクション)
→悪意ある URL 検出

🎚️ 柔軟なエンフォースメント

→Inspect only: 検出のみ。テスト・チューニング段階向け
→Inspect and block: 検出+ブロック。本番運用向け

📡 ストリーミング対応

→リアルタイムストリーミングで無制限トークンサポート
→ADK エージェントの streamQuery メソッドに対応

📄 ドキュメントスクリーニング

→PDF, CSV, TXT, Microsoft Office (Word, PowerPoint, Excel)
→入力サイズ上限: 4 MB

🔧 技術仕様

対応プロトコルとペイロード

トラフィック方向 プロトコル サニタイズ対象
Ingress (Client-to-Agent) ADK (streamQuery) リクエスト / レスポンス
Egress (A2A) A2A v1 Send Message, Agent Card, JSON-RPC, HTTP+JSON/REST
Egress (MCP) MCP tools/call, prompts/get (リクエスト/レスポンス)
Egress (外部 LLM) OpenAI API 互換 Chat Completions, Responses, Embeddings

信頼度レベル設定

レベル 検出確率 誤検知リスク 推奨用途
High 違反がほぼ確実な場合のみ 極めて低い 本番環境 (中断なし重視)
Medium and above バランスの取れた検出 中程度 標準的なエンタープライズ用途
Low and above わずかな兆候でも検出 高い 高リスク領域のインジェクション検知

🚀 設定方法

📌 前提条件:
  • Google Cloud プロジェクトで Model Armor API が有効化されていること
  • Agent Gateway がセットアップ済みであること
  • roles/modelarmor.admin IAM ロールが付与されていること
  • Model Armor テンプレートと Agent Gateway が同一リージョンにデプロイされていること

Step 1: Model Armor API の有効化

Bash 
gcloud services enable modelarmor.googleapis.com \
  --project=PROJECT_ID

Step 2: Model Armor テンプレートの作成

Agent Gateway と同じリージョンに Model Armor テンプレートを作成する。テンプレートでは検出フィルターの種類、信頼度レベル、エンフォースメントモードを設定する。

✓責任ある AI フィルターの閾値設定
✓プロンプトインジェクション / ジェイルブレイク検知の閾値設定
✓Sensitive Data Protection (機密データ保護) の設定
✓エンフォースメントタイプ選択 (INSPECT_ONLY / INSPECT_AND_BLOCK)

Step 3: Agent Gateway と Model Armor テンプレートの関連付け

Agent Gateway セットアップ時に、作成した Model Armor テンプレートをゲートウェイに関連付ける。Ingress / Egress それぞれに個別のテンプレートを指定可能。

Step 4: クロスプロジェクト構成の IAM 設定

Bash 
# テンプレートとゲートウェイが異なるプロジェクトにある場合

# Ingress の場合
gcloud projects add-iam-policy-binding TEMPLATE_PROJECT_ID \
  --member="serviceAccount:SERVICE_AGENT_SA" \
  --role="roles/modelarmor.user"

# Egress の場合
gcloud projects add-iam-policy-binding GATEWAY_PROJECT_ID \
  --member="serviceAccount:AGENT_GATEWAY_SA" \
  --role="roles/modelarmor.calloutUser"

gcloud projects add-iam-policy-binding TEMPLATE_PROJECT_ID \
  --member="serviceAccount:AGENT_GATEWAY_SA" \
  --role="roles/modelarmor.user"

💡 メリット

ビジネス面

✓コンプライアンスの統一的な適用 - 組織全体の AI エージェントに対してコンテンツセキュリティポリシーを一元管理
✓運用コストの削減 - エージェント個別のセキュリティ実装が不要に
✓リスクの軽減 - プロンプトインジェクションや機密データ漏洩による情報セキュリティインシデントのリスクを大幅に低減

技術面

✓インフラストラクチャレベルの適用 - フレームワークや実装に依存しない一貫した保護
✓段階的なロールアウト - Inspect only モードでテスト後に Inspect and block へ移行可能
✓Security Command Center 統合 - 既存のセキュリティ運用ワークフローに統合可能
✓ステートレス処理 - コンテンツを保存しないプライバシー重視の設計

⚠️ デメリット・制約事項

制限事項:
✗Ingress のストリーミングは ADK の streamQuery メソッドのみ対応
✗Model Armor と Agent Gateway は同一リージョンが必須 (クロスリージョン非対応)
✗Egress のインライン保護は MCP / OpenAI 互換 LLM / A2A に限定
✗Ingress のインライン保護は ADK で構築されたエージェントのみ対応
✗Client-to-Agent モードは Gemini Enterprise では非対応 (Agent Runtime のみ)
✗ファイルサイズ上限は 4 MB
💡 考慮すべき点:
  • 誤検知 (false positive) リスクがあるため、初期段階では Inspect only モードでの検証を推奨
  • クロスプロジェクト構成では双方のプロジェクトで十分な API クォータが必要
  • フィルター閾値は反復的なテストとチューニングが必要。代表的なプロンプトデータセットでの事前検証が重要

🎯 ユースケース

🏢 ユースケース 1: エンタープライズカスタマーサポート AI

シナリオ: 複数の ADK ベース AI カスタマーサポートエージェントを運用。顧客がクレジットカード番号や住所などの個人情報を誤入力するリスク、悪意あるユーザーによるプロンプトインジェクション攻撃からの保護が必要。

YAML 
# Model Armor テンプレート設定 (Ingress)
enforcement_type: INSPECT_AND_BLOCK
filters:
  prompt_injection:
    confidence_level: MEDIUM_AND_ABOVE
  jailbreak_detection:
    confidence_level: MEDIUM_AND_ABOVE
  sensitive_data_protection:
    inspect_template: projects/PROJECT_ID/locations/REGION/inspectTemplates/PII_TEMPLATE
    deidentify_template: projects/PROJECT_ID/locations/REGION/deidentifyTemplates/REDACT_TEMPLATE
✅ 効果: 顧客の個人情報が自動的にリダクションされ、エージェントに到達する前に保護される。プロンプトインジェクション攻撃は Medium 以上の信頼度で検出・ブロック。

🤝 ユースケース 2: マルチエージェント環境での外部 LLM 連携保護

シナリオ: 複数の AI エージェントが外部の LLM サービスや MCP サーバーと連携。エージェントが意図せず機密情報を外部に送信するリスクや、外部 LLM からの有害レスポンスを受信するリスクがある。

✅ 効果: Agent Gateway の Egress トラフィックに Model Armor を適用し、組織の知的財産や機密データの外部漏洩を防止。外部からの有害コンテンツもブロック。すべてのエージェント通信が一元的に監視・保護される。

🔗 関連サービス・機能

🔍 Security Command Center

Model Armor の検出結果 (Findings) が自動連携。セキュリティ運用ダッシュボードで確認可能。

📊 Cloud Logging

ポリシー違反イベントの詳細ログ記録。Inspect only モードでの監視にも活用。

🔐 Sensitive Data Protection

DLP テンプレートを使用した高度な機密データ保護と PII リダクション。

📋 Agent Registry

エージェント、エンドポイント、MCP サーバーの登録・メタデータ管理。

🛠️ Agent Development Kit (ADK)

Ingress のストリーミングサニタイゼーションに対応するエージェント開発フレームワーク。

🔑 Context-Aware Access

mTLS と DPoP によるエージェント ID の暗号的認証と Agent Gateway の認可決定。

📝 まとめ

Model Armor for Agent Gateway の GA リリースは、エンタープライズ AI エージェントのセキュリティガバナンスにおける重要なマイルストーンである。

インフラストラクチャレベルでコンテンツセキュリティガードレールを適用することで、エージェント開発者はビジネスロジックに集中しつつ、セキュリティチームは組織全体の AI 利用に対する一貫したポリシー適用を実現できる。

📌 推奨アクション:
  1. まず Inspect only モードで導入を検討
  2. 既存トラフィックパターンを分析
  3. 段階的に Inspect and block モードへ移行
