📋 概要

オンプレミスのベアメタル環境で Kubernetes を運用する Google Distributed Cloud (software only) for bare metal 1.36.0-gke.532 がダウンロード可能になりました。 Kubernetes 1.36 / containerd 2.2 / Ansible 2.18 へのランタイム最新化に加え、垂直 Pod 自動スケーリング (VPA) の GA、 レイヤー 4 ゲートウェイコントローラーのサポート追加、非推奨コンポーネントの削除、そしてアップグレード停止や CA ローテーション失敗といった運用上重要な多数の不具合修正を含むメジャーリリースです。

GKE On-Prem API クライアント (Google Cloud コンソール、gcloud CLI、Terraform) からのインストール・アップグレードは、リリース後約 7〜14 日で利用可能になります。

❌ Before (アップデート前の課題)
  • 垂直 Pod 自動スケーリングは Preview 段階で本番利用に制約
  • 異なる名前空間に同名の CA 証明書 Secret があるとクラスタアップグレードが停止
  • 自己管理クラスタ (admin / hybrid / standalone) の CA ローテーションが最終フェーズで失敗し管理不能に
  • レジストリミラー / プライベートレジストリの更新動作がクラスタタイプごとに不統一
  • 非推奨の anthos-metadata-agent / csi-snapshot-validation-webhook が残存
  • Bundled Ingress のステータス未更新、ノードプールのロールバック失敗などの不具合
✅ After (アップデート後の改善)
  • VPA が GA となり CPU / メモリの自動調整を本番環境で利用可能
  • Secret 名に名前空間プレフィックスを自動付与し、名前重複による停止を解消
  • レイヤー 4 ゲートウェイコントローラーのサポートを追加
  • containerd 2.2 + Kubernetes 1.36 でランタイムを最新化
  • CSI スナップショット検証を Webhook から CRD 内の CEL ルールへ移行しコンポーネント削減
  • レジストリミラー更新動作を全クラスタタイプで統一 (既存構成は維持)

1.36.0-gke.532 へのアップグレードによるコンポーネント構成の変化です。ランタイム (containerd / Ansible) の更新、非推奨コンポーネントの削除と後継機能への移行、垂直 Pod 自動スケーリングの GA 化、レイヤー 4 ゲートウェイコントローラーの追加が主な変更点です。

🚀 主要機能

1️⃣ Kubernetes 1.36 / containerd 2.2 へのアップデート

クラスタは v1.36.0-gke.2800 上で動作。containerd は 2.1 から 2.2 にアップグレードされ、新規クラスタインストールおよび Node Agent モードへのクラスタ移行では containerd が必須です。

2️⃣ Ansible 2.18 へのアップグレード

ターゲットノードに Python 3.8 以上が必要。RHEL 8 はデフォルトが Python 3.6 のため、RHEL 8.10 ノードには Python 3.9 のインストールが必要。RHEL 8.8 はサポート対象外になりました。

3️⃣ レイヤー 4 ゲートウェイコントローラーのサポート追加

レイヤー 4 (L4) ゲートウェイコントローラーがサポート対象に追加されました。

4️⃣ 垂直 Pod 自動スケーリング (VPA) の GA 🎉

コンテナの CPU / メモリのリソース要求・上限を、過去および現在の使用状況の分析に基づいて推奨・自動適用する機能が一般提供 (GA) に。リソース割り当ての適正化により、安定性とコスト効率が向上します。

5️⃣ 非推奨コンポーネントの削除
  • anthos-metadata-agent を削除 (後継は kubestore-collector)
  • csi-snapshot-validation-webhook を削除 (検証はデプロイされた CRD 内の CEL ルールでネイティブに処理)
6️⃣ レジストリミラー / プライベートレジストリの更新動作の統一

全クラスタタイプで更新動作を統一。既存の構成は維持されます。

7️⃣ Node Agent モードでの bmctl backup cluster の要件

管理ワークステーションと全ターゲットノードの /tmp に、バックアップアーカイブのバッファ用として 12 GB 以上の空き容量が必要。TMPDIR 環境変数でカスタム一時ディレクトリを設定可能です。

🔧 主な修正 (Fixed)

🛡️脆弱性修正 (詳細は Vulnerability fixes を参照)。cluster-proportional-autoscaler もセキュリティ対応のため更新
🔑異なる名前空間に同一名の CA 証明書 Secret が存在する場合にクラスタアップグレードが停止する問題を修正 (転送時に対象名前空間のプレフィックスを Secret 名に自動付与)
🔄自己管理クラスタ (admin / hybrid / standalone) で CA ローテーションが最終フェーズで失敗し管理不能になる問題を修正 (事前に 1.33.1000-gke.59 以上へのアップグレードが必要)
🌐Bundled Ingress 使用時に Ingress リソースのステータスが更新されない問題を修正
↩️古い CAPI ブートストラップ Secret が非推奨の kubelet フラグを保持していることに起因するノードプールのロールバック失敗を修正
♻️learner 昇格失敗後の不完全なクリーンアップにより etcd-events のインストールが無限リトライループに入る問題を修正
🏷️NodePool コントローラーの Status.ManagedFields 早期更新により、削除済みの taint やラベルがノードに残留する問題を修正
⏳過去に使用したクラスタ名でユーザークラスタを再作成すると PROVISIONING 状態で無期限に停止する問題を修正 (k8s-health-check サービスアカウント欠如が原因)
🔌etcd 暗号化更新中の kube-apiserver 再起動でコンテナが強制終了され、古いサービスエンドポイントや一時的な接続障害が発生する問題を修正
⏱️証明書ローテーション / etcd 暗号化更新時に、コントロールプレーンノードごとにインストーラーが 3 分間停止する問題を修正

垂直 Pod 自動スケーリングの設定例

クラスタ仕様で verticalPodAutoscaling を有効化し、ワークロードごとに VerticalPodAutoscaler カスタムリソースを定義します。

YAML VerticalPodAutoscaler カスタムリソース 
apiVersion: "autoscaling.k8s.io/v1"
kind: VerticalPodAutoscaler
metadata:
  name: hamster-vpa
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind: Deployment
    name: hamster
  resourcePolicy:
    containerPolicies:
      - containerName: '*'
        minAllowed:
          cpu: 100m
          memory: 50Mi
        maxAllowed:
          cpu: 1
          memory: 500Mi
        controlledResources: ["cpu", "memory"]

⚙️ 設定方法 (アップグレード手順)

✅ 前提条件

✓アップグレードは admin クラスタから行い、その後に関連するユーザークラスタをアップグレードする
✓ターゲットノードに Python 3.8 以上がインストールされていること (RHEL 8.10 の場合は Python 3.9)
✓Node Agent モードで bmctl backup cluster を使う場合、/tmp に 12 GB 以上の空き容量があること
✓CA ローテーションを行う場合は、事前にクラスタを 1.33.1000-gke.59 以上にアップグレードしておくこと
✓サードパーティストレージ使用時は、認定済みストレージパートナーの一覧を確認すること
1
新しい bmctl のダウンロードと認証設定
Bash Application Default Credentials (ADC) の設定 
# Application Default Credentials (ADC) の設定
gcloud auth application-default login

最新の bmctl を Google Distributed Cloud downloads の手順でダウンロードします。

2
クラスタ構成ファイルの更新
YAML anthosBareMetalVersion をアップグレード先バージョンに更新 
apiVersion: baremetal.cluster.gke.io/v1
kind: Cluster
metadata:
  name: cluster1
  namespace: cluster-cluster1
spec:
  type: admin
  # アップグレード先のバージョン (ダウンロードした bmctl のバージョンと一致させる)
  anthosBareMetalVersion: 1.36.0-gke.532
3
アップグレードの実行
Bash bmctl によるクラスタアップグレード 
bmctl upgrade cluster -c CLUSTER_NAME --kubeconfig ADMIN_KUBECONFIG

アップグレード操作はプリフライトチェックでクラスタの状態とノードの健全性を検証し、全コンポーネントのアップグレード後にヘルスチェックが実施されます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓運用リスクの低減: CA ローテーション失敗やアップグレード停止など、クラスタが管理不能・停止状態に陥る不具合を多数修正し、オンプレミス運用の信頼性が向上
✓コスト効率の向上: VPA の GA により、リソースの right-sizing を本番環境で活用でき、ハードウェアリソースの有効活用につながる

🔬 技術面のメリット

✓ランタイムの最新化: Kubernetes 1.36 と containerd 2.2 でアップストリームの最新機能・修正を利用可能
✓コンポーネントの簡素化: Webhook を CRD 内の CEL ルールに置き換え、運用対象コンポーネントを削減
✓一貫した挙動: レジストリミラーの更新動作が全クラスタタイプで統一され、構成管理が単純化

🚧 制限事項

✗GKE On-Prem API クライアントでの利用開始まで約 7〜14 日を要する
✗RHEL 8.8 はサポート対象外になった
✗RHEL 8.10 のノードには Python 3.9 のインストールが必要 (Ansible 2.18 の要件)
✗containerd は新規インストールおよび Node Agent モード移行で必須

💡 考慮すべき点

→Node Agent モードの bmctl backup cluster は /tmp に 12 GB 以上必要 (不足時は TMPDIR で変更)
→anthos-metadata-agent 依存の構成は kubestore-collector への移行を確認
→CA ローテーション予定なら、先に 1.33.1000-gke.59 以上へアップグレード
→サードパーティストレージは認定済みストレージパートナーの一覧を確認
