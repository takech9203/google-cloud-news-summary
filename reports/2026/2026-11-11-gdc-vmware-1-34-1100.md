# Google Distributed Cloud (software only) for VMware: 1.34.1100-gke.125 リリース

**リリース日**: 2026-11-11

**サービス**: Google Distributed Cloud (software only) for VMware

**機能**: バージョン 1.34.1100-gke.125 (パッチリリース)

**ステータス**: Announcement + Feature + Fixed (GA)

📊 [このアップデートのインフォグラフィックを見る](https://takech9203.github.io/google-cloud-news-summary/20261111-gdc-vmware-1-34-1100.html)

## 概要

Google Distributed Cloud (software only) for VMware のパッチバージョン **1.34.1100-gke.125** がダウンロード可能になりました。本バージョンは **Kubernetes v1.34.12-gke.500** 上で動作します。GDC (software only) for VMware は、オンプレミスの VMware vSphere 環境上に GKE ベースの Kubernetes クラスタを構築・運用するためのソフトウェアであり、ハイブリッドクラウド構成でコンテナワークロードを稼働させる企業が主な対象です。

今回のリリースの中心は **信頼を失った (distrusted) ルート CA への対応**です。eMudhra (emSign) および AAA Certificate Services のルート CA をシステムコンポーネント、コンテナベースイメージ、ノード OS イメージ (COS / Ubuntu) から削除し、侵害された eMudhra の中間 CA を拒否するように更新されています。あわせて Container-Optimized OS (COS) の milestone 121 (`cos-121-18867-652-7`) へのアップグレード、Ubuntu 22.04 ノード / 管理ワークステーションのベースイメージ更新 (`ubuntu-gke-op-2204-1-33-v20261024`、USN-8944-1 対応) が含まれます。

修正面では、脆弱性修正に加えて、ユーザークラスタ削除時に admin クラスタへ孤立した ClusterRoleBinding が残る問題、MetalLB アドレスプール更新時にクラスタが UPDATING 状態でスタックする問題、manual ロードバランサモードでの誤ったプリフライトチェック、audit-proxy の無限リトライ、プリフライトヘルスチェックが全 namespace をスキャンしてアップグレードが失敗する問題など、クラスタライフサイクル運用に関わる複数の不具合が修正されています。

**アップデート前の課題**

- 信頼を失った eMudhra (emSign) / AAA Certificate Services のルート CA がノード OS やコンテナベースイメージの信頼ストアに残っており、侵害された中間 CA 経由の証明書が受け入れられるリスクがあった
- ユーザークラスタを削除しても `k8s-health-check-reader-binding-<cluster-namespace>` という ClusterRoleBinding が admin クラスタに孤立したまま残っていた
- advanced ユーザークラスタで既存の MetalLB アドレスプールに IP アドレスを追加すると、クラスタが UPDATING 状態のままスタックしていた
- 制御プレーンのロードバランサモードが manual の場合でも、プリフライトチェックが制御プレーン VIP (`loadBalancer.vips.controlPlaneVIP`) を制御プレーンノードのサブネット内にあることを誤って要求していた
- audit-proxy が恒久的なエラーに対しても監査ログのエクスポートを無限にリトライし、過剰な監査ログトラフィックを発生させていた
- Kubernetes プリフライトヘルスチェックが対象クラスタの namespace だけでなく admin クラスタの全 namespace をスキャンし、無関係なクラスタに古い reconciling リソースがあるとアップグレードが失敗していた

**アップデート後の改善**

- システムコンポーネント / コンテナベースイメージ / COS 121 / Ubuntu 22.04 イメージから信頼を失ったルート CA が削除され、侵害された eMudhra 中間 CA が拒否されるようになった
- ヘルスチェック権限が namespace スコープの RoleBinding に変更され、レガシーな ClusterRoleBinding は自動的にクリーンアップされるようになった
- 既存 MetalLB アドレスプールへの IP 追加はバリデーション時に拒否されるようになった (IP を追加する場合は新しいアドレスプールを追加する運用に変更)
- manual ロードバランサモードでの誤った VIP サブネット検証が解消された
- audit-proxy は恒久的エラーで無限リトライしなくなり、監査ログトラフィックが抑制された
- プリフライトヘルスチェックが対象クラスタの namespace のみをスキャンするようになり、無関係なクラスタ起因のアップグレード失敗がなくなった

## サービスアップデートの詳細

### 主要機能

1. **信頼を失ったルート CA の削除 (Feature)**
   - システムコンポーネントとコンテナベースイメージを更新し、信頼を失った eMudhra (emSign) および AAA Certificate Services ルート CA を削除、侵害された eMudhra 中間 CA を拒否
   - Container-Optimized OS (COS) を milestone 121 (`cos-121-18867-652-7`) にアップグレードし、同ルート CA を削除
   - Ubuntu 22.04 ノードおよび管理ワークステーションのベースイメージを `ubuntu-gke-op-2204-1-33-v20261024` に更新し、eMudhra (emSign) ルート CA を削除 (Ubuntu セキュリティ通知 USN-8944-1 に対応)

2. **クラスタライフサイクル関連の修正 (Fixed)**
   - ユーザークラスタ削除時に admin クラスタに孤立した `k8s-health-check-reader-binding-<cluster-namespace>` ClusterRoleBinding が残る問題を修正。ヘルスチェック権限は namespace スコープの RoleBinding を使用するようになり、レガシー ClusterRoleBinding は自動クリーンアップされる
   - advanced ユーザークラスタで既存 MetalLB アドレスプールへの IP アドレス追加によりクラスタが UPDATING 状態でスタックする問題を修正 (更新はバリデーションで拒否され、新規アドレスプール追加で対応する方式に変更)
   - Kubernetes プリフライトヘルスチェックが admin クラスタの全 namespace をスキャンし、無関係なクラスタの古い reconciling リソースによりアップグレードが失敗する問題を修正

3. **その他の修正 (Fixed)**
   - [Vulnerability fixes](https://cloud.google.com/kubernetes-engine/distributed-cloud/vmware/docs/vulnerabilities) に記載の脆弱性を修正
   - 制御プレーンロードバランサモードが manual の場合に、プリフライトチェックが制御プレーン VIP を制御プレーンノードサブネット内に誤って要求する問題を修正
   - audit-proxy が恒久的エラーに対して監査ログエクスポートを無限リトライし、過剰な監査ログトラフィックを生成する問題を修正

GDC (software only) は Kubernetes と同様のバージョニングを採用し、最新 3 つのマイナーバージョンを同時サポートします。各マイナーバージョンは「初回リリースから 12 か月」または「3 つ後のマイナーバージョンのリリース」のいずれか遅い方までサポートされます。本リリース時点のサポート対象は 1.35 / 1.34 / 1.33 です。

## 設定方法

### 前提条件

1. 既存の GDC (software only) for VMware クラスタ (1.34 系へのアップグレードパスがあるバージョン) が稼働していること
2. サードパーティストレージベンダーを使用している場合、[GDC Ready storage partners](https://cloud.google.com/anthos/docs/resources/partner-storage) で本リリースの認定状況を確認すること

### 手順

#### ステップ 1: 新バージョンのダウンロードと管理ワークステーションの更新

```bash
# バンドルのダウンロード先とアップグレード手順はドキュメントを参照
# https://cloud.google.com/kubernetes-engine/distributed-cloud/vmware/docs/how-to/upgrading
```

ダウンロードページから 1.34.1100-gke.125 を取得し、アップグレードガイドに従って管理ワークステーションを更新します。

#### ステップ 2: クラスタのアップグレード

```bash
# 例: gkectl によるユーザークラスタのアップグレード
gkectl upgrade cluster \
  --kubeconfig ADMIN_CLUSTER_KUBECONFIG \
  --config USER_CLUSTER_CONFIG
```

リリース後約 7〜14 日で、GKE On-Prem API クライアント (Google Cloud コンソール、gcloud CLI、Terraform) からもこのバージョンが利用可能になります。

## メリット

### ビジネス面

- **サプライチェーンのセキュリティ強化**: 信頼を失った CA がオンプレミスクラスタの信頼ストアから排除され、侵害された中間 CA を悪用した中間者攻撃などのリスクを低減できる
- **運用コストの削減**: 孤立 RBAC リソースの自動クリーンアップやアップグレード失敗要因の解消により、クラスタライフサイクル運用時の手動対応が減少する

### 技術面

- **OS / イメージの一括更新**: COS 121 と Ubuntu 22.04 の新イメージにより、ノード OS レイヤーの CVE 対応と CA 更新が同時に適用される
- **RBAC の最小権限化**: ヘルスチェック権限がクラスタ全体の ClusterRoleBinding から namespace スコープの RoleBinding に変更され、権限境界が適切になった
- **アップグレードの信頼性向上**: プリフライトチェックが対象クラスタの namespace のみを検証するようになり、環境内の他クラスタの状態に起因する誤検知が解消された

## デメリット・制約事項

### 制限事項

- 既存の MetalLB アドレスプールへの IP アドレス追加はバリデーションで拒否されるようになった。IP を追加したい場合は新しいアドレスプールを追加する必要がある (運用手順の変更が必要)
- リリース直後は GKE On-Prem API クライアント (コンソール / gcloud / Terraform) からの利用に約 7〜14 日かかる

### 考慮すべき点

- eMudhra (emSign) または AAA Certificate Services 配下の証明書を社内サービスや外部連携で使用している場合、本バージョン適用後に TLS 接続が失敗する可能性があるため、事前に証明書チェーンを確認して別の CA への移行を済ませておく必要がある
- サードパーティストレージを使用している場合は、ストレージパートナーの本リリースに対する認定状況を事前に確認する

## ユースケース

### ユースケース 1: セキュリティコンプライアンス対応としての定期パッチ適用

**シナリオ**: 金融機関がオンプレミス VMware 環境で GDC クラスタを運用しており、社内規定で「信頼を失った CA の排除と月次の脆弱性パッチ適用」が義務付けられている。

**効果**: 1.34.1100-gke.125 へのアップグレードだけで、ノード OS (COS / Ubuntu)、システムコンポーネント、コンテナベースイメージの CA 更新と CVE 修正が一括適用され、個別対応が不要になる。

### ユースケース 2: マルチクラスタ環境でのアップグレード失敗の解消

**シナリオ**: 1 つの admin クラスタ配下で多数のユーザークラスタを運用しており、一部クラスタの古い reconciling リソースが原因で他クラスタのアップグレードがプリフライトチェックで失敗していた。

**効果**: プリフライトヘルスチェックが対象クラスタの namespace のみをスキャンするようになり、無関係なクラスタの状態に影響されずにアップグレードを進められる。また、クラスタ削除時の孤立 ClusterRoleBinding も自動クリーンアップされ、admin クラスタの RBAC リソースが整理される。

## まとめ

本リリースは、信頼を失った eMudhra (emSign) / AAA Certificate Services ルート CA の排除というセキュリティ対応を中心に、クラスタライフサイクル運用の信頼性を高める修正を多数含むパッチリリースです。1.34 系を運用中の環境では、CA 排除と脆弱性修正の観点から早期の適用を推奨します。適用前には、該当 CA 配下の証明書を利用している社内 / 外部サービスがないか、および MetalLB アドレスプールの運用手順変更の影響を確認してください。
