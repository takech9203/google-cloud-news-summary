☁️ BigQuery ✅ GA (一般提供)

🧩 AI.PARSE_DOCUMENT 関数が一般提供 (GA) に

非構造化ドキュメントを SQL 1 つで構造化 JSON に変換

リリース日: 2026-11-02

📌 概要

BigQuery の AI.PARSE_DOCUMENT 関数が 一般提供 (GA) になりました。 Document AI のレイアウトパーサーを使用して、PDF などの非構造化ドキュメントから タイトル・見出し・段落・リスト・テーブル・画像といったレイアウト要素を抽出し、 構造化された JSON に変換するスカラー関数です。 SQL クエリ 1 つでドキュメント解析が完結するため、別途 Document AI パイプラインを構築する必要がありません。

BigQuery がプロジェクト内に Document AI プロセッサ (bq-created-layout-parser) を 自動プロビジョニング・管理するため、モデルの作成やトレーニングは不要です。 解析結果はエージェントワークフローへの入力、SQL 分析、AI.CHUNK_DOCUMENT によるチャンク化に活用できます。 RAG パイプラインやドキュメント分析基盤を構築するデータエンジニア、データアナリスト、AI アプリケーション開発者に重要なアップデートです。

❌ Before (アップデート前の課題)

  • BigQuery の外部で Document AI プロセッサを手動で作成・管理し、パイプラインを構築する必要があった
  • クエリごとの冗長なプロセッサプロビジョニングを防ぐ仕組みを自前で用意する必要があった
  • 解析結果を BigQuery に取り込む ETL 処理が別途必要だった

✅ After (アップデート後の改善)

  • SQL 関数 1 つで Cloud Storage や ObjectRef (Google Drive 含む) 上のドキュメントを構造化 JSON に変換
  • プロジェクトごとに単一プロセッサを自動作成・再利用し、プロビジョニング管理が不要に
  • raw-docai 出力を AI.CHUNK_DOCUMENT に直接渡せ、「解析 → チャンク化」を SQL のみで構成可能

Cloud Storage や Google Drive 上の非構造化ドキュメントを AI.PARSE_DOCUMENT が Document AI レイアウトパーサー (BigQuery が自動管理) で解析し、構造化 JSON として返します。 raw-docai スキーマの出力は AI.CHUNK_DOCUMENT に直接渡して、RAG 用のチャンク化まで SQL で完結できます。

⚡ 主要機能

📄 1. レイアウト要素の抽出と構造化 JSON 出力

タイトル、見出し、段落、リスト、テーブル、画像などのレイアウト要素を抽出。 テーブルは HTML (<table>...</table>) 形式で返却され、 各ブロックにはページ番号と正規化された位置情報 (bbox) が付与されます。

🤖 2. プロセッサの自動プロビジョニング

初回実行時に bq-created-layout-parser プロセッサをプロジェクトに自動作成。 プロジェクトごとに単一のプロセッサを再利用するため、クエリ間での冗長なプロビジョニングを防止。 プロセッサを削除しても次回実行時に自動再作成されます。

🗂️ 3. 2 種類の出力スキーマ

layout-v1 (デフォルト): 読み取り順のフラットなブロックリスト。SQL 分析やエージェントワークフロー向けのコンパクト形式。
raw-docai: Document AI のネストされたレイアウトツリー全体。階層関係を保持し、AI.CHUNK_DOCUMENT への入力に使用。

🔑 4. 柔軟な入力ソースと認証

Cloud Storage URI (STRING) または ObjectRef 値 (OBJ.MAKE_REF、OBJ.LIST、オブジェクトテーブル) を入力として受け付け。 Google Drive のファイルも ObjectRef 経由でサポート (エンドユーザー認証情報を使用)。 EUC または Cloud リソース接続のいずれかで認証可能です。

ステップ 1: 単一ドキュメントの解析

SQL デフォルトの layout-v1 スキーマで解析 (初回実行時にプロセッサ自動作成) 
SELECT AI.PARSE_DOCUMENT(
  'gs://cloud-samples-data/documentai/SampleDocuments/OCR_PROCESSOR/Winnie_the_Pooh_3_Pages.pdf'
) AS parsed_doc;

ステップ 2: フォルダ内の全ドキュメントを一括解析

SQL OBJ.LIST でプレフィックス配下の全 PDF を解析 
SELECT
  uri,
  AI.PARSE_DOCUMENT(ref) AS parsed_doc
FROM OBJ.LIST('gs://my-bucket/documents/*.pdf');

ステップ 3: ブロックを行に展開して SQL 分析

SQL 各レイアウト要素を 1 行ずつに展開してテーブルとして分析 
SELECT
  INT64(block.id) AS block_id,
  JSON_VALUE(block.type) AS block_type,
  INT64(block.page_number) AS page_number,
  JSON_VALUE(block.content) AS content
FROM UNNEST(
  JSON_QUERY_ARRAY(
    AI.PARSE_DOCUMENT('gs://my-bucket/documents/manual.pdf').blocks
  )
) AS block;

ステップ 4: AI.CHUNK_DOCUMENT と連携したチャンク化

SQL raw-docai スキーマの解析結果からセマンティックチャンクを生成 
SELECT uri, chunk_id, start_page, end_page, content
FROM AI.CHUNK_DOCUMENT((
  SELECT
    uri,
    AI.PARSE_DOCUMENT(
      ref,
      options => JSON '{"schema": "raw-docai"}'
    ) AS parsed_document
  FROM OBJ.LIST('gs://my-bucket/documents/*.pdf')
));

💡 メリット

💼 ビジネス面

✓ドキュメント処理基盤の構築コスト削減: Document AI パイプラインを別途構築・運用することなく、SQL だけで非構造化ドキュメントの構造化が可能
✓GA による本番利用の安心感: 一般提供となったことで、SLA の対象として本番ワークロードに組み込める

⚙️ 技術面

✓プロビジョニングの自動化: プロセッサの作成・管理を BigQuery が代行し、プロジェクトごとに単一プロセッサを再利用するため冗長なリソースが発生しない
✓パイプラインの SQL 完結: OBJ.LIST による一括処理、AI.CHUNK_DOCUMENT によるチャンク化まで、解析から RAG 前処理までを BigQuery 内で完結
✓用途別の 2 スキーマ: SQL 分析向けのフラットな layout-v1 と、階層構造を保持する raw-docai を使い分け可能

⚠️ デメリット・制約事項

制限事項

✗最大ドキュメント長は 130 ページ。特定のページ範囲の指定はサポートされない
✗Google Drive のファイルは ObjectRef 値として渡す場合のみサポート。Drive URI を STRING として直接渡すことはできない
✗AI.CHUNK_DOCUMENT との連携は raw-docai スキーマのみサポート (layout-v1 は不可)
✗Document AI レイアウトパーサー自体の制限事項 (対応ファイル形式など) にも従う

考慮すべき点

⚠️Document AI API の有効化が前提のため、組織ポリシーで API 利用が制限されている環境では事前調整が必要
⚠️認証方式 (EUC か Cloud リソース接続か) により必要な IAM ロールが異なるため、設計時に認証パターンを決めておく必要がある
⚠️raw-docai スキーマの出力は冗長なため、SQL 分析用途にはデフォルトの layout-v1 が推奨される

🎯 ユースケース

🔍 ユースケース 1: BigQuery 上での RAG パイプライン構築

シナリオ: 社内マニュアルや契約書などの PDF を Cloud Storage に蓄積しており、これらを検索可能なナレッジベースとして生成 AI アプリケーションから利用したい。

SQL 実装例: 解析 + チャンク化を SQL のみで実行 
SELECT uri, chunk_id, start_page, end_page, content
FROM AI.CHUNK_DOCUMENT((
  SELECT uri,
    AI.PARSE_DOCUMENT(ref, options => JSON '{"schema": "raw-docai"}') AS parsed_document
  FROM OBJ.LIST('gs://knowledge-base/docs/*.pdf')
));

効果: 解析とチャンク化を SQL のみで実行でき、生成したチャンクに埋め込みを付与してベクトル検索に利用するまでの RAG 前処理を BigQuery 内で完結できる。

📊 ユースケース 2: 帳票・レポートのテーブルデータ抽出と SQL 分析

シナリオ: 財務レポートや調査資料の PDF に含まれるテーブルデータを抽出し、BigQuery で集計・分析したい。

効果: layout-v1 スキーマではテーブルが HTML 形式で抽出され、ブロックタイプ・ページ番号付きで行に展開できるため、非構造化ドキュメント内の表データをそのまま SQL 分析の対象にできる。

📝 まとめ

AI.PARSE_DOCUMENT 関数の GA により、PDF などの非構造化ドキュメントを SQL 関数 1 つで構造化 JSON に変換し、分析や RAG パイプラインに組み込めるようになりました。 Document AI プロセッサの管理が不要になり、AI.CHUNK_DOCUMENT との連携でチャンク化まで BigQuery 内で完結します。

🚀 次のアクション: Cloud Storage にドキュメント資産を持つ組織は、まずサンプル PDF での解析を試し、 layout-v1 / raw-docai スキーマの使い分けを検証することを推奨します。
