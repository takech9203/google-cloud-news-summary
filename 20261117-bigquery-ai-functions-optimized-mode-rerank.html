🗄️ BigQuery ✅ GA (一般提供) 🤖 AI.IF / AI.CLASSIFY 最適化モード 🔍 AI.SEARCH rerank

📝 概要

BigQuery の AI 関数に関する 2 つの機能が GA (一般提供) になりました。

⚡ 1. 管理型 AI 関数の最適化モード (optimized mode)

AI.IF と AI.CLASSIFY で、大規模データセット処理時の LLM トークン消費量とクエリレイテンシを大幅削減。GA に伴い対象クエリタイプが拡大し、マルチラベル分類にも対応。「ジョブ情報」タブで最適化結果の相対品質も確認可能に。

🔍 2. AI.SEARCH の rerank オプション

検索対象テキストが検索クエリにどれだけ適切に回答しているかに基づき、ベクトル検索・ハイブリッド検索の候補を Ranking API でスコアリングしてセマンティックに再ランク付け。

数千行から数十億行規模のデータに対して SQL だけで生成 AI による分類・フィルタリング・セマンティック検索を行いたいデータアナリスト、データエンジニアに、コスト効率と検索品質の両面で大きな価値を提供します。

💡 補足: 同日に GA となった AI.RANK 関数は別レポートで解説されています。

🔄 Before / After

❌ アップデート前の課題

  • 行ごとにリモート LLM (Gemini) を呼び出すため、数百万〜数十億行ではトークン消費・コストが膨大、レイテンシも長い
  • 最適化モード (Preview) は対象クエリタイプが限定的で、マルチラベル分類は非対応
  • 最適化クエリの結果品質を確認する手段がなく、蒸留モデル推論の信頼性を把握しにくい
  • AI.SEARCH はエンベディング距離による順序付けのみで、「回答としての適切さ」での並べ替えには別途処理が必要

✅ アップデート後の改善

  • 最適化モードが GA 化。蒸留モデル推論で LLM 呼び出し回数を大幅削減し、トークン消費とレイテンシを低減
  • 対象クエリタイプが拡大し、output_mode => 'multi' のマルチラベル分類でも最適化が適用可能に
  • 「ジョブ情報」タブで相対品質情報を確認でき、コスト削減と品質のトレードオフを可視化
  • rerank => TRUE を指定するだけで Ranking API によるセマンティック再ランク付けを実行、rerank_score 付きで関連性の高い結果を取得

最適化モードでは、BigQuery がデータの代表サンプルのみを Gemini でラベル付けし、エンベディングを特徴量として軽量な蒸留モデルをクエリ実行中に学習します。品質チェックに合格すると、大多数の行は蒸留モデルで推論されるため、Gemini の呼び出し回数 (= トークン消費) が大幅に削減されます。

🚀 主要機能

⚡ 管理型 AI 関数の最適化モード (GA)

  • AI.IF と AI.CLASSIFY で optimization_mode => 'MINIMIZE_COST' を指定 (エンベディング提供時はデフォルトで有効) すると、行ごとの LLM 呼び出しの代わりに蒸留モデルによる推論を実行
  • 動作フロー: ① サンプリングとラベル付け → ② 蒸留モデルのジャストインタイム学習 → ③ LLM 結果に対する品質チェック → ④ 蒸留モデルによる推論 (一部行は LLM にフォールバック)
  • エンベディングは AI.EMBED による手動生成、または BigQuery の自律的エンベディング生成を利用可能

🏷️ 最適化モードの対象拡大とマルチラベル分類対応

  • GA に伴い、より多くのクエリタイプが最適化モードの対象に
  • AI.CLASSIFY のマルチラベル分類 (1 つの入力に複数カテゴリを付与) でも最適化モードを利用可能に

📋 ジョブ情報タブでの品質情報の表示

  • Google Cloud コンソールのクエリ結果ペインの「ジョブ情報」タブに、最適化されたクエリ結果の相対的な品質情報を表示
  • 蒸留モデルの結果が LLM の結果とどの程度一致するかを把握し、コストと品質のバランスを判断できる

🔍 AI.SEARCH の rerank オプション (GA)

  • rerank => TRUE を指定すると、ベクトル検索 / ハイブリッド検索の候補を Ranking API (Agent Search) でスコアリングし、検索クエリへの関連性で再ランク付け
  • 結果には rerank_score カラムが付与され、関連性の高い順に並べ替え
  • reranker オブジェクトで候補数 (num_candidates、デフォルト top_k * 5、最大 10,000,000 行) やランキングモデル (デフォルト semantic-ranker-default@latest) を調整可能

⚡ 最適化モード (AI.IF / AI.CLASSIFY)

項目詳細
対象関数AI.IF、AI.CLASSIFY のみ
有効化方法optimization_mode => 'MINIMIZE_COST' (エンベディング提供時はデフォルト)
必要な入力対象カラムのエンベディング (同一モデル・同一次元で生成されたもの)
最小行数約 3,000 行 (蒸留モデルの学習に必要)
推奨エンベディングモデルtext-embedding-005、Gemini エンベディング (マルチモーダルは gemini-embedding-2)
非対応max_error_ratio 引数は最適化モードでは未サポート
品質保証蒸留モデルが品質しきい値を満たさない場合はクエリがエラーで失敗

🔍 AI.SEARCH の rerank オプション

項目詳細
構文AI.SEARCH(..., rerank => TRUE [, options => '{"reranker": {...}}'])
column_to_search の要件STRING 型のみ (NULL / 空文字の行は再ランク前に除外)
query_value の要件空でない STRING リテラルまたはクエリパラメータ (ObjectRef は非対応)
num_candidates再ランク対象の候補数。デフォルトは top_k * 5、上限 10,000,000 行
ランキングモデルデフォルトは semantic-ranker-default@latest (省略推奨)
必要な API / 権限Discovery Engine API の有効化、discoveryengine.rankingConfigs.rank 権限 (roles/discoveryengine.viewer に含まれる)
認証エンドユーザー認証情報で Ranking API を呼び出し

🔧 設定方法

📌 前提条件

  • 管理型 AI 関数を実行するための権限を設定する (生成 AI 関数の権限設定)
  • 最適化モードを使う場合: 対象カラムのエンベディングを用意する (自律的エンベディング生成または AI.EMBED)
  • rerank を使う場合: クエリ実行プロジェクトで Discovery Engine API (discoveryengine.googleapis.com) を有効化し、roles/discoveryengine.viewer 相当の権限を付与する

ステップ 1: エンベディング付きテーブルを作成する (最適化モード)

SQL 自律的エンベディング生成を使用したテーブルの作成 
-- 自律的エンベディング生成を使用したテーブルの作成
CREATE TABLE my_dataset.bbc_news (
  title STRING,
  body STRING,
  body_embedding STRUCT<result ARRAY<FLOAT64>, status STRING>
    GENERATED ALWAYS AS (
      AI.EMBED(
        body,
        connection_id => '<my_connection_id>',
        task_type => 'CLASSIFICATION',
        endpoint => 'text-embedding-005')
    ) STORED
    OPTIONS(asynchronous = TRUE)
);

INSERT INTO my_dataset.bbc_news (title, body)
SELECT title, body FROM `bigquery-public-data.bbc_news.fulltext`;

自律的エンベディング生成を有効にすると、AI.IF / AI.CLASSIFY の呼び出し時に BigQuery が自動的にエンベディングを利用します。

ステップ 2: 最適化モードで AI.CLASSIFY を実行する

SQL 最適化モードによる分類 
SELECT
  title,
  body,
  AI.CLASSIFY(
    body,
    categories => ['tech', 'sport', 'business', 'other'],
    embeddings => body_embedding,
    optimization_mode => 'MINIMIZE_COST'  -- エンベディング提供時はデフォルトのため省略可
  ) AS category
FROM my_dataset.bbc_news;

実行後、コンソールのクエリ結果ペインの「ジョブ情報」タブで最適化結果の相対品質情報を確認できます。

ステップ 3: AI.SEARCH で rerank を有効化する

SQL rerank オプション付きセマンティック検索 
SELECT base.name, base.description, distance, rerank_score
FROM AI.SEARCH(
  TABLE mydataset.products,
  'description',
  "A really fun toy",
  rerank => TRUE,
  options => '{"reranker": {"num_candidates": 50}}'
);

ベクトル検索の候補が Ranking API で再スコアリングされ、rerank_score の高い順 (検索クエリへの回答としての適切さの順) に結果が返されます。

⚠️ デメリット・制約事項

🚧 制限事項

✗最適化モードは AI.IF と AI.CLASSIFY のみ対応 (他の管理型 AI 関数は対象外)
✗最適化モードには約 3,000 行以上の入力が必要 (蒸留モデルの学習に十分なデータが必要)
✗蒸留モデルが品質しきい値を満たさない場合、クエリはエラーで失敗 (カテゴリのサンプル不足、true/false の偏りなどが原因になりうる)
✗エンベディングは全行で同一モデル・同一次元である必要がある
✗最適化モードでは max_error_ratio 引数は使用不可
✗rerank では column_to_search が STRING 型である必要があり、ObjectRef (マルチモーダル) の検索クエリは非対応
✗rerank 対象テキストがランキングモデルのトークン上限を超える場合、超過分は切り捨て

🤔 考慮すべき点

  • 最適化モードは蒸留モデルによる近似推論であり、LLM の行ごと推論と結果が完全一致するわけではない。品質情報を確認した上で用途に応じて使い分ける
  • rerank は Ranking API の呼び出しが追加で課金され、プロジェクトの Agent Search ランキング API クォータを消費する
  • エンベディングはオンザフライ生成も可能だが、再利用のためマテリアライズ (事前計算・保存) が推奨

シナリオ: 1 つの記事が「テクノロジー」と「スポーツ」の両方に該当するなど、複数カテゴリへのタグ付けを大規模に行いたい。

効果: GA で最適化モードがマルチラベル分類 (output_mode => 'multi') に対応したため、複数タグの自動付与もコスト効率よく実行可能。

📚 3. 社内ナレッジ検索・RAG の検索精度向上

シナリオ: 製品ドキュメントや FAQ を AI.SEARCH で検索しているが、ベクトル距離だけでは質問への回答として最適な文書が上位に来ないことがある。

  rerank => TRUE

効果: Ranking API が質問文と候補文書を突き合わせてスコアリングするため、RAG やチャットボットに渡すコンテキストの関連性が向上。
