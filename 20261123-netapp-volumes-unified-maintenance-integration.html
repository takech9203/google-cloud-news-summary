☁️ Google Cloud NetApp Volumes

🔧 Unified Maintenance 統合
メンテナンスの可視化と自動通知

リリース日: 2026-11-23
NetApp Volumes Unified Maintenance Feature 通知方式変更の Announcement

📌 概要

Google Cloud NetApp Volumes が Unified Maintenance と統合されました。 Flex Unified / Flex File / Standard / Premium / Extreme のすべてのサービスレベルで、 ストレージプールに影響する計画メンテナンスイベントを Cloud Hub (Maintenance ページ) で確認でき、 Cloud Logging に自動記録されるイベントログに対して ログベースのアラートポリシーで自動通知を構成できるようになりました。

⚠️ 通知方式の移行アナウンス: 従来の NetApp Volumes メンテナンス用 Google グループへのメール通知は 2026 年 12 月 31 日で終了します。2027 年以降は Unified Maintenance が計画メンテナンス通知の 唯一のソースとなるため、移行期間中に Cloud Logging ベースのアラートへ切り替えが必要です。

❌ Before: アップデート前の課題

  • 通知は Google グループへの参加とメール確認に依存し、プロジェクトやストレージプール単位での機械的な追跡が困難
  • Cloud Logging での追跡や、ログベースアラートで PagerDuty / Slack などへ自動連携する標準手段がない
  • 他の Google Cloud サービスの計画メンテナンスとあわせてコンソールで一元確認するビューがない

✅ After: アップデート後の改善

  • Cloud Hub の Maintenance ページで予定・進行中のメンテナンスと過去 30 日間の履歴を一元確認
  • 標準化されたイベントログ (maintenance.googleapis.com/maintenance_events) を Cloud Logging に自動記録、Logs Explorer でクエリ可能
  • ログベースアラートで Email / Pub/Sub / PagerDuty / Slack / SMS / Webhook へ自動通知
  • 業務に支障がある場合、開始 5 営業日前までにリスケジュールをリクエスト可能

ストレージプールへの計画メンテナンスイベントは Unified Maintenance に集約され、Cloud Hub での可視化と Cloud Logging へのイベントログ記録を経由して、ログベースアラートで任意の通知チャネルに配信されます。 Google グループへのメール通知は 2026 年 12 月 31 日までの併送です。

⚙️ 主要機能

🖥️ 1. Cloud Hub でのメンテナンスイベント可視化

✓Maintenance テーブルに予定・進行中のメンテナンスイベントを表示
✓Maintenance history テーブルに過去 30 日間の完了・キャンセル済みイベントを表示
✓説明、タイムライン、影響を受けるストレージプール名、ロケーション、進行状態を確認可能

📋 2. Cloud Logging によるイベントログ追跡

✓ログ ID maintenance.googleapis.com/maintenance_events で標準化されたライフサイクルイベントを自動記録
✓リソースタイプ netapp.googleapis.com/StoragePool でフィルタリング可能
✓jsonPayload.state で SCHEDULED / STARTED / SUCCEEDED / CANCELLED の状態絞り込み

🔔 3. ログベースアラートによる自動通知

✓新規スケジュール、状態変化、開始・終了時刻の変更、特定ロケーションへの影響を条件に構成可能
✓Email / Pub/Sub / PagerDuty / Slack / SMS / Webhook をサポート。Webhook 経由で ServiceNow、Datadog、OpsGenie にも連携可能

📅 4. メンテナンスウィンドウのリスケジュール

✓業務と競合する破壊的メンテナンスは、開始の 5 営業日前までに Cloud Customer Care ケースでリスケジュールをリクエスト可能
✓リクエストにはプロジェクト ID、リージョン、ストレージプール ID、メンテナンス名、現在のウィンドウ、希望ウィンドウ (UTC)、ビジネス上の理由を含める

項目詳細

🗄️ メンテナンス中のストレージプールへの影響

  • ストレージプールが DEGRADED 状態になる
  • プール更新、レプリケーション、CMEK ワークフローなどの操作が利用不可になる
  • 書き込みレイテンシが増加し、スループットが低下する
  • 復旧は自動で、数秒から数時間を要する
💡 ファイルプロトコル (NFS/SMB) の観点: アプリケーションが I/O ポーズを処理できる限りメンテナンスは非破壊的です。 I/O ポーズは Standard / Premium / Extreme では通常数秒〜最大 30 秒程度、Flex では最大 70 秒程度です。

🛠️ 設定方法

📋 前提条件

  • Cloud Hub の利用には、Cloud Hub ドキュメントの「Before you begin」に記載された前提条件と IAM ロールが必要
  • アラート通知には Cloud Monitoring の通知チャネルの設定が必要

ステップ 1: Logs Explorer でメンテナンスイベントログを確認

Logging Query NetApp Volumes のメンテナンスイベントログを表示 
log_id("maintenance.googleapis.com/maintenance_events") AND
jsonPayload.resource.type="netapp.googleapis.com/StoragePool"

Logs Explorer で上記フィルタを実行すると、ストレージプールの Unified Maintenance イベントログを確認できます。特定の状態に絞り込む場合は jsonPayload.state="SCHEDULED" などを追加します。

ステップ 2: ログベースのアラートポリシーを作成

Logging Query 新規スケジュールイベントを対象にした包含フィルタ 
log_id("maintenance.googleapis.com/maintenance_events") AND
jsonPayload.resource.type="netapp.googleapis.com/StoragePool" AND
jsonPayload.state="SCHEDULED"

Logs Explorer の「Create log alert」からアラートポリシーを作成し、Email、Pub/Sub、PagerDuty、Slack、SMS、Webhook などの通知チャネルを割り当てます。アラートは Cloud Monitoring の上限の対象です。

⚖️ メリットと制約事項

✅ ビジネス面のメリット
  • 計画メンテナンスの予見性向上: ウィンドウを事前に把握し、業務影響のある時間帯と競合する場合は 5 営業日前までにリスケジュールを依頼でき、業務影響を最小化
  • 他サービスとの一元管理: Cloud Hub 上で他の Unified Maintenance 対応サービスとあわせて一元的に把握でき、運用ガバナンスが向上
✅ 技術面のメリット
  • 標準化されたログスキーマ: Cloud SQL や Managed Lustre など他サービスと共通のログ ID と状態モデルを使うため、サービス横断で同じアラート基盤を再利用可能
  • 既存の運用ツールとの統合: ログベースアラートと通知チャネル (Webhook / Pub/Sub 含む) により、PagerDuty、Slack、ServiceNow などの既存インシデント管理フローへ自動連携
⚠️ 制限事項
  • Google グループへのメール通知は 2026 年 12 月 31 日で終了。以降は Unified Maintenance が唯一の通知ソースとなるため、期限までにログベースアラートへの移行が必要
  • Unified Maintenance は計画メンテナンスのみを対象とし、計画外のインシデント (障害・性能劣化など) はカバーしない。計画外イベントは Personalized Service Health ダッシュボードで確認
  • メンテナンスアクティビティデータは 60 日間の保持期間後に削除 (完全消去には最大 80 日)
  • 定期的またはリージョン全体にわたる必須のインフラ更新は、リスケジュールの対象外となる場合がある
💭 考慮すべき点
  • リスケジュールのリクエストはメンテナンス開始の 5 営業日前までに Cloud Customer Care ケースで行う必要がある
  • ログベースアラートは Cloud Monitoring のアラート上限 (クォータ) の対象
  • メンテナンス中はストレージプールが DEGRADED 状態となり書き込みレイテンシが増加するため、iSCSI 利用時はタイムアウト設定 (特に Windows の MPIO 設定) をメンテナンスイベントに合わせて構成しておくことを推奨

💼 ユースケース

🚨 ユースケース 1: オンコールチームへのメンテナンス自動通知

シナリオ: NetApp Volumes 上で基幹ファイル共有を運用しており、メンテナンス予定を見逃すと業務時間帯の性能劣化がインシデント扱いになってしまう。

Logging Query スケジュール時点で通知するアラートフィルタ 
log_id("maintenance.googleapis.com/maintenance_events") AND
jsonPayload.resource.type="netapp.googleapis.com/StoragePool" AND
jsonPayload.state="SCHEDULED"

上記フィルタでログベースアラートを作成し、通知チャネルに PagerDuty / Slack を設定する。

効果: メンテナンスがスケジュールされた時点でオンコールチームに自動通知され、事前のユーザー周知やバッチ処理のスケジュール調整が可能に。メンテナンス起因の性能劣化を誤って障害対応しないで済む。

📆 ユースケース 2: 業務ピークと競合するメンテナンスウィンドウのリスケジュール

シナリオ: 月末バッチの実行時間帯に破壊的メンテナンスがスケジュールされていることを Cloud Hub で発見した。

効果: メンテナンス開始の 5 営業日前までに、ストレージプール ID・メンテナンス名・希望ウィンドウ (UTC)・ビジネス上の理由を添えて Cloud Customer Care ケースを起票することで、ウィンドウの変更をリクエスト可能。業務ピークとメンテナンスの競合を回避できる。
