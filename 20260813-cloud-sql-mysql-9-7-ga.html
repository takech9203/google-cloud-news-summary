🗄️ MySQL 9.7 が GA に

ベクトル検索の新フォーマット / Hypergraph オプティマイザ / JSON Duality Views / 移行パス
リリース日: 2026-08-13
通常サポート開始: 2026-08-06

📋 概要

Cloud SQL for MySQL で MySQL 9.7 (マイナーバージョン 9.7.1) が GA になりました。 サポート対象メジャーバージョンは 5.6 / 5.7 / 8.0 / 8.4 / 9.7 の 5 系列となります (デフォルトは引き続き MySQL 8.4)。

最大のポイントは、MySQL 9.7 を指定してインスタンスを作成すると、gcloud CLI・コンソール・REST API のいずれでも Cloud SQL edition が既定で Enterprise Plus になる ことです。 Enterprise Plus は 99.99% の可用性 SLA (メンテナンス込み)、データキャッシュ、読み取りプール、最大 35 日の PITR ログ保持などを備えますが、Enterprise edition より vCPU・メモリ単価が高くなります。

❌ アップデート前の課題

  • 最新メジャーバージョンは 8.4 までで、MySQL 9.x のコミュニティ機能 (標準ベクトル型、Hypergraph オプティマイザ、JSON Duality Views) をマネージド環境で利用できなかった
  • ベクトル検索は独自仕様に依存。特別な COMMENT / CONSTRAINT と VECTOR(dim) USING VARBINARY が必須、上限 16,000 次元・デフォルト値なし
  • 1 テーブルにベクトル埋め込み列は 1 つのみ (インデックスの有無にかかわらず)
  • 8.4 では mysql_native_password が「非推奨」でも接続できたため、認証移行を先延ばしにできてしまった
  • innodb_log_file_size や replica_parallel_type など旧世代フラグへの依存が検知されなかった

✅ アップデート後の改善

  • MySQL 9.7 (9.7.1) が GA になり、マネージド環境で MySQL 9.x の主要機能を利用可能に
  • ベクトル検索がコミュニティ標準フォーマットへ移行。COMMENT / CONSTRAINT 不要、上限 16,383 次元 (デフォルト 2,048)、USING VARBINARY は任意に
  • インデックスを作成しないテーブルなら複数のベクトル埋め込み列を保持可能に
  • ベクトル埋め込みの追加に cloudsql_vector フラグ不要。インデックス作成 + ANN 検索時のみ on に簡素化
  • Hypergraph オプティマイザを optimizer switch で有効化可能に
  • JSON Duality Views で同一データを SQL と JSON ドキュメントの両方で操作可能に
  • 8.4 からの in-place アップグレードと DMS 移行の 2 経路が明確化
  • 9.7 指定だけで Enterprise Plus が既定選択され、edition 指定漏れを回避

⚡ 主要機能

🔎 1. ベクトル検索 (コミュニティ標準フォーマット + ANN インデックス)

コミュニティ版 MySQL 9.0 で導入されたベクトルサポート・ストレージ機能との統合を優先した仕様に変更。ベクトルインデックスは引き続き Google の ScaNN (Scalable Nearest Neighbors) アルゴリズムで構築され、ANN 検索には approx_distance、KNN 検索には vector_distance 関数を使用します。ストレージフォーマット、次元数上限、COMMENT / CONSTRAINT の扱い、vector_to_string の出力形式が 8.4 以前から変わります。

🧠 2. Hypergraph オプティマイザ

複雑な多テーブルクエリ向けに設計された、代替の結合プラン作成 (join-planning) フレームワーク。optimizer_switch で有効化します。デフォルトで常用されるものではなく、対象クエリを見極めて適用します。

🧩 3. JSON Duality Views

リレーショナル SQL モデルと階層的な JSON ドキュメントモデルを橋渡しし、同一の基礎データに対して両方のインターフェイスで操作できるようにする機能です。

🔄 4. アップグレード・移行パス

Cloud SQL for MySQL 8.4 からの in-place メジャーバージョンアップグレード と、Database Migration Service (DMS) による MySQL 8.4 からの移行をサポート。メジャーバージョンのスキップは不可のため、8.0 以前はまず 8.4 へ。アップグレード前に gcloud beta sql instances pre-check-major-version-upgrade でプリチェックを実行できます。

🔐 5. 認証プラグインの破壊的変更

mysql_native_password が 完全に削除 されます (8.4 では「非推奨」だが既存アカウントは接続可能だった)。MySQL 9.7 に接続する組み込み認証のすべてのデータベースユーザーは caching_sha2_password の使用が必須です。

🚩 6. データベースフラグの追加・削除

追加 (サポート) 9 件、削除 7 件。詳細は「技術仕様」セクションの一覧を参照してください。

ℹ️ 全バージョン共通のベクトル関連の制限事項
  • ベクトルインデックスは 1 テーブルに 1 つのみ
  • ベクトル埋め込み列は生成列 (generated column) にできない
  • ベクトル埋め込み列を持つテーブルのテーブルレベルパーティショニングは非対応
  • 主キーに BIT / BINARY / VARBINARY / JSON / BLOB / TEXT および空間データ型を使う場合、ベクトルインデックスは非対応 (複合主キーにも含められない)
  • ベクトルインデックスが存在する場合、ベーステーブルの主キーに制約を追加できない
  • ベクトルインデックスが存在するテーブルでは実行できない DDL 操作がある
  • approx_distance は ORDER BY または SELECT リスト内でのみ使用可能
  • WHERE の述語は approx_distance の評価後に評価される
  • ベクトルインデックスの作成には、ベーステーブルに 1,000 件以上の埋め込みが必要 (未満なら作成失敗)

🛠️ 設定方法

✅ 前提条件

✓組み込み認証を使用するすべてのユーザーを caching_sha2_password に移行 (9.7 では mysql_native_password が完全削除のため必須)
✓クライアント・コネクタ・MySQL Shell を MySQL 9.x 対応版へ更新。Cloud SQL Auth Proxy 利用時は allowPublicKeyRetrieval=true (mysql クライアントなら --get-server-public-key) を構成
✓削除されたフラグ (innodb_log_file_size、replica_parallel_type など) を使用していないか棚卸し
✓Enterprise Plus edition を使う場合、リージョンが Enterprise Plus に対応していることを確認
✓アップグレードの場合、Cloud SQL Admin API 有効 + 追加ディスク容量・メモリ (テーブルあたり最低 100 KB 目安) の余裕を確認

1️⃣ MySQL 9.7 インスタンスを新規作成 (Enterprise Plus / 既定)

Bash 
# --edition を指定しない場合、MYSQL_9_7 では自動的に Enterprise Plus edition になる
gcloud sql instances create my-mysql97 \
  --database-version=MYSQL_9_7 \
  --region=us-central1 \
  --tier=db-perf-optimized-N-4

--edition を省略しても Enterprise Plus が選択されます。明示する場合は --edition=ENTERPRISE_PLUS を付与します。

2️⃣ あえて Enterprise edition で作成

Bash 
gcloud sql instances create my-mysql97-ent \
  --database-version=MYSQL_9_7 \
  --edition=ENTERPRISE \
  --cpu=4 \
  --memory=16GB \
  --region=us-central1

コスト最適化を優先する場合や Enterprise Plus 非対応リージョンでは --edition=ENTERPRISE を明示。Enterprise edition の vCPU は 1 または 2〜96 の偶数、メモリは vCPU あたり 0.9〜6.5 GB かつ 256 MB の倍数、最低 3.75 GB (3,840 MB) の制約があります。

3️⃣ 既存ユーザーの認証プラグインを移行

SQL 
ALTER USER 'username'@'%' IDENTIFIED WITH caching_sha2_password BY 'user_password';

MySQL 9.7 へ上げる前に、組み込み認証を使うすべてのユーザーに対して実行します。

4️⃣ アップグレード可否をプリチェック

Bash 
gcloud beta sql instances pre-check-major-version-upgrade INSTANCE_NAME \
  --target-database-version=MYSQL_9_7 \
  --project=PROJECT_ID \
  --async

プリチェックは連続するメジャーバージョン間の互換性を確認します (インスタンスは RUNNING 状態で、ブロッキング操作が保留されていないことが条件。上限 3 時間)。

5️⃣ in-place メジャーバージョンアップグレードを実行

Bash 
gcloud sql instances patch INSTANCE_NAME \
  --database-version=MYSQL_9_7

Cloud SQL はアップグレード後に自動でバックアップを作成しますが、事前に手動バックアップの取得を推奨。問題発生時はアップグレード前バックアップを 8.4 のリカバリインスタンスへリストアして切り戻します。

6️⃣ アップグレード可能なターゲットバージョンを確認 (REST API)

Bash 
curl -X GET \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://sqladmin.googleapis.com/sql/v1beta4/projects/PROJECT_ID/instances/INSTANCE_NAME"

レスポンスの upgradableDatabaseVersions に、対象インスタンスがアップグレード可能なバージョンが列挙されます。

💡 メリット

💼 ビジネス面

🌐 AI / 検索ワークロードの選択肢拡大

コミュニティ標準のベクトルストレージフォーマットに揃うことで、OSS MySQL 9.x エコシステムのツールやドライバとの相互運用性が高まり、ベンダー固有仕様への依存を減らせる

🛡️ 既定で高可用性構成

MySQL 9.7 指定時に Enterprise Plus が既定になるため、99.99% SLA (メンテナンス込み) やサブ秒のメンテナンスダウンタイムといった水準を意識せず得られる

🗓️ 移行計画が立てやすい

8.4 からの in-place アップグレードと DMS 移行の 2 つの公式パスが同時提供され、通常サポート開始日 (2026 年 8 月 6 日) も明示されている

⚙️ 技術面

🧠 複雑クエリの最適化余地

Hypergraph オプティマイザにより、多テーブル結合の実行計画品質を optimizer switch 単位で検証・改善できる

🧩 リレーショナルとドキュメントの統合

JSON Duality Views により、同一データに対して SQL と JSON ドキュメントの両アクセスパターンを二重管理なしに扱える

📐 ベクトル設計の柔軟化

次元数上限 16,383 (デフォルト 2,048) と、インデックス非作成テーブルでの複数ベクトル列サポートにより、スキーマ設計の自由度が向上

🧹 運用フラグの近代化

レガシーな InnoDB ログ / undo 関連フラグや旧用語フラグが整理され、接続メモリ上限やロール必須化などの管理系フラグが新たに公開

⚠️ デメリット・制約事項

🚧 制限事項

✗mysql_native_password の完全削除により、非対応のクライアント・アプリケーションは接続不能になる (8.4 のような猶予なし)
✗BigQuery のフェデレーテッドクエリは caching_sha2_password 非対応のため、MySQL 9.7 では組み込み認証ユーザーでのフェデレーテッドクエリが実質利用不可 (回避策なし)
✗innodb_log_file_size、innodb_log_files_in_group、innodb_undo_tablespaces、mysql_native_password_proxy_users、replica_parallel_type、slave_parallel_type、temptable_use_mmap は使用不可
✗MySQL Telemetry、PGO、Replication Applier Metrics Component は非サポート
✗8.0 / 8.4 で GA 版ベクトル検索を利用中の場合、フォーマット変更差分 (vector_to_string 出力形式、COMMENT / CONSTRAINT の扱い) の事前確認が必要
✗メジャーバージョンのスキップ不可のため、5.7 → 9.7、8.0 → 9.7 の直接アップグレードはできない
✗MySQL 8.0 以降はレガシー HA 構成 (フェイルオーバーレプリカ) 非対応、リージョン HA 構成のみ

🤔 考慮すべき点

💰 コスト増の可能性: --edition を指定しないと Enterprise Plus になるため、Enterprise edition 前提の見積もりのままだと想定外の請求増につながる。us-central1 の N2 系では vCPU 単価が約 30%、メモリ単価が 30% 高い。
  • リージョン制約: Enterprise Plus 非対応リージョンでは Enterprise Plus インスタンスを作成できない。対応リージョンを選ぶか Enterprise edition を明示する
  • Hypergraph オプティマイザは万能ではない: optimizer switch で有効化する任意機能。クエリ特性によっては従来オプティマイザのほうが良い計画を出す可能性があり、本番適用前にワークロード単位での検証が必要
  • プリチェックは完全ではない: MySQL Shell のアップグレードチェッカーがすべての非互換性を検出できるとは限らず、プリチェック通過後もアップグレードが失敗する可能性がある
  • リードレプリカも既定で Enterprise Plus: レプリカ作成時も同じ既定挙動のため、レプリカ側の edition と単価も確認する
  • ベクトルインデックスの再構築: 大量の DML 操作後は再構築を推奨。リーフあたり 100 ベクトル以上を目安にするとリコールが安定する

🎯 ユースケース

🔎 ユースケース 1: MySQL 上での RAG / 類似検索基盤の刷新

シナリオ: Cloud SQL for MySQL 8.4 上でベクトル検索 (GA 版) を運用中だが、独自の VARBINARY フォーマットと COMMENT / CONSTRAINT による識別のため OSS ツールチェーンとの相互運用に手間がかかっている。埋め込みモデルの更新で次元数も 16,000 を超える見込み。

SQL 
-- MySQL 9.7: USING VARBINARY は任意、上限 16,383 次元
CREATE TABLE items (
  id BIGINT PRIMARY KEY,
  title VARCHAR(255),
  embedding VECTOR(3072)
);

-- ANN 検索 (cloudsql_vector を on にしてベクトルインデックスを作成済みの場合)
SELECT id, title
FROM items
ORDER BY approx_distance(embedding, string_to_vector('[...]'), 'distance_measure=cosine')
LIMIT 10;

効果: コミュニティ標準フォーマットで相互運用性が向上し、16,383 次元まで対応。インデックスを作らないテーブルでは複数のベクトル列を保持でき、複数の埋め込みモデルを並行評価しやすくなる。

🧠 ユースケース 2: 複雑な分析系 JOIN クエリのプラン改善

シナリオ: 10 テーブル規模の JOIN を含むレポーティングクエリで、従来のオプティマイザが選ぶ結合順序が安定せず、実行時間のばらつきが大きい。

SQL 
-- セッション単位で Hypergraph オプティマイザを試験的に有効化し、
-- EXPLAIN ANALYZE で従来プランと比較する
SET SESSION optimizer_switch = 'hypergraph_optimizer=on';
EXPLAIN ANALYZE SELECT /* 複雑な多テーブル JOIN */ ...;

効果: 多テーブル結合向けに設計された結合プラン作成フレームワークにより、複雑クエリの実行計画を改善できる可能性。セッション単位で切り替えて A/B 比較できるため、本番影響を抑えて評価できる。

🧩 ユースケース 3: リレーショナルとドキュメント API の二重実装の解消

シナリオ: 正規化されたリレーショナルスキーマをマスターとしつつ、モバイルアプリ向けには入れ子の JSON ドキュメントを返す必要があり、アプリケーション層で変換ロジックとキャッシュを二重に維持している。

効果: JSON Duality Views が同一の基礎データに対してリレーショナル SQL と階層的 JSON ドキュメントの両モデルを提供するため、変換ロジックの実装・同期コストを削減できる。

MySQL 9.7 自体に追加料金はありません。料金は Cloud SQL の通常の課金要素 (CPU とメモリ、ストレージとネットワーク、インスタンス料金、Cloud DNS 料金、拡張サポート料金) で構成され、選択した Cloud SQL edition によって vCPU とメモリの単価が変わります。MySQL 9.7 では未指定時に Enterprise Plus が既定となるため、edition の違いがコストに直結します。

🌍 利用可能リージョン

MySQL 9.7 は Cloud SQL for MySQL のメジャーバージョンとして提供され、Enterprise edition と Enterprise Plus edition の両方 でサポートされます。ただし Enterprise Plus edition と対応マシンシリーズはリージョンによって提供状況が異なります。

⚠️ 注意: MySQL 9.7 を指定しても、選択したリージョンが Enterprise Plus に対応していない場合は、Enterprise Plus 対応リージョンを選ぶか Enterprise edition を明示する必要があります。リージョンごとの対応 edition とマシンシリーズは Cloud SQL のリージョン提供状況 を確認してください。

🔗 関連サービス・機能

🚚 Database Migration Service (DMS)

MySQL 8.4 から Cloud SQL for MySQL 9.7 への移行パスとして利用。継続的移行および 1 回限りの移行に対応。

⭐ Cloud SQL Enterprise Plus edition

MySQL 9.7 指定時の既定 edition。データキャッシュ、最適化された書き込み、読み取りプール、Managed Connection Pooling、高度な DR、書き込みエンドポイント、最大 35 日の PITR ログ保持、30 日の Query Insights メトリクス保持などを提供。

🔐 Cloud SQL Auth Proxy / Cloud SQL コネクタ

caching_sha2_password を使う場合、TCP ソケット接続では --get-server-public-key (JDBC では allowPublicKeyRetrieval=true) が必要。Unix ソケット + Auth Proxy + caching_sha2_password の組み合わせは非対応。

📊 BigQuery フェデレーテッドクエリ

caching_sha2_password 非対応のため、MySQL 9.7 インスタンスとの併用は制約が大きい。データ連携方式の見直しが必要。

🗂️ Database Center

組織内のすべての Cloud SQL インスタンスとデータベースバージョンを一覧し、9.7 への移行計画やフリートインベントリの棚卸しに利用可能。

🩺 メジャーバージョンアップグレードのプリチェック

gcloud beta sql instances pre-check-major-version-upgrade で 9.7 へのアップグレード準備状況を評価。

📚 Knowledge Catalog (旧 Dataplex Universal Catalog)

2026 年 8 月 7 日以降、HA 構成で新規作成された Cloud SQL for MySQL インスタンス (8.0 以降) はニアリアルタイムでメタデータを送信する設定が既定で有効。

📝 まとめ

✅ 大きな節目: Cloud SQL for MySQL 9.7 の GA は、コミュニティ標準のベクトルフォーマット、Hypergraph オプティマイザ、JSON Duality Views という MySQL 9.x の主要機能をマネージド環境に持ち込む大きな節目です。
🚨 破壊的変更に注意: mysql_native_password の完全削除を含みます。まずは組み込み認証ユーザーとクライアントを caching_sha2_password へ移行し、削除される 7 つのフラグの利用状況を棚卸しした上で、gcloud beta sql instances pre-check-major-version-upgrade によるプリチェックで 8.4 からのアップグレード可否を評価してください。
⚠️ 最も見落としやすい変更: 新規作成時は --edition を指定しなくても Enterprise Plus edition が既定 になります。同一スペックで Enterprise edition より約 30% 単価が高くなるため、コスト前提とリージョンの Enterprise Plus 対応状況を確認し、必要に応じて --edition=ENTERPRISE を明示する運用ルールの整備を推奨します。
