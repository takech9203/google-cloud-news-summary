🌊 Dataflow: Eager Watermark Advancement が GA

Dataflow Streaming Engine GA (一般提供)
リリース日: 2026-11-17

📌 概要

Dataflow の Streaming Engine ジョブ向けに Eager Watermark Advancement (積極的なウォーターマーク前進) が GA になりました。 有効にすると、遅れて到着したレコードがウォーターマークの前進を停滞させなくなり、ウィンドウ集計の結果出力やイベントタイム タイマーがスケジュールどおりに実行されます。 遅延レコードは破棄されず、オンタイムのデータと並行して処理されます。

ウォーターマークは「このウィンドウのデータはすべて到着したはず」と Dataflow が判断するしきい値で、ウィンドウのクローズやイベントタイム タイマーの発火を駆動します。 従来は未処理イベントの最小タイムスタンプを追跡するため、1 件の大幅に遅延したレコードがパイプライン全体のウォーターマークを凍結させる可能性がありました。

💡 こんなユーザーに有効: オフライン復帰後にバッファ済みデータをまとめて送信する IoT / モバイル ソース、過去のイベント タイムスタンプを持つ Pub/Sub メッセージや Kafka パーティションのバックログを扱うパイプラインの運用者。 ウィンドウ集計やステートフル処理を使う場合は、有効化前に allowed lateness (許容遅延) の設定が必要です。

❌ Before: アップデート前の課題

  • 遅延レコードが 1 件でも到着すると、ウォーターマークが最小タイムスタンプに固定され、パイプライン全体の前進が停滞
  • ウィンドウ集計の結果出力とイベントタイム タイマーの発火が遅延し、オンタイム データの結果まで待たされる
  • 停滞解消の瞬間に溜まったウィンドウが一斉クローズし、ワーカー使用率のスパイクが発生
  • IoT のバッファ送信や Kafka バックログ流入のたびに出力レイテンシが予測不能

✅ After: アップデート後の改善

  • 遅延レコードの処理とウォーターマーク前進が分離され、オンタイム データに基づいて前進
  • ウィンドウ結果とタイマーがスケジュールどおり実行され、出力レイテンシが予測可能に
  • 遅延レコードは並行処理され、allowed lateness に従い late パネとして出力
  • 一斉クローズによるスパイクが緩和され、リソース使用が平準化
  • 全 Beam SDK (Java / Python / Go) で SDK アップグレード不要、オプション指定のみ

Eager Watermark Advancement を有効にすると、遅延レコードはウォーターマークの前進から切り離されて並行処理され、オンタイム データによるウィンドウ集計とタイマーは停滞せずにスケジュールどおり実行されます。 遅延レコードは allowed lateness の範囲内であれば late パネとして出力されます。

⚡ 主要機能

1️⃣ ウォーターマーク前進と遅延レコード処理の分離

従来は 1 件の遅延レコードが全下流ステージのウォーターマークを凍結。有効化後は、遅延レコードはステージのウォーターマークを保持せずに処理され、ウォーターマークはオンタイム データに基づいて前進します。

2️⃣ スケジュールどおりのウィンドウ出力とタイマー発火

ウィンドウ集計の結果とイベントタイム タイマーが遅延レコードの影響を受けずに予定どおり実行。溜まったウィンドウの一斉クローズによるワーカー使用率スパイクも緩和され、使用率が平準化されます。

3️⃣ 遅延レコードの継続処理 (破棄ではない)

遅延レコードはオンタイム データと並行して処理され、allowed lateness 内であれば late パネとして出力。超過したレコードはウィンドウ結果から除外されるため、事前の設定確認が重要です。

4️⃣ 専用モニタリング メトリクスの提供

per_stage_data_watermark_age_with_late_data は本機能がない場合のウォーターマーク経過時間を示し、差分で削減されたレイテンシを確認できます。 per_stage_oldest_pending_element_age は最古の未処理要素の経過時間を示し、allowed lateness に近づくと破棄リスクを察知できます。

🛠️ 設定方法

✅ 前提条件

✓ジョブが Streaming Engine を使用するストリーミング パイプラインであること
✓想定される遅延をカバーする allowed lateness をウィンドウ戦略に設定すること (例: Window.into(...).withAllowedLateness(Duration.standardMinutes(60)))
✓トリガー、累積モード (accumulation mode)、PaneInfo の扱いが late パネを正しく処理できることを確認すること

ステップ 1: allowed lateness の設定を確認する

Java 1 時間の遅延を許容するウィンドウ設定 
// Java の例: 1 時間の遅延を許容するウィンドウ設定
PCollection<KV<String, Long>> counts = input
    .apply(Window.<KV<String, Long>>into(FixedWindows.of(Duration.standardMinutes(5)))
        .withAllowedLateness(Duration.standardHours(1))
        .triggering(AfterWatermark.pastEndOfWindow()
            .withLateFirings(AfterPane.elementCountAtLeast(1)))
        .accumulatingFiredPanes())
    .apply(Count.perKey());
⚠️ 注意: 従来はウォーターマークの停滞により遅延レコードが「オンタイム」と誤分類される副次的な安全網がありました。有効化後はより多くのレコードが正しく late と判定されます。allowed lateness が不足していると破棄が増えるため、事前に設定を見直してください。

ステップ 2: サービス オプションを指定してジョブを起動する

Bash Flex Template の例 
gcloud dataflow flex-template run JOB_NAME \
    --template-file-gcs-location=TEMPLATE_LOCATION \
    --region=REGION \
    --enable-streaming-engine \
    --additional-experiments=enable_eager_watermark_advancement

Terraform の場合は google_dataflow_flex_template_job リソースで enable_streaming_engine = true と additional_experiments = ["enable_eager_watermark_advancement"] を指定します。

ステップ 3: 有効化と破棄率をモニタリングする

Bash ジョブログで有効化を確認 
# ジョブログで有効化を確認
# "Eager watermark advancement is enabled for this job." が出力される
gcloud logging read 'resource.type="dataflow_step" AND "Eager watermark advancement"' --limit 5

有効化後は、ジョブ情報パネルのカスタム カウンタ droppedDueToLateness を監視し、遅延による破棄が許容範囲内であることを確認します。破棄が多い場合は allowed lateness を延長します。

👍 メリット

💼 ビジネス面

  • 出力レイテンシの予測可能性: ダッシュボードやアラートなどリアルタイム分析の結果が、少数の遅延データに左右されずスケジュールどおりに届く
  • SLO 達成の容易化: イベントタイム ベースの集計結果の提供時間が安定し、下流システムとのレイテンシ SLO を立てやすい
  • 導入コストの低さ: SDK アップグレード不要でサービス オプションの指定のみ。既存パイプラインへの適用障壁が低い

⚙️ 技術面

  • ウォーターマーク停滞の解消: 1 件の遅延レコードがパイプライン全体のウィンドウ出力とタイマーを凍結させる問題が解消
  • リソース使用の平準化: 溜まったウィンドウの一斉クローズによるワーカー使用率スパイクが緩和
  • 可観測性の向上: 専用メトリクスでレイテンシ削減効果と破棄リスクを定量的に把握

⚠️ デメリット・制約事項

🚫 制限事項

✕Streaming Engine を使用するストリーミング ジョブ専用 (バッチジョブや Streaming Engine 無効のジョブでは利用不可)
✕実行中のジョブでオン / オフを切り替えられず、新規ジョブまたは置換ジョブ (--update) が必要
✕すべてのソースが有界 (bounded) の場合、ジョブは自動的に完了しないため、手動でドレインが必要
✕処理の遅さ (重い計算、遅い RPC、CPU / メモリのボトルネック) に起因するウォーターマーク ラグは改善されない。あくまで遅延到着データの影響を分離する機能

🤔 考慮すべき点

  • 従来はウォーターマーク停滞が遅延レコードを「オンタイム」扱いにする意図しない安全網として機能していた。有効化後はより多くのレコードが正しく late と判定されるため、allowed lateness が不足していると破棄が増える
  • トリガー、累積モード、PaneInfo の処理が late パネを正しく扱えるか、有効化前に確認が必要
  • 有効化後は droppedDueToLateness カウンタと per_stage_oldest_pending_element_age メトリクスを監視し、破棄率が許容範囲内か継続的に確認する
  • 無効化する場合は、オプションを外した置換ジョブを起動する。ウォーターマークは後退しないため、新ジョブは旧ジョブのウォーターマークを引き継ぐ

🎯 ユースケース

📱 ユースケース 1: IoT デバイスのオフライン復帰によるバッファ データ流入

シナリオ: 工場のセンサーや車載デバイスがネットワーク断から復帰し、オフライン中にバッファした数時間分の過去タイムスタンプ付きデータを一斉送信する。従来はこの古いデータがウォーターマークを引き戻し、直近のリアルタイム集計の出力まで停滞していた。

Bash 実装例 
gcloud dataflow flex-template run iot-aggregation \
    --template-file-gcs-location=gs://my-bucket/templates/iot-agg.json \
    --region=asia-northeast1 \
    --enable-streaming-engine \
    --additional-experiments=enable_eager_watermark_advancement

効果: リアルタイム データのウィンドウ集計はスケジュールどおり出力され、復帰デバイスの過去データは allowed lateness の範囲内で late パネとして並行処理される。ダッシュボードの更新遅延が解消される。

📨 ユースケース 2: アイドル状態の Kafka パーティションへのバックログ流入

シナリオ: イベントタイム (CreateTime) を使用する Kafka ソースで、長時間アイドルだったパーティションに古いイベントのバックログが流入する。従来はパイプライン全体のウォーターマークが停滞し、イベントタイム タイマーに依存するステートフル処理 (セッション管理、タイムアウト検知など) が遅延していた。

効果: イベントタイム タイマーが予定どおり発火し、セッション確定やタイムアウト検知のレイテンシが安定する。バックログは並行処理されるため、データの取りこぼしもない (allowed lateness 内)。

🔗 関連サービス・機能

⚙️ Dataflow Streaming Engine

本機能の前提。パイプライン実行をワーカー VM から Dataflow サービス バックエンドに移し、リソース削減と柔軟なオートスケーリングを実現する

📨 Pub/Sub

代表的なストリーミング ソース。イベント タイムスタンプ属性を使用する場合、ソース ウォーターマークより古いメッセージが本機能の対象となる

📊 Cloud Monitoring

per_stage_data_watermark_age_with_late_data などの専用メトリクスで本機能の効果と破棄リスクを監視できる

🧩 Apache Beam (windowing / triggers / allowed lateness)

ウィンドウ戦略、トリガー、allowed lateness の設定が本機能の挙動 (late パネ出力と破棄) を決定する

📝 まとめ

Eager Watermark Advancement の GA により、少数の遅延レコードがストリーミング パイプライン全体の出力を停滞させる長年の課題が、SDK アップグレード不要のサービス オプション 1 つで解消できるようになりました。 ウィンドウ集計やイベントタイム タイマーを使用する Streaming Engine ジョブを運用しているなら、まず allowed lateness が想定遅延をカバーしているかを確認した上で有効化し、 droppedDueToLateness カウンタと専用メトリクスで破棄率とレイテンシ削減効果を検証することを推奨します。
