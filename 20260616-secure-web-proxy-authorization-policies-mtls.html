🔐 Secure Web Proxy: Authorization Policies と Frontend mTLS 統合

Secure Web Proxy Preview
2026-06-16

📋 概要

Secure Web Proxy に Authorization Policies (認可ポリシー) と Frontend mTLS 統合 の 2 つの新機能が Preview として追加。アウトバウンドトラフィックに対して ID ベースおよびコンテンツベースのアクセス制御を実現し、ゼロトラストアーキテクチャに適合した ID 中心のセキュリティモデルを提供する。

❌ Before (アップデート前)

  • IP アドレス、SA、セキュアタグ、宛先ホスト名に基づくフィルタリングのみ
  • リクエストコンテンツに基づく制御が不可
  • 外部認可エンジンへの委譲 (Service Extensions) 非対応
  • クライアント証明書による暗号的 ID 検証手段なし
  • SWP / ALB / CSM で異なるポリシー API が必要

✅ After (アップデート後)

  • 統一 AuthzPolicy API で SWP / ALB / CSM を一括管理
  • Service Extensions で外部認可エンジンに判断委譲可能
  • Frontend mTLS で SPIFFE ID / DNS SAN に基づく制御
  • リクエストレベル認可 + コンテンツスキャンの両方をサポート
  • ゼロトラストモデルの完全な実装が可能

🏗️ アーキテクチャ図

⚡ 主要機能

📋 1. Authorization Policies (認可ポリシー)

統一された AuthzPolicy API を使用し、ソース、宛先、リクエスト属性に基づくアクセス制御ルールを定義。

ALLOW
条件一致で転送
DENY
403 で拒否
CUSTOM
外部に委譲
→Gateway リソースにアタッチしてアウトバウンドトラフィックのセキュリティ境界を定義

🔐 2. Frontend mTLS 統合

クライアントが Secure Web Proxy に接続する際に相互 TLS ハンドシェイクを実施し、暗号的に ID を検証。

→TrustConfig リソースでクライアント証明書を検証
→URI_SAN (SPIFFE ID) や DNS SAN などの ID 属性を抽出
→抽出した ID を Authorization Policies で使用しきめ細かなアクセス制御を実施
→Explicit Proxy Routing モードでのみサポート

🔄 3. Service Extensions による認可委譲

CUSTOM アクションにより、外部認可エンジンに判断を委譲可能。

→REQUEST_AUTHZ: リクエストメタデータとヘッダーに基づく認可判断 (ID 検証、権限確認)
→CONTENT_AUTHZ: データペイロードに基づく認可判断 (機密データ保護、脅威検出、Model Armor 連携)
→failOpen 設定により、拡張機能タイムアウト時の動作を制御可能

🔧 技術仕様

Authorization Policies の構成要素

項目詳細
APIAuthzPolicy (network-security)
ポリシープロファイルREQUEST_AUTHZ / CONTENT_AUTHZ
アクションALLOW / DENY / CUSTOM
ソース条件サービスアカウント、セキュアタグ、mTLS 証明書の principals
宛先条件ホスト名 (exact)、パス (exact / prefix)
前提条件TLS インスペクションの有効化が必須

Frontend mTLS の構成要素

項目詳細
認証モードREJECT_INVALID / ALLOW_INVALID_OR_MISSING_CLIENT_CERT
証明書リソースTrustConfig (Certificate Manager)
ポリシーリソースServerTlsPolicy (network-security)
サポートする IDSPIFFE ID (URI_SAN)、DNS SAN
デプロイモードExplicit Proxy Routing モードのみ

💻 設定方法

認可ポリシーの YAML 設定例 (mTLS ベース)

YAML 
name: test-authz-policy-mtls
target:
  resources:
    - "projects/PROJECT_ID/locations/LOCATION/gateways/swp1"
  policyProfile: REQUEST_AUTHZ
httpRules:
  - to:
      operations:
        - hosts:
            - exact: "example.com"
          paths:
            - exact: "/mcp"
    from:
      sources:
        - principals:
            - principalSelector: CLIENT_CERT_URI_SAN
              principal:
                exact: "spiffe://PROJECT_ID.global.123.workload.id.goog/ns/ns1/sa/hellomcp"
    action: ALLOW

前提条件

💡 必須条件:
  • Secure Web Proxy が Explicit Proxy Routing モードでデプロイ済み
  • TLS インスペクションが有効化済み
  • IAM ロール: Certificate Manager Owner, Compute Network Admin, Compute Security Admin, Networksecurity Admin

ServerTlsPolicy リソース作成

YAML 
name: SERVER_TLS_POLICY_NAME
mtlsPolicy:
  clientValidationMode: REJECT_INVALID
  clientValidationTrustConfig: projects/PROJECT_ID/locations/LOCATION/trustConfigs/TRUST_CONFIG_NAME
Bash 
gcloud network-security server-tls-policies import SERVER_TLS_POLICY_NAME \
  --source=server_tls_policy.yaml \
  --location=LOCATION

# Authorization Policy のインポート
gcloud beta network-security authz-policies import my-authz-policy \
  --source=authz-policy.yaml \
  --location=LOCATION

✅ メリット

ビジネス面

🎯ゼロトラスト戦略の実現: IP ベースではなく ID ベースの認可
🔧統合的なポリシー管理: SWP / ALB / CSM を同一 API で管理
📋コンプライアンス強化: コンテンツスキャンと ID 検証の組み合わせ

技術面

🔐暗号的な ID 検証: mTLS でなりすましを防止
🔄柔軟な認可委譲: Service Extensions でカスタムロジック委譲可能
🏷️SPIFFE 準拠: サービスメッシュやワークロード ID 管理と統合

⚠️ 制約事項・考慮点

制限事項:
  • Frontend mTLS は Explicit Proxy Routing モードでのみサポート (Next Hop / PSC モード非対応)
  • Authorization Policies は URL リスト (UrlList) や正規表現マッチングをサポートしない
  • TLS インスペクションの有効化が必須
  • 同一ゲートウェイで Authorization Policies と Gateway Security Policies の同時使用不可 (排他的)
  • Authorization Extensions は FQDN ベースのターゲットのみサポート
  • Preview ステータスのため Pre-GA Offerings Terms が適用
💡 考慮すべき点:
  • Gateway Security Policies から移行時、URL リストの代替手段を事前に検討
  • mTLS 導入時は証明書ライフサイクル管理 (発行、更新、失効) の運用設計が必要
  • failOpen 設定がセキュリティと可用性のトレードオフとなる

💡 ユースケース

🤖 UC1: AI エージェントの外部 API アクセス制御

シナリオ: 複数の AI エージェントが外部 API にアクセスする環境で、各エージェントがアクセスできる宛先を SPIFFE ID に基づいて制御。

効果: 認証済みの AI エージェントのみが特定の外部 API にアクセス可能となり、不正なエージェントからの API 呼び出しを防止。

🛡️ UC2: コンテンツスキャンによるデータ漏洩防止

シナリオ: アウトバウンドトラフィックに機密データが含まれていないか、Model Armor や Sensitive Data Protection と連携してスキャン。

効果: CONTENT_AUTHZ プロファイルにより、PII や機密データの外部流出を検知・ブロック。

🏢 UC3: マルチテナント環境でのテナント別アクセス制御

シナリオ: GKE クラスタ内で各テナントのワークロードがアクセスできる外部サービスをサービスアカウントやセキュアタグに基づいて制限。

効果: テナントごとに異なる認可ポリシーを適用し、アイソレーションを確保しつつ統一プロキシインフラを共有可能。
