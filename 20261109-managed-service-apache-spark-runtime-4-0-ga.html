📋 概要

Managed Service for Apache Spark (旧称: Google Cloud Serverless for Apache Spark) のランタイムバージョン 4.0 が GA になりました。 Apache Spark 4.2.0、Java 25、Python 3.13、Scala 2.13.17 など最新コンポーネントで構成され、サーバーレス Spark の実行基盤が大幅に刷新されています。

単なるコンポーネント更新に留まらず、バッチワークロードがデフォルトでプレミアムティア + Lightning Engine で実行されるなど、実行モデルのデフォルトが大きく変わるメジャーアップデートです。 メモリシェイプによる設定簡素化、fast-startup VM、Lakehouse runtime catalog のデフォルト化、DCU (Data Compute Units) クォータの導入が含まれます。

💡 対象読者: ETL パイプラインやデータレイクハウス処理をサーバーレス Spark で運用しているデータエンジニア、Dataproc Serverless からの移行を検討しているチーム。一方で SparkR バッチ、Jupyter セッション、Persistent History Server など一部機能が非サポートとなるため、移行時には挙動変更の確認が必要です。

😣 Before: ランタイム 3.0 までの課題

  • Lightning Engine やプレミアムティアの利用には compute.tier / disk.tier など複数プロパティの個別設定が必要
  • ドライバ/エグゼキュータのメモリは手動調整が必要で、サイジングに試行錯誤
  • Iceberg テーブル利用には Spark カタログの明示的な構成が必要
  • Compute Engine CPU / ディスククォータを他ワークロードと奪い合う構造

😀 After: ランタイム 4.0 での改善

  • デフォルトでプレミアムティア + Lightning Engine。dataproc.tier 1 つでティアを制御
  • メモリシェイプ (デフォルト highmem: 7.75 GiB/vCPU) で Spark ヒープとオーバーヘッドを自動サイジング
  • Lakehouse runtime catalog がデフォルトになり、カタログ設定なしで Iceberg テーブルを利用可能
  • fast-startup VM でドライバ起動時間を短縮
  • GPU を使わないワークロードは専用の DCU クォータを消費し、Compute Engine クォータと分離

ランタイム 4.0 では、プレミアムティア + Lightning Engine + highmem メモリシェイプがデフォルトとなり、ユーザーが個別にプロパティを設定しなくても高性能な構成でバッチワークロードが実行されます。クォータも Compute Engine から専用の DCU クォータに移行します。

⚙️ 主要機能

1️⃣ 最新コンポーネントへの刷新

→Apache Spark 4.2.0、BigQuery Connector 0.46.0、Cloud Storage Connector 4.0.7、Java 25、Python 3.13、Scala 2.13.17 を搭載
→デフォルト文字エンコーディングは UTF-8
→Python 環境の管理が Conda から Pixi に変更

2️⃣ プレミアムティア + Lightning Engine がデフォルト

→バッチは dataproc.tier を standard にしない限りプレミアムティアで実行 (インタラクティブセッションは常にプレミアムティア)
→プレミアムティアのバッチは Lightning Engine をデフォルトで使用 (オプトアウトは spark.dataproc.engine=default)
→セッションで使う場合は spark.dataproc.engine=lightningEngine、Native Query Execution は spark.dataproc.lightningEngine.runtime=native を追加
→従来の spark.dataproc.driver.compute.tier などの個別プロパティは廃止され、dataproc.tier 1 つでリソースが決まる

3️⃣ メモリシェイプの導入

→メモリをシェイプ (highmem / standard) で指定する新方式。デフォルトは highmem (7.75 GiB/vCPU)、standard は 3.75 GiB/vCPU
→Spark ヒープとメモリオーバーヘッドへの分割は自動 (spark.driver.memory などの手動設定が不要に)
→分割比率の変更には spark.driver.memoryOverheadFactor / spark.executor.memoryOverheadFactor を使用

4️⃣ fast-startup VM によるドライバ起動高速化

→プレミアムティアでデフォルトのドライバ構成 (4 vCPU、メモリシェイプ使用、ディスク 450 GiB 以下、メモリ手動設定・GPU なし) の場合、ドライバが fast-startup VM で起動し、起動時間が短縮される

5️⃣ Lakehouse runtime catalog がデフォルトカタログ

→デフォルトの Spark カタログが Lakehouse runtime catalog になり、カタログを構成せずに Apache Iceberg テーブルの作成・クエリが可能
→従来の事前構成済み bigquery Spark カタログも引き続き利用可能

6️⃣ DCU クォータの導入

→GPU を使わないワークロードは Dataproc API の DCU クォータ (dataproc.googleapis.com/data_compute_units) を消費
→GPU、予約、グローバル Compute Engine クォータは DCU クォータモデルの対象外

🧮 DCU 消費量の計算

DCU 使用量はノードごとに VM シェイプから算出されます。

→vCPU あたり 0.6 DCU
→メモリ 1 GB あたり 0.1 DCU (vCPU あたり 8 GB まで)
→vCPU あたり 8 GB を超えるメモリ (拡張メモリ) は 1 GB あたり 0.2 DCU
→プレミアムティアのノードは同一シェイプのスタンダードティアの 1.5 倍の DCU としてカウント
💡 計算例: スタンダードティアで 4 vCPU / 16 GB メモリのノードは 4 × 0.6 + 16 × 0.1 = 4 DCU。ドライバ 1 + エグゼキュータ 10 のバッチは 44 DCU、同じ構成をプレミアムティアで実行すると 66 DCU を消費します。

🛠️ 設定方法

✅ 前提条件

✓Dataproc API が有効化されている Google Cloud プロジェクト

ステップ 1: ランタイム 4.0 でバッチワークロードを送信

Bash デフォルトでプレミアムティア + Lightning Engine + highmem で実行 
gcloud dataproc batches submit pyspark gs://my-bucket/my_job.py \
  --region=us-central1 \
  --version=4.0 \
  --subnet=projects/my-project/regions/us-central1/subnetworks/my-subnet

ステップ 2: 必要に応じてティアやメモリシェイプを変更

Bash スタンダードティアで実行する場合 (Lightning Engine は使用不可) 
# スタンダードティアで実行する場合 (Lightning Engine は使用不可)
gcloud dataproc batches submit pyspark gs://my-bucket/my_job.py \
  --region=us-central1 \
  --version=4.0 \
  --subnet=my-subnet \
  --properties=dataproc.tier=standard,spark.dataproc.executor.memory.shape=standard
⚠️ 注意: メモリシェイプと spark.driver.memory / spark.executor.memory などの手動メモリ設定は同時指定できません。

ステップ 3: DCU クォータの確認・調整

→Google Cloud コンソールの「割り当て」ページ (Dataproc API) で data_compute_units クォータを確認し、必要に応じて引き上げを申請
→使用量が上限に近づいたときに自動でクォータを引き上げる quota adjuster の有効化も検討可能

✓予測可能な料金モデル: プレミアムティアの DCU 単価に Lightning Engine、拡張メモリ、シャッフル集約型ジョブ向けインフラの利用料が含まれ、追加コンピュート費用なしで全プレミアム機能にアクセス可能
✓運用負荷の軽減: チューニング用プロパティの削減により、Spark 設定の属人化や試行錯誤の工数を削減

🔧 技術面

✓設定の簡素化: ティア、メモリシェイプ、ディスクサイズがそれぞれ少数のプロパティで決まり、従来の個別プロパティ群が不要に
✓最新スタックの利用: Spark 4.2.0、Java 25、Python 3.13 など最新のランタイムで、新しい言語機能やライブラリを利用可能
✓レイクハウス対応の強化: Lakehouse runtime catalog により Iceberg テーブルをゼロコンフィグで利用でき、BigQuery との連携も bigquery カタログで維持
✓クォータの分離: Spark ワークロードが Compute Engine クォータを消費しなくなり、同一プロジェクト内の他ワークロードとのクォータ競合を回避

🚧 デメリット・制約事項

⛔ 制限事項

✗spark.dataproc.driver.compute.tier、spark.dataproc.executor.compute.tier、spark.dataproc.driver.disk.tier、spark.dataproc.executor.disk.tier プロパティは非サポート (dataproc.tier を使用)
✗spark.memory.offHeap.enabled / spark.memory.offHeap.size (オフヒープメモリ) プロパティは非サポート
✗SparkR バッチは非サポート (代替: sparklyr)
✗Jupyter セッションは非サポート (代替: Spark Connect セッション)
✗Persistent History Server (PHS) は非サポート (代替: Spark UI)
✗Cloud Storage ステージングバケットは使用されない
✗サブネットワークの明示指定が必須。デュアルスタック (IPv4/IPv6) および IPv6 専用サブネットは非サポート
✗GPU、予約、グローバル Compute Engine クォータは DCU クォータモデルの対象外
✗autoscaling (デフォルト有効) と分散 Spark XGBoost は併用不可 (spark.dynamicAllocation.enabled=false で回避)

🤔 考慮すべき点

⚠️ デフォルトがプレミアムティアに変更: プレミアム DCU 単価 (約 1.5 倍の DCU カウント) で課金されるため、コスト重視のワークロードは dataproc.tier=standard の明示設定を検討してください。
⚠️ メモリ使用量の増加: デフォルトの highmem シェイプは 3.0 ランタイムのデフォルトより多くのメモリ (7.75 GiB/vCPU) を割り当てるため、DCU 消費が増えます。コスト最適化には standard シェイプの検討も有効です。
⚠️ カスタム BigQuery コネクタ利用時の注意: 独自の Spark BigQuery コネクタ JAR を追加する場合、dataproc.artifacts.remove=spark-bigquery-connector を設定しないとバッチワークロードが失敗します。
⚠️ 移行前の DCU クォータ確認: ランタイム 4.0 へのオンボーディング時は、想定ワークロードに対して十分な DCU クォータがあるか必ず確認してください。

🎯 ユースケース

📈 ユースケース 1: 大規模 ETL パイプラインの高速化

シナリオ: Cloud Storage 上の Parquet データを変換して BigQuery にロードする夜間 ETL バッチの実行時間が長く、コスト削減と SLA 短縮が課題。

Bash 実装例 
gcloud dataproc batches submit pyspark gs://my-bucket/etl_job.py \
  --region=asia-northeast1 \
  --version=4.0 \
  --subnet=my-subnet

効果: Lightning Engine がデフォルトで有効になり、コード変更なしで最大 4.9 倍のクエリ実行性能を得られる。実行時間短縮により DCU 課金時間も削減される。

🧊 ユースケース 2: Iceberg ベースのオープンレイクハウス構築

シナリオ: Apache Iceberg を中核としたレイクハウスを構築したいが、Spark カタログの構成・管理が負担になっている。

効果: Lakehouse runtime catalog がデフォルトカタログのため、カタログ設定なしで Iceberg テーブルの作成・クエリが可能。BigQuery との相互運用も bigquery カタログで維持でき、マルチエンジン分析基盤を素早く立ち上げられる。

⏱️ ユースケース 3: 起動レイテンシに敏感なスケジュールジョブ

シナリオ: Cloud Composer から高頻度で短時間の Spark ジョブを起動しており、ワークロードの起動時間がパイプライン全体のレイテンシのボトルネックになっている。

効果: デフォルトドライバ構成のままプレミアムティアで実行すれば fast-startup VM が適用され、起動時間が短縮される。標準/プレミアムティアの平均起動時間は 40〜50 秒。

💰 料金

サーバーレスデプロイは DCU (Data Compute Unit)、シャッフルストレージ、GPU (使用時) に対して秒単位で課金されます。 ランタイム 4.0 ではバッチワークロードがデフォルトでプレミアムティアとなるため、プレミアム DCU 単価が適用される点に注意が必要です。

📝 まとめ

ランタイム 4.0 は、Spark 4.2.0 / Java 25 / Python 3.13 への刷新に加え、プレミアムティア + Lightning Engine のデフォルト化、メモリシェイプ、DCU クォータ移行など実行モデルの大きな変更を伴う GA リリースです。

性能と設定の簡素化のメリットが大きい一方、デフォルトのティア変更によるコスト影響や SparkR / Jupyter セッション / PHS の非サポートなど移行時の確認事項も多いため、既存ワークロードは「Unsupported functionality and behavior changes」を確認のうえ、DCU クォータを事前に見積もってから段階的に 4.0 へ移行することを推奨します。
