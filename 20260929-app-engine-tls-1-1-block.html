🔒 App Engine: TLS 1.1 以前の非セキュアなトラフィックを恒久的にブロック

リリース日: 2026-09-29
☁️ App Engine ⛔ TLS 1.0 / 1.1 恒久ブロック Feature (セキュリティ強制適用) スタンダード / フレキシブル 全ランタイム

📌 概要

App Engine は、TLS バージョン 1.1 以前を使用する非セキュアなトラフィックを恒久的にブロックするようになりました。 スタンダード環境 (Go、Java、Node.js、PHP、Python、Ruby) とフレキシブル環境 (.NET、Go、Java、Node.js、PHP、Python、Ruby、カスタムランタイム) のすべてのランタイムに同一に適用されます。

ブロックの挙動はドメイン種別で異なります。appspot.com ドメインでは接続レベル (TLS ハンドシェイク自体) でブロックされる一方、カスタムドメインではハンドシェイクは成功する場合があり、その後のリクエストがブロックされます。

❌ Before (アップデート前の課題)

  • 既知の脆弱性を持つ TLS 1.0 / 1.1 が App Engine への接続に使用できる状態が残っていた
  • 2026 年 8 月の自動オプトイン後も 8 月末までオプトアウト可能で、非セキュアなトラフィックを受け入れる余地があった
  • TLS バージョンの強制には管理者による明示的な設定 (--ssl-policy) が必要だった

✅ After (アップデート後の改善)

  • TLS 1.1 以前のトラフィックが恒久的にブロックされ、全アプリで最低 TLS 1.2 が保証される
  • appspot.com ではハンドシェイク時点で接続を拒否し、非セキュアな接続の確立自体を防止
  • 古い TLS バージョンには設定で戻せなくなり、組織全体のセキュリティベースラインを強制 (移行に追加時間が必要な場合はサポートへ問い合わせ)

TLS 1.2 以降のトラフィックのみが App Engine アプリケーションに到達します。TLS 1.1 以前のトラフィックは、appspot.com ドメインでは接続レベルで、カスタムドメインではリクエストレベルでブロックされます。

⚠️ 注意: カスタムドメインでは TLS ハンドシェイクが成功する場合があるため、外部の SSL チェックサイトが「TLS 1.1 以前がまだサポートされている」と誤って判定する可能性があります。

⚙️ 主要機能

1️⃣ TLS 1.1 以前のトラフィックの恒久的ブロック

→TLS 1.1 以前を使用する非セキュアなトラフィックを恒久的にブロック
→スタンダード環境・フレキシブル環境のすべてのランタイム (カスタムランタイム含む) に適用
→恒久的にブロックされたプロジェクトでは、設定変更で古い TLS バージョンに戻すことは不可

2️⃣ ドメイン種別ごとのブロック挙動

→appspot.com ドメイン: TLS ハンドシェイク自体が拒否され、接続レベルでブロック
→カスタムドメイン: ハンドシェイクは成功する場合があるが、リクエストが 400 Bad Request - The request was malformed エラーでブロック (接続は確立されるがリクエストは拒否)

3️⃣ 新規アプリケーションのデフォルト動作

→新規アプリでは、デフォルトで TLS 1.2 以降とサポート対象の暗号スイートによるセキュアなトラフィックのみ許可
→デフォルトの暗号スイートで十分な場合、外部アプリケーションロードバランサの構成は不要

4️⃣ 移行猶予のためのサポート窓口

→恒久的にブロックされ、TLS 1.2 以降への切り替えに追加時間が必要な場合は、Google Cloud サポートへの問い合わせが必要

🛠️ 設定方法

📋 前提条件

✓Google Cloud CLI (gcloud) がインストールされていること
✓対象の App Engine アプリケーションに対する更新権限があること

ステップ 1: 最低 TLS バージョンの明示的な設定

--ssl-policy フラグで最低許可 TLS バージョンを指定します。

Bash gcloud による最低 TLS バージョン設定 
# アプリ作成時に最低 TLS バージョンを設定
gcloud app create --ssl-policy=TLS_VERSION_1_2

# 既存アプリの最低 TLS バージョンを更新
gcloud app update --ssl-policy=TLS_VERSION_1_2
💡 ポイント: TLS_VERSION_1_2 を指定すると、TLS 1.2 以降とモダンな暗号スイートのみが許可されます。恒久的にブロックされたプロジェクトでは、この設定を使用して古い TLS バージョンに戻すことはできません。

ステップ 2 (任意): ロードバランサによる TLS 制御の強化

カスタムドメインで接続レベル (ハンドシェイク) での拒否が必要な場合や、異なる暗号スイートセットが必要な場合は、グローバル外部アプリケーションロードバランサ + サーバーレス NEG を構成し、SSL ポリシーで TLS バージョンや暗号スイートを制御します。

Bash SSL ポリシーの作成例 (最低 TLS 1.2、MODERN プロファイル) 
# 例: SSL ポリシーの作成 (最低 TLS 1.2、MODERN プロファイル)
gcloud compute ssl-policies create my-ssl-policy \
    --profile=MODERN \
    --min-tls-version=1.2

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓コンプライアンス対応: 既知の脆弱性を持つ TLS 1.0 / 1.1 が排除され、PCI DSS などモダンな TLS を要求するセキュリティ基準への準拠が容易に
✓運用負荷ゼロのセキュリティ強化: プラットフォーム側で強制されるため、アプリごとの個別対応や監視が不要

🔧 技術面のメリット

✓セキュリティベースラインの保証: 全 App Engine アプリで最低 TLS 1.2 とセキュアな暗号スイートを保証
✓接続レベルの防御 (appspot.com): 非セキュアな接続はハンドシェイク段階で拒否され、アプリに到達しない

🚧 制限事項

✗恒久ブロック後は --ssl-policy で古い TLS バージョンに戻せない (追加の移行時間が必要な場合はサポートへ問い合わせ)
✗カスタムドメインで接続レベル (ハンドシェイク) の拒否が必要な場合は、グローバル外部アプリケーションロードバランサの構成が必要
✗デフォルトと異なる暗号スイートセットが必要な場合も、ロードバランサと SSL ポリシーの利用を推奨

🤔 考慮すべき点

!TLS 1.0 / 1.1 のみ対応の古いクライアント (レガシー組み込み機器、古い OS / ブラウザ、古い HTTP ライブラリなど) はアクセスが失敗するため、クライアント側の TLS 対応状況の確認が必要
!カスタムドメインでは 400 Bad Request で失敗し、TLS エラーではなく HTTP エラーとして観測される
!外部 SSL チェックサイトはハンドシェイク成功のみを検証し、「TLS 1.1 以前がサポートされている」と誤報告する可能性

🎯 ユースケース

💡 ユースケース 1: レガシークライアントの影響調査と移行

シナリオ: カスタムドメインで公開している App Engine アプリに、古い組み込み機器やレガシーシステムからのアクセスがある。TLS 1.1 以前のクライアントは 400 Bad Request で失敗するようになるため、影響範囲を特定し、クライアント側を TLS 1.2 以降へ更新する。

Bash TLS バージョンごとの接続確認 
# TLS 1.2 での接続確認 (成功するはず)
curl -v --tls-max 1.2 --tlsv1.2 https://YOUR_APP.appspot.com/

# TLS 1.1 での接続確認 (appspot.com ではハンドシェイクが失敗するはず)
curl -v --tls-max 1.1 https://YOUR_APP.appspot.com/

効果: 恒久ブロックによる影響を事前に把握し、レガシークライアントの計画的な更新につなげられる。

💡 ユースケース 2: カスタムドメインでの接続レベル拒否の実現

シナリオ: セキュリティ要件として、カスタムドメインでも TLS 1.1 以前をハンドシェイク段階で拒否したい (リクエストレベルの 400 エラーでは不十分)。

実装例: グローバル外部アプリケーションロードバランサ + サーバーレス NEG で App Engine にルーティングし、SSL ポリシー (--min-tls-version=1.2) を適用する。
