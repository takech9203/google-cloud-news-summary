☁️ Cloud Service Mesh 🛡️ セキュリティアップデート GCP-2026-076

🔒 Cloud Service Mesh セキュリティパッチ
1.31.3-asm.3 / 1.30.7-asm.3 / 1.29.10-asm.0

📅 リリース日: 2026-11-02

📋 概要 — 何が起きたのか

In-cluster (クラスタ内コントロールプレーン) の Cloud Service Mesh に対し、サポート対象の 3 マイナーバージョンすべてをカバーする セキュリティパッチが同時リリースされました。Security Bulletin GCP-2026-076 (上流 ISTIO-SECURITY-2026-008 / CVE-2026-111943) を解決します。

2026 年 10 月に秘密鍵の漏えいが公表された eMudhra 中間認証局 (CA) 証明書への信頼を Istio ベースイメージから削除するものです。 漏えいした鍵を持つ攻撃者は、パブリックに信頼されたルートにチェーンする任意ドメインの偽造証明書を作成できる可能性がありました。 ブラウザは Certificate Transparency (CT) で保護されますが、Envoy・Go・ztunnel は CT を強制しないため、 システム CA バンドルを信頼するメッシュ構成が影響を受けます。

❌ アップデート前の課題

  • CA バンドルが、秘密鍵漏えいが公表された eMudhra 中間 CA (および emSign ルート) を信頼しており、偽造証明書を受け入れるリスク
  • Envoy・Go・ztunnel は CT を強制しないため、偽造証明書を CT ログで検出できない
  • tls.mode: SIMPLE (カスタム CA なし) の外部 TLS 接続や RequestAuthentication の JWKS 取得など、システム CA 依存の経路が偽造証明書を信頼する可能性
  • Proxy / Control Plane / Distroless / CNI に CVSS 9.8 の High を含む未修正のプラットフォーム CVE

✅ アップデート後の改善

  • ベースイメージの CA バンドルを更新し、漏えいした eMudhra 中間 CA への信頼を削除
  • istiod・istioctl・pilot-agent を Go 1.26.10 でビルドし、漏えい鍵を含む証明書チェーンをコード側でも拒否
  • 3 つのサポート対象マイナーバージョンすべてにパッチが提供され、どの系列からでも即座に修正版へ移行可能
  • Envoy も更新 (v1.39.5-dev / v1.38.8-dev / v1.37.10-dev) され、High 2 件・Medium を含む CVE を一括修正

漏えいした eMudhra 中間 CA の鍵で偽造された証明書は、システム CA バンドルを信頼する外部 TLS 接続 (tls.mode: SIMPLE) や JWKS 取得の経路で受け入れられるリスクがありました。パッチ適用版へアップグレードすることで、 CA バンドルの更新と Go 1.26.10 による証明書チェーン拒否が有効になります。

⚠️ 影響を受ける構成 (上流 ISTIO-SECURITY-2026-008 より)

💡 補足: メッシュ内部の mTLS (Istio 独自の CA による相互 TLS) は影響を受けません。リスクがあるのは、Istio がシステム CA バンドルを信頼する以下のような構成です。
構成リスク内容
DestinationRule で tls.mode: SIMPLE かつカスタム CA 未指定外部サービスへの TLS 接続で偽造証明書を信頼する可能性
RequestAuthentication による JWKS 取得JWKS エンドポイントへの接続で偽造証明書を信頼する可能性
XDS_ROOT_CA=SYSTEMxDS 接続の検証にシステム CA を使用している場合

🛠️ 設定方法 — アップグレード手順

📌 前提条件

  • In-cluster Cloud Service Mesh v1.29 以降を運用していること (1.31.3-asm.3 へは v1.29+ から直接アップグレード可能)
  • v1.28 以前の場合は EOL のため、まずサポート対象バージョンへの移行を計画すること
  • Managed Cloud Service Mesh の場合は自動更新のため対応不要
1
パッチ適用版の asmcli でコントロールプレーンをアップグレード
Bash asmcli によるカナリアアップグレード 
./asmcli install \
  --project_id PROJECT_ID \
  --cluster_name CLUSTER_NAME \
  --cluster_location CLUSTER_LOCATION \
  --fleet_id FLEET_PROJECT_ID \
  --output_dir DIR_PATH \
  --enable_all \
  --ca mesh_ca

asmcli install は既存のコントロールプレーンと並行して新しいリビジョンをインストールします (カナリアアップグレード)。アップグレード中の CA 変更はダウンタイムの原因となるため、既存と同じ CA を指定します。

2
ワークロードを新リビジョンへ移行して再起動
Bash 名前空間の切り替えとサイドカー再注入 
# 名前空間に新しいリビジョンラベルを付与
kubectl label namespace NAMESPACE istio-injection- istio.io/rev=REVISION --overwrite

# サイドカーを新バージョンで再注入するためワークロードを再起動
kubectl rollout restart deployment -n NAMESPACE

名前空間を新リビジョンに関連付けて Pod を再起動すると、パッチ適用済み Envoy のサイドカーが注入されます。問題が発生した場合は、ラベルを旧リビジョンに戻すことでロールバックできます。

3
(代替) すぐにアップグレードできない場合の緩和策
YAML 外部サービス向け DestinationRule で明示的に CA を指定する例 
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: external-service
spec:
  host: external.example.com
  trafficPolicy:
    tls:
      mode: SIMPLE
      caCertificates: /etc/certs/custom-ca.pem  # システム CA への依存を排除

外部サービス向けの DestinationRule に caCertificates または credentialName を設定してシステム CA バンドルへの依存を排除するか、漏えいした中間 CA の CRL を caCrl に構成します。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓サプライチェーンリスクの低減: パブリック CA の鍵漏えいという外部起因インシデントに、パッチ適用のみで対応。脆弱性対応 SLA などコンプライアンス要件を満たしやすい
✓全サポートバージョンへの同時提供: 1.29 / 1.30 / 1.31 のどの系列でも最小の変更 (パッチアップグレード) で対応でき、メジャーアップグレードを急ぐ必要がない

🔧 技術面のメリット

✓多層防御: CA バンドルからの削除 (全バージョン) に加え、1.30 / 1.31 では Go 1.26.10 のビルドレベルでも漏えい鍵を含むチェーンを拒否
✓プラットフォーム CVE の一括修正: CVSS 9.8 の High を含む複数 CVE が修正され、イメージスキャンの指摘事項を削減
✓カナリアアップグレード対応: リビジョンベースでワークロード単位の段階的な移行・ロールバックが可能

🚫 制限事項

✗v1.28 以前は EOL のためパッチ提供なし。サポート対象バージョンへのアップグレードが必須
✗上流 Istio の 1.29 系は Go 1.25 (パッチ提供終了) ビルドのため Go レベルの拒否機構がなく、更新済み CA バンドルのみに依存。1.29 利用者は 1.30+ への移行計画を推奨
✗Envoy には組み込みの distrust リストがないため、サイドカー / ゲートウェイの保護は更新済み CA バンドルに依存

🤔 考慮すべき点

⚠️サイドカーへのパッチ反映には、リビジョン切り替え後にワークロードの再起動 (再注入) が必要
⚠️GKE 上の ISTIOD を使う In-cluster Cloud Service Mesh は非推奨 (deprecated)。中長期的には Managed Cloud Service Mesh への移行も検討に値する
⚠️メッシュ内部の mTLS は影響を受けないが、tls.mode: SIMPLE の外部接続や JWKS 取得など、システム CA 依存構成の棚卸しが必要

💡 ユースケース

🚨 ユースケース 1: 外部 API と TLS 連携するメッシュの緊急パッチ適用

シナリオ: In-cluster Cloud Service Mesh 1.31 上のマイクロサービスが、DestinationRule (tls.mode: SIMPLE、カスタム CA なし) で外部 SaaS API に接続。偽造証明書による中間者攻撃のリスクを排除したい。

Bash 1.31.3-asm.3 の導入例 
./asmcli install --project_id my-project --cluster_name prod-cluster \
  --cluster_location asia-northeast1 --fleet_id my-fleet \
  --output_dir ./asm-1313 --enable_all --ca mesh_ca
# → 1.31.3-asm.3 を新リビジョンとして導入し、名前空間を段階的に切り替え

効果: 更新済み CA バンドルと Go 1.26.10 により、漏えいした eMudhra 中間 CA にチェーンする偽造証明書が拒否され、外部 TLS 接続の安全性が回復する。

🧊 ユースケース 2: すぐにアップグレードできないクラスタの暫定防御

シナリオ: 変更凍結期間中でコントロールプレーンのアップグレードができないが、GCP-2026-076 のリスクを即時に緩和したい。

効果: 外部サービス向け DestinationRule に caCertificates / credentialName を設定してシステム CA への依存を排除する (または漏えい中間 CA の CRL を caCrl に構成する) ことで、アップグレード前でも偽造証明書の受け入れを防止。凍結解除後に正式にパッチへアップグレードする。

🔗 関連サービス・機能

☁️ Managed Cloud Service Mesh

Google がコントロールプレーンを管理する形態。本脆弱性は自動更新で解決されるため顧客対応不要。In-cluster (ISTIOD on GKE) は非推奨のため移行先の候補。

☸️ GKE (Google Kubernetes Engine)

In-cluster Cloud Service Mesh の主要な実行基盤。クラスタ側の Security Bulletin も併せて確認が必要。

🔍 Artifact Analysis / Container Scanning
