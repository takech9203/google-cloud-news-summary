🛡️ Google SecOps Marketplace アップデート

Google Chronicle 統合 v97.0 (アラート同期ロジック更新) / GitSync v53.0 (Chronicle API 対応)
Google SecOps Marketplace SOAR REGRESSIVE (GitSync v53.0)
📅 リリース日
2026-10-07

📝 概要

Google SecOps Marketplace の 2 つの統合が更新されました。Google Chronicle 統合 v97.0 では、SOAR のケース・アラートの変更 (優先度、ステータスなど) を Google SecOps (SIEM) へ同期する Sync Job のアラート同期ロジックが更新されました。

GitSync v53.0 は、プレイブックや統合などの SOAR 構成資産を Git で管理する Power-up が最新の Chronicle API に対応したアップデートです。ただし REGRESSIVE (後方非互換) とマークされており、既存ユーザーはリポジトリブランチの移行とコンテンツの再エクスポートが必須です。Chronicle API 対応環境と従来環境では JSON 構成ファイルの形式が異なり、同じブランチを同時に使用できません。

🚨 レガシー API 廃止スケジュール: レガシー SIEM API (Backstory API / Ingestion API) は 2027 年 7 月 20 日にシャットダウン予定。2026 年 10 月 26 日以降は新規インスタンスからレガシー API を呼び出せなくなります。SOAR と SIEM を連携運用する管理者は計画的な移行が必要です。

❌ アップデート前の課題

  • GitSync は従来のプラットフォーム API (*.siemplify-soar.com/api/) を使用し、Chronicle API 対応環境では 401 Unauthorized や接続エラーが発生
  • エクスポートされる JSON 構成ファイルはレガシー形式で、Chronicle API のリソース識別子・フィールド形式に非対応
  • カスタム統合はファイル単位で転送され、大きな統合では転送に時間がかかる
  • オントロジーマッピングがソース別に整理されておらず、ルール競合が発生し得た
  • 読み取り専用のシステムアイテムが同期対象に含まれ、権限エラーの原因に

✅ アップデート後の改善

  • GitSync v53.0: Chronicle REST API 接続 + Google Cloud IAM ランタイム自動認証 (Git リポジトリの認証情報のみ設定すればよい)
  • GitSync v53.0: 「Include Playbook Blocks」オプションでプレイブックブロックも一緒にエクスポート/インポート可能
  • GitSync v53.0: カスタム統合を .zip アーカイブで直接転送し、転送時間を短縮
  • GitSync v53.0: マッピングルールを /Ontology/Mappings/<Source_Name>/ 配下にソース別整理し競合を防止
  • GitSync v53.0: 読み取り専用システムアイテムを同期から自動除外し権限エラーを防止
  • Chronicle 統合 v97.0: Sync Job のアラート同期ロジックを更新

GitSync v53.0 は Chronicle API 経由で IAM 自動認証を行い、新形式の構成ファイルを専用ブランチへエクスポートします。レガシーブランチの構成ファイルとは非互換のため、ブランチ移行と再エクスポートが必須です。

⚡ 主要機能

1️⃣ Google Chronicle 統合 v97.0: Sync Job のアラート同期ロジック更新

→SOAR で管理されるケースとアラートのフィールド (優先度、ステータス、タイトルなど) を Google SecOps へ同期
→1 回のイテレーションで最大 1,000 ケースと 1,000 アラートを同期
→Chronicle Alerts Connector / Chronicle Alerts Creator Job で作成されたアラートに対応 (非推奨の Alerts Connector / IOCs Connector のアラートには非対応)
→レガシー API の非推奨化に先立ち、Chronicle API を使用するよう明示的に構成する必要がある

2️⃣ GitSync v53.0: Chronicle API 対応環境のサポート REGRESSIVE

→Chronicle REST API 経由の接続と Google Cloud IAM によるランタイム自動認証
→JSON 構成ファイルが Chronicle API のリソース識別子・フィールド形式に変更 (移行前のブランチとは非互換)
→「Include Playbook Blocks」によるプレイブックブロックの専用同期オプションを追加
→カスタム統合の .zip アーカイブ直接転送による転送時間の短縮
→ソース別オントロジーマッピング (/Ontology/Mappings/<Source_Name>/) による競合防止
→組み込みシステムデフォルトの自動除外による権限エラー防止

3️⃣ 必須の移行作業 (GitSync 既存ユーザー)

→リポジトリブランチの移行とコンテンツの再エクスポートが必要
→Chronicle API 対応環境への移行は一方向の移行であり、レガシーエンドポイントには戻せない

🛠️ 設定方法 (GitSync のブランチ移行: 推奨の専用ブランチ方式)

✅ 前提条件

  • Google SecOps プラットフォームが Chronicle API 対応環境 (secops.google.com または *.chronicle.security.google.com) に移行済みであること
  • Content Hub で GitSync パッケージがバージョン 53.0 以降に更新されていること
  • GitSync は Shared Instance として構成すること (全プラットフォームコンポーネントとスケジュールジョブがリポジトリ構成にアクセスできるようにするため)

📌 移行手順

  1. レガシー環境からベースラインを Push
    移行前の環境から Push Content ジョブをフル実行し、既存ブランチ (例: main) にクリーンなバックアップをコミット。
  2. 新しい Git ブランチを作成
    Bash専用ブランチの作成
    git checkout -b gitsync-chronicle-api
git push origin gitsync-chronicle-api
    専用ブランチにより Chronicle API 形式の構成を分離し、移行前構成のアーカイブをそのまま保持できる。
  3. 統合インスタンスのアップグレードと再構成
    Content Hub で GitSync が v53.0 以降であることを確認し、Settings > Integrations > GitSync で Branch パラメータを gitsync-chronicle-api に更新。Ping アクションで接続を確認。既存の Shared Instance の削除・再作成は不要。
  4. Chronicle API 形式のベースラインを Push
    Chronicle API 対応インスタンスから Push Content ジョブをフル実行し、新ブランチに更新済みの構成ファイルを格納。新ブランチの初期化時や移行時は必ず Push Content を最初に実行。
  5. 検証と Pull 同期の有効化
    リポジトリのファイル構造を確認し、必要に応じてスケジュールされた Pull Content ジョブを有効化。
💡 既存ブランチを再利用する場合 (Option 2): バックアップタグの作成 (git tag backup-legacy-pre-migration) → 同期ジョブの一時停止 → レガシーディレクトリの削除 → ベースライン Push → 同期再開の手順。GitSync はリモートリポジトリへ直接 push する (Pull Request を作成しない) ため、ブランチ保護ルールが有効な場合は例外設定が必要です。

⚠️ デメリット・制約事項

🚧 制限事項

✗後方非互換 (REGRESSIVE): GitSync v53.0 の構成ファイル形式は移行前のブランチと非互換。ブランチ移行とコンテンツの再エクスポートが必須
✗一方向の移行: Chronicle API 対応環境への移行は一方向のインフラ移行で、レガシーエンドポイントには戻せない
✗レガシーブランチの Pull 不可: レガシー構成ファイルを含むブランチを Pull すると General error performing Job Pull Content や 400 Bad Request / 404 Not Found エラーが発生。先に Push Content でブランチを新形式に更新する必要がある
✗Sync Job の対象制限: Chronicle Alerts Connector / Alerts Creator Job 由来のアラートのみ対象。非推奨コネクタ (Alerts Connector、IOCs Connector) のアラートは同期されない
✗同期件数の上限: Sync Data Job は 1 イテレーションあたり最大 1,000 ケース・1,000 アラート

🤔 考慮すべき点

⚠️ ブランチ保護ルール: GitSync は Pull Request を作成せずリモートリポジトリへ直接 push するため、ブランチ保護 (レビュー必須など) が有効なブランチでは push が失敗します。専用ブランチの利用、または GitSync 用アカウントの例外設定が必要です。
⚠️ Pull Content のタイムアウト: 複数の商用統合を一度にインポートするとジョブ実行の 5 分タイムアウトを超過する場合があります。事前に Content Hub から必要な商用統合をインストールしておくか、タイムアウト時はジョブを再実行してください。
🚨 Commit Passwords オプション: Password 型以外のパラメータ (Application ID、Client ID、ユーザー名、URL など) は常に平文でエクスポートされます。公開/共有リポジトリでは Commit Passwords を絶対に有効化しないでください。
💡 認証方式の一致: Google Chronicle 統合の Sync Job は、統合構成と同一の認証方式 (Chronicle API) を使用するよう明示的に構成する必要があります。

📦 ユースケース 1: Chronicle API 対応環境への GitSync 移行

シナリオ: SOAR のプレイブックとコネクタ構成を GitSync の main ブランチで管理している組織が、プラットフォームの Chronicle API 対応環境への移行に伴い GitSync v53.0 へアップデートする。

Bash専用ブランチ方式での移行
# 移行前: レガシー環境からフル Push でバックアップ (main ブランチへ)
# 移行後: 専用ブランチを作成
git checkout -b gitsync-chronicle-api
git push origin gitsync-chronicle-api
# GitSync の Branch パラメータを gitsync-chronicle-api に変更し Ping で確認
# Chronicle API 対応インスタンスからフル Push Content を実行

効果: 移行前構成のアーカイブを main ブランチに保持したまま、Chronicle API 形式の構成管理を新ブランチで開始でき、履歴を壊さずに安全に移行できる。
