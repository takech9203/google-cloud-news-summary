🔐 Looker (Google Cloud core)
Workforce Identity Federation サポート

Google アカウント不要 — Okta や Microsoft Entra ID などの外部 IdP だけで Looker に SSO

📝 概要

Looker (Google Cloud core) が、Looker 26.18 以降のインスタンスで Workforce Identity Federation を Preview としてサポートしました。 Okta、Microsoft Entra ID、PingIdentity などの外部 ID プロバイダ (IdP) でユーザーを認証でき、 ユーザーごとに Google アカウントを作成・管理する必要がなくなります。

管理者はインスタンスの作成・編集時に Workforce Identity をプライマリ認証方式として選択でき、 オプションでセカンダリ Google OAuth を有効化して安全なバックアップアクセス手段を確保できます。 認証後は looker.instances.login IAM 権限の確認を経て、ユーザーが Just-In-Time (JIT) でプロビジョニングされます。

❌ Before: アップデート前の課題

  • 認証は Google OAuth (IAM 連携) ベースで、ユーザーごとに Google アカウント (Cloud Identity / Workspace) が必須
  • 外部 IdP 利用時も GCDS などで ID を Google アカウントに同期する運用が前提で、ライフサイクル管理の負担が発生
  • SAML / OIDC をプライマリ認証にしても、バックアップ用 Google OAuth には Google アカウントが必要

✅ After: アップデート後の改善

  • 外部 IdP (OIDC / SAML 2.0) の資格情報だけで Looker に SSO 可能に
  • 同期レス (sync-less) のため GCDS などのユーザー同期ツールの運用が不要
  • IdP の属性 (クレーム) を Looker のユーザー属性・グループにマッピングし、ロール付与や行レベルフィルタに活用可能
  • セカンダリ Google OAuth で IdP 障害時も管理者アクセスを維持

⚡ 主要機能

🏢 1. 外部 IdP によるプライマリ認証

→OIDC または SAML 2.0 に対応する任意の IdP (Microsoft Entra ID、Okta、PingIdentity など) を利用可能
→インスタンスの作成・編集時に「Workforce Identity Federation (SAML/OIDC)」をプライマリ認証方式として選択
→Google アカウントの作成・同期が不要な同期レス構成

🛟 2. セカンダリ Google OAuth によるバックアップアクセス

→既存インスタンスの編集時に「Enable Secondary OAuth」トグルを有効化すると Google OAuth をセカンダリ認証として利用可能
→IdP 側の障害や設定ミス時にも、IAM ロールを持つ管理者・ユーザーが安全にアクセスを維持

🧩 3. 属性マッピングと JIT プロビジョニング

→IdP のクレームを google.email (必須)、attribute.given_name / attribute.family_name (必須)、google.groups (グループミラーリング用) にマッピング
→カスタムクレームは attribute.<attribute_name> として Looker のユーザー属性に連携し、接続のパラメータ化や行レベルフィルタに活用可能
→初回サインイン時にユーザーを JIT 作成し、グループ・ロールのマッピングとデフォルトロール / グループを適用

🎛️ 4. Looker 管理パネルでの制御

→[管理] > [認証] > [Workforce Identity] で、ユーザーマージ方式 (Google / SAML / OIDC)、ログインページのバイパス (デフォルト有効)、属性マッピング、グループミラーリングを設定可能

Bash Looker Instance User ロールの付与 
# 特定ユーザーに Looker Instance User ロールを付与
gcloud projects add-iam-policy-binding PROJECT_ID \
  --role="roles/looker.instanceUser" \

# IdP のグループ単位で付与
gcloud projects add-iam-policy-binding PROJECT_ID \
  --role="roles/looker.instanceUser" \
  --member="principalSet://iam.googleapis.com/locations/global/workforcePools/POOL_ID/group/GROUP_ID"

🛠️ 設定方法

✅ 前提条件

✓Google Cloud 組織が設定済みであること (Workforce Identity プールは組織レベルのリソース)
✓Looker 26.18 以降の Looker (Google Cloud core) インスタンス (パブリックなセキュア接続を使用)
✓OIDC または SAML 2.0 に対応した外部 IdP

📑 手順

  1. 🏊 Workforce Identity プールとプロバイダを作成 IAM の Workforce Identity プールを作成し、IdP をプロバイダとして登録します。属性マッピングで google.email、attribute.given_name、attribute.family_name を必ず設定し、グループミラーリングを使う場合は google.groups もマッピングします。
  2. 🛡️ Workforce プリンシパルに IAM ロールを付与 roles/looker.instanceUser または roles/looker.admin を、principal:// / principalSet:// 形式のプリンシパル識別子で付与します。
  3. 🔐 インスタンスでプライマリ認証方式を選択 Google Cloud コンソールでインスタンスの作成または編集を行い、認証セクションで「Workforce Identity Federation (SAML/OIDC)」を選択します。必要に応じて既存インスタンスの編集時に「Enable Secondary OAuth」を有効化してバックアップアクセスを設定します (セカンダリ OAuth は作成後の編集でのみ設定可能)。
  4. 🎛️ Looker 管理パネルで詳細を設定 Looker インスタンスの [管理] > [認証] > [Workforce Identity] ページで、ユーザーマージ方式、属性マッピング、グループマッピング、新規ユーザーのデフォルトロール / グループを設定します。
  5. ⏱️ (推奨) 拡張セッション長ポリシーを設定 Access Context Manager の GcpUserAccessBinding で、Looker インスタンスを所有するプロジェクトをスコープにした拡張セッション長 (最大 90 日) を設定します。
YAML esl-binding.yaml (拡張セッション長ポリシー) 
# esl-binding.yaml
scopedAccessSettings:
  - scope:
      clientScope:
        restrictedProject:
          name: projects/PROJECT_NUMBER
    activeSettings:
      sessionSettings:
        sessionLength: 7776000s
        sessionLengthEnabled: true
        sessionReauthMethod: LOGIN
Bash 拡張セッション長バインディングの作成 
gcloud access-context-manager cloud-bindings create \
  --organization=ORG_ID \
  --federated-principal="principalSet://cloudresourcemanager.googleapis.com/organizations/ORG_ID/type/WorkforcePool" \
  --binding-file="esl-binding.yaml"

⚖️ メリットと制約事項

💼 ビジネス面のメリット
  • Google アカウント管理の廃止: ユーザーごとの Google アカウント発行・同期 (GCDS など) が不要になり、ID 管理の運用コストとオンボーディング期間を削減
  • 既存 IdP への統合: Okta や Entra ID を認証の単一ソースとして維持したまま Looker を導入でき、MFA や条件付きアクセスなどのセキュリティポリシーを IdP 側で一元適用
🔧 技術面のメリット
  • 同期レスのフェデレーション: ID は IdP 側にのみ存在し、退職者アカウントの消し忘れなどのリスクを低減
  • 属性ベースのアクセス制御: IdP のクレームをロール付与や行レベルフィルタ、接続のパラメータ化に活用
  • バックアップ経路の確保: セカンダリ Google OAuth で IdP 障害時も管理者アクセスを維持
🚧 制限事項
  • Preview 機能のため Pre-GA Offerings Terms が適用 (SLA 対象外)
  • Looker 26.18 以降のインスタンスのみ対応
  • Preview 中はパブリックなセキュア接続のみ (Private Service Connect / プライベートサービスアクセスは非対応)
  • 拡張セッション長には OIDC は Authorization Code フロー + offline_access (または SCIM)、SAML は SCIM プロビジョニングが必須
  • 属性の鮮度チェック (24 時間しきい値) により、IdP から属性を更新できない場合はセッションが無効化され再認証が必要
⚠️ 考慮すべき点
  • google.email、attribute.given_name、attribute.family_name の属性マッピング未設定は認証失敗の原因になるため、プロバイダ作成時に必ず設定
  • ユーザー API キートークンは 1 時間で失効しアクティブな IdP セッションが必要。自動化にはサービスアカウント (API 専用アカウント) を検討
  • スケジュール配信・アラートは所有者のサインインが約 90 日間ないと一時停止。拡張セッション長ポリシーの設定を推奨
  • セカンダリ Google OAuth はインスタンス作成時ではなく、作成後の編集でのみ有効化可能

🔗 関連サービス・機能

🏊 IAM Workforce Identity Federation

本機能の基盤。組織レベルの Workforce Identity プールとプロバイダで外部 IdP とのフェデレーションを構成。

🎫 Security Token Service (STS)

IdP のアサーションを Google Cloud の短命なフェデレーテッドトークンに交換 (RFC 8693 準拠)。

⏱️ Access Context Manager

拡張セッション長 (最大 90 日) ポリシーを Looker (Google Cloud core) 向けに設定するために使用。

📜 Cloud Audit Logs / Cloud Logging

詳細監査ログで IdP から受信した属性を記録し、属性マッピングのトラブルシューティングに活用。

🗄️ Cloud SQL

Looker 以外にも Workforce Identity Federation 認証に対応するサービスの一例 (MySQL / PostgreSQL のマネージド接続)。

📌 まとめ

Looker (Google Cloud core) の Workforce Identity Federation 対応により、 Google アカウントを管理せずに Okta や Entra ID などの既存 IdP だけで Looker への SSO が実現できるようになりました。 Google Workspace を導入していない組織にとって Looker (Google Cloud core) 採用の大きな障壁が取り除かれます。 Preview 段階のためパブリック接続のみの対応などの制約はありますが、 外部 IdP を標準とする組織は属性マッピングとグループミラーリングの設計を含めた検証を始めることを推奨します。
