Google Distributed Cloud for Bare Metal v1.35.300

CSI スナップショットバリデーションを Webhook から CEL へ刷新

Google Distributed Cloud Announcement
2026-07-20

📋 概要

Google Distributed Cloud (software only) for bare metal の新パッチリリース 1.35.300-gke.87 が公開されました。Kubernetes v1.35.3-gke.400 をベースとし、CSI スナップショットバリデーションの仕組みを大幅に刷新する重要なアーキテクチャ変更とセキュリティ脆弱性の修正を含んでいます。

最も注目すべき変更点は、非推奨となっていた csi-snapshot-validation-webhook コンポーネントの完全削除です。バリデーション機能は Kubernetes ネイティブの Common Expression Language (CEL) ルールに置き換えられました。

✗Webhook コンポーネントの証明書管理が必要でセキュリティメンテナンスの負担が増加

✓独立した Webhook コンポーネントの運用・監視・証明書管理が不要に

⚡ 主要機能

1. csi-snapshot-validation-webhook の削除

非推奨だった csi-snapshot-validation-webhook コンポーネントが完全に削除されました。VolumeSnapshot、VolumeSnapshotContent、VolumeSnapshotClass の CRD に対するバリデーションが CEL ルールに移行し、Webhook Pod のデプロイ、Service、ValidatingWebhookConfiguration リソースが不要になりました。

2. CEL ベースの CRD バリデーション

Kubernetes の Common Expression Language (CEL) を使用して、CRD の x-kubernetes-validations フィールドにバリデーションルールを直接定義します。API Server 内でネイティブに実行されるため、外部通信のオーバーヘッドがゼロになり、CRD 定義とバリデーションロジックが一体化して管理が容易になりました。

3. セキュリティ脆弱性の修正

複数のセキュリティ脆弱性が修正されています。詳細は Google Distributed Cloud for bare metal の Vulnerability fixes ページを参照してください。

🔧 CEL バリデーションの仕組み

CEL (Common Expression Language) は Kubernetes 1.25 から導入されたバリデーション機構で、CRD の OpenAPI スキーマ内に直接バリデーションルールを記述できます。

YAML 
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: volumesnapshots.snapshot.storage.k8s.io
spec:
  versions:
    - name: v1
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              x-kubernetes-validations:
                - rule: "has(self.source.persistentVolumeClaimName) || has(self.source.volumeSnapshotContentName)"
                  message: "source must specify either persistentVolumeClaimName or volumeSnapshotContentName"
                - rule: "!(has(self.source.persistentVolumeClaimName) && has(self.source.volumeSnapshotContentName))"
                  message: "source cannot specify both persistentVolumeClaimName and volumeSnapshotContentName"

💡 ユースケース

🏢 ユースケース 1: エンタープライズのオンプレミス Kubernetes 環境

シナリオ: 大規模なオンプレミス環境で数百の PersistentVolume のスナップショットを日次で取得しているチームが、Webhook の TLS 証明書期限切れにより定期バックアップが失敗するインシデントを経験。

Bash 
# 1.35.300-gke.87 にアップグレード
bmctl upgrade cluster -c production-cluster --kubeconfig /path/to/admin-kubeconfig

# アップグレード後、Webhook 関連リソースが自動削除されていることを確認
kubectl get validatingwebhookconfigurations | grep snapshot
# (出力なし = 正常に削除済み)

# スナップショット作成が正常に動作することを確認
kubectl apply -f daily-snapshot.yaml

効果: 証明書管理の負担がゼロになり、Webhook 起因の障害リスクが完全に排除。スナップショット操作の信頼性が 100% に向上。

🏪 ユースケース 2: Edge コンピューティング環境でのリソース最適化

シナリオ: 小売店舗の Edge ノードで Google Distributed Cloud を運用しており、限られたハードウェアリソース内でコンテナワークロードを最大化したい。

効果: Webhook Pod (通常 2 レプリカ) と関連リソースが削除されることで、CPU とメモリの使用量が削減。リソース制約の厳しい Edge 環境において、ワークロード用に確保できるリソースが増加。
