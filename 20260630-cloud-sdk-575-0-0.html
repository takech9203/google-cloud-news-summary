📋 概要

Cloud SDK 575.0.0 は 30 以上のサービス にまたがる大規模アップデート。AI エージェント管理からデータベース DR、コンテナオーケストレーションまで、エンタープライズ運用の成熟度を大きく引き上げるリリースです。

Before / After

Before (従来)

  • Agent Registry はコンソール/REST API のみ
  • AlloyDB フェイルオーバーは手動操作のみ
  • Fleet Rollouts はプレビュー段階
  • Cloud Run デプロイ前検証にサードパーティが必要
  • Regional MIG resize-requests はベータ

After (575.0.0)

  • gcloud agent-registry で CLI 管理が可能に
  • --failover フラグで CLI から直接実行
  • Fleet Rollouts/RolloutSequences が GA に
  • --dry-run でデプロイ前確認が可能
  • Regional MIG resize-requests が GA 昇格

🚀 主要機能

1. Agent Registry コマンドグループの追加

GA

gcloud agent-registry コマンドグループにより、AI エージェント、MCP サーバー、エンドポイントの登録・検索・管理が CLI から可能に。Gemini Enterprise Agent Platform のガバナンスレイヤーとして、組織内のエージェント統合管理を実現します。

→agents list, agents describe, services update などのサブコマンドを提供
→IAM ロール: roles/agentregistry.admin, roles/agentregistry.editor, roles/agentregistry.viewer

2. AlloyDB クロスリージョンフェイルオーバー

Beta

gcloud beta alloydb clusters promote に --failover フラグが追加。セカンダリクラスタをプライマリに昇格させる際にフェイルオーバーモードを指定でき、リージョン障害時の DR が CLI から実行可能になりました。

→最大 5 つのセカンダリクラスタをサポート
→ゼロデータロスのスイッチオーバーも引き続きサポート

3. GKE Hub Fleet Rollouts / RolloutSequences

GA

フリートベースのロールアウトシーケンスが GA 昇格。開発 → ステージング → 本番の段階的クラスタアップグレードが正式サポートされ、各フリート間で soak time を設定して安全性を確保できます。

4. Cloud Run の多数の改善

Beta GA

デプロイの安全性と利便性が大幅に向上しました。

✓--dry-run: deploy/update/delete の実行前に変更内容を確認 (Beta)
✓--sandbox-launcher: セキュリティ強化サンドボックスでのコンテナ起動 (Beta)
✓--workdir: コンテナのワーキングディレクトリ指定が GA 昇格
✓--tail: ジョブ実行のログをリアルタイム追跡 (Beta)
✓describe-latest: 最新のジョブ実行情報を取得

5. Compute Engine GA 昇格・新コマンド群

GA

Regional MIG resize-requests が GA 昇格し、大規模バッチ/HPC ワークロードでの VM 一括確保が正式サポートに。さらに set-machine-resources, set-quic-override, set-iam-policy など多数の新コマンドが追加されました。

📦 その他の注目アップデート

→Apigee API Proxy インポート: gcloud apigee apis import で ZIP/YAML 形式の API Proxy バンドルをアップロード
→Cloud Data Lineage: gcloud datalineage processes コマンドグループ追加でデータリネージを CLI 管理
→Cloud Storage: ストリーミングダウンロードで MD5 ハッシュ検証追加 + RAPID ストレージ対応
→GKE カスタムイメージ: --image / --image-project フラグが GA 昇格

Breaking Changes

Cluster Director: staticNodeCount のデフォルト値 1 が廃止
明示的に staticNodeCount を指定する必要があります。既存のスクリプトやテンプレートを確認してください。

制限事項・注意点

制限事項

考慮すべき点
→Fleet Rollouts: 全クラスタが同一リリースチャネルおよび同一マイナーバージョンである必要がある
→Agent Registry: プロジェクトレベルのスコープであり、組織レベルの一元管理には各プロジェクトでの API 有効化が必要
→Cloud Run Regional inference (Beta): 全リージョン検索のためレスポンスタイムに影響する可能性

💡 ユースケース

🤖 ユースケース 1: マルチエージェント環境のガバナンス

シナリオ: 複数チームが独自に AI エージェントを開発・デプロイしている組織で、エージェントの一覧管理・重複検出・セキュリティ監査を行いたい。

Bash 
# 全エージェントの一覧取得
gcloud agent-registry agents list \
  --project=my-project \
  --location=us-central1

# 特定エージェントの詳細確認
gcloud agent-registry agents describe my-support-agent \
  --project=my-project \
  --location=us-central1

# エージェントのエンドポイント更新
gcloud agent-registry services update my-support-agent \
  --project=my-project \
  --location=us-central1 \
  --interfaces=url=https://new-api.example.com/agent,protocolBinding=HTTP_JSON

効果: 組織全体のエージェント資産の可視化、重複実装の発見、セキュリティポリシーの統一適用が可能に。

🗄 ユースケース 2: AlloyDB マルチリージョン DR

シナリオ: ミッションクリティカルなデータベースワークロードにおいて、リージョン障害時に自動的にセカンダリリージョンにフェイルオーバーさせたい。

Bash 
# セカンダリクラスタへのフェイルオーバー
gcloud beta alloydb clusters promote my-secondary-cluster \
  --region=us-east4 \
  --project=my-project \
  --failover

効果: RTO (Recovery Time Objective) の短縮と、DR 手順の自動化による運用負荷軽減。

🔄 ユースケース 3: GKE 段階的アップグレード

シナリオ: 数百のクラスタを運用する組織で、新バージョンを dev → staging → production の順に段階的に適用し、各段階で検証時間を確保したい。

効果: バージョンアップに起因する障害の早期検出と、本番環境への影響最小化。
