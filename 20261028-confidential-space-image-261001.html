🔒 Confidential Space Security Fix Announcement

🛡️ Confidential Space 新イメージ 261001

侵害された CA 証明書の削除 & 非 root コンテナ実行のサポート
リリース日: 2026-10-28
CVE-2026-111943
eMudhra (emSign) 下位 CA 8 件の秘密鍵侵害 (GCP-2026-071 / 重要度 Medium)
UID 0 → 100000
非 root 実行時のユーザー名前空間マッピング (コンテナ → VM)
2026-11-09
旧イメージへのアテステーショントークン発行停止開始

📋 概要

Confidential Space の新イメージ バージョン 261001 がリリースされました。 セキュリティ修正と新機能の 2 つの重要な変更を含みます。

1️⃣ 侵害された CA 証明書の削除 (セキュリティ修正)

セキュリティ速報 GCP-2026-071 (CVE-2026-111943) で公表された eMudhra (emSign) 下位 CA 証明書の秘密鍵侵害に対応。 ベース OS である Container-Optimized OS (COS) の OS トラストストアから該当証明書を削除。 旧イメージへのアテステーショントークン発行は段階的に停止されるため、全ユーザーに早急なイメージ更新が推奨されます。

2️⃣ 非 root コンテナ実行のサポート (新機能)

ワークロード作成者は起動ポリシー tee.launch_policy.nonroot_container で非 root 実行を必須化でき、 オペレーターはメタデータ変数 tee-nonroot-container で有効化。 コンテナブレイクアウト時の影響を低減し、マルチパーティコラボレーションの多層防御を強化します。

🔄 Before / After

❌ Before (イメージ 261000 以前)

  • OS トラストストアに秘密鍵侵害が報告された eMudhra (emSign) 下位 CA 証明書が含まれ、外部 TLS 接続に対する MitM 攻撃・通信偽装のリスク
  • ワークロードコンテナは root として実行され、コンテナブレイクアウト時に Confidential VM 上で特権アクセスを許す可能性
  • 作成者がオペレーターに対して実行権限の制限を強制する手段がなかった

✅ After (イメージ 261001)

  • 侵害された CA 証明書をトラストストアから削除し、偽造 TLS 証明書を信頼するリスクを解消
  • 非 root 実行でコンテナ内 UID/GID 0〜65535 を VM 上の非特権 ID (100000 以降) にマッピング。脱出したプロセスも非特権アクセスのみ
  • 起動ポリシー nonrootonly で非 root 実行を必須化 (フェイルセーフ)。未設定なら起動自体が失敗

ステップ 1: 現在使用中のイメージバージョンを確認

Bash 使用中イメージの特定 
gcloud compute disks list \
  --filter="sourceImage ~ 'confidential-space'" \
  --format="table(name, users[0], sourceImage)"

プロジェクト内の VM インスタンスが使用している Confidential Space イメージのバージョンを特定します。

ステップ 2: ワークロード作成者 — 起動ポリシーの設定 (非 root 実行を必須化する場合)

Dockerfile イメージラベルで起動ポリシーを設定 
# Dockerfile でイメージラベルとして起動ポリシーを設定
LABEL "tee.launch_policy.nonroot_container"="nonrootonly"

nonrootonly を設定すると、オペレーターに非 root 実行を強制できます。USER 命令の追加は不要です。

ステップ 3: ワークロードオペレーター — 最新イメージで VM を作成し非 root 実行を有効化

Bash Confidential VM の作成 
gcloud compute instances create cs-workload-vm \
  --machine-type=n2d-standard-4 \
  --confidential-compute \
  --shielded-secure-boot \
  --image-project=confidential-space-images \
  --image-family=confidential-space \
  --service-account=WORKLOAD_SA@PROJECT_ID.iam.gserviceaccount.com \
  --scopes=cloud-platform \
  --metadata="^~^tee-image-reference=LOCATION-docker.pkg.dev/PROJECT_ID/REPO/workload:latest~tee-nonroot-container=true"

--image-family=confidential-space により最新イメージ (261001) が使用され、tee-nonroot-container=true で非 root 実行が有効になります。

ステップ 4: データコラボレーター — アテステーションポリシーでイメージバージョンを確認

Text アクセスポリシーへの条件追加 
int(assertion.swversion[0]) >= 260701

セキュリティ速報では、リライングパーティ (検証側) のアクセスポリシーに上記の条件を追加し、新しいバージョンの Confidential Space イメージであることを確認することが推奨されています。

💪 メリット

💼 ビジネス面

✓セキュリティインシデントへの迅速な対応: 侵害された CA を信頼し続けることによる MitM 攻撃・通信偽装のリスクを排除し、機密データコラボレーションの信頼性を維持できる
✓コンプライアンス強化: 最小権限の原則に基づくコンテナ実行により、規制要件やセキュリティ監査への対応力が向上する

⚙️ 技術面

✓コンテナブレイクアウトの影響低減: ユーザー名前空間の隔離により、コンテナから脱出したプロセスも VM 上では非特権アクセスに制限される
✓フェイルセーフな権限制御: 作成者が nonrootonly を設定すれば、オペレーター側の設定漏れがあってもワークロードは起動せず、root での意図しない実行を防げる
✓アプリケーション変更不要: Dockerfile への USER 命令の追加が不要で、既存のコンテナイメージをそのまま非 root 実行に移行できる

⚠️ デメリット・制約事項

🚧 制限事項

  • 非 root コンテナ実行は confidential-space-261001 以降でのみサポート。古いイメージで設定しても無視され root として実行される
  • デフォルトは unrestricted / false のため、明示的に設定しない限り従来どおり root で実行される

🤔 考慮すべき点

  • 2026 年 11 月 9 日以降、Google Cloud Attestation は 260701 より古いイメージへ、Intel Trust Authority は 261001 より古いイメージへアテステーショントークンを送信しなくなる。期日までのイメージ更新が必須
  • 2027 年 1 月 11 日にはイメージ 260701〜261000 から STABLE 属性が削除され、STABLE ベースのアテステーションポリシーを使用している環境も影響を受ける
  • イメージの更新には VM の再作成が必要。本番ワークロードの無停止移行にはマネージドインスタンスグループ (MIG) の活用が推奨される
  • 非 root 実行を必須化 (nonrootonly) する場合、オペレーター全員が tee-nonroot-container=true とイメージ 261001 以降を使用するよう事前の調整が必要

🤝 ユースケース 2: マルチパーティ計算での非 root 実行の必須化

シナリオ: ワークロード作成者 (分析アルゴリズム提供者) が、データ保有者の懸念に応えるため、ワークロードコンテナの実行権限を最小化したい。オペレーター (インフラ運用者) の設定ミスで root 実行されることも防ぎたい。

Dockerfile 非 root 実行の必須化

効果: オペレーターが tee-nonroot-container=true を設定しない限りワークロードが起動しないため、常に非 root での実行が保証される。コンテナブレイクアウトが発生しても VM 上では非特権アクセスに制限され、機密データの保護レベルが向上する。

📝 まとめ

Confidential Space イメージ 261001 は、eMudhra (emSign) CA 証明書侵害 (CVE-2026-111943) に対応するセキュリティ修正と、非 root コンテナ実行という防御強化機能を含む重要なリリースです。

  • 2026 年 11 月 9 日以降は旧イメージへのアテステーショントークン発行が順次停止 → 全環境で期日前のイメージ更新 (VM 再作成) を実施
  • アテステーションポリシーへのバージョン条件 (int(assertion.swversion[0]) >= 260701) の追加を推奨
  • 多層防御の強化として非 root コンテナ実行の採用を検討
