🔐 Cloud Load Balancing: ポスト量子鍵交換サポート

Cloud Load Balancing GA TLS Security
2026-06-02

📋 概要

Google Cloud は、Application Load Balancer および外部プロキシ Network Load Balancer において、TLS ポスト量子鍵交換のサポートを GA (一般提供) として開始しました。ハイブリッド鍵交換方式 X25519MLKEM768 を使用し、量子コンピュータによる将来的な暗号解読リスクからトラフィックを保護します。

⚠️ 重要な背景: Google は、TLS で使用される非対称暗号が早ければ 2029 年にも量子コンピュータによって破られる可能性があると推定しています。「Harvest Now, Decrypt Later (今収集して、後で復号する)」攻撃への対策が急務です。

❌ Before (アップデート前)

  • 量子コンピュータの脅威に対する防御手段がロードバランサレベルで未提供
  • 「Harvest Now, Decrypt Later」攻撃により、記録された暗号化トラフィックが将来復号されるリスク
  • ECDHE (Perfect Forward Secrecy) でも量子コンピュータによる鍵交換の解読には対応不可

✅ After (アップデート後)

  • SSL ポリシーの設定一つで即座にポスト量子鍵交換を有効化
  • ハイブリッド方式 (X25519MLKEM768) で古典的暗号 + ポスト量子暗号の二重保護
  • 段階的ロールアウトにより互換性問題にも猶予期間を確保

⚡ 主要機能

🔑 X25519MLKEM768 ハイブリッド鍵交換

→古典的暗号 (X25519) + ポスト量子暗号 (MLKEM768) のハイブリッド
→NIST 開発・検証アルゴリズムに基づき IETF 標準に準拠
→いずれか一方が破られても、もう一方が保護を維持

🎛️ SSL ポリシーによる制御

→3 つのモード: ENABLED / DEFAULT / DEFERRED
→全プロファイルと組み合わせ可能 (COMPATIBLE, MODERN, RESTRICTED, CUSTOM, FIPS_202205)
→任意の最小 TLS バージョン設定と併用可能

🔄 段階的ロールアウト計画

→Phase 1 (~2026/10): デフォルト無効、オプトインで有効化
→Phase 2 (2026/10~2027/10): デフォルト有効、DEFERRED で延期可能
→Phase 3 (2027/10~): 常時有効、延期オプションなし

🤝 後方互換性の確保

→TLS 1.3 / X25519MLKEM768 未対応クライアントは影響なし
→既存のロードバランサ接続は中断されない

📅 段階的ロールアウトスケジュール

Phase 1: 2026年6月 ~ 2026年10月
デフォルト無効 / オプトイン有効化
post-quantum-key-exchange: ENABLED を明示的に設定することで有効化。設定しない場合はポスト量子保護は適用されない。
Phase 2: 2026年10月 ~ 2027年10月
デフォルト有効 / 延期可能
すべての SSL ポリシーでデフォルト有効に移行。互換性問題がある場合は DEFERRED で延期可能。
Phase 3: 2027年10月以降
常時有効 / 延期不可
ポスト量子鍵交換が全環境で必須に。延期オプションは廃止。それまでに互換性問題を解決する必要がある。

⚙️ 設定方法

💡 前提条件:
  • Cloud Load Balancing が設定済み (対象のロードバランサ種別)
  • TargetHttpsProxy または TargetSslProxy が構成済み
  • IAM 権限: compute.sslPolicies.create, compute.sslPolicies.update

Step 1: SSL ポリシーの作成 (グローバル)

Bash 
gcloud compute ssl-policies create my-pq-ssl-policy \
  --profile MODERN \
  --min-tls-version 1.2 \
  --post-quantum-key-exchange ENABLED

Step 2: SSL ポリシーの作成 (リージョン)

Bash 
gcloud compute ssl-policies create my-pq-ssl-policy \
  --profile MODERN \
  --min-tls-version 1.2 \
  --region asia-northeast1 \
  --post-quantum-key-exchange ENABLED

Step 3: 既存の SSL ポリシーの更新

Bash 
gcloud compute ssl-policies update my-existing-policy \
  --post-quantum-key-exchange ENABLED

Step 4: SSL ポリシーをターゲットプロキシにアタッチ

Bash 
gcloud compute target-https-proxies update my-https-proxy \
  --ssl-policy my-pq-ssl-policy

⚠️ デメリット・制約事項

制限事項

✗フロントエンド接続 (クライアントとロードバランサ間) のみが対象。バックエンド接続にはポスト量子保護は適用されない
✗クライアントが TLS 1.3 と X25519MLKEM768 の両方をサポートしている必要がある
✗認証 (証明書) に対する量子コンピュータの攻撃にはこの機能では対応できない

考慮すべき点

  • ポスト量子鍵交換により、TLS ハンドシェイクのデータサイズが増加する可能性がある (MLKEM768 の公開鍵・暗号文のサイズ)
  • 一部の古いクライアントやプロキシが X25519MLKEM768 を含む ClientHello を正しく処理できない可能性がある
  • 2027年10月以降はオプトアウト不可のため、それまでに互換性問題を解決する必要がある
  • 内部パススルー Network Load Balancer や外部パススルー Network Load Balancer は対象外

🏦 金融機関のデータ保護

銀行や証券会社が顧客の金融取引データを長期的に保護。量子コンピュータの実用化後に過去の取引情報が復号されるリスクを排除。

Bash 
# 金融機関向け: 最高セキュリティプロファイルでPQ有効化
gcloud compute ssl-policies create finance-pq-policy \
  --profile RESTRICTED \
  --min-tls-version 1.2 \
  --post-quantum-key-exchange ENABLED

gcloud compute target-https-proxies update banking-proxy \
  --ssl-policy finance-pq-policy

効果: PCI DSS や金融規制への準拠を強化。顧客の金融データを将来の量子攻撃から保護。

効果: HIPAA 準拠を強化し、患者データの長期的な機密性を確保。遺伝子情報のような数十年間にわたり価値を持つデータを量子コンピュータの脅威から保護。

📝 まとめ

Cloud Load Balancing におけるポスト量子鍵交換サポートは、量子コンピュータ時代に向けた重要なセキュリティ強化です。特に長期的なデータ機密性が求められる組織は、SSL ポリシーで post-quantum-key-exchange を ENABLED に設定し、即座にポスト量子保護を有効化することを強く推奨します。

推奨アクション:
  • 追加コストなしで利用可能
  • 互換性のあるクライアントのみに適用されるため既存システムへの影響なし
  • Phase 1 の今こそ、先行的にポスト量子保護を有効化する最適なタイミング
