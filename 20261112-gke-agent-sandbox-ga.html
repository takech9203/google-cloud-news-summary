📌 概要

Agent Sandbox on GKE が一般提供 (GA) になりました。AI エージェントのような 「分離された・ステートフルな・単一レプリカのワークロード」の実行に最適化された仕組みで、 オープンソース (Kubernetes SIG Apps 配下) のコントローラを GKE クラスタに導入して利用します。

AI エージェントは LLM が生成した信頼できないコードを実行することが多く、ノードのカーネルからの分離が不可欠です。 Agent Sandbox は GKE Sandbox (gVisor / microVM) によるカーネルレベル分離を備えた専用 Pod を各エージェントに提供し、 標準の Kubernetes API で管理できます。ウォームプールにより通常 1 秒未満で実行環境を払い出せるため、対話型エージェントのレイテンシ要件にも対応します。

❌ Before: アップデート前の課題

  • 信頼できないコードの安全な実行には、gVisor ノードプール・NetworkPolicy・セキュリティ設定を個別に設計・組み合わせる必要があった
  • ステートフルで単一レプリカの環境は StatefulSet などによる複雑な構成管理が必要だった
  • Pod のスケジューリングとイメージ取得・起動を待つ必要があり、高速な環境払い出しが困難だった

✅ After: アップデート後の改善

  • Sandbox カスタムリソースで、安定したホスト名・ネットワーク ID・永続ストレージを持つ分離環境を宣言的 API ひとつで管理
  • SandboxClaim / SandboxWarmPool / SandboxTemplate のクレームモデルとウォームプールでサブセカンドプロビジョニング
  • GA により、サポート対象のすべての GKE バージョンで追加費用なしに本番利用可能 (GKE リソース自体の料金は適用)
💡 選択の指針: 公式ドキュメントでは多くのエージェントワークロードには、同一ノード上でより多くのエージェントを実行できる Agent Substrate on GKE が推奨されています。Agent Sandbox on GKE は 「各エージェントに専用 Pod が必要」「GPU/TPU を使う」「完全な Kubernetes PodSpec が必要」「GKE Autopilot で実行する」ケースに適しています。

アプリケーションは SandboxClaim を作成するだけで、コントローラがウォームプールから準備済みの Sandbox (カーネル分離された専用 Pod) を 1 秒未満で割り当てます。Sandbox Router が安定したエンドポイントを提供し、エージェント Pod へのトラフィックを中継します。

⚡ 主要機能

🔒 1. カーネルレベルの分離

→GKE Sandbox (gVisor または microVM) により、LLM が生成した信頼できないコードをノードのカーネルから分離
→セルフマネージドのオープンソース Kata Containers との組み合わせも可能 (ただし Google Cloud 製品ではなく、サポート・SLA 対象外)
→SandboxTemplate ごとにデフォルト拒否の NetworkPolicy が自動作成され、内部ネットワークや GKE コントロールプレーンへの不正アクセスを防止

🚀 2. サブセカンドプロビジョニング (ウォームプール)

→SandboxWarmPool が準備完了状態の Pod を持つ Sandbox をプールとして維持
→SandboxClaim 作成時にイメージ取得や起動を待たずに割り当て、通常 1 秒未満で実行環境を提供
→Pod スナップショットと組み合わせると、事前構成済みの状態から Pod を復元可能

🧩 3. クレームモデルによる宣言的な環境リクエスト

→SandboxClaim / SandboxWarmPool / SandboxTemplate の 3 つのカスタムリソースで、環境のリクエストとプロビジョニングの実装詳細を分離
→StatefulSet と異なり、利用者は基盤の Pod やストレージ構成を直接管理せずに Sandbox をリクエスト可能
→プールに準備済み Sandbox がない場合は、コントローラがテンプレートから新規作成

→Python SDK (k8s-agent-sandbox) などのクライアントライブラリで、Kubernetes YAML を管理せずに Sandbox リソースを操作可能
→LangChain や Vertex AI Agentic SDK などの Python ベースのエージェントフレームワークから直接分離環境を作成・利用できる

🛡️ 推奨セキュリティポリシー適用時の必須設定

推奨の secure-sandbox-policy (ValidatingAdmissionPolicy) を適用した場合、Sandbox / SandboxTemplate のマニフェストには以下が必須です。

必須設定内容
runtimeClassName: gvisorgVisor ランタイムで実行 (microVM を含む他ランタイムは拒否)
automountServiceAccountToken: falseデフォルトのサービスアカウントトークンの自動マウントを禁止
securityContext.runAsNonRoot: trueroot ユーザーでの実行を禁止
securityContext.capabilities.drop: ["ALL"]すべての Linux ケーパビリティを削除
resources.limitsDoS 防止のため CPU / メモリ上限を必須化
nodeSelector / tolerationssandbox.gke.io/runtime: gvisor をターゲットにし、対応する taint への toleration を含める
🚫 禁止事項: hostNetwork / hostPID / hostIPC、privileged: true、HostPath ボリューム、capabilities.add、hostPort、カスタム sysctl などは禁止されます。

ステップ 1: 環境変数の設定とクラスタ作成

BashAutopilot クラスタの作成 (gVisor は自動で有効)
export CLUSTER_NAME="agent-sandbox-cluster"
export LOCATION="us-central1"
export AGENT_SANDBOX_VERSION="v1.0.6"

# Autopilot クラスタを作成 (gVisor は自動で有効)
gcloud container clusters create-auto ${CLUSTER_NAME} \
  --location=${LOCATION}

# 認証情報を取得
gcloud container clusters get-credentials ${CLUSTER_NAME} \
  --location=${LOCATION}

💡 Standard クラスタの場合は --sandbox=type=gvisor を指定した gVisor 有効のノードプールを別途作成します。

ステップ 4: Sandbox リソースのデプロイ

YAMLsandbox.yaml — 推奨ポリシー準拠の Sandbox 定義
apiVersion: agents.x-k8s.io/v1beta1
kind: Sandbox
metadata:
  name: sandbox-example
spec:
  podTemplate:
    spec:
      runtimeClassName: gvisor
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
      nodeSelector:
        sandbox.gke.io/runtime: gvisor
      tolerations:
        - key: "sandbox.gke.io/runtime"
          value: "gvisor"
          effect: "NoSchedule"
      containers:
        - name: my-container
          image: busybox
          command: ["/bin/sh", "-c"]
          args: ["sleep 3600000"]
          securityContext:
            capabilities:
              drop: ["ALL"]
            allowPrivilegeEscalation: false
          resources:
            limits:
              cpu: "100m"
              memory: "128Mi"
Bashデプロイと確認
kubectl apply -f sandbox.yaml
kubectl get sandbox
💡 ヒント: 高速な起動が必要な場合は、SandboxTemplate / SandboxWarmPool / SandboxClaim を使うクレームモデルを利用します。 Python クライアントを使う場合は、Sandbox Router を agent-sandbox-system 名前空間にデプロイします。

⚙️ 技術面

✓VM 相当の分離と Kubernetes ネイティブ運用の両立: 宣言的・標準化された API により、VM に近い分離・永続性特性を Kubernetes プリミティブだけで実現
✓サブセカンドの環境払い出し: ウォームプールにより対話型エージェントに必要な低レイテンシを実現
✓多層防御: gVisor によるカーネル分離 + デフォルト拒否 NetworkPolicy + ValidatingAdmissionPolicy による構成強制

⚠️ デメリット・制約事項

🚧 制限事項

✗Pod スナップショットは GKE 1.35.3-gke.1234000 以降が必要で、gVisor のみ対応 (microVM 不可)。E2 マシンタイプおよび TPU では利用不可
✗GPU / TPU は gVisor ランタイムかつサポート対象のモデル / バージョンでのみ利用可能 (microVM 非対応)
✗推奨セキュリティポリシーを適用すると gVisor 以外のランタイム (microVM 含む) は拒否される
✗Pod スナップショットなど一部の基盤機能は Preview 段階またはリージョン限定の場合がある

🤔 考慮すべき点

⚠️オープンソースのコントローラは利用者自身がインストール・アップグレードを管理する必要がある (v1.0.0 より前からのアップグレードでは v1beta1 API への移行が必要)
⚠️アイドル状態の自動検出は行われないため、サスペンドの判断ロジックはアプリケーション側で実装する必要がある
⚠️GKE Sandbox ランタイム (gVisor / microVM) を指定しない場合はカーネル分離なしで実行されるため、信頼できないコードの実行には使用しないこと
⚠️多くのエージェントワークロードでは Agent Substrate on GKE の方が集積度が高く推奨される。専用 Pod、GPU/TPU、完全な PodSpec、Autopilot が必要な場合に Agent Sandbox を選択する

💰 料金・利用可能リージョン

💵 料金: Agent Sandbox on GKE はオープンソースソフトウェアであり、追加料金なしで利用できます。 ただし、作成するリソース (Agent Sandbox コントローラが使用するコンピュートリソースを含む) には通常の GKE 料金が適用されます。

📝 まとめ

Agent Sandbox on GKE の GA により、LLM が生成する信頼できないコードをカーネルレベルで分離しつつ、 1 秒未満で払い出せるエージェント実行環境を、追加費用なしに標準の Kubernetes API で構築できるようになりました。

🚀 推奨アクション: AI エージェント基盤を GKE 上に構築している、または検討中のチームは、まず Agent Substrate on GKE との比較 (専用 Pod、GPU/TPU、完全な PodSpec、Autopilot の要否) でアーキテクチャを選定し、該当する場合はオープンソースのコントローラと推奨セキュリティポリシーを導入して評価を始めることを推奨します。
