📋 概要: CI/CD 運用の「予測可能性」を高めるリリース

CodeMender は、コードベースの脆弱性をスキャン (cm find)・検証 (cm verify)・修正 (cm fix) する自律型 AI エージェント。 推論はクラウド側のホスト型エンジン、コマンド実行・パッチ適用はローカルの OS レベルサンドボックス内で行う実行モデルを採用している。

v0.22.0 の中心テーマは CI/CD 運用の予測可能性。 --duration による実行時間の時間ボックス化、CSV エクスポート/インポート、終了コードの整理に加え、 ADC トークン保護や Trojan Source 対策などセキュリティ上重要なバグ修正 6 件を含む。

❌ Before (アップデート前の課題)

  • 実行時間上限の CLI オプションがなく、CI ランナー側の timeout-minutes に依存。強制終了すると発見済みの結果も喪失
  • 出力は table / JSON / SARIF のみで CSV 未対応。スプレッドシート連携に変換処理が必要
  • 一般失敗とプロンプトインジェクション停止の終了コードが CI ゲート失敗と区別しにくい
  • テストパターンに一致するコメントを含むだけのファイルがスキャンから誤スキップ
  • レポート再インポートで finding が重複登録
  • ADC トークンが googleapis.com 以外へ送信され得た
  • サンドボックス外実行でも警告なし / hash-based .pyc 未ブロック
  • Bidi 制御文字・不可視文字が除去されず表示 (Trojan Source リスク)

✅ After (v0.22.0 での改善)

  • --duration / --timeout / CM_DURATION で上限設定。上限到達時も部分結果を報告して exit 50
  • cm find --diff では --fail-on ゲートを先に評価し、CI ゲートの信頼性を維持
  • --format csv と CSV インポートに対応し、外部ツールと直接連携
  • exit 1 = CI ゲート失敗専用、exit 2 = 一般失敗・フィルタ停止に整理
  • 誤スキップ解消でスキャンカバレッジ改善、再インポートは冪等化
  • ADC トークン送信先を googleapis.com に限定
  • サンドボックス外実行の警告表示、.pyc ブロック + 生成バイトコード削除
  • Bidi 制御文字・不可視文字を表示前に除去

💡 ポイント: v0.22.0 では --duration による時間ボックス化が可能になり、上限到達時も収集済みの結果を報告してから exit 50 で終了する。 cm find --diff では --fail-on ゲートが先に評価されるため CI ゲートの判定が優先され、CSV エクスポート/インポートにより外部ワークフローとの連携も双方向化された。

🚀 主要機能

⏱️ 1. 実行時間の上限 (--duration / --timeout / CM_DURATION)

  • cm find / cm fix / cm verify / cm session resume に --duration フラグ (エイリアス --timeout) を追加
  • 環境変数 CM_DURATION でも設定可能。CI/CD パイプライン全体での一括設定に向く
  • 上限到達時は 停止 → 収集済み結果の報告 → exit 50 の順で終了。部分結果が失われない
  • cm find --diff では --fail-on ゲートを先に評価。ブロッキング finding があれば時間切れでも exit 1

📄 2. CSV エクスポート/インポート

  • cm find と cm report が --format csv と .csv 出力ファイルをサポート
  • cm report import が JSON / SARIF に加えて CSV を受け付ける
  • スプレッドシートでのトリアージ結果や、CSV を出力する既存スキャナの結果を直接連携可能

🔢 3. 終了コードの整理

  • 一般的な失敗とプロンプトインジェクションフィルタによる停止は exit 2
  • exit 1 は CI ゲート失敗 (--fail-on) 専用として予約
  • 「脆弱性検出による意図的なブロック」と「実行エラー」を終了コードだけで判別できる

🔧 4. バグ修正 (6 件)

  • ファイル検出の修正: テストパターン・生成コードマーカーに一致するコメント/文字列による誤スキップを解消
  • インポートの冪等化: cm report import の再インポートで finding が重複しない
  • ADC トークン保護: googleapis.com 以外のエンドポイントへトークンを送信しない
  • サンドボックス外実行の警告: --sandbox=false 時などに警告を表示
  • Python バイトコードの遮断: hash-based .pyc をブロックし、セッション生成バイトコードを削除
  • 表示偽装対策: Bidi 制御文字・不可視文字を信頼できないテキストの表示前に除去

ステップ 1: CLI を v0.22.0 に更新

Bash CLI アップデート 
cm update

--duration フラグ、CSV 対応、終了コードの整理、セキュリティ関連のバグ修正が適用される。

ステップ 2: 実行時間の上限を設定して実行

Bash 時間上限付きのスキャン・検証・修正 
# フラグで指定 (エイリアス --timeout も利用可)
cm find . --diff=origin/main --fail-on=CRITICAL,HIGH --duration 20m

# 環境変数で一括設定 (CI/CD 向け)
export CM_DURATION=30m
cm verify FINDING_ID
cm fix FINDING_ID

上限に達すると、それまでの結果を報告して exit 50 で終了。cm find --diff ではブロッキング finding があれば exit 1 となる。

ステップ 3: CSV エクスポート / インポートを利用

Bash CSV 連携 
# スキャン結果を CSV で出力 (--output の拡張子 .csv でも可)
cm find . --diff=origin/main --format csv --output findings.csv

# 登録済み findings を CSV でエクスポート
cm report --format csv --output report.csv

# 外部ツールやスプレッドシート由来の CSV をインポート
cm report import --file ./findings.csv

同じファイルを再インポートしても finding は重複登録されない (v0.22.0 で修正)。

ステップ 4: CI/CD の終了コードハンドリングを更新

Bash 終了コードによる分岐処理 
cm find . --diff=origin/main --fail-on=CRITICAL,HIGH --duration 20m
status=$?
case "$status" in
  0)  echo "クリーン: ブロッキングな finding なし" ;;
  1)  echo "CI ゲート失敗: CRITICAL/HIGH の finding あり"; exit 1 ;;
  2)  echo "実行エラーまたはプロンプトインジェクションフィルタによる停止"; exit 1 ;;
  50) echo "時間上限到達: 部分的な結果を確認 (ブロッキング finding はなし)" ;;
esac

exit 1 が CI ゲート失敗専用になったため、ゲート判定とエラー処理を明確に分岐できる。

✨ メリット

💼 ビジネス面

✓CI/CD コストと実行時間の予測可能性: --duration で実行を時間ボックス化でき、パイプラインの SLA とトークン消費を制御。時間切れでも部分結果が得られ、投入した実行時間が無駄にならない
✓既存ワークフローとの統合コスト削減: CSV 対応により、スプレッドシートや既存の脆弱性管理ツールとの間でデータを変換なしに往復できる
✓資格情報・サプライチェーンリスクの低減: ADC トークンの送信先制限、.pyc 遮断、Bidi 制御文字の除去でエージェント実行のセキュリティリスクがさらに低下

🔧 技術面

✓CI ゲートの一貫性: 時間切れ時も --fail-on ゲートが先に評価され、「時間切れによるブロッキング finding の見逃し」が起きない
✓終了コードによる明確な分岐: exit 1 (ゲート失敗) / exit 2 (一般失敗・フィルタ停止) / exit 50 (時間上限) の区別でエラーハンドリングが単純化
✓スキャンカバレッジの改善: テストパターン・生成コードマーカー一致による誤スキップが解消され、スキャン漏れがなくなる
✓インポートの冪等性: 再インポートで重複しないため、CI で定期的に外部スキャナの結果を取り込む運用が安全
✓表示偽装への防御: Bidi 制御文字・不可視文字の除去により、Trojan Source 型の攻撃でレビュー担当者の目を欺く手口に対抗

⚠️ デメリット・制約事項

🚧 制限事項

  • CodeMender は Preview であり、限定された顧客のみ利用可能。Pre-GA Offerings Terms が適用される
  • 時間上限到達時の結果は部分的なものであり、完了時と同等のカバレッジは保証されない。exit 50 を「クリーン」と同一視しない運用設計が必要
  • cm report import が受け付ける CSV の形式 (必要なカラムなど) は cm report import --help で確認が必要

🤔 考慮すべき点

  • 終了コードの整理 (一般失敗が 2 に統一、1 が CI ゲート専用化) により、既存パイプラインの終了コード判定スクリプトは挙動が変わる可能性がある。更新時にエラーハンドリングを見直すこと
  • CM_DURATION をグローバルに設定するとすべての cm コマンドに適用される。長時間かかる deep スキャン (cm find --deep) には個別の値を検討
  • ファイル検出の修正によりスキャン対象が増えるため、スキャン時間・トークン消費・finding 件数が増える可能性がある
  • サンドボックス外実行 (--sandbox=false) の警告が CI ログに出力されるため、ログベースの監視でノイズにならないよう運用を調整

🎯 ユースケース

1️⃣ 時間ボックス化された PR ゲートスキャン

シナリオ: PR ごとの cm find --diff が大きな変更セットで長引き CI 全体が遅延。ランナーの timeout-minutes で強制終了すると結果が一切残らず、再実行コストが高い。

Bash PR ゲートスキャン 
cm find . --diff=origin/main \
  --fail-on=CRITICAL,HIGH \
  --duration 15m \
  --format=sarif --output=codemender.sarif
✅ 効果: 15 分で確実にジョブが返り、時間切れでも結果が SARIF として得られる。ブロッキング finding があれば --fail-on ゲートが先に評価されて exit 1 となり、時間切れを理由に危険な変更がすり抜けない。

2️⃣ スプレッドシート / 外部スキャナとの CSV 連携

シナリオ: セキュリティチームが脆弱性トリアージをスプレッドシートで管理し、既存 SAST ツールも CSV でレポートを出力。これらの findings を CodeMender の検証・自動修正パイプラインに流したい。

Bash CSV による双方向連携 
# 外部ツールの CSV をインポート (再実行しても重複しない)
cm report import --file ./external-findings.csv

# finding ID を確認して検証・修正へ
cm report
cm verify FINDING_ID
cm fix FINDING_ID

# 結果を CSV でエクスポートしてスプレッドシートに戻す
cm report --format csv --output triage-results.csv
✅ 効果: JSON/SARIF への変換スクリプトが不要になり、トリアージ台帳と CodeMender の間で findings を双方向に同期できる。インポートが冪等なため、定期ジョブでの再取り込みも安全。

3️⃣ v0.22.0 のセキュリティ修正による防御強化

シナリオ: 外部由来のリポジトリ (OSS フォークなど) を CodeMender でスキャンしており、リポジトリに悪意あるコードが含まれる可能性を想定した多層防御を維持したい。

✅ 効果: (1) ADC トークンが googleapis.com 以外へ送信されず、エージェントが誘導されても資格情報が漏れない。(2) hash-based .pyc のブロックとセッション生成バイトコードの削除で、バイトコード経由のコード実行・永続化を防止。(3) Bidi 制御文字・不可視文字の除去で、表示偽装によるターミナル出力の欺瞞に対抗。cm update するだけで 3 つの防御が適用される。

📝 まとめ

CodeMender v0.22.0 は、--duration による実行時間の時間ボックス化、CSV エクスポート/インポート、終了コードの整理 (1 = CI ゲート専用 / 2 = 一般失敗・フィルタ停止 / 50 = 時間上限) により、CI/CD 組み込み時の予測可能性と既存ワークフローとの連携性を大きく高めるリリース。

ADC トークンの送信先制限や Bidi 制御文字の除去などセキュリティ上重要な修正も含まれるため、cm update での早期アップデートを推奨。終了コードの意味が変わるため、既存パイプラインのエラーハンドリングの見直しもあわせて行いたい。
