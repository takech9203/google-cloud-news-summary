🔗 Cloud Service Mesh: EnvoyFilter API の限定サポート

2026-05-20
Cloud Service Mesh Stable

📋 概要

Google Cloud は、Managed Cloud Service Mesh の TRAFFIC_DIRECTOR 実装 において、 Stable チャネルで EnvoyFilter API の限定的なサポートを開始しました。 標準の Istio API では実現できないデータプレーンの拡張機能を、マネージドサービスメッシュ環境で安全に利用できるようになります。

EnvoyFilter API は、Envoy プロキシが生成する設定を直接カスタマイズするための高度な API です。 ローカルレートリミットや gRPC-Web フィルタなど、 特定のユースケースに対応するための HTTP フィルタチェーンの拡張が Stable チャネルでサポートされます。

❌ Before (アップデート前)

  • 標準 Istio API では HTTP フィルタチェーンのカスタマイズ不可
  • ローカルレートリミット等には セルフマネージドコントロールプレーンが必要
  • Stable チャネルでは EnvoyFilter API を使えなかった

✅ After (アップデート後)

  • Stable チャネルで EnvoyFilter API が利用可能に
  • マネージドコントロールプレーンの恩恵を維持しつつ拡張可能
  • サポート対象のエクステンションが明確に定義

⚡ 主要機能

🔧 HTTP フィルタチェーンのカスタマイズ

→HTTP_FILTER を指定してカスタムフィルタを挿入
→INSERT_FIRST / INSERT_BEFORE オペレーション対応
→workloadSelector で対象ワークロードを限定可能

🚦 ローカルレートリミット

→トークンバケットアルゴリズムによる柔軟なレート制御
→ダウンストリーム接続単位のレートリミット設定
→X-RateLimit レスポンスヘッダー付与オプション

🌐 gRPC-Web フィルタ

→ブラウザベースの gRPC クライアントとバックエンド間の通信を仲介
→プロトコル変換をサイドカーレベルで実行

🛡️ マネージドな安全性

→Google がサポートする拡張機能リストが明確に定義
→自動アップグレード・高可用性を維持

🛠️ 設定方法

前提条件

📋 前提条件:
→Cloud Service Mesh が TRAFFIC_DIRECTOR 実装の Stable チャネルでプロビジョニング済み
→GKE クラスタに Envoy サイドカーインジェクションが有効な名前空間が存在
→対象ワークロードがデプロイ済み

Step 1: 名前空間のサイドカーインジェクション有効化

Bash サイドカーインジェクション設定 
kubectl label namespace TARGET_NAMESPACE \
  istio.io/rev- istio-injection=enabled --overwrite

Step 2: EnvoyFilter リソースの作成 (ローカルレートリミット例)

YAML EnvoyFilter マニフェスト 
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: frontend-local-ratelimit
  namespace: my-namespace
spec:
  workloadSelector:
    labels:
      app: frontend
  configPatches:
  - applyTo: HTTP_FILTER
    match:
      context: SIDECAR_INBOUND
      listener:
        filterChain:
          filter:
            name: "envoy.filters.network.http_connection_manager"
            subFilter:
              name: "envoy.filters.http.router"
    patch:
      operation: INSERT_BEFORE
      value:
        name: envoy.filters.http.local_ratelimit
        typed_config:
          "@type": type.googleapis.com/udpa.type.v1.TypedStruct
          type_url: type.googleapis.com/envoy.extensions.filters.http.local_ratelimit.v3.LocalRateLimit
          value:
            stat_prefix: http_local_rate_limiter
            token_bucket:
              max_tokens: 100
              tokens_per_fill: 100
              fill_interval: 60s
            filter_enabled:
              runtime_key: local_rate_limit_enabled
              default_value:
                numerator: 100
                denominator: HUNDRED
            filter_enforced:
              runtime_key: local_rate_limit_enforced
              default_value:
                numerator: 100
                denominator: HUNDRED

Step 3: 設定の適用と検証

Bash 適用とステータス確認 
# EnvoyFilter の適用
kubectl apply -f envoyfilter.yaml

# ステータスの確認
kubectl get envoyfilter -n my-namespace frontend-local-ratelimit -o yaml

Step 4: 設定の伝播確認

Bash Envoy 設定ダンプで伝播確認 
gcloud beta container fleet mesh debug proxy-config POD_NAME.NAMESPACE \
  --type=listener \
  --membership=MEMBERSHIP_ID \
  --location=MEMBERSHIP_LOCATION \
  --project=PROJECT_ID \
  --output=yaml | grep local_ratelimit -C 5

⚖️ メリット・デメリット

✅ メリット

ビジネス面
→SLA が求められる本番ワークロードでローカルレートリミット等を安心して利用可能
→マネージドコントロールプレーンの恩恵 (自動アップグレード、パッチ適用) を維持
技術面
→外部レートリミットサービスなしでワークロード単位の過負荷保護
→標準 Istio API の制約を超えた Envoy ネイティブ機能の活用
→filter_enabled / filter_enforced で段階的ロールアウト可能

⚠️ デメリット・制約

制限事項
→ADD, REMOVE, REPLACE オペレーションは利用不可
→applyTo は HTTP_FILTER のみ (CLUSTER, ROUTE_CONFIGURATION 等は非対応)
→サポート対象エクステンションは Local Rate Limit と gRPC-Web のみ
考慮事項
→不正な設定はメッシュ全体を不安定にする可能性あり
→Envoy バージョンアップグレード時に互換性保証なし
→エクステンション固有の API 正確性は Google サポート対象外

💡 ユースケース

🛒 ユースケース 1: マイクロサービスのローカルレートリミット

シナリオ: EC サイトのフロントエンドサービスがトラフィックスパイクに対して自己防衛する必要がある。外部レートリミットサービスなしで Pod レベルのレート制御を実現。

効果: 各 Pod が毎分 1000 リクエスト超のトラフィックを 429 で拒否。レスポンスヘッダーで残りトークン数をクライアントに通知。

📝 まとめ

💡 要点: Cloud Service Mesh の Stable チャネル (TRAFFIC_DIRECTOR 実装) で EnvoyFilter API が限定的にサポートされ、本番環境でのデータプレーン拡張が実現しました。 特にローカルレートリミットは、外部サービスなしでワークロード単位の過負荷保護を実現する実用的な機能です。 利用を検討する際は、サポート対象のフィールドとエクステンションの制限を確認し、標準 Istio API で代替可能な場合はそちらを優先することを推奨します。
