🗂️ Cloud Asset Inventory が Cloud KMS
KajPolicyConfig リソースタイプに対応

Cloud Asset Inventory Cloud KMS GA (一般提供)
📅 リリース日: 2026-11-10
🏷️ Key Access Justifications / Assured Workloads

📝 概要

Cloud Asset Inventory で、Cloud KMS の新しいリソースタイプ cloudkms.googleapis.com/KajPolicyConfig が ExportAssets / ListAssets / BatchGetAssetsHistory / QueryAssets / Feed の各 API を通じて一般公開されました。組織・フォルダ・プロジェクトに設定された デフォルト Key Access Justifications (KAJ) ポリシー を、他の Google Cloud リソースと同様に一元的に棚卸し・監査・監視できます。

💡 KajPolicyConfig とは: Key Access Justifications のデフォルトポリシーを組織・フォルダ・プロジェクト単位で定義するリソース。 KAJ は Google が顧客の暗号鍵にアクセスする際の理由 (justification) を可視化し、許可する理由コードをポリシーで制御する機能で、 Assured Workloads と組み合わせてコンプライアンス要件の厳しいワークロードで利用されます。 デフォルトポリシーは、そのリソース配下で新規作成される Cloud KMS 鍵に自動適用されます。

🎯 主な対象ユーザー: 規制業種 (金融、公共など) で Assured Workloads や KAJ を利用し、 組織全体の鍵アクセス制御ポリシーの設定状況を監査・追跡する必要がある セキュリティ管理者・コンプライアンス担当者

❌ Before (アップデート前の課題)

  • デフォルト KAJ ポリシーの棚卸しには Cloud KMS API (getKajPolicyConfig) や gcloud beta kms kaj-config describe をリソースごとに個別呼び出し
  • 設定変更履歴を時系列で追跡する標準的な手段がない
  • 変更のリアルタイム検知・通知の仕組みを独自構築する必要あり

✅ After (アップデート後の改善)

  • ExportAssets: 組織配下の全 KajPolicyConfig を BigQuery / Cloud Storage へ一括エクスポート
  • BatchGetAssetsHistory: 変更履歴 (最大 35 日間) を監査証跡として取得
  • Feed (Pub/Sub): ポリシー作成・変更をほぼリアルタイムに検知・自動対応
  • QueryAssets: BigQuery SQL 構文で直接クエリ

組織・フォルダ・プロジェクトに設定されたデフォルト KAJ ポリシー (KajPolicyConfig) のメタデータを Cloud Asset Inventory が収集し、エクスポート・一覧取得・履歴照会・SQL クエリ・変更通知の各 API から利用できます。

⚙️ 主要機能

1️⃣ 対応 API (5 種類)

→ExportAssets: 指定時点の KajPolicyConfig メタデータを BigQuery / Cloud Storage へ一括エクスポート
→ListAssets: プロジェクト・フォルダ・組織スコープでの一覧取得
→BatchGetAssetsHistory: 変更履歴の取得 (最大 35 日間)
→QueryAssets: BigQuery SQL 構文によるクエリ
→Feed: Pub/Sub 経由での変更監視

2️⃣ KajPolicyConfig リソースとは

→組織 (organizations/{ORG}/kajPolicyConfig)、フォルダ (folders/{FOLDER}/kajPolicyConfig)、プロジェクト (projects/{PROJECT}/kajPolicyConfig) 単位で設定するデフォルト KAJ ポリシー
→defaultKeyAccessJustificationPolicy.allowedAccessReasons に許可する理由コード (例: CUSTOMER_INITIATED_ACCESS、GOOGLE_INITIATED_SYSTEM_OPERATION) を定義
→デフォルトポリシーは配下で新規作成される Cloud KMS 鍵に自動適用 (既存鍵には適用されない)

3️⃣ 既存の Cloud KMS 対応リソースタイプとの統合

→Cloud Asset Inventory はすでに CryptoKey、CryptoKeyVersion、KeyRing、AutokeyConfig、EkmConfig などに対応済み
→KajPolicyConfig の追加により、鍵管理関連の構成を包括的に棚卸し可能に

🔬 技術仕様

項目詳細
アセットタイプcloudkms.googleapis.com/KajPolicyConfig
提供サービスCloud Key Management Service (cloudkms.googleapis.com)
対応 APIExportAssets、ListAssets、BatchGetAssetsHistory、QueryAssets、Feed
非対応 API分析 (Analysis) API (公式アセットタイプ一覧に「Not available in the analysis APIs」と記載)
設定可能なスコープ組織 / フォルダ / プロジェクト
変更履歴の保持期間最大 35 日間 (Cloud Asset Inventory 共通仕様)

📄 KajPolicyConfig のデータ構造例

JSON 組織レベルのデフォルト KAJ ポリシー設定 
{
  "name": "organizations/ORGANIZATION_ID/kajPolicyConfig",
  "defaultKeyAccessJustificationPolicy": {
    "defaultPolicyAvailable": true,
    "allowedAccessReasons": [
      "CUSTOMER_INITIATED_ACCESS",
      "GOOGLE_INITIATED_SYSTEM_OPERATION"
    ]
  }
}

🛠️ 設定方法

✅ 前提条件

✓Cloud Asset API (cloudasset.googleapis.com) が有効化されていること
✓対象スコープに対する Cloud Asset Inventory の閲覧権限 (例: roles/cloudasset.viewer) があること
✓デフォルト KAJ ポリシー自体の管理には roles/cloudkms.keyAccessJustificationsPolicyConfigAdmin ロールが必要 (デフォルト KAJ ポリシーの設定は Assured Workloads の Japan Regions コントロールパッケージに登録されたフォルダ内の Cloud KMS 鍵が対象)
1️⃣ 一覧取得
gcloud asset list
→
2️⃣ エクスポート分析
gcloud asset export
→
3️⃣ 変更監視
gcloud asset feeds create

ステップ 1: KajPolicyConfig の一覧を取得する

Bash 組織配下のデフォルト KAJ ポリシー設定を一覧表示 
gcloud asset list \
  --organization=ORGANIZATION_ID \
  --asset-types="cloudkms.googleapis.com/KajPolicyConfig" \
  --content-type=resource

ステップ 2: BigQuery にエクスポートして分析する

Bash BigQuery へ一括エクスポート 
gcloud asset export \
  --organization=ORGANIZATION_ID \
  --asset-types="cloudkms.googleapis.com/KajPolicyConfig" \
  --content-type=resource \
  --bigquery-table="projects/PROJECT_ID/datasets/DATASET_ID/tables/kaj_policy_configs" \
  --output-bigquery-force

エクスポート後、BigQuery で allowedAccessReasons の内容を SQL で検証し、組織のポリシー基準から逸脱した設定を検出できます。

ステップ 3: Feed で変更を監視する

Bash Pub/Sub への変更通知フィードを作成 
gcloud asset feeds create kaj-policy-feed \
  --organization=ORGANIZATION_ID \
  --asset-types="cloudkms.googleapis.com/KajPolicyConfig" \
  --content-type=resource \
  --pubsub-topic="projects/PROJECT_ID/topics/kaj-policy-changes"

デフォルト KAJ ポリシーの作成・変更時に Pub/Sub へ通知が送信され、Cloud Functions などで自動検証・アラートを実装できます。

💪 メリット

💼 ビジネス面

✓コンプライアンス監査の効率化: 「鍵アクセス制御ポリシーの設定状況」を組織横断で一括棚卸しでき、監査対応の工数を削減
✓ガバナンス強化: ポリシー変更を履歴・通知として追跡でき、意図しないポリシー緩和を早期に検出

⚙️ 技術面

✓一元管理: Cloud KMS API の個別呼び出しスクリプトが不要になり、他のアセットと同じワークフロー (エクスポート、SQL クエリ、Feed) に統合
✓変更履歴の標準取得: 最大 35 日間の変更履歴を取得でき、独自の履歴管理基盤が不要に

⚠️ デメリット・制約事項

🚧 制限事項
  • 分析 (Analysis) API では KajPolicyConfig は利用できない (公式アセットタイプ一覧に記載)
  • リリースノートに記載された対応 API は ExportAssets / ListAssets / BatchGetAssetsHistory / QueryAssets / Feed であり、Search API は含まれていない
  • Cloud Asset Inventory の変更履歴の保持期間は最大 35 日間
🤔 考慮すべき点
  • Cloud Asset Inventory はリアルタイムクエリ用途には設計されていないため、最新のポリシー値を厳密に確認する場合は Cloud KMS API (getKajPolicyConfig) を直接呼び出す
  • デフォルト KAJ ポリシーは新規作成鍵にのみ適用され、既存鍵には適用されないため、既存鍵の KAJ ポリシーは鍵単位で確認する

🎯 ユースケース

🏦 ユースケース 1: 組織全体のデフォルト KAJ ポリシー監査

シナリオ: 金融機関が、全プロジェクト・フォルダのデフォルト KAJ ポリシーが社内基準 (許可する理由コードのホワイトリスト) に準拠しているかを四半期ごとに監査する。

Bash 実装例: BigQuery にエクスポートして基準外設定を SQL で抽出 
# 組織全体の KajPolicyConfig を BigQuery にエクスポートし、
# allowedAccessReasons が基準外の設定を SQL で抽出
gcloud asset export \
  --organization=ORGANIZATION_ID \
  --asset-types="cloudkms.googleapis.com/KajPolicyConfig" \
  --content-type=resource \
  --bigquery-table="projects/audit-prj/datasets/audit/tables/kaj_configs"

効果: 手動でのリソースごとの API 呼び出しが不要になり、監査作業を定期ジョブとして自動化できる。

🚨 ユースケース 2: KAJ ポリシー変更のリアルタイム検知

シナリオ: セキュリティ運用チームが、デフォルト KAJ ポリシーの変更 (許可理由コードの追加など) を即時に検知し、承認済みの変更かどうかを検証したい。

🔗 関連サービス・機能

→Cloud KMS: KajPolicyConfig を提供するサービス。CryptoKey、KeyRing、AutokeyConfig などの他の KMS リソースタイプもすでに Cloud Asset Inventory でサポート済み
→Key Access Justifications (KAJ): Google による鍵アクセスの理由を可視化・制御する機能。KajPolicyConfig はそのデフォルトポリシー設定
→Assured Workloads: デフォルト KAJ ポリシーの設定は Assured Workloads (Japan Regions コントロールパッケージ) に登録されたフォルダの Cloud KMS 鍵が対象
→BigQuery / Cloud Storage: ExportAssets のエクスポート先として利用
→Pub/Sub: Feed によるアセット変更通知の配信先として利用

📌 まとめ

Cloud Asset Inventory が Cloud KMS の KajPolicyConfig に対応したことで、 組織・フォルダ・プロジェクトに設定されたデフォルト Key Access Justifications ポリシーを、 棚卸し・履歴追跡・変更監視の標準ワークフローに組み込めるようになりました。 Assured Workloads や KAJ を利用する規制業種の組織は、 ExportAssets による定期棚卸しと Feed による変更監視を組み合わせ、 鍵アクセスガバナンスの自動化を検討することを推奨します。
