🔒 Secure Web Proxy: 全ポートリスニング機能

Secure Web Proxy Preview Networking

📋 概要

Secure Web Proxy のネクストホップモードに、all_ports: true を設定するだけで全ポート (1-65535) のトラフィックを一括インターセプトする新機能が Preview として追加されました。動的な環境や複数ポートを使用するサービスに特に有効で、ポートリスト管理の負荷を大幅に軽減します。

💡 対象ユーザー: Secure Web Proxy をネクストホップモードで利用しているネットワークセキュリティ管理者、クラウドインフラストラクチャチーム。特にマイクロサービスアーキテクチャや動的ポートワークロードを運用する組織。

🔄 Before / After 比較

❌ Before (従来)

  • リスニング対象のポートを ports フィールドに個別列挙
  • 新しいポート追加のたびに設定更新が必要
  • ポートリスト管理が煩雑
  • 設定漏れによるセキュリティギャップのリスク

✅ After (新機能)

  • all_ports: true で全ポート (1-65535) を自動インターセプト
  • ポートリストの個別管理が不要
  • 運用負荷が大幅に軽減
  • 全アウトバウンドトラフィックにセキュリティポリシーを漏れなく適用

⚡ 主要機能

🌐 全ポートリスニング

all_ports: true を指定するだけでポート 1-65535 を一括リスニング。ports フィールドとの同時指定は不可 (排他的)。routingMode: NEXT_HOP_ROUTING_MODE との組み合わせでのみ使用可能。

🔍 透過的トラフィックインターセプト

ワークロード側での設定変更が不要。ネットワークルーティングにより自動的にトラフィックを Secure Web Proxy に転送。HTTP(S) および TCP プロキシトラフィックをサポート。

🛡️ セキュリティポリシーの一括適用

全アウトバウンドトラフィックにセキュリティルールを適用。ソース (Secure Tag、サービスアカウント、IP) およびデスティネーション (ホスト名、URL) に基づくアクセス制御。

🔧 設定方法

前提条件

✓ Network Services API が有効化されていること
✓ 適切な IAM 権限 (Network Admin ロールなど)
✓ セキュリティポリシーとルールが作成済み
✓ デプロイ先の VPC ネットワークとサブネットが準備済み

Step 1: ゲートウェイ設定ファイルの作成

YAML 
# gateway.yaml
name: projects/PROJECT_ID/locations/REGION/gateways/swp1
type: SECURE_WEB_GATEWAY
addresses: ["10.0.0.100"]
all_ports: true
gatewaySecurityPolicy: projects/PROJECT_ID/locations/REGION/gatewaySecurityPolicies/policy1
network: projects/PROJECT_ID/global/networks/my-network
subnetwork: projects/PROJECT_ID/regions/REGION/subnetworks/my-subnet
routingMode: NEXT_HOP_ROUTING_MODE
⚠️ 注意: all_ports: true と ports フィールドを同時に指定することはできません。

Step 2: Secure Web Proxy インスタンスのデプロイ

Bash 
gcloud network-services gateways import swp1 \
  --source=gateway.yaml \
  --location=REGION

Step 3: ルーティングの設定 (静的ルート)

Bash 
gcloud compute routes create swp-route \
  --network=my-network \
  --next-hop-ilb=10.0.0.100 \
  --destination-range=0.0.0.0/0 \
  --priority=900 \
  --tags=use-swp \
  --project=PROJECT_ID

Step 4: ワークロード VM へのネットワークタグ付与

Bash 
gcloud compute instances create workload-vm \
  --subnet=my-subnet \
  --zone=ZONE \
  --image-project=debian-cloud \
  --image-family=debian-12 \
  --tags=use-swp

✅ メリット

ビジネス面

💰運用コストの削減 - ポートリストの継続的な管理・更新が不要。ネットワーク管理者の運用負荷を大幅に軽減。
🛡️セキュリティガバナンスの強化 - 全アウトバウンドトラフィックを漏れなく検査。コンプライアンス要件への対応が容易。
🚀迅速なサービス展開 - 新ポート追加時にプロキシ設定変更が不要。アプリケーションのデプロイ速度が向上。

技術面

⚙️設定のシンプル化 - all_ports: true の一行で全ポートインターセプト完了。設定ミスのリスク低減。
🔐ゼロトラストの実現 - デフォルト deny-all ポリシーと組み合わせて全アウトバウンド通信を制御。
🐳動的環境への対応 - マイクロサービスやコンテナワークロードなど、使用ポートが動的に変化する環境に最適。

⚠️ デメリット・制約事項

制限事項
  • Preview ステータスのため、本番環境での使用は SLA 対象外
  • all_ports: true と ports フィールドの同時指定は不可
  • 同一ネットワーク・リージョン内で他モードとの同時デプロイ不可
  • HTTP(S) および TCP プロキシのみサポート (その他はドロップ)
  • 1 VPC / 1 リージョンにつきネクストホップモードのインスタンスは 1 つのみ
  • IPv6 はサポートされていない (IPv4 のみ)
考慮すべき点
  • VM のバックグラウンドトラフィック (OS アップデートなど) もルーティング対象となるため、適切なポリシールール設定が必要
  • クロスリージョントラフィックはドロップされるため、Secure Web Proxy インスタンスと同じリージョンにクライアントを配置する必要あり
  • 全ポートインターセプトにより、データ処理課金が増加する可能性がある

🎯 ユースケース

🐳 マイクロサービス環境のエグレスセキュリティ

シナリオ: GKE 上で稼働する多数のマイクロサービスが、外部 API やサードパーティサービスに対して様々なポートでアウトバウンド通信を行っている。サービスごとに使用ポートが異なり、新しいサービスの追加も頻繁に発生。

効果: ポートリスト管理が不要。新マイクロサービス追加時もプロキシ設定変更なしにセキュリティポリシーが自動適用。

🏦 コンプライアンス要件への対応

シナリオ: 金融機関のクラウド環境で、規制要件により全アウトバウンドトラフィックの監査ログ取得と未承認外部通信の検知・ブロックが必要。

効果: 全ポートインターセプトでセキュリティギャップを排除。Cloud Audit Logs との統合で完全な監査証跡を自動記録。

📝 まとめ

Secure Web Proxy のネクストホップモードにおける全ポートリスニング機能は、アウトバウンドトラフィックのセキュリティ管理を大幅にシンプル化する重要なアップデートです。特に動的なポート使用が発生するマイクロサービス環境やコンテナワークロードにおいて、ポートリスト管理の運用負荷を排除しながら包括的なセキュリティポリシーの適用を実現します。
