📊 Spanner が近似集計関数をサポート

GoogleSQL / PostgreSQL 両ダイアレクトで APPROX_COUNT_DISTINCT と HyperLogLog++ 関数が利用可能に
リリース日: 2026-10-20

💡 概要

Spanner が GoogleSQL と PostgreSQL の両ダイアレクトで 近似集計関数 (approximate aggregate functions) をサポートしました。 個別値カウント (distinct count) の統計的推定値を生成し、 COUNT(DISTINCT ...) による正確な集計と比較して 高速かつ省リソースで結果を計算できます。

提供される機能は大きく 2 系統です。

⚡ APPROX_COUNT_DISTINCT
入力データから直接推定値を計算するシンプルな近似集計関数。PostgreSQL ダイアレクトでは spanner.approx_count_distinct。詳細な制御が不要なクイックなクエリ向け。
🧮 HyperLogLog++ (HLL++) 関数群
HLL_COUNT.INIT / EXTRACT / MERGE / MERGE_PARTIAL。 「スケッチ」と呼ばれるコンパクトなサマリーを生成・保存・マージでき、精度のカスタマイズ (10〜24) にも対応。

ユニークユーザー数などの集計を頻繁に実行するワークロードで、クエリ実行時間とコンピュートリソース消費を大きく削減できます。 BigQuery で長らく提供されてきた同等機能が、オペレーショナルデータベースである Spanner でも利用可能になりました。

❌ Before: アップデート前の課題

  • COUNT(DISTINCT ...) による正確な集計しか選択肢がなく、入力データ量に対して線形にメモリを消費。大規模データストリームでは実行時間とリソース消費が大きい
  • 中間結果 (スケッチ) を保存して後からマージするインクリメンタル集計を Spanner の SQL だけで実現できない
  • 近似集計には BigQuery など他サービスへのデータ移送が必要

✅ After: アップデート後の改善

  • APPROX_COUNT_DISTINCT により、近似結果を少ないリソースで高速に取得
  • HLL++ 関数により、スケッチの生成・保存・部分集計・再集計 (マージ) が可能に。精度 (10〜24) も指定可能
  • GoogleSQL / PostgreSQL のどちらでも同等の近似集計が利用可能

従来の COUNT(DISTINCT ...) による正確な集計 (Before) と、HLL++ スケッチに基づく近似集計 (After) の比較です。 近似集計ではスケッチを BYTES として保存し、後からマージ・再集計するインクリメンタルな処理も可能になります。

🔧 主要機能

1️⃣ APPROX_COUNT_DISTINCT (GoogleSQL)
→COUNT(DISTINCT expression) の近似結果を返す集計関数 (返り値は INT64)
→統計的推定値のため精度は落ちるが、非常に大きな入力に対して高いパフォーマンスを発揮
→入力データから直接計算するため、スケッチの保存や精度指定は不可 (詳細な制御が不要なクイックなクエリ向け)
2️⃣ HyperLogLog++ (HLL++) 関数 (GoogleSQL)
→HLL_COUNT.INIT(input [, precision]): 入力値を HLL++ スケッチ (BYTES) に集約。精度 10〜24 (デフォルト 15)
→HLL_COUNT.MERGE(sketch): 複数スケッチの和集合からカーディナリティ (INT64) を返す
→HLL_COUNT.MERGE_PARTIAL(sketch): 複数スケッチをマージして新しいスケッチ (BYTES) を返す
→HLL_COUNT.EXTRACT(sketch): 単一スケッチからカーディナリティ推定値を抽出
3️⃣ PostgreSQL ダイアレクト対応
→spanner.approx_count_distinct(expression): 非 NULL の個別値数の近似カウント (int8)
→hll_count.init / extract / merge / merge_partial も同様に提供
→パフォーマンス最大化にはカラムナストレージ有効化 (COLUMNAR POLICY enabled) とカラムナスキャンヒント (/*@ scan_method=columnar */) の併用を推奨
4️⃣ スケッチ (Sketches) の保存と連携
→スケッチはデータ集約のコンパクトなサマリー。保存して後からマージ (再集計) できる
→Dataflow、Apache Spark、ZetaSketch などの外部アプリケーションで構築した HLL++ スケッチを GoogleSQL で利用でき、その逆も可能

💻 クエリ例

SQL 近似集計関数の基本的な使い方 (GoogleSQL) 
-- APPROX_COUNT_DISTINCT: シンプルな近似個別値カウント
SELECT APPROX_COUNT_DISTINCT(x) AS approx_distinct
FROM UNNEST([0, 1, 1, 2, 3, 5]) AS x;
-- 結果: 5

-- HLL++: 国別にスケッチを生成し、マージして全体のユニーク顧客数を推定
SELECT HLL_COUNT.MERGE(hll_sketch) AS distinct_customers_with_open_invoice
FROM (
  SELECT country, HLL_COUNT.INIT(customer_id) AS hll_sketch
  FROM Invoices
  GROUP BY country
);

✨ メリット

💼 ビジネス面

✓コスト削減: 正確な集計 (COUNT(DISTINCT ...)) と比較して使用リソースが少なく、大規模データセットに対する分析クエリのコンピュート消費を抑えられる
✓分析の内製化: ユニークユーザー数などの集計のために BigQuery へデータを移送しなくても、Spanner 上で直接近似集計を実行できる

🔬 技術面

✓スケーラビリティ: 線形のメモリ使用が現実的でない大規模データストリームにも適用できる
✓インクリメンタル集計: スケッチを BYTES として保存し、MERGE / MERGE_PARTIAL で部分集計・再集計できるため、日次スケッチを保存して月次集計するといったパターンが実現できる
✓精度の制御: HLL++ 関数では精度 (10〜24) を指定して、誤差とストレージ/メモリのトレードオフを調整できる
✓エコシステム連携: Dataflow、Apache Spark、ZetaSketch で生成したスケッチと相互運用できる

⚠️ デメリット・制約事項

🚫 制限事項

✗返り値は統計的推定値であり、正確な値が必要なユースケース (課金、会計など) には適さない
✗APPROX_COUNT_DISTINCT は精度指定、スケッチの保存、部分集計・再集計に非対応 (必要な場合は HLL++ 関数を使用)
✗GoogleSQL の APPROX_COUNT_DISTINCT は ARRAY、STRUCT、PROTO、INTERVAL 型の入力に非対応
✗異なる型で初期化されたスケッチ同士はマージ不可。PostgreSQL の numeric から初期化したスケッチと GoogleSQL の NUMERIC から初期化したスケッチもマージ不可
✗HLL++ スケッチから値を削除することはできない
✗異なる精度のスケッチをマージすると、最も低い精度にダウングレードされる

🤔 考慮すべき点

⚠️ 注意:
  • 精度を上げるとスケッチの最大ストレージサイズが増加する (精度 15 で約 32 KiB、精度 24 で約 16 MiB)。保存するスケッチ数と精度のバランスを検討すること
  • PostgreSQL ダイアレクトで最良のパフォーマンスを得るには、カラムナストレージの有効化とカラムナスキャンヒントの使用が推奨されている

🎯 ユースケース

📈 ユースケース 1: ダッシュボード向けユニークユーザー数の高速集計

シナリオ: 数十億行のイベントテーブルから、日次アクティブユーザー数 (DAU) をダッシュボードに表示したい。 正確な値である必要はなく、応答速度とリソース消費を優先したい。

SQL 直近 30 日の近似 DAU を取得 
SELECT event_date, APPROX_COUNT_DISTINCT(user_id) AS approx_dau
FROM UserEvents
WHERE event_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
GROUP BY event_date;
✅ 効果: COUNT(DISTINCT user_id) と比較して高速かつ省リソースで日次ユニークユーザー数を取得できる。
🔀 ユースケース 2: スケッチの保存によるインクリメンタルなユニーク数集計

シナリオ: 日次でユニーク顧客数のスケッチを計算・保存しておき、月次や四半期のユニーク顧客数は 保存済みスケッチのマージだけで算出したい (生データの再スキャンを避けたい)。

SQL 日次スケッチの保存と月次マージ集計 
-- 日次バッチ: スケッチを生成して保存 (BYTES 列)
INSERT INTO DailyCustomerSketches (sketch_date, hll_sketch)
SELECT CURRENT_DATE(), HLL_COUNT.INIT(customer_id, 15)
FROM Orders
WHERE order_date = CURRENT_DATE();

-- 月次集計: 保存済みスケッチをマージするだけ
SELECT HLL_COUNT.MERGE(hll_sketch) AS monthly_unique_customers
FROM DailyCustomerSketches
WHERE sketch_date BETWEEN '2026-10-01' AND '2026-10-31';
✅ 効果: 月次集計時に生データを再スキャンする必要がなく、コンパクトなスケッチのマージのみで推定値を取得できる。

💰 料金

💡 ポイント: 近似集計関数の利用自体に追加料金はなし。 Spanner の通常の料金体系 (コンピュート容量、ストレージ、ネットワーク) が適用されます。 近似集計は正確な集計よりも少ないリソースでクエリを実行できるため、同じワークロードに必要な コンピュート消費の削減につながります。

📝 まとめ

Spanner の近似集計関数は、大規模データセットに対する個別値カウントを 「正確さと引き換えに高速・省リソース」で実行する選択肢を、 GoogleSQL / PostgreSQL 両ダイアレクトにもたらしました。

ダッシュボードやレポートで COUNT(DISTINCT ...) を多用しているワークロードでは、 APPROX_COUNT_DISTINCT への置き換えや、 HLL++ スケッチを保存するインクリメンタル集計パターンの導入を検討することを推奨します。
