📊 BigQuery GA (一般提供)

🔒 INFORMATION_SCHEMA.ROW_ACCESS_POLICIES ビューが GA

行レベルアクセスポリシーの棚卸し・監査が標準 SQL だけで完結
リリース日: 2026-11-18

📋 概要

BigQuery の INFORMATION_SCHEMA.ROW_ACCESS_POLICIES ビューが一般提供 (GA) になりました。 このビューをクエリすることで、データセットまたはリージョン単位で、アクティブな行レベルアクセスポリシー (row access policy) のメタデータを取得し、 フィルタ述語 (filter_predicate) を横断的に確認できます。

行レベルセキュリティは、テーブル内の特定の行へのアクセスをユーザー条件に基づいて制御する BigQuery の機能です。 今回の GA により、ポリシーの棚卸しや監査を標準 SQL だけで実行できるようになり、 データガバナンス担当者やセキュリティ管理者が組織内の行レベルセキュリティの適用状況を一元的に可視化できます。

💡 同日発表: BigQuery Lakehouse (Apache Iceberg) における行・列レベルセキュリティの GA も発表されており、 行レベルセキュリティの適用範囲拡大と、その運用・監査基盤の整備が同時に進んだ形です。

❌ Before (アップデート前の課題)

  • ポリシーの一覧確認は、テーブルごとにコンソールや bq ls --row_access_policies、Row Access Policy API で個別に実施
  • データセットやリージョン全体のフィルタ述語を SQL で横断的に棚卸しする標準手段がなかった
  • 監査時に作成日時・最終更新日時を含むメタデータの一括取得が困難

✅ After (アップデート後の改善)

  • SELECT 文 1 つで、データセット内またはリージョン内の全アクティブポリシーのメタデータを取得
  • filter_predicate を SQL で横断確認でき、意図しない・古いポリシーの検出が容易に
  • creation_time / last_modified_time で変更履歴の確認ポイントが明確になり監査対応が効率化

🗺️ アーキテクチャ図

管理者や監査担当者がデータセット単位またはリージョン単位で INFORMATION_SCHEMA をクエリし、 複数テーブルにまたがる行レベルアクセスポリシーのメタデータ (ポリシー名、フィルタ述語、作成・更新日時) を一括取得するフローです。

⚡ 主要機能

1️⃣ 行レベルアクセスポリシーの横断的なメタデータ取得

→データセット内またはリージョン内のすべてのアクティブな行レベルアクセスポリシーを 1 行ずつ返す
→プロジェクト ID、データセット名、テーブル名、ポリシー名を含むため、どのリソースにどのポリシーが適用されているかを一覧できる

2️⃣ フィルタ述語 (filter_predicate) の検査

→各ポリシーがどの行を可視にするかを定義する SQL ブール式を直接確認できる
→例: region = 'APAC' のような述語を横断的にレビューし、ガバナンスポリシーとの整合性を検証できる

3️⃣ 2 種類のスコープ (データセット / リージョン)

→データセット修飾子: DATASET_ID.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES — 特定データセット内のポリシーに限定
→リージョン修飾子: `region-REGION`.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES — プロジェクトレベルで指定リージョン内のポリシーを取得

📑 スキーマ

列名データ型内容
table_catalogSTRING行アクセスポリシーを含むプロジェクトの ID
table_schemaSTRING行アクセスポリシーを含むデータセット名
table_nameSTRING行アクセスポリシーを含むテーブル名
row_access_policy_nameSTRING行アクセスポリシーの名前
filter_predicateSTRINGこのポリシーでアクセス可能な行を定義する SQL ブール式
creation_timeTIMESTAMPポリシーの作成日時
last_modified_timeTIMESTAMPポリシーの最終更新日時
💡 ベストプラクティス: スキーマ変更時にクエリが壊れないよう、SELECT * ではなく列名を明示的に指定することが推奨されています。

🌐 スコープと構文

ビュー名リソーススコープリージョンスコープ
[PROJECT_ID.]region-REGION.INFORMATION_SCHEMA.ROW_ACCESS_POLICIESプロジェクトレベル指定リージョン
[PROJECT_ID.]DATASET_ID.INFORMATION_SCHEMA.ROW_ACCESS_POLICIESデータセットレベルデータセットのロケーション
  • INFORMATION_SCHEMA ビュー名は大文字と小文字が区別される
  • クエリ実行のロケーションはビューのリージョンと一致している必要がある
  • リージョン修飾子は階層的ではない (例: region-us マルチリージョンは us-west1 などの個別リージョンを含まない)

🔑 必要な権限

このビューをクエリするには、データセットまたはプロジェクトに対して以下の権限が必要です。

必要な IAM 権限

✓bigquery.rowAccessPolicies.get
✓bigquery.rowAccessPolicies.list

権限を含む事前定義ロール

✓BigQuery Data Owner (roles/bigquery.dataOwner)
✓BigQuery Admin (roles/bigquery.admin)
✓BigQuery Security Admin (roles/bigquery.securityAdmin)

🛠️ 設定方法

✅ 前提条件

  • 上記のいずれかの IAM ロール (または必要な権限を含むカスタムロール) が付与されていること
  • クエリ実行のロケーションが、対象の INFORMATION_SCHEMA ビューのリージョンと一致していること

ステップ 1: リージョン内のポリシーを横断確認

SQL us リージョン内の全アクティブポリシーを取得 
SELECT
  table_catalog, table_schema, table_name,
  row_access_policy_name, filter_predicate,
  creation_time, last_modified_time
FROM `region-us`.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES;

デフォルトプロジェクトの us リージョン内にあるすべてのアクティブな行レベルアクセスポリシーのメタデータを取得します。

ステップ 2: 特定データセット内のポリシーを確認

SQL データセット my_dataset 内のポリシーに限定 
SELECT
  table_name, row_access_policy_name, filter_predicate,
  creation_time, last_modified_time
FROM my_dataset.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES;

ステップ 3: テーブルごとのポリシー数を集計

SQL 特定テーブルのアクティブポリシー数をカウント 
SELECT COUNT(1) AS total_policies
FROM my_project.my_dataset.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES
WHERE table_name = 'my_table';

⚖️ メリットと制約事項

💼 ビジネス面のメリット
✓監査・コンプライアンス対応の効率化: 適用状況を SQL で一括取得でき、定期的なアクセス制御レビューや監査証跡の作成が容易に
✓ガバナンスの可視化: フィルタ述語を横断チェックでき、設定漏れや逸脱を早期に発見
⚙️ 技術面のメリット
✓標準 SQL による自動化: スケジュールクエリと組み合わせ、ポリシー棚卸しを定期自動実行するワークフローを構築可能
✓GA による本番利用の安心感: 監査パイプラインなど本番の運用プロセスに組み込みやすい
🚧 制限事項
✗グランティー情報と DDL 列は含まれない (IAM ポリシーバインディングに保存されるため)。プリンシパルの確認には bq ls --row_access_policies などを使用
✗非表示データセット (hidden datasets) および BigLake データセット内のポリシーは結果に含まれない
✗リージョン修飾子は階層的ではないため、複数リージョン横断にはリージョンごとのクエリと結果の結合が必要
⚠️ 考慮すべき点
•INFORMATION_SCHEMA クエリの結果はキャッシュされないため、実行のたびに課金が発生
•このビューはメタデータの可視化のみ。ポリシーの作成・変更・削除は DDL (CREATE ROW ACCESS POLICY など) や Row Access Policy API で実施

🎯 ユースケース

📝 ユースケース 1: 定期的なアクセス制御監査

シナリオ: 金融機関のデータガバナンスチームが、四半期ごとに BigQuery 内の行レベルアクセスポリシーの棚卸しを行い、承認済みのフィルタ述語のみが使われていることを確認する。

SQL 最終更新日時の降順でポリシーをレビュー 
SELECT
  table_catalog, table_schema, table_name,
  row_access_policy_name, filter_predicate, last_modified_time
FROM `region-us`.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES
ORDER BY last_modified_time DESC;

効果: 最近変更されたポリシーから優先的にレビューでき、未承認の述語変更や設定ミスを早期に検出できる。

🔍 ユースケース 2: ポリシー設定漏れの検出

シナリオ: マルチテナントの分析基盤で、テナント分離用の行レベルアクセスポリシーが対象テーブルすべてに設定されているかを確認したい。

効果: INFORMATION_SCHEMA.TABLES と組み合わせてポリシー未設定のテーブルを特定でき、テナント間のデータ漏えいリスクを低減できる。

💰 料金

  • 行レベルセキュリティ自体は BigQuery に追加費用なしで含まれる
  • オンデマンド料金のプロジェクトでは、INFORMATION_SCHEMA ビューへのクエリは処理バイト数が 10 MB 未満でも最低 10 MB 分のデータ処理料金が発生
  • 容量ベース (BigQuery Editions) のプロジェクトでは、購入済みスロットを消費
  • INFORMATION_SCHEMA クエリはキャッシュされないため、実行ごとに課金される (ストレージ料金は発生しない)

詳細は BigQuery の料金ページ を参照してください。
