☁️ Cloud Logging 📊 Cloud Monitoring 🔄 Changed

🛠️ Ops Agent 2.72.0
全ロギングパイプラインが Metrics Agent サービスに移行

📅 リリース日: 2026-11-17 | サービス: Cloud Logging / Cloud Monitoring (Ops Agent)

📌 概要

Ops Agent バージョン 2.72.0 で、サポートされているすべてのロギングパイプラインの処理が、 従来の Logging Agent サービス (Fluent Bit ベース) から Metrics Agent サービス (OpenTelemetry Collector ベース) に変更されました。 2.66.0 で始まったデフォルトパイプラインの移行が、2.72.0 で全サポート対象パイプラインに拡大された形です。

⚠️ 最重要ポイント: 旧バージョンから 2.72.0 以降にアップグレードすると、 一定期間ログが重複して取り込まれます。各サービスが独立に処理済みログの記録 (チェックポイント) を 保持しているためで、これは想定された動作 (expected) であり、障害ではありません。

❌ Before (〜 2.71.x)

  • ログ収集は Fluent Bit ベースの Logging Agent サービス、メトリクス収集は OpenTelemetry Collector ベースの Metrics Agent サービスの 2 系統が併存
  • 2.66.0 〜 2.71.x はデフォルトパイプラインのみ Metrics Agent サービスで処理される過渡的な構成
  • ロギングとメトリクスで処理基盤が異なり、エージェント内部のアーキテクチャが二重化

✅ After (2.72.0 〜)

  • すべてのロギングパイプラインを Metrics Agent サービス (OpenTelemetry Collector) が処理し、テレメトリー収集基盤が OpenTelemetry に統一
  • ログ・メトリクスの処理が同一サービスに集約され、内部アーキテクチャが一本化
  • 問題発生時は experimental_otel_logging: false による一時的なロールバック手段を提供

従来は Fluent Bit ベースの Logging Agent サービスがログを、OpenTelemetry Collector ベースの Metrics Agent サービスが メトリクスを処理する 2 系統構成でしたが、2.72.0 以降はすべてのロギングパイプラインも Metrics Agent サービスに集約されます。 各サービスが独自に処理済みログの記録を持つため、切り替え時には一時的なログ重複が発生します。

⚙️ 主要機能

1️⃣ 全ロギングパイプラインの Metrics Agent サービスへの移行

  • 2.66.0 で始まったデフォルトパイプラインの移行が、2.72.0 ですべてのサポート対象ロギングパイプラインに拡大
  • ログ処理の実体が Fluent Bit から OpenTelemetry Collector ベースのサービスに変更
  • ユーザー側の設定ファイル (config.yaml) の書式変更は不要

2️⃣ アップグレード時の一時的なログ重複 (想定された動作)

  • Logging Agent サービスと Metrics Agent サービスは、それぞれ独立に処理済みログの記録を保持
  • 切り替え時に、旧サービスが処理済みのログを新サービスが再処理するため、一定期間ログが重複
  • これは想定内の動作であり、エージェントの障害ではない

3️⃣ 一時的なロールバック手段の提供

  • 重複ログが問題になる場合、設定で従来の Logging Agent サービスに戻すことが可能
  • この設定は将来的に削除される予定のため、ロールバックが必要になった場合は Cloud カスタマーケアへの報告が推奨
  • ロールバック (逆方向の切り替え) 時にも同じ理由でログ重複が発生

📋 設定方法 (アップグレード手順)

💡 前提条件: Compute Engine VM に Ops Agent がインストールされていること / エージェントのアップグレード・設定変更を行うための VM への SSH / RDP アクセス権限
1

🔍 アップグレード前の影響確認

アップグレード後、一定期間ログが重複することを前提に、以下を事前に確認します。

  • ログベースの指標やログベースのアラートが、重複ログにより二重カウントされる可能性
  • ログシンク (BigQuery / Cloud Storage へのエクスポートなど) の下流で重複が影響しないか
  • ログ取り込み量の一時的な増加
2

⬆️ Ops Agent を 2.72.0 以降にアップグレード

Bash Linux: 最新バージョンへのアップグレード例 
# Linux: 最新バージョンへのアップグレード例
sudo bash add-google-cloud-ops-agent-repo.sh --also-install

アップグレード後、しばらくの間はログ重複が発生しますが、これは想定された動作です。

3

↩️ (必要な場合のみ) Logging Agent サービスへの一時的なロールバック

重複ログが運用上の問題を引き起こす場合のみ、以下の設定を追加します。

Bash ロールバック設定の追加と反映 
# 設定ファイルにロールバック設定を追記
sudo tee -a /etc/google-cloud-ops-agent/config.yaml <<EOF
logging:
  service:
    experimental_otel_logging: false
EOF

# エージェントを再起動して設定を反映
sudo systemctl restart google-cloud-ops-agent

# コンポーネントの起動状態を確認
sudo systemctl status "google-cloud-ops-agent*"
⚠️ 注意: この設定は将来的に削除される予定です。ロールバックが必要になった場合は、 Cloud カスタマーケアに問題を報告することが公式に推奨されています。 また、ロールバック時にも再度ログ重複が発生します。

⚖️ メリット / デメリット・制約事項

👍 メリット

✓テレメトリー基盤の将来性: 業界標準の OpenTelemetry ベースの処理基盤に統一され、オブザーバビリティ投資の長期的な継続性が向上
✓運用の予見性: ログ重複が「想定された動作」として公式に明示され、ロールバック手段も用意されているため、計画的なアップグレードが可能
✓アーキテクチャの統一: ログとメトリクスの処理が同一の Metrics Agent サービスに集約され、エージェント内部の 2 系統構成が解消
✓設定互換性の維持: ユーザー定義の config.yaml の書式はそのまま利用でき、移行は透過的に実施

👀 制限事項・考慮すべき点

✗アップグレード時 (およびロールバック時) に、一定期間ログが重複して取り込まれる
✗ロールバック用の experimental_otel_logging: false 設定は一時的な回避策で、将来削除予定。恒久的に継続できないため、問題がある場合は Cloud カスタマーケアへの報告が必要
⚠️重複ログは Cloud Logging の取り込み量としてカウントされ、重複期間中は取り込みコストが一時的に増加する可能性
⚠️ログベースの指標・アラート、ログシンク経由の下流システム (BigQuery、Cloud Storage など) で重複データが二重カウントされる可能性があるため、重複期間中の分析・集計には注意
⚠️大量の VM を運用している場合は、一斉アップグレードではなく段階的なロールアウトで影響範囲を限定することを推奨
⚠️期待どおり動作しない場合のトラブルシューティング手順 (公式ドキュメント「Upgraded logging pipelines」) を事前に確認

logging:
  service:
    experimental_otel_logging: false

効果: 従来の Logging Agent サービスでの処理に一時的に戻しつつ、Cloud カスタマーケアに問題を報告して恒久対応を検討する時間を確保できる。ただし再切り替え時にも重複が発生するため、切り替えタイミングは慎重に計画する必要がある。

💰 料金 / 🌏 利用可能リージョン

💰 料金: Ops Agent 自体は無料で利用できますが、収集されたログは Cloud Logging、 メトリクスは Cloud Monitoring の取り込み量に応じて課金されます。 アップグレード時の重複期間中は、重複したログも取り込み量としてカウントされるため、 一時的にログ取り込みコストが増加する可能性があります。 詳細は Google Cloud Observability の料金ページ を参照してください。
🌏 利用可能リージョン: Ops Agent は VM 上で動作するソフトウェアのアップデートであるため、 リージョンに依存せず、Ops Agent をサポートするすべての環境に適用されます。

🔗 関連サービス・機能

☁️ Cloud Logging

Ops Agent が収集したログの取り込み先。重複期間中はログエクスプローラーで同一内容のエントリが二重に表示される。

📊 Cloud Monitoring

Metrics Agent サービス (OpenTelemetry Collector) の本来の役割であるメトリクスの取り込み先。エージェントの稼働状況は agent.googleapis.com/agent/uptime メトリクスで確認できる。

🖥️ Compute Engine

Ops Agent の動作対象となる VM 基盤。

🔔 ログベースの指標 / アラート

重複ログにより一時的に二重カウントが発生し得るため、重複期間中の挙動に注意が必要。

📡 OpenTelemetry

新しいロギングパイプラインの処理基盤。Ops Agent は OTLP メトリクス・トレースの収集にも対応している。

🎯 まとめ

✓Ops Agent 2.72.0 で、すべてのロギングパイプラインの処理が Fluent Bit ベースの Logging Agent サービスから OpenTelemetry Collector ベースの Metrics Agent サービスに統一
✓アップグレード時には想定された動作として一定期間ログが重複するため、ログベースのアラートや取り込みコストへの影響を事前に評価し、段階的なロールアウトを計画することを推奨
✓重複が問題になる場合は experimental_otel_logging: false による一時的なロールバックが可能。ただし将来削除予定のため、恒久対応が必要な場合は Cloud カスタマーケアへ報告
