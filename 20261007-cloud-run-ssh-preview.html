⚡ Cloud Run: SSH サポート

Cloud Run Preview Serverless Security
📅 リリース日: 2026-10-07

📝 概要

Cloud Run のサービス・インスタンスへの SSH 接続機能が Preview として提供開始。 稼働中のコンテナインスタンスにセキュアでインタラクティブなシェル接続を確立し、 ファイルシステムやランタイム環境へ直接アクセスできます。本番環境のインスタンス上で、 リソース確認・設定検証・トラブルシューティングをその場で実行可能です。

セキュリティは IAP TCP forwarding (接続前の認証・認可)、 OS Login の短命 SSH 証明書 (有効期限 5 分)、 ログイン試行ごとの IAM 権限チェックの組み合わせで担保。 sshd などの Google 管理バイナリはセッション中のみコンテナにマウントされるため、 イメージへの SSH サーバー組み込みは不要です。

❌ Before: アップデート前の課題

  • 稼働中インスタンスへのシェル接続手段がなく、調査はログ・メトリクスなど間接的な手段に依存
  • ファイルシステムや実際の設定値を直接確認できず、デバッグコード追加 → 再デプロイの繰り返しが必要
  • コンテナ内部アクセスにはイメージへ SSH サーバーを自前で組み込み、セキュリティリスクを管理する必要

✅ After: アップデート後の改善

  • gcloud beta run services ssh / instances ssh でセキュアな対話シェル接続を確立
  • sshd は Google 管理・セッション中のみマウント。イメージ変更不要
  • IAP + 短命証明書 (5 分) + IAM チェックでセキュリティを担保したままデバッグ
  • インスタンス ID・リビジョン指定でピンポイント調査が可能

🔧 主要機能

1️⃣ サービス・インスタンスへの SSH 接続

→gcloud beta run services ssh SERVICE --region=REGION でサービスの稼働中インスタンスに接続
→gcloud beta run instances ssh INSTANCE --region=REGION で Cloud Run インスタンスに接続
→稼働インスタンスがない場合は SSH セッションのために新規インスタンスが自動起動 (課金対象)
→exit してもコンテナは再起動・停止されず、コンテナが生きている間は変更内容が維持される

2️⃣ 特定のインスタンス・リビジョンの指定

→--instance=INSTANCE_ID で特定インスタンスへ接続 (ID はログの labels フィールドで確認)
→--revision=REVISION で特定リビジョンへ接続
→問題が発生している個別インスタンスのピンポイント調査に有効

3️⃣ IAP + OS Login によるセキュアな接続

→IAP TCP forwarding が SSH をプロキシし、コンテナ到達前に認証・認可を実施
→context-aware access の併用で IP アドレス・デバイス属性ベースの制限も可能
→OS Login の SSH 証明書認証: gcloud CLI が有効期限 5 分の短命証明書を発行
→ログイン試行のたびに IAM 権限をチェック

4️⃣ Google 管理の SSH バイナリ

→sshd と証明書検証バイナリはセッション確立時に自動追加され、終了後に削除
→コンテナ内の既存 SSH 設定 (/etc/passwd エントリ含む) は無視され、Google 管理設定が優先
→OSS の著作権表示は /usr/share/licenses/google_ssh/THIRD_PARTY_NOTICES にマウント

5️⃣ アクセス制御・監査

→IAP の IAM ポリシーバインディングをプロジェクト・リージョン・サービス単位で設定可能
→組織ポリシーのカスタム制約で SSH 有効化自体を禁止することも可能
→Cloud OS Login API の監査ログ有効化で、SSH アクセスを Cloud Audit Logs で追跡

📋 前提条件

  • Cloud Run サービスが第 2 世代実行環境で稼働していること (デバッグツールはイメージに含めておく)
  • gcloud CLI を最新化: gcloud components update
  • 上記「必要な IAM ロール」の付与
Bash必要な API の有効化
gcloud services enable \
    run.googleapis.com \
    cloudresourcemanager.googleapis.com \
    iap.googleapis.com \
    oslogin.googleapis.com

ステップ 1: サービスで SSH を有効化

BashSSH の有効化
# 既存サービスの更新
gcloud beta run services update SERVICE_NAME --ssh

# または新規デプロイ時に有効化
gcloud beta run deploy SERVICE_NAME --image=IMAGE_URL --ssh
💡 ポイント: サービスでは明示的に SSH を有効化します。Cloud Run インスタンスでは SSH はデフォルトで有効であり、--no-ssh で無効化できます。

ステップ 2: IAP のアクセスポリシーを設定

BashIAP トンネルユーザーの許可
# 特定サービスに対して IAP トンネルユーザーを許可
gcloud beta iap tcp add-iam-policy-binding \
    --resource-type=cloud-run \
    --service=SERVICE_NAME \
    --region=REGION \
    --member='user:user@example.com' \
    --role='roles/iap.tunnelResourceAccessor'

プロジェクト単位・リージョン単位・サービス単位でアクセスポリシーを設定できます。

ステップ 3: SSH で接続

BashSSH 接続コマンド
# サービスに接続
gcloud beta run services ssh SERVICE_NAME \
    --region=REGION --project=PROJECT_ID

# 特定のインスタンスを指定して接続
gcloud beta run services ssh SERVICE_NAME \
    --region=REGION --project=PROJECT_ID --instance=INSTANCE_ID

# 特定のリビジョンを指定して接続
gcloud beta run services ssh SERVICE_NAME \
    --region=REGION --project=PROJECT_ID --revision=REVISION

# Cloud Run インスタンスに接続
gcloud beta run instances ssh INSTANCE \
    --region=REGION --project=PROJECT_ID

セッションを終了するには exit を入力します。

ステップ 4 (任意): SSH アクセスログの確認

BashCloud Audit Logs での SSH アクセス確認
gcloud logging read '
    logName="projects/PROJECT_ID/logs/cloudaudit.googleapis.com%2Fdata_access"
    AND protoPayload.serviceName="oslogin.googleapis.com"
    AND protoPayload.request.instance:"run.googleapis.com"
' --project=PROJECT_ID --freshness=1d \
  --format="table(timestamp, protoPayload.authenticationInfo.principalSubject:label=USER, protoPayload.request.instance:label=CLOUD_RUN_SERVICE)"
⚠️ 注意: SSH キー管理の監査ログを取得するには、事前に Cloud OS Login API の監査ログを有効化しておく必要があります。

💡 メリット

💼 ビジネス面

✓障害対応時間 (MTTR) の短縮: 稼働中インスタンス上で直接調査でき、「ログ追加 → 再デプロイ → 再現待ち」サイクルが不要に
✓サーバーレス移行の障壁低減: 「中に入って調査できない」という Cloud Run 採用時の懸念が解消され、VM / GKE からの移行判断がしやすくなる

🔧 技術面

✓セキュアバイデフォルト: IAP の認証・認可、OS Login の短命証明書 (5 分)、ログインごとの IAM チェックが組み込み済み。自前で SSH 基盤を構築する必要がない
✓イメージの変更不要: sshd などのバイナリは Google 管理でセッション中のみマウント
✓ピンポイント調査: インスタンス ID・リビジョン指定で特定インスタンスの問題切り分けが容易
✓監査可能性: Cloud Audit Logs で「誰がいつどのサービスに SSH したか」を追跡。組織ポリシーのカスタム制約で SSH 有効化自体の統制も可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 段階のため Pre-GA Offerings Terms が適用され、サポートが限定的な場合がある
✗対象はサービス (第 2 世代実行環境のみ) と Cloud Run インスタンスのみ。Cloud Run jobs とワーカープールは非サポート
✗SSH セッションは最大 24 時間で切断。IAP により非アクティブ 1 時間でも切断
✗SSH 使用時にイメージ内のホストキーが上書きされ、インスタンス再起動まで残る
✗Windows では PuTTY は非サポート (OpenSSH クライアントが必要)
✗ローカル OpenSSH クライアント利用時は証明書有効期限 (5 分) 切れ後に gcloud beta run services ssh の再実行が必要

🤔 考慮すべき点

  • SSH セッション中はインスタンスがアクティブに維持され、通常どおり課金が発生。稼働インスタンスがない場合は SSH のために新規インスタンスが起動される
  • コンテナへの変更はコンテナが生きている間のみ保持され、インスタンス入れ替えで失われる (永続的な変更は再デプロイで)
  • SSH 利用時はコンテナのセキュリティ強化 (非 root ユーザーでのアプリ実行など) をあわせて検討
  • 本番環境ではサービス単位の IAP ポリシーや組織ポリシーのカスタム制約での統制を推奨
  • VPC Service Controls 利用時はトンネリングが iaptunnel.googleapis.com を参照するため、境界設定の見直しが必要になる場合がある

🎯 ユースケース

🚨 ユースケース 1: 本番インシデントの即時調査

シナリオ: 本番の Cloud Run サービスで特定のインスタンスだけレイテンシが悪化。ログからは原因が特定できず、インスタンス内部のリソース状況や一時ファイルの状態を確認したい。

Bash問題インスタンスへの直接接続
# ログの labels フィールドから問題のインスタンス ID を特定し、直接接続
gcloud beta run services ssh my-api \
    --region=asia-northeast1 \
    --project=my-project \
    --instance=INSTANCE_ID

# 接続後、インスタンス内でリソースや設定を確認
cat /proc/meminfo
ls -la /tmp
env | sort

効果: 再デプロイやデバッグコードの追加なしに、問題が発生している個別インスタンスをその場で調査でき、MTTR を大幅に短縮。

🧪 ユースケース 2: 新リビジョンの設定検証

シナリオ: カナリアデプロイした新リビジョンで環境変数やマウントされたシークレット・ボリュームが意図どおり反映されているかを、トラフィックに影響を与えずに確認したい。

Bashリビジョン指定での接続
gcloud beta run services ssh my-api \
    --region=asia-northeast1 \
    --project=my-project \
    --revision=my-api-00042-abc

効果: リビジョン単位で実際のランタイム環境に入って設定を検証でき、設定ミスによる障害を本格的なトラフィック切り替え前に検出。

🔒 ユースケース 3: 統制された SSH アクセスの運用

シナリオ: セキュリティ要件の厳しい組織で、SSH デバッグを特定のサービス・特定のオンコール担当者のみに限定したい。

Bashオンコール担当者への限定的な許可
# オンコール担当者にのみ特定サービスへのトンネルアクセスを許可
gcloud beta iap tcp add-iam-policy-binding \
    --resource-type=cloud-run \
    --service=my-api \
    --region=asia-northeast1 \
    --member='group:oncall@example.com' \
    --role='roles/iap.tunnelResourceAccessor'

効果: IAM と IAP ポリシーによるきめ細かなアクセス制御と Cloud Audit Logs による監査を両立しながら、必要なメンバーにのみデバッグアクセスを提供。

💰 料金

SSH 機能自体の追加料金は発表されていませんが、以下の課金が発生します。

→SSH ではネットワーク Egress バイトに対して課金される
→SSH セッション中にアクティブに維持されるインスタンスに対して通常どおりの Cloud Run 課金が発生 (稼働インスタンスがない場合は SSH のために新規インスタンスが起動)

詳細は Cloud Run の料金ページを参照してください。

🔗 関連サービス・機能

🛡️ Identity-Aware Proxy (IAP): TCP forwarding で SSH 接続をプロキシし、認証・認可を実施。context-aware access で IP アドレスやデバイス属性に基づくアクセス制限も可能
🔑 OS Login: SSH 証明書認証によるユーザー認証を担当。有効期限 5 分の短命証明書を発行
📜 Cloud Audit Logs: OS Login API の監査ログを有効化することで、SSH アクセスの記録・追跡が可能
🔐 IAM / 組織ポリシー: ロールベースのアクセス制御に加え、カスタム制約で SSH 有効化の統制が可能
🧱 VPC Service Controls: 境界内での利用時はトンネリングが iaptunnel.googleapis.com を参照する点に注意
⚡ Cloud Run 第 2 世代実行環境: サービスで SSH を利用するための前提となる実行環境

📌 まとめ

Cloud Run への SSH サポートは、サーバーレス環境の最大の弱点であった 「稼働中インスタンスへの直接アクセスができない」という課題を、 IAP + OS Login による強固なセキュリティモデルを維持したまま解消する重要なアップデートです。

デバッグ用の再デプロイやイメージへの SSH サーバー組み込みが不要になり、本番インシデントの調査効率が大きく向上します。

推奨アクション: まずは開発・ステージング環境で gcloud beta run services ssh を試し、 本番利用時は IAP ポリシーと組織ポリシーによるアクセス統制、監査ログの有効化をあわせて設計することを推奨します。
