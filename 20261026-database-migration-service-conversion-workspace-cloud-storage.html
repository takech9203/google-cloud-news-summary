🔄 Database Migration Service
Cloud Storage からのスキーマインポートで変換ワークスペースを作成

Database Migration Service Feature 🪣 Cloud Storage
📅 リリース日: 2026-10-26

📝 概要

Database Migration Service (DMS) で、Cloud Storage バケットにアップロードしたスキーマメタデータファイルをインポートして、異種間 (heterogeneous) 移行用の変換ワークスペースを作成できるようになりました。 これにより、スキーマ変換フェーズにおいて DMS とソースデータベース間の直接的なネットワーク接続が不要になります。

Google 提供の抽出スクリプトをローカルで実行してスキーマメタデータを抽出し、その結果ファイルを Cloud Storage バケットにアップロードする方式が選択可能になりました。 ネットワーク制約の厳しいオンプレミス環境や、セキュリティポリシー上クラウドからの直接接続が許可されない環境からの移行で、スキーマ変換の評価・実施を早期に開始できます。

🛤️ 対応する 4 つの異種間移行パス

🗄️ Oracle → 🐘 Cloud SQL for PostgreSQL
🗄️ Oracle → 🐘 AlloyDB for PostgreSQL
🗄️ SQL Server → 🐘 Cloud SQL for PostgreSQL
🗄️ SQL Server → 🐘 AlloyDB for PostgreSQL

❌ Before: アップデート前の課題

  • ワークスペース作成時、DMS が接続プロファイル経由でソース DB に直接接続してスキーマを取得する必要があった
  • スキーマ変換フェーズの開始前に、ネットワーク接続性 (接続経路・ファイアウォール設定など) の確立が必須
  • ネットワーク準備が完了するまで、スキーマ変換の評価・作業に着手できなかった

✅ After: アップデート後の改善

  • 抽出スクリプトをローカル実行し Cloud Storage にアップロードするだけで、ソース DB へ接続せずにワークスペースを準備できる
  • スキーマ変換フェーズで DMS とソース DB 間の直接的なネットワーク接続が不要に
  • コンソールに加え gcloud CLI (create / seed) でも Cloud Storage からの初期化が可能に

スキーマメタデータをローカルで抽出して Cloud Storage にアップロードすることで、DMS はバケットからスキーマを読み込んで変換ワークスペースを初期化します。 スキーマ変換フェーズでは DMS からソースデータベースへの直接のネットワーク接続は不要です。

⚙️ 主要機能

🪣 1. Cloud Storage を使用したソーススキーマの初期化

→ソース接続方法として、従来の「直接データベース接続」に加えて「Cloud Storage」を選択可能
→Google 提供の Python 抽出スクリプトをローカルで実行し、生成されたスキーマメタデータ JSON ファイルをバケットにアップロード
→コンソールの「Define source and pull schema snapshot」ページでバケット内のフォルダを選択し、スキーマスナップショットを取得

⌨️ 2. gcloud CLI によるワークスペース作成と初期化 (seed)

→gcloud database-migration conversion-workspaces create で空のワークスペースを作成
→conversion-workspaces seed --gcs-path=gs://BUCKET/PREFIX/ で Cloud Storage 上のスキーマメタデータファイルをパースして読み込み

🔁 3. スキーマスナップショットの更新 (リフレッシュ)

→ソーススキーマの変更時や対象オブジェクト追加時は、抽出スクリプトを再実行し、JSON ファイルを同じフォルダに上書きアップロードしてスナップショットを更新可能
→既存のワークスペース機能 (決定論的スキーマ変換、インタラクティブ SQL エディタ、Gemini 支援変換など) はそのまま利用可能

ステップ 1: スキーマメタデータの抽出とアップロード

コンソールの変換ワークスペース作成フローで「Source connection method」に Cloud Storage を選択し、Google 提供のメタデータ抽出ユーティリティをダウンロード。 ソースデータベースに対してローカルで実行し、生成されたスキーマメタデータ JSON ファイルを Cloud Storage バケットの専用フォルダにアップロードします。

ステップ 2: 空の変換ワークスペースを作成 (gcloud の場合)

Bash 変換ワークスペースの作成 
gcloud database-migration conversion-workspaces create WORKSPACE_ID \
  --region=REGION \
  --source-database-engine=ORACLE \
  --destination-database-engine=POSTGRESQL

WORKSPACE_ID にワークスペースの識別子、REGION に作成先リージョンを指定します。

ステップ 3: Cloud Storage のスキーマファイルでワークスペースを初期化

Bash Cloud Storage からの初期化 (seed) 
gcloud database-migration conversion-workspaces seed WORKSPACE_ID \
  --region=REGION \
  --gcs-path=gs://BUCKET_NAME/PREFIX/

バケット内のスキーマメタデータファイルがパースされ、変換ワークスペースに読み込まれます。 コンソールの場合は「Pull schema snapshot and continue」をクリック後、「Select and convert objects」ページで変換対象オブジェクトを選択して変換を実行します。

⚖️ メリットと制約事項

👍 メリット

  • 移行プロジェクトの早期着手: ネットワーク接続準備 (接続経路構築、ファイアウォール調整など) の完了を待たずにスキーマ変換を開始できる
  • セキュリティ要件への適合: クラウドからソース DB への直接接続を許可できない環境でもスキーマ変換フェーズを進められる
  • CLI による自動化: create / seed コマンドでワークスペースの作成・初期化をスクリプト化できる
  • スナップショットの再取得に対応: スキーマ変更時は再抽出 + 上書きアップロードでリフレッシュ可能

⚠️ デメリット・制約事項

  • 抽出ユーティリティ自体は、実行元マシンからソース DB へのネットワーク接続が必要 (抽出作業はソース DB に到達可能な環境で行う)
  • スキーマ変更時や対象オブジェクト追加時は、抽出を再実行して同じフォルダに上書きアップロードし、スナップショットを再取得する必要がある
  • 接続が不要になるのはスキーマ変換フェーズのみ。実際のデータ移行 (移行ジョブ) では引き続きソース DB への接続が必要

💡 ユースケース

🏃 ユースケース 1: ネットワーク接続準備と並行したスキーマ変換の先行実施

シナリオ: オンプレミスの Oracle データベースを AlloyDB for PostgreSQL に移行するプロジェクトで、VPN などの接続経路の構築に時間がかかっている。

Bash 実装例 
# 1. ローカルで抽出した JSON を Cloud Storage にアップロード
gsutil cp ./schema-metadata/*.json gs://my-dms-schema-bucket/oracle-erp/

# 2. 空のワークスペースを作成し、バケットから初期化
gcloud database-migration conversion-workspaces create oracle-erp-cw \
  --region=asia-northeast1 \
  --source-database-engine=ORACLE \
  --destination-database-engine=POSTGRESQL
gcloud database-migration conversion-workspaces seed oracle-erp-cw \
  --region=asia-northeast1 \
  --gcs-path=gs://my-dms-schema-bucket/oracle-erp/

効果: ネットワーク構築と並行してスキーマ変換・互換性課題の洗い出しを進められ、移行プロジェクト全体のリードタイムを短縮できる。

🔒 ユースケース 2: 直接接続が許可されない環境からの移行アセスメント

シナリオ: セキュリティポリシーにより、クラウドサービスから社内の SQL Server への直接接続が許可されていない企業が、Cloud SQL for PostgreSQL への移行の実現性を評価したい。

効果: 社内で抽出したスキーマメタデータファイルのアップロードのみで変換ワークスペースを作成でき、変換結果 (変換可能なオブジェクト、要修正箇所) を事前に把握して移行可否を判断できる。

🔗 関連サービス・機能

🪣 Cloud Storage

抽出したスキーマメタデータ JSON ファイルの格納先。DMS サービスアカウントに roles/storage.objectViewer の付与が必要。

🐘 Cloud SQL for PostgreSQL / AlloyDB for PostgreSQL

Oracle / SQL Server からの異種間移行の移行先データベース。

🤖 Gemini (DMS の Gemini 支援変換): 変換ワークスペースで利用できる生成 AI によるスキーマ・コード変換支援機能。Cloud Storage 方式で作成したワークスペースでも利用可能です。

🎯 まとめ

DMS の異種間変換ワークスペースが Cloud Storage からのスキーマメタデータインポートに対応し、スキーマ変換フェーズにおけるソースデータベースへの直接ネットワーク接続が不要になりました。 ネットワーク制約のある環境からの Oracle / SQL Server → PostgreSQL 系移行を検討している場合は、接続経路の準備を待たずにスキーマ変換アセスメントを先行して開始することを推奨します。
