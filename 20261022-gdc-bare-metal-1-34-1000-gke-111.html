📝 概要

Google Distributed Cloud (software only) for bare metal のバージョン 1.34.1000-gke.111 がダウンロード可能になりました。 本バージョンは Kubernetes v1.34.7-gke.200 上で動作します。 リリース後、GKE On-Prem API クライアント (Google Cloud コンソール、gcloud CLI、Terraform) でインストールやアップグレードに利用可能になるまで約 7〜14 日かかります。

最大の改善点は、バンドル型 BGP ロードバランシングを使用するクラスタにおけるコントロールプレーンのフェイルオーバー動作の改善です。 従来は最大 20 秒間の API サーバー接続障害が発生する可能性がありましたが、修正後は正常なコントロールプレーンノードへのフェイルオーバーが約 4 秒で完了します。

❌ アップデート前の課題

  • BGP LB 使用クラスタで、CP ノード再起動時に最大 20 秒間 API サーバーへの接続障害が発生する可能性
  • CP 構成更新時に複数の API サーバーが同時に再起動し、コントロールプレーンが一時的に利用不能に
  • NodePool コントローラーが部分的な reconciliation 失敗時に Status.ManagedFields を早期更新し、削除されたはずの taint やラベルがノードに残留
  • メンテナンスモード移行時の BareMetalMachine コンディションに問題

✅ アップデート後の改善

  • 正常 CP ノードへのフェイルオーバーが約 4 秒で完了 (最大 20 秒 → 約 4 秒)
  • CP 構成更新時に API サーバーがローリングで再起動され、全体停止が解消
  • 削除された taint やラベルの残留問題が解消
  • 「Vulnerability fixes」記載の脆弱性を修正
💡 補足: 同日にリリースされた VMware 版 (Google Distributed Cloud for VMware) のアップデートは別レポートで扱われています。本インフォグラフィックはベアメタル版のみを対象とします。サードパーティのストレージベンダーを利用している場合は、事前認定済みストレージパートナーの一覧の確認が推奨されています。

バンドル型 BGP ロードバランシングでは、各コントロールプレーンノードが外部ピア (ToR スイッチなど) と BGP セッションを確立してコントロールプレーン VIP を広報します。 本アップデートにより、アップグレードや構成更新でノードが再起動した際の正常ノードへのフェイルオーバーが最大 20 秒から約 4 秒に短縮されました。

バンドル型 BGP ロードバランシングの構成 (参考)

クラスタ構成ファイルの loadBalancer セクションで mode: bundled、type: bgp を指定して有効化します。 各 CP ノードはインフラ内の 1 つ以上の外部ピアと BGP セッションを確立し、コントロールプレーン VIP の広報は CP ノードの IP アドレスから開始されます。

YAML バンドル型 BGP ロードバランシング構成例 
apiVersion: baremetal.cluster.gke.io/v1
kind: Cluster
spec:
  loadBalancer:
    mode: bundled
    type: bgp
    localASN: CLUSTER_ASN
    bgpPeers:
    - ip: PEER_IP
      asn: PEER_ASN
      controlPlaneNodes:   # 省略可。省略時は全 CP ノードが全ピアに接続
      - CP_NODE_IP
    ports:
      controlPlaneLBPort: 443
    vips:
      controlPlaneVIP: 10.0.0.8
      ingressVIP: 10.0.0.1

主な技術要件 (公式ドキュメントより)

✓コントロールプレーン VIP 用と Service VIP 用のピアリングセッションは分離されている
✓eBGP ピアリングのみサポート (マルチホップはデフォルトで有効)
✓高可用性のため、外部ピアは少なくとも 2 つ指定することが推奨
✓BGP ADD-PATH (RFC 7911) の受信モードでの利用と、ネットワーク側での ECMP の有効化が推奨

前提条件

✓既存の GDC (software only) for bare metal クラスタが稼働していること
✓アップグレードパスがサポートされていることを公式ドキュメント「Upgrade clusters」で確認すること

ステップ 1: クラスタ構成ファイルのバージョン更新

YAML クラスタ構成ファイル 
apiVersion: baremetal.cluster.gke.io/v1
kind: Cluster
metadata:
  name: CLUSTER_NAME
  namespace: cluster-CLUSTER_NAME
spec:
  anthosBareMetalVersion: 1.34.1000-gke.111

anthosBareMetalVersion をターゲットバージョンに更新します。ワーカーノードプールを選択的にアップグレードする場合は、NodePool スペックの anthosBareMetalVersion で制御できます (CP ノードとロードバランサーノードプールは常にアップグレード対象)。

ステップ 2: アップグレードの実行

Bash bmctl によるアップグレード 
bmctl upgrade cluster -c CLUSTER_NAME --kubeconfig=ADMIN_KUBECONFIG

詳細な手順やアップグレードの一時停止・再開機能については、公式ドキュメント「Upgrade clusters」を参照してください。

🎯 ユースケース

🔄 ユースケース 1: BGP ロードバランシングを使用する本番クラスタのアップグレード

シナリオ: ToR スイッチと BGP ピアリングするバンドル型 BGP ロードバランシング構成の HA クラスタで、定期的なバージョンアップグレードを実施。 従来は CP ノードの再起動のたびに最大 20 秒の API 接続断が発生し、CI/CD パイプラインや運用ツールの kubectl 操作がタイムアウトすることがあった。

効果: 1.34.1000-gke.111 以降はフェイルオーバーが約 4 秒で完了するため、アップグレード中の API 操作への影響が大幅に軽減される。

🛠️ ユースケース 2: コントロールプレーン構成の変更作業

シナリオ: 本番稼働中のクラスタで CP の構成パラメータを更新する必要があるが、従来は複数の API サーバーが同時に再起動し、コントロールプレーンが一時的に利用不能になるリスクがあった。

効果: 本バージョンでは API サーバーの同時再起動問題が修正されており、構成更新作業をより安全に実施できる。

📌 まとめ

GDC (software only) for bare metal 1.34.1000-gke.111 は、バンドル型 BGP ロードバランシング使用時のコントロールプレーンフェイルオーバーを最大 20 秒から約 4 秒へ大幅に改善し、構成更新時の API サーバー同時再起動問題や脆弱性も修正した、運用安定性を高めるリリースです。

BGP ロードバランシングを使用する本番クラスタの管理者は、サポートされるアップグレードパスを確認のうえ、早期の適用を検討することを推奨します。 bmctl でのアップグレードはすぐに可能ですが、GKE On-Prem API クライアント経由の場合はリリース後約 7〜14 日かかる点に注意してください。
