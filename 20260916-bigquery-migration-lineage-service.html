🔍 移行リネージサービス
Migration Lineage Service — 移行元 DWH のデータフローを自動可視化

📅 リリース日: 2026-09-16

📌 概要

BigQuery Migration Service に 移行リネージサービス (Migration Lineage Service) が Preview として追加。 移行元データベースのクエリログを解析し、データフローと接続関係をグラフとして自動可視化する。 テーブル・ビューはノード、データの流れはエッジとして表現され、カラムレベルのリネージまでドリルダウンできる。

対象は Teradata / Snowflake / Amazon Redshift などのレガシー DWH から BigQuery への移行を計画する データエンジニア・アーキテクト。移行前に依存関係を把握することで、移行の順序付けや影響範囲の特定を効率化できる。

❌ Before (アップデート前)

  • テーブル・ビュー間の依存関係の把握には、SQL スクリプトやクエリログの手動解析が必要
  • 依存関係や利用状況 (どのユーザー・パイプラインがどのテーブルを読み書きしているか) を体系的に可視化する手段が BigQuery Migration Service 内になかった

✅ After (アップデート後)

  • クエリログからデータフローと接続関係を自動的にグラフとして可視化
  • テーブルレベルに加えカラムレベルのリネージも確認可能。エッジから生成元の SQL スクリプトまで追跡できる
  • ノードごとのユーザー・パイプライン・SQL スクリプトを一覧・CSV ダウンロードし、移行計画の裏付けデータとして活用可能

🗣️ 対応 SQL 方言 (4 種類)

🟠 Amazon Redshift SQL
❄️ Snowflake SQL
🟤 Teradata SQL
☁️ GoogleSQL (BigQuery)

移行元データベースから dwh-migration-dumper ツールでメタデータとクエリログを抽出して Cloud Storage にアップロードし、 BigQuery Migration Service のリネージジョブがそれを解析してデータフローの可視化グラフを生成する。

⚡ 主要機能

📊 1. データフローの可視化 (Data Flow タブ)

  • ノード = テーブル / ビュー、エッジ = 左から右へのデータの流れとしてグラフ表示
  • スキーマごとに色分けされたバーで、同一スキーマのテーブルを視覚的に識別
  • アイコンで「ビュー」「常時全体リフレッシュ」「短命テーブル」「7 日以上書き込みのない静的テーブル」などの特性を判別
  • テーブルをクリック → カラム一覧 (名前・データ型) → カラムクリックでカラムレベルのリネージグラフへ
  • WHERE や GROUP BY 句による影響もエッジとして表示。「Show non-data edges」トグルでデータ転送のみにフィルタ可能

🔗 2. 接続・利用状況の分析 (Connections / Users / Pipelines / Code タブ)

  • Connections: 現在のノードから近い順に上流 (プロデューサー) / 下流 (コンシューマー) を一覧表示。CSV ダウンロード可能
  • Users: ノードを読み書きしたスクリプトの実行ユーザーをアクション数順に表示
  • Pipelines: ノードを読み書きしたパイプラインを表示
  • Code: ノードを読み書きした SQL スクリプトを該当箇所ハイライト付きで表示

🧬 3. エッジの詳細分析 (Details / Code タブ)

  • エッジに述語 (predicate) とカテゴリが付与され、どの操作 (集計、完全コピー、関数計算、フィルタ、JOIN キー、GROUP BY キーなど) で接続が生じたかを確認可能
  • dat (データ転送)、res (フィルタ・制限)、grp (グループ化) などの述語タイプで接続の性質を分類
  • Code タブでは、そのエッジを生成した SQL スクリプトをソース・ターゲットのハイライト付きで表示

Step 1: dwh-migration-dumper でメタデータとクエリログを抽出

移行元データベース (Redshift / Snowflake / Teradata / BigQuery) に対して実行し、ソースシステムのダンプ (ZIP) を生成する。BigQuery をソースとする例:

Bash メタデータとクエリログの抽出 
dwh-migration-dumper --connector bigquery
dwh-migration-dumper --connector bigquery-logs

Step 2: Cloud Storage にアップロード

生成された ZIP ファイルを Cloud Storage バケットにアップロードする。

Step 3: リネージをトレース (コンソール)

  1. Google Cloud コンソールで「Your migration services」ページに移動
  2. 「Trace Lineage」で「Trace translation」をクリック
  3. 「Lineage configuration」で表示名、処理ロケーション、入力ディレクトリ (ログ ZIP の Cloud Storage パス) を指定
  4. 「Trace」をクリック
⚠️ 注意: ジョブは入力サイズによっては完了までに数時間かかる場合がある。完了後、トレースされた移行リネージへのリンクが提供される。

Step 3 (代替): BigQuery Migration API でトレース

Bash API 経由でリネージジョブを作成 
curl -d "{
  \"tasks\": {
    \"TASK_NAME\": {
      \"type\": \"Experimental_Lineage\",
      \"translation_details\": {
        \"target_base_uri\": \"BUCKET_PATH\",
        \"source_target_mapping\": {
          \"source_spec\": { \"base_uri\": \"BUCKET_PATH\" }
        },
        \"target_types\": \"LINEAGE\"
      }
    }
  }
}" \
-H "Content-Type:application/json" \
-H "Authorization: Bearer TOKEN" \
-X POST https://bigquerymigration.googleapis.com/v2/projects/PROJECT_ID/locations/LOCATION/workflows

API 経由の場合、LOCATION には eu または us を指定する。 完了後、taskResult.translationTaskResult.consoleUri フィールドのリンクからリネージビューを開ける。

💡 メリット

💼 ビジネス面

✓移行計画の精度向上: 依存関係を事前に可視化し、移行の順序付けや段階的な移行計画を根拠に基づいて立案できる
✓移行リスクの低減: 見落としがちな依存関係 (WHERE / JOIN / GROUP BY による間接的な影響を含む) を把握し、移行後の障害リスクを削減

⚙️ 技術面

✓カラムレベルの追跡: テーブル単位だけでなくカラム単位のリネージを確認し、変換ロジックの影響範囲を詳細に分析
✓SQL スクリプトへの遡及: 各エッジを生成した SQL スクリプトをハイライト付きで確認し、依存関係の根拠を直接検証
✓利用状況データの取得: ノードごとのユーザー・パイプライン・接続ノードの一覧を CSV でダウンロードし、移行対象の棚卸しに活用

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 段階のため Pre-GA Offerings Terms が適用 (「現状のまま」提供、サポートが限定される場合がある)
✗処理対象は移行元データベースの最も古いログの先頭 5 GB まで
✗対応 SQL 方言は Amazon Redshift SQL / Snowflake SQL / Teradata SQL / GoogleSQL の 4 種類に限定

🤔 考慮すべき点

  • リネージジョブは入力サイズによって完了までに数時間かかる場合がある
  • ランディングページのオブジェクト総数が移行元の実際のオブジェクト数と一致するか要確認。テーブル数が想定より少ない場合はログファイルの誤りや 5 GB 制限超過の可能性があり、リネージの再生成が必要
  • サポート・フィードバックは専用窓口 (bq-edw-migration-support@google.com) への連絡が必要

効果: 依存関係の少ない末端テーブルから段階的に移行するウェーブ計画を、実際のクエリログに基づいて策定できる。

2️⃣ 未使用・静的テーブルの特定による移行スコープ削減

シナリオ: 移行対象のテーブル数を削減するため、ほとんど更新されていないテーブルや短命なテーブルを特定したい。

効果: Data Flow グラフのアイコン (7 日以上書き込みのないテーブル、短命テーブル) により静的データや一時テーブルを視覚的に識別し、移行スコープの最適化や長期保存ストレージの活用判断に役立てられる。

3️⃣ レポート改修時の影響範囲分析

シナリオ: 移行に伴い特定カラムの変換ロジックを変更する必要があり、そのカラムに依存する下流のビューやテーブルを特定したい。

効果: カラムレベルのリネージグラフとエッジの述語 (AGGREGATE、FUNCTION、EXACT_COPY など) により、対象カラムの下流への伝播を SQL スクリプトレベルまで追跡できる。

🌏 利用可能リージョン

BigQuery SQL translator と同じ処理ロケーション (東京 asia-northeast1、大阪 asia-northeast2 を含むアジア太平洋、ヨーロッパ、米国などの選択されたロケーション) で利用可能。 API でリネージジョブを実行する場合の処理ロケーションは eu または us を指定する。 詳細は SQL translator and migration lineage locations を参照。

🧩 関連サービス・機能

→BigQuery Migration Service: 移行リネージはその一機能。アセスメント、SQL 翻訳 (バッチ / インタラクティブ / API)、データ転送など移行の各フェーズを支援
→BigQuery migration assessment: 移行の実現可能性・コスト・工数を評価。リネージと組み合わせて移行計画を立案
→dwh-migration-dumper: 移行元 DB からメタデータとクエリログを抽出するオープンソース CLI ツール。リネージの入力データ生成に使用
→Cloud Storage: 抽出したログ ZIP ファイルの配置先
→Dataplex Universal Catalog データリネージ: Google Cloud 上のサービス間リネージを追跡。移行リネージサービスは移行「元」システムを対象とする点で補完関係

📝 まとめ

移行リネージサービスは、レガシー DWH から BigQuery への移行計画で最も手間のかかる「依存関係の把握」をクエリログに基づいて自動可視化する機能。 Teradata / Snowflake / Amazon Redshift からの移行を検討している場合は、まず dwh-migration-dumper でログを抽出してリネージをトレースし、 移行アセスメントと組み合わせて移行ウェーブの計画に活用することを推奨。 Preview 段階のため、ログ処理の 5 GB 制限などの制約を理解した上で利用したい。
