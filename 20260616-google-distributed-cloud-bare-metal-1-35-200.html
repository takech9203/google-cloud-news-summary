📋 概要

Google Distributed Cloud (software only) for bare metal 1.35.200-gke.66 がリリースされました。 Kubernetes v1.35.3-gke.400 上で動作し、前回パッチ (1.35.100-gke.72) から約 4 週間後のリリースです。

本リリースは etcd 関連の安定性向上、ノードプール更新時の信頼性改善、コントロールプレーン操作時のダウンタイム削減 に焦点を当てたバグ修正パッチです。

💡 注意: GKE On-Prem API クライアント (Google Cloud コンソール, gcloud CLI, Terraform) でのアップグレードが利用可能になるまで、リリース後 7 ~ 14 日かかります。bmctl による直接ダウンロードは即座に利用可能です。

🔄 Before / After 比較

❌ Before (1.35.100-gke.72)

  • ノードプール更新中の障害でテイント/ラベルが永続的に残留
  • etcd-events Pod が古いデータで無限リトライループ
  • etcd 暗号化時に API サーバーが突然終了 (最大 5 分間のタイムアウト)

  • テイント/ラベルが障害時も正常に反映
  • etcd-events データディレクトリが適切にクリア + リトライロジック追加
  • API サーバーのグレースフルシャットダウン実装
  • 証明書ローテーション待機時間が最適化

🔑 主要修正内容

✅ 修正 1: ノードプールテイント/ラベル残留問題

→ノードプール更新中の一時的/部分的な障害が発生しても、テイント/ラベルが永続的に残留しなくなった
→NodePool カスタムリソースの仕様変更がワーカーノードに確実に反映
→ノードのスケジューリング動作が意図しない状態で固定されることがなくなり、運用の信頼性が向上

📦 修正 2: etcd-events Pod 起動時データディレクトリ問題

→マシン初期化フェーズで etcd-events Pod が古いデータディレクトリを読み込む問題を解決
→障害時に /var/lib/etcd-events ディレクトリが適切にクリアされるように改善
→kubeadm-reset に一時的な API エラーに対するリトライロジックが追加
→古いメンバー ID で再参加する無限リトライループが解消

⚡ 修正 3: etcd 暗号化更新時の API サーバー安定性向上

→etcd 暗号化の有効化/更新時に API サーバーが突然終了する問題を修正
→最大 5 分間の接続タイムアウトやワークロード障害が解消
→API サーバーのグレースフルシャットダウンが適切に実行されるように

🔐 修正 4: コントロールプレーン証明書ローテーション停滞解消

→証明書ローテーション/etcd 暗号化更新時にインストーラーがノードあたり 3 分間停滞する問題を修正
→ノードが一時的に Unknown ステータスを報告する問題が解消
→503 Service Unavailable や ImagePullBackOff エラーなどの一時的なルーティング障害を防止

→脆弱性修正一覧に記載された脆弱性が修正されました

🚀 アップグレード手順

前提条件

  • ✅ 既存の Google Distributed Cloud (bare metal) 1.35.x クラスタが稼働していること

⚠️ 制限事項
  • GKE On-Prem API クライアント経由でのアップグレードはリリース後 7 ~ 14 日間利用不可

🎯 ユースケース

💻 ユースケース 1: 大規模ノードプール運用環境

シナリオ: 数十台のワーカーノードを持つクラスタで、ノードプールのテイント/ラベルを頻繁に更新する運用環境。一時的なネットワーク障害で更新が部分的に失敗すると、一部ノードにテイントが残留し、Pod が意図しないノードにスケジュールされる問題が発生していた。

YAML 
apiVersion: baremetal.cluster.gke.io/v1
kind: NodePool
metadata:
  name: gpu-pool
  namespace: cluster-prod
spec:
  clusterName: prod-cluster
  nodes:
  - address: 10.0.1.10
  - address: 10.0.1.11
  taints:
  - key: nvidia.com/gpu
    value: "true"
    effect: NoSchedule
✅ 効果: テイント/ラベルの更新が障害に対して堅牢になり、NodePool カスタムリソースの宣言的な状態が常にノードに正確に反映されるようになる。

🏢 ユースケース 2: 高可用性が求められるコントロールプレーン運用

シナリオ: 金融機関や通信事業者など、コントロールプレーンの高可用性が厳しく求められる環境。定期的な証明書ローテーションや etcd 暗号化ポリシーの更新で、API サーバーの中断やノードの Unknown ステータスが発生していた。

✅ 効果: 証明書ローテーションや暗号化更新時のダウンタイムが大幅に削減。コントロールプレーンノードが 3 台の構成で以前は合計 9 分以上の停滞が発生していたが、これが解消される。
