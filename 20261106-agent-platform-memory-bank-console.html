🧠 Memory Bank が Google Cloud コンソールで管理可能に

専用「Memory Bank」ページから、エージェントの長期記憶の作成・設定・inspect (検査) が GUI で完結

📌 概要

Memory Bank は、ユーザーとエージェントの会話から長期記憶 (メモリ) を LLM で自動生成・統合し、セッションをまたいだパーソナライズを実現するマネージドサービスです。今回のアップデートで、スタンドアロンの Memory Bank インスタンスを、デプロイ済みエージェントの「Deployments」ページとは独立した専用ページで一覧・管理できるようになりました。

コンソール上では、インスタンスの作成 (Google マネージド鍵 / Cloud KMS (CMEK) の選択を含む)、非構造化/構造化メモリの閲覧・フィルタリング・編集、リビジョン履歴の確認、Generation / Retrieval / Retention の動作設定、プロファイルスキーマの追加・編集までが GUI で完結します。さらに「Link to an agent」から、プロジェクト ID・リージョン・Memory Bank ID が事前入力された Python コードスニペットを取得し、ADK エージェントへの組み込みをすぐに始められます。

Agent Runtime にデプロイ済みのエージェント側でも、Memories タブに key:value スコープフィルタリングと「View revisions」が追加され、Service configuration から Generation / Retrieval / Retention を設定できます。コードを書かずにメモリの監査・管理ができることが、このアップデートの主要な価値です。

❌ Before (アップデート前の課題)

  • インスタンスの作成や設定 (メモリトピック、埋め込みモデル、TTL など) は google-cloud-agentplatform SDK や REST API 経由のみ
  • メモリやリビジョン履歴の確認・監査にも RetrieveMemories / ListMemoryRevisions などの API 呼び出しが必要で、非エンジニアには困難
  • スタンドアロンインスタンスをデプロイ済みエージェントと区別して一元的に把握する専用画面がなかった

✅ After (アップデート後の改善)

  • 専用の Memory Bank ページから一覧・作成・基本情報/ラベル編集・削除が GUI で完結
  • Memories タブで非構造化/構造化の切り替え、スコープ (key:value) フィルタリング、編集・削除、リビジョン履歴の確認が可能
  • Configuration タブで Generation / Retrieval / Retention / プロファイルスキーマを閲覧・編集
  • 「Link to an agent」で事前入力済みの ADK 連携用コードスニペットを取得可能

⚙️ 主要機能

1️⃣ 📑 Memory Bank の一覧と作成 (Memory Bank ページ)

  • スタンドアロンインスタンスを Deployments ページとは別の専用ページで一覧・管理
  • 基本情報やラベルの編集、インスタンスの削除が可能
  • 「Create memory bank」から、デフォルトのメモリ設定と Google マネージド暗号化 / Cloud KMS (CMEK) を選択して作成

2️⃣ 🔍 メモリの inspect とフィルタリング (Memories タブ)

  • Unstructured (非構造化) / Structured (構造化) ビューの切り替え
  • key:value のスコープペアまたはスコープチップによるフィルタリング
  • 非構造化メモリの編集・削除
  • Memory details パネルで構造化プロファイルと背後のファクトを inspect
  • 「View revisions」でメモリのリビジョン履歴を確認

3️⃣ 🛠️ インスタンスとスキーマの設定 (Configuration タブ)

  • Details: インスタンスの基本情報
  • Generation: メモリ抽出のトグル、パースペクティブ (一人称/三人称)、マネージド/カスタムトピック
  • Retrieval: 類似検索の埋め込みモデル (最初のメモリ保存前のみ変更可能)
  • Retention: メモリの有効期限とリビジョン履歴の TTL
  • Schemas: 構造化プロファイルのスキーマの追加・編集

4️⃣ 🔗 エージェント連携スニペット (Link to an agent)

  • プロジェクト ID・リージョン・Memory Bank ID が事前入力されたインストールコマンドと Python コードを取得
  • Agent Development Kit (ADK) との接続や、メモリ取得コードの雛形として利用可能

5️⃣ 🚀 Agent Runtime 側のメモリ管理強化 (Deployments ページ)

  • デプロイ済みエージェントの Memories タブに key:value スコープフィルタリングと「View revisions」を追加
  • Service configuration の Memory bank セクションから Generation / Retrieval / Retention を設定可能

🧩 Memory Bank の主な構成要素とデフォルト設定

項目詳細
メモリ生成モデル (Generation)デフォルトは gemini-3.5-flash (抽出・統合に使用)
類似検索の埋め込みモデル (Retrieval)デフォルトは text-embedding-005 (最初のメモリ保存前のみ変更可能)
リビジョン履歴 TTL (Retention)デフォルトは 365 日
マネージドメモリトピックUSER_PERSONAL_INFO / USER_PREFERENCES / KEY_CONVERSATION_DETAILS / EXPLICIT_INSTRUCTIONS (デフォルトで全て有効)。カスタムトピックの定義も可能
メモリの種類非構造化メモリ (自然言語のファクト) と構造化プロファイル (STRUCTURED_PROFILE、スキーマに沿って LLM が生成・更新)
スコープ{"user_id": "123"} のような key:value ペア。メモリはスコープ単位で分離され、スコープは生成時に決まり不変
暗号化Google マネージド暗号鍵または Cloud KMS (CMEK)。global エンドポイントでは CMEK 不可。スタンドアロンはリージョナル/マルチリージョナル (us / eu) で CMEK 可、Agent Runtime デプロイ済みはシングルリージョンのみ CMEK 対応
エンドポイントリージョナルに加え、マルチリージョナル (us / eu) とグローバル (global) をサポート

Memory Bank インスタンスの作成

コンソールの Memory Bank ページで Create memory bank をクリック。デフォルトのメモリ設定で作成され、暗号化方式として Google マネージド暗号鍵または Cloud KMS 鍵を選択できます。

2

動作の設定 (Configuration タブ)

→ Generation: メモリ抽出のオン/オフ、パースペクティブ、マネージド/カスタムトピック
→ Retrieval: 埋め込みモデル (最初のメモリを保存する前に設定)
→ Retention: メモリの有効期限とリビジョン履歴の TTL
→ Schemas: 構造化プロファイル用スキーマの追加・編集

3

エージェントとの接続 (Link to an agent)

プロジェクト・リージョン・Memory Bank ID が埋め込まれたインストールコマンドと Python コードが表示されます。SDK で接続する場合の例:

Bash SDK のインストール 
pip install "google-cloud-agentplatform>=2.0.1"
Python クライアント接続とメモリ取得 
import agentplatform

client = agentplatform.Client(
    project="PROJECT_ID",
    location="LOCATION",  # Memory Bank がサポートするリージョン、us / eu / global も指定可能
)

# メモリの取得 (スコープベース)
results = client.memory_banks.memories.retrieve(
    name=memory_bank_name,
    scope={"user_id": "123"},
)

メモリの inspect (Memories タブ)

Unstructured / Structured ビューを切り替え、key:value スコープでフィルタリング。Memory details パネルで構造化プロファイルと背後のファクトを確認し、View revisions でリビジョン履歴を追跡できます。

✨ メリット

💼 ビジネス面

  • 運用の民主化: SDK や API を使わずにメモリの状態を監査・管理でき、エンジニア以外の運用担当者やデータ管理者もメモリのガバナンスに参加できる
  • 導入までの時間短縮: 事前入力されたコードスニペットにより、Memory Bank をエージェントに組み込むまでのセットアップ時間を短縮

🔧 技術面

  • 可観測性の向上: スコープフィルタリングとリビジョン履歴の GUI 表示で、「いつ・どの会話からメモリがどう変化したか」をコードなしで追跡
  • 構成管理の一元化: Generation / Retrieval / Retention / Schemas をスタンドアロンとデプロイ済みの両方でコンソールから統一的に管理
  • セキュリティ要件への対応: 作成時に Cloud KMS (CMEK) 暗号化を選択でき、コンプライアンス要件に合わせた構成が GUI で可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Retrieval の埋め込みモデルは、最初のメモリを保存する前にのみ設定可能 (保存後は変更不可)
✗global エンドポイント (location="global") では CMEK を使用できない。Agent Runtime デプロイ済みのインスタンスはシングルリージョンの場合のみ CMEK 対応
✗コンソールで編集・削除が明示されているのは非構造化メモリで、構造化プロファイルは Memory details パネルでの inspect とリビジョン確認が中心

🤔 考慮すべき点

⚠️ 注意:
  • Memory Bank は生成 AI 機能であり、Generative AI Service Specific Terms が適用される
  • Agent Runtime の組み込み Memory Bank を使用している場合、Agent Runtime インスタンスを削除するとメモリも削除される
  • 削除したメモリのリビジョンにアクセスできるのは削除後 48 時間以内。復元が必要な場合はこの回復ウィンドウ内にロールバックが必要

🎯 ユースケース

🧹 ユースケース 1: 運用チームによるメモリの監査とクリーンアップ

シナリオ: カスタマーサポートエージェントが蓄積したユーザーメモリに、誤った情報や古い情報が含まれていないかを運用チームが定期的に確認したい。

実装例: Memories タブで user_id:<対象ユーザー> のスコープフィルタを適用し、非構造化メモリを確認。誤った内容は GUI 上で編集・削除し、「View revisions」で変更の経緯を監査する。

効果: API を呼び出すスクリプトを用意することなく、メモリの品質管理とガバナンスを運用フローに組み込める。

🗂️ ユースケース 2: 構造化プロファイルのスキーマ設計と検証

シナリオ: ユーザーの技術スタックや好みを固定スキーマの構造化プロファイルとして保持し、セッション開始時に低レイテンシで読み込みたい。

実装例: Configuration タブの Schemas からプロファイルスキーマを追加し、会話を経て生成されたプロファイルを Memory details パネルで確認。各フィールドのリビジョン履歴から、どの会話がどのフィールドを更新したかを検証する。

効果: スキーマ設計から生成結果の検証までを GUI で反復でき、プロファイル駆動のパーソナライズを短いサイクルで改善できる。

🤖 ユースケース 3: 新規エージェントへの Memory Bank 組み込み

シナリオ: 新しく開発する ADK エージェントに長期記憶を持たせたいが、セットアップコードを一から書きたくない。

実装例: Memory Bank ページでインスタンスを作成し、「Link to an agent」から自分のプロジェクト・リージョン・Memory Bank ID が入った Python コードを取得してエージェントに組み込む。

効果: 接続情報の転記ミスを防ぎつつ、ADK エージェントへのメモリ機能追加を最短手順で実現できる。
