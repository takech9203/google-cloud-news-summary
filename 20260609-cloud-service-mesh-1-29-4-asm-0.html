📋 概要

Cloud Service Mesh のインクラスター版として、バージョン 1.29.4-asm.0 がリリースされた。Istio 1.29.4 の機能を基盤とし、データプレーンには Envoy v1.37.4-dev が採用されている。GKE クラスター上でサービスメッシュを運用する組織に向けた、安定性とセキュリティの向上を目的としたパッチリリースである。

⚠️ 重要: Cloud Service Mesh 1.26 のインクラスター版がサポート終了。1.26 を使用中のユーザーは、サポートされているバージョンへの早急なアップグレードが推奨されます。

asmcli のダウンロード

Bash 
# 最新の asmcli をダウンロード
curl https://storage.googleapis.com/csm-artifacts/asm/asmcli > asmcli

# 実行権限を付与
chmod +x asmcli

Cloud Service Mesh のインストール (Google Cloud 上の GKE)

Bash 
./asmcli install \
  --project_id PROJECT_ID \
  --cluster_name CLUSTER_NAME \
  --cluster_location CLUSTER_LOCATION \
  --fleet_id FLEET_PROJECT_ID \
  --output_dir DIR_PATH \
  --enable_all \
  --ca mesh_ca

Cloud Service Mesh のインストール (Google Cloud 外)

Bash 
./asmcli install \
  --fleet_id FLEET_PROJECT_ID \
  --kubeconfig KUBECONFIG_FILE \
  --output_dir DIR_PATH \
  --platform multicloud \
  --enable_all \
  --ca mesh_ca \
  --custom_overlay OVERLAY_FILE

ワークロードの再デプロイ

Bash 
# namespace にラベルを付与
kubectl label namespace NAMESPACE istio-injection=enabled --overwrite

kubectl rollout restart deployment -n NAMESPACE

🔴 デメリット・制約事項

✗GKE Autopilot 非対応: インクラスター版は GKE Standard のみ
✗ネイティブサイドカー非対応: K8s 1.28+ のネイティブサイドカー機能利用不可
✗Proxyless gRPC の制限: LEAST_REQUEST LB と http2MaxRequests CB が利用不可
✗フリート登録必須: 全クラスターが同一フリートに登録される必要あり
✗asmcli は Linux のみ: インストールツールは Linux OS でのみ動作
✗多数の非サポート環境変数: 上記テーブル参照
💡 考慮すべき点:
  • アップグレード時にゲートウェイの個別アップグレードが必要になる場合がある
  • PILOT_DNS_JITTER_DURATION 非サポートのため DNS ジッター制御は標準動作に固定
  • topology.istio.io/locality 非サポートのため、アノテーションでのローカリティ制御は不可 (DestinationRule は利用可)
  • Telemetry CRD の customTags の formatter が使えないため、トレーシングタグのカスタムフォーマットに制約あり

🎯 ユースケース

🔒 ユースケース 1: マイクロサービスのゼロトラスト通信

シナリオ: 複数のマイクロサービスで構成された e コマースアプリケーションで、サービス間通信を暗号化し認証・認可を適用。

効果: サービス間通信が mTLS で暗号化され、認可されたサービスのみが通信可能なゼロトラスト環境を実現。

YAML 
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: ecommerce
spec:
  mtls:
    mode: STRICT
---
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: order-service-policy
  namespace: ecommerce
spec:
  selector:
    matchLabels:
      app: order-service
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/ecommerce/sa/checkout-service"]

🚀 ユースケース 2: カナリアデプロイによる安全なリリース

シナリオ: 新バージョンのサービスを段階的にロールアウトし、問題検出時に即座にロールバック。

効果: トラフィックの 10% のみを新バージョンに振り分け、メトリクスを監視しながら段階的に割合を増やすことでリリースリスクを最小化。

YAML 
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payment-service
spec:
  hosts:
  - payment-service
  http:
  - route:
    - destination:
        host: payment-service
        subset: v1
      weight: 90
    - destination:
        host: payment-service
        subset: v2
      weight: 10

🌍 ユースケース 3: マルチクラスター環境でのサービスメッシュ統合

シナリオ: 複数リージョンの GKE クラスターでサービスメッシュを統合し、リージョン障害時のフェイルオーバーを実現。

効果: フリートに登録されたクラスター間でサービスディスカバリが統合され、単一リージョン障害時に他リージョンへ自動フェイルオーバー。
