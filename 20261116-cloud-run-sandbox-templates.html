🧱 サンドボックステンプレート

独自コンテナイメージによるサンドボックス起動とインメモリボリュームの動的マウント
リリース日: 2026-11-16

📝 概要

Cloud Run のサンドボックス機能にサンドボックステンプレートが Preview として追加されました。 サンドボックスをメインコンテナとは別のコンテナとして、独自のコンテナイメージ (例: python:3.12-slim、node:22-slim、カスタム実行環境) から起動できます。 さらに、インメモリボリュームの動的マウントにより、メインコンテナとサンドボックス間でのファイル共有も可能になりました。

Cloud Run サンドボックスは、AI エージェントが生成したコードや信頼できないコードを低レイテンシかつ分離された環境で安全に実行するための機能です。 本機能はサービス、ジョブ、ワーカープール、インスタンスのすべての Cloud Run リソースタイプで利用できます。

🤖 主な対象ユーザー: AI エージェントのコード実行基盤 (Code Interpreter 型ワークロード)、マルチテナントのコード実行サービス、ブラウザ自動化などを Cloud Run 上で構築する開発者

❌ Before: アップデート前の課題

  • サンドボックスはホストコンテナのルートファイルシステムをベースに実行されるため、必要なランタイムやツール (Python、Node.js など) をすべてメインコンテナのイメージに同梱する必要があり、イメージが肥大化
  • サンドボックス専用の実行環境 (特定バージョンのランタイムやライブラリ構成) をメインアプリと独立して管理できない
  • ファイル共有はホストディレクトリのバインドマウントが中心で、複数サンドボックス間のテナントごとのファイル分離を宣言的に構成する仕組みがない

✅ After: アップデート後の改善

  • 最大 10 個の専用コンテナイメージをテンプレートとして宣言し、sandbox do/run --template で指定イメージからサンドボックスを起動可能
  • サンドボックス専用のランタイムやツールを分離でき、メインコンテナを軽量に維持
  • subPath + --template-var でサンドボックスごとに分離されたサブディレクトリのみをマウントし、他サンドボックスのファイルの閲覧・改変を防止
  • テンプレートからの起動はオンデマンドで、新しい VM のプロビジョニングや新規インスタンスの課金は発生しない

⚙️ 主要機能

1. 📦 専用コンテナイメージ (Dedicated container images)

→python:3.12-slim や busybox:latest などの個別イメージをテンプレートとして宣言可能
→メインコンテナには不要なランタイムやツールをサンドボックス側に分離し、メインコンテナを軽量化
→テンプレートは Cloud Run リソースごとに最大 10 個まで構成可能

2. ⚡ オンデマンドのサンドボックス起動 (On-demand instantiation)

→sandbox CLI (/usr/local/gcp/bin/sandbox) がテンプレートから新しいサンドボックスコンテナを起動
→新しい VM のプロビジョニングや新規インスタンス分の課金なしで、メインコンテナの CPU / メモリの範囲内で動作
→--template 省略時は従来どおりホストコンテナのファイルシステムをベースとしたローカルサンドボックスで実行

3. 🔒 サンドボックスごとに分離されたファイル共有 (Isolated file sharing)

→インメモリボリュームをメインコンテナと複数のサンドボックスで共有可能
→subPath により各サンドボックスには分離されたサブディレクトリのみをマウントし、他サンドボックスのファイルの閲覧・改変を防止
→subPath の $(VARIABLE_NAME) プレースホルダを実行時に --template-var フラグで解決し、サンドボックスごとに異なるサブディレクトリを動的に指定

4. 🧠 動的なボリュームマウント

→sandbox do / sandbox run の --mount フラグ (テンプレートモードでは type=volume,src=<ボリューム名>,dst=<パス>[,volume-subpath=<サブパス>][,readonly]) で実行時にインメモリボリュームをマウント
→信頼できないコードに共有する場合は ,readonly の付与を推奨

Cloud Run Admin API (REST) での構成例

JSON サンドボックステンプレートの構成 
{
  "launchStage": "BETA",
  "template": {
    "containers": [
      {
        "image": "IMAGE_URL",
        "sandboxLauncher": true,
        "volumeMounts": [
          { "name": "shared-vol", "mountPath": "/mnt/data" }
        ]
      }
    ],
    "sandboxes": {
      "templates": [
        {
          "name": "py12-template",
          "image": "python:3.12-slim",
          "volumeMounts": [
            {
              "name": "shared-vol",
              "mountPath": "/workspace",
              "subPath": "$(SANDBOX_DIR)"
            }
          ]
        }
      ]
    },
    "volumes": [
      { "name": "shared-vol", "emptyDir": { "medium": "MEMORY" } }
    ]
  }
}
⚠️ subPath の注意点: プレースホルダ変数名には ASCII 文字とアンダースコアのみ使用可能 (数字とハイフンは非サポート)。 また、subPath はディレクトリを自動作成しないため、sandbox do / sandbox run の実行前にメインコンテナ側で mkdir -p などにより解決後のディレクトリを作成しておく必要があります。

ステップ 1: サンドボックステンプレートとインメモリボリュームを構成する

Bash Cloud Run Admin API で PATCH 
curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -X PATCH \
  "https://run.googleapis.com/v2/projects/PROJECT_ID/locations/REGION/services/SERVICE?updateMask=launchStage,template.containers,template.sandboxes,template.volumes" \
  -d '{
    "launchStage": "BETA",
    "template": {
      "containers": [
        {
          "image": "IMAGE_URL",
          "sandboxLauncher": true,
          "volumeMounts": [{ "name": "shared-vol", "mountPath": "/mnt/data" }]
        }
      ],
      "sandboxes": {
        "templates": [
          {
            "name": "py12-template",
            "image": "python:3.12-slim",
            "volumeMounts": [
              { "name": "shared-vol", "mountPath": "/workspace", "subPath": "$(SANDBOX_DIR)" }
            ]
          }
        ]
      },
      "volumes": [{ "name": "shared-vol", "emptyDir": { "medium": "MEMORY" } }]
    }
  }'

メインコンテナ (sandboxLauncher: true)、サンドボックステンプレート、インメモリボリュームをまとめて構成します。YAML 構成でも同様の設定が可能です。

ステップ 2: テンプレートを指定してサンドボックスを実行する

Bash sandbox CLI でのテンプレート指定実行 
# エフェメラルなサンドボックスでコマンドを実行し、終了時に削除
sandbox do --template=py12-template -- /usr/bin/python3 -c "print('Hello from Python')"

# バックグラウンドのサンドボックスを起動して exec で実行
sandbox run my-python-sandbox --template=py12-template --detach -- /usr/bin/sleep 1h
sandbox exec my-python-sandbox -- /usr/bin/python3 -c "print('Hello from running sandbox')"

メインコンテナ内から sandbox CLI の --template フラグでテンプレート名を指定すると、テンプレートのイメージをベースにサンドボックスコンテナが起動します。

ステップ 3: サンドボックス専用サブディレクトリを動的にマウントする

Bash --template-var によるプレースホルダ解決 
# メインコンテナ側で共有ボリューム上にサブディレクトリを作成
mkdir -p /mnt/data/my-python-sandbox

# --template-var でプレースホルダを解決してサンドボックスを実行
sandbox do --template=py12-template \
  --template-var=SANDBOX_DIR=my-python-sandbox \
  -- /usr/bin/python3 /workspace/script.py

テンプレートの subPath に定義した $(SANDBOX_DIR) が実行時に解決され、該当のサブディレクトリのみがサンドボックスの /workspace にマウントされます。

✓イメージ管理の効率化: サンドボックス用ランタイムをメインアプリのビルドパイプラインから切り離し、ビルド・デプロイ・脆弱性管理のサイクルを分離して運用可能

✓マルチテナントの安全性向上: テナントごとにファイル空間を分離した構成を宣言的に実現し、信頼できないコード実行サービスのセキュリティリスクを低減

🔧 技術面

✓メインコンテナの軽量化: サンドボックスでのみ必要なランタイムをテンプレート側に分離し、メインコンテナの起動時間とアタックサーフェスを削減
✓実行環境の柔軟な切り替え: 最大 10 個のテンプレートで、言語やツールチェーンの異なる複数の実行環境を 1 つの Cloud Run リソース上で提供
✓低レイテンシのオンデマンド起動: テンプレートからのサンドボックス起動は同一インスタンス内で完結し、レイテンシに最適化
✓サンドボックスごとのファイル分離: subPath + --template-var により、共有ボリューム上で各サンドボックスに専用サブディレクトリのみを見せる構成を実現

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 機能であり、Pre-GA Offerings Terms が適用される (サポートが限定される場合がある)
✗サンドボックステンプレートは 1 つの Cloud Run リソースにつき最大 10 個まで
✗テンプレートごとに個別の CPU / メモリ上限は設定できず、メインコンテナの上限を共有する
✗テンプレートのボリュームマウントは、Cloud Run リソース上のインメモリボリュームのみ参照できる
✗subPath はディレクトリを自動作成しないため、事前にメインコンテナ側で作成が必要
✗subPath のプレースホルダ変数名に数字とハイフンは使用できない

🤔 考慮すべき点

→インメモリボリュームへの書き込みはコンテナのメモリ使用量としてカウントされるため、メインコンテナのメモリ上限はアプリケーション + 同時実行サンドボックス + ボリューム使用量を見込んでサイジングする
→インメモリボリュームにはサイズ上限 (sizeLimit) の設定が推奨 (未設定時は全コンテナ合計メモリの半分が自動設定され、OOM クラッシュの原因になり得る)
→外向きネットワークはデフォルトでブロック。--allow-egress を有効にすると VPC 内エンドポイントにも到達可能になるため、信頼できないコードでは慎重に判断する
→信頼できないコードにボリュームを共有する場合は readonly マウントを検討し、シークレットを含むパスは絶対にマウントしない
→環境変数はホストコンテナから継承されないため、必要な変数は --env で明示的に渡す (シークレットの受け渡しには使用しない)

🎯 ユースケース

🤖 ユースケース 1: AI エージェントのコード実行環境 (Code Interpreter)

シナリオ: LLM エージェントが生成した Python コードを安全に実行したい。エージェント本体は Node.js 製で、メインコンテナに Python ランタイムを同梱したくない。

Bash 生成コードのエフェメラル実行 
# py12-template (python:3.12-slim) を宣言しておき、
# エージェントアプリから生成コードをエフェメラルに実行
sandbox do --template=py12-template -- /usr/bin/python3 -c "GENERATED_CODE"

✅ 効果: メインコンテナは Node.js のみの軽量イメージを維持しつつ、生成コードは分離された Python 3.12 環境で実行できる。ネットワークはデフォルト遮断のため、信頼できないコードの外部通信リスクも抑制できる。

🏢 ユースケース 2: マルチテナントのコード実行サービス

シナリオ: SaaS 上で複数テナントのスクリプトを同一インスタンス内で実行するが、テナント間でファイルを見せ合いたくない。

Bash テナント専用サブディレクトリのマウント 
mkdir -p /mnt/data/tenant-a
sandbox do --template=py12-template \
  --template-var=SANDBOX_DIR=tenant-a \
  -- /usr/bin/python3 /workspace/run.py

✅ 効果: 共有インメモリボリューム上のテナント専用サブディレクトリのみが各サンドボックスにマウントされ、他テナントのファイルの閲覧・改変を防げる。

🔄 ユースケース 3: メインコンテナと実行環境のライフサイクル分離

シナリオ: データ変換ジョブで、特定バージョンのツールチェーン (例: 特定バージョンの CLI ツール群) が必要だが、ジョブ本体のイメージ更新と独立して管理したい。

✅ 効果: サンドボックステンプレートのイメージだけを差し替えることで、メインコンテナのビルド・再デプロイを最小限にしつつ実行環境を更新できる。

💰 料金

サンドボックステンプレートからのサンドボックス起動は、新しい VM のプロビジョニングや新規インスタンス分の課金を発生させず、 メインコンテナに割り当てられた CPU / メモリを共有して動作します。 課金は通常の Cloud Run の料金体系 (インスタンスに割り当てた CPU / メモリ / リクエスト) に従います。

💡 注意: インメモリボリュームへの書き込みは、書き込んだコンテナのメモリ使用量としてカウントされます。

詳細は Cloud Run 料金ページ を参照してください。

🔗 関連サービス・機能

→Cloud Run サンドボックス (code execution): 本テンプレート機能の基盤。sandbox do / run / exec CLI によるコード実行、tar アーカイブによるファイルシステムの永続化・スナップショットなどを提供

📌 まとめ

サンドボックステンプレートにより、Cloud Run サンドボックスはホストコンテナのファイルシステム依存から脱却し、 専用イメージによる実行環境の分離と、インメモリボリュームの動的マウントによる サンドボックスごとのファイル分離を宣言的に構成できるようになりました。

AI エージェントのコード実行基盤やマルチテナントのコード実行サービスを Cloud Run で構築しているチームは、 メインコンテナの軽量化とテナント分離の強化のために本機能の評価を推奨します。

⚠️ Preview 機能のため、本番適用時は Pre-GA の制約とメモリサイジング (共有 CPU / メモリとインメモリボリュームの消費) を十分に検証してください。
