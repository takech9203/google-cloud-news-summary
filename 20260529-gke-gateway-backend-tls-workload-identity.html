🔐 GKE Gateway バックエンド認証 TLS & Workload Identity 既知の問題

Google Kubernetes Engine GA Known Issue
2026-05-29

📋 概要

GKE に関する2つの重要なアップデートが発表されました。Gateway バックエンド認証 TLS のサポートにより、Gateway からバックエンド Pod や InferencePool への接続でサーバー証明書の検証が可能になりました。また、GKE 1.35 以降での Workload Identity タイムアウト問題 が報告されています。

🔄 Before / After

❌ Before

  • Gateway からバックエンド Pod への TLS 証明書検証ができなかった
  • InferencePool への通信でバックエンドの身元確認が不十分
  • バックエンド TLS 対応 GatewayClass が限定的
  • GKE 1.35 でノード起動時の認証失敗リスク

✅ After

  • BackendTLSPolicy で Gateway-バックエンド間 TLS 認証が設定可能
  • Service, InferencePool, ServiceImport 等に適用可能
  • 主要5つの GatewayClass でサポート
  • Workload Identity 問題の公式ワークアラウンド提供

⚡ 主要機能

1. バックエンド認証 TLS (Backend Authenticated TLS)

🔒 概要: GKE Gateway ロードバランサーが接続先バックエンドの身元を TLS ハンドシェイク中に検証する機能
🔑 Gateway が TLS クライアントとして動作し、信頼済み CA に対してバックエンドサーバーの証明書を検証
🔄 新しい接続が確立されるたびに検証が実行され、Gateway が信頼されたバックエンドとのみ通信することを保証

2. 対応 GatewayClass

GatewayClass ロードバランサータイプ スコープ TLS 制限
gke-l7-global-external-managed グローバル外部 ALB シングルクラスタ Service / ServiceImport のみ
gke-l7-regional-external-managed リージョン外部 ALB シングルクラスタ 全ターゲット対応
gke-l7-rilb リージョン内部 ALB シングルクラスタ 全ターゲット対応
gke-l7-global-external-managed-mc グローバル外部 ALB マルチクラスタ Service / ServiceImport のみ
gke-l7-global-regional-managed-mc グローバル/リージョン管理 マルチクラスタ 全ターゲット対応

⚠️ 既知の問題: Workload Identity タイムアウト

⚠️ 影響範囲: GKE バージョン 1.35 以降のクラスタで、Workload Identity を使用して Google Cloud API に認証するすべてのワークロード。ノード起動直後の数秒間に発生します。

症状

❌GKE メタデータサーバーへの一時的な接続タイムアウト
❌接続拒否 (Connection Refused) エラー
❌Pod 起動直後の認証失敗

根本原因

GKE メタデータサーバーが新しく作成された Pod 上でリクエストの受付を開始するまでに数秒を要するため、ノード起動直後にワークロードが認証を試行すると失敗します。ノードのスケールアップやローリングアップデート時に顕在化する可能性があります。

ワークアラウンド

1
initContainer でメタデータサーバーの準備を待機
推奨: メタデータサーバーにリトライ付きリクエストを送り、準備完了後にメインコンテナを起動
2
アプリケーションコード内でリトライロジックを実装
起動時に数秒間待機し、認証リクエストをリトライする
3
Google Cloud クライアントライブラリを最新バージョンに更新
最新ライブラリにはメタデータサーバーへの接続リトライ機能が組み込み済み

📐 技術仕様

BackendTLSPolicy フィールドリファレンス

フィールド 説明
targetRefs ポリシーを適用するバックエンドリソース (Service, InferencePool, ServiceImport, GCPInferencePoolImport)
validation.hostname Gateway が TLS ハンドシェイク時に使用するホスト名 (SNI)
validation.subjectAltNames バックエンド証明書に対して検証する SAN (Hostname / URI / SPIFFE ID)
validation.caCertificateRefs 同一 Namespace 内の ConfigMap リスト (最大8つ)。ca.crt キーに PEM CA 証明書を含む
validation.wellKnownCACertificates 自己管理 TrustConfig 使用時は System を設定
options GKE 固有オプション。networking.gke.io/backend-trust-config で外部 TrustConfig を参照

🛠️ 設定方法

前提条件

✓GKE クラスタがバックエンド TLS をサポートするバージョンで稼働
✓バックエンド Pod が HTTPS サーバーを実行
✓CA 証明書が PEM 形式で準備済み

Step 1: CA 証明書を ConfigMap として作成

YAML ConfigMap - CA 証明書 
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-backend-ca
data:
  ca.crt: |
    -----BEGIN CERTIFICATE-----
    <PEM エンコードされた CA 証明書データ>
    -----END CERTIFICATE-----

Step 2: Service をターゲットとした BackendTLSPolicy

YAML BackendTLSPolicy - Service ターゲット 
apiVersion: gateway.networking.k8s.io/v1
kind: BackendTLSPolicy
metadata:
  name: secure-backend-policy
spec:
  targetRefs:
    - group: ""
      kind: Service
      name: my-service-name
  validation:
    hostname: "backend.example.com"
    caCertificateRefs:
      - group: ""
        kind: ConfigMap
        name: my-backend-ca

Step 3: InferencePool をターゲットとした BackendTLSPolicy

YAML BackendTLSPolicy - InferencePool ターゲット 
apiVersion: gateway.networking.k8s.io/v1
kind: BackendTLSPolicy
metadata:
  name: secure-backend-policy-inferencepool
spec:
  targetRefs:
    - group: "inference.networking.k8s.io"
      kind: InferencePool
      name: my-inference-pool
  validation:
    hostname: "backend.example.com"
    caCertificateRefs:
      - group: ""
        kind: ConfigMap
        name: my-backend-ca

Step 4: ポリシーの適用状態を確認

Bash ポリシー確認コマンド 
kubectl describe backendtlspolicy secure-backend-policy

Status.Ancestors セクションに Accepted と ResolvedRefs の条件が Status: "True" で表示されることを確認します。

Workload Identity タイムアウト対策: initContainer パターン

YAML initContainer でメタデータサーバー待機 
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-initcontainer
spec:
  serviceAccountName: <KSA_NAME>
  initContainers:
    - image: gcr.io/google.com/cloudsdktool/cloud-sdk:alpine
      name: workload-identity-initcontainer
      command:
        - '/bin/bash'
        - '-c'
        - |
          curl -sS -H 'Metadata-Flavor: Google' \
            'http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/token' \
            --retry 30 --retry-connrefused --retry-max-time 60 \
            --connect-timeout 3 --fail --retry-all-errors > /dev/null \
            && exit 0 \
            || echo 'Retry limit exceeded.' >&2; exit 1
  containers:
    - image: gcr.io/your-project/your-image
      name: your-main-application-container

🎯 ユースケース

🤖 ユースケース 1: AI 推論サービスのセキュア化

シナリオ: 社内の LLM 推論サービスを GKE Inference Gateway 経由で提供し、Gateway からモデルサーバーへの通信を暗号化・認証したい。

効果: Gateway と推論サーバー間の通信が TLS で保護され、中間者攻撃のリスクを排除。モデルへのリクエストとレスポンスの機密性を確保。

🔧 ユースケース 2: Workload Identity タイムアウトへの対策

シナリオ: GKE 1.35 クラスタで Workload Identity を使用するマイクロサービスが、ノードのオートスケーリング時に認証エラーを経験。

効果: initContainer がメタデータサーバーの準備完了を確認してからメインコンテナが起動するため、認証失敗を防止。

🌐 ユースケース 3: マルチクラスタ環境でのエンドツーエンド暗号化

シナリオ: 複数リージョンに分散した GKE クラスタで、マルチクラスタ Gateway を使用してすべてのバックエンド通信を暗号化したい。

効果: マルチクラスタ環境でも一貫したバックエンド TLS ポリシーを適用し、クラスタ間通信のセキュリティを確保。

⚠️ 制限事項・注意点

制限事項:
  • gke-l7-global-external-managed と gke-l7-global-external-managed-mc では Service/ServiceImport のみサポート (InferencePool 非対応)
  • BackendTLSPolicy はターゲットリソースと同一 Namespace に配置が必要 (クロスネームスペース不可)
  • caCertificateRefs で参照可能な ConfigMap は最大 8 つ
  • wellKnownCACertificates: "System" と caCertificateRefs の同時使用は不可
  • バックエンド Pod が HTTPS サーバーを実行している必要あり
考慮すべき点:
  • GKE 1.35 以降では Workload Identity タイムアウト問題が発生する可能性あり
  • TrustConfig は Gateway と同じプロジェクト・ロケーションに作成が必要
  • 複数 Gateway から Service を使用する場合、各ロケーションに同名 TrustConfig が必要
