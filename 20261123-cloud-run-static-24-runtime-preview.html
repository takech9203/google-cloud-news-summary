Cloud Run Buildpacks Preview

⚡ Static 24 ランタイム登場

Dockerfile 不要で静的サイト / SPA を Cloud Run にデプロイ
リリース日: 2026-11-23

📋 概要

Buildpacks と Cloud Run で、静的コンテンツ配信専用の新ランタイム Static 24 (ランタイム ID: static24) が Preview として発表されました。 静的ウェブサイト、SPA、SSG の出力 (HTML / CSS / JavaScript / メディアファイル) を、 Dockerfile を書かずに、事前構成済みの Nginx ウェブサーバーでソースから直接デプロイできます。

gcloud beta run deploy --base-image=static24 を実行するだけで、 最適化された Nginx 構成 (sendfile、tcp_nopush、tcp_nodelay、オープンファイルキャッシュ) 上でコンテンツが配信され、 Nginx と OS のセキュリティパッチは自動ベースイメージ更新によって Google が管理します。

React Vue Angular Astro Hugo Jekyll Eleventy Next.js (静的エクスポート) Nuxt (静的エクスポート)

❌ Before: アップデート前の課題

  • Nginx コンテナイメージを自作する必要があり、Dockerfile と nginx.conf (ポート 8080、gzip、SPA フォールバックなど) を自前で設定
  • Nginx / OS のセキュリティパッチ適用 (再ビルド・再デプロイ) を利用者自身が継続的に実施
  • SPA ルーティング対応、セキュリティヘッダー、キャッシュ制御を個別に設計・実装

✅ After: アップデート後の改善

  • --base-image=static24 指定だけで、Dockerfile もウェブサーバー設定も不要でソースから直接デプロイ
  • 自動ベースイメージ更新により Nginx / OS のパッチは Google 管理で適用
  • SPA フォールバック、クリーン URL、gzip、nosniff ヘッダー、隠しファイルブロック、非 root 実行がゼロコンフィグ

従来は Dockerfile と Nginx 設定を自作してコンテナを運用する必要がありましたが、 Static 24 ランタイムでは静的ファイルのディレクトリを指定してデプロイするだけで、 事前構成済み Nginx による配信とパッチ管理が Google 側で提供されます。

🚀 主要機能

1️⃣ ゼロコンフィグの静的配信

  • index.html を含むディレクトリを --source で指定するだけでデプロイ可能
  • Nginx はポート 8080 (Cloud Run のデフォルトポート) で自動構成
  • クリーン URL に対応 (/about へのリクエストを拡張子なしで /about.html にマッピング)

2️⃣ SPA クライアントサイドルーティング対応

  • パスが物理ファイル・ディレクトリ・.html に一致しない場合、URL をリダイレクトせず /index.html をフォールバックとして返す
  • React Router などのクライアントサイドルーター (/dashboard/settings のようなルート) がそのまま動作

3️⃣ パフォーマンス最適化

  • sendfile、tcp_nopush、tcp_nodelay、オープンファイルキャッシュを有効化した最適化済み Nginx 構成
  • 動的 gzip 圧縮が組み込み。gzip_static on; により事前圧縮済み .gz ファイルの直接配信に対応
  • ETag / Last-Modified を自動付与し 304 Not Modified で再検証可能。デフォルトの Cache-Control: max-age は付与せず、新しいデプロイが即座に反映

4️⃣ 組み込みセキュリティ

  • X-Content-Type-Options: nosniff ヘッダーを付与
  • .git や .env などの隠しファイル・ディレクトリへのリクエストをブロック
  • コンテナは非 root ユーザーで実行

5️⃣ 2 つのデプロイ方式

  • ビルドなし (--no-build): ビルド済みファイルを static24 ベースイメージに直接アップロードし、Cloud Build をバイパス (ローカルや CI でビルド済みの場合に推奨)
  • ビルドあり: Cloud Build と Buildpacks でコンテナイメージ化し、Artifact Registry 経由でデプロイ

📂 ディレクトリ検出の仕様

Static ランタイムはサブディレクトリをスキャンしません。 index.html を含む静的ファイルは、カレントディレクトリまたは --source フラグで指定したディレクトリ (例: --source ./dist) の直下に置く必要があります。

状況挙動
dist/index.html があるのに --source . + --no-build でデプロイ❌ Nginx が /workspace ルートから配信し 403 Forbidden になる
dist/index.html があるのに --source . + ビルドありでデプロイ❌ Buildpacks がビルドステップで静的ファイルを検出できず失敗
--source ./dist を指定✅ 正常にデプロイ・配信される
⚠️ 注意: gcloud run deploy は .gitignore / .gcloudignore を尊重します。 一般的なフロントエンドリポジトリでは dist/ や build/ がデフォルトで ignore されているため、 デプロイ時にビルド成果物が除外されていないか確認が必要です。

ステップ 1: 静的ファイルを準備する

Bash SPA / SSG プロジェクトのビルド 
# 例: SPA / SSG プロジェクトをビルドして ./dist に成果物を出力
npm run build

index.html が出力ディレクトリ (例: ./dist) の直下にあることを確認します。

ステップ 2a: ビルドなしでデプロイする (ビルド済みファイル向け、推奨)

Bash --no-build で Cloud Build をバイパス 
gcloud beta run deploy SERVICE \
  --source ./dist \
  --no-build \
  --base-image=static24 \
  --project PROJECT_ID

静的ファイルが static24 ベースイメージへ直接アップロードされ、Cloud Build をバイパスして高速にデプロイされます。

ステップ 2b: ビルドありでデプロイする

Bash Cloud Build + Buildpacks 経由 
gcloud beta run deploy SERVICE \
  --source ./dist \
  --base-image=static24 \
  --project PROJECT_ID

Cloud Build と Buildpacks が静的ファイルをコンテナイメージにパッケージ化し、Artifact Registry に格納してからデプロイします。

ステップ 3 (任意): 事前圧縮アセットを用意する

Bash gzip_static 用の .gz ファイル生成 
# HTML/CSS/JS/JSON/SVG を元ファイルを残したまま gzip 圧縮 (-9 で最小サイズ)
find ./dist -type f \
  \( -name "*.html" -o -name "*.css" -o -name "*.js" \
     -o -name "*.json" -o -name "*.svg" \) \
  -exec gzip -9 --keep {} +

Accept-Encoding: gzip を含むリクエストに対して、対応する .gz ファイルが存在すれば Nginx がそれを直接配信し、リクエストごとの圧縮 CPU コストを削減できます。 元ファイルは .gz ファイルと同じ場所に残しておく必要があります。

⚖️ メリット・制約事項

💪 メリット

ビジネス面
✓運用コスト削減: Dockerfile・Nginx 設定の作成/保守、パッチ適用の運用が不要になり、アプリ開発に集中できる
✓デリバリー高速化: --no-build なら CI のビルド成果物をそのままアップロードでき、Cloud Build を経由しない分デプロイが速い
技術面
✓セキュアバイデフォルト: 非 root 実行、nosniff、隠しファイルブロック、Google 管理パッチが標準
✓SPA / SSG にそのまま対応: フォールバックやクリーン URL が設定なしで機能
✓Cloud Run の機能を活用: スケールトゥゼロ、リビジョン管理、カスタムドメインなど

🚧 制限事項

✗静的ファイルの配信のみ: カスタムのサーバーサイドコードは実行不可
✗nginx.conf のカスタム上書き不可: Nginx 構成は事前定義に固定
✗コンテナ内リバースプロキシ不可: /api/* の振り分けには外部アプリケーションロードバランサまたは Firebase Hosting の rewrites を使用
✗サブディレクトリは検出されない: index.html は --source 指定ディレクトリ直下に必要

🤔 考慮すべき点

  • Preview 段階: 本番利用は提供条件を確認のうえ判断。デプロイは gcloud beta run deploy を使用
  • .gitignore / .gcloudignore の影響: dist/ や build/ の除外に注意
  • デフォルトで Cache-Control: max-age なし: 長期キャッシュが必要なら Cloud CDN などと組み合わせを検討

💡 ユースケース

🖥️ ユースケース 1: SPA フロントエンド + Cloud Run API バックエンド

シナリオ: React 製の管理画面 (SPA) と Cloud Run 上の API サービスを単一ドメインで運用したい。

Bash 実装例 
# フロントエンド (静的) を Static 24 でデプロイ
npm run build
gcloud beta run deploy frontend \
  --source ./dist --no-build --base-image=static24

# 外部アプリケーションロードバランサで
#   /        -> frontend (static24)
#   /api/*   -> backend (Cloud Run API サービス)
# にルーティング

効果: フロントエンドの Nginx コンテナを自作・保守することなく、SPA ルーティング対応済みの配信基盤と API バックエンドを統一ドメインで運用できる。

📄 ユースケース 2: SSG サイトの CI/CD デプロイ

シナリオ: Hugo や Astro で生成するドキュメントサイト・コーポレートサイトを、CI パイプラインから毎回自動デプロイしたい。

効果: CI でビルドした public/ や dist/ を --no-build でそのままアップロードするだけでよく、Cloud Build を経由しないためデプロイが高速。ETag による再検証とデプロイ即時反映の両立で、更新頻度の高いサイトにも適する。

🎯 まとめ

Static 24 ランタイムの登場により、静的サイトや SPA を Cloud Run でホストする際の Dockerfile・Nginx 設定・パッチ運用が不要になり、 gcloud beta run deploy --base-image=static24 だけで最適化済みのセキュアな配信基盤を利用できるようになりました。

フロントエンドの配信に自前の Nginx コンテナを使っているチームは、まずステージング環境で --no-build デプロイを試し、ロードバランサと組み合わせた API ルーティング構成を検証することをおすすめします。
