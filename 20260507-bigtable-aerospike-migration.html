🗄️ Bigtable: Aerospike マイグレーションツール

Cloud Bigtable Preview
2026-05-07

📋 概要

Aerospike から Bigtable へのデータ移行を最小限またはゼロダウンタイムで実現するマイグレーションツールが Preview として公開されました。 オープンソースのアダプターライブラリ、Kafka Connect Bigtable sink コネクタ、および AerospikeBackupToBigtable Dataflow ジョブを組み合わせた構成です。

❌ Before (アップデート前)

  • 独自のカスタムツールを開発する必要があった
  • ダウンタイムなしの移行を実現するストリーミングレプリケーション機構が未提供
  • データモデルの違い (型付きビン vs. raw bytes) を橋渡しするアダプターが存在しなかった

✅ After (アップデート後)

  • 公式オープンソースツールセットでゼロダウンタイム移行が可能
  • Kafka を介した CDC でリアルタイムレプリケーションが実現
  • アダプターライブラリがデータモデル変換を自動処理
  • Dataflow ジョブによるバックアップの並列インポートが可能

🏗️ アーキテクチャ図

Aerospike から Bigtable への 2 つの移行パス: Kafka を介したリアルタイム変更ストリーミング (上部) と、asbackup + Dataflow によるバックアップインポート (下部) を並行実行してゼロダウンタイム移行を実現します。

⚡ 主要機能

🔄 変更データストリーミング (CDC)

Aerospike XDR を使用して変更を Kafka にストリーミング。Kafka Connect Bigtable sink コネクタがリアルタイムで Bigtable に書き込み。

💾 バックアップインポート

asbackup ツールで完全バックアップを作成し、Cloud Storage 経由で AerospikeBackupToBigtable Dataflow ジョブにより並列インポート。

🔀 Replicator SMT

Kafka Connect 内で動作し、Aerospike 形式のメッセージを Bigtable 互換形式に変換。アダプターライブラリがスキーママッピングを処理。

🕐 LUT ベースの整合性管理

Last Update Time (LUT) をタイムスタンプとして使用し、REPLACE_IF_NEWEST 設定により最新レコードのみを適用。

Aerospike 機能 サポート 説明
Hybrid Memory Architecture (HMA) ✅ SSD ストレージ層または In-memory 層に移行

Step 1: Aerospike XDR の設定

Aerospike Config 
xdr {
  dc aerospike-kafka-source {
    connector true
    node-address-port <aerospike_connect_host> <aerospike_connect_port>
    namespace <your_namespace_to_replicate> {
    }
  }
}

Step 2: Kafka Source コネクタの設定

YAML 
service:
  port: <port_to_run_on>
producer-props:
  bootstrap.servers:
    - <kafka_host>
format:
  mode: json
  metadata-key: metadata
routing:
  mode: static
  destination: <kafka_topic>

Step 3: バックアップの作成とアップロード

Bash 
# Aerospike バックアップの作成（複数ファイルに分割）
asbackup --namespace <namespace> --output-file-prefix <prefix> --file-limit <size_limit>

# Cloud Storage へのアップロード
gsutil -m cp <backup_files> gs://<bucket_name>/aerospike-backup/

Step 5: Kafka Connect Bigtable Sink の設定

Properties 
connector.class=com.google.cloud.kafka.connect.bigtable.BigtableSinkConnector
gcp.bigtable.project.id=<project_id>
gcp.bigtable.instance.id=<instance_id>
insert.mode=REPLACE_IF_NEWEST
topics=<kafka_topic>
💡 Step 6 カットオーバー: consumer_lag メトリクスを監視し、レプリケーションが安定した後にアプリケーショントラフィックを Bigtable に切り替えます。

📋 前提条件

✓ Aerospike Enterprise Edition (XDR が必要。Community Edition はオフライン移行のみ)
✓ Apache Kafka クラスタ (自己管理またはオンプレミス)
✓ Google Cloud プロジェクト (Bigtable、Cloud Storage、Dataflow が有効)
✓ 適切な IAM ロールとネットワーク接続の設定

タイムスタンプベースの競合解決で移行中のデータ整合性を確保。

⚠️ 制限事項・注意点

制限事項
  • UDF、HyperLogLog、GeoJSON は移行非対応 (アプリケーション側で再実装が必要)
  • Aerospike XDR は Enterprise Edition のみ (Community Edition はオフライン移行のみ)
  • セカンダリインデックスは直接移行されず再実装が必要
  • レコードキーは直接移行されず、レコードダイジェストが行キーとして使用される
  • Kafka Connect Bigtable sink は自己管理 Kafka クラスタでのみサポート (Google Cloud Managed Kafka は非対応)
考慮すべき点
  • 移行中は read-your-writes の厳密な一貫性が保証されない
  • LUT はノードのシステムクロックに基づくため、厳密に単調増加しない可能性がある
  • データ転送中チェックサムは実行されない (エンドツーエンドの整合性チェックは独自実装が必要)
  • カットオーバー前にレプリケーションが安定するまで待機する必要がある

💡 ユースケース

🎯 高トラフィック AdTech プラットフォームの移行

シナリオ: リアルタイム入札システムで Aerospike を使用しているが、運用負荷軽減とコスト最適化のためにマネージドサービスへの移行を検討。

効果: ゼロダウンタイムで移行が完了し、Bigtable のオートスケーリングにより入札リクエストのスパイクに自動対応。Enterprise Plus エディションの In-memory 層でサブミリ秒レイテンシを維持可能。

🌐 IoT データプラットフォームのクラウド移行

シナリオ: オンプレミスの Aerospike クラスタで IoT センサーデータを管理しているが、データ量増加に伴いスケーリングの限界に直面。

効果: Bigtable の自動スケーリングとペタバイト級ストレージ容量でデータ増加の懸念解消。Dataflow との統合により既存データパイプラインとの連携も容易。
