🛡️ Google SecOps / SOAR アップデート

リリース日: 2026-10-18
☁️ Google SecOps 🧩 Google SecOps SOAR Feature (GA) Announcement Deprecated

クローズ済みケースの再オープン設定・SOAR Release 6.3.103 ロールアウト・ListCaseEvents API 非推奨化

📌 概要

Google SecOps / SOAR に関する 3 件のアップデートが発表されました。中心となるのは、Source Grouping Identifier (ソースグルーピング識別子) によるアラートグルーピング時に、クローズ済みケースを再オープンするかどうかを設定できる新機能です。有効化すると、クローズ済みケースと同じ識別子の新規アラート受信時にケースが自動的に再オープンされ、アラートが直接取り込まれます。QRadar の offense ID のように外部システム側でグループ ID が付与されたアラートを扱う SOC チームにとって、外部システムとのケース状態の整合性 (パリティ) を保ちやすくなる重要な改善です。

→SOAR Release 6.3.103 が第 1 フェーズのリージョンへロールアウト開始 (Release 6.3.102 は 2026-10-17 に全リージョンで利用可能に)
→2026-10-12 付で ListCaseEvents API エンドポイントが非推奨化。代替は ListCaseEvidenceData API。SOAR API を利用した自動化・外部連携は移行対応が必要

❌ Before (アップデート前の課題)

  • グルーピングはオープン状態のアラート/ケースのみ対象。クローズ済みケースは再オープンされず、同じ識別子のアラートがクローズ後に再発すると常に新規ケースを作成
  • 同一インシデントの再燃 (例: QRadar の同一 offense のアラート再発) でも新規ケースが乱立し、調査コンテキストが分断・重複ケースの管理負荷が発生
  • 外部システムではひとつのグループ (offense) なのに、Google SecOps 側では複数ケースに分かれ、ケース状態の整合性が取りにくい
  • ケースイベント取得は ListCaseEvents API に依存。レガシー SOAR API は Chronicle API への移行対象で、パフォーマンス面の課題も指摘

✅ After (アップデート後の改善)

  • SOAR 設定で再オープンを有効化すると、同じソースグルーピング識別子の新規アラート受信時にケースが自動再オープンされ、アラートを直接取り込み
  • 重複する新規ケースの作成が削減され、第三者システムとのパリティを確保しやすい (Google はベストプラクティスとして有効化を推奨)
  • オプトイン方式のため、従来どおり新規ケースを作成する運用 (デフォルト動作) も選択可能
  • ケース証跡データ取得はリソース指向の ListCaseEvidenceData API (Chronicle API) に一本化され、移行先が明確に

⚙️ サービスアップデートの詳細 (主要機能)

1. 🔄 クローズ済みケースの再オープン設定 Feature

✓「SOAR Settings > Advanced > Alerts Grouping」の「Allow reopening closed cases when grouping by source grouping identifier」オプションで制御
✓有効時: クローズ済みケースと同じソースグルーピング識別子の新規アラート受信で、ケースを自動再オープンし、アラートを直接取り込み
✓無効時 (デフォルト): 従来どおり新規ケースを作成
✓Google は、重複ケース削減と第三者システムとのパリティ確保のため、有効化をベストプラクティスとして推奨

2. 🚀 SOAR Release 6.3.103 のロールアウト開始 Announcement

✓Release 6.3.103 が第 1 フェーズのリージョンにロールアウト中
✓ロールアウト対象リージョンは SOAR gradual release ページで確認可能
✓Release 6.3.102 は 2026-10-17 に全リージョンで利用可能に

3. ⛔ ListCaseEvents API エンドポイントの非推奨化 Deprecated

✗2026 年 10 月 12 日付で ListCaseEvents API エンドポイントが非推奨に
✓代替として ListCaseEvidenceData API エンドポイント (projects.locations.instances.cases.caseEvidenceDatas/list) を使用
✓背景: レガシー SOAR API 全体が Chronicle API へ移行中。移行期限は 2026 年 11 月 30 日から 2027 年 3 月 31 日に延長 (2026-10-12 発表)

🔬 技術仕様

📋 アラートグルーピングの主な設定 (SOAR Settings > Advanced > Alerts Grouping)

設定項目詳細
Max. alerts grouped into a case 1 ケースにグルーピングする最大アラート数 (30)。上限到達後は新規ケースを開始
Timeframe for grouping alerts グルーピングの対象時間 (0.5〜24 時間、30 分刻み)。Source Grouping Identifier によるグルーピングには適用されない
Group entities and source grouping identifiers in the same case 有効時、まず同一ソースグルーピング識別子のアラートを探し、見つからない場合は共通エンティティを持つケースを探してグルーピング
Allow reopening closed cases when grouping by source grouping identifier ✨ 今回追加。有効時、クローズ済みケースと同一識別子のアラート受信でケースを再オープン。無効時 (デフォルト) は新規ケースを作成
💡 ポイント:
  • Source Grouping Identifier によるグルーピングは sourceGroupIdentifier と maxAlertsInCase のみに基づいて行われ、タイムフレームは使用されない
  • グルーピングルールは Alert Type → Product → Data Source → Fallback Rule の階層順でマッチング

🔁 ListCaseEvents API の移行

項目詳細
非推奨エンドポイントListCaseEvents
非推奨日2026 年 10 月 12 日
移行先ListCaseEvidenceData (GET .../projects/{project}/locations/{location}/instances/{instance}/cases/{case}/caseEvidenceDatas)
関連レガシー SOAR API 全体の Chronicle API への移行期限は 2027 年 3 月 31 日に延長済み

🛠️ 設定方法

✅ 前提条件

✓Google SecOps SOAR の管理者権限 (SOAR Settings へのアクセス権) を持っていること
✓Source Grouping Identifier を使用するグルーピングルールが構成されていること (例: QRadar などグループ ID 付きアラートを送るコネクタ)

📝 手順

1

アラートグルーピング設定を開く

Google SecOps コンソールで「SOAR Settings > Advanced > Alerts Grouping」に移動します。

2

再オープン設定を有効化する

General セクションの「Allow reopening closed cases when grouping by source grouping identifier」を有効にします。有効化後、クローズ済みケースと同じソースグルーピング識別子を持つ新規アラートを受信すると、ケースが自動的に再オープンされます。

3

(API 利用者) ListCaseEvents の呼び出しを移行する

ListCaseEvents を使用しているスクリプトや連携を特定し、ListCaseEvidenceData API エンドポイントへ置き換えます。

Bash 移行後の呼び出し例 (Chronicle API / v1alpha) 
# 移行後の呼び出し例 (Chronicle API / v1alpha)
curl -s \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://chronicle.googleapis.com/v1alpha/projects/PROJECT_ID/locations/LOCATION/instances/INSTANCE_ID/cases/CASE_ID/caseEvidenceDatas"

💡 メリット

💼 ビジネス面

✓重複ケースの削減: 同一インシデントの再燃で新規ケースが乱立しなくなり、ケース管理のオーバーヘッドと SOC アナリストの調査工数を削減
✓外部システムとのパリティ: QRadar の offense など、第三者システム側のグループ単位と Google SecOps のケースが一対一で対応しやすくなり、運用の一貫性が向上

🔧 技術面

✓調査コンテキストの維持: 再オープンされたケースに過去の調査履歴と新しいアラートが集約され、インシデントの全体像を把握しやすい
✓オプトイン方式: デフォルトは従来動作 (新規ケース作成) のままで、既存の運用フローへの影響なしに段階的に導入可能
✓API の近代化: ListCaseEvidenceData はリソース指向の Chronicle API であり、レガシー API のパフォーマンス問題を回避

⚠️ デメリット・制約事項

🚧 制限事項

✗再オープン機能は Source Grouping Identifier によるグルーピングのみが対象。エンティティベースのグルーピングではクローズ済みケースは再オープンされない
✗Source Grouping Identifier によるグルーピングにはタイムフレーム設定が適用されないため、時間的に大きく離れたアラートでも同一識別子であれば同じケースに集約される
✗1 ケースあたりの最大アラート数 (30) の制限は引き続き適用される

🤔 考慮すべき点

→クローズ済みケースが自動で再オープンされるため、ケースのクローズを完了指標 (SLA・メトリクス) に使っている場合は、再オープンによる統計への影響を確認する必要がある
→再オープン時に実行されるプレイブックやワークフローの挙動を事前にテストすることを推奨
→ListCaseEvents を使用する既存の自動化・連携は、移行期限 (2027 年 3 月 31 日) を待たず早期に ListCaseEvidenceData へ移行すべき

🎯 ユースケース

ユースケース 1: QRadar offense と連動したケースライフサイクル管理

シナリオ: MSSP が QRadar コネクタで取り込んだアラートを offense ID (Source Grouping Identifier) でグルーピングしている。いったん収束してケースをクローズした後、同じ offense で新たなアラートが発生した。

Text 実装例: グルーピングルールと設定 
グルーピングルール:
  Category = Data Source
  Value = QRadar
  Group by = Source Grouping Identifier

SOAR Settings > Advanced > Alerts Grouping:
  Allow reopening closed cases when grouping by source grouping identifier = 有効

効果: QRadar 側の offense 単位と Google SecOps のケースが一致し続け、再発アラートは過去の調査履歴を持つケースに自動集約される。新規重複ケースの作成が防止され、トリアージ時間が短縮される。

ユースケース 2: ListCaseEvents からの API 移行

シナリオ: ケースのイベント情報を外部のチケットシステムに同期するスクリプトが ListCaseEvents を使用している。

効果: ListCaseEvidenceData へ移行することで、非推奨 API の停止リスクを回避し、Chronicle API ベースの安定した連携を維持できる。移行は SOAR API 全体の Chronicle API 移行 (期限: 2027 年 3 月 31 日) の一環として計画的に実施できる。
