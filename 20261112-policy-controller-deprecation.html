🛡️ Policy Controller 非推奨化の発表

2027 年 12 月 31 日にサポート終了 — Kubernetes ネイティブのポリシー機構への移行が必要
リリース日: 2026-11-12
Policy Controller GKE Enterprise Deprecated (非推奨)

📌 概要

Google Cloud は 2026 年 11 月 12 日付けで Policy Controller を非推奨 (Deprecated) とすることを発表しました。 Policy Controller は Open Policy Agent (OPA) Gatekeeper をベースとしたマネージドなアドミッションコントロールサービスで、 GKE Enterprise のフリート機能として Kubernetes クラスタ全体へのポリシー適用を提供してきましたが、 2027 年 12 月 31 日にサポート終了 (End of Support) を迎えます。

フリートで Policy Controller を運用している組織は、アドミッションポリシーを ValidatingAdmissionPolicy、Pod Security Admission、 または セルフマネージド OPA Gatekeeper へ移行する必要があります。 GKE は Policy Controller がインストールされたクラスタの 1.39 以降へのアップグレードをブロックするため、 実質的な移行期限はサポート終了日より早く訪れます。

⏮️ アップデート前 (これまで)
  • GKE Enterprise の一部として、テンプレートライブラリ、ポリシーバンドル (Pod Security バンドルなど)、監査機能を含むマネージドなポリシー適用基盤を提供
  • インストール、アップグレード、スケーリング、モニタリングは Google Cloud が管理
  • Cloud Customer Care によるサポートを提供
⏭️ アップデート後 (影響)
  • 2027 年 1 月 31 日以降、未有効のフリートホストプロジェクトでは新規有効化が不可に
  • Policy Controller がインストールされたクラスタは GKE 1.39 以降へアップグレード不可 (ブロック)
  • 2027 年 12 月 31 日にテクニカルサポート、GKE 1.38 以前でのセキュリティパッチ、コンソールダッシュボードが終了
  • ValidatingAdmissionPolicy (推奨)、Pod Security Admission、セルフマネージド OPA Gatekeeper への移行が必要
💡 ポイント: 移行は実行中のワークロードには影響しません。Policy Controller はリソースの作成・更新リクエストを評価するため、削除しても実行中のワークロードは再起動・変更されません。

🔀 移行先の選択肢

1️⃣ ValidatingAdmissionPolicy 推奨
✓リソースの作成・更新時に単一リソースを検証するポリシーに適する。Policy Controller テンプレートライブラリの大半のテンプレートはこの方式で動作
✓Kubernetes に組み込みで、GKE 1.30 以降で追加費用なしに利用可能。Cloud Customer Care が GKE の一部としてサポート
✓Rego の代わりに CEL (Common Expression Language) 式を使用し、Webhook を介さず API サーバーが直接評価
2️⃣ Pod Security Admission Pod セキュリティバンドルの推奨移行先
✓pss-baseline-v2022、pss-restricted-v2022、psp-v2022 バンドルの事前定義 Pod セキュリティ制御の移行先
✓Kubernetes に組み込みで、GKE ではデフォルトで有効。追加費用なしで Customer Care のサポート対象
3️⃣ セルフマネージド OPA Gatekeeper
✓ValidatingAdmissionPolicy で表現できないポリシー向け: クラスタ内の他リソースを参照する参照型 (referential) ポリシー、Rego を維持したいポリシー、既存リソースの監査 (audit)
✓ConstraintTemplate に CEL ルールを追加すると、Gatekeeper が API サーバー適用用の ValidatingAdmissionPolicy を生成し、監査コントローラーが既存リソースをチェック可能
✗インストール・アップグレード・運用はユーザー自身が実施。Customer Care はオープンソース Gatekeeper をサポートせず、サポートは GitHub の Gatekeeper コミュニティ経由

1
ポリシーの棚卸しとバックアップ
Bash 適用中のポリシーの確認とバックアップ 
# フリート内で Policy Controller が稼働するクラスタを特定
gcloud container fleet policycontroller describe --project=PROJECT_ID

# 各クラスタで適用中の制約を一覧表示 (適用アクションと違反数を確認)
kubectl get constraints \
  -o custom-columns='KIND:.kind,NAME:.metadata.name,ACTION:.spec.enforcementAction,VIOLATIONS:.status.totalViolations,BUNDLE:.metadata.labels.policycontroller\.gke\.io/bundleName'

# ConstraintTemplate と制約をバックアップ
kubectl get constrainttemplates -o yaml > policy-controller-templates-backup.yaml
kubectl get constraints -o yaml > policy-controller-constraints-backup.yaml
⚠️ 注意: テンプレートライブラリはデフォルトで全テンプレートをインストールし、ポリシーバンドルは dryrun で制約をインストールするため、クラスタ上のテンプレート・制約が実際に「適用しているポリシー」と一致するとは限りません。ACTION 列が空の制約はデフォルトの deny です。Policy Controller を削除するとすべての ConstraintTemplate・制約・ミューテーターが削除されるため、バックアップは必須です。
2
制約ごとに移行先へ変換・並行テスト
YAML K8sAllowedRepos 制約の ValidatingAdmissionPolicy 版 (Warn/Audit で並行稼働) 
# 例: 許可リポジトリ制約 (K8sAllowedRepos) の ValidatingAdmissionPolicy 版
# まず validationActions: ["Warn", "Audit"] で既存制約と並行稼働させて結果を比較
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: allowed-repos
spec:
  policyName: allowed-repos
  validationActions: ["Warn", "Audit"]
  matchResources:
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: ["kube-system", "gatekeeper-system"]

結果が一致したら validationActions: ["Deny"] に変更し、Policy Controller 側の制約を削除します。これにより適用のギャップなしに置き換えられます。

3
Policy Controller の削除
Bash クラスタからのアンインストールとフリート設定の削除 
# クラスタから Policy Controller をアンインストール
gcloud container fleet policycontroller disable \
  --memberships=MEMBERSHIP_NAME \
  --project=PROJECT_ID

# アンインストール完了を確認 (state が NOT_INSTALLED になるまで待機)
gcloud container fleet policycontroller describe \
  --memberships=MEMBERSHIP_NAME \
  --project=PROJECT_ID \
  --format="yaml(membershipStates)"

# 後から登録するクラスタへの自動インストールを防ぐ (フリートレベルのデフォルト設定を削除)
gcloud container fleet policycontroller enable \
  --no-fleet-default-member-config \
  --project=PROJECT_ID
⚠️ 注意: アンインストール完了前にフリート機能の削除やクラスタの登録解除を行うと、Policy Controller が管理されないまま動き続けるため注意が必要です。detach コマンドも Policy Controller を残したまま管理を停止するため使用しないでください。
4
(Gatekeeper へ移行する場合) セルフマネージド Gatekeeper のインストール
Bash gator によるテストとインストール前の確認 
# カスタム ConstraintTemplate を移行先の Gatekeeper バージョンの gator でテスト
gator test --filename=TEMPLATE_FILE

# Policy Controller 削除後、gatekeeper-system 名前空間の消滅を確認してから Helm でインストール
kubectl get namespace gatekeeper-system
💡 ヒント: Policy Controller と Gatekeeper は同じ gatekeeper-system 名前空間、同じ CustomResourceDefinition、同じ Webhook 名を使用するため、共存できません。バックアップしたリソースを再適用する際は、status フィールド、app.kubernetes.io/managed-by: anthospolicycontroller.googleapis.com ラベル、policycontroller. プレフィックスのラベル・アノテーションなどを削除してから適用します。Autopilot クラスタでは、ミューテーション Webhook のワイルドカードルールが拒否されるため、disableMutation: true などの Helm 設定が必要です。

⚖️ メリットとデメリット・制約事項

✅ メリット

💼 ビジネス面
✓追加費用なしの移行先: ValidatingAdmissionPolicy と Pod Security Admission は Kubernetes / GKE 組み込み機能であり追加費用なしで利用でき、Cloud Customer Care のサポート対象 (GKE の一部として)
✓ベンダー中立なポリシー基盤: Kubernetes 標準 API (CEL ベース) への移行により、ポリシー定義の移植性が向上
🔧 技術面
✓Webhook レス化による信頼性向上: ValidatingAdmissionPolicy は API サーバーが CEL 式を直接評価するため、Webhook のレイテンシや可用性リスクがない
✓ワークロードへの無影響: 移行・Policy Controller の削除は実行中のワークロードを再起動・変更しない (アドミッション時のみ評価されるため)

⚠️ デメリット・制約事項

🚧 制限事項
✗Policy Controller がインストールされたクラスタは GKE 1.39 以降へのアップグレードがブロックされ、移行完了まで GKE バージョンが 1.38 以前に固定される
✗2027 年 1 月 31 日以降、未有効のフリートホストプロジェクトでは新規有効化が不可
✗ValidatingAdmissionPolicy は既存リソースの監査 (audit) に対応せず、参照型ポリシーを表現できない。これらにはセルフマネージド Gatekeeper が必要
✗セルフマネージド Gatekeeper は Customer Care のサポート対象外で、インストール・アップグレード・スケーリング・監視をユーザーが担う。テンプレートライブラリとポリシーバンドルも含まれない

🤔 考慮すべき点

→ポリシー移行前に Policy Controller だけを削除しない (ポリシー適用のギャップが生じる)。重要なポリシーから先に ValidatingAdmissionPolicy へ移行し、Warn/Audit での並行稼働で結果を比較してから Deny に切り替える
→ValidatingAdmissionPolicy はデフォルトでシステム名前空間を除外しないため、kube-system などの除外設定を明示する必要がある (Standard クラスタ)
→CEL は欠落フィールドでエラーを返すため、has() マクロによる存在確認が必要。failurePolicy: Fail ではエラー時にリクエストが拒否される点も Policy Controller (フェイルオープン) と異なる
→CI パイプラインで gator や kpt による事前検証をしている場合、移行後は kubectl apply --dry-run=server によるサーバーサイドドライランへの切り替えが必要
→Gatekeeper の新しい Rego エンジンは検証が厳格で、カスタム ConstraintTemplate が拒否される場合がある。移行前に gator test での検証が必要

🎯 ユースケース

💡 ユースケース 1: テンプレートライブラリ中心の利用者が ValidatingAdmissionPolicy へ移行

シナリオ: 許可イメージリポジトリ (K8sAllowedRepos) やラベル必須などテンプレートライブラリの単一リソース検証ポリシーを deny で運用している組織。

YAML K8sAllowedRepos 相当の ValidatingAdmissionPolicy 実装例 
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: allowed-repos
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods", "pods/ephemeralcontainers"]
  variables:
    - name: repos
      expression: "['us-docker.pkg.dev/example-project/example-repo/']"
    - name: images
      expression: >-
        object.spec.containers.map(c, c.image) +
        (has(object.spec.initContainers) ? object.spec.initContainers.map(c, c.image) : []) +
        (has(object.spec.ephemeralContainers) ? object.spec.ephemeralContainers.map(c, c.image) : [])
  validations:
    - expression: >-
        variables.images.all(image, variables.repos.exists(repo, image.startsWith(repo)))
      messageExpression: >-
        'container images must come from one of these repositories: ' + variables.repos.join(', ')
      reason: Forbidden
✅ 効果: Webhook 不要・追加費用なしの Kubernetes 組み込み機能で同等のポリシーを維持しつつ、GKE 1.39 以降へのアップグレードが可能になる。
💡 ユースケース 2: Pod セキュリティバンドル利用者が Pod Security Admission へ移行

シナリオ: pss-baseline-v2022 や pss-restricted-v2022 バンドルで Pod のセキュリティ標準を適用している組織。

✅ 効果: GKE でデフォルト有効の Pod Security Admission に名前空間ラベルで同等の制御を移行でき、Customer Care のサポートを受けながら運用を継続できる。バンドルでカバーされない個別制御は ValidatingAdmissionPolicy で補完する。
💡 ユースケース 3: 参照型ポリシーや監査が必要な組織がセルフマネージド Gatekeeper へ移行

シナリオ: クラスタ内の他リソースを参照するポリシー (Ingress のホスト名重複チェックなど) や、既存リソースの違反監査を必要とする組織。

✅ 効果: Policy Controller は Gatekeeper ベースのため、ConstraintTemplate と制約は同じ API のまま移行できる。ConstraintTemplate に CEL ルールを追加すれば、API サーバー適用用の ValidatingAdmissionPolicy 生成と監査の両方を利用できる。

📝 まとめ

Policy Controller の非推奨化は、GKE Enterprise でポリシー適用を運用するすべての組織に影響する重要な発表です。 GKE 1.39 以降へのアップグレードがブロックされるため、実質的な移行期限はサポート終了日 (2027 年 12 月 31 日) より早く訪れます。

まずは kubectl get constraints で適用中のポリシーを棚卸し・バックアップし、 単一リソース検証は ValidatingAdmissionPolicy、 Pod セキュリティバンドルは Pod Security Admission、 参照型・監査が必要なポリシーはセルフマネージド Gatekeeper という方針で、 Warn/Audit での並行稼働を挟みながら計画的に移行を進めることを推奨します。
