📅 リリース日: 2026-11-03

💽 GKE: Local SSD の混在構成 (Mixed Local SSD)

1 枚の Local SSD を「エフェメラルストレージ」と「raw ブロックストレージ」に分割して同一ノードで併用

📌 概要

GKE 1.37.0-gke.3570000 以降で、ノードに接続された各 Local SSD の容量を エフェメラルストレージとraw ブロックストレージに分割して利用できるようになりました。 --ephemeral-storage-local-ssd フラグの capacity プロパティを指定すると、GKE はその容量だけをエフェメラルストレージとしてフォーマットし、残りは未フォーマットの raw ブロックデバイスとしてノードに提供します。

エフェメラル部分は各 Local SSD に均等分割されたうえで RAID-0 アレイとして結合され、標準の emptyDir ボリュームとして利用可能。 raw ブロック部分は、データベースやキャッシュのようにダイレクトディスクアクセスで性能を最大化したいワークロードが local PersistentVolume を通じて利用できます。

❌ Before: 全量どちらか一方のみ

  • Local SSD は「全量エフェメラル」(--ephemeral-storage-local-ssd) か「全量 raw ブロック」(--local-nvme-ssd-block) の二択だった
  • raw ブロックとエフェメラルの両方が必要な場合、ノードやディスクを用途別に分ける必要があり、ハードウェア使用率が低下
  • raw ブロック専用ノードプールの別運用でクラスタ管理オーバーヘッドが増加

✅ After: 1 枚の SSD を分割して併用

  • 1 台のノード上で、同じ Local SSD をエフェメラルと raw ブロックに分割して併用可能に
  • DB・キャッシュなどの高性能ワークロードが raw ブロックを使いつつ、同一ノードのサイドカーやログは標準の emptyDir を利用
  • 専用ノード・ディスクが不要になり、ハードウェア使用率の最大化と管理負荷の軽減を実現

💡 ポイント: capacity で指定した容量が各 Local SSD に均等に割り当てられて RAID-0 のエフェメラルストレージとなり、残りの容量は各ディスクごとに未フォーマットの raw ブロックデバイスとして提供されます。

⚡ 主要機能

1️⃣ capacity プロパティによる容量分割

  • --ephemeral-storage-local-ssd フラグに capacity サブフィールドを指定し、エフェメラルとしてフォーマットする容量を設定
  • 指定値は 0 より大きく、物理 Local SSD 総容量 (ディスク数 × ディスクあたり容量) 未満である必要あり
  • Local SSD 数が構成可能なマシンタイプでは count も指定。-lssd タイプなど固定数では省略可能 (GKE が VM シェイプから自動計算)

2️⃣ エフェメラルストレージ部分 (RAID-0)

  • 指定容量が各 Local SSD に均等に分割され、RAID-0 アレイとして結合
  • 標準の emptyDir ボリュームとして、通常の GKE エフェメラルボリュームと同じ方法でアクセス可能
  • GKE がシステム用に一部を予約するため、割り当て可能容量は capacity 指定値より少なくなる

3️⃣ raw ブロックストレージ部分

  • 各ディスクの残容量が、未フォーマットの個別 raw ブロックデバイスとしてノードに提供される
  • GKE はフォーマットもマウントも行わず、ユーザーが StorageClass + local PersistentVolume + PersistentVolumeClaim で手動構成
  • データベースやキャッシュなど、直接ディスクアクセスによる高性能が必要なワークロードに最適

4️⃣ ノードラベルによる識別

  • 混在構成ノードには cloud.google.com/gke-ephemeral-storage-local-ssd: "true" と cloud.google.com/gke-local-nvme-ssd-partition: "true" の両方のラベルが付与される
  • gke-local-nvme-ssd-partition ラベルは、全量 raw ブロック構成で使われる gke-local-nvme-ssd=true ラベルとは別物である点に注意

📄 raw ブロック用 StorageClass の例

PersistentVolume のバインドを Pod スケジューリングまで遅延させるため、volumeBindingMode: WaitForFirstConsumer の StorageClass 作成が推奨されています。

YAML local-storage StorageClass 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: "local-storage"
provisioner: "kubernetes.io/no-provisioner"
volumeBindingMode: "WaitForFirstConsumer"

🛠️ 設定方法

✅ 前提条件

✓GKE Standard クラスタであること (Autopilot は非対応)
✓クラスタ / ノードプールのバージョンが 1.37.0-gke.3570000 以降 (それ未満の場合はバージョンフラグで明示指定)
✓Local SSD をサポートするマシンタイプを使用 (リージョンとマシンタイプにより接続可能なディスク数が異なる)
1

混在構成のクラスタを作成

Bash クラスタ作成 (混在 Local SSD 構成) 
# Local SSD 数が構成可能なマシンタイプの場合
gcloud container clusters create CLUSTER_NAME \
    --machine-type=MACHINE_TYPE \
    --ephemeral-storage-local-ssd count=NUMBER_OF_DISKS,capacity=CAPACITY

# Local SSD 数が固定のマシンタイプ (-lssd タイプなど) の場合
gcloud container clusters create CLUSTER_NAME \
    --machine-type=MACHINE_TYPE \
    --ephemeral-storage-local-ssd capacity=CAPACITY

CAPACITY にはエフェメラルストレージとしてフォーマットする総容量 (例: 200GB) を指定。この設定はデフォルトノードプールにのみ適用されます。

2

既存クラスタにノードプールを追加

Bash ノードプール追加 
gcloud container node-pools create POOL_NAME \
    --cluster=CLUSTER_NAME \
    --machine-type=MACHINE_TYPE \
    --ephemeral-storage-local-ssd count=NUMBER_OF_DISKS,capacity=CAPACITY
3

ノードラベルの確認

Bash ラベル確認 
kubectl describe node NODE_NAME

出力に cloud.google.com/gke-ephemeral-storage-local-ssd: "true" と cloud.google.com/gke-local-nvme-ssd-partition: "true" の両方のラベルが含まれることを確認します。

4

raw ブロック容量の利用

WaitForFirstConsumer の StorageClass を作成し、local PersistentVolume をプロビジョニングして PersistentVolumeClaim で要求します。エフェメラル容量は通常の emptyDir ボリュームとしてそのまま利用できます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット
  • ハードウェア使用率の最大化: raw ブロック用に専用ノードやディスク全体を割り当てる必要がなく、購入済みの Local SSD 容量を無駄なく活用
  • 運用コストの削減: 用途別に分かれていたノードプールを統合でき、クラスタ管理オーバーヘッドが減少
🔬 技術面のメリット
  • 性能と利便性の両立: DB・キャッシュは低レイテンシ・高 IOPS を確保しつつ、サイドカーやログは標準のエフェメラルストレージを利用
  • 標準 API での利用: emptyDir と local PersistentVolume という Kubernetes 標準の仕組みで利用でき、Pod スケジューリングとの統合も可能
🚧 制限事項
  • GKE Autopilot では利用不可 (Standard のみ)
  • カスタム ComputeClass は混在構成を非サポート
  • Linux ノードイメージ (COS、Ubuntu) のみ。Windows Server 非対応
  • capacity は作成後に変更不可
  • システム予約により割り当て可能なエフェメラル容量は指定値より少ない
  • ノードメモリスワップとの併用では dedicated Local SSD プロファイルは非対応 (ブートディスク / エフェメラル Local SSD プロファイルは併用可)
⚠️ 考慮すべき点
  • 共有 I/O: RAID-0 と raw ブロックは同じ物理 SSD を共有するため、一方の高負荷 I/O が他方のスループットに影響する可能性
  • メンテナンスイベント: ストレージ最適化の Z3 / Z4D VM では、メンテナンス時にデータが保持されない可能性があり、raw ブロック利用は非推奨
  • 手動構成が必要: raw ブロック部分のデバイス構成・容量管理・中断対処はユーザーの責任
  • RAID DaemonSet の禁止: コミュニティの RAID DaemonSet (gke-daemonset-raid-disks.yaml) を混在構成ノードで実行すると、GKE 管理のエフェメラル容量が破壊される
  • 永続性や特殊な性能要件がないワークロードには、従来どおり全量エフェメラル構成を推奨

🎯 ユースケース

📊 ユースケース 1: 高性能データベースとサイドカーの同居

シナリオ: 低レイテンシ・高 IOPS が必要なセルフマネージドのデータベース (分散 KVS や検索エンジンなど) を GKE 上で運用し、同じ Pod / ノードでログ収集サイドカーやコンテナキャッシュも動かしたい。

Bash DB 用ノードプールの作成例 
gcloud container node-pools create db-pool \
    --cluster=my-cluster \
    --machine-type=n2-standard-32 \
    --ephemeral-storage-local-ssd count=4,capacity=400GB

raw ブロック部分 (残容量) を local PersistentVolume としてデータベースに割り当て、エフェメラル部分 (400GB から予約分を除いた容量) をログやキャッシュ用の emptyDir として利用。

✨ 効果: データベースはダイレクトディスクアクセスで最大性能を得ながら、専用ノードを分離せずにサイドカー用ストレージも確保でき、ノード数とコストを削減。

🚀 ユースケース 2: キャッシュ層のハードウェア使用率最適化

シナリオ: Local SSD を raw ブロックで使うインメモリキャッシュ (永続化オフロード付き) を運用しているが、ディスク全体をキャッシュに割り当てると容量が余り、エフェメラルストレージ不足で別のディスクが必要になっていた。

✨ 効果: 1 枚の Local SSD をキャッシュ用 raw ブロックとエフェメラルストレージに分割できるため、余剰容量を無駄にせず、ノードあたりのディスク枚数を削減。

💰 料金

混在構成で Local SSD 容量を分割しても、料金はエフェメラル / raw ブロックの割り当て比率に関係なく、ノードに接続された物理 Local SSD の総容量に対して課金されます。 Local SSD は GB あたり月額の従量課金で、Spot VM 向けの割引価格や、リソースベースの確約利用割引 (CUD) も利用できます。

🔗 関連サービス・機能

💽 Compute Engine Local SSD: 本機能の基盤となる物理接続型の高性能一時ストレージ。IOPS とレイテンシの特性、マシンシリーズ対応状況は Compute Engine 側の仕様に準拠
📁 GKE Local SSD エフェメラルストレージ (全量構成): 永続性や特殊な性能要件がない場合に推奨される従来構成。emptyDir によるアクセス方法は共通
🧱 GKE Local SSD raw ブロックストレージ (全量構成): ディスク全体を raw ブロックとして使う既存機能。混在構成とはノードラベルや RAID DaemonSet の扱いが異なる
💾 GKE ノードメモリスワップ: ブートディスクプロファイルまたはエフェメラル Local SSD プロファイルで混在構成と併用可能
🗄️ local PersistentVolume / StorageClass: raw ブロック部分を Pod スケジューリングと統合して利用するための Kubernetes 標準機能

📝 まとめ

GKE 1.37.0-gke.3570000 以降の Standard クラスタで、Local SSD をエフェメラルストレージと raw ブロックストレージに分割して併用できるようになり、 高性能データベース・キャッシュと通常のファイルストレージ需要を同一ノードで両立できるようになりました。

raw ブロック専用のノードプールを分けて運用しているチームは、本機能によるノード統合とハードウェア使用率改善を検討する価値があります。 導入時は capacity が作成後に変更できない点と、共有 I/O による性能影響を考慮したサイジングを行ってください。
