Google SecOps SecOps SIEM Pre-GA (パイプライン機能)

✂️ Unroll プロセッサ (イベントブレーキング)

データ処理パイプラインでバッチログを個別イベントに自動分割
📅 リリース日: 2026-08-24

📌 概要

Google SecOps のデータ処理パイプライン (Data Processing Pipelines) が、新たに Unroll プロセッサ (イベントブレーキング) をサポートしました。 複数イベントの配列 (array) やスライス (slice) を含む 1 件のログエントリを、 パース・取り込みの前段で複数の個別ログイベントへ自動分割できます。

多くの SaaS やセキュリティ製品の API は、複数イベントを 1 つの JSON 配列としてまとめて返します。 Unroll プロセッサはこの「イベント分割」をパイプライン内で完結させ、 外部ツールでの事前分割処理を不要にします。

❌ Before (アップデート前の課題)

  • バッチ形式のログを 1 件として取り込むと、パーサーが個々のイベントを正しく分解・UDM 変換できない場合があった
  • イベント分割には外部スクリプトや中間処理基盤が必要だった
  • 既存プロセッサ (Filter / Transform / Redaction) にはログを複数イベントに分割する機能がなかった

✅ After (アップデート後の改善)

  • Unroll プロセッサでログ配列を個別イベントへ自動展開 (イベントブレーキング)
  • パース・取り込みの前段で分割がパイプライン内に完結し、外部の分割処理が不要に
  • Transform プロセッサ (ParseJSON など) との組み合わせで JSON / XML / CSV / YAML のバッチログにも対応
💡 プリパース要件: Unroll プロセッサは構造化データ入力が前提で、生の文字列ペイロードには直接動作しません。 生ログはまず Transform プロセッサ (例: set(body, ParseJSON(body))) でパースし、その後段に Unroll を配置します。

イベント配列を含む生ログはまず Transform プロセッサで構造化データにパースされ、その後段の Unroll プロセッサで個別のログイベントに分割されてから、Google SecOps のパーサー (UDM 変換) と取り込みに渡されます。

⚡ 主要機能

✂️ 1. イベントブレーキング (Event Breaking)

→1 件のログエントリに含まれるイベントの配列・スライスを、複数の個別ログイベントへ自動展開
→分割はパース・取り込みの前段 (プリパース) で実行され、後段のパーサーは 1 イベント = 1 ログ として処理可能
→OpenTelemetry Collector の unrollprocessor をベースにした標準技術

🔄 2. Transform プロセッサとの連携 (プリパース要件)

→生文字列には直接動作せず、パース済み JSON / XML / CSV などの構造化された内部オブジェクト表現が必要
→生 JSON の場合は前段に OTTL 文 set(body, ParseJSON(body)) の Transform プロセッサを配置
→CSV / XML / YAML 形式も同様のプリパース用 Transform ステップで対応可能

🧩 3. 既存プロセッサ群への追加

→Filter (条件・正規表現・重大度)、Redaction (機密データのマスキング)、Transform (フィールド操作・パース) に加え Unroll が選択可能に
→Bindplane コンソールの Edit Processors ウィンドウから追加でき、Input / Output ペインで処理結果を即座にテスト・確認可能

🔧 技術仕様

Unroll プロセッサの要件と仕様

プロセッサの実行順序

データ処理コンテナのプロセッサノード内では、プロセッサは記載順に逐次実行されます。 最初のプロセッサが生ストリームデータを処理し、その出力が次のプロセッサの入力になります。 

[Stream (生ログ)]
  → Transform: set(body, ParseJSON(body))   # 生文字列を構造化データにパース
  → Unroll: イベント配列を個別ログに分割     # Event Breaking
  → (必要に応じて Filter / Redaction など)
  → Destination: Google SecOps (パース・取り込み)

🛠️ 設定方法

前提条件

✓Google SecOps Enterprise または Enterprise Plus のライセンス
✓Bindplane コンソール (バージョン 1.96.4 以降) のインストールと SecOps インスタンスとの接続設定 (または Data Pipeline API の直接利用)
✓Chronicle API 管理者ロール (roles/chronicle.admin)、または chronicle.logProcessingPipelines.* 権限を含むカスタムロール

手順

1

パイプラインとストリームの構成

Bindplane コンソールの SecOps Pipelines タブで対象パイプラインを開き (未作成なら Create SecOps Pipeline)、Pipeline configuration カードでログタイプと取り込み方法を指定したストリームを追加。

2

Transform プロセッサ (プリパース) の追加

Processor ノードから Edit Processors ウィンドウを開き、Add Processor で Transform プロセッサを追加。生 JSON の場合は次の OTTL 文を設定。

set(body, ParseJSON(body))
3

Unroll プロセッサの追加

Transform プロセッサの後段に Unroll プロセッサを追加し、分割対象の配列を指定。Input / Output ペインで受信サンプルデータに対する分割結果を即座に確認可能。

4

ロールアウト

Start rollout をクリックしてパイプラインを有効化。成功するとデータ処理コンテナのバージョン番号がインクリメントされ、以降の受信データに Unroll 処理が適用される。

🎯 メリット

💼 ビジネス面

✓取り込みデータの品質向上: バッチログが個々のイベントとして正しく UDM 化され、検索・検知ルール・ダッシュボードでのイベント単位の分析精度が向上
✓運用コストの削減: 取り込み前段の外部分割スクリプトや中間処理基盤が不要になり、構築・保守コストを削減

⚙️ 技術面

✓パイプライン内で完結: Transform → Unroll の 2 プロセッサ構成だけでバッチログを個別イベントへ展開
✓標準技術ベース: OpenTelemetry unrollprocessor がベース。OTTL による柔軟な前処理 (ParseJSON / ParseCSV / ParseXML) と組み合わせ可能
✓即時テスト可能: Bindplane の Input / Output ペインで分割結果を保存時に即座に検証

⚠️ デメリット・制約事項

制限事項

✗生文字列に直接動作しないため、必ず前段に対応する Transform プロセッサ (ParseJSON など) の配置が必要
✗1 つのパイプラインに定義できるプロセッサは最大 10 個
✗データ処理パイプライン機能自体が Pre-GA (Pre-GA Offerings Terms 対象) で、サポート限定や後方互換性のない変更の可能性あり
✗Google SecOps Enterprise / Enterprise Plus ユーザーのみ利用可能
⚠️ 考慮すべき点
  • パーサー到達前に生ログを変更するため、分割・変換が既存パーサーの UDM イベント生成に影響しないか有効化前の検証が必要
  • イベント分割により取り込みイベント数が増加するため、後段の検知ルールやダッシュボードへの影響 (イベント件数の変化) を考慮
  • Data Processing Manager のフィルタは Chronicle Ingestion API の受信後に適用されるため、Ingestion API のクォータ・上限対策としては機能しない (ソース側でのフィルタリングを推奨)

💡 ユースケース

📦 ユースケース 1: SaaS API からのバッチ JSON ログの分割取り込み

シナリオ: SaaS 製品の監査ログ API が複数イベントを 1 つの JSON 配列 (例: {"events": [ {...}, {...}, {...} ]}) として返す。 フィード経由でそのまま取り込むと 1 件のログとして扱われ、イベント単位の検知・検索ができない。

Text プロセッサ構成 (実行順) 
1. Transform: set(body, ParseJSON(body))   # 生 JSON 文字列を構造化オブジェクトへ
2. Unroll: events 配列を個別ログイベントに展開

✅ 効果: 配列内の各イベントが個別のログとして SecOps パーサーに渡り、 イベント単位で正確に UDM 変換・検知ルール評価が行われる。

🗂️ ユースケース 2: CSV / XML 形式のエクスポートログのイベント分割

シナリオ: レガシー機器やアプライアンスが複数レコードを 1 つの CSV / XML ペイロードとしてまとめて送信しており、レコード単位での分析が必要。

✅ 効果: Parse CSV / Parse XML の Transform プロセッサでプリパースした後に Unroll プロセッサを適用することで、 レコードごとの個別ログイベントとして取り込める。外部での事前分割処理が不要になる。

🔗 関連サービス・機能

🖥️ Bindplane (コンソール / エージェント): データ処理パイプラインの構成・管理 UI。Unroll プロセッサの追加・テスト・ロールアウトに使用 (バージョン 1.96.4 以降が必要)
🔌 Google SecOps Data Pipeline API (Chronicle API): Bindplane コンソールを使わずにパイプラインをプログラマティックに構成する場合に使用
🧩 UDM (Unified Data Model): 分割後の個別イベントがパーサーにより変換されるデータモデル。パイプラインによる生ログ変更は UDM 変換結果に影響するため事前検証が必要
📡 OpenTelemetry Collector (unrollprocessor / OTTL): Unroll プロセッサのベース実装。Transform プロセッサの記述には OTTL を使用
🧹 Filter / Redaction プロセッサ: 同じパイプライン内で組み合わせ可能。ノイズ除去による取り込みコスト削減や機密データのマスキングに使用

📝 まとめ

Unroll プロセッサの追加により、複数イベントを含むバッチ形式のログを Google SecOps のパイプライン内で個別イベントに分割してから取り込めるようになり、 外部の前処理基盤が不要になりました。

バッチ JSON を返す SaaS API のログや CSV / XML 形式のエクスポートログを扱っている場合は、 Transform (ParseJSON など) + Unroll の構成を検証し、 UDM 変換への影響を確認した上でパイプラインへの導入を検討することを推奨します。
