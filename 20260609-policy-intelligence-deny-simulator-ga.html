🔒 Policy Simulator for Deny Policies

Policy Intelligence GA
2026-06-09

📋 概要

Policy Intelligence の Policy Simulator for Deny Policies が一般提供 (GA) となった。IAM の拒否ポリシーを本番環境に適用する前に、その変更がプリンシパルのアクセスにどのような影響を与えるかをシミュレーションで確認できる。

過去 90 日間のアクセスログを分析し、提案された拒否ポリシーの変更が実際のアクセスパターンに与える影響をレポート。意図しないアクセスブロックを事前に検出し、重要なサービスやユーザーが誤ってロックアウトされることを防止する。

✅ GA 昇格のメリット: 本番環境での利用に対する SLA が適用され、エンタープライズグレードのセキュリティポリシー管理ワークフローに組み込むことが可能に。

🔄 Before / After 比較

❌ Before (アップデート前)

  • 拒否ポリシーの影響を事前に把握する手段がなく、本番適用後に問題が発覚
  • 大規模組織で影響範囲の特定が困難
  • テスト用にステージング環境が必要で、本番のアクセスパターンを再現できない
  • Preview 段階で SLA 未適用、ミッションクリティカルなワークフローに組み込み困難

✅ After (アップデート後)

  • 過去 90 日間の実アクセスログに基づきシミュレーション実行、影響プリンシパルを特定
  • 「適用」「修正」「キャンセル」の判断ワークフローが確立
  • GA 昇格で SLA 適用、セキュリティガバナンスパイプラインに組み込み可能
  • コンソールから直感的にシミュレーション開始・結果確認・ポリシー適用が一貫して実施可能

🏗️ アーキテクチャ図

Policy Simulator は管理者が拒否ポリシーを作成または編集した後、実際に適用する前にシミュレーションを実行し、過去のアクセスパターンに基づいて影響を分析するワークフローを提供する。

flowchart TD
    A["セキュリティ管理者"] --> B{"拒否ポリシーの作成/編集"}
    B --> C["Policy Simulator 実行"]
    C --> D["過去90日間のアクセスログ取得"]
    D --> E["アクセス試行のリプレイ"]
    E --> F{"影響分析"}
    F -->|アクセス遮断あり| G["Access Revoked レポート"]
    F -->|影響なし| H["安全確認"]
    G --> I{"判断"}
    H --> J["ポリシー適用"]
    I -->|修正| B
    I -->|適用| J
    I -->|キャンセル| K["変更取消"]
    J --> L["拒否ポリシー有効化"]

⚡ 主要機能

📊 アクセスログベースのシミュレーション

  • 過去 90 日間の組織のアクセスログを取得し分析
  • 各プリンシパルの最新アクセス試行を特定
  • 提案された拒否ポリシーに基づきリプレイ
  • 組織が 90 日未満の場合は全アクセスログを使用

📋 Access Changes レポート

  • 「Access Revoked」(アクセス遮断) として報告
  • 影響を受けるプリンシパル、リソース、権限を詳細表示
  • アクセス試行回数と最終アクセス日を表示
  • CSV 形式でのエクスポートに対応

🧪 シミュレーション管理

  • 新規ポリシー作成時 (Test policy) にシミュレーション可能
  • 既存ポリシー編集時 (Test changes) にもシミュレーション可能
  • ユーザーあたり最大 50 件の同時シミュレーション
  • 過去 14 日間のシミュレーション履歴を保持

🚀 ワンクリックポリシー適用

  • シミュレーション結果確認後「Set policy」で本番適用
  • 「Modify policy」で拒否ポリシーエディタに遷移
  • 「適用」「修正」「キャンセル」のアクション選択

⚙️ 設定方法

前提条件

必要な準備:
  1. Policy Simulator API と Identity and Access Management API が有効化されていること
  2. シミュレーション実行者に roles/iam.denyAdmin ロールが付与されていること
  3. API 有効化には roles/serviceusage.serviceUsageAdmin ロールが必要

Step 1: API の有効化

Bash 
# Policy Simulator API を有効化
gcloud services enable policysimulator.googleapis.com

✅ メリット

ビジネス面

✓運用リスクの低減: 拒否ポリシーの誤設定によるサービス障害やロックアウトを事前に防止し、ダウンタイムやインシデント対応コストを削減
✓コンプライアンス対応の効率化: ポリシー変更の影響を事前に可視化し、監査証跡の作成やガバナンスレビューの効率が向上
✓意思決定の迅速化: 定量的なシミュレーション結果に基づきポリシー変更の可否を判断、承認プロセスが短縮

技術面

✓実データに基づく検証: ステージング環境では再現できない本番のアクセスパターン (90 日分) を使用してシミュレーション
✓プロアクティブなセキュリティ管理: リアクティブ (事後対応) からプロアクティブ (事前予防) なポリシー管理への移行
✓GA レベルの信頼性: SLA 適用により CI/CD パイプラインや自動化ワークフローに安心して組み込み可能

⚠️ デメリット・制約事項

制限事項

✗Workload Identity Pool のフェデレーション ID はシミュレーション対象外
✗Credential Access Boundaries (ダウンスコープ) 使用時、トークンブローカーの権限変更影響は評価されない
✗シミュレーションのタイムアウトは 24 時間。大規模組織では時間がかかる場合あり
✗リプレイ期間は結果整合性のため、直近数日のアクセスログが反映されない場合がある (最大 15 日のずれ)
✗Workforce Identity のプリンシパル識別子を使用する拒否ルールはエラーになる

考慮すべき点

  • 90 日間使用されていない権限はシミュレーション対象外 (障害時の緊急アクセスなど)
  • シミュレーション結果はアクセスログの時点の状態を基にするため、現在とは異なる場合がある
  • 同時実行数 50 件の制限があるため、大規模自動化パイプラインでは実行計画の調整が必要

💡 ユースケース

🎯 ユースケース 1: 管理権限の集中化

シナリオ: 組織全体でカスタムロールの管理を特定のセキュリティチームに限定。全ユーザーに対して roles.create、roles.update、roles.delete を拒否し、例外としてセキュリティチームのみ許可。

JSON 
{
  "deniedPrincipals": [
    "principalSet://goog/public:all"
  ],
  "exceptionPrincipals": [
    "principalSet://goog/group/security-admins@example.com"
  ],
  "deniedPermissions": [
    "iam.googleapis.com/roles.create",
    "iam.googleapis.com/roles.delete",
    "iam.googleapis.com/roles.update"
  ]
}

効果: シミュレーションにより、セキュリティチーム以外でカスタムロールを管理しているプリンシパルを事前に特定し、移行計画を策定できる。

🎯 ユースケース 2: プロジェクト単位のアクセス制限

シナリオ: 本番プロジェクトでサービスアカウントキーの作成・削除を制限。開発チームには他プロジェクトの権限を維持させつつ、本番の鍵操作を制限。

JSON 
{
  "deniedPrincipals": [
    "principalSet://goog/group/engineering@example.com"
  ],
  "exceptionPrincipals": [
    "principalSet://goog/group/prod-ops@example.com"
  ],
  "deniedPermissions": [
    "iam.googleapis.com/serviceAccountKeys.create",
    "iam.googleapis.com/serviceAccountKeys.delete"
  ]
}

効果: 本番適用前にシミュレーションで現在サービスアカウントキーを使用している開発者を特定して事前に通知。

🎯 ユースケース 3: セキュリティポリシーの段階的展開

シナリオ: 新しいセキュリティ要件に基づき複数の拒否ポリシーを組織全体に展開。各ポリシーの影響を個別にシミュレーションし、安全に段階的に適用。

効果: 各拒否ポリシーの影響範囲を事前に把握し、影響が小さいものから順に適用することで、リスクを最小化した段階的展開が可能。
