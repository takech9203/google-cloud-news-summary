AlloyDB for PostgreSQL 🤖 AI / Gemini Preview

🛠️ AI による SQL クエリチューニング
ai.tune_sql 関数が Preview に

リリース日: 2026-11-02
Google Cloud Release Notes

📌 概要

AlloyDB for PostgreSQL で、AI を使って SQL クエリをチューニングできる ai.tune_sql 関数が Preview として利用可能になりました。google_ml_integration 拡張機能 1.6.2 以降で提供され、LLM (大規模言語モデル) がクエリ実行プラン・スキーマ・ランタイム統計を分析して最適化の推奨事項を提示します。

パフォーマンスのボトルネックを特定し、クエリ書き換え / インデックス (式・GIN・ScaNN) / 統計収集 / GUC フラグ / ANALYZE・VACUUM に関する推奨を提供。SQL チューニングの専門知識がない開発者でも、SELECT 文 1 つで専門家レベルの包括的なチューニング分析を得られます。

❌ Before (アップデート前)

  • EXPLAIN ANALYZE の出力を人間が読み解き、ボトルネックを手動で特定する必要があった
  • インデックス設計・統計収集・GUC 調整・VACUUM 戦略など、複数観点の最適化には PostgreSQL の深い専門知識が必要だった
  • 既存の Index Advisor はインデックス推奨が中心で、クエリ書き換えやパラメータチューニングまでは得られなかった

✅ After (アップデート後)

  • SELECT ai.tune_sql(...) を実行するだけで、LLM がボトルネック要約と最適化推奨を自動生成
  • クエリ書き換え、インデックス (式 / GIN / ScaNN)、ANALYZE、GUC フラグ、VACUUM まで複数領域の推奨を一度に取得
  • hypopg による仮想インデックス評価で、実際に作成せずに推奨の妥当性を評価可能

🏗️ アーキテクチャ (処理フロー)

ai.tune_sql を呼び出すと、AlloyDB がクエリの実行プランと関連スキーマを収集して Vertex AI に登録した Gemini モデルへ送信し、LLM が生成したボトルネック分析と最適化推奨を返します。

⚡ 主要機能 — 1 回の呼び出しで 6 領域の推奨

📝 クエリ要約 (Query summary)

パフォーマンスボトルネックを分析し、原因を自然言語で要約。例: 相関サブクエリ (NOT IN) によるネステッドループを特定し、アンチ結合 (NOT EXISTS) への変換を提案。

🔄 クエリ書き換え (Query rewrite)

元のクエリと等価で、より効率的なクエリへの書き換え手法を提案。

🗂️ インデックス推奨

式インデックス、GIN、ScaNN などのインデックスタイプを推奨。hypopg 拡張機能で推奨の評価・生成を実施。

📊 統計収集の推奨

実行プランに基づき、テーブルの ANALYZE と複数列に対する統計収集を推奨。

⚙️ GUC フラグチューニング

実行プランと、メモリ・バッファの使用量などのシステム情報を分析し、新しい GUC 値を推奨。

🧹 ANALYZE / VACUUM の推奨

ANALYZE / VACUUM の履歴と、ライブ・デッドタプル数に基づいてテーブルへの実行を推奨。

🚀 設定方法 (3 ステップ)

💡 前提条件: ① PostgreSQL 18 以降の AlloyDB インスタンス / ② psql または AlloyDB Studio へのアクセス / ③ Vertex AI 連携の有効化 / ④ google_ml_integration 1.6.2 以降と google_db_advisor、hypopg の有効化 (CREATE EXTENSION IF NOT EXISTS hypopg;)

ステップ 1: Gemini モデルのエンドポイントを登録

SQL グローバルモデルエンドポイントの登録例 (gemini-3.5-flash) 
CALL google_ml.create_model(
  model_id => 'gemini-3.5-flash-global',
  model_request_url => 'https://aiplatform.googleapis.com/v1/projects/PROJECT_ID/locations/global/publishers/google/models/gemini-3.5-flash:generateContent',
  model_qualified_name => 'gemini-3.5-flash',
  model_provider => 'google',
  model_type => 'llm',
  model_auth_type => 'alloydb_service_agent_iam');

→ インスタンスのリージョンでモデルが利用可能な場合は、リージョナルモデルエンドポイント (例: gemini-2.5-pro) も登録できます。

ステップ 2: SQL チューニングを有効化

SQL セッション単位での有効化 
SET google_db_advisor.llm_model_id = 'gemini-3.5-flash-global';
SET google_db_advisor.enable_ai_tune_sql = on;

→ SET は現在のセッションのみ有効。永続化するには ALTER DATABASE データベース名 SET フラグ名 = 値; を両フラグに実行するか、インスタンスのデータベースフラグとして構成します。

ステップ 3: ai.tune_sql を実行

SQL AI チューニングの実行 
SELECT ai.tune_sql(query => 'SQL_QUERY', explain_analyze => TRUE);

→ 出力には、標準のクエリプランに続いて、クエリ要約、書き換え提案、統計収集・GUC フラグ・VACUUM に関する AI 生成の推奨事項が表示されます。

⚖️ メリットと制約事項

👍 メリット

✓チューニング工数の削減: 専門家が手動で行っていた実行プラン分析と最適化検討を自動化し、解決までの時間を短縮
✓専門知識の民主化: PostgreSQL チューニングの深い知識がない開発者でも専門家レベルの推奨を取得
✓多面的な推奨: 書き換え・インデックス・統計・GUC・VACUUM を単一ツールでカバー
✓実行プランに基づく精度: explain_analyze => TRUE で実際の実行プランを取得し、より正確な推奨を実現
✓AI 向けインデックスにも対応: ScaNN インデックスの推奨で、ベクトル検索ワークロードの最適化にも活用可能

⚠️ 制限事項・考慮点

✗プリペアド / パラメータ化ステートメント: クエリ書き換え推奨は非対応 (その他の推奨は提供)。$1 などのプレースホルダーは代表的なリテラル値に置換が必要
✗explain_analyze = TRUE では読み取り専用 SELECT のみ: INSERT / UPDATE / DELETE / SELECT INTO / SELECT FOR UPDATE はエラー
✗Preview ステータス: Pre-GA Offerings Terms が適用され、サポートが限定される場合あり
✗生成時間: 推奨の生成には 2〜4 分程度かかる
✗実行コスト: デフォルトではクエリが実際に実行されるため、重いクエリは注意 (FALSE で EXPLAIN のみに変更可能)
⚠️ 注意: 推奨事項は LLM の支援により生成されるため不正確な内容が含まれる可能性があり、適用前に独立した検証が必要です (出力にもその旨の注記が表示されます)。

🎯 ユースケース

1️⃣ スロークエリのボトルネック特定と書き換え

シナリオ: Query Insights で特定したスロークエリ (相関サブクエリを含む NOT IN 条件) の原因を調査し、最適化したい。

SQL 実装例 
SELECT ai.tune_sql(
  'SELECT * FROM store_sales
   WHERE ss_customer_sk NOT IN (
     SELECT sr_customer_sk FROM store_returns
     WHERE sr_item_sk = ss_item_sk)');

効果: 公式ドキュメントの例では、約 288 万回のインデックススキャンを伴うネステッドループ実行 (103 秒超) がボトルネックと特定され、NOT EXISTS (アンチ結合) への変換により Hash Anti Join を使って大幅に実行時間を削減できるという推奨が得られます。

2️⃣ インデックス・統計・VACUUM を含む包括的なチューニング

シナリオ: 複雑な分析クエリに対して、インデックス追加だけでなく統計収集やテーブルメンテナンスまで含めた最適化方針を検討したい。

効果: 単一の ai.tune_sql 呼び出しで、式 / GIN / ScaNN インデックスの推奨、複数列統計の ANALYZE 推奨、GUC フラグの調整案、ライブ / デッドタプル数に基づく VACUUM 推奨を一括で取得でき、チューニング方針の検討を効率化できます。

🔗 関連サービス・機能

🤖 Vertex AI

ai.tune_sql が分析に使用する Gemini モデルのエンドポイントを提供。AlloyDB の Vertex AI 連携の有効化が前提。

🧩 google_ml_integration 拡張機能

AlloyDB から Vertex AI のモデルを呼び出すための拡張機能。バージョン 1.6.2 以降で ai.tune_sql を提供。

🗂️ AlloyDB Index Advisor (google_db_advisor)

既存のインデックス推奨機能。ai.tune_sql は同じ拡張機能群と関連フラグを利用。

🧪 hypopg 拡張機能

仮想 (hypothetical) インデックスの評価に使用され、インデックス推奨の評価・生成を支える。

🔍 Query Insights / pg_stat_statements

チューニング対象のクエリ特定に併用。プレースホルダー付きクエリはリテラル値に置換してから ai.tune_sql に渡す。

🖥️ AlloyDB Studio

psql クライアントの代わりに、ブラウザから ai.tune_sql を実行可能。

✅ まとめ

AlloyDB の ai.tune_sql は、LLM を活用してクエリ書き換えからインデックス、統計、GUC フラグ、VACUUM まで包括的なチューニング推奨を提供する Preview 機能です。

PostgreSQL 18 以降のインスタンスと Vertex AI 連携を準備し、スロークエリに対してまず試してみることを推奨します。ただし推奨事項は LLM 生成のため、適用前に必ず内容を検証してください。
