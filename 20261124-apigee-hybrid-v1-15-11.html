🚀 Apigee hybrid v1.15.11 パッチリリース

Valkey 移行の既定化 (ApigeeRedis → ApigeeValkey) と多数のセキュリティ修正
リリース日
2026-11-24

📌 概要

2026 年 11 月 24 日、Google Cloud は Apigee hybrid の更新バージョン v1.15.11 をリリースしました。 コンテナイメージは Helm チャートに統合されており、チャートのアップグレードでイメージも自動更新されます。

最大のポイントは、ApigeeRedis → ApigeeValkey の段階的移行 (phased migration) の一環として、 ao.args.valkeyBackend のデフォルトが true に変更され、 ランタイムのキーバリューストアが Valkey に切り替わることです。

⛔ 重要: v1.15.11 へアップグレードする前に、必ず v1.15.10 を経由する必要があります (v1.14 からの場合もまず v1.15.10 へ)。 apigee-operator のアップグレード時に ApigeeRedis が v1.15.10 経由で更新済みかを検証し、満たさない場合はエラーで停止します。

😰 アップデート前の課題 (Before)

  • ao.args.valkeyBackend のデフォルトは false で、ランタイムの KVS は引き続き ApigeeRedis (Valkey 移行は未完了)
  • apigee-runtime の管理ポート (例: 8843) でコネクションカウントがリークし、HPA の AverageValue が実態より膨張 → レプリカ数が maxReplicas に張り付き
  • 別セッションやマスキングエラー介在時に、デバッグセッションでペイロード・クエリパラメータ・ヘッダー・フロー変数がマスクされず表示
  • OAuth 2.0 の redirect_uri 検証に非厳密なサブリソースマッチングによるバイパス、Jython サンドボックスエスケープ等の問題
  • OASValidation で大きな OpenAPI 3.0 仕様を扱うと Message Processor でメモリリーク・OutOfMemoryError
  • synchronizer.pollInterval 等の同期間隔設定が Helm チャート・オペレーターに無視される

😊 アップデート後の改善 (After)

  • ao.args.valkeyBackend がデフォルト true になり、ランタイムが ApigeeValkey を使用。v1.15.10 経由をオペレーターが自動検証
  • コネクションカウントリークが修正され、HPA が実際の負荷に基づき適切にスケール
  • デバッグセッションのマスキング処理が修正され、機微情報の露出リスクを低減
  • redirect_uri 検証修正 + <EnforceStrictCallbackURI> の強制、Jython / JavaCallout / Script / JavaScript サンドボックス強化
  • OASValidation のコンパイル済み仕様をコンテンツハッシュで共有しメモリリーク解消。再帰スキーマは検証エラーとして報告
  • pollInterval が有効化 (60 秒未満は 60 秒へ)。圧縮 SSE の破損、HTTP/2 疑似ヘッダー問題も修正。多数の CVE 対応 + 弱い DH TLS 暗号スイート無効化

v1.15.11 は Valkey 移行の「切替フェーズ」にあたり、v1.15.10 (準備フェーズ) を必ず経由する必要があります。 apigee-operator がアップグレードパスを検証し、切替後もロールバックに備えて apigee-redis チャートは維持します。

⚙️ サービスアップデートの詳細 (主要機能)

1️⃣ ApigeeRedis → ApigeeValkey 移行の既定化 (段階的移行の切替フェーズ)
→ao.args.valkeyBackend のデフォルトが true に変更され、ランタイムの KVS が ApigeeValkey に移行
→v1.15.11 の前に v1.15.10 の適用が必須。オペレーターのアップグレード時 (--dry-run=server 時も含む) に ApigeeRedis の hybrid-version ラベルが 1.15.10 以降であることを検証し、満たさない場合は ApigeeRedis default in namespace ... で始まるエラーで停止
✗検証をスキップする disableMandatoryPreviousHybridVersionCheckForValkey は設定しないこと (公式に非推奨)
→overrides.yaml の redis ブロックと同内容の valkey ブロックを追加 (redis.image はコピーしない)。redis ブロックがなければ valkey ブロックも不要
→切替後も apigee-redis チャートはアンインストールせず、他のチャートと一緒にアップグレードを継続 (フォールバック・ロールバックに必要)
2️⃣ ランタイム・運用面の主要な修正
✓583672651: apigee-runtime HTTP サーバー管理ポート (例: 8843) のコネクションカウントリークを修正。HPA の AverageValue 膨張とレプリカ数の maxReplicas 張り付きを解消
✓582790971: 別セッション・マスキングエラー介在時にデバッグセッションでペイロード等がマスクされず表示される問題を修正
✓582790249: メッセージのない例外で失敗したポリシーの Execution エントリがデバッグトレースから欠落する問題を修正
✓579213551: OASValidation の大きな OpenAPI 3.0 仕様によるメモリリーク・OutOfMemoryError を修正。コンパイル済み仕様をコンテンツハッシュで共有し、再帰スキーマは検証エラーとして報告
✓572875915: synchronizer.pollInterval、envs[].pollInterval 等が無視される問題を修正 (60 秒未満は 60 秒に引き上げ)
✓572025634: 圧縮された text/event-stream レスポンスが EventFlow を持つプロキシで破損する問題を修正 (圧縮済み SSE は EventFlow 処理をスキップしてパススルー)
✓554114419: HTTP/2 フローで createNew="true" の AssignMessage / HTTPModifier / RaiseFault ポリシーが :path / :authority 疑似ヘッダーを設定できない問題を修正
3️⃣ Apigee 固有のセキュリティ修正 🔐
✓579642864: OAuth 2.0 の redirect_uri 検証における非厳密なサブリソースマッチングのバイパスを修正し、GenerateAuthorizationCode ポリシーで <EnforceStrictCallbackURI> を強制
✓579642568: Jython サンドボックスエスケープを修正
✓579640924: JavaCallout、Script、JavaScript ポリシーのサンドボックスを強化
✓519116013: apigee-hybrid-cassandra コンテナのポート 7070 (Prometheus jmx_exporter) で弱い Diffie-Hellman (DH) TLS 暗号スイートを無効化
4️⃣ コンポーネント横断の CVE 対応 🛡️
→インフラ系コンテナイメージに多数の CVE 修正を適用 (個別の列挙は公式リリースノートを参照)
→対象コンポーネント例: apigee-asm-ingress / apigee-asm-istiod (CVE-2026-111943、CVE-2026-116587、CVE-2026-128085 など)、apigee-connect-agent / apigee-operators / apigee-redis / apigee-prometheus-adapter (CVE-2026-97033〜97054 系列)、apigee-fluent-bit (CVE-2026-27171、CVE-2026-85091)、apigee-hybrid-cassandra / apigee-hybrid-cassandra-client、apigee-mart-server / apigee-mint-task-scheduler、apigee-runtime / apigee-synchronizer (CVE-2026-102554、CVE-2026-49875、CVE-2026-50645)、apigee-stackdriver-logging-agent、apigee-open-telemetry-collector など

🛠️ 設定方法 (アップグレード手順)

✅ 前提条件

✓クラスタが Apigee hybrid v1.15.10 以降で稼働していること (v1.14 からの場合は先に v1.15.10 へアップグレード)
✓現行クラスタ構成を反映した overrides.yaml が利用できること
✓Valkey 切替時にレート制限カウンタがゼロにリセットされるため、トラフィックの少ない時間帯にアップグレードを計画すること

ステップ 1: ApigeeRedis のバージョン確認と overrides の更新

Bash ApigeeRedis のバージョンラベル確認 
# ApigeeRedis リソースのバージョンラベルを確認 (1.15.10 以降であること)
kubectl -n APIGEE_NAMESPACE get apigeeredis default \
  -o jsonpath='{.metadata.labels.apigee\.cloud\.google\.com/hybrid-version}'

出力が空、または 1.15.10 より前の場合は、先に全チャートを v1.15.10 にアップグレードします。 あわせて overrides.yaml に valkey ブロックを追加し、ao.args.valkeyBackend: false を設定している場合はその行を削除します。

ステップ 2: CRD の更新とオペレーター・各チャートのアップグレード

Bash apigee-operator のアップグレード 
# 更新された Apigee CRD (ApigeeValkey CRD を含む) をインストールした後、
# apigee-operator をアップグレード (ApigeeRedis の v1.15.10 経由更新が検証される)
helm upgrade operator apigee-operator/ \
  --install \
  --namespace APIGEE_NAMESPACE \
  --atomic \
  -f overrides.yaml

オペレーターのアップグレード後、apigee-valkey チャートをインストールし、default という名前の ApigeeValkey リソースが稼働状態になるのを待ってから、組織 (org) と環境 (env) をアップグレードします。 apigee-redis チャートもアンインストールせず、他のチャートと一緒にアップグレードを継続します。 詳細な順序は「Upgrading Apigee hybrid to v1.15.11」を参照してください。

ステップ 3: ランタイムが Valkey を使用していることを確認

組織・環境のアップグレード後、公式手順の「verify that the runtime uses Valkey」に従い、ランタイムが ApigeeValkey を使用していることを確認します。 問題が発生した場合は、v1.15.10 で使用していた overrides ファイルを用いた v1.15.10 へのロールバック手順が提供されています (ロールバック後はランタイムが ApigeeRedis に戻り、レート制限カウンタは再度リセットされます)。

💡 メリット

💼 ビジネス面

✓セキュリティリスクの低減: OAuth 2.0 の redirect_uri 検証バイパスやポリシーサンドボックスエスケープ、デバッグセッションでの機微情報露出といった API 基盤の根幹に関わる問題が修正され、コンプライアンス・監査対応の負担が軽減される
✓運用コストの最適化: HPA のレプリカ数が maxReplicas に張り付く問題の修正により、不要なランタイム Pod によるリソース消費が解消される

🔧 技術面

✓Valkey 移行の自動検証: apigee-operator がアップグレードパス (v1.15.10 経由) を自動検証するため、誤った順序でのアップグレードによる障害を未然に防げる
✓適用の容易さ: パッチリリースのコンテナイメージは Helm チャートに統合されており、通常のチャートアップグレードフローで修正済みイメージが自動反映される
✓安全なロールバック経路: apigee-redis チャートを維持する設計により、ApigeeValkey に問題が発生した場合でも v1.15.10 へのロールバックでランタイムを ApigeeRedis に戻せる

⚠️ デメリット・制約事項

🚧 制限事項

✗v1.15.10 の経由が必須: v1.15.9 以前や v1.14 から直接 v1.15.11 へはアップグレードできない。apigee-operator の検証により満たさない場合はエラーで停止する
✗検証をスキップする disableMandatoryPreviousHybridVersionCheckForValkey は設定しないことが公式に明記されている

🤔 考慮すべき点

!レート制限カウンタのリセット: ApigeeValkey への移行時に KVS 内のレート制限カウンタがゼロにリセットされる。ランタイム Pod の再起動中は新旧 Pod が別々のカウンタを保持するため、一時的にレート制限を超えるリクエストが許可される可能性がある。トラフィックの少ない時間帯での実施を推奨
!apigee-redis チャートの維持: 切替後もアンインストールしてはならない。ApigeeValkey が稼働していない場合のフォールバックとロールバックに必要
!Vault で Redis パスワードを管理している場合は、apigee-redis ロールの bound_service_account_names に apigee-valkey-default と apigee-valkey-envoy-default の追加が必要
!プライベートレジストリを使用している場合は apigee-valkey イメージの事前コピーが必要
!修正された CVE は多数のコンポーネントにまたがるため、自組織の脆弱性スキャン指摘と公式リリースノートの CVE 一覧を突き合わせて対応状況を確認することが望ましい

🎯 ユースケース

📈 ユースケース 1: HPA の異常スケールに悩む環境の是正

シナリオ: apigee-runtime のレプリカ数が負荷に関係なく常に maxReplicas に張り付いており、クラスタリソースを過剰に消費している。

効果: v1.15.11 の修正 (Bug ID: 583672651) により、管理ポートのコネクションカウントリークが解消され、HPA の AverageValue メトリクスが実際の負荷を反映するようになる。結果として適正なレプリカ数での運用が可能になり、ノードリソースのコストが最適化される。

🏦 ユースケース 2: 規制産業における OAuth フローの脆弱性対応

シナリオ: 金融・医療など規制産業の API 基盤で OAuth 2.0 認可コードフローを利用しており、redirect_uri 検証バイパス (Bug ID: 579642864) のようなセキュリティ問題への SLA 内対応が求められている。

効果: v1.15.11 への Helm チャートアップグレードのみで redirect_uri 検証修正と <EnforceStrictCallbackURI> の強制が適用され、サンドボックス強化 (Jython / JavaCallout / Script / JavaScript) もあわせて取り込める。

🗺️ ユースケース 3: Valkey 移行を含むバージョンアップ計画の策定

シナリオ: v1.15.9 以前を運用中で、サポート継続のために最新パッチへの追随が必要だが、Redis → Valkey というデータストア移行が含まれるため慎重に計画したい。

効果: v1.15.10 (準備) → v1.15.11 (切替) という公式の段階的移行パスに沿い、オペレーターの自動検証とロールバック手順を活用することで、リスクを抑えた移行計画を立てられる。レート制限カウンタのリセットを考慮し、低トラフィック時間帯に切替を実施する。

🔗 関連サービス・機能

→Valkey (ApigeeValkey): Redis 互換のオープンソースキーバリューストア。本リリースでランタイムの既定の KVS バックエンドとなり、レート制限カウンタなどを保持する

📝 まとめ

Apigee hybrid v1.15.11 は、ApigeeRedis から ApigeeValkey への段階的移行の「切替フェーズ」にあたる重要なパッチリリースであり、 ao.args.valkeyBackend のデフォルトが true になるため v1.15.10 の経由が必須です。 HPA の異常スケールや OAuth redirect_uri 検証バイパス、ポリシーサンドボックスエスケープなど運用・セキュリティ両面の重要な修正と多数の CVE 対応が含まれるため、 v1.15 系の運用環境では、レート制限カウンタのリセットを考慮して低トラフィック時間帯に切替を計画し、検証環境での確認を経て早期に適用することを推奨します。
