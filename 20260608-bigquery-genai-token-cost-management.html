📊 BigQuery: 生成 AI 関数のトークンベースコスト管理

BigQuery GA 生成 AI
2026-06-08

🎯 概要

BigQuery の生成 AI 関数 (AI.GENERATE、AI.CLASSIFY、AI.IF、AI.SCORE、AI.AGG など) に対して、日次トークンクォータを設定してコストを管理・制限する機能が一般提供 (GA) となった。

プロジェクトレベルおよびユーザーレベルで入力/出力トークンの日次使用量に上限を設定でき、生成 AI 関数の利用に伴う予期しないコスト増大を防止できる。

🤖 背景: BigQuery の生成 AI 関数は Vertex AI の Gemini モデルへリクエストを送信するため、処理するトークン数に応じて Vertex AI 側の課金が発生する。従来のバイトベースのクォータでは LLM 推論のトークンコストを正確に反映できなかった。

🔄 Before / After 比較

❌ Before (従来)

  • トークン消費量を直接制限する手段がなかった
  • QueryUsagePerDay クォータはバイトベースで LLM トークンコストを反映せず
  • 複雑なクエリでトークン消費が想定外に膨らむリスク
  • 大量データへの AI 関数実行時にコスト予測が困難

✅ After (新機能)

  • プロジェクト/ユーザーレベルで入力/出力トークンの日次クォータ設定
  • クエリ実行前のプリチェックで残りクォータを確認
  • 超過時はクエリを拒否する仕組みで予算超過を防止
  • 実行中のクエリもクォータ超過時に新規 LLM 呼び出しを停止

⚡ 主要機能

🎛️ 日次トークンクォータの設定

入力/出力トークン (プロジェクトレベル / ユーザーレベル) の日次上限を Google Cloud コンソールの IAM & Admin > Quotas & System Limits から設定可能。

🔒 二段階のクォータ適用

実行前プリチェック + 実行中の適用。クォータ枯渇時はクエリ拒否、実行中超過時は新規 LLM 呼び出しを停止。

🌐 グローバルスコープ集計

トークン使用量は全リージョンにわたってグローバルに集計。キャッシュトークンはカウント対象外。

二段階のクォータ適用メカニズム

Stage 1: プリチェック

クエリ実行前にクォータが枯渇している場合、クエリを開始前に拒否。無駄な計算リソース消費を回避。

Stage 2: 実行中適用

実行中にクォータ超過した場合、新規 LLM 呼び出しを停止し部分的な結果を返却 (max_error_ratio に依存)。

⚙️ 設定方法

前提条件

必要な権限: Quota Administrator (role/servicemanagement.quotaAdmin) ロール、または serviceusage.quotas.update 権限を持つカスタムロール

設定手順

1
Quotas & System Limits ページに移動
Google Cloud コンソールで IAM & Admin > Quotas & System Limits に移動
2
BigQuery API でフィルタリング
Service フィルタで BigQuery API を選択し、設定したいクォータを検索
3
クォータ値の編集
対象クォータを選択 → Edit → 新しい値を入力 → Submit request
⚠️ 注意: 低い値への変更は数分以内に反映。高い値への変更には承認プロセスが必要な場合がある。

💡 ユースケース

📋 ユースケース 1: データ分析チームの予算管理

シナリオ: データ分析チームが AI.CLASSIFY や AI.GENERATE を使用して大量テキストデータを分類・分析しているが、月次予算を超過するリスクがある。

効果: 日次のトークン消費に上限を設けることで、月次予算内に収まるよう自動的にコストが制御される。

👥 ユースケース 2: マルチテナント環境でのユーザー別制限

シナリオ: 複数チームが同一プロジェクトで BigQuery 生成 AI 関数を利用。特定チームの大量利用が他チームに影響を与えないようにしたい。

効果: GenAiInputTokensPerUserPerDay により各ユーザー/サービスアカウントの日次利用量を自動制限し、公平なリソース配分を実現。

🚨 ユースケース 3: 本番環境の暴走防止

シナリオ: バッチ処理で AI.GENERATE を数百万行に対して実行するジョブがあり、想定外の入力データ増加によるコスト暴走を防ぎたい。

効果: プロジェクトレベルのクォータにより、入力行数が予想を超えても日次コスト上限が保証される。

コード例: 事前トークン数推定

SQL AI.COUNT_TOKENS で事前にトークン消費量を推定 
-- 事前にトークン数を推定
SELECT AI.COUNT_TOKENS(
    description,
    endpoint => 'gemini-2.5-flash'
  ).result AS tokens
FROM `project.dataset.products`
WHERE category IS NULL;

✅ メリット

💰 ビジネス面

→予算超過の防止: 日次上限で想定外のコスト増大を防止
→部門別コスト管理: ユーザーレベルクォータでチーム/SA ごとの公平な利用確保
→FinOps の実現: トークン単位の可視化と上限設定でコストガバナンス向上

🔧 技術面

→プロアクティブ制御: 実行前チェックで無駄なリソース消費を回避
→グローバル集計: 複数リージョンを一元管理でオペレーション負荷軽減
→AI.COUNT_TOKENS 併用: 事前にトークン数を推定してクォータ消費を予測可能

⚠️ デメリット・制約事項

制限事項

✗クォータはグローバルスコープのみ対応。リージョン単位での個別設定は不可
✗百万トークン単位で追跡されるため、小さいクォータ値では精度が低い場合あり
✗個別ユーザー/SA にカスタムクォータを割り当て不可 (全ユーザー一律適用)
✗Provisioned Throughput 使用時は高い値に設定が必要 (トークンベース課金ではないため)

考慮すべき点

!プロジェクトレベルクォータに達すると、個別ユーザーのクォータ残があっても全員がブロック
!実行中クォータ超過時、部分的な結果のみ返却の可能性 → max_error_ratio の適切な設定が重要
!日次クォータは太平洋時間の深夜にリセット

💵 料金情報

BigQuery 生成 AI 関数のコストは以下の 2 つの要素から構成される:

📊 BigQuery コンピュート費用

クエリ処理に使用されるコンピュートリソースの料金

🤖 Vertex AI 推論費用

Gemini モデルへのリクエストに伴うトークンベースの課金 (入力/出力トークン数に基づく)

💡 ポイント: Gemini 2.0 以降のモデルを使用する場合、BigQuery からの呼び出しにはバッチ API レートが適用される。

🌍 利用可能リージョン

トークンクォータはグローバルスコープで適用されるため、BigQuery の生成 AI 関数がサポートされるすべてのリージョンで利用可能。

📝 まとめ

BigQuery 生成 AI 関数のトークンベースコスト管理が GA になったことで、組織は AI 関数の利用に伴うコストをプロアクティブに制御できるようになった。特に大規模データセットに対する AI 推論を実行する環境では、予算超過リスクの軽減とガバナンス強化に直結する機能であり、本番環境での BigQuery 生成 AI 関数の利用を検討しているすべてのチームが設定を検討すべきである。
