🪣 Cloud Storage: ライフサイクル管理のサイズ条件

Cloud Storage Feature
2026-07-20

📋 概要

Google Cloud Storage の Object Lifecycle Management に sizeAboveBytes および sizeBelowBytes 条件が追加されました。オブジェクトのサイズに基づいてライフサイクルアクション（ストレージクラスの変更や削除）を実行するかどうかを制御できるようになります。

最小サイズしきい値と最大サイズしきい値を定義することで、コスト効率の高いストレージ管理を実現します。データレイクやログ管理など、多様なサイズのオブジェクトが混在する環境で、きめ細かいコスト最適化が可能になります。

❌ Before (課題)

✗小さなオブジェクトにも一律でクラス変更が実行され、オペレーションコストが節約を上回る場合があった
✗サイズ範囲に基づくフィルタリングが不可能で、全オブジェクトに一律適用するしかなかった
✗サイズベースの管理にはカスタムスクリプトや外部ツールが必要だった

✅ After (改善)

✓sizeAboveBytes で指定バイト数より大きいオブジェクトのみにアクション適用可能
✓sizeBelowBytes で指定バイト数より小さいオブジェクトのみにアクション適用可能
✓両条件を組み合わせて特定のサイズ範囲内のオブジェクトを対象としたルール定義が可能

🏗️ アーキテクチャ図

Object Lifecycle Management がオブジェクトを評価する際の判定フロー。サイズ条件は他の条件（age、matchesStorageClass など）と AND 条件で組み合わされ、すべての条件を満たした場合にのみアクションが実行されます。

⚡ 主要機能

📏 sizeAboveBytes 条件

オブジェクトのデータサイズが指定値より大きい場合に条件が満たされる。ライフサイクルアクションの最小サイズしきい値を定義するために使用。

小さなオブジェクトでストレージクラス変更のコストが節約を上回るケースの除外に有効

📐 sizeBelowBytes 条件

オブジェクトのデータサイズが指定値より小さい場合に条件が満たされる。ライフサイクルアクションの最大サイズしきい値を定義するために使用。

大きなオブジェクトを特定のルールから除外する場合に有効

🎯 サイズ範囲指定

sizeAboveBytes と sizeBelowBytes を同一ルール内で組み合わせて使用可能。特定のサイズ範囲（例: 1MB〜100MB）のオブジェクトのみを対象としたルールを作成可能。

既存の条件（age、matchesStorageClass、matchesPrefix/Suffix など）と組み合わせ可能

🔧 技術仕様

サイズ条件の仕様

項目 詳細
sizeAboveBytesオブジェクトサイズが指定バイト数を超える場合に真
sizeBelowBytesオブジェクトサイズが指定バイト数未満の場合に真
最大指定値5 TiB (5,497,558,138,880 bytes)
評価対象オブジェクトのデータサイズのみ（メタデータは除外）
組み合わせ同一ルール内で両条件を併用可能（サイズ範囲指定）
利用可能アクションDelete, SetStorageClass, AbortIncompleteMultipartUpload

項目 詳細

⚙️ 設定方法

💡 前提条件: Google Cloud プロジェクト作成済み / Cloud Storage バケット作成済み / storage.buckets.update 権限を持つ IAM ロール（Storage Admin など）が付与されていること

ステップ 1: ライフサイクル設定ファイルの作成

3 つのルールを定義する例: (1) 5MB を超える Standard オブジェクトを 365 日後に Nearline に移行、(2) 1KB 未満のオブジェクトを 90 日後に削除、(3) 1MB〜100GB のオブジェクトを 180 日後に Coldline に移行。

JSON 
{
  "lifecycle": {
    "rule": [
      {
        "action": {
          "type": "SetStorageClass",
          "storageClass": "NEARLINE"
        },
        "condition": {
          "age": 365,
          "matchesStorageClass": ["STANDARD"],
          "sizeAboveBytes": 5242880
        }
      },
      {
        "action": {
          "type": "Delete"
        },
        "condition": {
          "age": 90,
          "sizeBelowBytes": 1024
        }
      },
      {
        "action": {
          "type": "SetStorageClass",
          "storageClass": "COLDLINE"
        },
        "condition": {
          "age": 180,
          "sizeAboveBytes": 1048576,
          "sizeBelowBytes": 107374182400
        }
      }
    ]
  }
}

ステップ 2: gcloud CLI でライフサイクル設定を適用

Bash 
# ライフサイクル設定ファイルを適用
gcloud storage buckets update gs://MY_BUCKET --lifecycle-file=lifecycle.json

ステップ 3: 設定の確認

Bash 
# 現在のライフサイクル設定を確認
gcloud storage buckets describe gs://MY_BUCKET --format="json(lifecycle)"

ステップ 4: REST API での設定（代替方法）

Bash 
# JSON API を使用して設定を適用
curl -X PATCH --data-binary @lifecycle.json \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://storage.googleapis.com/storage/v1/b/MY_BUCKET?fields=lifecycle"

✅ メリット

💰 ビジネス面

✓コスト最適化の精度向上: 小さなオブジェクトの移行によるオペレーションコスト超過を防止
✓運用の簡素化: カスタムスクリプト不要でネイティブにサイズベースポリシーを実装
✓ガバナンスの強化: データサイズに応じた保持・削除ポリシーを宣言的に定義可能

🔧 技術面

✓きめ細かいルール定義: 既存条件とサイズ条件を自由に組み合わせ可能
✓宣言的設定: JSON/XML で管理でき、IaC との統合が容易
✓スケーラビリティ: オブジェクト数に関係なく自動的にルールを評価・適用

⚠️ デメリット・制約事項

⚠️ 制限事項:
  • サイズ条件の最大値は 5 TiB まで。それ以上のオブジェクトには対応できない
  • オブジェクトのメタデータサイズは評価対象外
  • 階層的名前空間（HNS）バケットでは sizeBelowBytes で空フォルダの削除は不可
  • ライフサイクル設定変更後、反映まで最大 24 時間のタイムラグ
💡 考慮すべき点:
  • サイズ条件は他の条件と AND で評価される。意図しないオブジェクトが対象外にならないようルール全体の設計を慎重に
  • 圧縮済みオブジェクトは圧縮後のサイズで評価される
  • 複数ルールが同時に条件を満たした場合、Delete が SetStorageClass より優先。SetStorageClass 間ではより低コストのクラスが優先

🎯 ユースケース

1. 小さなオブジェクトのストレージクラス移行除外

シナリオ: データレイクに数バイトのメタデータファイルから数 GB のデータファイルまでが混在。365 日後に Nearline に移行したいが、小さなファイルは移行コストが節約を上回るため除外したい。

JSON 
{
  "action": { "type": "SetStorageClass", "storageClass": "NEARLINE" },
  "condition": {
    "age": 365,
    "matchesStorageClass": ["STANDARD"],
    "sizeAboveBytes": 5242880
  }
}
効果: 5MB 以下のオブジェクトを除外し、不要な Class A オペレーション料金の発生を防止。小さなオブジェクトが多い環境では、年間数百〜数千ドルのコスト削減が見込める。

2. 一時ファイルのサイズベース自動削除

シナリオ: 一時的に生成する小さなログフラグメントや空ファイルを 30 日後に自動削除。大きなログファイルは監査目的で保持。

JSON 
{
  "action": { "type": "Delete" },
  "condition": {
    "age": 30,
    "sizeBelowBytes": 1024,
    "matchesPrefix": ["tmp/", "logs/fragments/"]
  }
}
効果: 1KB 未満の一時ファイルが 30 日後に自動削除され、ストレージの無駄を排除。大きなログファイルは影響を受けず保持される。

3. サイズ範囲に基づく段階的アーカイブ

シナリオ: メディアファイル管理で、中程度サイズ（1MB〜1GB）のファイルは早期に Coldline へ移行し、1GB 以上のファイルはアクセス頻度が高いため Standard に長く保持。

JSON 
{
  "action": { "type": "SetStorageClass", "storageClass": "COLDLINE" },
  "condition": {
    "age": 90,
    "matchesStorageClass": ["STANDARD"],
    "sizeAboveBytes": 1048576,
    "sizeBelowBytes": 1073741824
  }
}
効果: ファイルサイズに応じた最適なストレージクラス移行戦略を実現。中サイズファイルは早期に低コストクラスへ移行しつつ、大きなファイルへの高速アクセスを維持。

💰 料金情報

✅ Object Lifecycle Management 自体には追加料金は発生しません。ライフサイクルアクションの実行に伴う以下のコストのみが発生します。
項目 料金 (USD)
SetStorageClass アクション (Class A オペレーション)$0.05 / 10,000 オペレーション (Standard)
Delete アクション無料
Standard ストレージ保存料金$0.020 / GiB / 月〜
Nearline ストレージ保存料金$0.010 / GiB / 月〜
Coldline ストレージ保存料金$0.004 / GiB / 月〜
Archive ストレージ保存料金$0.0012 / GiB / 月〜
Nearline 取得料金$0.01 / GiB
Coldline 取得料金$0.02 / GiB
Archive 取得料金$0.05 / GiB
💡 コスト最適化のポイント: sizeAboveBytes 条件を活用することで、SetStorageClass の Class A オペレーション費用が保存料金の節約を上回るケースを回避できます。例えば 1KB のオブジェクトを Standard から Nearline に移行しても月額 $0.00001 の節約にしかなりませんが、5MB 以上のオブジェクトでは月額 $0.05 の節約となり、オペレーション費用を大幅に上回ります。

🌍 利用可能リージョン

✅ 全リージョン対応: この機能はすべての Cloud Storage リージョン、マルチリージョン、およびデュアルリージョンで利用可能です。特定のリージョン制限はありません。

🔗 関連サービス・機能

Autoclass

アクセスパターンに基づいてストレージクラスを自動移行。matchesStorageClass 条件との併用はできない。

Storage Intelligence

バケットの使用状況を分析し、コスト最適化の推奨事項を提供。サイズ条件のしきい値決定に活用可能。

Object Versioning

バージョン管理オブジェクトにもサイズ条件が適用。numNewerVersions や isLive 条件と組み合わせ可能。

Terraform

google_storage_bucket リソースで IaC としてサイズ条件を含むライフサイクルルールを管理可能。

📝 まとめ

sizeAboveBytes と sizeBelowBytes 条件の追加により、オブジェクトサイズに基づくきめ細かいライフサイクルポリシーの定義が可能になりました。特にストレージクラス移行のコスト効率を最適化したい場合や、サイズに基づくデータ保持ポリシーを実装したい場合に有効です。

推奨アクション: 既存のライフサイクルルールにサイズ条件を追加することで、即座にコスト最適化を実現できます。大量のオブジェクトを管理しているすべてのユーザーにおいて設定の見直しを推奨します。
