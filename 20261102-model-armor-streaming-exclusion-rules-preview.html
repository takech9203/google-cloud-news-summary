🛡️ Model Armor: ストリーミングサニタイズで除外ルールをサポート

リリース日: 2026-11-02 | Google Cloud Release Notes
Model Armor Preview AI セキュリティ ストリーミング

📌 概要

Model Armor のストリーミングサニタイズ API である StreamSanitizeUserPrompt (ユーザープロンプト) と StreamSanitizeModelResponse (モデルレスポンス) で、テンプレート単位の除外ルール (Exclusion Rules) がサポートされました (Preview)。 辞書 (dictionary) ベースおよび正規表現 (regex) ベースの除外ルールにより、 プロンプトインジェクション / ジェイルブレイク検出 (PROMPT_INJECTION_AND_JAILBREAK) と 責任ある AI (RESPONSIBLE_AI) フィルタの誤検知 (false positive) を軽減できます。

除外ルールの評価方法はストリーミングモードで異なります。バッファモード (STREAMING_MODE_BUFFERED) は部分一致と完全一致の両方をサポートし、全チャンク収集後にコンテンツ全体を評価します。 リアルタイムモード (STREAMING_MODE_REALTIME) は部分一致のみをサポートし、処理チャンクごとに独立評価します。 非ストリーミング API で先行提供されていた除外ルールが、低レイテンシが求められるストリーミングのユースケースにも拡大された形です。

❌ Before (アップデート前の課題)

  • ストリーミングサニタイズでは除外ルールを利用できず、誤検知をテンプレート設定で回避する手段がなかった
  • 「kill process 1234」や「ignore the emails」のような正当な技術的・業務的表現が、危険コンテンツやインジェクション試行として誤ってブロックされていた
  • 回避にはフィルタの信頼度しきい値の緩和や独自の後処理実装が必要で、セキュリティ低下や実装コスト増加を招いていた

✅ After (アップデート後の改善)

  • ストリーミングでも辞書・正規表現ベースの除外ルールが評価され、マッチ時はフィルタ結果が NO_MATCH_FOUND にオーバーライド
  • バッファモード: 部分一致・完全一致の両方をストリーム全体のコンテンツに適用可能
  • リアルタイムモード: 部分一致でチャンクごとの低レイテンシ処理を維持したまま誤検知を抑制
  • 非ストリーミング / ストリーミング API で同一テンプレートを共有し、誤検知対策を一元管理

🏗️ アーキテクチャ図

⚙️ 主要機能

1️⃣ バッファモード (STREAMING_MODE_BUFFERED) での除外ルール評価

  • すべてのストリームチャンクを収集し、結合された完全なコンテンツに対して除外ルールを評価
  • 部分一致 (MATCHING_SCOPE_PARTIAL_MATCH、デフォルト): 辞書フレーズまたは正規表現パターンが任意の部分文字列にマッチすると、該当フィルタタイプの matchState を NO_MATCH_FOUND にオーバーライド
  • 完全一致 (MATCHING_SCOPE_FULL_MATCH): パターンがストリームコンテンツ全体 (先頭から末尾まで) にマッチした場合のみオーバーライド。いずれかのチャンクがパターンを超えるテキストを追加するとマッチせず MATCH_FOUND を維持

2️⃣ リアルタイムモード (STREAMING_MODE_REALTIME) での除外ルール評価

  • 処理されたチャンク (sanitizationMetadata.streamChunkProcessed に返却) ごとに独立して評価
  • 部分一致のみサポート。処理チャンク内でマッチするとそのチャンクの matchState を NO_MATCH_FOUND にオーバーライドし、後続チャンクも独立して評価を継続
  • 除外対象のフレーズが複数の処理チャンクに分割されている場合、部分的な断片はマッチしない
  • 完全一致を含むテンプレートを使用すると INVALID_ARGUMENT エラーでリクエストが拒否される

3️⃣ 対象フィルタとオーバーライド動作

  • 対象は PROMPT_INJECTION_AND_JAILBREAK と RESPONSIBLE_AI の 2 種類
  • マッチすると該当フィルタタイプ全体 (RESPONSIBLE_AI の場合は全安全カテゴリ) の結果がオーバーライドされる。個別フレーズ単位の除外ではない点に注意
  • Cloud Logging (logSanitizeOperations) 有効時、modelarmor.googleapis.com/exclusion_rule_overridden_filters ラベルでオーバーライドの発生を追跡可能

🧩 除外ルールの設定例 (filterRuleSettings)

JSON テンプレートの filterRuleSettings 定義 
{
  "filterConfig": {
    "filterRuleSettings": {
      "ruleSets": [
        {
          "filterTypes": ["PROMPT_INJECTION_AND_JAILBREAK"],
          "rules": [
            {
              "exclusionRule": {
                "regex": {
                  "pattern": "(?i)\\b(?:ignore\\s+(?:the\\s+)?(?:emails?|spams?|warnings?|drafts?))\\b"
                },
                "matchingScope": "MATCHING_SCOPE_PARTIAL_MATCH"
              }
            }
          ]
        },
        {
          "filterTypes": ["RESPONSIBLE_AI"],
          "rules": [
            {
              "exclusionRule": {
                "dictionary": {
                  "wordList": {
                    "words": ["kill process", "abort retry"]
                  }
                },
                "matchingScope": "MATCHING_SCOPE_PARTIAL_MATCH"
              }
            }
          ]
        }
      ]
    }
  }
}

🛠️ 設定方法

📝 前提条件

✓Model Armor テンプレートが作成済みで、対象フィルタ (PROMPT_INJECTION_AND_JAILBREAK または RESPONSIBLE_AI) が有効化されていること
✓リアルタイムモードを使用する場合、除外ルールのマッチングスコープが MATCHING_SCOPE_PARTIAL_MATCH であること (完全一致はバッファモード専用)

ステップ 1: テンプレートに除外ルールを追加

Bash テンプレートの filterRuleSettings を更新 
curl -X PATCH \
  -d "$EXCLUSION_RULES_UPDATE" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://modelarmor.LOCATION.rep.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/templates/TEMPLATE_ID?updateMask=filterConfig.filterRuleSettings"

$EXCLUSION_RULES_UPDATE には上記「技術仕様」の filterRuleSettings JSON を設定し、updateMask=filterConfig.filterRuleSettings で除外ルールのみを更新します。

ステップ 2: ストリーミングサニタイズを実行 (Python SDK)

Python StreamSanitizeUserPrompt の実行例 
from google.cloud import modelarmor_v1beta

client = modelarmor_v1beta.ModelArmorClient(
    transport="grpc",
    client_options={"api_endpoint": f"modelarmor.{location}.rep.googleapis.com"},
)
template_name = client.template_path(project_id, location, template_id)

prompt_chunks = [
    "Summarize my inbox and",
    " ignore the emails from the marketing vendor.",
]

# STREAMING_MODE_REALTIME または STREAMING_MODE_BUFFERED を指定
streaming_mode = modelarmor_v1beta.StreamingMode.STREAMING_MODE_REALTIME

def request_generator():
    for chunk in prompt_chunks:
        yield modelarmor_v1beta.SanitizeUserPromptRequest(
            name=template_name,
            user_prompt_data=modelarmor_v1beta.DataItem(text=chunk),
            streaming_mode=streaming_mode,
        )

stream = client.stream_sanitize_user_prompt(requests=request_generator())
for response in stream:
    print(response)
💡 ポイント: 除外ルールがマッチした場合、レスポンスの filter_match_state が NO_MATCH_FOUND となり、sanitization_metadata.stream_chunk_processed に処理チャンクが返却されます。モデルレスポンス側も同様に stream_sanitize_model_response で実行できます。

💡 メリット

💼 ビジネス面

✓ユーザー体験の維持: 正当な業務表現 (「kill process」「ignore the emails」など) の誤ブロックによる、チャットボットやコパイロットの応答中断を防止
✓セキュリティと利便性の両立: フィルタのしきい値を緩和せず、特定の既知パターンのみをピンポイントで除外できるため、全体のセキュリティレベルを維持
✓運用コストの削減: アプリケーション側の独自誤検知回避ロジックが不要になり、テンプレート設定の変更のみで対応が完結

🔧 技術面

✓ストリーミングとの統合: 低レイテンシが求められるリアルタイムモード (無制限トークン対応) でも、チャンク単位の独立評価で除外ルールを適用可能
✓設定の一元管理: 非ストリーミング / ストリーミング API で同一テンプレートの除外ルールを共有でき、ポリシー管理が一貫
✓可観測性: Cloud Logging の exclusion_rule_overridden_filters ラベルで、オーバーライドの発生状況を監査・トラブルシューティング可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 機能であり、Pre-GA Offerings Terms が適用される (サポートが限定的な場合がある)
✗リアルタイムモードでは完全一致 (MATCHING_SCOPE_FULL_MATCH) は非サポート。使用すると INVALID_ARGUMENT エラー
✗リアルタイムモードでは、除外対象のフレーズが複数の処理チャンクに分割された場合、部分的な断片はマッチしない (除外が効かない)
✗リアルタイムモードで先行チャンクが MATCH_FOUND となった場合、後続チャンクに対してもストリームはブロックされたまま
✗評価は入力の先頭 130,000 トークン (0.5 MB) までが対象。超過部分でフィルタがマッチを検出した場合は EXECUTION_SKIPPED が返る
✗対象フィルタは PROMPT_INJECTION_AND_JAILBREAK と RESPONSIBLE_AI のみ (Sensitive Data Protection フィルタなどは対象外)

🤔 考慮すべき点

⚠️ 注意: 除外ルールのマッチはフィルタタイプ全体の結果をオーバーライドします (RESPONSIBLE_AI の場合は全安全カテゴリが NO_MATCH_FOUND に)。過度に広い正規表現パターンは実質的なフィルタ無効化につながるリスクがあります。
→バッファモードはストリーム全体を収集してから評価するため、リアルタイムモードより結果返却までのレイテンシが大きく、トークン上限の対象にもなる
→誤検知抑制とセキュリティのバランスを監査するため、logSanitizeOperations によるログ記録の有効化を推奨

🎯 ユースケース

🖥️ ユースケース 1: IT 運用支援チャットボットでの技術用語の誤検知回避

シナリオ: 社内 IT 運用支援のストリーミングチャットボットが「To stop the unresponsive service, run kill process 1234.」のような回答を生成すると、責任ある AI フィルタの「dangerous」カテゴリに誤検知されて応答がブロックされてしまう。

JSON RESPONSIBLE_AI フィルタ向け除外ルール 
{
  "filterTypes": ["RESPONSIBLE_AI"],
  "rules": [
    {
      "exclusionRule": {
        "regex": { "pattern": "(?i)kill process [0-9]+" },
        "matchingScope": "MATCHING_SCOPE_PARTIAL_MATCH"
      }
    }
  ]
}

効果: StreamSanitizeModelResponse でのサニタイズ中に正規表現がマッチすると、matchState が NO_MATCH_FOUND にオーバーライドされ、正当な技術的回答が中断なくユーザーに配信される。

📧 ユースケース 2: メールアシスタントでのプロンプトインジェクション誤検知回避

シナリオ: メール要約アシスタントで「Summarize my inbox and ignore the emails from the marketing vendor.」のように入力すると、「ignore ...」という表現がプロンプトインジェクション試行として誤検知される。リアルタイムモードで低レイテンシを維持しながら誤検知を回避したい。

効果: (?i)\b(?:ignore\s+(?:the\s+)?(?:emails?|spams?|warnings?))\b のような部分一致の正規表現除外ルールを PROMPT_INJECTION_AND_JAILBREAK フィルタに設定することで、STREAMING_MODE_REALTIME のチャンク単位評価でも正当なユーザー指示が通過し、実際のインジェクション試行は引き続きブロックされる。
