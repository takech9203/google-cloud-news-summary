📝 概要

2026 年 11 月 18 日、Google Cloud は Apigee hybrid v1.17.4 をリリースしました。パッチリリースのためコンテナイメージは Helm チャートに統合されており、Helm チャートでアップグレードするとイメージも自動更新されます (手動でのイメージ変更は通常不要)。

最大の新機能は、ランタイムコンポーネント (apigeeIngressGateway、connectAgent、ingressGateways、istiod、mart、mcpServer、redis、redis.envoy、runtime、synchronizer、watcher) に対する Kubernetes Pod Topology Spread Constraints のサポートです。Pod をアベイラビリティゾーンやノード間に分散配置 (maxSkew: 1) でき、overrides.yaml でグローバル設定またはコンポーネント単位の設定が可能です。

さらに、JavaCallout ポリシーで実行されるカスタム Java コードを含む Apigee ランタイムにおける CVE-2026-114938 の緩和、Message Processor のメモリリーク修正、LLMTokenQuota ポリシーのトークンカウント修正、synchronizer の pollInterval 設定が無視される問題の修正など、運用上重要な修正が多数含まれます。本番運用中のすべてのユーザーにアップグレードが推奨されるリリースです。

❌ Before (アップデート前の課題)

  • ランタイム Pod の Topology Spread Constraints を overrides.yaml から構成できず、ゾーン障害時の可用性設計の選択肢が限られていた
  • Apigee ランタイム (JavaCallout のカスタム Java コードを含む) に CVE-2026-114938 の脆弱性が存在
  • プロキシデプロイ・環境リロード・削除時に Message Processor でメモリリークが発生 (OASValidation 仕様の重複保持、環境ロードリソースやデバッグセッションマネージャーの未解放、HealthMonitorServiceImpl の登録残留)
  • LLMTokenQuota がセマンティックキャッシュから返されたレスポンスにもトークンをカウントし、クォータを不必要に消費
  • apigee-env Helm チャートとオペレーターが synchronizer の pollInterval 設定を無視

✅ After (アップデート後の改善)

  • topologySpreadConstraints (グローバル) / <component>.topologySpreadConstraints (個別) で maxSkew: 1 のゾーン・ノード分散配置が可能に
  • CVE-2026-114938 を緩和 (バグ ID: 586658318)。既存 JavaCallout コードの変更は不要
  • メモリリークが修正され、デプロイ・リロード反復時のメモリ安定性が向上 (バグ ID: 579213551)
  • キャッシュ応答はトークン数ゼロとしてカウントされ、analytics に ai_llm_response_token_count を記録しない (バグ ID: 576697209)
  • pollInterval 設定が正しく反映 (60 秒未満は 60 秒に引き上げ) (バグ ID: 572875915)

💡 ポイント: v1.17.4 では、overrides.yaml で定義した Topology Spread Constraints に基づき、Kubernetes スケジューラが Apigee hybrid のランタイム Pod をアベイラビリティゾーン・ノード間に偏りなく (maxSkew: 1) 分散配置します。これにより単一ゾーン障害時の影響を最小化できます。

🚀 主要機能・修正内容

1. 🆕 Kubernetes Pod Topology Spread Constraints のサポート (新機能)
  • 対象コンポーネント: apigeeIngressGateway、connectAgent、ingressGateways、istiod、mart、mcpServer、redis、redis.envoy、runtime、synchronizer、watcher
  • Pod をアベイラビリティゾーンおよびノード間に分散配置 (maxSkew: 1)
  • overrides.yaml の topologySpreadConstraints プロパティでグローバルに有効化・カスタマイズ可能
  • <component>.topologySpreadConstraints でコンポーネント単位のオーバーライドも可能
2. 🔒 セキュリティ修正: CVE-2026-114938 の緩和 (バグ ID: 586658318)
  • JavaCallout ポリシーで実行されるカスタム Java コードを含む Apigee ランタイムの脆弱性を緩和
  • 顧客側でコールアウトコードの変更は不要
3. 🧠 Message Processor のメモリリーク修正 (バグ ID: 579213551)
  • プロキシデプロイ、環境リロード、環境削除時のメモリリークを修正
  • コンパイル済み OASValidation 仕様をコンテンツハッシュで共有
  • 置き換えられた・失敗した環境ロードのリソースおよびデバッグセッションマネージャーを解放
  • ヘルスモニタ登録解除時に HealthMonitorServiceImpl の登録を適切に削除
4. 🤖 LLMTokenQuota ポリシーのトークンカウント修正 (バグ ID: 576697209)
  • SemanticCacheLookup によるセマンティックキャッシュからのレスポンスにトークンをカウントしていた問題を修正
  • キャッシュ応答はトークン数ゼロとしてカウントされ、analytics に ai_llm_response_token_count を記録しない
5. 🔄 synchronizer の pollInterval 設定の修正 (バグ ID: 572875915)
  • apigee-env Helm チャートとオペレーターが synchronizer.pollInterval、envs[].pollInterval、envs[].components.synchronizer.pollInterval を無視していた問題を修正
  • 設定値が有効になり、60 秒未満の値は 60 秒に引き上げられる

📄 overrides.yaml の設定例 (Topology Spread Constraints)

YAML overrides.yaml — グローバル / コンポーネント単位の設定 
# グローバル設定: すべての対象ランタイムコンポーネントに適用
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway

# コンポーネント単位のオーバーライド例

  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: ScheduleAnyway

ステップ 1: v1.17.4 へのアップグレード

Bash Apigee オペレーターのアップグレード 
# Helm チャートのリポジトリを v1.17.4 に更新し、各チャートをアップグレード
# (パッチリリースのためイメージは Helm チャートに統合されており、自動的に更新される)
helm upgrade operator apigee-operator/ \
  --install \
  --namespace APIGEE_NAMESPACE \
  --atomic \
  -f overrides.yaml

詳細な手順は公式ドキュメント「Upgrading Apigee hybrid to v1.17.4」を参照してください。新規インストールの場合は「The big picture」から開始します。

# overrides.yaml に topologySpreadConstraints を追加した後、

💼 ビジネス面

✓可用性の向上: ランタイム Pod がゾーン間に均等分散されるため、単一ゾーン障害時でも API トラフィック処理を継続しやすくなり、SLA 達成に寄与
✓セキュリティリスクの低減: CVE-2026-114938 への対応により、JavaCallout を利用するカスタムロジックを含むランタイムのリスクが緩和
✓AI コストの適正化: セマンティックキャッシュヒット時にトークンクォータを消費しなくなり、LLM プロキシのクォータ管理が実際の LLM 消費量と一致

🔬 技術面

✓宣言的な配置制御: Kubernetes 標準の Topology Spread Constraints を overrides.yaml から宣言的に管理でき、既存の tolerations や nodeSelector と組み合わせた柔軟なスケジューリングが可能
✓運用の安定性: Message Processor のメモリリーク修正により、頻繁なプロキシデプロイや環境リロードを行う CI/CD 環境でのメモリ圧迫・再起動リスクが減少
✓設定の確実な反映: synchronizer の pollInterval が正しく反映され、構成変更の同期間隔を意図通りに制御可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Topology Spread Constraints の対象は apigeeIngressGateway、connectAgent、ingressGateways、istiod、mart、mcpServer、redis、redis.envoy、runtime、synchronizer、watcher のランタイムプール系ワークロードであり、Cassandra (StatefulSet) は対象外
✗synchronizer の pollInterval に 60 秒未満の値を設定しても、60 秒に引き上げられる

🤔 考慮すべき点

⚠️ゾーン分散を有効化する場合、各ゾーンに十分なノードリソースがないと Pod のスケジューリングに影響する可能性があるため、whenUnsatisfiable の挙動 (厳格に配置不可とするか、ベストエフォートとするか) を含めて事前に検証環境で確認する
⚠️パッチリリースとはいえセキュリティ修正 (CVE-2026-114938) を含むため、計画的かつ早期のアップグレードを推奨
⚠️overrides.yaml はアップグレードや構成変更のたびに使用されるため、バージョン管理されたリポジトリでの管理を徹底する

🎯 ユースケース

🏦 ユースケース 1: マルチゾーン構成での API ゲートウェイ可用性強化

シナリオ: 金融系サービスの API 基盤として Apigee hybrid を GKE のリージョナルクラスタ (3 ゾーン) で運用しており、ゾーン障害時にも API 処理能力の大幅な低下を避けたい。

YAML 実装例: overrides.yaml 
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway

ingressGateways:
  - name: prod-ingress
    topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway

効果: runtime や ingress gateway の Pod がゾーン間で偏りなく配置され、1 ゾーン喪失時でも残りのゾーンでトラフィックを処理でき、可用性が向上する。

🤖 ユースケース 2: LLM プロキシでのセマンティックキャッシュとトークンクォータの併用

シナリオ: Apigee hybrid を LLM API のゲートウェイとして利用し、SemanticCacheLookup でキャッシュヒット率を高めつつ、LLMTokenQuota でテナントごとのトークン消費を制限している。

効果: v1.17.4 以降、キャッシュから返されたレスポンスはトークン数ゼロとして扱われるため、実際には LLM を呼び出していないリクエストでクォータが消費されず、テナントへの公平なクォータ適用とコスト削減効果の最大化が実現できる。

🔁 ユースケース 3: 頻繁なプロキシデプロイを行う CI/CD 環境の安定化

シナリオ: 開発環境で 1 日に何十回もプロキシのデプロイや環境リロードを実施しており、Message Processor のメモリ使用量が徐々に増加して定期的な再起動が必要だった。

効果: メモリリーク修正 (バグ ID: 579213551) により、デプロイ・リロードを繰り返してもメモリ使用量が安定し、運用負荷と予期しない再起動のリスクが低減する。

💰 料金

Apigee hybrid 自体のソフトウェアアップデートに追加料金は発生しません。Apigee の料金はサブスクリプション (Standard/Enterprise 等) または従量課金 (Pay-as-you-go) モデルに基づきます。詳細は Apigee 料金ページ を参照してください。

📌 まとめ

Apigee hybrid v1.17.4 は、CVE-2026-114938 の緩和を含むセキュリティ修正と、Message Processor のメモリリークや LLMTokenQuota のトークンカウントなど運用に直結するバグ修正を含む重要なパッチリリースです。

新たにサポートされた Pod Topology Spread Constraints により、ランタイムコンポーネントのゾーン・ノード分散を宣言的に制御でき、可用性設計の幅が広がります。

Apigee hybrid v1.17 系を運用中の場合は、検証環境での確認を経て早期に v1.17.4 へアップグレードし、マルチゾーンクラスタでは topologySpreadConstraints の導入を検討することを推奨します。
