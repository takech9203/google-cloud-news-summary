📌 概要

Google DeepMind が開発した AI コードセキュリティエージェント CodeMender v0.7.0 がリリース。 脆弱性スキャン (cm find)、PoC エクスプロイトによる実証検証 (cm verify)、修正パッチの自動生成 (cm fix) を ローカル CLI とクラウド側推論エンジンの連携で実行するエージェントのメンテナンスリリースである。

❌ Before (アップデート前の課題)

  • 長時間スキャン・修復中のネットワーク瞬断で CLI セッションが不安定になり、処理が中断される可能性
  • ディレクトリ除外ルールが設定ファイルと CLI フラグで統一されておらず、管理に一貫性がない
  • cm report で DISMISSED (却下済み) が誤って OPEN として分類
  • 子ワーカープロセスの内部セッションログ書き込みでサンドボックス権限拒否エラーが発生
  • サンドボックスポリシーにリポジトリルート外 (隣接ディレクトリ) へのトラバーサルを許す余地

✅ After (v0.7.0 での改善)

  • 自動再接続と一時的エラー回復により長時間ワークフロー中の CLI セッションの安定性が向上
  • 除外ルールが scan_config.exclude_dirs に標準化され、設定ファイルと CLI フラグ間で一貫した管理が可能に
  • DISMISSED ファインディングが正しく分類され、トリアージ状況を正確に把握可能に
  • 内部セッションログのディスク書き込みを抑止し、権限拒否エラーを解消
  • ポリシー強化でリポジトリルート外へのトラバーサル・ファイル参照を防止

ローカル CLI がクラウド側のエージェントと連携してスキャン・検証・修復を行うワークフローにおいて、v0.7.0 では CLI とエージェント間の ネットワークストリームの回復性、除外設定の統一、サンドボックスの境界制御がそれぞれ強化された。

⚡ 主要機能・変更点

🔄 1. ネットワークストリームの回復性 (Network stream resilience)

→自動再接続と一時的エラーからの回復により、CLI セッションの安定性が向上
→長時間実行されるスキャン・修復ワークフロー中のネットワーク瞬断による処理中断リスクを低減
→セッションデータの最大 7 日間保持による「再開」に頼らず、処理を継続できるケースが増加

📄 2. 設定の統一性 (Configuration uniformity)

→ディレクトリ除外ルールを設定ファイルと CLI スキャンフラグの間で scan_config.exclude_dirs の下に標準化
→node_modules、vendor、dist、bin などの依存関係・ビルド成果物の除外を一元管理
→除外設定はスキャンのレイテンシとトークン消費の削減に直結し、一貫した管理が運用効率に寄与

🐛 3. バグ修正 (3 件)

✓cm report の分類修正: DISMISSED ファインディングがサマリーテーブルで誤って OPEN と分類される問題を修正
✓サンドボックス権限エラーの解消: 子ワーカープロセスの内部セッションログのディスク書き込みを抑止し、権限拒否エラーを解決
✓サンドボックスコマンドポリシーの強化: リポジトリルート外の隣接ディレクトリへのディレクトリトラバーサル・ファイル参照を防止

🛠️ 設定方法

✅ 前提条件

✓Google Cloud プロジェクトで必要な API と IAM ロールを設定済みであること
✓CodeMender CLI バイナリをインストールし、Application Default Credentials (ADC) で認証済みであること
✓スキャン対象のソースコードをワークスペースに配置済みであること

1️⃣ ステップ 1: CLI を最新バージョンに更新

公式ドキュメントの手順に従い、CodeMender CLI を v0.7.0 に更新する。

Bash バージョン確認 
# バージョン確認
cm --version

2️⃣ ステップ 2: ディレクトリ除外設定を確認・移行

config.yaml のディレクトリ除外ルールが scan_config.exclude_dirs の下に標準化されたため、既存の除外設定を確認する。

YAML .codemender/config.yaml (例) 
# .codemender/config.yaml (例)
scan_config:
  exclude_dirs:
    - node_modules
    - vendor
    - dist
    - bin
💡 ポイント: CLI スキャンフラグとの間で除外ルールが統一されるため、設定ファイル側の記述を確認しておく。

3️⃣ ステップ 3: スキャンとレポートの動作確認

Bash スキャンとレポートの確認 
# 対象モジュールをスキャン
cm find ./src/auth/

# レポートで DISMISSED / OPEN の分類が正しいことを確認
cm report

💡 メリット

💼 ビジネス面

✓長時間スキャンの運用信頼性向上: ネットワーク瞬断による処理中断が減ることで、大規模コードベースに対するスキャン・修復ジョブの再実行コストとトークン消費の無駄を削減
✓正確なトリアージ状況の把握: cm report の分類修正により、却下済みファインディングが未対応として二重カウントされず、セキュリティ対応の進捗管理の精度が向上

⚙️ 技術面

✓設定管理の一元化: scan_config.exclude_dirs への標準化により、設定ファイルと CLI フラグ間の除外ルールの不整合を解消
✓サンドボックス境界の強化: リポジトリルート外へのディレクトリトラバーサル防止により、AI エージェントがローカルでコマンドを実行する際の安全性が向上
✓CI/CD パイプラインの安定化: ヘッドレス実行時にもネットワーク回復性の恩恵を受けられ、自動化パイプラインでの失敗率低減が期待できる

⚠️ デメリット・制約事項

🚧 制限事項

•CodeMender は Preview 段階の製品であり、Pre-GA Offerings Terms が適用される
•スキャンは 10〜50 ファイル程度のバッチまたは対象モジュール単位での実行が推奨されている

🤔 考慮すべき点

→除外ルールの標準化に伴い、既存の config.yaml で独自の除外設定を運用している場合は、scan_config.exclude_dirs 形式への整合を確認する必要がある
→サンドボックスポリシーの強化により、リポジトリルート外のファイル参照に依存していたビルド・テストプロセスは、project_paths などで明示的にアクセスパスを許可する構成を検討する必要がある

🎯 ユースケース

🌙 ユースケース 1: 大規模モノレポの夜間フルスキャン

シナリオ: 数百モジュールを含むモノレポに対して、CI/CD パイプラインから夜間に CodeMender のスキャンを実行。従来はネットワークの一時的な障害でセッションが中断し、翌朝に再実行が必要になるケースがあった。

Bash ヘッドレス実行例 
# ヘッドレス実行 (自動再接続により長時間ジョブの安定性が向上)
cm find ./services/payments/ -y

✅ 効果: 自動再接続と一時的エラー回復により長時間ジョブの完走率が向上し、再実行によるトークン消費と運用工数を削減できる。

📈 ユースケース 2: トリアージ済みファインディングの進捗レポート

シナリオ: セキュリティチームが cm report のサマリーテーブルを使って脆弱性対応の進捗を経営層に報告。従来は DISMISSED が OPEN として集計され、未対応件数が実際より多く見えていた。

✅ 効果: v0.7.0 では DISMISSED が正しく分類されるため、レポートを手動補正することなく正確な対応状況を報告できる。
