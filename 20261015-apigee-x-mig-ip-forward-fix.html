🔧 Apigee X: MIG スタートアップスクリプトの
IP フォワーディング設定永続化の修正

☁️ Apigee X ✅ 修正 (Fixed) 🌐 ネットワーキング
📅 リリース日: 2026-10-15
🐞 Bug ID: 466116259

📝 概要

外部トラフィックを Apigee にルーティングする MIG (マネージドインスタンスグループ) のスタートアップスクリプトが更新されました。 カーネルパラメータ net.ipv4.ip_forward が /etc/sysctl.d/ に書き込まれるようになり、 再起動や OS アップデートで設定がリセットされてもトラフィック転送が停止しなくなります。

MIG ベースの northbound ルーティングは、VPC ピアリング構成の Apigee で外部アプリケーションロードバランサからのトラフィックを Apigee インスタンスへ中継する標準的な構成です。 MIG の VM 自体はユーザー管理 (スケーリング、パッチ適用、メンテナンスはユーザー責任) ですが、トラフィックルーティング用のスタートアップスクリプトは Apigee が提供しており、今回はこの提供スクリプトが修正されました。

❌ Before (アップデート前の課題)

  • net.ipv4.ip_forward の設定が永続化されず、MIG インスタンスの再起動や OS アップデートでリセットされることがあった
  • 設定がリセットされると、ロードバランサから Apigee へのトラフィック転送が停止し、API トラフィックに影響する可能性があった

✅ After (アップデート後の改善)

  • net.ipv4.ip_forward が /etc/sysctl.d/ に書き込まれ、再起動・OS アップデート後も IP フォワーディング設定が維持される
  • 無関係な iptables NAT ルールには変更を加えないため、既存ネットワーク設定への副作用がない
⚠️ 重要: 修正は既存インスタンスに自動では反映されません。インスタンスの次回の再起動または再作成時に適用されます。MIG ベースのルーティングで外部トラフィックを受けているすべての Apigee X ユーザーが対象です。

外部クライアントからのリクエストはグローバル外部アプリケーションロードバランサを経由して MIG に到達し、MIG の VM が Apigee インスタンスへトラフィックを転送します。 今回の修正により、転送に必要な net.ipv4.ip_forward が /etc/sysctl.d/ に永続化され、再起動後も転送が継続されます。

🛠️ 主要な修正内容

1️⃣ net.ipv4.ip_forward の永続化

MIG 用スタートアップスクリプトが net.ipv4.ip_forward を /etc/sysctl.d/ に書き込むように変更。再起動や OS アップデートでカーネルパラメータがリセットされても、インスタンスがトラフィック転送を停止しなくなった。

2️⃣ 無関係な iptables NAT ルールへの非干渉

スクリプトは無関係な iptables NAT ルールを変更しない。MIG VM 上でユーザーが独自に設定している NAT ルールに影響を与えない。

3️⃣ 適用タイミング

既存インスタンスには自動適用されない。インスタンスが次回再起動または再作成されたタイミングで修正が反映される。

🔄 運用上の対応 (修正の反映方法)

既存の MIG インスタンスは 次回の再起動または再作成時 に修正されたスタートアップスクリプトの動作を取り込みます。 修正を能動的に反映したい場合は、MIG のインスタンスを再作成します。

Bash MIG のインスタンスをローリング置換して修正を反映する例 
# MIG のインスタンスをローリング置換して修正を反映する例
gcloud compute instance-groups managed rolling-action replace $MIG_NAME \
  --project $PROJECT_ID --region $REGION
💡 ヒント: MIG は通常複数台 (ドキュメントの手順では最小 2 台) で構成されるため、ローリング置換によりトラフィックへの影響を抑えながら反映できます。

⚖️ メリット / デメリット・制約事項

👍 メリット

💼 ビジネス面
✓可用性リスクの低減: 再起動・OS アップデート起因の API トラフィック断リスクが解消され、API 基盤の安定性が向上
✓運用負荷の軽減: 再起動後の IP フォワーディング設定の手動復旧が不要に
🔧 技術面
✓設定の永続化: /etc/sysctl.d/ への書き込みで OS 標準の仕組みによりカーネルパラメータを維持
✓副作用のない修正: 無関係な iptables NAT ルールに手を加えず、既存のカスタムネットワーク設定と共存

⚠️ 制約・考慮点

🚧 制限事項
✗修正は既存インスタンスに自動反映されず、再起動または再作成が必要
✗対象は MIG ベースの northbound ルーティング構成のみ (Private Service Connect ベースの構成では MIG が不要)
🤔 考慮すべき点
→MIG の VM はユーザー管理のため、修正の反映タイミング (再起動・再作成) はユーザー側でコントロールが必要
→長期的には、MIG ベース構成から Private Service Connect ベースの northbound ルーティングへの移行も選択肢 (公式移行手順あり)

🎯 ユースケース

💡 ユースケース 1: OS アップデートを安全に実施したい運用チーム

シナリオ: MIG VM の定期的な OS パッチ適用や再起動を実施すると、IP フォワーディング設定がリセットされて API トラフィックが停止するリスクがあった。

効果: 設定が /etc/sysctl.d/ に永続化されるため、再起動を伴うメンテナンスを行ってもトラフィック転送が継続され、安心してパッチ運用ができる。

💡 ユースケース 2: 過去にトラフィック断を経験した環境の恒久対策

シナリオ: MIG インスタンスの再起動後に Apigee へのトラフィックが流れなくなる事象が発生し、暫定対処をしていた。

Bash ローリング置換で全インスタンスを再作成し、修正済みスクリプトの動作を反映 
gcloud compute instance-groups managed rolling-action replace $MIG_NAME \
  --project $PROJECT_ID --region $REGION

効果: 恒久対策として修正済みの動作が反映され、以降の再起動・OS アップデートでも転送が維持される。

🔗 関連サービス・機能

🖥️ Compute Engine (MIG / インスタンステンプレート)

northbound ルーティング用 VM の実行基盤。スタートアップスクリプトはインスタンステンプレートのメタデータで指定される。

⚖️ Cloud Load Balancing (グローバル外部アプリケーションロードバランサ)

外部クライアントからのトラフィックを MIG バックエンドに分散する。

🔌 Private Service Connect (PSC)

MIG を使わない northbound ルーティングの代替手段。MIG ベース構成からの移行手順も公式に提供されている。

🌐 VPC ネットワークピアリング

MIG ベース構成の前提となる、ユーザー VPC と Apigee VPC の接続方式。

📌 まとめ

MIG ベースの northbound ルーティングを使用する Apigee X 環境における、再起動・OS アップデート起因のトラフィック転送停止という運用リスクを恒久的に解消する修正です。 修正はインスタンスの再起動または再作成時に反映されるため、該当構成を運用しているチームは、計画的なローリング置換などで早期に修正を取り込むことを推奨します。
