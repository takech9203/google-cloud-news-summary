Looker (Google Cloud core) GA (一般提供) データリネージは Preview

📚 Knowledge Catalog による
メタデータの自動カタログ化・取り込みが GA

リリース日: 2026-10-21

💡 概要

Looker (Google Cloud core) のメタデータを Knowledge Catalog (旧 Dataplex Catalog) に自動的にカタログ化・取り込みする機能が一般提供 (GA) になりました。本番環境の LookML、LookML プロジェクト、ダッシュボードのメタデータをインデックス化・保存・管理でき、組織全体のデータ資産とその関係性を単一のビューで把握できます。

今回の GA では、より詳細な粒度のメタデータ (ディメンション / メジャーの定義、デフォルトクエリ、リレーションシップ) のサポートが追加されたほか、新しいアセットタイプとして LookML ダッシュボード、LookML ダッシュボードエレメント、エージェントが追加されました。BI 環境のメタデータをデータカタログに統合することで、データディスカバリ、影響分析、変更管理をデータガバナンス基盤上で一元的に行えます。

📌 注意: BigQuery から Looker ダッシュボードまでのデータフローを可視化するデータリネージ統合は、引き続き Preview として提供されます。

❌ Before (アップデート前の課題)

  • Preview (Pre-GA) 提供で「現状のまま」かつ限定的なサポートのため、本番ワークロードでの採用判断が難しかった
  • 取り込まれるメタデータの粒度が限られ、ディメンション / メジャー定義、デフォルトクエリ、リレーションシップは対象外だった
  • LookML ダッシュボード、LookML ダッシュボードエレメント、エージェントはカタログ化の対象外だった

✅ After (アップデート後の改善)

  • 自動カタログ化・取り込みが GA となり、本番環境のデータガバナンス基盤として安心して利用可能に
  • ディメンション / メジャー定義、デフォルトクエリ、リレーションシップなど詳細なメタデータを検索・参照可能に
  • LookML ダッシュボード、LookML ダッシュボードエレメント、エージェントの 3 アセットタイプが新たに対象となりカバレッジ拡大

Looker (Google Cloud core) がファーストパーティコネクタ経由で LookML・ダッシュボード・エージェントのメタデータをリージョナル Cloud Storage に発行し、バッチ同期プロセスで Knowledge Catalog に取り込まれます。取り込まれたメタデータは検索・ガバナンス・影響分析に活用でき、データリネージは Preview として提供されます。

🚀 主要機能

1️⃣ メタデータの自動カタログ化・取り込み (GA)
→Looker (Google Cloud core) インスタンスでデフォルトで有効。設定変更なしでメタデータが自動的に Knowledge Catalog へ取り込まれる
→LookML モデルを本番環境に push すると、ビュー / Explore の詳細、フィールド定義、モデル情報が自動同期
→ダッシュボードのタイトル、所有者、使用統計などのメタデータもカタログに反映
→内部バッチ同期は約 4 時間ごとに実行、Looker からのデータはおよそ 1 時間ごとに Knowledge Catalog へ反映
2️⃣ より詳細な粒度のメタデータのサポート 🆕
✓ディメンション / メジャーの定義
✓デフォルトクエリ
✓リレーションシップ (アセット間の関係性)
3️⃣ 新しいアセットタイプ 🆕
✓LookML ダッシュボード
✓LookML ダッシュボードエレメント
✓エージェント
→既存の対象アセット (Looker インスタンス、ダッシュボード、ダッシュボードエレメント、Look、LookML プロジェクト、モデル、Explore、ビュー) に加えて拡充
4️⃣ Knowledge Catalog での検索・キュレーション
→検索ページで System フィルタ (Looker) や Type エイリアスを使ってアセットを絞り込み可能
→system=Looker AND type=DASHBOARD のようなキーワード検索や自然言語検索に対応
→アスペクト (ビジネスメタデータ) を Looker アセットに付与し、ビジネス観点での検索・キュレーションが可能
5️⃣ データリネージ統合 (引き続き Preview)
→BigQuery → LookML ビュー / Explore → ダッシュボード / Look という end-to-end のデータフローを可視化
→スキーマ変更前の下流影響分析や、経営ダッシュボードの指標の上流監査に活用可能

🛠️ 設定方法

📋 前提条件

✓Looker (Google Cloud core) インスタンスをホストする Google Cloud プロジェクトで Dataplex API (dataplex.googleapis.com) が有効であること
✓閲覧ユーザーに roles/dataplex.viewer と roles/looker.schemaViewer が付与されていること

ステップ 1: 統合の状態確認・有効化

統合はデフォルトで有効です。無効化されている場合は、以下のコマンドで有効化します。

Bash 
gcloud looker instances update INSTANCE_NAME --catalog-integration-enabled
💡 ヒント: 有効化後、Looker データが Knowledge Catalog で利用可能になるまで最大 1 日かかります。無効化する場合は --no-catalog-integration-enabled フラグを使用します (無効化後も既存メタデータはカタログに残りますが、更新は停止します)。

ステップ 2: メタデータ閲覧用ロールの付与

Bash 
gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member=PRINCIPAL_TYPE:PRINCIPAL_ID \
  --role=roles/looker.schemaViewer
⚠️ 注意: roles/looker.schemaViewer はプロジェクトレベルで付与する必要があり、付与されたユーザーは統合が有効なプロジェクト内のすべての Looker (Google Cloud core) インスタンスのメタデータを閲覧できます。

ステップ 3: Knowledge Catalog で検索

Google Cloud コンソールの Knowledge Catalog の検索ページで、Filters パネルの System セクションから Looker を選択するか、検索フィールドにクエリを入力します。

Text 
system=Looker AND type=DASHBOARD

💼 ビジネス面

✓データディスカバリの向上: 組織全体のダッシュボード、Explore、ビューを横断検索でき、既存のデータ資産の再利用が促進される
✓ガバナンスの一元化: BigQuery などのデータ資産と Looker の BI 資産を同じカタログで管理でき、アスペクトによるビジネスメタデータの付与・検索が可能
✓GA による本番採用の安心感: Pre-GA 提供条件から GA に昇格したことで、エンタープライズのデータガバナンス基盤として本番採用しやすくなった

🔧 技術面

✓設定不要の自動同期: デフォルトで有効であり、LookML の本番 push に追随してメタデータが自動的にカタログへ同期される
✓詳細メタデータによる理解促進: ディメンション / メジャーの定義やリレーションシップまでカタログで確認でき、セマンティックレイヤーの理解や変更管理が容易になる
✓影響分析: データリネージ (Preview) と組み合わせることで、BigQuery のスキーマ変更が影響するダッシュボードを事前に特定できる

⚠️ デメリット・制約事項

🚧 制限事項

✗Looker のメタデータはカタログに即時反映されない (バッチ同期は一定間隔で実行され、データ更新は約 1 時間ごと)
✗この統合用のパブリック API は公開されていない
✗データリネージ統合は引き続き Preview であり、以下の制限がある
  • リネージは BigQuery データソースのみサポート
  • オブジェクトレベル (テーブル、ビュー、Explore、ダッシュボード) のリネージのみで、カラムレベルのリネージは未サポート
  • リネージの同期には通常 4 時間、最大 8 時間程度かかる
  • 複雑なカスタム SQL (Liquid テンプレート、複雑な JOIN を含む派生テーブルなど) を使う LookML は完全にパースされず、ノードが分断される場合がある

🤔 考慮すべき点

⚡roles/looker.schemaViewer はプロジェクトレベルで付与する必要があり、付与されたユーザーはプロジェクト内の統合が有効な全インスタンスのメタデータを閲覧できる
⚡リネージでは LookML 内の SQL テーブル参照の大文字・小文字が BigQuery テーブルと厳密に一致している必要がある (不一致だと下流リネージが表示されない)
⚡VPC Service Controls を利用している場合は、Dataplex API を制限付きサービスとして構成し、メタデータ転送に使用される内部 Cloud Storage リソースへのアクセスを許可する必要がある

🎯 ユースケース

📐 ユースケース 1: スキーマ変更前の影響分析

シナリオ: データエンジニアが BigQuery テーブルのカラム削除を計画しており、どの Looker ダッシュボードに影響するか事前に確認したい。

  1. Knowledge Catalog で対象の BigQuery テーブルを検索
  2. Lineage タブでリネージグラフを開く (Preview)
  3. 下流の LookML ビュー → Explore → ダッシュボードを特定
  4. ノードの Aspects セクションで所有者 (メールアドレス) を確認し、事前に連絡

✅ 効果: ダッシュボードの破損を未然に防ぎ、変更管理プロセスを安全に実施できる。

🔍 ユースケース 2: 組織横断の BI 資産ディスカバリ

シナリオ: データアナリストが新しい分析を始める前に、既存のダッシュボードやディメンション / メジャーの定義を調べて重複開発を避けたい。

✅ 効果: system=Looker の検索でダッシュボードや Explore を横断的に発見でき、GA で追加されたディメンション / メジャー定義により指標の意味をカタログ上で直接確認できる。

データリネージ (Preview) で上流データソースとして可視化される。BigQuery テーブルから Looker ダッシュボードまでのデータフローを追跡可能

サービス境界内での統合をサポート

📝 まとめ

Looker (Google Cloud core) のメタデータ自動カタログ化が GA となり、ディメンション / メジャー定義などの詳細メタデータと LookML ダッシュボード・エージェントを含む新アセットタイプが加わったことで、BI レイヤーまで含めたデータガバナンスを Knowledge Catalog 上で実現できるようになりました。

Looker (Google Cloud core) を利用中の組織は、統合がデフォルトで有効である点と roles/looker.schemaViewer の権限設計を確認した上で、カタログ検索と (Preview の) リネージによる影響分析の活用を検討することを推奨します。
