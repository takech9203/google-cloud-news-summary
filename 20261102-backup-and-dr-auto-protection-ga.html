☁️ Backup and DR ✅ GA (一般提供)

🛡️ 自動保護ポリシーによる Compute Engine リソース保護の自動化が GA

📅 リリース日: 2026-11-02

📝 概要

Backup and DR Service で、Compute Engine のインスタンスとディスクの保護を大規模に自動化する 自動保護ポリシー (Auto-protection policies) が一般提供 (GA) になりました。 ユーザー定義のリソースラベル (例: env=prod) を条件に、複数プロジェクトにまたがる対象リソースを自動識別し、 指定したバックアッププランを自動割り当てします。

ラベルを付与するだけで新規リソースも自動的に保護対象となり、「ポリシーベース」のデータ保護ガバナンスを組織全体で実現できます。 バックアップ管理者とワークロード管理者の双方に専用ビューが提供され、マッチ数・保護済み数・失敗数を一元監視できます。

❌ Before: 手動割り当ての課題
  • バックアッププランはリソース単位で手動選択が必要。数百〜数千台の VM フリートでは運用負荷が大きい
  • 新規作成リソースは管理者が気付くまで未保護となり、保護漏れのリスクがあった
  • 複数プロジェクトを一貫したルールで保護する仕組みがなく、プロジェクトごとに個別運用
✅ After: ラベルベースの自動化
  • リソースラベルを条件とするポリシーで、合致リソースへバックアッププランを自動割り当て
  • 同一組織内の複数ワークロードプロジェクトをポリシーバインディングで一元管理
  • ラベル付きの新規リソースを自動検出し、保護漏れを構造的に防止
  • コンソール / gcloud CLI / API から作成・編集・監視が可能 (マッチ / 保護 / 失敗数を可視化)

アップデート前はリソースごとに手動でバックアッププランを割り当てる必要がありましたが、 アップデート後は自動保護ポリシーがラベルに基づいて複数プロジェクトのリソースを自動検出し、 バックアッププランを割り当ててバックアップ Vault に保存します。

⚡ 主要機能

🏷️ 1. ラベルベースの自動保護ポリシー

ユーザー定義のリソースラベル (例: env=prod) を条件 (criteria) として、合致する Compute Engine インスタンスまたは ディスクに指定のバックアッププランを自動割り当て。ポリシー作成後、マッチするリソースの識別と関連付けのスケジューリングが自動実行されます (初回は通常最大 2 時間、場合によっては最大 8 時間)。

🔗 2. プロジェクト横断の保護 (ポリシーバインディング)

バックアップ Vault プロジェクトで作成したポリシーに、同一組織内の複数のワークロードプロジェクトをバインディングとして追加可能。 プロジェクトが異なる場合は、バックアップ Vault サービスエージェントにオペレーターロールを付与することでクロスプロジェクト保護を実現します。

👀 3. 管理者ロールごとの可視化ビュー

✓バックアップ管理者: バックアップ Vault プロジェクトでポリシー一覧・詳細・保護対象リソース (マッチ数 / 保護済み数 / 失敗数) を確認
✓ワークロード管理者: 「このプロジェクトに適用されたポリシー」タブから、適用ポリシー・条件ラベル・バックアッププラン・ステータスを確認

🧰 4. 複数の管理インターフェース

Google Cloud コンソール、gcloud CLI (gcloud beta backup-dr auto-protection-policies など)、 API でポリシーの作成・更新・削除・閲覧が可能です。

🛠️ 設定方法

✅ 前提条件

✓バックアップ Vault プロジェクト (Vault・バックアッププラン・ポリシーを格納) とワークロードプロジェクト (保護対象リソースを格納) を用意し、課金を有効化
✓両プロジェクトで Backup and DR API と Compute Engine API を有効化
✓バックアップ Vault と、保護対象のリソースタイプ・リージョンに対応するバックアッププランを作成
✓必要な IAM ロールを付与
🏷️ ラベル付与
→
📋 ポリシー作成
→
🔗 プロジェクトをバインド
→
📊 保護状況を確認
1
保護対象リソースにラベルを付与する
Bashラベル付与
# Compute Engine インスタンスにラベルを付与
gcloud compute instances add-labels INSTANCE_NAME \
  --labels=env=prod \
  --zone=ZONE

# ディスクにラベルを付与
gcloud compute disks add-labels DISK_NAME \
  --labels=env=prod \
  --zone=ZONE

保護したいリソースに、ポリシーの条件として使用するキーと値のペア (例: env=prod) を付与します。

2
自動保護ポリシーを作成する
Bashポリシー作成
gcloud beta backup-dr auto-protection-policies create POLICY_NAME \
  --location=LOCATION \
  --criteria=key=env,values=prod \
  --backup-plan-details="resource-type=compute.googleapis.com/Instance,backup-plan=projects/BACKUP_VAULT_PROJECT/locations/LOCATION/backupPlans/BACKUP_PLAN" \
  --description="Production VM auto-protection"

ラベル条件、リソースタイプ、適用するバックアッププランを指定してポリシーを作成します。

3
ワークロードプロジェクトをポリシーにバインドする
Bashバインディング作成
gcloud beta backup-dr auto-protection-bindings create BINDING_NAME \
  --auto-protection-policy=POLICY_NAME \
  --location=LOCATION \
  --scope=projects/WORKLOAD_PROJECT_ID

保護したいワークロードプロジェクトごとに繰り返します。作成後、ポリシーが自動的にマッチするリソースを識別し、バックアッププランの関連付けをスケジュールします。

4
保護状況を確認する
Bash保護状況の確認
# ポリシーの一覧表示
gcloud beta backup-dr auto-protection-policies list --location=LOCATION

# ポリシーにマッチしたリソースの一覧表示
gcloud beta backup-dr binding-matching-resources list \
  --auto-protection-policy-binding=BINDING_NAME \
  --auto-protection-policy=POLICY_NAME \
  --location=LOCATION

マッチ数・保護済み数・保護失敗数をコンソールまたは CLI で確認できます。

💡 メリット

💼 ビジネス面
✓データ保護ガバナンスの強化: 「本番リソースは必ずバックアップされる」状態をポリシーとして担保し、コンプライアンス対応が容易に
✓運用コストの削減: リソース単位の手動割り当てが不要になり、大規模フリートの運用工数を大幅削減
✓保護漏れリスクの低減: 新規リソースも自動保護され、ヒューマンエラーによる未設定を構造的に防止
⚙️ 技術面
✓宣言的なデータ保護: 既存のラベル管理メカニズムを流用でき、IaC やオートスケール環境と親和性が高い
✓クロスプロジェクト対応: Vault プロジェクトに管理を集約しつつ、複数ワークロードプロジェクトを一元保護
✓ロール分離に対応した可視性: 管理者がそれぞれの視点で適用状況 (マッチ / 保護済み / 失敗) を監視可能

⚠️ デメリット・制約事項

🚫 制限事項
  • 対応リソースは Compute Engine インスタンスとディスクのみ (Cloud SQL などその他のワークロードは対象外)
  • 1 つのポリシーは単一リージョンのみ保護。複数リージョンはリージョンごとにポリシーを作成する必要あり
  • 同一プロジェクトに複数ポリシーを適用する場合、すべてのポリシーで同じラベルキーを使用する必要あり (例: env=prod と env=test は可、env=prod と tier=gold の併用は不可。別プロジェクトなら異なるキーも可)
  • Terraform でのポリシー管理は今後のリリースで対応予定
🤔 考慮すべき点
  • 初回のポリシー構成と保護スケジューリングには通常最大 2 時間 (最大 8 時間) かかり、作成直後は即時保護されない
  • ポリシーバインディングはワークロードプロジェクトごとに作成が必要。新規プロジェクト追加時の運用フローに組み込むこと
  • ラベル付与の規律 (命名規則、付与の徹底) が自動化の実効性を左右するため、組織のラベリング標準の事前整備が重要
  • クロスプロジェクト構成ではサービスエージェントへのオペレーターロール付与が必要で、IAM 設計の考慮が必要

🎯 ユースケース

🏭 ユースケース 1: 本番環境 VM フリートの保護の標準化

シナリオ: 複数のプロジェクトに数百台の本番 VM が存在し、チームごとに VM が随時作成される。全本番 VM に日次バックアップ (Vault 保存) を確実に適用したい。

Bash実装例
# 本番 VM 向けポリシーを作成し、ワークロードプロジェクトをバインド
gcloud beta backup-dr auto-protection-policies create prod-vm-protection \
  --location=asia-northeast1 \
  --criteria=key=env,values=prod \
  --backup-plan-details="resource-type=compute.googleapis.com/Instance,backup-plan=projects/backup-admin-prj/locations/asia-northeast1/backupPlans/daily-vault-plan"

gcloud beta backup-dr auto-protection-bindings create team-a-binding \
  --auto-protection-policy=prod-vm-protection \
  --location=asia-northeast1 \
  --scope=projects/team-a-prod

効果: env=prod ラベルを付けて作成された VM は自動的に日次バックアップの対象となり、チームごとの設定漏れがなくなる。

🔄 ユースケース 2: オートスケール・IaC 環境での保護の自動追従

シナリオ: Terraform で VM とディスクを頻繁に作成・破棄する環境で、作成のたびにバックアップ設定を人手で追加するのが追いつかない。

効果: IaC テンプレートでラベルを付与しておけば、プロビジョニングされたリソースが自動的にポリシーにマッチして保護される。バックアップ設定をデプロイパイプラインから分離でき、保護の追従が自動化される。

🏢 ユースケース 3: バックアップ管理の集約とロール分離

シナリオ: 情報システム部門がバックアップ Vault プロジェクトを一元管理し、各事業部のワークロードプロジェクトに保護ポリシーを適用したい。事業部側でも自分たちのリソースの保護状況を確認したい。

効果: 情シスは Vault プロジェクトでポリシーと保護状況 (マッチ / 保護済み / 失敗) を一元監視し、各事業部は「適用されたポリシー」ビューで自部門のリソース保護状況を確認できる。責任分界を保ちつつガバナンスを効かせられる。

💰 料金

自動保護ポリシー自体の追加料金に関する個別の記載は確認できませんでした。Backup and DR Service は月次の使用量ベースで課金され、 バックアップ管理料金とバックアップ Vault のストレージ料金などが発生します。自動保護ポリシーで保護されたリソースには、 通常のバックアッププラン適用時と同様に Backup and DR および Compute Engine (インスタンス・ディスク) の料金が適用されます。

🎁 無料トライアル: Backup and DR には 30 日間の無料トライアル (プロジェクトごとに 1 回、バックアップ Vault あたり 50 TiB まで) が用意されており、評価に利用できます。

→ 詳細: Backup and DR の料金

🌏 利用可能リージョン

公式ドキュメントにリージョン一覧の個別記載は確認できませんでした。ポリシー作成時にリソースが存在するリージョンを選択する方式であり、 1 ポリシーは単一リージョンを対象とします。最新のリージョン対応状況は Backup and DR ドキュメント を参照してください。

🧩 関連サービス・機能

→Compute Engine: 保護対象となるインスタンスとディスク。リソースラベルがポリシーのマッチング条件として使用される
→バックアップ Vault (Backup and DR): 自動割り当てされたバックアッププランのバックアップデータを、イミュータブル (変更不可)・インデリブル (削除不可) な形で保存する
→バックアッププラン (Backup and DR): スケジュール、保存先、保持期間を定義する。自動保護ポリシーはこのプランをマッチしたリソースに割り当てる
→IAM: ポリシー管理・適用承認・クロスプロジェクト保護に必要なロール (roles/backupdr.admin、roles/backupdr.computeEngineOperator など) を制御する
→Resource Manager (ラベル): リソースラベルの運用標準が本機能の実効性の基盤となる

📌 まとめ

自動保護ポリシーの GA により、Compute Engine インスタンスとディスクのバックアップ保護を 「リソース単位の手動作業」から「ラベルベースのポリシー駆動」へ転換できるようになりました。 大規模・マルチプロジェクト環境でバックアップの保護漏れに課題を持つ組織は、まずラベリング標準を整備した上で、 本番環境向けの自動保護ポリシーの導入を検討することを推奨します。
