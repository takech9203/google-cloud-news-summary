☁️ Google Cloud Managed Service for Apache Airflow (旧 Cloud Composer)

Orchestration Pipelines が一般提供 (GA) に

GA (一般提供) Orchestration Pipelines Data / AI パイプライン
リリース日: 2026-08-28

📌 概要

Managed Service for Apache Airflow (旧 Cloud Composer) の Orchestration Pipelines が GA になりました。 Google Cloud 上のデータ / AI パイプラインを対象とした、宣言型のオーケストレーション & 自動デプロイフレームワークです。

📝 YAML DSL で
パイプラインを宣言
→
🚀 デプロイ・バージョニングは
フレームワークが処理
→
🌀 Airflow DAG を
自動生成・実行

デプロイされたパイプラインは、ランナー環境として指定した Managed Airflow 環境 (Gen 2 / Gen 3、Airflow 2 / Airflow 3 対応) 上で実行されます。 DAG ファイルは自動生成されるため、ユーザーが DAG を直接管理する必要はありません。 主な対象は、データパイプラインの CI/CD を確立したいデータエンジニアやデータサイエンティストです。

❌ Before (アップデート前の課題)
  • Preview (Pre-GA) 提供で Pre-GA Offerings Terms が適用され、サポートが限定的な場合があった
  • Python で DAG を記述し、DAG ファイルの配置・更新・バージョン管理を自分で行う必要があった
  • パイプライン定義とアセットの一体的なバージョン管理・ロールバックや、環境ごとのデプロイ構成管理を自前で構築する必要があった
✅ After (アップデート後の改善)
  • GA となり、本番ワークロードでの利用に適した一般提供ステータスに
  • YAML ベースの宣言型 DSL で定義。Airflow DAG は自動生成・管理され、直接管理が不要に
  • 定義とアセットを「パイプラインバンドル」として単一ユニットでバージョン管理・デプロイ。ロールバックや特定リランの再現が容易に
  • GitHub Actions 連携の validate / deploy ワークフローがスキャフォールディングとして提供され、CI/CD を短時間で確立可能に

Git リポジトリ上の YAML パイプライン定義が GitHub Actions で検証・デプロイされ、Managed Airflow ランナー環境上で自動生成された DAG として BigQuery、Managed Service for Apache Spark、Dataform / dbt などの各エンジンにアクションを実行する構成です。

⚙️ 主要機能

📝 1. 宣言型 DSL (YAML ベース)
  • パイプライン・アクション・デプロイ構成を YAML で定義 (1 パイプライン = 1 ファイル)
  • pipelineId、description、owner、tags、defaults、triggers (cron)、actions で構成
  • 失敗時のメール通知 (onPipelineFailure、SendGrid 構成が必要) に対応
🌍 2. デプロイ環境 (Deployment Environments)
  • 開発 / ステージング / 本番など複数環境を定義可能
  • 環境ごとに個別のランナー環境とアーティファクトバケットを構成
  • ランナーは Managed Airflow 環境 (Gen 2 / Gen 3、Airflow 2 / Airflow 3)
📦 3. パイプラインバンドルによるバージョン管理
  • 定義 + アセットをバージョン付きパッケージとして単一ユニットでデプロイ
  • すべてのデプロイを追跡。ロールバックや実行の再現が容易
  • ローカルバンドル (開発用、md5 ベース ID) と Git コミット SHA にひも付くデプロイ (CI/CD 用) の 2 方式
🔌 4. 多様なアクションと実行エンジン
  • アクション: pyspark / notebook / sql / python / pipeline (Dataform / dbt)
  • エンジン: BigQuery、Managed Spark (既存 / エフェメラル / サーバーレス)、Airflow ワーカー、Dataform
  • 必要リソース (例: 特定構成の Spark クラスタ) の自動プロビジョニングも可能
🔐 5. 変数置換・シークレット管理と検証ツール
  • カスタム変数・環境変数・GitHub シークレットによるパラメータ化
  • デプロイ前に構文・セマンティクスをチェックする検証コマンドを提供
  • cron スケジュール実行と手動実行の両方をサポート

📄 パイプライン定義の例 (SQL アクション + BigQuery エンジン)

YAML orchestration-pipeline.yaml 
modelVersion: "1.0"
pipelineId: "sql-on-bigquery"
description: "A pipeline with a BigQueryInsertJob task."
runner: "airflow"
owner: "data-eng-team"
defaults:
  projectId: "example-project"
  location: "us-central1"
  executionConfig:
    retries: 0
triggers:
  - schedule:
      interval: "0 5 * * *"
      startTime: "2025-10-01T00:00:00"
      endTime: "2026-10-01T00:00:00"
      catchup: false
      timezone: "UTC"
actions:
  - sql:
      name: "run_bigquery_insert_job_select"
      query:
        path: "sql-scripts/count_rows.sql"
      engine:
        bigquery:
          location: "US"
          destinationTable: "example-project.example_dataset.example_table_query_results"

🛠️ 設定方法

💡 前提条件:
  • ランナー環境となる Managed Airflow 環境を作成しておく (作成には約 25 分。コンソール / gcloud CLI / Terraform で作成可能)
  • Cloud Composer API と、パイプラインアクションで使用するサービスの API を有効化
  • アーティファクト保存用の Cloud Storage バケットを用意
1

パイプラインバンドルのスキャフォールディングを初期化

Bash スキャフォールディングの初期化 (1 回のみ実行) 
gcloud beta orchestration-pipelines init PIPELINE_NAME \
  --environment DEPLOYMENT_ENVIRONMENT \
  --composer-environment RUNNER_ENVIRONMENT \
  --artifacts-bucket ARTIFACTS_BUCKET_NAME \
  --project PROJECT_ID \
  --region REGION \
  --service-account SERVICE_ACCOUNT

リポジトリ内に、パイプライン定義の例 (orchestration-pipeline.yaml)、デプロイ構成 (deployment.yaml)、 GitHub Actions の検証・デプロイワークフロー (.github/workflows/validate.yaml / deploy.yaml) が生成されます。 初期化は 1 回のみ実行 (再実行すると既存の構成変更が上書きされます)。

2

パイプラインをデプロイ

Bash デプロイ (開発用: ローカルバンドル) 
# 開発用: ローカルバンドルのデプロイ (デプロイ後は常に一時停止状態、手動トリガーで実行)
gcloud beta orchestration-pipelines deploy \
  --environment DEPLOYMENT_ENVIRONMENT \
  --local

# CI/CD 用: コミット済み変更のデプロイ (バンドル ID が Git コミット SHA にひも付く)

デプロイ完了後、バンドル ID / バージョン ID とともに各パイプラインのステータス (例: Pipeline 'example-pipeline': [OK] (Status: HEALTHY)) が出力されます。

✨ メリット

💼 ビジネス面

✓本番利用への適合: GA により本番のデータ / AI パイプラインへの適用判断がしやすく
✓チーム開発の標準化: Git + GitHub Actions によりソフトウェア開発と同様のプロセスで変更管理を統制
✓監査性とロールバック: すべてのデプロイがバージョンとして追跡され、問題時のロールバックや過去の実行の再現が容易

⚙️ 技術面

✓DAG 管理からの解放: YAML から DAG が自動生成され、DAG ファイルの記述・配置・更新が不要
✓インフラの抽象化: BigQuery / Managed Spark / Dataform / dbt をまたぐ処理を単一の宣言型定義で記述
✓環境分離: 開発 / ステージング / 本番を別ランナー環境・別バケットで構成し、安全なリリースフローを実現

⚠️ デメリット・制約事項

🚧 制限事項

✗pyspark / notebook アクションは全アクション共有の 1 つの requirements.txt のみサポート。uv によるパッケージビルドは Windows 非対応。プリビルドバイナリを持つ Python パッケージのみサポート
✗sql アクションの query キーでのインライン定義には制限がある (ドキュメントの Limitations を参照)
✗ローカルバンドルは常に一時停止状態でデプロイされ、スケジュールでは起動しない (手動トリガーのみ)
✗バンドルの「現在のバージョン」は常に 1 つのみ。現在のバージョン以外のパイプラインは手動トリガー不可
🤔 考慮すべき点
  • 利用可能なランナーは Managed Service for Apache Airflow のみ。Managed Airflow のクォータとシステム上限がすべて適用される
  • Git プロバイダは GitHub のみ記載。他の Git ホスティングとの CI/CD 連携は明記されていない
  • 古い Composer バージョンでは orchestration-pipelines パッケージの手動インストールが必要
  • 失敗時のメール通知にはランナー環境での SendGrid メールサービスの構成が必要

🎯 ユースケース

1️⃣ データパイプラインの CI/CD 確立

シナリオ: BigQuery の SQL 変換と PySpark ジョブから成る日次 ETL パイプラインを、コードレビューを経て安全に本番リリースしたい。

スクリプトを GitHub 管理

(validate.yaml)
→
🚀 merge で自動デプロイ
(deploy.yaml)
→
🔄 コミット SHA で
ロールバック可能

効果: 変更のたびに自動で検証・デプロイされ、リリースの一貫性と監査性が確保される。

2️⃣ マルチエンジンのデータ / AI ワークフロー統合

シナリオ: BigQuery での SQL 変換、Managed Spark でのノートブック実行、Dataform ワークフローの実行を 1 つのパイプラインとして依存関係付きでオーケストレーションしたい。

効果: dependsOn によるアクション間の依存定義だけで、複数エンジンにまたがる処理を単一の宣言型パイプラインとして管理でき、個別の Airflow DAG やオペレーターの実装が不要になる。

3️⃣ 開発・ステージング・本番の環境分離

シナリオ: 開発中のパイプラインをステージング用ランナー環境で検証してから本番環境へ昇格させたい。

効果: デプロイ環境ごとに個別のランナー環境・アーティファクトバケット・変数を構成でき、--local デプロイ (常に一時停止・手動トリガーのみ) を使った安全な開発検証と、コミットベースの本番デプロイを分離できる。

💰 料金

Orchestration Pipelines 自体の個別料金は公式ドキュメントに記載されていません。 ランナー環境として使用する Managed Service for Apache Airflow 環境のコストが発生し、Managed Airflow の料金体系が適用されます。 また、アクションの実行先である BigQuery や Managed Service for Apache Spark などの各サービスの利用料金が別途発生します。

詳細: Managed Service for Apache Airflow の料金ページ

VS Code / Antigravity からのパイプライン開発・デプロイを支援する拡張機能。

📝 まとめ

Orchestration Pipelines の GA により、Managed Airflow 上のデータ / AI パイプラインを YAML の宣言型定義と Git ベースの CI/CD で管理する手法が本番利用可能になりました。 Airflow DAG を直接管理する運用からの移行や、複数エンジンにまたがるパイプラインの標準化を検討しているチームは、 GitHub 上の公式コード例とスキャフォールディング (gcloud beta orchestration-pipelines init) から評価を始めることを推奨します。
