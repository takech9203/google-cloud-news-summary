📋 概要

Config Connector v1.152.0 がリリースされた。ComputeReservation の共有設定管理、 Direct Reconciliation の拡張、および複数のバグ修正が含まれている。

Config Connector は Kubernetes Resource Model (KRM) を使用して Google Cloud リソースを宣言的に管理するためのオープンソース Kubernetes アドオンである。 今回のリリースでは、Direct Controller への移行が継続的に進められており、Terraform ベースのコントローラーからの脱却による性能向上と信頼性改善が図られている。

Before / After

❌ Before (v1.151.x 以前)

  • ComputeReservation で予約共有設定を KRM で管理不可
  • ComputeForwardingRule のターゲット情報を status から確認不可
  • ComputeReservation / FirestoreIndex は Terraform ベースで高レイテンシ
  • SQLInstance で大文字小文字差分による不要なリコンシリエーション
  • Preview Tool が型付きリソースでクラッシュ

✅ After (v1.152.0)

  • spec.shareSettings でプロジェクト間予約共有を宣言的に管理
  • status.target で実際のターゲット情報を確認可能
  • Direct Reconciler opt-in で高速化・リソース効率改善
  • 大文字小文字を区別しない比較で不要なループ解消
  • Preview Tool の安定性向上

⚡ 主要機能

📌 1. ComputeReservation: spec.shareSettings フィールド追加

Compute Engine の予約リソースにおいて、プロジェクト間共有設定を KRM マニフェストから宣言的に管理可能に。

  • shareType で共有タイプ (SPECIFIC_PROJECTS など) を指定
  • projectMap で共有先プロジェクトを定義
  • 組織内の複数プロジェクト間で予約容量を効率的に配分する設定を GitOps ワークフローに組み込み可能

🔍 2. ComputeForwardingRule: status.target フィールド追加

Forwarding Rule の status に target フィールドが追加。Google Cloud API から返される実際のターゲットリソース情報を確認可能に。

  • spec.target で設定した参照が API 側でどのリソースに解決されたかを status から読み取り可能
  • トラブルシューティング時にターゲットの整合性を容易に検証

⚡ 3. Direct Reconciliation サポート拡張

対象リソース: ComputeReservation, FirestoreIndex

  • cnrm.cloud.google.com/reconciler: direct アノテーションで opt-in
  • Google Cloud Go SDK を直接使用し、Terraform の変換オーバーヘッドを排除
  • リコンシリエーションレイテンシの改善、CPU/メモリ消費の削減
  • 構造化された差分レポートの提供

📝 設定方法

前提条件

  • GKE クラスタに Config Connector がインストールされていること (v1.152.0 以上)
  • Workload Identity Federation for GKE が有効であること
  • 対象リソースの管理に必要な IAM 権限がサービスアカウントに付与されていること

Step 1: Config Connector のアップグレード

Bash 
# 最新のオペレーターバンドルをダウンロード
gcloud storage cp gs://configconnector-operator/1.152.0/release-bundle.tar.gz release-bundle.tar.gz
tar zxvf release-bundle.tar.gz

# オペレーターを適用
kubectl apply -f operator-system/configconnector-operator.yaml

Step 2: Direct Reconciler を opt-in で有効化 (ComputeReservation)

YAML 
apiVersion: compute.cnrm.cloud.google.com/v1beta1
kind: ComputeReservation
metadata:
  name: shared-reservation
  annotations:
    cnrm.cloud.google.com/reconciler: direct
spec:
  zone: asia-northeast1-a
  shareSettings:
    shareType: SPECIFIC_PROJECTS
    projectMap:
    - keyRef:
        external: "shared-project-id"
      value:
        projectIDRef:
          external: "shared-project-id"
  specificReservation:
    count: 5
    instanceProperties:
      machineType: n2-standard-8
      minCpuPlatform: "Intel Ice Lake"

Step 3: FirestoreIndex で Direct Reconciler を使用

YAML 
apiVersion: firestore.cnrm.cloud.google.com/v1beta1
kind: FirestoreIndex
metadata:
  name: my-index
  annotations:
    cnrm.cloud.google.com/reconciler: direct
spec:
  collectionRef:
    name: my-collection
  fields:
  - fieldPath: "field1"
    order: ASCENDING
  - fieldPath: "field2"
    order: DESCENDING

👍 メリット

🎯 ビジネス面

マルチプロジェクト予約管理の効率化

shareSettings フィールドにより、組織内の複数プロジェクト間で Compute Engine の予約容量を一元的かつ宣言的に管理でき、コスト最適化のガバナンスが強化される。

運用の可視性向上

status.target フィールドにより、Forwarding Rule の実際のルーティング状態を Kubernetes リソースの status から直接確認でき、問題の検出・解決が迅速化される。

🚀 技術面

リコンシリエーション性能の向上 - Direct Controller は Terraform 変換レイヤーを経由しないため、レイテンシが大幅に短縮され、CPU/メモリ消費も削減。

構造化された差分レポート - cnrm-controller-manager ログに構造化された差分を出力し、リコンシリエーションループの原因特定が容易に。

GitOps ワークフローとの親和性向上 - より多くのインフラ設定を KRM マニフェストとして Git リポジトリで管理可能に。

⚠️ 制約事項・注意点

⚠️ 制限事項:
  • Direct Reconciler は opt-in 方式であり、既存リソースに自動適用されない (アノテーション追加が必要)
  • shareSettings.shareType は Immutable - 共有タイプ変更にはリソース再作成が必要
  • Direct Controller はすべてのリソースタイプで利用可能ではない (段階的移行中)
💡 考慮すべき点:
  • Direct Controller 切り替え後は Terraform ベースと異なる動作の可能性あり - テスト環境での検証を推奨
  • FirestoreIndex は v1.123.0 で state-into-spec 設定に起因するリグレッションがあったため、既存環境では動作確認が重要
  • 本バージョンへのアップグレードは最大 3 マイナーバージョン前からのロールバックが可能 (namespaced mode)

💡 ユースケース

🎯 ユースケース 1: マルチチームでの予約容量共有

シナリオ: 大規模組織で、プラットフォームチームが Compute Engine の予約を一括購入し、複数のプロダクトチームのプロジェクトに共有配分する。

効果: 予約の共有設定が GitOps で管理され、チームの追加・削除も Pull Request ベースで監査可能に。Direct Reconciler により設定変更の反映も高速化。

🎯 ユースケース 2: Firestore インデックスの大規模管理

シナリオ: マイクロサービスアーキテクチャで多数の Firestore コレクションのインデックスを管理しており、リコンシリエーションの遅延がデプロイパイプラインのボトルネックになっている。

効果: Direct Reconciler を opt-in することで、インデックス作成・更新のリコンシリエーションが高速化され、CI/CD パイプラインのデプロイ時間が短縮。構造化された差分ログにより、インデックス変更の追跡も容易に。
