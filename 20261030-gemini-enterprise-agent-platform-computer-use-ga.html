🖥️ Computer use ツールが GA に

Human-in-the-Loop (HITL) 安全ガバナンスを導入 — GUI 操作エージェントをエンタープライズ水準の統制で本番展開

📋 概要

Computer use ツールは、Gemini モデルがスクリーンショットで画面を観察し、マウスクリック・スクロール・キーボード入力などの UI アクションを生成することで、ブラウザ・モバイル・デスクトップの GUI を操作するエージェントを構築できる機能です。フォーム入力の自動化、UI フローの自動テスト、Web サイトを横断した調査などに対応します。

GA リリースの目玉は、包括的な Human-in-the-Loop (HITL) 安全ガバナンスです。金融取引の完了や機密データの変更など、モデルが自律実行すべきでないアクションについて、実行前にエンドユーザーの確認を求めます。開発者は確認ポリシーを選択的にオーバーライドでき、組織管理者は組織ポリシー制約 vertexai.configurableComputerUseToolSafetyPolicies で開発者設定に優先する組織全体のガードレールを強制できます。

❌ Before (アップデート前の課題)

  • GUI を自律操作するエージェントは、金融取引や機密データ変更などの高リスクアクションを含むため、統制された形での本番利用が困難
  • HITL 確認の挙動をアプリケーション要件に合わせて細かく制御する公式な仕組みが限定的
  • 開発者ごとの安全設定を組織レベルで統一的に強制するガバナンス手段がなかった

✅ After (アップデート後の改善)

  • Computer use ツールが GA となり、本番ワークロードでの利用を正式サポート
  • disabled_safety_policies フィールドで 7 種類のデフォルト HITL 確認ポリシーを個別に設定・オーバーライド可能
  • 組織ポリシー制約により、開発者設定に優先する組織全体のガードレールを強制可能
💡 ポイント: 開発者の柔軟性と組織のガバナンスを両立させる 2 層構造により、エンタープライズ環境で GUI 操作エージェントを安全に本番展開するための基盤が整いました。対象はプラットフォームチーム、セキュリティ管理者、エージェント開発者です。

エージェントが Computer use ツールで UI アクションを生成すると、HITL 確認ポリシーが評価され、高リスクアクションにはユーザー確認が要求されます。開発者はポリシーを選択的にオーバーライドできますが、組織ポリシーのガードレールが常に優先されます。

⚡ 主要機能

🚀 1. Computer use ツールの GA 化

スクリーンショットによる画面観察と UI アクション (クリック、スクロール、キーボード入力など) の生成により、GUI 操作エージェントを構築。ブラウザ・モバイル・デスクトップのマルチ環境をサポート。各アクションにはモデルの意図 (reasoning) を説明する intent フィールドが付与されます。

👨‍💻 2. 開発者レベルの HITL 確認ポリシー設定

Computer use 設定の disabled_safety_policies フィールドに対象ポリシーを列挙することで、デフォルトの HITL 確認を選択的に無効化可能。GenerateContent API と Interactions API の両方で設定でき、HITL 確認機能は Gemini 3.5 Flash 以降のモデルで利用できます。

🏢 3. 組織レベルのガードレール (組織ポリシー制約)

制約 ID vertexai.configurableComputerUseToolSafetyPolicies により、組織管理者が Organization Policy Service を使い、開発者による HITL 確認の無効化を組織・フォルダ・プロジェクト単位で禁止可能。組織ポリシーは開発者レベルの設定に優先 (supersede) します。ポリシー変更の伝播には最大 1 時間かかります。

🔍 4. プロンプトインジェクション検出

Gemini 3.5 Flash 以降でサポートされるオプトイン機能。スクリーンショットにプロンプトインジェクション攻撃の可能性がないかを検査します (デフォルトは無効)。

🔧 技術仕様

🛡️ オーバーライド可能な HITL 確認ポリシー (7 種類)

ポリシー 対象アクション
FINANCIAL_TRANSACTIONS 金融取引の最終ステップの完了 (支払い、送金、マネーオーダー、サブスクリプションの開始・変更、予約の完了など)
SENSITIVE_DATA_MODIFICATION 医療・金融・行政記録などの機密情報の変更
COMMUNICATION_TOOL コミュニケーションツールへのアクセスや使用 (送信、共有、投稿など)
ACCOUNT_CREATION ユーザー/サービスアカウントを作成・プロビジョニングする登録・サインアップフローの操作
DATA_MODIFICATION ブラウザデータやファイルの変更・管理・共有・保存・送信・削除
USER_CONSENT_MANAGEMENT ユーザー同意ダイアログやバナーでの意思決定
LEGAL_TERMS_AND_AGREEMENTS 利用規約の同意、プライバシーポリシーダイアログ、法的通知など法的拘束力のある同意画面の操作

⌨️ 開発者レベルの設定例 (Python / GenerateContent API)

Python disabled_safety_policies の設定例 
generate_content_config = genai.types.GenerateContentConfig(
    tools=[
        types.Tool(
            computer_use=types.ComputerUse(
                environment=types.Environment.ENVIRONMENT_MOBILE,
                disabled_safety_policies=[
                    types.SafetyPolicy.FINANCIAL_TRANSACTIONS,
                    types.SafetyPolicy.COMMUNICATION_TOOL,
                ]
            )
        ),
    ],
)

✋ HITL 確認フロー (safety_decision)

モデルの応答に含まれる safety_decision が require_confirmation の場合、クライアントはアクション実行前にエンドユーザーの確認を取得する必要があります。ユーザーが承認した場合は、FunctionResponse に safety_acknowledgement: true を含めて返します。

JSON require_confirmation を含むモデル応答例 
{
  "function_call": {
    "name": "click_at",
    "args": {
      "x": 60,
      "y": 100,
      "safety_decision": {
        "explanation": "CAPTCHA チャレンジに遭遇しました。ユーザーによる操作が必要です。",
        "decision": "require_confirmation"
      }
    }
  }
}

🛠️ 設定方法

📌 前提条件

  • Google Cloud プロジェクトで Gemini Enterprise Agent Platform を利用可能であること
  • 組織ポリシーを設定する場合は、組織管理者権限 (Organization Policy 管理ロール) が必要
  • クライアント側でアクション実行ロジック (Playwright などによる UI 操作) を実装すること

📝 手順

1

開発者レベルで HITL 確認ポリシーを設定

Computer use 設定の disabled_safety_policies に、アプリケーション要件上オーバーライドしたいポリシーを列挙します。設定しないポリシーはデフォルトの HITL 確認が維持されます。

2

組織レベルのガードレールを設定 (管理者)

Google Cloud コンソールまたは gcloud CLI で組織ポリシーを作成します。変更の伝播には最大 1 時間かかる点に注意してください。

Bash 組織ポリシー制約の設定 
# Google Cloud CLI で組織ポリシー制約を設定
# 制約 ID: vertexai.configurableComputerUseToolSafetyPolicies
gcloud org-policies set-policy policy.yaml
3

クライアントで safety_decision をハンドリング

require_confirmation を受け取った場合にエンドユーザーへ確認を求め、承認時には FunctionResponse に safety_acknowledgement を含めて返すループを実装します。

⚠️ デメリット・制約事項

🚧 制限事項

✗HITL 確認機能は Gemini 3.5 Flash 以降のモデルでのみ利用可能
✗組織ポリシー変更の伝播には最大 1 時間かかる
✗アクション実行ロジック (クリック、入力などの実装) はクライアント側で開発する必要がある (function calling と同様のモデル)
✗プロンプトインジェクション検出はデフォルト無効のオプトイン機能

🤔 考慮すべき点

  • HITL 確認を無効化する場合、金融取引や機密データ変更が自律実行されるリスクを十分に評価すること
  • エージェントはサンドボックス化された環境 (サンドボックス VM、コンテナ、権限を制限したブラウザプロファイルなど) で実行することが公式に推奨
  • プロンプト、スクリーンショット、提案アクション、safety レスポンス、実行アクションの詳細ログを監査用に保持することを推奨
  • ナビゲーション先を制御するための許可リスト / ブロックリストの実装を推奨

🎯 ユースケース

🏦 ユースケース 1: 金融系業務での統制されたエージェント展開

シナリオ: 金融機関がバックオフィス業務 (レガシー Web システムへのデータ入力) を Computer use エージェントで自動化したいが、支払い実行などの高リスク操作は必ず人間の承認を必須としたい。

Text 実装例 
1. 組織管理者が vertexai.configurableComputerUseToolSafetyPolicies 制約で
   FINANCIAL_TRANSACTIONS と SENSITIVE_DATA_MODIFICATION の無効化を禁止
2. 開発者は他のポリシー (USER_CONSENT_MANAGEMENT など) のみ
   アプリ要件に応じてオーバーライド
3. クライアントは require_confirmation 受信時に承認 UI を表示

効果: 開発者の設定ミスや意図的な無効化があっても、組織ポリシーが優先されるため、金融取引には常に人間の確認が強制される。

🧪 ユースケース 2: Web / モバイルアプリの UI 自動テスト

シナリオ: QA チームがブラウザ・モバイル環境のユーザーフロー (サインアップ、購入フローなど) の自動テストを構築する。テスト環境では確認ダイアログを省略してテストを高速化したい。

効果: テスト用プロジェクトでは disabled_safety_policies で確認を省略して回帰テストを無人実行しつつ、本番プロジェクトには組織ポリシーでガードレールを適用する、といった環境ごとの使い分けができる。
