BigQuery GA (一般提供) Enterprise / Enterprise Plus 限定

📊 BigQuery リザベーション
Project caps と Principal ベースルーティングが GA

プロジェクト単位の上限設定と ID 単位のクエリルーティングで、リザベーションを分割せずにワークロードを制御
リリース日: 2026-11-11

📝 概要

BigQuery のワークロード管理 (リザベーション) に関する 2 つの機能が GA になりました。いずれも BigQuery Enterprise / Enterprise Plus エディションでのみ利用できます。

🧢 1. Project caps (スケジューリングポリシー)

リザベーション内でプロジェクトごとに「最大スロット数」と「最大同時実行クエリ数」の上限を設定。デフォルトのフェアスケジューリングをカスタマイズし、特定プロジェクトによるキャパシティの過剰消費を防止。リザベーションレベルのデフォルトと、アサインメントルール (Project cap) による個別オーバーライドの 2 段階で設定可能。

🔀 2. Principal ベースのリザベーションルーティング

アサインメントにオプションの principal プロパティを指定し、ユーザー・サービスアカウント・サードパーティ ID 単位でクエリのルーティング先リザベーションを制御。従来のリソース階層 (プロジェクト・フォルダ・組織) 単位より、きめ細かなワークロード分離が可能に。

❌ Before: アップデート前の課題

  • フェアスケジューリングではキャパシティを均等に分け合うため、特定プロジェクトのスロット消費や同時実行数に明示的な上限を設けられなかった
  • 特定プロジェクトの暴走的なクエリ実行が他プロジェクトの性能に影響するのを防ぐには、リザベーションを分割するしかなかった
  • アサインメントはプロジェクト・フォルダ・組織単位のみで、特定ユーザーや SA のクエリだけ別リザベーションに振り分けられなかった
  • ID ごとのワークロード分離には、ユーザーやワークロードごとにプロジェクトを分ける必要があった

✅ After: アップデート後の改善

  • プロジェクトごとの最大スロット数 (最小 100) と最大同時実行数を設定でき、1 つのリザベーションを複数プロジェクトで安全に共有可能に
  • リザベーションレベルのデフォルト + プロジェクト単位のオーバーライドの 2 段階で柔軟に制御
  • principal 指定でユーザー・SA・サードパーティ ID 単位のルーティング制御が可能に
  • 同一階層では principal 一致が汎用アサインメントより優先され、プロジェクト構成を変えずに ID ベースの分離を実現

⚙️ 主要機能

🧢 Project caps による上限設定

✓最大スロット数 (Maximum slots): 対象プロジェクトのスロット消費を制限。最小許容値は 100。厳密な制限ではなく近似的な上限として適用
✓最大同時実行数 (Maximum concurrency): 同時に許可されるクエリ数を制限。クエリの受付 (admission) 時のみ適用され、実行中のクエリはキャンセルされない。実行中クエリ数より低い値に変更した場合、新規クエリはキューイングされる

🪜 2 段階の設定レベル (デフォルトとオーバーライド)

✓リザベーションレベルのデフォルト: 「Project Concurrency」「Project Max Slots」を設定すると、アサインされたすべてのプロジェクトに適用
✓プロジェクト単位のオーバーライド: アサインメントルール (ルールタイプ「Project cap」) で特定プロジェクトの上限を個別に設定し、デフォルトを上書き

🔀 Principal ベースのリザベーションルーティング

✓アサインメント作成時に principal プロパティを指定すると、ジョブ実行者の ID でルーティング先を制御
✓対応 ID: Google アカウント (ユーザー) / サービスアカウント / Workforce Identity プールの単一 ID / Workload Identity プールの単一 ID
✓設定方法: コンソール (User フィールド) / SQL (CREATE ASSIGNMENT の principal オプション) / bq CLI (--principal フラグ)

🧭 アサインメントの評価ロジック

✓リソース階層 (プロジェクト → フォルダ → 組織) の順に評価
✓各階層では、まず principal 一致のアサインメントを確認し、なければ principal 未設定の汎用アサインメントを確認。どちらもなければ次の階層へ
⚠注意: principal 付きのフォルダレベルアサインメントより、principal なしのプロジェクトレベルアサインメントが優先される。プロジェクトレベルの汎用アサインメントがある環境では、同じプロジェクトレベルにユーザー専用アサインメントを作成すること

🛠️ 設定方法

📋 前提条件:
  • BigQuery Enterprise または Enterprise Plus エディションのリザベーションを使用していること
  • 管理プロジェクトに対する bigquery.reservations.create / bigquery.reservationAssignments.create 権限を持っていること
  • アサインメント対象リソースとリザベーションが同一組織・同一ロケーションにあること
1

リザベーションにデフォルトのスケジューリングポリシーを設定

コンソールの BigQuery > 管理 > Workload management からリザベーションを作成・編集し、Advanced settings で以下を設定します。これらはアサインされたすべてのプロジェクトに対するデフォルト値として機能します。

  • Override project concurrency: プロジェクトごとの同時実行クエリ数の上限
  • Override project max slots: プロジェクトごとのスロット消費の上限
2

特定プロジェクトに Project cap (オーバーライド) を作成

コンソールの Workload management > Assignment rules タブから、ルールタイプ「Project cap」を選択してプロジェクト・リザベーション・Max slots / Max concurrency を指定します。

Bash bq CLI での例 (プロジェクト単位のオーバーライドはジョブタイプを未設定にする) 
bq mk \
  --project_id=ADMIN_PROJECT_ID \
  --location=LOCATION \
  --reservation_assignment \
  --reservation_id=RESERVATION_NAME \
  --assignee_type=PROJECT \
  --assignee_id=TARGET_PROJECT_ID

Project cap の assignee はプロジェクトのみで、ジョブタイプは未設定 (JOB_TYPE_UNSPECIFIED) である必要があります。

3

Principal ベースのアサインメントを作成

SQL の CREATE ASSIGNMENT DDL で principal オプションを指定します。

SQL CREATE ASSIGNMENT での principal 指定 
CREATE ASSIGNMENT
  `ADMIN_PROJECT_ID.region-LOCATION.RESERVATION_NAME.ASSIGNMENT_ID`
OPTIONS (
  assignee = 'projects/PROJECT_ID',
  job_type = 'QUERY',
  principal = 'principal://goog/subject/user-a@example.com');

bq CLI の場合は --principal フラグを使用します。

Bash bq CLI での principal 指定例 
bq mk \
  --project_id=ADMIN_PROJECT_ID \
  --location=LOCATION \
  --reservation_assignment \
  --reservation_id=RESERVATION_NAME \
  --assignee_type=PROJECT \
  --assignee_id=PROJECT_ID \
  --job_type=QUERY \
  --principal='principal://iam.googleapis.com/projects/-/serviceAccounts/batch-sa@example.iam.gserviceaccount.com'
⚠️ 注意: アサインメント作成後は、少なくとも 5 分待ってからクエリを実行してください。待たない場合、クエリがオンデマンド料金で課金される可能性があります。

💪 メリット

💼 ビジネス面

✓リザベーション統合によるコスト最適化: ノイジーネイバー対策のためのリザベーション分割が不要になり、1 つの大きなリザベーションを安全に共有してスロット利用効率を向上
✓部門・チーム単位の公平なキャパシティ配分: 特定部門のワークロードが他部門の SLA に影響することを防止
✓GA による本番適用: Preview から GA に昇格し、本番環境のワークロード管理設計に正式に組み込み可能

🔧 技術面

✓ID ベースのワークロード分離: 同一プロジェクト内でも BI ツール用 SA、ETL パイプライン、アドホッククエリを別々のリザベーションへ
✓フェアスケジューリングの柔軟なカスタマイズ: デフォルトとオーバーライドの 2 段階制御で、きめ細かくかつ低管理負荷の運用
✓実行中クエリへの非破壊性: 同時実行数の上限は受付時のみ適用され、設定変更が実行中のクエリを中断しない
✓Workforce / Workload Identity 連携に対応: サードパーティ ID 基盤を利用する環境でも ID 単位のルーティングが可能

⚠️ デメリット・制約事項

🚧 制限事項

✗BigQuery Enterprise / Enterprise Plus エディション限定 (Standard エディションおよびオンデマンドでは利用不可)
✗最大スロット数は厳密な制限ではなく近似的な上限であり、最小値は 100
✗Project cap (オーバーライド) の assignee はプロジェクトのみで、フォルダ・組織には設定できない
✗ML_EXTERNAL ジョブのトレーニングフェーズにはプロジェクトレベルのスロット上限が適用されない
✗principal には単一 ID のみ指定可能で、グループは指定できない。ユーザー専用アサインメントはプロジェクトあたりデフォルト 100 件まで

🤔 考慮すべき点

  • 設定変更の反映に最大 1 分かかり、最大スロットのオーバーライド変更は新規クエリの開始後に有効になる
  • 同時実行数の上限を実行中クエリ数より下げると新規クエリはキューイングされるため、レイテンシ要件のあるワークロードでは注意が必要
  • principal なしのプロジェクトレベルアサインメントは、principal 付きのフォルダレベルアサインメントより優先される。プロジェクトレベルの汎用アサインメントが存在する場合、特定ユーザーを確実にルーティングするには同じプロジェクトレベルにユーザー専用アサインメントを追加する必要がある
  • アサインメント作成直後 (5 分以内) のクエリはオンデマンド課金になる可能性がある

🎯 ユースケース

📈 ユースケース 1: 全社共有リザベーションのノイジーネイバー対策

シナリオ: データ分析基盤チームが 5,000 スロットの Enterprise リザベーションを 20 のプロジェクトで共有。月初のレポート処理で特定プロジェクトがスロットを占有し、他プロジェクトのダッシュボード更新が遅延する問題が発生していた。

実装例:

Plan 設定方針 
1. リザベーションのデフォルトとして Project Max Slots = 1000、
   Project Concurrency = 20 を設定
2. レポート処理プロジェクトには Assignment rule (Project cap) で
   Max slots = 2000 の個別オーバーライドを設定
✅ 効果: どのプロジェクトも設定した上限を超えてスロットを消費できなくなり、リザベーションを分割することなくノイジーネイバー問題を解消。スロットの利用効率も維持できる。

🔀 ユースケース 2: 同一プロジェクト内での BI とバッチのワークロード分離

シナリオ: 1 つのデータウェアハウスプロジェクトに、Looker などの BI ツールが使うサービスアカウントと、夜間 ETL 用のサービスアカウント、アナリストのアドホッククエリが同居しており、ETL 実行中に BI ダッシュボードの応答が悪化する。

実装例:

SQL BI 用サービスアカウントの専用ルーティング 
-- BI 用サービスアカウントを低レイテンシ重視のリザベーションへ
CREATE ASSIGNMENT `admin-prj.region-asia-northeast1.bi-reservation.bi-sa-assign`
OPTIONS (
  assignee = 'projects/dwh-project',
  job_type = 'QUERY',
  principal = 'principal://iam.googleapis.com/projects/-/serviceAccounts/looker-sa@dwh-project.iam.gserviceaccount.com');

-- その他のクエリはプロジェクトレベルの汎用アサインメントで既定のリザベーションへ
✅ 効果: プロジェクトを分割することなく、ID 単位で BI・ETL・アドホックのワークロードを別々のリザベーションに分離でき、相互干渉を防止できる。

📌 まとめ

BigQuery のリザベーション管理に 「プロジェクト単位の上限 (Project caps)」 と 「ID 単位のルーティング (principal)」 という 2 つの強力な制御軸が GA として加わり、リザベーションを分割せずにノイジーネイバー対策とワークロード分離を実現できるようになりました。

Enterprise / Enterprise Plus エディションで複数プロジェクト・複数ワークロードがリザベーションを共有している環境では、INFORMATION_SCHEMA やリザベーションモニタリングで現状のスロット消費を把握した上で、デフォルトのスケジューリングポリシーと principal ベースのアサインメントの導入を検討することを推奨します。
