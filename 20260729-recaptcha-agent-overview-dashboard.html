reCAPTCHA / Google Cloud Fraud Defense GA (Feature)

🤖 Agent overview ダッシュボード

AI エージェントトラフィックを「検証済み」と「疑わしい」に分けて可視化
📅 リリース日: 2026-07-29

📌 概要

Google Cloud Fraud Defense (reCAPTCHA の進化形) のホームページに Agent overview ダッシュボード が追加。 自サイトに到達する AI エージェントや自動化ツールのトラフィック (エージェンティックトラフィック) を可視化し、 検証済みエージェント (verified agents) と 疑わしいエージェント (suspected agents) を区別して表示する。

狙いは「ショッピングアシスタントや検索インデクサーのような価値ある自動化トラフィックを妨げることなく、セキュリティポリシーを洗練させる」こと。 AI エージェントがユーザーの代理として商品を検索・比較・購入する時代に、「自動化 = すべてブロック」という前提は事業機会の損失につながる。 本ダッシュボードは、ブロック/許可の判断前に 「そもそも誰が来ているのか」を測定する可観測性レイヤー を提供する。

❌ Before: アップデート前の課題

  • 既存モニタリングはキー単位の Bots タブ (Score overview / Challenges) 中心で、エージェントの「身元」に着目したビューがなかった
  • 「正当な AI エージェント」と「悪意ある自動化」が低スコア側に混在し、集計値からは切り分け不能
  • どの AI エージェントが実際に訪問しているのか、識別名の一覧を把握する手段がなかった
  • 検証済みエージェント許可ポリシーの候補と流量を事前に見積もれなかった

✅ After: アップデート後の改善

  • エージェンティックトラフィックの全体像を 単一画面 で確認可能に
  • 検証済み / 疑わしいセッション数・ユニーク検証済みエージェント数 の 3 指標をスコアカードで提示
  • 時系列チャートを「検証済み (アイデンティティ別積み上げ)」と「疑わしい (集計)」で切り替え、上位エージェントを個別に識別
  • Web Bot Auth (WBA) と User-Agent / IP ベースの 2 方式の分類結果を可視化
  • 識別インフラ拡張に追随し、データ粒度が自動的に向上
💡 対象ユーザー: Web サイトのセキュリティ担当者、不正対策チーム、EC / メディアサイトの運用担当者。 2026-07-24 に Preview となった Policy Engine の CEL ルール (verified_bots 変数) と組み合わせることで、 「まず観測し、次にポリシー化する」 という運用サイクルが成立する。

エージェントからのリクエストは Web Bot Auth の署名検証、または User-Agent / IP ベースのアイデンティティ照合によって 「検証済み」「疑わしい」に分類され、Agent overview ダッシュボードで集計・可視化される。 観測結果は Policy Engine の CEL ルール設計へフィードバックできる。

🔢 1. Performance scorecards (パフォーマンススコアカード)

検証済み / 疑わしいエージェントセッションの総量と、検出された「個別の検証済みエージェントの数」(ユニーク数) をハイレベルな指標として表示。 選択期間のエージェンティック活動のサマリーとして機能する。

📈 2. Traffic chart (トラフィックチャート)

セッション量を表示する時系列チャート。チャートトグルで 2 つのビューを切り替え可能。

→Verified agents: 確認済みアイデンティティごとの積み上げ棒グラフ。上位エージェントを表示し、残りは Other verified agents に集約
→Suspected agents: エージェンティックな挙動を示すが公式検証されていない自動化トラフィックの集計ビュー

🗓️ 3. Time filters (期間フィルタ)

Last 30 days (過去 30 日間) または This month (今月) を選択してデータを表示。

🔐 4. エージェント検証方式の二階層構成

→Web Bot Auth (WBA): IP ベース検証を補強/置換する暗号学的標準。エージェントがリクエストに暗号署名を付与し、送信元 IP に依存せず身元を証明
→User-Agent / IP ベース: User-Agent 文字列と送信元 IP を検査して自動化エージェント (ボット、クローラー、スクリプト) を識別・検証する従来手法

🔄 5. 識別インフラの継続的拡張

Fraud Defense の識別インフラ拡張により、認識されるエージェントリストの拡大に伴いダッシュボードが自動的により多くのデータを取得。 No verified agent traffic detected yet と表示される場合は、トラフィックが追跡対象の検証済みアイデンティティリストに由来していないことを意味する。

📐 エージェント指標の定義

指標定義
Verified agent sessions
(検証済みエージェントセッション)		 公式に検証された AI エージェントによるセッション総数。Fraud Defense が身元と送信元を (暗号学的手法などで) 確認し、説明責任を担保。信頼できる自動化の量を把握する指標

(疑わしいエージェントセッション)		 HTTP ヘッダー等で自らエージェントと 自己申告 している、またはエージェンティックな挙動を示すが、身元を公式に検証できないセッションの総数

(ユニーク検証済みエージェント)		 検証された個別のエージェントアイデンティティの数。特定の正当なツールと一般的な自動化された悪用とを区別できる
セッション 1 回の Fraud Defense 保護対象インタラクション (a single Fraud Defense-protected interaction)

⚖️ 「検証済み」と「疑わしい」の本質的な違い

観点✅ Verified agents⚠️ Suspected agents
身元の根拠暗号署名 (WBA) または照合済みの User-Agent / IP自己申告ヘッダー、または挙動からの推定
なりすまし耐性WBA の場合は署名検証により高い (IP から独立)低い (ヘッダーは容易に偽装可能)
説明責任担保される担保されない
ダッシュボード表示アイデンティティ別に個別表示 (+ Other verified agents)集計値のみ

✍️ Web Bot Auth の仕組み (Google の公開実装仕様)

Google の Web Bot Auth 実装は現時点で 実験的 (experimental) な位置づけ。

項目内容
ベース仕様IETF ドラフト draft-meunier-web-bot-auth-architecture (HTTP Message Signatures for automated traffic)
署名標準RFC 9421 (HTTP Message Signatures)
公開鍵ディレクトリhttps://agent.bot.goog/.well-known/http-message-signatures-directory
署名主体の識別Signature-Agent ヘッダーに g="https://agent.bot.goog" が設定される (ラベル g= に注意)
検証対象ヘッダーラベル g が付いた Signature および Signature-Input ヘッダー
対象 User-AgentGoogle-Agent (一部のリクエストのみ署名対象)
標準化状況IETF WBA Working Group で策定中のドラフト仕様。今後変更の可能性あり
⚠️ 重要な注意点 (Google 公式ドキュメント):
  • すべての Google User-Agent が Web Bot Auth を使用しているわけではない
  • プロトコルを使用するエージェントの すべてのリクエストに署名しているわけではない
  • 段階的ロールアウトの間は、IP アドレス、逆引き DNS、User-Agent 文字列による従来の検証を併用することを推奨
  • 公開鍵セットは Cache-Control に従ってキャッシュし、ファイルから消えた古いキー (期限切れ/失効の可能性) は削除する
  • 署名の有効期限ウィンドウと公開鍵セットの Cache-Control は別物であり、個別に検証する

📋 手順

1
Fraud Defense ホームページを開く
Google Cloud コンソールで reCAPTCHA / Google Cloud Fraud Defense のページに移動。ホームページ上に Agent overview ダッシュボードが表示される。
2
期間を選択する
Time filters で Last 30 days または This month を選択し、分析対象期間を決める。
3
スコアカードで全体量を把握する
検証済みエージェントセッション数 / 疑わしいエージェントセッション数 / ユニーク検証済みエージェント数を確認。 No verified agent traffic detected yet の場合、トラフィックが追跡対象アイデンティティリストに由来していないことを意味する。
4
トラフィックチャートでアイデンティティ別に分析する
トグルを Verified agents に切り替えて上位の個別エージェントを確認。次に Suspected agents で未検証の自動化トラフィックの推移を確認。
5
観測結果を Policy Engine のルールへ反映する (任意)
2026-07-24 に Preview となった Policy Engine では、CEL 条件式で verified_bots 変数を利用可能。ダッシュボードで確認した検証済みエージェントをチャレンジ免除ルールとして明示的に許可できる。
YAML Policy Engine: 検証済みエージェントのチャレンジ免除ルール例 
challenge_rule_groups:
  - actions: ['*']
    challenge_rules:
      # ダッシュボードで確認した検証済みエージェントはチャレンジ免除
      - condition: 'verified_bots.exists(e, e.name == "google-agent")'
        no_challenge: {}
      # それ以外の低スコアトラフィックにはチャレンジを適用
      - condition: 'score < 0.5'
        challenge:
          difficulty: BALANCE

🎯 メリット

💼 ビジネス面

✓価値ある自動化トラフィックの保護: 収益・流入に貢献するエージェントの誤ブロックリスクを事前観測で低減
✓エージェンティックコマース対応の意思決定材料: AI エージェント経由の流入量を定量把握し、UX / API 提供の投資判断に活用
✓セキュリティポリシーの段階的洗練: 「まず観測 → 次にポリシー化」で一斉ブロックによる機会損失を回避
✓追加実装なしで可視化: 既存の Fraud Defense 統合をそのまま活用可能

⚙️ 技術面

✓なりすまし耐性のあるアイデンティティ: WBA により身元が IP から切り離され暗号学的に検証。IP レンジ管理依存の脆弱性を回避
✓自己申告と検証済みの明確な分離: User-Agent 偽装による通過を検知の観点で扱える
✓アイデンティティ別の粒度: エージェント別内訳で特定エージェントの急増などの異常検知に活用
✓識別リストの自動追随: ユーザー側の追加作業なしにカバレッジが向上

⚠️ デメリット・制約事項

🚧 制限事項

✗期間フィルタは Last 30 days / This month の 2 択のみ。任意の期間指定は記載なし
✗内訳表示は「上位エージェント + Other verified agents」形式。全アイデンティティの個別列挙ではない
✗追跡アイデンティティリスト外のエージェントは「検証済み」に計上されない
✗WBA は IETF ドラフト仕様で Google 実装も実験的段階。仕様変更の可能性あり
✗Google 自身もすべてのリクエストに署名していないため、WBA のみに依存すると取りこぼしが発生

🤔 考慮すべき点

!「疑わしい」は「悪意がある」と同義ではない: 正当だが WBA 未対応のエージェントも含まれる。そのままブロック根拠にすると正当なトラフィックを損なう可能性
!観測とエンフォースメントは別機能: 実際の制御には Policy Engine (Preview)、firewall policies、Cloud Armor 等の組み合わせが必要
!自前検証時のフォールバック設計: WBA を自組織で検証する場合、IP ベース検証へのフォールバックを必ず用意 (Google 公式推奨)
!保護対象としてインストルメントされていないエンドポイントのエージェントトラフィックは計上されない

💼 ユースケース

🛒 1. EC サイトでの AI ショッピングアシスタント流入の把握

シナリオ: AI ショッピングアシスタント経由の商品閲覧・カート追加増加の仮説はあるが実流量が不明。既存ボット対策ルールでの意図しないブロックを検証したい。

  1. Agent overview で Last 30 days を選択し、Verified agent sessions の推移を確認
  2. Traffic chart を Verified agents に切り替え、上位の個別エージェントアイデンティティを特定
  3. 流入が増加傾向であれば、Policy Engine の verified_bots ルールでチャレンジを免除

✨ 効果: 正当な AI エージェント経由の購買機会を保全しつつ、未検証の自動化トラフィックへの防御は維持。

📰 2. メディアサイトにおける未検証スクレイパーの識別

シナリオ: AI 学習用途と思われる大量クロールを受けている。正当な検索インデクサーは許可し、身元不明のスクレイパーはレート制限したい。

  1. Traffic chart を Suspected agents に切り替え、未検証トラフィック量の推移を把握
  2. Verified agents ビューで許可すべき検索インデクサー等のアイデンティティを確定
  3. 検証済みエージェントを許可し、それ以外の低スコアトラフィックへ段階的にチャレンジを適用

✨ 効果: 検索流入に必要なクローラーのアクセスを維持したまま、身元不明の自動化アクセスに対する制御を導入。

📊 3. エージェント許可ポリシー導入前の影響評価

シナリオ: 自動化トラフィックへの一律チャレンジ適用を検討中だが、事業側から「AI エージェント経由の売上に影響しないか」と懸念。

✨ 効果: 検証済み / 疑わしいの内訳とセッション量を提示することで、ポリシー適用の影響範囲を数値で示し、事業部門との合意形成を促進。

✨ まとめ

Agent overview ダッシュボードは、AI エージェントがユーザーの代理として Web を操作する時代に、サイト運営者が最初に必要とする 「可観測性」 を提供するアップデート。暗号署名 (Web Bot Auth) で身元が検証されたエージェントと、 自己申告のみのエージェントを明確に分離して計測できる点が重要であり、 「自動化トラフィックを一律ブロック」から 「検証済みエージェントには信頼のレーンを用意する」 という発想への転換を実務レベルで支える。

推奨アクション: まず Fraud Defense ホームページで過去 30 日間の検証済み / 疑わしいセッションの内訳を確認し、 エージェント流入の実態を把握したうえで、Policy Engine (Preview) の verified_bots ルールによる許可ポリシー設計へ進む。
