🔒 Cloud SQL for PostgreSQL: QueryData PSV サポート

Cloud SQL for PostgreSQL Preview
2026-06-16

📋 概要

Cloud SQL for PostgreSQL の QueryData ツールが、パラメータ化セキュアビュー (PSV) をサポートしました。自然言語でデータベースに問い合わせを行うアプリケーションにおいて、データベースレベルでの行アクセス制御を自動適用し、プロンプトインジェクション攻撃やデータの過剰公開を防止します。

💡 ポイント: QueryData は自然言語の質問をコンテキストセットを使って正確な SQL に変換する NL2SQL エンジンです。PSV パラメータを API リクエストに含めることで、生成される SQL がどのようなものであっても行レベルのアクセス制御が保証されます。

Before / After 比較

❌ Before (PSV 統合前)

  • プロンプトインジェクション攻撃による全データ露出リスク
  • NL2SQL モデルが適切な範囲を超えた SQL を生成する可能性
  • 自然言語クエリ実行時に行レベルアクセス制御を適用する標準方法がない

✅ After (PSV 統合後)

  • PSV パラメータにより行レベルセキュリティが自動適用
  • ユーザーの表現方法に関わらずアクセス可能データを厳密に制御
  • プロンプトインジェクション攻撃に対するDB レベル防御層を追加

🏗️ アーキテクチャ図

エンドユーザーの自然言語クエリが QueryData API と PSV を経由して安全に処理される流れを示します。

アプリケーションがユーザー認証情報に基づいた PSV パラメータを付与することで、データベースレベルでの行アクセス制御が実現されます。

⚡ 主要機能

🔑 QueryData API での PSV パラメータサポート

→API リクエストに parameterized_secure_view_parameters フィールドを追加可能
→アプリケーションのユーザー認証情報に基づいたパラメータ値を指定
→パラメータは SQL 実行全体を通じて一貫して適用

🛡️ 動的行レベルセキュリティ

→WITH (security_barrier) 句による行レベルセキュリティの適用
→名前付きビューパラメータ ($@parameter_name 構文) によるユーザー固有のフィルタリング
→悪意のある関数やオペレーターがフィルタリング前に行値にアクセスすることを防止

🤖 クエリ実行時の自動制限適用

→パラメータ化ビューにアクセスするクエリに対して追加の制限を自動適用
→パラメータ値に基づくチェックの回避攻撃を防止
→単一の共有データベースロールで全アプリケーションユーザーを管理可能
📝 背景: 2026年6月12日にリリースされたパラメータ化セキュアビュー自体は PostgreSQL のビューを拡張する機能です。今回 (6月16日) のアップデートはこの PSV を QueryData (自然言語クエリエンジン) と統合し、NL2SQL のセキュリティを強化するものです。

⚙️ 設定方法

前提条件:
1.Cloud SQL for PostgreSQL インスタンスが作成済みであること
2.cloudsql.enable_parameterized_views データベースフラグが有効 (再起動必要)
3.QueryData のコンテキストセットが作成・アップロード済みであること

Step 1: パラメータ化セキュアビューの作成

SQL 
-- parameterized_views 拡張機能の有効化
CREATE EXTENSION parameterized_views;

-- パラメータ化セキュアビューの作成
CREATE VIEW app_schema.user_orders_view WITH (security_barrier) AS
SELECT order_id, order_date, total_amount, status
FROM app_schema.orders
WHERE customer_id = $@app_user_id;

Step 2: アプリケーション用データベースロールの設定

SQL 
-- アプリケーション用ロールの作成
CREATE ROLE app_query_role WITH LOGIN PASSWORD 'secure_password';

-- ビューへのアクセス権付与
GRANT USAGE ON SCHEMA app_schema TO app_query_role;
GRANT SELECT ON app_schema.user_orders_view TO app_query_role;

-- ベーステーブルへの直接アクセスを拒否
REVOKE ALL PRIVILEGES ON app_schema.orders FROM app_query_role;

Step 3: コンテキストセットの作成

JSON 
{
  "templates": [
    {
      "nl_query": "注文を表示して",
      "sql": "SELECT * FROM app_schema.user_orders_view",
      "intent": "ユーザーの注文一覧を表示する"
    }
  ]
}

Step 4: QueryData API リクエストに PSV パラメータを含める

Bash 
curl -X POST \
  "https://geminidataanalytics.googleapis.com/v1beta/projects/PROJECT_ID/locations/REGION:queryData" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -d '{
    "prompt": "注文を表示して",
    "context": {
      "parameterized_secure_view_parameters": {
        "parameters": {
          "app_user_id": "123"
        }
      }
    }
  }'

✅ メリット

ビジネス面

✓データ漏洩リスクの大幅低減 - 自然言語インターフェースを提供しつつ、権限外のデータアクセスを防止
✓コンプライアンス対応の簡素化 - 行レベルアクセス制御がDB レベルで自動適用、監査対応が容易
✓自然言語アプリの安全な展開 - セキュリティ懸念なく NL2SQL 機能を本番導入可能

技術面

✓多層防御の実現 - アプリケーション層 + データベース層の二重セキュリティ
✓ロール管理の簡素化 - 個々のユーザーごとのDBロール不要、単一の共有ロールで運用可能
✓プロンプトインジェクション耐性 - NL2SQL が生成するSQL に関わらず、PSV が行レベルでデータを制限

⚠️ デメリット・制約事項

制限事項

✗cloudsql.enable_parameterized_views フラグの有効化にはデータベースの再起動が必要
✗parameterized_views 拡張機能は各データベースで個別に作成が必要
✗パラメータ化ビューをユーザー定義関数内で参照するとエラー (親クエリで直接参照する必要あり)
✗Preview 段階のため、SLA や本番環境での利用保証はない

考慮すべき点

📌コンテキストセットの品質が SQL 生成精度に直接影響 - 十分なテンプレートの準備が必要
📌PSV パラメータ値はアプリケーション側で適切に管理・提供する必要がある
📌コンテキストセットの作成可能リージョンは 4 リージョンに限定

💡 ユースケース

🛒 カスタマーサービス自動化

シナリオ: EC サイトのカスタマーサポートチャットボットが、ユーザーの自然言語質問に対して注文情報を返す

SQL 
CREATE VIEW store.customer_orders_view WITH (security_barrier) AS
SELECT order_id, order_date, shipping_status, total_amount
FROM store.orders
WHERE customer_id = $@authenticated_customer_id;

効果: 「全員の注文を見せて」といったプロンプトインジェクションにも耐性があり、ユーザーは自分の注文情報のみを取得可能。

🏢 マルチテナント SaaS アプリケーション

シナリオ: 複数企業が共有するデータベース上で、各テナントが自然言語で自社データのみを検索

SQL 
CREATE VIEW saas.tenant_analytics_view WITH (security_barrier) AS
SELECT metric_name, metric_value, recorded_at
FROM saas.analytics_data
WHERE tenant_id = $@current_tenant_id;

効果: テナント間のデータ分離がデータベースレベルで保証され、NL2SQL モデルの生成するSQL に関わらずデータ漏洩を防止。

QueryData の PSV サポートは、自然言語クエリアプリケーションにデータベースレベルのセキュリティを追加する重要なアップデートです。プロンプトインジェクション攻撃への耐性と行レベルアクセス制御を同時に実現し、NL2SQL を活用したアプリケーションを安心して本番環境に展開できるようになります。自然言語インターフェースを提供するすべてのアプリケーション開発者は、PSV の導入を検討することを推奨します。
