🔒 Cloud SQL for MySQL: パラメータ化セキュアビュー

Preview Cloud SQL for MySQL
2026-07-13

📋 概要

Cloud SQL for MySQL において、パラメータ化セキュアビュー (Parameterized Secure Views) が Preview として利用可能になりました。ビュー定義内でセッション変数を参照することで、ユーザーごとのデータアクセス制御を単一のビューで実現する機能です。

特に NL2SQL (自然言語からSQL) を使用するアプリケーションにおいて、プロンプトインジェクション攻撃やデータの意図しない漏洩を防ぐためのデータベースレベルのセキュリティ対策として有効です。

💡 要件: Cloud SQL for MySQL 8.0.43 以降、メンテナンスバージョン R20260320.00_20 以降が必要です。

🔄 Before / After 比較

❌ Before (従来)

  • ユーザーごとに複数の静的ビューを個別に作成・管理
  • LLM 生成 SQL が意図しないデータ範囲を返すリスク
  • エンドユーザーごとに個別のDBユーザー/ロールが必要
  • プロンプトインジェクション攻撃への防御手段が限定的

✅ After (パラメータ化セキュアビュー)

  • 単一のビューで複数ユーザーのアクセスを柔軟に制御
  • セッション変数による行レベルセキュリティを保証
  • 単一のDBロールで全エンドユーザーに対応可能
  • クエリに対する自動的な制限が適用

🏗️ アーキテクチャ図

アプリケーションがパラメータ化セキュアビューを通じてデータにアクセスする際のフローです。セッション変数によってビューのフィルタ条件が動的に決定されます。

sequenceDiagram
    participant App as アプリケーション
    participant MySQL as Cloud SQL for MySQL
    participant View as パラメータ化セキュアビュー
    participant Table as ベーステーブル

    App->>MySQL: SET_VIEW_VARS ヒント付きクエリ または execute_parameterized_query
    MySQL->>MySQL: セッション変数を設定 (例: @local_customer_id = 5)
    MySQL->>View: ビューにクエリ実行
    View->>View: WHERE句でセッション変数を評価 (customer_id = @local_customer_id)
    View->>Table: フィルタ条件に一致する行のみ取得
    Table-->>View: 該当ユーザーのデータのみ返却
    View-->>MySQL: フィルタ済み結果セット
    MySQL-->>App: ユーザーに許可されたデータのみ返却

⚡ 主要機能

🗄️ セッション変数によるパラメータ化ビュー定義

CREATE VIEW 文の WHERE / ON / HAVING 句でセッション変数 (@variable_name) を使用可能。単一ビューで複数フィルタ条件をパラメータとして受付。

🔧 2つのクエリ実行方式

SET_VIEW_VARS ヒントを使用した SELECT 文による直接クエリ、または mysql.execute_parameterized_query ストアドプロシージャによる実行。

🛡️ 自動クエリ制限の適用

SELECT 文のみ許可。ユーザー定義関数やストアドプロシージャの呼び出し、変数の代入、複数文の連結を禁止。

🔐 行レベルセキュリティの実現

悪意のある関数やオペレータがビュー処理完了前に行データにアクセスすることを防止。アプリケーション認証情報に基づく名前付きパラメータでデータ制限。

📐 技術仕様

バージョン要件

項目 要件

セッション変数の使用可能箇所

句 使用可否
WHERE ✓ 可
ON ✓ 可

SELECT リスト ✗ 不可
その他 ✗ 不可

🛠️ 設定方法

ステップ 1: データベースフラグの有効化

cloudsql_parameterized_secure_view フラグをインスタンスに対して有効化します。再起動は不要です。

ステップ 2: パラメータ化セキュアビューの作成

SQL 
-- WHERE 句でセッション変数を使用したビュー作成
CREATE VIEW v_orders AS
SELECT * FROM orders
WHERE customer_id = @local_customer_id
  AND year >= @earliest_year;

ステップ 3: ビューへのクエリ実行

方法 1: SET_VIEW_VARS ヒントを使用

SQL 
SELECT /*+ SET_VIEW_VARS(local_customer_id=5, earliest_year=2021) */
  * FROM v_orders;

方法 2: mysql.execute_parameterized_query プロシージャを使用

SQL 
CALL mysql.execute_parameterized_query(
  'SELECT * FROM db.v_orders',
  'local_customer_id = 5, earliest_year = 2021');

✅ メリット

💼 ユーザー管理の簡素化

単一のデータベースロールで全エンドユーザーに対応でき、ユーザーごとの個別ロール作成が不要になります。

🤖 NL2SQL アプリのセキュリティ強化

自然言語クエリを利用するアプリケーションにおいて、データベースレベルでアクセス制御を実施し、意図しないデータ漏洩を防止。

🔄 柔軟なアクセス制御

単一のビュー定義で複数のクエリパターンに対応し、静的ビューの乱立を回避できます。

🛡️ プロンプトインジェクション対策

クエリ実行時の自動制限により、悪意あるクエリからデータを保護します。

⚙️ 運用負荷の軽減

フラグ変更にデータベース再起動が不要であり、既存環境への導入が容易です。

⚠️ 制約事項・注意点

⚠️ Preview 機能: 本番環境での利用は推奨されません。Pre-GA の利用規約が適用されます。

制限事項

✗セッション変数は WHERE / ON / HAVING 句でのみ使用可能 (SELECT リストは不可)
✗パラメータ化セキュアビューに対して EXPLAIN は使用不可
✗クエリは SELECT 文のみ許可。UDF やストアドプロシージャ呼び出しは不可
✗execute_parameterized_query 使用時は複数文の連結は不可
✗MySQL 8.0.43 未満のバージョンでは利用不可

考慮すべき点

!Preview 段階のため、サポートが限定的である可能性あり
!SET_VIEW_VARS ヒントで指定する変数は、ビューで参照されている全変数と一致する必要がある (過不足があるとエラー)

🎯 ユースケース

💬 ユースケース 1: NL2SQL アプリケーションでのデータセキュリティ

シナリオ: ユーザーが自然言語で「自分の注文を見せて」と入力するアプリケーション。LLM が SQL に変換する際に意図しないデータ範囲のクエリが生成されるリスクがある。

SQL 
-- ビュー作成: customer_id でフィルタ
CREATE VIEW v_user_orders AS
SELECT order_id, order_date, status, total
FROM orders
WHERE customer_id = @local_customer_id;

-- アプリケーション側でユーザー認証情報に基づき変数を設定してクエリ
SELECT /*+ SET_VIEW_VARS(local_customer_id=12345) */
  * FROM v_user_orders;
効果: LLM がどのような SQL を生成しても、パラメータ化セキュアビューを経由する限り、認証されたユーザーに対応するデータのみが返却される。プロンプトインジェクション攻撃によるデータ漏洩リスクを軽減。

🏢 ユースケース 2: マルチテナントアプリケーションでの行レベルアクセス制御

シナリオ: 複数の顧客がデータベースを共有する SaaS アプリケーションにおいて、各テナントが自身のデータのみにアクセスできるよう制御する。

SQL 
-- テナントごとのデータアクセスを制御するビュー
CREATE VIEW v_tenant_data AS
SELECT * FROM shared_table
WHERE tenant_id = @local_tenant_id;

-- テナント認証後にクエリ実行
CALL mysql.execute_parameterized_query(
  'SELECT * FROM app_db.v_tenant_data',
  'local_tenant_id = 42');
効果: 単一のデータベースロールで全テナントに対応でき、テナントごとの個別ユーザー作成が不要。接続プーリングの効率化にも寄与。
