🔒 Managed Cloud Service Mesh
Distroless プロキシイメージのガイダンス更新

オンボーディング経路ごとにプロキシイメージのデフォルトと選択肢が明確化
📅 リリース日: 2026-08-20

📋 概要

Managed Cloud Service Mesh におけるプロキシイメージタイプ (default / distroless) の利用ガイダンスが更新されました。 クラスタのオンボーディング経路 (直接オンボーディングか、ISTIOD からの移行か) によって、使用されるプロキシイメージのデフォルトと選択肢が明確に定義されました。

🆕 直接オンボーディングしたクラスタ (TRAFFIC_DIRECTOR 実装): デフォルトで distroless イメージ を使用。default や debug などの他イメージタイプはサポートされない
🔄 ISTIOD から TRAFFIC_DIRECTOR に移行したクラスタ: デバッグ用バイナリを含む default イメージ がデフォルト。MeshConfig または Pod アノテーション sidecar.istio.io/proxyImageType: distroless で distroless へオプトイン可能
💡 Google の推奨: distroless イメージはコンテナの内容を必要最小限のパッケージに限定することで攻撃対象領域を削減し、CVE スキャナの誤検出 (ノイズ) を低減するため、セキュリティ向上の観点から distroless イメージの利用が推奨されています。

❌ アップデート前の課題

  • 移行クラスタは「移行時にイメージタイプは変更されない」との説明にとどまり、移行後のデフォルト動作が不明確
  • distroless へオプトインする具体的な方法 (MeshConfig / Pod アノテーション) と優先順位が未整理
  • 直接オンボーディングクラスタで default イメージが非サポートである点や、オーバーライドの扱いが明示されていなかった

✅ アップデート後の改善

  • 直接オンボーディングクラスタは distroless のみサポート (default は非サポート) と明記
  • 移行クラスタのデフォルトは default で、MeshConfig または Pod アノテーションで distroless へオプトイン可能と明確化
  • 使用中のイメージタイプの確認手順がドキュメント化され、Pod アノテーションが MeshConfig より優先されることも明示

⭐ 主要機能

1️⃣ 直接オンボーディングクラスタ: distroless イメージのみサポート

✓マネージド TRAFFIC_DIRECTOR コントロールプレーンに直接オンボーディングしたクラスタでは、distroless イメージタイプのみがサポートされる
✗default イメージはサポートされず、変更もできない
✗他のイメージタイプへのオーバーライド指定は無視される

2️⃣ 移行クラスタ: default がデフォルト、distroless へオプトイン可能

✓ISTIOD から TRAFFIC_DIRECTOR に移行したクラスタは、デバッグ用バイナリを含む default イメージがデフォルト
✓セキュリティ向上のため、MeshConfig または Pod アノテーションで distroless イメージへ明示的にオプトイン可能
✗明示的なオーバーライド値として許可されるのは distroless のみ。debug などの非 distroless イメージタイプは非サポート

3️⃣ プロキシイメージタイプの確認手順のドキュメント化

✓istio-proxy コンテナのイメージパスに -distroless が含まれるかで、Pod のイメージタイプを判別可能
✓設定意図の確認方法として、Pod アノテーションと MeshConfig (defaultConfig.image.imageType) の 2 つの確認手順を提示
✓Pod アノテーションは MeshConfig より優先される

🔧 技術仕様

📊 プロキシイメージタイプの比較

項目 📦 default イメージ 🔒 distroless イメージ
含まれるバイナリ プロキシ + デバッグ用バイナリ プロキシのみ
シェル / curl / ping の実行 ✅ 可能 ❌ 不可 (バイナリ非搭載)
セキュリティ 攻撃対象領域が相対的に大きい 攻撃対象領域を最小化、CVE スキャナの誤検出を削減
直接オンボーディングクラスタ ❌ サポート対象外 ✅ デフォルトかつ唯一のサポート対象
移行クラスタ (ISTIOD → TRAFFIC_DIRECTOR) ✅ デフォルト ✅ MeshConfig または Pod アノテーションでオプトイン可能

⚙️ 設定方法 (優先順位: Pod アノテーション > MeshConfig)

YAML MeshConfig (メッシュ全体に適用) 
apiVersion: v1
kind: ConfigMap
metadata:
  name: istio-release-channel
  namespace: istio-system
data:
  mesh: |-
    defaultConfig:
      image:
        imageType: distroless
YAML Pod アノテーション (ワークロード単位で適用) 
sidecar.istio.io/proxyImageType: distroless
⚠️ 注意: イメージタイプの変更を反映するには、各 Pod の再起動と再インジェクションが必要です。

🛠️ 設定手順

📌 前提条件

✓Managed Cloud Service Mesh (Istio API、TRAFFIC_DIRECTOR コントロールプレーン実装) を使用していること
✓自クラスタのコントロールプレーン実装 (直接オンボーディングか ISTIOD からの移行か) を把握していること
1

現在のプロキシイメージタイプを確認する

Bash istio-proxy コンテナのイメージパスを取得 
kubectl get pod POD_NAME -n NAMESPACE \
  -o jsonpath='{.spec.containers[?(@.name=="istio-proxy")].image}'

イメージパスのタグまたはサフィックスに -distroless が含まれていれば distroless イメージ、含まれていなければ default イメージを使用しています。

2

設定意図 (アノテーション) を確認する

Bash Pod アノテーションの確認 
kubectl get pod POD_NAME -n NAMESPACE \
  -o jsonpath='{.metadata.annotations["sidecar.istio.io/proxyImageType"]}'

Pod アノテーションが設定されている場合、MeshConfig の設定より優先されます。MeshConfig 側は istio-system Namespace の istio-RELEASE_CHANNEL ConfigMap にある defaultConfig.image.imageType を確認します。

3

(移行クラスタの場合) distroless へオプトインする

MeshConfig の imageType: distroless 設定、または対象ワークロードへの sidecar.istio.io/proxyImageType: distroless アノテーション付与のいずれかを行い、Deployment を再起動します。

Bash Deployment の再起動 
kubectl rollout restart deployment -n NAMESPACE DEPLOYMENT_NAME

default イメージへ戻す場合は、アノテーションまたは MeshConfig の imageType フィールドを削除し、Deployment を再起動します。

⚖️ メリットと制約事項

💼 ビジネス面のメリット
  • セキュリティコンプライアンスの強化: 必要最小限のパッケージのみで攻撃対象領域が削減され、セキュリティ基準への準拠が容易に
  • 脆弱性管理コストの削減: CVE スキャナの誤検出 (false positive) が減少し、脆弱性トリアージの運用負荷を軽減
🔧 技術面のメリット
  • デフォルト動作の明確化: 経路ごとのデフォルトが明文化され、意図しないイメージタイプでの運用を防止
  • 柔軟なオプトイン手段: メッシュ全体 (MeshConfig) とワークロード単位 (Pod アノテーション) の 2 通りで段階的な適用が可能
🚧 制限事項
  • 直接オンボーディングクラスタでは distroless のみサポート。default への変更は不可 (オーバーライドは無視される)
  • 移行クラスタでも、許可されるオーバーライド値は distroless のみ (debug などは非サポート)
  • イメージタイプの変更反映には各 Pod の再起動・再インジェクションが必要
⚠️ 考慮すべき点
  • distroless はプロキシ以外のバイナリを含まないため、コンテナ内でシェルや curl、ping などのデバッグユーティリティを実行できない
  • デバッグにはエフェメラルコンテナのアタッチ、または gcloud beta container fleet mesh debug proxy-status / proxy-config を使用 (デバッグ用ベースイメージは不要)

🎯 ユースケース

1. 移行クラスタのセキュリティ強化

シナリオ: ISTIOD から TRAFFIC_DIRECTOR に移行したクラスタを運用しており、セキュリティ監査で sidecar プロキシコンテナ内の不要なバイナリ (シェル、curl など) が指摘された。

YAML MeshConfig でメッシュ全体を distroless 化 
apiVersion: v1
kind: ConfigMap
metadata:
  name: istio-release-channel
  namespace: istio-system
data:
  mesh: |-
    defaultConfig:
      image:
        imageType: distroless

✨ 効果: メッシュ全体のプロキシが distroless イメージに切り替わり (Pod 再起動後)、攻撃対象領域の削減と CVE スキャナのノイズ低減を実現。

2. ワークロード単位での段階的な distroless 移行

シナリオ: 移行クラスタでいきなりメッシュ全体を distroless 化するのはリスクがあるため、まず一部のワークロードから段階的に適用したい。

✨ 効果: Pod アノテーション sidecar.istio.io/proxyImageType: distroless を対象 Deployment のみに付与することで、影響範囲を限定しながら distroless 移行を検証できる。アノテーションは MeshConfig より優先されるため、混在環境でも制御しやすい。
