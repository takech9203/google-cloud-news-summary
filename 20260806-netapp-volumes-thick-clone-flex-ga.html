☁️ Google Cloud NetApp Volumes GA (一般提供)

🧱 Flex Unified Default-mode で
シッククローン (シンクローン分割) が GA

📅 リリース日: 2026-08-06

📌 概要

Google Cloud NetApp Volumes の Flex Unified Default-mode サービスレベルで、 シッククローン (シンクローン分割: thin clone split) 機能が GA になりました。 2026 年 7 月 2 日の Preview 発表から約 1 か月での GA 昇格です。

Flex Unified ではスナップショットからボリュームを作成すると、デフォルトでソースボリュームとデータブロックを共有する シンクローンが作成されます。数秒で作成でき容量消費もわずかですが、ソースボリュームとの依存関係が残り、 クローンが存在する間はソースを削除できませんでした。今回の分割機能により、共有ブロックをすべてクローン側へコピーして 完全に独立したシッククローンへ変換できるようになりました。

❌ Before: アップデート前の課題

  • Default-mode ではシンクローンを独立させる GA 手段がなく、クローンが存在する限りソースボリュームを削除できない
  • クローンの元になったスナップショットも、クローン削除まで削除できない
  • ONTAP-mode では 2026 年 5 月に GA 済みだったが、Default-mode は Preview 止まり

✅ After: アップデート後の改善

  • シンクローンを分割 (split) してシッククローンへ変換し、完全に独立したボリュームとして扱える
  • ソースボリュームの削除・ライフサイクル管理をクローンと切り離せる
  • コンソール / gcloud CLI から分割操作・進行監視が可能、SLA 対象の GA 機能として本番利用可能
🎯 対象ユーザー: Flex Unified Default-mode でテスト・開発環境のボリューム複製を運用しているストレージ管理者、 クローンを長期利用する際にソースボリュームとライフサイクルを分離したいユーザー

シンクローンはソースボリュームとデータブロックを共有し依存関係を持ちますが、分割操作により共有ブロックがすべてクローンへコピーされ、 相互に独立した 2 つのボリュームになります。

⚙️ 主要機能

✂️ 1. シンクローンの分割 (thin clone split)

シンクローンとソースボリューム間で共有されているデータブロックを、共有がなくなるまでクローン側へコピー。 分割完了後は 2 つのボリュームが完全に独立し、ソースボリュームの削除が可能になります。

🖥️ 2. コンソールと gcloud CLI からの操作

コンソールのボリューム一覧、ソースボリューム詳細の「Associated clones」セクション、クローンボリューム詳細ページのいずれからも 「Split clone」を実行可能。CLI では gcloud netapp volumes start-split で分割を開始し、 gcloud netapp volumes get-split-status で進行状況を監視できます。

🧩 3. 各サービスレベルにおけるクローン動作の統一

Standard / Premium / Extreme / Flex File ではクローンは作成直後に自動分割される常時シッククローン。 Flex Unified ではデフォルトでシンクローンが作成され、必要に応じて明示的に分割してシッククローン化する選択が可能です。

✅ 分割の前提条件

✓分割後のフルプロビジョニングサイズを収容できるストレージプールの空き容量
✓分割対象クローンの子クローンを事前に削除
✓分割対象クローンのバックアップを事前に削除
✓分割対象クローンのレプリケーションを停止・削除

🚫 分割中の制限

✗スケジュールされたスナップショット・バックアップの作成・管理・実行
✗新しいシンクローンやレプリケーションの作成
✗分割中ボリュームのリバート (revert)

🛠️ 設定方法

📋 前提条件: Flex Unified Default-mode のストレージプールにシンクローン (スナップショットから作成したボリューム) が存在し、 プールに分割後の容量を収容できる空き容量があること (不足時はプール容量を増やしてから再実行)。

ステップ 1: クローンの分割を開始する

Bash 分割の開始 
gcloud netapp volumes start-split CLONE_VOLUME_NAME \
  --project=PROJECT_ID \
  --location=LOCATION \
  --source-volume=SOURCE_VOLUME_NAME

CLONE_VOLUME_NAME に分割したいクローンボリューム名、SOURCE_VOLUME_NAME にクローンの作成元ボリューム名を指定。 コンソールの場合はボリューム一覧またはクローンボリューム詳細ページから「Split clone」を選択します。

ステップ 2: 分割の進行状況を監視する

Bash 分割ステータスの確認 
gcloud netapp volumes get-split-status CLONE_VOLUME_NAME \
  --project=PROJECT_ID \
  --location=LOCATION \
  --source-volume=SOURCE_VOLUME_NAME

分割のステータスはコンソールのボリューム一覧ページと通知バーにも表示されます。分割中もボリューム詳細ページにはアクセスできますが、 一部操作に制限があります。

⚖️ メリットと制約事項

💼 ビジネス面のメリット
  • ライフサイクル管理の柔軟性: クローンとソースを独立管理でき、テスト環境の昇格や環境払い出しの自由度が向上
  • GA による本番利用: 本番ワークロードに適したサポートレベルで利用可能
🔧 技術面のメリット
  • 依存関係の解消: ソースボリューム・スナップショットの削除が可能になり、不要リソースの整理が容易に
  • 段階的な容量コミット: まずシンクローンで素早く安価に複製 → 長期利用が決まった時点で分割してシッククローン化
🚧 制限事項
  • 分割中はスナップショット・バックアップのスケジュール実行、新規シンクローン作成、レプリケーション作成、リバートが不可
  • 分割前に子クローン・バックアップ・レプリケーションの削除が必要
  • Flex Unified のレプリケーションは分割完了後にのみ利用可能
⚠️ 考慮すべき点
  • 分割によりストレージプールの容量使用量が大幅に増加し、コストが増加する可能性がある
  • プールの空き容量が不足している場合は、容量を増やしてから分割を再実行する必要がある

💡 ユースケース

🚀 ユースケース 1: テスト環境の本番昇格

シナリオ: 本番ボリュームのスナップショットからシンクローンを作成してアップグレード検証を実施し、 検証済み環境をそのまま独立した環境として長期運用したい。

Bash 検証完了後、クローンを分割して独立させる 
# 検証完了後、クローンを分割して独立させる
gcloud netapp volumes start-split verified-clone \
  --project=my-project \
  --location=asia-northeast1 \
  --source-volume=prod-volume

✅ 効果: 検証済みボリュームがソースから独立し、本番ボリュームのライフサイクル (削除・変更) に影響されない環境として運用できる。

🗑️ ユースケース 2: ソースボリュームの廃止

シナリオ: 旧ボリュームから作成したクローンを新環境として使い続けたいが、旧ソースボリュームは削除してコストを削減したい。

✅ 効果: クローンを分割することでソースへの依存が解消され、旧ボリュームとそのスナップショットを安全に削除できる。

💰 料金と利用可能リージョン

💵 料金

シッククローン分割機能自体の追加料金は Release Notes に記載なし。ただし、分割後はクローンが独自にストレージプール容量を消費するため、 プール容量の使用量増加に伴いコストが増加する可能性があります。NetApp Volumes の課金はプールのロケーション・サービスレベル・割り当て容量に基づきます。

📝 まとめ

Flex Unified Default-mode でシンクローンをソースボリュームから独立したシッククローンへ分割する機能が GA となり、 クローンとソースのライフサイクルを分離した柔軟なボリューム運用が可能になりました。 Flex Unified でクローンを長期利用しているユーザーは、分割前提条件 (子クローン・バックアップ・レプリケーションの削除) と プール容量への影響を確認したうえで、本機能の活用を検討することを推奨します。
