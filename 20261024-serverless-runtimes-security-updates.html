📌 概要

2026 年 10 月 24 日、Google Cloud はサーバーレスコンピューティングの全 5 サービスに対して、同一文面のセキュリティ注記を一斉掲載しました。サポート対象の 7 言語ランタイム (Go / Node.js / Java / PHP / Python / Ruby / .NET) すべてに重要なセキュリティアップデートが含まれ、ベースイメージのスタック (google-22 / google-22-full / google-24 / google-24-full) とその基盤 OS パッケージも更新されています。

🚨 求められるユーザーアクション (全サービス共通・即時): 「更新された依存関係でリソースをリビルドし、再デプロイすることで、直ちに保護措置を講じてください」。詳細は Google Cloud セキュリティ情報 (Security bulletins) を参照。

今回の一斉更新は、直近に公開された 2 件のセキュリティ情報と整合します。GCP-2026-071 (eMudhra 下位 CA 証明書 8 件の秘密鍵侵害、CVE-2026-111943、Medium) は App Engine / Cloud Run / Cloud Run functions を影響プロダクトに明記し、推奨 Go バージョン (1.26.10 / 1.27.3) が今回のパッチと一致。GCP-2026-072 (PHP コア脆弱性「PHP2Shell」、Critical) の修正バージョンは今回の PHP パッチ (8.2.35 / 8.3.36 / 8.4.27 / 8.5.12) と完全に一致します。

❌ Before: アップデート前の課題

  • eMudhra 下位 CA 侵害 (GCP-2026-071) により、古い CA トラストストアを含むイメージ・ランタイムのワークロードは外部 TLS 接続で中間者 (MitM) 攻撃を受けるリスク
  • PHP2Shell (CVE-2026-109618 / CVE-2026-109619、CVSS 9.2) は、脆弱な PHP で認証不要のリモートコード実行を許す状態
  • 過去にビルドしたコンテナイメージには、古いランタイム・OS パッケージ・CA バンドルが焼き込まれたまま残存

✅ After: アップデート後の改善

  • サーバーレス全サービスで、全言語ランタイム (Go 1.24+ / Node.js 22+ / Java 17+ / PHP 8.2+ / Python 3.10+ / Ruby 3.3+ / .NET 6+) にパッチ済みバージョンを提供
  • google-22 / google-24 系スタックと基盤 OS パッケージも更新。リビルドだけで最新のセキュリティ修正を取り込める
  • サービス・言語を問わず「リビルド + 再デプロイ」の単一アクションで保護完了

💡 主要なポイント

1️⃣ 7 言語ランタイムの一斉パッチ

サポート対象のすべての言語ランタイムに重要なセキュリティアップデートが含まれます。パッチバージョンの詳細は下記「技術仕様」を参照。

2️⃣ スタック (ベースイメージの OS レイヤ) も更新

google-22、google-22-full、google-24、google-24-full の 4 スタックと基盤 OS パッケージが更新。スタックは Linux ディストリビューションと OpenSSL や curl などのシステムパッケージで構成され、Google Cloud's buildpacks のベースイメージ (Ubuntu ベース) として、ソースデプロイや自動ベースイメージ更新の基盤になります。

3️⃣ 求められるアクションは「リビルド + 再デプロイ」で統一

「更新された依存関係でリソースをリビルドし、再デプロイすることで、直ちに保護措置を講じる」ことが全サービス共通で指示されています。Cloud Run の自動ベースイメージ更新を有効にしている場合でも、Go や Java などのコンパイル言語の言語レベル修正を取り込むにはリビルドが必要です。

4️⃣ 関連するセキュリティ情報

GCP-2026-071 (eMudhra CA 侵害) は App Engine / Cloud Run / Cloud Run functions を影響プロダクトに明記し、推奨 Go バージョン (1.26.10 / 1.27.3) が今回のパッチと一致。今回の PHP パッチバージョンは GCP-2026-072 / GCP-2026-070 (PHP2Shell) の修正バージョンと一致します (PHP 8.1 以前には修正なし)。

ステップ 1: App Engine (スタンダード / フレキシブル環境) — 再デプロイ

Bash 
# 依存関係を更新したうえでソースから再デプロイ
gcloud app deploy

再デプロイにより、パッチ済みのランタイムでアプリケーションが再ビルドされます。フレキシブル環境でカスタムランタイムを利用している場合は、イメージ内の依存関係とベースイメージを更新してから再デプロイします。

ステップ 2: Cloud Run — リビルドして再デプロイ

Bash 
# ソースからサービスを再デプロイ (パッチ済みランタイム / スタックでビルドされる)
gcloud run deploy SERVICE --source .
⚠️ 注意: 自動ベースイメージ更新を有効にしているサービスでも、Go や Java などのコンパイル言語は自動ベースイメージ更新では再コンパイルされないため、言語レベルの修正を取り込むにはリビルドと再デプロイが必要です。

ステップ 3: Cloud Run functions — 再デプロイ

Bash 
# 関数を再デプロイ
gcloud run deploy FUNCTION --source . --function FUNCTION_ENTRYPOINT

ステップ 4: Buildpacks を直接利用している場合 — イメージの再ビルド

Bash 
# pack CLI などで最新のビルダー / スタックを使ってイメージを再ビルド
pack build IMAGE_NAME --builder gcr.io/buildpacks/builder

更新された google-22 / google-24 系スタックでイメージを再ビルドし、デプロイ先 (Cloud Run、GKE など) に再デプロイします。

👍 メリット

💼 ビジネス面

✓対応判断の単純さ: サービス・言語を問わず「依存関係を更新してリビルド + 再デプロイ」という単一のアクションで対応が完了するため、複数サービスを運用する組織でも対応方針を一本化できる
✓マネージドランタイムの価値: ランタイム本体と OS パッケージのパッチ作成・配布は Google が実施済みのため、ユーザーは脆弱性の調査やパッチ適用の作業自体を行う必要がない

🔧 技術面

✓ランタイムと OS の両レイヤをカバー: 言語ランタイム (7 言語) とスタックの OS パッケージの両方が更新されており、再ビルドするだけで CA トラストストアを含む基盤レイヤの修正も取り込める
✓全サーバーレスサービスで同一基盤: App Engine、Cloud Run、Cloud Run functions、Buildpacks が共通のスタック (google-22 / google-24 系) を基盤とするため、修正が一貫して展開される

⚠️ デメリット・制約事項

🚧 制限事項

✗サポート対象外 (End of Support) のランタイムバージョンにはパッチが提供されない。該当する場合はサポート対象バージョンへのアップグレードが前提となる
✗リビルドと再デプロイはユーザー自身が実施する必要があり、実施するまでワークロードは保護されない可能性がある
✗Cloud Run の自動ベースイメージ更新は OS・ランタイムレイヤを自動更新するが、コンパイル言語 (Go / Java など) のアプリケーションは自動では再コンパイルされないため、今回のような言語レベルの修正には再ビルドが必要

🤔 考慮すべき点

⏱️ 即時対応: 注記は「直ちに (immediate)」の対応を求めています。定期リリースを待たず、臨時の再デプロイを計画すべきです。
🖥️ カスタムイメージは対象外: 自前でビルド・管理しているカスタムコンテナイメージ (GKE / Compute Engine 上のワークロードを含む) は今回のサーバーレス側更新の対象外であり、GCP-2026-071 のガイダンスに従って OS ベンダー経由でトラストストアを更新する必要があります。
🗃️ ビルドキャッシュに注意: CI/CD パイプラインでビルドキャッシュを利用している場合、古いランタイム・ベースイメージがキャッシュから再利用されないよう注意してください。

🎯 ユースケース

1. 多言語マイクロサービスを Cloud Run で運用するチームの一斉対応

シナリオ: Go、Node.js、Python のサービスを gcloud run deploy --source で複数運用している。

Bash 
# 各サービスの依存関係を更新してから一括再デプロイ (CI/CD の再実行でも可)
gcloud run deploy api-go --source ./services/api-go
gcloud run deploy web-node --source ./services/web-node
gcloud run deploy batch-py --source ./services/batch-py

効果: すべてのサービスがパッチ済みランタイムと更新済みスタックで再ビルドされ、CA 侵害 (MitM) リスクを含む既知の脆弱性への暴露を解消できる。

2. 自動ベースイメージ更新を有効にした Go サービス

シナリオ: Cloud Run で --base-image と自動更新を有効にした Go サービスを運用しており、「自動更新があるから対応不要」と判断しそうになっている。

効果: 自動ベースイメージ更新は OS レイヤを自動更新するが、Go はコンパイル言語のため言語レベルの修正 (Go 1.26.10 / 1.27.3 など) は再ビルドしないと取り込まれない。今回の注記どおりリビルド + 再デプロイを実施することで、言語ランタイムレイヤまで含めて確実に保護される。

3. App Engine スタンダード環境の PHP アプリケーション

シナリオ: PHP 8.3 で App Engine スタンダード環境のアプリケーションを運用しており、10/21〜10/22 の PHP2Shell 対応 (再デプロイ) は実施済み。

効果: 今回の注記は PHP (8.3.36) を含む全ランタイムとスタックの更新を対象とするため、改めて依存関係を更新して再デプロイすることで、PHP レイヤに加えて OS パッケージ・CA トラストストアのレイヤまで最新の修正を取り込める。

📝 まとめ

Google Cloud のサーバーレスコンピューティング全サービス (App Engine スタンダード / フレキシブル環境、Buildpacks、Cloud Run、Cloud Run functions) で、7 言語すべてのサポート対象ランタイムと google-22 / google-24 系スタックが一斉にセキュリティ更新されました。更新内容は、eMudhra CA 侵害 (GCP-2026-071) で予告されたサーバーレスランタイムへの展開、および PHP2Shell (GCP-2026-072) の修正バージョンと整合しています。

Google 側のパッチ提供は完了しているため、残る対応はユーザー側の「更新された依存関係でのリビルドと再デプロイ」のみです。サーバーレス上の全ワークロードを棚卸しし、直ちに再デプロイを実施してください。自動ベースイメージ更新を有効にしている場合も、Go / Java などのコンパイル言語はリビルドしない限り言語レベルの修正が反映されない点に注意が必要です。
