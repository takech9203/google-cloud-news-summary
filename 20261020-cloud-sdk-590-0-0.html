📝 概要

Google Cloud CLI (gcloud) の バージョン 590.0.0 がリリースされた。 本リリースは 3 件の破壊的変更 (Breaking Changes) を含む重要なアップデートであり、 gcloud-man-pages、App Engine の app-engine-grpc、Cloud Build Local Builder (cloud-build-local) の各コンポーネントが削除された。 特に gcloud-man-pages は 586.0.0 (2026-09-22) で予告されていた通りの削除であり、 今後はビルトインの --help フラグを使用する。

機能面では、Cloud Resource Manager のガバナンス系コマンド群、Cloud Dataflow の config-store-settings、BigLake Iceberg カタログのフェデレーション関連フラグ、 Compute Engine の --instance-flexibility-policy、GKE Hub の Config Management フラグ、 Network Security の WildFire 分析コマンドなど、多数のコマンド・フラグが GA に昇格した。 セキュリティ面では、バンドル Python ライブラリの更新 (pyOpenSSL 26.4.0 / cryptography 50.0.1) と CVE-2026-39820 対応が含まれる。

⚠️ 対象ユーザー: CI/CD パイプラインやローカル環境で gcloud CLI を利用するすべてのユーザー。 特に削除されたコンポーネントに依存しているユーザーは、アップデート前に影響を確認すること。

🔄 Before / After

❌ アップデート前の課題

  • gcloud-man-pages / app-engine-grpc / cloud-build-local が非推奨のまま配布され、依存を残した環境が存在し得た
  • Cloud Run のドメインマッピングは実際に作成するまで利用可否を検証できなかった
  • Compute Engine インスタンステンプレートの export / import コマンドが未提供だった
  • GKE で --num-nodes=0 でのクラスタ作成ができなかった
  • Cloud SQL は PostgreSQL 19 に未対応だった
  • Resource Manager / Dataflow の一部機能は GA 前で、本番採用の判断が難しかった

✅ アップデート後の改善

  • 削除済みコンポーネントの代替が明確化 (man ページ → --help、ローカルビルダー → Cloud Build 本体)
  • Python ライブラリ更新と CVE-2026-39820 対応で CLI のセキュリティ姿勢が向上
  • gcloud beta run domain-mappings create --dry-run で作成前の事前検証が可能に
  • instance-templates export/import で IaC 的なテンプレート構成管理が容易に
  • GKE: --num-nodes=0、Windows Server ltsc2025、kubelet reservedSystemCpus が利用可能に
  • Cloud SQL で POSTGRES_19 が選択可能に
  • 多数のコマンド・フラグが GA に昇格し、SLA のもと本番利用が可能に

590.0.0 への更新で 3 つのコンポーネントが削除され、コマンドドキュメントはビルトインの --help に、ローカルビルドはマネージドの Cloud Build に移行する構成となる。

💥 破壊的変更 (Breaking Changes)

1️⃣ gcloud-man-pages コンポーネントの削除
man gcloud 形式で参照していた man ページコンポーネントが削除。586.0.0 (2026-09-22) で非推奨化が予告され、予定通り 590.0.0 で削除された。
代替: 各コマンドで --help フラグを使用 (例: gcloud compute instances create --help)
2️⃣ app-engine-grpc コンポーネントの削除
App Engine 用の gRPC 拡張コンポーネントが gcloud CLI から削除。インストール済みの環境では、更新後にコンポーネントが存在しなくなる。
3️⃣ Cloud Build Local Builder (cloud-build-local) の削除
ローカルマシン上で Cloud Build のビルドを実行する Local Builder コンポーネントが削除。ローカル検証に依存していた CI/CD フローは、Cloud Build 本体でのビルド実行への移行が必要。

🔒 セキュリティ関連の更新

🐍 バンドル Python ライブラリの更新
Linux / Windows / Alpine ベース Docker イメージのバンドル Python が pyOpenSSL 26.4.0 / cryptography 50.0.1 に更新。32-bit Windows はサポート可能な最新版 (pyOpenSSL 26.2.0 / cryptography 48.0.1) を使用。
🛡️ CVE-2026-39820 対応
Cloud Bigtable コンポーネントを 1.26.4 でリビルドし CVE-2026-39820 を解消。Cloud Bigtable Emulator (cbt-emulator) も同 CVE 対応でリビルド。
🔑 Apigee mTLS 認証の修正
Mutual TLS (mTLS) で認証するユーザーが gcloud apigee コマンド実行時に UnauthorizedRequestError で失敗する問題を修正。

🚀 主要な GA 昇格

🏛️ Cloud Resource Manager: ガバナンス系コマンド群
capability-configs / boundary-configs / boundaries の 3 コマンド群が GA に昇格。
🧊 BigLake: Iceberg フェデレーテッドカタログ
iceberg catalogs create|update の --federated-catalog-identity-mode と --metadata-service-directory-name が GA。--catalog-type で federated 値をサポート。
🌊 Cloud Dataflow: 構成ストア設定
gcloud dataflow config-store-settings が GA に昇格。
🖥️ Compute Engine: インスタンス柔軟性ポリシー
--instance-flexibility-policy フラグが GA。さらに instance-templates export/import コマンドを追加 (テンプレートの構成ファイル出力・取り込み)。
⎈ GKE Hub: Config Management フラグ
Config Management 関連フラグが GA に昇格。--no-install-connect-agent フラグを追加。
🔥 Network Security: WildFire 分析コマンド
WildFire 分析関連コマンドが GA に昇格。

✨ その他の注目機能

🤖 AI / Vertex AI (Beta)
  • gcloud beta ai endpoints deploy-model が GDC 接続エンドポイント上の Gemini デプロイで自動リソース (automatic resources) をリクエストするように変更
  • レプリカ数未指定の場合、gemini-2.5-flash に限り最小レプリカ数がデフォルト 1 に
  • --machine-type や --accelerator など専有リソース用フラグ指定時は警告を表示し専有リソースでデプロイ
🆔 Agent Identity (Beta)
gcloud beta agent-identity auth-providers resolve-authorization コマンドを追加。
🗄️ データベース関連
  • AlloyDB: beta alloydb instances create|update に --enable-public-dns フラグを追加
  • Cloud SQL: データベースバージョンに POSTGRES_19 を追加、MySQL レプリカ再作成用フラグを追加
  • Database Migration: --failback フラグを追加
  • Spanner: Spanner CLI のエラー出力を改善
⎈ Kubernetes Engine
  • kubelet オプションに reservedSystemCpus を追加
  • Windows ノードイメージ ltsc2025 をサポート
  • デフォルト kubectl を 1.35.9 に更新
  • --num-nodes=0 でのクラスタ作成をサポート
🌐 ネットワーク / サーバーレス関連
  • Cloud Run: beta run domain-mappings create に --dry-run フラグを追加 (ドメインの利用可否を含む事前検証)
  • network-connectivity: internal-ranges に --purpose フラグを追加
  • Service Extensions: extension-bindings と cdn-edge-extensions コマンドグループを追加
  • App Engine: beta app migrate-to-run のデフォルトリージョンを us-central1 から App Engine アプリケーションのリージョンに変更
🧩 その他
  • Cloud IAM: iam workforce-pools providers create-oidc|create-saml|update-oidc|update-saml に --vendor-type フラグを追加
  • Certificate Authority Service: privateca subordinates list に --filter フラグを追加
  • Cloud Dataplex: dbt metadata-jobs create のドット入りリソース名拒否と、同一エントリ ID 衝突でジョブ全体が失敗する問題を修正
  • Cloud Workstations: ブースト構成に enable-automatic-failover を追加

👍 メリット

💼 ビジネス面

✓本番採用の判断が容易に: Resource Manager のガバナンス系コマンドや Dataflow の config-store-settings など多数の機能が GA となり、本番環境での利用判断がしやすくなった
✓セキュリティコンプライアンスの維持: CVE-2026-39820 対応と暗号ライブラリ更新により、CLI を含むツールチェーンの脆弱性管理要件を満たしやすくなった

🔧 技術面

✓CLI のスリム化: 利用頻度の低いコンポーネントの削除により、インストールサイズと保守対象が削減された
✓IaC 運用の強化: instance-templates export/import により Compute Engine テンプレートの構成ファイル管理が可能になった
✓安全な事前検証: Cloud Run の --dry-run により、ドメインマッピングを作成せずに検証できるようになった

⚠️ デメリット・制約事項

🚧 制限事項

✗gcloud-man-pages 削除後は man コマンドでの CLI ドキュメント参照ができない (--help のみ)
✗cloud-build-local 削除により、Cloud Build のビルドをローカルで実行する公式コンポーネントはなくなった
✗32-bit Windows は最新の pyOpenSSL / cryptography に追従できず、1 世代前のバージョン (26.2.0 / 48.0.1) に留まる

🤔 考慮すべき点

  • CI/CD パイプラインで削除対象コンポーネントを明示的にインストールしている場合 (gcloud components install cloud-build-local など)、590.0.0 以降はインストールが失敗する可能性があるため、スクリプトの修正が必要
  • apt / yum でコンポーネントを個別パッケージ (例: google-cloud-cli-cloud-build-local) として導入している環境も、パッケージ構成の見直しが必要
  • gcloud beta app migrate-to-run のデフォルトリージョンが変更されたため、us-central1 前提の移行スクリプトは挙動が変わる点に注意

🎯 ユースケース

💼 ユースケース 1: CI/CD パイプラインの 590.0.0 対応

シナリオ: GitHub Actions や Cloud Build で gcloud CLI の最新イメージを使用しており、一部ジョブで cloud-build-local によるローカルビルド検証を行っている。

Bash cloud-build-local から Cloud Build 本体への移行 
# 変更前 (590.0.0 で失敗する)
gcloud components install cloud-build-local
cloud-build-local --config=cloudbuild.yaml --dryrun=true .

# 変更後 (Cloud Build 本体で検証)
gcloud builds submit --config=cloudbuild.yaml .

効果: 削除済みコンポーネントへの依存を排除し、マネージドな Cloud Build に一本化することでパイプラインの破損を回避できる。

🌐 ユースケース 2: Cloud Run カスタムドメインの安全な事前検証

シナリオ: 本番サービスにカスタムドメインを割り当てる前に、ドメインが利用可能かどうかを確認したい。

Bash --dry-run によるドメインマッピング事前検証 
gcloud beta run domain-mappings create \
  --service=prod-frontend \
  --domain=www.example.com \
  --region=asia-northeast1 \
  --dry-run

効果: 実リソースを作成せずにドメインマッピングの妥当性 (ドメインの利用可否を含む) を検証でき、本番変更作業のリスクを低減できる。
