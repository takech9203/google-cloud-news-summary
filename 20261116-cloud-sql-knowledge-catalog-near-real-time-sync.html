🗄️ Cloud SQL: Knowledge Catalog への
ニアリアルタイム メタデータ同期

✅ GA (一般提供) Cloud SQL for MySQL Cloud SQL for PostgreSQL Knowledge Catalog (旧 Dataplex Universal Catalog)
📅 リリース日: 2026-11-16

📋 概要

Cloud SQL for MySQL / PostgreSQL の Knowledge Catalog 統合のメタデータ同期が ニアリアルタイム化されました。2026 年 4 月 18 日より前に作成されたインスタンスでも、 統合を有効化するだけでスキーマとメタデータの更新が従来の「1 日 1 回」ではなく「ニアリアルタイム」で同期されます。 2026 年 4 月 18 日以降に作成されたインスタンスではデフォルトで有効です。

対象は新ネットワーク アーキテクチャ上で稼働する MySQL 8.0 以降 / PostgreSQL 14.0 以降のインスタンス。 スキーマ変更 (DDL) が数分以内にカタログへ反映されるため、メタデータの鮮度が大幅に向上し、 AI エージェントのグラウンディングやデータ ディスカバリの精度向上につながります。

10 分以内
新しい DDL / スキーマ変更のカタログ反映
1 日 1 回 → NRT
同期頻度がバッチからニアリアルタイムへ
最大 40% → 最小限
抽出処理の CPU 使用量 (大規模スキーマの場合)

❌ Before: アップデート前の課題

  • 2026-04-18 より前に作成されたインスタンスでは、メタデータの更新頻度は約 1 日 1 回。スキーマ変更の反映に最大 48 時間かかる場合があった
  • カタログと実際の DB スキーマに乖離が生じやすく、データ ディスカバリや AI エージェントのグラウンディングで古い情報を参照するリスクがあった
  • 1 日 1 回のバッチ抽出は、10,000 テーブル以上の大規模スキーマでCPU を最大 40% 消費することがあった

✅ After: アップデート後の改善

  • 既存インスタンスでも統合を有効化するだけでニアリアルタイム同期が適用される
  • DDL やスキーマ変更が 10 分以内に Knowledge Catalog へ反映 (有効化直後の既存リソースは 24 時間以内)
  • ニアリアルタイム統合ではCPU への影響が最小限
  • 1 日 1 回モードのインスタンスも無効化→再有効化の簡単な操作で移行可能

⚙️ 主要機能

1️⃣ 既存インスタンスでのニアリアルタイム同期の有効化

→2026 年 4 月 18 日より前に作成されたインスタンスで、バージョンとネットワーク アーキテクチャの条件を満たす場合、Knowledge Catalog 統合を有効化するとニアリアルタイム同期が適用される
→既に 1 日 1 回モードで統合が有効な場合は、統合を無効化してから再有効化することでニアリアルタイムに切り替え可能

2️⃣ タイムスタンプ テーブルによる変更検知

→アセットの作成・更新時刻を追跡するタイムスタンプ テーブルがインスタンス内に作成される
→MySQL では mysql データベース内、PostgreSQL では cloudsqladmin データベース内の resource_timestamps テーブル
→DDL 発生時に統合がタイムスタンプ テーブルを照会し、最近変更されたアセットを特定して最新スキーマを Knowledge Catalog にロード
→統合を支えるクエリには --Dataplex コメントが付与され、アクティブ クエリの確認画面で識別できる

3️⃣ 新規インスタンスでのデフォルト有効化

→2026 年 4 月 18 日以降に作成されたインスタンスでは、Knowledge Catalog 統合 (ニアリアルタイム同期) がデフォルトで有効
→2026 年 3 月 19 日〜4 月 18 日に作成された一部のインスタンスもこのカテゴリに含まれる場合があり、インスタンスの設定で確認できる

項目条件
データベース バージョンMySQL 8.0 以降 / PostgreSQL 14.0 以降
ネットワーク アーキテクチャ新ネットワーク アーキテクチャ
作成日が 2026-04-18 以降ニアリアルタイム同期がデフォルトで有効
作成日が 2026-04-18 より前統合の有効化 (既に有効な場合は無効化→再有効化) でニアリアルタイムに移行
上記条件を満たさない場合従来どおり 1 日 1 回のバッチ同期 (バージョンが古い、または旧ネットワーク アーキテクチャ)

⏱️ 同期のタイミングと整合性

項目詳細
新規の DDL / スキーマ変更10 分以内に Knowledge Catalog に反映
有効化直後の既存リソース24 時間以内に反映
更新の取りこぼし時結果整合性により通常 24 時間以内に反映
無効化の反映ニアリアルタイム統合のインスタンスでは最大 10 分
CPU 使用量ニアリアルタイム統合では影響は最小限 (1 日 1 回モードでは大規模スキーマで最大 40% の CPU 使用の可能性)

🛠️ 設定方法

✅ 前提条件

✓プロジェクトで Dataplex API が有効になっていること
✓Knowledge Catalog 上で Cloud SQL のメタデータを閲覧するには cloudsql.schemas.view 権限が必要 (プロジェクト レベルで付与。この権限を持つユーザーはプロジェクト内のすべての Cloud SQL インスタンスのメタデータを閲覧可能な点に注意)
✓対象インスタンスが MySQL 8.0 以降または PostgreSQL 14.0 以降で、新ネットワーク アーキテクチャ上で稼働していること

📝 ステップ 1: 既存インスタンスで統合を有効化

Bash Knowledge Catalog 統合の有効化 
gcloud sql instances patch INSTANCE_NAME \
    --enable-dataplex-integration

条件を満たすインスタンスでは、このコマンドだけでニアリアルタイム同期が有効になります。

📝 ステップ 2: 1 日 1 回モードからニアリアルタイムへ切り替え (統合が既に有効な場合)

Bash 無効化→再有効化でニアリアルタイムに切り替え 
# 統合を一度無効化
gcloud sql instances patch INSTANCE_NAME \
    --no-enable-dataplex-integration

# 再度有効化するとニアリアルタイム同期に切り替わる
gcloud sql instances patch INSTANCE_NAME \
    --enable-dataplex-integration

📝 ステップ 3: 統合の有効化を確認

Bash 統合ステータスの確認 
gcloud sql instances describe INSTANCE_NAME

出力の enableDataplexIntegration が true になっていることを確認します。

💡 メリット

💼 ビジネス面

✓データ ガバナンスの鮮度向上: スキーマ変更が数分以内にカタログへ反映され、カタログの情報を信頼して意思決定やデータ活用を進められる
✓AI 活用の品質向上: Knowledge Catalog は AI エージェントのグラウンディングに利用されるコンテキスト エンジンであり、最新のスキーマ情報に基づく正確な応答が期待できる
✓運用コストの削減: カタログ反映を待つ手動確認や、メタデータの乖離に起因するトラブルシューティングが減少

⚙️ 技術面

✓低い CPU オーバーヘッド: 1 日 1 回のバッチ抽出と比較して、インスタンスの CPU への影響が最小限
✓簡単な移行パス: gcloud sql instances patch による有効化 (または無効化→再有効化) のみで移行できる
✓結果整合性の保証: 更新が取りこぼされた場合でも、通常 24 時間以内に結果整合的に反映される

⚠️ デメリット・制約事項

🚫 制限事項

✗対象は MySQL 8.0 以降 / PostgreSQL 14.0 以降かつ新ネットワーク アーキテクチャのインスタンスのみ。条件を満たさない場合は従来どおり 1 日 1 回の同期
✗データベース名を変更した場合、ニアリアルタイムで反映されるのはデータベースの更新のみで、配下のテーブルとのマッピングは結果整合的に反映
✗短時間の大量 DDL、クローン インスタンス、バックアップからの復元、メモリ不足、再起動、ネットワーク障害などでは更新メッセージが欠落し、結果整合 (通常 24 時間以内) となる場合がある
✗2026-04-18 より前に作成されたインスタンスのうち、Assured Workloads への登録によりリソースへのアクセスが制限されているものは統合が無効化される

🤔 考慮すべき点

⚠️1 日 1 回モードからの切り替えには、統合の無効化→再有効化という明示的な操作が必要 (自動では切り替わらない)
⚠️有効化直後は既存リソースのカタログ反映に最大 24 時間かかるため、切り替え直後にすべてのアセットが見えるわけではない
⚠️cloudsql.schemas.view 権限はプロジェクト レベルで付与されるため、メタデータの閲覧範囲に関するアクセス制御の設計を確認しておく
⚠️旧ネットワーク アーキテクチャのインスタンスで利用したい場合は、新ネットワーク アーキテクチャへのアップグレードを検討

🎯 ユースケース

📦 ユースケース 1: 既存インスタンス群のニアリアルタイム同期への一括移行

シナリオ: 2026 年 4 月 18 日より前に作成した多数の Cloud SQL for PostgreSQL 14 インスタンスで、データ カタログの鮮度を上げるためにニアリアルタイム同期へ移行したい。

Bash プロジェクト内の全インスタンスで統合を有効化 
gcloud sql instances list --format="(NAME)" \
  | tail -n +2 | xargs -t -I % gcloud sql instances patch % --enable-dataplex-integration

効果: 条件を満たすインスタンスはニアリアルタイム同期となり、スキーマ変更が 10 分以内に Knowledge Catalog へ反映される。

🚀 ユースケース 2: アジャイル開発環境でのスキーマ変更の即時カタログ反映

シナリオ: マイクロサービス開発チームが頻繁にテーブル追加やカラム変更を行っており、データ分析チームが Knowledge Catalog 経由で最新スキーマを検索・参照している。

効果: DDL 実行から 10 分以内にカタログへ反映されるため、分析チームは常に最新のスキーマ情報に基づいてデータ ディスカバリやリネージ管理を行える。カタログを参照する AI エージェントも古いスキーマによる誤回答を回避しやすくなる。

📝 まとめ

Cloud SQL for MySQL / PostgreSQL の Knowledge Catalog 統合がニアリアルタイム化され、 既存インスタンスでも統合の有効化 (または無効化→再有効化) だけでスキーマ変更を 10 分以内にカタログへ反映できるようになりました。 データ カタログの鮮度は AI エージェントのグラウンディングやデータ ガバナンスの品質に直結するため、 MySQL 8.0 / PostgreSQL 14.0 以降かつ新ネットワーク アーキテクチャのインスタンスでは、 ニアリアルタイム同期への切り替えを推奨します。
