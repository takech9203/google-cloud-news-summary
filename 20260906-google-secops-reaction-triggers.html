⚡ リアクショントリガー (Reaction Triggers) によるプレイブックの自動実行

調査中のケース・アラートの状態変化に反応してプレイブックを自動起動 — インジェスト後のイベント駆動自動化が実現

📌 概要

Google SecOps がプレイブックの新しいトリガー方式 リアクショントリガー (Reaction Triggers) を Preview として発表しました。インジェスト後 (post-ingestion) トリガーとして機能し、調査中のケースやアラートに対するリアルタイムの更新イベント (担当者変更、タグ追加、優先度変更、新規エンティティ追加など) に反応してプレイブックを自動的に起動できます。

従来の標準トリガー (インジェストトリガー) が取り込みの瞬間にのみ実行されるのに対し、リアクショントリガーはアクティブな調査の進行中に発生する状態変化に基づいてプレイブックを自動化します。アラートの状態が変化した際にアナリストが手動でプレイブックをアタッチする必要がなくなります。

🎯 対象ユーザー: Google SecOps SOAR でインシデント対応を自動化している SOC チームやセキュリティエンジニア。エスカレーション通知、追加エンティティの自動エンリッチメント、外部 ITSM との同期など、調査ライフサイクル中盤のワークフロー自動化に有効です。

❌ Before (アップデート前の課題)

  • プレイブックの自動アタッチはインジェストトリガーに限定され、取り込み時点でのみ起動
  • 調査中に優先度・担当者・タグなどが変化した場合、手動でプレイブックをアタッチする必要があった
  • インジェスト後に追加されたエンティティへの自動エンリッチメントの仕組みがなかった

✅ After (アップデート後の改善)

  • 担当者変更・タグ追加・優先度変更・エンティティ追加などのリアルタイム更新イベントで自動起動
  • 状態変化時の手動アタッチ作業が不要に
  • From/To 状態や追加条件を細かく指定し、不要な実行を抑制しながらイベント駆動の自動化を構成可能

🏗️ アーキテクチャ図

インジェスト後の調査中に発生したケース・アラートの更新イベントをリアクショントリガーが検知し、設定された条件に一致した場合にプレイブックを自動実行するフローです。

🔧 主要機能

1️⃣ インジェスト後のイベント駆動トリガー

プレイブックの初期セットアップ時に設定するインジェスト後トリガーとして動作。標準トリガーが取り込み時に即時実行されるのに対し、リアクショントリガーはアクティブな調査中のリアルタイムな変更や特定イベントに基づいてプレイブックを自動化します。

2️⃣ スコープに応じたトリガーの動的フィルタリング

プレイブック作成時に選択するスコープ (Alert / Case) に応じて、利用可能なリアクショントリガーが動的に絞り込まれます。Alert スコープではアラートレベルのイベントトリガー、Case スコープではケースレベルのトリガーが表示されます。

3️⃣ 柔軟な条件設定

  • 優先度・担当者などの変更トリガーでは「変更前 (From)」「変更後 (To)」の状態を指定可能。ANY や OR 条件による複数状態の組み合わせにも対応
  • Entity Added トリガーでは AND / OR の論理演算子による複数条件フィルタリングが可能 (例: Entity.Identifier contains @google.com AND Entity.Type is USERUNIQNAME)
  • 「追加条件 (Define additional conditions)」でトリガーと直接関係しない条件 (例: ケース優先度が High の場合のみ実行) を定義し、不要な実行を削減

🔀 カスタムフィールド変更トリガーのトグル動作

トグル状態動作
Off (無効)その状態の値をチェックしない (任意の値に一致し、変更前後の値に関係なく発火)
On (有効)特定の値をチェックする (フィールドを空のままにすると空文字列の検索を意味し、空だったフィールドが更新されたときの発火などを表現できる)

1

プレイブックの作成とスコープ選択

  • Add New Playbook or Block をクリックして新しいプレイブックを作成
  • Create New ダイアログで Scope を選択 — Alert (アラートレベルのイベントトリガー) / Case (ケースレベルのトリガー)
  • Create をクリック
2

リアクショントリガーの配置

  • Step Selection パネルで Triggers を選択
  • Reaction タブで、選択したスコープで利用可能なイベントベーストリガーを表示
  • 対象のトリガーをプレイブックデザイナーのトリガーターゲットエリアにドラッグ
3

トリガー条件の設定

  • トリガーをダブルクリックしてサイドドロワーを開く (Conditions タブは選択したトリガーに合わせて自動更新)
  • Entity Added: 「任意のエンティティ」または「特定のエンティティ」を選択し、プロパティと論理演算子 (AND / OR) で条件を定義
  • Priority Changed 系: 「Priority changed from」「Priority changed to」を設定 (特定の優先度または ANY、OR による複数組み合わせが可能)
  • Custom Field Changed 系: 対象フィールドを選択し、From / To の状態とトグルを設定
  • Case Assignee / Stage / Tag 系: 変更前後の担当者・ステージやタグを設定
  • 必要に応じて Define additional conditions (optional) で追加条件を定義し、不要な実行を抑制

💡 メリット

💼 ビジネス面

  • 対応時間の短縮: 優先度が Critical に上がった瞬間に通知・エスカレーションが自動実行され、重大インシデントへの初動が早くなる
  • 運用負荷の削減: 状態変化のたびの手動アタッチが不要になり、アナリストは調査に集中できる
  • 外部システムとの整合性維持: 担当者変更などを外部 ITSM へ自動同期し、チケット情報の乖離を防止

🔧 技術面

  • イベント駆動の自動化: インジェスト時点だけでなく、調査ライフサイクル全体に自動化ポイントを設けられる
  • 細粒度の条件制御: From/To 状態、エンティティプロパティ条件、追加条件で発火条件を精密に制御
  • スコープベースの設計: Alert / Case のスコープに応じたトリガーセットで適切なレベルの自動化を設計

⚠️ デメリット・制約事項

🚧 制限事項
  • Preview 機能であり、Google Security Operations Service Specific Terms の Pre-GA Offerings Terms が適用。サポートが限定される可能性があり、他の Pre-GA バージョンとの互換性が保証されない場合がある
  • 環境によっては機能が表示されない場合があり、プレビュー機能の管理設定または管理者への確認が必要
  • Entity Added トリガーの条件は、エンティティタイプの厳密な技術構文 (例: USERUNIQNAME、DestinationURL) を大文字小文字を区別して評価
  • Entity Added トリガーは、初回アラートインジェスト時に作成されたエンティティには反応しない (インジェスト後に追加されたエンティティのみが対象)
🤔 考慮すべき点
  • 条件を緩く設定すると意図しないプレイブック実行が増える可能性があるため、追加条件 (additional conditions) の活用による絞り込みを推奨
  • Case Stage Changed トリガーで利用できる調査ステージは、管理者が SOAR 設定で事前に構成したものに依存

🎯 ユースケース

🔍 ユースケース 1: 新規発見エンティティの自動エンリッチメント (Alert スコープ)

シナリオ: 調査の進行中に、初回インジェスト後の新しいエンティティがアクティブな調査にアタッチされる。追加のタイミングにかかわらず、全エンティティを自動的にエンリッチしたい。

Config 実装例 
トリガー: Entity Added
条件例: Entity.Identifier contains @google.com AND Entity.Type is USERUNIQNAME
アクション: エンリッチメントプレイブックを実行し、レピュテーションデータを取得

効果: Entity Added トリガーが新規エンティティを検知してエンリッチメントプレイブックを自動実行し、即座にレピュテーション情報が提供される。

🚨 ユースケース 2: インシデントの動的エスカレーションと通知 (Alert スコープ)

シナリオ: アラートの優先度が Medium から Critical に変更された際に、シニアステークホルダーへ自動的に通知したい。

効果: Alert Priority Changed トリガーがワークフローを実行し、ケース担当者への自動メール送信とインシデント対応 Slack チャネルへの通知が行われる。

🎫 ユースケース 3: クロスプラットフォームのチケット同期 (Case スコープ)

シナリオ: セキュリティケースが一般キューから専門の SOC ロールやユーザーに再割り当てされた際に、外部 ITSM プラットフォームとの厳密な整合性を維持したい。

効果: Case Assignee Changed トリガーが発火し、外部チケッティングシステムのオーナーフィールドを自動更新するとともに、新しい担当者へ運用サマリーを送信する。

🔗 関連サービス・機能

📥 インジェストトリガー (Manage playbook triggers)

新しいアラートやケースがシステムに入った時点でプレイブックを自動アタッチする従来のトリガー。リアクショントリガーはこれを補完し、インジェスト後のイベントに対応します。

🤖 Google SecOps SOAR プレイブック

事前定義された条件で起動する自動化プロセス。今回のアップデートで起動条件の選択肢が調査ライフサイクル全体に拡張されました。

✨ Gemini によるプレイブック作成

プレイブックの作成・編集に Gemini を活用可能。リアクショントリガーを含むプレイブック構築の起点となります。

💬 外部 ITSM / チャットツール連携

リアクショントリガーと組み合わせることで、担当者変更や優先度変更を外部チケッティングシステムや Slack などへリアルタイムに反映できます。

📝 まとめ

リアクショントリガーの登場により、Google SecOps のプレイブック自動化はインジェスト時点の一度きりのトリガーから、調査ライフサイクル全体をカバーするイベント駆動型の自動化へと進化しました。

  • SOC チームは、優先度変更時のエスカレーション、新規エンティティの自動エンリッチメント、ITSM とのチケット同期といった中間フェーズの手作業を削減できる
  • Preview 機能のため、まずは検証環境で Reaction タブのトリガーと条件設定を試すことを推奨
  • 既存のインジェストトリガーベースのプレイブックとの役割分担を設計することが重要
