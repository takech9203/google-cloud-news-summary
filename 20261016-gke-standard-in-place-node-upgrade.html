🔄 GKE Standard: CPU ノードプールの
インプレースノードアップグレード

リリース日: 2026-10-16
GKE Standard Compute Engine Change (全 GKE バージョン適用) 要設定: maxUnavailable > 0

📝 概要

GKE Standard の CPU ノードプールでは、ノードのバージョンアップグレード時に VM を削除・再作成する代わりに、 既存の Compute Engine VM をインプレース (in place) で更新できるようになりました。 ノードが基盤の VM をそのまま保持するため、アップグレード中もコンピュート容量が維持され、 リソース (容量) 不足によるアップグレードの失敗・停滞リスクが低減されます。

💡 有効化の条件: surge upgrade (サージアップグレード) で maxUnavailable フィールドを 0 より大きい値に設定すること。本変更は全 GKE バージョンに適用されます。 オプトアウトしたい場合は Cloud Customer Care への連絡が必要です。

🔴 Before: アップデート前の課題

  • maxUnavailable を使った固定容量アップグレードでも、ノード再作成時に VM が削除・新規作成され、予約由来でない容量は一時的に解放されていた
  • 容量が解放された隙に他の利用者がリソースを確保すると、同じマシンタイプの VM を再取得できず、アップグレードが失敗・停滞するリスクがあった
  • リソース制約の厳しい環境では、容量確保のために予約の利用などの追加対策を検討する必要があった

🟢 After: アップデート後の改善

  • CPU ノードプールのバージョンアップグレードで maxUnavailable > 0 の場合、GKE が同一の Compute Engine インスタンスを再利用し、既存 VM をインプレースで更新
  • ノードが基盤の VM を保持するため、アップグレード中もコンピュート容量が維持され、容量不足による失敗・停滞リスクが低減
  • サージノード用リソースを確保できない場合でも、既存ノードを 1 台ずつインプレース更新してアップグレードを進行できる

従来は VM の削除時に容量が解放され再取得に失敗するリスクがありましたが、今回のアップデートにより maxUnavailable > 0 の CPU ノードプールでは同一 VM をインプレースで更新するため、 容量を保持したままアップグレードが完了します。

⚙️ 主要機能

1️⃣ Compute Engine インスタンスの再利用によるインプレース更新

→CPU ノードプールのバージョンアップグレードで maxUnavailable > 0 の場合、GKE は同一の Compute Engine インスタンスを再利用し、ノードの既存容量を保持
→VM の削除・再作成が発生しないため、容量の一時解放に伴う再取得失敗のリスクがなくなる

2️⃣ リソース制約環境でのアップグレード信頼性向上

→リソース不足が原因でノードアップグレードが失敗・停滞するリスクを低減
→サージノード (maxSurge) 用の追加容量が確保できない場合でも、maxUnavailable の予算内で既存ノードを 1 台ずつインプレース更新して進行可能

3️⃣ 全 GKE バージョンへの適用とオプトアウト

→特定バージョンへのアップグレードに限らず、全 GKE バージョンに適用
→オプトアウトする場合は Cloud Customer Care に連絡

有効化条件surge upgrade で maxUnavailable > 0 を設定

❌ インスタンスが再利用されない (削除・再作成される) ケース

以下のシナリオでは GKE は既存インスタンスを再利用せず、削除して再作成します (予約由来でない容量は一時的に解放)。

✖バージョンアップグレード以外のノードプール更新 (マシンタイプ、ディスクタイプ、ディスクサイズの変更など)
✖GPU または TPU を含むノードプールのバージョンアップグレード
✖Spot VM またはプリエンプティブル VM を使用するノードプールのバージョンアップグレード
✖未完了の surge upgrade のロールバック
✖ノードの自動修復 (auto-repair)

📋 surge upgrade の設定プロファイル例

説明設定典型的なユースケース
バランス型 (デフォルト)。低速だが最も中断が少ないmaxSurge=1 maxUnavailable=0ほとんどのワークロード
バランス型。リソース制約環境向け、サージリソース不要maxSurge=0 maxUnavailable=1リソース制約のあるノードプール

⚠️ 注意: 新規作成されるノードプールのデフォルトは maxSurge=1、maxUnavailable=0 です。 インプレース更新の恩恵を受けるには maxUnavailable を 0 より大きい値に明示的に設定する必要があります。 また、Spot VM を使用するノードでは可用性保証がないため surge upgrade の設定値は無視されます。

🛠️ 設定方法

📌 前提条件

✓GKE Standard クラスタの CPU ノードプールであること (Autopilot ではノードプール設定をユーザーが管理しないため対象外)
✓ノードプールのアップグレード戦略が surge upgrade (SURGE) であること

ステップ 1: 既存ノードプールで maxUnavailable を 0 より大きい値に設定

Bash 
gcloud container node-pools update NODE_POOL_NAME \
    --cluster=CLUSTER_NAME \
    --max-surge-upgrade=0 --max-unavailable-upgrade=1

固定容量でアップグレードする場合の設定例です。maxSurge=0、maxUnavailable=1 とすることで、 サージノード用の追加リソースを使わずに 1 台ずつノードをインプレースで更新します。

ステップ 2: (新規作成の場合) 固定容量アップグレード設定でクラスタ/ノードプールを作成

Bash 
# クラスタ作成時に設定する場合
gcloud container clusters create CLUSTER_NAME \
    --max-surge-upgrade=0 --max-unavailable-upgrade=1

# 既存クラスタにノードプールを作成する場合
gcloud container node-pools create NODE_POOL_NAME \
    --num-nodes=NUMBER_NODES --cluster=CLUSTER_NAME \
    --max-surge-upgrade=SURGE_NODES --max-unavailable-upgrade=UNAVAILABLE_NODES

ステップ 3: 設定の確認

Bash 
gcloud container node-pools describe NODE_POOL_NAME \
    --cluster=CLUSTER_NAME

surge upgrade が有効なノードプールでは strategy が SURGE と表示されます。 upgradeSettings の maxUnavailable が 0 より大きいことを確認してください。

💪 メリット

💼 ビジネス面

  • アップグレードの信頼性向上: 容量不足による失敗・停滞リスクが低減され、クラスタのバージョン維持 (セキュリティパッチ適用など) を計画どおり進めやすい
  • 追加コストなしの容量保持: サージノード用の追加 VM を作成せずに容量を保持できるため、リソース制約環境でも追加の予約購入などを減らせる可能性

🔧 技術面

  • コンピュート容量の維持: アップグレード中に容量が解放されず、同一マシンタイプの再取得に失敗するリスクがない
  • リソース逼迫環境での進行保証: サージ用容量が確保できなくても maxUnavailable の予算で 1 台ずつインプレース更新して進行可能
  • 移行作業が不要: maxUnavailable > 0 を設定済みであれば、全 GKE バージョンで自動的に適用

⚠️ デメリット・制約事項

🚫 制限事項

✖対象は CPU ノードプールのバージョンアップグレードのみ。マシンタイプ、ディスクタイプ、ディスクサイズ変更などではインスタンスは再利用されない
✖GPU / TPU を含むノードプール、Spot VM / プリエンプティブル VM を使用するノードプールのバージョンアップグレードは対象外
✖未完了の surge upgrade のロールバックやノード自動修復時もインスタンスは再利用されない
✖デフォルト設定 (maxSurge=1、maxUnavailable=0) では有効にならず、maxUnavailable > 0 の明示的な設定が必要

🤔 考慮すべき点

⚠️maxUnavailable > 0 に設定すると、その台数分のノードが同時に利用不可になる。他のノードに空き容量がない場合、Pod はアップグレード完了まで Pending 状態で待機する可能性
⚠️Drain 時には PodDisruptionBudget と GracefulTerminationPeriod が最大 1 時間尊重されるが、1 時間を超えると残りの Pod は強制退避
⚠️オプトアウトにはセルフサービスの設定がなく、Cloud Customer Care への連絡が必要
⚠️中断を最小化したいワークロードでは、従来どおり maxSurge ベースの設定 (サージノード方式) との使い分けを検討

🎯 ユースケース

📍 ユースケース 1: 容量が逼迫したリージョンでのクラスタアップグレード

シナリオ: 特定のマシンタイプの在庫が逼迫しているゾーンで GKE Standard クラスタを運用しており、過去にノードアップグレード時の VM 再作成で容量を確保できず、アップグレードが停滞したことがある。

Bash 
gcloud container node-pools update prod-pool \
    --cluster=prod-cluster \
    --max-surge-upgrade=0 --max-unavailable-upgrade=1
✅ 効果: バージョンアップグレード時に既存 VM がインプレースで更新されるため、容量が解放されず、在庫逼迫による再取得失敗が発生しない。アップグレードが確実に進行する。

💰 ユースケース 2: 予約を使わないコスト重視環境での定期アップグレード

シナリオ: Compute Engine の予約 (reservation) を購入せずにコストを抑えて運用しており、毎月の GKE マイナーバージョン/パッチアップグレードを自動アップグレードに任せたいが、容量リスクが懸念だった。

✅ 効果: maxUnavailable > 0 を設定しておけば、予約なしでもアップグレード中の容量が VM ごと保持されるため、追加の予約コストをかけずにアップグレードの信頼性を確保できる。

🔗 関連サービス・機能

🖥️ Compute Engine

GKE Standard のノードは Compute Engine VM 上で動作。本アップデートはこの VM をインプレースで更新する仕組みであり、Compute Engine の容量 (在庫) や予約 (reservation) の考え方と密接に関連。

🔀 GKE ノードアップグレード戦略 (surge upgrade / blue-green upgrade)

本機能は surge upgrade の maxUnavailable 設定に基づく。中断を最小化したい場合はサージノード方式 (maxSurge) や blue-green upgrade との使い分けが必要。

🛡️ PodDisruptionBudget (PDB)

ノード Drain 時に最大 1 時間尊重されるため、ワークロードの可用性要件に合わせた PDB の設定が重要。

📈 クラスタオートスケーラー

surge upgrade はクラスタオートスケーラーと連携し、アップグレード中のノードへの変更を防止する。

📌 まとめ

GKE Standard の CPU ノードプールで、maxUnavailable > 0 の surge upgrade 設定時に 既存 VM をインプレース更新する動作が全バージョンで有効になり、 容量不足によるアップグレードの失敗・停滞リスクが大幅に低減されました。 リソース逼迫環境や予約なしで運用しているクラスタでは、ノードプールの maxUnavailable 設定を見直し、 GPU/TPU・Spot VM ノードプールなど対象外のケースを確認した上で、 固定容量アップグレードの活用を検討することを推奨します。
