📊 Looker データリネージが GA

リリース日: 2026-10-26
Looker (Google Cloud core) Knowledge Catalog Data Lineage API 一般提供 (GA)

📋 概要

Knowledge Catalog における Looker (Google Cloud core) のデータリネージ (系統) サポートが 一般提供 (GA) になりました。 BigQuery のデータソースから Looker のセマンティックレイヤー (LookML ビュー / Explore) を経て、 ダッシュボード、ダッシュボードエレメント、Look、LookML ダッシュボード、 Conversational Analytics エージェントといった下流アセットに至る end-to-end のデータフローを可視化できます。

今回の GA では LookML ダッシュボードと Conversational Analytics エージェントまでの可視性が追加されたほか、 リネージの有効化が Data Lineage API とサービスレベルの取り込み制御 (ingestion control) で 独立管理されるようになり、Looker 内部の Knowledge Catalog メタデータ設定から分離されました。 取り込み制御は組織・フォルダ・プロジェクトの各レベルで設定できます。

💡 補足: 2026-10-21 に GA となった Knowledge Catalog によるメタデータの自動カタログ化の時点では、 データリネージ統合は Preview のままでした。今回のアップデートで、リネージ統合自体が GA に昇格しています。

❌ Before (アップデート前の課題)

  • データリネージ統合は Preview 提供で、本番のデータガバナンス・監査ワークフローへの組み込み判断が難しかった
  • LookML ダッシュボードや Conversational Analytics エージェントまでの end-to-end の可視性が提供されていなかった
  • リネージの有効化設定が Looker の Knowledge Catalog メタデータ統合設定と結び付き、Looker Admin パネル内の Preview 用設定に依存していた

✅ After (アップデート後の改善)

  • GA となり、データガバナンス・影響分析・監査ワークフローの本番基盤として利用可能に
  • LookML ダッシュボードと Conversational Analytics エージェントを含む end-to-end のリネージ可視性を追加
  • Data Lineage API とサービスレベルの取り込み制御で独立管理。組織・フォルダ・プロジェクトの各レベルで制御可能 (Looker Admin パネルでの設定は不要)

BigQuery のデータソースから LookML ビュー / Explore を経由して、ダッシュボード・Look・LookML ダッシュボード・ Conversational Analytics エージェントに至るデータフローを Knowledge Catalog のリネージグラフで 双方向に追跡できます。 右方向に下流影響を評価し、左方向に上流の出所を監査できます。

⚡ 主要機能

1️⃣ End-to-end データリネージの GA

BigQuery ソース → LookML ビュー / Explore → ダッシュボード / Look / LookML ダッシュボード / Conversational Analytics エージェントのデータフローを可視化。 リネージグラフは対象アセットを中央ノードとし、左に上流ソース、右に下流コンシューマを表示する双方向レイアウト。 下流影響分析 (例: カラム削除前に破損し得るダッシュボードを特定) と上流データ監査 (指標の出所・変換・管理の連鎖を追跡) に対応します。

2️⃣ LookML ダッシュボードと Conversational Analytics エージェントのサポート (今回追加)

GA ローンチで、LookML ダッシュボードと Conversational Analytics エージェントまでの end-to-end の可視性が追加されました。 サポート対象の Looker アセット: Looker ダッシュボード、ダッシュボードエレメント (タイル)、Look、 LookML ダッシュボード、Looker エージェント (Conversational Analytics エージェント)、LookML Explore、LookML ビュー。

3️⃣ リネージ有効化の独立管理 (今回変更)

リネージの有効化は Data Lineage API とサービスレベルの取り込み制御で管理され、 Looker 内部の Knowledge Catalog メタデータ統合のオプトアウト設定から分離されました。 Looker Admin パネルでの設定は不要です。Preview 期間中に Looker Admin パネルで構成した設定はリネージ統合に適用されなくなりました。 Data Lineage API が有効なプロジェクトの Looker (Google Cloud core) インスタンスでは、リネージ取り込みがデフォルトで有効です。

4️⃣ 組織・フォルダ・プロジェクトレベルの取り込み制御

データリネージの取り込みを組織、フォルダ、プロジェクトの各レベルで制御可能。 Knowledge Catalog は プロジェクト → フォルダ → 組織 の順にリソース階層を評価し、 最初に明示的に設定された構成を適用します (どのレベルにも設定がない場合はシステムデフォルト)。 サービス統合 (LOOKER_CORE など) ごとに独立して構成を解決します。

5️⃣ リネージの閲覧とフィルタリング

Knowledge Catalog の検索ページで BigQuery テーブルや Looker アセットを検索し、詳細ページの Lineage タブでグラフを表示。 List ビューではエンティティタイプでフィルタ可能 (例: Looker Dashboard、LookML Dashboard、 Looker Look に絞り込み、中間の LookML ビュー / Explore を除外)。 ノードの Aspects セクションから下流アセットの所有者 (メールアドレス) を確認できます。

🛠️ 設定方法

✅ 前提条件

✓Looker (Google Cloud core) インスタンスと BigQuery データをホストする各 Google Cloud プロジェクトで Data Lineage API (datalineage.googleapis.com) が有効であること
✓閲覧ユーザーに roles/looker.schemaViewer、roles/dataplex.catalogViewer (または同等権限)、roles/datalineage.viewer が付与されていること

📝 ステップ 1: Data Lineage API の有効化と取り込み設定の確認

Data Lineage API を有効化し、Looker (Google Cloud core) のサービスレベルのリネージ統合が有効であることを確認します (API が有効なプロジェクトではデフォルトで有効)。 フォルダや組織内の全プロジェクトに対して一括で API を有効化するには、hierarchical service activation のルールに従います。

📝 ステップ 2: 閲覧用 IAM ロールの付与

Bash looker.schemaViewer ロールの付与 (gcloud CLI のみ) 
gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member=PRINCIPAL_TYPE:PRINCIPAL_ID \
  --role=roles/looker.schemaViewer
💡 ポイント: roles/looker.schemaViewer は gcloud CLI でのみ付与でき、プロジェクトレベルでの付与が必須です。

💼 ビジネス面

✓本番ガバナンス基盤としての採用: GA 昇格により、データガバナンス・影響分析・監査ワークフローの本番基盤として安心して利用できる
✓AI 活用まで含めた可視性: Conversational Analytics エージェントがリネージ対象になり、AI エージェントが参照するデータの出所まで追跡でき、AI 活用時の説明責任を果たしやすくなる
✓変更管理の安全性向上: スキーマ変更前に影響を受けるダッシュボードと所有者を特定でき、ダッシュボード破損のリスクを低減できる

⚙️ 技術面

✓有効化管理の簡素化: Looker Admin パネルでの設定が不要になり、Data Lineage API とサービスレベルの取り込み制御のみで管理できる
✓階層的な取り込み制御: 組織・フォルダ・プロジェクトの各レベルで制御でき、開発用プロジェクトの除外やガバナンスポリシーの一括適用が可能
✓双方向リネージ: 下流影響分析と上流監査の両方向にグラフを辿れ、List ビューのエンティティフィルタでユーザー向けアセットに絞り込める

⚠️ デメリット・制約事項

🚧 制限事項

✗リネージは Looker (Google Cloud core) インスタンスのみサポート (Looker (original) は非対応)
✗データソースは BigQuery のみサポート
✗リネージはオブジェクトレベルのみで、カラムレベルのリネージは未サポート
✗リネージデータはリアルタイムではない (同期は通常 4 時間、Looker メタデータエクスポートのタイミングによっては最大 8 時間。初回同期は最大 24 時間)
✗複雑なカスタム SQL (Liquid テンプレート、複雑な JOIN を含む派生テーブルなど) で定義された LookML は完全にパースされず、ノードが分断される場合がある

🤔 考慮すべき点

  • LookML 内の SQL テーブル参照は、対応する BigQuery テーブルと大文字・小文字が厳密に一致している必要がある (不一致だと下流リネージがグラフに表示されない)
  • Preview 期間中に Looker Admin パネルで構成した設定は適用されなくなったため、取り込み制御の現在の構成を Data Lineage API で確認し、意図した有効 / 無効状態かを検証する必要がある
  • プロジェクトレベルの設定がフォルダ・組織レベルの設定より優先されるため、階層全体での設定の整合性に注意が必要
  • roles/looker.schemaViewer はプロジェクトレベルで付与され、付与されたユーザーは統合が有効なプロジェクト内の全インスタンスのメタデータを閲覧できる

💡 ユースケース

🔎 ユースケース 1: BigQuery スキーマ変更前の下流影響分析

シナリオ: データエンジニアが BigQuery テーブルのカラム削除を計画しており、 影響を受ける Looker ダッシュボードや Conversational Analytics エージェントを事前に特定したい。

Text 実装例 
1. Knowledge Catalog の Search で対象の BigQuery テーブルを検索
2. Lineage タブでリネージグラフを表示し、右方向 (下流) を確認
3. List ビューでエンティティフィルタに「Looker Dashboard」「LookML Dashboard」
   「Looker Look」を指定し、ユーザー向けアセットに絞り込み
4. 各ノードの Aspects セクションで所有者 (メールアドレス) を確認し、事前に連絡

効果: スキーマ変更によるダッシュボード破損を未然に防ぎ、所有者への事前連絡を含む安全な変更管理プロセスを実現できる。

🏢 ユースケース 2: 組織全体でのリネージ取り込みポリシーの一元管理

シナリオ: ガバナンス管理者が、本番環境のプロジェクト群ではリネージを有効化し、 開発用フォルダ配下ではリネージ取り込みを無効化したい。

効果: 組織・フォルダ・プロジェクトレベルの取り込み制御により、開発ワークロードを除外しつつ 本番環境で一貫したリネージポリシーを適用できる。プロジェクトレベルの明示的な設定が最優先されるため、個別の例外設定も可能。

📑 ユースケース 3: 経営ダッシュボード指標の上流監査

シナリオ: 監査担当者が、経営ダッシュボードや Look に表示される指標の出所、変換、 管理の連鎖 (chain of custody) を確認したい。

効果: リネージグラフを左方向 (上流) に辿ることで、指標が LookML Explore / ビューを経由して どの BigQuery テーブルに由来するかを追跡でき、監査ワークフローを効率化できる。

💰 料金

  • Looker (Google Cloud core) のデータリネージは一般提供されていますが、課金は将来の日付から開始され、事前に Mandatory Service Announcement (MSA) で通知されます

リネージグラフの表示・検索基盤。2026-10-21 に GA となったメタデータの自動カタログ化と組み合わせて、検索・ガバナンス・リネージを一元化できる。

🗄️ BigQuery

🤖 Conversational Analytics

Looker データに自然言語で質問できるエージェント。今回の GA でリネージの下流アセットとして可視化されるようになった。

📝 まとめ

Looker (Google Cloud core) のデータリネージが GA となり、BigQuery から LookML ダッシュボードや Conversational Analytics エージェントまでの end-to-end のデータフローを 本番ガバナンス基盤として追跡できるようになりました。 有効化管理が Looker 内部設定から Data Lineage API とサービスレベルの取り込み制御に移行したため、 既存ユーザーはまず現在の取り込み構成を確認し、組織・フォルダ・プロジェクトレベルでのポリシー設計と、 課金開始 (MSA で事前通知) に備えたコスト計画を進めることを推奨します。
