Cloud Composer Gen 3 から Cloud Run 内部 Ingress へのアクセス

Cloud Composer Beta Networking
2026-06-02

📋 概要

Cloud Composer の Managed Airflow (Gen 3) 環境において、 内部 Ingress に制限された Cloud Run エンドポイントに、環境のネットワークアタッチメントを経由してアクセスできるようになりました。

--cloud-run-functions-routing via-network-attachment オプションを使用して、 Cloud Run へのトラフィックをネットワークアタッチメント経由でルーティングし、セキュアな内部通信を実現します。

💡 ポイント: セキュリティ要件の高いエンタープライズ環境で、データパイプラインのオーケストレーションと内部サービス間の通信を安全に行いたいデータエンジニアや MLOps エンジニアに特に有用です。

🔄 Before / After 比較

❌ Before

  • Cloud Run の Ingress を「internal」に制限すると、テナントプロジェクトの Airflow ワーカーからアクセス不可
  • DAG から呼び出すには Ingress 制限を緩和する必要があった
  • セキュリティポリシーとオーケストレーション要件にトレードオフが存在

✅ After

  • 内部 Ingress 制限を維持したまま、Airflow DAG から Cloud Run を呼び出し可能
  • Ingress 設定を緩和する必要なし、セキュリティポリシーを維持
  • .run.app / .cloudfunctions.net ドメインが自動ルーティング

⚡ 主要機能

🔀 Cloud Run トラフィックルーティング設定

--cloud-run-functions-routing パラメータにより、Cloud Run へのトラフィックルーティング方式を制御可能

  • direct (デフォルト): 通常の Google API ルーティング
  • via-network-attachment: ネットワークアタッチメント経由でルーティング

🌐 対象ドメインの自動ルーティング

以下のドメインへのトラフィックが自動的にネットワークアタッチメント経由でルーティングされます。

  • .run.app ドメイン
  • .cloudfunctions.net ドメイン
  • カスタムドメイン (Private IP 環境ではデフォルトでネットワークアタッチメント経由)

🔗 VPC 接続操作との同時実行

VPC ネットワークへの接続操作と同時に設定可能。既存環境への後付け設定にも対応し、gcloud CLI / REST API の両方で設定できます。

🔧 技術仕様

ルーティング設定オプション

項目 詳細
パラメータ名 (gcloud) --cloud-run-functions-routing
API フィールド config.nodeConfig.trafficRoutingConfig.cloudRunFunctionsRouting
値: direct デフォルト。通常の Google API ルーティングを使用
値: via-network-attachment ネットワークアタッチメント経由でルーティング
対象ドメイン .run.app, .cloudfunctions.net
API バージョン v1beta1
gcloud コンポーネント gcloud beta composer

前提条件と制約

項目 詳細
ネットワーキングタイプ Private IP 必須
VPC 接続 環境が VPC ネットワークに接続済みであること
切断制限 ルーティング有効時は VPC 切断不可 (先にデフォルトルーティングに戻す必要あり)
対応バージョン すべての Managed Airflow (Gen 3) バージョン

API リクエスト例

JSON 
{
  "config": {
    "nodeConfig": {
      "trafficRoutingConfig": {
        "cloudRunFunctionsRouting": "VIA_NETWORK_ATTACHMENT"
      }
    }
  }
}

📝 設定方法

⚠️ 前提条件: Managed Airflow (Gen 3) 環境が作成済み / Private IP ネットワーキング使用 / VPC ネットワークに接続済み (または同時接続) / gcloud CLI beta コンポーネントがインストール済み

Step 1: 環境のネットワーキングタイプを確認

Bash 
gcloud beta composer environments describe ENVIRONMENT_NAME \
    --location LOCATION \
    --format="get(config.privateEnvironmentConfig)"

Step 2: VPC ネットワーク接続の確認または設定

Bash 
# VPC ネットワークへの接続 (未接続の場合)
gcloud beta composer environments update ENVIRONMENT_NAME \
    --location LOCATION \
    --network NETWORK_ID \
    --subnetwork SUBNETWORK_ID

# 既存のネットワークアタッチメントを使用する場合
gcloud beta composer environments update ENVIRONMENT_NAME \
    --location LOCATION \
    --network-attachment projects/PROJECT/regions/REGION/networkAttachments/ATTACHMENT_NAME

Step 3: Cloud Run トラフィックルーティングを有効化

Bash 
gcloud beta composer environments update ENVIRONMENT_NAME \
    --location LOCATION \
    --cloud-run-functions-routing via-network-attachment

# VPC 接続と同時に設定する場合
gcloud beta composer environments update ENVIRONMENT_NAME \
    --location LOCATION \
    --network NETWORK_ID \
    --subnetwork SUBNETWORK_ID \
    --cloud-run-functions-routing via-network-attachment

Step 4: 設定の確認

Bash 
gcloud beta composer environments describe ENVIRONMENT_NAME \
    --location LOCATION \
    --format="get(config.nodeConfig.trafficRoutingConfig)"

Step 5: (オプション) デフォルトルーティングに戻す

Bash 
gcloud beta composer environments update ENVIRONMENT_NAME \
    --location LOCATION \
    --cloud-run-functions-routing direct

✅ メリット

💼 ビジネス面

✓ セキュリティコンプライアンスの維持: 内部 Ingress 制限を解除せず安全なアクセスを実現。規制要件に準拠
✓ 運用の簡素化: VPN やプロキシの回避策が不要に。インフラの複雑性を低減
✓ コスト効率: VPN ゲートウェイやプロキシ VM が不要。ネットワーキングコストを削減

🔧 技術面

✓ ゼロトラストとの親和性: 内部トラフィックのみ許可する構成を維持しながらオーケストレーション可能
✓ シンプルな設定: 単一の gcloud コマンドまたは API 呼び出しで完了
✓ 既存環境への適用: 再作成なしに後付けで設定可能

⚠️ 制限事項・注意点

制限事項

🚫 環境は Private IP ネットワーキングを使用する必要がある (Public IP では利用不可)
🔒 ルーティング有効時は VPC ネットワークからの切断不可 (先にデフォルトルーティングに戻す必要がある)
🧪 現時点では Beta 機能。gcloud beta および v1beta1 API でのみ利用可能
📄 Terraform での設定は公式ドキュメントでまだ明記されていない

考慮すべき点

💡 ルーティングは .run.app と .cloudfunctions.net の全トラフィックに適用 (特定サービスのみの選択的ルーティングは不可)
🛡️ VPC ネットワーク側でのファイアウォールルールやルーティング設定が適切に構成されている必要がある
🌐 DNS 解決はデフォルトの方法で行われるため、プライベート DNS ゾーンとの相互作用を考慮すること
📐 環境の内部 IP 範囲 (デフォルト: 100.64.128.0/20) と VPC サブネットワークの IP 範囲が重複しないこと

🎯 ユースケース

🤖 ML パイプラインでの内部モデルサービングエンドポイント呼び出し

シナリオ: ML エンジニアが Airflow DAG からモデル推論サービス (Cloud Run にデプロイ、内部 Ingress に制限) を呼び出してバッチ推論パイプラインを構築

効果: モデルサービングの内部 Ingress 制限を維持しながら、Airflow からの自動バッチ推論が可能。外部公開のリスクなくパイプラインを運用できる。

Python 
from airflow import DAG
from airflow.providers.http.operators.http import SimpleHttpOperator
from datetime import datetime

with DAG(
    "ml_batch_inference",
    start_date=datetime(2026, 6, 1),
    schedule_interval="@daily",
) as dag:
    call_inference = SimpleHttpOperator(
        task_id="call_model_endpoint",
        http_conn_id="internal_cloud_run",
        endpoint="/predict",
        method="POST",
        data='{"instances": [...]}',
        headers={"Content-Type": "application/json"},
    )

🔄 マイクロサービスアーキテクチャでのイベント処理

シナリオ: データエンジニアが、内部に制限された複数の Cloud Run サービス (データ変換、バリデーション、通知) を Airflow DAG から順番に呼び出してデータパイプラインを構成

効果: 全サービスを内部 Ingress に制限したまま、Airflow によるオーケストレーションが可能。サービスメッシュなしにセキュアなサービス間連携を実現。

🏦 セキュリティ要件の厳しい金融データ処理

シナリオ: 金融機関が PCI DSS や SOC 2 などの規制要件に準拠しつつ、Cloud Run 上のデータ処理サービスを Airflow から呼び出す

効果: すべてのサービスを内部ネットワーク内に閉じたまま、データ処理パイプラインを安全にオーケストレーション。コンプライアンス監査への対応も容易に。
