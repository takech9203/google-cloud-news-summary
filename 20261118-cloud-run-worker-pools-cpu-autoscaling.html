⚡ Cloud Run ワーカープールの
CPU オートスケーリング

☁️ Cloud Run Preview 🏭 Worker Pools
📅 リリース日: 2026-11-18

📋 概要

Cloud Run ワーカープールで、平均 CPU 使用率に基づくオートスケーリングが Preview として利用可能になりました。--scaling=auto フラグを指定するだけで、 デフォルトの CPU ターゲット (60%) で 1〜100 インスタンスの範囲を自動調整。 カスタムターゲット (10%〜90%) や最小・最大インスタンス数の指定にも対応します。

ワーカープールは HTTP リクエストを受け付けないバックグラウンド処理 (Pub/Sub の Pull 型コンシューマや Kafka コンシューマなど) 向けの Cloud Run リソースです。 リクエスト駆動のスケーリングが使えないため、これまで自動化には追加の仕組みが必要でしたが、 今回のアップデートで Cloud Run 本体のマネージド機能として実現できるようになりました。

❌ Before: アップデート前の課題

  • 手動スケーリング (固定インスタンス数) がデフォルト。--instances を人手やスクリプトで変更する必要があった
  • 自動化には CREMA などのカスタムオートスケーラーを別途デプロイ・運用する必要があった
  • Prometheus クエリや KEDA ベースの YAML、専用サービスアカウントなどセットアップが煩雑で運用負荷が高かった

✅ After: アップデート後の改善

  • --scaling=auto を指定するだけでマネージドな CPU オートスケーリングが有効化
  • デフォルトで CPU 60% ターゲット・1〜100 インスタンス。--scaling-cpu-target / --min / --max でカスタマイズ可能
  • 追加のオートスケーラー運用が不要。スケーリング設定の変更では新リビジョンも作成されない

ワーカープールの全インスタンスの平均 CPU 使用率を 1 分間隔で評価し、 ターゲット使用率との比から必要なインスタンス数を再計算するオートスケーリングループです。 スケールダウン時は 5 分間の安定化ウィンドウにより、インスタンス数の頻繁な増減 (フラッピング) を防ぎます。

🚀 主要機能

1️⃣ デフォルト CPU ターゲットによるオートスケーリング

  • --scaling=auto の指定で、CPU 使用率 60% をターゲットに 1〜100 インスタンスで自動スケール
  • デフォルトターゲットのまま、--min / --max のみのカスタマイズも可能
  • スケーリングモードやインスタンス上限の変更では新しいリビジョンは作成されない

2️⃣ カスタム CPU ターゲットの設定

  • --scaling-cpu-target で 0.1〜0.90 (10%〜90%) の範囲を指定可能
  • 高めのターゲット (80〜90%): 安定したバックグラウンド処理・バッチ処理向け。リソース効率とコストを最適化
  • 低めのターゲット (20〜40%): スパイクの多いワークロードやレイテンシ要件が厳しい処理向け。余裕を持った先行プロビジョニング

3️⃣ スケーリング動作の制御

  • 必要インスタンス数は「直近 1 分間の平均 CPU 使用量 ÷ インスタンスあたりの CPU 数 ÷ CPU ターゲット」を切り上げて算出
  • プールレベルで計算し、インスタンススプリットの設定に応じてアクティブなリビジョンへ配分
  • スケールダウンには 5 分間 (300 秒) の安定化ウィンドウを使用し、直近 5 分間の最大推奨値を維持

4️⃣ デフォルト設定への復元

  • --scaling-cpu-target=default や --min=default / --max=default で、オートスケーリングを有効にしたままデフォルト値 (60%、1〜100 インスタンス) に戻せる

📄 YAML 設定例

YAML WorkerPool のオートスケーリング設定 
apiVersion: run.googleapis.com/v1
kind: WorkerPool
metadata:
  name: WORKER_POOL
  annotations:
    run.googleapis.com/launch-stage: BETA
    run.googleapis.com/scalingMode: automatic
    run.googleapis.com/scaling-cpu-target: 'CPU_TARGET'
    run.googleapis.com/minScale: 'MIN_INSTANCES'
    run.googleapis.com/maxScale: 'MAX_INSTANCES'
💡 カスタムアノテーション (scaling-cpu-target、minScale、maxScale) は省略するとデフォルト値が使われます。 手動スケーリングから切り替える場合は run.googleapis.com/manualInstanceCount アノテーションを削除します。

1デフォルト CPU ターゲットでオートスケーリングを有効化
Bash gcloud でオートスケーリングを有効化 
# 新規デプロイ時
gcloud beta run worker-pools deploy WORKER_POOL \
  --image=IMAGE_URL \
  --scaling=auto

# 既存ワーカープールの更新
gcloud beta run worker-pools update WORKER_POOL \
  --scaling=auto

CPU 使用率 60% をターゲットに、1〜100 インスタンスの範囲で自動スケールします。

2カスタム CPU ターゲットとインスタンス上限を設定
Bash カスタムターゲットと上限の指定 
gcloud beta run worker-pools update WORKER_POOL \
  --scaling-cpu-target=0.75 \
  --min=2 \
  --max=50

CPU ターゲットは 0.1〜0.90 の範囲で指定。省略した設定にはデフォルト値 (60%、最小 1、最大 100) が適用されます。

3(必要に応じて) デフォルト設定に戻す
Bash デフォルト値への復元 
gcloud beta run worker-pools update WORKER_POOL \
  --scaling-cpu-target=default \
  --min=default \
  --max=default
4スケーリング動作をモニタリング

Cloud Monitoring で run.googleapis.com/container/instance_count メトリクスを確認し、 負荷テストの結果に基づいてターゲットを調整します。まずはデフォルトターゲットから始めることが推奨されています。

💪 メリット

💼 ビジネス面

✅運用コストの削減: カスタムオートスケーラー (CREMA など) の構築・運用が不要になり、スケーリングの仕組みを Google のマネージド機能に任せられる
✅インフラコストの最適化: 負荷の低い時間帯はインスタンスを自動縮小し、ピーク時のみ拡張。固定インスタンス数運用に比べて無駄な稼働を削減

🛠️ 技術面

✅設定の簡素化: フラグ 1 つ (--scaling=auto) で有効化でき、gcloud / YAML / REST API のいずれからも設定可能
✅安定したスケーリング動作: 5 分間のスケールダウン安定化ウィンドウと切り上げ計算により、インスタンス数の振動 (フラッピング) を抑制
✅リビジョンを増やさない設定変更: スケーリングモードやターゲット、上限値の変更では新リビジョンが作成されず、変更の影響範囲が小さい
✅ワークロード特性に合わせた調整: CPU ターゲットを 10〜90% の範囲で調整でき、レイテンシ重視・コスト重視のどちらにも最適化できる

⚠️ デメリット・制約事項

🚧 制限事項

❌Preview (Pre-GA) 機能であり、Pre-GA Offerings Terms が適用される。サポートが限定される可能性がある
❌最小インスタンス数は 1 以上が必須で、ゼロへのスケールインはできない (停止するには手動スケーリングで 0 を指定)
❌スケーリング指標は CPU 使用率のみ。メモリ使用率やキューの深さ (未処理メッセージ数) ベースのスケーリングには対応しない
❌CREMA によるスケーリングと併用不可 (CREMA 利用中は手動スケーリングへの切り替えが必要)

🤔 考慮すべき点

  • CPU 使用率はキューのバックログを直接反映しないため、Pub/Sub や Kafka の未処理メッセージ数に厳密に追従させたい場合は、引き続き CREMA (KEDA ベース) などの外部メトリクスオートスケーリングが適する場合がある
  • 単一スレッドのアプリをマルチ CPU インスタンスで動かすと平均 CPU 使用率が低く観測され、スケーリング判断に影響する可能性がある
  • スケールアップによりバックエンド (Cloud SQL など) への接続数が増えるため、--max で上限を適切に設定することが推奨される
  • スケールダウンは 5 分間の安定化ウィンドウの影響で緩やかに進むため、急激なコスト削減は期待しない

🎯 ユースケース

📨 ユースケース 1: Pub/Sub Pull 型コンシューマの自動スケーリング

シナリオ: Pub/Sub サブスクリプションからメッセージを Pull して処理するワーカープールを運用。 日中はメッセージ流量が多く、夜間はほぼゼロになるため、固定インスタンス数では ピーク時に処理遅延が発生し、閑散時にはリソースが無駄になっていた。

Bash 実装例 
gcloud beta run worker-pools deploy pubsub-consumer \
  --image=us-docker.pkg.dev/PROJECT_ID/repo/consumer:latest \
  --scaling=auto \
  --min=1 \
  --max=30
✅ 効果: CPU 負荷の増減に応じてインスタンス数が 1〜30 の範囲で自動調整され、 ピーク時の処理遅延と閑散時の無駄な稼働コストの両方を削減できる。

🔄 ユースケース 2: バッチ的なデータ変換ワーカーのコスト最適化

シナリオ: レイテンシ要件が緩いデータ変換処理をワーカープールで実行。 リソース効率を最大化してコストを抑えたい。

Bash 実装例 
gcloud beta run worker-pools update batch-transformer \
  --scaling-cpu-target=0.85 \
  --max=20
✅ 効果: CPU ターゲットを 85% に引き上げることで各インスタンスを高い使用率で稼働させ、 必要なインスタンス数を最小化してインフラコストを削減できる。

💰 料金・利用可能リージョン

💵 料金: CPU オートスケーリング自体に追加料金はなく、ワーカープールのインスタンスが稼働した分の vCPU・メモリに対して Cloud Run のインスタンスベース課金が適用されます。 稼働インスタンス数が負荷に追従するため、固定インスタンス数での運用に比べて低負荷時のコストを抑えられます。 詳細は Cloud Run の料金ページ を参照。
🌍 利用可能リージョン: リリースノートおよびドキュメントにリージョン制限の記載はありません。 最新情報は Cloud Run のドキュメント を参照してください。

🔗 関連サービス・機能

⚡ Cloud Run サービス (metrics-based scaling)

リクエスト駆動のサービスでは従来から CPU 使用率とリクエスト同時実行数によるオートスケーリングが提供されており、今回ワーカープールにも CPU ベースの仕組みが拡張された。

🧩 Cloud Run External Metrics Autoscaling (CREMA)

KEDA ベースで Kafka や Prometheus などの外部メトリクスによりワーカープールをスケールする仕組み。キュー長ベースのスケーリングが必要な場合の選択肢だが、CPU オートスケーリングとは併用不可。

📈 Cloud Monitoring

run.googleapis.com/container/cpu/utilizations (スケーリング指標) や run.googleapis.com/container/instance_count (インスタンス数) のメトリクスでスケーリング動作を監視し、ターゲット調整に活用。

📨 Pub/Sub / Managed Service for Apache Kafka

ワーカープールの代表的なワークロードソース。メッセージ処理負荷が CPU 使用率としてスケーリングに反映される。

📝 まとめ

Cloud Run ワーカープールにマネージドな CPU オートスケーリングが追加され、 これまでカスタムオートスケーラーの構築・運用が必要だった負荷追従型のスケーリングが --scaling=auto フラグ 1 つで実現できるようになりました。

👉Pub/Sub コンシューマやバックグラウンド処理をワーカープールで運用しているチームは、まずデフォルトターゲット (60%) で有効化
👉Cloud Monitoring のインスタンス数メトリクスを観察しながら、ワークロード特性に合わせて CPU ターゲットと最小・最大インスタンス数を調整することを推奨
