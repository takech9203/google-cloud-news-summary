Data Lineage API searchLineageStreaming

Knowledge Catalog Preview

Google Cloud Release Notes

📋 概要

Data Lineage API に searchLineageStreaming メソッドが追加されました。 指定したアセットの Fully Qualified Name (FQN) を起点として、幅優先探索 (BFS) により リネージリンクをストリーミング形式で取得する機能です。

複数レベル、複数リージョン、複数プロジェクトにまたがるリネージグラフの探索を一度のリクエストで実行でき、 ストリーミングレスポンスにより大規模なリネージグラフでもタイムアウトすることなく効率的に結果を取得できます。

❌ Before (従来の searchLinks)

  • 単一レベルのリネージしか取得不可
  • 多段階追跡に複数回 API 呼び出しが必要
  • 大規模グラフでタイムアウト発生
  • 複数プロジェクト/リージョンの統合検索が困難
  • カラムレベルとテーブルレベルの同時取得が制限的

✅ After (searchLineageStreaming)

  • 最大深度 100 のマルチレベルリネージを一括取得
  • ストリーミングでリアルタイム返却、タイムアウト回避
  • 複数リージョン/プロジェクト横断の自動探索
  • ワイルドカードによるカラムレベルリネージ一括取得
  • プロセスメタデータもオプションで取得可能

🏗️ アーキテクチャ図

searchLineageStreaming はルートエンティティから幅優先探索を実行し、各深度のリネージリンクを発見次第ストリーミングレスポンスとして返却します。探索方向は上流 (UPSTREAM) または下流 (DOWNSTREAM) を指定可能です。

⚡ 主要機能

🔍 幅優先探索 (BFS)

  • レイヤーごとのグラフ探索
  • UPSTREAM / DOWNSTREAM 方向指定
  • 最大深度 100 (デフォルト: 5)

📡 ストリーミングレスポンス

  • リンク発見次第リアルタイム返却
  • タイムアウトリスクを排除
  • 大規模グラフでも効率的

🌐 マルチロケーション横断探索

  • 複数リージョンを一括指定
  • クロスプロジェクト自動探索
  • 課金プロジェクトは 1 つ

📐 カラムレベルリネージ (CLL)

  • カラム単位の依存関係追跡
  • ワイルドカード (*) で全カラム一括取得
  • テーブルとカラムの同時検索

🔧 パイプラインインサイト

  • maxProcessPerLink でプロセス情報取得
  • FieldMask で完全メタデータ取得
  • displayName, system 属性対応

🛠️ 設定方法

📋 前提条件:
  • Data Lineage API が有効化されていること
  • IAM ロール roles/datalineage.viewer 以上が付与されていること
  • エンティティレベル: datalineage.events.get 権限
  • カラムレベル: datalineage.events.getFields 権限

Step 1: API の有効化

Bash 
gcloud services enable datalineage.googleapis.com --project=PROJECT_ID

Step 2: 下流リネージの検索 (基本)

Bash 
curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -X POST https://datalineage.googleapis.com/v1/projects/my-project/locations/us:searchLineageStreaming \
  --data '{
    "parent": "projects/my-project/locations/us",
    "locations": ["us"],
    "rootCriteria": {
      "entities": {
        "entities": [{
          "fullyQualifiedName": "bigquery:my-project.dataset.source_table"
        }]
      }
    },
    "direction": "DOWNSTREAM"
  }'

Step 3: マルチリージョン + 深層探索

Bash 
curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -X POST https://datalineage.googleapis.com/v1/projects/my-project/locations/us:searchLineageStreaming \
  --data '{
    "parent": "projects/my-project/locations/us",
    "locations": ["us", "us-east1", "europe-west1"],
    "rootCriteria": {
      "entities": {
        "entities": [{
          "fullyQualifiedName": "bigquery:my-project.dataset.source_table"
        }]
      }
    },
    "direction": "DOWNSTREAM",
    "limits": {
      "maxDepth": 10,
      "maxResults": 5000,
      "maxProcessPerLink": 5
    }
  }'

Step 4: カラムレベルリネージ (ワイルドカード)

Bash 
curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -X POST https://datalineage.googleapis.com/v1/projects/my-project/locations/us:searchLineageStreaming \
  --data '{
    "parent": "projects/my-project/locations/us",
    "locations": ["us"],
    "rootCriteria": {
      "entities": {
        "entities": [{
          "fullyQualifiedName": "bigquery:my-project.dataset.my_table",
          "field": ["*"]
        }]
      }
    },
    "direction": "DOWNSTREAM"
  }'

💼 ビジネス面

影響分析の迅速化

スキーマ変更やテーブル削除前に下流への影響範囲を即座に特定。計画外のダウンタイムや障害を防止。

コンプライアンス対応

データの出自と変換履歴を完全に追跡。GDPR、SOC2 などの規制要件への対応を支援。

データ品質管理

問題のあるデータソースから影響を受ける全ダウンストリームアセットを特定。品質問題の波及範囲を即時把握。

⚙️ 技術面

タイムアウト回避

ストリーミングレスポンスにより、大規模グラフでもリクエスト切断リスクを排除。

API 呼び出し回数の削減

従来の searchLinks を複数回呼ぶ必要なし。単一リクエストでマルチレベルリネージを取得。

きめ細かい制御

maxDepth、maxResults、フィルタにより必要な範囲のみを効率的に取得。

クロスプロジェクト対応

組織内の複数プロジェクトにまたがるデータパイプラインの全体像を単一 API コールで把握。

⚠️ 制約事項・注意点

Preview ステータス

Pre-GA Offerings Terms が適用。サポートが限定的であり、本番ワークロードでの利用は慎重に検討が必要。

制限事項

  • maxDepth の上限は 100、maxResults の上限は 10,000
  • レスポンスの unreachable フィールドに到達不能なリソースが含まれる場合、結果が不完全な可能性
  • カラムレベルリネージには追加権限 (datalineage.events.getFields) が必要
  • Data Lineage API は CMEK (顧客管理暗号鍵) をサポートしていない
  • リクエストパスの parent とリクエストボディ内の parent プロパティが一致している必要がある

🎯 ユースケース

📝 ユースケース 1: スキーマ変更の影響分析

シナリオ: BigQuery ソーステーブルからカラムを削除する前に、そのカラムに依存する全ての下流テーブルやダッシュボードを特定したい。

効果: カラム削除によって破損する可能性のある Looker ダッシュボードや下流テーブルを事前に特定し、安全なスキーマ変更を実現。

Bash 
curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -X POST https://datalineage.googleapis.com/v1/projects/my-project/locations/us:searchLineageStreaming \
  --data '{
    "parent": "projects/my-project/locations/us",
    "locations": ["us"],
    "rootCriteria": {
      "entities": {
        "entities": [{
          "fullyQualifiedName": "bigquery:my-project.dataset.source_table",
          "field": ["email"]
        }]
      }
    },
    "direction": "DOWNSTREAM",
    "limits": { "maxDepth": 20 }
  }'

🔍 ユースケース 2: データ品質問題のルート原因分析

シナリオ: 下流レポートでデータ品質の問題が報告された。問題の発生源を特定するために上流を遡り、データの出自を確認したい。

効果: 問題のあるレポートテーブルから上流に遡り、どの変換プロセスがデータを加工したかを含めて完全なデータフローを可視化。

Bash 
curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -X POST https://datalineage.googleapis.com/v1/projects/my-project/locations/us:searchLineageStreaming \
  --data '{
    "parent": "projects/my-project/locations/us",
    "locations": ["us", "us-east1"],
    "rootCriteria": {
      "entities": {
        "entities": [{
          "fullyQualifiedName": "bigquery:my-project.analytics.report_table"
        }]
      }
    },
    "direction": "UPSTREAM",
    "limits": { "maxDepth": 15, "maxProcessPerLink": 3 }
  }'

🌍 ユースケース 3: マルチリージョンのデータガバナンス監査

シナリオ: 組織のデータガバナンスポリシーに基づき、特定の機密データが複数リージョンにわたってどのように流通しているかを監査したい。

効果: 単一の API コールで複数リージョン/プロジェクトを横断したデータフローの全体像を把握し、データレジデンシー要件の遵守を確認。
