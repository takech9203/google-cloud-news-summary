エージェントリビジョン管理とトラフィック分割

Gemini Enterprise Agent Platform Preview
2026-05-15

📋 概要

Gemini Enterprise Agent Platform において、エージェントリビジョン管理とトラフィック分割機能が Public Preview として利用可能になりました。

デプロイされたエージェントのイミュータブル（不変）なリビジョンを作成し、複数のアクティブなリビジョン間でトラフィックを分割することで、カナリアデプロイメントや安全なテストが実現します。

💡 ポイント: リビジョンの作成機能は常に有効であり、明示的に有効化する必要はありません。v1beta1 API、Console、Agent Platform SDK、REST API のいずれからも設定が可能です。

🔄 Before / After 比較

❌ Before

  • 新バージョンのデプロイで全トラフィックが即座に切り替わり、問題発生時の影響範囲が大きかった
  • 以前のバージョンへの迅速なロールバック手段がなかった
  • 段階的なデプロイメント戦略が取れなかった

✅ After

  • イミュータブルなリビジョンによるバージョン管理が可能に
  • パーセンテージベースのトラフィック分割でカナリアデプロイメントを実現
  • トラフィック設定の変更だけで即座にロールバック可能
  • 特定リビジョンへの直接クエリで個別テストも可能

⚡ 主要機能

📦 イミュータブルリビジョン

Versioned fields を更新すると自動的に新しい不変リビジョンを作成。一意のリソース名で識別され、動作の再現性を保証。

🔀 トラフィック分割

Manual: 整数パーセンテージで各リビジョンにトラフィックを配分（合計100%）
Always Latest: 全トラフィックを最新リビジョンに自動ルーティング

📋 リビジョン状態管理

Active: クエリ受付可能
Deprecated: クエリ不可（削除対象候補）
古いリビジョンの非推奨化でリソースクォータを管理

🎯 直接クエリ

特定リビジョンのリソースパスに直接クエリを送信可能。トラフィック分割ルールをバイパスして個別テストができる。

🔧 技術仕様

Versioned Fields（リビジョン作成トリガー）

以下のフィールドを更新すると新しいリビジョンが作成されます。Unversioned fields の更新は全リビジョンに共通で適用されます。

カテゴリ フィールド
PackageSpec pickleObjectGcsUri, dependencyFilesGcsUri, requirementsGcsUri, pythonVersion
DeploymentSpec env[], secretEnv[], firstPartyImageOverride, agentServerMode, pscInterfaceConfig, minInstances, maxInstances, resourceLimits, containerConcurrency
その他 classMethods[], agentFramework, SourceCodeSpec (source, languageSpec), identityType, agentCard[]

API エンドポイント

HTTP 
PATCH https://{LOCATION}-aiplatform.googleapis.com/v1beta1/projects/{PROJECT_ID}/locations/{LOCATION}/reasoningEngines/{RESOURCE_ID}?update_mask=traffic_config

🛠️ 設定方法

📝 前提条件:
  • Gemini Enterprise Agent Platform にエージェントがデプロイ済みであること
  • v1beta1 API へのアクセスが可能であること
  • エージェントのリソース ID を把握していること

Step 1: クライアント初期化

Python 
import vertexai
from google.genai import types as genai_types

http_options = genai_types.HttpOptions(
    api_version="v1beta1",
)

client = vertexai.Client(
    project="PROJECT_ID",
    location="LOCATION",
    http_options=http_options,
)

Step 2: リビジョンの一覧確認

Python 
revisions = client.agent_engines.runtimes.revisions.list(
    name="projects/PROJECT_ID/locations/LOCATION/reasoningEngines/RESOURCE_ID"
)

for revision in revisions:
    print(revision)

Step 3: トラフィック分割の設定（パーセンテージベース）

Python 
client.agent_engines.update(
    name="projects/PROJECT_ID/locations/LOCATION/reasoningEngines/RESOURCE_ID",
    config={
        "traffic_config": {
            "trafficSplitManual": {
                "targets": [
                    {
                        "runtimeRevisionName": "...runtimeRevisions/REVISION_ID_1",
                        "percent": 90,
                    },
                    {
                        "runtimeRevisionName": "...runtimeRevisions/REVISION_ID_2",
                        "percent": 10,
                    },
                ]
            }
        }
    },
)

🎯 ユースケース

🐤 ユースケース 1: カナリアデプロイメント

シナリオ: 本番環境のカスタマーサポート AI エージェントの新バージョンをリリースする際、まず10%のトラフィックで動作確認してから全面展開。

効果: 新バージョンに問題があった場合、影響は10%のトラフィックのみ。即座にトラフィックを元のリビジョンに戻してロールバック可能。

🔬 ユースケース 2: A/B テスト

シナリオ: 異なるプロンプト設定や処理ロジックを持つ2つのエージェントバージョンの性能を比較。

効果: 同一条件下でリアルトラフィックを使った比較テストが可能。データに基づいた意思決定ができる。

⏪ ユースケース 3: 安全なロールバック

シナリオ: 新バージョンのエージェントで応答品質の低下が検知されたため、即座に前バージョンに戻したい。

効果: トラフィック設定を変更するだけで、再デプロイを待たずに即座にロールバックが完了。

✅ メリット

💼 ビジネス面

→リスクの最小化: カナリアデプロイメントで全ユーザーへの影響を回避
→ダウンタイムの削減: トラフィック設定変更だけで即座にロールバック
→段階的な展開: ビジネスクリティカルなエージェントを安全に更新

🔧 技術面

→イミュータブル性: 動作の再現性と追跡可能性を保証
→柔軟なトラフィック制御: A/B テストやカナリアリリースに対応
→API 互換性: REST API と SDK の両方から操作可能、CI/CD 統合も容易

⚠️ デメリット・制約事項

制限事項
  • 現時点では v1beta1 API でのみ利用可能（Preview ステータス）
  • トラフィック分割はルート ReasoningEngine リソースへのクエリのみが対象
  • パーセンテージは整数値のみ対応し、合計が100%になる必要がある
  • Pre-GA 機能のため、サポートが限定的である可能性
考慮すべき点
  • 古いリビジョンを放置するとリソースクォータを消費するため、定期的な非推奨化・削除が必要
  • セキュリティ脆弱性を含む古いリビジョンが残存するリスクがあるため、適切なライフサイクル管理が必要
  • 特定リビジョンへのクエリ権限とルートエージェントへのクエリ権限が独立しているため、IAM 設定に注意

🔗 関連サービス
