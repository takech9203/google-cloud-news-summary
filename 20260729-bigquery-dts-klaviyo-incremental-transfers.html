📣 BigQuery Data Transfer Service
Klaviyo 転送での増分データ転送サポート

Klaviyo → BigQuery 転送で「前回転送以降の差分のみ」を取り込めるように
BigQuery Data Transfer Service Klaviyo コネクタ Preview リリース日: 2026-07-29

📌 概要

BigQuery Data Transfer Service (DTS) の Klaviyo コネクタが 増分データ転送 (Incremental transfers) に対応しました (Preview)。 これまで転送実行のたびに Klaviyo のデータセット全体をロードする フル転送 のみでしたが、 転送構成の write preference で Full / Incremental を選択できるようになり、 Incremental では「前回の転送以降に変更されたデータのみ」を転送できます。

増分転送では書き込み方式として Append または Upsert の write mode を指定します。 いずれも ウォーターマーク列 (TIMESTAMP 型・単調増加) の指定が必須で、Upsert ではさらに 主キー が必要です。対象は Klaviyo の E コマース / メールマーケティングデータを BigQuery に集約して分析するデータエンジニア・アナリティクスチームです。

❌ Before (アップデート前)

  • 毎回 Klaviyo の対象オブジェクト全件を転送するフル転送のみ
  • データ量の増加に比例して API 呼び出し量と実行時間が増え続ける
  • Upsert / Append などの書き込みセマンティクスを転送構成側で制御できない
  • 対象期間が広い転送は FAILED_PRECONDITION の失敗要因になり得た

✅ After (アップデート後)

  • write preference で Incremental を選択し差分のみ転送
  • Append (追記) / Upsert (更新または挿入) の 2 モードを選択可能
  • Klaviyo API 呼び出し量と転送実行時間の削減が期待できる
  • Upsert では宛先テーブルが主キーでクラスタ化されクエリ最適化も同時に実現

Klaviyo API から取得したデータが DTS の Klaviyo コネクタを経由して BigQuery に取り込まれるパイプラインです。 write preference が Incremental の場合はウォーターマーク列で差分を判定し、 Append または Upsert のいずれかで宛先テーブルに書き込まれます。

⚙️ 主要機能

1️⃣ フル転送と増分転送の選択 (write preference)

  • 転送構成のセットアップ時に Full または Incremental を選択
  • Full: 転送実行のたびに Klaviyo の全データを転送 (従来の動作)
  • Incremental (Preview): 前回転送以降に変更されたデータのみを転送し、全体ロードを回避
  • 1 つの転送構成でサポートできるのは増分 / フルのいずれか一方のみ

2️⃣ Append write mode (追記モード)

  • 宛先テーブルに新規行を挿入するのみのモード
  • 既存レコードの有無をチェックしないため、データ重複が発生する可能性がある
  • ウォーターマーク列の指定が必須
  • レコード作成時にのみ設定され以後変化しない列 (例: CREATED_AT 相当) が推奨

3️⃣ Upsert write mode (更新または挿入モード)

  • 主キーの存在チェックにより、行の更新か新規挿入かを自動判定
  • ウォーターマーク列と主キーの両方の指定が必須
  • ウォーターマーク列には変更ごとに更新される列 (例: UPDATED_AT / LAST_MODIFIED 相当) が推奨
  • 主キーは 1 列以上・全行で NULL でなく一意な値が必要 (自動採番 ID、不変のシーケンス ID など)
  • 一意性に不安がある場合は、データ損失・破損を避けるため Append モードが推奨

4️⃣ 初回転送時のフルロード動作

  • 既存の転送構成を初めて増分モードに更新した場合、最初の 1 回は全データを転送
  • 以降の増分転送では、新規行と更新行のみが転送される

🛠️ 設定方法

✅ 前提条件

  • Klaviyo 側: READ ONLY 以上のアクセスレベルを持つ read-only の private API キーを用意
  • BigQuery 側: DTS の有効化に必要な作業を完了し、転送先データセットを作成しておく
  • IAM: BigQuery Admin (roles/bigquery.admin) ロールの付与を管理者に依頼 (必要な権限: bigquery.transfers.update, bigquery.transfers.get, bigquery.datasets.get, bigquery.datasets.getIamPolicy, bigquery.datasets.update, bigquery.datasets.setIamPolicy, bigquery.jobs.create)
  • Pub/Sub による転送実行通知を設定する場合は pubsub.topics.setIamPolicy も必要 (メール通知のみなら不要)

1️⃣ Google Cloud コンソールで転送構成を作成する

  1. Data transfers ページに移動し、Create transfer をクリック
  2. Source で Klaviyo - Preview を選択
  3. Data source details で Private API Key、Start Date (任意、デフォルトは実行日の 3 か月前)、Klaviyo objects to transfer を設定
  4. Destination settings の Dataset で作成済みデータセットを選択し、Display name を入力
  5. Schedule options で Repeat frequency (Custom / On-demand も選択可) と開始時刻を設定
  6. write preference で Full または Incremental を選択。Incremental の場合は Append / Upsert の write mode と、ウォーターマーク列 (Upsert では加えて主キー) を指定
  7. 任意で Notification options のメール / Pub/Sub 通知を有効化し、Save をクリック

2️⃣ bq コマンドラインツールで転送構成を作成する

Bash Klaviyo 転送構成の作成 (構文) 
bq mk --transfer_config \
  --project_id=PROJECT_ID \
  --data_source=klaviyo \
  --display_name=NAME \
  --target_dataset=DATASET \
  --params='PARAMETERS'
パラメータ説明
assetsBigQuery に転送する Klaviyo オブジェクトのパス
connector.authentication.privateApiKeyKlaviyo アカウントの private API キー
connector.startDate (任意)転送に含める新規レコードの開始日 (YYYY-MM-DD 形式)。デフォルトは転送実行日の 3 か月前
Bash 実行例 
bq mk --transfer_config \
  --target_dataset=mydataset \
  --data_source=klaviyo \
  --display_name='My Transfer' \
  --params='{
    "assets": ["Events", "Flows"],
    "connector.authentication.privateApiKey": "pk_123456789123",
    "connector.startDate": "2025-10-20"
  }'

転送構成を保存すると、Klaviyo コネクタはスケジュール設定に従って転送実行を自動的にトリガーします。 スケジュール外で手動実行したい場合はバックフィル実行を開始します。

3️⃣ 増分転送の初回実行を確認する

💡 ポイント: 既存の転送構成を初めて増分取り込みモードに変更した場合、直後の 1 回目は全データが転送されます。 2 回目以降の実行で新規行・更新行のみが転送されることを、転送実行履歴と宛先テーブルの行数で確認してください。

💪 メリット

💼 ビジネス面

✓運用コストの低減: 全件ロードを差分のみに絞ることで、BigQuery のロード処理量と Klaviyo API 側の消費リソースを削減。取り込み後のストレージ・クエリ料金にも波及
✓データ鮮度の向上余地: 1 回の転送量が小さくなり、より高い頻度のスケジュールを現実的に運用しやすい
✓コード不要の実装: DTS がマネージドでスケジュール実行するため、増分同期ロジックの自前実装・保守が不要

🔧 技術面

✓実行時間の短縮: 変更分のみの転送で実行時間を短縮。対象期間が広い場合の FAILED_PRECONDITION リスク低減にも寄与
✓書き込みセマンティクスの選択: イベント系データは Append、最新状態を保持したい Profiles などは Upsert という使い分けが可能
✓クエリ性能の副次的改善: Upsert では宛先テーブルが主キーでクラスタ化され、主キーフィルタのクエリのスキャン量削減が期待できる

⚠️ デメリット・制約事項

🚫 制限事項

✗ウォーターマーク列に選択できるのは TIMESTAMP 型の列のみ
✗増分取り込みは、有効なウォーターマーク列を持つアセットのみサポート
✗ウォーターマーク列の値は単調増加である必要がある
✗増分転送はソーステーブルの削除操作を同期できない
✗1 つの転送構成でサポートできるのは増分またはフルのいずれか一方のみ
✗最初の増分取り込み実行後は、アセットリスト内のオブジェクトを更新できない
✗最初の増分取り込み実行後は、write mode を変更できない
✗最初の増分取り込み実行後は、ウォーターマーク列または主キーを変更できない
✗宛先テーブルは主キーでクラスタ化され、クラスタ化テーブルの制限が適用される
✗増分モードへの更新直後の最初の転送では全データが転送される
✗Append モードは既存レコードをチェックしないため、データ重複が発生する可能性がある

🤔 考慮すべき点

⚠️ Preview 段階である: 本機能および Klaviyo コネクタは Preview で、「Pre-GA Offerings Terms」が適用されます。 Pre-GA 機能は "as is" で提供され、サポートが限定される場合があります。サポート / フィードバックは dts-preview-support@google.com へ。
⚠️ 設計変更が後戻りできない: アセットリスト、write mode、ウォーターマーク列、主キーは初回の増分実行後に変更不可。 対象オブジェクトとキー設計を事前に確定させる必要があります。
⚠️ 削除が反映されない: Klaviyo 側で削除されたレコードは宛先テーブルに残り続けるため、 論理削除の扱いや定期的なフル再取り込みなど、運用設計での補完が必要です。
⚠️ 主キーの一意性: 主キー列の値が一意でない場合、データ損失・破損の恐れがあります。 一意性に確信が持てない場合は Append モードの選択が推奨されます。
💡 SLO の適用範囲: Data Delivery SLO は Google Cloud 内ソースからの自動スケジュール転送に適用され、 Klaviyo のようなサードパーティ / 非 Google Cloud ソースからの転送には適用されません。
🔑 API キーのアクセスレベル: private API キーが READ ONLY 未満の場合、 PERMISSION_DENIED: Permission denied. Your API key may lack required access scopes が発生します。

🎯 ユースケース

📈 ユースケース 1: Events テーブルの追記型インクリメンタル取り込み

シナリオ: E コマース事業者が Klaviyo の Events (Placed Order、Viewed Product など) を日次で取り込み。 イベントは一度記録されたら更新されない追記型データだが、これまで毎回全件転送で蓄積量の増加に伴い転送時間が伸びていた。

Plaintext 転送構成例 
Source           : Klaviyo - Preview
Assets           : Events
write preference : Incremental
write mode       : Append
watermark column : datetime (TIMESTAMP)

効果: 前回転送以降に発生したイベントのみが転送され、実行時間と API 呼び出し量を削減。 イベントは更新されないため Append モードでも重複が発生しにくい。

👤 ユースケース 2: Profiles テーブルの最新状態同期 (Upsert)

シナリオ: 顧客プロファイル (Profiles) の最新のマーケティング同意状況やセグメント属性を BigQuery 側で常に最新に保ちたい。 プロファイルは既存行の更新も頻繁に発生するため、追記のみでは最新状態を表現できない。

Plaintext 転送構成例 
Source           : Klaviyo - Preview
Assets           : Profiles
write preference : Incremental
write mode       : Upsert
watermark column : updated (TIMESTAMP)
primary key      : id

効果: updated 列で変更行を検出し、id を主キーとして更新 / 挿入するため、宛先テーブルが常にソースの最新状態を反映。 加えて id でクラスタ化され、特定プロファイルを絞り込むクエリのスキャン量が抑えられる。

🗂️ ユースケース 3: マスタ系はフル転送、トランザクション系は増分転送に分離

シナリオ: Accounts や Tags のようにウォーターマーク列を持たない小規模なマスタ系オブジェクトと、 Events / Profiles のように大量に増減するオブジェクトを同じパイプラインで扱っている。

効果: 「1 つの転送構成では増分 / フルの一方のみ」の制約に対応するため、転送構成を 「マスタ系 = Full」「トランザクション系 = Incremental」の 2 つ以上に分割。 オブジェクトの特性ごとに最適な取り込み方式とスケジュールを設定できる。

🌍 利用可能リージョン

BigQuery Data Transfer Service は BigQuery と同様にマルチリージョンリソースであり、加えて多数の単一リージョンが利用可能です。

  • 転送先データセットの作成時にロケーションを指定し、転送構成自体は転送先データセットと同じロケーションに設定される
  • DTS はデータの処理とステージングを転送先データセットと同じロケーションで実行する
  • DTS は、データが保存されている任意のリージョンから、転送先データセットが存在する任意のロケーションへの転送をサポートする

詳細は Dataset locations and transfers および Dataset locations を参照してください。

📝 まとめ

Klaviyo → BigQuery 転送に増分データ転送 (Preview) が追加され、従来のフル転送のみという制約が解消されました。 Events のような追記型データは Append、Profiles のような更新を伴うデータは Upsert という使い分けにより、 転送量・実行時間の削減と最新状態の維持を同時に実現できます。

ただしアセットリスト・write mode・ウォーターマーク列・主キーは初回の増分実行後に変更できず、削除操作も同期されないため、 既存の Klaviyo 転送を移行する前に対象オブジェクトとキー設計を確定させ、Preview の利用条件 (Pre-GA Offerings Terms) を確認した上で 検証環境から適用することを推奨します。
