Confidential Compute GPU & Runtime 3.0

Managed Service for Apache Spark Feature Change Preview (GPU)
📅 2026-07-13

📋 概要

Managed Service for Apache Spark のクラスタイメージバージョン 2.1/2.2/2.3 で、g4-standard-48 GPU マシンタイプでの Confidential Compute がサポートされました。GPU ワークロードでもインラインメモリ暗号化による機密データ保護が可能になります。

同時に、サーバーレス ランタイム 3.0 の Executor デフォルト設定が変更され、スケールトゥゼロによるコスト最適化が実現しました。さらに全ランタイムで spark.scheduler.listenerbus.exitTimeout が 30 秒に標準化されています。

🔄 Before / After

❌ Before

  • g4-standard-48 で Confidential Compute 利用不可
  • 初期 Executor 数 = 2 (小規模ジョブでも余剰リソース)
  • minExecutors = 2 (アイドル時もリソース保持)
  • listenerbus タイムアウト未設定 (終了処理が長時間化)

✅ After

  • g4-standard-48 で AMD SEV ベースの Confidential Compute 利用可能
  • initialExecutors = 1 (高速スタートアップ)
  • minExecutors = 0 (完全スケールトゥゼロ)
  • exitTimeout = 30s (安定したジョブ終了処理)

クラスタデプロイメントでは Confidential Compute により GPU メモリを含むメモリ全体が暗号化される。サーバーレスデプロイメントではランタイム 3.0 の新デフォルトにより、真に必要なリソースのみが割り当てられる。

🔷 主要機能

🔒 Confidential Compute for g4-standard-48 GPU

→クラスタイメージバージョン 2.1, 2.2, 2.3 で利用可能
→AMD SEV (Secure Encrypted Virtualization) テクノロジー使用
→AMD EPYC Turin プロセッサ搭載
→Master / Worker 両方に g4-standard-48 を指定
→Ubuntu イメージの使用が必須

⚡ ランタイム 3.0 Executor デフォルト変更

→spark.dynamicAllocation.minExecutors: 2 → 0
→spark.executor.instances: 2 → 1
→spark.dynamicAllocation.initialExecutors: 2 → 1
→Dynamic Allocation による完全スケールトゥゼロが可能に

⏰ listenerbus exitTimeout の標準化

→全ランタイムで spark.scheduler.listenerbus.exitTimeout を 30 秒に設定
→ジョブ終了時のイベントバス処理タイムアウトが明確化
→異常なジョブ終了時のリソース解放が改善

📝 設定方法

💡 前提条件:
  • Confidential Compute 対応ゾーンで AMD EPYC Turin をサポートしていること
  • クラスタイメージバージョン 2.1, 2.2, または 2.3 を使用すること
  • サポートされる Ubuntu イメージを使用すること

Step 1: Confidential Compute 有効なクラスタの作成

Bash 
gcloud dataproc clusters create CLUSTER_NAME \
    --confidential-compute-type=SEV \
    --image-version=2.3-ubuntu22 \
    --zone=ZONE \
    --master-machine-type=g4-standard-48 \
    --worker-machine-type=g4-standard-48 \
    --num-workers=2

Master と Worker の両方で g4-standard-48 を指定する。

Step 2: ランタイム 3.0 の Executor 設定カスタマイズ (必要な場合)

Bash 
gcloud dataproc batches submit spark \
    --runtime-version=3.0 \
    --properties="spark.dynamicAllocation.minExecutors=2,spark.dynamicAllocation.initialExecutors=4" \
    --class=com.example.MySparkJob \
    --jars=gs://my-bucket/my-job.jar

新デフォルトが不十分な場合、明示的にプロパティを上書きできる。

✅ メリット

🏢 ビジネス面

💰規制対応の強化: 金融、医療、政府機関などで GPU ベースの AI/ML ワークロードのデータ保護要件を満たせる
💲コスト削減: 小規模ジョブや間欠的ワークロードで不要なリソース消費が削減される
🛡運用リスク軽減: listenerbus タイムアウト明示化でジョブ終了処理の予測可能性が向上

💻 技術面

🔒インラインメモリ暗号化: AMD SEV によりハイパーバイザからもデータを保護
📈スケールトゥゼロ: minExecutors=0 でアイドル時はリソース完全解放
⚡高速スタートアップ: initialExecutors=1 でリソース取得が高速化

⚠️ デメリット・制約事項

🚧 制限事項
  • Confidential Compute はライブマイグレーション非対応 (ホストメンテナンス時にインスタンス終了)
  • g4-standard-48 の Confidential Compute は現在 Preview ステージ
  • Confidential Compute 対応ゾーンが限定的 (全リージョンで利用可能ではない)
  • GPU ファームウェアのフラッシュは禁止 (システム不安定化のリスク)
💡 考慮すべき点
  • 既存ワークロードへの影響: initialExecutors=2 を前提としていた場合、スタートアップ並列度が低下する可能性
  • パフォーマンスプロファイル: spark.dynamicAllocation.profile=performance 設定時は initialExecutors=10 が優先
  • コスト vs レイテンシ: Executor 数削減はコスト減だが、スケールアップ速度に依存しレイテンシに影響する可能性
  • listenerbus タイムアウト: 30 秒は大量イベント生成ジョブで不十分な場合あり

🎯 ユースケース

🏥 ユースケース 1: 医療画像の機密 AI 推論

シナリオ: 医療機関が患者の画像データを GPU で AI 推論する際、データプライバシー保護が法規制で求められる。

Bash 
gcloud dataproc clusters create medical-ai-cluster \
    --confidential-compute-type=SEV \
    --image-version=2.3-ubuntu22 \
    --zone=us-central1-a \
    --master-machine-type=g4-standard-48 \
    --worker-machine-type=g4-standard-48 \
    --num-workers=4 \
    --properties="spark.executor.resource.gpu.amount=1"

効果: GPU メモリを含む全メモリがハードウェアレベルで暗号化され、HIPAA 準拠のデータ処理を実現。

📊 ユースケース 2: コスト最適化されたバッチ ETL パイプライン

シナリオ: 日次 ETL パイプラインで、データ量に応じてリソース使用量が大きく変動する場合。

Bash 
gcloud dataproc batches submit spark \
    --runtime-version=3.0 \
    --properties="spark.dynamicAllocation.maxExecutors=100" \
    --class=com.example.DailyETL \
    --jars=gs://my-bucket/etl.jar

効果: 最小 0 Executor から開始し、実際のデータ量に応じて自動スケール。小データの日は最小コスト、大データの日は最大 100 Executor まで自動スケールアウト。

🌎 利用可能リージョン

Confidential Compute (g4-standard-48, AMD SEV) は AMD EPYC Turin をサポートするゾーンで利用可能。以下のコマンドで対応ゾーンを確認できます:

Bash 
gcloud compute zones describe ZONE --format="value(availableCpuPlatforms)"
💡 サーバーレスランタイム 3.0 は全ての Managed Service for Apache Spark 対応リージョンで利用可能。ランタイム 3.0 ではリージョン内のマルチゾーンへのノード配置がデフォルトで有効になり、リソースの obtainability が向上しています。
