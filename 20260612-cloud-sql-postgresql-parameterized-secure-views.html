🔒 Cloud SQL for PostgreSQL:
Parameterized Secure Views

Cloud SQL for PostgreSQL Preview
2026-06-12

📋 概要

Cloud SQL for PostgreSQL に Parameterized Secure Views（パラメータ化セキュアビュー）機能が Preview として追加されました。ビュー定義内に名前付きパラメータ（ユーザー ID やリージョンなど）を使用し、クエリ実行時にアプリケーションがパラメータ値を提供することで、ユーザーごとに異なるデータセットを返すきめ細かなアクセス制御を実現します。

💡 主なユースケース: Natural Language to SQL（NL2SQL）アプリケーションにおけるセキュリティ強化。プロンプトインジェクション攻撃や意図しないデータアクセスのリスクをデータベースレベルで防御します。

対象ユーザー

→ マルチテナントアプリケーションの開発者
→ AI/ML を活用した自然言語クエリインターフェースを構築するチーム
→ データベースレベルでの最小権限原則を徹底したいセキュリティ担当者

🔄 Before / After 比較

❌ Before（課題）

✗GRANT 文ではビューが返すデータを動的に制限できない
✗NL2SQL アプリで生成 SQL の範囲を制限する仕組みがない
✗RLS は DB ユーザー単位の制御でアプリユーザー単位は困難
✗プロンプトインジェクション攻撃への DB レベル防御が不足

✅ After（改善）

✓$@parameter_name 構文でアプリユーザー単位のアクセス制御
✓security_barrier で悪意ある関数によるデータ漏洩を防止
✓標準インターフェースでパラメータ値を安全に渡せる
✓自動的なクエリ制限（読み取り専用、再帰禁止、EXPLAIN 禁止）

⚡ 主要機能

🏷️ 名前付きビューパラメータ

$@parameter_name 構文で WHERE 句内にパラメータを定義。大文字・小文字を区別し、英字/アンダースコアで始まる名前を使用。

🛡️ Security Barrier

WITH (security_barrier) オプションで、悪意のある関数やオペレータがフィルタリング前の行データにアクセスすることを防止。

🔌 複数のクエリ実行 API

JSON API: ワンショット実行
CURSOR API: 大規模クエリ向けバッチフェッチ
Prepared Statements: 再利用可能なクエリプラン

🚫 クエリ制限の自動適用

読み取り専用（SELECT のみ）/ 再帰呼び出し禁止 / dblink 等のエクステンション制限 / EXPLAIN 文禁止

📐 技術仕様

項目詳細
パラメータ構文$@parameter_name
パラメータ名の制約先頭: 英字 (a-z) またはアンダースコア / 後続: 英字・アンダースコア・数字
大文字小文字区別あり
ビューオプションWITH (security_barrier) 必須
必要なエクステンションparameterized_views
必要なデータベースフラグcloudsql.enable_parameterized_views = on

🔧 設定方法

ステップ 1: データベースフラグの有効化

インスタンスで cloudsql.enable_parameterized_views フラグを有効にします（再起動が必要）。

Bash 
gcloud sql instances patch INSTANCE_NAME \
  --database-flags cloudsql.enable_parameterized_views=on

ステップ 2: エクステンションの作成

SQL 
-- 管理者ユーザーで接続して実行
CREATE EXTENSION parameterized_views;

ステップ 3: パラメータ化セキュアビューの作成

SQL 
CREATE VIEW app_schema.user_items_view WITH (security_barrier) AS
SELECT item_id, item_name, description
FROM app_schema.items
WHERE owner_id = $@current_user_id;

ステップ 4: アプリケーション用ロールの作成と権限付与

SQL 
-- アプリケーション用のデータベースロールを作成
CREATE ROLE psv_user WITH LOGIN PASSWORD 'PASSWORD';

-- ビューとスキーマへのアクセス権を付与
GRANT USAGE ON SCHEMA app_schema TO psv_user;
GRANT SELECT ON app_schema.user_items_view TO psv_user;

-- ベーステーブルへの直接アクセスを拒否
REVOKE ALL PRIVILEGES ON app_schema.items FROM psv_user;

ステップ 5: パラメータ化ビューのクエリ実行

SQL 
-- JSON API を使用したクエリ実行
SELECT * FROM parameterized_views.execute_parameterized_query(
    query => 'SELECT * FROM app_schema.user_items_view',
    param_names => ARRAY ['current_user_id'],
    param_values => ARRAY ['123']
);

-- Prepared Statement を使用したクエリ実行
PREPARE get_items (TEXT) AS RESTRICTED
SELECT item_id, item_name FROM app_schema.user_items_view
WHERE item_name LIKE $1;

EXECUTE get_items ('%Laptop%')
WITH VIEW PARAMETERS (current_user_id := '123');

DEALLOCATE get_items;

✅ メリット

💼 ビジネス面

✓コンプライアンス強化: 最小権限原則を DB レベルで実現し、監査要件への対応を簡素化
✓AI アプリの安全な展開: NL2SQL アプリのデータ漏洩リスクを大幅に低減
✓マルチテナント対応の簡素化: ビューレベルでのデータ分離で実装を削減

🔧 技術面

✓プロンプトインジェクション対策: DB レベルのセキュリティ境界
✓PostgreSQL 互換: 標準ビュー構文の拡張で既存知識を活用可能
✓自動的なクエリ制限: 追加のセキュリティ実装が不要
✓複数の API: ユースケースに応じた使い分けが可能

⚠️ デメリット・制約事項

⚠️ Preview ステータス: SLA 対象外であり本番環境での利用は推奨されません（Pre-GA Offerings Terms が適用）。

制限事項

✗フラグ有効化にはデータベースの再起動が必要
✗parameterized_views エクステンションを各 DB に個別にインストールする必要あり
✗ユーザー定義関数内からのパラメータ化ビュー参照はエラー（直接参照のみ対応）
✗dblink や pg_cron などバックグラウンドセッション開始エクステンションは使用不可

考慮すべき点

→ フラグ有効化に伴うダウンタイムの計画が必要
→ 既存アプリコードをパラメータ化クエリインターフェースに対応させる改修が必要
→ JSON API の結果セットサイズ制限があるため、大量データには CURSOR API を検討

🎯 ユースケース

📊 ユースケース 1: NL2SQL アプリケーションのデータセキュリティ

シナリオ: 社内 DB に対して自然言語でクエリを発行するアプリ。エンドユーザーが「自分の注文を表示して」と入力すると、そのユーザーの注文のみが返却される。

SQL 
-- 注文ビューの作成
CREATE VIEW orders_view WITH (security_barrier) AS
SELECT order_id, product_name, quantity, order_date
FROM orders
WHERE customer_id = $@authenticated_user_id;

-- アプリケーションからのクエリ実行
SELECT * FROM parameterized_views.execute_parameterized_query(
    query => 'SELECT * FROM orders_view WHERE order_date > ''2026-01-01''',
    param_names => ARRAY ['authenticated_user_id'],
    param_values => ARRAY ['user_12345']
);
効果: プロンプトインジェクション攻撃が行われても、認証されたユーザーのデータのみが返却され、他のユーザーのデータ露出リスクを排除。

🏢 ユースケース 2: マルチテナント SaaS アプリケーション

シナリオ: 複数企業が共有 DB を使用する SaaS で、各テナントが自社のデータのみにアクセスできるようにする。

SQL 
-- テナント別ビューの作成
CREATE VIEW tenant_data_view WITH (security_barrier) AS
SELECT record_id, data_field, created_at
FROM shared_table
WHERE tenant_id = $@current_tenant_id AND region = $@user_region;
効果: データベースレベルでのテナント分離により、アプリケーションロジックの不具合によるクロステナントデータアクセスを防止。

🔗 関連サービス・機能

Cloud SQL RLS

DB ユーザー単位の行レベルセキュリティ。PSV はアプリユーザー単位で RLS を補完。

カラムレベルセキュリティ

特定カラムへのアクセス制御。PSV と組み合わせて多層的データ保護を実現。

Cloud SQL IAM 認証

インスタンスレベルのアクセス制御。PSV はデータレベルでより細かい制御を追加。

Vertex AI / Gemini

NL2SQL アプリ構築において、PSV がデータセキュリティレイヤーとして機能。

📝 まとめ

Cloud SQL for PostgreSQL の Parameterized Secure Views は、特に AI/NL2SQL アプリケーションにおけるデータセキュリティの課題を解決する重要な機能です。データベースレベルで最小権限原則を実現し、プロンプトインジェクション攻撃への防御を提供します。

推奨: 現在 Preview 段階ですが、マルチテナントアプリケーションや自然言語クエリインターフェースの構築を検討しているチームは、開発・テスト環境での評価を開始することを推奨します。
