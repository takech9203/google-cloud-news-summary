🛡️ Cloud Armor: 事前構成 WAF ルールセット
(CRS 3.3 / 3.0 stable) のセキュリティ修正と機能強化

Google Cloud Armor Security (セキュリティ修正・機能強化) 事前構成 WAF ルール: v33-stable / v3.0 stable

📌 概要

Google Cloud Armor の事前構成 WAF ルール (preconfigured WAF rules) に、セキュリティ修正と機能強化が適用されました。 対象は OWASP ModSecurity Core Rule Set (CRS) 3.3 ベースの v33-stable 系 12 ルールセットと、CRS 3.0 ベースの stable 系 10 ルールセットです。

事前構成 WAF ルールは SQLi / XSS / RCE など OWASP Top 10 に代表される Web 攻撃を検出するシグネチャ群で構成されます。 更新は canary 版で先行リリース後に stable 版へ昇格する運用のため、今回の stable 反映により、これらのルールセットを利用するすべてのセキュリティポリシーに設定変更なしで最新の検出ロジックが適用されます。

❌ Before (アップデート前の課題)

  • 旧バージョンの stable ルールセットには、最新の攻撃手法や回避テクニックに対する検出の抜けや、誤検知 (false positive) につながる既知の問題が残っていた
  • canary 版に先行適用されていた修正が stable 版には未反映で、stable 版のみを利用する環境では最新の検出改善を享受できていなかった

✅ After (アップデート後の改善)

  • CRS 3.3 系 (v33-stable) の 12 ルールセットと CRS 3.0 系 (stable) の 10 ルールセットにセキュリティ修正と機能強化が反映
  • stable を参照するセキュリティポリシーは設定変更なしで自動的に更新後のシグネチャで評価
  • SQLi / XSS / LFI / RFI / RCE / メソッド強制 / スキャナ検出 / プロトコル攻撃 / PHP / セッション固定 (CRS 3.3 では加えて Java / Node.js) で検出品質が向上
💡 ポイント: 追加の設定作業は不要ですが、シグネチャの挙動が変わる可能性があるため、opt-out している署名 ID や感度レベル (sensitivity) のチューニング内容の確認が推奨されます。

🧩 事前構成 WAF ルールの基本仕様

項目詳細
ベースOWASP ModSecurity Core Rule Set (CRS)。最新の脅威への保護には CRS 4.22 (*-v422-stable) の利用が推奨されており、CRS 3.3 / 3.0 もサポート継続中
感度レベル (sensitivity)0〜4。デフォルトは 4 (全シグネチャを評価)。低い感度ほど誤検知の少ない高信頼シグネチャのみを評価
チューニングopt_out_rule_ids で特定シグネチャの除外、opt_in_rule_ids (sensitivity 0 時) で特定シグネチャのみ有効化が可能
シグネチャ ID 形式CRS 3.3: owasp-crs-v030301-id<ルール番号>-<カテゴリ> / CRS 3.0: owasp-crs-v030001-id<ルール番号>-<カテゴリ>
canary / stable更新は canary 版に先行リリース後、stable 版へ昇格。canary をプレビューモードで高優先度に置き、stable を適用モードで運用する構成が推奨

🛠️ 設定方法 (更新影響の確認手順)

今回の更新は stable ルールセットに自動反映されるため、新規の設定作業は不要です。以下は更新内容が自身のトラフィックに与える影響を確認するための手順です。

✅ 前提条件

✓Cloud Armor セキュリティポリシーで *-v33-stable または *-stable (CRS 3.0) の事前構成 WAF ルールを使用していること
✓セキュリティポリシーのログ (Cloud Logging) を確認できる権限があること

ステップ 1: 使用中の事前構成 WAF ルールを確認

Bash セキュリティポリシーのルール式を一覧 
gcloud compute security-policies describe POLICY_NAME \
    --format="value(rules.match.expr.expression)"

セキュリティポリシー内で evaluatePreconfiguredWaf('sqli-v33-stable', ...) のように v33-stable / stable 系ルールセットを参照しているルールを特定します。

ステップ 2: ログで誤検知の有無を確認

Bash Cloud Logging で WAF マッチログを確認 
gcloud logging read \
  'resource.type="http_load_balancer" AND jsonPayload.enforcedSecurityPolicy.name="POLICY_NAME"' \
  --limit 50 --format json

更新後のシグネチャで正当なトラフィックがブロックされていないかを確認します。詳細なマッチ情報が必要な場合は verbose logging の有効化が有用です (本番環境での長期間の有効化は非推奨)。

ステップ 3: 必要に応じてチューニング

Bash 感度調整と特定シグネチャの opt-out 
gcloud compute security-policies rules update PRIORITY \
    --security-policy POLICY_NAME \
    --expression "evaluatePreconfiguredWaf('sqli-v33-stable', {'sensitivity': 1, 'opt_out_rule_ids': ['owasp-crs-v030301-id942350-sqli']})"
⚠️ 注意: 誤検知が確認された場合は、感度レベルの調整や opt_out_rule_ids による特定シグネチャの除外でチューニングします。opt-out するシグネチャ ID はルールセットのバージョン (CRS 3.0 / 3.3) と一致させる必要があります。

⚖️ メリットと制約事項

👍 メリット

ビジネス面

  • 運用負荷ゼロでのセキュリティ向上: stable ルールセット利用環境には更新が自動反映され、パッチ適用作業なしで最新の攻撃検出が有効になる
  • コンプライアンス維持: OWASP Top 10 対策として採用している場合、検出品質の継続的な改善により防御水準を維持できる

技術面

  • 広範な攻撃カテゴリのカバー: SQLi / XSS / LFI / RFI / RCE / プロトコル攻撃など主要カテゴリ全体で修正・強化
  • 旧バージョン利用環境もカバー: 最新の CRS 4.22 だけでなく、CRS 3.3 / 3.0 の stable 系にも修正が提供

⚠️ 制限事項・考慮点

  • 個別シグネチャ単位の変更詳細はリリースノートに記載がなく、挙動の変化はログでの観測により確認する必要がある
  • CRS 3.0 系には Java / Node.js ルールセットが存在しないため、これらの攻撃カテゴリの保護には CRS 3.3 以降への移行が必要
  • シグネチャ更新により、これまで通過していたリクエストが新たにマッチする (またはその逆の) 可能性があり、更新後は誤検知・検知漏れの確認が推奨
  • Google は最新の脅威への保護として CRS 4.22 (*-v422-stable) の利用を推奨。特に CRS 3.0 からの移行検討の好機
  • canary 版をプレビューモード (高優先度) で併用していれば、今後の更新も本番影響前にログで検証できる

🎯 ユースケース

💼 ユースケース 1: stable ルールセット利用環境での更新影響確認

シナリオ: EC サイトの外部アプリケーション ロードバランサに sqli-v33-stable と xss-v33-stable を sensitivity 1 で適用している。今回の更新で正当なトラフィックへの影響がないか確認したい。

Bash canary 版をプレビューモードで高優先度に配置し事前検証 
# canary 版をプレビューモードで stable より高い優先度に配置し、今後の更新を事前検証する
gcloud compute security-policies rules create 900 \
    --security-policy prod-policy \
    --expression "evaluatePreconfiguredWaf('sqli-v33-canary', {'sensitivity': 1})" \
    --action deny-403 \
    --preview
✅ 効果: stable 版への更新が本番トラフィックに与える影響を、canary 版のプレビューログで事前に把握でき、誤検知時のチューニングを先回りで実施できる。

🏗️ ユースケース 2: CRS 3.0 から新バージョンへの移行計画

シナリオ: 長期間 sqli-stable (CRS 3.0) を利用しているレガシーシステムで、今回の更新を機にルールセットのバージョン棚卸しを行う。

✅ 効果: CRS 3.0 も引き続き修正が提供されていることを確認しつつ、Java / Node.js 攻撃カテゴリや最新シグネチャを含む CRS 3.3 / 4.22 への段階的な移行計画を立てられる。移行時はプレビューモードでの検証により安全に切り替えられる。
