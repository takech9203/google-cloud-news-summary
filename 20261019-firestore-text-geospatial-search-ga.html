🔥 Firestore: テキスト検索と地理空間検索が GA に

リリース日: 2026-10-19
Firestore Firestore with MongoDB compatibility GA (一般提供) Enterprise edition

📌 概要

Firestore および Firestore with MongoDB compatibility で、テキスト検索 (Text search) と地理空間検索 (Geospatial search) が一般提供 (GA) になりました。両機能は Firestore Enterprise edition のデータベースで利用でき、ネイティブ (Core / Pipeline) と MongoDB 互換 API の両方のインターフェースから同じデータベースエンジン上で実行できます。

これまで外部検索サービス (Elasticsearch / Algolia など) や Geohash ワークアラウンドが必要だった全文検索・位置情報検索を、データベース内で完結させるアーキテクチャを本番環境で採用できるようになりました。

❌ Before: アップデート前の課題

  • 全文検索には Elasticsearch / Algolia / Typesense などの外部検索サービスへのデータ同期が必要で、追加コスト・運用負荷・データ整合性の管理が発生
  • 位置情報検索は Geohash + GeoFire のワークアラウンドが必要で、複数クエリの発行、クライアントサイドでの偽陽性フィルタリング、高緯度での精度低下という制約
  • GA 前のステータスだったため、本番ワークロードでは SLA や長期サポートの観点で慎重な判断が必要

✅ After: アップデート後の改善

  • テキストインデックスを作成するだけで documentMatches 式 (ネイティブ Pipeline) や $text 演算子 (MongoDB 互換) によるデータベースネイティブな全文検索が GA 品質で利用可能
  • 地理空間インデックス (2dsphere) により geoDistance 式や $near 演算子で距離ベースの近傍検索がサーバーサイドで完結、偽陽性フィルタリングが不要に
  • GA 昇格で本番利用が正式サポートされ、外部検索サービスとの同期パイプラインの構築・運用コストを削減

これまで外部検索サービスや Geohash ワークアラウンドが必要だった全文検索・位置情報検索が、Firestore Enterprise edition のテキストインデックス・地理空間インデックスによりデータベース内で完結します。ネイティブ Pipeline と MongoDB 互換 API のどちらからも利用できます。

⚙️ 主要機能

📝 1. テキスト検索 (Text search)

✓テキストインデックスを作成したフィールドへの全文検索。複数インデックスがある場合は Firestore が自動選択
✓キーワード検索、完全一致フレーズ検索 ("belgian waffles")、スペース区切りの AND 条件、ハイフンによる除外条件 (coffee -waffles) をサポート
✓デフォルトは作成日時 (新しい順) ソート。score() による関連度スコアソートや addFields でのスコア付与も可能
✓インデックス単位のデフォルト言語設定 + MongoDB 互換 API では $language 引数でクエリ単位の言語指定が可能

📍 2. 地理空間検索 (Geospatial search)

✓ネイティブ Pipeline: search() ステージ内の geoDistance 式で指定 GeoPoint からの距離 (メートル単位、<= のみ) によるフィルタリング
✓MongoDB 互換 API: $near + $geometry (GeoJSON) で近い順ソートの結果を取得。$maxDistance / $minDistance で距離範囲を制御
✓対象フィールドは GeoJSON オブジェクトまたは GeoPoint 型

🗂️ 3. パーティション化インデックス

✓テキスト/地理空間インデックスを特定フィールド (文字列型、トップレベル) でパーティション化し、等価フィルタと組み合わせた高速なクエリが可能
✓例: city でパーティション化し、「パリ市内のレストランに限定したテキスト検索」を効率的に実行

🔄 4. 両インターフェースでの GA

✓Firestore (ネイティブ: Core / Pipeline 操作) と Firestore with MongoDB compatibility の両方で同時に GA
✓MongoDB 互換アプリケーションは $text / $near という使い慣れた演算子をそのまま利用可能

🔬 技術仕様: ネイティブ vs MongoDB 互換

項目 Firestore (ネイティブ) Firestore with MongoDB compatibility
テキスト検索の構文 Pipeline の search() ステージ + documentMatches 式 find / aggregate 内の $text: { $search: ... }
地理空間検索の構文 search() ステージ + geoDistance 式 (<= のみ) $near + $geometry ($maxDistance / $minDistance)
必要なインデックス テキストインデックス / 地理空間インデックス テキストインデックス / 2dsphere インデックス
ソート デフォルトは作成日時順。score() でスコア順に変更可 $near は近い順に自動ソート
言語設定 インデックスのデフォルト言語 + 言語オーバーライドパス $language 引数でクエリごとに指定可
対応エディション Firestore Enterprise edition Firestore Enterprise edition

テキスト検索のクエリ構文例 (ネイティブ Pipeline)

JavaScript Node.js / Pipeline search() ステージ 
// キーワード検索
await db.pipeline().collection('restaurants')
  .search({ query: documentMatches('waffles') })
  .execute();

// 完全一致フレーズ + スコア順ソート
await db.pipeline().collection('restaurants')
  .search({
    query: documentMatches('"belgian waffles"'),
    sort: score().descending()
  })
  .execute();

地理空間検索のクエリ例 (MongoDB 互換)

JavaScript $near 演算子による近傍検索 
// 指定地点から 500m 以上 2000m 以内のドキュメントを近い順に取得
db.myCollection.find({
  location: {
    $near: {
      $geometry: { type: 'Point', coordinates: [ -122.084, 37.4221 ] },
      $maxDistance: 2000,
      $minDistance: 500
    }
  }
})

🛠️ 設定方法

前提条件

✓Firestore Enterprise edition のデータベースを使用していること (テキスト検索・地理空間検索は Enterprise edition が必須)
✓検索対象フィールドに対してテキストインデックスまたは地理空間インデックスを作成済みであること
✓地理空間検索の対象フィールドは GeoJSON オブジェクトまたは GeoPoint 型であること

ステップ 1: テキストインデックスの作成

Bash gcloud CLI 
gcloud firestore indexes composite create \
  --database='DATABASE_ID' \
  --collection-group=COLLECTION_GROUP \
  --field-config=field-path=FIELD_NAME,search-config='{"text-spec": {"index-specs": [{"index-type": "tokenized", "match-type": "match-globally"}]}}' \
  --search-index-options=text-language=en \
  --async
💡 ヒント: MongoDB 互換 API 用のインデックスを作成する場合は --api-scope=mongodb-compatible-api を追加します。Google Cloud コンソールの「データベース > インデックス」からも Search Type に「Text」を選択して作成できます。

ステップ 2: 地理空間インデックスの作成

Bash gcloud CLI 
gcloud firestore indexes composite create \
  --database='DATABASE_ID' \
  --collection-group=COLLECTION_GROUP \
  --field-config=field-path=FIELD_NAME,search-config='{"geo-spec": {}}' \
  --async

コンソールでは Search Type に「Geo (2dsphere)」を選択します。インデックス作成完了後 (一覧に緑のチェックマークが表示された後)、検索クエリを実行できます。

ステップ 3: 検索クエリの実行

JavaScript mongosh / MongoDB 互換 API でのテキスト検索 
db.cities.find({ $text: { $search: "french bread" } })

ネイティブの場合は各言語の SDK (Web / iOS / Android / Node.js / Python / Java / Go) から Pipeline の search() ステージを使用します。

💡 メリット

💼 ビジネス面

✓外部検索サービスのコスト削減: Elasticsearch / Algolia などの外部検索基盤とデータ同期パイプラインが不要になり、ライセンス/利用料と運用工数を削減
✓本番採用の正式サポート: GA 昇格により本番ワークロードでの利用が正式にサポートされ、ミッションクリティカルなアプリにも採用しやすい
✓MongoDB からの移行促進: $text / $near という MongoDB 標準演算子がそのまま使え、移行時の検索機能の書き換えが最小限で済む

🔧 技術面

✓アーキテクチャの簡素化: 検索がデータベース内で完結するため、データ同期の遅延や整合性の問題が発生しない
✓Geohash ワークアラウンドからの脱却: 複数クエリ + クライアントサイドの偽陽性フィルタリングが不要になり、読み取りコストとレイテンシを削減
✓柔軟な検索構文: フレーズ検索、除外条件、スコアソート、パーティション絞り込みなど実用的な検索要件に対応

⚠️ デメリット・制約事項

制限事項

✕テキスト検索・地理空間検索は Firestore Enterprise edition 専用。Standard edition のデータベースでは利用不可
✕ネイティブの geoDistance は「以下 (<=)」演算子のみサポート (距離はメートル単位)
✕MongoDB 互換 API では $near と $text を同一クエリで併用不可。$near は集計 (aggregation) クエリ、$not / $nor との併用、複数条件 $or へのネスト (単独の場合を除く) も非サポート
✕パーティションフィールドは文字列型のトップレベルフィールド 1 つのみ。クエリ時は $and (等価フィルタ) での結合が必要
✕ネイティブのテキスト検索は constraints/firestore.managed.disableEnhancedTextSearch 組織ポリシーがデフォルト適用される Assured Workloads の in-use データレジデンシー制御パッケージでは利用不可

考慮すべき点

⚠️Enterprise edition は読み取り/書き込みがドキュメント単位ではなくユニット単位 (読み取り 4 KiB / 書き込み 1 KiB) で課金され、Standard edition とはコストモデルが異なる
⚠️テキスト/地理空間インデックスへの書き込みは書き込みユニットを消費するため、インデックス対象フィールドが多い・大きい場合は書き込みコストが増加
⚠️スコア順ソートはドキュメントごとの正確なスコア計算・比較が必要で、デフォルトの作成日時順ソートより多くの計算を要する

🎯 ユースケース

🛒 ユースケース 1: アプリ内コンテンツ検索 (EC・メディアアプリ)

シナリオ: EC アプリで商品名・説明文に対するキーワード検索を提供したい。これまでは Algolia にデータを同期して検索機能を実現していた。

JavaScript 除外条件つきキーワード検索 + スコア順 
// 商品説明に対するキーワード検索 (除外条件つき) + スコア順
await db.pipeline().collection('products')
  .search({
    query: documentMatches('ワッフル -冷凍'),
    sort: score().descending()
  })
  .execute();

効果: 外部検索サービスとの同期パイプラインが不要になり、データの鮮度と整合性が向上。運用コンポーネントが削減される。

🍽️ ユースケース 2: 近隣店舗検索 (位置情報サービス)

シナリオ: フードデリバリーアプリで、ユーザーの現在地から一定距離内のレストランを近い順に表示したい。

JavaScript MongoDB 互換 API: 現在地から 2km 以内を近い順に取得 
db.restaurants.find({
  location: {
    $near: {
      $geometry: { type: 'Point', coordinates: [ 139.7671, 35.6812 ] },
      $maxDistance: 2000
    }
  }
})

効果: Geohash ベースの複数クエリ + クライアントサイドフィルタリングが不要になり、実装がシンプルになるとともに読み取りコストとレイテンシが削減される。

🔄 ユースケース 3: MongoDB ワークロードの移行

シナリオ: セルフマネージドの MongoDB で $text / $near を使った検索機能を持つアプリケーションを、フルマネージドなデータベースへ移行したい。

効果: 検索クエリの構文をほぼそのまま維持したまま Firestore with MongoDB compatibility へ移行でき、GA 品質のサポートの下で運用負荷を削減できる。

💰 料金

テキスト検索・地理空間検索に固有の追加料金は発表されていませんが、前提となる Firestore Enterprise edition はユニットベースの課金モデルを採用しています (以下は us-central1 の例)。

🌏 利用可能リージョン

Enterprise edition が利用可能なリージョンで使用できます。最新のリージョン情報は公式ドキュメントの Locations ページを参照してください。

💡 補足: ネイティブのテキスト検索は、in-use データレジデンシーを強制する Assured Workloads 制御パッケージではサポートされません。

🔗 関連サービス・機能

🏢 Firestore Enterprise edition

本機能の前提となるエディション。Pipeline 操作と MongoDB 互換操作をサポートし、ユニットベースの課金モデルを採用。

🔎 Firestore Pipeline (search ステージ)

テキスト検索・地理空間検索を実行するネイティブのクエリインターフェース。

🤖 Vertex AI / Firestore ベクトル検索

セマンティック検索が必要な場合の補完的な選択肢。キーワード検索 (テキスト検索) と組み合わせたハイブリッドな検索体験を構築可能。

🔒 Assured Workloads

in-use データレジデンシー制御パッケージ利用時はネイティブのテキスト検索が制限されるため、コンプライアンス要件との整合を確認する必要がある。

📝 まとめ

Firestore と Firestore with MongoDB compatibility のテキスト検索・地理空間検索が GA となり、これまで外部検索サービスや Geohash ワークアラウンドに頼っていた全文検索・位置情報検索をデータベース内で完結できるようになりました。検索機能を含むアプリケーションのアーキテクチャ簡素化や MongoDB からの移行を検討しているチームは、Enterprise edition の課金モデル (ユニット単位、インデックス書き込みコスト) を評価した上で、テキスト/地理空間インデックスの導入を検討することを推奨します。
