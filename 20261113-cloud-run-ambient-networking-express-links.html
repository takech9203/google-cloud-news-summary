🛡️ Ambient Networking と Express Links

フルマネージド Envoy サイドカーで、認証コードもサービスメッシュも不要なサービス間接続へ
📅 リリース日: 2026-11-13

📝 概要

Ambient Networking は、Cloud Run の各コンテナインスタンス内にフルマネージドな Envoy サイドカーを配置し、トラフィック管理・セキュリティ・可観測性を簡素化する基盤機能です。サイドカーはネットワークトラフィックをインターセプトし、Cloud Run が配布するルーティング・セキュリティポリシーを適用します。デプロイ・設定・管理はすべて Google Cloud が行い、サービスメッシュのリソース定義は不要です。

Express Links はその最初の主要機能の 1 つで、同一プロジェクト・同一リージョン内の Cloud Run サービス同士を、認証コードなし・サービスメッシュ構成なしで接続します。ソースアプリが平文 HTTP で送信すると、サイドカーが OIDC ID トークンを自動取得して Authorization ヘッダーに注入し、HTTPS (一方向 TLS) で宛先に転送します。

🎯 対象ユーザー: Cloud Run 上でマイクロサービス間通信を構築する開発者、カスタムプロキシやサービスメッシュの運用負荷を削減したいプラットフォームチーム。Ambient Networking は Agent Gateway on Cloud Run の基盤でもあり、今後の高度なネットワーキング機能の土台となります。

🔄 Before / After

😣 アップデート前の課題

  • IAM 保護されたサービスの呼び出しには、OIDC ID トークンを取得して Authorization: Bearer に付与するコードの実装が必要
  • 認証コードを避けるには Cloud Service Mesh が必要で、VPC・バックエンドサービス・ルーティングルール・Cloud DNS の構成が必須
  • 高度なトラフィック管理にはカスタムプロキシの自前構築・保守、またはメッシュ概念の学習が必要
  • 宛先 URL のハードコードにより、宛先変更時にソースアプリの修正・再デプロイが必要

😊 アップデート後の改善

  • フルマネージド Envoy サイドカーが自動で動作し、プロキシの構築・保守が不要に
  • Express Link を作成するだけで平文 HTTP で呼び出し可能。トークン取得・注入と HTTPS 暗号化はサイドカーが自動実施し、認証コードを排除
  • --matches-hostname でカスタムホスト名 (例: http://my-backend) を構成。宛先変更は Express Link の再作成のみで、アプリの修正・再デプロイ不要
  • VPC・NEG・バックエンドサービスのプロビジョニングなしでポイントツーポイント接続を実現

🚀 主要機能

1️⃣ Ambient Networking (フルマネージド Envoy サイドカー)

  • 各コンテナインスタンス内で、アプリコンテナと並行してフルマネージド Envoy サイドカーが動作
  • ネットワークトラフィックをインターセプトし、Cloud Run が配布するルーティング・セキュリティポリシーを適用
  • 有効化しただけではトラフィックは変更されずそのまま通過 — 既存の HTTP / TCP トラフィックはそのまま動作するオプトイン型の基盤機能
  • サイドカーのデプロイ・設定・アクセスは Google Cloud が管理。サービスメッシュリソースの定義は不要

2️⃣ Ambient Networking のスコープ (global / regional)

  • Regional (デフォルト): ポリシーをサービスと同一リージョン内に限定。データレジデンシー (DRZ) 要件 (保存時・使用時・転送時) をサポート
  • Global: 任意のリージョンの宛先へのルーティングを許可
  • Agent Gateway on Cloud Run は regional、Express Links は global スコープが必要

3️⃣ Express Links (認証コード不要のサービス間接続)

  • 同一プロジェクト・同一リージョン内のソース/宛先 Cloud Run サービスを接続するルーティングリソース (gcloud beta network-services express-links で管理)
  • 宛先の決定論的 URL 宛ての平文 HTTP リクエストをインターセプトし、ソースのサービスアカウントの OIDC ID トークンを注入して HTTPS で転送
  • --matches-hostname でカスタムホスト名を構成し、宛先 URL をアプリから抽象化
  • 宛先側では通常どおり IAM (Cloud Run Invoker ロール) で呼び出し元を検証

4️⃣ ネットワーク接続性との関係

  • Express Link はリクエストのインターセプトと認証情報注入を構成するもので、基盤ネットワーク経路を置き換えるものではない
  • 宛先の Ingress が「すべて」の場合は VPC や Egress 設定は不要
  • Ingress が「内部」または「内部と Cloud Load Balancing」の場合は、Direct VPC Egress または (Private Google Access を有効にした) サーバーレス VPC アクセスコネクタ経由のルーティングが必要

🆚 Express Links を使わない場合との比較

ステップExpress Link なしExpress Link あり
1. 宛先サービスのデプロイIAM 認証必須 (--no-allow-unauthenticated) でデプロイ同じ
2. Invoker 権限の付与ソースのサービスアカウントに roles/run.invoker を付与同じ
3. アウトバウンドリクエストの構成OIDC ID トークンを取得し Authorization: Bearer ヘッダーに付与するコードを実装認証コードなしで平文 http:// リクエストを送信

🔑 必要な API とロール

項目詳細
必要な APICloud Run API、Network Services API、Traffic Director API
構成に必要なロールCloud Run Developer (roles/run.developer)、Service Account User (roles/iam.serviceAccountUser)
Express Link リソース管理Network Services Admin (roles/networkservices.admin)
サービス ID に必要なロールTraffic Director Client (roles/trafficdirector.client)、Cloud Trace Agent (roles/cloudtrace.agent)
リソース要件CPU 制限を +1 vCPU、メモリ制限を +1 GiB 引き上げ (サイドカーがインスタンスの CPU / メモリを共有)
💡 補足: サービス ID に必要なロールが不足していても Cloud Run リソースのデプロイ自体は成功しますが、Ambient Networking に依存する機能は動作しません (必要なロールがないとデプロイ自体が失敗する Cloud Service Mesh とは挙動が異なります)。

📄 YAML での設定 (アノテーション)

YAML Ambient Networking のアノテーション 
spec:
  template:
    metadata:
      annotations:
        run.googleapis.com/ambient-networking: 'true'
        run.googleapis.com/ambient-scope: global  # または regional

🔧 設定方法

✅ 前提条件

✓Cloud Run、Network Services、Traffic Director の各 API を有効化する
✓ソースサービスの CPU 制限を 1 vCPU、メモリ制限を 1 GiB 引き上げる
✓サービス ID に roles/trafficdirector.client と roles/cloudtrace.agent を付与する
✓(Express Links の場合) ソース/宛先の Cloud Run サービスが同一プロジェクト・同一リージョンに存在すること
1
Ambient Networking を有効化する
Bash gcloud beta run deploy / update 
# 新規サービスの場合
gcloud beta run deploy SERVICE \
  --image=IMAGE_URL \
  --ambient-networking \
  --ambient-scope=global \
  --region=REGION

# 既存サービスの場合
gcloud beta run services update SERVICE \
  --ambient-networking \
  --ambient-scope=global \
  --region=REGION

Express Links を使う場合、ソースサービスには global スコープが必要です。無効化するには --no-ambient-networking フラグを使用します。

2
Express Link を作成する
Bash gcloud beta network-services express-links create 
gcloud beta network-services express-links create EXPRESS_LINK_NAME \
  --location=global \
  --source-services=//run.googleapis.com/projects/PROJECT_ID/locations/REGION/services/SOURCE_SERVICE \
  --destination-services=//run.googleapis.com/projects/PROJECT_ID/locations/REGION/services/DESTINATION_SERVICE

コマンド完了後、ルーティング設定が実行中のソースサービスインスタンスに伝播するまで最大 2 分かかります。カスタムホスト名を使う場合は --matches-hostname="HOSTNAME" を指定します (指定すると決定論的 URL の代わりにそのホスト名のみがインターセプト対象になります)。

3
宛先サービスに Invoker 権限を付与する
Bash roles/run.invoker の付与 (データプレーン認証に必須) 
gcloud run services add-iam-policy-binding DESTINATION_SERVICE \
  --member="serviceAccount:SOURCE_SA@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/run.invoker" \
  --region=REGION
4
動作確認
Bash Express Link のステータス確認 
# Express Link の基本設定を確認
gcloud beta network-services express-links describe EXPRESS_LINK_NAME \
  --location=global

# フルステータス (connectionStatus、cloudRunSourceInfo) を確認
gcloud beta network-services express-links describe 'EXPRESS_LINK_NAME?view=EXPRESS_LINK_VIEW_FULL#' \
  --location=global

💼 ビジネス面

🚀 開発速度の向上

認証処理のボイラープレートコードが不要になり、開発者はビジネスロジックに集中できる

🧰 運用負荷の削減

カスタムプロキシやサービスメッシュの構築・保守が不要になり、プラットフォーム運用コストを削減できる

📦 アプリケーションのポータビリティ

認証・ルーティングをインフラ側にオフロードすることで、アプリコードが Google Cloud 固有の実装に依存しなくなる

🔬 技術面

🛡️ フルマネージドなデータプレーン

Envoy サイドカーのデプロイ・パッチ・運用はすべて Google Cloud が管理

🔒 自動的なセキュリティ

OIDC ID トークンの取得・注入と HTTPS (一方向 TLS) 暗号化を自動実施。IAM による呼び出し元検証と組み合わせ可能

🏷️ 宛先 URL の抽象化

カスタムホスト名により論理アドレスで呼び出し可能。宛先変更は Express Link の再作成のみで完了

🪶 既存トラフィックへの非侵襲性

Ambient Networking を有効化しただけではトラフィックは変更されず、機能ごとにオプトインできる

⚠️ デメリット・制約事項

🚧 制限事項 (Ambient Networking)

✗UDP トラフィックは非サポート (HTTP と TCP のみ)
✗インバウンドリクエストはエンドツーエンドの HTTP/2 に非対応
✗第 1 世代実行環境は非サポート (未指定の場合は第 2 世代が使用される)
✗コンテナインスタンスの起動に時間がかかるようになる
✗Regional スコープは *.googleapis.com を Private Google Access の IP に解決する VPC ネットワークに非対応
✗サイドカーがインスタンスの CPU / メモリを共有するため、リソース制限の引き上げ (CPU +1 vCPU、メモリ +1 GiB) が必要

🚧 制限事項 (Express Links)

✗ソース/宛先は Cloud Run サービスのみ (ジョブ、ワーカープール、インスタンスは非サポート)
✗クロスプロジェクト・クロスリージョン構成は非サポート
✗ソースサービスには global スコープの Ambient Networking が必須 (regional スコープでは Express Link の作成は成功するがトラフィックはルーティングされない)
✗既存の Express Link のソース/宛先/カスタムホスト名はインプレース更新不可 (削除して再作成が必要。update コマンドで更新できるのは説明のみ)
✗宛先サービスはデフォルトの run.app URL が有効である必要がある
✗非決定論的 URL 宛てのリクエストはインターセプトされず 403 Forbidden になる
✗リクエストに既に Authorization ヘッダーが含まれる場合はトークンを注入せずそのまま転送。X-Serverless-Authorization ヘッダーへの自動注入は非サポート
✗Identity-Aware Proxy (IAP) で保護された宛先サービスへの転送は不可
✗Agent Identity + mTLS バウンドトークン構成のソースサービス、および Agent Gateway + Secure Web Proxy 経由のアウトバウンド構成は非サポート (Agent Gateway は regional スコープを要求するため Express Links と併用不可)
✗1 つの Express Link につき宛先は 1 サービス、プロジェクトあたり最大 5,000 個まで

🤔 考慮すべき点

⚠️ Preview 機能: Pre-GA Offerings Terms が適用され、サポートが限定される可能性があります。本番環境への適用は慎重に判断してください。
⚠️ 宛先削除時の挙動: 宛先サービスを削除しても Express Link は古い構成を保持し続けるため、宛先変更時は Express Link の削除・再作成を忘れないようにしてください。
⚠️ 内部 Ingress の場合: 宛先の Ingress が「内部」の場合は、従来どおり Direct VPC Egress またはサーバーレス VPC アクセスコネクタによる経路の確保が別途必要です。

🎯 ユースケース

1️⃣ マイクロサービス間認証のオフロード

シナリオ: Cloud Run 上のフロントエンド API サービスから、IAM で保護されたバックエンドサービスを呼び出す。従来はアプリ内で ID トークンの取得・付与コードを言語ごとに実装していた。

Bash 実装例 
# ソースサービスで Ambient Networking (global) を有効化
gcloud beta run services update frontend --ambient-networking --ambient-scope=global --region=us-central1

# Express Link を作成
gcloud beta network-services express-links create frontend-to-backend \
  --location=global \
  --source-services=//run.googleapis.com/projects/my-project/locations/us-central1/services/frontend \
  --destination-services=//run.googleapis.com/projects/my-project/locations/us-central1/services/backend

# アプリケーションからは平文 HTTP で呼び出すだけ
# http://backend-<project-number>.us-central1.run.app

✨ 効果: 認証コードをアプリケーションから排除し、言語ごとの認証ライブラリ実装・トークンキャッシュ管理が不要になる。

2️⃣ カスタムホスト名による宛先の抽象化

シナリオ: ソースアプリケーションが http://my-backend という論理アドレスで宛先を呼び出し、宛先サービスの実体を環境ごと・移行時に切り替えたい。

✨ 効果: --matches-hostname="my-backend" を指定した Express Link の削除・再作成だけで宛先を変更でき、ソースアプリの修正や再デプロイが不要になる。

3️⃣ サービスメッシュなしのポイントツーポイント接続

シナリオ: 少数の Cloud Run サービス間の認証付き通信のために Cloud Service Mesh を導入すると、VPC ネットワーク、NEG、バックエンドサービス、Cloud DNS レコードの構成が過剰になる。

✨ 効果: メッシュ関連リソースのプロビジョニングなしで、自動的な認証情報注入付きのサービス間接続を実現できる。

💰 料金

🎁 Preview 期間中は Ambient 機能に対する課金は適用されません (Billing for ambient features isn't enforced during Preview)。Ambient Networking のサイドカー使用には Cloud Run の料金が適用されます。
⚠️ リソース料金への影響: サイドカーはコンテナインスタンスの CPU / メモリを共有するため、有効化の前提として CPU 制限 +1 vCPU、メモリ制限 +1 GiB の引き上げが必要であり、その分のリソース料金には影響する点に留意してください。詳細は Cloud Run 料金ページ を参照してください。

🧩 関連サービス・機能

🤖 Agent Gateway on Cloud Run

Ambient Networking (regional スコープ) を基盤に、エージェントのトラフィックを組織が一元管理するアクセス・セキュリティポリシーで統制する機能

🕸️ Cloud Service Mesh

従来のサービスメッシュによるサービス間接続の選択肢。Express Links は VPC・バックエンドサービス等の構成なしでこれを代替するシンプルな手段を提供

🚦 Traffic Director

Ambient Networking の利用に API の有効化とサービス ID への roles/trafficdirector.client 付与が必要

🔍 Cloud Trace

サービス ID に roles/cloudtrace.agent が必要で、リクエストのトレースと連携

🔐 IAM (Cloud Run Invoker)

Express Links 利用時も宛先サービスでの呼び出し元検証は従来どおり roles/run.invoker で行う

🌐 Direct VPC Egress / サーバーレス VPC アクセス

宛先の Ingress が「内部」の場合に必要となるネットワーク経路

📌 まとめ

Ambient Networking は Cloud Run にフルマネージドな Envoy サイドカーによるデータプレーンをもたらし、Express Links はその最初の実用機能として、認証コードもサービスメッシュも不要な Cloud Run サービス間接続を実現します。Cloud Run でマイクロサービス構成を運用しているチームは、Preview 段階の制約 (同一プロジェクト・同一リージョン、リソース制限の引き上げなど) を確認したうえで、開発環境での検証を始めることをおすすめします。
