🛡️ Google SecOps: Response Health Hub

レスポンスとプレイブックの健全性を一元モニタリングするキュレート済みダッシュボード
リリース日: 2026-10-12
☁️ Google SecOps 📊 Response Health Hub リリース済み (Spotlight Feature)

📋 概要

Google SecOps に、SOAR の プレイブックとインテグレーションの健全性を一元監視 するキュレート済みダッシュボード 「Response Health Hub」が追加されました。複数の環境 (Environment) にまたがる 実行量・レイテンシ・自動化の有効性・インテグレーション健全性 を監視する中央ロケーションです。

→実行量・キュー滞留・完了成功率、アタッチ率と再実行 (rerun) 率を可視化
→エンドツーエンドのプレイブック実行レイテンシとアクション単位のレイテンシを計測
→失敗したプレイブックのサマリーやアクションの失敗理由を表示
→自動クローズと手動クローズの MTTR (平均解決時間) を比較し、自動化効果を定量評価
🎯 対象ユーザー: プレイブックとインテグレーションの健全性・パフォーマンス・自動化効率を監視したい セキュリティエンジニア、SOAR エンジニア、SOC マネージャー。問題の特定・診断・修復ワークフローがダッシュボードとしてパッケージ化されています。

😣 Before (アップデート前の課題)

  • 失敗やレイテンシの調査は、個々のケースのプレイブック モニタリングを個別に開く必要があり、環境横断の一元ビューがなかった
  • 実行量・キュー滞留・再実行率・インテグレーション障害などの運用メトリクスの俯瞰には、カスタム ダッシュボードの自作が必要だった
  • 自動化の効果 (自動クローズと手動クローズの MTTR 比較など) を定量測定する標準的な手段がなかった

😊 After (アップデート後の改善)

  • 1 つのキュレート済みダッシュボードで、実行量・成功率・キュー滞留・レイテンシ・失敗傾向・インテグレーション健全性を環境横断で一元監視
  • 最も遅い実行 Top 30 や失敗率の高いプレイブック Top 30 など、ドリルダウン可能なウィジェットで根本原因の特定が容易に
  • 自動 vs 手動クローズの MTTR 比較や利用ランキングで、自動化の有効性 (ROI) を定量評価可能に

複数環境のプレイブック・インテグレーション・ケースから収集された実行メトリクスが Response Health Hub に集約され、 SOC チームは 実行量 / レイテンシ / 健全性 / 自動化効果の 4 つの観点 から対応ワークフローを一元監視できます。

⚙️ 主要機能: 5 つのセクション構成

📦 1. Volume & Adoption (実行量と採用状況の追跡)

  • プレイブック総実行数、実行回数 Top 30 のプレイブック、日次実行トレンド (折れ線グラフ)
  • PENDING_IN_QUEUE ステータスで実行待ちのプレイブック数 (キュー滞留) を表示
  • 完了済みプレイブックの実行成功率 (COMPLETED と FAILED の内訳) を円グラフで表示

📎 2. Playbook Attachment Rates (アタッチ率と再実行のインサイト)

  • ケース/アラートあたりの平均・最大プレイブック アタッチ数を表示
  • アタッチ数と再実行 (rerun) 頻度でランキングし、再実行率の高いプレイブックを特定

⏱️ 3. Response Execution Time (実行レイテンシの診断)

  • エンドツーエンドの平均プレイブック実行時間 (トリガー/アタッチから全ステップ完了まで。アクション実行、ステップ遷移、キュー遅延、手動アクション待ち時間を含む)
  • 個々のアクションの平均実行時間 (開始から結果保存まで) で、待ち時間とアクティブな実行時間を区別可能
  • 最も遅いプレイブック実行 Top 30 / アクション実行 Top 30 をリスト表示

🩺 4. Playbook Health (プレイブックとインテグレーションの健全性監視)

  • 直近 30 件の失敗したプレイブックのサマリー (失敗したアクション、ステータス、エラーメッセージ、ケース ID リンク)
  • 失敗率の高いプレイブック Top 30、強制終了 (TERMINATED) されたプレイブック Top 30
  • 失敗したプレイブック率/インテグレーション率の時系列推移、アクションの失敗理由 (FAULTED、UNHANDLED_TIMEDOUT、PENDING_ACTION_TIMEOUT など)

🤖 5. Integrations Utilization and Automation Effectiveness (自動化の有効性メトリクス)

  • インテグレーションとアクションの利用ランキング
  • 自動クローズ (AUTOMATIC) と手動クローズのケース比率、および両者の MTTR (平均解決時間) 比較

🔍 ダッシュボードレベルのフィルタ

フィルタ説明
Global Time Filter期間フィルタ (デフォルト: 過去 7 日間)。ただし「Playbooks Pending in Queue」ウィジェットは固定の 7 日間ルックバックで現在のキュー数を表示
Playbook Simulatedプレイブック シミュレータでの実行 (playbook.simulated) を含めるか (デフォルト: false = 本番実行のみ)
Execution Scope Filter実行スコープ (playbook.metadata.execution_scope) によるフィルタ
Environments Filter複数の SecOps 環境 (playbook.metadata.environments、case.environment) を同時選択可能 (デフォルト: Default Environment)

🔬 技術仕様

📖 主要な用語とメトリクスの定義

用語定義
プレイブック実行時間プレイブックがトリガーされてアラート/ケースにアタッチされてから全ステップ完了までのエンドツーエンド経過時間 (アクション実行、ステップ遷移、キュー遅延、手動アクション待ちを含む)
アクション実行時間個々のアクションが実行を開始してから結果が保存されるまでのアクティブな実行時間
アタッチされたプレイブックアラートの取り込み/作成時にトリガーされ、ケースまたはアラートにリンクされたプレイブック
再実行 (rerun) プレイブックすでにアタッチ済みのケース/アラートに対して再トリガーされたプレイブック実行
Faulted実行中にエラーまたはタイムアウトが発生したアクション (FAULTED、FAULTED_AND_SKIPPED、UNHANDLED_TIMEDOUT、PENDING_ACTION_TIMEOUT)
Terminatedアナリストが手動停止した、または完了前にアラート/ケースがクローズされたプレイブック実行 (TERMINATED)
MTTRケース作成からクローズまでの平均経過時間 (分)。プレイブックによる自動クローズ (AUTOMATIC) と手動クローズを比較

💪 メリット

💼 ビジネス面

✓自動化 ROI の可視化: 自動クローズと手動クローズの MTTR 比較により、SOAR 自動化への投資効果を経営層や SOC マネージャーに定量的に示せる
✓SOC 運用の信頼性向上: プレイブックの失敗やインテグレーション障害を早期に検知し、自動化が「静かに壊れている」状態を防げる
✓構築コスト不要: キュレート済みダッシュボードとして提供されるため、カスタム ダッシュボードを自作することなくすぐに利用開始できる

🔧 技術面

✓レイテンシのボトルネック切り分け: エンドツーエンド実行時間とアクティブなアクション実行時間を分離計測でき、「インテグレーションが遅い」のか「手動承認待ちが長い」のかを切り分けられる
✓障害の根本原因特定の高速化: 失敗サマリーのケース ID リンクからプレイブック サマリーに直接ジャンプし、ステップログ確認からアクション再実行まで一気通貫
✓インテグレーション障害の横断検知: 複数プレイブックの同時失敗時に、共有インテグレーションの問題 (認証情報の期限切れ、レート制限など) を Failed Integrations % Over Time やアクション失敗理由から特定できる

⚠️ デメリット・制約事項

🚧 制限事項

✗Response Health Hub は 読み取り専用 で直接編集できない。カスタマイズには複製が必要
✗「Playbooks Pending in Queue」ウィジェットは固定の 7 日間ルックバックで表示され、Global Time Filter の影響を受けない
✗クエリ可能な SOAR ケースデータは 2025 年 5 月 10 日以降 に生成されたものに限られる (ネイティブ ダッシュボード共通の制約)
✗プレイブック データソースのクエリ期間は 最大 365 日 (ネイティブ ダッシュボード共通の制約)

🤔 考慮すべき点

  • 閲覧には IAM 権限と SOAR ロールの両方 が必要なため、SOC メンバーへのアクセス権設計を事前に確認する
  • デフォルトでは Playbook Simulated フィルタが false のため、シミュレータでのテスト実行は表示されない (テスト実行の分析には明示的な切り替えが必要)
  • メトリクスを見るだけでは問題は解決しないため、特定した事象 (認証エラー、タイムアウト、キュー滞留など) ごとの修復手順を運用 Runbook に組み込むことが望ましい

💡 ユースケース

🔥 ユースケース 1: プレイブック失敗の急増を調査する

シナリオ: Playbook Execution Success Rate で失敗率の上昇を検知した SOAR エンジニアが、原因を特定して修復する。

  1. Top 30 Failure Rate Playbooks で失敗数・失敗率の高いプレイブックを特定
  2. Failed Playbooks % Over Time で、失敗が突発的 (プレイブック編集や認証情報の期限切れ直後) か恒常的かを判断
  3. Latest 30 Failed Playbook Summary で Action / Action Status / Action Message を確認し、失敗したステップと正確なエラーメッセージを把握
  4. Case ID リンク から該当ケースを開き、Playbooks タブのプレイブック サマリーでステップログを確認。根本原因の対処後にアクションまたはプレイブック全体を再実行
✅ 効果: 失敗したプレイブックの特定から根本原因の把握、再実行までをダッシュボード起点で完結でき、対応自動化の停止時間を最小化できる。

🔌 ユースケース 2: インテグレーション障害 (認証エラー・タイムアウト) の切り分け

シナリオ: 複数のプレイブックが同時に失敗しており、共有しているサードパーティ インテグレーションの問題が疑われる。

  1. Failed Integrations % Over Time で失敗スパイクが特定のインテグレーションと相関しているかを確認
  2. Actions Failure Rate で Failure % / Failure Statuses / Latest Failure Reasons を確認
  3. Response > IDE または Settings > SOAR Settings > Environments で、該当環境のインテグレーション インスタンス設定と認証情報をテスト
失敗理由診断と対処
FAULTED + 401/403API キーやトークンの期限切れ・権限不足 → 認証情報を更新
UNHANDLED_TIMEDOUT外部エンドポイントの応答遅延やリモート エージェントの問題
PENDING_ACTION_TIMEOUT手動入力待ち/非同期コールバックのタイムアウト
✅ 効果: プレイブック個別の問題かインテグレーション共通の問題かを迅速に切り分け、認証情報更新などの修復アクションに直結できる。

📈 ユースケース 3: 自動化の有効性を定量評価する

シナリオ: SOC マネージャーが四半期レビューで SOAR 自動化の効果を報告する。

✅ 効果: 自動クローズと手動クローズの比率および MTTR 比較、インテグレーション/アクション利用ランキングから、自動化によって短縮された解決時間と、追加で自動化すべき領域 (手動待ちが長いプレイブックなど) をデータに基づいて提示できる。

🚦 ユースケース 4: キュー滞留と過剰トリガーの最適化

シナリオ: Playbooks Pending in Queue の値が高止まりしており、アラート急増や過剰に広いトリガー条件により実行パイプラインが飽和している。

✅ 効果: トリガー条件の絞り込み、再利用可能ブロックによる冗長なプレイブックの統合、一括アクション/フィルタの活用によりキュー滞留を解消し、対応遅延を防止できる。

🔗 関連サービス・機能

📊 キュレート済みダッシュボード (Curated Dashboards)
Response Health Hub は Google SecOps の事前定義キュレート済みダッシュボードの 1 つ。SOAR ケース、SOAR プレイブック、Ingestion metrics など他のカテゴリのダッシュボードと併用できる
🧩 ネイティブ ダッシュボード (Native Dashboards)
Response Health Hub を複製してカスタマイズする際の基盤。YARA-L クエリの playbook / case データソースを使って独自ウィジェットを追加可能
📘 SOAR プレイブック / プレイブック モニタリング
ダッシュボードの失敗サマリーからケースのプレイブック サマリー (ステップログ、エラー詳細、再実行) に直接遷移して修復作業を行う
🛰️ リモート エージェント
UNHANDLED_TIMEDOUT の診断時に、リモート実行されるインテグレーションのエージェント健全性のトラブルシューティングと組み合わせる
🔐 Cloud IAM
ダッシュボードとプレイブック データへのアクセスは Chronicle API の IAM ロール/権限で制御される

🎯 まとめ

Response Health Hub により、これまで個別のケース画面やカスタム ダッシュボードに分散していた SOAR プレイブックの運用監視が、 環境横断の単一ダッシュボード に集約されました。

SOAR を本番運用しているチームは、まずデフォルト設定でダッシュボードを確認して 失敗率・キュー滞留・レイテンシのベースライン を把握し、 認証エラーやタイムアウトなど事象別の修復手順を 運用 Runbook に組み込む ことを推奨します。
