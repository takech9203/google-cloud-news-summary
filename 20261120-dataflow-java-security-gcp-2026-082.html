☕ Dataflow: Java ワーカーセキュリティアップデート

CVE-2026-114938 (Critical RCE) への 2 段構えの対応 — サービス側 intrinsic 無効化 + Beam 2.78.0 パッチ済み OpenJDK
📅 リリース日: 2026-11-20

📋 概要

2026 年 11 月 20 日、Dataflow は OpenJDK の Critical 脆弱性 CVE-2026-114938 (セキュリティ速報 GCP-2026-082) に対応する 2 段構えのセキュリティアップデートをリリースしました。

🛡️ 対応 1: サービス側セキュリティアップデート

Google 提供の標準 Java 17 / 21 / 25 ワーカーコンテナで、すべての Apache Beam SDK バージョンを対象に、脆弱性の原因である HotSpot の Base64 intrinsic を無効化 (-XX:-UseBASE64Intrinsics)。

☕ 対応 2: Apache Beam 2.78.0 ワーカーイメージの OpenJDK パッチ

パッチ済み OpenJDK (17.0.21.1+2 / 21.0.13.1+2 / 25.0.5.1+2) を適用。対象は Portable Runner を使用しないジョブ (バッチ: Non-Portable Runner、ストリーミング: Streaming Java Runner)。Portable Runner 用と Flex Template ベースイメージのパッチ版は作成中 (in progress)。

🚨 最重要ポイント: 既存のストリーミングジョブは、サービス側の JVM オプション更新もパッチ済みワーカーイメージも自動的には取り込みません。保護を適用するには、ストリーミングジョブの更新 (置換ジョブの起動) または再起動が必要です。カスタムコンテナ使用ジョブは environment_variables experiment による緩和策を自分で適用する必要があります。

🔄 Before / After

❌ アップデート前の課題

  • 標準 Java ワーカーコンテナ上のジョブも、AVX-512 VBMI 対応マシンタイプ上で未パッチの OpenJDK 17.0.6+ を実行する場合、CVE-2026-114938 の影響を受ける可能性があった
  • 恒久対策となるパッチ済み OpenJDK を含むワーカーイメージが提供されていなかった
  • GCP-2026-082 の全体ガイダンスでは「ワーカー JVM に JDK_JAVA_OPTIONS 緩和策を適用し、パッチ済みイメージ公開後にジョブを再起動する」という暫定対応のみが案内されていた

✅ アップデート後の改善

  • サービス側アップデートにより、標準 Java 17 / 21 / 25 ワーカーコンテナでは全 Beam SDK バージョンで脆弱な Base64 intrinsic を無効化 (-XX:-UseBASE64Intrinsics)
  • Portable Runner 非使用ジョブ向けに、パッチ済み OpenJDK を含む Apache Beam 2.78.0 ワーカーイメージを提供
  • カスタムコンテナ / ジョブレベル向けに --experiments="environment_variables=JDK_JAVA_OPTIONS=-XX:-UseBASE64Intrinsics" 緩和オプションを案内

Dataflow の対応は、標準ワーカーコンテナへのサービス側 intrinsic 無効化と、Beam 2.78.0 イメージへのパッチ済み OpenJDK 適用の 2 系統です。いずれの場合も、既存のストリーミングジョブは更新または再起動しない限り保護が適用されない点が最重要ポイントです。

⚡ サービスアップデートの詳細 (主要機能)

1️⃣ サービス側セキュリティアップデート (全 Beam SDK バージョン対象)
→Google 提供の標準 Java 17 / 21 / 25 ワーカーコンテナで、脆弱な HotSpot Base64 intrinsic を無効化 (-XX:-UseBASE64Intrinsics)
→すべての Apache Beam SDK バージョンに適用されるため、SDK をアップグレードできないジョブも新規起動時に保護される
2️⃣ Apache Beam 2.78.0 ワーカーイメージの OpenJDK パッチ
→パッチ済み OpenJDK (Java 17: 17.0.21.1+2、Java 21: 21.0.13.1+2、Java 25: 25.0.5.1+2) を適用
→対象は Portable Runner を使用しないジョブ (バッチ: Non-Portable Runner、ストリーミング: Streaming Java Runner)
→Portable Runner 用および Flex Template ベースイメージのパッチ済みワーカーイメージは作成中 (in progress)
3️⃣ カスタムコンテナ / ジョブレベル向けの緩和用パイプラインオプション
→--experiments="environment_variables=JDK_JAVA_OPTIONS=-XX:-UseBASE64Intrinsics" で Base64 intrinsic をジョブレベルで明示的に無効化
→Classic Template / Flex Template では --additional-experiments (REST API では additionalExperiments) で同じ値を指定
→緩和の有効化はワーカーログの Picked up JDK_JAVA_OPTIONS: -XX:-UseBASE64Intrinsics で確認可能
4️⃣ 既存ストリーミングジョブへの適用ガイダンス
→既存のストリーミングジョブはサービス側 JVM オプション更新もパッチ済みワーカーイメージも自動取得しない
→適用にはストリーミングジョブの更新 (置換ジョブの起動) または再起動が必要

🔧 設定方法

📌 前提条件

✓影響条件の確認: Java 17 (Beam SDK 2.56.0+) / 21 / 25 ランタイム、AVX-512 VBMI 対応マシンタイプ、ワーカーコードでの信頼できない Base64 入力のデコード、の 3 条件に該当するジョブを特定していること
✓対象プロジェクトでの Dataflow ジョブの起動・更新権限があること
1 カスタムコンテナ使用ジョブ (またはジョブレベルで明示的に無効化したい場合) に緩和オプションを設定する
Bash 緩和用パイプラインオプション 
# 通常のパイプライン起動時
--experiments="environment_variables=JDK_JAVA_OPTIONS=-XX:-UseBASE64Intrinsics"

# Classic Template / Flex Template を gcloud CLI で起動する場合
--additional-experiments="environment_variables=JDK_JAVA_OPTIONS=-XX:-UseBASE64Intrinsics"

REST API では additionalExperiments に同じ値を指定します。緩和が有効になっていることは、ワーカーログに次のエントリが出力されることで確認できます。

Log ワーカーログでの適用確認 
Picked up JDK_JAVA_OPTIONS: -XX:-UseBASE64Intrinsics
2 既存のストリーミングジョブを更新または再起動する
Bash 置換ジョブの起動 (ジョブの更新) — Java パイプラインの例 
--update --jobName=EXISTING_JOB_NAME

既存のストリーミングジョブはサービス側 JVM オプション更新やパッチ済みワーカーイメージを自動的に取り込みません。ストリーミングジョブの更新 (置換ジョブの起動) またはジョブの再起動を実施します。

3 (恒久対策) Apache Beam 2.78.0 へアップグレードし、必要に応じて GC を調整する
Bash OOM 発生時 (JDK-8319713 / ParallelGC) は G1 GC を使用 
--experiments=java_gc=UseG1GC

Portable Runner を使用しないジョブは、Apache Beam 2.78.0 へのアップグレードでパッチ済み OpenJDK を含むワーカーイメージを取得できます。アップグレード後に ParallelGC に影響する JDK-8319713 に起因する OOM エラーが発生した場合は、--experiments=java_gc=UseG1GC で G1 ガベージコレクタを構成します。

⚖️ メリットと制約事項

👍 メリット

ビジネス面

  • Critical 脆弱性への迅速な保護: サービス側アップデートが全 Beam SDK バージョンの標準ワーカーコンテナに適用され、SDK アップグレードを待たずに新規起動ジョブが保護される
  • 影響範囲の明確化による対応工数の削減: 3 条件 (ランタイム / マシンタイプ / コードパス) による影響判定基準が明示され、デフォルトの E2 / N1 ワーカーや Java 8 / 11 のジョブは対応不要と切り分けられる

技術面

  • intrinsic 無効化とパッチ済み JDK の 2 段構え: サービス側の即時緩和と Beam 2.78.0 イメージの恒久対策の両方を提供
  • ファーストパーティ Beam 変換の安全性確認済み: 調査対象をカスタムコードに絞れる

⚠️ デメリット・制約事項

制限事項

  • パッチ済み OpenJDK 入りワーカーイメージは Apache Beam 2.78.0 のみで、Portable Runner 非使用ジョブ (Non-Portable Runner / Streaming Java Runner) に限定
  • Portable Runner 用ワーカーイメージと Flex Template ベースイメージのパッチ版は作成中 (in progress)
  • カスタムコンテナはサービス側アップデートの対象外で、environment_variables experiment による緩和策を自分で適用する必要がある

考慮すべき点

  • 既存のストリーミングジョブは何もしなければ保護されない — 更新 (置換ジョブ) または再起動が必須
  • Beam 2.78.0 アップグレード後、JDK-8319713 (ParallelGC) により OOM が発生する場合は --experiments=java_gc=UseG1GC を構成
  • Flex Template ランチャー VM は、マシンタイプ上書き時やフォールバック時に影響を受ける可能性があるため構成確認が必要
  • -XX:-UseBASE64Intrinsics は緩和策であり、恒久対策はパッチ済み OpenJDK 入りイメージへの移行

💡 ユースケース

🚨 ユースケース 1: カスタムコンテナを使うストリーミングパイプラインの緊急対応

シナリオ: C3 マシンタイプ上でカスタムコンテナを使用し、外部システムから受信したメッセージに含まれる Base64 データをカスタム変換でデコードしている長期稼働ストリーミングジョブを運用している。

Bash 緩和オプション付きの置換ジョブを起動してジョブを更新 
mvn compile exec:java -Dexec.args="... \
  --update --jobName=EXISTING_JOB_NAME \
  --experiments=environment_variables=JDK_JAVA_OPTIONS=-XX:-UseBASE64Intrinsics"

効果: 3 条件すべてに該当する高リスク構成に対し、ジョブ更新 1 回で Base64 intrinsic の無効化を適用できる。ワーカーログの Picked up JDK_JAVA_OPTIONS エントリで適用を確認できる。

📋 ユースケース 2: 影響範囲の棚卸しによる対応優先順位付け

シナリオ: 多数の Dataflow ジョブを運用する組織が、CVE-2026-114938 への対応要否をジョブごとに判定したい。

効果: デフォルトの E2 / N1 ワーカーや Arm ベース VM、Java 8 / 11、Beam SDK 2.56.0 より前の Java 17 のジョブは影響なしと即座に除外でき、AVX-512 VBMI 対応マシンタイプ + Java 17 (Beam 2.56.0+) / 21 / 25 + 信頼できない Base64 入力をデコードするカスタムコードを持つジョブに対応を集中できる。
