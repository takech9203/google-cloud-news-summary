Direct Iceberg access

AlloyDB for PostgreSQL Preview PostgreSQL 18+
📅 リリース日: 2026-11-04 | Apache Iceberg テーブルへの直接クエリ

📋 概要

AlloyDB for PostgreSQL で、Cloud Storage または Lakehouse runtime catalog 上の Apache Iceberg テーブルを直接クエリできる「Direct Iceberg access」が Preview になりました。PostgreSQL 18 以降の AlloyDB で、標準の SQL (SELECT) により Iceberg データセットを読み取れます。

最大の特徴は 組み込み列指向エンジン (Columnar Engine) との統合です。ストリーミングによる直接スキャンに加え、google_columnar_engine_add() でテーブルをメモリに取り込むことで、スキャン・結合・集計を高速化し、サブ秒レベルの分析クエリを実現します。AlloyDB のヒープテーブル (運用データ) と Iceberg テーブル (履歴データ) の JOIN も可能で、複雑な ETL パイプラインなしにレイクハウスへアクセスできる Zero-ETL の重要なアップデートです。

❌ Before: アップデート前の課題

  • AlloyDB から Cloud Storage 上の Iceberg テーブルを直接クエリできず、ETL パイプラインでデータをコピー・移動する必要があった
  • 運用データと履歴データの横断分析には別の分析基盤 (BigQuery など) への統合が必要で、鮮度維持とパイプライン運用のコストが発生
  • オープンフォーマット (Iceberg) のデータを PostgreSQL の使い慣れた SQL で扱えなかった

✅ After: アップデート後の改善

  • Zero-ETL レイクハウスアクセス: データをコピーせず外部の Iceberg データセットをその場でクエリ
  • トランザクションと分析の統合: ヒープテーブルのライブな運用データと Iceberg の履歴データを JOIN 可能
  • 柔軟なカタログ統合: gs:// (Cloud Storage) と bl:// (Lakehouse runtime catalog) の両方をサポート
  • 列指向エンジンによる高速化: メモリ取り込みでサブ秒レベルの分析処理

AlloyDB は USING iceberg で定義したテーブル経由で Cloud Storage 上の Iceberg データを直接スキャンするか、列指向エンジンのメモリに取り込んで高速に分析クエリを処理します。運用データ (ヒープテーブル) との JOIN も単一の SQL で実行できます。

⚡ 主要機能

1️⃣ Iceberg テーブルへの直接クエリ (Zero-ETL)

→PostgreSQL の Table Access Method (TAM) インターフェース (USING iceberg) で、Cloud Storage 上の Iceberg テーブルを AlloyDB のテーブルとして定義
→標準 SQL (SELECT) でクエリ可能。ETL パイプラインの構築・管理・保守が不要
→CREATE TABLE ... AS SELECT で書き込み可能なローカルコピーの作成も可能

2️⃣ 2 つの読み取りモード

→直接スキャン (Direct scan): 最新の Iceberg スナップショットを Cloud Storage からストリーミングで読み取り、列指向エンジンが処理
→列指向エンジンアクセラレーション: google_columnar_engine_add() でメモリ上の列指向ストアに取り込み、スループットを最大化・レイテンシを最小化

3Iceberg テーブルを作成
SQL 
-- Cloud Storage パスから作成する例
CREATE TABLE customer_orders (
  order_id BIGINT,
  customer_id INT,
  order_status TEXT,
  total_amount DOUBLE PRECISION,
  order_date DATE,
  is_completed BOOLEAN
) USING iceberg
WITH (
  uri = 'gs://my-iceberg-analytics-bucket/datasets/sales/customer_orders'
);
💡 ヒント: カラム名とデータ型は、基盤となる Iceberg テーブルのスキーマと一致させる必要があります。Lakehouse runtime catalog の場合は uri に bl://projects/PROJECT_ID/catalogs/CATALOG_NAME/databases/DATABASE_NAME/tables/TABLE_NAME 形式を指定します。
4クエリの実行と列指向エンジンへの取り込み
SQL 
-- 標準 SQL でクエリ (運用テーブルとの JOIN も可能)
SELECT c.customer_name, SUM(o.total_amount) AS historical_spend
FROM customer_orders o
JOIN customers c ON o.customer_id = c.customer_id
GROUP BY c.customer_name;

-- 列指向エンジンに取り込んで高速化
SELECT google_columnar_engine_add('customer_orders');

-- 基盤の Iceberg テーブルに新しいスナップショットが書き込まれたら更新
SELECT google_columnar_engine_refresh('customer_orders');

-- 列指向エンジンの利用を EXPLAIN で確認 (Custom Scan (ColumnarScan) が表示される)
EXPLAIN (ANALYZE, COSTS OFF)
SELECT SUM(total_amount) FROM customer_orders WHERE is_completed = true;

✓データ活用のリードタイム短縮: 運用データと履歴データを単一 SQL で横断分析し、インサイトを迅速に獲得

⚙️ 技術面

✓Zero-ETL アーキテクチャ: USING iceberg のテーブル定義だけでアクセスでき、データの二重管理が不要
✓列指向エンジンによる高速化: メモリ上の列指向ストアでスキャン・結合・集計がサブ秒レベル
✓使い慣れた PostgreSQL インターフェース: 標準 SQL、GRANT、EXPLAIN など既存の運用ノウハウを活用

⚠️ デメリット・制約事項

🚫 制限事項

✗PostgreSQL 18 以降の AlloyDB でのみ利用可能
✗読み取り専用 (SELECT のみ)。Iceberg テーブルへの書き込み (INSERT / UPDATE / DELETE / TRUNCATE) は非サポート
✗Iceberg テーブルの作成は alloydbsuperuser ロールを持つユーザーのみ可能
✗データファイルは Parquet のみサポート (ORC は非サポート)
✗Iceberg v2 の delete files、v3 の deletion vectors は非サポート
✗ポイントインタイムクエリ (スナップショット指定) は非サポート
✗ALTER TABLE によるスキーマ変更は非サポート。基盤の Iceberg テーブルがスキーマ移行を経ていないことが前提
✗Lakehouse runtime catalog はエンドユーザー認証情報モードのみ (credential vending モードや他の REST カタログは非対応)
✗Requester Pays の Cloud Storage バケットは非サポート
✗部分的な取り込み (partial population) は非サポート。テーブル全体が列指向エンジンのメモリまたは SSD 領域に収まる必要がある

🤔 考慮すべき点

⚠️ Preview 機能: Pre-GA Offerings Terms が適用され、サポートが限定的な場合があります。本番環境への適用は GA を待つことを推奨します。
  • 列指向エンジン利用時は取り込み時点のスナップショットでクエリが実行されるため、基盤データ更新後は google_columnar_engine_refresh() での更新が必要 (更新しないと古いデータが返る可能性)
  • 直接スキャンでは REPEATABLE READ / SERIALIZABLE トランザクション内でも各ステートメントが最新スナップショットを読むため、トランザクション分離の挙動が通常のテーブルと異なる
  • 大きな Parquet row group を含むテーブルの取り込みでは、ワーカーあたりの population heap メモリ上限を超える場合がある (vCPU の少ないインスタンスで発生しやすい)。google_job_scheduler.max_parallel_workers_per_job = 0 の設定などで回避可能
  • 列指向エンジン用のメモリ割り当て (google_columnar_engine.memory_size_in_mb) の設計が必要

🎯 ユースケース

🔗 ユースケース 1: 運用データと履歴データの横断分析

シナリオ: EC サイトの顧客マスタは AlloyDB で管理し、過去数年分の注文履歴は Iceberg 形式で Cloud Storage のデータレイクハウスに保存。顧客ごとの累計購入額を分析したい。

SQL 
SELECT
  c.customer_name,
  c.account_tier,
  COUNT(o.order_id) AS total_orders,
  SUM(o.total_amount) AS historical_spend
FROM customer_orders o  -- Iceberg テーブル (Cloud Storage)
JOIN customers c        -- AlloyDB ヒープテーブル (運用データ)
  ON o.customer_id = c.customer_id
WHERE o.is_completed = true
GROUP BY c.customer_name, c.account_tier
ORDER BY historical_spend DESC;
✅ 効果: ETL なしでライブな顧客データと大量の履歴データを単一 SQL で結合分析でき、データ統合パイプラインの構築・運用が不要になる。

📊 ユースケース 2: 列指向エンジンによる高速ダッシュボード

シナリオ: BI ダッシュボードから Iceberg 上の売上データに集計クエリが頻繁に発行される。Cloud Storage への直接スキャンではレイテンシが要件を満たさない。

SQL 
-- よく使うカラムだけを列指向エンジンに取り込み
SELECT google_columnar_engine_add('customer_orders', 'customer_id,order_status');

-- 取り込み状態を確認 (status が USABLE ならキャッシュ済み)
SELECT relation_name, status FROM g_columnar_relations
WHERE relation_name = 'customer_orders';
✅ 効果: 以降のクエリはメモリ上の列指向ストアから読み取られ、サブ秒レベルの分析処理が可能になる。

📥 ユースケース 3: レイクハウスデータの選択的な取り込み

シナリオ: 直近のデータのみを AlloyDB 上で加工・更新したい。

SQL 
CREATE TABLE local_customer_orders AS
SELECT * FROM customer_orders
WHERE order_date >= '2026-01-01';
✅ 効果: Iceberg データの独立した書き込み可能なローカルコピーを簡単に作成でき、必要なデータだけを AlloyDB に取り込める。

🧩 関連サービス・機能

⚡ AlloyDB 列指向エンジン (Columnar Engine): 本機能の中核。Iceberg テーブルをメモリに取り込み、スキャン・結合・集計を高速化する
🪣 Cloud Storage: Iceberg テーブルのデータ (Parquet) とメタデータ (JSON / Avro) の格納先
📚 Lakehouse runtime catalog (BigLake): Iceberg テーブルのメタデータカタログ。bl:// URI でカタログ経由のアクセスが可能
📊 BigQuery: 同日に GA となった AlloyDB への BigQuery データ同期 (alloydb_sync) と組み合わせると、BigQuery とレイクハウス双方のデータを AlloyDB で活用できる (詳細は別レポート参照)
🧊 Apache Iceberg: オープンなテーブルフォーマット。スキーマ・スナップショット管理を提供する

📝 まとめ

Direct Iceberg access により、AlloyDB は運用データベースとデータレイクハウスの境界をまたぐ Zero-ETL な分析基盤へと進化しました。PostgreSQL 18 以降のクラスタで USING iceberg テーブルを定義するだけで、Cloud Storage 上の Iceberg データを標準 SQL でクエリでき、列指向エンジンとの組み合わせで高速な分析も可能です。Iceberg ベースのレイクハウスを運用している組織は、Preview 段階の制約 (読み取り専用、Parquet のみ等) を踏まえた上で、ETL パイプライン削減の効果を検証することを推奨します。
