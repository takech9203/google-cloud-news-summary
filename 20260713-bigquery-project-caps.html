☁️ 概要

BigQuery の Project Caps (Scheduling Policies) は、リザベーション内の各プロジェクトに対して最大スロット消費量と最大同時実行クエリ数を制限できる新機能です。マルチテナント環境で複数のチームやプロジェクトが同じリザベーションを共有する大規模組織にとって特に有用です。

Before / After 比較

❌ Before (従来)

  • フェアスケジューリングのみで特定プロジェクトがスロットを独占する可能性
  • プロジェクト単位での同時実行クエリ数制限が不可
  • リソース分離のために複数リザベーションへの分割が必要

✅ After (Project Caps)

  • リザベーションレベルでデフォルトのスロット・同時実行上限を一括適用
  • プロジェクトごとに個別のオーバーライド設定が可能
  • 単一リザベーション内で複数プロジェクトの制御が完結

⚡ 主要機能

🎚️ Maximum Slots (最大スロット制限)

✓プロジェクトが消費できるスロット数の上限を設定
✓最小許容値: 100 スロット
✓近似的なキャップとして機能 (厳密なハードリミットではない)

🔄 Maximum Concurrency (最大同時実行数)

✓同時実行クエリ数の上限を設定
✓アドミッション時にのみ適用
✓実行中のクエリはキャンセルされない

🎯 プロジェクト固有のオーバーライド

✓デフォルト設定を個別プロジェクトで上書き可能
✓アサインメントルール (Project Cap タイプ) で設定
✗フォルダー・組織レベルは非対応

⏱️ 即時反映

✓変更後最大 1 分で適用
✓Max Slots オーバーライドは新クエリ開始時に反映
✓既存クエリの自動キャンセルなし

Step 1: デフォルト Project Cap を設定 (Console)

BigQuery > Capacity management > リザベーション > Advanced settings から、Override project concurrency と Override project max slots を設定します。

Step 2: プロジェクト固有のオーバーライドを SQL で設定

SQL 
CREATE ASSIGNMENT
  `admin_project.region-us.my_reservation.project_a_cap`
OPTIONS (
  assignee = 'projects/my-project-a',
  scheduling_policy_max_slots = 600,
  scheduling_policy_concurrency = 100
);

Step 3: bq コマンドラインで設定

Bash 
bq mk \
  --project_id=ADMIN_PROJECT_ID \
  --location=us \
  --reservation_assignment \
  --reservation_id=my_reservation \
  --assignee_id=my-project-a \
  --assignee_type=PROJECT \
  --scheduling_policy_max_slots=600 \
  --scheduling_policy_concurrency=100

Step 4: 既存の設定を変更

SQL 
ALTER ASSIGNMENT
  `admin_project.region-us.my_reservation.project_a_cap`
SET OPTIONS (
  scheduling_policy_max_slots = 800,
  scheduling_policy_concurrency = 150
);

Step 5: 設定の確認

SQL 
SELECT *
FROM `region-us`.INFORMATION_SCHEMA.ASSIGNMENTS
WHERE assignment_type = 'PROJECT_CAP';
💡 ヒント: 設定を削除する場合は、値を null に設定するか、アサインメント自体を削除します。

ビジネス面

🛡️SLA の保護 - 重要プロジェクトを他の突発的ワークロードから保護
🏢マルチテナント管理の簡素化 - リザベーションの乱立を防止

技術面

🎛️きめ細かいリソース制御 - プロジェクト単位での詳細なガバナンス
📋キューイング制御 - レイテンシーの予測性を向上
🔧運用の柔軟性 - デフォルト + オーバーライドの二層構造

⚠️ デメリット・制約事項

⚠️ Preview 段階の制限: 本番環境での利用はサポートが限定的 (Pre-GA Offerings Terms が適用)

制限事項

✗Maximum Slots は厳密なハードリミットではなく近似的なキャップ (瞬間的に超過の可能性あり)
✗フォルダーおよび組織レベルでの設定は非対応 (プロジェクト単位のみ)
✗Maximum Slots のオーバーライド変更は新しいクエリの開始を待って反映
✗設定変更の反映に最大 1 分を要する

考慮すべき点

→最小スロット値 100 のため、小規模リザベーションでは設定粒度に制約あり
→同時実行数制限はアドミッション時のみ適用。実行中クエリの即座のキャンセルはなし
→過度に厳しい設定はアイドルスロットを発生させ、リザベーション全体の効率が低下する可能性
→フィードバックは bigquery-wlm-feedback@google.com へ送信

💡 ユースケース

🏢 ユースケース 1: マルチチーム環境でのリソース分離

シナリオ: データエンジニアリング、データサイエンス、BI チームが 1000 スロットのリザベーションを共有。ML トレーニングクエリが BI ダッシュボードに影響。

SQL 
-- データサイエンスプロジェクトに厳しい制限
CREATE ASSIGNMENT
  `admin.region-us.shared_reservation.ds_cap`
OPTIONS (
  assignee = 'projects/data-science-prod',
  scheduling_policy_max_slots = 300,
  scheduling_policy_concurrency = 10
);

-- BI プロジェクトには緩い制限
CREATE ASSIGNMENT
  `admin.region-us.shared_reservation.bi_cap`
OPTIONS (
  assignee = 'projects/bi-dashboard-prod',
  scheduling_policy_max_slots = 500,
  scheduling_policy_concurrency = 200
);

効果: BI ダッシュボードの応答時間が安定し、データサイエンスの大規模クエリによるスロット独占が防止される。

🔀 ユースケース 2: 開発環境と本番環境のリソース制御

シナリオ: コスト最適化のために dev/prod を同一リザベーションに配置。開発者のアドホッククエリが本番ジョブに影響。

SQL 
-- 開発プロジェクトのスロットと同時実行を厳しく制限
CREATE ASSIGNMENT
  `admin.region-us.main_reservation.dev_cap`
OPTIONS (
  assignee = 'projects/analytics-dev',
  scheduling_policy_max_slots = 200,
  scheduling_policy_concurrency = 20
);

効果: 開発環境からの突発的なクエリ負荷が本番環境に影響を与えなくなり、本番ジョブの安定性が向上。

🌐 ユースケース 3: SaaS プロバイダのテナント分離

シナリオ: SaaS プラットフォームで各テナント (顧客企業) ごとに GCP プロジェクトを割り当て。テナント間のリソース公平性を保証する必要がある。

効果: テナントごとのスロット消費量と同時実行数を制限し、ノイジーネイバー問題を防止。全テナントに対する SLA を保証。

💳 料金

✅ Project Caps 機能自体には追加料金はかかりません。 料金はリザベーションで利用する BigQuery エディションのスロット料金に基づきます。

BigQuery エディション別スロット料金

エディション 料金モデル コミットメント割引
Standard スロット時間単位 (PAYG) コミットメントなし
Enterprise スロット時間単位 (PAYG) 1 年: 20% 割引、3 年: 40% 割引
Enterprise Plus スロット時間単位 (PAYG) 1 年: 20% 割引、3 年: 40% 割引
⚠️ 注意: Standard エディションでは最大 1,600 スロット、最大 10 リザベーションの制限があります。Enterprise / Enterprise Plus エディションでは最大 200 リザベーションまで作成可能で、Project Cap の設定にはこれらのエディションが推奨されます。

🌍 利用可能リージョン

Project Caps は BigQuery リザベーションがサポートされる全リージョンおよびマルチリージョンで利用可能です。リザベーション作成時に指定したロケーションに従います。

🔗 関連サービス・機能

BigQuery Reservations
Project Caps はリザベーション機能の一部として動作し、スロットベースの容量管理を前提とする
BigQuery Autoscaling
オートスケーリングと組み合わせ可能。スケールアップ時にもプロジェクト単位の制限が維持される
BigQuery Editions
利用可能なワークロード管理機能はエディション (Standard/Enterprise/Enterprise Plus) により異なる
Idle Slot Sharing
制限されたプロジェクトが使い切れないスロットは、他のプロジェクトにアイドルスロットとして共有
Query Queues / Target Concurrency
リザベーション全体の同時実行ターゲットと Project Cap の同時実行制限は独立して動作

📝 まとめ

BigQuery Project Caps (Scheduling Policies) は、マルチプロジェクト環境におけるリソースガバナンスの課題を解決する重要な機能です。リザベーション内で各プロジェクトのスロット消費量と同時実行数を制御することで、ノイジーネイバー問題を防止し、ワークロードの優先度に応じた柔軟なリソース配分を実現します。

💡 推奨アクション: 現在 Preview 段階ですが、複数チームがリザベーションを共有する組織では、早期に検証を開始し、GA に向けた運用設計を進めることを推奨します。
