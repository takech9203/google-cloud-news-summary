📋 JupyterLab クライアントサイドログの
Cloud Logging 転送

リリース日: 2026-09-21

📌 概要

Agent Platform Workbench (Gemini Enterprise Agent Platform のノートブックコンポーネント、旧 Vertex AI Workbench) のインスタンスイメージリリース 20260920.00_p0 が公開。JupyterLab がクライアントサイド (ブラウザ側) で発生するログをインスタンスのバックエンドに転送し、Cloud Logging に表示する機能が追加された。

これまでブラウザの開発者ツールでしか確認できなかったフロントエンド起因の問題を、Cloud Logging 上でサーバーサイドのログと合わせて調査できるようになり、ノートブック環境のデバッグとトラブルシューティングが容易になる。

📤 転送対象のログ種別 (4 種類)

🖥️ コンソールエラー console errors
⚠️ キャッチされない例外 uncaught exceptions
❌ 未処理 Promise リジェクション unhandled promise rejections
🌐 失敗したネットワークリクエスト failed network requests

😓 Before: アップデート前の課題

  • ✗UI のコンソールエラーや例外はユーザーのブラウザ内でのみ発生し、管理者やサポート担当者が直接確認できない
  • ✗フロントエンド起因の問題調査では、ユーザーに再現してもらい開発者ツールの出力を共有してもらう必要があった
  • ✗SSH 接続での journalctl -u jupyter.service や診断ツールではサーバーサイドのログしか取得できず、クライアント側の事象と突き合わせが困難

😊 After: アップデート後の改善

  • ✓4 種類のクライアントサイドログが自動的にインスタンスバックエンドへ転送され、Cloud Logging に表示される
  • ✓ブラウザ側の事象をサーバーサイドのログと同じ場所 (Cloud Logging) から調査でき、問題の切り分けが容易に
  • ✓ユーザーのブラウザに依存せず障害情報を収集でき、再現依頼や開発者ツールの出力共有の手間を削減
💡 補足: 本リリースには「上流依存パッケージの最新化 (Installed latest packages from upstream dependencies)」も含まれるが、これは定常的なパッケージ更新 (Change) である。

これまでブラウザ内に閉じていた JupyterLab のクライアントサイドログが、インスタンスバックエンド経由で Cloud Logging に集約され、Logs Explorer から調査できるようになる。

⚡ 主要機能

1. 📤 クライアントサイドログの自動転送

JupyterLab のフロントエンドで発生したログをインスタンスバックエンドへ転送。転送されたログは Cloud Logging に表示され、Logs Explorer などから検索・調査できる。

2. 🧾 転送対象のログ種別

コンソールエラー / キャッチされない例外 / 未処理の Promise リジェクション / 失敗したネットワークリクエストの 4 種類を転送対象とする。

3. 📦 上流依存パッケージの最新化 (Change)

20260920.00_p0 リリースには、上流依存パッケージの最新版へのアップデートも含まれる。

必要な権限logging.logEntries.create 権限 (Logs Writer ロール roles/logging.logWriter に含まれる)
⚠️ 権限に注意: Cloud Logging へのログ書き込みには、Workbench インスタンスが使用するサービスアカウントに logging.logEntries.create 権限が必要。権限が不足している場合、ログの送信は PERMISSION_DENIED で失敗する。

⚖️ メリット・制約事項

💼 ビジネス面のメリット

  • ✓サポート対応の効率化: 「ノートブックが動かない」という問い合わせに対し、開発者ツールの出力を依頼せずに Cloud Logging から直接クライアントサイドの事象を確認できる
  • ✓問題解決までの時間短縮: フロントエンドとバックエンドのログを 1 か所で突き合わせられるため、原因の切り分けが速くなる

🔬 技術面のメリット

  • ✓可観測性の向上: これまで欠落していたクライアントサイドの障害情報 (例外、Promise リジェクション、ネットワークエラー) が観測可能に
  • ✓既存のログ基盤との統合: Cloud Logging に集約されるため、ログベースの指標やアラートなど既存の運用フローに組み込める
  • ✓追加設定が不要: イメージリリースに含まれる機能であり、JupyterLab 側での個別セットアップなしに利用できる

🚧 考慮すべき点

  • ⚠20260920.00_p0 リリース以降のイメージで提供されるため、古いイメージのままのインスタンスでは利用できない
  • ⚠Cloud Logging へのログ取り込みは Cloud Logging の料金体系 (無料枠超過分の取り込み課金) の対象となるため、ログ量の増加に留意
  • ⚠サービスアカウントに Cloud Logging への書き込み権限がない場合、ログは記録されない

🎯 ユースケース

🔍 ユースケース 1: JupyterLab UI の不具合調査

シナリオ: データサイエンティストから「ノートブックのセル実行結果が表示されない」「UI が固まる」といった報告を受けた管理者が原因を調査する。

実装例: Logs Explorer で対象インスタンスのログをフィルタリングし、報告時刻付近のコンソールエラーやキャッチされない例外を確認する。

効果: ユーザーのブラウザ環境に立ち入ることなく、クライアントサイドで発生した例外やエラーを特定できる。

🌐 ユースケース 2: ネットワーク起因の障害切り分け

シナリオ: プロキシや VPC 構成の変更後、JupyterLab から特定の API 呼び出しが失敗するようになった。

効果: 失敗したネットワークリクエストが Cloud Logging に記録されるため、どのリクエストがいつ失敗したかを時系列で確認でき、ネットワーク設定起因かアプリケーション起因かの切り分けが容易になる。
