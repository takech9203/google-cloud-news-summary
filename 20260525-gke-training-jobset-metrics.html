☁️ 概要

GKE において、ML/AI トレーニング JobSet の効率性をモニタリングするための 2 つの新しいシステムメトリクスが Preview として利用可能になりました。

「Goodput」(生産的な時間の割合) という概念に基づき、トレーニングジョブがリソースを確保してから実際にアクセラレータが生産的に活用されるまでのプロセスを可視化します。特に TPU マルチスライス環境での大規模分散トレーニングにおいて、スケジューリングの遅延やリソース利用の非効率性を特定するための重要な指標です。

🔄 Before / After 比較

❌ Before (アップデート前)

  • スケジューリング遅延を計測する標準メトリクスがなかった
  • アクセラレータの実効利用率を JobSet 単位で把握できなかった
  • 非効率性がインフラ起因かアプリ起因か切り分け困難
  • ML Goodput Measurement ライブラリへの依存 (アプリコードへの組み込みが必須)

✅ After (アップデート後)

  • scheduling_goodput で Pod スケジューリング遅延を即座に検出
  • proxy_runtime_goodput で実効生産性を自動推定
  • JobSet ダッシュボードの「Training Goodput」タブで一元確認
  • GKE インフラ起因 vs ML アプリ起因の明確な切り分け

⚡ 主要機能

📐 scheduling_goodput (スケジューリング Goodput)

JobSet の作成時刻を起点として、すべての必要な Pod が Ready 状態になっている時間の割合を測定します。

→値が低い場合: Pod スケジューリング遅延、イメージプル時間、リソース割り当て問題を示唆
→メトリクスタイプ: GAUGE, DOUBLE (0.0 - 1.0)
→サンプリング間隔: 60 秒ごと

🚀 proxy_runtime_goodput (プロキシランタイム Goodput)

すべてのアクティブなアクセラレータが生産的に動作している時間の割合を推定します。アプリケーションの計装なしに利用可能です。

→アクセラレータの Duty Cycle が 10% を超えている時間に基づき計算
→メトリクスタイプ: GAUGE, DOUBLE (0.0 - 1.0)
→アプリケーションコードの変更不要

📊 JobSet モニタリングダッシュボード統合

Google Cloud コンソールの JobSet モニタリングダッシュボードに「Training Goodput」タブとして統合されています。

→ノードプールの健全性メトリクスとの相関分析が可能
→Goodput 低下とノードプール障害の関連を視覚的に確認
→PromQL クエリでカスタムダッシュボード構築可能

Goodput と Badput の関係

📐 Scheduling 層

Goodput: 全リソースが利用可能な時間の割合
Badput: スケジューリング待ち・リソース不足の時間
Badput = 1 - scheduling_goodput

🚀 Runtime 層

Goodput: アクセラレータが生産的に動作する時間の割合
Badput: アクセラレータがアイドル/非生産的な時間
Badput = 1 - proxy_runtime_goodput

⚙️ 設定方法

前提条件

✓GKE クラスタが稼働していること (JobSet メトリクスをサポートするバージョン)
✓TPU または GPU ノードプールが構成されていること
✓JobSet API が有効化されていること
✓Cloud Monitoring API が有効であること

ステップ 1: JobSet を使用したトレーニングワークロードのデプロイ

YAML 
apiVersion: jobset.x-k8s.io/v1alpha2
kind: JobSet
metadata:
  name: my-training-jobset
spec:
  replicatedJobs:
  - name: worker
    replicas: 2
    template:
      spec:
        parallelism: 4
        completions: 4
        template:
          spec:
            containers:
            - name: training
              image: my-training-image:latest
              resources:
                limits:
                  google.com/tpu: 4
💡 ポイント: JobSet リソースをデプロイすると、GKE は自動的に Goodput メトリクスの収集を開始します。追加の設定は不要です。

ステップ 2: PromQL クエリでメトリクスを確認

PromQL

    cluster_name="my-cluster"
  }[${__interval}]
)

# Proxy Runtime Goodput の時系列平均

    cluster_name="my-cluster"
  }[${__interval}]
)

ステップ 3: アラートの設定 (オプション)

Bash 
# gcloud を使用してアラートポリシーを作成
gcloud alpha monitoring policies create \
  --display-name="Low Scheduling Goodput Alert" \
  --condition-display-name="Scheduling Goodput below 80%" \
  --condition-filter='resource.type="k8s_entity" AND metric.type="kubernetes.io/jobset/scheduling_goodput"' \
  --condition-threshold-value=0.8 \
  --condition-threshold-comparison=COMPARISON_LT \
  --notification-channels="projects/my-project/notificationChannels/12345"

⚠️ デメリット・制約事項

⚠️ Preview ステータス: 本番環境での利用には注意が必要です。「Pre-GA Offerings Terms」が適用されます。

制限事項

✗データ可視化までの遅延が最大 3600 秒 (1 時間) と長く、リアルタイムのトラブルシューティングには不向き
✗proxy_runtime_goodput は推定値。正確なランタイム Goodput には ML Goodput Measurement ライブラリの計装が別途必要
✗サンプリング間隔 60 秒のため、短時間のスパイクや一時的な問題は検出されない可能性
✗7 日以上経過した JobSet に対しては一部メトリクスが利用できない制約あり

考慮すべき点

✗Duty Cycle > 10% の閾値が全ワークロードに適切とは限らない (データロード中心のワークロードで誤検出の可能性)
✗GA 移行時に仕様変更が発生する可能性
✗GPU ワークロードでの proxy_runtime_goodput の精度は TPU と異なる場合あり

🎯 ユースケース

🧠 ユースケース 1: TPU マルチスライス分散トレーニングの最適化

シナリオ: LLM トレーニングを TPU v5p マルチスライスで実行中。完了までの実時間が理論値より大幅に長い。原因がスケジューリングかアクセラレータ利用率かを切り分けたい。

効果: scheduling_goodput = 0.95, proxy_runtime_goodput = 0.60 であれば、スケジューリングは良好だがアクセラレータ利用効率に問題があることが判明。チェックポイント保存頻度やデータパイプライン最適化に注力すべきと判断可能。

👥 ユースケース 2: Kueue マルチテナント環境での公平性モニタリング

シナリオ: 複数チームが共有 GKE クラスタ上で Kueue を使用。特定チームの JobSet で scheduling_goodput が著しく低いとの報告。

効果: チーム間の scheduling_goodput を比較し、Kueue の ResourceFlavor や ClusterQueue 設定の適切性を客観評価。リソース割り当てポリシー調整の根拠として活用。

🛠️ ユースケース 3: ノードプール障害の影響評価

シナリオ: TPU ノードプールでメンテナンスイベント発生後、トレーニングジョブの再開に時間がかかっている。

効果: scheduling_goodput の急落タイミングとノードプール中断イベントを照合。インフラ障害がトレーニング効率に与えた影響を定量レポートし、SRE チームへの改善要求の根拠に。

📝 まとめ

今回の GKE トレーニング JobSet Goodput メトリクスの追加は、大規模 ML/AI トレーニングワークロードの運用効率を定量的に把握するための重要なアップデートです。

scheduling_goodput によるインフラ層の可視化と proxy_runtime_goodput によるアクセラレータ効率の推定を組み合わせることで、トレーニングの非効率性の原因を迅速に特定し、コスト最適化とトレーニング時間の短縮を実現できます。

💡 推奨アクション: TPU/GPU を使用した大規模トレーニングを運用しているチームは、まず JobSet モニタリングダッシュボードで現状の Goodput を確認し、ベースラインを設定することを推奨します。
