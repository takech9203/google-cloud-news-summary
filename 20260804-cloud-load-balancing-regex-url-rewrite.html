Cloud Load Balancing 🌐 ネットワーキング Preview

✂️ 正規表現による URL リライト
(regexRewrite) が Preview に

リリース日: 2026-08-04

📌 概要

Application Load Balancer の URL マップにおいて、ルートルールに対する正規表現 URL リライト (regexRewrite) が Preview として利用可能になりました。RE2 構文の正規表現でリクエストパスをマッチ・キャプチャし、バックエンドに転送する前に URL パスのコンポーネントを置換・削除・並べ替えできます。

pathPattern でパスの一部をキャプチャし、pathSubstitution でキャプチャグループを参照しながらパスを再構築します。名前付きグループ (\g<name>) と番号参照 (\1) の両方に対応。API ゲートウェイ的なパス変換を、アプリケーションコードや追加プロキシなしにロードバランサーのレイヤーで宣言的に実現できます。

😣 Before (アップデート前)

  • URL リライトは pathPrefixRewrite (プレフィックス置換) と pathTemplateRewrite (ワイルドカード) に限られていた
  • パス途中の複数セグメントを抽出して結合・並べ替えるような複雑な変換は不可能
  • バックエンドのアプリケーションや別途プロキシでの実装が必要だった

😊 After (アップデート後)

  • RE2 正規表現でパスをマッチ・キャプチャし、キャプチャグループで新しいパスを再構築できる
  • 名前付き (\g<name>) と番号 (\1) の両方でコンポーネントの置換・削除・並べ替えが可能
  • リージョナル/クロスリージョン内部 ALB、リージョナル/グローバル外部 ALB で URL マップの設定のみで実現

クライアントのリクエストパスを URL マップで RE2 正規表現によりマッチ・キャプチャし、置換後のパスでバックエンドサービスに転送するフロー

⚙️ 主要機能

1️⃣ 正規表現によるパスのマッチとキャプチャ (pathPattern)

routeRules[].routeAction.urlRewrite.regexRewrite.pathPattern に RE2 構文の正規表現を指定。受信リクエストパスの一部をキャプチャグループ (...) で抽出できます。名前付きキャプチャグループは (?<name>re) または (?P<name>re) 形式で定義します。

2️⃣ キャプチャグループを使ったパスの再構築 (pathSubstitution)

pathSubstitution でバックエンドへ送るパスを再構築。名前付き構文 \g<name> または番号構文 \1、\2 でキャプチャグループを参照できます。名前付きグループには番号と名前の両方が付与されるため、どちらでも参照可能です。

3️⃣ 動作例: パスコンポーネントの置換

受信リクエストの URL パス
/api/users/21334/profile.json
↓
pathPattern: /api/users/(?<id>\d+)/(?<path>[a-z]+\.json) でキャプチャ
↓
pathSubstitution: /users/\g<id>/\g<path> で再構築
↓
バックエンドに送信されるパス
/users/21334/profile.json

📝 URL マップ設定例

公式ドキュメントの設定例です。/region/us-central1/bucket/my-bucket/stage/dev/object.pdf のようなリクエストが /us-central1/my-bucket-dev/object.pdf にリライトされてバックエンドサービスにプロキシされます。

YAML regexRewrite を使った URL マップ設定 
defaultService: projects/example-project/regions/us-central1/backendServices/default-bs
name: regex-rewrite-url-map
pathMatchers:
- name: region-matcher
  defaultService: projects/example-project/regions/us-central1/backendServices/default-bs
  routeRules:
  - matchRules:
    - prefixMatch: /region/
    priority: 1
    service: projects/example-project/regions/us-central1/backendServices/rewrite-bs
    routeAction:
      urlRewrite:
        regexRewrite:
          pathPattern: "/region/(?<reg>[a-z0-9-]+)/bucket/(?<bkt>[a-z0-9-]+)/stage/(?<stg>[a-z0-9-]+)/object\\.pdf"
          pathSubstitution: "/\\g<reg>/\\g<bkt>-\\g<stg>/object.pdf"

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✅ アプリケーション改修の削減: URL 構造の変更やレガシーパスの吸収をロードバランサー側の設定だけで実現でき、バックエンドのコード変更やリリース作業を減らせる
✅ 追加コンポーネント不要: パス変換のためだけに別途プロキシや API ゲートウェイを構築・運用する必要がなくなる

🛠️ 技術面のメリット

✅ 複雑なパス変換に対応: パス途中のセグメント抽出、コンポーネントの結合 (例: \g<bkt>-\g<stg>)、削除、並べ替えを正規表現で宣言的に記述できる
✅ 既存のルートルールと統合: URL マップの routeRules の一部として設定するため、マッチ条件 (matchRules) やバックエンド選択と組み合わせた柔軟なルーティングが可能

🚧 制限事項

❌ Preview 機能であり、Pre-GA Offerings Terms が適用される (サポートが限定される場合がある)
❌ クラシック Application Load Balancer では利用できない
❌ regexRewrite は pathPrefixRewrite や pathTemplateRewrite と同一ルートルール内で併用できない
❌ キャプチャグループは最大 8 個、pathPattern / pathSubstitution は各 250 文字まで。RE2 構文のうち URL マップで許可されるオペレーターには制限がある
⚠️ 考慮すべき点:
  • URL マップでの正規表現マッチングは、メモリ消費とリクエスト処理レイテンシの面でコストが高い。公式ドキュメントでは、正規表現が 1 つの場合で約 100 マイクロ秒/リクエスト、5 つの場合で約 200 マイクロ秒/リクエストのレイテンシ増加が目安として示されている
  • リライト後のパスがバックエンドアプリケーションのルーティングと整合しているか、デプロイ前に十分なテストが必要

💡 ユースケース

🔀 ユースケース 1: 外部公開 API パスと内部パスの分離

シナリオ: 外部向けには /api/users/{id}/profile.json という API パスを公開しつつ、バックエンドサービスは /users/{id}/profile.json という内部パス構造で実装されている。

YAML 実装例 
routeAction:
  urlRewrite:
    regexRewrite:
      pathPattern: "/api/users/(?<id>\\d+)/(?<path>[a-z]+\\.json)"
      pathSubstitution: "/users/\\g<id>/\\g<path>"

効果: 外部公開する URL 構造とバックエンドの実装を疎結合に保ち、バックエンドの変更なしに公開 API パスを維持できる。

🧩 ユースケース 2: パスコンポーネントの結合・並べ替え

シナリオ: /region/{region}/bucket/{bucket}/stage/{stage}/object.pdf のような冗長なパスを受け付け、バックエンドには {bucket}-{stage} のように複数セグメントを結合した短いパス /{region}/{bucket}-{stage}/object.pdf で転送したい。

/region/us-central1/bucket/my-bucket/stage/dev/object.pdf
↓
✂️ regexRewrite で抽出・結合
↓
/us-central1/my-bucket-dev/object.pdf

効果: 従来のプレフィックス置換では不可能だった複数セグメントの抽出・結合・並べ替えを、ロードバランサーの設定のみで実現できる。

🔗 関連サービス・機能

🃏 パステンプレートによるワイルドカードマッチング (pathTemplateRewrite)

ワイルドカード構文と名前付き変数によるパス変換。単純なセグメント単位の変換であればこちらでも対応可能。regexRewrite とは同一ルールで併用不可。

🔍 正規表現マッチャー (regexMatch)

ルートルールの matchRules でパス・ヘッダー・クエリパラメータを正規表現でマッチする機能 (同じく Preview)。マッチ条件とリライトを組み合わせた高度なルーティングが可能。

🕸️ Cloud Service Mesh

URL マップベースの高度なトラフィック管理を共有する関連プロダクト。

🎯 まとめ

Application Load Balancer の URL マップで正規表現によるパスリライトが可能になり、これまでバックエンドや追加プロキシで実装していた複雑な URL 変換をロードバランサー層で完結できるようになりました。まだ Preview のため本番適用は慎重に判断しつつ、正規表現マッチングによるレイテンシ増加とキャプチャグループ数・文字数の制限を考慮した上で、パス変換要件のあるワークロードでの検証を始めることをおすすめします。
