SKU 属性と詳細使用量単位を追加

料金データの BigQuery エクスポートで生成 AI SKU のモデル別・トークン単位分析が可能に
📅 リリース日: 2026-10-21
🏷️ sku_attributes / sku_granular_usage_units

📝 概要

Cloud Billing の料金データ (pricing data) の BigQuery エクスポートに、 SKU 属性 (sku_attributes) と 詳細使用量単位 (sku_granular_usage_units) の 2 つのフィールドが Preview として追加されました。 エクスポートされた料金テーブルから SKU のメタデータを構造化データとして取得できます。

sku_attributes は SKU を説明する key-value ペアで、例えば Key: model_name / Value: gemini_2_5_flash のように、 どの生成 AI モデルに対応する SKU かをプログラムから判別できます。 sku_granular_usage_units は tokens のような SKU の詳細な使用量単位を示します。

🤖 対象は生成 AI SKU: いずれのフィールドも現時点では生成 AI (Generative AI) 関連の SKU に限定されています。 Vertex AI や Gemini API の利用が拡大する中で、モデル別・モダリティ別・トークン種別ごとの単価分析を BigQuery 上で機械的に行いたい FinOps チームやコスト管理担当者に有用なアップデートです。

🔄 Before / After

❌ Before: アップデート前の課題

  • SKU 情報は sku.id と人間可読の sku.description (文字列) が中心で、「どのモデルの SKU か」「入力/出力どちらのトークンか」は説明文の文字列解析に頼る必要があった
  • 使用量単位は pricing_unit (例: GiBy.mo) と pricing_unit_description のみで、生成 AI 特有の「トークン」粒度の単位情報を構造化データとして取得できなかった
  • モデル単位の単価比較やトークン単価の集計など、生成 AI コスト分析のクエリを安定して書くことが難しかった

✅ After: アップデート後の改善

  • sku_attributes の key-value ペア (例: model_name, serving_method, modality, token_type) で SKU の属性をクエリで直接フィルタ・集計できる
  • sku_granular_usage_units により tokens のような詳細な使用量単位を取得できる
  • モデル別 (gemini_2_5_flash)、提供方式別 (batch)、モダリティ別 (text)、トークン種別 (input) といった軸での料金分析が SQL で可能に

Cloud Billing の料金データは毎日 BigQuery にエクスポートされ、新フィールドの sku_attributes と sku_granular_usage_units を使って 生成 AI SKU のモデル別・トークン単位の料金分析が可能になります。

⚡ 主要機能

🏷️ 1. SKU 属性 (sku_attributes)

✓SKU を説明する key-value ペアの構造体 (Struct)
✓Key の例: model_name, serving_method, modality, token_type
✓Value の例: gemini_2_5_flash, batch, text, input
✓生成 AI SKU に限定して提供される
model_name = gemini_2_5_flash serving_method = batch modality = text token_type = input

📏 2. 詳細使用量単位 (sku_granular_usage_units)

✓SKU の詳細な使用量単位を示す文字列 (String) フィールド
✓例: tokens
✓従来の pricing_unit (例: GiBy.mo) より生成 AI の課金実態に即した粒度の単位情報を提供
✓生成 AI SKU に限定して提供される

Bash API 有効化とデータセット作成 
# BigQuery Data Transfer Service API を有効化
gcloud services enable bigquerydatatransfer.googleapis.com --project=BILLING_EXPORT_PROJECT

エクスポート先のデータセットはマルチリージョン (EU / US) またはサポート対象のリージョンロケーションで作成します。

⚙️ ステップ 2: 料金データエクスポートの有効化

Google Cloud コンソールの「お支払い」→「課金データのエクスポート」(Billing export) ページで、 Pricing (料金) エクスポートを有効化し、プロジェクトとデータセットを選択して保存します。

📊 ステップ 3: 新フィールドのクエリ

SQL 生成 AI SKU の属性と詳細使用量単位を確認する例 
-- 生成 AI SKU の属性と詳細使用量単位を確認する例
SELECT
  sku.id AS sku_id,
  sku.description AS sku_description,
  attr.key AS attribute_key,
  attr.value AS attribute_value,
  sku_granular_usage_units
FROM
  `BILLING_EXPORT_PROJECT.billing_export.cloud_pricing_export`,
  UNNEST(sku_attributes) AS attr
WHERE
  attr.key = 'model_name'

エクスポートされた cloud_pricing_export テーブルに対して、sku_attributes を展開して モデル名などの属性でフィルタできます (フィールド形式は Preview のため変更される可能性があります)。

💼 ビジネス面

✓生成 AI コストの可視化: どのモデル (例: Gemini 2.5 Flash) にどのような単価が設定されているかを構造化データで把握でき、FinOps レポートの精度が向上
✓コスト予測の精緻化: トークンなどの詳細使用量単位をもとに、生成 AI ワークロードの単価分析とコスト見積もりがしやすくなる

⚙️ 技術面

✓文字列解析からの脱却: sku.description の文字列パースに依存せず、key-value 属性で安定したクエリを記述できる
✓既存パイプラインへの統合: 既存テーブルにフィールドが追加される形のため、既存の BigQuery 分析基盤やダッシュボードに組み込みやすい

⚠️ デメリット・制約事項

🚫 制限事項

✗Preview 機能であり、sku_attributes および sku_granular_usage_units のフィールド形式とデータは今後変更される可能性がある
✗両フィールドとも対象は生成 AI SKU に限定されている
✗料金データエクスポートは有効化した日以降のデータのみが収集され、過去に遡ってのバックフィルは行われない

🤔 考慮すべき点

→形式変更の可能性があるため、本番のダッシュボードや自動処理に組み込む場合はスキーマ変更への耐性を考慮する
→BigQuery へのエクスポートデータの保存と分析には BigQuery のストレージ料金とクエリ (コンピューティング) 料金が発生する
→料金データエクスポートの有効化には Billing Account Administrator という強い権限が必要なため、権限付与の運用に注意する

🎯 ユースケース

📒 ユースケース 1: Gemini モデル別の単価カタログ作成

シナリオ: 複数の Gemini モデルを利用する組織で、モデルごと・トークン種別 (入力/出力) ごとの単価一覧を自動生成し、社内のコスト見積もりに活用したい。

SQL モデル別・トークン種別の単価カタログ 
SELECT
  MAX(IF(attr.key = 'model_name', attr.value, NULL)) AS model_name,
  MAX(IF(attr.key = 'token_type', attr.value, NULL)) AS token_type,
  sku_granular_usage_units,
  sku.description
FROM
  `BILLING_EXPORT_PROJECT.billing_export.cloud_pricing_export`,
  UNNEST(sku_attributes) AS attr
GROUP BY
  sku.id, sku_granular_usage_units, sku.description
✅ 効果: モデル名やトークン種別を文字列解析なしで取得でき、単価カタログの生成・更新を自動化できる。

🧭 ユースケース 2: FinOps チームによる生成 AI コストガバナンス

シナリオ: FinOps チームが、バッチ処理 (serving_method: batch) とオンライン処理で単価がどう異なるかを分析し、コスト最適化の推奨 (バッチ API への移行など) を行いたい。

✅ 効果: 提供方式やモダリティといった属性軸で単価を比較でき、データに基づいた生成 AI コスト最適化の提案が可能になる。
