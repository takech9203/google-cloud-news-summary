🚀 Apache Beam SDK 2.78.0 サポート開始

BigQuery クォータ attribution / Iceberg AddFiles / Secret Manager による AWS 認証情報管理
📅 リリース日: 2026-11-17

📋 概要

Dataflow が Apache Beam SDK 2.78.0 (Java / Python / Go) をサポートしました。2.78.0 は 2026 年 11 月 17 日にリリースされた最新安定版で、Google Cloud サービスとの連携強化を中心に多数の新機能が追加されています。

3 言語
Java / Python / Go の全 SDK に対応
5+ I/O 強化
BigQuery / Iceberg / Firestore / Splunk / Debezium
Python 3.11+
Python 3.10 サポートは削除

特に注目すべきは次の 3 点です。マルチクラウド構成やデータレイクハウス (Iceberg) 構成で Dataflow を利用するユーザーにとって、運用面・セキュリティ面の改善が大きいリリースです。

1️⃣全 SDK で BigQuery API のクォータ・課金を任意のプロジェクトに付け替えられる attribution 機能
2️⃣Managed I/O における Apache Iceberg の AddFiles サポート (Java / Python) と Java での複数テーブルへの動的ファイル登録
3️⃣Python パイプラインでの AWS 認証情報の Secret Manager 解決
❌ Before (アップデート前の課題)
  • BigQuery API のクォータ消費・課金が実行プロジェクトまたはデータ所在プロジェクトに紐付き、別プロジェクトへ付け替える手段がなかった
  • Iceberg テーブルへ既存データファイルを登録する AddFiles 操作が Managed I/O で利用できず、複数テーブルへの登録は個別の変換が必要
  • Java FirestoreIO は 500/50/5 ルールの書き込みランプアップスロットリングが常に有効で、プロビジョニング済み環境でも初期スループットが抑制
  • Beam YAML から Splunk への書き込みを直接定義できなかった
  • DebeziumIO の readAsJson() では op や MySQL file/pos、PostgreSQL lsn/txId などのメタデータを取得不可
  • Python から AWS サービス接続時、認証情報をプレーンテキストのオプションとして渡す必要があった
✅ After (アップデート後の改善)
  • Java (--bigQueryQuotaProjectId)、Python (quota_project_id)、Go (bigqueryio.WithQuotaProject) でクォータ・課金プロジェクトを指定可能
  • ICEBERG_ADD_FILES で Iceberg へのファイル登録が可能。Java では path_pattern の glob と {name} プレースホルダーで複数テーブルへ動的登録
  • withRampupThrottlingDisabled() で FirestoreIO の書き込みランプアップをオプトアウト可能
  • Beam YAML に WriteToSplunk が追加され、YAML 定義だけで Splunk 書き込みを構築
  • DebeziumIO でフルメタデータフラグを有効にすると op と残りの source フィールドを取得可能
  • --aws_credentials_secret_manager で AWS 認証情報を Secret Manager のシークレットとして解決

Beam SDK 2.78.0 で強化された I/O コネクタと新機能のマップです。3 言語の SDK から Dataflow パイプラインを構築し、BigQuery・Iceberg・Firestore・Splunk・Debezium との連携が改善され、Python では AWS 認証情報を Secret Manager から解決できます。

⭐ 主要機能

1️⃣ BigQuery API のクォータ・課金プロジェクト attribution (Java / Python / Go)

→BigQuery API 呼び出しのクォータ消費と課金を、任意の Google Cloud プロジェクトに帰属させることが可能
→Python: ReadFromBigQuery の quota_project_id パラメータ。WriteToBigQuery はファイルロードとストリーミング挿入に対応 (Storage Write API は Java バックエンドのため未対応)
→Java: --bigQueryQuotaProjectId パイプラインオプション / Go: bigqueryio.WithQuotaProject

2️⃣ Managed I/O: Apache Iceberg AddFiles (Java / Python)

→Managed.ICEBERG_ADD_FILES により、既存データファイルを書き直さずに Iceberg テーブルのメタデータに登録可能
→Java では path_pattern の glob と {name} プレースホルダーにより、1 つの変換で複数テーブルへ動的にファイルを登録 (競合テーブルは個別に拒否、他テーブルへの登録は継続)
⚠️注意: Java の Iceberg AddFiles はコーダー変更のため、ストリーミングパイプラインの更新互換性に影響あり

3️⃣ FirestoreIO の書き込みランプアップスロットリング オプトアウト (Java)

→RpcQosOptions.Builder.withRampupThrottlingDisabled() で 500/50/5 ルールに基づくランプアップを無効化可能
→DatastoreIO と同等の挙動が FirestoreIO でも選択可能に

4️⃣ SplunkIO の Beam YAML サポートと DebeziumIO のメタデータ強化

→Beam YAML に WriteToSplunk (SchemaTransform) が追加され、YAML 定義でパイプラインを記述可能
→SplunkIO の書き込みエラーがステータスコード・メッセージ・ペイロードを保持するよう修正
→DebeziumIO の readAsJson() にフルメタデータフラグ (デフォルト無効) が追加され、op や source の残りフィールド (MySQL file/pos、PostgreSQL lsn/txId など) を取得可能

5️⃣ AWS 認証情報の Secret Manager 解決 (Python)

→新しい --aws_credentials_secret_manager オプションで、AWS 認証情報をプレーンテキストではなくシークレット仕様として解決
→AwsSecret による AWS Secrets Manager サポートと、全 AWS クライアントのデフォルトを設定する AwsOptions (--aws_*) も追加

📝 その他の変更点 (Beam 2.78.0)

✓Flink ランナーのソースメトリクス転送が最大 1 秒 1 回に抑制され、読み取り時の CPU オーバーヘッドを削減
✓Java の GcsUtil がデフォルトで java-storage クライアント (V2) を使用 (--experiments=disable_gcsutil_v2 で旧動作に戻せる)
✓全 SDK に --dataflow_container_base_repository オプションが追加され、カスタムコンテナイメージリポジトリを指定可能
💥 破壊的変更: JmsIO が jakarta.jms (JMS 3.1) へ移行 (Java 17 必須)、Beam SQL の Data Catalog テーブルプロバイダ削除、Python の GCS ステージングバケット所有権チェックの厳格化など
🗑️ 非推奨/削除: Python 3.10 サポート削除、Twister2 ランナー削除

⚖️ メリットと制約事項

💼 メリット (ビジネス面)

✓コスト帰属の明確化: BigQuery API のクォータ・課金を任意のプロジェクトに付け替えられるため、チーム・部門単位のコスト配賦やチャージバックが容易に
✓レイクハウス移行の加速: Iceberg AddFiles により既存ファイルを書き直さずテーブルに取り込めるため、移行時の処理コストと時間を削減

🛠️ メリット (技術面)

✓セキュリティ向上: Python パイプラインの AWS 認証情報を Secret Manager で管理でき、プレーンテキストでの受け渡しを排除
✓I/O の柔軟性向上: Firestore 書き込みのランプアップ制御、Beam YAML からの Splunk 書き込み、Debezium の CDC メタデータ取得など、コネクタの制御粒度が向上

🚧 制限事項

✗Python の BigQuery クォータプロジェクト指定は Storage Write API (Java バックエンド) には未対応
✗DebeziumIO のフルメタデータはデフォルト無効で、明示的なフラグ指定が必要
✗Java の Iceberg AddFiles のコーダー変更および Go の int16/uint16 行コーダー変更は、ストリーミングパイプラインの更新 (update) 互換性に影響

🤔 考慮すべき点

⚠️Python 3.10 サポートが削除されたため、実行環境の Python バージョン確認が必要
⚠️JmsIO 利用者は jakarta.jms への移行と Java 17 ランタイムが必要
⚠️Beam SQL の Data Catalog テーブルプロバイダは削除済み (GCP Data Catalog の廃止に伴う)
⚠️FirestoreIO のランプアップ無効化は、Firestore 側のキャパシティを超えた書き込みスパイクを招く可能性があるため、プロビジョニング状況を確認のうえ利用する

🎯 ユースケース

💰 ユースケース 1: マルチプロジェクト環境での BigQuery コスト配賦

シナリオ: データ基盤チームが共有データプロジェクトの BigQuery テーブルを読み取るパイプラインを複数の利用部門向けに運用しており、API クォータと課金を利用部門ごとのプロジェクトに帰属させたい。

Python 実装例 
ReadFromBigQuery(
    table="shared-data:warehouse.sales",
    quota_project_id="dept-a-billing",
)

効果: 部門ごとのクォータ分離とコスト可視化が実現し、共有プロジェクトのクォータ枯渇を防止できる。

🧊 ユースケース 2: 既存 Parquet ファイル群の Iceberg レイクハウスへの登録

シナリオ: Cloud Storage 上に蓄積された既存の Parquet ファイルを、再書き込みせずに複数の Iceberg テーブルへ登録してレイクハウスを構築したい。

効果: Java の ICEBERG_ADD_FILES と path_pattern の {name} プレースホルダーにより、1 つの変換でテーブル別にファイルを動的登録でき、データコピーのコストと時間を削減できる。

🔐 ユースケース 3: Secret Manager による S3 連携パイプラインの認証情報管理

シナリオ: AWS S3 からデータを取り込む Python パイプラインで、アクセスキーをパイプラインオプションに直接記述せず安全に管理したい。

効果: --aws_credentials_secret_manager により認証情報が Secret Manager で一元管理され、ジョブメタデータやログへの認証情報露出リスクを低減できる。
