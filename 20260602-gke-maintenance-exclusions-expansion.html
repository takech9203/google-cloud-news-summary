🎛️ GKE メンテナンス除外機能の拡張

Google Kubernetes Engine GA Maintenance Exclusions
2026-06-02

📋 概要

GKE のメンテナンス除外機能が大幅に拡張された。ノードプール単位のメンテナンス除外がリリースチャネルに登録されたクラスタで利用可能になり、「No upgrades」スコープの最大期間が 90 日に延長された。

これにより、リリースチャネルの恩恵を受けながら、従来 No channel 構成でしか実現できなかったきめ細かなアップグレード制御が可能になる。

❌ Before

  • ノードプール単位の自動アップグレード無効化には No channel 構成が必要
  • No channel では加速パッチ、ロールアウトシーケンシング、Autopilot が利用不可
  • 「No upgrades」除外の最大期間に制約あり
  • ノードプールごとの柔軟なアップグレード戦略が困難

✅ After

  • リリースチャネル登録のまま、ノードプール単位でメンテナンス除外を設定可能
  • 「No upgrades」除外が最大 90 日まで設定可能
  • リリースチャネルの全機能を活用しながら個別制御が可能
  • No channel からリリースチャネルへの移行が容易に

⚡ 主要機能

📦 ノードプール単位のメンテナンス除外

→リリースチャネルに登録されたクラスタで利用可能
→個別ノードプールに対して自動アップグレードを無効化
→除外の終了時刻はクラスタのマイナーバージョンの End of Support 日を自動追跡
→End of Support 到達時、GKE は必須の自動アップグレード実行後に除外を再アクティブ化

📅 「No upgrades」除外期間の延長

→最大 90 日まで設定可能に (推奨は 30 日以内)
→コントロールプレーンとノードの両方のアップグレードを完全停止
→大規模イベント期間中の変更凍結や長期バージョン検証に対応

🔗 リリースチャネルとの統合強化

→加速パッチアップグレード、ロールアウトシーケンシング、長期サポート (Extended) との併用が可能
→No channel からリリースチャネルへの移行パスが明確化

⚙️ 設定方法

💡 前提条件: GKE クラスタがリリースチャネル (Rapid/Regular/Stable/Extended) に登録済み、Standard モードのクラスタであること、gcloud CLI が最新バージョンであること。

Step 1: ノードプールメンテナンス除外の設定 (新規作成時)

Bash 新規ノードプール作成時に除外を設定 
gcloud container node-pools create POOL_NAME \
    --cluster CLUSTER_NAME \
    --location=CONTROL_PLANE_LOCATION \
    --add-maintenance-exclusion-until-end-of-support

Step 2: 既存ノードプールへのメンテナンス除外追加

Bash 既存ノードプールに除外を追加 
gcloud container node-pools update POOL_NAME \
    --cluster CLUSTER_NAME \
    --location=CONTROL_PLANE_LOCATION \
    --add-maintenance-exclusion-until-end-of-support

Step 3: クラスタレベルの「No upgrades」除外設定 (最大 90 日)

Bash クラスタレベルの除外 (90日間) 
gcloud container clusters update CLUSTER_NAME \
    --add-maintenance-exclusion-name "extended-freeze" \
    --add-maintenance-exclusion-start 2026-06-01T00:00:00Z \
    --add-maintenance-exclusion-end 2026-08-30T00:00:00Z \
    --add-maintenance-exclusion-scope no_upgrades

Step 4: ノードプールメンテナンス除外の削除

Bash 除外の削除 
gcloud container node-pools update POOL_NAME \
    --cluster CLUSTER_NAME \
    --location=CONTROL_PLANE_LOCATION \
    --remove-maintenance-exclusion-until-end-of-support

⚖️ メリット・デメリット

✅ ビジネス面のメリット

💼運用の柔軟性向上: クリティカルなワークロードのノードプールのみ制御し、その他は自動アップグレードの恩恵を享受
🎯大規模イベント対応: ブラックフライデーや年末商戦など最大 90 日間の変更凍結が可能
💰移行コスト削減: No channel からリリースチャネルへの移行が容易に

✅ 技術面のメリット

🔧きめ細かな制御: ノードプール単位でアップグレード戦略を分離し、異なる SLA 要件に対応
🔒セキュリティと安定性の両立: 加速パッチを一部で活用しつつ他は手動管理
🤖End of Support 自動追跡: 除外終了時刻が自動的に追跡され手動管理不要

⚠️ 制限事項・考慮点

  • Autopilot クラスタでは利用不可 (GKE がノードを管理するため)
  • ノードプールあたり 1 つの除外のみ設定可能
  • 将来の開始日時を指定できない (即時開始のみ)
  • ノードバージョンアップグレードのみを防止 (セキュリティパッチ等は防止しない)
  • 90 日間の No upgrades 使用時、重要なセキュリティパッチ適用が遅延する可能性 (推奨は 30 日以内)
  • 長期除外後、End of Support 到達時に複数バージョンアップグレードが連続実行される可能性
  • バージョンスキューポリシーの遵守はユーザー責任
  • End of Support 到達時は除外に関係なく必須アップグレードが実行される

💡 ユースケース

🛒 ユースケース 1: 大規模 EC サイトのピーク期間対応

シナリオ: ブラックフライデーからサイバーマンデーを含む年末商戦期間 (約 60 日間) 中のクラスタ変更を完全に凍結したい。

Bash 年末商戦期間中のメンテナンス除外 (60日間) 
gcloud container clusters update production-cluster \
    --add-maintenance-exclusion-name "holiday-freeze-2026" \
    --add-maintenance-exclusion-start 2026-11-01T00:00:00Z \
    --add-maintenance-exclusion-end 2026-12-31T23:59:59Z \
    --add-maintenance-exclusion-scope no_upgrades

効果: ピーク期間中の予期しないクラスタ変更によるサービス影響を排除。

🔄 ユースケース 2: 段階的アップグレード戦略

シナリオ: テスト用ノードプールは自動アップグレードを許可し、本番ワークロード用ノードプールは手動管理したい。

Bash 本番用ノードプールにメンテナンス除外を設定 
# 本番用ノードプールにメンテナンス除外を設定
gcloud container node-pools update production-pool \
    --cluster my-cluster \
    --location=us-central1 \
    --add-maintenance-exclusion-until-end-of-support

# テスト用ノードプールはそのまま (自動アップグレード有効)
# staging-pool は何も設定しない

効果: テスト用で新バージョン確認後、本番を手動アップグレードする段階的戦略を実現。

🚀 ユースケース 3: No channel からリリースチャネルへの移行

シナリオ: 従来 No channel 構成でノードプールの自動アップグレードを無効化していたクラスタをリリースチャネルに移行。

Bash リリースチャネルへの移行手順 
# 1. クラスタをリリースチャネルに登録
gcloud container clusters update my-cluster \
    --release-channel regular

# 2. 手動管理が必要なノードプールにメンテナンス除外を設定
gcloud container node-pools update critical-pool \
    --cluster my-cluster \
    --location=us-central1 \
    --add-maintenance-exclusion-until-end-of-support

効果: リリースチャネルの追加機能を活用しながら、従来と同等のアップグレード制御を維持。

🔗 関連サービス・機能

メンテナンス除外の全機能を利用するために必要。Rapid/Regular/Stable/Extended の各チャネルで利用可能。

⏰ GKE メンテナンスウィンドウ

メンテナンス除外と組み合わせて、自動メンテナンスの実行タイミングを制御。

🔄 GKE ロールアウトシーケンシング

リリースチャネル登録クラスタで利用可能。複数クラスタ間のアップグレード順序を制御。

📊 Cloud Monitoring

クラスタのバージョン状態やアップグレードイベントの監視。

📏 GKE バージョンスキューポリシー

コントロールプレーンとノード間のバージョン差を管理。メンテナンス除外使用時は手動で遵守が必要。

📝 まとめ

今回の GKE メンテナンス除外機能の拡張は、クラスタのアップグレード管理における柔軟性を大幅に向上させるアップデートである。特に、ノードプール単位のメンテナンス除外により、No channel 構成を選択する必要性がほぼなくなり、リリースチャネルの全機能を活用しながらきめ細かなアップグレード制御が可能になった。

GKE クラスタを運用するすべてのチームは、現在の No channel 構成をリリースチャネルへ移行することを検討すべきである。
