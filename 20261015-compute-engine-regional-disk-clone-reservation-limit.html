💾 Compute Engine アップデート

ゾーンブートディスクのクローンによるリージョナルディスク作成 /
予約キャパシティ上限エラー RESERVATION_CAPACITY_LIMIT_EXCEEDED の導入
Compute Engine Preview (リージョナルディスククローン) Change (予約上限エラー)
📅 リリース日: 2026-10-15

📝 概要

2026 年 10 月 15 日、Compute Engine に 2 つのアップデートが発表されました。

1️⃣ ゾーンブートディスクのリージョナルクローン (Preview)

ゾーンブートディスクをクローンしてリージョナルディスク (Hyperdisk Balanced High Availability 含む) を直接作成可能に。スナップショットを経由せず、既存ゾーンワークロードを 2 ゾーンレプリケーションの HA 構成へ簡単に移行できます。ゾーンの Hyperdisk Balanced / Extreme をクローンすると、Hyperdisk Balanced High Availability ボリュームとして作成されます。

2️⃣ 新エラー RESERVATION_CAPACITY_LIMIT_EXCEEDED の導入 (Change)

オンデマンド予約の作成や既存予約のインスタンス数増加時に、ゾーンのマシンファミリー予約キャパシティ上限に達している場合、HTTP 429 とともに明確なエラー理由コードが返るようになり、自動化処理のエラーハンドリングやトラブルシューティングが容易になりました。

❌ Before: アップデート前の課題

  • ゾーンブートディスクのリージョナル化はスナップショット経由の複数ステップが必要
  • ディスククローンによるリージョナルディスク作成はデータディスクのみ対応
  • 予約キャパシティ上限超過に専用のエラー理由コードがなかった

✅ After: アップデート後の改善

  • 1 回のクローン操作でブートディスクをリージョナルディスクへ複製 (Preview)
  • ゾーンワークロードの HA 化がシンプルに
  • RESERVATION_CAPACITY_LIMIT_EXCEEDED (HTTP 429) で対処判断が明確に (別マシンファミリー / 別ゾーン選択)

ゾーンブートディスクを直接クローンすることで、同一リージョン内の 2 ゾーン (ソースディスクのゾーン + 指定した 2 つ目のゾーン) にレプリカを持つリージョナルディスクを作成できます。ゾーンの Hyperdisk Balanced / Extreme がソースの場合、クローンは Hyperdisk Balanced High Availability ボリュームになります。

⚙️ 主要機能

🔁 ゾーンブートディスクのリージョナルクローン (Preview)
✓ゾーンのブートディスク / データディスクをクローンして新しいリージョナルディスクを作成
✓対応ソース: Hyperdisk Balanced、Hyperdisk Extreme (イメージ由来を除く)、Standard / Balanced / SSD Persistent Disk
✓ソースが Hyperdisk Balanced / Extreme の場合、クローンは常に Hyperdisk Balanced High Availability となる (プロビジョニング済みパフォーマンスは引き継がれない)
✓サイズやプロビジョニング済みパフォーマンスの指定は gcloud CLI / REST のみ (コンソール不可)
⏱️ リージョナルクローンの可用性特性
✓作成後、平均 3 分以内に使用可能
✓完全レプリケーション (RPO ほぼゼロ) までは数十分かかる場合がある
✓プレウォーミング不要、作成直後からフルパフォーマンス (データディスクの場合)
🚨 RESERVATION_CAPACITY_LIMIT_EXCEEDED エラーの導入 (Change)
✓オンデマンド予約の作成 / 予約インスタンス数増加時、ゾーンのマシンファミリー予約キャパシティ上限到達でリクエストが失敗
✓HTTP ステータスコードは 429。別のマシンファミリーまたはゾーンの選択が推奨される
Text エラーメッセージ例 
Failed to reserve additional capacity for '{machine_family}'
because reservation capacity limit exceeded in '{zone}'.
Select a different machine family or zone.

🔬 技術仕様

📋 リージョナルクローンのサポート状況 (クローンタイプ別)

クローンタイプ 用途 サポートされるディスクタイプ
ゾーンディスク → ゾーンクローン スケールアウト、テスト環境複製、マルウェアスキャン、プロジェクト間移動 Standard / Balanced / SSD PD、Hyperdisk 全タイプ (Hyperdisk Balanced High Availability を除く)
ゾーンディスク → リージョナルクローン ゾーンワークロードの HA 化、リージョナルブートディスクの作成 Preview Standard / Balanced / SSD PD、Hyperdisk Extreme、Hyperdisk Balanced
リージョナルディスク → リージョナルクローン HA ワークロードのテスト・スケールアウト リージョナル PD (Standard / Balanced / SSD)、Hyperdisk Balanced High Availability

⚠️ 主な制限事項とレート制限

項目詳細
レプリカゾーンリージョナルクローンのレプリカゾーンの 1 つは、ソースディスクのゾーンと一致する必要がある
イメージ由来のブートディスクイメージから作成されたゾーンブートディスクのリージョナルクローンは、スナップショット経由の作成と同程度の時間がかかる
レート制限 (イメージ由来のブートディスク)60 分間に最大 6 個のリージョナルクローン (ソースディスクのスナップショット作成数と共有)。超過後は 10 分ごとに 1 個
レート制限 (容量)ゾーンディスクからのリージョナルクローンは 15 分ごとに最大 1 TiB (バースト上限 257 TiB)
暗号化CMEK / CSEK で暗号化されたソースディスクのクローンには同じ鍵が必要
非対応タイプHyperdisk ML / Hyperdisk Throughput はリージョナルクローン不可 (スナップショット経由で Hyperdisk Balanced High Availability を作成する)

🚨 RESERVATION_CAPACITY_LIMIT_EXCEEDED エラー

項目詳細
エラー理由コードRESERVATION_CAPACITY_LIMIT_EXCEEDED
HTTP ステータスコード429
発生条件オンデマンド予約の作成または予約インスタンス数の増加時に、ゾーンがリクエストしたマシンファミリーの予約キャパシティ上限に達している場合
推奨対処別のマシンファミリーまたは別のゾーンを選択する

🛠️ 設定方法

✅ 前提条件

✓ソースのゾーンディスクがサポート対象タイプ (Hyperdisk Balanced、Hyperdisk Extreme、Standard / Balanced / SSD PD) であること
✓リージョナルクローンのレプリカゾーンの 1 つがソースディスクのゾーンと一致すること
✓サイズやプロビジョニング済みパフォーマンスを指定する場合は gcloud CLI または REST を使用すること

ステップ 1: ゾーンブートディスクからリージョナルクローンを作成する (gcloud)

Bash リージョナルクローンの作成 
gcloud compute disks create TARGET_DISK_NAME \
    --region=REGION \
    --replica-zones=SOURCE_ZONE,SECOND_ZONE \
    --source-disk=SOURCE_DISK_NAME \
    --source-disk-zone=SOURCE_ZONE
💡 ポイント: レプリカゾーンの 1 つ (SOURCE_ZONE) はソースディスクのゾーンと一致させる必要があります。ソースが Hyperdisk Balanced / Extreme の場合、作成されるディスクは Hyperdisk Balanced High Availability となります。

👍 メリット

💼 ビジネス面
✓HA 移行の迅速化: ゾーン障害に備えたリージョナルディスクへの移行が 1 回のクローン操作で完結し、DR / HA 対応のリードタイムを短縮
✓運用の予見性向上: 予約作成失敗の原因が RESERVATION_CAPACITY_LIMIT_EXCEEDED として明示され、キャパシティ計画の判断材料が明確に
🔧 技術面
✓スナップショット経由の手順が不要に: ブートディスクを直接リージョナルクローンでき、中間リソースの管理が減る
✓自動化のエラーハンドリング改善: HTTP 429 + 明確な理由コードにより、IaC / スクリプトでのリトライ・フォールバック (別ゾーン / 別マシンファミリー切り替え) を実装しやすい

⚠️ デメリット・制約事項

🚧 制限事項
✗ゾーンブートディスクのリージョナルクローンは Preview であり、Pre-GA 利用規約が適用され、サポートが限定される場合がある
✗イメージから作成されたブートディスクのクローンは遅く、レート制限 (60 分で 6 個、スナップショットと共有) がある
✗ソースが Hyperdisk Balanced / Extreme の場合、クローンはプロビジョニング済みパフォーマンスを引き継がないため、必要に応じて明示的に指定が必要 (パフォーマンス指定時はサイズ指定も必須)
✗Hyperdisk ML / Hyperdisk Throughput ボリュームはリージョナルクローン非対応
🤔 考慮すべき点
  • リージョナルクローンは作成後約 3 分で使用可能になるが、RPO がほぼゼロになるまで数十分かかる場合があるため、切り替えタイミングに注意
  • クローン作成中はソースディスクが接続されたインスタンスを起動できないなど、クローン全般の制約が適用される
  • 予約を自動作成するワークフローでは、RESERVATION_CAPACITY_LIMIT_EXCEEDED (429) を想定したエラーハンドリング (別ゾーン / 別マシンファミリーへのフォールバック) の追加を検討

🎯 ユースケース

🏢 ユースケース 1: 既存ゾーンワークロードの HA 化

シナリオ: 単一ゾーンで稼働中の重要な VM (Hyperdisk Balanced ブートディスク) を、ゾーン障害に耐えられる構成に移行したい。

Bash ゾーンブートディスクをリージョナル (Hyperdisk Balanced High Availability) にクローン 
# ゾーンブートディスクをリージョナル (Hyperdisk Balanced High Availability) にクローン
gcloud compute disks create my-boot-disk-regional \
    --region=asia-northeast1 \
    --replica-zones=asia-northeast1-a,asia-northeast1-b \
    --source-disk=my-boot-disk \
    --source-disk-zone=asia-northeast1-a

✨ 効果: スナップショットの作成・管理を介さずにリージョナルブートディスクを取得でき、片方のゾーンで障害が発生しても他方のレプリカからデータにアクセスできる。

🤖 ユースケース 2: 予約自動化における上限エラーのハンドリング

シナリオ: バッチ基盤のスケール時にオンデマンド予約を自動作成しているが、特定ゾーンのマシンファミリーで予約キャパシティ上限に達することがある。

✨ 効果: RESERVATION_CAPACITY_LIMIT_EXCEEDED (HTTP 429) を検知して、別ゾーンや別マシンファミリーでの予約作成に自動フォールバックするロジックを実装でき、キャパシティ確保の成功率を高められる。
