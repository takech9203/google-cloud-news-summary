Iceberg テーブルの行レベル/列レベルセキュリティが GA

✅ GA (一般提供) BigQuery (Lakehouse) Apache Iceberg データガバナンス
📅 リリース日: 2026-11-18
☁️ Google Cloud アップデート

📌 概要

Lakehouse ランタイムカタログ内の Apache Iceberg テーブルに対して、BigQuery の 行レベルセキュリティ (RLS) と、動的データマスキングを含む 列レベルセキュリティ (CLS) が GA になりました。 ポリシーは GoogleSQL の DDL で管理でき、オープンフォーマットの Iceberg テーブルにも BigQuery ネイティブテーブルと同じ きめ細かいアクセス制御 (FGAC) を適用できます。

重要なのは credential vending (認証情報ベンディング) モードとの統合です。 Iceberg REST カタログエンドポイントは、全保護列へのマスクなしアクセス権 + (行レベルポリシーがある場合) フィルタなしの行アクセス権 を持つプリンシパルにのみストレージ認証情報を発行するため、Spark や Trino など外部エンジンの Cloud Storage 直接アクセス経路からの ポリシー迂回を防止できます。

あわせて INFORMATION_SCHEMA.ROW_ACCESS_POLICIES ビューも GA になり、データセットまたはリージョン全体の 行レベルアクセスポリシーとフィルタ述語を SQL で一括監査できるようになりました。

❌ Before: アップデート前の課題

  • Iceberg REST カタログエンドポイント管理のテーブルは FGAC 非対応で、テーブル単位・バケット単位のアクセス制御しかできなかった
  • 機密列や特定行の保護には、ビューの乱立やデータの物理分割など回避策の設計・運用が必要だった
  • ポリシーの棚卸しは bq ls --row_access_policies などテーブル単位の確認が中心で、横断的な SQL 監査手段が GA 未提供だった

✅ After: アップデート後の改善

  • Iceberg テーブルに BigQuery と同じ行レベル/列レベルセキュリティ (動的マスキング含む) を GoogleSQL DDL で適用可能に
  • credential vending により、フルアクセス権を持つプリンシパルにのみ認証情報を発行し、外部エンジン経由のポリシー迂回を防止
  • INFORMATION_SCHEMA.ROW_ACCESS_POLICIES でリージョン/データセット全体のポリシーを SQL で監査可能に

📝 ポリシー管理の DDL 例

SQL 行レベルアクセスポリシーの作成・削除 
-- Iceberg テーブルに行レベルアクセスポリシーを作成
CREATE ROW ACCESS POLICY sales_region_filter
ON my_project.my_dataset.iceberg_sales
GRANT TO ("group:apac-sales@example.com")
FILTER USING (region = "APAC");

-- 行レベルアクセスポリシーの削除
DROP ROW ACCESS POLICY sales_region_filter
ON my_project.my_dataset.iceberg_sales;

-- すべての行レベルアクセスポリシーの削除
DROP ALL ROW ACCESS POLICIES ON my_project.my_dataset.iceberg_sales;

🛠️ 設定方法

✅ 前提条件

  • Lakehouse ランタイムカタログと Apache Iceberg REST カタログエンドポイントが構成済みであること
  • ポリシー迂回を防ぐには、カタログエンドポイントを credential vending モードで構成すること (自動プロビジョニングされたカタログエンドポイントサービスアカウントに、対象バケットの roles/storage.objectUser を付与)
  • 行レベルアクセスポリシーの管理には bigquery.rowAccessPolicies.* 権限 (例: roles/bigquery.admin または roles/bigquery.dataOwner) が必要
1

credential vending モードのカタログを確認

Bash カタログエンドポイントのサービスアカウントを確認 
# カタログエンドポイントのサービスアカウントを確認
gcloud biglake iceberg catalogs describe CATALOG_ID \
  --project=PROJECT_ID \
  --format='value(biglake-service-account)'

credential vending モードのカタログでは、このサービスアカウントに対象 Cloud Storage バケットの roles/storage.objectUser が必要です。

2

Iceberg テーブルに行レベルアクセスポリシーを作成

SQL 行レベルアクセスポリシーの作成 
CREATE ROW ACCESS POLICY apac_only
ON my_project.my_dataset.iceberg_sales
GRANT TO ("group:apac-analysts@example.com")
FILTER USING (region = "APAC");
3

列レベルセキュリティ (ポリシータグ) とマスキングを適用

機密列にポリシータグを付与し、データポリシーでマスキングルール (ハッシュ、NULL 化など) を設定します。アクセス権のないユーザーのクエリ結果では、対象列がマスクされた値で返却されます。

4

ポリシーの監査

SQL リージョン全体のポリシーを棚卸し 
SELECT table_name, row_access_policy_name, filter_predicate
FROM `region-us`.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES
ORDER BY table_name;

💪 メリット

💼 ビジネス面

✓オープンレイクハウスでのコンプライアンス対応: Iceberg テーブルのまま、個人情報保護や地域別アクセス制限などの規制要件 (GDPR など) に対応したきめ細かいアクセス制御を実現
✓ガバナンスの一元化: BigQuery と外部エンジン (Spark / Trino) に一貫したポリシーを適用でき、エンジンごとのアクセス制御の重複実装が不要に
✓監査の効率化: INFORMATION_SCHEMA ビューで全ポリシーを SQL で棚卸しでき、監査対応の工数を削減

⚙️ 技術面

✓ポリシー迂回の防止: credential vending により、ストレージ直接アクセス経路でも行/列ポリシーが実質的に強制される (フルアクセス権がないプリンシパルには認証情報が発行されない)
✓DDL ベースの宣言的管理: GoogleSQL DDL で管理できるため、Terraform や CI/CD と組み合わせた Infrastructure as Code 運用が容易
✓ビュー乱立の解消: 行フィルタや列マスキング目的の認可ビューを大量に作成・維持する必要がなくなる

⚠️ デメリット・制約事項

🚫 制限事項

✗credential vending は Apache Iceberg REST カタログエンドポイントのみサポート。Apache Hive カタログエンドポイントでは利用不可
✗Iceberg REST カタログエンドポイントは Iceberg V2 テーブル (GA) / V3 テーブル (Preview) をサポート。V1 テーブルは非対応
✗行レベルセキュリティには BigQuery 共通の制約が適用 (レガシー SQL 非対応、JSON 列へのポリシー適用不可、ワイルドカードテーブル非対応、テーブルプレビュー/サンプリング非互換など)
✗データマスキングはサブクエリを含まない行アクセスポリシーとのみ互換

🤔 考慮すべき点

⚠️credential vending モードでは、保護テーブルへの外部エンジンからのストレージ直接アクセスはフルアクセス権を持つプリンシパルのみ。既存パイプライン (サービスアカウント) の権限設計の見直しが必要
⚠️DML やテーブルコピーなど全行アクセスを要する操作には TRUE フィルタ (全行アクセス許可) の付与が必要
⚠️VPC Service Controls 境界内のバケットを使用する場合、カタログエンドポイントのサービスアカウント (blirc-...@gcp-sa-biglakerestcatalog.iam.gserviceaccount.com) に対する ingress ルールの構成が必要

🎯 ユースケース

🌏 ユースケース 1: マルチエンジン環境での地域別データアクセス制御

シナリオ: グローバル企業が売上データを Iceberg テーブルとして Cloud Storage に保持し、BigQuery で BI 分析、Spark で ML パイプラインを実行。各地域の担当者には自地域のデータのみを見せたい。

SQL 実装例 
CREATE ROW ACCESS POLICY apac_sales_filter
ON lakehouse_project.sales_ds.iceberg_sales
GRANT TO ("group:apac-team@example.com")
FILTER USING (sales_region = "APAC");
✅ 効果: BigQuery 経由のクエリでは行フィルタが適用され、credential vending により Spark からのストレージ直接アクセスもフルアクセス権を持つパイプライン用サービスアカウントに限定。地域別のテーブル分割やビュー運用が不要に。

🏦 ユースケース 2: 機密列のマスキングと定期的なポリシー監査

シナリオ: 金融機関が顧客データを含む Iceberg テーブルを運用。アナリストには口座番号などの機密列をマスクして提供しつつ、監査部門は適用中のポリシーを四半期ごとに棚卸ししたい。

SQL 実装例 
SELECT table_catalog, table_schema, table_name,
       row_access_policy_name, filter_predicate
FROM `region-us`.INFORMATION_SCHEMA.ROW_ACCESS_POLICIES;
✅ 効果: 機密列はポリシータグと動的マスキングで保護され、監査部門は SQL 一発でリージョン全体のポリシーとフィルタ述語を確認可能。手動でのテーブル単位の確認作業が不要に。

📝 まとめ

Lakehouse ランタイムカタログの Iceberg テーブルに BigQuery の行レベル/列レベルセキュリティが GA となり、 credential vending との連動によって外部エンジン経由のポリシー迂回も防げるようになったことで、 オープンフォーマットのレイクハウスでもエンタープライズレベルのデータガバナンスが実現できます。

Iceberg テーブルを Spark や Trino と併用している環境では、以下の対応を推奨します。

  • カタログエンドポイントの credential vending モード化
  • パイプライン用サービスアカウントの権限 (TRUE フィルタ等) の見直し
  • INFORMATION_SCHEMA.ROW_ACCESS_POLICIES による定期的なポリシー監査の運用への組み込み
