🖼️ Gemini 画像生成モデルの
Cloud Storage 直接出力が GA

Direct Cloud Storage output persistence — base64 デコード & 再アップロードはもう不要
📅 リリース日: 2026-10-26

📝 概要

Gemini 画像生成モデルの生成画像を Cloud Storage バケットに直接書き込む機能が一般提供 (GA) になりました。 generateContent / streamGenerateContent リクエストで outputConfig.outputUriPrefix と generationConfig.responseFormat[].image.delivery: "URI" を設定すると、 生成・編集された画像がインラインの base64 バイト列ではなく指定バケットに直接書き込まれ、レスポンスにはオブジェクト URI (fileData.fileUri) が返されます。

🤖 対象モデル (4 モデル): gemini-nano-banana-2.1 / gemini-3.1-flash-image / gemini-3.1-flash-lite-image / gemini-3-pro-image

❌ Before (アップデート前の課題)

  • 生成画像はレスポンス内にインラインの base64 エンコードされたバイト列 (inlineData) として返され、レスポンスサイズが肥大化
  • 保存にはクライアント側で base64 をデコードし、Cloud Storage などへ別途アップロード処理を実装する必要があった

✅ After (アップデート後の改善)

  • リクエスト設定だけで、生成画像がサービス側から Cloud Storage へ直接書き込み
  • レスポンスは fileData.fileUri の URI のみ。デコード・アップロード処理が不要に
  • 出力オブジェクトはバケットの暗号化設定 (CMEK 含む) とライフサイクルルールを継承し、既存ガバナンスをそのまま適用可能

画像の新規生成だけでなく画像編集にも対応。保存・配信・後続処理パイプラインを構築する開発者の手間を大きく削減します。

クライアントが Cloud Storage 出力を指定してリクエストを送ると、サービスが生成画像をバケットへ直接書き込み、レスポンスにはインラインバイトの代わりにオブジェクト URI が返されます。

⚡ 主要機能

🪣 1. Cloud Storage への直接出力

  • outputConfig.outputUriPrefix に出力先 (例: gs://BUCKET_NAME/PREFIX/) を指定
  • generationConfig.responseFormat[].image.delivery を "URI" に設定
  • 生成画像は gs://BUCKET_NAME/PREFIX/image_{GENERATION_ID}.{EXTENSION} の命名パターンで書き込み (複数候補時は CANDIDATE_INDEX、1 候補に複数画像時は IMAGE_INDEX を付加)

📄 2. テキスト・画像混在レスポンスへの対応

  • TEXT と IMAGE の混在レスポンスでは、テキストパートは従来どおり parts[].text にインラインで返却
  • 生成画像パートのみが Cloud Storage に書き込まれ、parts[].fileData オブジェクトとして返却

💭 3. Thinking 画像・ストリーミングへの対応

  • thinkingConfig.includeThoughts: true の場合、中間の思考画像 (parts[].thought: true) も thought_image_{GENERATION_ID} プレフィックスで書き込み
  • streamGenerateContent では、各画像の書き込み完了後に fileData.fileUri を参照するレスポンスチャンクを送信

🎨 4. 画像編集にも対応

  • 新規生成だけでなく、generateContent / streamGenerateContent による画像編集の出力も同じ設定で Cloud Storage に直接保存可能

📤 リクエスト例 (REST)

Bash generateContent で Cloud Storage 出力を指定 
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://aiplatform.googleapis.com/v1/projects/PROJECT_ID/locations/global/publishers/google/models/gemini-nano-banana-2.1:generateContent" \
  -d '{
    "contents": [
      {
        "role": "USER",
        "parts": [
          { "text": "Create an architectural rendering of a sustainable glass greenhouse in alpine snow." }
        ]
      }
    ],
    "generationConfig": {
      "responseModalities": ["TEXT", "IMAGE"],
      "responseFormat": [
        { "image": { "delivery": "URI" } }
      ]
    },
    "outputConfig": {
      "outputUriPrefix": "gs://BUCKET_NAME/PREFIX/"
    }
  }'

🛠️ 設定方法

✅ 前提条件

✓リクエストを認証するプリンシパルが、出力先バケットに対する storage.objects.create 権限 (roles/storage.objectCreator などに含まれる) を持っていること
✓出力先の Cloud Storage バケットが存在すること
⚠️ フェイルファスト設計: サービスは画像生成前に、呼び出し元の認証情報で対象バケットへの storage.objects.create 権限を検証します。バケットが存在しない場合、書き込み権限がない場合、または VPC Service Controls の境界により書き込みがブロックされる場合は、生成前に 403 PERMISSION_DENIED エラーでリクエストが失敗します。

Bash Storage Object Creator ロールの付与

gcloud storage buckets add-iam-policy-binding gs://BUCKET_NAME \

ステップ 2: Cloud Storage 出力を指定してリクエストを送信

generateContent または streamGenerateContent リクエストで、outputConfig.outputUriPrefix と generationConfig.responseFormat[].image.delivery: "URI" の両方を設定します (上記リクエスト例を参照)。

💡 メリット

💼 ビジネス面

✓パイプライン構築の簡素化: 保存処理をサービス側に任せられ、画像生成ワークロードの開発・運用コストを削減
✓ガバナンスの一元化: 出力オブジェクトがバケットの CMEK 暗号化設定とライフサイクルルールを継承し、既存のデータガバナンスポリシーをそのまま適用可能

⚙️ 技術面

✓レスポンスの軽量化: base64 バイト列の代わりに URI が返され、レスポンスサイズを削減
✓クライアント実装の削減: base64 デコードと Cloud Storage へのアップロード処理が不要に
✓ストリーミング対応: 各画像の書き込み完了後に URI を含むチャンクが届き、ストリーミング処理と組み合わせ可能
✓フェイルファスト設計: 権限不足やバケット不存在は生成前に 403 エラーで検出され、無駄な生成処理が発生しない

⚠️ デメリット・制約事項

🚫 制限事項

✗対象は上記 4 つの Gemini 画像生成モデルに限られる
✗テキストのみのレスポンスや、セーフティフィルタによりブロックされたリクエストでは、Cloud Storage にオブジェクトは書き込まれない
✗混在レスポンスのテキストパートは引き続きインラインで返される (書き込まれるのは画像パートのみ)

🤔 考慮すべき点

→出力先バケットへの storage.objects.create 権限の付与が事前に必要
→VPC Service Controls の境界が書き込みをブロックすると、リクエスト自体が 403 PERMISSION_DENIED で失敗
→thinkingConfig.includeThoughts: true では中間の思考画像もバケットに書き込まれるため、オブジェクト数とストレージ使用量が増加する点に留意

🎯 ユースケース

🌐 ユースケース 1: 画像生成 Web サービスの配信パイプライン

シナリオ: ユーザーのプロンプトから画像を生成し、CDN 経由で配信する Web サービス。従来はアプリケーションサーバーが base64 をデコードして Cloud Storage にアップロードしていた。

JSON 実装例: リクエスト設定の抜粋 
{
  "generationConfig": {
    "responseModalities": ["TEXT", "IMAGE"],
    "responseFormat": [{ "image": { "delivery": "URI" } }]
  },
  "outputConfig": { "outputUriPrefix": "gs://my-app-images/generated/" }
}

効果: アプリケーションサーバーは返された fileData.fileUri をメタデータとして保存するだけでよく、画像バイトの中継処理が不要になり、サーバーのメモリ・帯域の負荷を削減できる。

🔐 ユースケース 2: CMEK とライフサイクル管理による生成画像のガバナンス

シナリオ: コンプライアンス要件により、生成コンテンツを顧客管理暗号鍵 (CMEK) で暗号化し、一定期間後に自動削除したい企業。

効果: 出力オブジェクトは出力先バケットの CMEK 設定を継承し、バケットのライフサイクル管理ルールに従うため、Cloud Storage 側の設定だけで暗号化と保持期間のポリシーを一元管理できる。

🔗 関連サービス・機能

🪣 Cloud Storage: 生成画像の出力先。オブジェクトはバケットの暗号化設定 (CMEK 含む) とライフサイクル管理ルールを継承する
🔑 IAM: 出力先バケットへの書き込みには storage.objects.create 権限 (roles/storage.objectCreator など) が必要
🛡️ VPC Service Controls: 境界によりバケットへの書き込みがブロックされる場合、リクエストは生成前に失敗する
🔐 Cloud KMS (CMEK): 出力先バケットに CMEK を設定している場合、生成画像も顧客管理鍵で暗号化される

📌 まとめ

Gemini 画像生成モデルの出力を Cloud Storage へ直接永続化できる機能が GA となり、base64 デコードと再アップロードという定型処理が不要になりました。

画像生成パイプラインを運用しているチームは、outputConfig.outputUriPrefix と delivery: "URI" の設定への移行を検討し、出力先バケットの IAM 権限・CMEK・ライフサイクルルールを事前に整備することを推奨します。
