Compute Engine: リージョナル MIG の代替ゾーン VM 修復

Compute Engine GA
2026-07-21

📋 概要

リージョナル マネージド インスタンス グループ (MIG) において、VM を元のゾーンで修復できない場合に代替ゾーンで自動修復する機能が一般提供 (GA) としてリリースされました。ゾーン障害時やリソース不足時でもアプリケーションの可用性を維持できます。

従来、MIG 内の VM が障害を起こした場合は元のゾーンでのみ修復を試みていましたが、本機能を有効にすると、キャパシティとクォータに基づいて代替ゾーンを自動選択し VM を再作成します。GPU や大容量メモリ VM、Spot VM など需要の高いリソースに特に有効です。

Before / After 比較

❌ Before (従来)

  • 元のゾーンでのみ修復を試行
  • ゾーン障害時に修復が完了しない
  • GPU 等の需要の高いリソースで修復が長時間停滞
  • 手動での別ゾーンへの移行が必要

✅ After (新機能)

  • 代替ゾーンを自動選択して修復
  • ゾーン障害時の可用性が向上
  • インテリジェントなゾーン選択でリソース確保率向上
  • 手動介入なしで自動復旧

⚡ 主要機能

🌐 代替ゾーンでの自動 VM 修復

→元のゾーンで VM を修復できない場合、MIG が自動的に他の選択済みゾーンで VM を再作成
→ゾーン選択はキャパシティとクォータに基づいてインテリジェントに実行
→VM の URL はゾーン情報を含むため、ゾーン変更時に URL が変更される

🔗 Update on Repair との連携

→代替ゾーン修復を有効にする場合、update on repair (修復時更新) の有効化が必須
→修復時に最新のインスタンステンプレートとインスタンスごとの構成が適用される

📐 柔軟なターゲット分散シェイプとの統合

→BALANCED: リソース可用性を優先しつつ、可能な限り均等に分散
→ANY: リソース取得を最大限に優先し、リザベーション活用も最適化

🔧 技術仕様

項目 詳細
対象 MIG タイプ リージョナル MIG のみ (ゾーナル MIG は対象外)
対応分散シェイプ BALANCED, ANY
非対応分散シェイプ EVEN, ANY_SINGLE_ZONE
ステートフル MIG 非対応 (ステートフル構成を持つ MIG では利用不可)
必須設定 update on repair (forceUpdateOnRepair) の有効化
instance redistribution NONE に設定する必要あり (BALANCED シェイプの場合)

REST API 設定

JSON 
{
  "instanceLifecyclePolicy": {
    "onRepair": {
      "allowChangingZone": "YES"
    },
    "forceUpdateOnRepair": "YES"
  }
}

⚙️ 設定方法

💡 前提条件:
  • リージョナル MIG が作成済みであること (または新規作成すること)
  • ターゲット分散シェイプが BALANCED または ANY であること
  • ステートフル構成を使用していないこと

既存の MIG に代替ゾーン修復を有効化

Bash 
gcloud compute instance-groups managed update MIG_NAME \
  --on-repair-allow-changing-zone=YES \
  --force-update-on-repair \
  --region=REGION

新規 MIG の作成時に代替ゾーン修復を有効化

Bash 
gcloud compute instance-groups managed create MIG_NAME \
  --template=INSTANCE_TEMPLATE_URL \
  --size=SIZE \
  --zones=ZONES \
  --target-distribution-shape=SHAPE \
  --instance-redistribution-type=none \
  --on-repair-allow-changing-zone=YES \
  --force-update-on-repair

Terraform での設定

HCL 
resource "google_compute_region_instance_group_manager" "default" {
  name               = "example-rmig"
  base_instance_name = "example-rmig-instance"
  region             = "us-central1"
  target_size        = 3

  distribution_policy_target_shape = "BALANCED"

  version {
    instance_template = google_compute_instance_template.default.id
  }

  instance_lifecycle_policy {
    default_action_on_failure = "REPAIR"
    force_update_on_repair    = "YES"
    on_repair {
      allow_changing_zone = "YES"
    }
  }

  update_policy {
    instance_redistribution_type = "NONE"
    type                         = "OPPORTUNISTIC"
    minimal_action               = "REPLACE"
    max_surge_fixed              = 0
    max_unavailable_fixed        = 6
  }
}

⚠️ 制約事項・考慮点

制限事項
✗EVEN および ANY_SINGLE_ZONE のターゲット分散シェイプでは利用不可
✗ステートフル MIG (ステートフル構成を持つ MIG) では利用不可
✗update on repair の有効化が必須 (修復時にテンプレートが更新される)
✗VM のゾーン変更に伴い VM の URL が変更される

考慮すべき点

→VM の URL を直接参照しているシステムがある場合は影響を受ける可能性がある
→代替ゾーンへの修復によりゾーン間の VM 分散が偏る可能性がある
→instance redistribution を NONE に設定するため、プロアクティブな再分散は行われない
→ステートフルディスクや IP アドレスを持つワークロードでは別途高可用性設計が必要

🎯 ユースケース

🖥️ GPU ワークロードの高可用性確保

AI/ML トレーニングジョブで GPU 付き VM を使用するリージョナル MIG を運用。特定のゾーンで GPU キャパシティが逼迫した場合にもワークロードを継続したい。

効果: GPU リソースが利用可能なゾーンへ自動的に VM が移行されるため、ハードウェア不足によるワークロード停止を回避
Bash 
gcloud compute instance-groups managed create ml-training-mig \
  --template=gpu-instance-template \
  --size=8 \
  --zones=us-central1-a,us-central1-b,us-central1-c \
  --target-distribution-shape=any \
  --instance-redistribution-type=none \
  --on-repair-allow-changing-zone=YES \
  --force-update-on-repair

💰 Spot VM を使用するバッチ処理の耐障害性向上

コスト最適化のために Spot VM でバッチ処理を実行。Spot VM はプリエンプトされる可能性があり、特定ゾーンのキャパシティが不足する場合がある。

効果: Spot VM がプリエンプトされた後の再作成時に、代替ゾーンで VM が復旧するためバッチ処理の完了率が向上

🌐 ゾーン障害に対するサービスの自動復旧

Web アプリケーションをリージョナル MIG で運用しており、ゾーン障害発生時にも自動的にサービスを復旧させたい。

効果: ゾーン障害が発生しても、MIG が自動的に正常なゾーンで VM を再作成し、手動介入なしでサービスが復旧

💲 料金

本機能自体に追加料金は発生しません。通常の Compute Engine VM の料金が適用されます。代替ゾーンで修復された VM も、そのゾーンの通常の VM 料金で課金されます。

📝 まとめ

リージョナル MIG の代替ゾーン VM 修復機能の GA により、ゾーン障害やリソース不足時における VM の自動復旧が実現しました。特に GPU ワークロードや Spot VM を利用する環境では、リソース取得性の向上が大きなメリットとなります。

導入推奨: 既存のリージョナル MIG に対しても --on-repair-allow-changing-zone=YES フラグの追加のみで有効化できるため、高可用性が求められるワークロードでは積極的な導入を推奨します。
