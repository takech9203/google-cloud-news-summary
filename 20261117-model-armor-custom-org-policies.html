🛡️ Model Armor: FloorSetting リソースに対する
カスタム組織ポリシーが GA

AI 保護のベースラインを組織レベルで技術的に強制 — フロア設定の緩和・無効化を API レベルでブロック

📋 概要

Model Armor の FloorSetting (フロア設定) リソースに対して、カスタム組織ポリシーを適用できる機能が GA になりました。 Responsible AI フィルタやプロンプトインジェクション・ジェイルブレイク検出などの必須フィルタの有効化を、組織レベルで強制できます。

組織ポリシー管理者は Common Expression Language (CEL) で記述したカスタム制約を modelarmor.googleapis.com/FloorSetting および modelarmor.googleapis.com/Template リソースの CREATE / UPDATE 操作に適用し、ポリシーに準拠しない変更を API レベルで拒否できます。

🎯 主な対象ユーザー: AI ガバナンスやコンプライアンス要件を持つ大規模組織のセキュリティ管理者・プラットフォームチーム。分散した各プロジェクトチームに AI 活用の自由度を与えつつ、組織全体のセキュリティ基準からの逸脱をプログラマティックに防止できます。

❌ Before (アップデート前の課題)

  • フロア設定自体の更新を組織レベルで強制する仕組みがなく、権限を持つ管理者がフィルタを無効化・緩和する変更を防げなかった
  • Responsible AI やプロンプトインジェクション検出の有効化は、運用ルールやレビューといった人手のプロセスに依存
  • 組み込みのマネージド制約では、フィルタ構成のフィールド単位の細かな制御ができなかった

✅ After (アップデート後の改善)

  • FloorSetting 更新時に必須フィルタの有効化を API レベルで強制可能に
  • CEL 条件式で resource.filterConfig 配下のフィールド単位の細かな制御 (有効/無効、信頼度レベル、SDP テンプレートなど) が可能に
  • 組織・フォルダ・プロジェクトの各階層で適用でき、違反操作は FAILED_PRECONDITION エラーで自動的に拒否

組織ポリシー管理者が定義したカスタム制約が、FloorSetting の作成・更新操作をセキュリティ境界で検証し、必須フィルタが無効化された構成変更をブロックします。準拠した FloorSetting が配下のテンプレートの最低保護レベルを保証し、生成 AI アプリケーションを保護します。

⭐ 主要機能

1️⃣ FloorSetting リソースへのカスタム制約 (GA)

modelarmor.googleapis.com/FloorSetting リソースの CREATE / UPDATE 操作に CEL 条件式による制約を適用可能。 フロア設定の強制有効化 (resource.enableFloorSettingEnforcement == true) や、Gemini Enterprise Agent Platform 向けフロア設定での Cloud Logging 有効化などを強制できます。

2️⃣ フィルタ構成のフィールド単位の制御

プロンプトインジェクション・ジェイルブレイクフィルタの有効化と信頼度レベル (piAndJailbreakFilterSettings)、 Responsible AI フィルタの種類と信頼度レベル (raiSettings.raiFilters)、 Sensitive Data Protection の基本/高度構成 (sdpSettings)、悪意のある URI フィルタ、多言語検出などを細かく制御できます。

3️⃣ 階層的なポリシー適用と継承

組織・フォルダ・プロジェクトレベルでポリシーを適用でき、デフォルトで配下リソースに継承されます。 dry-run モードと Policy Simulator により、本番適用前に影響範囲をテスト可能です。

📝 カスタム制約の定義例 (フロア設定の強制有効化)

YAML constraint.yaml — フロア設定の強制有効化を要求 
name: organizations/ORGANIZATION_ID/customConstraints/custom.requireFloorSettingEnforcement
resourceTypes:
- modelarmor.googleapis.com/FloorSetting
methodTypes:
- CREATE
- UPDATE
condition: "resource.enableFloorSettingEnforcement == true"
actionType: ALLOW
displayName: Require floor settings enforcement
description: Requires that floor settings enforcement is enabled for all floor setting configurations.

⚙️ 設定方法

✅ 前提条件

✓組織 ID を把握していること
✓組織ポリシーの管理: 組織リソースに対する Organization Policy Administrator (roles/orgpolicy.policyAdmin) ロール
✓フロア設定の更新: プロジェクト・フォルダ・組織リソースに対する Model Armor Admin (roles/modelarmor.admin) ロール
1

カスタム制約を定義して適用する

CEL 条件式で FloorSetting の必須フィールドを検証するカスタム制約を組織に登録します。

Bash カスタム制約の適用と確認 
# constraint.yaml を作成後、制約を適用
gcloud org-policies set-custom-constraint constraint.yaml

# 制約が作成されたことを確認
gcloud org-policies list-custom-constraints --organization=ORGANIZATION_ID
2

制約を参照する組織ポリシーを適用する

Bash dry-run 検証から本番適用まで 
# policy.yaml の例:
# name: projects/PROJECT_ID/policies/custom.requireFloorSettingEnforcement
# spec:
#   rules:
#   - enforce: true

# dry-run モードで事前検証 (推奨)
gcloud org-policies set-policy policy.yaml --update-mask=dryRunSpec

# 問題なければ本番適用
gcloud org-policies set-policy policy.yaml --update-mask=spec
💡 ポイント: ポリシーの反映には最大 15 分程度かかります。適用後、制約に違反する FloorSetting の更新操作は HTTP 412 (FAILED_PRECONDITION) エラーで拒否されます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

  • AI ガバナンスの強制力向上: 組織標準を運用ルールではなく技術的な制御として強制でき、コンプライアンス監査への対応が容易に
  • 分散チームの自律性と統制の両立: 各チームに管理を委譲しつつ、セキュリティベースラインを下回る変更を自動防止

🔧 技術面のメリット

  • フィールド単位の細かな制御: CEL で信頼度レベルや SDP テンプレート指定まで制御可能
  • 安全な導入プロセス: dry-run モードと Policy Simulator で事前検証
  • 階層的な継承: 組織で一度定義すれば配下に自動継承、個別設定の手間と漏れを削減

🚧 制限事項

  • methodTypes は CREATE / UPDATE のみ対象。既存リソースには次回更新時まで適用されない
  • 多くのリソースタイプで 1 リソースタイプあたり最大 20 個のカスタム制約という上限
  • CEL 条件式は最大 1,500 文字、制約 ID は最大 70 文字 (custom. プレフィックス除く)
  • カスタム制約にはバージョニングがなく、更新は既存制約の上書き

⚠️ 考慮すべき点

  • ポリシー反映に数分〜最大 15 分程度かかるため、適用直後の動作確認はタイミングに注意
  • actionType: ALLOW は条件を満たす操作のみ許可 (条件外はすべて拒否)。条件式の設計ミスで意図しない操作まで拒否される可能性 → dry-run での事前検証を推奨
  • フロア設定の UI はプロジェクトレベルのみ。組織・フォルダレベルの管理には API が必要

💡 ユースケース

🔐 ユースケース 1: 全社的なプロンプトインジェクション対策の強制

シナリオ: 複数の事業部がそれぞれのプロジェクトで生成 AI アプリケーションを開発している企業で、セキュリティチームはすべてのプロジェクトでプロンプトインジェクション・ジェイルブレイク検出が常に有効であることを保証したい。

YAML テンプレートにフィルタ有効化を要求するカスタム制約 
name: organizations/ORGANIZATION_ID/customConstraints/custom.requirePiAndJailbreakFilter
resourceTypes:
- modelarmor.googleapis.com/Template
methodTypes:
- CREATE
- UPDATE
condition: "has(resource.filterConfig.piAndJailbreakFilterSettings.filterEnforcement) && resource.filterConfig.piAndJailbreakFilterSettings.filterEnforcement == 'ENABLED'"
actionType: ALLOW
displayName: Require prompt injection and jailbreak filter
description: All templates must have the prompt injection and jailbreak filter enabled.

✅ 効果: フィルタを無効化したテンプレートの作成・更新が API レベルで拒否され、全プロジェクトでプロンプトインジェクション対策が維持される。

🏦 ユースケース 2: フロア設定の無効化・緩和の防止

シナリオ: 規制業界の企業が、Model Armor のフロア設定による保護を組織全体のベースラインとして運用している。権限を持つプロジェクト管理者による意図的・偶発的なフロア設定の無効化を防ぎたい。

✅ 効果: resource.enableFloorSettingEnforcement == true を要求するカスタム制約により、フロア設定の強制を無効化する更新が拒否され、保護レベルの後退 (ポリシーリグレッション) を防止できる。

📝 まとめ

FloorSetting リソースに対するカスタム組織ポリシーの GA により、Model Armor による AI 保護のベースラインそのものを組織レベルで技術的に強制できるようになり、AI ガバナンスの「最後の抜け穴」であったフロア設定の緩和・無効化を防止できます。 生成 AI を全社展開している組織は、まず dry-run モードで必須フィルタ (Responsible AI、プロンプトインジェクション・ジェイルブレイク検出) を要求するカスタム制約を検証し、段階的に本番適用することを推奨します。
