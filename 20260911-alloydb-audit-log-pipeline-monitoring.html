pgAudit パイプラインのステータス・スループット・バックログを Cloud Monitoring で可視化
リリース日
2026-09-11

📌 概要

AlloyDB for PostgreSQL のインスタンス・ノードで、監査ログ (pgAudit) パイプラインのステータス、スループット、バックログを Cloud Monitoring でモニタリングできるようになりました。 alloydb.googleapis.com/InstanceNode リソースに 3 つの新メトリクスが追加され、Metrics Explorer から確認できます。

AlloyDB は監査ログを非同期のマネージドパイプラインで処理し、ノードのローカルストレージに一時バッファリングした後、Cloud Logging へ安全に転送します。高パフォーマンスなロギングを実現する一方、ログ生成レートが取り込み容量を超えるとバックプレッシャーが発生する可能性があり、今回のアップデートでその健全性を定量的に把握できるようになりました。

💡 なぜ重要か: pgAudit で政府機関・金融・ISO 認証などのコンプライアンス要件を満たしている組織にとって、監査ログの欠落や遅延は重大なリスクです。本機能はそのリスクを早期に検知するための可観測性を提供します。

❌ Before: アップデート前の課題

✗非同期処理のため、Cloud Logging への反映遅延の程度を把握する手段がない
✗バックプレッシャーの発生を確認できず、ディスク枯渇による再起動・クラッシュや監査証跡の欠落を予測困難
✗Cloud Logging への実効スループットを定量的に確認できない

✅ After: アップデート後の改善

✓backlog_bytes_count で処理待ちバックログを監視し、バックプレッシャーを早期検知
✓processed_bytes_count / processed_entries_count で転送スループットを定量把握
✓アラートポリシーと組み合わせて遅延・ディスク枯渇リスクをプロアクティブに検知

pgAudit が生成した監査レコードはノード上のローカルバッファに一時保存され、非同期パイプラインで Cloud Logging に転送されます。今回追加された 3 つのメトリクスにより、このパイプラインのバックログとスループットを Cloud Monitoring で監視し、バックプレッシャーをアラートで検知できます。

⭐ 主要機能: 3 つの新メトリクス

📦 監査ログバックログサイズの監視GAUGE / Bytes

backlog_bytes_count

→ノード上で処理・Cloud Logging へのアップロード待ちの監査ログバックログサイズ (バイト) を提供
→値が持続的に高い・増加し続けている場合は、パイプラインにバックプレッシャーが発生しているサイン

📤 処理済み監査ログバイト数の監視DELTA / Bytes

processed_bytes_count

→Cloud Logging へ正常に処理・転送された監査ログの合計バイト数
→パイプラインの実効スループットをバイト単位で把握できる

🔢 処理済み監査ログエントリ数の監視DELTA / Count

processed_entries_count

→Cloud Logging へ正常に処理・転送された監査ログエントリの合計数
→ワークロードごとの監査ログ生成量の傾向分析に活用できる

🔧 技術仕様

📋 新規メトリクス一覧

モニタリング対象リソース: alloydb.googleapis.com/InstanceNode

メトリクス名 (node/database/logging/audit/ 配下)表示名種別 / 値型単位説明
backlog_bytes_count Audit log backlog size GAUGE / INT64 Bytes (By) 処理・アップロード待ちの監査ログバックログサイズ。持続的な高値・増加はバックプレッシャーを示す
processed_bytes_count Processed audit log bytes DELTA / INT64 Bytes (By) Cloud Logging へ正常に転送された監査ログの合計バイト数
processed_entries_count Processed audit log entries DELTA / INT64 Count (1) Cloud Logging へ正常に転送された監査ログエントリの合計数

🛠️ 設定方法

✅ 前提条件

✓AlloyDB インスタンスで pgAudit 拡張が有効化・構成されていること
✓監査ログの閲覧: プロジェクトで Data Access 監査ログが有効 + roles/logging.privateLogViewer ロール
✓メトリクスの閲覧: Cloud Monitoring へのアクセス権 (例: roles/monitoring.viewer)

📝 手順

  1. Metrics Explorer でメトリクスを確認
    Text Metrics Explorer での確認 
    Google Cloud コンソール → Monitoring → Metrics Explorer
リソースタイプ: AlloyDB InstanceNode (alloydb.googleapis.com/InstanceNode)
メトリクス: node/database/logging/audit/backlog_bytes_count など

    対象リソースとメトリクスを選択し、ノードごとのバックログサイズやスループットを可視化します。

  2. バックログ増加に対するアラートポリシーを作成
    Bash gcloud によるアラートポリシー作成例 
    # 例: バックログサイズに対するアラートポリシーの作成 (gcloud)
gcloud alpha monitoring policies create \
  --display-name="AlloyDB Audit Log Backlog Alert" \
  --condition-display-name="Audit log backlog sustained high" \
  --condition-filter='resource.type="alloydb.googleapis.com/InstanceNode" AND metric.type="alloydb.googleapis.com/node/database/logging/audit/backlog_bytes_count"' \
  --condition-threshold-value=1073741824 \
  --condition-threshold-comparison=COMPARISON_GT \
  --condition-threshold-duration=600s \
  --notification-channels=CHANNEL_ID

    バックログサイズが一定値 (例: 1 GiB) を 10 分以上超過した場合に通知するアラートを設定し、バックプレッシャーを早期に検知します。しきい値はワークロードのログ生成量に応じて調整してください。

💪 メリット

💼 ビジネス面

✓コンプライアンスリスクの低減: 監査証跡の欠落・遅延の予兆を早期検知でき、政府機関・金融・ISO 認証などの監査要件への準拠を維持しやすい
✓障害の未然防止: ローカルディスク枯渇によるインスタンスの再起動・クラッシュをバックログ監視で事前に回避

⚙️ 技術面

✓可観測性の向上: ブラックボックスだった監査ログ転送パイプラインの内部状態 (バックログ・スループット) を定量的に把握
✓標準ツールとの統合: Metrics Explorer、ダッシュボード、アラートポリシーなど既存の運用ツールをそのまま活用可能
✓ノード単位の粒度: InstanceNode リソースへのメトリクスのため、プライマリ・リードプールなどノード単位で状態を把握できる

⚠️ デメリット・制約事項

🚧 制限事項
  • 監査レコードの作成・処理は引き続き非同期であり、Cloud Logging への反映遅延自体がなくなるわけではない (遅延の程度を可視化する機能である)
  • 最大ログ取り込みレート 90 MiB/秒、単一監査レコード最大 1 MB という制約は変わらない
🤔 考慮すべき点
  • バックプレッシャー検知後の根本対応 (pgAudit の記録対象の絞り込み、ワークロードの見直しなど) は利用者側で実施する必要がある
  • pgAudit の設定によっては監査ログ生成量が大きくなり、ローカルディスクの一時領域を消費する点に引き続き注意

🎯 ユースケース

🏦 ユースケース 1: 金融システムにおける監査証跡の完全性監視

シナリオ: 金融機関が AlloyDB 上の勘定系データベースに pgAudit を適用し、すべての READ/WRITE 操作を記録。監査証跡の欠落は規制違反につながるため、パイプラインの健全性を常時監視したい。

実装例:

Text 監視フロー 
1. Metrics Explorer で backlog_bytes_count のダッシュボードを作成
2. バックログが 10 分間しきい値を超えた場合のアラートポリシーを設定
3. アラート発報時は pgaudit.log の記録対象を確認し、ログ生成レートを調整
✅ 効果: バックプレッシャーの持続による監査証跡の欠落・インスタンス障害を未然に防ぎ、規制対応の信頼性を高める。

🔍 ユースケース 2: 監査ログ遅延を考慮したセキュリティ調査

シナリオ: セキュリティチームが Cloud Logging 上の pgAudit ログを SIEM に連携してリアルタイム分析を実施。非同期パイプラインの遅延により、イベント検知が遅れる可能性がある。

✅ 効果: backlog_bytes_count の監視により現在の転送遅延の程度を推定でき、SIEM 側の検知ロジックやインシデント調査時のタイムラインの解釈精度が向上する。

📝 まとめ

AlloyDB の監査ログパイプラインの内部状態が Cloud Monitoring のメトリクスとして公開され、バックログ・スループットの可視化とアラート設定が可能になりました。

pgAudit をコンプライアンス目的で利用している場合、監査証跡の欠落やディスク枯渇による障害を未然に防ぐため、backlog_bytes_count に対するアラートポリシーの設定を推奨します。
