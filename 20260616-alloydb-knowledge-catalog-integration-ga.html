📋 概要

AlloyDB for PostgreSQL と Knowledge Catalog (旧 Dataplex Catalog) の統合機能が一般提供 (GA) となりました。AlloyDB のメタデータが Knowledge Catalog に自動的に同期され、データガバナンスと分析のための統一的なメタデータビューが提供されます。

クラスタ、インスタンス、データベース、スキーマ、テーブル、ビュー、カラムといった階層的なリソースのメタデータが、ほぼリアルタイム (5分以内) で Knowledge Catalog に反映されます。主キーや外部キーなどの拡張メタデータ詳細も含まれます。

🎯 対象ユーザー: 大規模なデータ基盤を運用する組織のデータエンジニア、データスチュワード、Solutions Architect

🔄 Before / After 比較

❌ Before

  • 直接 DB 接続して情報スキーマを参照する必要があった
  • 組織全体でのデータアセットの可視性が低かった
  • PII ラベリングや変更追跡が手動で煩雑
  • Preview 段階ではメタデータ同期が数時間おき

✅ After

  • 新規クラスタでデフォルト有効、追加設定不要
  • ほぼリアルタイム (5分以内) でメタデータ同期
  • 主キー・外部キー等の拡張メタデータを自動取得
  • キーワード検索・自然言語検索でデータ発見可能
  • アスペクト機能で PII ラベル等のガバナンス強化

⚡ 主要機能

🔄
ほぼリアルタイムのメタデータ同期
2026/4/3 以降のクラスタでは 5 分以内に反映。Pub/Sub トピックを通じたイベント駆動型同期。抽出プロセス自体は通常数秒で完了。
🔑
拡張メタデータの自動取得
主キー、外部キー (参照テーブル・カラムマッピング含む)、データ型、文字セット、コレーション、作成日時等を自動収集。
📂
階層的リソースナビゲーション
Cluster > Instance > Database > Schema > Table/View > Column の階層構造でメタデータを表示・検索・依存関係を可視化。
🏷️
メタデータエンリッチメント
カスタムアスペクトタイプを作成し、PII ラベリング、データ品質スコア等のビジネスメタデータを付加。アスペクトによる検索も可能。
🔍
キーワード検索
system=AlloyDB AND type=Database のような構造化クエリで AlloyDB アセットを横断的に検索可能。
💬
自然言語検索 (Preview)
「売上に関連する AlloyDB テーブルを表示」のような日常言語でデータアセットを発見可能。

⚙️ 設定方法

💡 前提条件: Dataplex API がプロジェクトで有効化されていること / 適切な IAM ロールが付与されていること / AlloyDB のプライマリクラスタであること (セカンダリクラスタは非サポート)

ステップ 1: 統合の有効化 (既存クラスタの場合)

新規クラスタではデフォルトで有効です。2026年2月26日以前に作成されたクラスタでは手動有効化が必要です。

Bash 
# gcloud CLI で有効化
gcloud alloydb clusters update CLUSTER_ID \
  --region=REGION \
  --enable-dataplex-integration

ステップ 2: 統合状態の確認

Bash 
# クラスタの dataplexConfig を確認
gcloud alloydb clusters describe CLUSTER_ID --region=REGION
# 出力に dataplexConfig: enabled: true が含まれていれば有効

ステップ 3: Knowledge Catalog での検索

Google Cloud コンソールの Knowledge Catalog 検索ページから AlloyDB アセットを検索できます。

Search Query 
# キーワード検索の例
system=AlloyDB AND type=Database
system=AlloyDB AND type=Table

# PII ラベル付きアセット検索
aspect:pii AND system=AlloyDB

ステップ 4: アスペクトによるメタデータエンリッチメント (オプション)

カスタムアスペクトタイプを作成し、AlloyDB アセットにビジネスメタデータ (PII ラベル等) を付加します。

🎯 ユースケース

🏦 ユースケース 1: PII データのガバナンス管理
シナリオ: 金融機関が AlloyDB 上の顧客データベースに含まれる PII カラム (氏名、メールアドレス、口座番号等) を特定し、適切なアクセス制御とデータ保護ポリシーを適用したい。

効果: 組織全体の PII データの所在を可視化し、GDPR や個人情報保護法への準拠を効率的に管理できる。
🔗 ユースケース 2: マイクロサービス間のデータ依存関係分析
シナリオ: 複数のマイクロサービスが AlloyDB の異なるデータベースを使用しており、スキーマ変更前にダウンストリームへの影響を把握したい。

効果: 外部キー情報と階層構造の可視化により、テーブル間の依存関係を一元的に確認でき、安全なスキーマ変更計画を立案できる。
🔎 ユースケース 3: データ分析チームのセルフサービスデータ発見
シナリオ: データアナリストが分析に必要なデータセットを、DBA に問い合わせることなく自分で発見したい。

効果: 自然言語検索とアスペクトによるビジネスメタデータにより、技術的な知識がなくても必要なデータを発見・理解できる。

⚠️ 制約事項・考慮点

制限事項:
  • DB あたり最大 100 万テーブル、テーブルあたり平均 150 カラム。超過時はメタデータ抽出されない
  • セカンダリクラスタ (クロスリージョンレプリケーション用) は DB/Schema/Table/View メタデータ統合非サポート
  • 初回同期には最大 48 時間かかる場合あり
  • 高頻度のメタデータ変更 (100 DDL/秒以上) 時は同期が最大 30 分間一時停止する可能性あり
  • ネットワーク障害時は最大 48 時間以内に反映

考慮すべき点

  • メタデータ抽出は AlloyDB クラスタの CPU リソースを消費 (小規模マシンで大規模スキーマの場合、最大 5% 程度の CPU 増加)
  • 2026/2/26〜4/3 に作成されたクラスタは「数時間ごと」の同期。リアルタイム同期にはサポートへの連絡が必要
  • インスタンスが存在しない/停止中の場合、メタデータ削除に最大 7 日かかる
