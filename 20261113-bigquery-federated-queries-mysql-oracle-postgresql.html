🔍 BigQuery: MySQL / Oracle / PostgreSQL への連携クエリ

接続 (Connection) と EXTERNAL_QUERY による Federated Queries
📅 リリース日: 2026-11-13

📝 概要

BigQuery から MySQL、Oracle、PostgreSQL への接続 (Connection) を作成し、 EXTERNAL_QUERY 関数による連携クエリ (Federated Queries) を実行できるようになりました (Preview)。

これまで連携クエリの対象は Cloud SQL、AlloyDB、Spanner が中心でしたが、今回のアップデートで オンプレミス、Compute Engine 上のセルフマネージドインスタンス、他クラウドでホストされたデータベースに対しても、 データを移動せずに BigQuery から直接クエリできます。Oracle は Oracle Database@Google Cloud や Oracle Exadata Database Service もサポート対象です。

💡 こんな人に有用: オンプレミスや他クラウドの業務データベースと BigQuery 上の分析データを ETL なしで結合したいデータエンジニア・データアナリスト

❌ Before: アップデート前の課題

  • 連携クエリは Cloud SQL / AlloyDB / Spanner などに限定。オンプレミスや他クラウド、セルフマネージドの DB は Data Transfer Service や ETL で BigQuery に取り込む必要があった
  • Oracle Database を BigQuery から直接クエリする手段がなく、複製・同期の仕組みを別途構築・運用
  • バッチ取り込み間隔に依存し、ソース DB の最新データのリアルタイム参照が困難

✅ After: アップデート後の改善

  • 接続リソースを作成するだけで EXTERNAL_QUERY により MySQL / Oracle / PostgreSQL をその場でクエリし、BigQuery テーブルと JOIN 可能
  • オンプレミス (Cloud VPN / Interconnect 経由)、GCE 上のセルフマネージド、パブリック IP / ネットワークアタッチメント経由のクラウドホスト型など幅広い環境に対応
  • TLS モード選択、カスタム CA、CMEK、Private Service Connect によるエンタープライズ向けセキュリティ構成

BigQuery が接続リソースを介して外部の MySQL / Oracle / PostgreSQL にクエリを送信し、結果を GoogleSQL のデータ型に変換して 一時テーブルとして返すデータフローです。経路はネットワークアタッチメント経由のプライベート接続と、 パブリック IP + TLS の 2 方式から選択できます。

⚙️ 主要機能

1️⃣ MySQL / Oracle / PostgreSQL への接続リソース作成

✓Google Cloud コンソールまたは bq mk --connection コマンド (--connector_configuration フラグ) で接続を作成
✓ホスト:ポート、データベース名、ユーザー名・パスワードを指定。認証情報はデフォルトで Google 管理の暗号鍵、オプションで CMEK (Cloud KMS) により保護
✓接続のリージョンはクエリを実行する BigQuery リージョンと一致させる必要がある

2️⃣ EXTERNAL_QUERY 関数による連携クエリ

✓外部データベースの SQL 方言でクエリを記述し、結果を GoogleSQL のデータ型に変換した一時テーブルとして取得
✓BigQuery 上のテーブルと外部データベースのライブデータを JOIN 可能
✓INFORMATION_SCHEMA (MySQL / PostgreSQL) や Oracle のデータディクショナリビュー (all_tables、all_tab_columns) によるスキーマ確認にも対応

3️⃣ 柔軟なネットワーク接続とセキュリティ構成

✓プライベート接続: BigQuery 接続と同一リージョンのネットワークアタッチメントを経由 (Cloud VPN / Cloud Interconnect でオンプレミスにも到達可能)
✓パブリック接続: Google の IP アドレスレンジをデータベース側のファイアウォールで許可
✓TLS モード: ENCRYPT_VERIFY_CA_AND_HOST (推奨)、ENCRYPT_VERIFY_CA、ENCRYPT_VERIFY_NONE、DISABLE から選択。カスタム CA の PEM 証明書も指定可能

  • プライベート接続は BigQuery 接続と同一リージョンにネットワークアタッチメントを作成、パブリック接続は Google の IP レンジをファイアウォールで許可

ステップ 1: 接続の作成 (MySQL の例)

Bash bq mk --connection による接続作成 
bq mk --connection \
  --location=us-central1 \
  --project_id=PROJECT_ID \
  --connector_configuration '{
    "connector_id": "mysql",
    "endpoint": { "host_port": "10.10.0.2:3306" },
    "asset": { "database": "DATABASE" },
    "authentication": {
      "username_password": {
        "username": "USERNAME",
        "password": { "plaintext": "PASSWORD" }
      }
    },
    "tls": { "mode": "ENCRYPT_VERIFY_CA_AND_HOST" },
    "network": {
      "private_service_connect": {
        "network_attachment": "projects/PROJECT_ID/regions/NA_REGION/networkAttachments/ATTACHMENT_NAME"
      }
    }
  }' \
  CONNECTION_ID

パブリック IP で接続する場合は network オブジェクトを省略します。コンソールの場合は「データを追加」→ データソースで MySQL を選択し、「BigQuery Federation」ソリューションカードから作成します。

ステップ 2: 連携クエリの実行 (Oracle の例)

SQL BigQuery テーブルと Oracle のライブデータを JOIN 
SELECT
  bq_cust.customer_id,
  bq_cust.customer_name,
  oracle_orders.order_id,
  oracle_orders.order_status,
  oracle_orders.order_total
FROM mydataset.customers AS bq_cust
JOIN EXTERNAL_QUERY(
  'projects/my-project/locations/us-central1/connections/oracle_prod_conn',
  '''SELECT customer_id, order_id, order_status, order_total
     FROM orders
     WHERE order_date >= SYSDATE - 1''') AS oracle_orders
ON bq_cust.customer_id = oracle_orders.customer_id;

BigQuery 上の顧客テーブルと Oracle 上のライブな注文データを直接 JOIN する例です。

💪 メリット

💼 ビジネス面

✓ETL パイプラインの削減: データを BigQuery にコピーせずその場で分析できるため、データ複製パイプラインの構築・運用コストを削減
✓最新データへのアクセス: バッチ取り込みの待ち時間なしに、業務データベースのライブデータを BigQuery の分析に組み込める
✓マルチクラウド・ハイブリッド対応: オンプレミスや他クラウドの DB も Cloud VPN / Cloud Interconnect やパブリック IP 経由で分析対象に

🔧 技術面

✓GoogleSQL との統合: EXTERNAL_QUERY の結果は GoogleSQL のデータ型に変換され、BigQuery テーブルとシームレスに JOIN・加工できる
✓セキュアな接続: TLS モードの選択、カスタム CA、CMEK、Private Service Connect ネットワークアタッチメントによるプライベート接続に対応
✓クエリの追跡: 連携クエリにはプロジェクト ID と BigQuery ジョブ ID を含むコメントが付与され、DB 側ログで BigQuery 起点のクエリを識別可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 機能であり、Pre-GA Offerings Terms が適用される (サポートは bq-3p-federation-support@google.com 宛)
✗EXTERNAL_QUERY による読み取り専用クエリのみ実行可能 (DDL / DML は非サポート)。外部テーブルや外部データセットとしてのマッピングも不可
✗SQL プッシュダウン非対応: フィルタ・列プルーニングの自動的な押し下げは AlloyDB / Cloud SQL / Spanner のみ。転送量を抑えるには EXTERNAL_QUERY 内の SQL で述語と列射影を明示的に指定する必要がある
✗DNS ピアリングは非サポート。IP アドレスまたは VPC 内で解決可能なホスト名で接続
✗認証はデータベースのユーザー名・パスワードのみ (Oracle の Kerberos、RADIUS、OCI IAM などは非サポート)
✗Oracle ではユーザー定義型、SDO_GEOMETRY、コレクション型、BFILE などの複合型・独自型は非サポート
✗1 つの連携クエリで使用できる接続は最大 10 個。クロスリージョンクエリはプロジェクトあたり 1 日 1 TB まで

🤔 考慮すべき点

  • 連携クエリのレイテンシは、DB への直接クエリや BigQuery ストレージへのクエリより大きくなる可能性がある
  • 非アクティブな接続はハイバネートされることがあり、一定時間後の最初のクエリはコネクタ初期化のため 1 分以上かかる場合がある
  • クエリの実行ロケーションは接続リソースのリージョンと一致させる必要があり、ネットワークアタッチメントも BigQuery 接続と同一リージョンに配置
  • 本番データベースへの分析クエリによる負荷を避けるため、リードレプリカへの接続を検討する
  • VPC Service Controls で Compute Engine API が制限されているプロジェクトでは、ネットワークアタッチメントを使う連携クエリが失敗する場合があるため、適切な ingress / egress ルールの構成が必要

🎯 ユースケース

🏢 ユースケース 1: オンプレミス Oracle の業務データと BigQuery のリアルタイム結合分析

シナリオ: 基幹システムの注文データがオンプレミスの Oracle Database (19c) にあり、顧客マスタや行動ログは BigQuery にある。日次バッチの取り込みを待たずに最新の注文状況を分析したい。

SQL 実装例 
SELECT c.segment, o.order_status, SUM(o.order_total) AS total
FROM mydataset.customers AS c
JOIN EXTERNAL_QUERY(
  'projects/my-project/locations/us-central1/connections/oracle_prod_conn',
  'SELECT customer_id, order_status, order_total FROM orders WHERE order_date >= SYSDATE - 1'
) AS o ON c.customer_id = o.customer_id
GROUP BY c.segment, o.order_status;
✅ 効果: Cloud Interconnect とネットワークアタッチメント経由で Oracle に直接クエリでき、ETL の構築なしに直近データの分析が可能になる。

☁️ ユースケース 2: 他クラウドでホストされた PostgreSQL のデータ統合

シナリオ: 他クラウド上にホストされた PostgreSQL 16 に SaaS アプリケーションのデータがあり、BigQuery でのクロスソース分析に取り込みたいが、常時同期パイプラインは運用したくない。

✅ 効果: パブリック IP + TLS (CA・ホスト名検証) で安全に接続し、必要なときだけ EXTERNAL_QUERY で最新データを取得できる。データ複製が不要になり運用負荷を削減できる。

💰 料金

連携クエリ自体に対する BigQuery の追加料金はありません。コストは次の 3 要素で構成されます。

🖥️
外部 DB 側のコンピュート
クエリ実行コスト (データベースの提供元・ホスティング環境に依存)
🔄
データ転送 (Egress)
クエリ結果を外部 DB から BigQuery へ転送する帯域コスト (ホスティングプロバイダの Egress 課金)
🔍
BigQuery 側のコンピュート
BigQuery でのクエリ実行コスト (通常の BigQuery 料金)
💡 コスト最適化のヒント: 帯域コストを抑えるため、EXTERNAL_QUERY 内の SQL で不要な列・行を除外することが推奨されています。 接続経路に Google Cloud のネットワークコンポーネントを使う場合は、VPC、Cloud VPN、Cloud NAT、Cloud Interconnect の料金が別途適用される場合があります。

🌏 利用可能リージョン

MySQL / Oracle / PostgreSQL への連携クエリは、接続リソースを作成できるすべての BigQuery リージョンでサポートされます。

📍 リージョンの制約: クエリの実行ロケーションは接続リソースのリージョンと一致している必要があり、 ネットワークアタッチメントを使う場合はアタッチメントと BigQuery 接続を同一リージョンに配置する必要があります。

🔗 関連サービス・機能

🗄️ Cloud SQL / AlloyDB / Spanner 連携クエリ
従来からサポートされている Google Cloud マネージド DB への連携クエリ。SQL プッシュダウンも適用される
📦 BigQuery Data Transfer Service
MySQL / Oracle / PostgreSQL のデータを BigQuery に取り込む選択肢。反復的な大規模分析ではストレージへの取り込みが有利な場合がある
🔌 Cloud VPN / Cloud Interconnect
オンプレミスのデータベースへプライベートに到達するためのネットワーク接続
🛡️ VPC ネットワークアタッチメント (Private Service Connect)
パブリックインターネットを経由しないプライベート接続経路を提供
🔐 Cloud KMS (CMEK)
接続に保存するデータベース認証情報を顧客管理の暗号鍵で保護
📋 Cloud Logging
クエリに付与される BigQuery ジョブ ID 入りコメントにより、DB 側ログで連携クエリを追跡可能

📌 まとめ

  • BigQuery の連携クエリが Google Cloud マネージドデータベース以外の MySQL、Oracle、PostgreSQL に拡大し、オンプレミスや他クラウドのデータを ETL なしで直接分析可能に
  • SQL プッシュダウンが適用されないため、EXTERNAL_QUERY 内でのフィルタ・列指定が性能とコストの鍵
  • ハイブリッド環境のデータ統合を検討しているチームは、Preview の制約を確認のうえリードレプリカへの接続から試すことを推奨
