📋 BigQuery: カスタム組織ポリシーによるワークロード管理リソースの制御

BigQuery Preview Governance Cost Management
2026-05-18

🎯 概要

BigQuery のワークロード管理リソースに対して、カスタム組織ポリシー (Custom Organization Policy) を使用して特定の操作を許可または拒否できるようになりました。

対象リソースは Reservations (予約)、Assignments (割り当て)、Capacity Commitments (容量コミットメント)、BI Reservations (BI 予約) の 4 種類です。

Organization Policy Service の CEL (Common Expression Language) 条件を使用して、リソースの作成や更新時に制約を適用し、コスト管理やコンプライアンス要件への対応が可能になります。

💡 対象ユーザー: 大規模組織で BigQuery の容量管理を集中制御したい組織管理者やクラウドアーキテクト。特に、複数のプロジェクトやチームが BigQuery のリザベーションを使用する環境向け。

🔄 Before / After 比較

❌ Before (アップデート前)

  • ワークロード管理リソースに対する操作を組織レベルで一元制御する手段がなかった
  • IAM 権限のみでは細かい条件付き制約を表現できなかった
  • 個々のプロジェクトで独自にスロットを購入することを防ぐのが困難
  • カスタム組織ポリシーは Dataset、Table 等には対応済みだがワークロード管理は未対応

✅ After (アップデート後)

  • Reservation、Assignment、CapacityCommitment、BiReservation に対してカスタム制約を定義可能
  • CEL 条件でスロット数、エディション、リージョン等に基づくポリシーを作成
  • 組織/フォルダ/プロジェクトの各レベルで階層的にポリシーを適用可能
  • ドライラン機能で影響範囲を事前にテスト可能

🧮 CEL 条件によるきめ細かい制御

  • リソースのフィールド値に基づいて条件を記述
  • スロット数の上限、特定エディションの強制、リージョン制限
  • ALLOW / DENY の両方をサポート

🏢 階層的なポリシー継承

  • 組織レベルのポリシーがフォルダ・プロジェクトに自動継承
  • 下位レベルで親ポリシーをオーバーライド可能
  • タグベースの条件付きルールに対応

🔧 設定方法

📋 前提条件:
  • Google Cloud 組織が存在すること
  • Organization Policy Administrator (roles/orgpolicy.policyAdmin) IAM ロールが付与されていること
  • BigQuery Reservation API (bigqueryreservation.googleapis.com) が有効化されていること

Step 1: カスタム制約の作成

YAML constraint-limit-slots.yaml 
name: organizations/123456789/customConstraints/custom.limitReservationSlots
resourceTypes:
  - bigqueryreservation.googleapis.com/Reservation
methodTypes:
  - CREATE
  - UPDATE
condition: "resource.slotCapacity > 1000"
actionType: DENY
displayName: Limit reservation slot capacity
description: Deny reservations with more than 1000 slots.
Bash 制約を組織に適用 
# 制約を組織に適用
gcloud org-policies set-custom-constraint constraint-limit-slots.yaml

Step 2: 組織ポリシーの作成と適用

YAML policy-limit-slots.yaml 
name: projects/my-project/policies/custom.limitReservationSlots
spec:
  rules:
    - enforce: true
Bash ポリシーを適用 
# ポリシーを適用
gcloud org-policies set-policy policy-limit-slots.yaml

Step 3: ポリシーの検証

Bash 検証コマンド 
# 制約の確認
gcloud org-policies list-custom-constraints --organization=123456789

# ポリシーの確認
gcloud org-policies list --project=my-project

# ドライランモードでテスト
gcloud org-policies set-policy policy-limit-slots.yaml --update-mask=dryRunSpec
⚠️ 注意: ポリシーが有効になるまで最大 15 分かかる場合があります。ドライランモードでは、実際にはブロックせずにポリシー違反をログに記録します。

💼 ユースケース

🎯 ユースケース 1: スロット購入の上限制御

シナリオ: 大規模組織で、個々のチームが独自にスロットを大量購入してコストが膨らむことを防ぎたい。

YAML 500 スロット以上の購入を拒否 
name: organizations/123456789/customConstraints/custom.limitCommitmentSlots
resourceTypes:
  - bigqueryreservation.googleapis.com/CapacityCommitment
methodTypes:
  - CREATE
condition: "resource.slotCount > 500"
actionType: DENY
displayName: Limit capacity commitment size
description: Individual teams cannot purchase more than 500 slots.

効果: チームごとのスロット購入を 500 スロット以下に制限し、大規模な容量変更はプラットフォームチームの承認を経る運用を強制。

🔒 ユースケース 2: Enterprise Plus エディションの強制

シナリオ: セキュリティ要件として、すべてのリザベーションで Enterprise Plus エディションの使用を義務付けたい。

YAML Enterprise Plus 以外を拒否 
name: organizations/123456789/customConstraints/custom.enforceEnterprisePlus
resourceTypes:
  - bigqueryreservation.googleapis.com/Reservation
methodTypes:
  - CREATE
  - UPDATE
condition: "resource.edition != 'ENTERPRISE_PLUS'"
actionType: DENY
displayName: Enforce Enterprise Plus edition
description: All reservations must use Enterprise Plus edition.

効果: CMK、VPC Service Controls 対応など Enterprise Plus の高度なセキュリティ機能を組織全体で確実に利用可能に。

📊 ユースケース 3: BI 予約容量の制限

シナリオ: BI Engine の予約容量が過剰に割り当てられることを防ぎ、コストを管理したい。

YAML BI 予約を 10GB 以下に制限 
name: organizations/123456789/customConstraints/custom.limitBiReservation
resourceTypes:
  - bigqueryreservation.googleapis.com/BiReservation
methodTypes:
  - UPDATE
condition: "resource.size > 10737418240"
actionType: DENY
displayName: Limit BI reservation to 10GB
description: BI reservation cannot exceed 10GB (10737418240 bytes).

効果: BI Engine の予約容量を 10GB 以下に制限し、不要なメモリ確保によるコスト増を防止。

✅ メリット

💼 ビジネス面

  • コスト管理の強化: 不適切なスロット購入や過大な容量コミットメントを組織レベルで防止
  • ガバナンスの一元化: 複数チーム・プロジェクトにまたがる容量管理ルールを集中管理
  • コンプライアンス対応: 特定リージョンでのみ容量購入可能にするなど、データ主権要件への対応

⚙️ 技術面

  • 宣言的なポリシー管理: YAML ベースの制約定義で Infrastructure as Code としてバージョン管理可能
  • CEL による柔軟な条件記述: リソースの任意フィールドに基づく条件を記述可能
  • ドライランによる安全な検証: ポリシーの影響を事前にテスト可能

⚠️ 制限事項・注意点

制限事項

  • Preview ステータス: SLA の適用対象外であり、本番環境での利用には注意が必要
  • 制約数の上限: リソースタイプあたりのカスタム制約は最大 20 個まで
  • 適用ラグ: ポリシーの適用には最大 15 分のラグが発生する可能性がある
  • CEL 条件の長さ: 最大 1000 文字まで
⚠️ 考慮すべき点:
  • 既存のリザベーションがポリシーに違反している場合、UPDATE メソッドの制約を適用すると変更がブロックされる
  • 組織ポリシーの階層継承を理解し、意図しないブロックが発生しないよう設計が必要
  • ドライランモードで十分にテストしてから本番適用することを推奨
