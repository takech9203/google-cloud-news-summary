📋 概要

Google Distributed Cloud (software only) for bare metal (旧称 Anthos clusters on bare metal) のバージョン 1.34.1100-gke.125 がダウンロード可能になりました。Kubernetes v1.34.12-gke.500 上で動作し、直前パッチ 1.34.1000-gke.111 (2026-10-22、Kubernetes v1.34.7-gke.200) からベース Kubernetes も更新されています。

本リリースの柱は 2 つです。

🔐 1. セキュリティ強化 (ルート CA トラストストア更新)

信頼が失効 (distrusted) した eMudhra (emSign) および AAA Certificate Services ルート CA をシステムコンポーネントとコンテナベースイメージのトラストストアから削除し、侵害された eMudhra 中間 CA を拒否。

🔧 2. クラスタライフサイクル管理の不具合修正 (8 件)

孤立 ClusterRoleBinding、残存ローカル PV、etcd メンバー誤削除など、クラスタの作成・削除・アップグレードに関わる問題を修正。

💡 対象読者: オンプレミスのベアメタル環境で GDC クラスタを運用する管理者。同日に GDC (software only) for VMware でも同一バージョン番号 1.34.1100 がリリースされています (別レポート)。同じ CA トラストストア更新は 1.35 系列では 1.35.700-gke.124 (2026-11-04) で先行導入済みです。

🔄 Before / After

😣 Before (〜1.34.1000)

  • 失効した eMudhra (emSign) / AAA Certificate Services ルート CA がトラストストアに残存
  • ユーザークラスタ削除で admin クラスタに孤立 ClusterRoleBinding が残り手動掃除が必要
  • ノード削除後もローカル PersistentVolume が GC されず残存
  • IP プレフィックス共有時 (例: 10.201.0.2 と 10.201.0.26) に誤った etcd メンバーを削除 → ノード NotReady / アップグレード停止
  • bmctl check cluster --snapshot が panic で失敗する競合状態
  • アップグレード中の構成ドリフトチェックが version not supported で失敗
  • audit-proxy が恒久的エラーでも無限再試行し過剰な監査ログトラフィック
  • プリフライトチェックが admin クラスタの全 namespace をスキャンし無関係なクラスタでアップグレード失敗

😀 After (1.34.1100-gke.125)

  • 失効ルート CA を削除、侵害された中間 CA を拒否し証明書リスクを低減
  • ヘルスチェック権限を namespace スコープの RoleBinding 化、レガシー CRB は自動クリーンアップ
  • ノード削除時にローカル PV を自動ガベージコレクション (アップグレード後に作成した PV に適用)
  • etcd メンバー特定の部分一致誤削除を解消し、コントロールプレーンノードのリセット / 削除が安全に
  • イメージ展開中の再起動による containerd 状態破損への耐性向上
  • Vulnerability fixes 記載の脆弱性を修正

⭐ 主要機能・修正内容

📣 1. バージョン 1.34.1100-gke.125 の提供開始 Announcement

✓Kubernetes v1.34.12-gke.500 上で動作
✓GKE On-Prem API クライアント (Google Cloud コンソール、gcloud CLI、Terraform) でのインストール / アップグレード対応はリリース後約 7〜14 日
✓サードパーティストレージ利用時は認定済みストレージパートナー一覧を確認

🔐 2. 信頼失効ルート CA の削除 Security

✓システムコンポーネントとコンテナベースイメージのトラストストアから eMudhra (emSign) / AAA Certificate Services ルート CA を削除
✓侵害された eMudhra 中間 CA を拒否
✓1.35 系列では 1.35.700-gke.124 (2026-11-04) で先行導入済みの、系列横断トラストストア更新

🔧 3. クラスタライフサイクル関連の不具合修正 Fixed

  • Vulnerability fixes に記載の脆弱性を修正
  • ユーザークラスタ削除時の孤立 ClusterRoleBinding 問題を修正 (namespaced RoleBinding 化 + レガシーオブジェクトの自動クリーンアップ)
  • bmctl check cluster --snapshot の panic: send on closed channel 競合状態を修正
  • ノード削除時のローカル PersistentVolume ガベージコレクションを修正 (アップグレード後に作成された PV に適用、既存の孤立 PV は手動削除)
  • IP プレフィックス共有時の etcd / etcd-events メンバー誤削除を修正
  • イメージ展開中のノード再起動に対する containerd の状態破損耐性を向上
  • アップグレード / ロールバック中の構成ドリフトヘルスチェックの version not supported エラーを修正
  • audit-proxy の恒久的エラー時の無限再試行を修正
  • Kubernetes プリフライトヘルスチェックのスキャン範囲を対象クラスタの namespace に限定

🛠️ 設定方法

✅ 前提条件

✓既存の GDC (software only) for bare metal クラスタが 1.34 系列へのアップグレードパス上にあること (1.34.x からのパッチアップグレード、または 1.33 系列からのマイナーアップグレード)
✓サードパーティストレージ利用時は、本リリースで認定済みのストレージパートナーであることを確認
1

アップグレード計画の確認

公式の Upgrade clusters ドキュメントに従い、admin クラスタ → ユーザークラスタの順でアップグレードを計画します。

2

bmctl によるアップグレード (例)

Bash bmctl アップグレードコマンド 
# クラスタ構成ファイルの anthosBareMetalVersion を 1.34.1100-gke.125 に更新後
bmctl upgrade cluster -c CLUSTER_NAME \
    --kubeconfig ADMIN_KUBECONFIG

GKE On-Prem API クライアント (Console / gcloud / Terraform) を使用する場合は、リリースから約 7〜14 日後にバージョンが選択可能になります。

3

既存の孤立リソースのクリーンアップ確認

ローカル PersistentVolume の GC 修正は、1.34.1100 へのアップグレード後に作成された PV にのみ適用されます。アップグレード前に孤立した PV が残っている場合は手動削除が必要です。

Bash 孤立したローカル PV の確認例 
# 孤立したローカル PV の確認例
kubectl get pv --kubeconfig ADMIN_KUBECONFIG | grep -i released

🎯 メリット

💼 ビジネス面

✓セキュリティコンプライアンスの維持: 業界的に信頼が失効した CA をオンプレミス環境のトラストストアからも排除し、エアギャップ気味の環境でもパブリッククラウドと同等の証明書衛生を維持できる
✓運用コストの削減: 孤立 ClusterRoleBinding や残存 PV の手動クリーンアップ作業が不要になり、クラスタの作成・削除を繰り返す環境 (検証環境、マルチテナント基盤) の運用負荷が下がる

⚙️ 技術面

✓アップグレードの信頼性向上: etcd メンバー誤削除、プリフライトチェックの過剰スキャン、構成ドリフトチェックの誤検知という、アップグレード停止につながる 3 つの問題が同時に解消
✓診断ツールの安定化: bmctl check cluster --snapshot の panic 修正により、障害調査時のスナップショット取得が安定
✓ノード障害耐性の向上: イメージ展開中の再起動による containerd 状態破損への耐性が向上し、不意の電源断などからの復旧性が向上

⚠️ デメリット・制約事項

🚧 制限事項

▲ローカル PersistentVolume の GC 修正は、1.34.1100-gke.125 へのアップグレード後に作成された PV にのみ適用。既存の孤立 PV は手動削除が必要
▲GKE On-Prem API クライアント (Console / gcloud / Terraform) からの利用はリリース後約 7〜14 日待つ必要がある

🤔 考慮すべき点

❗削除された eMudhra (emSign) / AAA Certificate Services ルート CA にチェーンする証明書を社内システムや外部連携先で使用している場合、システムコンポーネントからの TLS 接続が失敗するようになるため、事前に証明書の発行元を確認する
❗サードパーティストレージベンダー利用時は、本リリースでの認定状況をアップグレード前に確認する

📝 まとめ

1.34.1100-gke.125 は、信頼失効した eMudhra (emSign) / AAA Certificate Services ルート CA のトラストストアからの削除と、アップグレード停止や孤立リソース残存につながる 8 件の不具合修正を含む、1.34 系列の重要なパッチリリースです。特にクラスタの作成・削除を頻繁に行う環境や、コントロールプレーンノードの入れ替えを予定している環境では、etcd メンバー誤削除や孤立 ClusterRoleBinding の修正の恩恵が大きいため、早期の適用を推奨します。適用前には、削除された CA にチェーンする証明書を利用していないかの確認を忘れないでください。
