🔍 Vertex AI Search: PREFIX / PARTIAL / EXISTS Filter

Vertex AI Search (Agent Search) Public Preview
2026-06-08

📋 概要

Vertex AI Search (Agent Search) の検索クエリフィルタリング機能が大幅に強化されました。新たにプレフィックス一致（前方一致）、部分一致、EXISTS フィルタの3つのフィルタタイプが追加され、従来の完全一致ベースのフィルタリングの制約を解消します。

対象: カスタム検索、メディア検索、ウェブサイト検索を構築している開発者、検索エンジニア。EC サイト、コンテンツ管理システム、メディアプラットフォームでの検索精度向上に有用です。

Before / After

❌ Before (課題)

  • 完全一致 (ANY) しか使えず、先頭部分での絞り込みが不可
  • フィールド値の一部しか知らない場合、結果が返らない
  • NULL チェックにワークアラウンドが必要
  • 複雑なフィルタ条件の組み合わせが困難

✅ After (改善)

  • PREFIX で先頭文字列に基づく効率的なフィルタリング
  • PARTIAL で部分的な単語マッチングが可能
  • EXISTS で有効な値の存在チェックを標準化
  • ANY, IN, EXISTS を組み合わせた高度なフィルタ式

⚡ 主要機能

🎯 プレフィックス一致 (PREFIX)

フィールド値が特定の文字列で始まるかどうかに基づいてフィルタリング。カテゴリの階層構造やプロダクトコードの先頭部分での検索に最適。

→ スキーマフィールドで prefixMatchable: true を設定して有効化
→ 例: category: PREFIX("electronics/smartphones")

🔎 部分一致 (PARTIAL)

クエリがフィールド値に含まれる単語の一部と一致するかどうかでフィルタリング。ANY オペレータとは異なり完全一致を必要としない柔軟なマッチング。

→ スキーマフィールドで partialMatchable: true を設定して有効化
→ 例: department: PARTIAL("クラウド インフラ")

📦 EXISTS フィルタ

ドキュメントのフィールドに値が存在し、デフォルト値でないことを条件にフィルタリング。データ品質の担保やオプショナルフィールドの有無による絞り込みに最適。

→ カスタム検索とメディア検索の両方で利用可能
→ 例: EXISTS(description) AND status: ANY("active")

📐 技術仕様

フィルタ式の比較

フィルタタイプ 動作 完全一致要求 対応検索タイプ
ANY フィールド値が指定値のいずれかと完全一致 はい カスタム、メディア、ウェブサイト
PREFIX フィールド値が指定文字列で始まる いいえ (先頭一致) カスタム、メディア
PARTIAL フィールド値の一部の単語がクエリに含まれる いいえ (部分一致) カスタム、メディア
EXISTS フィールドに非デフォルト値が存在する N/A カスタム、メディア
IN 数値フィールドが指定範囲内 N/A (範囲指定) カスタム、メディア

スキーマフィールド設定

プレフィックス一致および部分一致を利用するには、対象フィールドのスキーマ設定で明示的に機能を有効化する必要があります。

JSON スキーマフィールド設定例 
{
  "structSchema": {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "properties": {
      "category": {
        "type": "string",
        "indexable": true,
        "retrievable": true,
        "prefixMatchable": true,
        "partialMatchable": true
      },
      "product_code": {
        "type": "string",
        "indexable": true,
        "prefixMatchable": true
      },
      "description": {
        "type": "string",
        "indexable": true,
        "searchable": true
      }
    },
    "type": "object"
  }
}

🔧 設定方法

💡 前提条件: Vertex AI Search が有効化済み / 検索アプリとデータストアが作成済み / 構造化データまたはメタデータ付き非構造化データがインポート済み / フィールドが indexable に設定済み

Step 1: スキーマフィールドの設定更新

Bash API でスキーマを更新 
curl -X PATCH \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://discoveryengine.googleapis.com/v1/projects/PROJECT_ID/locations/global/collections/default_collection/dataStores/DATA_STORE_ID/schemas/default_schema" \
  -d '{
    "structSchema": {
      "properties": {
        "category": {
          "type": "string",
          "indexable": true,
          "prefixMatchable": true,
          "partialMatchable": true
        }
      }
    }
  }'

Step 2: フィルタ付き検索リクエストの実行

Bash PREFIX フィルタを使用した検索 
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://discoveryengine.googleapis.com/v1/projects/PROJECT_ID/locations/global/collections/default_collection/engines/APP_ID/servingConfigs/default_search:search" \
  -d '{
    "query": "search query",
    "filter": "category: PREFIX(\"elec\")"
  }'
Bash EXISTS + ANY を組み合わせた検索 
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://discoveryengine.googleapis.com/v1/projects/PROJECT_ID/locations/global/collections/default_collection/engines/APP_ID/servingConfigs/default_search:search" \
  -d '{
    "query": "search query",
    "filter": "EXISTS(description) AND status: ANY(\"active\", \"pending\")"
  }'

✅ メリット

📈 ビジネス面

✔検索精度の向上: ユーザーがフィールド値の完全な値を知らなくても適切な結果を取得可能
✔データ品質の制御: EXISTS で必須情報が欠落したドキュメントを排除
✔EC サイト検索改善: カテゴリ先頭文字列での柔軟なナビゲーション

🛠️ 技術面

✔フィルタ式の表現力向上: 複雑な条件を単一式で表現可能
✔クエリ処理の効率化: インデックスレベルでのプレフィックス一致
✔NULL 安全なクエリ設計: EXISTS でフィールド存在チェックを簡素化

⚠️ デメリット・制約事項

制限事項
  • パブリックプレビュー段階 - GA 時に仕様変更の可能性あり
  • スキーマフィールドの事前設定が必要 (既存フィールド変更時はリインデックスの可能性)
  • indexable フィールドは最大 50 個までの制限
  • EXISTS は現在カスタム検索とメディア検索で利用可能
考慮すべき点
  • PREFIX はフィールド値の先頭からのみ一致 (中間一致・後方一致には非対応)
  • PARTIAL 多用時は意図しないマッチの可能性あり - 適切なフィルタ設計が重要
  • 大規模データストアではリインデックスに時間がかかる場合がある
  • Preview 機能のため「Pre-GA Offerings Terms」が適用される

💡 ユースケース

🛒 EC サイトでの商品カテゴリフィルタリング

シナリオ: 商品カテゴリの階層構造 (例: "electronics/smartphones/android") に基づき、先頭部分指定で配下すべての商品を取得

JSONフィルタ式
{
  "query": "最新モデル",
  "filter": "category: PREFIX(\"electronics/smartphones\")"
}

効果: "electronics/smartphones/android"、"electronics/smartphones/ios" 等のサブカテゴリ配下すべてが単一フィルタ式で取得可能

🎬 メディアプラットフォームでの品質フィルタリング

シナリオ: 説明文や評価が設定されているコンテンツのみを検索結果に表示し、未入力メタデータのコンテンツを除外

JSONフィルタ式
{
  "query": "料理レシピ",
  "filter": "EXISTS(description) AND EXISTS(media_content_rating) AND category: ANY(\"cooking\")"
}

効果: メタデータが充実したドキュメントのみ返却され、検索結果の品質が一定以上に保たれる

🏢 企業内文書検索での部分一致活用

シナリオ: 部門名やプロジェクト名が長い場合に、正確な名称を覚えていなくても目的の文書を発見

JSONフィルタ式
{
  "query": "セキュリティガイドライン",
  "filter": "department: PARTIAL(\"クラウド インフラ\")"
}

効果: "クラウド インフラストラクチャ運用部" や "クラウド インフラ設計チーム" など部分マッチする部門の文書が返却される
