リリース日: 2026-10-28

🔐 セキュリティ情報 GCP-2026-071 への対応
eMudhra (emSign) CA 証明書の秘密鍵侵害 (CVE-2026-111943)

📌 概要

eMudhra (emSign) の下位 CA 証明書 8 件 (AAA Certificate Services によるクロス署名を含む) の秘密鍵が、 不十分な暗号学的乱数 (弱いエントロピー) で生成されていたため再構成可能と報告されました。 攻撃者が秘密鍵を復元すると、信頼された TLS 証明書を偽造し、これらの CA を信頼したままの TLS クライアント・コンテナ・SDK に対して 中間者 (MitM) 攻撃 を行えます。

対応として、Google は AlloyDB for PostgreSQL のマネージドコンポーネントを更新しています。証明書ストアの修正は 新しいメンテナンスバージョン として提供され、スケジュールされたメンテナンス時に AlloyDB が自動適用するため、 マネージドインスタンスの手動更新は不要です。セルフサービスメンテナンスによる早期適用も可能です。

✅ 重要: Google Cloud のインフラストラクチャ自体は侵害されておらず、Google Cloud ワークロードに対する悪用の痕跡も確認されていません。Google 管理環境では侵害された CA をブロック・不信頼化する事前対策が実施済みです。

❌ アップデート前の課題

  • 侵害された eMudhra (emSign) 下位 CA を信頼したままの TLS クライアントは、外部 TLS 接続において MitM 傍受やトラフィック偽装のリスクに晒されていた
  • AlloyDB Auth Proxy の旧バージョン (v1.17.2 未満) や、古い CA バンドルを含む言語ランタイム・OS は、侵害された CA への信頼を削除する修正を含んでいなかった

✅ アップデート後の改善

  • 証明書ストアの修正が新メンテナンスバージョンとして配布され、スケジュールメンテナンス時に自動適用。マネージドインスタンスの手動更新が不要に
  • セルフサービスメンテナンスで、スケジュールを待たずに修正を早期適用できる
  • 更新版 Auth Proxy (v1.17.2 以降) と更新済みのランタイム / OS CA 証明書で、クライアント側でも侵害された CA への信頼を排除

🕵️ 脆弱性の背景 (GCP-2026-071)

2026 年 10 月 17 日、セキュリティ研究者から eMudhra の下位 CA 証明書 8 件 (AAA Certificate Services によるクロス署名を含む) に関連する秘密鍵の侵害が Google に報告されました。 これらの秘密鍵は不十分な暗号学的乱数で生成されており、攻撃者による再構成が可能です。該当 CA 証明書は信頼が取り消され、失効処理が進行中です。

⚠️ 影響範囲: AlloyDB のほか、Cloud SQL、gcloud CLI、GKE、Compute Engine、Cloud Run など多数の Google Cloud / Firebase プロダクトが影響対象として挙げられています。

レスポンスの maintenanceVersionName フィールドで、インスタンスが実行中のメンテナンスバージョンを確認します (例: "maintenanceVersionName": "POSTGRES_16.20251015.04_00")。

ステップ 2: セルフサービスメンテナンスで修正を早期適用 (任意)

Bash クラスタを最新メンテナンスバージョンに更新 
gcloud alloydb clusters update CLUSTER_ID \
  --region LOCATION_ID \
  --maintenance-version=latest
💡 ポイント: AlloyDB のメンテナンスはクラスタレベルで実行され、クラスタ内のインスタンスの更新順序は AlloyDB が決定します。デナイ期間 (deny period) はセルフサービスメンテナンスをブロックしません。

🎯 メリット

💼 ビジネス面

✓運用負荷の最小化: マネージドインスタンス側の修正は Google が新メンテナンスバージョンとして配布するため、ユーザーは証明書ストアの手動更新作業が不要
✓リスクの早期低減: セルフサービスメンテナンスがすでに利用可能なため、次回のスケジュールメンテナンスを待たずに修正を適用できる

🔧 技術面

✓多層的な修正: インスタンス側 (メンテナンスバージョン) と接続経路 (Auth Proxy / Language Connectors のランタイム・CA 証明書) のそれぞれで侵害された CA への信頼を排除できる
✓影響の封じ込め: Google Cloud インフラストラクチャ自体は侵害されておらず、Google 管理環境では侵害された CA をブロック・不信頼化する事前対策が実施済み

⚠️ デメリット・制約事項

考慮すべき点
  • クライアント側コンポーネント (Auth Proxy、Language Connectors のランタイム / OS CA 証明書) の更新はユーザーの責任で実施する必要がある
  • スタンドアロンのプロキシバイナリを使用している場合、プロキシ本体の更新に加えてホスト OS の CA 証明書更新も必要になる
  • AlloyDB のメンテナンスはクラスタレベルで実行されるため、インスタンス単位での適用はできない (インスタンスごとの更新順序は AlloyDB が決定する)
  • Compute Engine や GKE 上で自前管理している OS やカスタムコンテナイメージは、AlloyDB 側の対応とは別に、OS ベンダー経由でトラストストアを更新する必要がある (GCP-2026-071 の全般ガイダンス参照)

☁️ GKE / Compute Engine / Cloud Run: GCP-2026-071 の影響を受ける他のプロダクト。自前管理の OS・コンテナイメージはトラストストアの更新が別途必要

📝 まとめ

eMudhra 下位 CA の秘密鍵侵害 (GCP-2026-071 / CVE-2026-111943) に対し、AlloyDB では証明書ストアの修正が 新メンテナンスバージョンとして配布され、スケジュールメンテナンスで自動適用されるため、インスタンス側のユーザー作業は不要です。 急ぐ場合はセルフサービスメンテナンスで早期適用できます。

一方、AlloyDB Auth Proxy (v1.17.2 以降) やスタンドアロンバイナリのホスト CA 証明書、 Language Connectors のランタイム / OS CA 証明書 (例: Go 1.26.10 / 1.27.3 以降) といった クライアント側の更新はユーザーの対応が必須のため、自環境の接続方式を棚卸しして速やかに更新することを推奨します。
