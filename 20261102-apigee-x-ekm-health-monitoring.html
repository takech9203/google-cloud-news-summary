🔐 Apigee X: EKM ヘルスモニタリング

Apigee X Feature (新機能) Cloud EKM Cloud Logging
リリース日: 2026-11-02
Google Cloud News

📝 概要

Apigee X に Cloud External Key Manager (Cloud EKM) のヘルスモニタリング機能が追加されました。 CMEK (顧客管理暗号鍵) に Cloud EKM を利用している場合、EKM の健全性を Cloud Logging で監視し、 鍵の無効化や到達不能などの問題に対してログベースのアラートを構成できます。

外部鍵マネージャーが到達不能になったり鍵が無効化されると、暗号化に依存する Apigee のサービス (プロキシのデプロイ、分析処理など) が影響を受けます。本機能により、こうした EKM 起因の障害を プロアクティブに検知・通知できるようになりました。

🎯 対象ユーザー: 規制・コンプライアンス要件により外部鍵管理 (EKM) を使った CMEK 構成で Apigee を運用している組織。 ロールアウトは 2026 年 11 月 2 日開始、全ゾーンへの展開完了まで 4 営業日以上かかる場合があります。

❌ Before (アップデート前)

  • EKM の鍵が到達不能・無効化されても、Apigee 側から健全性を直接監視する仕組みがなかった
  • プロキシのデプロイ失敗など操作が失敗して初めて気付くことが多く、原因切り分けに時間がかかった
  • EKM 関連の障害を検知してアラート通知する標準的な方法がなかった

✅ After (アップデート後)

  • EKM の問題 (アクセス拒否、鍵の無効化、課金無効化、到達不能) を検知すると Cloud Logging にログを自動生成
  • Logs Explorer のクエリ Apigee EKM key health issue detected で簡単に検索可能
  • ログベースのアラートポリシーでプロアクティブに検知・通知できる

⚡ 主要機能

1️⃣ Cloud Logging への EKM 問題のログ出力

Apigee が Cloud EKM の問題を検知すると、Cloud Logging にログエントリを自動生成します。

✓検知対象: 鍵の状態が「拒否 (denied)」に変化、鍵の無効化、課金の無効化、鍵への到達不能
✓ログには問題が発生している組織とインスタンスの詳細を含む (セキュリティ上の理由から鍵名は含まれない)

2️⃣ Logs Explorer での EKM ログ検索

Google Cloud コンソールの Logs Explorer で、クエリ Apigee EKM key health issue detected を実行することで EKM 関連ログを検索できます。問題が発生している場合、イベントの詳細を示すログエントリが結果に表示されます。

3️⃣ ログベースのアラート構成

同じクエリフィルタを使ってログベースのアラートポリシーを作成し、EKM 関連エラー発生時に通知を受け取れます。Cloud Logging の「ログベースのアラートポリシーの構成」手順に従って設定します。

項目詳細
ログ生成頻度鍵が到達不能な間、約 1 時間に 1 回ログエントリを生成 (問題解消までアラート通知が繰り返される)
復旧通知なし。EKM が再度到達可能になってもログエントリや通知は生成されない
アラートの自動解決エラーログの生成が止まると、アラートポリシーの自動クローズ設定に基づき自動的に解決される
復旧確認方法API プロキシのデプロイなど、鍵を必要とする操作を実行して成功を確認する
ログ内容組織・インスタンスの詳細を含む。鍵名はセキュリティ上の理由で含まれない

🛠️ 設定方法

⚠️ 前提条件:
  1. Apigee 組織が組織の作成時に CMEK + Cloud EKM を使用するよう構成されていること (既存組織での有効化は不可)
  2. Cloud Logging の Logs Explorer およびアラートポリシーを操作できる権限があること
1

Logs Explorer で EKM 関連ログを確認する

Google Cloud コンソールで Logs Explorer を開き、以下のクエリを実行します。Cloud EKM の問題が発生している場合、イベントの詳細を示すログエントリが表示されます。

Query Logs Explorer クエリ 
Apigee EKM key health issue detected
2

ログベースのアラートを作成する

ステップ 1 と同じクエリフィルタを使用して、Cloud Logging のログベースのアラートポリシーを作成し、通知チャンネル (メール、PagerDuty など) を設定します。

3

復旧の確認

復旧時のログエントリは生成されないため、問題解消後は API プロキシのデプロイなど鍵を必要とする操作を実行し、成功することを確認して Cloud EKM が再度到達可能になったことを検証します。

💡 メリット

💼 障害の早期検知によるダウンタイム削減

EKM 起因の問題をプロアクティブに検知できるため、API 基盤の停止時間を最小化し、エンドユーザーへの影響を抑えられる。

💼 コンプライアンス要件と運用性の両立

規制要件で外部鍵管理 (EKM) が必須の組織でも、鍵管理起因の障害に対する監視体制を標準機能で整備できる。

⚙️ 原因切り分けの迅速化

「Apigee の障害」なのか「外部鍵マネージャーの問題」なのかをログから即座に判別でき、トラブルシューティングが効率化される。

⚙️ 既存の監視基盤との統合

Cloud Logging のログベースアラートという標準的な仕組みを使うため、既存の通知チャンネルやインシデント管理フローにそのまま組み込める。

⚠️ デメリット・制約事項

🚫 制限事項

✗組織の作成時に CMEK + EKM を構成した Apigee 組織でのみ利用可能。既存組織での有効化は不可 (EKM を使いたい場合は新規組織を作成してリソースを移行する必要がある)
✗Apigee hybrid は対象外 (Apigee X のみ)
✗復旧時の通知は生成されないため、復旧確認は手動で行う必要がある

🤔 考慮すべき点

⚠️鍵が到達不能な間は約 1 時間ごとにログ生成・アラート通知が繰り返されるため、ノイズを考慮したアラートポリシー設計 (自動クローズ設定など) が必要
⚠️Apigee のログは EKM 接続や鍵の状態の問題を示すのみ。EKM 自体の詳細なトラブルシューティング (ネットワーク診断、外部鍵マネージャー側の問題) は範囲外で、アラート受信後は Cloud EKM 側の健全性と構成を調査する必要がある
⚠️ロールアウトには 4 営業日以上かかる場合があり、完了までは機能が利用できないインスタンスがある

✅ まとめ

Apigee X で Cloud EKM を利用する CMEK 構成において、これまで検知が難しかった外部鍵マネージャー起因の障害 (鍵の無効化・到達不能など) を Cloud Logging で監視し、アラート通知できるようになりました。

EKM を利用している組織は、クエリ Apigee EKM key health issue detected を使ったログベースアラートを早期に設定し、 復旧通知が生成されない点を踏まえた運用手順 (鍵を使う操作による復旧確認) の整備を推奨します。
