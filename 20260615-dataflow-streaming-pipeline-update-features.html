Dataflow GA

📋 概要

Dataflow がストリーミングジョブのパイプライン更新機能を大幅に拡張しました。5 つの新機能が GA として利用可能になり、ストリーミングパイプラインのデプロイメントと運用管理が大幅に簡素化されます。

従来は手動で複数のステップを踏む必要があったパイプラインの入れ替え作業が、宣言的な API 呼び出しで自動化できるようになり、ダウンタイムの最小化とデータの整合性確保を両立できます。

🔄 Before / After 比較

❌ アップデート前

  • 手動で旧ジョブのドレイン開始・完了待ち・新ジョブ起動が必要
  • 破壊的変更時は手動の stop-and-replace が必須
  • ドレイン中のスタックに手動監視・介入が必要
  • 既存ジョブの有無を確認して create/update を切り替え
  • 同一ジョブ名での並列更新不可

✅ アップデート後

  • 宣言的 API で stop-and-replace の全プロセスを自動化
  • 同一ジョブ名での並列更新が可能に
  • タイムアウト設定でスタックジョブを自動キャンセル
  • 更新戦略の明示的選択が可能
  • テンプレートの upsert 方式で起動を簡素化

⭐ 主要機能 (5 つの新機能)

⚙️ 1. 自動化された Stop-and-Replace 更新

  • 宣言的なワークフローにより、手動のプロシージャルステップを排除
  • 新ジョブのリソースは旧ジョブ稼働中にプロビジョニング
  • 旧ジョブには自動的にドレインシグナルが送信される
  • ドレイン完了後（またはタイムアウト後）、新ジョブが即座にデータ処理を開始
  • 重複データ不可だが短い処理停止は許容できるパイプラインに最適

🔀 2. 同一ジョブ名での並列更新

  • --update フラグと update_strategy_parallel_job_update を組み合わせ
  • 前回のジョブ開始から最低 2 分後に新ジョブを開始可能
  • ジョブ名の一貫性が保たれ、モニタリングや運用管理が簡素化

⏰ 3. ドレイン中ジョブの自動キャンセル

  • parallel_replace_job_max_stop_duration でタイムアウトを指定
  • parallel_replace_job_cancel_on_drain_timeout はデフォルト true
  • タイムアウト後に旧ジョブを自動キャンセルしスタック状態を解消
  • false に設定すると自動キャンセルを無効化可能

🎯 4. 更新戦略の明示的設定

  • update_strategy_parallel_job_update: 並列更新（stop-and-replace を含む）
  • update_strategy_in_place_update: 標準のインプレース更新
  • 両戦略は排他的で、他の設定を変更せずに戦略のみを切り替え可能

📦 5. テンプレート Upsert 機能

  • create_or_update_job エクスペリメントを使用
  • Classic Templates、Flex Templates、Terraform、Config Connector に対応
  • アクティブジョブが存在すれば更新、存在しなければ新規作成
  • プログラム的なジョブ存在確認ロジックが不要に

🔧 技術仕様

サービスオプション一覧

オプション 必須/任意 説明
update_strategy_parallel_job_update 必須 (同一ジョブ名更新時) 並列更新を実行するための戦略指定
update_strategy_in_place_update 任意 標準インプレース更新を実行 (並列更新と排他的)
parallel_replace_job_max_stop_duration 必須 (Stop-and-Replace 時) ドレインの最大待機時間 (例: 30m, 1h)
parallel_replace_job_min_parallel_pipelines_duration 必須 (並列パイプライン更新時) 並列稼働の最小時間 (0s ~ 744h)
parallel_replace_job_name / parallel_replace_job_id 必須 (異なるジョブ名更新時) 旧ジョブの識別 (名前または ID)
parallel_replace_job_cancel_on_drain_timeout 任意 (デフォルト: true) タイムアウト時の自動キャンセルの有効/無効
create_or_update_job 任意 テンプレートの upsert 動作を有効化

Stop-and-Replace と並列パイプライン更新の使い分け

ワークフロー 使用条件 ユースケース
Stop-and-Replace max_stop_duration を設定し、min_parallel_pipelines_duration は設定しない 重複データ不可、短い処理停止は許容
並列パイプライン更新 min_parallel_pipelines_duration を設定 ダウンタイム最小化が最優先、重複データは許容可能

📝 設定方法

💡 前提条件: Google Cloud プロジェクトで Dataflow API が有効化されていること / Streaming Engine ジョブであること / 適切な IAM 権限 (Dataflow 管理者または編集者ロール)

自動 Stop-and-Replace 更新 (Java SDK)

Bash 同一ジョブ名で stop-and-replace 更新を実行 
# 同一ジョブ名で stop-and-replace 更新を実行
mvn compile exec:java -Dexec.mainClass=com.example.MyPipeline \
  -Dexec.args="--runner=DataflowRunner \
  --project=PROJECT_ID \
  --region=REGION \
  --jobName=MY_STREAMING_JOB \
  --update \
  --dataflowServiceOptions=update_strategy_parallel_job_update \
  --dataflowServiceOptions=parallel_replace_job_max_stop_duration=30m"

異なるジョブ名での更新 (Python SDK)

Bash 異なるジョブ名で更新を実行 
# 異なるジョブ名で更新を実行
python my_pipeline.py \
  --runner=DataflowRunner \
  --project=PROJECT_ID \
  --region=REGION \
  --job_name=MY_NEW_JOB \
  --dataflow_service_options="parallel_replace_job_name=MY_OLD_JOB" \
  --dataflow_service_options="parallel_replace_job_max_stop_duration=30m"

gcloud CLI でのテンプレート Upsert

Bash Flex Template の upsert 起動 
# Flex Template の upsert 起動
gcloud dataflow flex-template run MY_JOB_NAME \
  --template-file-gcs-location=gs://BUCKET/template.json \
  --region=REGION \
  --additional-experiments="create_or_update_job" \
  --additional-experiments="update_strategy_parallel_job_update" \
  --additional-experiments="parallel_replace_job_max_stop_duration=30m"

Terraform での設定

HCL Terraform による宣言的パイプライン管理 
resource "google_dataflow_flex_template_job" "streaming_job" {
  provider = google-beta
  name     = "my-streaming-job"
  region   = "us-central1"

  container_spec_gcs_path = "gs://my-bucket/templates/my-template.json"

  parameters = {
    inputSubscription = "projects/my-project/subscriptions/my-sub"
    outputTable       = "my-project:my_dataset.my_table"
  }

  additional_experiments = [
    "parallel_replace_job_max_stop_duration=30m",
    "parallel_replace_job_cancel_on_drain_timeout=true",
    "update_strategy_parallel_job_update",
    "create_or_update_job"
  ]
}

💡 ユースケース

🚀 CI/CD パイプラインでの自動デプロイ

シナリオ: GitHub Actions や Cloud Build からストリーミングパイプラインを自動デプロイ。コード変更がマージされるたびに新しいバージョンをデプロイ。

Bash Cloud Build ステップでの実行 
gcloud dataflow flex-template run my-etl-pipeline \
  --template-file-gcs-location=gs://my-bucket/templates/etl-v${BUILD_ID}.json \
  --region=us-central1 \
  --additional-experiments="create_or_update_job" \
  --additional-experiments="update_strategy_parallel_job_update" \
  --additional-experiments="parallel_replace_job_max_stop_duration=15m" \
  --additional-experiments="parallel_replace_job_cancel_on_drain_timeout=true"

効果: デプロイスクリプトが冪等になり、初回デプロイも再デプロイも同一コマンドで対応可能。

💹 ゼロダウンタイムを要求するリアルタイムデータパイプライン

シナリオ: 金融データのリアルタイム処理パイプラインで、ビジネスロジック更新時にデータ損失やダウンタイムを許容できない場合。

Bash 並列パイプライン更新 (最低 5 分間の並列稼働を保証) 
python my_pipeline.py \
  --runner=DataflowRunner \
  --project=my-project \
  --region=us-central1 \
  --job_name=financial-stream-processor \
  --update \
  --dataflow_service_options="update_strategy_parallel_job_update" \
  --dataflow_service_options="parallel_replace_job_min_parallel_pipelines_duration=5m" \
  --dataflow_service_options="parallel_replace_job_max_stop_duration=30m"

効果: 新旧パイプラインが最低 5 分間並列稼働し、データ処理の連続性が保証される。

📜 Terraform による宣言的なインフラ管理

シナリオ: Terraform で Dataflow パイプラインを管理。terraform apply のたびにジョブ状態に応じた適切な動作 (新規作成 or 更新) を自動で実行。

効果: Terraform の宣言的モデルとの親和性が高まり、ジョブのライフサイクル管理が単純化。状態ドリフトへの対応も容易に。

⚖️ メリット・デメリット

✅ ビジネス面のメリット

  • 運用コスト削減: パイプライン更新作業の自動化で手動オペレーション工数を大幅削減
  • ダウンタイム最小化: 並列更新やリソースの事前プロビジョニングでデータ処理中断を最小限に
  • リスク低減: 自動キャンセルやタイムアウト設定で長時間の二重課金を防止

✅ 技術面のメリット

  • 宣言的ワークフロー: 単一 API 呼び出しで CI/CD 統合が容易
  • IaC 親和性: Terraform / Config Connector 管理が大幅に簡素化
  • 柔軟な戦略選択: パイプライン特性に応じた最適戦略を選択可能
  • 冪等性: upsert 機能でテンプレート起動コードに冪等性を実現
⚠️ 制限事項・注意点
  • 自動更新は Streaming Engine ジョブのみ 対応 (Classic Streaming 非対応)
  • 同一ジョブ名更新は前回のジョブ開始から 最低 2 分のインターバル が必要
  • 並列パイプラインの同一入力ソース読み取りはデータ重複・順序問題の可能性あり
  • Pub/Sub: 同一サブスクリプションの複数パイプライン使用は非推奨
  • Kafka: 重複最小化にはオフセットコミットの有効化が必要
  • 自動キャンセル無効化時は、両ジョブ稼働によるコスト二重発生に注意

💰 料金情報

パイプライン更新機能自体に追加料金はありません。ただし以下のコストが発生します。

項目 料金への影響
並列稼働期間中の二重リソース 新旧両ジョブの vCPU、メモリ、ストレージが課金対象
Stop-and-Replace のリソース事前プロビジョニング 新ジョブリソースが旧ジョブ稼働中にプロビジョニングされ、短時間の二重課金が発生
Streaming Engine の使用 自動更新には Streaming Engine が必須 (追加料金なし)

ストリーミング入力ソースとして使用する場合、並列更新時のオフセットコミット設定が重要

📌 まとめ

今回の Dataflow ストリーミングパイプライン更新機能の拡張は、ストリーミングジョブの運用管理を根本的に改善するアップデートです。

🎯 推奨アクション: Terraform や Config Connector で Dataflow パイプラインを管理しているチームは、create_or_update_job エクスペリメントの導入を早期に検討することを推奨します。CI/CD パイプラインとの統合が大幅に容易になります。
