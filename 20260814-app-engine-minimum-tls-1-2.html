📋 概要

Google Cloud は 2026 年 8 月 14 日、App Engine の standard 環境および flexible 環境において、 アプリケーションを最小 TLS バージョン 1.2 以降へ自動的にオプトインすることを発表しました。 適用後は TLS 1.2 / 1.3 とサポート対象 cipher suite のみが許可され、TLS 1.1 以前の通信は拒否されます。

レガシー TLS が必要な場合は 2026 年 8 月末までコンソールまたは gcloud CLI からオプトアウト (TLS_VERSION_1_0) が可能ですが、2026 年 9 月以降は TLS 1.1 以前が恒久的にブロックされる可能性があり、 ブロック後はオプトアウト設定自体が選択できなくなります。より長い移行期間が必要な場合はサポートへの問い合わせが案内されています。

📌 対象ランタイム: 今回のリリースノートでは 6 つのランタイム向けに同一内容が告知 — flexible 環境: Go / Java / Ruby、standard 環境: Go / Python / Ruby (内容は共通)

❌ アップデート前の課題

  • TLS 1.2 以降の強制には利用者自身による SSL ポリシーの明示的な変更が必要で、未対応アプリは TLS 1.1 以前を受け付け続けていた
  • デフォルトが安全でない状態 (TLS 1.0+) のため、設定漏れがそのままセキュリティリスクとして残存
  • cipher suite / TLS バージョンの細かな制御にはグローバル外部 ALB + SSL ポリシーの構成が必要 (この点は現在も同様)

✅ アップデート後の改善

  • 既存アプリを TLS 1.2 以降へ自動オプトイン — 設定変更なしにセキュアなデフォルトが適用
  • 新規アプリは当初から TLS 1.2 以降 + サポート対象 cipher suite のみを許可
  • デフォルト設定で足りる場合、レガシー TLS ブロックのためのグローバル外部 ALB 構成が不要
  • 2026 年 9 月以降、appspot.com では TLS ハンドシェイク自体を拒否する接続レベルのブロックへ

App Engine フロントエンドが TLS バージョンを判定し、TLS 1.2 以降のみをアプリケーションへ通します。 既定の cipher suite で要件を満たせない場合、またはカスタムドメインでハンドシェイクレベルの拒否が必要な場合は、 グローバル外部 Application Load Balancer と SSL ポリシーを併用します。

⚡ 主要機能

1️⃣ 既存アプリケーションの TLS 1.2 以降への自動オプトイン

2026 年 8 月から、App Engine がアプリケーションを TLS 1.2 以降 (サポート対象 cipher suite 付き) へ自動的にオプトイン。対象は standard / flexible 環境 (Go / Java / Python / Ruby の各ランタイム向けに告知)。

2️⃣ 2026 年 8 月末までのオプトアウト

レガシー TLS 1.1 以前が必要な場合、コンソールまたは gcloud CLI からオプトアウト可能。期限は 2026 年 8 月末まで。追加の移行期間が必要な場合は Google Cloud サポートへ問い合わせ。

3️⃣ 2026 年 9 月以降の恒久的ブロック

TLS 1.1 以前の安全でないトラフィックを恒久的にブロックする可能性。appspot.com ドメインは接続レベルでブロック、カスタムドメインは接続成立の可能性はあるがリクエストがブロックされる。恒久ブロック後は SSL ポリシーの選択自体が利用不可に。

4️⃣ 新規アプリケーションのデフォルト変更

新規に作成する App Engine アプリケーションは、既定で TLS 1.2 以降とサポート対象 cipher suite のみを許可。

5️⃣ Application Load Balancer が不要になるケースの明確化

TLS 1.2 以降 + 既定の cipher suite で足りる場合、グローバル外部 ALB の構成は不要。別の cipher suite セットやカスタムドメインでのハンドシェイクレベル拒否が必要な場合のみ ALB を構成する。

🛠️ 設定方法

📌 前提条件

  • 対象の App Engine アプリケーション (standard / flexible 環境) が存在するプロジェクトへのアクセス権
  • アプリケーション設定を更新できる権限
  • gcloud CLI で操作する場合は gcloud のインストールと認証

ステップ 1: SSL ポリシーの確認・変更 (Google Cloud コンソール)

  1. App Engine の [設定 (Settings)] ページを開く
  2. [Application settings] タブで [Edit application settings] をクリック
  3. [SSL Policy] リストから選択:
    • TLS 1.2+ (Modern ciphers) (既定値): TLS 1.2 以降とモダンな cipher suite のみを許可
    • TLS 1.0+ (Obsolete): TLS 1.1 以前を許可 (オプトアウト)
  4. [Save] をクリック
⛔ 重要: 2026 年 9 月以降に古い TLS バージョンが恒久的にブロックされたプロジェクトでは、このオプトイン設定は選択できません。

ステップ 2: gcloud CLI で SSL ポリシーを設定

Bash SSL ポリシーの設定 
# 既存アプリケーションの最小 TLS バージョンを TLS 1.2 以降に設定 (推奨)
gcloud app update --ssl-policy=TLS_VERSION_1_2

# 新規アプリケーション作成時に最小 TLS バージョンを指定
gcloud app create --ssl-policy=TLS_VERSION_1_2

# レガシー TLS を許可する (オプトアウト / 2026 年 8 月末まで)
gcloud app update --ssl-policy=TLS_VERSION_1_0

--ssl-policy に指定できる値は TLS_VERSION_1_0 と TLS_VERSION_1_2 の 2 つです。Google は最新のサポート対象 TLS バージョンへのアップデートを推奨しています。

ステップ 3: (必要な場合) グローバル外部 ALB で TLS / cipher を制御

Bash ロードバランサ用 SSL ポリシーの作成例 
# 例: ロードバランサ用の SSL ポリシーを作成する
gcloud compute ssl-policies create modern-tls-policy \
    --profile=MODERN \
    --min-tls-version=1.2

カスタムドメインで TLS 1.1 以前の接続をハンドシェイクレベルで拒否したい場合、または既定と異なる cipher suite セットが必要な場合は、Cloud Load Balancing + サーバーレス NEG の構成が必要です。

💡 メリット

💼 ビジネス面

✓コンプライアンス要件への適合: PCI DSS など TLS 1.2 以降を求める各種セキュリティ基準への準拠が容易に
✓設定作業の削減: 自動オプトインにより多数のアプリを個別に設定変更する運用負荷が軽減
✓設定漏れリスクの排除: セキュアな設定がデフォルトになり、脆弱な構成が残るリスクを低減

⚙️ 技術面

✓ロードバランサ不要でのレガシー TLS ブロック: 既定の cipher suite で足りる場合、ALB なしで安全でないトラフィックをブロック可能
✓接続レベルでの拒否: 2026 年 9 月以降、appspot.com ではハンドシェイク自体が拒否され、外部スキャンツールにも正しく非対応と認識される
✓モダンな cipher suite への統一: AEAD 系 (GCM / ChaCha20-Poly1305) を中心に統一

⚠️ デメリット・制約事項

🚧 制限事項

✗オプトアウトが可能なのは 2026 年 8 月末まで。それ以降は選択できなくなる可能性がある
✗恒久的にブロックされたプロジェクトでは、SSL ポリシーのオプトイン設定自体が利用不可に
✗App Engine の SSL ポリシーは TLS_VERSION_1_0 / TLS_VERSION_1_2 の 2 択で、cipher suite の個別指定は不可
✗カスタムドメインでは 9 月以降もハンドシェイク自体は成立し得る。ハンドシェイクレベルの拒否にはグローバル外部 ALB が必要

🤔 考慮すべき点

  • クライアント側の互換性調査が急務: 古い OS / ブラウザ、組み込み機器、レガシー HTTP クライアント、社内バッチなど TLS 1.1 以前しか話せないクライアントは、8 月中は 400 Bad Request、9 月以降は接続不能に
  • 400 Bad Request の切り分け: 9 月より前はハンドシェイク成功後にリクエスト拒否となるため、アプリのバグと誤認しやすい。TLS バージョン起因を疑う
  • 外部 SSL チェックサイトの結果は当てにならない: ハンドシェイクの成否のみを検証するツールでは 9 月より前は誤表示される
  • 移行期間が足りない場合: 事前に Google Cloud サポートへ問い合わせが必要
  • 設定はアプリケーション単位: SSL ポリシーはアプリ (プロジェクト) レベルの設定で、サービスやバージョン単位では変更不可

🎯 ユースケース

📦 ユースケース 1: レガシークライアントを抱える B2B API の段階的移行

シナリオ: App Engine standard 環境 (Python) の B2B API に、取引先の古いシステムから TLS 1.1 でアクセスがある。8 月の自動オプトインでの即時障害を回避したい。

Bash一時オプトアウトと切り戻し
# 一時的にオプトアウトして移行猶予を確保する (2026 年 8 月末まで)
gcloud app update --ssl-policy=TLS_VERSION_1_0

# 取引先のクライアント改修完了後、TLS 1.2 以降へ切り替える
gcloud app update --ssl-policy=TLS_VERSION_1_2

効果: 取引先の改修スケジュールに合わせて切り替えタイミングを制御できる。ただし 8 月末以降はオプトアウト不可となるため、期限内の改修完了とサポートへの事前相談が前提。

🛡️ ユースケース 2: コンプライアンス監査に向けた TLS 1.2 以降の強制

シナリオ: TLS 1.2 以降を必須とするセキュリティ基準の監査を控え、flexible 環境 (Java) で TLS 1.1 以前が確実に拒否されることを証明したい。

Bash強制設定と検証
# 明示的に TLS 1.2 以降を強制する
gcloud app update --ssl-policy=TLS_VERSION_1_2

# TLS 1.1 でのアクセスを試行して拒否されることを確認する
curl -v --tlsv1.1 --tls-max 1.1 https://PROJECT_ID.REGION_ID.r.appspot.com/

効果: サポート対象 cipher suite に限定された TLS 1.2 / 1.3 のみで配信。2026 年 9 月以降 appspot.com ではハンドシェイク自体が拒否され、外部スキャンツールでも正しく非対応と判定される。

⚖️ ユースケース 3: カスタムドメインでのハンドシェイクレベル拒否

シナリオ: カスタムドメインで公開中のアプリで、TLS 1.1 以前を「リクエスト拒否」ではなく「ハンドシェイク拒否」にしたい。あるいは既定と異なる cipher suite セットが必要。

効果: グローバル外部 ALB + サーバーレス NEG を構成し、SSL ポリシーで TLS バージョン / cipher を制御することで、接続レベルの拒否と柔軟な cipher suite 制御が可能に。あわせて Ingress 制御で App Engine URL 経由のロードバランサバイパスを防止することが推奨される。

💰 料金

今回のリリースノートおよび公式ドキュメントには、この TLS 設定変更に伴う料金の変更に関する記載はありません。 App Engine の SSL ポリシー設定自体は、アプリケーションレベルの設定として提供されています。

🔗 関連サービス・機能

  • Cloud Load Balancing (グローバル外部 ALB): 既定以外の cipher suite サポートやカスタムドメインでのハンドシェイクレベル拒否に必要。SSL ポリシーで TLS バージョン / cipher を制御
  • サーバーレス NEG: Cloud Load Balancing から App Engine アプリへトラフィックをルーティングする構成要素
  • SSL ポリシー: ロードバランサがクライアントとネゴシエートする TLS バージョン / cipher を定義する仕組み
  • App Engine カスタムドメインの SSL (Google 管理証明書): カスタムドメインの HTTPS 配信を自動化。TLS ポリシーとあわせて構成を確認
  • App Engine の Ingress 制御: ロードバランサを経由しない直接アクセスを制限し、Cloud Armor や SSL ポリシーのバイパスを防止
  • Cloud Run へのマイグレーション: flexible 環境では 2026 年 6 月に gcloud beta app migrate-to-run による移行が Preview 提供。長期的なモダナイゼーションの選択肢
