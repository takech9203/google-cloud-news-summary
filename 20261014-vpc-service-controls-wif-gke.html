🛡️ VPC Service Controls: Workload Identity Federation for GKE のイングレス/エグレスルール対応

VPC Service Controls Preview 📅 リリース日: 2026-10-14

イングレス/エグレスルールで GKE Pod の Kubernetes アイデンティティ (Kubernetes サービスアカウント / Namespace / クラスタ) を直接プリンシパルとして指定できるようになりました。中間 IAM サービスアカウントの impersonation なしで、境界をまたぐアクセスを最小権限で制御できます。

📋 概要

VPC Service Controls のイングレスルールおよびエグレスルールで、Workload Identity Federation for GKE のプリンシパルを指定可能に (Preview)。サービス境界で保護されたリソースへのアクセスを、GKE Pod の Kubernetes アイデンティティ単位で許可できます。

❌ Before: アップデート前の課題

  • GKE Pod の Kubernetes アイデンティティをルールのプリンシパルとして直接指定できなかった
  • 境界をまたぐアクセスには中間 IAM サービスアカウントへの impersonation (借用) 構成が必須だった
  • Namespace やクラスタといった Kubernetes の論理単位で制御粒度を揃えられなかった

✅ After: アップデート後の改善

  • Kubernetes サービスアカウント (名前 / ID)、Namespace、クラスタを直接プリンシパル指定可能に
  • impersonation を介さずに cross-perimeter access を許可できる
  • Kubernetes の運用単位に沿った最小権限ポリシーを定義できる
💡 対象ユーザー: GKE ワークロードから境界をまたいで保護リソースにアクセスする構成を設計するセキュリティ管理者や、サービス境界を運用するプラットフォームチームに有用なアップデートです。

サービス境界の外側にある GKE Pod が、Workload Identity Federation for GKE のアイデンティティ (Kubernetes サービスアカウント / Namespace / クラスタ) を根拠に、イングレスルールで許可された保護リソースへアクセスする構成です。ルールに合致しないアイデンティティからのアクセスは境界で拒否されます。

⚙️ 主要機能

1️⃣ Kubernetes サービスアカウント単位のプリンシパル指定

特定の Kubernetes サービスアカウントを使用するすべての GKE Pod を、サービスアカウント名または ID (UID) で指定可能。Pod 単位ではなくアイデンティティ単位で制御するため、Pod の再作成やスケールに影響されません。

2️⃣ Namespace 単位のプリンシパル指定

サービスアカウントやクラスタを問わず、特定の Kubernetes Namespace 内のすべての GKE Pod を principalSet で一括指定可能。チームや環境 (prod / staging など) を Namespace で分離している場合に、その単位でアクセスを許可できます。

3️⃣ クラスタ単位のプリンシパル指定

特定の GKE クラスタ内のすべての Pod を principalSet で一括指定可能。クラスタ全体を信頼単位としたシンプルなポリシー設計ができます。

4️⃣ IAM 形式と SPIFFE 形式の両方をサポート

完全な IAM プリンシパル識別子形式と、等価な SPIFFE 形式のどちらでも指定可能。SPIFFE 構文で作成したルールを含むサービス境界を describe / 取得すると、アイデンティティは SPIFFE 形式で返されます。

🔬 技術仕様: 指定可能なプリンシパル形式

プリンシパルタイプ 識別子形式
🔑 Kubernetes サービスアカウント名で指定 (単一) principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/NAMESPACE/sa/KUBERNETES_SERVICE_ACCOUNT
🆔 Kubernetes サービスアカウント ID で指定 (単一) principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/kubernetes.serviceaccount.uid/SERVICEACCOUNT_ID
📁 Namespace 内のすべての Pod principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/namespace/NAMESPACE
🚢 クラスタ内のすべての Pod principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/kubernetes.cluster/https://container.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/clusters/CLUSTER_NAME
🏷️ SPIFFE 形式 (サービスアカウント指定の例) principal://PROJECT_ID.svc.id.goog/ns/NAMESPACE/sa/KUBERNETES_SERVICE_ACCOUNT

📄 イングレスルールでの指定例

YAML ingress-policy.yaml (イングレスルールの例) 
- ingressFrom:
    identities:
    - principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/prod/sa/app-reader
    sources:
    - resource: projects/GKE_PROJECT_NUMBER
  ingressTo:
    operations:
    - serviceName: storage.googleapis.com
      methodSelectors:
      - method: "*"
    resources:
    - "*"

🛠️ 設定方法

✅ 前提条件

✓GKE クラスタで Workload Identity Federation for GKE が有効化されていること (有効化すると PROJECT_ID.svc.id.goog 形式の Workload Identity Pool がプロジェクトに作成される)
✓VPC Service Controls のサービス境界が構成済みで、アクセスポリシーを管理する権限があること
✓イングレス/エグレスルールの仕様 (Ingress and egress rules) を理解していること
1

イングレス (またはエグレス) ポリシーファイルを作成

Workload Identity Federation for GKE プリンシパルを identities 属性に指定します。

Bash ポリシーファイルの作成 (Namespace 単位の例) 
cat > ingress-policy.yaml <<EOF
- ingressFrom:
    identities:
    - principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/namespace/prod
    sources:
    - resource: projects/GKE_PROJECT_NUMBER
  ingressTo:
    operations:
    - serviceName: storage.googleapis.com
      methodSelectors:
      - method: "*"
    resources:
    - "*"
EOF
2

サービス境界を更新

Bash gcloud でイングレスポリシーを適用 
gcloud access-context-manager perimeters update PERIMETER_NAME \
  --set-ingress-policies=ingress-policy.yaml \
  --policy=POLICY_ID

更新後、gcloud access-context-manager perimeters describe でルールが反映されたことを確認します (SPIFFE 構文で作成したルールは SPIFFE 形式で返されます)。

💪 メリット

💼 ビジネス面

  • 最小権限の徹底によるリスク低減: 境界をまたぐアクセスを必要なワークロードのアイデンティティ (サービスアカウント / Namespace / クラスタ) に限定でき、データ流出リスクを抑制
  • 運用コストの削減: 中間 IAM サービスアカウントの作成・管理・impersonation 構成が不要になり、構成の複雑さと管理対象が減少

🔧 技術面

  • Kubernetes ネイティブな粒度での制御: サービスアカウント、Namespace、クラスタに対応したポリシーを記述可能
  • キーレス認証との一貫性: WIF for GKE の短期トークンに基づくキーレス認証を境界制御までエンドツーエンドで活用
  • 柔軟な識別子形式: IAM プリンシパル識別子形式と SPIFFE 形式の両方で指定可能

⚠️ デメリット・制約事項

🚧 制限事項
  • Preview 段階の機能であり、Pre-GA Offerings Terms が適用される (サポートが限定される可能性あり)
  • アクセスポリシーあたり WIF for GKE プリンシパルは 1,000 個までという上限がある
  • WIF for GKE プリンシパルは、削除済みプリンシパル構文 (deleted principal syntax) をサポートしない
  • WIF for GKE を含むサードパーティ系アイデンティティは、イングレス/エグレスルールでのみ指定可能で、Access Context Manager のアクセスレベルでは使用できない
🤔 考慮すべき点
  • クラスタや Namespace 単位の principalSet は便利な一方、許可範囲が広くなるため、機密性の高いリソースへはサービスアカウント単位の指定を検討する
  • 前提として GKE クラスタで Workload Identity Federation for GKE を有効化しておく必要がある

🎯 ユースケース

📦 ユースケース 1: 境界外の GKE アプリから保護された Cloud Storage への限定アクセス

シナリオ: データ分析基盤のプロジェクトを VPC Service Controls で保護しており、別プロジェクトの GKE クラスタで稼働するバッチアプリケーションから保護された Cloud Storage バケットへ読み取りアクセスさせたい。

YAML サービスアカウント単位での許可例 
- ingressFrom:
    identities:
    - principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/batch/sa/gcs-reader
    sources:
    - resource: projects/GKE_PROJECT_NUMBER
  ingressTo:
    operations:
    - serviceName: storage.googleapis.com
      methodSelectors:
      - method: "*"
    resources:
    - "*"

✨ 効果: 中間 IAM サービスアカウントの impersonation 構成なしで、特定の Kubernetes サービスアカウントを使う Pod のみに境界内リソースへのアクセスを許可できる。

👥 ユースケース 2: Namespace 単位でのチーム別アクセス許可

シナリオ: マルチテナントの GKE クラスタで、チームごとに Namespace を分離して運用している。prod Namespace のワークロードにのみ、境界で保護された BigQuery へのアクセスを許可したい。

✨ 効果: principalSet://.../namespace/prod を指定することで、サービスアカウントやクラスタを個別に列挙せずに Namespace 単位で一括許可でき、チームの追加・変更時のポリシー管理が簡素化される。

🔗 関連サービス・機能

  • 🔑 Workload Identity Federation for GKE: GKE ワークロードがサービスアカウントキーなしで Google Cloud API に認証するための仕組み。本アップデートのプリンシパルの基盤で、クラスタで有効化すると PROJECT_ID.svc.id.goog の Workload Identity Pool が作成される
  • 🚪 Access Context Manager: サービス境界やアクセスレベルを管理するサービス。WIF for GKE プリンシパルはアクセスレベルでは使用できず、イングレス/エグレスルールでのみ指定可能
  • 🌐 IAM Workload Identity Federation / Workforce Identity Federation: 外部ワークロード・人材のアイデンティティ連携。これらのプールのプリンシパルも同様にイングレス/エグレスルールで指定できる
  • 🚢 GKE (Google Kubernetes Engine): 本機能の対象となるワークロード実行環境

📝 まとめ

VPC Service Controls のイングレス/エグレスルールで Workload Identity Federation for GKE プリンシパルを直接指定できるようになり、GKE ワークロードの境界をまたぐアクセスを中間 IAM サービスアカウントなしで最小権限に制御できるようになりました。GKE とサービス境界を併用している環境では、既存の impersonation ベースの構成を簡素化できる可能性があるため、Preview 段階で評価を始めることを推奨します。本番適用にあたっては、アクセスポリシーあたり 1,000 プリンシパルの上限と Pre-GA 利用条件に留意してください。
