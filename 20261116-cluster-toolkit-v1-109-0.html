🛠️ Cluster Toolkit v1.109.0 リリース

hostNetwork の無効化 (Breaking Change) と新機能群
📅 リリース日: 2026-11-16
🏷️ HPC / AI / ML クラスタ構築ツール

📋 概要

Cluster Toolkit は、ブループリント (YAML) と再利用可能なモジュールで Google Cloud のベストプラクティスに沿った HPC / AI / ML クラスタを効率的にプロビジョニングするオープンソースツール。v1.109.0 には Breaking Change と重要なセキュリティ修正が含まれる。

⚠️ Breaking Change: gcluster job submit に --service-account フラグを渡すと、 Cloud TPU / Pathways ワークロードで hostNetwork が無効化される。Pod はノードプールのサービスアカウントではなく、 Workload Identity Federation for GKE で認証されるようになる。GPU ジョブは従来通り hostNetwork: true を維持。

🔄 Before / After

❌ アップデート前の課題
  • --service-account 指定の TPU/Pathways ジョブでも hostNetwork が有効で、Workload Identity Federation 構成と不整合
  • Slurm クラスタにブラウザベースのデスクトップ環境の標準手段がなかった
  • プライベートレジストリ利用時は --image-pull-secret の明示指定が必須
  • batch-job-template でインスタンステンプレート使用時にカスタムサービスアカウントを指定できない
  • 旧来の schedmd-slurm-gcp-v6-nodeset-tpu パーティションの job_submit.lua にコマンドインジェクション脆弱性
✅ アップデート後の改善
  • TPU/Pathways ジョブは hostNetwork 無効化により Workload Identity Federation で Pod 単位認証
  • remote-desktop モジュールでブラウザベースの noVNC デスクトップが利用可能に
  • kubernetes.io/dockerconfigjson シークレットを自動検出してイメージプルに使用
  • インスタンステンプレートとカスタムサービスアカウントの併用が可能に
  • job_submit.lua のパーティション名検証でコマンドインジェクションを防止

v1.109.0 では、--service-account 指定時の TPU/Pathways ジョブが hostNetwork 無効化により Workload Identity Federation で認証されるようになり (Breaking)、GKE・Slurm 双方に新機能が追加された。

💥 Breaking Change: hostNetwork の無効化

gcluster job submit に --service-account フラグを渡した場合の動作変更。

✓Pod は Workload Identity Federation for GKE を使用して、指定した Kubernetes サービスアカウントとして認証
✓GPU ジョブは hostNetwork: true を維持し、GKE ノードプールのサービスアカウントとして認証
✗hostNetwork に依存したネットワーク構成 (ホストのネットワーク名前空間を前提とした通信など) を TPU/Pathways ジョブで使用している場合は影響を受けるため、アップグレード前に確認が必要

📊 --service-account フラグの動作 (v1.109.0 以降)

ワークロード種別hostNetworkPod の認証方法
⚡ Cloud TPU ジョブ 無効 (Breaking Change) Workload Identity Federation for GKE (指定したサービスアカウント)
🧭 Pathways ジョブ 無効 (Breaking Change) Workload Identity Federation for GKE (指定したサービスアカウント)
🎮 GPU ジョブ hostNetwork: true (従来通り) GKE ノードプールのサービスアカウント

✨ 主要機能 (7 つのアップデート)

🖱️ ① Slurm 向けブラウザベース noVNC デスクトップ
新しい remote-desktop モジュールで、ブラウザから Slurm クラスタのグラフィカルデスクトップにアクセス可能。可視化ツールや GUI アプリの利用が容易に。
🚀 ② GKE 上の A5X ベアメタル対応
A5X ベアメタルインスタンスを GKE で利用するためのブループリントサポートを追加。大規模 AI ワークロード向け最新ハードウェアをプロビジョニング可能。
📈 ③ ML Diagnostics サイドカーコンテナ
ML Diagnostics コレクターをネイティブサイドカーとして追加。gcluster job にテレメトリポート用フラグも追加され、診断性が向上。
🧭 ④ --pathways-run-sps-workload フラグ
Shared Pathways Service (SPS) ワークロード実行用フラグを追加。gcluster job inspect に --filter=pathways-sps フィルタも追加。
🔑 ⑤ イメージプルシークレットの自動検出
ターゲット Namespace 内の kubernetes.io/dockerconfigjson シークレットを自動検出。プライベートレジストリ利用時の明示指定が不要になるケースが増加。
👤 ⑥ batch-job-template のカスタム SA 対応
Compute Engine インスタンステンプレートとカスタムサービスアカウントの併用が可能に。Batch ジョブの最小権限構成がしやすくなった。
🛡️ ⑦ Slurm パーティション名の検証 (セキュリティ強化)
job_submit.lua でパーティション名を検証しコマンドインジェクションを防止。旧来の schedmd-slurm-gcp-v6-nodeset-tpu パーティション利用クラスタが対象 (v1.98.0 以降は Slurm 25.05 以上で影響、より古い Toolkit は全 Slurm バージョンで影響)。適用には v1.109.0 へのアップグレード + gcluster deploy + コントローラノード再起動が必要。

⚙️ 技術仕様: 主な追加・変更フラグ

🔧 設定方法

📌 前提条件

✓Cluster Toolkit v1.109.0 (gcluster バイナリ) の取得・ビルド
✓GKE クラスタまたは Slurm クラスタのデプロイ環境 (gcloud、kubectl、Terraform など)
✓TPU/Pathways ジョブで --service-account を使用する場合、Workload Identity Federation for GKE の構成

ステップ 1: Cluster Toolkit を v1.109.0 に更新

Bash gcluster バイナリのビルド 
git clone https://github.com/GoogleCloudPlatform/cluster-toolkit.git
cd cluster-toolkit
git checkout v1.109.0
make

ステップ 2: (Slurm TPU パーティション利用時) セキュリティ修正の適用

Bash 再デプロイとコントローラ再起動 
./gcluster deploy <デプロイメントフォルダ>
# デプロイ後、Slurm コントローラノードを再起動

schedmd-slurm-gcp-v6-nodeset-tpu パーティションを使用するクラスタでは、再デプロイとコントローラノードの再起動によりコマンドインジェクション対策を適用する。

ステップ 3: サービスアカウントを指定したジョブの送信

Bash gcluster job submit (Workload Identity Federation 認証) 
./gcluster job submit \
  --cluster=CLUSTER_NAME \
  --project=PROJECT_ID \
  --location=LOCATION \
  --name=train-job \
  --image=IMAGE \
  --compute-type=v5litepod-32 \
  --command="python3 train.py" \
  --service-account=KSA_NAME

TPU/Pathways ジョブでは hostNetwork が無効化され、Workload Identity Federation for GKE を介して指定サービスアカウントで認証される。

⚖️ メリットと制約事項

👍 メリット
  • セキュリティ体制の強化: Workload Identity Federation によるワークロード単位の最小権限認証と、Slurm のコマンドインジェクション対策でリスク低減
  • 運用負荷の軽減: イメージプルシークレット自動検出や noVNC デスクトップで手作業・追加ツール整備が不要に
  • Pod 単位の ID 分離: ノードのサービスアカウントに依存しない、きめ細かな IAM 制御が可能
  • 最新ハードウェア対応: A5X ベアメタル (GKE) で大規模 AI ワークロードの基盤選択肢が拡大
  • 診断性の向上: ML Diagnostics サイドカー化とテレメトリポートフラグで観測・診断が容易に
⚠️ 制約・注意点
  • Breaking Change のため、--service-account 指定の既存 TPU/Pathways ジョブで hostNetwork 前提の構成は動作が変わる
  • GPU ジョブは引き続き hostNetwork: true のため、認証挙動が TPU/Pathways と異なる点に注意
  • セキュリティ修正の適用にはアップグレード + gcluster deploy + コントローラノード再起動が必要
  • Workload Identity Federation の事前構成 (KSA と IAM の紐付け) を確認すること
  • シークレット自動検出で意図しないシークレットが使われないよう、Namespace 内のシークレット管理を見直すこと
⚠️ 推奨: 旧来の schedmd-slurm-gcp-v6-nodeset-tpu パーティションを使用しているクラスタは、速やかに v1.109.0 へアップグレードすることが推奨される (ネイティブ GCE TPU ノードセットは影響なし)。

💡 ユースケース

🎯 ユースケース 1: TPU トレーニングジョブの最小権限化

シナリオ: 複数チームが共有する GKE クラスタ上で TPU トレーニングジョブを実行しており、チームごとに異なる Cloud Storage バケットや BigQuery データセットへのアクセス権限を分離したい。

Bash チーム専用 KSA でのジョブ送信例 
./gcluster job submit \
  --cluster=shared-ai-cluster \
  --project=my-project \
  --location=us-central1 \
  --name=team-a-train \
  --image=us-docker.pkg.dev/my-project/team-a/train:v1 \
  --compute-type=v5litepod-32 \
  --command="python3 train.py" \
  --service-account=team-a-ksa

効果: hostNetwork が無効化され、ジョブはチーム専用の Kubernetes サービスアカウント経由で Workload Identity Federation 認証されるため、ノードのサービスアカウント権限に依存しない最小権限構成を実現できる。

🖥️ ユースケース 2: Slurm クラスタでの可視化作業

シナリオ: HPC シミュレーションの結果を GUI ベースの可視化ツールで確認したいが、ローカルに VNC クライアントを導入せずブラウザだけで完結させたい。

効果: remote-desktop モジュールの noVNC デスクトップにより、ブラウザから直接 Slurm クラスタのデスクトップ環境へアクセスでき、可視化・デバッグ作業の環境準備が大幅に簡素化される。

📝 まとめ

Cluster Toolkit v1.109.0 は、TPU/Pathways ジョブにおける hostNetwork 無効化という Breaking Change と、 Slurm のコマンドインジェクション対策という重要なセキュリティ修正を含むリリース。 --service-account を使用している TPU/Pathways ワークロードの挙動変更を確認したうえで、 特に旧来の Slurm TPU パーティションを使用しているクラスタは速やかに v1.109.0 へアップグレードし、 再デプロイとコントローラノードの再起動を実施することを推奨する。
