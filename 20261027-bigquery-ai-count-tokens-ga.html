🔢 AI.COUNT_TOKENS 関数が一般提供 (GA) に

SQL だけでプロンプトのトークン数を事前見積もり — AI 関数のコスト管理を本番ワークフローへ
📅 リリース日: 2026-10-27

📋 概要

BigQuery の AI.COUNT_TOKENS 関数が GA (一般提供) となった。テキスト文字列のトークン数を SQL クエリ内で直接見積もるユーティリティ関数で、AI 関数の利用コストはトークン数に基づいて課金されるため、 AI.GENERATE などの呼び出しコストを実行前に把握できる。

トークンカウント処理は BigQuery 内で実行されるため、この関数自体は Vertex AI 側の課金を発生させないのが大きな特長。見積もり対象は入力トークン数のみで、 思考 (thinking) トークンや出力トークンは含まれない。実際に処理されたトークン数はクエリ結果ペインの「ジョブ情報」タブで確認できる。

❌ Before (アップデート前の課題)

  • Preview ステータスのため GA レベルの提供条件が適用されず、本番ワークロードへの組み込みには慎重な判断が必要だった
  • Preview 以前は BigQuery SQL 内でトークン数を事前見積もりする手段がなく、AI.GENERATE 等の実行コストを事前に把握できなかった
  • コスト確認は Cloud Billing レポートなどによる事後確認が中心で、実行前のコスト予測が困難だった

✅ After (アップデート後の改善)

  • GA となり、本番環境のコスト見積もり・コスト管理ワークフローに正式に利用可能に
  • 任意のテキスト入力のトークン数を SQL で即座に見積もれる (BigQuery 内で処理、Vertex AI 課金なし)
  • endpoint 引数でモデルを指定すると、使用予定モデルのトークン化ルールに基づいた見積もりが可能
🎯 対象ユーザー: BigQuery で生成 AI 関数を活用するデータエンジニア、データサイエンティスト、アナリスト

⚡ 主要機能

1️⃣ SQL 内でのトークン数見積もり

→テキスト文字列 (STRING) の入力トークン数を SQL クエリ内で直接見積もる
→例: SELECT AI.COUNT_TOKENS("Token count isn't always equal to word count.").result → 結果は約 11
→テーブルの列に適用し、行ごとのトークン数を一括で算出することも可能

2️⃣ モデル指定によるトークン化ルールの選択

→endpoint 引数で生成 AI モデル名を指定すると、そのモデルのトークン化ルールでカウント
→endpoint を省略した場合は、AI.GENERATE 関数のデフォルトモデルを使用

3️⃣ Vertex AI 課金なしのコスト見積もり

→トークンカウントは BigQuery 内で処理され、この関数は Vertex AI の課金を発生させない
→見積もり対象は入力トークンのみ (思考トークン・出力トークンは含まれない)
→実際のトークン消費量はクエリ結果ペインの「ジョブ情報」タブで確認可能

🔧 技術仕様

関数シグネチャ

SQL AI.COUNT_TOKENS 関数シグネチャ 
AI.COUNT_TOKENS(
  INPUT
  [, endpoint => ENDPOINT]
)

引数と出力

項目詳細
INPUTトークン数をカウントする入力テキスト (STRING)
ENDPOINTトークン化ルールに使用する生成 AI モデル名 (STRING リテラル、省略可)。省略時は AI.GENERATE のデフォルトモデルを使用
戻り値STRUCT 値
result入力の合計トークン数 (INT64)。入力が NULL または API エラー時は NULL
full_response入力のモダリティとトークン数を含む JSON。入力が NULL または API エラー時は NULL

出力例

SQL テーブル列へのトークンカウント適用 
SELECT review, AI.COUNT_TOKENS(review).*
FROM `bigquery-public-data.imdb.reviews`
LIMIT 2;

💡 メリット

💼 ビジネス面

✓コストの事前予測: AI 関数実行前にトークン数を把握でき、大規模データセットに対する生成 AI 処理のコストを事前見積もりして予算超過を防止
✓見積もり自体が低コスト: BigQuery 内処理で Vertex AI 課金が発生せず、見積もりのための追加コストを最小限に抑制
✓GA による本番利用の安心感: 本番環境のコスト管理ワークフローへ正式に組み込める

⚙️ 技術面

✓SQL 完結のワークフロー: 外部ツールや SDK (Vertex AI の countTokens API など) を使わず、BigQuery の SQL だけでトークン見積もりから AI 関数実行まで完結
✓モデル別のトークン化ルール対応: endpoint 引数により、実際に使用するモデルに即した正確な見積もりが可能
✓詳細情報の取得: full_response の JSON からモダリティ別のトークン数を取得でき、プログラマティックな処理に活用可能

⚠️ デメリット・制約事項

制限事項

✗見積もり対象は入力トークン数のみで、思考 (thinking) トークンや出力トークンの数は結果に含まれない
✗入力が NULL の場合や API エラーが発生した場合、result と full_response は NULL になる
✗入力は STRING 型のテキストが対象
⚠️ 考慮すべき点:
  • あくまで「見積もり (estimate)」であり、実際にクエリで処理された正確なトークン数は、クエリ結果ペインの「ジョブ情報」タブでの確認が必要
  • 出力トークン数は実行してみないと分からないため、総コストの厳密な事前算出はできない
  • トークン単位の課金管理には、BigQuery のトークンクォータ (AI input/output tokens per day) の設定も併せて検討するとよい

🎯 ユースケース

📊 ユースケース 1: 大規模バッチ推論前のコスト見積もり

シナリオ: 数百万行のレビューデータに AI.GENERATE で感情分析を実行する前に、入力トークンの総量を見積もり、コストを予測したい。

SQL 入力トークン総量の見積もり 
SELECT
  SUM(AI.COUNT_TOKENS(review).result) AS total_input_tokens
FROM `bigquery-public-data.imdb.reviews`;

効果: Vertex AI の課金を発生させずに入力トークン総量を把握し、モデルの単価と掛け合わせて推論コストの概算を事前に算出できる。

✂️ ユースケース 2: プロンプト設計の最適化

シナリオ: AI.GENERATE に渡すプロンプトテンプレートを複数案比較し、トークン効率のよいものを選定したい。

効果: 各テンプレート案のトークン数を SQL で即座に比較でき、同等の品質でトークン消費 (コスト) の少ないプロンプトを選択できる。

💰 料金

✅ Vertex AI 課金なし: AI.COUNT_TOKENS のトークンカウント処理は BigQuery 内で実行され、この関数自体は Vertex AI の課金を発生させない。

クエリの実行に使用するコンピュートリソースについては、通常の BigQuery の料金体系が適用される。詳細は BigQuery の料金ページ を参照。

🔗 関連サービス・機能

🤖 AI.GENERATE / AI.GENERATE_TEXT

推論を実行する汎用生成 AI 関数。AI.COUNT_TOKENS はこれらの呼び出しコスト見積もりに使用し、endpoint 省略時は AI.GENERATE のデフォルトモデルのトークン化ルールが適用される。

🏷️ AI.CLASSIFY / AI.IF / AI.SCORE / AI.AGG

マネージド AI 関数。トークン使用量が Vertex AI 課金に直結するため、事前見積もりと組み合わせたコスト管理が有効。

📏 トークンクォータ (Control costs with token quotas)

プロジェクト単位・ユーザー単位で 1 日あたりの入力/出力トークン数に上限を設定できる BigQuery のコスト管理機能。AI.COUNT_TOKENS による事前見積もりと併用することで多層的なコスト管理が可能。

☁️ Vertex AI

BigQuery の生成 AI 関数のバックエンド。AI.COUNT_TOKENS 自体は Vertex AI の課金を発生させない。

📝 まとめ

AI.COUNT_TOKENS 関数の GA 昇格により、BigQuery の生成 AI 関数を使う際のコスト見積もりを本番環境のワークフローに正式に組み込めるようになった。 トークンカウントは BigQuery 内で完結し Vertex AI の課金が発生しないため、大規模バッチ推論の実行前見積もりやプロンプト最適化に気軽に活用できる。 生成 AI 関数を本番運用しているチームは、トークンクォータと組み合わせたコスト管理体制の整備を推奨する。
