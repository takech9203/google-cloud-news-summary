☁️ 概要

Gemini Enterprise Agent Platform のネットワーキングコンポーネントである Agent Gateway が一般提供 (GA) となった。Agent Gateway は、エージェントエコシステムにおけるすべてのエージェンティックなインタラクションを保護・ガバナンスするためのセキュリティゲートウェイである。

IAP (Identity-Aware Proxy)、Model Armor、Semantic Governance Policies などと連携し、多層的なセキュリティを提供する。Client-to-Agent (Ingress) モードと Agent-to-Anywhere (Egress) モードの 2 つのデプロイメントモードをサポート。

🔄 Before / After

❌ Before (課題)

  • エージェント間通信のセキュリティを個別管理
  • アウトバウンド通信の一元的アクセス制御が困難
  • AI 固有のセキュリティリスクへのネットワーク防御不足
  • エージェント通信の可視性が限定的

✅ After (改善)

  • 統一ゲートウェイで全通信を一元管理
  • IAP + Model Armor + Semantic Governance の多層防御
  • 最小権限モデルによるデフォルトブロック
  • Cloud Logging / Trace で包括的な可観測性
  • mTLS + DPoP による自動暗号化

⭐ 主要機能

🛡️ Client-to-Agent (Ingress)

クライアントからエージェントへの通信を保護。アクセスできるクライアントとセキュリティポリシーを制御。query / streamQuery メソッドをサポート。

🌐 Agent-to-Anywhere (Egress)

エージェントから外部サーバー、ツール、API への通信を保護。MCP サーバーへのアクセス制御を実現。Agent Runtime / Gemini Enterprise 両方をサポート。

🔒 多層的アクセス制御

IAP 認証・認可 (デフォルト有効)、Model Armor (プロンプトインジェクション防止)、Semantic Governance (コンテキスト認識)、Service Extensions (カスタム認可) を統合。

🔗 プロトコルサポート

MCP A2A REST gRPC

フレームワーク非依存で動作

📋 Agent Registry 統合

未登録リソースへのアクセスをデフォルトでブロック。エージェント・ツール・MCP サーバーの一元管理。ツール名や読み取り/書き込み権限に基づく細粒度制御。

⚙️ 技術仕様

項目 詳細
デプロイメントモード Client-to-Agent (Ingress) / Agent-to-Anywhere (Egress)

🛠️ 設定方法

💡 前提条件: Gemini Enterprise Agent Platform が有効、Agent Registry にリソース登録済み、Agent Identity が構成済みであること。

Step 1: Agent Gateway リソースの作成

Bash 
# Agent-to-Anywhere (Egress) モードでゲートウェイを作成
gcloud beta agent-gateways create GATEWAY_NAME \
  --project=PROJECT_ID \
  --location=REGION \
  --mode=agent-to-anywhere

Step 2: エージェントデプロイ時にゲートウェイを指定

Python 
remote_agent = client.agent_engines.create(
    agent=local_agent,
    config={
        "agent_gateway_config": {
            "agent_to_anywhere_config": {
                "agent_gateway": "projects/PROJECT_ID/locations/REGION/agentGateways/GATEWAY_ID"
            },
        },
        "identity_type": types.IdentityType.AGENT_IDENTITY,
    },
)

Step 3: IAM ポリシーバインディングの設定

Bash 
# エージェントに対して IAP Egressor ロールを付与
gcloud alpha iap web add-iam-policy-binding \
  --resource-type=agent-registry \
  --endpoint=ENDPOINT_ID \
  --region=REGION \
  --project=PROJECT_ID \
  --member=MEMBER \
  --role=roles/iap.egressor

🎯 ユースケース

🤖 マルチエージェントシステムのセキュリティ統制

企業内で複数の AI エージェントが異なるチームによって開発・デプロイされている環境で、各エージェントがアクセスできるツールや外部 API を一元管理。エージェントごとの最小権限アクセスにより、権限昇格や意図しないリソースアクセスを防止。

🛡️ AI セキュリティガードレールの適用

顧客対応用エージェントがプロンプトインジェクション攻撃を受けた場合の機密データ漏洩防止。Model Armor との統合により、エージェント入出力のリアルタイムコンテンツスキャンを適用し、攻撃を自動ブロック。

📈 メリット

💼 ビジネス面

  • 一元的なガバナンス: 複数ランタイム・デプロイメントを一箇所で管理
  • コンプライアンス強化: 通信ログの自動記録で監査対応
  • 運用コスト削減: 個別セキュリティ設定が不要

🔧 技術面

  • ゼロトラスト: 最小権限の原則に基づくアクセス制御
  • 自動暗号化: mTLS ハンドシェイクの自動化
  • フレームワーク非依存: 一貫したセキュリティを提供
  • 包括的な可観測性: Cloud Logging / Trace 統合

⚠️ 制限事項・注意点

  • ⚠️ 同一プロジェクト・リージョン内の全 Runtime エージェントは同じゲートウェイにバインド必須
  • ⚠️ 一度バインドした Runtime エージェントはアンバインド不可
  • ⚠️ Gemini Enterprise は Egress モードのみサポート
  • ⚠️ Ingress モードでは query / streamQuery のみガバナンス対象
  • ⚠️ Gateway 有効化後は SCC Agent Engine Threat Detection 利用不可
  • ⚠️ 1 つの Gateway で Gemini Enterprise と Agent Runtime の同時サポート不可
💡 推奨: アンバインド不可のため、テスト時は専用プロジェクトの使用が推奨されている。

🔗 関連サービス

📋 Agent Registry

エージェント、ツール、MCP サーバーの一元カタログ。Gateway がアクセスポリシー適用時にメタデータを参照。

🔑 Agent Identity

エージェントの一意な ID。mTLS と DPoP による暗号化認証に使用。

🛡️ Identity-Aware Proxy

Gateway のデフォルト認可レイヤー。IAM ポリシーに基づきエージェントの ID を検証。

🧠 Model Armor

プロンプトインジェクション、有害コンテンツ、機密データ漏洩に対するランタイム保護。

🔍 Agent Observability

Gateway が生成するテレメトリデータの可視化・分析を担当。

⚙️ Agent Runtime / Gemini Enterprise

Gateway がトラフィックをガバナンスする対象ランタイム。
