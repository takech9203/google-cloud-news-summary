📋 概要

2026 年 10 月 21 日、PHP コア言語ランタイムに影響する 2 件の重大な脆弱性 CVE-2026-109618 と CVE-2026-109619 (いずれも Critical、CVSS 9.2) が協調的に公開されました。認証不要のリモートコード実行 (RCE) や メモリ内容の漏えいにつながる可能性があり、PHP 5.4 から 8.5.11 までの全バージョンが影響を受けます。

Google Cloud は同日、PHP ワークロードを実行する 5 つのプロダクト (App Engine スタンダード / フレキシブル環境、Cloud Run、Cloud Run functions、Buildpacks) で パッチ適用済みランタイム (PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35) の提供を一斉に発表しました。 Google Cloud 自体は脆弱ではありませんが、顧客の PHP ワークロードは影響を受ける可能性があるため、 サービスごとに「自動でパッチ適用済み」か「再デプロイ / 再ビルドが必要」かの確認が重要です。

😰 Before (アップデート前の課題)

  • PHP 5.4〜8.5.11 の全バージョンに、OOM 処理時にリクエスト内部データが部分的にしか初期化されない問題 (CVE-2026-109618) と、解放済みメモリの内部状態が後続リクエストで再利用されうる問題 (CVE-2026-109619) が存在
  • 悪用されると、認証なしのリモートコード実行やメモリ開示、データの窃取・改ざん・破壊のリスク
  • 脆弱性公開時点では、Google Cloud 上の PHP ワークロードも修正版適用まで影響を受ける状態

😊 After (アップデート後の改善)

  • パッチ適用済み PHP ランタイム (8.5.12 / 8.4.27 / 8.3.36 / 8.2.35) が 5 プロダクトすべてで利用可能に
  • App Engine スタンダード環境の PHP ワークロードは 自動的にパッチ適用済み (アクション不要)
  • 自動ベースイメージ更新を有効化した Cloud Run / Cloud Run functions は 再デプロイなしで自動的にパッチ適用済み
  • それ以外のワークロードも、再デプロイ / 再ビルドのみで修正版ランタイムを取り込める

💡 主要なポイント

1️⃣ 5 つのプロダクトで同日にパッチ提供
App Engine スタンダード / フレキシブル環境、Cloud Run、Cloud Run functions、Buildpacks の PHP ランタイムが一斉に更新。対象は PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35。
2️⃣ 自動パッチと手動対応の区分
App Engine スタンダード環境と、自動ベースイメージ更新を有効化した Cloud Run / Cloud Run functions は自動的に保護。ソースからデプロイしたワークロードや Buildpacks ベースのイメージは、ユーザー自身の再デプロイ / 再ビルドが必要。
3️⃣ PHP 8.1 以前はパッチ対象外
PHP 8.1 以前は EOL (サポート終了) のため修正版は提供されない。該当バージョンの利用者は PHP 8.2 以降へのアップグレードと再デプロイが必要。

🔄 Cloud Run の自動ベースイメージ更新の仕組み: 自動ベースイメージ更新を有効にすると、ベースイメージ (OS と言語ランタイム) のセキュリティパッチを Google が自動的に適用します。 再ビルドや再デプロイは不要で、新しいリビジョンも作成されず、ゼロダウンタイムで更新されます。 gcloud functions コマンドや Cloud Functions v2 API でデプロイされた関数では、自動セキュリティ更新がデフォルトで有効です。

⚙️ 設定方法 (対応手順)

📌 前提条件

✓利用中の PHP バージョンがサポート対象 (PHP 8.2 以降) であることを確認。PHP 8.1 以前の場合は、まず 8.2 以降へのランタイムアップグレードが必要
✓自分のワークロードが「自動パッチ適用済み」か「要再デプロイ」かを上記の表で確認

ステップ 1: App Engine フレキシブル環境 — 依存関係を更新して再デプロイ

Bash ソースから再デプロイ 
# 依存関係を更新したうえでソースから再デプロイ
gcloud app deploy

カスタムランタイムを利用している場合は、イメージ内の PHP 依存関係を更新してから再デプロイします。

ステップ 2: Cloud Run / Cloud Run functions — 再デプロイ

Bash 再デプロイと自動ベースイメージ更新の有効化 
# ソースからサービスを再デプロイ (パッチ済みランタイムでビルドされる)
gcloud run deploy SERVICE --source .

# 以後の自動パッチ適用のため、自動ベースイメージ更新を有効化する例
gcloud run deploy SERVICE --source . --base-image php85 --automatic-updates

自動ベースイメージ更新が有効なリソースは、すでにパッチ適用済みのため対応は不要です。

ステップ 3: Buildpacks — ワークロードを再ビルド

google-22 または google-24 タグのパッチ済み PHP ランタイムを使用して、ワークロードを再ビルドします。

⚖️ メリットと制約事項

✅ ビジネス面のメリット

✓重大リスクの迅速な低減: CVSS 9.2 の Critical 脆弱性に対し、脆弱性公開と同日にパッチ済みランタイムが全対象プロダクトで提供され、エクスポージャ期間を最小化
✓運用負荷の軽減: App Engine スタンダード環境および自動ベースイメージ更新が有効な Cloud Run / Cloud Run functions では、ユーザーのアクションなしで保護が完了

✅ 技術面のメリット

✓マネージドランタイムの価値: ランタイム層のセキュリティ対応を Google が実施するため、ユーザーはアプリケーション層に集中できる
✓ゼロダウンタイム更新: 自動ベースイメージ更新では新しいリビジョンを作成せず、無停止でパッチを適用
✓複数 PHP バージョンへの同時対応: 8.2 / 8.3 / 8.4 / 8.5 の 4 系統すべてに修正版が提供され、バージョンアップを急がずにパッチを適用できる

⚠️ 制限事項

✗PHP 8.1 以前のランタイムには修正版が提供されない (EOL)。PHP 8.2 以降へのアップグレードが必須
✗自動ベースイメージ更新を有効にしていない Cloud Run / Cloud Run functions、App Engine フレキシブル環境、Buildpacks ベースのワークロードは、ユーザー自身が再デプロイ / 再ビルドするまで脆弱な状態が続く
✗自前でビルドしたコンテナイメージ (GKE 上の PHP コンテナなどを含む) の再ビルド・再デプロイはユーザーの責任で行う必要がある

🤔 考慮すべき点

⚠Cloud Armor のマネージドルール (File Upload / RFI カテゴリ) や大きなリクエストボディを制限するルールは緩和策として有効だが、あくまで補完的な対策であり、パッチ適用の代替にはならない
⚠影響範囲の確認には On-Demand Scanning API / Artifact Analysis によるイメージスキャンや Security Command Center の脅威検出が活用できる
⚠Cloud Marketplace 経由でデプロイした PHP ベースのソリューション (CMS、LAMP スタックなど) は、ソリューションプロバイダーの更新適用または直接の PHP パッチ適用が必要

💼 ユースケース

🔁 ユースケース 1: ソースデプロイしている Cloud Run サービスの一斉パッチ適用

シナリオ: 複数の Cloud Run サービスを gcloud run deploy --source で運用しているが、 自動ベースイメージ更新は有効化していない。今回の脆弱性に対応しつつ、今後は自動でパッチが適用されるようにしたい。

Bash 実装例 
gcloud run deploy my-php-service \
  --source . \
  --base-image php85 \
  --automatic-updates

効果: 再デプロイにより今回のパッチ済みランタイム (PHP 8.5.12 など) が即時適用され、 以後のランタイムセキュリティパッチは再デプロイなしで自動適用されるようになる。

🛠️ ユースケース 2: App Engine フレキシブル環境のカスタムランタイムの更新

シナリオ: App Engine フレキシブル環境でカスタムランタイムを使い、独自に PHP をバンドルしている。

効果: イメージ内の PHP 依存関係を 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 のいずれかに更新して再デプロイすることで、 RCE / メモリ開示のリスクを解消できる。

🔗 関連サービス・機能

🛡️ Cloud Armor: マネージドルール (File Upload / RFI カテゴリ) により、パッチ適用までの間の緩和策として悪用の試みをブロックできる
🔍 Security Command Center: コンテナおよび Cloud Run に対する脅威検出で、悪用の兆候を監視できる
📦 Artifact Analysis / On-Demand Scanning API: コンテナイメージをスキャンし、脆弱な PHP バージョンを含むイメージを特定できる
🕵️ Google Security Operations: 本脆弱性に関連する 23 件のキュレート済み検出ルール (Mandiant Frontline Threats ルールパック) が追加された
⚓ GKE: パッチ済み PHP を含むコンテナイメージへの更新と Pod の再デプロイが必要 (本 Release Notes の対象外だが、セキュリティブログで案内)

📝 まとめ

✅ 対応不要: App Engine スタンダード環境、および自動ベースイメージ更新が有効な Cloud Run / Cloud Run functions は、すでにパッチ適用済み。
⚠️ 速やかな対応が必要: それ以外の PHP ワークロード (App Engine フレキシブル環境、ソースデプロイの Cloud Run / Cloud Run functions、Buildpacks ベース) は、再デプロイ / 再ビルドを速やかに実施すること。
🚨 PHP 8.1 以前は要移行: EOL のためパッチが提供されない。PHP 8.2 以降への移行を直ちに計画すること。

CVSS 9.2 の Critical な PHP コア脆弱性 2 件に対し、Google Cloud は 5 つのプロダクトでパッチ済みランタイム (8.5.12 / 8.4.27 / 8.3.36 / 8.2.35) を脆弱性公開と同日に提供しました。 マネージドランタイムの自動保護を活用しつつ、手動対応が必要なワークロードを確実に洗い出して対処しましょう。
