📊 BigQuery Preview

⚡ Apache Arrow 形式でのクエリ結果取得

クエリ結果を列指向フォーマットで直接取得し、分析パイプラインへの取り込みを高速化
リリース日: 2026-10-30

📝 概要

BigQuery のクエリ結果を Apache Arrow 形式で直接取得できる機能が Preview として発表されました。 従来のキーバリューペアエンコーディング (STRUCT_ENCODING) と比較して、シリアライズ効率と取得速度が向上します。

利用方法は 2 つあります。

🔌 方法 1
jobs.query
queryResultsFormat = ARROW
📡 方法 2
Storage Read API
ReadRows で _default ストリームを読む

Apache Arrow は列指向のインメモリデータフォーマットで、pandas や PyArrow などのデータ分析ツールと親和性が高く、 大量のクエリ結果を分析基盤やアプリケーションに高速に取り込みたいデータエンジニアやデータサイエンティストにとって有用なアップデートです。

❌ Before (アップデート前の課題)

  • jobs.query の結果はキーバリューペアエンコーディング (STRUCT_ENCODING) で返却され、シリアライズ / デシリアライズのオーバーヘッドが大きい
  • Arrow 形式での取得には Storage Read API で読み取りセッション (ReadSession) を作成してテーブルを読む必要があり、クエリジョブの結果を直接 Arrow で受け取る手段がなかった

✅ After (アップデート後の改善)

  • queryResultsFormat を ARROW に設定するだけで、IPC シリアライズされた Arrow スキーマ / RecordBatch を直接取得
  • ジョブの _default ストリームへの ReadRows で、ReadSession 不要の高スループットストリーミング
  • arrowSerializationOptions で圧縮コーデック (LZ4_FRAME / ZSTD) を指定可能

🚀 主要機能

1️⃣ jobs.query での Arrow サポート

→QueryRequest の queryResultsFormat を ARROW に設定すると、QueryResponse に IPC シリアライズされた Arrow スキーマ (arrowSchema.serializedSchema) と最初のページの RecordBatch (arrowRecordBatch.serializedRecordBatch) が返却される
→最初のページの行数は pageRowCount で返却される
→arrowSerializationOptions.bufferCompression で圧縮コーデック (COMPRESSION_UNSPECIFIED / LZ4_FRAME / ZSTD) を指定可能

2️⃣ ReadRows によるクエリ結果の直接ストリーミング

→クエリジョブの特別なストリーム projects/{PROJECT_ID}/locations/{LOCATION}/jobs/{JOB_ID}/streams/_default に対して ReadRows を呼び出すことで、任意のクエリジョブの結果を直接ストリーミング可能
→ジョブの _default ストリームの出力は、ジョブ作成時の指定にかかわらず常に Arrow 形式がデフォルト
→クエリジョブが実行中の場合、Storage Read API はジョブの完了を自動的に待機してから結果をストリーミング
→ReadRowsResponse の total_estimated_row_count にクエリ結果の推定行数が設定される

3️⃣ クライアントライブラリとの統合

→Python クライアントライブラリでは query_and_wait() に query_results_format=enums.QueryResultsFormat.ARROW と compression_codec を指定し、to_arrow_iterable() で pyarrow.RecordBatch のイテラブルとして結果を取得可能

⚙️ 技術仕様

jobs.query で Arrow 形式を使用した場合の動作

項目詳細
リクエスト設定QueryRequest.queryResultsFormat を ARROW に設定
圧縮オプションarrowSerializationOptions.bufferCompression: COMPRESSION_UNSPECIFIED / LZ4_FRAME / ZSTD
レスポンス (スキーマ)arrowSchema.serializedSchema (IPC シリアライズされた Arrow スキーマ)
レスポンス (データ)arrowRecordBatch.serializedRecordBatch (最初のページの IPC シリアライズされた RecordBatch)
レスポンス (行数)pageRowCount (最初のページで返却された行数)
標準フィールド従来の rows / schema フィールドは設定されない

後続ページの取得jobs.getQueryResults は Arrow 形式に非対応。残りの結果は Storage Read API の ReadRows でジョブの _default ストリームからストリーミング

ReadRows の _default ストリーム名の形式

Text ストリーム名の形式 
projects/PROJECT_ID/locations/LOCATION/jobs/JOB_ID/streams/_default
  • PROJECT_ID: クエリジョブを実行したプロジェクト ID
  • LOCATION: クエリジョブを実行したロケーション (例: us、us-central1)
  • JOB_ID: BigQuery クエリジョブの ID
💡 ヒント: ReadRowsRequest の arrow_serialization_options フィールドで、圧縮などの Arrow シリアライズオプションをオーバーライドできます (ジョブの _default ストリームでサポート)。

ステップ 1: Python クライアントライブラリで Arrow 形式を指定してクエリを実行

Python query_and_wait で Arrow 形式を取得 
from typing import Iterable
import pyarrow
from google.cloud.bigquery import enums
from google.cloud import bigquery

def query_and_wait_arrow() -> Iterable[pyarrow.RecordBatch]:
    client = bigquery.Client()
    query = """
        SELECT name, number, state
        FROM `bigquery-public-data.usa_names.usa_1910_current`
        LIMIT 100000
    """
    # Arrow 形式 (LZ4_FRAME 圧縮) で結果を直接取得
    results = client.query_and_wait(
        query,
        query_results_format=enums.QueryResultsFormat.ARROW,
        compression_codec=enums.QueryResultsCompressionCodec.LZ4_FRAME,
    )
    # pyarrow.RecordBatch のイテラブルとして返却
    return results.to_arrow_iterable()

公式ドキュメントに掲載されている Python のサンプルです。to_arrow_iterable() で各バッチを Apache Arrow 形式のまま処理できます。

ステップ 2: REST API で直接指定する場合

JSON jobs.query リクエストボディ 
{
  "query": "SELECT name, number, state FROM `bigquery-public-data.usa_names.usa_1910_current` LIMIT 100000",
  "useLegacySql": false,
  "queryResultsFormat": "ARROW",
  "arrowSerializationOptions": {
    "bufferCompression": "LZ4_FRAME"
  }
}

jobs.query のリクエストボディに queryResultsFormat と arrowSerializationOptions を指定します。 レスポンスの jobComplete が true の場合、arrowSchema.serializedSchema と arrowRecordBatch.serializedRecordBatch から結果を読み取ります。

✅ メリット

💼 ビジネス面

✓データ取得の高速化: 従来のキーバリューペアエンコーディングと比較して取得速度が向上し、分析結果の提供までの時間を短縮
✓既存エコシステムの活用: Apache Arrow は pandas / PyArrow など主要なデータ分析ツールが対応する標準フォーマットであり、追加の変換コストなしに分析パイプラインへ組み込める

🔧 技術面

✓シリアライズ効率の向上: 列指向の Arrow 形式により、STRUCT_ENCODING と比較してシリアライズ / デシリアライズのオーバーヘッドを削減
✓読み取りセッション不要のストリーミング: ジョブの _default ストリームで、ReadSession を作成せずに高スループットでストリーミング
✓圧縮コーデックの選択: LZ4_FRAME / ZSTD の圧縮でネットワーク転送量を削減
✓ジョブ完了の自動待機: ジョブ実行中に ReadRows を呼び出しても API が完了を自動待機するためポーリング処理が不要

⚠️ デメリット・制約事項

制限事項

✗Preview 段階の機能であり、Pre-GA Offerings Terms が適用される (サポートが限定される場合がある)
✗jobs.getQueryResults メソッドは Arrow 形式に非対応。初回レスポンスに含まれない残りの結果は Storage Read API の ReadRows でストリーミングする必要がある
✗queryResultsFormat を ARROW に設定した場合、QueryResponse の標準の rows / schema フィールドは設定されない
✗結果が初回レスポンスに収まらない場合、最初のページで空のシリアライズ済み Arrow データが返ることがある
⚠️ 考慮すべき点:
  • 既存のコードが QueryResponse の rows / schema フィールドに依存している場合は、Arrow データの読み取り処理への変更が必要
  • フィードバックやサポートのリクエストは専用メールアドレス (bq-arrow-support-in-query-results-preview@google.com) 宛てに送付

🎯 ユースケース

📊 ユースケース 1: pandas / PyArrow を使ったデータ分析パイプラインの高速化

シナリオ: データサイエンティストが BigQuery 上の大規模データセットに対してクエリを実行し、結果を pandas DataFrame に取り込んで機械学習の特徴量エンジニアリングを行う。

Python 実装例 
results = client.query_and_wait(
    query,
    query_results_format=enums.QueryResultsFormat.ARROW,
    compression_codec=enums.QueryResultsCompressionCodec.LZ4_FRAME,
)
for batch in results.to_arrow_iterable():
    df = batch.to_pandas()  # Arrow からゼロコピーに近い変換
    # 特徴量エンジニアリング処理

効果: JSON ベースの行データを DataFrame に変換するオーバーヘッドが削減され、大量データの取り込み時間を短縮できる。

📡 ユースケース 2: クエリ結果の高スループットストリーミング

シナリオ: アプリケーションがクエリジョブを発行し、数百万行の結果を下流の処理系へ転送する。

効果: ジョブの _default ストリーム (.../jobs/{JOB_ID}/streams/_default) に対して ReadRows を呼び出すだけで、ReadSession の作成なしに結果を Arrow 形式で高スループットにストリーミングできる。ジョブ実行中でも API が完了を自動待機するため、ポーリングロジックの実装が不要になる。

📌 まとめ

BigQuery のクエリ結果を Apache Arrow 形式で直接取得できるようになり、pandas / PyArrow ベースの分析パイプラインへのデータ取り込みが高速化・効率化されます。

大量のクエリ結果をアプリケーションや分析基盤へ転送しているワークロードでは、Preview 段階のうちに queryResultsFormat=ARROW と ReadRows による直接ストリーミングを検証し、 取得速度と転送コストの改善効果を確認することを推奨します。
