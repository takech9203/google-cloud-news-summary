🛡️ 認可ポリシーの DENY_BY_DEFAULT アクションが GA

リリース日: 2026-11-19

📋 概要

Application Load Balancer の認可ポリシー (Authorization Policy) における DENY_BY_DEFAULT アクションが GA になりました。 対象はリージョン外部 / リージョン内部 / クロスリージョン内部 Application Load Balancer です。

DENY_BY_DEFAULT ポリシーを転送ルール (forwarding rule) にアタッチすると、 「デフォルト拒否」のセキュリティベースラインが確立され、 ALLOW / CUSTOM ポリシーで明示的に許可されない限り、すべてのリクエストがブロックされます。 ゼロトラストの基本原則「明示的に許可されたものだけを通す」をロードバランサーレイヤーで実現するアップデートです。

❌ Before (アップデート前)

  • ALLOW ポリシーが 1 つもない状態では、リクエストがデフォルトで許可され、「デフォルト拒否」を認可ポリシーだけで確立できなかった
  • IAP や Service Extensions などの CUSTOM ポリシーのみの構成では、マッチしないトラフィックが素通りするリスク
  • ALLOW ポリシーの一時的な削除・更新中は、リソースが無防備になる可能性

✅ After (アップデート後)

  • 転送ルールに DENY_BY_DEFAULT をアタッチするだけで、明示的に許可されないリクエストをすべてブロック
  • ALLOW ポリシーの更新・削除中でも保護が維持される
  • CUSTOM ポリシー (IAP、Service Extensions) のみの構成でも、許可判定を通過しなかったトラフィックを確実に遮断

⚡ 主要機能

🛡️ 1. デフォルト拒否のセキュリティベースライン

DENY_BY_DEFAULT ポリシーを転送ルールにアタッチすると、ALLOW または CUSTOM ポリシーで 明示的に許可されないすべてのリクエストをブロック。ALLOW ポリシーが未構成の場合や、 メンテナンスで一時的に削除された場合でもリソースを保護します。

🔢 2. 明確な評価順序

認可ポリシーは CUSTOM → DENY → ALLOW → DENY_BY_DEFAULT の順で評価されます。 DENY_BY_DEFAULT は、リクエストがそれ以前の段階 (ALLOW ポリシー、または REQUEST_AUTHZ / CONTENT_AUTHZ ステージで評価された CUSTOM ポリシー) で明示的に許可されなかった場合にのみ拒否を実行します。

📊 3. Cloud Logging との統合

DENY_BY_DEFAULT で拒否されたリクエストはログに details: "denied_by_default" として記録。 ALLOW ポリシーも構成されている場合、ALLOW に一致しなかった拒否は details: "denied_as_no_allow_policies_matched_request" として記録されます。 ログベースのアラートで拒否イベントを監視できます。

ポリシーの制約

項目 詳細
アタッチ先 ロードバランサーの転送ルール (forwarding rule)
アタッチ可能数 1 つの転送ルールに DENY_BY_DEFAULT ポリシーは 1 つのみ
HTTP ルール (httpRules) 構成不可 (全トラフィックに適用されるため)。細かな制御は別の ALLOW / DENY / CUSTOM ポリシーと組み合わせる
デフォルト動作 DENY_BY_DEFAULT 未構成かつ ALLOW 未構成の場合、リクエストはデフォルトで許可

ポリシー定義例

YAML DENY_BY_DEFAULT ポリシー定義 
name: my-authz-policy-deny-by-default
target:
  loadBalancingScheme: EXTERNAL_MANAGED
  resources:
  - "https://www.googleapis.com/compute/v1/projects/PROJECT_ID/regions/LOCATION/forwardingRules/LB_FORWARDING_RULE"
action: DENY_BY_DEFAULT

🚀 設定方法

💡 前提条件: リージョン外部 / リージョン内部 / クロスリージョン内部 Application Load Balancer が構成済みで、 ポリシーのターゲットとなる転送ルールの名前を確認していること。

1DENY_BY_DEFAULT ポリシーを YAML で定義

Bash ポリシー YAML の作成 
cat >authz-policy-deny-by-default.yaml <<EOF
name: my-authz-policy-deny-by-default
target:
  loadBalancingScheme: EXTERNAL_MANAGED
  resources:
  - "https://www.googleapis.com/compute/v1/projects/PROJECT_ID/regions/LOCATION/forwardingRules/LB_FORWARDING_RULE"
action: DENY_BY_DEFAULT
EOF

loadBalancingScheme はリージョン外部 ALB では EXTERNAL_MANAGED、 リージョン内部 / クロスリージョン内部 ALB では INTERNAL_MANAGED を指定します。 クロスリージョン内部 ALB の場合、resources のパスは global/forwardingRules/... 形式になります。

2ポリシーをインポートして作成

Bash gcloud によるポリシー作成 
# リージョンの場合
gcloud network-security authz-policies import my-authz-policy-deny-by-default \
    --source=authz-policy-deny-by-default.yaml \
    --location=LOCATION

# クロスリージョン内部 ALB の場合
gcloud network-security authz-policies import my-authz-policy-deny-by-default \
    --source=authz-policy-deny-by-default.yaml \
    --location=global

3許可したいトラフィックを ALLOW / CUSTOM ポリシーで定義

DENY_BY_DEFAULT はすべてのトラフィックに適用されるため、通過させたいトラフィックは別途 ALLOW ポリシー (IP レンジ、パス、サービスアカウント、セキュアタグなどの条件) や CUSTOM ポリシー (IAP、認可拡張機能) で明示的に許可します。

4(推奨) 拒否イベントのログアラートを構成

Text Cloud Logging クエリ (拒否トラフィックの捕捉) 
logName: "projects/PROJECT_ID/logs/loadbalancing.googleapis.com%2Fexternal_regional_requests"
resource.type="http_external_regional_lb_rule"
(jsonPayload.authzPolicyInfo.policies.details="denied_by_default" OR
 jsonPayload.authzPolicyInfo.policies.details="denied_as_no_allow_policies_matched_request")

上記のクエリでログベースのアラートを構成すると、ALLOW ポリシーの有無にかかわらず、 拒否されたトラフィックをすべて捕捉できます。

💡 メリット

📈 ビジネス面

✓ セキュリティ ポスチャの向上: 「明示的に許可されたものだけを通す」ゼロトラスト原則をロードバランサーレイヤーで強制でき、コンプライアンス要件への対応が容易に
✓ 運用リスクの低減: ポリシーのメンテナンス中 (ALLOW ポリシーの一時的な削除・更新時) でもリソースが無防備になることを防げる

⚙️ 技術面

✓ シンプルな構成: YAML 数行 + gcloud コマンド 1 回でベースラインを確立。アプリケーションやバックエンドの変更は不要
✓ 段階的な評価モデルとの統合: CUSTOM → DENY → ALLOW → DENY_BY_DEFAULT という明確な評価順序に組み込まれ、既存の認可ポリシーと矛盾なく共存
✓ 可観測性: 拒否理由 (denied_by_default など) がログに記録され、ログベースのアラートで監視可能

⚠️ デメリット・制約事項

制限事項

✗ グローバル外部 Application Load Balancer では DENY_BY_DEFAULT はサポートされない
✗ 1 つの転送ルールにアタッチできる DENY_BY_DEFAULT ポリシーは 1 つのみ
✗ DENY_BY_DEFAULT ポリシーには HTTP ルール (httpRules) を構成できない (全トラフィックに適用されるため)
⚠️ 考慮すべき点: DENY_BY_DEFAULT を適用すると、ALLOW / CUSTOM ポリシーで明示的に許可されていないトラフィックはすべて遮断されます。 適用前に必要な ALLOW ポリシーを漏れなく定義し、正当なトラフィックの遮断を検知できるよう、 ログベースのアラートの併用が推奨されます。

🎯 ユースケース

🔐 ユースケース 1: CUSTOM ポリシー (IAP) のみに依存する構成の保護

シナリオ: 社内向け Web アプリケーションをリージョン内部 Application Load Balancer で公開し、 IAP (CUSTOM ポリシー) で認証・認可を実施。IAP のルールにマッチしないトラフィックが素通りするリスクを排除したい。

YAML IAP に委譲する CUSTOM ポリシーに加えて DENY_BY_DEFAULT を併用 
name: my-authz-policy-deny-by-default
target:
  loadBalancingScheme: INTERNAL_MANAGED
  resources:
  - "https://www.googleapis.com/compute/v1/projects/PROJECT_ID/regions/LOCATION/forwardingRules/LB_FORWARDING_RULE"
action: DENY_BY_DEFAULT

効果: CUSTOM ポリシーで明示的に許可されなかったリクエストは DENY_BY_DEFAULT により 確実にブロックされ、認可の抜け漏れを防げる。

🔄 ユースケース 2: ポリシーメンテナンス中のフェイルセーフ

シナリオ: ALLOW ポリシーの条件 (許可 IP レンジやパス) を定期的に更新しており、 更新作業中に一時的に ALLOW ポリシーを削除・再作成することがある。

効果: DENY_BY_DEFAULT がベースラインとして常に有効なため、ALLOW ポリシーが存在しない瞬間が あってもリクエストはデフォルトで拒否され、意図しない全開放状態を回避できる。

🔗 関連サービス・機能

🔑 Identity-Aware Proxy (IAP)

CUSTOM ポリシーの認可プロバイダとして委譲可能。DENY_BY_DEFAULT と組み合わせることで、IAP で許可されなかったトラフィックを確実に遮断できる。

🔌 Service Extensions (認可拡張機能)

ext_authz プロトコル対応の独自認可サービスへ認可判断を委譲する CUSTOM ポリシーを構成可能。

📊 Cloud Logging

認可ポリシーの評価結果 (authzPolicyInfo) がリクエストログに記録され、ログベースのアラートを構成できる。

🛡️ Google Cloud Armor

バックエンド サービスに適用する WAF・DDoS 対策。転送ルールに適用する認可ポリシーとはレイヤーが異なり、併用できる。

📌 まとめ

DENY_BY_DEFAULT アクションの GA により、リージョン外部 / リージョン内部 / クロスリージョン内部 Application Load Balancer で「デフォルト拒否」のセキュリティベースラインを宣言的に確立 できるようになりました。

IAP や Service Extensions のみに依存する構成や、ALLOW ポリシーのメンテナンスが頻繁な環境では、 認可の抜け漏れを防ぐフェイルセーフとして導入を検討することを推奨します。 導入時は必要な ALLOW / CUSTOM ポリシーを事前に整備し、ログベースのアラートで拒否トラフィックを監視してください。
