📊 カスタマーホスト型 Looker から Looker (Google Cloud core) へ
シングルホップ・セルフサービス移行

統合スクリプト + Cloud KMS CMEK で、サポートチケット不要の移行が Preview で登場

📝 概要

カスタマーホスト型 (オンプレミス / セルフマネージド) の Looker インスタンスから Looker (Google Cloud core) へ、 中間ステップなしで直接移行できるセルフサービス移行が Preview として利用可能になりました。 統合 Python スクリプト looker_export.py が、DB・LookML Git リポジトリ・暗号鍵のエクスポートと Cloud KMS CMEK による暗号化を一括実行。暗号化済み成果物を Cloud Storage にアップロードすれば、 そのままターゲットインスタンスにインポートでき、手動ハンドオフやサポートチケットは不要です。

🎯 対象ユーザー: カスタマーホスト型 Looker を運用しており、インフラ管理の負担を手放してマネージドな Looker (Google Cloud core) に移行したい管理者。鍵の生成・共有から成果物の受け渡しまでを自分のプロジェクト内で完結でき、 移行のスケジュールとセキュリティを自らコントロールできます。

❌ Before: Looker 支援型の移行

  • Looker チームへのチケット起票と移行アンケートの記入から開始
  • Looker SRE が GPG 鍵ペアを生成して公開鍵を共有するなど、Google 側との手動のやり取りが複数回発生
  • バックアップ・暗号化・チェックサム生成を個別のスクリプト / コマンドで実行
  • バックアップファイルを Looker チームに引き渡し、Looker 側でインポート・検証してもらう必要があり、顧客側で完結できない

✅ After: シングルホップ・セルフサービス移行

  • 単一の looker_export.py が事前チェック・DB 抽出・ステージング・暗号化・マニフェスト生成を一括実行
  • 自分の Cloud KMS CMEK で暗号化。GPG 鍵の受け渡しが不要になり、鍵のライフサイクルを顧客自身が管理
  • Cloud Storage にアップロードしてターゲットインスタンスに直接インポート
  • 手動ハンドオフ・サポートチケットなしで移行が完結

⚙️ 主要機能

🐍 1. 統合エクスポートスクリプト looker_export.py

✓ツール・KMS アクセス・KEK アンラップ・ディスク容量の事前チェックを実行
✓mysqldump --single-transaction または mydumper による読み取り専用の DB 抽出
✓models、bare_models、deploy_keys、git_hooks、.persistent_store などのファイルシステムをステージング
✓LOOKER_MASTER_KEY を CMEK でラップし、Tink Streaming AEAD (AES128_CTR_HMAC_SHA256_1MB) で暗号化、metadata.json (マニフェスト) を生成

🔑 2. Cloud KMS CMEK による顧客管理の暗号化

✓移行専用の CMEK (インスタンスレベルの CMEK とは別) でエクスポートデータを暗号化
✓GPG 鍵ペアの共有が不要になり、鍵の管理を顧客自身のプロジェクト内で完結

⚡ 3. 2 つのエクスポートモード

モード特徴
シングルスレッド
(mysqldump)		 ソース DB への負荷が低く、追加パッケージ不要。大規模 DB では低速
マルチスレッド
(mydumper)		 エクスポートが約 3〜10 倍高速化、myloader による並列リストア対応。CPU/I/O/接続数の負荷は高め。MYDUMPER_THREADS (デフォルト 4) と MYDUMPER_CHUNK_ROWS でチューニング可能

🔍 4. 診断スクリプト collect_looker_diagnostics.py (任意)

✓読み取り専用・標準ライブラリのみ・ダウンタイム不要で実行可能
✓ディスク使用量、ディレクトリ構造、DB バージョン / 照合順序、テーブルごとのサイズを確認し、レポートを /tmp/looker_infra_report.txt に出力
✓ステージングに必要な 1.5 倍の空きディスク容量の確認と、エクスポートモードの選択に活用 (DB が 75 GB 超なら mydumper を推奨)

📦 エクスポート成果物

${BACKUP_DIR}/final_artifacts/ に生成される 5 つのファイルのみを Cloud Storage にアップロードします (スクリプト・ログ・未暗号化のステージングファイルはアップロードしない)。

ファイル内容

📊 インポート
  1. 移行用サービスアカウントの作成と権限付与 (任意)
    Bash サービスアカウント作成と IAM 権限付与 
    gcloud iam service-accounts create EXPORT_SA_NAME \
    --project=PROJECT_ID \
    --display-name="Looker Core migration export"

gcloud kms keys add-iam-policy-binding KEY_NAME \
    --project=PROJECT_ID --location=REGION --keyring=KEY_RING \
    --member="serviceAccount:EXPORT_SA_NAME@PROJECT_ID.iam.gserviceaccount.com" \
    --role="roles/cloudkms.cryptoKeyEncrypterDecrypter"

gcloud storage buckets add-iam-policy-binding gs://YOUR_MIGRATION_BUCKET_NAME \
    --member="serviceAccount:EXPORT_SA_NAME@PROJECT_ID.iam.gserviceaccount.com" \
    --role="roles/storage.objectUser"

    エクスポート用とインポート用の ID は別々でも可。サービスアカウントキーを使う場合は chmod 600 で保護し、移行完了後に削除します。

  2. エクスポートホストの準備
    Bash スクリプトの取得と依存関係のインストール 
    git clone https://github.com/looker-open-source/customer-scripts.git
cd customer-scripts/export-to-core
pip3 install -r requirements.txt

    認証は gcloud auth application-default login、または GOOGLE_APPLICATION_CREDENTIALS にサービスアカウントの JSON キーを設定。

  3. エクスポートと暗号化 — まず全ノードで Looker を停止 (DB ダンプと Git リポジトリのポイントインタイム整合性を確保) してから実行
    Bash 環境変数を設定してエクスポートを実行 
    export ON_PREM_LOOKER_DATA_DIR="ON_PREM_LOOKER_DATA_DIR"
export BACKUP_DIR="BACKUP_DIR"
export DB_HOST="DB_HOST"
export DB_USER="DB_USER"
export DB_NAME="DB_NAME"
export KMS_KEY_NAME="projects/PROJECT_ID/locations/REGION/keyRings/KEY_RING/cryptoKeys/KEY_NAME"
# export USE_MYDUMPER="true"   # 任意: マルチスレッドモード

./looker_export.py

    MYSQL_PWD と LOOKER_MASTER_KEY は実行時にエコーなしでプロンプト入力されます。

  4. Cloud Storage へのアップロード
    Bash 暗号化済み成果物のアップロード 
    gcloud storage cp "${BACKUP_DIR}/final_artifacts/*" "gs://YOUR_MIGRATION_BUCKET_NAME/MIGRATION_FOLDER/"
gcloud storage ls -l "gs://YOUR_MIGRATION_BUCKET_NAME/MIGRATION_FOLDER/"
  5. インポート — Cloud Storage からのインポート手順に従ってターゲットの Looker (Google Cloud core) インスタンスでインポートを実行し、インポート後の最終設定 (接続・認証などの確認) を行います。

💼 ビジネス面

✓移行の内製化: サポートチケットや Looker チームとの手動ハンドオフが不要になり、自社のスケジュールで移行を計画・実行できる
✓マネージド環境への移行促進: インフラの設置・構成・保守の負担を手放し、マネージドな運用に移行しやすくなる

⚙️ 技術面

✓セキュリティの自己管理: 自分の CMEK で暗号化するため鍵の外部共有が不要。ローテーションや無効化も顧客側で制御可能
✓運用の単純化: 複数の個別スクリプトが単一の統合スクリプトに集約され、事前チェックも自動化
✓大規模環境への対応: mydumper のマルチスレッドモードでエクスポートを約 3〜10 倍高速化

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 段階: Pre-GA Offerings Terms が適用。Preview 期間中は Cloud Customer Care のサポート対象外 (フィードバックは専用メールアドレス宛)
✗増分・再開不可: エクスポートは毎回最初からやり直し。インポートはターゲットの既存データ / 設定を完全に上書き
✗設定の大部分はコピーされない: setting テーブルで転送されるのは closed_system と crypt_canary_gcm のみ。その他はインポート後に再構成が必要
✗OAuth の DB トークンは除外 (セキュリティ上の理由): インポート後にユーザーの再認証が必要
✗個々の開発者ワークスペース (models-user-*) はエクスポートされない
✗Enterprise/Embed エディションのインスタンスレベル CMEK はインスタンス作成時にのみ設定可能で、後から有効化できない

🤔 考慮すべき点

⚠️エクスポート実行前に全ノードで Looker を停止する必要があり、ダウンタイムが発生する
⚠️ステージング用にソースデータの約 1.5 倍の空きディスク容量が必要 (診断スクリプトで事前確認を推奨)
⚠️DB が 75 GB 超の場合は mydumper (マルチスレッドモード) 推奨だが、ソース DB への CPU/I/O 負荷が高くなる
⚠️Cloud Storage には final_artifacts/ 内の 5 つの成果物のみをアップロードし、スクリプト・ログ・未暗号化ファイルはアップロードしない

🎯 ユースケース

📦 ユースケース 1: オンプレミス Looker のマネージド環境への移行

シナリオ: オンプレミスで Looker を自社運用している企業が、サーバー保守やアップグレード作業の負担を削減するため、 Looker (Google Cloud core) への移行を計画。セキュリティポリシー上、データの暗号鍵を外部 (Looker チーム) と共有することは避けたい。

Bash 実装例 
# 1. 診断スクリプトで移行可否とエクスポートモードを確認
python3 collect_looker_diagnostics.py

# 2. Looker を停止してエクスポート + CMEK 暗号化
./looker_export.py

# 3. Cloud Storage にアップロードしてインポート
gcloud storage cp "${BACKUP_DIR}/final_artifacts/*" \
    "gs://YOUR_MIGRATION_BUCKET_NAME/MIGRATION_FOLDER/"
✅ 効果: 鍵の受け渡しや Looker チームとのハンドオフなしに、自社の Cloud KMS CMEK で暗号化したまま移行が完結する。

🚀 ユースケース 2: 大規模データベースを持つインスタンスの高速移行

シナリオ: 内部データベースが 75 GB を超える大規模なカスタマーホスト型 Looker インスタンスを、 ダウンタイムを最小限に抑えて移行したい。

✅ 効果: USE_MYDUMPER="true" によるマルチスレッドモードでエクスポートを約 3〜10 倍高速化し、 myloader による並列リストアと合わせて移行時間 (ダウンタイム) を短縮できる。

📌 まとめ

カスタマーホスト型 Looker から Looker (Google Cloud core) への移行が、 統合 Python スクリプトと Cloud KMS CMEK によるセルフサービス方式で完結できるようになり、 サポートチケットや鍵の受け渡しといった従来の手動プロセスが不要になりました。

オンプレミス Looker の移行を検討している場合は、まず診断スクリプトでインスタンスの移行適合性を確認し、 前提条件 (MySQL 8.0+ / MariaDB 10.4+、utf8mb4 など) を満たしたうえで Preview を評価することを推奨します。 なお、エクスポート時のダウンタイムと、インポート後の設定再構成・ユーザー再認証を移行計画に織り込んでください。
