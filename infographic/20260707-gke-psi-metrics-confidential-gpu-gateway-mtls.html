📈 機能 1: PSI メトリクス収集

👁 可観測性 | GKE 1.34+ | GA

Linux カーネルの Pressure Stall Information (PSI) メトリクスを cAdvisor 経由で収集し、CPU・メモリ・I/O の輻輳時間とストール時間を監視可能にします。

収集されるメトリクス

→container_pressure_cpu_stalled_seconds_total - CPU ストール時間
→container_pressure_memory_stalled_seconds_total - メモリストール時間
→container_pressure_io_stalled_seconds_total - I/O ストール時間
💻 ノード
(Linux Kernel PSI)
→
⚙ cAdvisor
(メトリクス公開)
→
📊 Prometheus
(収集・保存)
→
📈 Cloud Monitoring
(可視化・アラート)
項目詳細
必要バージョンGKE 1.34 以降
収集方法ClusterNodeMonitoring カスタムリソース
メトリクスソースcAdvisor
収集間隔30秒 (デフォルト)
対象リソースCPU、メモリ、I/O
メトリクス形式Prometheus counter

設定方法

YAML 
apiVersion: monitoring.googleapis.com/v1
kind: ClusterNodeMonitoring
metadata:
  name: psi-collector
spec:
  selector:
    matchLabels: {}
  endpoints:
    - path: /metrics/cadvisor
      scheme: https
      interval: 30s
      tls:
        insecureSkipVerify: true
      metricRelabeling:
        - action: keep
          sourceLabels: [__name__]
          regex: container_pressure_(cpu|memory|io)_(waiting|stalled)_seconds_total
Bash 
kubectl apply -f psi-prometheus-collector.yaml

🔒 機能 2: Confidential GKE Nodes + GPU

🛡 セキュリティ | GKE 1.35.3+ | Preview

GPU ワークロードを Confidential Computing 環境で実行可能に。Intel TDX (Trust Domain Extensions) によりGPU メモリ内のデータを使用中も暗号化保護します。

主要要件

→GKE バージョン 1.35.3-gke.1389000 以降
→対応 GPU: NVIDIA RTX PRO 6000
→対応マシンタイプ: 特定の G4 マシンタイプ
→Confidential 技術: Intel TDX
→VM タイプ: Spot VM または Flex-start VM (必須)

ワークロード

🔒 Confidential
GKE Nodes
→
🔐 Intel TDX
メモリ暗号化
→
✅ データ保護

ComputeClass 設定例

YAML 
apiVersion: cloud.google.com/v1
kind: ComputeClass
metadata:
  name: confidential-gpu-ml
spec:
  nodePoolConfig:
    confidentialNodeType: TDX
  priorityDefaults:
    location:
      zones: ['us-central1-a']
    priorities:
      - gpu:
          type: nvidia-rtx-pro-6000
          count: 1
        driverVersion: default
        spot: true
  activeMigration:
    optimizeRulePriority: true
  nodePoolAutoCreation:
    enabled: true

📜 機能 3: VPA 決定ログ

👁 可観測性 | GKE 1.36.0+ | Preview

VerticalPodAutoscaler の決定イベントを Cloud Logging に記録し、オートスケーリングの動作理由を透明化します。

記録される4種類のログ

1.推奨更新 (Update recommendation) - VPA が新しいリソース推奨値を計算
2.Pod 退避 (Evict Pod) - VPA が Pod をスケーリングのため退避
3.退避時の推奨適用 (Apply recommendation on eviction) - 退避時にリソースを適用
4.インプレース推奨適用 (Apply recommendation in place) - 再起動なしでリソース変更
項目詳細
必要バージョンGKE 1.36.0-gke.1601000 以降
ログ出力先Cloud Logging
ログ名container.googleapis.com/vpa-controller
ログ形式JSON (jsonPayload)
有効化フラグ--logging=SYSTEM,KCP_VPA

有効化コマンド

Bash 
# 新規クラスタ
gcloud container clusters create CLUSTER_NAME \
  --location=LOCATION \
  --project=PROJECT_ID \
  --logging=SYSTEM,KCP_VPA

# 既存クラスタ
gcloud container clusters update CLUSTER_NAME \
  --location=LOCATION \
  --project=PROJECT_ID \
  --logging=SYSTEM,KCP_VPA

🔐 機能 4: Gateway バックエンド mTLS

🛡 セキュリティ | Gateway API 1.5+ | GA

GKE Gateway ロードバランサーがバックエンド Pod に クライアント証明書を提示 して自身の身元を証明。ゼロトラストアーキテクチャの実装を容易にします。

対応 GatewayClass

✓gke-l7-global-external-managed - グローバル外部 LB
✓gke-l7-regional-external-managed - リージョナル外部 LB
✓gke-l7-rilb - リージョナル内部 LB
🌐 クライアント
→
🔒 Gateway LB
(証明書提示)
↔
✅ バックエンド Pod
(証明書検証)
💡 ポイント: spec.tls.backend.clientCertificateRef フィールドで構成。バックエンド認証 TLS (サーバー証明書検証) と組み合わせて完全な双方向 TLS を実現できます。

設定手順

Bash 
# Step 1: クライアント証明書の Secret 作成
kubectl create secret tls gateway-client-identity \
  --cert=PATH_TO_CERT_FILE \
  --key=PATH_TO_KEY_FILE \
  --namespace=default
YAML 
# Step 2: Gateway リソースで証明書を参照
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: default
spec:
  gatewayClassName: gke-l7-global-external-managed
  tls:
    backend:
      clientCertificateRef:
        group: ""
        kind: Secret
        name: gateway-client-identity
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate

⚡ 機能 5: サージアップグレード上限引き上げ

🔧 運用効率 | GKE Standard | GA

GKE Standard クラスタにおいて、同時にアップグレードできるノード数 (maxSurge + maxUnavailable) の合計上限が 100 に引き上げられました。

新しい上限値

設定項目上限値デフォルト
maxSurge1001
maxUnavailable1000
maxSurge + maxUnavailable (合計)1001
⚡ 効果: 大規模ノードプール (数百〜数千ノード) のアップグレード時間を大幅に短縮。例: 1000 ノードクラスタで maxSurge=100 に設定すると、従来の 1/100 の速度でローリングアップグレードが完了します。

🎯 ユースケース

🤖 ユースケース 1: AI/ML ワークロードの機密データ処理

シナリオ: 金融機関が顧客の取引データを使用した不正検知モデルを GKE 上で学習させたいが、データ保護規制によりデータが処理中も暗号化されている必要がある。

効果: GPU メモリ内のモデルデータと学習データが Intel TDX により暗号化され、規制要件を満たしながら高性能な GPU 処理が可能。

🔒 ユースケース 2: ゼロトラストセキュリティ

シナリオ: マイクロサービスアーキテクチャの Web アプリケーションにおいて、外部ロードバランサーからバックエンド Pod までの通信を完全に暗号化し、双方向の認証を行いたい。

効果: ロードバランサーとバックエンド Pod 間の通信が mTLS で保護され、中間者攻撃のリスクを排除。

📈 ユースケース 3: リソースボトルネックの可視化と VPA 最適化

シナリオ: マイクロサービス群において、一部の Pod が断続的にレスポンス遅延を引き起こしているが、CPU 使用率は高くない。根本原因の特定と VPA チューニングが必要。

効果: PSI メトリクスにより I/O やメモリの圧迫が原因と特定でき、VPA 決定ログによりオートスケーラーが適切にリソースを調整しているかを確認。データに基づいた VPA ポリシーの最適化が可能。

✔ メリット

ビジネス面

✓障害の予防的検知: PSI メトリクスにより、リソース輻輳がパフォーマンス低下に至る前に検知・対処
✓コンプライアンス対応: Confidential GPU により規制産業 (金融、医療) でも GPU ベースの AI/ML ワークロードを安全に実行可能
✓運用コスト削減: サージアップグレード上限引き上げにより大規模クラスタのメンテナンスウィンドウを短縮
✓セキュリティ態勢の強化: Gateway mTLS によりゼロトラストアーキテクチャの実装が容易

技術面

✓詳細なリソース監視: PSI メトリクスは従来の CPU/メモリ使用率よりも正確にリソース競合を検出
✓VPA の透明性: 決定ログにより動作理由が明確、推奨値の信頼度 (LOW/HIGH) も把握可能
✓標準 API 準拠: Gateway mTLS は標準 Gateway API 仕様に準拠、ポータビリティ確保
✓スケーラビリティ: 100 ノード同時アップグレードで数千ノード規模のクラスタも高速更新

⚠ 制約事項・注意点

⚠ 制限事項
  • Confidential GPU: Preview 段階。G4 マシンタイプと NVIDIA RTX PRO 6000 に限定。Spot VM / Flex-start VM 必須
  • VPA ログ: Preview 段階。GKE 1.36.0+ 必須。Cloud Logging の追加料金が発生
  • PSI メトリクス: GKE 1.34+ 必須。ClusterNodeMonitoring の構成が必要 (デフォルト収集されない)
  • Gateway mTLS: Gateway API 1.5+ 必須。一部の GatewayClass (gke-l7-gxlb) は非対応
  • サージアップグレード: maxSurge を高く設定する場合、追加ノード分のリソースクォータとコストが必要
💡 考慮すべき点
  • Confidential GKE Nodes の GPU ドライバ自動インストール使用時、コントロールプレーンのバージョンアップグレードが即座にノード再作成をトリガー (メンテナンスポリシー無視)
  • PSI メトリクスの収集は追加の Prometheus スクレイピングを導入するため、モニタリングコストが増加する可能性あり
  • VPA ログのフィールドに機密情報や個人情報を含めないよう注意
  • サージアップグレードの高い並列度は、リソースクォータ不足によるアップグレード失敗リスクあり
