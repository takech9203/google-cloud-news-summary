🛡️ GKE サイドカー向け認可ポリシー
(GCPAuthzPolicy) が Preview に

📅 リリース日: 2026-11-02

📋 概要

GKE 上の Cloud Service Mesh サイドカーに対して、認可ポリシー (GCPAuthzPolicy) を構成できるようになりました (Preview)。 Gateway API を構成 API とする Cloud Service Mesh でのみサポートされます。

GCPAuthzPolicy は Kubernetes カスタムリソース (networking.gke.io/v1) として定義し、Namespace 全体または特定のワークロード (Pod ラベルセレクタ) を対象に、受信 HTTP リクエストの ALLOW / DENY を宣言的に制御できます。 さらに GCPAuthzExtension を使えば、ext_proc gRPC 対応の外部認可エンジンへ認可判断を委譲 (CUSTOM アクション) することも可能です。

mTLS による認証 (SPIFFE ID) と組み合わせた L7 レベルのきめ細かなアクセス制御を、マネージドなメッシュで実現できる、ゼロトラストセキュリティの中核となるアップデートです。

❌ Before: アップデート前の課題

  • Gateway API 構成のサイドカーでは、受信 HTTP リクエストに対する宣言的な認可ポリシーを構成する手段がなかった
  • ワークロード・Namespace 単位のインバウンド制御には、アプリ側実装や別の仕組みが必要だった
  • 独自の認可ロジックをメッシュのデータプレーンに組み込む標準的な方法がなかった

✅ After: アップデート後の改善

  • GCPAuthzPolicy で Namespace 全体 / ワークロード単位の ALLOW / DENY を宣言的に制御
  • mTLS の SPIFFE ID (principal)、パス、HTTP メソッドに基づく L7 認可が可能に
  • GCPAuthzExtension で 外部認可エンジンへの委譲 (CUSTOM) が可能に

💡 ポイント: 受信リクエストはアプリケーションに到達する前に Envoy サイドカーで GCPAuthzPolicy に基づき評価され、ALLOW / DENY が判定されます。CUSTOM アクションの場合、サイドカーは GCPAuthzExtension で参照される外部認可エンジンの応答を待ってからリクエストを転送または拒否します。

⚙️ 主要機能

1️⃣ Namespace 単位の認可ポリシー

→targetRefs で kind: Pod と空のセレクタ (selector: {}) を指定することで、Namespace 内のすべての Pod を対象にポリシーを適用
→特定のパスプレフィックスや HTTP メソッドへの受信リクエストを一括で ALLOW / DENY 可能

2️⃣ ワークロード単位の認可ポリシー

→Pod のラベルセレクタ (matchLabels) で特定のワークロードのみを対象に指定
→アウトバウンド専用ワークロード (cron ジョブなど) への受信リクエストをすべて拒否する、といった制御が可能
→拒否されたリクエストの呼び出し元には HTTP 403 Forbidden が返される

3️⃣ mTLS ID (SPIFFE ID) ベースの ALLOW ポリシー

→from.sources.principals で spiffe://cluster.local/NAMESPACE/pod1 のような SPIFFE ID を指定し、mTLS で認証された特定の呼び出し元のみを許可
→条件に一致しないリクエストはプロキシが HTTP 403 Forbidden で拒否

4️⃣ 外部認可エンジンへの委譲 (GCPAuthzExtension)

→ext_proc gRPC プロトコル対応の独自の認可サービス (callout ベース) を Kubernetes にデプロイし、GCPAuthzExtension リソースで登録
→action: CUSTOM と customProviders.extensionRefs で認可判断を外部エンジンに委譲
→forwardHeaders (転送ヘッダー)、failOpen (障害時の挙動)、timeout を構成可能
→拡張がエラー終了した場合や failOpen: false で呼び出しが失敗・タイムアウトした場合は HTTP 500 が返される

設定例: ワークロードへの ALLOW ポリシー

YAML SPIFFE ID ベースの ALLOW ポリシー 
apiVersion: networking.gke.io/v1
kind: GCPAuthzPolicy
metadata:
  name: my-workload-authz
  namespace: NAMESPACE
spec:
  targetRefs:
  - group: ""
    kind: Pod
    selector:
      matchLabels:
        app: EXAMPLE_APP
  rules:
  - from:
      sources:
      - principals:
        - principal:
            type: Exact
            value: "spiffe://cluster.local/NAMESPACE/pod1"
    action: ALLOW
  enforcementLevel: L7

🛠️ 設定方法

✅ 前提条件

✓Gateway API を構成 API (--config-api gateway) とする Cloud Service Mesh がセットアップ済み (Gateway API と Authorization Extensions の理解が前提)
✓GKE クラスタが fleet に登録され、Workload Identity Federation for GKE と Gateway API が有効化済み
1Namespace 全体への DENY ポリシーの適用
Bash Namespace 全体に DENY ポリシーを適用 
cat >ns-authz-policy-deny.yaml <<EOF
apiVersion: networking.gke.io/v1
kind: GCPAuthzPolicy
metadata:
  name: ns-authz
  namespace: NAMESPACE
spec:
  targetRefs:
  - group: ""
    kind: Pod
    selector: {}
  rules:
  - to:
      operations:
      - paths:
        - type: Prefix
          value: "/bad_token"
    action: DENY
  enforcementLevel: L7
EOF
kubectl apply -f ns-authz-policy-deny.yaml

空のセレクタ (selector: {}) により Namespace 内のすべての Pod が対象となり、/bad_token 配下への受信 HTTP リクエストが拒否されます。

2外部認可エンジンへの委譲 (任意)
Bash GCPAuthzExtension の登録 
# GCPAuthzExtension CRD のインストール (未導入の場合)
kubectl apply -f https://raw.githubusercontent.com/GoogleCloudPlatform/gke-gateway-api/main/config/crd/networking.gke.io_gcpauthzextensions.yaml

# 認可拡張リソースの作成
cat >authz-extension.yaml <<EOF
apiVersion: networking.gke.io/v1
kind: GCPAuthzExtension
metadata:
  name: my-authz-ext
  namespace: NAMESPACE
spec:
  backendRef:
    group: ""
    kind: Service
    name: authz-service
    port: PORT
  authority: "authz-service.NAMESPACE.svc.cluster.local"
  forwardHeaders:
  - Authorization
  failOpen: false
  timeout: "100ms"
  wireFormat: ExtProcGRPC
EOF
kubectl apply -f authz-extension.yaml

ext_proc gRPC に対応した認可サービスを登録し、GCPAuthzPolicy の action: CUSTOM と customProviders.extensionRefs から参照することで、認可判断を外部エンジンに委譲できます。

💎 メリット

💼 ビジネス面

  • ゼロトラストセキュリティの強化: サービス間通信の認可をプラットフォームレイヤーで一元的に適用でき、内部不正や侵害時の横展開 (ラテラルムーブメント) のリスクを低減
  • 既存の認可基盤の再利用: 独自の認可エンジン (ポリシー判定サービス) をメッシュに統合でき、既存のセキュリティ投資を活用可能

🔧 技術面

  • 宣言的な L7 アクセス制御: Kubernetes カスタムリソースとして GitOps で管理でき、アプリコードの変更なしに認可を適用
  • 柔軟な適用範囲: Namespace 全体から特定ワークロード単位まで、ラベルセレクタで細かく制御
  • mTLS ID との統合: SPIFFE ID による呼び出し元の検証で、ネットワーク位置に依存しない ID ベースの認可を実現

⚠️ デメリット・制約事項

🚧 制限事項

▸Preview (Pre-GA) 機能であり、Pre-GA Offerings Terms が適用され、サポートが限定される可能性がある
▸Gateway API を構成 API とする Cloud Service Mesh のみでサポート (Istio API 構成のクラスタでは利用不可)
▸認可ポリシーの作成・変更後、サイドカーでの適用開始まで最大 15 分かかる場合がある
▸Gateway API 構成のクラスタでは、同一 fleet 内での istio / gateway config-api の混在やマルチクラスタのサービスディスカバリ・負荷分散が未サポート、FQDN のみサポートなどの制限がある

🤔 考慮すべき点

→外部認可エンジン利用時はリクエストパスに認可問い合わせが入るため、レイテンシと timeout / failOpen の設計 (フェイルオープン / フェイルクローズ) を慎重に検討する必要がある
→failOpen: false で拡張の呼び出しが失敗・タイムアウトすると呼び出し元に HTTP 500 が返るため、認可エンジン自体の可用性設計が重要になる

🎯 ユースケース

🕒 ユースケース 1: アウトバウンド専用ワークロードの保護

シナリオ: cron ジョブのように外部への呼び出しのみを行うワークロードに対し、想定外の受信リクエストをすべて遮断したい。

効果: 対象ワークロードへの該当パスの受信 HTTP リクエストはサイドカーで拒否され (HTTP 403)、アプリケーションに到達しない。攻撃対象領域を縮小できる。

💳 ユースケース 2: 決済 API への独自認可エンジンによる判断の委譲

シナリオ: /api/payments-schedule のような機密性の高い API について、社内の認可基盤 (OPA など ext_proc gRPC 対応エンジン) でトークン検証やポリシー判定を行いたい。

効果: action: CUSTOM と GCPAuthzExtension により、サイドカーが認可エンジンの応答を待ってから転送。Authorization ヘッダーを forwardHeaders で転送し、集中管理された認可ロジックをメッシュ全体で再利用できる。
