🗄️ Cloud SQL for MySQL GA (一般提供)

🔵🟢 Blue-Green デプロイメントが GA

ダウンタイム最小でメジャーバージョンアップグレード・構成変更を本番適用
📅 リリース日: 2026-11-17

📌 概要

Cloud SQL for MySQL の Blue-Green デプロイメントが一般提供 (GA) になりました。 MySQL 8.0 → 8.4 のメジャーバージョンアップグレードやハードウェア・構成変更のステージングを、 ダウンタイムを最小限に抑えながら実行できる機能です。

Cloud SQL が本番環境 (Blue) のクローンとして一時的なステージング環境 (Green) を自動作成し、 継続的な論理レプリケーションで同期を維持。Green 環境で本番トラフィックに影響を与えずに 互換性・性能を検証し、準備が整ったら高速なスイッチオーバー (接続エンドポイントの切り替え) を実行します。 同日の Cloud SDK 594.0.0 では gcloud sql blue-green-deployments コマンドグループも GA に昇格しています。

❌ Before (アップデート前の課題)

  • メジャーバージョンアップグレード (8.0 → 8.4) を本番に直接実行すると、長いダウンタイムや失敗リスクを伴った
  • 本番相当の検証環境には、クローン作成・レプリケーション設定・エンドポイント切り替えを手動で構築・運用する必要があった
  • マシンタイプやデータベースフラグ変更の影響を本番に影響なく事前検証する標準的な仕組みがなかった

✅ After (アップデート後の改善)

  • Green 環境の作成・変更適用・継続的レプリケーションの維持まで Cloud SQL が自動化し GA 品質で利用可能
  • スイッチオーバーは計画的な操作として実行され、ダウンタイムは Enterprise Plus で通常サブ秒 / Enterprise で通常 60 秒未満
  • メジャーバージョンアップグレード時は事前チェック API が自動実行され互換性の問題を事前検出
  • コンソール・gcloud CLI・Admin API・Terraform から宣言的・プログラマブルに管理可能

Cloud SQL が本番環境 (Blue) のクローンとして Green ステージング環境を作成し、継続的レプリケーションで同期しながら検証を行い、 スイッチオーバーで接続エンドポイントを入れ替えて Green を新しい本番インスタンスに昇格させる流れです。

⚡ 主要機能

🚀 1. メジャーバージョンアップグレードのステージング

→ターゲットバージョン (例: MYSQL_8_4) を指定すると、Green 環境を新バージョンで作成
→Green 作成前にアップグレード事前チェック API が自動実行され、互換性の問題を事前検証

🔧 2. ハードウェア・構成変更のステージング

→ターゲットバージョンを指定しない場合、現行バージョンのまま Green 環境を作成
→マシンタイプ変更 (CPU / RAM スケーリング)、データベースフラグのテスト、ストレージ変更の評価に利用可能

⏱️ 3. 高速スイッチオーバー

→ユーザーが開始する計画的な操作として、安全性の事前チェック後に接続エンドポイントを入れ替え
→ダウンタイムは Enterprise Plus: 通常サブ秒 / Enterprise: 通常 60 秒未満
→旧 Blue はスタンドアロンの読み書きインスタンスとして保持され、問題発生時の参照や性能比較に利用可能

🖥️ 4. マルチインターフェース対応

→Google Cloud コンソール / gcloud CLI (gcloud sql blue-green-deployments、GA 昇格)
→Cloud SQL Admin API (blueGreenDeployments リソース) / Terraform (blue_green_deployment ブロック)

Green インスタンス名BLUE_INSTANCE_NAME-green-UNIQUE_ID の形式で自動生成 (Blue 名は最大 48 文字に切り詰め、UNIQUE_ID は 16 進数 8 文字)

🛠️ 設定方法

✅ 前提条件

✓Cloud SQL for MySQL インスタンス (Enterprise / Enterprise Plus、MySQL 5.7 以降) が新ネットワークアーキテクチャ上で稼働
✓自動バックアップとバイナリログが有効
✓Blue インスタンスが最新のメンテナンスバージョンを実行
✓リードレプリカが構成されていないこと (リードレプリカ付きインスタンスは非対応)

ステップ 1: Blue-Green デプロイメントの作成

Bash デプロイメントの作成 
# メジャーバージョンアップグレード (MySQL 8.0 → 8.4) をステージングする場合
gcloud sql blue-green-deployments create DEPLOYMENT_NAME \
  --source-instance=SOURCE_INSTANCE_ID \
  --target-database-version=MYSQL_8_4 \
  --region=REGION \
  --async

# ハードウェア・構成変更のみをステージングする場合 (--target-database-version を省略)
gcloud sql blue-green-deployments create DEPLOYMENT_NAME \
  --source-instance=SOURCE_INSTANCE_ID \
  --region=REGION \
  --async

Cloud SQL が Green インスタンスをプロビジョニングし、要求された変更を適用した上で、Blue から Green への継続的な論理レプリケーションを開始します。 メジャーバージョンアップグレードを含む場合は数分以上かかることがあります。

ステップ 2: ステータス確認と検証

Bash デプロイメントの状態確認 
# デプロイメントの状態と Green インスタンスの接続情報を確認
gcloud sql blue-green-deployments describe DEPLOYMENT_NAME \
  --region=REGION

state が SWITCHOVER_READY になったら、Green インスタンスに接続してアプリケーションの互換性テストやクエリ性能の検証を実施します。 この間も Blue は本番トラフィックを処理し続けます。

ステップ 3: スイッチオーバーの実行と後片付け

検証完了後、スイッチオーバーを実行すると、Cloud SQL が安全性の事前チェックを行い、接続エンドポイントを入れ替えて Green を本番の読み書きインスタンスに昇格させます。 動作確認後、デプロイメントを削除してクリーンアップします。

💡 ヒント: 旧 Blue インスタンスはデフォルトで保持されるため、不要であれば --delete-old-source フラグ (Terraform では delete_old_source_on_destroy = true) で削除し、課金を停止できます。

👍 メリット

💼 ビジネス面

✓ダウンタイムの最小化: アップグレードに伴うサービス停止を秒単位に抑え、SLA への影響やビジネス機会の損失を低減
✓アップグレードリスクの低減: 本番と同期された環境で事前検証してから切り替えるため、障害や手戻りのリスクを大幅に削減

⚙️ 技術面

✓運用の自動化: クローン作成・レプリケーション設定・エンドポイント切り替えがマネージドなワークフローとして自動化
✓事前チェックの組み込み: 互換性の問題を Green 作成前に検出
✓IaC 対応: Terraform の blue_green_deployment ブロックでライフサイクル全体を宣言的に管理
✓切り戻しの容易さ: 旧 Blue がスタンドアロンとして保持され、可観測性データの参照や性能比較が可能

⚠️ デメリット・制約事項

🚫 制限事項

✗Cloud SQL for PostgreSQL / SQL Server は非対応 (MySQL のみ)
✗リードレプリカを持つインスタンスは非対応
✗Private Service Connect のアウトバウンド構成は非対応
✗MySQL の IAM グループ認証とは互換性がなく、スイッチオーバー失敗の原因となる可能性
✗旧ネットワークアーキテクチャのインスタンスは非対応 (新ネットワークアーキテクチャへの移行が必要)
✗メジャーバージョンアップグレードは MySQL 8.0 → 8.4 のみサポート。MySQL 8.0.18 は非対応

🤔 考慮すべき点

⚠️ 計画的な操作専用: スイッチオーバーは Blue インスタンスが正常 (RUNNING) であることが前提。 Green は計画外の障害時のフェイルオーバー先としては使用できないため、自動復旧には高可用性 (HA) 構成や DR レプリカを併用してください。
  • Green のプロビジョニングや旧 Blue のスタンドアロン化は、選択したリージョン / ゾーンのコンピュートリソースの空き状況に影響を受ける可能性がある
  • 可観測性や Query Insights のデータは Blue / Green で独立して記録され、履歴データはスイッチオーバー時に引き継がれない。切り替え前後の性能比較には旧 Blue を一定期間保持する
  • Terraform 管理の場合、blue_green_deployment ブロックを定義せずにコンソールや gcloud でデプロイメントを作成すると、terraform apply 実行時にデプロイメントと Green インスタンスが削除されるため注意

🎯 ユースケース

📈 ユースケース 1: MySQL 8.0 から 8.4 へのメジャーバージョンアップグレード

シナリオ: 本番の EC サイトが Cloud SQL for MySQL 8.0 を使用しており、MySQL 8.4 へのアップグレードが必要だが、 長時間のメンテナンスウィンドウを確保できない。

Bash 実装例 
gcloud sql blue-green-deployments create ec-mysql84-upgrade \
  --source-instance=ec-prod-mysql \
  --target-database-version=MYSQL_8_4 \
  --region=asia-northeast1 \
  --async
✅ 効果: 事前チェックで互換性の問題を検出した上で、MySQL 8.4 の Green 環境でアプリケーションを十分に検証し、 秒単位のダウンタイムで本番を切り替え可能。問題があればスイッチオーバー前にデプロイメントを削除するだけで、本番 (Blue) に影響なく中止できる。

🖥️ ユースケース 2: マシンタイプ変更・データベースフラグの事前検証

シナリオ: ピークトラフィック増加に備えてマシンタイプのスケールアップと複数のデータベースフラグの変更を計画しているが、 本番への影響を事前に確認したい。

✅ 効果: ターゲットバージョンを指定せずにデプロイメントを作成し、Green 環境で新しいハードウェア構成やフラグ設定の性能を 実トラフィック相当のデータで検証できる。検証に合格した構成のみを、最小限のダウンタイムで本番に反映できる。

💰 料金

Blue-Green デプロイメント期間中は、Blue と Green の 2 つのインスタンスが稼働するため、 Green インスタンス分の料金が追加で発生します。

⚠️ 注意: スイッチオーバー後も旧 Blue インスタンスはデフォルトで保持されるため、 不要になった時点で削除しないと課金が継続します。

📝 まとめ

Cloud SQL for MySQL の Blue-Green デプロイメントの GA により、これまで高リスク・長時間ダウンタイムを伴いがちだった メジャーバージョンアップグレードや構成変更を、検証済みの状態から秒単位のダウンタイムで本番適用できるようになりました。

🎯 推奨アクション: MySQL 8.0 を利用中のチームは、8.4 へのアップグレード計画にこの機能の採用を検討し、 まずリードレプリカの有無やネットワークアーキテクチャなどの前提条件を確認することを推奨します。
