📊 BigQuery: グラフメジャーと GRAPH_EXPAND が GA
生成 AI 関数で gemini-4-carbon をサポート

BigQuery GA (一般提供) Gemini 4 Carbon リリース日: 2026-11-10

📝 概要

BigQuery Graph の メジャー (measure) 機能と GRAPH_EXPAND テーブル値関数 (TVF) が 一般提供 (GA) になりました。メジャーはノード/エッジテーブルの PROPERTIES 句内で MEASURE キーワードを使って定義する集計プロパティで、集計をテーブルの KEY にロックすることで、 結合で行が重複しても重複カウント (overcounting) を起こさない正確な集計を実現します。

同日、BigQuery の生成 AI 関数が Google の最新フロンティアモデル gemini-4-carbon をサポート (GA)。 SQL の AI.GENERATE などから、より高度な推論能力をデータ分析パイプラインに組み込めます。

🎯 主な対象ユーザー: ディメンショナルモデル (スタースキーマ/スノーフレークスキーマ) 上でセマンティックレイヤーを構築する データエンジニア/アナリティクスエンジニア、SQL ベースで LLM を活用するデータアナリスト

❌ Before (アップデート前の課題)

  • ファクト × ディメンションの結合で行が重複 (ファンアウト) し、SUM / COUNT で重複カウントが発生。サブクエリや COUNT(DISTINCT ...) で集計粒度を手動管理
  • 集計ロジック (ビジネスメトリクス定義) をクエリごとに記述し、定義の一貫性維持が困難
  • 複数のルートノードテーブル (ファクトテーブル) を持つグラフの展開に非対応
  • GRAPH_EXPAND の出力スキーマを実行せずに確認する手段がなかった

✅ After (アップデート後の改善)

  • メジャーが KEY 基準で集計を定義するため、行が重複しても AGG 関数で常に正しい集計結果 (GA)
  • 条件付き DISTINCT カウントや派生メジャーなど、複雑なメジャー式を一元定義
  • GRAPH_EXPAND が複数ファクトテーブルに対応、start_node でサブグラフ選択
  • BQ.SHOW_GRAPH_EXPAND_SCHEMA で出力スキーマを事前確認
  • OPTIONS 句の extensions + Knowledge Catalog 自動カタログ化で自然言語検索に対応
  • 生成 AI 関数で gemini-4-carbon が利用可能 (GA)

メジャーを定義したプロパティグラフを GRAPH_EXPAND TVF でフラットなテーブルに展開し、AGG 関数でキー単位に正確な集計を行うデータフローです。 グラフとメジャーは Knowledge Catalog に自動カタログ化され、Data Studio からも利用できます。

⚡ 主要機能

1️⃣ グラフメジャー (GA)

PROPERTIES 句内で MEASURE(集計式) AS 名前 として定義する集計プロパティ。 集計はテーブルの KEY を基準に定義されるため、結合で行が重複しても正しく集計されます。

✓サポート集計関数: SUM / AVG / COUNT / MIN / MAX / AGG (派生メジャー用)。AGG 以外は DISTINCT をサポート
✓集計関数内の式・条件ロジック、条件付き DISTINCT カウント、集計関数外のスカラー演算、AGG でラップした派生メジャーを定義可能

2️⃣ GRAPH_EXPAND TVF (GA)

GRAPH_EXPAND(graph_name [, start_node => 'NodeName'] [, flatten_results => TRUE|FALSE]) でグラフをリレーショナルテーブルとしてクエリ。 ルートノードテーブルから一連の LEFT JOIN でフラット化テーブルを生成します。

✓デフォルトは <要素>_<プロパティ> 形式の列名で出力。flatten_results => FALSE で STRUCT によるネスト階層出力も可能
✓複数ファクトテーブル対応: start_node で展開するサブグラフを指定。複数の GRAPH_EXPAND を共有ディメンションで JOIN しても各メジャーはそれぞれの粒度で正確に集計

3️⃣ BQ.SHOW_GRAPH_EXPAND_SCHEMA システムプロシージャ

CALL BQ.SHOW_GRAPH_EXPAND_SCHEMA(graph_name [, start_node [, flatten_results]], output_schema) で、 GRAPH_EXPAND を実際に実行せずに出力スキーマを JSON で取得。 各列の名前・型・モードに加え、メジャーには "is_measure": true、description や synonyms も含まれます。

4️⃣ OPTIONS 句での extensions (カスタムメタデータ)

ラベルやプロパティ (メジャー定義含む) の OPTIONS() 句で description、synonyms、extensions を定義可能。 extensions は文字列ペアの配列 (ARRAY<STRUCT<STRING, STRING>>) で、[('currency', 'USD')] のような単位・フォーマットルールを表現。 自然言語クエリインターフェースのコンテキスト提供と発見性向上に使われ、GQL クエリの結果には影響しません。

5️⃣ エコシステム統合

✓メジャーとグラフは BigQuery コネクタ経由で Data Studio からサポート
✓Knowledge Catalog に自動カタログ化され、自然言語やドメインシノニムで検索可能

6️⃣ 生成 AI 関数での gemini-4-carbon サポート (GA)

BigQuery の生成 AI 関数 (AI.GENERATE など) で、Google のフロンティアモデル gemini-4-carbon が利用可能に。 コーディング、金融、法務、サイバーセキュリティ、科学などの複雑なタスク向けモデルで、 入出力合計 1,048,576 トークンの統一上限、設定可能な思考レベル (LOW/MEDIUM/HIGH)、暗黙的コンテキストキャッシュが特徴です (Gemini Enterprise Agent Platform 側でも同日 GA)。

🔧 技術仕様

📋 GRAPH_EXPAND の引数

引数型説明
graph_name STRING グラフ名 ('[project_id.]dataset.graph' 形式)
start_node STRING (省略可) トラバースを開始するノードテーブル名。複数のルートノードテーブルを持つグラフでは必須
flatten_results BOOL (省略可、デフォルト TRUE) TRUE: 全プロパティを <要素>_<プロパティ> 形式のトップレベル列にフラット化 / FALSE: ルートノードはトップレベル列、隣接テーブルは STRUCT 列

⚠️ 入力グラフの制約

項目詳細
ルートノードテーブル start_node を指定しない場合、スキーマ関係グラフにおいて単一のルートノードテーブル (他のすべての隣接ノードと多対一の関係) が必要
多対多 (M:N) 関係 中間ジャンクションテーブルを単独のエッジテーブルとしてモデル化すると関係が曖昧 (N:1 でも 1:1 でもない) になり無視される。ジャンクションテーブルをノードテーブルに昇格させ、各ディメンションへの N:1 エッジを定義する
メジャーの参照 メジャー列は直接 SELECT できず、必ず AGG() 関数でラップする。GQL クエリからはメジャープロパティを参照できない
キャッシュ 基になるグラフを変更しても GRAPH_EXPAND を呼び出すクエリのキャッシュ結果は無効化されないため、正確な出力にはキャッシュ取得の無効化が必要
エディション GQL クエリの実行には、オンデマンド料金または Enterprise / Enterprise Plus エディションの予約が必要

💻 メジャー定義とクエリの例

SQL メジャー付きプロパティグラフの定義と集計 
-- メジャー付きプロパティグラフの定義 (抜粋)
CREATE OR REPLACE PROPERTY GRAPH university.SchoolGraph
  NODE TABLES (
    university.College KEY(college_id) PROPERTIES(college_id, college_name),
    university.Department KEY(dept_id)
      PROPERTIES(dept_id, dept_name, college_id, budget,
                 MEASURE(SUM(budget)) AS total_budget),
    university.Course KEY(course_id)
      PROPERTIES(course_id, course_name, credits, dept_id,
                 MEASURE(COUNT(course_id)) AS course_count)
  )
  EDGE TABLES (
    university.Department AS CollegeDept
      SOURCE KEY (college_id) REFERENCES College (college_id)
      DESTINATION KEY (dept_id) REFERENCES Department (dept_id),
    university.Course AS DeptCourse
      SOURCE KEY (dept_id) REFERENCES Department (dept_id)
      DESTINATION KEY (course_id) REFERENCES Course (course_id)
  );

-- GRAPH_EXPAND + AGG で重複カウントなしに集計
SELECT
  College_college_name,
  AGG(Department_total_budget) AS college_budget,
  AGG(Course_course_count) AS total_courses
FROM GRAPH_EXPAND("university.SchoolGraph")
GROUP BY College_college_name;
💡 ポイント: 学部 (Department) が複数のコース (Course) と結合されて行が重複しても、 AGG(Department_total_budget) は予算をキー単位で 1 回だけ集計します。

🔍 出力スキーマの確認

SQL BQ.SHOW_GRAPH_EXPAND_SCHEMA の使用例 
DECLARE result_schema STRING DEFAULT '';
CALL BQ.SHOW_GRAPH_EXPAND_SCHEMA('university.SchoolGraph', result_schema);
SELECT result_schema;
-- 出力例: {"fields":[{"name":"Department_total_budget","type":"FLOAT",
--          "mode":"NULLABLE","is_measure":true}, ...]}

ステップ 1: メジャー付きプロパティグラフを定義する

SQL ファクトテーブルをルートノードとして MEASURE を定義 
CREATE OR REPLACE PROPERTY GRAPH mydataset.MyGraph
  NODE TABLES (
    mydataset.Orders KEY(order_id)
      PROPERTIES(order_id, customer_id, amount,
                 MEASURE(SUM(amount)) AS total_amount,
                 MEASURE(COUNT(DISTINCT customer_id)) AS unique_customers),
    mydataset.Customers KEY(customer_id) PROPERTIES(customer_id, region)
  )
  EDGE TABLES (
    mydataset.Orders AS OrderCustomer
      SOURCE KEY (order_id) REFERENCES Orders (order_id)
      DESTINATION KEY (customer_id) REFERENCES Customers (customer_id)
  );

ステップ 2: スキーマを確認してクエリする

SQL スキーマ確認とメジャーの集計 
-- 出力スキーマを確認
DECLARE schema STRING;
CALL BQ.SHOW_GRAPH_EXPAND_SCHEMA('mydataset.MyGraph', schema);
SELECT schema;

-- メジャーをクエリ
SELECT
  Customers_region,
  AGG(Orders_total_amount) AS region_revenue,
  AGG(Orders_unique_customers) AS region_customers
FROM GRAPH_EXPAND("mydataset.MyGraph")
GROUP BY Customers_region;

💡 メリット

💼 ビジネス面

✓メトリクス定義の一元化: 収益やユニークカスタマー数などのビジネスメトリクスをグラフスキーマ上で一度定義すれば、どのクエリからも一貫した定義で利用でき、セマンティックレイヤーとして機能
✓自然言語分析との親和性: description / synonyms / extensions のメタデータと Knowledge Catalog への自動カタログ化により、自然言語によるデータ検索・クエリの精度と発見性が向上
✓BI ツールからの利用: Data Studio の BigQuery コネクタからメジャーとグラフを直接利用でき、BI レイヤーでの重複カウント事故を防止

⚙️ 技術面

✓重複カウントの構造的防止: 集計がテーブルの KEY にロックされるため、ファンアウトする JOIN でもサブクエリや DISTINCT の手作業なしで正確な集計を保証
✓複数ファクトテーブルの正確な分析: start_node で各サブグラフを展開して共有ディメンションで JOIN しても、各メジャーはそれぞれの粒度 (grain) で干渉なく集計
✓スキーマの事前検証: BQ.SHOW_GRAPH_EXPAND_SCHEMA により、クエリを実行せずに列名・型・メジャー判定を CI/CD やツールから検証可能
✓最新モデルの SQL 統合: gemini-4-carbon を生成 AI 関数から直接呼び出せるため、ETL パイプラインの外に出ることなく高度な LLM 処理を実行

⚠️ デメリット・制約事項

🚫 制限事項

✗メジャープロパティは GQL クエリから直接参照できず、GRAPH_EXPAND + AGG() 経由でのみ利用可能
✗start_node を指定しない場合、グラフは単一のルートノードテーブルを持つ必要がある。多対多関係はジャンクションテーブルをノードに昇格させてモデル化が必要
✗すべてのエッジが無視されるグラフでは GRAPH_EXPAND / BQ.SHOW_GRAPH_EXPAND_SCHEMA はエラーになる
✗flatten_results => FALSE は、要素テーブルのプロパティ名が隣接要素テーブル名と重複する場合には使用不可
✗一部の BigQuery エディションで作成された予約ではこの機能を利用できない場合がある
⚠️ 考慮すべき点:
  • 基になるグラフの変更ではクエリキャッシュが無効化されないため、GRAPH_EXPAND を呼び出すクエリではキャッシュ結果の取得を無効化することを推奨
  • ルートノードテーブルから到達できないデータは出力に含まれない (例: コースを持たない学部は結果から除外)。未マッチ行の扱いは、メジャー式をインラインで書くかプロパティ経由で書くかで変わるため、意図に合わせて選択
  • gemini-4-carbon は高度な推論 (思考トークン) を行うモデルであり、大量行に対する生成 AI 関数の適用ではトークン消費とコストに注意

🎯 ユースケース

📐 ユースケース 1: スタースキーマ上のセマンティックレイヤー構築

シナリオ: 売上ファクトテーブルと顧客・商品・地域のディメンションテーブルを持つ組織が、「総売上」「ユニーク顧客数」などのメトリクス定義を全社で統一したい。

SQL 任意のディメンション軸で集計 
-- ファクトテーブルにメジャーを定義し、GRAPH_EXPAND で任意のディメンション軸で集計
SELECT Region_region_name, AGG(Sales_total_revenue) AS revenue
FROM GRAPH_EXPAND("sales.SalesGraph")
GROUP BY Region_region_name;

効果: メトリクス定義がグラフスキーマに一元化され、どの軸で集計しても重複カウントのない一貫した数値が得られる。Knowledge Catalog 経由で自然言語検索も可能になる。

🏫 ユースケース 2: 複数ファクトテーブルの横断分析

シナリオ: 大学のデータ基盤で、コース数 (Course ファクト) と教員給与総額 (Instructor ファクト) を、共有ディメンション (Department / College) を軸にまとめて分析したい。

SQL start_node 指定による複数ファクトの JOIN 
SELECT
  C.College_college_name,
  AGG(C.Course_course_count) AS total_courses,
  AGG(I.Instructor_total_salary) AS total_faculty_salary
FROM GRAPH_EXPAND("university.SchoolGraphMultiRoot", start_node => "Course") AS C
INNER JOIN GRAPH_EXPAND("university.SchoolGraphMultiRoot", start_node => "Instructor") AS I
  ON C.Department_dept_id = I.Department_dept_id
GROUP BY C.College_college_name;

効果: 異なる粒度のファクトテーブルを JOIN しても、各メジャーがそれぞれの粒度で正確に集計され、手作業のサブクエリ分解が不要になる。

🤖 ユースケース 3: gemini-4-carbon による高度なデータ分析

シナリオ: 法務・金融ドメインの長文ドキュメントを格納したテーブルに対し、SQL から高度な推論を伴う要約・分類を行いたい。

効果: 生成 AI 関数のモデルとして gemini-4-carbon を指定することで、複雑な実世界タスクに強いフロンティアモデルの推論能力を、データを BigQuery から移動させずに活用できる。

💰 料金

🕸️ グラフ / GQL クエリ

GQL クエリの実行には、オンデマンド料金 (スキャン量ベース) または Enterprise / Enterprise Plus エディションの予約 (スロットベース) が必要です。 グラフの基になるテーブルのストレージ課金は 1 回のみで、同一テーブル上に複数のグラフモデルを作成しても追加のストレージ料金は発生しません。

🤖 生成 AI 関数

クエリ実行に使用するコンピュートリソースへの課金に加え、リモートモデルが Gemini Enterprise Agent Platform のモデルを呼び出すため、 Agent Platform 側の料金 (gemini-4-carbon のトークン課金) も発生します。

詳細は BigQuery の料金ページ および BigQuery ML の料金 を参照してください。

🌏 利用可能リージョン

公式ドキュメントにリージョン別の提供状況の明記はありません。生成 AI 関数のモデル別サポートロケーションは BigQuery のロケーション を参照してください (Agent Platform のモデルはマルチリージョンエンドポイントのみをサポートします)。

🔗 関連サービス・機能

  • Knowledge Catalog: メジャーとグラフが自動カタログ化され、自然言語やドメインシノニムで検索可能
  • Data Studio: BigQuery コネクタ経由でメジャーとグラフを利用可能
  • Spanner Graph: 同じ GQL (ISO/IEC 39075) ベースのグラフクエリを提供するオペレーショナルデータベース側の対応機能
  • Gemini Enterprise Agent Platform: 生成 AI 関数が呼び出すモデル (gemini-4-carbon は同日 GA) の提供基盤
  • BigQuery editions / Reservations: GQL クエリ実行の前提となる課金・キャパシティ管理

📌 まとめ

グラフメジャーと GRAPH_EXPAND の GA により、BigQuery 上で重複カウントのない正確なメトリクス定義をスキーマレベルで一元管理する、セマンティックレイヤー的なアプローチが本番利用可能になりました。

スタースキーマや複数ファクトテーブルを扱うデータ基盤では、既存の集計クエリをメジャー定義へ移行することで、集計事故の防止と自然言語分析への対応を同時に進められます。

あわせて生成 AI 関数で gemini-4-carbon が利用可能になったため、SQL ベースの高度な LLM 活用もあわせて検討することをおすすめします。
