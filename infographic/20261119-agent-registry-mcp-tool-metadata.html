🔧 MCP ツールのプロトコルレベルメタデータ対応

IAP ポリシーヒント / HITL 制御 / プロバイダーメタデータ属性
📅 リリース日: 2026-11-19

📝 概要

Agent Registry が Model Context Protocol (MCP) ツールのプロトコルレベルメタデータをサポートしました (Preview)。 MCP 仕様に準拠したツールアノテーション (ツールの挙動ヒント) を Agent Registry に登録・保持できるようになり、 ツール有効化のための Identity-Aware Proxy (IAP) ポリシーヒント、Human-in-the-Loop (HITL) 制御、 およびプロバイダーメタデータ属性として活用できます。

MCP サーバー登録時の toolspec.json に MCP 仕様の Tool オブジェクトスキーマに準拠した annotations (readOnlyHint、destructiveHint、idempotentHint、openWorldHint) を含めることができ、 これらのヒントが IAP のポリシー評価属性 (例: iap.googleapis.com/mcp.tool.isReadOnly) や、 MCP クライアントでのユーザー確認プロンプト (HITL) の判断材料として利用されます。

💡 ポイント: 「どのエージェントが」「どのような特性のツールを」呼び出せるかという粒度で統制したい Solutions Architect やプラットフォーム管理者にとって、エージェントガバナンスをツールレベルまで深化させる重要なアップデートです。

❌ Before: アップデート前の課題

  • 手動登録した MCP サーバーはエンドポイント URL とツール一覧の登録が中心で、ツールのリスク特性 (読み取り専用か、破壊的操作を伴うか) を IAP ポリシーによるツール単位の有効化制御に直接結び付ける標準的な仕組みがなかった
  • MCP ツールの挙動ヒントをレジストリ経由でクライアントに伝搬し、ユーザー確認 (HITL) の要否判断に活用する一貫したメタデータ基盤がなかった
  • MCP サーバーやツールの提供元 (プロバイダー) に関する付加的な属性情報をレジストリ上で構造化して保持する手段が限られていた

✅ After: アップデート後の改善

  • toolspec.json の MCP 準拠アノテーションが取り込まれ、IAP の条件付き egress ポリシーで iap.googleapis.com/mcp.toolName や iap.googleapis.com/mcp.tool.isReadOnly を参照したツール単位のアクセス制御が可能に
  • ツールアノテーションが MCP クライアントに送信され、ユーザーへの確認プロンプト (HITL 制御) を出すかどうかの判断に利用可能に
  • プロバイダーメタデータ属性 (key-value 形式の attributes、例: agentregistry.googleapis.com/system/RuntimeReference) でリソースの付加情報を構造化して保持・参照可能に

⚡ 主要機能

1️⃣ MCP ツールのプロトコルレベルメタデータ登録

→MCP サーバー登録時の toolspec.json に、MCP Tool オブジェクトスキーマ準拠の annotations (title、readOnlyHint、destructiveHint、idempotentHint、openWorldHint) を含めて登録可能
→登録されたメタデータは読み取り専用の McpServer ディスカバリリソースとして公開され、get_mcp_server などで参照できる

2️⃣ IAP ポリシーヒントによるツール有効化制御

→IAP のエージェント間 egress ポリシーの CEL 条件式で、api.getAttribute('iap.googleapis.com/mcp.toolName', '') や api.getAttribute('iap.googleapis.com/mcp.tool.isReadOnly', false) などの属性を参照可能
→「このエージェントは読み取り専用ツールのみ呼び出せる」といったツール特性ベースの最小権限ポリシーを定義できる

3️⃣ Human-in-the-Loop (HITL) 制御

→ツールアノテーションは MCP クライアントに送信され、ツールの基本的なリスクを示すヒントとして機能する
→多くのクライアントはヒントを信頼できない情報 (untrusted) として扱うが、ユーザーへの確認プロンプトをいつ表示するかの判断に利用できる

4️⃣ プロバイダーメタデータ属性

→リソースに key-value 形式の属性 (AttributesEntry: key は文字列、value は Struct 形式) を保持
→例として、ホスティング先ランタイムを示す agentregistry.googleapis.com/system/RuntimeReference 属性があり、IAM ポリシー評価に使われるエージェントプリンシパルにも埋め込まれる

🔬 技術仕様

📋 MCP ツールアノテーション (プロトコルレベルメタデータ)

フィールド説明デフォルト
titleツールの人間可読なタイトル-
readOnlyHinttrue の場合、ツールは環境を変更しない (データ取得のみ)false
destructiveHinttrue の場合、破壊的 (永続的) な変更を行う可能性がある。readOnlyHint == false のときのみ意味を持つtrue
idempotentHinttrue の場合、同じ引数での繰り返し呼び出しは追加の影響を持たない。readOnlyHint == false のときのみ意味を持つfalse
openWorldHinttrue の場合、外部エンティティの「オープンワールド」と対話する (例: Web 検索はオープン、メモリツールはクローズド)true

🛡️ IAP ポリシーで参照できる主な属性

属性説明
iap.googleapis.com/mcp.toolName呼び出し対象の MCP ツール名
iap.googleapis.com/mcp.tool.isReadOnlyツールが読み取り専用かどうか
iap.googleapis.com/request.auth.type認可タイプ (例: MCP)

📄 toolspec.json の例

JSON 
{
  "tools": [
    {
      "name": "get_customer_info",
      "description": "Retrieves customer details from the database.",
      "annotations": {
        "title": "Get Customer Info",
        "readOnlyHint": true,
        "idempotentHint": true
      }
    },
    {
      "name": "create_support_ticket",
      "description": "Creates a new support ticket in the issue tracking system.",
      "annotations": {
        "title": "Create Support Ticket",
        "destructiveHint": true,
        "idempotentHint": false,
        "openWorldHint": true
      }
    }
  ]
}
💡 補足: ツール仕様ファイルの最大サイズは 10 KB です。

ステップ 1: アノテーション付きツール仕様で MCP サーバーを登録

Bash 
gcloud agent-registry services create SERVER_NAME \
  --project=PROJECT_ID \
  --location=REGION \
  --display-name="DISPLAY_NAME" \
  --mcp-server-spec-type=tool-spec \
  --mcp-server-spec-content=toolspec.json \
  --interfaces=url=SERVER_URL,protocolBinding=jsonrpc

toolspec.json に MCP 仕様準拠の annotations を含めることで、 プロトコルレベルメタデータが McpServer ディスカバリリソースに登録されます。

ステップ 2: ツールメタデータを参照する IAP egress ポリシーを作成

JSON 
{
  "policy": {
    "bindings": [
      {
        "role": "roles/iap.egressor",
        "members": [
          "principal://iam.googleapis.com/projects/1234567890/locations/global/workloadIdentityPools/my-pool.svc.id.goog/subject/ns/default/sa/my-ae-agent"
        ],
        "condition": {
          "title": "Allow read-only egress to MCP server tools",
          "expression": "api.getAttribute('iap.googleapis.com/mcp.toolName', '') == 'GitHubTool' && api.getAttribute('iap.googleapis.com/mcp.tool.isReadOnly', false) == true && api.getAttribute('iap.googleapis.com/request.auth.type', '') == 'MCP'"
        }
      }
    ]
  }
}
Bash 
gcloud iap web set-iam-policy agents-iap-policy.json \
  --project=PROJECT_ID \
  --resource-type=agent-registry \
  --mcp-server=MCP_SERVER_ID \
  --region=REGION

CEL 条件式でツール名や読み取り専用ヒントを参照し、特定エージェントに対してツール単位のアクセスを許可します。

⚠️ 注意: Google 管理のリモート MCP サーバー (自動登録) は global ロケーションにのみ作成されるため、 IAP ポリシーも --region=global で適用します。

💪 メリット

💼 ビジネス面

🔐 エージェントガバナンスの強化
ツールのリスク特性 (読み取り専用/破壊的) に基づく最小権限ポリシーを組織的に適用でき、エージェントによる意図しない破壊的操作のリスクを低減できる
📋 コンプライアンス対応
HITL 制御により、重要な操作の前に人間の確認を挟む統制を仕組みとして組み込める

🔧 技術面

🧩 標準準拠のメタデータ
MCP 仕様 (Tool オブジェクトスキーマ) に準拠したアノテーションをそのまま登録でき、既存の MCP エコシステムと互換性がある
🔗 ポリシーとメタデータの連動
レジストリに登録したツールメタデータが IAP の CEL 条件式から属性として参照できるため、ツール追加時もポリシー定義を汎用的に保てる (例: isReadOnly == true のツールのみ許可)

⚠️ デメリット・制約事項

🚧 制限事項

✗本機能は Preview であり、GA 前の機能は変更される可能性がある
✗ツール仕様ファイル (toolspec.json) の最大サイズは 10 KB
✗自動登録される Google / Google Cloud リモート MCP サーバーの McpServer リソースは global ロケーションにのみ作成されるため、リージョンを指定した参照や IAP ポリシー適用は NOT_FOUND エラーになる (リージョンでの管理が必要な場合は手動登録が必要)

🤔 考慮すべき点

→ツールアノテーションは多くの MCP クライアントで信頼できない情報 (untrusted) として扱われるヒントであり、それ単体をセキュリティ境界と見なすべきではない。IAP ポリシーなどの強制力のある制御と組み合わせて利用する
→destructiveHint と idempotentHint は readOnlyHint == false のときのみ意味を持つ
→手動登録では Agent Registry がサーバーを自動検査しないため、ツール仕様の正確な登録・更新は運用側の責任となる

🎯 ユースケース

📖 ユースケース 1: 読み取り専用ツールに限定したエージェント運用

シナリオ: 社内データ参照用のオーケストレーターエージェントに、外部 MCP サーバーのツールのうち読み取り専用のものだけを許可したい。

CEL 
// IAP egress ポリシーの CEL 条件式:
api.getAttribute('iap.googleapis.com/mcp.tool.isReadOnly', false) == true
  && api.getAttribute('iap.googleapis.com/request.auth.type', '') == 'MCP'

効果: ツールが追加されても、readOnlyHint: true のツールのみ自動的に許可対象となり、破壊的操作を伴うツールへのアクセスをポリシーレベルで遮断できる。

🙋 ユースケース 2: 破壊的ツール実行前の人間による承認 (HITL)

シナリオ: チケット作成やリソース削除など destructiveHint: true のツールについて、エージェントが自律実行する前にユーザー確認を挟みたい。

効果: Agent Registry 経由で配信されるツールアノテーションをもとに、MCP クライアントが確認プロンプトの表示要否を判断でき、重要操作に対する Human-in-the-Loop 統制を実現できる。

📌 まとめ

Agent Registry が MCP ツールのプロトコルレベルメタデータに対応したことで、 ツールのリスク特性に基づく IAP ポリシー制御と HITL 統制を、 レジストリを起点に一貫して構成できるようになりました。

エージェントが利用する MCP ツールのガバナンスを強化したい組織は、まず toolspec.json にアノテーションを付与して登録し、 iap.googleapis.com/mcp.tool.isReadOnly などの属性を使った egress ポリシーの適用を検討することを推奨します。 Preview 機能のため、本番適用時は仕様変更の可能性に留意してください。
