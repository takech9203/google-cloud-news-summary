☁️ Cloud Number Registry ⚠️ Breaking Change Preview

🧭 Cloud Number Registry
プロジェクト指定 (Project Designation) の強制適用

リリース日: 2026-10-30
カテゴリ: ネットワーク / IPAM
⏰ 2026/11/25
この日以降、指定プロジェクト (designated project) が構成されていない組織では、Cloud Number Registry のリソースディスカバリが停止します。 既存の検出済みリソースも更新されなくなるため、期限までの対応確認が必要です。

📋 概要

Google Cloud の IP アドレス管理 (IPAM) サービスである Cloud Number Registry に破壊的変更が発表されました。 組織内で Cloud Number Registry を管理するプロジェクトを org-number-registries リソースとして明示的に指定することが、 ディスカバリ継続の必須条件 になります。

Cloud Number Registry は組織全体の IP アドレス使用状況の表示・管理・計画を行うサービスで、読み取り専用のディスカバリプロセスが組織全体の IP アドレス情報をインポートします。 指定プロジェクトがない構成では、新しいリソースが検出されなくなるだけでなく、既存の検出済みリソースも更新されず、 実態と乖離した IPAM 情報 になってしまいます。

❌ Before (アップデート前の課題)

  • 指定プロジェクトを構成していなくてもディスカバリが動作するケースがあり、組織の IP アドレス情報を含むプロジェクトの 管理境界が曖昧 になる可能性があった
  • 組織全体の IP アドレス情報という機密性の高いデータへのアクセス制御が、専用の指定プロジェクトに基づいて 一貫して強制されていなかった

✅ After (2026/11/25 以降)

  • 指定プロジェクトがない構成では 新規リソースのディスカバリが停止
  • 既存の検出済みリソースは残るが 更新されなくなる (例: サブネットを削除しても検出済みレンジは残存)
  • ディスカバリと更新の継続には、組織に対する 指定プロジェクトの確認または構成が必須

2026 年 11 月 25 日を境に、指定プロジェクトの有無によって Cloud Number Registry のディスカバリ動作が変わります。 指定プロジェクトがない場合、検出済み情報は残るものの更新されず、実際のネットワーク構成と乖離していきます。

🔧 サービスアップデートの詳細

1️⃣ 指定プロジェクトの強制適用

→2026 年 11 月 25 日以降、指定プロジェクトがない構成ではリソースディスカバリが停止する
→既存の検出済みリソースは削除されないが、更新もされない (ソースリソースの変更が反映されなくなる)

2️⃣ 指定プロジェクトの仕組み

→組織レベルで Cloud Number Registry IPAM Admin ロール (roles/cloudnumberregistry.ipamAdmin) を付与された IAM プリンシパルが、org-number-registries リソースを作成してプロジェクトを指定
→1 つの組織で Cloud Number Registry を利用できるプロジェクトは 1 つのみ
→指定プロジェクトには組織全体の IP アドレスレンジ情報が格納されるため、専用の新規プロジェクトを作成して IAM ポリシーでアクセスを制限することを強く推奨

3️⃣ セットアップ時の前提条件化 (関連する変更)

→同日のリリースノートでは、組織に対して Cloud Number Registry をセットアップする前に、管理用プロジェクトの指定が必須であることも案内されている

📐 技術仕様

🔎 対応が必要かどうかの判断

状況 2026/11/25 以降の動作 必要なアクション
✅ 指定プロジェクトを構成済み ディスカバリは継続 不要 (指定内容の確認を推奨)
⚠️ 指定プロジェクトが未構成で利用中 ディスカバリ停止・既存検出レンジが未更新のまま残存 期限までにプロジェクトを指定する
➖ Cloud Number Registry を未利用 影響なし 新規セットアップ時はプロジェクト指定が前提条件

ロール 付与スコープ 用途
Cloud Number Registry IPAM Admin
(roles/cloudnumberregistry.ipamAdmin)		 組織 プロジェクト指定 (org-number-registries の一覧表示・作成・削除)
Cloud Number Registry IPAM Admin
(roles/cloudnumberregistry.ipamAdmin)		 プロジェクト IPAM 管理スコープの作成などのセットアップ・管理

✓対象プロジェクトで Cloud Number Registry API が有効化されていること

ステップ 1: 既存のプロジェクト指定を確認する

Bash 既存のプロジェクト指定を一覧表示 
gcloud alpha number-registry org-number-registries list \
    --organization=ORGANIZATION_ID \
    --location=global

組織に対して既にプロジェクトが指定されているかを確認します。コンソールでは Cloud Number Registry ページの [Manage] タブにある [Manage designated project] パネルの [Admin project] フィールドでも確認できます。

ステップ 2: プロジェクトを指定する (未指定の場合)

Bash org-number-registries リソースを作成してプロジェクトを指定 
gcloud alpha number-registry org-number-registries create ORG_NUMBER_REGISTRY \
    --admin-project=projects/PROJECT_ID \
    --target-scopes=organizations/ORGANIZATION_ID \
    --organization=ORGANIZATION_ID \
    --location=global

コンソールでは [Manage designated project] パネルからプロジェクトを選択して [Designate project] をクリックします。

ステップ 3: (参考) Cloud Number Registry の構成状況を確認する

Bash 組織での構成状況を確認 
gcloud alpha number-registry ipam-admin-scopes check-availability \
    --scopes=organizations/ORGANIZATION_ID \
    --location=global
💡 結果の読み方: 組織で Cloud Number Registry が既に構成済みの場合は UNAVAILABLE、未構成の場合は AVAILABLE が返ります。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓アクセス管理の明確化: 組織全体の IP アドレス情報の格納先が明示的に指定された単一プロジェクトに限定され、ガバナンスが強化される
✓推奨構成への統一: 専用プロジェクト + IAM ポリシーによるアクセス制限という推奨構成が組織全体で強制される

🛠️ 技術面のメリット

✓管理境界の一元化: 1 組織 1 プロジェクトの原則が強制され、IPAM 管理スコープの配置先が明確になる
✓セットアップフローの整合性: セットアップ時に指定プロジェクトとの一致が検証され、意図しないプロジェクトでの構成を防げる

🚧 制限事項

✗1 つの組織で利用できるプロジェクトは 1 つのみ
✗指定プロジェクトがない場合、2026/11/25 以降は新規リソースが検出されず、既存の検出済みリソースも更新されない
✗セットアップ済みプロジェクトの指定を削除するには、先に Cloud Number Registry の廃止 (decommission) が必要
✗Preview 段階のサービスであり、Pre-GA Offerings Terms が適用される

🤔 考慮すべき点

⚠️対応期限 (2026/11/25) までに組織のプロジェクト指定状況の確認が必要
⚠️ディスカバリ停止で検出済みレンジが実構成と乖離し、IP 利用状況や空きレンジ検索の結果が信頼できなくなる
⚠️指定プロジェクトには組織全体の IP アドレス情報が集約されるため、閲覧が必要なプリンシパルを限定するアクセス権設計が重要

🎯 ユースケース

📊 ユースケース 1: 既存利用組織の対応確認

シナリオ: Cloud Number Registry を既に利用して組織の IP アドレス利用状況を可視化しているが、プロジェクト指定が行われているか不明。

Bash 確認と指定の実行例 
# プロジェクト指定の有無を確認
gcloud alpha number-registry org-number-registries list \
    --organization=123456789 \
    --location=global

# 未指定であれば専用プロジェクトを指定
gcloud alpha number-registry org-number-registries create my-org-registry \
    --admin-project=projects/ipam-admin-project \
    --target-scopes=organizations/123456789 \
    --organization=123456789 \
    --location=global

✨ 効果: 2026 年 11 月 25 日以降もディスカバリと検出済みレンジの更新が継続され、IPAM 情報の鮮度が維持される。

🔒 ユースケース 2: 新規セットアップ時のセキュアな構成

シナリオ: これから組織に Cloud Number Registry を導入する。組織全体の IP アドレス情報へのアクセスを限定したい。

✨ 効果: Cloud Number Registry 専用の新規プロジェクトを作成して指定し、そのプロジェクトへの IAM アクセスを必要最小限のプリンシパルに限定することで、組織全体の IP アドレスレンジ情報の閲覧範囲を制御できる。

🌏 利用可能リージョンと関連サービス

🌐 ロケーション: Cloud Number Registry のリソース (org-number-registries、IPAM 管理スコープ、レジストリブック) は global ロケーション で管理されます。

🔗 関連サービス・機能

🖥️ Compute Engine / VPC
ディスカバリプロセスは組織内の Compute Engine リソース (VPC ネットワーク、サブネットなど) の IP アドレス情報をインポートする。検出済みレンジを変更するには、ソースとなる Compute Engine リソース側を変更する。
🔐 IAM (Identity and Access Management)
プロジェクト指定には組織レベルの Cloud Number Registry IPAM Admin ロールが必要。指定プロジェクトへのアクセス制御にも IAM ポリシーを使用する。
🏢 Resource Manager (組織)
Cloud Number Registry は組織単位で動作し、指定プロジェクトは組織に属している必要がある。
🌍 BYOIP (Bring Your Own IP)
BYOIP の public advertised prefix も専用の realm (byoip-ipv4 / byoip-ipv6) としてディスカバリの対象になる。
