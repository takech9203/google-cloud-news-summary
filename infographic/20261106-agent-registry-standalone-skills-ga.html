🗂️ Agent Registry: スタンドアロンスキルが GA に
スキルセキュリティスキャン・ガバナンス機能も提供開始

Agent Registry GA: スタンドアロンスキル 提供開始: セキュリティスキャン・ガバナンス Preview: CMEK 📅 リリース日: 2026-11-06

📝 概要

Agent Registry のスタンドアロンスキル (standalone skills) が一般提供 (GA) になりました。 スタンドアロンスキルは、エージェントへの指示 (SKILL.md)、オプションのスクリプト、ドメイン知識を モジュール化されたパッケージとしてまとめたもので、特定のエージェントデプロイメントから独立して管理できます。

あわせてスキルのセキュリティスキャンとガバナンス機能も提供開始。 アップロードされたスキルリビジョンを LLM ベースのスキャナーで自動スキャンし、 不正なデータ持ち出し・認証情報の露出・プロンプトインジェクションなどのリスクを Finding リソースとして検出します。 カスタム組織ポリシーによる全社的なスキャン強制、最小権限 IAM、CMEK (Preview) もサポートされます。

❌ Before (アップデート前の課題)

  • スタンドアロンスキルは 2026 年 7 月から Preview 段階で、本番利用には Pre-GA 提供条件が適用
  • プロンプトインジェクションや認証情報の埋め込みを自動検出する仕組みがなく、手動レビューに依存
  • 「スキャン無効スキルの登録禁止」などのポリシーを一元的に強制する手段がなかった
  • 保管時暗号化は Google デフォルトのみで、顧客管理鍵の選択肢がなかった

✅ After (アップデート後の改善)

  • Skill / SkillRevision / Publisher の 3 階層リソースが GA に。登録・バージョン管理・セマンティック検索・ガバナンスを正式サポート
  • アップロード時に LLM セキュリティスキャンが自動実行 (デフォルト ENABLED_BLOCKING)、結果は Finding リソースで確認
  • カスタム組織ポリシー制約で組織・フォルダ単位のスキャン強制が可能に
  • roles/agentregistry.user などで最小権限のスキル管理を実現
  • Cloud KMS の CMEK で保管時保護 (Preview、us / eu)
💡 ポイント: 複数のチーム・プロジェクトにまたがって AI エージェントのスキル (再利用可能なタスクロジック) を 安全に共有・統制したいプラットフォームチームやセキュリティ管理者にとって重要なマイルストーンです。

スキル開発者が ZIP パッケージをアップロードすると、Agent Registry が SkillRevision としてバージョン管理し、 LLM ベースのスキャナーが非同期にセキュリティスキャンを実行します。検出された問題は Finding リソースとして公開され、 ブロッキングポリシーの場合は問題のあるリビジョンのダウンロードやデフォルトリビジョンへの昇格がブロックされます。

⚡ 主要機能

1️⃣ スタンドアロンスキルの 3 階層リソースモデル (GA)

→Publisher: スキルの出所・検証ティア・命名プレフィックスを確立。Google 管理の FIRST_PARTY (例: cloud.google.com) と、カスタムスキルに自動割り当てされる PRIVATE の 2 種類
→Skill (コンテナ): 利用者が実行時に発見・解決するトップレベルリソース。defaultRevision ポインタを保持
→SkillRevision: イミュータブルなスナップショット。更新時は新リビジョンを作成するため、決定論的な実行・制御されたロールバック・監査可能性を確保
→スキル識別子は URN 形式 (例: urn:skill:projects-PROJECT_NUMBER:locations:global:private-incident-triage)

2️⃣ パッケージ仕様とバリデーション

→オープン標準の Agent Skills Specification に準拠した ZIP アーカイブとしてパッケージング
→アーカイブのルートに SKILL.md (YAML フロントマター + 自然言語の指示) が必須
→登録時に仕様準拠とペイロード制約を検証し、メタデータを検索用にインデックス化

3️⃣ 自動セキュリティスキャン

→アップロード時に SKILL.md・スクリプト・アセットを LLM で解析し、不正なデータ持ち出し・認証情報の露出・プロンプトインジェクションなどを検出
→検出結果は読み取り専用の Finding リソース (projects/.../locations/.../findings/FINDING_ID) として公開
→3 つのスキャンポリシー: ENABLED_BLOCKING (デフォルト: 問題検出時に DL とデフォルトリビジョン昇格をブロック) / ENABLED_NONBLOCKING (監査モード: 警告付きで許可) / DISABLED (スキャン無効)
⚠️LLM による解析は確率的であり、偽陽性・偽陰性が発生しうるため、検出結果は開発者による確認が必要

4️⃣ 組織ポリシーによるスキャン強制

→agentregistry.googleapis.com/Skill へのカスタム組織ポリシー制約で、CREATE / UPDATE 操作時にスキャンポリシーを評価
→例: resource.scanningConfig.policy == "DISABLED" を DENY して、スキャン無効化スキルの登録を組織全体で禁止
→Resource Manager タグによる条件付き除外 (テスト用プロジェクトの免除など) にも対応

5️⃣ 最小権限のスキル管理アクセス

→roles/agentregistry.user ロールで、エージェント・MCP サーバー・エンドポイントの編集権限なしに、スキル管理とスキャン設定のみを許可
→スキルリソース単位の IAM ポリシー (getIamPolicy / setIamPolicy) で、特定スキルへのアクセスを個別制御

6️⃣ CMEK によるスキルペイロードの保護 Preview

→Cloud KMS の顧客管理暗号鍵でスキルリビジョンのペイロードを保管時に暗号化
→対象ロケーションの SkillEncryptionSpec リソースを構成して利用 (対応: us / eu)

📦 リソースモデルとライフサイクル

項目詳細
リソース階層Publisher → Skill (コンテナ) → SkillRevision (イミュータブル)
リビジョンのリソース名projects/PROJECT_NUMBER/locations/LOCATION/skills/SKILL_ID/revisions/REVISION_ID
ライフサイクル状態 (targetState)DRAFT / ACTIVE / DISABLED / DEPRECATED / DECOMMISSIONED
パブリッシャー種別FIRST_PARTY (Google 管理・全プロジェクトで発見可能) / PRIVATE (private- プレフィックス自動付与)
パッケージ仕様Agent Skills Specification 準拠の ZIP (ルートに SKILL.md 必須)

📏 ペイロード制約 (インジェスト時)

制約項目上限
ZIP アーカイブサイズ (圧縮後)最大 1 MB
展開後の合計サイズ (スキャン有効時)最大 10 MB
個別ファイルサイズ (スキャン有効時)最大 1 MB
ディレクトリのネスト深度最大 8 階層
⚠️ 注意: スキャン有効時にサイズ上限を超えると、リビジョン作成が INVALID_ARGUMENT エラーで失敗するか、スキャンステータスが UNSUPPORTED_FORMAT になります。

🔐 IAM ロール (最小権限設計)

ロール用途
roles/agentregistry.userスキル・スキルリビジョンの作成/更新/削除、スキャン設定。エージェントや MCP サーバーの編集権限なし
roles/agentregistry.viewerスキル・リビジョン・パブリッシャー等の読み取り専用アクセス
roles/agentregistry.editorスキルに加え、エージェント・MCP サーバー・エンドポイントの編集
roles/agentregistry.admin全リソースへのフルアクセス。セキュリティ Finding の閲覧、CMEK 構成、スキル IAM ポリシー管理
roles/orgpolicy.policyAdmin組織・フォルダレベルでのスキャンポリシー強制
🛡️ セキュリティ推奨: roles/agentregistry.admin / roles/agentregistry.editor は信頼できる管理者のみに付与し、 エージェント自身には付与しないことが推奨されています (ツールアノテーションの悪意ある変更や不正エージェントの登録を防ぐため)。

🔑 CMEK の要件 (Preview)

項目詳細
対応スキルロケーションus / eu のみ (global は非対応)
必要な Cloud KMS 鍵ロケーションus → us、eu → europe (マルチリージョンの対称鍵)

ステップ 1: スキャンポリシー付きでスキルを登録

Bash スキルの登録 
gcloud agent-registry skills create SKILL_ID \
  --project=PROJECT_ID \
  --location=LOCATION \
  --display-name="DISPLAY_NAME" \
  --description="DESCRIPTION" \
  --payload="LOCAL_ZIP_PATH"
💡 ヒント: 新規スキルのスキャンポリシーはデフォルトで ENABLED_BLOCKING です。 スキャンが完了して問題が検出されなかった場合のみ、初期リビジョンが自動的に Active 状態に遷移します。

ステップ 2: 組織ポリシーでスキャンを強制

YAML skills-scan-constraint.yaml 
name: organizations/ORGANIZATION_ID/customConstraints/custom.skillsScanningEnforcement
resourceTypes:
- agentregistry.googleapis.com/Skill
methodTypes:
- CREATE
- UPDATE
condition: resource.scanningConfig.policy == "DISABLED"
actionType: DENY
displayName: Prevent Disabling Skills Scanning
description: Prevents creating or updating skills with scanning disabled.
Bash 制約とポリシーの適用 
gcloud org-policies set-custom-constraint skills-scan-constraint.yaml
gcloud org-policies set-policy skills-scan-policy.yaml

すべてのスキルでブロッキングモードを必須にする場合は、condition: resource.scanningConfig.policy == "ENABLED_BLOCKING" と actionType: ALLOW を設定します。

ステップ 3: CMEK の構成 (Preview、任意)

Bash SkillEncryptionSpec の構成 
gcloud alpha agent-registry skill-encryption-spec update \
  --project=PROJECT_ID \
  --location=SKILL_LOCATION \
  --kms-key=projects/KMS_PROJECT_ID/locations/KMS_LOCATION/keyRings/KEY_RING/cryptoKeys/KEY_NAME
⚠️ 注意: 対象ロケーション (us または eu) にスキルを登録する前に実行する必要があります。

ステップ 4: ライフサイクル状態の管理

Bash スキルの状態遷移 
gcloud agent-registry skills update SKILL_ID \
  --project=PROJECT_ID \
  --location=LOCATION \
  --target-state=DISABLED

DRAFT / ACTIVE / DISABLED / DEPRECATED / DECOMMISSIONED の各状態に遷移できます。

💪 メリット

💼 ビジネス面

  • エンタープライズガバナンスの確立: GA により SLA が適用され、本番環境でスキルの一元管理・共有・統制を安心して導入できる
  • サプライチェーンリスクの低減: 侵害・悪意あるスキルがエージェントに到達する前に自動スキャンで検出・ブロック
  • コンプライアンス対応: 組織ポリシーによる全社的なスキャン強制と CMEK による鍵管理で、規制要件や社内ポリシーに対応

⚙️ 技術面

  • 決定論的な実行と安全なロールバック: イミュータブルな SkillRevision にピン留めでき、defaultRevision ポインタを戻すだけでロールバック可能
  • 最小権限の運用: roles/agentregistry.user やスキル単位の IAM で、スキル管理者とレジストリ管理者の職務分離が可能
  • 監査可能性: 過去のリビジョンが明示的に削除されるまで保持され、履歴の検査が可能

⚠️ デメリット・制約事項

🚧 制限事項

✗セキュリティスキャンは LLM ベースの確率的な解析であり、偽陽性・偽陰性が発生する可能性がある。実行ごとに結果が変動したり、検出詳細にハルシネーションが含まれる可能性があるため、修正適用前に開発者による確認・検証が必須
✗スキャン有効時のペイロードサイズ制限 (展開後合計 10 MB、個別ファイル 1 MB) が適用される
✗スキャン設定の変更は変更後に作成されたリビジョンにのみ適用され、既存リビジョンは遡及スキャンされない
✗CMEK は Preview で、対応ロケーションは us / eu のみ (global 非対応)。スキルが既に存在するロケーションでは鍵の設定・変更ができない
✗カスタム Publisher リソースは登録できない (プライベートスキルには自動的に private- プレフィックスが付与される)

🤔 考慮すべき点

⚠️ CI/CD への影響: ENABLED_BLOCKING (デフォルト) では、スキャン保留中や Finding が存在するリビジョンの ダウンロード・デフォルトリビジョン昇格がブロックされるため、CI/CD パイプラインでのリリースフローに影響する可能性があります。
⚠️ デフォルトリビジョンの削除: デフォルトリビジョンに設定されているリビジョンを削除すると、 ポインタがクリアされてスキルが DISABLED 状態に遷移します。
💰 スキャン課金の開始: スキャン料金は 2026 年 12 月 31 日まで無料ですが、2027 年 1 月 1 日から従量課金が始まるため、 リビジョン作成頻度が高い場合はコストを見積もっておきましょう。

🎯 ユースケース

🏢 ユースケース 1: 組織全体でのセキュアなスキル共有基盤

シナリオ: 複数の開発チームがそれぞれ AI エージェント用のスキル (インシデントトリアージ、レポート作成など) を開発しており、プラットフォームチームが品質とセキュリティを統制しながら全社で再利用できるようにしたい。

Bash 実装例 
# プラットフォームチーム: 組織ポリシーでスキャン無効化を禁止
gcloud org-policies set-custom-constraint skills-scan-constraint.yaml
gcloud org-policies set-policy skills-scan-policy.yaml

# 開発チーム: roles/agentregistry.user のみでスキルを登録・バージョン管理
gcloud agent-registry skills create incident-triage \
  --project=governance-project \
  --location=global \
  --display-name="Incident Triage" \
  --payload="./incident-triage.zip"
✅ 効果: 開発チームはレジストリ全体の管理権限なしでスキルを自律的に管理でき、 プラットフォームチームはすべてのスキルが自動スキャンを通過することを組織ポリシーで保証できる。

🏦 ユースケース 2: 規制業界でのスキルペイロード保護

シナリオ: 金融機関が社内ノウハウを含むスキルパッケージを Agent Registry で管理したいが、保管時暗号化の鍵を自社で管理することが社内規程で求められている。

✅ 効果: us または eu ロケーションで SkillEncryptionSpec に Cloud KMS の CMEK を構成することで、 鍵のローテーション・アクセス制御・監査ログ・ライフサイクルを自社で管理しながらスキルを登録できる (Preview)。

Agent Registry でのスキルの登録・保存・検索・管理は無料です。課金が発生するのはスキル脆弱性スキャンのみです。

🌍 利用可能リージョン

✓スキルのレジストリロケーションとしては global などが利用可能 (詳細はドキュメントを参照)
✓CMEK (Preview) は us および eu ロケーションのみ対応で、それぞれ Cloud KMS の us / europe マルチリージョン鍵が必要

🔗 関連サービス・機能

🔑 Cloud KMS: CMEK によるスキルペイロードの保管時暗号化で使用。鍵のローテーション、アクセス制御、監査ログを顧客側で管理
🏛️ Organization Policy Service: agentregistry.googleapis.com/Skill に対するカスタム制約でスキャンポリシーを組織・フォルダ単位で強制。gcp.restrictNonCmekServices 等の CMEK 組織ポリシーとも連携
🔐 IAM: 事前定義ロール (agentregistry.user / viewer / editor / admin) とスキルリソース単位の IAM ポリシーによるアクセス制御
🏷️ Resource Manager (タグ): 組織ポリシーの条件付き除外 (テストプロジェクトの免除など) に使用
🚪 Agent Gateway / Identity-Aware Proxy (IAP): 登録済みリソースへのエージェント通信は IAP のイーグレスポリシー (roles/iap.egressor) で制御
🪣 Cloud Storage: スキル ZIP アーカイブを Cloud Storage バケットからインポートする場合は標準の Cloud Storage 料金が適用

📌 まとめ

Agent Registry のスタンドアロンスキルが GA となり、AI エージェントの再利用可能なタスクロジックを 本番環境でバージョン管理・検索・統制できる基盤が整いました。

LLM ベースの自動セキュリティスキャン、組織ポリシーによる強制、最小権限 IAM、 CMEK (Preview) の組み合わせにより、エージェントスキルのサプライチェーンセキュリティをエンタープライズレベルで確保できます。

💡 推奨アクション: エージェント基盤を運用している組織は、 スキャンポリシーのデフォルト (ENABLED_BLOCKING) がリリースフローに与える影響の確認と、 2027 年 1 月から始まるスキャン課金のコスト見積もりを進めることを推奨します。
