🔐 SECURE_CONTEXT 関数

リクエストスコープのコンテキストベースフィルタリングで、マルチテナントの動的アクセス制御を実現

リリース日: 2026-11-02
Google Cloud News

📝 概要

BigQuery の GoogleSQL に新しいセキュリティ関数 SECURE_CONTEXT が Preview として追加されました。 SECURE_CONTEXT(key) は、クエリ実行時にリクエスト単位 (request-scoped) で渡されたセキュアコンテキストパラメータの値を返す関数です。 jobs.query / jobs.insert API の secureContext フィールドに渡したユーザー属性・部門 ID・テナント識別子などに基づいて、 論理ビュー (logical view) 内で動的にデータをフィルタリング・評価できます。

従来は属性値ごとに静的なビューを個別作成する必要がありましたが、1 つのビュー定義で多数のテナント・属性に対応できるようになり、 大規模マルチテナントシステムや動的な属性ベースアクセス制御 (ABAC) の実装が BigQuery ネイティブにサポートされました。

🎯 対象ユーザー: SaaS などのマルチテナント型データ基盤を BigQuery 上に構築しているアプリケーション開発者・データプラットフォームエンジニア。 ただし、信頼できるアプリケーション (中間層サービス) のみが secureContext を設定できる設計が前提です。

❌ Before: アップデート前の課題

  • 属性やテナントごとにフィルタ条件を変えるには、属性値ごとに個別の静的ビューを作成・管理する必要があった
  • 大規模マルチテナントでは、テナントごとのテーブル・データセット分離やビューの量産は運用負荷が高く非現実的だった
  • クエリリクエスト単位で実行時コンテキスト (部門 ID、テナント ID など) をビューに安全に引き渡す標準的な仕組みがなかった

✅ After: アップデート後の改善

  • secureContext フィールドのキーと値を、論理ビュー内の SECURE_CONTEXT(key) で参照し動的にフィルタリング可能に
  • 静的ビューの量産が不要になり、1 つのビュー定義で多数のテナント・属性に対応
  • 大規模マルチテナントにおける動的な属性ベースアクセス制御 (ABAC) の実装パターンを BigQuery ネイティブにサポート

🏗️ アーキテクチャ図

信頼できる中間層アプリケーションがエンドユーザーを認証し、検証済みの属性を secureContext としてクエリリクエストに付与します。 論理ビュー内の SECURE_CONTEXT がその値を実行時に評価し、該当する行のみを返します。

⚡ 主要機能

1️⃣ リクエストスコープのセキュアコンテキストパラメータ

  • jobs.query / jobs.insert API リクエストペイロードの secureContext.secureParameterEntries フィールドにキーと値のペアを渡す
  • 論理ビュー内で SECURE_CONTEXT('キー名') として参照し、実行時に値が解決される
  • key は定数の非 NULL STRING リテラルまたはクエリパラメータで指定 (暗黙の型変換は不可)

2️⃣ 論理ビューでの動的フィルタリング

  • ビュー定義の WHERE 句などで SECURE_CONTEXT を使用し、ユーザー属性・部門 ID・テナント識別子に基づく動的なフィルタリングと評価が可能
  • 属性値ごとに静的ビューを個別作成する必要がなくなる

3️⃣ マルチステートメントクエリセッションとの連携

  • セッション利用時は、セッション作成時 (createSession: true) にセキュアコンテキストパラメータを指定する
  • セッション作成後の後続クエリは初期セッションコンテキストを自動的に継承し、secureContext の変更や新規指定はできない (コンテキストの固定化)

📋 SECURE_CONTEXT 関数の仕様

項目詳細
構文SECURE_CONTEXT(key)
戻り値の型STRING
key の型定数の非 NULL STRING リテラルまたはクエリパラメータ (coercion 不可)

📨 API リクエスト例 (secureContext フィールド)

JSON jobs.query リクエストボディ 
{
  "query": "SELECT * FROM my_dataset.sales_view",
  "useLegacySql": false,
  "secureContext": {
    "secureParameterEntries": {
      "user_dept": "Sales",
      "user_region": "US"
    }
  }
}

👁️ ビュー定義の例

SQL SECURE_CONTEXT を使用した論理ビュー 
CREATE OR REPLACE VIEW my_dataset.sales_view AS
WITH Orders AS (
  SELECT 1001 AS order_id, 'Sales' AS department, 250.00 AS amount UNION ALL
  SELECT 1002 AS order_id, 'Engineering' AS department, 500.00 AS amount UNION ALL
  SELECT 1004 AS order_id, 'Sales' AS department, 430.50 AS amount
)
SELECT order_id, department, amount
FROM Orders
WHERE department = SECURE_CONTEXT('user_dept');
💡 動作例: secureContext に {"secureParameterEntries": {"user_dept": "Sales"}} を渡して SELECT * FROM my_dataset.sales_view を実行すると、department = 'Sales' の行 (order_id 1001 と 1004) のみが返されます。

👍 メリット

💼 ビジネス面

✅ マルチテナント基盤の運用コスト削減: テナント・属性ごとに静的ビューやテーブルを量産する必要がなくなり、ビュー管理の運用負荷を大幅に削減できる
✅ 大規模 SaaS への適用: テナントごとのテーブル/データセット分離がデータ規模的に非現実的な大規模マルチテナントシステムでも、動的な属性ベースアクセス制御を実装できる

⚙️ 技術面

✅ 1 ビューで多数の属性値に対応: 実行時にリクエストから値を注入するため、ビュー定義は 1 つで済み、スキーマ変更やテナント追加時のビュー再作成が不要
✅ セッションでのコンテキスト固定: マルチステートメントセッションではセッション作成時のコンテキストが継承され、後続クエリによる改変ができないため、セッション内で一貫したコンテキストを保証できる
✅ アプリケーションロジックの簡素化: SQL 文字列へのテナント ID の動的埋め込み (SQL 組み立て) を避け、構造化された API フィールドでコンテキストを渡せる

⚠️ デメリット・制約事項

🚫 制限事項

❌ 論理ビューの定義内でのみ使用可能。アドホッククエリのトップレベル、マテリアライズドビュー、一時セッションビューでの呼び出しはエラーになる
❌ セキュアコンテキストで渡せる値は STRING 型のみ
❌ SAFE. プレフィックスは非サポート (SAFE.SECURE_CONTEXT(key) は解析エラー)
❌ 参照したキーがリクエストに存在しない場合、クエリはエラーで失敗する (NULL は返らない)
❌ セッション利用時はセッション作成時にのみコンテキストを指定でき、後から変更・追加できない
❌ Preview 機能のため、Pre-GA Offerings Terms が適用され、サポートが限定される場合がある

🤔 考慮すべき点

🛡️ 信頼境界の設計が必須: SECURE_CONTEXT はクエリリクエストペイロードの値をそのまま評価します。 secureContext を設定できるのは、クライアントを認証し検証済み属性を代理設定する信頼できるアプリケーション・中間層サービスに限定すること。 信頼できないエンドユーザー、クライアント、AI エージェントに直接設定を許すと、属性を偽装してビューのアクセス制御を回避できてしまいます。
🔍 サイドチャネル露出: ビュー内のフィルタはハードな分離境界ではありません。 ビューに任意の SQL を発行できる呼び出し元は、フィルタ対象外の行で失敗する式、処理バイト数などのクエリ統計、クエリ実行時間を通じて、 除外された行の存在や値を推測できる可能性があります。ビューに到達する SQL が信頼できない場合 (AI エージェント生成 SQL など)、 ビューフィルタのみでのテナント分離に依存しないこと。
📌 Google の推奨との位置づけ: 多くのマルチテナントワークロードでは、 テーブル/データセットレベルのテナント分離 + IAM ベースのアクセス制御、行レベルセキュリティ (RLS)、列レベルセキュリティ (CLS) の組み合わせが、 厳格なテナント分離とデータ漏洩防止のための Google 推奨ベストプラクティスであり続けます。 SECURE_CONTEXT はそれが非現実的な大規模・動的ケース向けの選択肢です。

🎯 ユースケース

🏢 ユースケース 1: 大規模マルチテナント SaaS のテナント別データフィルタリング

シナリオ: 数千テナントを抱える SaaS で、全テナントのデータを共有テーブルに格納している。 テナントごとにデータセットやビューを分けるのは管理上非現実的。

SQL テナント別フィルタリングビュー 
CREATE OR REPLACE VIEW app_dataset.tenant_orders_view AS
SELECT order_id, product, amount
FROM app_dataset.all_orders
WHERE tenant_id = SECURE_CONTEXT('tenant_id');

アプリケーションの中間層がエンドユーザーを認証し、検証済みの tenant_id を secureContext に設定してクエリを発行する。

✨ 効果: テナント追加のたびにビューを作成する運用が不要になり、1 つのビュー定義で全テナントに対応できる。

📊 ユースケース 2: 部門・地域などユーザー属性ベースの動的フィルタリング

シナリオ: 社内 BI アプリケーションで、ログインユーザーの所属部門と担当地域に応じて売上データの表示範囲を変えたい。

✨ 効果: user_dept や user_region のような複数のコンテキストパラメータを 1 リクエストで渡し、 ビュー側で動的に評価することで、属性の組み合わせごとのビュー作成なしに属性ベースアクセス制御を実現できる。

💰 料金

SECURE_CONTEXT は GoogleSQL の関数であり、この機能固有の追加料金に関する記載はありません。 クエリの実行には通常の BigQuery の料金 (オンデマンドまたはエディションの課金) が適用されます。 詳細は BigQuery 料金ページ を参照してください。

📌 まとめ

🔐 SECURE_CONTEXT 関数の Preview 提供により、BigQuery の論理ビューで実行時コンテキストに基づく動的フィルタリングが可能になり、 大規模マルチテナントシステムでのビュー量産やテーブル分離の負荷を軽減できます。

ただしビューフィルタはハードな分離境界ではなく、secureContext の設定は信頼できる中間層に限定する設計が必須です。 導入検討時は、RLS・CLS・IAM による従来の分離手法との比較を行い、信頼境界を明確にした上で評価することを推奨します。
