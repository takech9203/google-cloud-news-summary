🔄 _Trace バケットの再プロビジョニング機能が GA

データレジデンシー / CMEK 要件を既存バケットに事後適用
📅 リリース日: 2026-11-06

📝 概要

Cloud Trace のトレースデータを保存する _Trace オブザーバビリティバケットについて、既存バケットを 再プロビジョニング (reprovision) する機能が一般提供 (GA) になりました。 実行すると、バケットの保存ロケーションと暗号化設定が、組織・フォルダ・プロジェクトに設定した 「オブザーバビリティバケットのデフォルト設定」と一致するように作り直されます。

データレジデンシー (データ保存場所) や顧客管理の暗号鍵 (CMEK) に関する規制・コンプライアンス要件を、 すでにトレースデータの取り込みが始まった既存プロジェクトでも事後的に満たすための機能です。 CMEK の遡及適用、ロケーションの移動、またはその両方を 1 回のオペレーションで実施できます。

⚠️ 重要: 再プロビジョニングは破壊的 (destructive) なオペレーションです。 実行前に保存されていたトレースデータは完全に削除され、復元できません。 再プロビジョニング後のデータセットには、オペレーション開始以降に送信されたデータのみが含まれます。

❌ Before: アップデート前の課題

  • _Trace バケットは作成後に変更・削除できず、要件に合わないロケーションや Google デフォルト暗号化で自動作成されたバケットを是正する手段がなかった
  • 取り込み開始前にデフォルト設定や手動作成で構成しなかった場合、後からデータレジデンシーや CMEK の規制要件を満たすことが困難だった
  • 2026 年 8 月のアップデートで Cloud KMS 鍵の更新 (update) は可能になったが、ロケーション変更や「Google デフォルト暗号化 → CMEK」への切り替えには非対応だった

✅ After: アップデート後の改善

  • 既存の _Trace バケットに対して、デフォルト設定に基づく再プロビジョニングを API で実行し、保存ロケーションの変更や CMEK の遡及適用が可能に
  • 「CMEK のみ適用」「ロケーションのみ移動」「移動 + CMEK 適用」の 3 パターンに対応
  • Admin Activity 監査ログに実行者・対象バケットが記録され、コンプライアンス対応の証跡を残せる

再プロビジョニングはデフォルト設定を参照して新しい _Trace バケットを作成し、旧バケットを削除する長時間実行オペレーションです。 旧バケット内の既存トレースデータは復元不可能な形で削除されます。

⚡ 主要機能

🔑 1. CMEK の遡及適用

バケットのロケーションを変えずに、デフォルト設定で指定した Cloud KMS 鍵 (CMEK) による暗号化へ切り替え可能。 従来はバケット作成時にしか CMEK 構成を決められず、Google デフォルト暗号化から CMEK への変更手段がありませんでした。

🌍 2. 保存ロケーションの変更

_Trace バケットをデフォルト設定で指定した新しいロケーションに移動 (Google デフォルト暗号化のまま、または CMEK 適用と同時に)。 データレジデンシー規制で特定リージョンへの保存が求められる場合に利用します。

⏱️ 3. 長時間実行オペレーションとしての実行・監視

projects.locations.buckets.reprovision API を呼び出すと長時間実行オペレーション (Operation) が返ります。 operations.get で done: true になるまでポーリングして完了を確認 (完了まで約 4〜5 時間を想定)。 HTTP 503 / UNAVAILABLE の場合は指数バックオフでリトライします。

📋 4. 監査ログによる証跡

Admin Activity 監査ログにメソッド google.cloud.observability.v1.Observability.ReprovisionBucket として記録され、 実行者と対象バケットを追跡可能です。

🛠️ 設定方法

前提条件

✓対象プロジェクトで roles/observability.editor (または同等の権限を持つロール) が付与されていること
✓組織・フォルダ・プロジェクトのいずれかに、オブザーバビリティバケットのデフォルト設定 (デフォルト保存ロケーションと、CMEK を使う場合はロケーションごとの Cloud KMS 鍵) が構成されていること
✓既存データが削除されても問題ないことを確認済みであること (必要に応じて事前にエクスポートや分析を完了させる)

⚙️ ステップ 1: デフォルト設定の構成

組織・フォルダ・プロジェクトレベルで、デフォルト保存ロケーションと (CMEK を使う場合は) Cloud KMS 鍵を設定します。詳細は Set defaults for observability buckets を参照してください。

🚀 ステップ 2: 再プロビジョニングの実行

Observability API の projects.locations.buckets.reprovision メソッドを呼び出します。レスポンスとして長時間実行オペレーション (Operation) が返ります。

👀 ステップ 3: オペレーションの監視

operations.get で Operation.done が true になるまでポーリングします。成功時は response にバケットの新しい状態が、失敗時は error に gRPC ステータスが含まれます。オペレーション中は 2 つの _Trace バケットが一時的に表示されることがありますが、対応は不要です (成功時は旧バケット、失敗時は新バケットが削除されます)。

🔗 ステップ 4: 移行後の後処理

ロケーションを変更した場合、BigQuery へのリンク (リンク済みデータセット) は削除されるため再作成が必要です。また、分析ビューのパスも更新します。完了直後は旧バケットのキャッシュにより Trace エクスプローラにデータが表示されないことがありますが、約 10 分で自動的に解消します。

⚖️ メリットと制約事項

👍 メリット

💼 ビジネス面
✓規制要件への事後対応: すでに稼働中のプロジェクトでも、データレジデンシーや CMEK の規制・コンプライアンス要件を満たせる
✓監査証跡: Admin Activity 監査ログに実行記録が残り、「いつ・誰が・どのバケットを」是正したかを証明できる
⚙️ 技術面
✓プロジェクト再作成が不要: プロジェクトを作り直したり、トレース収集の仕組みを再構築したりする必要がない
✓1 オペレーションで完結: ロケーション移動と CMEK 適用を 1 回の API 呼び出しで同時に実施できる

⚠️ 制限事項・考慮すべき点

🚫 制限事項
✗既存データの完全削除: 開始前に保存されたトレースデータは完全に削除され、復元できない
✗バケットにつき 1 回しか実行できない (2 回目以降は FAILED_PRECONDITION)
✗対象は _Trace バケットのみ
✗CMEK から Google 管理の暗号化へ戻すことはできない
✗オペレーションのキャンセル・取り消しは不可
🤔 考慮すべき点
•完了まで約 4〜5 時間。オペレーション中の Trace エクスプローラや Observability Analytics でのクエリ動作は未定義のため、完了まで利用を避ける
•ロケーション変更時は BigQuery リンク済みデータセットが削除されるため、リンクの再作成と分析ビューのパス更新が必要
•実行前にデフォルト設定が意図したロケーション・鍵になっているか必ず確認 (現状と同じ設定なら INVALID_ARGUMENT で失敗)

🎯 ユースケース

🏦 ユースケース 1: 既存プロジェクトへの CMEK の遡及適用

シナリオ: 金融機関で、全テレメトリーデータに CMEK 適用を義務付ける社内セキュリティポリシーが制定された。 しかし既存プロジェクトの _Trace バケットは、トレース取り込み開始時に Google デフォルト暗号化で自動作成されていた。

Text 実装例 
1. プロジェクト (またはフォルダ/組織) のデフォルト設定に、バケットのロケーションに
   対応する Cloud KMS 鍵を設定
2. projects/PROJECT_ID/locations/LOCATION/buckets/_Trace に対して reprovision を実行
3. operations.get で完了を監視 (約 4〜5 時間)

効果: バケットのロケーションを変えずに CMEK が適用され、以降のトレースデータが顧客管理鍵で暗号化される。

🇪🇺 ユースケース 2: データレジデンシー規制への対応

シナリオ: 欧州の規制により、オブザーバビリティデータを特定リージョン内に保存する必要が生じたが、 既存の _Trace バケットは別のロケーションに自動作成されていた。

効果: デフォルト設定で対象リージョンを指定して再プロビジョニングすることで、バケットが規制に適合したロケーションに移動し、 組織ポリシー (ロケーション制限) と組み合わせて以降の逸脱も防止できる。

🔗 関連サービス・機能

→Cloud KMS: CMEK による暗号化に使用。鍵のロケーションはバケットのロケーションと一致している必要がある
→組織ポリシー (Organization Policy): ロケーション制限や CMEK 必須化のポリシーと組み合わせることで、新規バケットの逸脱を防止できる (2026 年 6 月 1 日以降、バケット作成フローで強制される)
→BigQuery: _Trace バケットのデータセットをリンクして分析可能。ロケーション変更時はリンクの再作成が必要
→Cloud Audit Logs: 再プロビジョニングの実行記録が Admin Activity 監査ログに記録される
→Cloud Logging: ログバケットにも同様のデフォルト設定・CMEK の概念があり、オブザーバビリティ全体のデータガバナンスとして併せて設計することが多い

💡 まとめ

既存の _Trace バケットを再プロビジョニングして、データレジデンシーと CMEK の規制要件を事後的に満たせるようになりました。

⚠️ 実行前の確認を: 既存トレースデータは完全に削除される破壊的オペレーションであり、実行は 1 回限りです。 デフォルト設定の内容とデータ削除の影響を十分に確認したうえで計画的に実施してください。
✅ 推奨: コンプライアンス要件があるプロジェクトでは、組織ポリシーとデフォルト設定を併用して、 新規バケットの逸脱防止も合わせて構成することを推奨します。
