Cloud SDK (gcloud CLI) Breaking Changes GA/Beta 昇格

⚡ gcloud CLI 594.0.0
フラグ優先順位の Breaking Changes と主要コマンドの GA 昇格

📅 リリース日: 2026-11-17

📋 概要

2026 年 11 月 17 日、Google Cloud CLI (gcloud) バージョン 594.0.0 がリリースされた。 gcloud auth、gcloud billing accounts、gcloud compute shared-vpc の各コマンド群における フラグと位置引数の優先順位に関する 3 件の Breaking Changes が含まれ、 これらのコマンドを利用するスクリプトや CI/CD パイプラインに影響する可能性がある。

従来は位置引数の後に --account や --project フラグを指定するとフラグの値が位置引数を上書きする一貫性のない動作が存在したが、 594.0.0 では 位置引数が常に優先される よう修正された。さらに、billing accounts の IAM 系コマンドと shared-vpc では位置引数が 必須化 され、フラグによる代替指定ができなくなった。

あわせて、Cloud SQL ブルーグリーンデプロイメント、Cloud Run リージョナルエンドポイント、Cloud Tasks バッチ操作などの GA 昇格、 GKE のクラスタスケールツーゼロ用フラグ追加など、多数の機能昇格・追加も含まれている。

🔴 Before (593.x 以前) の課題

  • 位置引数の後に --account を指定すると フラグが位置引数を上書き し、意図しないアカウントの認証情報が使用される可能性
  • IAM 系コマンドで ACCOUNT_ID を省略して --account で代替でき、認証用アカウントと操作対象の課金アカウントが混同されるリスク
  • shared-vpc で --project が PROJECT_ID を上書きし、意図しないプロジェクトへ共有 VPC 操作が実行される可能性
  • 指定順によって動作が変わり、スクリプトの挙動が予測しにくい

🟢 After (594.0.0 以降) の改善

  • 位置引数 (ACCOUNT_NAME / ACCOUNT_ID / PROJECT_ID) が 常にフラグより優先。指定順に依存しない一貫した動作に
  • billing accounts の IAM 系と shared-vpc では 位置引数が必須化 され、操作対象が明示的に
  • --account は本来の用途 (認証アカウント指定 + auth 系での位置引数省略時の代替) に整理
  • 意図しないアカウント・プロジェクトへの操作という事故リスクが低減

💡 ポイント: 594.0.0 以降は、位置引数とフラグを同時に指定した場合、指定順にかかわらず位置引数が常に優先される。 スクリプト内で両方を指定していた場合、使用されるアカウント / プロジェクトが変わる 可能性がある。

🚨 Breaking Changes (3 件)

1️⃣ gcloud auth 系コマンド: --account と ACCOUNT_NAME の優先順位修正

→対象: print-access-token、print-identity-token、login、application-default login、activate-service-account
→従来は位置引数の後に --account を指定するとフラグが位置引数 (旧名: ACCOUNT、現名: ACCOUNT_NAME) を上書きしていたが、修正後は 位置引数が常に優先
→ACCOUNT_NAME が省略された場合は、引き続き --account が適用される

2️⃣ gcloud billing accounts IAM 系: ACCOUNT_ID の必須化

→対象: get-iam-policy、set-iam-policy、add-iam-policy-binding、remove-iam-policy-binding
→位置引数 (旧名: ACCOUNT、現名: ACCOUNT_ID) が常に優先されるように変更
✗ACCOUNT_ID は常に必須 となり、--account フラグによる代替指定は不可 (エラーになる)

3️⃣ gcloud compute shared-vpc: PROJECT_ID の必須化

→対象: gcloud compute shared-vpc 配下のコマンド
→従来は位置引数の後に --project を指定するとフラグが PROJECT_ID を上書きしていたが、修正後は 位置引数が常に優先
✗PROJECT_ID は常に必須 となり、--project フラグによる代替指定は不可 (エラーになる)

🔧 技術仕様: Breaking Changes の影響マトリクス

コマンド変更内容影響を受けるパターン

gcloud billing accounts get-iam-policy ほか IAM 系 3 コマンド 位置引数優先 + ACCOUNT_ID 必須化 --account のみで課金アカウントを指定していたスクリプト (エラーになる)

🔍 影響確認のポイント

Bash 影響を受ける可能性のあるパターンの例 
# パターン 1: 位置引数とフラグの同時指定 (使用されるアカウントが変わる)
gcloud auth print-access-token user-a@example.com --account=user-b@example.com
# 593.x 以前: user-b のトークン → 594.0.0 以降: user-a のトークン

# パターン 2: 位置引数の省略 (594.0.0 以降はエラー)
gcloud billing accounts get-iam-policy --account=0X0X0X-0X0X0X-0X0X0X
# 594.0.0 以降: ACCOUNT_ID 位置引数が必須のためエラー

# パターン 3: 位置引数の省略 (594.0.0 以降はエラー)
gcloud compute shared-vpc enable --project=my-host-project
# 594.0.0 以降: PROJECT_ID 位置引数が必須のためエラー

✅ メリット

💼 ビジネス面

✓運用事故リスクの低減: 意図しないアカウントや課金アカウント、プロジェクトに対する IAM 操作・VPC 操作という潜在的なセキュリティ / ガバナンスリスクが解消される
✓監査性の向上: 操作対象リソースが位置引数で明示的に指定されるため、スクリプトのレビューや監査で対象を特定しやすくなる

🛠️ 技術面

✓一貫性のある引数解決: フラグと位置引数の指定順に依存しない予測可能な動作となり、スクリプトの信頼性が向上する
✓フラグの役割の明確化: --account は認証アカウントの指定、位置引数は操作対象の指定という役割分担が明確になる
✓自動化機能の拡充: Cloud Tasks のバッチ操作 GA、Cloud Run リージョナルエンドポイント GA など、CI/CD・自動化で利用できる GA 機能が増加した

⚠️ デメリット・制約事項

🚫 制限事項
  • gcloud billing accounts の IAM 系コマンドでは ACCOUNT_ID 位置引数が必須となり、--account フラグのみの指定ではエラーになる
  • gcloud compute shared-vpc では PROJECT_ID 位置引数が必須となり、--project フラグのみの指定ではエラーになる
🤔 考慮すべき点
  • サイレントな動作変更に注意: auth 系コマンドでは位置引数とフラグを併用していた場合、エラーにならずに 使用されるアカウントが変わる ため、エラー検知では発見できない。スクリプトの棚卸しが必要
  • CI/CD 環境のベースイメージ (Cloud Build のビルダーイメージ、GitHub Actions の setup-gcloud など) は自動的に新バージョンへ更新されることが多いため、更新タイミングを把握しておく
  • gcloud alpha/beta tasks delete の --from-file フラグは非推奨となったため、--tasks-from-file への移行も合わせて行う

🎯 ユースケース

📦 ユースケース 1: CI/CD パイプラインの影響調査と修正

シナリオ: 複数のサービスアカウントを切り替えながら gcloud コマンドを実行する CI/CD パイプラインで、gcloud auth print-access-token に位置引数と --account フラグの両方を指定していた。

Bash実装例
# 修正前: 位置引数とフラグが混在し、593.x 以前はフラグが優先されていた
TOKEN=$(gcloud auth print-access-token "$DEFAULT_ACCOUNT" --account="$DEPLOY_ACCOUNT")

# 修正後: 使用したいアカウントを位置引数で一意に指定
TOKEN=$(gcloud auth print-access-token "$DEPLOY_ACCOUNT")
✨ 効果: バージョンアップ後も意図したアカウントのトークンが確実に取得され、デプロイ先の取り違えを防止できる。

📬 ユースケース 2: Cloud Tasks バッチ操作 GA を活用したタスク運用の効率化

シナリオ: 大量のタスクを個別の gcloud tasks create-http-task 呼び出しで作成しており、実行時間と API 呼び出し数が課題だった。

Bash実装例
# JSON/YAML ファイルから複数タスクを一括作成 (GA)
gcloud tasks batch-create --queue=my-queue --location=us-central1 --tasks-file=tasks.yaml

# タスクレベルのリトライ設定 (GA) でキュー設定を個別に上書き
gcloud tasks create-http-task my-task \
  --queue=my-queue --url=https://example.com/handler \
  --max-attempts=3 --max-retry-duration=600s
✨ 効果: タスクの一括作成・一括削除により運用スクリプトが簡素化され、タスク単位のリトライ制御も GA 機能として本番利用できる。

💰 料金

gcloud CLI (Cloud SDK) 自体は 無料 で利用できる。 コマンドから操作する各サービス (Cloud SQL、Cloud Run、Cloud Tasks など) にはそれぞれのサービスの料金が適用される。

📝 まとめ

gcloud CLI 594.0.0 は、--account / --project フラグと位置引数の優先順位を修正する 3 件の Breaking Changes を含むリリースであり、auth 系コマンドでは エラーにならずに使用アカウントが変わる 可能性がある点が特に注意を要する。

CI/CD パイプラインや運用スクリプトで対象コマンドを使用している場合は、アップグレード前に位置引数とフラグの併用・省略パターンを棚卸しし、 位置引数で操作対象を明示する形へ修正 することを推奨する。 あわせて、Cloud SQL ブルーグリーンデプロイメントや Cloud Tasks バッチ操作など GA 昇格した機能の活用も検討したい。
