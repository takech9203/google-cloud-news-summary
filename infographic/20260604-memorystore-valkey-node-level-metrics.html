☁️ 概要

Memorystore for Valkey に Cloud Monitoring 向けの追加ノードレベルメトリクスが導入されました。インスタンス内の個々のノードの健全性とパフォーマンスに関する詳細なインサイトが得られ、ノードの問題をトラブルシューティングし、パフォーマンスを最適化するために使用できます。

マルチシャード構成やレプリカを持つ大規模なインスタンスを運用するチームに特に有用で、ホットスポットの特定やノード単位のキャパシティプランニングを実現します。

🔄 Before / After 比較

❌ アップデート前の課題

  • インスタンスレベルの集約メトリクスのみ利用可能
  • 個々のノードのパフォーマンス問題の特定が困難
  • シャード間のデータ偏りやホットスポット検出に外部ツールが必要
  • 特定ノードのメモリ圧迫やレプリケーション遅延の原因特定に時間がかかる

✅ アップデート後の改善

  • 個々のノードの CPU、メモリ、接続数、コマンド統計を直接確認可能
  • ノード間のリソース使用量を比較してホットスポットを即座に特定
  • 永続化（RDB/AOF）状態やレプリケーションオフセットをノード単位で監視
  • データ整合性の問題を早期検出

📈 主要メトリクスカテゴリ

全てのノードレベルメトリクスは instance/node/ プレフィックスで統一されています。

💡 メトリクスプレフィックス: memorystore.googleapis.com/instance/node/{category}/{metric_name}

🔌 クライアント接続

  • connected_clients - アクティブ接続数
  • blocked_clients - ブロック接続数
  • tracking_clients - トラッキング登録数
  • maxclients - 最大同時接続数
  • pubsub_clients - Pub/Sub クライアント数

⚙️ CPU / メモリ

  • cpu/utilization - CPU 使用率 (0.0-1.0)
  • memory/utilization - メモリ使用率
  • memory/usage - 総メモリ使用量
  • memory/rss_usage - 物理メモリ割り当て量
  • memory/peak_usage - ピークメモリ
  • memory/dataset_usage - データセット使用量

📊 コマンド統計

  • usec_count - 合計実行時間
  • calls_count - 呼び出し回数/分
  • rejected_calls_count - 拒否コマンド数
  • failed_calls_count - 失敗コマンド数

💾 永続化

  • rdb_bgsave_in_progress - BGSAVE 実行状態
  • rdb_last_bgsave_status - 最後の BGSAVE 成否
  • aof_fsync_lag - AOF fsync 遅延
  • aof_last_write_status - AOF 書き込み成否

🔄 レプリケーション

  • offset - レプリケーションオフセット
  • primary_sync_in_progress - 同期進行状態
  • sync_full_count - 完全再同期の回数

🔑 キースペース / ネットワーク

  • total_keys - 格納キーの総数
  • keyspace_hits_count - 成功キー検索数
  • keyspace_misses_count - 失敗キー検索数
  • net_input_bytes_count - 受信バイト数
  • net_output_bytes_count - 送信バイト数

⚡ 設定方法

📋 前提条件:
  • Memorystore for Valkey インスタンスが作成済み
  • Cloud Monitoring API が有効化済み
  • 適切な IAM 権限（monitoring.viewer ロール以上）が付与済み

Step 1: インスタンス確認

Bash 
# Memorystore for Valkey インスタンスの一覧を確認
gcloud memorystore instances list --location=us-central1

Step 2: メトリクスディスクリプターの確認

Bash 
# ノードレベルメトリクスのディスクリプターを確認
gcloud monitoring metrics-descriptors list \
  --filter='metric.type=starts_with("memorystore.googleapis.com/instance/node/")'

Step 3: アラートポリシー作成

Bash 
# CPU 使用率 80% 超過アラートの作成例
gcloud alpha monitoring policies create \
  --display-name="Valkey Node CPU Alert" \
  --condition-display-name="Node CPU > 80%" \
  --condition-filter='metric.type="memorystore.googleapis.com/instance/node/cpu/utilization" AND resource.type="memorystore.googleapis.com/Instance"' \
  --condition-threshold-value=0.8 \
  --condition-threshold-comparison=COMPARISON_GT \
  --condition-threshold-duration=300s \
  --notification-channels=projects/PROJECT_ID/notificationChannels/CHANNEL_ID

⚠️ 制約事項・考慮点

制限事項:
  • 現在 Preview ステータス - GA 時に仕様変更の可能性あり
  • Preview 機能には SLA が適用されない
  • 一部メトリクス (pubsub_clients, watching_clients) は Valkey 8.0 以降 のみ対応
考慮すべき点:
  • ノードレベルメトリクスの増加により Cloud Monitoring の取り込み量が増加する可能性（ただし通常無料）
  • 大規模インスタンスではダッシュボードのクエリ設計を適切に行う必要あり
  • アラート閾値はノードタイプや用途に応じて個別調整が必要

🎯 ユースケース

🔥 ユースケース 1: シャード間のホットスポット検出

シナリオ: 6 シャード構成のインスタンスで、特定キーパターンにアクセスが集中し、一部シャードでレイテンシが増加。

方法: instance/node/cpu/utilization で全ノードの CPU 使用率を比較 + instance/node/keyspace/total_keys でキー分散を確認。

効果: 特定ノードへの負荷集中を即座に把握し、キー設計の見直しやシャード数調整を迅速に判断。

🔄 ユースケース 2: レプリカ昇格前のデータ整合性確認

シナリオ: メンテナンスやフェイルオーバーの際、レプリカをプライマリに昇格させる前にデータ同期状態を確認したい。

方法: instance/node/replication/offset でプライマリとレプリカのオフセット差分を確認 + sync_full_count の増加を監視。

効果: レプリカがプライマリと完全同期していることを確認してから昇格を実行、データ損失リスクを排除。

💾 ユースケース 3: メモリ圧迫の早期検知とエビクション防止

シナリオ: キャッシュ用インスタンスで特定ノードのメモリ使用率が急増、意図しないキーエビクション発生前にアラートを受けたい。

方法: instance/node/memory/utilization に 75% 閾値アラートを設定 + evicted_keys_count の増加傾向を監視。

効果: 75% 超過時点で通知を受け、シャード追加やデータ整理を事前実行しサービス影響を回避。
