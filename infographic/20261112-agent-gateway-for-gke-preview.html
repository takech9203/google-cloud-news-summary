🚪 Agent Gateway for GKE

Gemini Enterprise Agent Platform — GKE 上のエージェントトラフィックを一元ガバナンス
📅 リリース日: 2026-11-12
GKE Agent Platform Preview

📋 概要

Gemini Enterprise Agent Platform の Agent Gateway for GKE が Preview として公開されました。 GKE 1.37.2-gke.1042000 以降のクラスタ (現時点では Rapid チャンネル) を対象に、GKE 上で稼働するエージェントへの流入 (Client-to-Agent)、エージェントからの流出 (Agent-to-Anywhere)、エージェント間 (Agent-to-Agent) のすべてのトラフィックを制御する一元的な管理レイヤーを提供します。

これまで GKE 向けは「Coming soon」の位置づけでしたが、今回のアップデートにより、自己管理の GKE クラスタ上のエージェントと MCP サーバーにも、 Agent Runtime 上のエージェントと同じ Agent Identity・Agent Registry・ポリシーによるガバナンスを適用できるようになります。 構成は Kubernetes ネイティブで、サイドカーレスの ambient ネットワーキングと GKE Gateway API を活用します。

😣 Before: アップデート前の課題

  • Agent Gateway のガバナンス (Agent Identity、Agent Registry、アクセスポリシー、Model Armor) は Agent Runtime / Gemini Enterprise が中心で、自己管理の GKE 上のエージェントは対象外 (「Coming soon」で早期アクセス申請が必要)
  • GKE 上の流入・流出・エージェント間トラフィックに一貫したアイデンティティベースの制御を適用するには、サービスメッシュのサイドカー導入や Envoy 設定などを自前で設計・運用する必要があった
  • プロンプトインジェクション対策などの安全性スクリーニングをエージェントコードやクラスタごとに個別実装する必要があった

😊 After: アップデート後の改善

  • GKE 1.37.2-gke.1042000 以降で Agent Gateway for GKE を Preview 利用でき、GKE 上のエージェントと MCP サーバーが Agent Platform のガバナンス対象に
  • Agent Runtime と同一の Agent Identity・Agent Registry・ポリシーを適用し、Kubernetes ネイティブなリソースと GKE Gateway API でガバナンスを構成可能に
  • ambient ネットワーキングによりサイドカーなしで流出トラフィックを Secure Web Proxy へリダイレクトし、クラスタを出る前にポリシーを適用
  • SPIFFE ベースのアクセス制御、Model Armor スクリーニング、TLS インスペクション、拡張バインディングによるカスタムポリシーエンジン連携が可能に

クライアントからの流入は GKE Gateway (リージョナルアプリケーションロードバランサ) が、エージェントからの流出は ambient ネットワーキング経由の Secure Web Proxy が、クラスタ内のエージェント間通信は Namespace 単位の Layer 7 ambient プロキシが、それぞれ中央で定義したポリシーを適用します。

⚡ 主要機能

🔀 1. 3 つの通信経路を対象とした一元的なトラフィックガバナンス

→Client-to-Agent (流入): GKE Gateway (リージョナル ALB) 経由でクラスタに入り、エージェント到達前に認証とポリシーチェックを実施
→Agent-to-Anywhere (流出): ambient ネットワーキングがサイドカーなしでアウトバウンドを Secure Web Proxy へリダイレクトし、クラスタを出る前にポリシー適用
→Agent-to-Agent (クラスタ内): Namespace 単位の Layer 7 ambient プロキシがエージェント間トラフィックを統制

☸️ 2. Kubernetes ネイティブなポリシー構成

→Kubernetes ネイティブのリソースと GKE Gateway API でガバナンスを構成
→Agent Runtime 上のエージェントと同じ Agent Identity・Agent Registry・ポリシーが GKE 上のエージェントにもそのまま適用

🔐 3. アイデンティティベースのアクセス制御と安全性ガードレール

→各エージェントの SPIFFE アイデンティティに基づくアクセス制御
→Model Armor によるプロンプト / レスポンスのスクリーニング (プロンプトインジェクション、ジェイルブレイク、機密データ漏洩のブロック)
→流出エージェントトラフィックの TLS インスペクション
→拡張バインディング (extension bindings) によるカスタムポリシーエンジンの組み込み

📊 4. プロトコル対応と可観測性

→MCP (SSE / HTTP POST)、A2A、REST / gRPC (HTTP/1.1、HTTP/2) をサポート
→MCP トラフィックは JSON-RPC リクエストを検査し、ツール名・メソッド属性単位の細かなアクセスポリシーを適用可能
→アクセスログとトレースを Cloud Logging / Cloud Trace に集約 (Agent Observability)

ステップ 1: Rapid チャンネルのクラスタを用意

Bash Rapid チャンネルで対象バージョン以降のクラスタを作成 
# Rapid チャンネルで対象バージョン以降のクラスタを作成
gcloud container clusters create CLUSTER_NAME \
  --location=us-central1 \
  --release-channel=rapid \
  --cluster-version=1.37.2-gke.1042000

GKE 1.37.2-gke.1042000 以降が必要です。既存クラスタの場合はバージョンとチャンネルを確認します。

ステップ 2: 流入 (Client-to-Agent) の構成

GKE Gateway API を使用して Gateway リソース (リージョナルアプリケーションロードバランサ) を作成し、クライアントからエージェントへのトラフィックを Agent Gateway の認証・ポリシーチェック経由にします。

ステップ 3: 流出 (Agent-to-Anywhere) の構成

ambient ネットワーキングを有効化した Namespace でエージェントを稼働させ、GCPBackend カスタムリソースで Secure Web Proxy をゲートウェイエンドポイントとして定義します。

YAML Secure Web Proxy をゲートウェイエンドポイントとして登録 
# 例: Secure Web Proxy をゲートウェイエンドポイントとして登録
apiVersion: networking.gke.io/v1
kind: GCPBackend
metadata:
  name: swp-backend
  namespace: AGENT_NAMESPACE
spec:
  serviceUris:
    - //networkservices.googleapis.com/projects/PROJECT_ID/locations/REGION/gateways/SWP_NAME

ステップ 4: Agent Registry への登録とポリシー定義

Agent Platform の中央コントロールプレーンでエージェントと MCP サーバーを Agent Registry に登録し、アクセスポリシーや Model Armor テンプレートを定義します。

Bash Agent Gateway の管理コマンド 
# Agent Gateway の管理には gcloud network-services agent-gateways を使用
gcloud network-services agent-gateways --help
💡 補足: 詳細な手順は公式ドキュメント「Agent Gateway for GKE overview」を参照してください。

👍 メリット

💼 ビジネス面

既存 GKE 投資の活用
エージェントを Agent Runtime へ移行することなく、既に運用している GKE クラスタのまま Agent Platform の統一ガバナンスを導入できる。
一貫したセキュリティポスチャ
Agent Runtime / Gemini Enterprise / GKE (さらに cross-cloud) にまたがり、1 つのレジストリと 1 セットのポリシーで最小権限の統制を実現。
監査対応の簡素化
アクセスログとトレースが Cloud Logging / Cloud Trace に集約され、エージェント活動の完全な監査証跡を確保できる。

⚙️ 技術面

サイドカーレスの流出制御
ambient ネットワーキングによる Secure Web Proxy へのリダイレクトで、Pod へのサイドカー注入やアプリケーションコードの変更が不要。
クラスタを出る前のポリシー適用
流出ポリシーはトラフィックがクラスタを離れる前に適用され、データ流出 (exfiltration) リスクを低減。
Kubernetes ネイティブな運用
GKE Gateway API と Kubernetes リソースで構成でき、使い慣れたツールチェーンで運用可能。
細粒度のツール認可
MCP の JSON-RPC 検査により、呼び出せる MCP ツールを名前・メソッド属性単位で制御。

⚠️ デメリット・制約事項

🚧 制限事項

  • Preview 段階の機能であり、Pre-GA Offerings Terms が適用される。機能や提供時期は変更される可能性がある
  • GKE 1.37.2-gke.1042000 以降が必要で、現時点では Rapid リリースチャンネルのみで利用可能 (他チャンネルは近日対応予定)
  • 利用可能リージョンは europe-west1 と us-central1 の 2 リージョンに限定
  • Agent Gateway インスタンス 1 つあたり、Agent Registry 登録リソースは最大 5,000 まで

🤔 考慮すべき点

  • 自己管理型デプロイモデルのため、GKE Gateway (ロードバランサ) や Secure Web Proxy などのプロキシインフラはユーザープロジェクト内で自ら作成・運用する必要がある
  • Rapid チャンネルは最新機能をいち早く利用できる一方、本番ワークロードには安定性の観点で注意が必要。本番導入は他チャンネルへの展開を待つ判断も検討する
  • GKE ambient ネットワーキング (Preview) には、流出ポリシーが Namespace 単位、ホスト名フィルタリングに TLS インスペクションが必要、TLS インスペクション利用時は Secure Web Proxy のプライベート CA 証明書をコンテナイメージへ手動で組み込む必要がある、などの制限がある
  • Model Armor、Secure Web Proxy、アプリケーションロードバランサ、Cloud Logging / Cloud Trace など、組み合わせるサービスは各サービスの標準料金で課金される

🎯 ユースケース

🧩 ユースケース 1: GKE 上のマルチエージェントシステムへの統一ガバナンス導入

シナリオ: GKE 上で複数の LLM エージェントと MCP サーバーを運用している企業が、どのエージェントがどの外部 API・MCP ツールを呼び出せるかをアイデンティティベースで制御し、プロンプトインジェクション対策を全エージェントに一括適用したい。

🔗 ユースケース 2: クラスタ内エージェント間 (A2A) 通信の統制と可視化

シナリオ: 同一クラスタ内でオーケストレーターエージェントが複数のサブエージェントにタスクを委譲する構成で、エージェント間の呼び出し関係を統制・監査したい。

✅ 効果: Namespace 単位の Layer 7 ambient プロキシが A2A トラフィックを統制し、SPIFFE アイデンティティに基づき「どのエージェントがどのエージェントを呼び出せるか」を制御。呼び出しのログとトレースは Cloud Logging / Cloud Trace に集約され、マルチエージェントの挙動を可視化できる。

🧰 関連サービス・機能

🌐 Agent Gateway for cross-cloud

前日 (2026-11-11) に Limited Preview となった、Google Cloud 外 (EKS / AKS / OpenShift / ベアメタル) の Kubernetes クラスタ向けデプロイモデル。GKE 版と合わせて「どこで動くエージェントも 1 つのガバナンス」が揃いつつある。

📒 Agent Registry / Agent Identity

エージェントと MCP サーバーの中央レジストリと検証可能なアイデンティティ基盤。Agent Runtime と GKE で共通に利用される。

🚪 GKE Gateway API

Client-to-Agent トラフィックの入口となるリージョナルアプリケーションロードバランサを Kubernetes ネイティブに構成。

📡 GKE ambient ネットワーキング

サイドカーレスでトラフィックを横取りする L4 ノードプロキシ / L7 プロキシ基盤。Agent-to-Anywhere とクラスタ内 A2A の統制を担う。

🛡️ Secure Web Proxy

流出トラフィックのポリシー適用ポイント。URL フィルタリングや TLS インスペクションを提供。

🤖 Model Armor

プロンプト / レスポンスの安全性スクリーニング (プロンプトインジェクション、ジェイルブレイク、機密データ漏洩対策)。

📊 Cloud Logging / Cloud Trace

エージェントのアクセスログと OpenTelemetry トレースの集約先 (Agent Observability)。

📝 まとめ

Agent Gateway for GKE の Preview 公開により、Google 管理ランタイム (Agent Runtime / Gemini Enterprise)、cross-cloud に続いて、 自己管理の GKE クラスタでも Agent Platform の統一ガバナンスが利用可能になりました。

GKE Gateway API と ambient ネットワーキングを組み合わせたサイドカーレス構成で、流入・流出・エージェント間のすべてのトラフィックに SPIFFE アイデンティティベースの制御と Model Armor スクリーニングを適用できる点が特長です。

GKE でエージェントを運用するプラットフォーム / セキュリティチームは、Rapid チャンネルの検証用クラスタ (us-central1 または europe-west1) で ambient ネットワーキングと Gateway API の構成検証から始めることを推奨します。
