🗂️ Agent Registry
クロスプロジェクト管理境界

Agent Registry Preview AI エージェント Resource Manager
📅 リリース日: 2026-10-30

📌 概要

Agent Registry がクロスプロジェクト管理境界に対応しました (Preview)。 中央の「管理プロジェクト」から、複数の Google Cloud プロジェクトにまたがる AI エージェント・MCP サーバー・ツールを一元的に検出・検索・ガバナンスできます。

管理境界は Resource Manager の BoundaryConfig / Boundary / CapabilityConfig リソースで定義され、管理プロジェクトとメンバープロジェクトの 2 つのロールに 「管理ガバナンス」と「コンピュート実行」を分離することでマルチテナント分離を実現します。 各チームはメンバープロジェクトで自由にエージェントを構築し、管理者は境界全体の統一ビューを維持できます。

❌ Before: プロジェクト単位のサイロ

  • 検出・検索の範囲が単一のガバナンスプロジェクト内に限定
  • 複数プロジェクトの横断把握にはプロジェクトごとの個別クエリが必要
  • 他プロジェクトの資産確認には各プロジェクトへの個別の閲覧権限付与が必要

✅ After: 管理プロジェクトで一元化

  • 境界内の全メンバープロジェクトのエージェント・MCP サーバー・ツールを自動集約 (ロールアップ)
  • 1 回の list / search リクエストで境界全体の統合された結果セットを取得
  • 管理プロジェクトの Viewer 権限だけで境界全体を検出・検索可能
  • API 有効化・クォータ・課金・アクセス制御を管理プロジェクトに一元化
💡 誰に重要か: 組織全体でエージェントや MCP サーバーが増えるなか、 プロジェクト単位のサイロを超えてエージェント資産を統制したい プラットフォームチーム・セキュリティ管理者・AI エージェント基盤の設計者に重要なアップデートです。

Resource Manager の BoundaryConfig / Boundary / CapabilityConfig リソースがメンバープロジェクト群を中央の管理プロジェクトに接続し、 各メンバープロジェクトにデプロイされたエージェント・MCP サーバー・ツールが 管理プロジェクトの Agent Registry に自動的に集約される構成です。

⚡ 主要機能

🔍 1. 管理プロジェクトによる一元的な検出・検索

  • 管理プロジェクトがクロスプロジェクトの list / search リクエストのターゲットとして機能
  • 同一ロケーションのリソースを管理プロジェクトと全メンバープロジェクト横断で集約し、統合された結果セットとして返却
  • 単一プロジェクト検出とクロスプロジェクト検出は同一の API メソッドを使用 (対象プロジェクトのロールでスコープが決まる)
  • 特定メンバープロジェクトへの絞り込みは --filter="project_id=MEMBER_PROJECT_ID" で指定

📡 2. 自動検出リソースの境界横断ロールアップ

  • Agent Runtime の reasoning engine、Cloud Run サービス、GKE デプロイメントなどを自動取り込みし管理プロジェクトに集約
  • 手動登録の Service / Binding リソースは作成したプロジェクトにスコープ (境界全体で見せたい場合は管理プロジェクトに作成)
  • スタンドアロンの Skill / SkillRevision / Publisher / AiApplication は境界をまたいで集約されない (Google 管理スキルは任意のプロジェクトで検出可能)

🏷️ 3. 柔軟な境界定義 (タグベースのメンバーシップ)

  • タグキーなし: 組織・フォルダ配下の全子プロジェクトが単一境界に含まれる
  • タグキーあり (例: 123456789012/env): タグ値フィルタ (例: env=prod) で複数境界に分割。タグを継承・付与したプロジェクトは自動的に境界へ参加
  • 1 プロジェクトは親フォルダ・組織ごとに最大 1 つの境界にのみ所属可能

🧰 4. 管理プロジェクトのプロビジョニング方式の選択

  • セルフマネージド: --management-project で既存プロジェクトを指定。CapabilityConfig と同じ親の直下にあり、他の CapabilityConfig と兼任不可。削除後も通常プロジェクトとして保持
  • Google マネージド: フラグ省略で専用プロジェクトを自動作成 (ID プレフィックス google-mpf / google-mpo)。CapabilityConfig 削除とともに削除
  • いずれも CapabilityConfig 作成時に agentregistry.googleapis.com が管理プロジェクトで自動有効化

🔧 技術仕様

📋 管理境界を構成する Resource Manager リソース

リソース役割
BoundaryConfig 組織・フォルダに設定し、境界の分割ルールを確立。タグキー (単一) を指定するとタグフィルタベースの複数境界に分割可能
Boundary メンバープロジェクトの境界 (ペリメータ)。タグ値フィルタ (例: env=prod) でメンバーシップを動的に評価
CapabilityConfig 境界を管理プロジェクトに紐付け、有効化する管理機能を指定。Agent Registry では AGENT_MANAGEMENT (gcloud では agent-management) を構成

🌐 ロケーションごとのクエリロールアップ

クエリ対象集約動作
単一リージョン (例: us-central1, europe-west1) 同一リージョンの自動検出リソースを管理プロジェクト + 全メンバープロジェクト横断で集約。管理プロジェクト上の同リージョンの Service / Binding も含む
マルチリージョン (例: us, eu) 同一マルチリージョンのリソースを横断集約。単一リージョンのリソースは含まない
global global にデプロイされたリソースを横断集約。マルチリージョン・単一リージョンのリソースは含まない
スタンドアロン / メンバープロジェクト そのプロジェクト単体・そのロケーションのみ。クロスプロジェクトロールアップなし
⚠️ 境界と CapabilityConfig の関係: 複数の境界が同一の CapabilityConfig にアタッチされると、全境界のメンバープロジェクトが 同じ管理プロジェクトのレジストリに集約されます。環境ごとに可視性を分離したい場合は、 境界ごとに別の CapabilityConfig と管理プロジェクトを作成してください。

🔐 IAM ロール (管理境界での権限付与)

付与レベル対象
管理プロジェクト 境界横断で検出・管理するユーザー・サービスに Agent Registry ロールを付与。管理プロジェクトの Viewer は個別権限なしで境界全体を検索可能
メンバープロジェクト 特定プロジェクト内でエージェントやツールを構築・登録・保守する開発者にロールを付与
境界構成リソース BoundaryConfig / Boundary / CapabilityConfig の作成・管理には、親フォルダ・組織への管理者ロールが必要
👁️Agent Registry API Viewer (roles/agentregistry.viewer): エージェント、MCP サーバー、ツールなどの閲覧・検索
✏️Agent Registry API Editor (roles/agentregistry.editor): 登録・更新・削除を含む編集アクセス
🛡️Agent Registry API Admin (roles/agentregistry.admin): バインディングやスキル IAM ポリシーを含む全操作
👤Agent Registry User (roles/agentregistry.user): 閲覧に加え、スタンドアロンスキルとスキルリビジョンの作成・更新・削除

🛠️ 設定方法

✅ 前提条件:
  • 構成コマンドを実行するプロジェクトで Resource Manager API (cloudresourcemanager.googleapis.com) を有効化
  • 対象フォルダ・組織に対する境界構成リソースの管理者ロールを保有
  • (既存プロジェクトを管理プロジェクトにする場合) CapabilityConfig と同じ親の直下・ACTIVE 状態・他の CapabilityConfig の管理プロジェクトでないこと
1
Resource Manager API の有効化
Bash Resource Manager API を有効化 
gcloud services enable cloudresourcemanager.googleapis.com \
  --project=PROJECT_ID

管理境界の構成コマンドを実行するプロジェクトで Resource Manager API を有効化します。

2
CapabilityConfig の作成 (境界と管理プロジェクトの紐付け)
Bash agent-management 付き CapabilityConfig を作成 
gcloud resource-manager capability-configs create \
  CAPABILITY_CONFIG_ID \
  --folder=FOLDER_ID \
  --types=agent-management \
  --boundaries=folders/FOLDER_ID/boundaries/BOUNDARY_ID \
  --display-name="DISPLAY_NAME"
  • 組織レベルで作成する場合は --folder の代わりに --organization=ORGANIZATION_ID を指定
  • 既存プロジェクトを管理プロジェクトにする場合は --management-project=projects/PROJECT_NUMBER を追加。省略すると Google マネージド管理プロジェクトを自動作成
  • 作成時に agentregistry.googleapis.com が管理プロジェクトで自動的に有効化される
  • レガシーの app-management (app-enabled folder) が有効なフォルダには境界・CapabilityConfig を作成できない
3
メンバープロジェクトへのタグ付与 (タグベース境界の場合)
Bash タグ値をプロジェクトにバインド 
gcloud resource-manager tags bindings create \
  --tag-value=TAG_VALUE_NAME \
  --parent=//cloudresourcemanager.googleapis.com/projects/PROJECT_NUMBER

タグフィルタ付きの境界では、一致するタグ値 (例: 123456789012/env/prod) をバインドしたプロジェクトが動的に境界へ参加します。 タグフィルタなしのフォルダ・組織全体の境界では配下の全プロジェクトが自動的に含まれるため、このステップは不要です。

4
権限付与と運用開始

境界の確立後、管理プロジェクト上で境界横断の検出・管理を行うユーザー・サービスアカウントに Agent Registry ロールを付与します。メンバープロジェクト内でローカル操作が必要な場合は、 該当メンバープロジェクトで Agent Registry API を有効化します。

✨ メリット

💼 ビジネス面

✓エージェント資産の全社的なガバナンス: 分散する AI エージェント・MCP サーバー・ツールを単一の管理プロジェクトから統制。シャドー AI エージェントの把握やコンプライアンス対応が容易に
✓チームの自律性と中央統制の両立: 各チームは自分のプロジェクトで自由に構築・デプロイ、管理者は境界全体の統一ビューを維持
✓運用コストの集約: API 有効化、クォータ割り当て、課金を管理プロジェクトに一元化

⚙️ 技術面

✓マルチテナント分離: 管理ガバナンスとコンピュート実行を分離し、チーム間で他のメンバープロジェクトへの直接アクセスが不要
✓権限管理の簡素化: 管理プロジェクトの Viewer 権限だけで境界内全プロジェクトの資産を検索可能
✓API の一貫性: 単一プロジェクト検出とクロスプロジェクト検出が同一 API メソッドで動作し、クライアント実装を変えずにスコープ拡張
✓タグによる動的メンバーシップ: タグ付与だけで境界への参加・離脱が自動反映。環境別 (prod / dev など) の境界分割も可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 段階の機能であり、Pre-GA Offerings Terms が適用される。サポートが限定される可能性
✗1 プロジェクトは親フォルダ・組織ごとに最大 1 つの境界にのみ所属可能 (BoundaryConfig のタグキーは単一、有効タグ値はタグキーごとに 1 つ)
✗クエリのロールアップは同一ロケーション内に限定。単一リージョン / マルチリージョン / global をまたぐ集約は行われない
✗メンバープロジェクトで手動登録した Service / Binding リソースは管理プロジェクトにロールアップされない
✗スタンドアロンの Skill / SkillRevision / Publisher / AiApplication リソースは境界をまたいで集約されない
✗レガシーの app-management が有効なフォルダには境界・CapabilityConfig を作成できない
✗Workforce Identity Federation のサポートは限定的 (エラー時は Cloud Identity / Google Workspace 管理の標準 Google アカウントでアクセス)

🤔 考慮すべき点

⚠️ 可視性の分離: 複数境界を同一の CapabilityConfig にアタッチすると全境界が同じレジストリに集約される。 環境ごとに分離したい場合は境界ごとに別の CapabilityConfig と管理プロジェクトを用意する。
🔒 セキュリティ: roles/agentregistry.admin / roles/agentregistry.editor は信頼できる管理者のみに付与する。 エージェント自身へ直接付与すると、ツールアノテーション (readOnlyHint、destructiveHint など) の改ざんや 悪意ある外部エージェントの登録につながるリスクがある。
💡 中央登録の強制: 組織ポリシー constraints/gcp.restrictServiceUsage でメンバープロジェクトの agentregistry.googleapis.com をブロック (自動検出には影響しない)、または IAM Deny ポリシーで メンバープロジェクトの services.* / bindings.* 書き込み権限を拒否する方法がある。
🗑️ 削除時の注意: Google マネージドの管理プロジェクトは CapabilityConfig の削除とともに削除される。

🎯 ユースケース

📚 ユースケース 1: 全社 AI エージェントカタログの構築

シナリオ: 複数の事業部がそれぞれのプロジェクトで Agent Runtime (reasoning engine)、Cloud Run、GKE 上に エージェントや MCP サーバーをデプロイしている。プラットフォームチームは全社のエージェント資産を一元把握し、 オーケストレーターから横断的に利用可能にしたい。

Bash 組織レベルで境界と CapabilityConfig を構成 
# 組織レベルで境界と CapabilityConfig を構成
gcloud resource-manager capability-configs create org-agent-governance \
  --organization=ORGANIZATION_ID \
  --types=agent-management \
  --boundaries=organizations/ORGANIZATION_ID/boundaries/BOUNDARY_ID \
  --display-name="Org-wide Agent Governance"

# 管理プロジェクトで境界全体のエージェントを検索
# (特定メンバープロジェクトに絞る場合)
# --filter="project_id=MEMBER_PROJECT_ID"

効果: 各事業部のデプロイ済みエージェント・MCP サーバーが管理プロジェクトに自動集約され、 オーケストレーターや開発者は単一のエンドポイントから全社の資産を検出・検索できる。

🏷️ ユースケース 2: 環境別 (prod / dev) のガバナンス分離

シナリオ: 本番環境と開発環境のプロジェクトが同一フォルダに混在しており、 本番エージェントのカタログを開発環境とは分離して統制したい。

効果: BoundaryConfig にタグキー (例: env) を設定し、 env=prod / env=dev のタグ値フィルタで境界を分割。境界ごとに別の CapabilityConfig と管理プロジェクトを割り当てることで、環境ごとに独立した可視性とガバナンスを実現。 プロジェクトへのタグ付与だけで境界メンバーシップが自動反映される。

🛡️ ユースケース 3: 中央集権的なエージェント登録ポリシーの強制

シナリオ: セキュリティチームは、カスタムエージェントや外部 MCP サーバーの手動登録を 管理プロジェクトのみに限定し、メンバープロジェクトでの野良登録を防ぎたい。

効果: 組織ポリシー constraints/gcp.restrictServiceUsage でメンバープロジェクトの agentregistry.googleapis.com を拒否 (管理プロジェクトでオーバーライド) するか、 IAM Deny ポリシーで Service / Binding の書き込み権限を拒否することで、 すべての手動登録を管理プロジェクトに集約。自動検出によるランタイムワークロードの取り込みは影響を受けない。

🌍 利用可能リージョン

管理プロジェクトでのクロスプロジェクトロールアップは、Agent Registry がサポートする すべてのロケーションで利用できます (例: us-central1、europe-west1、us、eu、global)。

詳細は Agent Registry locations を参照してください。

🔗 関連サービス・機能

→Resource Manager: 管理境界の基盤。BoundaryConfig / Boundary / CapabilityConfig リソースと管理機能 (capabilities) の構成を担う
→Agent Gateway: Agent Registry と統合してポリシー適用を行うゲートウェイ。エージェントからの Egress トラフィックの認証・認可に IAP API を使用
→Identity-Aware Proxy (IAP): 登録済みリソースへのエージェント通信制御に IAP Egress ポリシー (roles/iap.egressor) を使用
→Vertex AI Agent Runtime / Cloud Run / GKE: メンバープロジェクトにデプロイされたこれらのランタイム上のエージェント・MCP サーバーが自動検出の対象
→Resource Manager タグ / 組織ポリシー / IAM Deny ポリシー: 境界メンバーシップの動的管理と、登録ポリシーの強制に利用

📝 まとめ

Agent Registry のクロスプロジェクト管理境界 (Preview) により、組織・フォルダ配下に分散する AI エージェント・MCP サーバー・ツールを中央の管理プロジェクトから 一元的に検出・検索・統制できるようになりました。

エージェントのマルチプロジェクト展開が進む組織では、Resource Manager の境界構成とタグ設計、 管理プロジェクトへの権限集約、メンバープロジェクトでの登録制限ポリシーを含めた ガバナンス設計を早期に検討することを推奨します。
