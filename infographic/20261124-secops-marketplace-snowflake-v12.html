❄️ Snowflake 統合 v12.0
Execute Simple Query の SQL インジェクション対策

📅 リリース日: 2026-11-24 ｜ サービス: Google SecOps Marketplace (Response Integrations) ｜ 機能: Execute Simple Query アクションの入力検証強化

📝 概要

2026 年 11 月 24 日、Google SecOps Marketplace の Snowflake 統合が Version 12.0 に更新されました。 今回の更新は新機能の追加ではなく、SOAR プレイブックから Snowflake にクエリを実行する Execute Simple Query アクションのセキュリティ強化 (SQL インジェクション対策) です。

Table、Fields To Return、Where Filter、Sort Field、Sort Order の 5 つのパラメータに入力検証 (input validation) が追加され、ステートメント区切り文字・コメントマーカー・ドル引用文字列・対応の取れていない引用符や括弧を含む入力が拒否されます。 あわせて 1 回のリクエストで実行できる SQL ステートメントは 1 つに制限されます。

💡 なぜ重要か: SOAR の統合アクションは、アラートやケースに含まれる攻撃者由来のデータ (エンティティ値、プレースホルダ展開された文字列など) をパラメータとして受け取ることが多く、SQL クエリの組み立てに使われる場合は SQL インジェクションの温床になり得ます。Snowflake はログイン履歴やクエリ履歴などの調査に有用なデータを保持しているため、SecOps から Snowflake を照会するプレイブックを運用している環境では早期アップデートを推奨します。

❌ Before (アップデート前の課題)

  • Table や Where Filter などのパラメータ値をもとに SQL を組み立てるが、構文レベルの検証なし
  • プレースホルダ経由で攻撃者が影響を与え得る値が渡ると、区切り文字 (;) やコメントマーカーで意図しない SQL を注入・連結されるリスク
  • 1 リクエストに複数の SQL ステートメントが含まれることを防ぐ仕組みがなかった

✅ After (アップデート後の改善)

  • 5 つのパラメータに入力検証を追加し、危険な構文要素を含む入力を拒否
  • ステートメント区切り文字 / コメントマーカー / ドル引用文字列 / 不対応の引用符・括弧をクエリ実行前に遮断
  • 1 リクエスト = 単一 SQL ステートメントに制限し、連結による多段実行を防止

🏗️ アーキテクチャ図

Version 12.0 では、プレイブックから渡されたパラメータが Snowflake SQL API に送られる前に入力検証レイヤーを通過するようになり、SQL インジェクションにつながる構文要素を含む入力はクエリ実行前に拒否されます。

⚙️ 主要機能

1️⃣ 5 パラメータへの入力検証の追加

対象パラメータ: Table、Fields To Return、Where Filter、Sort Field、Sort Order。SQL インジェクションに悪用される代表的な構文要素を検出し、リクエストを拒否します。

2️⃣ 拒否される入力パターン

🚫 ステートメント区切り文字 複数ステートメントの連結 (例: ... ; DROP TABLE ... のような注入) を防止
🚫 コメントマーカー クエリ後半を無効化してフィルタ条件を迂回する手口を防止
🚫 ドル引用文字列 Snowflake がサポートするドル引用 ($$...$$) を使ったエスケープ回避を防止
🚫 不対応の引用符・括弧 文字列リテラルやサブクエリの構造を壊してクエリ構文を改変する手口を防止

3️⃣ 単一 SQL ステートメントへの制限

Execute Simple Query の 1 回のリクエストで実行できる SQL ステートメントは 1 つのみに制限されました。クエリの連結による多段実行 (データ抽出 + 改ざんの同時実行など) を構造的に防止します。

パラメータ必須説明今回の検証対象
Database必須クエリ対象のデータベース名-

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓SOAR プラットフォーム経由のデータ侵害リスクの低減: Snowflake に格納された業務データ・セキュリティデータへの不正クエリ実行の攻撃経路が塞がれ、コンプライアンス・監査面での安全性が向上
✓運用変更なしで適用可能: 検証は統合内部で行われるため、正当なパラメータを使う既存プレイブックは原則そのまま動作

🔧 技術面のメリット

✓多層防御の強化: プレースホルダ展開で攻撃者由来の値が混入しても、クエリ実行前の検証レイヤーで遮断
✓単一ステートメント制限: ステートメント連結による多段攻撃 (データ抽出 + 改ざんの同時実行など) を構造的に防止

⚠️ デメリット・制約事項

⚠拒否対象の文字列 (セミコロン、コメント、ドル引用、不対応の引用符・括弧) を正当な用途で Where Filter などに含めていたプレイブックは、更新後にアクションが失敗する可能性
⚠Where Filter は従来から LIMIT/SORT キーワード不可・単一引用符のみサポートという制約があり、今回の検証強化と合わせて書き方に注意が必要
⚠自由度の高いクエリが必要な場合は Execute Custom Query アクションがあるが、SQL 文字列をそのまま渡す設計のため、信頼できない値の埋め込みは引き続き避けるべき

🎯 ユースケース

🎣 ユースケース 1: アラートエンティティを使った Snowflake 照会の安全化

シナリオ: フィッシングアラートの調査プレイブックで、アラートから抽出したユーザー名をプレースホルダとして Where Filter に埋め込み、Snowflake 上のログインイベントテーブルを照会している。

効果: 攻撃者がエンティティ値に SQL 構文 (例: ' OR 1=1 --) を仕込んでも、コメントマーカーや不対応の引用符が検証で拒否され、意図しないデータ抽出やフィルタ迂回が防止される。

🧑‍💻 ユースケース 2: SOC のセルフサービスクエリの統制

シナリオ: SOC アナリストが手動アクションとして Execute Simple Query を実行し、Snowflake 上の調査用データセットを照会する運用をしている。

効果: 入力ミスや意図的な複数ステートメントの実行 (照会に加えた更新・削除操作の混入など) が単一ステートメント制限により防止され、照会用途に限定した統制が利く。

🔗 関連サービス・機能

🧾 Execute Custom Query アクション (同統合)

任意の SQL を実行するアクション。LIMIT が自動付与されるが、クエリ文字列自体を渡す設計のため、今回の Simple Query のようなパラメータ単位の検証とは性質が異なる。

📥 Google SecOps Snowflake ログ取り込み (SNOWFLAKE パーサー)

Snowflake の LOGIN_HISTORY / QUERY_HISTORY を Cloud Storage または Amazon S3 経由で SecOps に取り込む機能。統合アクションによる照会と組み合わせて Snowflake 環境の監視・調査が可能。

📘 Google SecOps SOAR プレイブック

本アクションの主な実行主体。プレースホルダ展開によりアラート由来の値がパラメータに入るため、今回の検証強化の恩恵を直接受ける。
