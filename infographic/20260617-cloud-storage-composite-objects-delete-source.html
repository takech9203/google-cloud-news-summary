🪣 Cloud Storage: コンポジットオブジェクト作成時のソースオブジェクト自動削除

Cloud Storage GA
2026-06-17

📋 概要

Cloud Storage のコンポジットオブジェクト作成機能に、コンポジション処理の一環として一時ソースオブジェクトを自動削除するオプションが追加されました。deleteSourceObjects オプションにより、コンポジション処理とソース削除をアトミックに実行でき、早期削除料金の免除やソフトデリート/オブジェクトバージョニングの影響回避が実現されます。

💡 対象ユーザー: 大容量ファイルの並列アップロード、ログファイルの結合、データパイプラインでのオブジェクト連結を行うすべての Cloud Storage ユーザー

Before / After 比較

❌ Before (従来)

  • コンポジション後に追加の Delete API リクエストが必要
  • ストレージクラスの最低保存期間に基づく早期削除料金が発生する可能性
  • ソフトデリート/バージョニング有効時にソースオブジェクトが残存し追加ストレージ料金が発生

✅ After (新機能)

  • コンポジション処理の一部としてソースオブジェクトをハード削除 (追加リクエスト不要)
  • 早期削除料金の対象外
  • ソフトデリート/バージョニングによる保持なし (データはコンポジットオブジェクトに保存)

⚡ 主要機能

1. deleteSourceObjects オプション

→JSON API の Compose リクエストボディに "deleteSourceObjects": true を指定
→コンポジション成功時にソースオブジェクトをハード削除
→デフォルトは false (従来の動作と互換)
→gcloud CLI では --delete-source-objects フラグとして提供

2. 早期削除料金の免除

→ストレージクラスの最低保存期間に関係なく早期削除料金が発生しない
→Nearline (30日)、Coldline (90日)、Archive (365日) でも追加課金なし

3. ソフトデリート/バージョニングのバイパス

→削除されたオブジェクトはソフトデリートやバージョニングによって保持されない
→データはコンポジットオブジェクトに保存されるため、データ損失リスクなし

🔧 技術仕様

JSON API リクエスト

項目 詳細
エンドポイント POST https://storage.googleapis.com/storage/v1/b/{bucket}/o/{destinationObject}/compose
新規パラメータ deleteSourceObjects (boolean)
デフォルト値 false
最大ソースオブジェクト数 32
ソースオブジェクト要件 同一バケット内、同一ストレージクラス

必要な IAM 権限

権限 用途
storage.objects.create コンポジットオブジェクトの作成
storage.objects.get ソースオブジェクトの読み取り
storage.objects.delete 既存オブジェクトの上書き時
storage.objects.list ワイルドカード使用時
💡 推奨 IAM ロール: roles/storage.objectUser (Storage Object User)

📝 設定方法

前提条件

✓Cloud Storage バケットが作成済み
✓roles/storage.objectUser 以上の IAM ロールが付与済み
✓ソースオブジェクトが同一バケット内・同一ストレージクラス

gcloud CLI

Bash 
gcloud storage objects compose \
  gs://BUCKET_NAME/SOURCE_OBJECT_1 gs://BUCKET_NAME/SOURCE_OBJECT_2 \
  gs://BUCKET_NAME/COMPOSITE_OBJECT_NAME \
  --delete-source-objects

✅ メリット

ビジネス面

✓コスト削減: 早期削除料金が免除され、Nearline/Coldline/Archive の一時オブジェクトワークフローのコストが削減
✓ストレージ料金の最適化: ソフトデリートやバージョニングによる不要なストレージ料金発生を回避

技術面

✓API 呼び出し数の削減: コンポジションと削除を 1 リクエストで完了、オペレーション料金も節約
✓アトミック性の向上: コンポジションと削除が一体で実行され、中間状態での不整合が発生しにくい
✓並列コンポジットアップロードの簡素化: 大容量ファイルアップロードにおける一時オブジェクト管理が容易に

⚠️ デメリット・制約事項

制限事項

✗コンポジットオブジェクトには MD5 ハッシュメタデータフィールドがない (CRC32C のみ)
✗1 回のコンポーズリクエストで最大 32 個のソースオブジェクト
✗ソースオブジェクトは同一バケット内かつ同一ストレージクラスが必要
✗XML API では deleteSourceObjects オプションは利用不可 (JSON API とクライアントライブラリのみ)

考慮すべき点

✗deleteSourceObjects で削除されたオブジェクトは復元不可能 (ソフトデリート/バージョニングをバイパス)
✗リテンションポリシー設定済みバケットでは一時オブジェクトの削除ができない場合あり
✗デフォルトオブジェクトホールド有効時はホールドの解除が必要
✗Python/Node.js クライアントライブラリでは並列コンポジットアップロードが未サポート

🎯 ユースケース

1. 大容量ファイルの並列コンポジットアップロード

シナリオ: 10 GB のファイルを 32 チャンクに分割して並列アップロードし、コンポジットオブジェクトとして再構築

Bash 
gcloud storage objects compose \
  gs://my-bucket/upload-chunks/chunk_* \
  gs://my-bucket/final/large-file.dat \
  --delete-source-objects

効果: 一時チャンクファイルを自動削除し、追加の Delete リクエストと早期削除料金を回避

2. ログファイルの定期的な結合

シナリオ: 時間ごとに生成されるログファイル (Coldline ストレージ) を日次で 1 つのファイルに結合

JSON 
{
  "sourceObjects": [
    {"name": "logs/2026-06-17/hour-00.log"},
    {"name": "logs/2026-06-17/hour-01.log"},
    {"name": "logs/2026-06-17/hour-23.log"}
  ],
  "destination": {"contentType": "text/plain"},
  "deleteSourceObjects": true
}

効果: Coldline の 90 日最低保存期間に関わらず、時間別ログを早期削除料金なしで即座に削除可能

3. オブジェクトへのデータ追記

シナリオ: 既存のデータファイルに新しいデータを追記

Bash 
# 追記データを一時オブジェクトとしてアップロード
echo 'new data' | gcloud storage cp - gs://my-bucket/temporary_object

# 既存オブジェクトと一時オブジェクトをコンポーズ + ソース削除
gcloud storage objects compose \
  gs://my-bucket/existing_object gs://my-bucket/temporary_object \
  gs://my-bucket/existing_object \
  --delete-source-objects

効果: 一時オブジェクトと旧バージョンを自動削除し、バージョニング/ソフトデリートによる追加ストレージ課金を回避

💰 料金

コンポーズ操作は Class A オペレーションとして課金。deleteSourceObjects オプション自体に追加料金はなく、コスト削減効果があります。

シナリオ 従来 deleteSourceObjects 使用時
Nearline 一時オブジェクト (30日未満で削除) 早期削除料金あり 早期削除料金なし
Coldline 一時オブジェクト (90日未満で削除) 早期削除料金あり 早期削除料金なし
Archive 一時オブジェクト (365日未満で削除) 早期削除料金あり 早期削除料金なし
ソフトデリート有効バケット 保持期間分のストレージ料金 追加ストレージ料金なし
Delete API リクエスト ソースオブジェクト数 x 削除リクエスト料金 不要

📌 まとめ

deleteSourceObjects オプションは、並列アップロードやオブジェクト結合ワークフローにおけるコスト最適化と運用簡素化を実現する重要な機能です。特に Nearline/Coldline/Archive ストレージクラスの一時オブジェクトを使用するユースケースでは、早期削除料金の免除により大幅なコスト削減が期待できます。

💡 推奨アクション: 並列コンポジットアップロードやログ結合処理を行っているユーザーは、既存のワークフローに本オプションを組み込むことを推奨します。
