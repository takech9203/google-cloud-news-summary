🔐 GKE Gateway フロントエンド mTLS

クライアント証明書検証による強力な認証機能

GKE GA
2026-06-04

📋 概要

GKE Gateway がフロントエンド mTLS (mutual TLS) をサポートしました。この機能により、Gateway がクライアントから提示された証明書を検証し、認証を行うことが可能になります。

フロントエンド mTLS は、クライアントとロードバランサ間の通信において、サーバー側がクライアントの身元を暗号的に検証するセキュリティメカニズムです。ゼロトラストアーキテクチャやコンプライアンス要件の厳しい環境において、API やアプリケーションへのアクセスを証明書ベースで制御する必要があるエンタープライズユーザーを対象としています。

💡 対象業界: 金融、医療、政府機関など、強力なクライアント認証が必要な業界で特に有用です。

🔄 Before / After 比較

❌ Before (アップデート前)

  • フロントエンドのクライアント証明書検証には別途カスタムソリューションやサードパーティ製品が必要
  • Gateway API のネイティブ機能としてクライアント認証を統合管理する手段がなかった
  • mTLS 実現にはロードバランサの設定を手動で直接操作する必要があった

✅ After (アップデート後)

  • GKE Gateway リソースを通じて宣言的にフロントエンド mTLS を設定可能
  • ServerTLSPolicy + TrustConfig で Kubernetes ネイティブなワークフロー
  • クライアント検証モードを選択して柔軟なセキュリティポリシー適用が可能

⚡ 主要機能

🔑 クライアント証明書検証

→ServerTLSPolicy リソースでクライアント認証ポリシーを定義
→TrustConfig リソースで信頼済み CA 証明書チェーンを管理
→GKE Gateway コントローラが LB への設定を自動反映

🛡️ クライアント検証モード

→ALLOW_INVALID_OR_MISSING_CLIENT_CERT: 証明書が無効/未提示でもリクエスト転送
→REJECT_INVALID: 有効な証明書を提示したクライアントのみアクセス許可

📤 証明書メタデータのヘッダー転送

→クライアント証明書情報をカスタムリクエストヘッダーでバックエンドに転送
→SPIFFE ID、SAN、発行者情報なども含めることが可能

🔧 設定方法

📝 前提条件: GKE クラスタ稼働中 / Gateway API 有効 / Certificate Manager API 有効 / Network Security API 有効

Step 1: TrustConfig リソースの作成

信頼済み CA 証明書を含む TrustConfig リソースを作成します。

Bash 
# TrustConfig YAML を作成
cat << EOF > trust_config.yaml
name: my-trust-config
trustStores:
- trustAnchors:
  - pemCertificate: |
      -----BEGIN CERTIFICATE-----
      # ルート CA 証明書の内容
      -----END CERTIFICATE-----
EOF

# TrustConfig をインポート (グローバル)
gcloud certificate-manager trust-configs import my-trust-config \
  --source=trust_config.yaml \
  --location=global

Step 2: ServerTLSPolicy の作成

YAML 
name: my-frontend-mtls-policy
mtlsPolicy:
  clientValidationMode: REJECT_INVALID
  clientValidationTrustConfig: projects/PROJECT_ID/locations/global/trustConfigs/my-trust-config
Bash 
# ServerTLSPolicy をインポート
gcloud network-security server-tls-policies import my-frontend-mtls-policy \
  --source=server_tls_policy.yaml \
  --location=global

Step 3: Gateway リソースの設定

YAML 
kind: Gateway
apiVersion: gateway.networking.k8s.io/v1
metadata:
  name: my-gateway
spec:
  gatewayClassName: gke-l7-global-external-managed
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls:
      mode: Terminate
      certificateRefs:
      - name: my-tls-secret

Step 4: 証明書メタデータヘッダーの設定 (オプション)

YAML 
headerAction:
  requestHeadersToAdd:
  - headerName: "X-Client-Cert-Present"
    headerValue: "{client_cert_present}"
  - headerName: "X-Client-Cert-Chain-Verified"
    headerValue: "{client_cert_chain_verified}"
  - headerName: "X-Client-Cert-Hash"
    headerValue: "{client_cert_sha256_fingerprint}"

✅ メリット

💼 ビジネス面

✓コンプライアンス対応強化: PCI DSS、HIPAA、FedRAMP などの規制要件をネイティブに実現
✓セキュリティ態勢の向上: ゼロトラストモデルでのクライアント認証レイヤー追加
✓運用コスト削減: サードパーティ mTLS ソリューション不要、GKE Gateway で統合管理

🔬 技術面

✓宣言的設定: Kubernetes リソースとして管理、GitOps ワークフローと統合容易
✓柔軟な検証モード: ALLOW モードで監視し、問題なければ REJECT へ段階的移行
✓豊富な証明書メタデータ: ヘッダー経由でバックエンドに伝達、アプリ層で認可判断に活用

⚠️ デメリット・制約事項

制限事項:
  • 対応 GatewayClass は 3 種類に限定
  • TrustConfig は Gateway と同じロケーション (グローバルまたは同一リージョン) に作成が必要
  • Certificate Manager の TrustConfig リソースにサイズ制限 (クォータ) が存在

🤔 考慮すべき点

!クライアント証明書の配布・管理・失効処理は別途検討が必要 (Private CA や外部 PKI との連携)
!mTLS はクライアント側にも証明書管理の負担を課すため、利用者への影響を事前に評価すべき
!REJECT_INVALID モードに移行する前に、ALLOW モードで十分なテストと監視を推奨

🎯 ユースケース

🤝 ユースケース 1: API ゲートウェイでのパートナー認証

シナリオ: B2B プラットフォームで、外部パートナーからの API アクセスをクライアント証明書で認証。パートナーごとに異なる証明書を発行し、アクセス元を暗号的に特定する。

YAML 
# ServerTLSPolicy: パートナー証明書の検証 (厳格モード)
name: partner-api-mtls
mtlsPolicy:
  clientValidationMode: REJECT_INVALID
  clientValidationTrustConfig: projects/my-project/locations/global/trustConfigs/partner-trust-config

効果: IP アドレスベースのフィルタリングよりも堅牢なクライアント認証が実現し、証明書の失効管理により即時のアクセス無効化も可能。

🏢 ユースケース 2: マイクロサービス間通信のゼロトラスト化

シナリオ: クラスタ外部から内部サービスにアクセスする場合に、VPN 接続に加えてクライアント証明書による多層的な認証を適用。

効果: VPN 突破時にも証明書がない限りサービスへのアクセスが拒否されるため、多層防御が実現する。

✅ フロントエンド mTLS 自体には追加料金は発生しません。

ただし、以下の関連リソースにはそれぞれの料金体系が適用されます。

リソース 料金
GKE Gateway (ロードバランサ) Application Load Balancer の標準料金に準ずる
Certificate Manager (TrustConfig) Certificate Manager の料金に準ずる
Private CA (証明書発行) CA Service の料金に準ずる

🌍 利用可能リージョン

🌐グローバル: gke-l7-global-external-managed を使用する場合、全リージョンから利用可能
📍リージョナル: gke-l7-regional-external-managed および gke-l7-rilb を使用する場合、Application Load Balancer がサポートされている全リージョンで利用可能

🔗 関連サービス・機能

📜Certificate Manager: TrustConfig リソースを管理し、信頼済み CA 証明書を保持
🔒Network Security API: ServerTLSPolicy リソースの作成・管理に使用
🏛️CA Service: クライアント証明書の発行に活用可能
🔐Backend TLS (BackendTLSPolicy): バックエンド方向の TLS 検証。フロントエンド mTLS と組み合わせてエンドツーエンド mTLS を実現
🛡️Google Cloud Armor: フロントエンド mTLS と組み合わせてセキュリティポリシーを多層化
