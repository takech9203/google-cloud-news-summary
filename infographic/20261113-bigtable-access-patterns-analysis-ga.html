🗄️ Bigtable ✅ GA (一般提供) 📊 可観測性

📊 Bigtable アクセスパターン分析
「Access patterns」ページが GA に

リリース日: 2026-11-13

📝 概要

Google Cloud コンソールで Bigtable インスタンス/クラスタの読み取り・書き込みアクセスパターンを可視化できる Access patterns ページが GA になりました。 Bigtable がリクエストをサーバー側で自動的に 10 種類のクエリタイプ (ポイントリード、ショートスキャン、スパースリードなど) に分類し、QPS・レイテンシ・帯域幅・行スキャンのメトリクスを クエリタイプ別の内訳で表示します。

System insights (リソース使用率)、Key Visualizer (行キー分布) に続く 「クエリ中心」の第三の可観測性ツールとして、非効率なクエリパターンの検出、レイテンシのトラブルシューティング、 in-memory tier や Data Boost の適用対象ワークロードの特定に役立ちます。 Cloud Monitoring API 経由のプログラマティックな取得も可能です。

❌ Before: アップデート前の課題

  • ワークロードをクエリタイプ別に分解して分析する専用の可視化手段がなかった (System insights はリソース使用率、Key Visualizer は行キー分布のみ)
  • 返却行数よりはるかに多くの行をスキャンする「スパースリード」のような非効率パターンをコンソール上で直接特定することが困難
  • in-memory tier や Data Boost の適用に向くテーブル/アプリプロファイルを判断するデータが得にくかった

✅ After: アップデート後の改善

  • クラスタ/テーブル/アプリプロファイル単位で QPS 分布・レイテンシ (p50/p95/p99)・スキャン行数・セル数・送信バイト数をクエリタイプ別に可視化
  • Scanned rows vs Returned rows、Cells seen vs Sent cells の比較で読み取り効率の低下をコンソールで特定可能
  • ポイントリード中心 (in-memory tier 候補) や大規模スキャン (Data Boost 候補) をデータに基づいて特定
  • bigtable.googleapis.com/query_type/* メトリクスとして Monitoring API からも利用可能

🏗️ アーキテクチャ図

Bigtable が Data API リクエストをサーバー側でクエリタイプに自動分類して Cloud Monitoring に記録し、 コンソールの Access patterns ページでクエリタイプ別に可視化・分析して最適化アクションにつなげる流れです。

⚙️ 主要機能

1️⃣ クエリタイプ別のワークロード可視化

→受信リクエストを自動的に 10 種類のクエリタイプに分類し、クラスタごとの読み取り/書き込み/読み取り-書き込みクエリタイプの割合とレートを表示
→Group by オプションでテーブル別またはアプリプロファイル別に内訳を表示可能

2️⃣ 非効率なクエリパターンの検出とレイテンシ分析

→選択的なフィルタやガベージコレクション待ちセルにより返却量を大幅に上回るスキャンを行う「スパースリード」を特定
→フォワードスキャンより非効率な「リバーススキャン」をモニタリング
→サーバー側レイテンシのパーセンタイル (p99/p95/p50) をスキャン行数・返却行数・セル数と並べて比較し、レイテンシスパイクの原因を特定

3️⃣ 機能適用対象ワークロードの特定

→ポイントリードが多いテーブル/アプリプロファイルを特定し、Enterprise Plus エディションの in-memory tier の適用候補を発見
→大規模スキャンやバッチ読み取りワークロードを特定し、Data Boost サーバーレスコンピュートでサービングトラフィックから分離

4️⃣ Cloud Monitoring API によるプログラマティックアクセス

→bigtable.googleapis.com/query_type/* メトリクス (モニタリング対象リソース: bigtable_table) を Monitoring API、Metrics Explorer、カスタムダッシュボードから利用可能
→リソースラベル: project_id、instance、cluster、table / メトリクスラベル: query_type、app_profile、method

🔬 技術仕様

📈 Access patterns ページのチャートとメトリクス

メトリクス説明
QPS distribution選択した期間全体で集計した、クエリタイプ別のリクエスト割合と平均 QPS
Latencyクエリタイプ別のサーバー側レイテンシの推移 (p99 がデフォルト。p95、p50 に切り替え可能)
QPSクエリタイプ別の毎秒リクエスト数の推移
Returned rowsフィルタ適用後にクライアントへ返却された行数/秒
Scanned rowsフィルタ適用前に Bigtable が読み取った行数/秒 (Returned rows との比較で非効率なフィルタを特定)
Modified rows書き込みおよび読み取り-書き込みリクエストで変更された行数/秒
Cells seenフィルタ適用前に検査されたセル数/秒 (フィルタ除外分やガベージコレクション待ちセルを含む)
Sent cellsフィルタ適用後にクライアントへ返却されたセル数/秒
Sent bytes返却されたエンコード済み行データのバイト数/秒
💡 ポイント: すべてのチャートはクラスタ、テーブル、アプリプロファイルの各レベルで利用できます。

🏷️ 10 種類のクエリタイプ

クエリタイプメトリクスラベル分類基準 (概要)
ポイントリードQUERY_TYPE_POINT_READフィルタなしまたはシンプルフィルタの単一行キーのフォワード読み取りで、セル数・レスポンスサイズが小さい単一行の上限内
ショートスキャンQUERY_TYPE_SHORT_SCAN単一の連続行範囲のフォワードスキャンで、行数・セル数・バイト数が小さい上限内
リバースショートスキャンQUERY_TYPE_REVERSE_SHORT_SCANショートスキャンと同じ上限内のリバーススキャン
リバーススキャンQUERY_TYPE_REVERSE_SCANリバースショートスキャンに該当しないすべてのリバース読み取り
スパースリードQUERY_TYPE_SPARSE_READフィルタ除外や未回収セルにより、返却量を大幅に上回る行/セルをスキャンするフォワード読み取り
バルクリードQUERY_TYPE_BULK_READ複数行キー指定や大きな単一行の読み取りで、ポイントリードの上限を超えスパースリードに該当しないもの
その他の読み取りQUERY_TYPE_OTHER_READ大規模範囲スキャン、複数範囲スキャン、複雑なフィルタを使う読み取りなど、上記に該当しない ReadRows
ポイントライトQUERY_TYPE_POINT_WRITE単一行の MutateRow または小規模な MutateRows バッチ
その他の書き込みQUERY_TYPE_OTHER_WRITEポイントライトの上限を超える大規模なバッチ書き込みなど
読み取り-書き込みQUERY_TYPE_READ_WRITE条件付き書き込み (CheckAndMutateRow) やアトミックな増分/追記 (ReadModifyWriteRow)

🔄 読み取りクエリの評価順序

分類はメソッド名ではなく、リクエストパラメータ (行キー/範囲、reversed、フィルタ) と実行統計 (スキャン/返却した行数・セル数・バイト数) に基づき、リクエスト完了後にサーバー側で行われます。最初に一致したパターンが割り当てられます。

🛠️ 設定方法

✅ 前提条件

✓プロジェクトに対して Bigtable Viewer (または Bigtable Reader) と Monitoring Viewer の IAM ロールが付与されていること
✓分析対象の Bigtable インスタンスが存在すること

📍 ステップ 1: Access patterns ページを開く (インスタンスレベル)

  1. Google Cloud コンソールで Bigtable インスタンスの一覧を開く
  2. メトリクスを表示するインスタンスをクリックする
  3. ナビゲーションペインの Observability の下にある Access patterns をクリックする
  4. Cluster リストで分析対象のクラスタを選択する (デフォルトでは最初のクラスタが選択される)
💡 クラスタレベルで表示する場合: インスタンスの概要ページでクラスタ ID をクリックし、ナビゲーションペインの Access patterns をクリックします。

📍 ステップ 2: 内訳の切り替えと期間の調整

  1. Group by リストで内訳方法を選択する — None: クエリタイプのみで内訳表示 (デフォルト) / App profile: アプリプロファイル ID とアクセスパターンで内訳表示 / Table: テーブル ID とアクセスパターンで内訳表示
  2. 必要に応じて時間範囲セレクタで期間の変更や自動更新の切り替えを行う

💪 メリット

💼 ビジネス面

✓運用コストの最適化: スキャン過多な非効率クエリの特定・改善により、ノード CPU の無駄遣いを削減し、必要ノード数の抑制につなげられる
✓データドリブンな機能採用判断: in-memory tier や Data Boost の採用を、実測のアクセスパターンデータに基づいて判断できる

⚙️ 技術面

✓クエリ中心の可観測性: System insights (リソース使用率)、Key Visualizer (行キー分布) に加え、クエリタイプ別の分析軸が追加され、Bigtable の可観測性が向上
✓レイテンシトラブルシューティングの効率化: レイテンシパーセンタイルとスキャン/返却メトリクスを突き合わせ、レイテンシスパイクの原因となるアクセスパターンを素早く特定可能
✓自動化・連携が容易: 標準の Cloud Monitoring メトリクスとして提供されるため、既存のダッシュボードやアラートに組み込める

⚠️ デメリット・制約事項

🚫 制限事項

❗ SQL クエリは分類対象外: GoogleSQL for Bigtable のクエリはアクセスパターンとして分類されず、行・セル・バイトのアクセスパターンメトリクスに含まれません。QPS distribution、QPS、Latency チャートでは SQL クエリやその他の未分類リクエストは QUERY_TYPE_UNKNOWN として表示されます。

🤔 考慮すべき点

⚠️ 分類はパラメータと実行統計に基づく: メソッド名ではなくリクエストパラメータと実行統計で分類されるため、単一行読み取りでも複雑なフィルタや大量セルのスキャンがあるとスパースリード/バルクリード/その他の読み取りに分類されることがあります。
⚠️ 「シンプルフィルタ」が条件: ポイントリード、ショートスキャン、リバースショートスキャン、バルクリードに分類されるには、シンプルフィルタ (フィルタなし、column_range_filter、timestamp_range_filter、cells_per_column_limit_filter など) の使用が条件です。value_regex_filter、row_key_regex_filter、interleave、condition などは複雑なフィルタとして扱われます。

🔗 関連サービス・機能

📊 Cloud Monitoring アクセスパターンメトリクス (bigtable.googleapis.com/query_type/*) の基盤。Metrics Explorer やカスタムダッシュボード、API 経由での利用が可能。
🖥️ System insights クラスタ全体のリソース使用率 (CPU、ノード数、スループットなど) を表示する既存のモニタリングページ。Access patterns ページと補完関係。
🗺️ Key Visualizer 行キー範囲ごとのトラフィック分布を可視化し、ホットスポット検出に利用。クエリタイプ別分析と組み合わせて使用。
⚡ in-memory tier (Enterprise Plus) ポイントリード中心のワークロードの低レイテンシ化。Access patterns ページで適用候補を特定可能。
🚀 Data Boost 大規模スキャン/バッチ読み取りをサービングノードから分離するサーバーレスコンピュート。適用対象ワークロードの特定に活用。
📐 クエリ統計 (query stats) 個々の読み取りリクエストにおける rows seen / rows returned の比率を確認でき、Access patterns ページと併用して効率を評価。

🎁 まとめ

Bigtable のワークロードをクエリタイプ別に分析できる Access patterns ページが GA となり、 System insights、Key Visualizer と並ぶ第三の可観測性ツールとして追加コストの記載なく利用できるようになりました。

推奨アクション: まず Access patterns ページでスパースリードやリバーススキャンの有無を確認し、 非効率なフィルタ/スキーマの改善や、in-memory tier・Data Boost の適用判断に活用しましょう。
