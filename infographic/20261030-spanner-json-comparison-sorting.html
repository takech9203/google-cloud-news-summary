JSONB / JSON 値の比較・ソートと
検索インデックスによる等価比較の高速化

JSON 値をそのまま比較・GROUP BY / ORDER BY。CAST AS JSON と検索インデックスで半構造化データの活用がさらに進化

📋 概要

Spanner が JSONB (PostgreSQL ダイアレクト) および JSON (GoogleSQL ダイアレクト) 値に対する等価比較 (=, !=, IN など) と順序比較 (<, <=, >, >= など) をサポート。JSON / JSONB 値を他のデータ型へ変換することなく、そのまま GROUP BY 句や ORDER BY 句で使用できるようになりました。

さらに GoogleSQL では CAST(expression AS JSON) により幅広いデータ型を JSON に変換できるほか、JSON 値と非 JSON 値の直接比較では非 JSON 値を暗黙的に JSON へ型強制 (coercion) して比較します。加えて、検索インデックス (Search Index) で JSONB / JSON 列とそのサブパスへの = や IN などの等価比較を高速化できます。

❌ Before: アップデート前の課題

  • GROUP BY / ORDER BY には JSON_VALUE や LAX_INT64 などで一度別のデータ型 (STRING、INT64 など) に抽出・変換する必要があった
  • JSON 値と非 JSON 値 (数値・文字列リテラルなど) の比較には明示的な型変換の記述が必要だった
  • JSON ドキュメントの等価条件フィルタリングを効率的に高速化する手段が限られていた

✅ After: アップデート後の改善

  • JSON / JSONB 値を型変換なしでそのまま等価・順序比較、GROUP BY / ORDER BY に使用可能
  • CAST(expression AS JSON) と暗黙的型強制により json_col = 2 や json_col BETWEEN 1 AND 10 のような直接比較が可能
  • TOKENIZE_JSON / TOKENIZE_JSONB と検索インデックスで等価比較・包含判定・キー存在判定を高速化

従来は JSON 値を関数で別のデータ型へ変換してから比較・ソートする必要がありましたが、本アップデートにより JSON / JSONB のまま直接比較・集計・ソートでき、検索インデックスで等価比較を高速化できます。

✓JSON / JSONB 値同士を等価・順序で比較でき、GROUP BY / ORDER BY 句に直接使用可能

2️⃣ CAST AS JSON と非 JSON 値との比較における暗黙的型強制 (GoogleSQL)

✓CAST(expression AS JSON) で INT64、FLOAT32/64、NUMERIC、BOOL、STRING、BYTES、DATE、TIMESTAMP、INTERVAL、ARRAY、STRUCT、PROTO、ENUM、UUID、GRAPH_ELEMENT、GRAPH_PATH を JSON に変換可能
✓等価演算子 (=、!=、リスト形式の IN) では、Boolean、数値型、DATE、TIMESTAMP、UUID、STRING、ENUM、BYTES、および要素型がサポートされる ARRAY の暗黙的型強制をサポート
✓順序演算子 (<、<=、>、>=、BETWEEN) では、Boolean、数値型、DATE、TIMESTAMP、UUID、STRING、ARRAY をサポート (BYTES、RANGE、ENUM は JSON へのキャストで順序が保持されないため非サポート)

3️⃣ 検索インデックスによる JSON / JSONB 等価比較の高速化

✓GoogleSQL では TOKENIZE_JSON、PostgreSQL ダイアレクトでは TOKENIZE_JSONB でトークン化した列に CREATE SEARCH INDEX を作成
✓等価比較 (=、!=、<>、IN、NOT IN)、JSON 包含判定 (JSON_CONTAINS / @>、<@)、キー存在判定 (IS NOT NULL / ?、?|、?&) をインデックスで高速化
✓JSON 列全体だけでなく、doc.sub.path[0].key = "value" のようなサブパスに対する条件も高速化対象
✗<、<=、>、>= などの範囲比較は検索インデックスによる高速化の対象外

⚙️ 設定方法

📋 前提条件

✓Spanner データベース (GoogleSQL または PostgreSQL ダイアレクト) に JSON / JSONB 列が存在すること
✓検索インデックスを使用する場合は、Spanner Enterprise エディションまたは Enterprise Plus エディションであること

ステップ 1: JSON 値を直接比較・ソートするクエリを記述する (GoogleSQL)

SQL JSON 値の直接比較・GROUP BY / ORDER BY 
-- JSON 値を非 JSON 値と直接比較 (暗黙的型強制)
SELECT a.AlbumId
FROM Albums a
WHERE a.Metadata.MultiDiscCount = 2;

-- JSON 値を ORDER BY / GROUP BY に直接使用
SELECT a.Metadata.Genre AS genre, COUNT(*) AS cnt
FROM Albums a
GROUP BY genre
ORDER BY genre;

型変換関数を使わずに、JSON のサブパスをそのままフィルタ・集計・ソートに使用できます。

ステップ 2: 検索インデックスを作成して等価比較を高速化する

SQL TOKENIZE_JSON + CREATE SEARCH INDEX 
-- TOKENIZE_JSON で JSON 列をトークン化し、検索インデックスを作成
CREATE TABLE Albums (
  SingerId INT64 NOT NULL,
  AlbumId INT64 NOT NULL,
  Metadata JSON,
  MetadataTokens TOKENLIST AS (TOKENIZE_JSON(Metadata)) HIDDEN
) PRIMARY KEY (SingerId, AlbumId);

CREATE SEARCH INDEX AlbumsIndex ON Albums(MetadataTokens);

作成後、クエリオプティマイザが =、IN、JSON_CONTAINS、キー存在条件などをインデックスで高速化します。クエリ実行プランに Search index scan ノードが表示されるかでインデックス使用を確認できます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット
  • 開発生産性の向上: JSON データの集計・ソートに型変換の定型コードが不要になり、クエリがシンプルかつ保守しやすくなる
  • スキーマレスデータ活用の促進: 属性が可変な半構造化データ (商品カタログ、イベント属性など) をリレーショナルデータと同じ感覚で分析・集計できる
🔧 技術面のメリット
  • クエリ性能の向上: 検索インデックスにより JSON / JSONB 列とサブパスへの等価比較・包含判定・キー存在判定がインデックススキャンで高速化
  • 一貫した比較セマンティクス: JSON 型間・型内の比較ルールが明確に定義され、GROUP BY / ORDER BY / DISTINCT の挙動が予測可能
  • Spanner Graph との相乗効果: 動的プロパティは JSON 型として扱われるため、プロパティフィルタや GROUP BY / ORDER BY / RETURN DISTINCT で本機能の比較セマンティクスをそのまま活用可能
🚧 制限事項
  • JSON 型の列はプライマリキーやセカンダリインデックスのキーには使用不可
  • 検索インデックスは読み取り専用トランザクションでのみ使用される (読み書きトランザクションで強制使用するとエラー)
  • 検索インデックスで高速化されるのは等価比較・包含判定・キー存在判定のみ。範囲比較 (<, > など) や PostgreSQL の ->> によるテキスト抽出述語は対象外
  • 検索インデックスに格納する JSON ドキュメントのトークン出力サイズは 10 MB 未満であること (超過時は too many search token bytes エラー)
  • 検索インデックスは Enterprise / Enterprise Plus エディションで利用可能
⚠️ 考慮すべき点
  • 順序比較の暗黙的型強制では BYTES、RANGE、ENUM が非サポート (JSON へのキャストで順序が保持されないため)
  • IN 演算子の暗黙的型強制はリスト形式のみ対応し、最初のオペランドは JSON 式である必要がある
  • 大きなドキュメント全体の検索が不要な場合は、生成列でサブセットを抽出してインデックス化するのが推奨
  • JSONB のトップレベル空配列 [] が JSONB null より小さいなど、エッジケースの順序に注意

🎯 ユースケース

🛒 ユースケース 1: 可変属性を持つ商品カタログの集計・ソート

シナリオ: EC サイトで商品ごとに属性 (ブランド、カラー、評価など) が異なるため JSON 列で管理している。属性ごとの集計や評価順のソートを行いたい。

SQL JSON サブパスで直接ソート・集計 
-- 評価 (JSON サブパス) で直接ソート
SELECT p.ProductId, p.Attributes.brand, p.Attributes.rating
FROM Products p
ORDER BY p.Attributes.rating DESC
LIMIT 10;

-- ブランドごとに集計
SELECT p.Attributes.brand AS brand, COUNT(*) AS cnt
FROM Products p
GROUP BY brand;

効果: JSON_VALUE などによる型変換が不要になり、クエリが簡潔になる。属性スキーマの変更にもテーブル定義の変更なしで対応できる。

⚡ ユースケース 2: 検索インデックスによる JSON フィルタリングの高速化

シナリオ: 大量のイベントログを JSON 列で保持しており、status = "active" のような等価条件や特定キーの存在チェックで頻繁にフィルタリングする。

SQL 検索インデックスで高速化されるクエリ 
-- サブパスへの等価比較 (検索インデックスで高速化)
SELECT e.EventId
FROM Events e
WHERE e.Payload.status IN ("active", "pending");

-- キー存在判定 (検索インデックスで高速化)
SELECT e.EventId
FROM Events e
WHERE e.Payload.error_code IS NOT NULL;

効果: フルスキャンを避け、検索インデックスのスキャンにより読み取り専用トランザクションでのフィルタリングを高速化できる。
