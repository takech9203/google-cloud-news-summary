📅 リリース日: 2026-11-16
☁️ Google Cloud アップデート

📌 概要

Bigtable migration agent skill は、Apache HBase から Bigtable への移行を AI コーディングエージェントとの対話で計画・実行できるオープンソースのエージェントスキル (Apache 2.0 ライセンス) です。 GitHub の cloud-bigtable-ecosystem リポジトリで提供され、Gemini CLI、Claude Code、Antigravity、Cursor など Agent Plugins 互換のエージェントにインストールして使用します。

クラスタアセスメント、スキーマ・キャパシティプランニング、オフライン / オンラインのデータ移行、データ検証という 移行の全フェーズをカバーするランブックとスクリプトをエージェントに提供。 インフラ作成やデータ移動を伴うコマンドの実行前には必ず人間の承認を求める Human-in-the-loop 設計です。

🎯 対象ユーザー: オンプレミスやセルフマネージドの HBase クラスタを Bigtable へ移行したい データベース管理者・インフラエンジニア。従来は複数のドキュメントとオープンソースツールを自力で組み合わせる 必要があった移行作業を、エージェントとの対話で一貫して進められます。

❌ Before: アップデート前の課題

  • オフライン移行ガイド、HBase レプリケーションライブラリ、Schema Translation ツール、bigtable-beam-import など複数のドキュメント・ツールを自力で読み解いて組み合わせる必要があった
  • 移行前のクラスタアセスメント (スキーマ、GC ポリシー、リージョン分割、HDFS サイズ、コプロセッサの棚卸し) が手作業
  • スキーマ変換・キャパシティプランニング・事前分割テーブル作成などの計画立案が属人的で、ドキュメント化にも手間
  • 移行後のデータ検証 (行数照合、ハッシュ比較) の手順を個別に調べて実行する必要があった

✅ After: アップデート後の改善

  • スキルをインストールするだけで、アセスメントから検証までの 4 フェーズのワークフローを対話的に実行可能に
  • 付属の hbase_extractor.py でクラスタ情報を JSON として自動収集 (ローカル実行のため認証情報はエージェントに渡らない)
  • アセスメント結果から移行計画書 migration_plan.md を自動生成
  • オフライン移行 (ExportSnapshot + bigtable-beam-import) とオンライン移行 (WAL レプリケーション) の両方をエージェントがガイド

⚙️ 主要機能

🔍 Phase 1: クラスタアセスメント

  • hbase_extractor.py による自動収集と、対話形式のガイド付きチェックリストの 2 方式に対応
  • テーブルスキーマ、GC ポリシー (TTL / VERSIONS)、リージョン分割、HDFS サイズ、レプリケーションピア、コプロセッサを hbase_assessment_input.json に出力
  • --include-tables / --table-regex フラグで対象テーブルを絞り込み可能
  • スクリプトはローカル実行のため、クラスタの認証情報がエージェントに渡らない設計

📝 Phase 2: スキーマ・キャパシティプランニング

  • アセスメント JSON を解析し、移行計画書 migration_plan.md を生成
  • コプロセッサ・フィルタの代替策、GC ポリシーの変換、Bigtable インスタンスのプロビジョニング、事前分割 (pre-split) テーブル作成コマンドを含む

🚚 Phase 3: オフライン / オンラインのデータ移行

  • オフライン: HBase の ExportSnapshot で HFile を Cloud Storage にエクスポートし、bigtable-beam-import (Dataflow) でインポート。SequenceFile 経由の Dataflow テンプレートにも対応
  • オンライン: bigtable-hbase-replication ライブラリによる WAL ベースの非同期レプリケーション + スナップショットブートストラップで、ほぼ無停止の移行を実現

✅ Phase 4: データ検証

  • 行数照合: HBase の RowCounter と Bigtable の cbt count を比較 (期限切れセルの GC を考慮)
  • バイトレベル検証: HBase の HashTable と Dataflow の sync-table ジョブによるチェックサム比較

🧑‍⚖️ Human-in-the-loop 設計

  • インフラ作成やデータ移動を伴うコマンドの実行前に、必ず人間の承認を求めるワークフロー

🚀 設定方法

📋 前提条件

✓Google Cloud SDK と cbt CLI がインストールされ、gcloud auth login および gcloud auth application-default login で認証済みであること
✓移行先プロジェクトで Bigtable API、Bigtable Admin API、Dataflow API、Cloud Storage API が有効化されていること
✓(自動アセスメントを使う場合) ソースクラスタに到達できるホスト上に Python 3 と hbase shell (HDFS サイズ取得には hadoop CLI も) があること

ステップ 1: スキルのインストール

使用するコーディングエージェントに応じて、以下のいずれかを実行します。

Bash エージェント別インストールコマンド 
# Antigravity CLI
agy plugin install https://github.com/GoogleCloudPlatform/cloud-bigtable-ecosystem

# Claude Code
claude plugin marketplace add GoogleCloudPlatform/cloud-bigtable-ecosystem
claude plugin install bigtable@bigtable-marketplace

# Gemini CLI
gemini extensions install https://github.com/GoogleCloudPlatform/cloud-bigtable-ecosystem

ステップ 2: エージェントに移行を依頼

エージェントを起動し、HBase から Bigtable への移行を依頼すると、スキルが アセスメント → 計画 → 移行 → 検証 の 4 フェーズをガイドします。 自動アセスメントを使う場合は、エージェントの案内に従って hbase_extractor.py をソースクラスタに 接続できるホストで実行し、生成された hbase_assessment_input.json をエージェントに渡します。

Bash 対象テーブルを絞ってアセスメントを実行 
python3 hbase_extractor.py --include-tables my_table1,my_table2
💡 ポイント: 各フェーズでインフラ作成やデータ移動を伴うコマンドが提示された際は、内容を確認して承認します。

💡 メリット

💼 ビジネス面

  • 移行プロジェクトの期間短縮: アセスメントから検証までのワークフローが標準化され、ドキュメント調査やツール選定の時間を削減
  • 移行品質の底上げ: 行数照合とバイトレベルのチェックサム検証が手順に組み込まれ、データ欠損リスクを体系的に低減
  • 追加コストなし: スキル自体はオープンソースで無料。課金されるのは移行に使用する Bigtable、Dataflow、Cloud Storage などのリソースのみ

🔧 技術面

  • 既存の実績あるツールを統合: Schema Translation ツール、bigtable-beam-import、HBase レプリケーションライブラリなどをエージェントが適切な順序で使いこなす
  • セキュリティに配慮: アセスメントスクリプトはローカル実行でクラスタ認証情報がエージェントに渡らない。破壊的操作の前には必ず人間の承認が必要
  • オフライン / オンライン両対応: ダウンタイム許容度に応じて、スナップショットベースのオフライン移行と WAL レプリケーションによるほぼ無停止のオンライン移行を選択可能

⚠️ デメリット・制約事項

🚧 制限事項
  • Preview 段階であり、GA 前の機能として動作が予告なく変更される可能性がある。本番ワークロードでの利用はまだ非推奨
  • 現時点で利用できる移行パスは Apache HBase → Bigtable のみ (Cassandra、Aerospike は今後対応予定)
  • 自動アセスメントにはソースクラスタへのネットワーク到達性と、hbase shell などのローカルツールの導入が必要
🤔 考慮すべき点
  • エージェントが提示するコマンドは承認前に必ず内容を確認する (特にインスタンス作成や Dataflow ジョブ起動などコストが発生する操作)
  • スキルが利用する Bigtable 側の機能にも Preview 段階のものが含まれる可能性がある
  • オンライン移行は結果整合性ベースのレプリケーションのため、カットオーバー手順 (ピアの無効化・バッファのドレイン) をランブック通りに実施することが重要

🎯 ユースケース

📦 ユースケース 1: オンプレミス HBase クラスタの計画的なオフライン移行

シナリオ: 夜間メンテナンスウィンドウを確保できる社内分析基盤の HBase クラスタを Bigtable へ移行したい。テーブル数が多く、スキーマや TTL 設定の棚卸しが負担になっている。

Text 実装例 (オフライン移行の流れ) 
1. gemini extensions install https://github.com/GoogleCloudPlatform/cloud-bigtable-ecosystem
2. エージェントに「HBase クラスタを Bigtable に移行したい」と依頼
3. hbase_extractor.py でアセスメント JSON を生成しエージェントに提供
4. 生成された migration_plan.md をレビューし、承認しながら
   ExportSnapshot → Cloud Storage → bigtable-beam-import を実行
5. RowCounter / HashTable + sync-table で検証

✨ 効果: 手作業で数週間かかっていたアセスメント・計画立案が自動化され、 検証まで含めた一貫したプロセスで移行品質を担保できる。

🕐 ユースケース 2: ダウンタイムを許容できないサービスのオンライン移行

シナリオ: 24 時間稼働のユーザー向けサービスのバックエンド HBase を、 サービスを止めずに Bigtable へ移行したい。

✨ 効果: スキルが bigtable-hbase-replication ライブラリによる WAL レプリケーションとスナップショットブートストラップの手順をガイドし、ほぼ無停止でのカットオーバーを実現。 レプリケーションピアの無効化・再有効化といった間違えやすい手順もランブックに沿って安全に進められる。
