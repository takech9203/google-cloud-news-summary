⚙️ GKE: ワークロード最適化構成の生成

gcloud CLI で Redis / MySQL 向けの推奨構成 (ConfigMap / ComputeClass) を自動生成
📅 リリース日: 2026-08-05

📌 概要

GKE で、Redis や MySQL といった特定のワークロード向けにパフォーマンスを最適化した構成を gcloud CLI で生成できる機能が Preview として発表されました。 gcloud container workload profiles manifests create コマンドが、パフォーマンス推奨事項を反映した Kubernetes マニフェストを生成します。

生成されるマニフェストは、アプリケーションレベルの構成を含む ConfigMap と、 ノードレベルの構成を定義する ComputeClass の 2 種類。 チューニングの専門知識がなくても、Google の推奨構成を出発点として利用できます。

❌ Before: アップデート前の課題

  • Redis / MySQL のチューニング (io-threads や max_connections など) を各ソフトウェアのドキュメントを調査して手動で設計する必要があった
  • ワークロードに適したマシンタイプやノード構成を、利用者自身がベンチマークを繰り返して判断する必要があった
  • アプリ設定 (ConfigMap) とノード設定 (ComputeClass) を個別に整合させる作業が煩雑だった

✅ After: アップデート後の改善

  • gcloud CLI のコマンド 1 つで、ワークロードプロファイル (redis-7-caching、mysql-8-oltp) に基づく推奨構成を生成
  • アプリレベルとノードレベルの最適化が一括で YAML として出力され、レビュー・編集してから適用できる
  • OSS ベンチマーク (Memtier 2.2.1 / Sysbench 1.1.0) で改善効果を客観的に測定できる

🔧 主要機能

1️⃣ プロファイルに基づくマニフェスト生成

gcloud container workload profiles manifests create で、対象ワークロード (--workload=redis-7-caching や --workload=mysql-8-oltp)、クラスタバージョン、マシンタイプを指定して推奨マニフェストを生成。--output-path 指定で YAML ファイルとして保存できます。

2️⃣ アプリレベルの最適化 (ConfigMap)

アプリケーションが理解できる設定ファイルを ConfigMap として生成 (Redis: redis.conf、MySQL: default-auth.cnf)。Pod に Volume としてマウントし、アプリケーション起動時に参照させます。

3️⃣ ノードレベルの最適化 (ComputeClass)

ワークロードに適したノードのプロビジョニングを GKE に指示する ComputeClass を生成 (例: machineType: c4-standard-4、nodePoolAutoCreation: enabled: true)。Pod の nodeSelector (cloud.google.com/compute-class) で参照します。

4️⃣ ベンチマークによる効果測定

Redis の最適化は「読み書き比 4:1 のシングルノード look-aside キャッシュ」を Memtier 2.2.1 で、MySQL の最適化は「SSL 有効のシングルノード Read/Write OLTP (MySQL 8)」を Sysbench 1.1.0 で測定して決定されています。

生成されるマニフェストの例 (Redis)

YAML redis-7-caching プロファイルの生成例 
apiVersion: v1
kind: ConfigMap
metadata:
  name: redis.conf
data:
  redis.conf: |
    io-threads 2
    io-threads-do-reads yes
    save ""
---
apiVersion: cloud.google.com/v1
kind: ComputeClass
metadata:
  generateName: optimized-gke-redis-7-caching-
spec:
  nodePoolAutoCreation:
    enabled: true
  priorities:
  - machineType: c4-standard-4
  whenUnsatisfiable: DoNotScaleUp

ステップ 1: 最適化マニフェストの生成

Bash 推奨マニフェストの生成 
gcloud container workload profiles manifests create \
  --workload=redis-7-caching \
  --cluster-version=CLUSTER_VERSION \
  --options=machineType=MACHINE_TYPE \
  --output-path=/tmp/manifests.yaml

MySQL の場合は --workload=mysql-8-oltp を指定します。生成された推奨構成をレビューし、自身のユースケースに合わせて必要に応じて編集します。

ステップ 2: マニフェストの適用

Bash ConfigMap と ComputeClass の作成 
kubectl create -f /tmp/manifests.yaml

ステップ 3: 最適化を参照する Pod のデプロイ

YAML ConfigMap のマウントと ComputeClass の参照 
apiVersion: v1
kind: Pod
metadata:
  name: redis
spec:
  containers:
  - name: redis
    image: redis:7
    args:
    - /etc/gke/optimization/redis.conf
    volumeMounts:
    - name: gke-optimized-workload-config
      subPath: redis.conf
      mountPath: /etc/gke/optimization/redis.conf
      readOnly: true
  volumes:
  - name: gke-optimized-workload-config
    configMap:
      name: redis.conf
  nodeSelector:
    cloud.google.com/compute-class: optimized-gke-redis-7-caching-abc123
💡 ポイント: nodeSelector の ComputeClass 名は生成されたものに合わせて修正します。

ステップ 4: 最適化構成の適用確認

Bash 設定ファイルの読み込み確認 
# Redis の場合
kubectl exec redis -- redis-cli INFO server | grep config_file

# MySQL の場合
kubectl exec mysql -- mysql -e "SELECT DISTINCT VARIABLE_PATH FROM performance_schema.variables_info WHERE VARIABLE_PATH != '';"

✓宣言的な運用: 生成物は標準的な Kubernetes マニフェストであり、レビュー・編集・バージョン管理など既存の GitOps ワークフローに組み込みやすい

⚠️ 注意:
  • 推奨構成は特定のユースケース (Redis: 読み書き比 4:1 の look-aside キャッシュ、MySQL: シングルノード Read/Write OLTP) を前提に決定されているため、自身のユースケースが異なる場合はマニフェストの調整が必要
  • 適用前に推奨内容を Redis / MySQL の公式ドキュメントと照らし合わせてレビューすることが推奨される
  • ワークロード用に専用ノードプールの利用が推奨される

📝 まとめ

GKE 上の Redis / MySQL ワークロードに対して、Google の知見に基づくパフォーマンス最適化構成を gcloud CLI で簡単に生成できるようになりました。
