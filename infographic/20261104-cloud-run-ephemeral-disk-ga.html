📝 概要

Cloud Run のエフェメラルディスクが GA になりました。サービス・ジョブ・ワーカープールのインスタンスが稼働している間だけ存続するディスクベースのボリュームをマウントできる機能です。サイズとマウントパスを指定するだけで、Cloud Run が起動時にディスクを自動プロビジョニングし、ext4 でフォーマット + インスタンス固有キーで暗号化します。

従来の書き込み可能なローカルストレージ (インメモリボリューム) はメモリを消費していましたが、エフェメラルディスクはメモリとは独立したディスク領域を提供。大容量データの一時処理やディスクキャッシュを、メモリ増量のコストをかけずに実現できます。

❌ Before (アップデート前の課題)

  • インメモリボリュームはメモリを消費するため、大きな一時ファイルには高いメモリ割り当て = コスト増が必要だった
  • メモリに収まらない大規模データは、ファイル分割処理のオーケストレーションを自前で実装する必要があった
  • GA 以前はプレビュー段階で、本番ワークロードでの利用には SLA などの観点で慎重な判断が必要だった

✅ After (アップデート後の改善)

  • メモリと独立したディスクボリューム (1Gi〜100Gi) で、大容量の一時データをメモリ増量なしで処理可能に
  • GA となり、サービス・ジョブ・ワーカープールで本番利用前提の構成が可能に
  • 起動時に自動プロビジョニング・ext4 フォーマット・暗号化され、通常のファイル I/O でそのまま読み書き可能

ディスクはインスタンス起動時に自動作成・マウントされ、インスタンス終了時にデータごと完全に削除されます。終了前の SIGTERM から SIGKILL までの 10 秒間で、必要なデータを永続ストレージへ退避できます。

⚙️ 主要機能

💾 1. インスタンス専有のディスクベースボリューム

→サイズ (1Gi〜100Gi) とマウントパスを指定するだけで自動プロビジョニング
→起動時に ext4 でフォーマットされ、インスタンス固有のキーで暗号化
→特定インスタンスに専有され、他のインスタンスやリビジョンとは共有されない

🧩 2. サービス・ジョブ・ワーカープールすべてに対応

→Cloud Run のサービス、ジョブ、ワーカープールのいずれでも利用可能
→Google Cloud コンソール、gcloud CLI、YAML、Terraform で構成できる

📂 3. 通常のファイル I/O でアクセス可能

→各言語の標準ファイル操作ライブラリでそのまま読み書き可能
→ローカルファイルシステム前提の既存コンテナをコード変更なしで移行しやすい

🔄 4. ライフサイクルに連動したデータ削除

→シャットダウン (クラッシュ / スケールイン / 新リビジョン移行 / ジョブ完了) 時にデータは完全削除
→SIGTERM から SIGKILL までの 10 秒間で永続ストレージへの退避などのクリーンアップが可能

🔬 技術仕様

📏 ストレージとインスタンスの制限

フォーマット / 暗号化ext4 / インスタンス固有キーによる暗号化

📄 YAML での定義 (emptyDir / medium: Disk)

YAML Cloud Run サービス定義 
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: SERVICE
spec:
  template:
    spec:
      containers:
        - name: CONTAINER_NAME
          image: IMAGE_URL
          volumeMounts:
            - name: VOLUME_NAME
              mountPath: /mnt/my-volume
      volumes:
        - name: VOLUME_NAME
          emptyDir:
            medium: Disk
            sizeLimit: 10Gi

ステップ 1: サービスにエフェメラルディスクを追加

Bash gcloud でのボリューム追加 
gcloud run services update SERVICE \
  --execution-environment=gen2 \
  --add-volume=name=VOLUME_NAME,type=ephemeral-disk,size=10Gi \
  --add-volume-mount=volume=VOLUME_NAME,mount-path=/mnt/my-volume
💡 ヒント: size は 1Gi〜100Gi の範囲で指定。ジョブは gcloud run jobs update、ワーカープールは gcloud run worker-pools update を使用します (この 2 つでは --execution-environment の指定は不要)。

ステップ 2: アプリケーションからボリュームに読み書き

Python マウントパス配下へ通常のファイル操作で書き込み 
# Python の例: マウントパス配下へ通常のファイル操作で書き込み
f = open("/mnt/my-volume/sample-logfile.txt", "a")

マウントしたボリュームは通常のローカルファイルシステムと同様に扱えます。

ステップ 3: ボリュームの削除 (不要になった場合)

Bash ボリュームとマウントの削除 
gcloud run services update SERVICE \
  --remove-volume=VOLUME_NAME \
  --remove-volume-mount=/mnt/my-volume

ボリュームを削除するには、そのボリュームを使用するすべてのボリュームマウントも削除する必要があります。

💡 メリット

💼 ビジネス面

✓コスト最適化: 大きな一時ファイルのためのメモリ増量が不要になり、メモリコストを抑えて大規模データを処理できる
✓本番利用の安心感: GA により本番ワークロードでの採用判断がしやすくなった

🔧 技術面

✓大規模データ処理: メモリに収まらないデータセットもディスク上の一時領域で処理可能
✓既存コンテナとの互換性: 通常のファイル I/O でアクセスでき、既存アプリを変更なしで移行しやすい
✓セキュリティ: インスタンス固有キーで自動暗号化、他インスタンスと非共有

⚠️ デメリット・制約事項

🚧 制限事項

✗第 2 世代実行環境でのみ利用可能
✗インスタンスあたりデフォルト合計 10 GiB、プロジェクトあたりリージョンごとに 100 GiB の割り当て制限 (増加リクエスト可能)
✗デプロイ時には「インスタンスあたりのディスクサイズ × 最大インスタンス数」がリージョン割り当てを超えられない
✗/dev、/proc、/sys とそのサブディレクトリにはマウント不可
✗ジョブではライブマイグレーションがサポートされず、特に長時間実行ジョブの信頼性が低下する可能性

🤔 考慮すべき点

⚠️ データ消失に備えた退避設計: データはインスタンス終了 (クラッシュ、スケールイン、新リビジョン移行、ジョブ完了) とともに完全削除されます。永続化が必要なデータは SIGTERM 後 10 秒の猶予期間などを使って Cloud Storage 等へ退避する設計が必要です。
🚨 既知の問題: Google Cloud コンソールから新リビジョンをデプロイすると、ディスクボリュームがインメモリボリュームに変換されてしまいメモリ不足を引き起こす既知の問題があります。gcloud CLI / YAML (medium: Disk) でのデプロイを徹底してください。
💡 その他の考慮点:
  • 大量データをダウンロードする場合、Direct VPC を有効にしないとネットワーク転送速度が低下することがある
  • プロビジョニングしたディスクサイズ全体とインスタンスの稼働時間が課金に影響する

🎯 ユースケース

📹 ユースケース 1: 大容量ファイルのデータ処理

シナリオ: Cloud Run ジョブで数十 GB の動画やログファイルをダウンロードして変換・集計する。従来はファイル全体をメモリに載せるか、分割処理のオーケストレーションが必要だった。

Bash ジョブに 50Gi のスクラッチ領域を追加 
gcloud run jobs update video-transcode-job \
  --add-volume=name=scratch,type=ephemeral-disk,size=50Gi \
  --add-volume-mount=volume=scratch,mount-path=/mnt/scratch
✨ 効果: 大量のメモリを割り当てることなく一時作業領域を確保でき、コストを抑えながらより大きなデータセットを処理できる。

🌐 ユースケース 2: Web サービングのディスクキャッシュ

シナリオ: Cloud Run サービスで、リモートストレージから頻繁に取得するアセットやモデルファイルをローカルにキャッシュしてレスポンスを高速化したい。

✨ 効果: リモートストレージへのアクセスを減らしレイテンシを最適化。キャッシュはインスタンス終了時に自動で破棄されるため、後片付けの実装も不要。

💰 料金・利用可能リージョン

💵 料金: エフェメラルディスク専用の個別料金表は公開されていませんが、公式ドキュメントでは「プロビジョニングしたディスク全体のサイズと、それを使用するインスタンスの稼働時間がコストに寄与する」とされています。CPU・メモリ・ネットワーク下り (外向き) と合わせて、詳細は Cloud Run の料金ページを確認してください。
🌍 利用可能リージョン: エフェメラルディスクは、すべての Cloud Run のロケーションで利用できます。

🔗 関連サービス・機能

🪣 Cloud Storage

インスタンス終了前にディスク上のデータを退避する永続化先。Cloud Storage FUSE ボリュームマウントと使い分けることで、永続データと一時データを適切に分離できる。

📦 Cloud Run ボリュームマウント (in-memory / NFS / Cloud Storage)

エフェメラルディスクは既存のボリュームタイプを補完する選択肢で、メモリを消費しない一時領域が必要な場合に適する。

🔌 Direct VPC

大量データをディスクへダウンロードする際のネットワーク転送速度を確保するために有効化が推奨される。

📌 まとめ

Cloud Run のエフェメラルディスクが GA となり、メモリとは独立した最大 100Gi のディスクベース一時領域を、サービス・ジョブ・ワーカープールで本番利用できるようになりました。大容量ファイルの処理やディスクキャッシュのためにメモリを増量していたワークロードは、コスト削減の観点から移行を検討する価値があります。導入時は第 2 世代実行環境の利用、割り当て上限、インスタンス終了時のデータ消失を踏まえた退避設計に注意してください。
