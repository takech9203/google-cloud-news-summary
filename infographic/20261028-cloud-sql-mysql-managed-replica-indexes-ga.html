🗄️ Cloud SQL for MySQL ✅ GA (一般提供)
📅 リリース日: 2026-10-28

☁️ マネージドレプリカインデックスが一般提供 (GA) 開始

リードレプリカ再作成後もセカンダリインデックスを自動的に保持・復元

📝 概要

Cloud SQL for MySQL のマネージドレプリカインデックスが GA になりました。 Cloud SQL がプライマリインスタンス上でセカンダリインデックスのメタデータを追跡し、リードレプリカに複製して、 レプリカ再作成後にセカンダリインデックスを自動的に再構築します。

MySQL のリードレプリカは読み取り専用ですが、レポーティングや分析目的でレプリカ上にのみセカンダリインデックスを作成できます。 従来はプライマリのバックアップにレプリカ専用のインデックス定義が含まれないため、レプリカ再作成時にカスタムインデックスが失われていました。 レプリカでレポーティング・分析ワークロードを運用する DBA や SRE にとって、手動復旧という運用負荷を解消する重要なアップデートです。

❌ Before: アップデート前の課題

  • レプリカ再作成 (復旧・メンテナンス・障害時) でカスタムのセカンダリインデックスがすべて削除
  • mysql.addSecondaryIdxOnReplica の手動再実行や外部スキーマ追跡スクリプトの保守が必要
  • 再構築までインデックスなしクエリでレイテンシ急増・CPU 使用率上昇のリスク
  • 複数レプリカへの適用はレプリカごとに個別のストアドプロシージャ実行が必要

✅ After: アップデート後の改善

  • レプリカ再作成後、割り当てられたインデックスを自動的に再構築。手動復旧が不要に
  • 定義をプライマリで一元管理し名前付きレプリカグループに編成。フラグ 1 つで数百のインデックスを適用
  • レポーティング用のみ割り当て、DR 用はプライマリと同一スキーマ維持など役割別の選択的適用が可能
  • 専用ストアドプロシージャで進捗・実行時間・エラーを監視
💡 Google の推奨: セルフマネージドインデックスより、マネージドレプリカインデックスの使用が推奨されています。

プライマリインスタンス上でインデックス定義を一元管理し、レプリカグループに割り当てます。 レプリカ側のバックグラウンドプロセスが約 5 分間隔でインデックスを作成・維持し、レプリカ再作成後も自動的に再構築します。

⚡ 主要機能

🔄 1. インデックスの自動保持・復元

  • プライマリ上でセカンダリインデックスのメタデータを追跡し、リードレプリカに複製
  • レプリカのクラッシュや再作成後、マッピングされたインデックスを自動的に再構築
  • クエリスループットを維持し、インデックスなしクエリによるレイテンシ急増・CPU 上昇を防止

🗂️ 2. レプリカグループによる一元管理

  • プライマリ上で定義を一度作成し、名前付きレプリカグループに編成
  • レプリカ側はフラグ cloudsql_index_recreate_replica_group の設定だけでグループ内インデックスを適用
  • レポーティング用にはグループを割り当て、DR 用はインデックスなしで維持する役割別設定が可能

🛡️ 3. バックグラウンドによるバッチ実行とガードレール

  • 約 5 分間隔のバッチ処理。1 つのインデックスの失敗が後続の実行をブロックしない
  • レプリケーションラグが 20 分超で作成オペレーションを自動一時停止 (削除は停止しない)
  • マネージドインデックスのコメントに内部管理用 [SIC_X_Y] タグが付与 (機能への影響なし)

👀 4. 可観測性とセルフマネージドインデックスとの共存

  • cloudsql_replica_idx_show_status() / show_errors() / show_all() で進捗・エラー・実行時間を確認
  • 既存のセルフマネージドインデックスと同一インスタンス・同一テーブル上で共存し、ダウンタイムなしで段階的に移行可能

🛠️ 設定方法

📌 前提条件
  • Cloud SQL for MySQL 8.0 以降、Enterprise edition または Enterprise Plus edition のインスタンス
  • メンテナンスバージョンが R20260726.00_05 以降
  • ストアドプロシージャを実行するデータベースユーザーに cloudsqlsuperuser ロールが付与されていること
1

プライマリインスタンスでインデックス定義を作成

SQL プライマリで実行 
CALL mysql.cloudsql_replica_idx_defn_create(
  'INDEX_DEFINITION_NAME',
  'CREATE INDEX INDEX_NAME ON DATABASE.TABLE (COLUMNS)'
);

DDL 文はスキーマ修飾 (schema_name.table_name) が必要。返される一意の整数 ID (INDEX_DEFINITION_ID) を控えておく。

2

インデックス定義をレプリカグループにマッピング

SQL プライマリで実行 
CALL mysql.cloudsql_replica_idx_group_add(INDEX_DEFINITION_ID, 'REPLICA_GROUP');

指定したグループが存在しない場合、Cloud SQL が新規作成する。

3

リードレプリカにレプリカグループを割り当て

Bash gcloud CLI 
gcloud sql instances patch REPLICA_INSTANCE_NAME \
  --database-flags=EXISTING_FLAGS,cloudsql_index_recreate_replica_group=REPLICA_GROUP

データベースフラグのグループ名は、ステップ 2 で指定したグループ名と完全に一致させる必要がある。

4

リードレプリカでステータスを確認

SQL レプリカで実行 
-- 進捗・ステータスの確認
CALL mysql.cloudsql_replica_idx_show_status();

-- エラーの監査
CALL mysql.cloudsql_replica_idx_show_errors();

バックグラウンドプロセスは約 5 分間隔で動作するため、設定後すぐに反映されない場合がある。詳細な進捗レポートには MySQL Performance Schema のステージインストルメント・コンシューマの有効化が必要。

👍 メリット

💼 ビジネス面

✓運用負荷の削減: 手動のインデックス復旧作業や外部スキーマ追跡スクリプトの保守が不要になり、運用コストを削減
✓サービス品質の安定化: レプリカ復旧後もクエリパフォーマンスが自動維持され、レポーティング・分析系サービスの品質劣化を防止

⚙️ 技術面

✓一元管理とスケール: プライマリで一元管理し、フラグ 1 つで数百のインデックスを含むグループをレプリカに適用
✓プライマリの性能分離: セカンダリインデックスはレプリカ上にのみ作成され、プライマリのストレージ消費や書き込みレイテンシに影響しない
✓安全なガードレール: レプリケーションラグ 20 分超でインデックス作成を自動停止し、レプリケーションへの悪影響を抑制
✓段階的移行: セルフマネージドインデックスと共存可能で、ダウンタイムや読み取りワークロードの中断なしに移行できる

⚠️ デメリット・制約事項

🚫 制限事項

✗MySQL 8.0 以降、Enterprise / Enterprise Plus edition、メンテナンスバージョン R20260726.00_05 以降のインスタンスでのみサポート
✗外部サーバーレプリカでは非サポート (セルフマネージドのみ)
✗既存のインデックスメタデータの更新・変更は不可。変更には既存定義を削除 (またはグループから除外) して新しい定義を作成する必要がある
✗各ストアドプロシージャ呼び出しは COMMIT を実行するため、トランザクション内でロールバックできない

🤔 考慮すべき点

  • 作成・削除は約 5 分間隔のバックグラウンドバッチで実行され、即時反映されない。即時実行が必要なら mysql.addSecondaryIdxOnReplica (セルフマネージド) を利用
  • レプリカをプライマリに昇格すると、マネージドレプリカインデックスは自動削除される (約 5 分の遅延があり得る)。プライマリ側の定義とグループマッピングは保持
  • DR 切り替え時、旧プライマリがレプリカになっても自動ではインデックスが作成されない。必要なら旧プライマリに cloudsql_index_recreate_replica_group フラグを設定
  • セルフマネージドと同名のマネージド定義を登録すると FAILED ステータスが記録される (既存インデックスやトラフィックへの影響はなく、レプリカ再作成時に自動解決)

🎯 ユースケース

📊 ユースケース 1: レポーティング用レプリカのインデックスを障害後も自動維持

シナリオ: BI ツールの分析クエリを専用リードレプリカにオフロードし、分析用のセカンダリインデックスをレプリカにのみ作成。レプリカがハードウェア障害で再作成されるたびにインデックスが消え、手動復旧までダッシュボードの表示が極端に遅くなっていた。

SQL プライマリで定義を登録 
-- プライマリで定義を登録
CALL mysql.cloudsql_replica_idx_defn_create(
  'orders_report_idx',
  'CREATE INDEX idx_orders_created ON sales.orders (created_at, status)'
);
-- 返された IDXID をレポーティンググループに追加
CALL mysql.cloudsql_replica_idx_group_add(1, 'reporting');
Bash レポーティング用レプリカにグループを割り当て 
gcloud sql instances patch reporting-replica \
  --database-flags=cloudsql_index_recreate_replica_group=reporting

✅ 効果: レプリカ再作成後もインデックスが自動再構築され、手動復旧なしで分析クエリのパフォーマンスが維持される。

🏷️ ユースケース 2: 役割別レプリカ構成 (レポーティング用と DR 用の分離)

シナリオ: 同一プライマリ配下にレポーティング用レプリカと DR 用レプリカを運用。DR レプリカには書き込みオーバーヘッドやレプリケーションラグの要因となる余分なインデックスを持たせたくない。

✅ 効果: インデックスグループをレポーティング用レプリカにのみ割り当てることで、DR レプリカはプライマリと同一スキーマのまま維持でき、DR インスタンスへの書き込みトランザクションオーバーヘッドとレプリケーションラグを防げる。

🔀 ユースケース 3: セルフマネージドインデックスからの無停止移行

シナリオ: 既に mysql.addSecondaryIdxOnReplica でレプリカにインデックスを作成しているが、再作成時の消失リスクを解消したい。

✅ 効果: 既存のセルフマネージドインデックスと共存しながら、プライマリに定義を登録してグループに追加するだけで移行できる。次回のレプリカ再作成時に Cloud SQL が自動的にマネージドインデックスとして再作成する (即時移行したい場合はセルフマネージドインデックスを削除すれば約 5 分以内にマネージド側が作成される)。

✅ まとめ

マネージドレプリカインデックスの GA により、レプリカ再作成時のセカンダリインデックス消失という長年の運用課題が解消されました。

レプリカ上にカスタムインデックスを作成してレポーティング・分析ワークロードを運用しているチームは、 メンテナンスバージョン R20260726.00_05 以降への更新を確認のうえ、 セルフマネージドインデックスからマネージドレプリカインデックスへの移行を検討することを推奨します。
