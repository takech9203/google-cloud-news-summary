☁️ Personalized Service Health Feature リソースレベル影響特定は Preview
📅 リリース日: 2026-11-19

🤖 servicehealth-incident-correlation
エージェントスキルのサポート

「この障害は Google Cloud 側か?」の切り分けを、AI エージェントが標準化された手順と安全側の判定基準で実行

📝 概要

Personalized Service Health (PSH) がエージェントスキル servicehealth-incident-correlation をサポート。 Google Cloud のインシデントが特定のプロジェクトに影響しているかを確認し、 公開されている症状 (symptoms) とワークアラウンドを報告する手順を AI エージェントに提供する。 スキルは google/skills リポジトリで公開され、npx skills add でインストールできる。

🤖 エージェントスキルとは: AI エージェントに特定の知識と手順を再利用可能な形で与える標準化された仕組み。スクリプト、リファレンス資料、テンプレートなどを含み、スキルなしのエージェントよりも高い精度でタスクを実行できる。対象ユーザーはオンコール対応に AI エージェント (Gemini CLI、Claude、Antigravity など) を活用する SRE・運用チーム。
💡 中核原則: 「最もコストが高い誤りは誤った全面クリア (false all-clear) の報告」。スキルは読み取り専用の調査に特化している。

❌ Before (アップデート前の課題)

  • プロジェクト ID の特定方法、フィルタ構文、MERGED / FALSE_POSITIVE などのイベント状態の解釈をエージェントが知らず、調査精度が不安定
  • RELATED を「影響なし」と誤解釈、空の影響リストを「影響なし」と誤断定するなど、誤った全面クリア報告のリスク
  • 相関手順 (スコープ特定 → イベント取得 → 相関 → 判定 → 報告) を毎回プロンプトで指示する必要があった

✅ After (アップデート後の改善)

  • スキルをインストールするだけで、エージェントが体系的な 5 ステップのワークフローに従って調査を実行
  • IMPACTED / INCONCLUSIVE / NO_IMPACT_IDENTIFIED の明確な判定基準で、誤った全面クリアを避ける安全側の報告
  • PSH リモート MCP サーバーを主経路とし、gcloud CLI / REST API へのフォールバック手順も同梱

AI エージェントはスキルの手順に従い、PSH リモート MCP サーバー (フォールバックとして gcloud / REST API) からイベントと影響情報を取得し、プロジェクト単位の影響判定とレポートを生成する。

  • スコープ特定: プロンプト、アラートペイロード、リソースパスからプロジェクト ID を特定 (ホストの gcloud デフォルトプロジェクトには依存しない)。プロダクト、ロケーション、リソース、基準時刻を抽出
  • イベント取得: projects/{project_id}/locations/global を親として、state=ACTIVE や update_time ウィンドウなど範囲を限定したフィルタ付きで取得 (ページネーション対応)
  • 相関: プロダクトとロケーションの一致判定。MERGED は親インシデントまで追跡、EMERGING はアクティブ扱い、FALSE_POSITIVE / AUTO_CLOSED はマッチ対象外。時間ウィンドウのルール (ウィンドウ開始の最大 4 時間前までのマッチ、基準時刻の 1 時間以内にクローズした場合は「直近クローズ」として INCONCLUSIVE) も定義
  • 判定: 下記 3 種類の判定トークンを返す
  • 報告: 判定トークン、プロジェクト ID の取得元、イベントサマリー、プロダクト / ロケーション別の詳細ステータス表、リソースレベルの影響、最新の症状とワークアラウンド、PSH コンソールへのリンクを含むレポートを生成
🔴 IMPACTED 関連度が IMPACTED または RELATED のイベントあり
🟡 INCONCLUSIVE API 呼び出し失敗、プロダクト未対応、プロジェクト ID 不明など
🟢 NO_IMPACT_IDENTIFIED 影響は特定されず (ただし「全面クリア」とは表現しない)

2️⃣ PSH リモート MCP サーバーとの連携

→主要な通信経路は https://servicehealth.googleapis.com/mcp のリモート MCP サーバー (Streamable HTTP)
→MCP ツール: list_project_events (イベント一覧)、get_project_event (症状・ワークアラウンドを含む詳細)、list_project_impacts / get_project_impact (Preview のリソースレベル影響)
→MCP が利用できない場合は gcloud CLI (gcloud service-health events list) や REST API へのフォールバック手順をリファレンスとして同梱

3️⃣ リソースレベルの影響特定 Preview

→イベントの関連度が IMPACTED の場合、影響を受けている具体的なリソース (Cloud SQL インスタンス、GKE クラスタなど) を Impact リソース (projects/{PROJECT_ID}/locations/global/impacts/{IMPACT_ID}) として特定
→Impact には影響リソースのフルリソース名 (assetName)、Cloud Asset Inventory のリソースタイプ (assetType)、関連イベント、説明、タイムスタンプが含まれる
→スキルはこの情報を「参考情報」として扱い、影響リストが空でも「影響なし」とは判定しない

🚀 設定方法

📋 前提条件: Node.js / npm が利用可能な環境 (インストールに npx を使用) / エージェントスキルに対応した AI エージェント環境 / 対象プロジェクトで Service Health API が有効化済みであること

ステップ 1: スキルのインストール

Bash google/skills リポジトリからインストール 
npx skills add google/skills --skill servicehealth-incident-correlation

ステップ 2: Service Health API の有効化

Bash Service Health API を有効化 
gcloud services enable servicehealth.googleapis.com --project=PROJECT_ID
⚠️ 注意: リソースレベルの影響情報を受け取るには、インシデント開始の 24 時間以上前に API を有効化しておく必要がある。後から有効化した場合、過去 90 日分のプロジェクトレベルイベントはバックフィルされるが、リソースレベルの影響はバックフィルされない。

ステップ 3: 認証と IAM ロールの設定

Bash 認証のセットアップ 
gcloud auth login
# または
gcloud auth application-default login

調査を実行するプリンシパルに roles/servicehealth.viewer を、リモート MCP サーバーを使用する場合は roles/mcp.toolUser を付与する。

⚖️ メリットと制約事項

✅ メリット

💼 ビジネス面
✓障害切り分けの迅速化: 「自社側か Google 側か」の一次判定を体系的な手順で実行し、オンコール初動を短縮
✓誤判断リスクの低減: 不確実な場合は INCONCLUSIVE を返すため、障害の見逃しによる無駄なロールバックや復旧作業を回避
🔧 技術面
✓標準化された再利用可能な手順: フィルタ構文の制約 (繰り返しフィールドには = ではなく : を使用など)、イベント状態の解釈ルール、時間ウィンドウの扱いなど、PSH API の落とし穴がスキルに織り込み済み
✓読み取り専用で安全: OAuth スコープも servicehealth.read-only のため、エージェントに広い権限を与えずに運用可能
✓フォールバック経路の確保: MCP が使えない環境でも gcloud CLI / REST API での調査手順を同梱

⚠️ 制約事項・考慮点

🚧 制限事項
✗リソースレベルの影響特定は Preview で対応プロダクトが限定。対応外のプロダクトやコントロールプレーン / リージョンレベルの障害では、イベントが IMPACTED でも impacts.list が空リストを返す
✗リソースレベルの影響には、インシデント開始の 24 時間以上前の API 有効化が必要
✗対象はプロジェクト単位の障害確認・トリアージ。ローカルのコード / ビルドエラー、通常のアラート、PSH アラート設定、公開ステータス確認は対象外
🤔 考慮すべき点
→ヘッドレス (非対話) フローでプロジェクト ID が特定できない場合は即座に INCONCLUSIVE。アラートペイロードにプロジェクト ID を含める設計が必要
→NO_IMPACT_IDENTIFIED は「影響なしの保証」ではない。インシデント宣言は症状の発生より遅れる可能性があるため、他の情報源と併用を推奨
→list_project_events のフィルタでは relevance、ロケーション、開始 / 終了時刻によるフィルタリングは不可

🎯 ユースケース

💳 ユースケース 1: オンコールボットによるロールバック前の障害切り分け

シナリオ: 本番プロジェクトで Spanner への接続タイムアウトと 503 エラーが急増。デプロイ起因かプラットフォーム障害かを判断してからロールバックを実行したい。

Text プロンプト例とエージェントの動作 
プロンプト例:
「projects/payment-service-prod で Spanner の 503 エラーと接続タイムアウトが
発生している。ロールバックの前に、既知の Google Cloud インシデントが
影響していないか確認して」

エージェントの動作 (スキルの手順に従う):
1. プロンプトからプロジェクト ID (payment-service-prod) を特定
2. list_project_events を filter="category=INCIDENT state=ACTIVE" で呼び出し
3. 影響プロダクト (spanner.googleapis.com) と症状を相関
4. 該当イベントがあれば get_project_event で症状・ワークアラウンドを取得
5. 「Status: IMPACTED -- ...」形式で判定とワークアラウンドを報告
✅ 効果: プラットフォーム障害時の不要なロールバックを回避し、公開済みワークアラウンドに基づく適切な初動対応ができる。

🔔 ユースケース 2: アラート受信時の自動影響確認

シナリオ: Cloud Logging ベースの Service Health アラートや監視アラートを受信した際、CI/CD トリアージエージェントがアラートペイロード内のプロジェクト ID とリソースパスからスコープを特定し、影響を自動確認する。

✅ 効果: 影響を受けた具体的なリソース (assetName / assetType) まで特定 (Preview、対応プロダクトのみ) した構造化レポートが自動生成され、人手による Service Health ダッシュボードの確認作業を削減できる。

🔗 関連サービス・機能

→Personalized Service Health リモート MCP サーバー: スキルの主要な通信経路。https://servicehealth.googleapis.com/mcp エンドポイントで list_project_events / get_project_event などのツールを提供
→Service Health API (v1 / v1beta): イベント (projects.locations.events) とリソースレベルの影響 (projects.locations.impacts、v1beta Preview) を提供する基盤 API
→Cloud Logging: Service Health イベントはログとして記録され、アラートポリシーの条件として利用可能
→Model Armor: PSH MCP サーバーのツール呼び出しと応答をスクリーニングするオプションのセキュリティ機能
→Application Integration エージェントスキル: 同じ google/skills リポジトリで提供される Google Cloud プロダクトのエージェントスキル群の一例

💡 まとめ

servicehealth-incident-correlation エージェントスキルにより、「この障害は Google Cloud 側のインシデントか」という切り分け作業を、AI エージェントが標準化された手順と安全側の判定基準で実行できるようになった。

🚀 推奨アクション: オンコール対応に AI エージェントを組み込んでいるチームは、npx skills add google/skills --skill servicehealth-incident-correlation でスキルを導入し、あわせて対象プロジェクトで Service Health API を事前に有効化しておくことを推奨する。
