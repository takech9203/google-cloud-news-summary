📝 概要

2026 年 4 月 18 日より前に作成された既存インスタンスでも、Knowledge Catalog (旧 Dataplex Universal Catalog) 統合を有効化すると、スキーマとメタデータの更新がニアリアルタイムで同期されるようになりました。従来の 1 日 1 回のバッチ更新に代わり、新規インスタンスと同等の鮮度でカタログを維持できます。

対象は MySQL 8.0 以降 / PostgreSQL 14.0 以降かつ新ネットワークアーキテクチャ上で動作する適格インスタンス。統合がオフのインスタンスは有効化するだけで自動適用され、1 日 1 回更新で統合済みのインスタンスは無効化 → 再有効化の操作のみで切り替えられます。既存環境を作り直すことなく最新の同期方式へ移行できる点が大きな価値です。

❌ Before (アップデート前の課題)

  • 既存インスタンスはメタデータ更新が 1 日 1 回のバッチ反映に限定
  • スキーマ変更の反映に最大 1 日程度の遅延があり、ディスカバリーで古い情報が表示される可能性
  • ニアリアルタイム同期にはインスタンスの新規作成 (再作成) が必要で運用コストが大きい
  • バッチ抽出は小さいマシンタイプ + 大規模スキーマ (10,000 テーブル以上) で CPU 使用率が最大 40% に達することも

✅ After (アップデート後の改善)

  • 適格な既存インスタンスで統合を有効化するだけでニアリアルタイム同期が適用
  • DDL / スキーマ変更は 10 分以内に反映、既存リソースも 24 時間以内に登録
  • 1 日 1 回更新で統合済みでも無効化 → 再有効化のみで切り替え可能
  • 変更済みアセットのみを差分抽出するため CPU 使用率への影響は最小限
💡 対象読者: 2026 年 4 月以前から Cloud SQL を運用しており、データカタログの鮮度に課題を感じているデータプラットフォーム管理者・データガバナンス担当者。

既存の Cloud SQL インスタンスで DDL やスキーマ変更が発生すると、インスタンス内のタイムスタンプテーブルで変更アセットが特定され、従来の 1 日 1 回のバッチ更新に代わってニアリアルタイム (DDL 変更は 10 分以内) で Knowledge Catalog に同期されます。

⚡ 主要機能

1️⃣ 既存インスタンスへのニアリアルタイム同期の拡大

  • 2026/4/18 より前に作成されたインスタンスで、統合がオフの場合に有効化するとバッチ更新ではなくニアリアルタイム同期が適用
  • 2026/4/18 以降作成のインスタンスは従来どおりデフォルトで有効 (2026/3/19〜4/18 作成の一部インスタンスも該当する場合あり)
  • 新しい DDL / スキーマ変更は 10 分以内、既存リソースは 24 時間以内に反映

2️⃣ 1 日 1 回更新からの切り替え (無効化 → 再有効化)

  • 既に 1 日 1 回更新で統合が有効なインスタンスは、統合を一度無効化してから再有効化することでニアリアルタイム更新に切り替え
  • ニアリアルタイム統合中の無効化操作は最大 10 分かかる

3️⃣ タイムスタンプテーブルによる差分検出

  • アセットの作成・更新時刻を追跡するタイムスタンプテーブルを作成 (MySQL では mysql データベース内の resource_timestamps テーブル)
  • タイムスタンプテーブルを照会し、最近変更されたアセットのみを Knowledge Catalog にロード
  • 統合を支えるクエリには --Dataplex コメントが付与され、アクティブクエリ監視画面で識別可能

4️⃣ 結果整合性による信頼性の担保

  • ネットワーク不安定などの稀なケースで更新が欠落しても、通常 24 時間以内に結果整合的に反映

ステップ 1: 統合状態とインスタンス条件の確認

Bash インスタンス設定の確認 
# インスタンスの設定を確認 (enableDataplexIntegration の値を確認)
gcloud sql instances describe INSTANCE_NAME

出力の settings セクションで enableDataplexIntegration の値と、データベースバージョンを確認します。旧ネットワークアーキテクチャのインスタンスは、先に新ネットワークアーキテクチャへのアップグレードが必要です。

ステップ 2: 統合が未有効の場合 — 有効化

Bash Knowledge Catalog 統合の有効化 
# 既存インスタンスに Knowledge Catalog 統合を有効化 (ニアリアルタイム同期が適用される)
gcloud sql instances patch INSTANCE_NAME \
    --enable-dataplex-integration
Bash プロジェクト内の全インスタンスに一括有効化 
gcloud sql instances list --format="(NAME)" \
    | tail -n +2 | xargs -t -I % gcloud sql instances patch % --enable-dataplex-integration

ステップ 3: 1 日 1 回更新で統合済みの場合 — 無効化して再有効化

Bash 無効化 → 再有効化でニアリアルタイムに切り替え 
# 1. 統合を一度無効化 (ニアリアルタイム統合中の無効化は最大 10 分かかる)
gcloud sql instances patch INSTANCE_NAME \
    --no-enable-dataplex-integration

# 2. 統合を再有効化 (ニアリアルタイム更新に切り替わる)
gcloud sql instances patch INSTANCE_NAME \
    --enable-dataplex-integration
JSON REST API の場合: PATCH リクエストボディ 
{
  "settings": {
    "enableDataplexIntegration": true
  }
}

ステップ 4: 同期の確認

有効化後、Knowledge Catalog コンソールで Cloud SQL のアセットを確認します。新しい DDL やスキーマ変更は 10 分以内、既存リソースは 24 時間以内に反映されます。MySQL では mysql データベースの resource_timestamps テーブルを Google Cloud コンソールからクエリして、アセットの作成・更新時刻を確認することもできます。

🎯 メリット

💼 ビジネス面

✓データカタログの鮮度向上: 最大 1 日遅れだった既存環境でも、ほぼリアルタイムで最新メタデータを参照でき、データディスカバリーやガバナンス判断の信頼性が向上
✓移行コストの削減: インスタンスの再作成が不要。設定変更 (有効化、または無効化 → 再有効化) のみで最新の同期方式へ移行可能
✓新旧インスタンスの運用統一: 2026/4/18 前後で作成されたインスタンス間のカタログ鮮度の差がなくなり、組織全体で一貫したメタデータ運用が可能

⚙️ 技術面

✓差分ベースの効率的な同期: タイムスタンプテーブルで変更アセットのみを特定して同期。全スキーマを毎日抽出するバッチ方式に比べて CPU 使用率への影響が最小限
✓DDL 変更の迅速な反映: 新しい DDL やスキーマ変更は 10 分以内にカタログへ反映
✓結果整合性: 稀に更新が欠落しても通常 24 時間以内に結果整合的に反映され、カタログの正確性を担保
✓可観測性: 統合クエリは --Dataplex コメントで識別可能。アクティブクエリの監視で統合の動作を確認できる

⚠️ デメリット・制約事項

🚫 制限事項

✗対象は MySQL 8.0+ / PostgreSQL 14.0+ かつ新ネットワークアーキテクチャのインスタンスのみ。条件を満たさない場合は引き続き 1 日 1 回更新
✗1 日 1 回更新で統合済みのインスタンスは自動では切り替わらず、無効化 → 再有効化の手動操作が必要
✗データベースの名前変更時は、データベースの更新のみニアリアルタイム反映。配下のテーブルとのマッピングは結果整合
✗短時間での大量 DDL 実行、クローン作成 / バックアップ復元されたインスタンス、メモリ不足、再起動、ネットワーク障害ではメッセージがドロップされ、一時的に結果整合となる可能性
✗MySQL では DB・テーブル・ビューを削除して同名で再作成した場合、元のエントリがカタログに残る (PostgreSQL では期待どおり削除)
✗2026/4/18 より前に作成されたインスタンスで Assured Workloads によるリソースアクセス制限がある場合、Knowledge Catalog 統合はオフになる

🤔 考慮すべき点

  • ニアリアルタイム統合中のインスタンスの無効化処理には最大 10 分かかるため、切り替え作業は時間に余裕を持って計画する
  • 再有効化後、既存リソースの再登録には最大 24 時間かかるため、カタログ参照が集中する時間帯を避けて切り替えることを推奨
  • cloudsql.schemas.view 権限はプロジェクトレベルで付与されるため、プロジェクト内全インスタンスのメタデータが閲覧対象となるアクセス制御上の影響を確認する
  • 旧ネットワークアーキテクチャのインスタンスは、まず新ネットワークアーキテクチャへのアップグレードを検討する

💡 ユースケース

📦 ユースケース 1: 長期運用中の既存データベース群をニアリアルタイムカタログへ移行

シナリオ: 2024 年から運用している Cloud SQL for PostgreSQL 15 のインスタンス群 (新ネットワークアーキテクチャ) で Knowledge Catalog 統合が 1 日 1 回更新になっており、頻繁なスキーマ変更の反映遅延がデータアナリストのデータディスカバリーの妨げになっている。

Bash 実装例 
# 1 日 1 回更新のインスタンスを無効化 → 再有効化してニアリアルタイムに切り替え
gcloud sql instances patch analytics-db --no-enable-dataplex-integration
gcloud sql instances patch analytics-db --enable-dataplex-integration

✅ 効果: インスタンスを再作成することなく、スキーマ変更が 10 分以内に Knowledge Catalog へ反映されるようになり、アナリストが常に最新のテーブル構造を検索・参照できる。

🚀 ユースケース 2: アジャイル開発環境でのスキーマ変更の即時カタログ反映

シナリオ: マイクロサービス開発チームが Cloud SQL for MySQL 8.0 上で頻繁にテーブル追加・カラム変更を行っており、データスチュワードが変更を翌日まで把握できず、メタデータのエンリッチメント (アスペクト付与や PII 分類) が後手に回っている。

✅ 効果: DDL 変更が 10 分以内にカタログへ反映されるため、データスチュワードが新規テーブルやカラムの追加をほぼリアルタイムで検知し、ガバナンスポリシーの適用やメタデータの付与を迅速に実施できる。

💰 料金

Cloud SQL 側で Knowledge Catalog 統合 (ニアリアルタイム同期を含む) を有効化すること自体に追加料金は発生しません。Knowledge Catalog の利用料金はメタデータストレージ SKU に基づきます。

🎉 まとめ

2026 年 4 月 18 日より前に作成された既存の Cloud SQL for MySQL (8.0+) / PostgreSQL (14.0+) インスタンスでも、Knowledge Catalog 統合を有効化するだけでスキーマ・メタデータのニアリアルタイム同期 (DDL 変更は 10 分以内に反映) が利用できるようになりました。1 日 1 回更新で統合済みのインスタンスは、gcloud sql instances patch による無効化 → 再有効化の簡単な操作で切り替えられます。既存環境でカタログの鮮度に課題がある場合は、インスタンスのバージョンとネットワークアーキテクチャを確認のうえ、ニアリアルタイム同期への切り替えを推奨します。
