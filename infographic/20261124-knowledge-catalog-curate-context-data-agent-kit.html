📚 Knowledge Catalog: curate-context スキルでコンテキストセットをローカルキュレーション

Knowledge Catalog (旧 Dataplex Universal Catalog) Data Agent Kit Preview
📅 リリース日: 2026-11-24 ｜ 🛠️ 機能: Google Cloud Data Agent Kit の curate-context スキル

📝 概要

Google Cloud Data Agent Kit の curate-context スキルが Preview になりました。 対応するコーディングエージェント (Antigravity CLI、Claude Code、Codex CLI、VS Code 系 IDE など) 上で、 Knowledge Catalog のコンテキストセットを Open Knowledge Format (OKF v0.2) の Markdown バンドルとしてローカルに作成・インポート・編集・検証できます。 作成したバンドルは kcmd CLI (@google-cloud/kcmd) で Knowledge Catalog に公開し、 同梱の discover-assets スキルでリトリーバルをテストできます。

コンテキストセットは、テーブルのガイダンス、ビジネス定義、検証済み SQL などのドメイン知識をパッケージ化し、 AI エージェントを一貫したドメイン知識でグラウンディングする仕組みです。今回のアップデートで、Git 配下のローカル Markdown ファイルとして「Metadata as Code」スタイルの管理が可能になりました。 主な対象はデータエンジニア、アナリティクスエンジニア、データスチュワードです。

💡 相互運用性: Data Agent Kit で構築したコンテキストセットは、Knowledge Studio の エンリッチメントタスクで構築したものと同じエントリ階層を共有。クラウド管理のコンテキストセットを ローカルに pull してエディタやコーディングエージェントで洗練させることもできます。

❌ アップデート前の課題

  • 作成・管理はコンソールの Knowledge Studio (エンリッチメントタスク) や API / CLI 中心で、慣れたコーディングエージェントや IDE から直接オーサリングするワークフローがなかった
  • テーブルガイダンスやビジネス定義、検証済み SQL を Git のプルリクエストでレビューする、バージョン管理ベースの編集・レビューフローを組みにくかった
  • 公開前の SQL 妥当性検証や、変更の影響範囲 (関連するコンセプト文書・テーブルページ・SQL クエリ) の確認を開発環境内で完結できなかった

✅ アップデート後の改善

  • 自然言語プロンプトで BigQuery / Spanner / Cloud SQL / AlloyDB などのライブスキーマ検査とローカルドキュメントの取り込みを行い、OKF v0.2 Markdown バンドルとしてローカルに作成・編集できる
  • kcmd CLI で pull、--dry-run による差分プレビュー、承認済みバンドルの push が可能になり、Git の PR レビューと組み合わせた「Metadata as Code」運用が実現
  • 保存する SQL は公開前にコンパイルチェック (BigQuery ドライラン、Spanner クエリプラン、Cloud SQL / AlloyDB の EXPLAIN) で検証、discover-assets スキルで公開後の取得を即テスト可能

⭐ 主要機能

1. 🖊️ curate-context スキルによるローカルオーサリング

→ソーステーブル・ローカルファイル・ターゲット設定 (プロジェクト、ロケーション、コンテキストセット ID) を含むプロンプトから、ライブスキーマの検査、類似 (lookalike)・ステージング・非推奨テーブルのフラグ付け、既存のビジネス用語集とのマッチングを行い、オーサリングプランを提示
→提供されたソースに基づいてカラムを文書化し、カラム名からの推測による説明の捏造を避ける設計
→実行可能 SQL を各テーブルページの dataplex-types.global.queries アスペクト (userManaged: true) に保存し、公開前にテーブル行を読まずにコンパイルチェック (BigQuery ドライラン、Spanner クエリプラン、Cloud SQL for MySQL / PostgreSQL と AlloyDB の EXPLAIN)

2. 📦 Open Knowledge Format (OKF v0.2) バンドル

→YAML フロントマター付き Markdown と _links.yaml を含むローカル bundle/ ディレクトリとしてコンテキストセットを表現
→ルートルーター (agents.md)、データアセットインデックス、データセット/テーブルコンテキストページ、ビジネス文書という段階的開示 (progressive-disclosure) レイアウト
→_links.yaml に reference、definition、related のエントリリンクを記述

3. ⌨️ kcmd CLI による公開・同期

→スコープ付き npm パッケージ @google-cloud/kcmd として提供 (Node.js 22.12 以降が必要)
→リモートのコンテキストセットの pull、--dry-run による差分プレビュー、承認済みバンドルの push を実行
→ルートの catalog.yaml ファイルを管理 (手動編集は非推奨)

4. 🔍 discover-assets スキルによるリトリーバルテスト

→Data Agent Kit 同梱の discover-assets スキルで公開済みコンテキストセットへの問い合わせをテスト
→search_entries でコンテキストセットのエントリ (parent_entrygroup_type=context-set) を優先的に検索し、リモート MCP サーバーの lookup_context でエージェントの回答や SQL 生成をキュレート済み定義でグラウンディング
→Gemini Enterprise やカスタムエージェントも MCP / Knowledge Catalog API 経由で読み取り可能

5. 🔄 既存ワークフローとの相互運用

→Knowledge Studio のエンリッチメントタスクで構築したコンテキストセットと同じエントリ階層を共有し、相互運用が可能
→編集時は変更の波及効果 (影響を受けるコンセプト文書・テーブルページ・SQL クエリ) をフラグ表示し、プラン承認・公開プレビュー承認という明示的なヒューマンインザループを経て push

1kcmd CLI のインストール (リモート pull / publish を行う場合)

Bash kcmd CLI のインストール 
node --version   # 22.12 以降を確認
npm install -g @google-cloud/kcmd
kcmd --version
⚠️ 注意: スコープ付きの @google-cloud/kcmd パッケージのみをインストールします (npm / PyPI のスコープなし kcmd パッケージはインストールしないこと)。 ローカルの OKF ファイルのオーサリングのみであればスキップ可能で、未インストールの場合はエージェントが オーサリングプラン提示時に検出し、確認のうえインストールします。

2コンテキストセットの作成

コーディングエージェントに、ソーステーブル・ローカルファイル・ターゲット設定を含むプロンプトを入力します。

Prompt エージェントへのプロンプト例 
Build a Knowledge Catalog context set named sales-analytics in project
cymbal-analytics (location us) from BigQuery tables
cymbal-analytics.crm.accounts and cymbal-analytics.billing.mrr_movements,
using ./docs/revenue_definitions.md and ./sql/revenue_queries.sql.

エージェントが提示するオーサリングプラン (ターゲットレイアウト、検出アセット、計画された OKF ファイルとリンク、 競合・未解決の質問) をレビューして承認すると、bundle/ のオーサリングと検証が行われます。

3公開とアクセス付与

検証サマリーと公開プレビューをレビューして承認すると、kcmd 経由で Knowledge Catalog に push されます。 コンテキストセットは標準のプロジェクト閲覧者ロールや Dataplex Catalog Admin から読み取りアクセスを 継承しないため、公開後に明示的にリーダーアクセスを付与します。

Bash リーダーアクセスの付与 
gcloud dataplex entry-groups add-iam-policy-binding CONTEXT_SET_ID \
  --location=LOCATION \
  --project=PROJECT_ID \
  --member=PRINCIPAL \
  --role=roles/dataplex.contentUser

4discover-assets スキルでリトリーバルをテスト

新しいエージェントプロンプトで、「net revenue retention を計算するにはどのテーブルとフィルタを使うべきか」 のようなビジネス上の質問を投げかけ、キュレートした定義でグラウンディングされた回答・SQL が返ることを確認します。 Knowledge Studio の「Context sets」ページやコンテキストグラフの Explore でもエントリとリンクを確認できます。

💪 メリット

💼 ビジネス面

✓ドメイン知識の一貫したグラウンディング: テーブルガイダンス、ビジネス定義、検証済み SQL を一元的にパッケージ化し、Gemini Enterprise やカスタムエージェントなどのダウンストリーム AI エージェントが一貫した定義で回答・SQL を生成できる
✓ガバナンスとレビューの強化: バンドルと catalog.yaml を Git にコミットすることで、プルリクエストベースのレビューと変更履歴管理を実現。公開はプラン承認・公開プレビュー承認という明示的なヒューマンインザループを経る

🛠️ 技術面

✓Metadata as Code: コンテキストセットをローカルの Markdown ファイルとしてコードと同様に扱え、開発者の既存ワークフロー (コーディングエージェント、IDE、Git) に自然に統合できる
✓公開前の SQL 検証: 保存する SQL はテーブル行を読まずにコンパイルチェックされる (BigQuery ドライランは無料)。ハルシネーションしたクエリが公開されるリスクを低減
✓相互運用性: Knowledge Studio エンリッチメントタスクと同じエントリ階層を共有し、クラウド管理とローカルキュレーションを組み合わせ可能。BigQuery 以外にも Spanner、Cloud SQL、AlloyDB、BigLake、Dataproc Metastore など複数データソースに対応

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 段階: Pre-GA Offerings Terms の対象であり、サポートが限定される場合がある
✗スコープ外の操作: エントリの認定 (certify)、IAM 許可ポリシーの変更、ビジネス用語集の用語の作成・編集 (既存用語へのリンクは可)、ソースエントリへのアスペクト書き込み、パラメータ化されたクエリテンプレートエントリのオーサリング、スキーマ結合エントリリンクの作成、OSI セマンティックオントロジー YAML のオーサリングは curate-context スキルでは不可
✗ロケーション互換性: 各エントリリンクのターゲットはコンテキストセットのロケーションと一致するか、グローバルなビジネス用語集の用語である必要がある。複数ロケーションのテーブルを文書化する場合はロケーションごとに別のコンテキストセットを作成
✗クォータ: 大規模なコンテキストセット (100 エントリ以上、または 200 リンク以上) はリージョンごとのユーザー単位エントリリンクリクエストクォータの対象
✗バージョン履歴・Git 同期は非内蔵: Knowledge Catalog は最後に push された状態のみを保持し、Git とは自動同期しない。履歴管理には自前の Git リポジトリへのコミットが必要

🤔 考慮すべき点

→コンテキストセットは標準のプロジェクト閲覧者ロールや roles/dataplex.catalogAdmin から読み取りアクセスを継承しないため、公開後に roles/dataplex.contentUser を明示的に付与する必要がある
→コンテキストセットへのアクセス権はセマンティックメタデータとクエリテンプレートの読み取りを許可するのみで、基盤テーブルのアクセス制御はバイパスしない (ゼロコピーのデータプレーンセキュリティ)
→チームメイトが先に公開した変更と競合する場合は、push を承認せず、pull して変更を再適用してから再度公開プレビューを行う運用が推奨される
→サードパーティのコーディングエージェントを使う場合、別途サブスクリプションやモデル使用料金が発生する可能性がある

🎯 ユースケース

💰 ユースケース 1: 収益分析ドメインのコンテキストセットを新規作成

シナリオ: アナリティクスエンジニアが、CRM と課金の BigQuery テーブル、社内の指標定義ドキュメント、検証済みの収益系 SQL をもとに、AI エージェント向けの収益分析コンテキストセットを整備したい。

Prompt 実装例 
Build a Knowledge Catalog context set named sales-analytics in project
cymbal-analytics (location us) from BigQuery tables
cymbal-analytics.crm.accounts and cymbal-analytics.billing.mrr_movements,
using ./docs/revenue_definitions.md and ./sql/revenue_queries.sql.

効果: 類似・ステージング・非推奨テーブルの除外確認を経て、検証済み SQL とビジネス定義を含むコンテキストセットが公開され、discover-assets や Gemini Enterprise 経由のエージェントがキュレート済み定義でグラウンディングされた SQL を生成できる。

📋 ユースケース 2: ポリシー変更に伴う既存コンテキストセットの更新

シナリオ: データスチュワードが、Q4 のポリシー更新 (社内テストアカウントの除外) を net-revenue-retention の定義に反映させたい。

Prompt 実装例 
Pull the sales-analytics context set from project cymbal-analytics (location us).
Update the net-revenue-retention definition to exclude internal test accounts
(test_account_flag = FALSE) based on ./docs/q4_policy_update.md, check for
affected queries, and publish the update.

効果: 影響を受けるコンセプト文書・テーブルページ・SQL クエリが波及効果としてフラグ表示され、レビュー・承認を経て一貫性を保ったまま更新を公開できる。

🔍 ユースケース 3: 公開済みコンテキストセットのリトリーバルテスト

シナリオ: 公開したコンテキストセットが実際にエージェントの回答をグラウンディングするか検証したい。

Prompt 実装例 (discover-assets スキル経由で質問) 
Which tables and filters should I use to calculate net revenue retention?
Write a BigQuery SQL query for monthly expansion MRR using our curated revenue context.

効果: コンテキストセットのエントリが優先的に検索され (parent_entrygroup_type=context-set)、リモート MCP サーバーの lookup_context を通じてキュレート済み定義に基づく回答・SQL が返ることを確認できる。

💲 料金

→メタデータストレージ: コンテキストセットは標準の Knowledge Catalog エントリグループ・カスタムエントリ・アスペクトとして保存され、エントリ作成時に標準の Knowledge Catalog メタデータストレージ料金がエントリグループをホストするプロジェクトに適用。空のエントリグループには課金されない
→SQL 検証: SQL コンパイルチェックはテーブル行を読み取らない。BigQuery ドライランはクエリ料金が発生せず、Spanner / Cloud SQL / AlloyDB のクエリプラン・EXPLAIN は既存のプロビジョニング済みインスタンスを使用 (標準のインスタンス料金が適用)
→任意のライブテストクエリ: 集計や行数制限でスコープされたライブテストクエリを実行した場合は標準のクエリ料金が発生
→コーディングエージェント: サードパーティのコーディングエージェントを使用する場合、別途サブスクリプションまたはモデル使用料金が発生する可能性がある

詳細は Knowledge Catalog の料金ページ および BigQuery の料金ページ を参照してください。

curate-context スキルの Preview 提供により、Knowledge Catalog のコンテキストセットを 「Metadata as Code」として、使い慣れたコーディングエージェントと Git ワークフローの中でキュレーションできるようになりました。公開前の SQL コンパイルチェックや 明示的な承認フローにより、AI エージェントをグラウンディングするドメイン知識の品質を保ちながら運用できます。

🚀 データガバナンスと生成 AI 活用を両立させたいチームは、Data Agent Kit をインストールし、 小規模なドメインのコンテキストセットから試行を始めることをおすすめします。
