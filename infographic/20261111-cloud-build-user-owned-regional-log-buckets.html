🔨 Cloud Build 🔄 Change (デフォルト動作の変更)

☁️ Cloud Build のビルドログ保存先
ユーザー所有リージョナルバケットがデフォルトに

リリース日: 2026-11-11
Google Cloud Release Notes

📌 概要

Cloud Build でビルドログを Cloud Storage に保存する際、従来の Google Cloud 所有バケット (レガシーバケット) に代わり、 ユーザー所有のリージョナルバケットがデフォルトで使用されるようになりました。 ビルド設定で defaultLogsBucketBehavior: REGIONAL_USER_OWNED_BUCKET を指定した場合と同じ動作が、 明示的な設定なしで適用されます。

ビルドログはユーザー自身のプロジェクト内に Cloud Build が自動作成するビルドと同一リージョンのバケットに保存され、 保持期間や暗号化などのバケット設定を自分で管理できるようになります。データレジデンシー要件への準拠やログガバナンス強化に有効ですが、 Cloud Storage のストレージ料金が自分のプロジェクトに課金される点に注意が必要です。

😕 Before: アップデート前の課題

  • ログは Google Cloud 所有プロジェクト内のバケットに保存され、保持期間・ライフサイクル・暗号化などの設定を変更できなかった
  • ログはコンソールのビルド詳細ページ「ビルドログ」セクションからしか閲覧できなかった
  • バケットのリージョンは Google Cloud 側で定義され、ビルドのリージョンと一致するとは限らず、データレジデンシー対応が困難だった
  • リージョン整合やユーザー所有バケットの利用には defaultLogsBucketBehavior や logsBucket の明示的な設定が必要だった

😊 After: アップデート後の改善

  • 明示的な設定なしで、ユーザーのプロジェクト内にある Cloud Build 作成・ユーザー所有のバケットにデフォルトで保存
  • ログバケットが常にビルドと同一リージョンに作成され、データレジデンシー要件への準拠が容易に
  • 保持期間・ライフサイクルルールなどの設定変更や、バケット内のログの直接閲覧が可能に
  • 同一プロジェクト・同一リージョンの以降のビルドは作成済みバケットを再利用し、一貫したログ管理が可能に

Cloud Storage にビルドログを保存する場合のデフォルトの保存先が、Google Cloud 所有バケットから ユーザーのプロジェクト内のビルドと同一リージョンのユーザー所有バケットに変更されたことを示す Before/After 比較図

⚙️ 主要機能

1️⃣ ユーザー所有リージョナルバケットのデフォルト化

ビルドログを Cloud Storage に保存する場合、Cloud Build が作成するユーザー所有バケットがデフォルトで使用される。 バケットはユーザーのプロジェクト内に作成され、ビルドと同一リージョンに配置。 従来必要だった defaultLogsBucketBehavior: REGIONAL_USER_OWNED_BUCKET の明示的な設定が不要に。

2️⃣ リージョンごとのバケット自動作成・再利用

初回ビルド時に、ビルドを実行するリージョンに新しいバケットを自動作成。 同一プロジェクト・同一リージョンの以降のビルドは既存バケットを再利用。 複数リージョンでビルドする場合はリージョンごとに個別のバケットが作成される。

3️⃣ ユーザーによるバケット管理

作成されたバケットはユーザー所有のため、ユーザー作成バケットと同様に 保持期間・ライフサイクル・ラベルなどの設定変更が可能。 バケット内のビルドログを Cloud Storage から直接閲覧できる。

🔧 技術仕様

📋 ログ保存先の決定ロジック

設定動作
logging: CLOUD_LOGGING_ONLY ログは Cloud Logging のみに送信 (defaultLogsBucketBehavior は無視)
logging: NONE ログは保存されない
logsBucket を指定 指定したバケットに常に保存 (defaultLogsBucketBehavior は無視)
logsBucket 未指定 + REGIONAL_USER_OWNED_BUCKET Cloud Build 作成・ユーザー所有のリージョナルバケットに保存 (今回の変更によりデフォルト動作)
logsBucket 未指定 + LEGACY_BUCKET Google Cloud 所有プロジェクト内のバケットに保存 (従来のデフォルト動作を明示的に維持する場合に指定)

🔑 ログ閲覧に必要な IAM ロール

保存先必要なロール
ユーザー作成/ユーザー所有の Cloud Storage バケット Storage Object Viewer (roles/storage.objectViewer)
デフォルト (Google Cloud 所有) バケット Viewer (roles/viewer)
Cloud Logging Logs Viewer (roles/logging.viewer)

🛠️ 設定方法

✅ 前提条件

1. ビルドに使用するサービスアカウントに、ログバケットへの書き込み権限があること (同一プロジェクト + Cloud Build レガシーサービスアカウントなら追加権限不要。それ以外は Storage Admin roles/storage.admin などの付与が必要)
2. ビルドログの保存先として Cloud Storage を使用していること (logging が GCS_ONLY または LEGACY 相当)

ステップ 1: 現在のログ設定の確認

YAML cloudbuild.yaml — ログ関連フィールドを確認 
# cloudbuild.yaml の例: ログ関連フィールドを確認
steps:
  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-t', 'us-central1-docker.pkg.dev/myproject/myrepo/myimage', '.']
options:
  # logging / logsBucket / defaultLogsBucketBehavior の設定を確認
  defaultLogsBucketBehavior: REGIONAL_USER_OWNED_BUCKET

logsBucket を指定している場合は従来通りそのバケットが使用されます。 デフォルト動作に依存している場合は、今回の変更によりユーザー所有リージョナルバケットが使用されます。

ステップ 2: 従来の動作を維持したい場合 (レガシーバケットの明示指定)

YAML LEGACY_BUCKET の明示指定 
options:
  defaultLogsBucketBehavior: LEGACY_BUCKET

Google Cloud 所有バケットへの保存を継続したい場合は、defaultLogsBucketBehavior に LEGACY_BUCKET を明示的に設定します。

ステップ 3: Dockerfile からのビルド時の指定

Bash gcloud builds submit のフラグ指定 
# gcloud builds submit 実行時にフラグで指定
gcloud builds submit --default-buckets-behavior=regional-user-owned-bucket

# レガシー動作を維持する場合
gcloud builds submit --default-buckets-behavior=legacy-bucket

ビルド設定ファイルを使わずに Dockerfile からビルドする場合は、 --default-buckets-behavior フラグで動作を指定できます。

⚖️ メリットと注意点

💼 ビジネス面のメリット
✓データレジデンシー要件への準拠: ログが常にビルドと同一リージョンに保存され、データ所在地のコンプライアンス要件を満たしやすい
✓ガバナンスの向上: 組織のポリシー (保持期間、アクセス制御、監査) を自社の基準で適用できる
🔧 技術面のメリット
✓バケット設定の自由度: 保持期間・ライフサイクルルール・ラベルなどを自由に構成可能
✓ログへの直接アクセス: バケットからいつでも直接閲覧・取得でき、他ツールとの連携も容易
✓設定不要でベストプラクティス適用: 推奨構成 (ユーザー所有・リージョン整合バケット) がデフォルトに
⚠️ 制限事項
✗ユーザー所有バケットへのログ保存には Cloud Storage のストレージ料金が発生 (レガシーバケットでは課金なし)
✗複数リージョンでビルドする場合、リージョンごとにバケットが作成され、管理対象が増える
✗logging が CLOUD_LOGGING_ONLY/NONE の場合や logsBucket 定義済みの場合は影響なし
💡 考慮すべき点
→デフォルト動作依存の既存ビルドでは、ログ保存先と閲覧に必要な IAM ロールが変わる可能性 (roles/viewer → roles/storage.objectViewer)
→レガシーサービスアカウント以外では、バケット作成・書き込み権限 (Storage Admin など) の付与が必要な場合がある
→コストを抑えたい場合は、ライフサイクルルール (一定期間後の削除や低頻度アクセスクラスへの移行) の設定を推奨
→従来動作の維持には defaultLogsBucketBehavior: LEGACY_BUCKET を明示設定

🎯 ユースケース

🏦 ユースケース 1: データレジデンシー要件のある企業での CI/CD

シナリオ: 金融機関が、ビルドログを含むすべてのデータを特定リージョン (例: asia-northeast1) 内に保持することをコンプライアンス上求められている。

YAML cloudbuild.yaml — 追加設定なしでリージョン整合が実現 (明示する場合) 
steps:
  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-t', 'asia-northeast1-docker.pkg.dev/myproject/myrepo/app', '.']
options:
  defaultLogsBucketBehavior: REGIONAL_USER_OWNED_BUCKET

効果: asia-northeast1 で実行したビルドのログは自動的に同リージョンのユーザー所有バケットに保存され、 データ所在地要件を満たしつつ、監査時にはバケットから直接ログを取得できる。

🔐 ユースケース 2: ログ保持ポリシーの統一管理

シナリオ: 組織のセキュリティポリシーで、CI/CD ログを 90 日間保持した後に削除することが定められている。 従来の Google Cloud 所有バケットではバケット設定を変更できなかった。

効果: ユーザー所有バケットに対してライフサイクルルール (90 日後に削除) を設定でき、 組織のログ保持ポリシーを Cloud Build のログにも適用できる。保存コストの最適化にもつながる。

💰 料金

Cloud Build 自体の料金に変更はありませんが、ビルドログがユーザー所有バケットに保存されるため、 Cloud Storage のストレージ料金・オペレーション料金がユーザーのプロジェクトに課金されるようになります (従来の Google Cloud 所有バケットでは課金なし)。

🌏 利用可能リージョン

Cloud Build が利用可能なすべてのリージョンに適用されます。 ログバケットはビルドを実行するリージョンごとに作成されます。 利用可能なリージョンは Cloud Build のロケーション を参照してください。

🔗 関連サービス・機能

🪣 Cloud Storage

ビルドログの保存先。ユーザー所有バケットとして保持期間・ライフサイクル・暗号化などを管理できる

📋 Cloud Logging

ビルドログのもう 1 つの保存先 (logging: CLOUD_LOGGING_ONLY)。ログ検索性や保持期間の制御を重視する場合の選択肢

🔑 IAM

ユーザー所有バケットのログ閲覧には roles/storage.objectViewer、ビルド用サービスアカウントのバケット操作には roles/storage.admin などの権限管理が関連

📦 Artifact Registry

Cloud Build と組み合わせて使用される代表的なビルド成果物の保存先
