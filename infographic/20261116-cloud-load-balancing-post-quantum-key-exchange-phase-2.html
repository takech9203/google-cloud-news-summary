🔐 Cloud Load Balancing
TLS ポスト量子鍵交換が Phase 2 (デフォルト有効化) に移行

リリース日: 2026-11-16
⚖️ Cloud Load Balancing Feature (デフォルト有効化フェーズ) 🛡️ Post-Quantum Cryptography

📋 概要

Application Load Balancer および外部プロキシ Network Load Balancer における TLS ポスト量子鍵交換 (Post-Quantum Key Exchange) のロールアウトが Phase 2 (2026 年 10 月〜2027 年 10 月) に移行し、 デフォルトで有効になりました。 SSL ポリシーが未アタッチ、またはポスト量子鍵交換の設定を持たない SSL ポリシーを使用しているロードバランサーが対象です。

💡 なぜ今、耐量子化が必要なのか: Google は、研究が現在のペースで進めば、TLS で使用されている非対称暗号は早ければ 2029 年にも量子コンピュータによって破られる可能性があると考えています。 現在暗号化された通信を記録しておき、将来復号する「Harvest Now, Decrypt Later (今収集して後で復号する) 攻撃」への対策として、鍵交換の耐量子化は今すぐ対応すべき課題です。

採用されたのは X25519MLKEM768 — 古典暗号 (X25519) と NIST 標準のポスト量子暗号 (ML-KEM-768) を組み合わせたハイブリッド方式です。 クライアントが TLS 1.3 と X25519MLKEM768 のサポートを広告した場合にのみ使用されるため、未対応クライアントからの接続には影響しません。 互換性の問題がある場合は、SSL ポリシーで DEFERRED を設定すると 2027 年 10 月まで有効化を延期 (オプトアウト) できます。

❌ Before (Phase 1: オプトイン方式)

  • 利用には SSL ポリシーで明示的に ENABLED を設定 (オプトイン) する必要があった
  • SSL ポリシー未設定の大多数のロードバランサーでは、Harvest Now, Decrypt Later 攻撃に対して無防備なままだった
  • 組織全体への展開には、各プロジェクト・各ロードバランサーで個別の設定作業が必要だった

✅ After (Phase 2: デフォルト有効)

  • SSL ポリシーの設定なしで、ポスト量子鍵交換がデフォルトで有効に
  • 対応クライアント (TLS 1.3 + X25519MLKEM768) との通信が自動的に耐量子ハイブリッド鍵交換で保護される
  • 互換性の問題がある場合は DEFERRED 設定で 2027 年 10 月まで延期できる猶予を用意

Phase 2 ではフロントエンド TLS 接続においてポスト量子鍵交換がデフォルトで有効になり、対応クライアントとの間で自動的に X25519MLKEM768 ハイブリッド鍵交換が使用されます。 未対応クライアントやロードバランサーとバックエンド間の接続には影響しません。

⚡ 主要機能

1️⃣ ポスト量子鍵交換のデフォルト有効化 (Phase 2)

→2026 年 10 月以降、SSL ポリシーが未アタッチ、またはポスト量子鍵交換の設定がない SSL ポリシーを使用するロードバランサーでデフォルトで有効になる
→クライアントが TLS 1.3 と X25519MLKEM768 のサポートを広告した場合にのみ使用され、未対応クライアントとの接続は従来どおり動作

2️⃣ ハイブリッド鍵交換方式 X25519MLKEM768

→古典暗号 (X25519) と NIST 標準のポスト量子暗号 (ML-KEM-768) を組み合わせ、どちらか一方が破られても安全性が保たれる
→NIST が開発・検証したアルゴリズムを使用し、IETF で策定中の標準に準拠

3️⃣ SSL ポリシーによる延期 (オプトアウト) オプション

→post-quantum-key-exchange フィールドを DEFERRED に設定すると、2027 年 10 月まで有効化を延期可能
→クライアントや中間ネットワークデバイスに互換性の問題がある場合の猶予措置として利用できる
→Phase 3 (2027 年 10 月以降) では常時有効となり、DEFERRED 設定は効力を失う

ポスト量子鍵交換の動作仕様

項目詳細
鍵交換アルゴリズムX25519MLKEM768 (古典 + ポスト量子のハイブリッド)
必要な TLS バージョンTLS 1.3 (クライアント側が広告する場合のみ使用)
適用範囲フロントエンド TLS 接続のみ (クライアント ↔ ロードバランサー間)。バックエンド側接続は対象外
SSL ポリシープロファイルとの関係COMPATIBLE / MODERN / RESTRICTED / FIPS_202205 / CUSTOM のいずれのプロファイル、いずれの最小 TLS バージョン設定とも併用可能
対象外の暗号AES-128、AES-256、ChaCha20 などの対称暗号は量子コンピュータの脅威の対象外

post-quantum-key-exchange のモード

モード動作
ENABLEDポスト量子鍵交換を有効化。対応クライアントとの間で X25519MLKEM768 を使用
DEFAULTロードバランサーのデフォルト動作に従う (Phase 2 では有効)
DEFERRED2027 年 10 月までポスト量子鍵交換を一時的に無効化 (延期)

🛠️ 設定方法

前提条件

✓SSL ポリシーをサポートするロードバランサー (Application Load Balancer または プロキシ Network Load Balancer) を使用していること
✓SSL ポリシーを作成・変更できる IAM 権限があること

ステップ 1: 現在の SSL ポリシー構成を確認する

Bash SSL ポリシーの一覧表示 
# グローバル・リージョンの SSL ポリシーを一覧表示
gcloud compute ssl-policies list
✅ 推奨: SSL ポリシーが未アタッチ、またはポスト量子鍵交換の設定がない場合、Phase 2 ではデフォルトで有効になっています。そのまま有効を維持することが推奨されます。

ステップ 2 (延期が必要な場合のみ): DEFERRED を設定した SSL ポリシーを作成する

Bash 延期設定の SSL ポリシー作成例 
# グローバル SSL ポリシーの作成例 (延期設定)
gcloud compute ssl-policies create pqc-deferred-policy \
    --profile MODERN \
    --min-tls-version 1.2 \
    --post-quantum-key-exchange DEFERRED

クライアントや中間ネットワークデバイスとのネゴシエーションに問題がある場合のみ DEFERRED を設定します。作成したポリシーは TargetHttpsProxy または TargetSslProxy にアタッチします。

ステップ 3 (既存ポリシーを変更する場合): SSL ポリシーを更新する

Bash 既存 SSL ポリシーの更新例 
# 既存のグローバル SSL ポリシーの更新例
gcloud compute ssl-policies update SSL_POLICY_NAME \
    --post-quantum-key-exchange DEFERRED

# リージョン SSL ポリシーの場合
gcloud compute ssl-policies update SSL_POLICY_NAME \
    --region REGION \
    --post-quantum-key-exchange DEFERRED
⚠️ 注意: 延期はあくまで一時的な猶予措置です。Phase 3 (2027 年 10 月以降) では DEFERRED は効力を失うため、それまでにクライアント側の互換性対応を完了させる必要があります。

💪 メリット

💼 ビジネス面

✓将来の量子脅威への先行対応: Harvest Now, Decrypt Later 攻撃により現在記録された通信が将来復号されるリスクを、設定作業なしで軽減
✓コンプライアンス対応: NIST 標準のポスト量子暗号を採用し、耐量子暗号への移行を求める規制・業界要件への対応を前倒しできる
✓移行の猶予期間: 互換性に問題がある組織は 2027 年 10 月まで延期でき、計画的な移行が可能

⚙️ 技術面

✓ゼロコンフィグでの保護: SSL ポリシーの設定なしでデフォルト有効になり、大規模環境でも一括で耐量子保護が適用される
✓ハイブリッド方式による安全性: 万一 ML-KEM に脆弱性が見つかっても X25519 の安全性が維持される
✓後方互換性: TLS 1.3 + X25519MLKEM768 対応クライアントのみが対象で、未対応クライアントの接続には一切影響しない

⚠️ デメリット・制約事項

制限事項

✗フロントエンド TLS 接続 (クライアント ↔ ロードバランサー間) のみが対象で、ロードバランサーとバックエンド間の接続には適用されない
✗量子コンピュータによる認証 (証明書) への攻撃は本機能の対象外 (本機能は鍵交換の保護のみ)
✗DEFERRED による延期は 2027 年 10 月までの時限措置で、Phase 3 以降は設定しても効力を失う

考慮すべき点

→TLS 実装が古いクライアントや、TLS ハンドシェイクを検査する中間ネットワークデバイス (ファイアウォール、プロキシなど) で、大きくなった ClientHello / 鍵交換メッセージの処理に問題が発生する可能性がある
→延期 (オプトアウト) を選択した場合でも、2027 年 10 月までにクライアントアプリケーションと中間デバイスの互換性対応を完了させる移行計画が必要
→SSL ポリシーを多数のプロジェクトで標準化したい場合は、クロスプロジェクト SSL ポリシー参照 (Preview) の活用も検討できる

🎯 ユースケース

1. 公開 Web サービスの耐量子保護 (推奨: デフォルトのまま有効)

シナリオ: グローバル外部 Application Load Balancer で公開している Web サービスで、長期間秘匿が必要な個人情報や金融データを扱っている。将来の量子コンピュータによる復号リスク (Harvest Now, Decrypt Later) に備えたい。

Bash 明示的に ENABLED を設定する場合の例 
# 何も設定しない (デフォルトで有効) か、明示的に ENABLED を設定
gcloud compute ssl-policies create pqc-enabled-policy \
    --profile MODERN \
    --min-tls-version 1.2 \
    --post-quantum-key-exchange ENABLED

効果: Chrome など X25519MLKEM768 対応クライアントとの通信が自動的に耐量子ハイブリッド鍵交換で保護され、記録された通信が将来復号されるリスクを軽減できる。

2. レガシー環境を抱える企業での段階的移行

シナリオ: 社内システムのクライアントや中間ネットワーク機器 (TLS インスペクションを行うファイアウォールなど) が古く、ポスト量子鍵交換のネゴシエーションで問題が発生した。互換性対応が完了するまで有効化を延期したい。

効果: SSL ポリシーで DEFERRED を設定することで 2027 年 10 月まで有効化を延期でき、その間にクライアント・機器のアップデートを計画的に実施できる。Phase 3 の期限が明確なため、移行計画の締め切りとして活用できる。

🔗 関連サービス・機能

📜 SSL ポリシー

ポスト量子鍵交換のモード (ENABLED / DEFAULT / DEFERRED) を制御する設定の中核。プロファイル (COMPATIBLE / MODERN / RESTRICTED / FIPS_202205 / CUSTOM) や最小 TLS バージョンと組み合わせて利用する。

📄 Certificate Manager / Google マネージド SSL 証明書

ロードバランサーのフロントエンド TLS を構成する証明書管理サービス。ポスト量子鍵交換はこれらの証明書構成と独立して動作する。

🏢 クロスプロジェクト SSL ポリシー参照 (Preview)

管理プロジェクトで一元管理した SSL ポリシーを複数のサービスプロジェクトから参照でき、組織全体でポスト量子鍵交換の設定を標準化できる。

🔑 Cloud KMS のポスト量子暗号対応

Google Cloud は TLS 以外でも耐量子暗号への移行を進めており、組織全体の PQC 移行戦略の一部として位置づけられる。

📝 まとめ

✅ 推奨アクション: Cloud Load Balancing のポスト量子鍵交換が Phase 2 に移行し、デフォルトで有効になりました。 追加設定なしで Harvest Now, Decrypt Later 攻撃への耐性が得られるため、原則としてそのまま有効を維持することが推奨されます。

クライアントや中間機器で互換性の問題がある場合は SSL ポリシーの DEFERRED 設定で 2027 年 10 月まで延期できますが、 Phase 3 以降は延期できなくなるため、今のうちに自社環境での互換性検証と移行計画の策定を進めるべきです。
