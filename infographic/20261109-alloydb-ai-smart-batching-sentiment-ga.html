🚀 AlloyDB AI スマートバッチング &
ai.analyze_sentiment が GA

AI 関数を含む SQL をクエリ書き換えなしで大幅高速化。SQL だけでセンチメント分析を本番利用可能に

📝 概要

AlloyDB AI で 2 つの機能が 一般提供 (GA) になりました。

⚡ 1. AI 関数のスマートバッチング (AI function acceleration)

ai.if、ai.rank、ai.analyze_sentiment、ai.summarize、ai.extract、ai.classify、ai.generate を含むクエリで、対象の AI 操作を自動的にバッチ化・非同期評価し、クエリ実行速度を大幅に改善。PostgreSQL 17 以降で利用でき、PostgreSQL 18 以降ではデフォルトで有効です。

💬 2. ai.analyze_sentiment 関数の GA

SQL クエリ内でテキストのセンチメントを positive / negative / neutral にリアルタイム分類できる組み込み関数。Gemini の言語理解を ETL パイプラインなしでデータベース内の非構造化データに直接適用できます (PostgreSQL 17 以降)。

💡 誰に価値があるか: データベース内で LLM を活用したセマンティック検索・テキスト分析を行いたいデータエンジニア、アプリケーション開発者、大量データに対する AI クエリのパフォーマンスに課題を抱えていたユーザー。

❌ Before: アップデート前の課題

  • AI 関数が行ごと (row-by-row) に評価され、1 行ごとにモデル呼び出しのネットワークレイテンシが発生
  • 性能改善には複雑な配列ベース構造へのクエリ書き換えが必要
  • センチメント分析には外部 ML サービスへの ETL パイプライン構築が必要
  • AI 関数が GA 前のステータスで、本番採用にハードル

✅ After: アップデート後の改善

  • AI 操作を自動バッチ化・非同期評価。標準的な SQL のままで配列ベース関数と同等以上の性能
  • 選択性の高いリレーショナルフィルタを先に評価し、モデル呼び出し行数を最小化
  • 並列クエリと統合し、バッチ評価を並列ワーカーに分散
  • ai.analyze_sentiment が GA。SQL だけで本番のセンチメント分類が可能
  • PostgreSQL 18 以降は追加設定なしで有効

スマートバッチング有効時は、通常の WHERE 条件が先にインデックス等で評価され、候補行のみが AIFunctionApply ノードでバッチ化されて Gemini モデルに非同期送信されます。

⭐ 主要機能

⚡ 1. AI 関数のスマートバッチング (GA)

  • ai.if / ai.rank / ai.analyze_sentiment / ai.summarize / ai.extract / ai.classify / ai.generate が対象 (PostgreSQL 17 以降)
  • AI 操作を自動バッチ化し、高スループットの非同期評価にオフロード。配列構造への書き換え不要
  • PostgreSQL 18 以降はデフォルト有効 (google_ml_integration.enable_ai_function_acceleration)

🔍 2. 主要 SQL 句を横断した高速化

  • WHERE 句: 選択性の高い非 AI 述語を先に評価してから ai.if などでフィルタ
  • ORDER BY 句: ai.rank の関連度スコアをバッチ計算してからソート・LIMIT
  • SELECT 射影: スカラー AI 関数を結果行全体でバッチ化。ai.agg_summarize の行横断要約にも対応
  • JOIN ... ON: INNER JOIN のクロステーブル AI 条件を評価
  • DML: UPDATE / DELETE / INSERT ... SELECT の WHERE・ターゲットリスト・SET 式内の AI 関数も高速化

🧵 3. PostgreSQL 並列クエリとの統合

大規模テーブルのスキャン時に、バッチ評価を複数の並列バックグラウンドワーカーに分散 (Parallel Custom Scan (AIFunctionApply))。

💬 4. ai.analyze_sentiment 関数 (GA)

  • テキストを 'positive' / 'negative' / 'neutral' に分類する組み込み関数 (PostgreSQL 17 以降)
  • 単一文字列の分析、スカラー関数アクセラレーション、配列・カーソルベースの数千行規模のバッチ処理に対応
  • SELECT 射影、WHERE フィルタ、JOIN 句で利用可能

🛡️ 5. 安全なフォールバック動作

  • 高速化できないクエリパターンはエラーにならず、自動的に標準の行ごと実行にフォールバック
  • client_min_messages = DEBUG2 と EXPLAIN でフォールバック理由 (「AI function acceleration is not applied」) を診断可能

ステップ 1: 拡張のインストールと AI クエリエンジンの有効化

SQL拡張のセットアップ
-- 拡張のバージョン確認
SELECT extversion FROM pg_extension WHERE extname = 'google_ml_integration';

-- インストール / 更新
CREATE EXTENSION IF NOT EXISTS google_ml_integration;
ALTER EXTENSION google_ml_integration UPDATE;

-- AI クエリエンジンを有効化 (デフォルトは on、再起動不要)
SET google_ml_integration.enable_ai_query_engine = 'on';

ステップ 2: スマートバッチングの有効化 (インスタンスレベル)

Bashgcloud でデータベースフラグを設定
gcloud alloydb instances update INSTANCE_ID \
  --database-flags google_ml_integration.enable_ai_function_acceleration=on \
  --region=REGION_ID \
  --cluster=CLUSTER_ID \
  --project=PROJECT_ID
⚠️ 注意: PostgreSQL 17 ではデフォルト off のため明示的な有効化が必要です。セッション単位では SET google_ml_integration.enable_ai_function_acceleration = on; を使用します。

ステップ 3: スマートバッチングの適用確認

SQLEXPLAIN で実行計画を確認
EXPLAIN (COSTS OFF)
SELECT r.name, r.review
FROM restaurant_reviews r
WHERE ai.if('Is the following a positive review? Review: ' || r.review)
  AND r.city = 'Los Angeles';
✅ 確認ポイント: 実行計画に Custom Scan (AIFunctionApply) または Parallel Custom Scan (AIFunctionApply) ノードが表示されればスマートバッチングが適用されています。リレーショナルフィルタ (city = 'Los Angeles') が先にインデックスで評価され、一致した行のみがモデルにバッチ送信されます。

ステップ 4: ai.analyze_sentiment の利用

SQLセンチメント分析クエリ
SELECT id, review_content,
       ai.analyze_sentiment(review_content) AS sentiment
FROM reviews;

💪 メリット

💼 ビジネス面

✓AI 分析の民主化: ETL パイプラインや外部サービス連携なしで、SQL スキルだけでセンチメント分析や LLM ベースのフィルタリング・ランキングを実現
✓本番採用の安心感: スマートバッチングと ai.analyze_sentiment が GA となり、SLA を前提とする本番ワークロードで利用可能
✓コスト効率: リレーショナルフィルタを先に評価するため、モデル呼び出し行数が最小化され、モデル利用コストの無駄を削減

🛠️ 技術面

✓クエリ書き換え不要: 配列ベース関数と同等以上の性能を、標準的で読みやすい SQL のままで実現
✓行ごとのネットワークレイテンシを解消: 自動バッチ化と非同期評価でスループットが大幅向上
✓並列クエリ統合: 大規模テーブルではバッチ評価が並列ワーカーに分散されスケール
✓安全なフォールバック: 高速化できないパターンでも標準実行にフォールバックし、既存クエリへの影響リスクが低い

⚠️ デメリット・制約事項

🚫 制限事項 (フォールバックが発生するパターン)

✗ネストした AI 関数 (例: ai.if(ai.if(...))) は高速化不可
✗LEFT / RIGHT / FULL OUTER JOIN の ON 句内の AI 関数は非対応 (WHERE 句やサブクエリへの移動で回避可能)
✗AI 関数を直接ラップする集約 (例: AVG(ai.rank(...))) は非対応 (CTE やサブクエリで先に計算してから集約)
✗volatile 関数 (random()、clock_timestamp() など) を含む引数式は非対応
✗最初のテキスト入力以降の引数 (output_schema、categories、model_id など) は定数リテラルである必要あり
✗相関サブクエリや外側クエリの変数参照を含む AI 式は非対応
✗外部テーブル (postgres_fdw) やマテリアライズド CTE (WITH ... AS MATERIALIZED) のスキャンは非対応
✗1 つのテーブルスキャンでサポートされる AI 関数は最大 5 種類まで

🤔 考慮すべき点

  • PostgreSQL 17 ではデフォルト off のため明示的な有効化が必要 (PostgreSQL 18 以降はデフォルト on)
  • ai.extract と ai.classify は依然 Preview。google_ml_integration.enable_preview_ai_functions=on が必要
  • デフォルトモデル (gemini-2.5-flash-lite) がサポートされるリージョンで利用可能なため、リージョンのモデル対応状況の確認が必要
  • AI 関数呼び出し自体は AlloyDB では課金されないが、呼び出し先の Gemini モデルの利用料金は別途発生

🎯 ユースケース

💬 ユースケース 1: カスタマーレビューのリアルタイムセンチメント分類

シナリオ: EC サイトの商品レビューを、外部 ML パイプラインを構築せずに SQL だけでセンチメント分類し、ネガティブレビューを即座に検知したい。

SQLネガティブレビューのみ抽出 (スマートバッチングで高速評価)
SELECT id, review_content
FROM reviews
WHERE ai.analyze_sentiment(review_content) = 'negative';

効果: 数千行規模のレビューでも自動バッチ化により高速に分類でき、ETL なしでカスタマーサポートの優先対応キューを SQL だけで構築できる。

🔍 ユースケース 2: リレーショナルフィルタ + AI フィルタの高効率検索

シナリオ: 特定都市のレストランレビューから「ポジティブな内容」のものだけを抽出したい。全行をモデルに送るとコストとレイテンシが問題になる。

SQLリレーショナルフィルタが先に評価される
SELECT r.name, r.review
FROM restaurant_reviews r
WHERE ai.if('Is the following a positive review? Review: ' || r.review)
  AND r.city = 'Los Angeles';

効果: city = 'Los Angeles' がインデックスで先に評価され、候補行のみが Gemini にバッチ送信されるため、モデル呼び出しコストとクエリレイテンシの両方を最小化できる。

✏️ ユースケース 3: AI 生成を含む DML のバッチ処理

シナリオ: 既存テーブルの各行に対して要約列を一括生成したい。

SQLUPDATE の SET 式内の AI 関数も高速化
UPDATE reviews
SET summary = ai.summarize(review_content);

効果: DML (UPDATE の SET 式) 内の AI 関数もスマートバッチングで高速化され、行ごとのモデル呼び出しによる長時間実行を回避できる。

📌 まとめ

AlloyDB AI のスマートバッチング GA により、AI 関数を含む SQL クエリを書き換えなしで大幅に高速化でき、ai.analyze_sentiment の GA と合わせて「データベース内 AI」の本番採用ハードルが大きく下がりました。

推奨アクション:

  • PostgreSQL 17 クラスタでは google_ml_integration.enable_ai_function_acceleration=on を明示的に有効化
  • PostgreSQL 18 以降への移行を検討 (スマートバッチングがデフォルト有効)
  • EXPLAIN で AIFunctionApply ノードの確認から始める
