🔐 Developer Connect: Secret Manager 権限チェック強化

セキュリティ強化 Developer Connect Secret Manager IAM
2026-07-13

📋 概要

Developer Connect は、GitLab Enterprise (GLE) および Bitbucket Data Center (BBDC) 接続において、リポジトリ接続の作成・更新時に呼び出し元プリンシパルに対する Secret Manager の権限チェックを新たに実施するようになりました。

従来は Developer Connect サービスエージェント (P4SA) の資格情報のみで権限チェックが行われていましたが、今回の変更により、呼び出し元プリンシパル (エンドユーザーの資格情報) と P4SA の両方に対して secretmanager.versions.access IAM 権限を検証するようになりました。

💡 最小権限の原則 (Principle of Least Privilege)
接続管理権限を持つだけではシークレットにアクセスできなくなり、明示的なシークレットアクセス権限が必要になりました。

🔄 Before / After 比較

❌ 変更前の課題

  • P4SA の資格情報のみで権限チェック
  • 呼び出し元ユーザーのシークレットアクセス権限が未検証
  • 接続管理権限だけでシークレットを間接的に読み取り可能
  • 最小権限の原則が不完全

✅ 変更後の改善

  • 呼び出し元 + P4SA の両方で権限チェック
  • secretmanager.versions.access をデュアル検証
  • 不正アクセスリスクが大幅に軽減
  • 最小権限の原則に沿ったセキュリティモデル

⚡ 主要機能

🔒 デュアル権限チェック (Dual Permission Check)

→接続作成 (connections.create) 時に呼び出し元の権限を検証
→接続更新 (connections.update) 時にも同様のチェックを実施
→P4SA に対する既存の権限チェックは引き続き実施

👤 エンドユーザー資格情報による検証

→呼び出し元のエンドユーザー資格情報 (end-user credentials) を使用して権限を確認
→サービスアカウントキーやワークロードアイデンティティ連携による呼び出しにも適用

🎯 対象範囲の限定

✓GitLab Enterprise (GLE) 接続に適用
✓Bitbucket Data Center (BBDC) 接続に適用
✗GitHub、GitLab (SaaS)、Bitbucket Cloud には影響なし

🔧 技術仕様

項目 詳細
必要な IAM 権限 secretmanager.versions.access
推奨ロール roles/secretmanager.secretAccessor (Secret Manager Secret Accessor)
チェック対象 呼び出し元プリンシパル + P4SA の両方
影響を受ける操作 connections.create, connections.update
影響を受ける接続タイプ GitLab Enterprise (GLE), Bitbucket Data Center (BBDC)
P4SA 識別子 service-{PROJECT_NUMBER}@gcp-sa-devconnect.iam.gserviceaccount.com

IAM ポリシー設定例

JSON 
{
  "bindings": [
    {
      "role": "roles/secretmanager.secretAccessor",
      "members": [
        "user:developer@example.com",
        "serviceAccount:service-123456789@gcp-sa-devconnect.iam.gserviceaccount.com"
      ]
    }
  ]
}

📝 設定方法

以下の手順で権限を設定してください。

Step 1: 呼び出し元プリンシパルにシークレットアクセス権限を付与

Bash 
# 特定のシークレットに対して Secret Accessor ロールを付与
gcloud secrets add-iam-policy-binding SECRET_NAME \
    --member="user:DEVELOPER_EMAIL" \
    --role="roles/secretmanager.secretAccessor" \
    --project=PROJECT_ID

Step 2: P4SA のシークレットアクセス権限を確認・付与

Bash 
# Developer Connect サービスエージェントのシークレットアクセス権限を確認
gcloud secrets get-iam-policy SECRET_NAME \
    --project=PROJECT_ID \
    --format="table(bindings.role, bindings.members)"

# 必要に応じて P4SA に権限を付与
gcloud secrets add-iam-policy-binding SECRET_NAME \
    --member="serviceAccount:service-PROJECT_NUMBER@gcp-sa-devconnect.iam.gserviceaccount.com" \
    --role="roles/secretmanager.secretAccessor" \
    --project=PROJECT_ID

Step 3: 接続の作成または更新を実行

Bash 
# GitLab Enterprise 接続の作成例
gcloud developer-connect connections create CONNECTION_NAME \
    --location=REGION \
    --gitlab-enterprise-config-host-uri="https://gitlab.example.com" \
    --gitlab-enterprise-config-read-authorizer-credential-secret-version="projects/PROJECT_ID/secrets/SECRET_NAME/versions/latest" \
    --gitlab-enterprise-config-authorizer-credential-secret-version="projects/PROJECT_ID/secrets/SECRET_NAME/versions/latest" \
    --project=PROJECT_ID

✅ メリット

💼 ビジネス面

✓コンプライアンス強化: 最小権限の原則に基づくアクセス制御でセキュリティ監査要件を満たしやすくなる
✓リスク軽減: シークレットへの不正アクセスリスクが軽減され、データ漏洩の可能性が低下

🔧 技術面

✓多層防御: 呼び出し元と P4SA の両方で権限チェックを行いセキュリティレイヤーを追加
✓最小権限の徹底: 接続管理権限だけではシークレットにアクセス不可
✓透過的な適用: 既存接続には影響なく、新規作成・更新時のみチェック

⚠️ 制約事項・注意点

制限事項
  • 対象は GitLab Enterprise と Bitbucket Data Center 接続のみ。GitHub / GitLab SaaS / Bitbucket Cloud には非適用
  • 既存接続の更新時、これまで不要だったユーザーに secretmanager.versions.access 権限の新規付与が必要になる場合あり
考慮すべき点
  • 権限エラー発生時は、呼び出し元プリンシパルに roles/secretmanager.secretAccessor ロールを付与
  • CI/CD パイプラインで接続管理している場合、使用するサービスアカウントにもシークレットアクセス権限が必要
  • 組織ポリシーや VPC Service Controls との組み合わせで追加設定が必要な場合あり

💡 ユースケース

🏢 エンタープライズ開発チームの GitLab Enterprise 接続管理

シナリオ: 大規模な開発組織で、複数のチームが GitLab Enterprise を使用しており、チームごとに異なるシークレットで接続を管理している場合。

Bash 
# チーム A のシークレットにチーム A のメンバーのみアクセス権を付与
gcloud secrets add-iam-policy-binding team-a-gitlab-token \
    --member="group:team-a@example.com" \
    --role="roles/secretmanager.secretAccessor" \
    --project=project-id

# チーム B は team-a-gitlab-token にはアクセスできない
# → チーム B が team-a の接続を更新しようとしても権限エラーになる

効果: チーム間のシークレット分離が確保され、他チームの認証情報への間接的アクセスを防止。

🛡️ セキュリティインシデント対応時のアクセス制御

シナリオ: セキュリティ監査で、Developer Connect の接続管理権限を持つユーザーが不必要に多くのシークレットにアクセスできることが発覚した場合。

効果: 接続管理権限 (developerconnect.admin) とシークレットアクセス権限 (secretmanager.secretAccessor) が分離されるため、権限の棚卸しが容易になり、最小権限の原則に基づいたアクセス制御を実現。

📌 まとめ

今回の Developer Connect のセキュリティ強化は、最小権限の原則に基づき、GitLab Enterprise および Bitbucket Data Center 接続における Secret Manager シークレットへのアクセスを呼び出し元プリンシパルレベルでも検証するものです。

対応が必要なケース:
  • 今後接続を新規作成または更新する場合、呼び出し元に roles/secretmanager.secretAccessor ロールが付与されていることを確認
  • CI/CD パイプラインで接続管理を自動化している場合、使用するサービスアカウントへの権限付与を実施
  • 既存の接続には影響なし
