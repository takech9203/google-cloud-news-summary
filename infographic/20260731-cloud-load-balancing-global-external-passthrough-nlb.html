⚖️ グローバル外部パススルー Network Load Balancer

☁️ Cloud Load Balancing Preview 🌐 ネットワーキング
リリース日: 2026-07-31

📌 概要

リージョン外部パススルー Network Load Balancer のグローバル版となる グローバル外部パススルー NLB が Preview として登場。 Layer 4 のパススルー型ロードバランサーとして、複数リージョンにまたがるバックエンド (インスタンスグループ / NEG) に外部トラフィックを分散します。

グローバル分散配置された Maglev 上に構築され、Google のグローバルエニーキャスト IP ルーティングにより、 トラフィックが Google ネットワークに入った地点から最も近い正常なリージョンへ誘導。超低レイテンシと動的なリージョン間フェイルオーバーを実現します。

😣 Before: リージョナルのみ

  • パススルー型 (DSR、送信元 IP 保持、TCP/UDP 以外も対応) の外部 LB は単一リージョンのバックエンドにしか分散できない
  • マルチリージョン化にはリージョンごとに NLB を作成し、DNS ベースのルーティングで振り分ける必要があった
  • リージョン障害・容量超過時のフェイルオーバーを自前で設計・運用

😊 After: グローバル対応

  • 単一のエニーキャスト IP (AG0/AG1 の 2 IP) で複数リージョンへ L4 パススルー分散
  • 容量超過時は既存接続を維持したまま新規接続を近隣リージョンへ自動スピルオーバー
  • リージョン障害時は次に近いリージョンへ自動フェイルオーバー
  • 分離された 2 系統の基盤 (AG0/AG1) で LB 自体の耐障害性も向上

クライアントのトラフィックはエニーキャスト IP により最寄りの Google エッジから入り、最も近い正常なリージョンのバックエンドへパススルーで転送されます。 応答はロードバランサーを経由せず、バックエンドからクライアントへ直接返されます (Direct Server Return)。

⚡ 主要機能

🌐 1. グローバルエニーキャストルーティングによるマルチリージョン分散

✓Google のグローバルネットワーク上で動作する、グローバル分散された Maglev 上に構築
✓Google ネットワークへの入口に最も近いバックエンドリージョンへ自動的にトラフィックを誘導
✓容量超過時は既存接続を維持しつつ、新規接続を次に近い空き容量のあるリージョンへスピルオーバー
✓リージョンダウン時は次に近い利用可能なリージョンへ自動フェイルオーバー

🛡️ 2. アベイラビリティグループによる高可用性設計

✓ロードバランサーごとに 2 つのグローバル外部 IP アドレスを提供 (静的またはエフェメラル)
✓各 IP は分離・独立したコントロールプレーン/データプレーン基盤 (AG0、AG1) で提供され、一方の障害が他方に影響しない
✓転送ルール (親) を 1 つ作成すると、各 AG 用に読み取り専用の子転送ルールが 2 つ自動生成
✓クライアントは両方の IP に接続できる構成を推奨 (AG0 に接続できない場合は AG1 へ)

🔀 3. パススルー型 (DSR) による幅広いプロトコル対応

✓TCP、UDP、ESP、GRE、ICMP、ICMPv6 をサポート。IPv4 / IPv6 両対応
✓非プロキシのため、パケットの送信元/宛先 IP・プロトコル・ポートを変更せず転送 (クライアント送信元 IP を保持)
✓応答は LB を経由せずクライアントへ直接返送 (Direct Server Return)
✗TLS (SSL) はバックエンドで終端 (LB での SSL 終端は非対応)

🧩 構成コンポーネント

  • グローバル外部 IP アドレス × 2: アベイラビリティグループ AG0 / AG1 から 1 つずつ
  • グローバル転送ルール × 1: 2 つの IP を指定。作成時に AG ごとの読み取り専用の子転送ルールが 2 つ自動生成
  • グローバルバックエンドサービス × 1: 複数リージョンのバックエンドへの分散方法を定義
  • グローバルヘルスチェック: バックエンドサービスに関連付け
  • ファイアウォールルール: ロードバランシングトラフィックとヘルスチェックプローブの許可

🛠️ 設定方法

💡 前提条件: ① Premium ティアのネットワークサービスティアを使用 ② バックエンド (ゾーン MIG / ゾーン NEG) を対応リージョンに作成済み ③ TLS を扱う場合はバックエンドで SSL を終端
1
アベイラビリティグループごとにグローバル外部 IP を予約
Bash AG0 / AG1 それぞれの IP を予約 (IPv6 は --ip-version=IPV6) 
gcloud beta compute addresses create lb-ipv4-ag0 \
    --global \
    --purpose=PASSTHROUGH_LOAD_BALANCER_AVAILABILITY_GROUP0 \
    --ip-version=IPV4

gcloud beta compute addresses create lb-ipv4-ag1 \
    --global \
    --purpose=PASSTHROUGH_LOAD_BALANCER_AVAILABILITY_GROUP1 \
    --ip-version=IPV4
2
ヘルスチェックとグローバルバックエンドサービスを作成
Bash EXTERNAL_PASSTHROUGH スキームで作成 
gcloud compute health-checks create tcp hc-tcp-80 \
    --global \
    --port=80

gcloud beta compute backend-services create lb-backend-service \
    --load-balancing-scheme=EXTERNAL_PASSTHROUGH \
    --health-checks=hc-tcp-80 \
    --global
3
複数リージョンのバックエンドを追加
Bash us-west1 / europe-west2 の MIG を追加 
gcloud beta compute backend-services add-backend lb-backend-service \
    --instance-group=mig-us \
    --instance-group-zone=us-west1-a \
    --balancing-mode=UTILIZATION \
    --max-utilization=0.7 \
    --global

gcloud beta compute backend-services add-backend lb-backend-service \
    --instance-group=mig-eu \
    --instance-group-zone=europe-west2-a \
    --balancing-mode=UTILIZATION \
    --max-utilization=0.7 \
    --global
4
グローバル転送ルールを作成
Bash 1 つの転送ルールに AG0 / AG1 の 2 つの IP を指定 
gcloud beta compute forwarding-rules create lb-forwarding-rule-ipv4 \
    --load-balancing-scheme=EXTERNAL_PASSTHROUGH \
    --ip-protocol=TCP \
    --ports=80 \
    --backend-service=lb-backend-service \
    --global \
    --ip-addresses=lb-ipv4-ag0,lb-ipv4-ag1

IPv4 と IPv6 の両方を扱う場合は、それぞれの転送ルールを作成します。

💼 ビジネス面

✓グローバルサービスの構築簡素化: SSE、DNS ホスティング、リアルタイムビディング、RTC、ライブストリーミング、オンラインゲームなどの低レイテンシ L4 サービスを単一のロードバランサーで実現
✓可用性向上による機会損失の低減: リージョン障害時の自動フェイルオーバーと、分離された 2 系統の基盤 (AG0/AG1) によりサービス停止リスクを低減

⚙️ 技術面

✓エニーキャストによる超低レイテンシ: Google ネットワークへの入口に最も近いリージョンへ誘導
✓動的なクロスリージョンフェイルオーバー / スピルオーバー: 障害時は自動フェイルオーバー、容量超過時は新規接続のみをスピルオーバー
✓クライアント送信元 IP の保持: パススルー型 (DSR) のため元のパケットが変更されずに届く
✓幅広いプロトコル対応: TCP/UDP に加え、ESP、GRE、ICMP、ICMPv6 もグローバルに分散可能

⚠️ デメリット・制約事項

🚫 制限事項

✗Preview 段階であり、Pre-GA 利用規約が適用 (サポートが限定される場合あり)
✗GKE バックエンドは今回のリリースでは非対応
✗バックエンドを配置できるリージョンは 12 リージョンに限定
✗ロードバランサーでの SSL 終端は非対応 (バックエンドで終端が必要)
✗Premium ネットワークサービスティアのみ対応
✗バックエンドグループは、すべてインスタンスグループか、すべてゾーン NEG (GCE_VM_IP) のいずれかで統一が必要

🤔 考慮すべき点

⚠️LB ごとに 2 つの外部 IP (AG0 / AG1) が提供されるため、クライアント側で両方の IP に接続できる構成が必要 (一方に接続できない場合にもう一方へ切り替え)
⚠️リージョン間フェイルオーバー/スピルオーバーを活かすには、2 つ以上のリージョンにバックエンドを構成する必要がある
⚠️gcloud での構成には beta コンポーネントを使用する

🎯 ユースケース

📈 1. グローバル配信のリアルタイムビディング (アドテック) 基盤

シナリオ: 広告取引所からの入札リクエストを世界各地から受け付ける RTB システムでは、応答レイテンシが収益に直結。従来はリージョンごとに NLB を構築し DNS で振り分けていた。

効果: 単一のエニーキャスト IP で最寄りリージョンへ直接ルーティングされ超低レイテンシを実現。リージョン障害時も DNS の切り替えを待たずに自動フェイルオーバーできる。

🔒 2. Security Service Edge (SSE) / VPN ゲートウェイのグローバル提供

シナリオ: SSE ベンダーやセキュリティゲートウェイ事業者が、ESP や GRE などのトンネリングプロトコルを世界中の拠点から受け付ける必要がある。プロキシ型 LB ではこれらを扱えない。

効果: TCP/UDP に加えて ESP、GRE、ICMP、ICMPv6 をグローバルにパススルー分散でき、クライアント送信元 IP も保持されるため、セキュリティ製品の要件を満たしながらマルチリージョンで高可用な受け口を構築できる。

🎮 3. ライブストリーミング / オンラインゲームの UDP トラフィック分散

シナリオ: UDP ベースのリアルタイムトラフィックを最寄りリージョンで処理してレイテンシを最小化したい。特定リージョンへのトラフィック集中時の容量対策も必要。

効果: エニーキャストによる最寄りリージョンへのルーティングに加え、容量超過時には既存接続を維持したまま新規接続を近隣リージョンへスピルオーバーするため、ピーク時も安定したサービス品質を維持できる。

🔗 関連サービス・機能

⚖️ リージョン外部パススルー Network Load Balancer

本機能のリージョナル版。単一リージョンのバックエンドへの分散で、Standard ティアや、ウェイト付きロードバランシング・トラフィックステアリングなどの機能を提供。

🔄 内部パススルー Network Load Balancer

VPC ネットワーク内部のトラフィックを分散するパススルー型ロードバランサー。

🌐 Cloud DNS

従来のマルチリージョン L4 構成で使われていた DNS ベースのルーティング。本機能によりエニーキャスト IP での代替が可能に。

🖥️ Compute Engine (MIG / ゾーン NEG)

バックエンドとして使用するインスタンスグループおよびネットワークエンドポイントグループ。

📝 まとめ

外部パススルー NLB にグローバル版が登場し、これまでリージョン単位でしか構成できなかった L4 パススルー型の外部負荷分散を、 単一のエニーキャスト IP でマルチリージョンに展開できるようになりました。 SSE、アドテック、RTC、ゲームなどグローバルな低レイテンシ L4 サービスを運用している場合は、 Preview 段階の制約 (GKE 非対応、対応リージョン限定) を確認のうえ、検証環境での評価を推奨します。
