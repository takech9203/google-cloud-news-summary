🛡️ Google Cloud Armor
エッジセキュリティポリシーが ASN・NTI・HTTP フィルタリングをサポート

Google Cloud Armor Cloud CDN Preview 📅 リリース日: 2026-11-16

📋 概要

Cloud CDN のエッジキャッシュサービス向けのグローバルスコープ エッジセキュリティポリシー (CLOUD_ARMOR_EDGE) で、 ASN ベースのフィルタリング、Network Threat Intelligence (NTI)、 HTTP フィルタリング (Layer 7 属性) が Preview で利用可能になりました。

エッジセキュリティポリシーは Google ネットワークの最外周 (Cloud CDN キャッシュよりも上流) で適用されるため、 キャッシュからコンテンツが配信される前にリクエストのフィルタリングとアクセス制御を実施できます。 ネットワーク事業者単位 (ASN)、Google の脅威インテリジェンス、HTTP リクエスト属性 (ヘッダー、メソッド、パス、クエリ、スキーム) に基づくきめ細かい制御が、キャッシュ配信の手前で可能になります。

🎯 対象ユーザー: Cloud CDN でコンテンツを配信している事業者、特に地域・ネットワーク単位のアクセス制御、悪意のある送信元 (Tor 出口ノード、既知の悪性 IP など) のブロック、User-Agent やパスベースのフィルタリングをキャッシュ層の手前で行いたいユーザー。

😣 Before (アップデート前の課題)

  • エッジセキュリティポリシーのフィルタリング条件は限定的で、ASN・脅威インテリジェンス・HTTP 属性による高度なフィルタリングはバックエンドセキュリティポリシーでしか利用できなかった
  • バックエンドセキュリティポリシーはキャッシュミス時のみ適用されるため、キャッシュヒットしたコンテンツは高度な条件を適用できないまま配信される可能性があった
  • 特定の ASN や既知の悪性送信元をエッジでブロックするには、IP アドレスリストを手動管理する必要があった

😊 After (アップデート後の改善)

  • origin.asn による ASN ベースのフィルタリングで、ネットワーク事業者単位でキャッシュコンテンツへのアクセスを許可・拒否できる
  • NTI により Tor 出口ノード、既知の悪性 IP、低評価 VPN、匿名プロキシなどのカテゴリ制御をキャッシュ配信前のエッジで適用できる
  • HTTP フィルタリング (request.headers / method / path / query / scheme) による Layer 7 カスタムルールをエッジで評価できる

エッジセキュリティポリシーは Cloud CDN キャッシュの上流 (Google ネットワークの最外周) で適用され、キャッシュヒット・ミスを問わずすべてのリクエストを評価します。 今回のアップデートで ASN・NTI・HTTP 属性による評価がこのエッジ層で可能になりました。バックエンドセキュリティポリシーは、エッジポリシーを通過したキャッシュミスのリクエストに対してのみ適用されます。

⚡ 主要機能

1️⃣ ASN (Autonomous System Number) フィルタリング

✓クライアント IP アドレスに関連付けられた ASN (IP プレフィックスを管理するネットワーク事業者に基づく) でトラフィックを許可・拒否
✓カスタムルール言語の origin.asn 属性を使用 (例: origin.asn == 123)
✓特定のキャリア・ISP・クラウド事業者経由のアクセス制御を、IP リストの手動管理なしで実現

2️⃣ Network Threat Intelligence (NTI)

✓Google の脅威インテリジェンスデータに基づき、脅威カテゴリ単位でトラフィックを許可・ブロック
✓対応カテゴリ: Tor 出口ノード、既知の悪性 IP、検索エンジン (許可リスト用)、低評価 VPN プロバイダ、匿名プロキシ、クリプトマイナー、パブリッククラウド IP 範囲
✓evaluateThreatIntelligence マッチ式とフィード名で指定。利用には Cloud Armor Enterprise への加入が必要

3️⃣ HTTP フィルタリング (Layer 7 属性のカスタムルール)

✓HTTP リクエスト属性に基づくカスタム CEL ルールをエッジで評価
✓利用可能な属性: request.headers、request.method、request.path、request.query、request.scheme
✓特定 User-Agent の拒否や特定パスへのアクセス制限を、キャッシュ配信前に適用

🔎 エッジセキュリティポリシーの特性

✓Cloud CDN が有効なバックエンドサービス、および Cloud Storage バックエンドバケット (グローバル外部 / クラシック Application Load Balancer 配下) に適用可能
✓バックエンドセキュリティポリシーと同時に適用可能 (2 層防御)。バックエンドバケットに適用できるのはエッジセキュリティポリシーのみ
✓Identity-Aware Proxy (IAP) よりも先に評価・適用される

💡 補足: エッジセキュリティポリシーは上記属性のみに基づくフィルタリングをサポートします (WAF 事前構成ルール、ボット管理、レート制限などはバックエンドセキュリティポリシーの機能です)。

ルール例 (カスタムルール言語)

CEL カスタムルール言語の例 
# 特定の ASN からのトラフィックにマッチ (拒否ルールで使用)
origin.asn == 123

# 特定 ASN 以外のすべてにマッチ (特定事業者のみ許可したい場合)
origin.asn != 123

# IP 範囲 + User-Agent ヘッダーの組み合わせ
inIpRange(origin.ip, '1.2.3.4/32') && request.headers['user-agent'].contains('WordPress')

# パスベースのフィルタリング
request.path.matches('/example_path/')

🛠️ 設定方法

📌 前提条件

✓グローバル外部 Application Load Balancer またはクラシック Application Load Balancer で Cloud CDN を有効化していること
✓NTI を使用する場合は、Cloud Armor Enterprise に加入していること
✓セキュリティポリシーを作成・管理できる IAM 権限があること
1
エッジセキュリティポリシーを作成する (タイプ: CLOUD_ARMOR_EDGE)
Bash エッジセキュリティポリシーの作成 
gcloud compute security-policies create my-edge-policy \
    --type CLOUD_ARMOR_EDGE \
    --description "edge policy with ASN/NTI/HTTP filtering"
2
ASN / HTTP フィルタリングルールを追加する
Bash ASN / HTTP ルールの追加 
# 特定の ASN からのリクエストを拒否するルール
gcloud compute security-policies rules create 1000 \
    --security-policy my-edge-policy \
    --expression "origin.asn == 64512" \
    --action deny-403 \
    --description "block traffic from ASN 64512"

# HTTP 属性 (User-Agent) に基づくルール
gcloud compute security-policies rules create 1100 \
    --security-policy my-edge-policy \
    --expression "request.headers['user-agent'].contains('BadBot')" \
    --action deny-403 \
    --description "block requests with BadBot user-agent"
3
Network Threat Intelligence ルールを追加する (Cloud Armor Enterprise)
Bash NTI ルールの追加 
# Tor 出口ノードからのトラフィックを拒否するルール
gcloud compute security-policies rules create 1200 \
    --security-policy my-edge-policy \
    --expression "evaluateThreatIntelligence('iplist-tor-exit-nodes')" \
    --action deny-403 \
    --description "block Tor exit nodes"
4
Cloud CDN が有効なバックエンドサービス / バックエンドバケットにアタッチする
Bash ポリシーのアタッチ 
# バックエンドサービスへのアタッチ
gcloud compute backend-services update my-cdn-backend-service \
    --edge-security-policy my-edge-policy \
    --global

# バックエンドバケットへのアタッチ
gcloud compute backend-buckets update my-backend-bucket \
    --edge-security-policy my-edge-policy
💡 推奨: まずは --preview フラグ付きでルールを作成し、ログで影響範囲を確認してから本番適用することが推奨されます。

✨ メリット

💼 ビジネス面

✓コンテンツ保護の強化: ライセンス制約のあるコンテンツ配信で、地域だけでなくネットワーク事業者 (ASN) 単位でもアクセスを制御でき、配信ポリシー要件に柔軟に対応
✓キャッシュコンテンツの不正取得対策: Tor 出口ノードや既知の悪性 IP からのアクセスをキャッシュ配信前にブロックし、スクレイピング・不正ダウンロードのリスクを低減
✓運用負荷の削減: Google が維持する脅威インテリジェンスデータを利用でき、悪性 IP リストや事業者の IP レンジの手動管理が不要に

⚙️ 技術面

✓エッジでの早期ブロック: Google ネットワークの最外周でリクエストを拒否するため、不要なトラフィックがキャッシュやバックエンドに到達せず、リソース消費を抑制
✓キャッシュヒットにも適用: バックエンドセキュリティポリシーと異なり、キャッシュヒットするリクエストにも ASN / NTI / HTTP 条件を適用可能
✓2 層防御: エッジ + バックエンドセキュリティポリシーを同一バックエンドサービスに同時適用し、多層防御を構成

⚠️ デメリット・制約事項

制限事項

✗本機能は Preview のため SLA の対象外。本番環境での利用は慎重に判断が必要
✗NTI (Google Threat Intelligence) の利用には Cloud Armor Enterprise への加入が必要
✗利用できる属性は origin.asn / origin.ip / origin.region_code / request.* (headers, method, path, query, scheme) に限定 (WAF 事前構成ルール、ボディフィルタリング、ボット管理などは利用不可)

考慮すべき点

⚠️ 注意:
  • ASN は IP プレフィックスを管理するネットワーク事業者に基づいて決定されるため、CGNAT や大規模 ISP の ASN をブロックすると正規ユーザーも巻き込む可能性がある。まずはプレビューモード (--preview) で影響を確認することが望ましい
  • エッジセキュリティポリシーは IAP よりも先に評価されるため、エッジでブロックされたリクエストには IAP のサインインページも表示されない
  • バックエンドセキュリティポリシーはエッジポリシーを通過したキャッシュミスのリクエストにのみ適用される評価順序を理解した上でルールを設計する必要がある

🎯 ユースケース

📡 ユースケース 1: 特定ネットワーク事業者経由のキャッシュコンテンツアクセス制御

シナリオ: Cloud CDN で動画・画像コンテンツを配信しており、契約上、特定のネットワーク事業者 (ISP) 経由のアクセスのみに配信を限定したい。従来は事業者の IP レンジリストを手動管理していたが、更新漏れが頻発していた。

Bash 特定 ASN のみ許可するルール 
gcloud compute security-policies rules create 1000 \
    --security-policy my-edge-policy \
    --expression "origin.asn != 64500" \
    --action deny-403 \
    --description "allow only traffic from ASN 64500"

効果: IP リストの手動管理が不要になり、ネットワーク事業者単位の配信制御をエッジ (キャッシュ配信前) で確実に適用できる。

🕵️ ユースケース 2: 悪性送信元からのコンテンツスクレイピング対策

シナリオ: 公開コンテンツが Tor 経由や既知の悪性 IP から大量にスクレイピングされており、キャッシュヒットするためバックエンドセキュリティポリシーでは防げていなかった。

効果: エッジセキュリティポリシーで evaluateThreatIntelligence('iplist-tor-exit-nodes') や iplist-known-malicious-ips を使った拒否ルールを適用することで、キャッシュヒットの有無にかかわらず悪性送信元からのアクセスをエッジでブロックできる。

🧪 ユースケース 3: ステージング環境の HTTP 属性ベースの保護

シナリオ: Cloud CDN を有効にしたステージング環境のバックエンドバケットに対し、特定のカスタムヘッダーを持つリクエストのみアクセスを許可したい。バックエンドバケットにはエッジセキュリティポリシーしかアタッチできない。

効果: HTTP フィルタリング (request.headers) を使ったエッジセキュリティポリシーで、バックエンドバケット配信のコンテンツにもヘッダーベースのアクセス制御を適用できる。
