📋 概要

API Gateway のモデルルーティング機能で、1 つのモデルルーターが参照する Google API バックエンドを 異なるホスト・異なるプロジェクトに配置できるようになりました。 グローバルエンドポイント (aiplatform.googleapis.com)、リージョナルエンドポイント (us-central1-aiplatform.googleapis.com)、.vertexai.goog エンドポイントを 1 つのルーター内で混在可能です。

あわせてセキュリティ要件が強化され、ルーターが参照するすべてのバックエンドで https スキームが必須となりました (http バックエンドを含む API 構成の作成は失敗。デプロイ済みゲートウェイは影響なし)。

複数の基盤モデル (Gemini、Claude、OpenAI 互換モデルなど) へのルーティングレイヤーとして API Gateway を利用し、モデルごとに最適なリージョンやプロジェクトを使い分けたい組織にとって重要な改善です。

❌ Before: アップデート前の課題

  • 1 つのルーターが参照するすべてのバックエンドが単一のホスト名を共有する必要があった
  • グローバルとリージョナルのエンドポイントを 1 つのルーターで混在できなかった
  • 異なるプロジェクトのモデルエンドポイントを 1 つのルーターから参照できなかった

✅ After: アップデート後の改善

  • グローバル / リージョナル / .vertexai.goog の異なるホストを 1 つのルーターから参照可能
  • 異なるプロジェクトのモデルバックエンドを 1 つのルーターで参照可能
  • https 必須化でプロンプトペイロードと認証情報の転送時の保護を強化

クライアントのリクエストペイロード内の model 属性に基づき、モデルルーターが異なるホスト・異なるプロジェクトの Google API バックエンド (すべて https 必須) にルーティングします。認証は単一の OAuth 2.0 アクセストークンで行われ、任意の Google API ホストで有効です。

⚡ 主要機能

1️⃣ マルチホストバックエンドのサポート

→グローバル (aiplatform.googleapis.com)、リージョナル (例: us-central1-aiplatform.googleapis.com)、.vertexai.goog など異なるホストのバックエンドを 1 つのルーターに配置可能
→すべてのバックエンド (defaultModel.backend および各ルールの backend) に対し、任意の Google API ホストで有効な単一の OAuth 2.0 アクセストークンで認証

2️⃣ クロスプロジェクトバックエンドのサポート

→ルーターが参照するバックエンドを異なるプロジェクトに配置可能
→ゲートウェイのサービスアカウント (デフォルトの Compute Engine SA またはユーザー管理 SA) に、ターゲットモデルをホストする各プロジェクトで Agent Platform User (roles/aiplatform.user) ロールの付与が必要

3️⃣ https スキームの必須化 🔒

→ルーターが参照するすべてのバックエンドで https が必須
→http バックエンドを含む API 構成の作成は失敗する
→デプロイ済みの既存ゲートウェイには影響しない

🔧 技術仕様

バックエンドのホストとスキームに関するルール

項目詳細
サポートされるバックエンドGoogle API エンドポイントのみ (.googleapis.com または .vertexai.goog で終わるホスト名)
ホストの混在グローバル / リージョナル / .vertexai.goog エンドポイントを 1 つのルーター内で混在可能。異なるプロジェクトも可
スキームすべてのバックエンドで https が必須 (http は構成作成時に拒否)
エンドポイントの混在制限Google API エンドポイントとその他のエンドポイントを 1 つのルーター内で混在させることは不可
認証全バックエンドに対し、単一の OAuth 2.0 アクセストークンで認証 (任意の Google API ホストで有効)
pathTranslationCONSTANT_ADDRESS が必須 (APPEND_PATH_TO_ADDRESS は拒否)
targetModel<provider>/<model-id> 形式。provider は google、openai、anthropic のいずれか。構成作成 (デプロイ) 時に検証
ネットワークVPC Service Controls および Private Service Connect (PSC) エンドポイント構成は非サポート。パブリックなリージョナル / グローバルの MaaS オープンモデルエンドポイントのみ

構成上のその他の検証ルール

✗x-google-model-router 拡張は OpenAPI 3.x 仕様でのみサポート (OpenAPI 2.0 / Swagger は非サポート)
✗x-google-model-router はオペレーションレベルでのみ指定可能で、POST メソッドにのみ適用可能
✗同一オペレーションに x-google-model-router と x-google-backend の両方は指定不可
✗1 つの OpenAPI 仕様内でモデルルーティングオペレーションと非モデルルーティングオペレーションの混在は不可
⚠️ 注意: 構成検証はドメイン許可リストを強制しないため、すべてのバックエンド address が信頼できる Agent Platform エンドポイント (例: aiplatform.googleapis.com) のみを指すことを確認する必要があります。

🛠️ 設定方法

📌 前提条件

✓API 構成とゲートウェイの作成に API Gateway Admin (roles/apigateway.admin) ロールが必要
✓ゲートウェイのサービスアカウントに、ターゲットモデルをホストする各プロジェクトで Agent Platform User (roles/aiplatform.user) ロールが必要 (他プロジェクトのバックエンドはそのプロジェクトでも付与)
✓ルーティング対象のモデルが Agent Platform Model Garden でデプロイ済みの MaaS オープンモデルであること
✓ターゲットプロジェクトと API Gateway インスタンスが VPC Service Controls 境界で制限されていないこと

ステップ 1: OpenAPI 3.x 仕様で異なるホストのバックエンドを定義

YAML マルチホスト / クロスプロジェクトのルーター定義例 
x-google-api-management:
  backends:
    gemini-global:
      address: "https://aiplatform.googleapis.com/v1/projects/PROJECT_A/\
        locations/global/publishers/google/models/gemini-3.5-flash-lite:generateContent"
      deadline: 60.0
      pathTranslation: CONSTANT_ADDRESS
    claude-regional:
      address: "https://us-central1-aiplatform.googleapis.com/v1/projects/PROJECT_B/\
        locations/us-central1/publishers/anthropic/models/claude-opus-4-7:rawPredict"
      deadline: 60.0
      pathTranslation: CONSTANT_ADDRESS
  ai:
    models:
      routing:
        routers:
          multi-host-router:
            defaultModel:
              backend: gemini-global
              targetModel: google/gemini-3.5-flash-lite
            rules:
              - model: "claude-opus-4-7"
                backend: claude-regional
                targetModel: anthropic/claude-opus-4-7

グローバルエンドポイント (プロジェクト A) とリージョナルエンドポイント (プロジェクト B) を 1 つのルーター内で参照する例です。すべてのバックエンドで https を指定します。

ステップ 2: API 構成を作成しゲートウェイにデプロイ

作成した OpenAPI 3.x 仕様から API 構成を作成し、API Gateway インスタンスにデプロイします。デプロイ完了後、ゲートウェイの URL を取得します。

Bash ゲートウェイ URL の取得 
gcloud api-gateway gateways describe GATEWAY_ID \
  --location=GATEWAY_LOCATION \
  --project=PROJECT_ID \
  --format='value(defaultHostname)'

ステップ 3: ルーティング動作をテスト

Bash model 属性によるルーティングのテスト 
curl https://GATEWAY_URL/v1/chat/multi-host \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "model": "claude-opus-4-7",
    "messages": [
      { "role": "user", "content": "Explain recursion in one sentence." }
    ]
  }'

ペイロードの model 属性がルールにマッチすると該当バックエンド (この例ではリージョナルエンドポイント) に、マッチしない場合は defaultModel のバックエンドにルーティングされます。

💡 メリット

💼 ビジネス面

✓マルチプロジェクト運用への適合: モデルのデプロイをプロジェクト単位で分離している組織でも、単一のゲートウェイ / ルーターで統合的に AI トラフィックを管理できる
✓セキュリティ強化: https の必須化により、プロンプトペイロードや認証情報が転送中に保護されることが構成レベルで保証される

⚙️ 技術面

✓グローバルとリージョナルの併用: レイテンシやデータロケーションの要件に応じて、モデルごとにグローバル / リージョナルエンドポイントを使い分けられる
✓認証の簡素化: 複数ホスト・複数プロジェクトにまたがる場合でも、ゲートウェイは単一の OAuth 2.0 アクセストークンで全バックエンドに認証できる
✓観測性の向上: Cloud Logging の backendRequest.hostname フィールドでプロキシ先の Agent Platform バックエンドのホスト名を確認できる (ホスト名を共有する場合、このフィールドだけではモデルを特定できない点に注意)

⚠️ デメリット・制約事項

🚧 制限事項

✗バックエンドは Google API エンドポイント (.googleapis.com / .vertexai.goog) のみサポート。その他のエンドポイントとの混在は不可
✗http バックエンドを使用する API 構成の作成は失敗する (新規構成に適用。デプロイ済みゲートウェイは影響なし)
✗VPC Service Controls / Private Service Connect (PSC) エンドポイント構成は非サポート
✗モデルルーティングなしでデプロイした既存ゲートウェイへのモデルルーティング追加 (およびその逆) はできず、新しい API 構成とゲートウェイの作成が必要
✗パブリックプレビュー期間中は、リクエスト単位のターゲットモデル帰属情報 (per-request attribution) は利用不可 (構造化されたルーティング決定ログは将来のリリースで追加予定)

🤔 考慮すべき点

  • クロスプロジェクト構成では、ゲートウェイのサービスアカウントにモデルをホストする各プロジェクトで roles/aiplatform.user を付与する IAM 設計が必要
  • 構成検証はドメイン許可リストを強制しないため、バックエンドの address が信頼できるエンドポイントのみを指しているかのレビューが必要
  • 既存構成で http バックエンドを使用している場合、今後の構成再作成時に失敗するため、https への移行を計画すべき

🎯 ユースケース

🌍 ユースケース 1: グローバルとリージョナルエンドポイントの併用

シナリオ: データレジデンシー要件のある Claude モデルは us-central1 のリージョナルエンドポイントで、汎用的な Gemini モデルはグローバルエンドポイントで提供したい。

実装例: 1 つのルーターに、aiplatform.googleapis.com (グローバル) をデフォルト、us-central1-aiplatform.googleapis.com (リージョナル) をルールのバックエンドとして定義する。

効果: クライアントは単一のゲートウェイ URL に対して model 属性を切り替えるだけで、要件に応じたエンドポイントへ透過的にルーティングされる。

🏢 ユースケース 2: プロジェクト分離環境での統合 AI ゲートウェイ

シナリオ: チームごとにプロジェクトを分離してモデルをデプロイしているが、社内向けには単一の AI ゲートウェイを提供したい。

効果: ゲートウェイのサービスアカウントに各プロジェクトで roles/aiplatform.user を付与することで、1 つのルーターから複数プロジェクトのモデルバックエンドを参照でき、ゲートウェイの統合管理と課金・権限のプロジェクト分離を両立できる。

✓モデルルーターが異なるホスト・異なるプロジェクトの Google API バックエンドに対応し、グローバル / リージョナルエンドポイントの使い分けやマルチプロジェクト環境での統合 AI ゲートウェイ構築が現実的に
