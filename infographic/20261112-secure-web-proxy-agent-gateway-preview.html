🛡️ Secure Web Proxy を Agent Gateway としてデプロイ

AI エージェントの流出トラフィックを自社 VPC 内の単一適用点で統制
📅 リリース日: 2026-11-12
Secure Web Proxy Preview (申請制) AI エージェント MCP ネットワークセキュリティ

📝 概要

Secure Web Proxy (SWP) を Agent Gateway としてデプロイできる機能が Preview として発表されました。 GKE や Cloud Run 上で稼働する AI エージェントからのアウトバウンドトラフィックを、自社 VPC ネットワーク内の SWP インスタンスという 単一のポリシー適用点 (Policy Enforcement Point) に集約し、LLM・MCP ツール・リモートエージェント・外部 API・一般 Web 宛先との通信を一元的に保護・統制・監視できます。

💡 2 つのデプロイモデル: Agent Gateway には Gemini Enterprise / Agent Runtime 向けの Google 管理型と、今回の SWP による自己管理型があります。 自己管理型は VPC 境界・プライベート CA・ルーティングを自社管理下に置いたまま、Agent Registry 連携・一元アクセスポリシー・コンテンツガードレールといった Gemini Enterprise Agent Platform 共通のガバナンス機能を利用したい組織に向いています。

従来からエグレス統制の実績がある SWP の deny-all デフォルト・TLS インスペクション・Cloud Logging 統合の基盤の上に、 エージェント特有のガバナンス (MCP メソッドフィルタリング、Model Armor によるペイロード検査、エージェントアイデンティティ検証) が追加されます。

😣 Before: アップデート前の課題

  • SWP のポリシーは Web トラフィック統制が中心で、MCP の tools/list / tools/call などエージェント特有のプロトコル操作を識別・フィルタリングできなかった
  • プロンプトインジェクション対策や機密データ漏えい検査は、エージェントのコード内で Model Armor API を個別に呼び出すなどワークロードごとに実装が必要だった
  • Agent Platform のガバナンスを適用しつつ VPC 境界やプライベート CA を自社管理下に置く自己管理型の選択肢がなかった
  • プロキシの転送ログから「どのエージェントが、どの MCP ツールを、どのメソッドで呼んだか」を読み取れず、監査・インシデント調査が困難だった

😀 After: アップデート後の改善

  • agentGateway リソースの認可ポリシーを SWP で直接適用し、MCP ツール呼び出し制限・宛先フィルタリング・コンテンツサニタイズ連携を一元実施
  • Service Extensions の拡張バインディングで Model Armor や IAP をアタッチし、エージェントコード変更なしでガードレールを適用
  • GKE・Cloud Run 複数ランタイムの流出トラフィックを VPC 内プロキシルーティング / クロス VPC PSC で単一のプロキシ境界に集約
  • Cloud Logging に agentGatewayInfo (MCP メソッド・ツール名・Agent Registry 宛先 URN) が自動記録され、エージェント視点の可観測性を獲得

GKE / Cloud Run 上のエージェントの流出トラフィックは SWP に集約され、L4 ネットワークルール → TLS インスペクション → 拡張バインディング (IAP / Model Armor) → L7 MCP 認可ルールの順に評価されたうえで、許可された宛先にのみ転送されます。

⚡ 主要機能

🏢 1. 自己管理型 Agent Gateway (顧客管理インフラ)

✓SWP ゲートウェイを自社 VPC 内で運用し、ネットワークルーティング・IP アドレッシング・プライベート CA 証明書・TLS インスペクションを自社の完全な管理下に置ける
✓agentGateway リソースの selfManaged.resourceUris に既存の SWP を関連付けるだけで、Agent Platform 共通のガバナンス (一元アクセスポリシー、Agent Registry 連携、コンテンツガードレール) を利用可能
✓Google 管理型と共通のガバナンスソリューションを GKE / Cloud Run の自己ホスト型エージェントにも拡張

🧱 2. 2 層のポリシーアーキテクチャによる AI ポリシーの一元適用

→拡張バインディング (主要なガバナンス機構): ExtensionBinding で Model Armor (プロンプトインジェクション・ジェイルブレイク・機密データ漏えいのディープペイロード検査) や IAP (呼び出し元 ID の暗号学的検証) をゲートウェイに直接アタッチ。カスタム / サードパーティ製プロセッサも ProducerExtension + PSC サービスアタッチメント経由でバインド可能
→認可ポリシー (きめ細かな制御と例外): L4 ルールで信頼済み外部モデルエンドポイントの TLS インスペクションをバイパスし、L7 HTTP ルールで MCP メソッド (tools/list、tools/call) やツール名・引数レベルの許可 / 拒否を適用
⚠️ 注意: Agent Gateway 利用時に評価されるのは agentGateway リソースにアタッチしたポリシーのみ。配下の Gateway リソースに直接アタッチしたポリシーは無視されます。

🔀 3. マルチランタイム対応の流出トラフィック集約

✓GKE や Cloud Run など異なるランタイムのアウトバウンドトラフィックを単一のプロキシ境界に集約
✓同一 VPC 内は VPC 内プロキシルーティング、別 VPC・クロスプロジェクトはクロス VPC の PSC サービスアタッチメントで SWP に接続
✓Cloud Run は Ambient Networking サイドカー + Direct VPC egress + EgressRouting、GKE は ambient ネットワーキングによるサイドカーレスのリダイレクトで SWP に誘導

📊 4. エージェント認識型の可観測性

✓Cloud Logging のトランザクションログに agentGatewayInfo としてエージェント実行メタデータを自動記録
✓MCP メソッド・ツール名・Agent Registry 宛先の URN が含まれ、「どのエージェントがどのツールを呼んだか」を監査可能

🔬 技術仕様

⏱️ 認可ルールの評価順序

順序評価レイヤー内容
1️⃣ネットワーク (L4) 認可ルールSNI マッチルールに該当するトラフィック (例: 信頼済み外部モデルエンドポイントへの直接通信) は TLS インターセプトをバイパス
2️⃣TLS インターセプトバイパスされなかったトラフィックをゲートウェイの TLS インスペクションポリシーで復号
3️⃣拡張バインディングルールIAP によるリクエストヘッダー上の呼び出し元 ID 検証、Model Armor による復号済みペイロードのプロンプト安全性・機密データ漏えい検査
4️⃣HTTP (L7) 認可ルールMCP ツール制限・メソッドフィルタリングなどの HTTP レベル認可ポリシーを評価

🧩 主要リソースと役割

リソース役割
Gateway (type: SECURE_WEB_GATEWAY)VPC 内で動作するプロキシ本体。プロキシ専用サブネット・証明書・ServerTlsPolicy・GatewaySecurityPolicy を参照
agentGateway論理的な Agent Gateway。selfManaged.resourceUris で SWP を参照し、registries で Agent Registry と連携 (任意)
AuthzPolicyagentGateway をターゲットに L4 / L7 (MCP メソッド・ツール) ルールを定義
ExtensionBindingagentGateway に IAP / Model Armor / カスタムプロセッサをアタッチ。failOpen で障害時の挙動 (遮断 / 素通し) を制御
EgressRoutingCloud Run などのワークロードの流出トラフィックを SWP ゲートウェイに向けるルーティングポリシー

📜 MCP ツール制限ポリシーの例

tools/list によるツール探索と、承認済みツール (get_weather、get_location) に対する tools/call のみを許可する認可ポリシーの例です。

YAML MCP ツール制限の AuthzPolicy 
name: authz-policy-restrict-tools
target:
  resources:
  - "projects/PROJECT_ID/locations/LOCATION/agentGateways/AGENT_GATEWAY_NAME"
policyProfile: REQUEST_AUTHZ
httpRules:
- to:
    operations:
    - mcp:
        baseProtocolMethodsOption: MATCH_BASE_PROTOCOL_METHODS
        methods:
        - name: "tools/list"
        - name: "tools/call"
          params:
          - exact: "get_weather"
          - exact: "get_location"
  action: ALLOW

⚙️ 設定方法

✅ 前提条件

✓Preview 申請: 申請制の Preview のため、Google Cloud Agent Governance Preview のサインアップフォームからアクセスをリクエスト
✓API の有効化: networkservices、networksecurity、privateca、certificatemanager、serviceextensions、agentregistry、compute の各 API
✓IAM ロール: roles/compute.networkAdmin、roles/networksecurity.admin、roles/privateca.admin
✓VPC に REGIONAL_MANAGED_PROXY 目的のプロキシ専用サブネットを用意し、Certificate Manager にリージョナル SSL/TLS 証明書を登録
✓TLS インスペクション用の TlsInspectionPolicy (CA Service のプライベート CA 利用)、それを参照する GatewaySecurityPolicy、フロントエンド mTLS 用の ServerTlsPolicy を作成
1

SWP ゲートウェイを作成する

BashSWP ゲートウェイのデプロイ
# swp.yaml (抜粋): type: SECURE_WEB_GATEWAY、プロキシ専用サブネット、
# 証明書、serverTlsPolicy、gatewaySecurityPolicy を指定
gcloud network-services gateways import SECURE_WEB_PROXY_NAME \
  --source=swp.yaml \
  --location=REGION \
  --project=PROJECT_ID

明示的ルーティングモードの SWP ゲートウェイをデプロイします。作成後に addresses / ports フィールドは変更できない点に注意してください。

2

SWP を agentGateway リソースに関連付ける

BashagentGateway の作成
# agent-gateway.yaml:
#   selfManaged.resourceUris に SWP ゲートウェイを指定
#   registries に Agent Registry を指定 (任意)
gcloud beta network-services agent-gateways import AGENT_GATEWAY_NAME \
  --source=agent-gateway.yaml \
  --location=REGION \
  --project=PROJECT_ID

registries フィールドを指定すると Agent Registry による宛先・ツール解決と連携できます。

3

拡張バインディングと認可ポリシーを構成する

BashModel Armor 連携と MCP ツール制限
# Model Armor 拡張バインディング (プロンプト / レスポンスのサニタイズ)
gcloud beta service-extensions extension-bindings import ext-binding-model-armor \
  --source=ext-binding-model-armor.yaml \
  --location=REGION

# MCP ツール制限の認可ポリシー
gcloud network-security authz-policies import authz-policy-restrict-tools \
  --source=authz-policy-mcp.yaml \
  --location=LOCATION

IAP / Model Armor の拡張バインディングと MCP メソッド制限ポリシーは、SWP の Gateway リソースではなく agentGateway リソースをターゲットに構成します。

4

エージェントランタイムの流出トラフィックを SWP に向ける

BashCloud Run の EgressRouting 例
# Cloud Run の例: EgressRouting でサービスの流出トラフィックを SWP に誘導
gcloud alpha network-services egress-routings create my-run-egress-routing \
  --location=REGION \
  --project=PROJECT_ID \
  --gateway="//networkservices.googleapis.com/projects/PROJECT_ID/locations/REGION/gateways/SWP_NAME" \
  --sources="workloadUri=//run.googleapis.com/projects/PROJECT_ID/locations/REGION/services/SERVICE_NAME"

workloadUri にプロジェクトを指定すれば、プロジェクト内の全 Cloud Run サービスを単一ポリシーでルーティングすることも可能です。エージェントがゲートウェイをバイパスしないよう、サブネットの egress を SWP 宛てのみに制限する VPC ファイアウォールルールの構成が推奨されています。

👍 メリット

💼 ビジネス面

  • AI ガバナンスとコンプライアンスの一元化: 外部通信を単一の検査点に集約し、データプライバシー準拠・機密データ漏えい防止・プロンプトインジェクション対策を組織横断で統一適用
  • 主権・統制要件への適合: ネットワーク境界・プライベート CA・ルーティングを自社管理下に置けるため、厳格なネットワーク統制要件を持つ組織でも Agent Platform のガバナンスを採用可能
  • 監査性の向上: agentGatewayInfo により「どのエージェントがどの MCP ツールをいつ呼び出したか」を Cloud Logging で追跡でき、インシデント調査やコンプライアンスレポートが容易に

🔧 技術面

  • アプリケーション非侵襲のガードレール: Model Armor / IAP の適用やツール許可リストの変更がゲートウェイ側のポリシー変更だけで完結し、エージェントコードの修正・再デプロイ不要
  • deny-all からの段階的許可: SWP のデフォルト拒否の上に SNI バイパス・MCP メソッド・ツール引数の複数レイヤーで段階的に許可を定義し、最小権限のエグレス統制を実現
  • マルチランタイム・マルチ VPC 対応: GKE / Cloud Run / クロスプロジェクト環境のエージェントを PSC サービスアタッチメントや Shared VPC を介して単一のプロキシ境界に集約

⚠️ デメリット・制約事項

🚧 制限事項

✗申請制の Preview であり、Pre-GA Offerings Terms が適用される (SLA なし、サポート限定)
✗SWP ゲートウェイの addresses / ports は作成後に変更不可。serverTlsPolicy / certificateUrls の変更は EgressRouting を使うワークロードに自動伝播しないため、無停止変更には新ゲートウェイを作成して参照を切り替える手順が必要
✗SWP 共通の制限として、IPv4 のみ対応 (IPv6 非対応)、HTTP/3 非対応、デプロイはホストプロジェクトのみ (サービスプロジェクト不可)
✗agentGateway 利用時は配下の Gateway リソースに直接アタッチしたポリシーが無視されるため、既存の SWP ポリシー資産をそのまま流用できない

🤔 考慮すべき点

→エージェント専用ゲートウェイ推奨: 非エージェントワークロード用プロキシとの共用は、拡張バインディングや MCP フィルタなどエージェント固有ガードレールの分離性を損なう
→failOpen は重要な設計判断: false は拡張サービス到達不能時にトラフィックを遮断 (安全側)、true は未検査で素通し
→TLS インスペクションにはプライベート CA (Certificate Authority Service) の運用と、エージェント側でのルート CA 証明書の信頼設定が必要
→自己管理型のため、ポリシー設計・証明書ライフサイクル・サブネット設計などの運用責任は利用者側にある (ゼロメンテナンスを望む場合は Google 管理型 Agent Gateway を検討)

🎯 ユースケース

📋 ユースケース 1: MCP ツールの許可リスト運用

シナリオ: GKE 上のカスタマーサポートエージェントが外部 MCP ツールサーバーを利用するが、セキュリティチームは承認済みツール以外の呼び出しを組織として禁止したい。

YAML承認済みツールのみ許可する httpRules
httpRules:
- to:
    operations:
    - mcp:
        baseProtocolMethodsOption: MATCH_BASE_PROTOCOL_METHODS
        methods:
        - name: "tools/list"
        - name: "tools/call"
          params:
          - exact: "search_kb"
          - exact: "create_ticket"
  action: ALLOW

効果: プロンプトインジェクションなどで想定外のツールを呼び出そうとしても、ゲートウェイが tools/call の引数レベルで遮断。許可ツールの追加はポリシー更新のみで完結し、エージェントの再デプロイは不要。

🛡️ ユースケース 2: Model Armor によるプロンプト / レスポンスの全数検査

シナリオ: Cloud Run 上の複数のエージェントが外部 LLM や MCP サーバーと通信しており、機密データの漏えいとプロンプトインジェクションをエージェント実装に依存せず組織レベルで防ぎたい。

効果: agentGateway に Model Armor の拡張バインディング (failOpen: false) をアタッチするだけで、全エージェントの復号済みリクエスト / レスポンスがゲートウェイでサニタイズされる。検査テンプレートの変更も中央で一括管理できる。

🔍 ユースケース 3: マルチランタイム環境のエグレス監査統合

シナリオ: GKE と Cloud Run に分散したエージェント群の外部 API アクセスを、単一の検査点で記録・監査したい。

効果: 各ランタイムの流出トラフィックを VPC 内ルーティング / PSC / EgressRouting で単一の SWP に集約し、agentGatewayInfo 付きトランザクションログを Cloud Logging で横断分析。シャドー AI ツールの利用検知やインシデント時のフォレンジックが容易になる。

📌 まとめ

Secure Web Proxy を Agent Gateway としてデプロイできるようになったことで、GKE / Cloud Run 上の AI エージェントの流出トラフィックに対し、 自社 VPC 内の単一の適用点で MCP ツール制限・Model Armor によるペイロード検査・エージェント ID 検証・エージェント認識型ロギングを実現できるようになりました。

エージェントの外部通信統制を「アプリケーション実装任せ」から「ネットワーク境界での組織ポリシー」へ移行できる重要なアップデートです。 AI エージェントを本番運用する組織は、Preview 申請のうえ、エージェント専用 SWP ゲートウェイ + deny-all ベースの許可リスト設計を検証することを推奨します。
