TLS ルートによる SNI ベースルーティングが GA

📅 リリース日: 2026-11-09

📝 概要

プロキシ ネットワーク ロードバランサで、TLS ルート (TLSRoute API リソース) を使った SNI (Server Name Indication) ベースのルーティングが一般提供 (GA) になりました。 クライアントが TLS ハンドシェイクの ClientHello で送信する SNI ホスト名を検査し、ホスト名に応じて異なるバックエンド サービスへ TLS トラフィックを振り分けられます。

🔐 最大の特徴は TLS パススルー: ロードバランサは TLS を終端 (復号) せず、暗号化されたバイトストリームをそのままバックエンドへプロキシします。 証明書と秘密鍵はバックエンド側に保持したまま、クライアントからバックエンドまでエンドツーエンドの暗号化を維持。 単一の IP アドレスとポートで複数の TLS アプリケーションを収容しつつ、ゼロトラスト要件や mTLS にも対応できます。

🔄 Before / After

❌ アップデート前の課題

  • プロキシ NLB (ターゲット TCP プロキシ) は単一のデフォルト バックエンドにしか転送できず、ホスト名振り分けには ALB (L7、TLS 終端が必要) か、サービスごとの個別 IP/転送ルールが必要
  • L7 でホスト名ルーティングすると TLS をロードバランサで終端するため、証明書・秘密鍵をロードバランサ側に配置する必要があり、E2E 暗号化やバックエンド mTLS と両立しにくい
  • 複数の TLS アプリ公開にはアプリごとに外部 IPv4 アドレスを消費

✅ アップデート後の改善

  • TLSRoute で SNI ホスト名とバックエンドのマッピングを宣言的に定義し、L4 のままホスト名ベース振り分けが可能に
  • TLS パススルーにより、ロードバランサが秘密鍵や平文に一切アクセスせず、証明書をバックエンドに置いたまま E2E 暗号化を維持
  • 単一のアドレスとポートで複数アプリを収容し、IPv4 消費を削減
  • プラットフォーム管理者がコア インフラを、各サービス オーナーがルートとバックエンドを独立管理できる運用分担

⚡ 主要機能

1️⃣ SNI ホスト名ベースのルーティング

TLS ハンドシェイク時の SNI ホスト名 (ClientHello 内では非暗号化) を検査し、TLS ルート定義と照合してバックエンド サービスを選択。 完全一致とワイルドカード (例: *.example.com) の両方をサポート。

🧭 最長サフィックス一致: サブドメイン数が最も多いものを優先。 baz.bar.foo.com へのアクセスは *.foo.com より *.bar.foo.com、さらに baz.bar.foo.com の完全一致が優先。

2️⃣ TLS パススルー

一致したバックエンドへ、暗号化されたバイトストリームを TLS 接続を終端せずにそのままプロキシ。 ロードバランサは秘密鍵を保持せず平文データにアクセスしない。TLS 終端・証明書検証・復号はバックエンド アプリケーションが担当し、 mTLS (相互 TLS) をバックエンドで直接実施可能。

3️⃣ 厳格なフェイルクローズ動作

クライアントが TLS を使用しない、SNI を送信しない、SNI が有効な DNS 名でない、どの TLS ルートにも一致しない場合、 ロードバランサは接続をクローズします。

4️⃣ TLSRoute API リソースによる宣言的管理

gcloud network-services tls-routes コマンド群で TLS ルートを作成し、ターゲット TCP プロキシにアタッチ。 1 つの TLS ルートから 1 つ以上のバックエンド サービスを参照可能。 ルーティング構成サイズは専用のクォータ単位で管理され、describe コマンドで使用量を確認できます。

📄 TLSRoute リソースの定義例 (Compute Engine バックエンド)

YAML tls_route.yaml 
name: helloworld-tls-route
gateways:
  - projects/PROJECT_NUMBER/locations/global/gateways/gateway443
rules:
  - matches:
      - sniHost:
          - example.com
        alpn:
          - h2
    action:
      destinations:
        - serviceName: projects/PROJECT_NUMBER/locations/global/backendServices/https-helloworld-service

🛠️ 設定方法

✅ 前提条件

✓リージョン外部プロキシ NLB の基本構成 (VPC ネットワーク、プロキシ専用サブネット、転送ルール、ターゲット TCP プロキシ) が作成済み
✓バックエンド (MIG など) が TLS を終端する HTTPS/TLS サービスを公開し、ヘルスチェック (35.191.0.0/16) とプロキシからの通信を許可するファイアウォール ルールが設定済み

1TLS ルートの定義ファイルを作成

Bash SNI ホスト名とバックエンドのマッピングを定義 
cat > tls_route.yaml <<EOF
name: my-tls-route
rules:
  - matches:
      - sniHost:
          - app1.example.com
    action:
      destinations:
        - serviceName: projects/PROJECT_NUMBER/locations/REGION/backendServices/app1-backend-service
EOF

SNI ホスト名 (完全一致またはワイルドカード) とバックエンド サービスのマッピングを定義します。

2TLS ルートをインポートしてターゲット プロキシに関連付け

Bash gcloud network-services tls-routes 
gcloud network-services tls-routes import my-tls-route \
    --source=tls_route.yaml \
    --location=REGION
⚠️ 注意: ターゲット プロキシが TLS ルートを参照している場合、デフォルト バックエンド サービスは併用できません。

3ルーティングの検証

Bash SNI 一致/不一致の動作確認 
# SNI が一致する場合: バックエンドから応答が返る
curl https://app1.example.com --resolve app1.example.com:443:LB_IP_ADDRESS -k

# SNI が一致しない場合: 接続がリセットされる (フェイルクローズ)
curl https://unknown.example.com --resolve unknown.example.com:443:LB_IP_ADDRESS -k

openssl s_client -servername でサーバー証明書を確認すると、SNI だけでバックエンドが切り替わる (= ロードバランサが TLS を終端していない) ことを検証できます。

💡 メリット

💼 ビジネス面

  • IPv4 アドレスコストの削減: 単一の IP アドレスとポートで複数の TLS アプリを収容し、希少な外部 IPv4 の消費を削減
  • コンプライアンス対応: クライアントからバックエンドまで暗号化されたまま転送され、ゼロトラストや規制業界の E2E 暗号化要件を満たしやすい
  • 運用の分業: プラットフォーム管理者がコア インフラを、各サービス オーナーが自サービスのルートとバックエンドを独立管理

⚙️ 技術面

  • 秘密鍵の集中管理が不要: 証明書と秘密鍵をバックエンドに保持したまま運用でき、ロードバランサに鍵を渡す必要がない。バックエンドでの mTLS 検証も可能
  • 非 HTTP プロトコル対応: MongoDB のようなステートフルな非 HTTP アプリでも、SNI に基づく特定シャードへのルーティングが可能
  • 宣言的な構成管理: TLSRoute として gcloud / GKE Gateway API で管理でき、IaC に組み込みやすい

⚠️ デメリット・制約事項

🚫 制限事項

✗TLS ルートはリージョン外部プロキシ NLB で利用可能。クラシック プロキシ NLB とグローバル外部プロキシ NLB は非対応
✗ターゲット TCP プロキシは「単一バックエンド サービス」と「TLS ルート」を同時に構成できない
✗SNI ホスト名は 1 ルートあたり最大 16 個、同一ターゲット プロキシ全体で最大 1,000 個 (いずれも引き上げ不可)
✗非 TLS トラフィック、SNI なし、無効な DNS 名、不一致の SNI はすべて接続クローズ (フォールバック先を設定できない)

🤔 考慮すべき点

🔗 HTTP コネクション コアレッシング: ブラウザは RFC 7540 に従い、ワイルドカード証明書 (*.example.com) を提示したサーバーへの接続を同一 IP の他ホスト名にも再利用します。 SNI ベースルーティングでは接続確立後に宛先バックエンドが固定されるため、*.example.com と my.example.com を別バックエンドで提供する構成では HTTP リクエストが意図しないバックエンドに流れる可能性があります。
⚠️ L4 パススルーの制約: URL パスルーティング、ヘッダー操作、Cloud CDN、URL リライトなどの L7 機能は利用不可。必要な場合は Application Load Balancer + HTTPRoute を選択。
⚠️ GKE Gateway での制約: TLSRoute のルールは 1 つまで、backendRef も 1 つのみで、重み付きトラフィック分割は非対応。 BackendTLSPolicy、IAP、Google Cloud Armor セキュリティ ポリシーは TLSRoute バックエンドにアタッチ不可。
📏 クォータ消費: TLS ルートの複雑さ (ルール数、SNI ホスト名数) と参照する転送ルール数に応じて、ルーティング構成サイズのクォータ単位を消費します。

🎯 ユースケース

🏢 ユースケース 1: 単一 IP での複数 SaaS テナント/アプリケーションの集約

シナリオ: 複数の社内アプリ (app1.example.com、app2.example.com、*.api.example.com) を 1 つの外部 IP とポート 443 で公開したい。ただしセキュリティポリシー上、TLS 終端は各アプリのバックエンドで行う必要がある。

YAML アプリごとに TLS ルートを作成し、同一ターゲット TCP プロキシにアタッチ 
rules:
  - matches:
      - sniHost:
          - app1.example.com
    action:
      destinations:
        - serviceName: .../backendServices/app1-backend

✨ 効果: IPv4 アドレス 1 つで複数アプリを収容しつつ、証明書は各バックエンドで管理。 アドレスコストと証明書配布リスクを同時に削減。

🗄️ ユースケース 2: 非 HTTP ステートフル データベースのシャード ルーティング

シナリオ: MongoDB などの TLS 上で動作する非 HTTP プロトコルのクラスタで、クライアントが接続時に指定するホスト名 (例: shard1.db.example.com) に応じて特定のシャードへ接続を振り分けたい。

✨ 効果: L7 プロキシを介せない独自プロトコルでも、SNI だけでシャード単位のルーティングを実現。 接続は暗号化されたままシャードに到達。

⚓ ユースケース 3: GKE での TLS パススルー Gateway

シナリオ: GKE 上のマイクロサービスで、Pod 内で mTLS を終端するゼロトラスト構成を採りつつ、 複数ホスト名を 1 つの Gateway IP で公開したい。

✨ 効果: Gateway API の TLSRoute リソース (tls.mode: Passthrough) を使い、 gke-l7-regional-external-managed や gke-l7-rilb クラスの Gateway で SNI ベースルーティングを宣言的に構成。 ロードバランサに証明書を渡さず E2E 暗号化を維持。

→GKE Gateway API (TLSRoute): TLS パススルー Gateway として同機能を Kubernetes ネイティブに利用可能。gke-l7-regional-external-managed などの GatewayClass が TLSRoute をサポート
