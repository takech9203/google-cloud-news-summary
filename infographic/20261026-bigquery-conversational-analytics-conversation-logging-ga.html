📊 BigQuery Conversational analytics
会話ログ記録 (Conversation logging) が GA

リリース日: 2026-10-26
BigQuery Conversational Analytics GA (一般提供) 生成 AI / データエージェント

💡 概要

データエージェントとの会話を、エージェントと同じプロジェクト内の BigQuery テーブルに自動記録できるようになりました。 回答品質のレビュー・利用状況 (アダプション) の追跡・コストモニタリングを、使い慣れた GoogleSQL でそのまま実行できます。

各ターンごとに、ユーザーの質問、エージェントの回答 (テキスト、インサイト、前提、フォローアップ質問の提案、引用元、参照したデータ結果・チャート名)、レイテンシ、モデルのトークン使用量・モデルバージョン・終了理由 (finish reason)、エージェント ID・会話 ID・ユーザー ID、ステータスとエラー詳細を記録。 ログ行は BigQuery agent analytics スキーマに従い、BigQuery Storage Write API (gRPC) 経由で書き込まれます。

🎯 対象ユーザー: Conversational analytics のデータエージェントを運用するデータプラットフォーム管理者やアナリティクスエンジニア。複数エージェントのログを 1 つのテーブルに集約し、エージェント横断での品質・コスト分析が可能になります。

❌ Before: アップデート前の課題

  • 会話内容 (質問と回答) をテーブルとして蓄積し、SQL で分析する組み込みの仕組みがなかった
  • 品質レビューや利用追跡はプロジェクトレベルの Observability 指標 (Cloud Monitoring / Cloud Trace) に頼る必要があり、個々の会話ターンの内容までは確認できなかった
  • トークン使用量をエージェント別・ユーザー別・会話別に集計してコストを把握する手段が限られていた

✅ After: アップデート後の改善

  • エージェント単位でログ記録を有効化し、各ターンのイベント行をプロジェクト内の BigQuery テーブルに自動書き込み
  • 質問・回答・レイテンシ・トークン使用量・各種 ID が構造化され、GoogleSQL / Colab ノートブック / BigQuery agent analytics Python SDK で分析可能に
  • 初回書き込み時にテーブルを自動作成 (日次パーティショニング + event_type・agent・user_id クラスタリング) — スキーマ設計が不要に

ユーザーとデータエージェントの会話は、ターンごとにプライバシーチェック (行レベル/列レベルセキュリティ・データマスキングの有無を確認) を通過した後、サービスエージェントが Storage Write API (gRPC) でエージェントのプロジェクト内のログテーブルに書き込みます。

⚙️ 主要機能

1️⃣ 会話ターンの構造化ログ記録

  • ユーザーの質問、エージェントの回答 (テキスト、インサイト、前提、フォローアップ提案、引用元、データ結果・チャートの名前) を記録
  • ターンごとのレイテンシ、モデル呼び出しごとのトークン使用量・モデルバージョン・終了理由、ステータスとエラー詳細を記録
  • データエージェント ID・会話 ID・ユーザー ID が付与されるため、1 つのテーブルで複数エージェントを横断分析可能

2️⃣ ログテーブルの自動作成と最適化されたレイアウト

  • 初回ログ記録時に、サービスエージェントが宛先データセット内にテーブルを自動作成 (既存の互換テーブルには不足カラムを追加)
  • timestamp で日次パーティショニング、event_type・agent・user_id でクラスタリング
  • スキーマ変更は追加のみ (additive)。型やモードが競合するカラムがあると書き込みが停止する

3️⃣ ターンごとのプライバシーチェック

  • 回答開始前に、会話しているユーザーの認証情報でナレッジソーステーブルのメタデータを確認
  • 行レベルセキュリティ (行アクセスポリシー)、列レベルセキュリティ (ポリシータグ)、動的データマスキング使用時は、そのターンはログに記録されない (回答自体は通常どおり返される)
  • ログ記録のエラーが会話を失敗させることはない (ベストエフォートの書き込み)

4️⃣ 記録されない情報 (設計上の制限)

  • エージェントが実行した SQL クエリは記録されない (ユーザーが明示的に SQL の表示・説明を求めた場合のみ回答テキストに含まれ得る)
  • ツール呼び出しの名前や引数は書き込み前に除去され、トークン使用量・モデルバージョン・終了理由のみ保持
  • サムズアップ/ダウンのユーザーフィードバックは記録されない

🛠️ 設定方法

✅ 前提条件

✓宛先データセットがエージェントと同じプロジェクトに存在すること (データセットは事前に作成が必要)
✓ナレッジソースとして特定の BigQuery テーブルが選択されていること (検索スコープのみのエージェントは対象外)
✓サービスエージェントがログデータセットに対して roles/bigquery.dataEditor を持つこと

📋 手順

  1. BigQuery Studio でエージェントの設定を開く
    既存エージェントを編集する場合はビューセレクタを Draft に切り替え、ナレッジソースに特定の BigQuery テーブルが選択されていることを確認します。
  2. 会話ログ記録を有効化する
    Settings セクションの Conversation logging で Enable conversation logging をオンにします。
    • Dataset ID でエージェントのプロジェクト内の既存データセットを選択
    • Table ID で既存テーブルを選択するか、+ New table で新しいテーブル名 (例: agent_events) を入力して保存
    • Data logging & user disclosure notice を確認
    • 設定のバリデーションを待つ。サービスエージェントにアクセスがない場合は Grant Access をクリックして roles/bigquery.dataEditor を付与
  3. 動作確認
    エージェントを公開 (Publish) した後、公開済みエージェントのメインチャット画面からテスト質問を送信し (Preview セクションは記録されない)、BigQuery Studio で宛先データセットを更新してログテーブルが作成されたことを確認します。
SQL ログの確認例 (timestamp フィルタを必ず付与する) 
-- ログの確認例 (timestamp フィルタを必ず付与する)
SELECT event_type, agent, user_id, timestamp
FROM `PROJECT_ID.DATASET_ID.agent_events`
WHERE timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 DAY)
ORDER BY timestamp DESC;

🚀 メリット

💼 ビジネス面

✓回答品質の継続的レビュー: 質問と回答のペアを蓄積し、エージェントの回答品質を定期的に評価・改善できる
✓アダプションとコストの可視化: ユーザー ID・エージェント ID 単位で利用状況とトークン使用量を集計し、投資対効果を把握できる
✓追加課金なし: 会話ログ記録自体に個別の料金はなく、標準の BigQuery 料金のみで利用できる

🧑‍💻 技術面

✓スキーマ設計不要: 最適化されたパーティショニング・クラスタリング付きのテーブルが自動作成される
✓会話への非侵襲性: ログ記録のエラー (権限不足、データセット不存在、クォータ枯渇) が会話リクエストを失敗させることはない
✓既存の BigQuery ガバナンスを適用可能: ログテーブル自体にポリシータグ、データマスキング、行アクセスポリシー、パーティション有効期限 (保持期間) を設定できる

⚠️ デメリット・制約事項

🚫 制限事項

✗BigQuery Studio エージェントエディタの Preview ペインでの会話、データエージェントを介さない直接会話は記録されない
✗BigQuery テーブルをナレッジソースとするエージェントのみ対応。Looker、Data Studio、AlloyDB、Spanner、Cloud SQL のデータソースは非対応。検索スコープのみのエージェントや BigQuery プロパティグラフをナレッジソースとするエージェントも対象外
✗ナレッジソースに行アクセスポリシー、列レベルセキュリティ (ポリシータグ)、データマスキングが使われている場合、そのターンは記録されない (プライバシーチェックはビューの背後のテーブルまでは確認しない)
✗生成された SQL、ツール呼び出し、ADK のツール/リクエストイベント (TOOL_STARTING など) は記録されない。検証済みクエリで直接回答したターンは LLM_RESPONSE 行を書き込まず、失敗した検証済みクエリのターンは記録されない
✗サンプリング設定はなく、対象となる全ターンが記録される (サンプリングはクエリ時に実施する)

🤔 考慮すべき点

  • 書き込みはベストエフォートで限定的なリトライのみ。失敗したターンは記録されず、リトライにより重複行が発生し得る (event_id で重複排除する)
  • ログ記録の失敗はチャット UI にも Cloud Logging にも報告されない。テーブルが空のままであることが唯一の失敗シグナル
  • プライバシーチェックとログ書き込みはレイテンシを増加させる可能性がある
  • API 経由で 1 つのサービスアカウントを多数のエンドユーザーで共有する場合、全行にそのサービスアカウントのメールアドレスが記録される
  • Google はログ行を削除しないため、保持ポリシーに合わせてパーティション有効期限 (例: 90 日) を自分で設定する必要がある
  • VPC Service Controls 使用時は geminidataanalytics.googleapis.com と bigquery.googleapis.com を同じ境界に含め、サービスエージェントからの Ingress ルールの追加が必要

🎯 ユースケース

📝 ユースケース 1: エージェントの回答品質レビュー

シナリオ: 社内に展開した複数のデータエージェントについて、ユーザーの質問に対する回答の品質を定期的にレビューし、システムインストラクションや知識ソースの改善につなげたい。

SQL エージェント別に直近 7 日間のターンをサンプリングしてレビュー 
-- エージェント別に直近 7 日間のターンをサンプリングしてレビュー
SELECT *
FROM `PROJECT_ID.DATASET_ID.agent_events`
WHERE timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
QUALIFY ROW_NUMBER() OVER (PARTITION BY agent ORDER BY RAND()) <= 20;

効果: 全エージェントのログが 1 テーブルに集約されるため、横断的な品質評価と改善サイクルを SQL だけで回せる。

💰 ユースケース 2: トークン使用量によるコストモニタリング

シナリオ: データエージェントの利用拡大に伴い、エージェント別・ユーザー別のモデルトークン使用量を把握し、コストの予測と配賦を行いたい。

効果: 各モデル呼び出しのトークン使用量・モデルバージョンが記録されるため、利用部門ごとのコスト集計やヘビーユーザーの特定が可能になる。Cloud Monitoring の Observability 指標と組み合わせれば、プロジェクト全体の傾向と個別会話の詳細の両方を追跡できる。

💲 料金

✅ 会話ログ記録に対する個別の課金はありません。 エージェントのプロジェクトに対して、標準の BigQuery 料金が適用されます。
項目料金
データ取り込みBigQuery Storage Write API (gRPC) の取り込み料金 (請求先アカウントごとに月 2 TiB の無料枠があり、Storage Write API (gRPC) の使用量全体で共有)
ストレージ標準の BigQuery ストレージ料金
分析クエリ標準の BigQuery 分析料金 (timestamp でフィルタしてスキャン量を削減)
プライバシーチェックテーブルメタデータの読み取りとドライランクエリのみで、料金は発生しない

詳細は BigQuery の料金ページ を参照してください。

🔗 関連サービス・機能

📐 BigQuery agent analytics

会話ログのスキーマ定義と、ログ分析用の Python SDK を提供。

⚡ BigQuery Storage Write API

ログ行の書き込みに使用される gRPC ベースの取り込み API。

📈 Cloud Monitoring / Cloud Trace (エージェント Observability、Preview)

プロジェクトレベルの指標 (会話数、ユーザー数、レイテンシ、トークン使用量の予測など) とトレースを提供。会話ログ記録はこれを補完するターン単位の詳細ログ。なお、エージェントはプロジェクトレベルの Observability 設定を継承しない。

🤖 Conversational Analytics API (Gemini Data Analytics)

データエージェントの基盤となる API。エージェントの変更は Admin Activity 監査ログに記録される。

🔒 Cloud KMS (CMEK) / VPC Service Controls

ログデータセットの暗号化と境界セキュリティの構成に使用。

📌 まとめ

Conversational analytics の会話ログ記録が GA となり、データエージェントの会話を BigQuery テーブルに蓄積して品質・利用状況・コストを SQL で分析する運用が正式にサポートされました。

💡 推奨アクション (本番運用チーム向け):
  • ログデータセットを分離して作成する
  • パーティション有効期限による保持ポリシーを設定する
  • エージェントごとにログ記録を有効化する
⚠️ 導入前に理解しておくこと: プライバシーチェックの仕様 (行/列レベルセキュリティ使用時はログ記録されない) と、記録されない情報 (SQL、ツール呼び出し、フィードバック)。
