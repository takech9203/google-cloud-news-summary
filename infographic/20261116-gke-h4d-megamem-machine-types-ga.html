☸️ GKE: H4D megamem マシンタイプが GA

h4d-megamem-192 / h4d-megamem-192-lssd を GKE で利用可能に
📅 リリース日: 2026-11-16
Google Kubernetes Engine Compute HPC GA (一般提供)

📝 概要

H4D マシンシリーズの h4d-megamem-192 および h4d-megamem-192-lssd が GKE で一般提供 (GA) になりました。H4D は AMD EPYC Turin (第 5 世代) プロセッサと Titanium オフロードプロセッサを搭載した HPC (High Performance Computing) 向けコンピューティング最適化マシンシリーズです。 megamem は 192 vCPU / 3,024 GB メモリという H4D 最大のメモリ構成で、 -lssd バリアントでは 12,000 GiB の Titanium SSD が付属します。

Standard クラスタのノードプールに加え、GKE 1.37.2-gke.1325000 以降では ノードプール自動作成および Autopilot の Performance コンピューティングクラスでも利用可能。 製造業シミュレーション、気象予測、EDA、ライフサイエンスなど、大容量メモリと高速ノード間通信 (Cloud RDMA 最大 200 Gbps) を必要とするマルチノード HPC ワークロードに最適です。

❌ Before: アップデート前の課題

  • GKE で使える H4D はメモリ最大 1,488 GB (highmem) まで。大規模インメモリ計算や巨大メッシュのシミュレーションに対応が困難
  • Autopilot Performance クラスの H4D メモリ上限は 1,400 GiB に制限
  • 大容量メモリ + ローカル SSD 構成は highmem-lssd の 3,750 GiB までが上限

✅ After: アップデート後の改善

  • 192 vCPU / 3,024 GB の h4d-megamem-192 を Standard クラスタのノードプールで GA 利用可能に
  • h4d-megamem-192-lssd で 12,000 GiB の Titanium SSD 搭載構成を選択可能に
  • 1.37.2-gke.1325000 以降でノードプール自動作成・Autopilot に対応し、Autopilot メモリ上限が 3,024 GiB に拡大

Standard クラスタのノードプール、ノードプール自動作成、Autopilot の Performance コンピューティングクラスの 3 つの方法で H4D megamem ノードをプロビジョニングでき、Cloud RDMA による高速ノード間通信で マルチノード HPC ワークロードを実行します。

⚡ 主要機能

1️⃣ h4d-megamem-192 / h4d-megamem-192-lssd の GA 提供

→192 vCPU (SMT 無効のため 1 vCPU = 1 物理コア) と 3,024 GB メモリを搭載した H4D シリーズ最大メモリ構成
→-lssd バリアントは 32 x 375 GiB = 12,000 GiB の Titanium SSD を搭載し、大容量スクラッチ領域を提供
→Standard クラスタでノードプールを作成して利用可能

2️⃣ ノードプール自動作成への対応 (1.37.2-gke.1325000 以降)

→ワークロードの要求に応じて megamem マシンタイプのノードプールを GKE が自動的に作成 (node auto-provisioning)
→クラスタオートスケーリングと組み合わせた柔軟なキャパシティ管理が可能

3️⃣ Autopilot Performance コンピューティングクラスへの対応 (1.37.2-gke.1325000 以降)

→cloud.google.com/compute-class: Performance と cloud.google.com/machine-family: h4d のノードセレクタで megamem ノードを利用可能
→Performance クラスにおける H4D のメモリ上限が従来の 1,400 GiB から 3,024 GiB に拡大
→Pod ごとに専有ノードを割り当てる運用モデルで、ノード管理を GKE に委譲しながら HPC 性能を確保

🛠️ 設定方法

✅ 前提条件

✓GKE API が有効化されていること、gcloud CLI が最新版であること
✓H4D VM のキャパシティを消費オプション (予約、flex-start など) に応じて確保していること。H4D には Dense リソース割り当てが推奨
✓ノードイメージは Container-Optimized OS のみサポート
✓H4D が利用可能なロケーションを使用すること (Compute Engine のリージョン・ゾーン一覧で H4D をフィルタして確認)

ステップ 1: Standard クラスタで megamem ノードプールを作成

Bash 予約済みキャパシティを利用する例 
gcloud container node-pools create h4d-megamem-pool \
    --cluster=CLUSTER_NAME \
    --location=CONTROL_PLANE_LOCATION \
    --node-locations=COMPUTE_ZONE \
    --machine-type=h4d-megamem-192 \
    --reservation-affinity=specific \
    --reservation=RESERVATION_NAME \
    --num-nodes=NODE_COUNT
💡 ヒント: Cloud RDMA を利用する場合は、Falcon VPC ネットワークプロファイルを使用した専用 VPC / サブネットの作成と、マルチネットワーキングを有効にしたクラスタ構成が必要です。

ステップ 2: Autopilot の Performance コンピューティングクラスで利用 (1.37.2-gke.1325000 以降)

YAML Performance クラス + H4D マシンファミリーを指定した Pod 
apiVersion: v1
kind: Pod
metadata:
  name: hpc-megamem-pod
spec:
  nodeSelector:
    cloud.google.com/compute-class: Performance
    cloud.google.com/machine-family: h4d
  containers:
  - name: hpc-container
    image: IMAGE
    resources:
      requests:
        cpu: "180"
        memory: "2900Gi"

Performance コンピューティングクラスと H4D マシンファミリーをノードセレクタで指定します。 Pod は専有ノードに配置され、メモリは最大 3,024 GiB (1.37.2-gke.1325000 以降) まで要求できます。

⚖️ メリットと制約事項

💼 メリット (ビジネス面)

✓大規模 HPC の Kubernetes 集約: 専用 HPC クラスタで運用していたメモリ集約型ワークロードを GKE に集約し、インフラ運用の標準化とコスト最適化を推進
✓柔軟なキャパシティ調達: オンデマンド、1 年 / 3 年 CUD、予約、flex-start からバースト的な HPC 需要に合わせて選択可能

🔬 メリット (技術面)

✓H4D 最大のメモリ容量: ノードあたり 3,024 GB で、大規模インメモリ計算や巨大モデル・メッシュを単一または少数ノードで実行可能
✓高速スクラッチストレージ: -lssd の 12,000 GiB Titanium SSD で I/O 集約的な中間データ処理を高速化
✓一貫した性能: SMT 無効・オーバーコミットなし + Cloud RDMA 最大 200 Gbps でタイトに結合されたマルチノードアプリの性能を安定化
✓運用の自動化: ノードプール自動作成や Autopilot で HPC ノードのプロビジョニング・管理を GKE に委譲

🚫 制限事項

✗H4D は事前定義されたマシンタイプのみ。カスタムマシンタイプは利用不可
✗GPU は利用不可
✗インターネットへの下り (外向き) データ転送は 1 Gbps に制限
✗マシンイメージ作成、インスタンスイメージからのディスク作成、インスタンス間のディスク共有 (マルチライター / 読み取り専用) は非対応
✗Hyperdisk Balanced の性能は 15,000 IOPS / 240 MBps に制限
✗ライブマイグレーション非対応。ホストメンテナンス時は Terminate 動作 (-lssd はローカル SSD データ保持付き)、事前通知は 7 日前
⚠️ 考慮すべき点:
  • ノードイメージは Container-Optimized OS のみサポート
  • ライブマイグレーション非対応のため、ノードの中断対応 (メンテナンス通知のハンドリングなど) を設計に組み込む必要あり
  • 性能維持のため、ワークロードには 192 CPU 全部を割り当てず、システムデーモン用の CPU 余裕を残すことを推奨 (ベストプラクティス)
  • Cloud RDMA 利用時は gVNIC に加えて IRDMA 用 vNIC と Falcon VPC ネットワークプロファイルの構成が必要
  • H4D の利用可能リージョン / ゾーンは限定されるため、事前に空き状況とキャパシティ確保方法の確認が必要

🎯 ユースケース

🌀 ユースケース 1: 大規模メモリを必要とする科学技術シミュレーション

シナリオ: 気象予測や計算流体力学 (CFD) などで、巨大なメッシュデータをメモリ上に展開して解析する。 highmem (1,488 GB) ではメモリが不足し、ノード分割によるオーバーヘッドが課題だった。

Bash CFD 用ノードプールの作成例 
gcloud container node-pools create cfd-pool \
    --cluster=hpc-cluster \
    --machine-type=h4d-megamem-192 \
    --reservation-affinity=specific \
    --reservation=h4d-reservation \
    --num-nodes=4

効果: ノードあたり 3,024 GB のメモリで分割数を削減し、Cloud RDMA (最大 200 Gbps) で 残りのノード間通信を高速化することで、シミュレーション全体の実行時間を短縮。

🔌 ユースケース 2: Autopilot での EDA ワークロード実行

シナリオ: 半導体設計の検証ジョブ (EDA) をメモリ集約型のバッチとして実行したいが、 ノードプールの管理負荷を最小化したい。

効果: Autopilot の Performance コンピューティングクラスで machine-family: h4d を 指定するだけで、ジョブごとに専有の megamem ノードが自動プロビジョニングされ、 ノード管理なしで最大 3,024 GiB のメモリを利用可能。

💰 料金

H4D インスタンスはオンデマンドのほか、1 年 / 3 年のコミットメント利用割引 (CUD) で利用できます。 GKE Standard ではノードとして使用する Compute Engine リソース (vCPU、メモリ、Titanium SSD) に対して課金され、 Autopilot の Performance コンピューティングクラスではノード単位の課金モデルが適用されます。

  • Compute Engine VM インスタンスの料金
  • GKE の料金

🌍 利用可能リージョン

H4D マシンタイプは一部のリージョン / ゾーンで利用可能です (例: us-west4-a など)。 最新の提供状況は 利用可能なリージョンとゾーン で H4D をフィルタして確認してください。

📌 まとめ

H4D megamem マシンタイプの GKE での GA により、ノードあたり 3,024 GB のメモリと 最大 12,000 GiB の Titanium SSD を備えた HPC ノードを、 Standard・ノードプール自動作成・Autopilot のいずれの運用モデルでも利用できるようになりました。

メモリ集約型の HPC ワークロードを Kubernetes に移行・集約したい場合は、 GKE 1.37.2-gke.1325000 以降へのアップグレードと、 予約や flex-start によるキャパシティ確保方法の検討から始めることを推奨します。
