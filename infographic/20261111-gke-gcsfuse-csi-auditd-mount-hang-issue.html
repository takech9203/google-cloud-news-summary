⚠️ GKE: auditd 有効ノードで Cloud Storage FUSE CSI ドライバのマウントがハング

Google Kubernetes Engine (GKE) Cloud Storage FUSE CSI ドライバ Linux auditd ロギング 既知の問題・修正対応中
リリース日
2026-11-11

📌 概要

Linux syscall 監査が有効なノード (例: auditd ロギングを有効化した Container-Optimized OS ノード) で、 Cloud Storage FUSE CSI ドライバのボリュームマウントが無期限にハングする既知の問題が公表されました。

影響を受けると、Cloud Storage FUSE ボリュームを使用する Pod が Init:0/1 や ContainerCreating のまま起動できず、 削除中の Pod は Terminating のまま残り、ノードドレイン (ノードプールアップグレード時のドレインを含む) が完了しない可能性があります。 セキュリティ監査要件で auditd を有効化し、ML ワークロードなどが Cloud Storage バケットをマウントしているクラスタは特に注意が必要です。

🔥 原因: 影響バージョンでは Cloud Storage FUSE CSI ドライバが Debian 13 ベースイメージを使用し、 その mount ユーティリティが新しい Linux mount API を使用。syscall 監査がアクティブな場合、 FUSE ファイルシステム初期化前にカーネル内でマウント操作がハングします。 gcsfusecsi-node Pod の再起動では解消しません。修正は現在対応中 (a fix is in progress) です。

❌ 影響を受ける環境

  • Linux syscall 監査ルールがロードされているノード (auditd ロギング有効の COS ノードなど)
  • Cloud Storage FUSE CSI ドライバのボリュームを使用するワークロード
  • 影響を受ける GKE バージョン (下表参照) に該当するクラスタ

✅ 影響を受けない環境

  • syscall 監査ルールがロードされていないノード
  • GKE Autopilot (auditd ロギング非サポートのため、前提構成は主に Standard クラスタの COS ノードに該当)

auditd の syscall 監査ルールがロードされたノードでは、Debian 13 ベースの mount ユーティリティが使用する新しい Linux mount API の呼び出しが、 FUSE ファイルシステム初期化前にカーネル内でハングし、Pod のボリュームマウントが完了しなくなります。

🔍 問題の詳細

🚨 症状

1️⃣ Pod が起動しない

Cloud Storage FUSE ボリュームを使用する Pod が Init:0/1 や ContainerCreating のまま進まない。Pod イベントにマウントエラーが表示される。

2️⃣ Pod の削除が完了しない

削除中の Pod が Terminating 状態のまま残る。

3️⃣ ノードドレインが停止する

ノードのドレインが完了しない可能性。ノードプールアップグレード時のドレインも含むため、クラスタのアップグレード停滞リスクがある。

4️⃣ 再起動では復旧しない

gcsfusecsi-node Pod を再起動しても問題は解消されない。

Text Pod イベントに表示されるエラー例 
MountVolume.SetUp failed for volume "VOLUME_NAME" : rpc error:
  code = DeadlineExceeded desc = context deadline exceeded

MountVolume.SetUp failed for volume "VOLUME_NAME" : rpc error:
  code = Aborted desc = An operation with the given volume key TARGET_PATH already exists

🧬 根本原因

項目詳細
直接原因影響バージョンの Cloud Storage FUSE CSI ドライバが Debian 13 ベースイメージを使用し、その mount ユーティリティが新しい Linux mount API を使用する
発生条件ノードで syscall 監査 (auditd の監査ルール) がアクティブであること
ハング箇所FUSE ファイルシステムの初期化前に、マウント操作がカーネル内でハング
影響を受けない条件syscall 監査ルールがロードされていないノード

🛠️ 回避策: auditd ロギングの無効化とノードの再作成

Cloud Storage FUSE CSI ドライバを使用するクラスタで Linux auditd ロギングを無効化し、 その後、影響を受けるノードを再作成して、ノードにロードされている監査ルールをクリアします。

auditd ロギング用 DaemonSet の削除

公式ドキュメント (Linux auditd ロギング) の手順に従い、ロギング DaemonSet と関連リソースを削除します。

Bash
kubectl delete daemonset cos-auditd-logging -n cos-auditd
kubectl delete configmap fluent-bit-config -n cos-auditd
2

auditd 無効化用 DaemonSet の適用

cos-auditd-logging-disable DaemonSet を適用し、各ノードの systemd サービスの変更を元に戻します。

Bash
kubectl apply -f 'https://raw.githubusercontent.com/GoogleCloudPlatform/k8s-node-tools/master/troubleshooting/os-audit/cos-auditd-logging-disable.yaml'
3

影響を受けるノードの再作成

ノードにロードされている監査ルールをクリアするため、影響を受けるノードを再作成します。DaemonSet の削除だけでは、ロード済みの監査ルールはクリアされません。

⚠️ auditd ロギングを維持する必要がある場合: セキュリティ要件などで auditd を有効のまま維持する必要がある場合は、Cloud カスタマーケアに問い合わせるよう案内されています。修正は現在対応中です。

🤔 考慮すべき点

⚙️ 運用面の考慮事項

📈 アップグレードの停滞リスク

ノードドレインが完了しないため、ノードプールのアップグレードが停滞する可能性。影響バージョンへのアップグレードを計画している場合は、auditd と Cloud Storage FUSE CSI ドライバの併用有無を事前に確認する。

🔐 セキュリティ要件とのトレードオフ

回避策は auditd ロギングの無効化を伴うため、OS 監査ログをセキュリティフォレンジックに利用している環境では、無効化の影響をセキュリティチームと確認する必要がある。

🔄 ノード再作成が必須

auditd の DaemonSet を削除するだけでは、既にノードにロードされた監査ルールはクリアされないため、ノードの再作成が必要。

🚧 再有効化の制約

cos-auditd-logging-disable DaemonSet をデプロイした後は、ノードを再作成しない限り auditd ロギングを再有効化できない (公式ドキュメントの記載)。

🔎 影響確認のポイント

✓対象クラスタの GKE バージョンが影響バージョンに該当するかを確認する
✓Init:0/1 / ContainerCreating で停止している Pod のイベントに DeadlineExceeded / Aborted のマウントエラーが出ていないかを確認する
✓ノードに auditd の syscall 監査ルールがロードされているかを確認する (auditd ロギング DaemonSet のデプロイ有無など)

🔗 関連サービス・機能

🪣 Cloud Storage FUSE CSI ドライバ

Cloud Storage バケットをローカルファイルシステムとして GKE Pod にマウントする機能。ML ワークロードの学習データ・モデル・チェックポイントの保存に多く利用される。

🖥️ Container-Optimized OS (COS)

GKE ノードのデフォルトノードイメージ。auditd ロギングは COS ノードの GKE Standard クラスタでのみサポートされる。

🔍 Linux auditd ロギング

ノード上の OS 監査ログ (バイナリ実行、ログイン試行、ネットワーク接続など) を収集し Cloud Logging に送信する仕組み。DaemonSet でノードごとに構成する。

📊 Cloud Logging

auditd ログの送信先。回避策の実施後、LOG_ID("linux-auditd") のログが新規生成されていないことの確認に使用できる。

💡 まとめ

⚠️ 重要な既知の問題: auditd ロギングを有効化した GKE ノードで Cloud Storage FUSE CSI ドライバを使用している場合、 Pod の起動不能・削除停滞・ノードドレインの停滞 (アップグレード停滞を含む) が発生する可能性があります。
✓まず影響バージョンへの該当有無とマウントエラーの有無を確認する
✓auditd ロギングの無効化とノード再作成による回避策の適用を検討する
✓auditd を維持する必要がある場合は Cloud カスタマーケアへ問い合わせる
✓修正は現在対応中のため、今後の Release Notes の続報を確認する
