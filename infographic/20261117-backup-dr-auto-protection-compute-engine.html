☁️ Backup and DR Service GA (一般提供)

🛡️ Compute Engine の自動保護
(Auto-protection) が GA

ラベルベースのポリシーで VM・ディスクのバックアップ適用を大規模に自動化
📅 リリース日: 2026-11-17

📝 概要

Backup and DR Service の 自動保護ポリシー (Auto-protection policies) が GA になりました。 リソースラベル (例: env=prod) に基づいて、複数プロジェクトにまたがる Compute Engine インスタンス・ディスクを自動検出し、 バックアップ プランを自動割り当てします。 新規に作成・ラベル付けされたリソースも継続的に保護対象へ追加されるため、「保護漏れ」を防ぎながらバックアップ運用をポリシーベースで統制できます。

❌ Before: アップデート前の課題

  • バックアップ プランの割り当てはリソース単位で手動。大量リソース環境では運用負荷が高い
  • 新規 VM・ディスクへの適用漏れで未保護リソースが発生するリスク
  • 複数プロジェクト横断でラベル等の属性ベースに一括管理する仕組みがない
  • Preview 提供のため Pre-GA 条件下にあり本番利用に制約

✅ After: アップデート後の改善

  • ラベル (key-value) ベースのポリシーでバックアップ プランを自動割り当て
  • ポリシー バインディングで複数ワークロード プロジェクトを一元管理
  • gcloud backup-dr auto-protection-policies が GA トラックで利用可能、SLA 対象に
  • マッチング数・保護済み数・失敗数をコンソールで可視化、監査が容易に

バックアップ ボールト プロジェクトで定義した自動保護ポリシーが、バインディングされた複数のワークロード プロジェクト内のリソースをラベルで評価し、 合致するリソースにバックアップ プランを自動割り当てしてボールトへバックアップします。

⚙️ 主要機能

🏷️ 1. ラベルベースの自動マッチング

✓リソースラベル (例: env=prod) を条件 (criteria) に指定し、合致する VM / ディスクを自動検出
✓ポリシー作成後、マッチングと保護スケジューリングは通常 2 時間以内 (最大 8 時間) に完了
✓以降に作成・ラベル付けされたリソースも継続的に評価され、自動で保護対象に追加

🌐 2. クロスプロジェクト保護 (ポリシー バインディング)

✓同一組織内の複数ワークロード プロジェクトを 1 ポリシーにバインド可能 (デフォルト最大 50 プロジェクト)
✓ワークロード側でも「適用されたポリシー」を参照でき、バックアップ管理者とワークロード管理者の責務分担が可能

📈 3. 保護状況の可視化

✓ポリシーごとに「マッチングした / 保護済み / 保護に失敗した」リソース数をコンソールで確認可能
✓gcloud CLI (binding-matching-resources list など) や API でも照会可能

🔗 4. 既存のバックアップ プラン関連付けとの統合

✓手動関連付け済みのリソースが合致した場合、同じボールトのプランなら自動保護が関連付けを引き継ぎ、必要に応じてポリシーのプランへ更新
✓異なるボールトのプランの場合は既存の関連付けを削除してポリシーのプランで置き換え (事前のサービス エージェントへの権限付与が必要)

🛠️ 設定方法

💡 前提条件: ① バックアップ ボールトとバックアップ プランが作成済み (プランはリソースと同一リージョン) ② 必要な IAM ロールが付与済み (クロスプロジェクト構成ではサービス エージェントへのオペレーター ロール付与も必要) ③ 保護対象リソースにラベルが付与済み
1保護対象リソースにラベルを付与
BashVM / ディスクへのラベル付与
# VM インスタンスにラベルを付与
gcloud compute instances add-labels INSTANCE_NAME \
  --labels=env=prod \
  --zone=ZONE

# ディスクにラベルを付与
gcloud compute disks add-labels DISK_NAME \
  --labels=env=prod \
  --zone=ZONE
2自動保護ポリシーを作成
Bashラベル条件とバックアップ プランを指定してポリシー作成
gcloud backup-dr auto-protection-policies create POLICY_NAME \
  --location=LOCATION \
  --criteria=key=env,values=prod \
  --backup-plan-details="resource-type=compute.googleapis.com/Instance,backup-plan=projects/BACKUP_VAULT_PROJECT/locations/LOCATION/backupPlans/BACKUP_PLAN" \
  --description="Production VM auto-protection"

ディスクを保護する場合は resource-type=compute.googleapis.com/Disk を指定します。

3ワークロード プロジェクトをポリシーにバインド
Bashポリシー バインディングの作成
gcloud backup-dr auto-protection-bindings create BINDING_NAME \
  --auto-protection-policy=POLICY_NAME \
  --location=LOCATION \
  --scope=projects/WORKLOAD_PROJECT_ID

作成後、ポリシーが自動的にマッチングを行い、バックアップ プランの関連付けをスケジュールします。

4保護状況を確認
Bashポリシーとマッチングリソースの照会
# ポリシーの一覧と詳細
gcloud backup-dr auto-protection-policies list --location=LOCATION
gcloud backup-dr auto-protection-policies describe POLICY_NAME --location=LOCATION

# バインディングにマッチしたリソースの一覧
gcloud backup-dr binding-matching-resources list \
  --auto-protection-policy-binding=BINDING_NAME \
  --auto-protection-policy=POLICY_NAME \
  --location=LOCATION

コンソールの「Auto-protection policies」ページでは、マッチング数・保護済み数・保護失敗数をポリシー単位で確認できます。

✨ メリット

💼 ビジネス面

✓保護漏れリスクの低減: 新規リソースもラベル付与のみで自動保護。データ損失・コンプライアンス違反のリスクを軽減
✓運用コストの削減: リソース単位の手動割り当てが不要になり、大規模環境の運用工数を削減
✓ガバナンスの一元化: ボールト プロジェクト側で集中管理し、ワークロード側は閲覧のみとする責務分離が可能

⚡ 技術面

✓ラベル駆動の宣言的管理: 既存のラベル運用 (環境区分、重要度区分など) をそのままバックアップ ポリシーに転用
✓クロスプロジェクト対応: 1 ポリシーで最大 50 プロジェクトをカバーし、組織全体を少数のポリシーで統制
✓GA 品質: gcloud の GA トラックで利用可能になり、本番環境へ安心して導入できる

⚠️ デメリット・制約事項

🚧 制限事項

✗対応リソースは Compute Engine インスタンスとディスクのみ (Cloud SQL、Filestore などは対象外)
✗1 ポリシーは単一リージョンのみ保護 (マルチリージョン環境ではリージョンごとにポリシーが必要)
✗同一ワークロード プロジェクト内では、同じリソースタイプのポリシーは同じラベルキーを使い、ポリシーごとに異なるラベル値を指定する必要がある
✗ワークロード プロジェクトは、特定リージョンにつき単一のバックアップ ボールト プロジェクトのポリシーにのみ追加可能
✗1 回の調整で評価されるのはプロジェクトあたり最大 1,000 リソースで、超過分は保護失敗として報告される
✗Terraform でのポリシー管理は未対応 (将来のリリースで対応予定)
✗northamerica-northeast1 と asia-southeast3 リージョンでは利用不可

🤔 考慮すべき点

⚠️ 注意:
  • 自動保護が管理する関連付けは直接更新・削除できず、合致リソースに別プランを手動で関連付けることも不可 (オンデマンド バックアップは引き続き可能)
  • 既存の手動関連付けが異なるボールトのプランを使用している場合、自動保護により置き換えられる。事前に新しいボールトのサービス エージェントへオペレーター ロールを付与しないと保護が失われるため注意
  • 初回のマッチングと保護開始まで最大 8 時間かかる場合があり、即時の保護が必要なら手動関連付けを検討
  • ラベル付与の運用規律が前提。ラベル命名規則・付与ルールの整備 (組織ポリシーによるラベル強制など) と併せた導入が望ましい

🎯 ユースケース

🏢 ユースケース 1: 本番環境 VM の全社的な保護の標準化

シナリオ: 数十のプロジェクトに分散した本番 VM に対し、情報システム部門が統一されたバックアップ基準 (日次バックアップ・30 日保持など) を適用したい。

Bash本番 VM 用ポリシーの作成例
# 本番 VM 用ポリシーを作成し、各ワークロード プロジェクトをバインド
gcloud backup-dr auto-protection-policies create prod-vm-policy \
  --location=asia-northeast1 \
  --criteria=key=env,values=prod \
  --backup-plan-details="resource-type=compute.googleapis.com/Instance,backup-plan=projects/central-vault-prj/locations/asia-northeast1/backupPlans/daily-30d"

効果: 各チームは VM 作成時に env=prod ラベルを付けるだけで統一基準のバックアップが自動適用され、中央管理チームは保護状況をポリシー単位で監査できる。

🧪 ユースケース 2: 環境ごとに異なるバックアップ基準の適用

シナリオ: 同一プロジェクト内で、本番 (env=prod) は長期保持プラン、検証 (env=test) は短期保持プランと、環境に応じてバックアップ基準を変えたい。

効果: 同じラベルキー env に対して値ごとに別ポリシー・別バックアップ プランを割り当てることで、環境区分に応じたコスト最適なバックアップ運用をラベルだけで実現できる。

💰 料金 / 🌏 利用可能リージョン

💰 料金

自動保護ポリシー機能自体の追加料金に関する記載は確認できませんでした。保護されたリソースのバックアップには、Backup and DR Service の通常料金 (バックアップ ボールト ストレージなどの使用量ベースの月額課金) が適用されます。

✅ トライアル: Backup and DR には 30 日間の導入トライアルがあり、対象プロジェクトでバックアップ管理料金とボールト ストレージ料金なしで機能を評価できます。 詳細は 料金ページ を参照してください。

🌏 利用可能リージョン

northamerica-northeast1 および asia-southeast3 を除く、 Backup and DR が利用可能なすべてのリージョンで利用できます。

🔗 関連サービス・機能

→Compute Engine: 保護対象となる VM インスタンスとディスク。リソースラベルがポリシーのマッチング条件として使用される
→バックアップ ボールト (Backup Vault): バックアップの保管先。イミュータブル・削除不能なバックアップを Google 管理の分離環境に保管
→バックアップ プラン (Backup Plan): バックアップの頻度・保持期間・保管先を定義するポリシー。自動保護ポリシーが対象リソースに自動割り当てする
→IAM: 両プロジェクトでのロールベースのアクセス制御と、クロスプロジェクト保護時のサービス エージェントへの権限付与
→Cloud Logging / Cloud Monitoring: バックアップ運用の監査証跡の記録、運用メトリクスの監視とアラート

🚀 まとめ

✅ ポイント: Compute Engine リソースの自動保護が GA となり、ラベルベースのポリシーでプロジェクト横断のバックアップ適用を自動化できるようになりました。

大規模環境でバックアップの適用漏れに課題を抱えている組織は、ラベル運用ルールの整備と併せて自動保護ポリシーの導入を検討することを推奨します。 まずは検証環境のプロジェクトでポリシーを作成し、マッチング・保護状況の可視化を確認した上で本番展開するのが良いでしょう。
