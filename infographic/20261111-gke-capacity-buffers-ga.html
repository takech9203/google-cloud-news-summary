📝 概要

GKE の Capacity Buffers (容量バッファ) が、アクティブバッファとスタンバイバッファの両方を含めて一般提供 (GA) になりました。バージョン 1.37.1-gke.3020000 以降の Standard / Autopilot クラスタで利用できます。

Kubernetes のカスタムリソース CapacityBuffer (autoscaling.x-k8s.io/v1beta1) を宣言するだけで、クラスタオートスケーラーがバッファを「保留中の需要」として扱い、余剰容量を事前プロビジョニング。スケールアウトの高速化と GPU 不足などの容量制約 (stockout) リスクの軽減を実現します。

❌ Before (アップデート前の課題)

  • スケールアウトは新規ノードの起動待ちが必要で、急激なトラフィック増加時に Pod が Pending のまま待たされる
  • 余剰容量の確保にはバルーン Pod (低優先度プレースホルダ) を自前で構築・運用する必要
  • ゾーンの在庫状況によってはマシンタイプを確保できない容量制約 (stockout) のリスク
  • 待機容量を確保すると、未使用の間も稼働ノード分の料金が常に発生

✅ After (アップデート後の改善)

  • CapacityBuffer を宣言するだけで、オートスケーラーがバッファ容量を自動プロビジョニング・維持
  • アクティブバッファで稼働中ノードへ即スケジュール、スケールアップのレイテンシを最小化
  • スタンバイバッファはサスペンド中の CPU / メモリ課金なしで容量を事前確保
  • 固定数・リソース上限・パーセンテージ指定など柔軟なサイズ定義
  • GA となり本番環境で安心して利用可能 (Standard / Autopilot 両対応)

CapacityBuffer リソースを定義すると、クラスタオートスケーラーが待機容量を事前にプロビジョニングします。スケールアウト時には「アクティブバッファ → スタンバイバッファ (再開) → 新規ノード」の優先順位で Pending Pod がスケジュールされ、消費されたバッファは自動的に補充されます。

⚡ 主要機能

🟢 1. アクティブバッファ (Active buffer)

→稼働中のノードを待機容量として維持 (provisioningStrategy: "buffer.x-k8s.io/active-capacity"、デフォルト)
→ノードが起動済みのため、最小のレイテンシで Pod をスケジュール可能
→消費されると、互換性のあるスタンバイノードの再開または新規プロビジョニングで自動補充

🟡 2. スタンバイバッファ (Standby buffer)

→サスペンド状態のノードを待機容量として維持 (provisioningStrategy: "buffer.gke.io/standby-capacity")
→コスト効率が高い一方、ノード再開 (レジューム) の短い遅延が発生
→サスペンド猶予時間 (standby-capacity-init-time、デフォルト 5m) とリフレッシュ頻度 (standby-capacity-refresh-frequency、デフォルト 24h、最大 120h) をアノテーションで調整可能
→DaemonSet でサスペンド前にコンテナイメージをプリロードし、再開後の起動を高速化できる

📐 3. 柔軟なバッファサイズ定義

→固定レプリカ数: PodTemplate を参照し replicas でユニット数を直接指定
→リソース上限: CPU / メモリの総量を limits で指定し、ユニット数は自動計算
→パーセンテージベース: Deployment / StatefulSet / ReplicaSet / Job などを scalableRef で参照し、ワークロード規模に応じて動的調整
→replicas + percentage の大きい方を下限、limits を上限とする組み合わせも可能

🎯 4. スケジューリングの優先順位制御

📄 CapacityBuffer マニフェスト例 (スタンバイバッファ)

YAML カスタマイズ済みスタンバイバッファ 
apiVersion: autoscaling.x-k8s.io/v1beta1
kind: CapacityBuffer
metadata:
  name: customized-standby-buffer
  namespace: my-namespace
  annotations:
    buffer.gke.io/standby-capacity-init-time: "15m"
    buffer.gke.io/standby-capacity-refresh-frequency: "12h"
spec:
  podTemplateRef:
    name: buffer-unit-template
  replicas: 3
  provisioningStrategy: "buffer.gke.io/standby-capacity"

🛠️ 設定方法

✅ 前提条件

✓GKE クラスタ (Standard / Autopilot) がバージョン 1.37.1-gke.3020000 以降で稼働
✓Standard クラスタではノードプール自動作成の有効化を推奨 (スタンバイバッファでは必須。無効の場合は既存ノードプールのスケールアップのみ)
✓Autopilot クラスタのスタンバイバッファにはカスタム ComputeClass が必要
✓ノードベース課金モデルのワークロードであること (特定ハードウェアを選択する Autopilot ワークロードを含む)

ステップ 1: バッファユニットを定義する PodTemplate を作成

YAML buffer-pod-template.yaml 
apiVersion: v1
kind: PodTemplate
metadata:
  name: buffer-unit-template
  namespace: capacity-buffer-example  # CapacityBuffer と同じ namespace
template:
  spec:
    terminationGracePeriodSeconds: 0
    containers:
      - name: buffer-container
        image: registry.k8s.io/pause:3.9
        resources:
          requests:
            cpu: "1"
            memory: "1Gi"
          limits:
            cpu: "1"
            memory: "1Gi"

バッファ容量 1 ユニットあたりのリソース要件 (この例では 1 CPU / 1 GiB) を定義します。カスタム ComputeClass を使う場合は nodeSelector: cloud.google.com/compute-class: <名前> を追加します。

ステップ 2: CapacityBuffer リソースを作成して適用

Bash アクティブバッファの作成 
cat <<EOF > cb-fixed-replicas.yaml
apiVersion: autoscaling.x-k8s.io/v1beta1
kind: CapacityBuffer
metadata:
  name: fixed-replica-buffer
  namespace: capacity-buffer-example
spec:
  podTemplateRef:
    name: buffer-unit-template
  replicas: 3
  provisioningStrategy: "buffer.x-k8s.io/active-capacity"
EOF

kubectl apply -f cb-fixed-replicas.yaml

provisioningStrategy を "buffer.gke.io/standby-capacity" に変更するとスタンバイバッファになります。

ステップ 3: バッファのステータスを確認

Bash ステータス確認 
kubectl get capacitybuffer fixed-replica-buffer -n capacity-buffer-example
💡 確認ポイント: ステータスが ReadyForProvisioning となり、replicas フィールドに定義した数が反映されていれば成功です。バッファの変更が反映されるまでには最大 5 分程度かかることがあります。

👍 メリット

💼 ビジネス面

✓ユーザー体験の向上: トラフィック急増時のスケールアップ遅延を最小化し、レイテンシ悪化やリクエスト取りこぼしを防止
✓コスト最適化: スタンバイバッファならサスペンド中の CPU / メモリ課金なし。常時稼働のオーバープロビジョニングより低コスト
✓容量リスクの軽減: 需要ピーク時の容量制約 (stockout) リスクを事前プロビジョニングで回避

⚙️ 技術面

✓宣言的な容量管理: バルーン Pod などの自前の仕組みを廃止し、Kubernetes ネイティブなカスタムリソースで管理
✓自動補充: 消費されたバッファはスタンバイノードの再開や新規プロビジョニングで自動補充
✓柔軟なサイズ制御: 固定数・リソース上限・ワークロード比率を組み合わせ、下限と上限を設定可能
✓既存機能との統合: カスタム ComputeClass、workload separation、イメージプリロード用 DaemonSet と組み合わせて細かく制御

⚠️ デメリット・制約事項

🚫 制限事項
  • GKE バージョン 1.37.1-gke.3020000 以降が必要
  • ノードベース課金のみ対応。Autopilot の Pod ベース課金ワークロードでは使用不可
  • スタンバイバッファの追加制限:
    • Standard はノードプール自動作成が必須、Autopilot はカスタム ComputeClass が必須
    • GPU / TPU 搭載ノード、ローカル SSD は非対応
    • Confidential GKE Nodes は非対応
    • ノードイメージは Container-Optimized OS と Ubuntu のみ (Windows Server 非対応)
    • Compute Engine のサスペンド / レジューム制限に準拠: メモリ 208 GB 超のノード、CSEK 保護ディスク、ベアメタルインスタンスは非対応。サスペンド処理時間はメモリサイズに比例
  • スタンバイノードの再開には、そのマシンタイプ・CPU プラットフォーム世代のゾーン内空き容量が必要。サスペンドされた Spot VM は再開時にオンデマンド VM へ変換できない
🤔 考慮すべき点
  • バッファ容量はデフォルトで scalableRef 参照先に限定されず、制約が一致する任意の Pending Pod が消費できる。専用化には workload separation の設定が必要
  • スケールダウン時、余剰ノードは再サスペンドではなく削除され、スタンバイバッファは新規ノードのプロビジョニング + サスペンドで別途補充される
  • カスタム ComputeClass で activeMigration.optimizeRulePriority: true と高優先度の Spot VM ルールを併用すると、スタンバイノードが Spot VM へ移行され再開できなくなる場合がある
  • アクティブバッファの稼働ノードは vCPU / メモリ / ディスク / IP アドレスの Compute Engine クォータを消費。サスペンド済みノードも IP アドレスとディスククォータ (メモリ保存用 Persistent Disk を含む) は消費する
  • Kubernetes の ResourceQuota 上は、いずれのバッファユニットも Pod が稼働しているものとしてカウントされる
  • 多数の個別ワークロードにそれぞれ専用バッファを割り当てると、バッファごとにノードプールが必要となりプロビジョニング・補充が遅くなるため避ける

💡 ユースケース

🛒 ユースケース 1: スパイクトラフィックに備えるオンラインサービス

シナリオ: EC サイトのセール開始時やテレビ放映直後など、数分以内に数倍のトラフィックが発生するサービスで、HPA によるスケールアウトがノード起動待ちで間に合わない。

YAML パーセンテージベースのアクティブバッファ 
apiVersion: autoscaling.x-k8s.io/v1beta1
kind: CapacityBuffer
metadata:
  name: frontend-burst-buffer
  namespace: production
spec:
  scalableRef:
    apiGroup: apps
    kind: Deployment
    name: frontend
  percentage: 20          # 現在のレプリカ数の 20% を常にバッファとして確保
  provisioningStrategy: "buffer.x-k8s.io/active-capacity"

効果: 稼働中のアクティブバッファノードへ Pending Pod が即座にスケジュールされ、スケールアップのレイテンシがほぼゼロになる。ワークロードの規模に追従してバッファサイズも自動調整される。

🌙 ユースケース 2: コストを抑えた容量確保 (バッチ / 定時処理)

シナリオ: 毎日決まった時間帯に大量のバッチ処理を実行するが、稼働ノードを常時確保するとコストが高い。一方、実行時にノードを確保できない容量制約のリスクは避けたい。

効果: スタンバイバッファでノードをサスペンド状態で確保しておくことで、待機中は CPU / メモリのコンピュート料金なし (ディスク等の少額課金のみ) で容量を事前確保できる。バッチ開始時はノードの再開のみで済むため、新規プロビジョニングより高速かつ確実にスケールできる。イメージプリロード用 DaemonSet と組み合わせれば再開後の起動もさらに高速化できる。

💰 料金

Capacity Buffers 機能自体に追加料金はなく、ノードベース課金の標準的なコンピュート料金に準じます (事前プロビジョニングされた容量の課金)。

バッファタイプ課金内容
🟢 アクティブバッファ稼働中 VM に対して通常のノードベースのコンピュート料金が発生
🟡 スタンバイバッファ (サスペンド中)CPU / メモリのコンピュート料金は発生しない。VM ブートディスクやメモリ状態保存用ストレージ、静的外部 IP アドレスなどの少額の料金のみ発生
🟠 スタンバイバッファ (再開後)ワークロードをホストするために再開された時点から通常のノードベースのコンピュート料金が発生

詳細は GKE の料金ページ および サスペンド済みインスタンスの料金 を参照してください。

🌍 利用可能リージョン

リージョン固有の制限は公式ドキュメントに明記されていません。GKE バージョン 1.37.1-gke.3020000 以降のクラスタで利用できます。なお、スタンバイノードの再開には対象ゾーンの Compute Engine 空き容量が必要です。

🔗 関連サービス・機能

⚙️ GKE クラスタオートスケーラー / ノードプール自動作成
CapacityBuffer を保留中の需要として扱い、ノードのプロビジョニング・補充を行う基盤。Standard クラスタではノードプール自動作成の有効化を推奨
🖥️ カスタム ComputeClass
バッファノードのマシンファミリー優先順位 (N4 → C4 など) を制御。Autopilot のスタンバイバッファでは必須
⏸️ Compute Engine のサスペンド / レジューム
スタンバイバッファの基盤機能。サスペンド中はメモリ状態が Persistent Disk に保存される
🏷️ Workload Separation (taint / toleration)
特定ワークロード専用にバッファを予約する場合に使用
📈 Horizontal Pod Autoscaler (HPA)
Pod のスケールアウトを担当し、Capacity Buffers がそのための余剰ノード容量を事前確保する補完関係

🎯 まとめ

GKE Capacity Buffers の GA により、バルーン Pod などの自前の仕組みに頼らず、Kubernetes ネイティブなカスタムリソースでスケールアウト用の待機容量を宣言的に管理できるようになりました。

  • ⚡ 即応性重視 → アクティブバッファ (稼働中ノードへ即スケジュール)
  • 💰 コスト重視 → スタンバイバッファ (サスペンド中のコンピュート課金なし)
  • 🚀 バーストトラフィックや容量制約への備えが必要なら、GKE 1.37.1-gke.3020000 以降で既存のオーバープロビジョニング手法からの移行を検討
