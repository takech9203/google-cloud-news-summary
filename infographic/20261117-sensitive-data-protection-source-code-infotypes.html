📝 概要

Google Cloud の Sensitive Data Protection (旧 Cloud DLP) に、ソースコードを言語・カテゴリ単位で分類するための新しい組み込み infoType 検出器が追加され、すべてのリージョンで利用可能になりました。同日に発表された 2 つのリリースノートエントリから構成され、合計 25 種類の DOCUMENT_TYPE/R&D/SOURCE_CODE/* 検出器が追加されています。

DOCUMENT_TYPE 系の infoType はドキュメントのリスク評価とポリシー適用を支援するためのコンテンツ分類で、PII (個人識別情報) の検査スキャン結果と組み合わせることで特に有用になります。知的財産であるソースコードが Cloud Storage バケットや社内データ共有領域に意図せず保存されていないかを検出したいセキュリティチーム、データガバナンス担当者が主な対象ユーザーです。

❌ Before: アップデート前の課題

  • 既存の検出器は C / C++ / C# / Go / HTML / Java / JavaScript / JSON / PHP / PowerShell / Python / Rust / Shell / SQL / TypeScript などに限られ、Kotlin / Swift / Dart などモバイル開発言語、COBOL / Fortran などレガシー言語、HCL (Terraform) / Dockerfile などの IaC 関連ファイルを言語単位で識別できなかった
  • Markdown / XML / YAML / 設定ファイルなどを「ソースコード関連ドキュメント」としてカテゴリ分類する手段が限られていた
  • 汎用の SOURCE_CODE 検出では、どの言語・種別のコードが漏えいリスクにさらされているかを細かく把握できなかった

✅ After: アップデート後の改善

  • 18 のプログラミング言語・フォーマット (AWK / COBOL / Dart / Dockerfile / Fortran / Groovy / HCL / Kotlin / Lua / Objective-C / Perl / Proto / R / Ruby / Scala / Swift / TOML / VBA) を言語単位で検出可能に
  • 7 つのカテゴリ単位の分類により、言語を網羅的に列挙しなくても広くソースコード関連ファイルを捕捉可能に
  • すべての新検出器が ANY_LOCATION (全リージョン) で利用でき、データレジデンシー要件のある環境でも同じ検査テンプレートを利用可能

Cloud Storage や BigQuery などのデータソースを Sensitive Data Protection でスキャンすると、新しい DOCUMENT_TYPE 検出器がコンテンツを言語別・カテゴリ別に分類し、結果を Security Command Center や BigQuery、Pub/Sub へ連携してガバナンス対応につなげられます。

⚡ 主要機能

1️⃣ プログラミング言語別のソースコード検出器 (18 種類)

DOCUMENT_TYPE/R&D/SOURCE_CODE/AWK、COBOL、DART、DOCKERFILE、FORTRAN、GROOVY、HCL、KOTLIN、LUA、OBJECTIVE_C、PERL、PROTO、R、RUBY、SCALA、SWIFT、TOML、VBA の各ソースコードを検出します。

→モバイル開発言語 (Kotlin / Swift / Dart / Objective-C)、レガシー・業務系言語 (COBOL / Fortran / VBA)、インフラ・スキーマ定義系フォーマット (HCL / Dockerfile / TOML / Proto) まで幅広くカバー

2️⃣ ファイルカテゴリ別のソースコード検出器 (7 種類)

検出器分類対象
CONFIG_AND_DATA設定ファイルおよび構造化データソース
DOCUMENTドキュメントマークアップソース
EXECUTABLE実行可能なプログラミング言語のソースコード
MARKDOWNMarkdown 形式のテキスト
WEB_FRONTENDWeb フロントエンドのソースコード
XML / YAMLXML / YAML ソース
→個別言語を列挙しなくても、カテゴリ単位でソースコード関連ファイルを広く分類可能

3️⃣ 全リージョンでの提供

✓すべての新検出器の Availability は ANY_LOCATION であり、リージョンを問わず利用可能
✓データレジデンシー要件により特定リージョンで検査・ディスカバリを実行する構成でも、同一の検査テンプレートを適用できる

🛠️ 設定方法

📌 前提条件

✓Sensitive Data Protection (DLP API) が有効化されたプロジェクトがあること
✓検査ジョブまたはディスカバリスキャン構成を作成・編集できる IAM 権限があること

ステップ 1: 最新の組み込み infoType 一覧を確認する

Bash infoTypes.list メソッドで最新の組み込み infoType を取得 
# infoTypes.list メソッドで最新の組み込み infoType を取得
curl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://dlp.googleapis.com/v2/infoTypes" | grep "SOURCE_CODE"
💡 ヒント: Sensitive Data Protection チームは新しい infoType 検出器を定期的にリリースしており、infoTypes.list メソッドで最新の一覧を取得できます。

ステップ 2: 検査テンプレートに新しい infoType を追加する

Bash 検査テンプレートを作成し、新しいソースコード検出器を指定 
# 検査テンプレートを作成し、新しいソースコード検出器を指定
curl -s -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://dlp.googleapis.com/v2/projects/PROJECT_ID/locations/global/inspectTemplates" \
  -d '{
    "inspectTemplate": {
      "displayName": "source-code-classification",
      "inspectConfig": {
        "infoTypes": [
          { "name": "DOCUMENT_TYPE/R&D/SOURCE_CODE/KOTLIN" },
          { "name": "DOCUMENT_TYPE/R&D/SOURCE_CODE/DOCKERFILE" },
          { "name": "DOCUMENT_TYPE/R&D/SOURCE_CODE/CONFIG_AND_DATA" }
        ]
      }
    }
  }'
💡 ポイント: 検査テンプレートはディスカバリ (データプロファイリング) を含む Sensitive Data Protection の各サービスで共通して利用できます。既存のスキャン構成が使用する検査テンプレートを変更した場合、デフォルトでは変更は以降のスキャンにのみ適用されます。

⚖️ メリット・デメリット

💼 ビジネス面のメリット

✓知的財産の漏えいリスク可視化: ソースコードという知的財産が、本来あるべきでないストレージや共有データセットに存在していないかを言語単位で把握でき、リスク評価の精度が向上する
✓ポリシー適用の自動化: DOCUMENT_TYPE 分類と PII 検査結果を組み合わせ、文書のカテゴリに応じたガバナンスポリシーの適用判断に活用できる

🔧 技術面のメリット

✓検出粒度の向上: 汎用の SOURCE_CODE 検出だけでなく、Kotlin / Swift / HCL など言語別の検出により、どの開発チーム・システム由来のコードかの切り分けがしやすくなる
✓カテゴリ検出による網羅性: EXECUTABLE や CONFIG_AND_DATA などカテゴリ単位の検出器を使えば、言語を個別に列挙しなくても広くソースコード関連ファイルを捕捉できる
✓全リージョン対応: ANY_LOCATION で提供されるため、リージョン制約のある検査・ディスカバリ構成にもそのまま組み込める

⚠️ 制限事項

✗組み込み infoType 検出器は完全に正確な検出方法ではなく、規制要件への準拠を保証するものではない (Google は要件を満たすことを確認するための設定テストを推奨)
✗DOCUMENT_TYPE 系検出器はドキュメント分類 (DOCUMENT タイプ) であり、個々の PII 値の検出とは役割が異なる

🤔 考慮すべき点

→センシティビティスコアはいずれも SENSITIVITY_MODERATE であり、組織のリスク基準に応じてスコアの調整や検査テンプレートのルールセット設定を検討する
→ディスカバリ (継続的プロファイリング) と検査 (オンデマンドの詳細スキャン) のどちらで利用するかにより、コストモデルと得られる結果の粒度が異なる

🎯 ユースケース

📂 ユースケース 1: Cloud Storage 上のソースコード混入検出

シナリオ: データレイクとして利用している Cloud Storage バケットに、開発者が誤って Kotlin のアプリコードや Terraform (HCL) ファイル、Dockerfile をアップロードしていないかを継続的に監視したい。

JSON 実装例 
{
  "inspectConfig": {
    "infoTypes": [
      { "name": "DOCUMENT_TYPE/R&D/SOURCE_CODE/KOTLIN" },
      { "name": "DOCUMENT_TYPE/R&D/SOURCE_CODE/HCL" },
      { "name": "DOCUMENT_TYPE/R&D/SOURCE_CODE/DOCKERFILE" }
    ]
  }
}
✅ 効果: 知的財産であるソースコードや、インフラ構成情報を含む IaC ファイルの意図しない保存を早期に発見し、Security Command Center や Pub/Sub 経由の自動修復ワークフローにつなげられる。

🗃️ ユースケース 2: カテゴリ検出による設定ファイル・実行コードの棚卸し

シナリオ: 社内の共有データ領域に、認証情報を含み得る設定ファイルや実行可能なコードがどの程度存在するかを棚卸ししたい。利用言語が多岐にわたるため、個別言語の列挙は避けたい。

✅ 効果: CONFIG_AND_DATA と EXECUTABLE のカテゴリ検出器を使うことで、言語を網羅的に指定しなくてもソースコード関連ファイルを広く分類できる。シークレット系 infoType (PASSWORD、GCP_API_KEY など) と組み合わせれば、設定ファイル内の認証情報漏えいリスク評価も強化できる。

💰 料金

新しい infoType 検出器自体に追加料金はなく、Sensitive Data Protection の既存の料金体系 (ディスカバリは選択した料金モード、検査・変換は処理バイト数に基づく課金) の中で利用できます。

🌍 利用可能リージョン

✅ 全リージョン対応: 今回追加された 25 種類の検出器はすべて ANY_LOCATION (全リージョン) で利用可能です。データレジデンシー要件のある環境でも同じ検査テンプレートを利用できます。

🔗 関連サービス・機能

🛡️ Security Command Center

ディスカバリや検査の結果を SCC に発行し、組織全体のリスク管理に統合できる。SCC Enterprise サブスクリプションにはデフォルトのディスカバリサブスクリプションが無償で含まれる。

📊 BigQuery

スキャン結果 (検出結果・データプロファイル) を BigQuery に保存して分析できる。

📨 Pub/Sub

検出結果を Pub/Sub に発行し、隔離やアラートなどイベント駆動の修復ワークフローを構築できる。

🔑 シークレット系 infoType 検出器

PASSWORD、GCP_API_KEY、AWS_CREDENTIALS などの認証情報検出器と組み合わせることで、ソースコード・設定ファイル内の認証情報漏えい検出を強化できる。

📌 まとめ

Sensitive Data Protection のソースコード分類が 25 種類の新検出器で大幅に拡充され、モバイル開発言語から IaC、レガシー言語、カテゴリ単位の分類まで全リージョンでカバーできるようになりました。

ソースコードの意図しない保存は知的財産漏えいや認証情報流出の起点になり得るため、Cloud Storage や BigQuery を広く利用している組織は、検査テンプレートへの新 infoType の追加とディスカバリスキャンでの活用を検討することを推奨します。
