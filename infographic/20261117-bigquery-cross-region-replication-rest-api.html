📊 BigQuery クロスリージョンレプリケーション
REST API サポート

BigQuery GA (一般提供) 災害復旧 (DR) REST API
リリース日: 2026-11-17

💡 概要

BigQuery の REST API (datasets.insert / datasets.patch / datasets.update / datasets.get) で、 クロスリージョンデータセットレプリケーション (CRR) の構成・モニタリングと、 マネージド災害復旧 (DR) 用フェイルオーバー予約のアタッチ / デタッチが可能になりました。

これまでコンソールと SQL DDL に限定されていた DR 構成が、標準的な Dataset リソースの API 操作として扱えるようになり、 Infrastructure as Code (IaC) や自動化パイプラインへの組み込みが容易になります。

🎯 対象ユーザー: 多数のデータセットに DR 構成を一括適用・管理したいデータプラットフォーム管理者、 レプリケーション状態をプログラムから監視したい SRE / 運用チーム

❌ Before (アップデート前)

  • CRR とフェイルオーバー予約の構成はコンソールまたは SQL DDL (ALTER SCHEMA ADD REPLICA など) のみ。「CLI、クライアントライブラリ、API、Terraform は非サポート」と明記
  • 多数のデータセットへの DR 適用は DDL クエリジョブのスクリプト化が必要で、API ベースの構成管理と統合しにくい
  • レプリカ状態の確認はコンソールまたは INFORMATION_SCHEMA.SCHEMATA_REPLICAS へのクエリ実行が必要

✅ After (アップデート後)

  • datasets.insert の replicas フィールドで最初からレプリカ付きのデータセットを作成可能
  • datasets.patch / update でレプリカの追加・削除、failover_reservation_id によるフェイルオーバー予約のアタッチ / デタッチが可能
  • datasets.get の datasetView パラメータでレプリカメタデータを取得し、プログラムからモニタリング可能

🏗️ アーキテクチャ図

⚙️ 主要機能

1️⃣ データセット作成時のレプリカ指定 (datasets.insert)

作成リクエストの replicas フィールドにレプリカの id と location を指定し、最初からレプリケーション構成済みのデータセットを作成。プライマリレプリカも replicas に含める必要があります。

2️⃣ 既存データセットへのレプリカ追加・削除 (datasets.patch / update)

replicas フィールドの更新でセカンダリレプリカを追加。削除時は残すレプリカのみを含めたリクエストを送信します (プライマリレプリカは必ず含める)。

3️⃣ フェイルオーバー予約のアタッチ / デタッチ

failover_reservation_id フィールド (ADMIN_PROJECT.FAILOVER_RESERVATION 形式) で、Enterprise Plus のフェイルオーバー予約をアタッチしマネージド DR を有効化。セカンダリレプリカのバックフィル完了後にのみ設定可能です。

4️⃣ レプリケーション構成のモニタリング (datasets.get)

datasetView パラメータ (BASIC / BASIC_REPLICA_METADATA_VIEW / FULL) でレプリカメタデータを取得。sync_status など詳細な同期状態は INFORMATION_SCHEMA.SCHEMATA_REPLICAS や Cloud Monitoring 指標と併用します。

🔧 技術仕様

API メソッドと用途

メソッドエンドポイント用途
datasets.insert POST /bigquery/v2/projects/{PROJECT_ID}/datasets レプリカ付きデータセットの作成
datasets.patch PATCH /bigquery/v2/projects/{PROJECT_ID}/datasets/{DATASET_ID} レプリカの追加・削除、フェイルオーバー予約のアタッチ / デタッチ
datasets.update PUT /bigquery/v2/projects/{PROJECT_ID}/datasets/{DATASET_ID} patch と同様の更新操作
datasets.get GET /bigquery/v2/projects/{PROJECT_ID}/datasets/{DATASET_ID}?datasetView=... レプリカメタデータの取得・モニタリング

📝 レプリカ付きデータセットの作成

JSON datasets.insert リクエストボディ 
{
  "datasetReference": {
    "datasetId": "DATASET_ID",
    "projectId": "PROJECT_ID"
  },
  "location": "us",
  "replicas": [
    { "id": "us-replica", "location": "us" },
    { "id": "eu-replica", "location": "eu" }
  ]
}

📝 フェイルオーバー予約のアタッチ

JSON datasets.patch リクエストボディ 
{
  "failover_reservation_id":
    "ADMIN_PROJECT.FAILOVER_RESERVATION"
}

🚀 設定方法

✅ 前提条件

✓レプリカ管理のための bigquery.datasets.update 権限を持っていること
✓マネージド DR を使う場合は、Enterprise Plus エディションの予約で secondary_location を設定したフェイルオーバー予約を作成済みであること
✓フェイルオーバー予約のアタッチ時は、セカンダリレプリカの初期バックフィルが完了していること
1️⃣ レプリカ追加
datasets.patch

2️⃣ 状態確認
datasets.get

3️⃣ DR 有効化
予約アタッチ

ステップ 1: 既存データセットにセカンダリレプリカを追加

Bash datasets.patch でレプリカを追加 
curl -X PATCH \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://bigquery.googleapis.com/bigquery/v2/projects/PROJECT_ID/datasets/DATASET_ID" \
  -d '{
    "replicas": [
      { "id": "us-replica", "location": "us" },
      { "id": "eu-replica", "location": "eu" }
    ]
  }'
⚠️ 注意: レプリカの追加・削除時は、プライマリレプリカを必ず replicas フィールドに含めること。省略すると意図しない構成変更になる可能性があります。

ステップ 2: レプリカの作成状態を確認

Bash datasets.get でレプリカメタデータを取得 
curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://bigquery.googleapis.com/bigquery/v2/projects/PROJECT_ID/datasets/DATASET_ID?datasetView=BASIC_REPLICA_METADATA_VIEW"

初期コピーの完了は INFORMATION_SCHEMA.SCHEMATA_REPLICAS ビューの creation_complete 列でも確認できます。

ステップ 3: フェイルオーバー予約をアタッチ (マネージド DR)

Bash datasets.patch でフェイルオーバー予約をアタッチ 
curl -X PATCH \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://bigquery.googleapis.com/bigquery/v2/projects/PROJECT_ID/datasets/DATASET_ID" \
  -d '{ "failover_reservation_id": "ADMIN_PROJECT.FAILOVER_RESERVATION" }'

セカンダリレプリカのバックフィル完了後にのみ設定可能です。

👍 メリット

💼 ビジネス面

✓DR 構成の標準化と大規模展開: 多数のデータセットに API 経由で一括適用でき、組織全体の BCP 対応を効率化
✓運用コストの削減: コンソール操作や DDL のスクリプト化が不要になり、手作業と人的ミスを削減

🛠️ 技術面

✓IaC / 自動化との統合: 標準的な API 操作として構成管理ツールや CI/CD に組み込みやすい
✓プログラムによるモニタリング: datasetView で独自の監視・監査の仕組みを構築可能
✓DDL と API の使い分け: SQL DDL やコンソールと併用でき、チームのワークフローに合わせて選択可能

⚠️ デメリット・制約事項

制限事項

✗プライマリレプリカの昇格 (切り替え) は API 非対応。引き続き ALTER SCHEMA SET OPTIONS DDL またはコンソールが必要
✗datasets.get のビューには sync_status などクロスリージョンリクエストを要するフィールドは含まれない (詳細は INFORMATION_SCHEMA.SCHEMATA_REPLICAS を使用)
✗プライマリ切り替え中は datasets.get が旧プライマリにルーティングされ、replicas フィールドが古い情報を返す可能性
✗フェイルオーバー予約は Enterprise Plus エディションが必要で、バックフィル完了後にのみアタッチ可能
✗レプリカはリージョン / マルチリージョンごとに 1 つまで、対象はテーブル数 100,000 未満のデータセットなど、CRR 自体の制限が適用される

考慮すべき点

  • レプリカ更新時はプライマリレプリカを必ず replicas フィールドに含めること
  • DML 操作が頻繁なテーブルはファイル単位で再レプリケーションされ、データ転送コストが増大しやすい (DML の多いテーブルはレプリケーション対象外のデータセットに分離を推奨)
  • マネージド DR 有効化後は、書き込みは Enterprise Plus 予約のジョブのみに制限される

🎯 ユースケース

📦 ユースケース 1: Terraform / 自動化パイプラインによる DR 構成の一括管理

シナリオ: 金融系企業が、コンプライアンス要件として全業務データセットにクロスリージョンレプリカと DR 構成を適用。従来は DDL スクリプトを順次実行していた。

1. insert
replicas 付き作成
→
2. patch
replicas 追加
→
3. get / IS
バックフィル確認
→
4. patch
予約アタッチ

効果: プロビジョニングと DR 構成を単一の API ワークフローに統合し、構成漂流 (drift) の検出や監査も API で自動化できる。

🔍 ユースケース 2: レプリケーション構成の自動監査・モニタリング

シナリオ: SRE チームが、全プロジェクトのデータセットについて「レプリカが構成されているか」「どのリージョンにあるか」を定期的に棚卸ししたい。

効果: datasets.get?datasetView=BASIC_REPLICA_METADATA_VIEW を定期実行することで、クエリジョブを発行せずにレプリカ構成を取得。Cloud Monitoring のレプリケーション遅延指標 (dataset_staleness) と組み合わせて RPO の監視体制を構築できる。

💰 料金

💡 ポイント: 今回の API サポート自体に追加料金はありません。CRR とマネージド DR の利用には従来どおり以下の料金が発生します。
項目課金内容
🗄️ ストレージ セカンダリリージョンのストレージバイトは、別のコピーとしてセカンダリリージョンの料金で課金
🔄 データレプリケーション リージョン間のデータ転送量に応じて課金 (スロットリソースは消費しない)。マネージド DR はターボレプリケーションを使用し、物理 GiB 単位で課金
⚡ コンピューティング マネージド DR には Enterprise Plus エディションが必要。プライマリリージョンの容量のみ課金され、セカンダリの容量 (予約ベースライン分) は追加料金なし

詳細は BigQuery の料金ページ を参照してください。

🌏 利用可能リージョン

クロスリージョンレプリケーションは BigQuery のリージョン / マルチリージョン間で利用できます。

⚠️ 注意: マネージド災害復旧では us-central1 - us マルチリージョンなど、一部のリージョンペアは構成できません。詳細は データレプリケーションのドキュメント を参照してください。

🔗 関連サービス・機能

📅 BigQuery Reservations (Enterprise Plus)

マネージド DR のフェイルオーバー予約を提供。Reservation API には予約のフェイルオーバーを実行する failoverReservation メソッドがある。

📈 Cloud Monitoring

レプリケーション遅延 (bigquery.googleapis.com/storage/replication/dataset_staleness) やネットワーク下り (外向き) バイト数の指標で、RPO やデータ転送量を監視できる。

🗂️ INFORMATION_SCHEMA.SCHEMATA_REPLICAS

レプリカの作成完了状態 (creation_complete) や同期状態 (sync_status) を SQL で確認できるビュー。

📌 まとめ

✓CRR とマネージド DR が REST API から構成・監視可能に (GA)
✓コンソール / SQL DDL に限定されていた DR 構成を IaC や自動化パイプラインに組み込めるように
✓多数のデータセットを運用する組織は、API ベースでの DR 構成の標準化と自動監査の導入を検討する価値あり
⚠️ 注意: プライマリレプリカの昇格は引き続き DDL / コンソールでの操作が必要です。
