Gemini Enterprise GA (一般提供) Agent Identity
リリース日: 2026-11-13

🔐 A2A エージェント向け 3-legged OAuth (3LO) 認証が GA

Agent Identity auth manager でユーザー代理のツールアクセスをネイティブ統合 — 同意 UI・コールバック検証・会話再開はすべて Gemini Enterprise が自動管理

📌 概要

Gemini Enterprise で、Agent Identity auth manager を使用した A2A エージェントの 3-legged OAuth (3LO) 認証が一般提供 (GA) になりました。 Agent Development Kit (ADK) で構築し Agent Runtime にデプロイした A2A エージェントが、サインイン中の Gemini Enterprise ユーザーの代理として、 ダウンストリームの MCP サーバー・Google Cloud サービス・サードパーティ API に認証できます。

💡 最大のポイント: ツールがユーザー同意を必要とすると (adk_request_credential インタラプト / TASK_STATE_AUTH_REQUIRED)、 Gemini Enterprise が同意プロンプトの表示 → コールバック検証 (validateUserId) → 会話の自動再開までのクライアントサイド 3LO ワークフロー全体を自動管理。 開発者はカスタムの同意 UI やコールバック処理アプリを実装する必要がありません。

🎯 対象ユーザー: Gemini Enterprise 上でカスタム A2A エージェントを提供するエージェント開発者、 Jira・GitHub・Salesforce などの外部システムとユーザー権限で安全に連携するエンタープライズエージェントを構築するプラットフォームチーム。

❌ Before (アップデート前の課題)

  • 同意プロンプト表示・OAuth コールバック受信/検証・会話再開を処理するカスタム UI アプリの独自実装が必要
  • OAuth トークンの取得・保存・リフレッシュを扱うカスタムバックエンドと独自トークンストレージが必要
  • エージェントごとの個別実装でトークン管理・ガバナンス (可視化・取り消し) が分散し、セキュリティリスクが増大

✅ After (アップデート後の改善)

  • Gemini Enterprise が同意プロンプト・検証エンドポイント・会話再開を自動処理 — クライアントサイド UI の実装が不要に
  • auth manager が Google 管理のクレデンシャル保管庫にトークンを保存し、ADK がツール呼び出し時に自動取得・注入
  • エージェントの SPIFFE ID に基づく IAM 制御でアクセスの可視化・取り消しが可能になりガバナンス向上
  • GA となり本番環境のエンタープライズエージェントで安心して利用可能

    GE->>Agent: A2A リクエスト

ツールがユーザー同意を必要とすると、Gemini Enterprise が同意プロンプトの表示・コールバック検証・会話再開を自動管理し、 エージェントは Agent Identity auth manager からユーザー委任トークンを取得してツールを呼び出します。

⚙️ 主要機能

1️⃣ 同意プロンプトの自動表示 (Consent prompt)

→A2A エージェントが adk_request_credential ツールインタラプト (TASK_STATE_AUTH_REQUIRED) を返すと、Gemini Enterprise Web アプリが自動的にユーザーへサインインを促し、認可プロバイダーの認可 URI を開く
→開発者はエージェント側で認可フロー開始の UI を実装する必要がない

2️⃣ ユーザー検証とトークン保存 (User validation and token storage)

→ユーザーが同意すると、認可プロバイダーは検証エンドポイント https://vertexaisearch.cloud.google.com/validateUserId にリダイレクト
→Gemini Enterprise がセッション状態を検証し、Agent Identity auth manager で認証情報を確定
→OAuth トークンは Google 管理のクレデンシャル保管庫 (credential vault) に安全に保存

3️⃣ 会話の自動再開 (Conversation resumption)

→完了した adk_request_credential 応答が A2A エージェントに送り返される
→エージェントは auth provider からユーザーのアクセストークンを取得し、中断していたツール呼び出しを実行して会話を継続

4️⃣ 多様なダウンストリーム接続先への対応

→MCP サーバー: McpToolset + GcpAuthProviderScheme、または Agent Registry の AgentRegistry.get_mcp_toolset
→Google Cloud サービス: 例として BigQuery MCP サーバー
→サードパーティ API: AuthenticatedFunctionTool による REST API 呼び出し (Jira、GitHub、GitLab、Dropbox、Microsoft、Salesforce、ServiceNow などの 3LO 対応サービス)

ステップ 1: 3-legged OAuth auth provider のセットアップ

Authenticate using 3-legged OAuth with auth manager の手順に従い、OAuth クライアントアプリケーションを構成して 3LO auth provider を作成します。Gemini Enterprise 用には以下を設定します。

→OAuth クライアントの Authorized redirect URIs に auth provider のコールバック URI を追加: https://agentidentitycredentials.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/authProviders/AUTH_PROVIDER_NAME/oauthcallback
→Continue URI を Gemini Enterprise の検証エンドポイントに設定: https://vertexaisearch.cloud.google.com/validateUserId

ステップ 2: A2A エージェントコードの構成

Python ADK A2A エージェント + GcpAuthProviderScheme 
from google.adk.a2a.executor.a2a_agent_executor import A2aAgentExecutor
from google.adk.agents import LlmAgent
from google.adk.auth.credential_manager import CredentialManager
from google.adk.integrations.agent_identity import GcpAuthProvider, GcpAuthProviderScheme
from google.adk.runners import Runner
from google.adk.tools.mcp_tool.mcp_session_manager import StreamableHTTPConnectionParams
from google.adk.tools.mcp_tool.mcp_toolset import McpToolset
from vertexai.agent_engines.templates.a2a import A2aAgent, create_agent_card

# Gemini Enterprise のユーザー検証用リダイレクト URI
CONTINUE_URI = "https://vertexaisearch.cloud.google.com/validateUserId"

auth_scheme = GcpAuthProviderScheme(
    name="projects/PROJECT_ID/locations/LOCATION/authProviders/AUTH_PROVIDER_NAME",
    scopes=["OAUTH_SCOPE"],
    continue_uri=CONTINUE_URI,
)

mcp_tools = McpToolset(
    connection_params=StreamableHTTPConnectionParams(url="https://YOUR_MCP_SERVER_URL"),
    auth_scheme=auth_scheme,
)

adk_agent = LlmAgent(
    model="gemini-2.5-flash",
    name="AGENT_NAME",
    instruction="AGENT_INSTRUCTIONS",
    tools=[mcp_tools],
)

def build_runner() -> Runner:
    # デプロイ先ワーカープロセス内で GcpAuthProvider を登録する
    CredentialManager.register_auth_provider(GcpAuthProvider())
    return Runner(app_name=adk_agent.name, agent=adk_agent, ...)

a2a_agent = A2aAgent(
    agent_card=agent_card,  # A2A v0.3 インターフェースを追加した AgentCard
    agent_executor_builder=lambda: A2aAgentExecutor(runner=build_runner),
)

ステップ 3: Agent Identity を有効にしてデプロイし、アクセスを付与

Python Agent Runtime へのデプロイ (identity_type=AGENT_IDENTITY) 
import vertexai
from vertexai import types

client = vertexai.Client(
    project="PROJECT_ID", location="LOCATION",
    http_options=dict(api_version="v1beta1"),
)

remote_a2a_agent = client.agent_engines.create(
    agent=a2a_agent,
    config={
        "display_name": "AGENT_DISPLAY_NAME",
        "identity_type": types.IdentityType.AGENT_IDENTITY,
        "requirements": [
            "a2a-sdk[http-server]>=1.0.0",
            "google-cloud-aiplatform[agent_engines,adk]>=1.156.0",
            "google-adk[a2a,agent-identity,mcp]>2.7.1",
        ],
    },
)

デプロイ後、デプロイ済みエージェントの SPIFFE プリンシパルに auth provider への roles/agentidentity.user ロールを付与します。

Bash SPIFFE プリンシパルへの IAM ロール付与 
gcloud agent-identity auth-providers add-iam-policy-binding AUTH_PROVIDER_NAME \
  --project="PROJECT_ID" \
  --location="LOCATION" \
  --role="roles/agentidentity.user" \
  --member="principal://agents.global.org-ORGANIZATION_ID.system.id.goog/resources/aiplatform/projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/ENGINE_ID"
📌 最後に: デプロイ済み A2A エージェントを Gemini Enterprise に登録します。Agent Runtime にホストされているため、 Gemini Enterprise 側に https://www.googleapis.com/auth/cloud-platform スコープの OAuth 2.0 認可リソースを構成します。

💼 ビジネス面

✓開発コストの削減: 同意 UI・コールバック処理・トークン管理のカスタム実装が不要になり、エンタープライズエージェントの開発期間を短縮
✓ガバナンスの強化: エンドユーザーのアクセスイベントがエージェントの SPIFFE ID に紐付けられ、アクセスの可視化と取り消しが可能。ユーザー委任権限の統制が容易に
✓GA による本番適用: Pre-GA 条項の制約なく、SLA を前提とした本番ワークロードで利用可能

🛠️ 技術面

✓セキュアなトークン管理: OAuth トークンは Google 管理のクレデンシャル保管庫に保存。ハードコードされたシークレットや独自データベースでの保管が不要
✓ADK ネイティブ統合: ADK がツール実行をインターセプトし、auth manager から取得した認証ヘッダーをツール呼び出しや MCP サーバー呼び出しに自動注入
✓IAM・PAB・VPC Service Controls との統合: IAM 許可/拒否ポリシー、Principal Access Boundary、VPC Service Controls と統合し、エージェント単位の厳密なアクセス制御が可能
✓シームレスな会話体験: 認証後に会話が自動再開されるため、ユーザーは同意後に操作をやり直す必要がない

⚠️ デメリット・制約事項

🚧 制限事項

✗対象は ADK で構築し A2aAgent でラップして Agent Runtime にデプロイした A2A エージェント。他のホスティング形態 (例: Cloud Run 上のコンテナで Authorization ヘッダーを直接受け取る方式) は別の認可構成を使用
✗組み込みの A2aAgentExecutor の使用が必須 (カスタム AgentExecutor では adk_request_credential が TASK_STATE_AUTH_REQUIRED に変換されない)
✗AgentCard に A2A プロトコルバージョン 0.3 インターフェースの追加が必要
✗GitHub と Microsoft の 3LO 連携は単一スコープのみサポート (複数スコープのリクエストは不可)
✗Vertex AI Python SDK でのデプロイは v1beta1 API (http_options=dict(api_version="v1beta1")) が必要

🤔 考慮すべき点

⚠️ よくあるハマりどころ: CredentialManager.register_auth_provider(GcpAuthProvider()) をモジュールトップレベルのみで呼び出すと、 デプロイ後に No auth provider registered for custom auth scheme 'gcpAuthProviderScheme' エラーが発生。 必ず Runner を構築する関数内 (または set_up()) で登録すること。
→同じ OAuth クライアントを Gemini Enterprise のエージェント認可リソースと共用する場合、redirect URI に https://vertexaisearch.cloud.google.com/oauth-redirect も追加が必要
→ServiceNow はアプリケーションレベルで許可スコープを構成するため、必要スコープが構成に含まれていないと認証ループが発生する可能性
→auth provider とエージェントのリージョン整合性、および Agent Identity のサポートリージョンを事前に確認

📊 ユースケース 1: BigQuery MCP サーバーへのユーザー権限でのアクセス

シナリオ: 社内データ分析エージェントが、質問したユーザー自身の BigQuery 権限でデータセットをクエリ。エージェント自体に広い権限を与えず、ユーザーごとのアクセス制御 (行レベル・データセットレベル) をそのまま活かす。

Python BigQuery MCP サーバー連携の実装例 
auth_scheme = GcpAuthProviderScheme(
    name=f"projects/{project_id}/locations/LOCATION/authProviders/bq-auth-provider",
    scopes=["https://www.googleapis.com/auth/bigquery"],
    continue_uri="https://vertexaisearch.cloud.google.com/validateUserId",
)
bigquery_mcp_tools = McpToolset(
    connection_params=StreamableHTTPConnectionParams(
        url="https://bigquery.googleapis.com/mcp"
    ),
    auth_scheme=auth_scheme,
)

効果: 初回アクセス時のみ Gemini Enterprise が同意を求め、以降はユーザーの権限で安全にクエリを実行。監査ログもユーザーとエージェント双方に紐付く。

🔗 ユースケース 2: Jira / GitHub などサードパーティ SaaS との連携エージェント

シナリオ: 開発支援エージェントが、ユーザーの Jira アカウントでチケットを作成したり、GitHub リポジトリの情報を参照したりする。

効果: auth manager の 3LO auth provider が各 SaaS との OAuth フローとトークン保管を肩代わりし、Gemini Enterprise が同意 UI を自動提供。エージェント開発者は AuthenticatedFunctionTool でトークンを受け取って API を呼ぶだけでよい。

🗂️ ユースケース 3: Agent Registry 経由の MCP サーバー利用

シナリオ: プラットフォームチームが Agent Registry に MCP サーバーとアウトバウンド auth provider のバインディングを登録し、各エージェント開発者は AgentRegistry.get_mcp_toolset で統一的にツールを取得。

効果: 認証設定が Registry 側に集約され、エージェントごとの設定の重複や設定ミスを削減できる。
