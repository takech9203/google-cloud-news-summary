🛡️ CodeMender v0.17.0 アップデート

Gemini Enterprise Agent Platform Preview v0.17.0 Changed / Fixed
リリース日: 2026-10-28

📋 概要

Gemini Enterprise Agent Platform 上で提供される AI コードセキュリティエージェント CodeMender が v0.17.0 にアップデート。 CodeMender はコードベースの脆弱性をスキャン (cm find)、検証 (cm verify)、修正 (cm fix) する自律型エージェントで、 推論は Google Cloud 側のホスト型エージェント、コードの読み取り・ビルド・PoC 実行はローカルの cm CLI サンドボックス内で行われる。

v0.17.0 は 運用性 (operability) と CI/CD 統合の強化が中心のリリース。 診断情報を一括収集する cm support-bundle、装飾を抑止する --plain 出力、 認証・構成の失敗を Finding と区別する専用終了コード、 Cloud Logging 連携向けの cm stats --jsonl が追加された。 セキュリティ面でも --unrestricted フラグが --sandbox=false とコマンドポリシーに分離され、 .git/hooks 等の読み取り専用マウントでリポジトリポリシーの改変が防止される。

❌ Before: アップデート前の課題

  • 環境メタデータ・構成ポリシー・ヘルスレポート・セッションログを個別に収集する必要があり、サポート情報収集に手間
  • CLI 出力に絵文字・ANSI エスケープ・Unicode 罫線が含まれ、スクリーンリーダーや CI/CD ログと互換性に問題
  • 構成・認証の失敗に専用終了コードがなく、CI/CD が環境問題をセキュリティ Finding と混同する可能性
  • CI/CD 環境でも対話型ログインプロンプトが表示され、環境に応じた認証ガイダンスがない
  • cm stats に Cloud Logging 向けの単一行 JSON 形式がない
  • --unrestricted がサンドボックス無効化と実行安全性コントロール無効化を兼ね、多義的 (overloaded)
  • サンドボックス内で .git/hooks・.git/config・.codemender が変更可能で、ポリシー改変のリスク

✅ After: アップデート後の改善

  • 新コマンド cm support-bundle で診断情報を圧縮アーカイブとして一括収集
  • 永続フラグ --plain (環境変数 CM_PLAIN / config.yaml の output.plain) で装飾なし出力が可能に
  • 構成・認証の失敗に専用終了コード (認証情報の問題はコード 10 など) を割り当て、CI/CD で区別可能に
  • GitHub Actions・GitLab CI・Buildkite・Jenkins では環境固有の認証ガイダンスを表示
  • cm stats --jsonl でモデル・チーム属性付きの単一行 JSON を出力、Cloud Logging にシームレス統合
  • --sandbox=false + コマンドポリシーに分離され、個別制御が可能に
  • cm fix / cm verify 中は .git/hooks 等が読み取り専用マウントで改変防止

💡 ポイント: v0.17.0 では、CI/CD パイプラインを起点とした自動実行の信頼性 (専用終了コード・プレーン出力・認証ガイダンス)、サンドボックスの安全性 (フラグ分離・読み取り専用マウント)、運用の可観測性 (cm support-bundle・cm stats --jsonl) が一体的に強化された。

⚙️ 主要機能

🧰 1. サポートバンドル診断 (cm support-bundle)

環境メタデータ、構成ポリシー、ヘルスレポート、セッションログを 1 つの圧縮アーカイブとして収集する新コマンド。トラブルシューティングに必要な情報収集を一括化し、サポートへの連携や障害解析を効率化する。

📝 2. プレーン出力モード (--plain)

永続フラグ --plain により、装飾的な絵文字・ANSI エスケープシーケンス・Unicode 罫線の出力を抑止。環境変数 CM_PLAIN、または config.yaml の output.plain でも設定可能。スクリーンリーダー (アクセシビリティ) や CI/CD ログパイプラインとの互換性を確保する。

🚦 3. セットアップ失敗の専用終了コード

構成・認証の失敗に対して固有の終了コード (認証情報の問題はコード 10 など) を割り当て。CI/CD パイプラインが「環境セットアップの問題」と「セキュリティ Finding の検出」を終了コードで区別できるようになった。

🔑 4. CI/CD 向け認証ガイダンス

GitHub Actions、GitLab CI、Buildkite、Jenkins などの自動化された CI/CD システム内で実行されている場合、対話型ログインプロンプトの代わりに環境固有の認証ガイダンスを表示する。

📊 5. 単一行 JSONL 統計 (cm stats --jsonl)

cm stats に --jsonl フラグが追加され、モデル・チーム属性付きの単一行 JSON レコードを出力可能に。Cloud Logging やログ集約パイプラインへのシームレスな統合が可能になった。

🔀 6. サンドボックス/ポリシーフラグの分離

多義的だった --unrestricted フラグを、直交するフラグ (--sandbox=false) と構成可能なコマンドポリシーに置き換え。コンテナサンドボックス (OS レベル分離) と実行安全性コントロール (コマンドポリシー) を個別に制御できるようになった。

🔒 7. サンドボックス構成の保護

cm fix / cm verify の実行中、書き込み可能な実行サンドボックス内でも .git/hooks・.git/config・.codemender を読み取り専用でマウント。エージェントや実行されるツールによるリポジトリセキュリティポリシーの改変を防止する。

🐛 8. バグ修正

  • サンドボックス分離の無効化と対話型承認のスキップが同時に行われた状態でのコマンド実行時に、セキュリティ警告を表示
  • ホスト側のファイル検出・修復ファイル操作全体で allowedRoots のパス境界を強制し、宙に浮いたシンボリックリンク (dangling symlink) 経由のパストラバーサルを防止
  • cm fix 実行時に Finding の正確な行範囲を修復エージェントに供給し、手動ファイルスキャンのオーバーヘッドを排除
  • cm report import で位置情報のない Finding を先頭行デフォルトではなくファイルレベルの Finding として扱うよう修正
  • cm session cancel が、ローカル環境のオーバーライドに関係なくセッションの元のリージョンへリクエストをルーティングするよう修正
  • cm verify の Finding ステータス追跡を修正し、「悪用不可 (unexploitable)」の判定がローカル状態データベースに反映されるように (従来は Finding がオープンのまま残存)

💪 メリット

💼 ビジネス面

  • CI/CD 運用の信頼性向上: 専用終了コードにより環境セットアップの問題が Finding として誤検知されなくなり、分岐処理やアラートの精度が向上。環境固有の認証ガイダンスで認証トラブルの解決も迅速に
  • トラブルシューティングの効率化: cm support-bundle により障害解析やサポート連携に必要な情報を 1 コマンドで収集、問題解決までの時間を短縮
  • アクセシビリティの向上: --plain モードはスクリーンリーダー利用者への配慮であり、組織のアクセシビリティ要件にも対応しやすい

🔧 技術面

  • ログ基盤との統合: cm stats --jsonl の単一行 JSON を Cloud Logging に直接取り込め、チーム別・モデル別の利用状況を既存の可観測性基盤で分析可能
  • セキュリティ制御の明確化: --unrestricted の廃止により、「サンドボックスは無効化するがコマンドポリシーは維持」といった粒度の細かい制御が可能に
  • リポジトリポリシーの保護: .git/hooks・.git/config・.codemender の読み取り専用マウントで、実行中のポリシー改変リスクを排除
  • パストラバーサル対策: allowedRoots 境界の強制により、dangling symlink 経由でスキャン対象外のホストパスへアクセスされるリスクを低減

⚠️ デメリット・制約事項

🚧 制限事項

✗CodeMender は Preview (Pre-GA) であり、限定された顧客向けの提供。商用・本番目的での利用は不可で、テスト・評価目的に限定される
✗解析対象は、自身が所有または利用を許可されたコード、もしくは OSI 承認ライセンスで配布される OSS に限られる

🤔 考慮すべき点

⚠️ --unrestricted フラグの置き換えに注意: v0.17.0 で --unrestricted は直交フラグ (--sandbox=false) と構成可能なコマンドポリシーに置き換えられた。既存のスクリプトや CI/CD 設定で --unrestricted を使用している場合は、新しいフラグ体系への移行が必要。

⚠️ 終了コードに依存するパイプラインの確認: セットアップ失敗に専用終了コードが割り当てられたため、終了コードを判定している既存の CI/CD パイプラインは、新しいコード体系 (認証情報の問題 = コード 10 など) に合わせた分岐の見直しを推奨。

⚠️ サンドボックス無効化 + 承認スキップ: この組み合わせでの実行にはセキュリティ警告が表示される。実行する場合は、隔離された VM やコンテナ内での実行が推奨される。

🎯 ユースケース

🤖 ユースケース 1: GitHub Actions でのスキャン自動化の堅牢化

シナリオ: GitHub Actions 上で cm find を定期実行しているが、認証情報の期限切れによる失敗が「スキャン失敗」として扱われ、原因の切り分けに時間がかかっていた。また、ログに ANSI エスケープや絵文字が混ざり可読性が低かった。

YAML 
# GitHub Actions ステップの例
- name: CodeMender scan
  env:
    CM_PLAIN: "1"   # 装飾なし出力で CI ログを読みやすく
  run: |
    cm find . || status=$?
    if [ "${status:-0}" -eq 10 ]; then
      echo "::error::CodeMender credential issue (exit code 10)"
      exit 1
    fi

効果: 専用終了コードにより環境起因の失敗を Finding と区別して fail-fast でき、CI/CD 環境では環境固有の認証ガイダンスが表示されるため復旧も速い。CM_PLAIN によりログの可読性と後処理の安定性が向上する。

📊 ユースケース 2: Cloud Logging でのチーム別利用状況の可視化

シナリオ: 複数チームで CodeMender を共用しており、モデル別・チーム別のトークン利用状況をログ基盤で横断的に把握したい。

Bash 
# 単一行 JSON レコードをログパイプラインへ送出
cm stats --jsonl >> /var/log/codemender/stats.jsonl

効果: モデル・チーム属性付きの単一行 JSONL は Cloud Logging やログ集約パイプラインでそのまま構造化ログとして取り込めるため、チーム別のコスト配賦や利用傾向のダッシュボード化が容易になる。

🧰 ユースケース 3: 障害発生時のサポートバンドル収集

シナリオ: cm fix が特定リポジトリで失敗するが、原因が構成・認証・セッションのいずれにあるか切り分けられない。

Bash 
# 環境メタデータ・構成ポリシー・ヘルスレポート・セッションログを一括収集
cm support-bundle

効果: トラブルシューティングに必要な情報が 1 つの圧縮アーカイブにまとまるため、個別のログ収集作業が不要になり、障害解析やサポートへの情報提供が迅速化する。

📝 まとめ

CodeMender v0.17.0 は、cm support-bundle による診断情報の一括収集、--plain 出力、専用終了コード、cm stats --jsonl といった CI/CD・運用統合の強化と、--unrestricted の分離 (--sandbox=false + コマンドポリシー) や .git/hooks 等の読み取り専用マウントによるサンドボックスの安全性強化を同時に実現するアップデートである。

既存ユーザーは、--unrestricted を使用しているスクリプトの移行と、終了コードを判定する CI/CD パイプラインの分岐見直しを行いつつ、 CM_PLAIN と --jsonl を活用したログ基盤統合を進めることを推奨する。
