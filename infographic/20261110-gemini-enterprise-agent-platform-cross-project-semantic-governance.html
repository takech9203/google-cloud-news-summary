🛡️ セマンティックガバナンスポリシーのクロスプロジェクトガバナンス

複数プロジェクトの AI エージェントをハブ & スポークで一元統制
Gemini Enterprise Agent Platform 管理境界は Preview 📅 リリース日: 2026-11-10

📋 概要

セマンティックガバナンスポリシーがマルチプロジェクト (ハブ & スポーク) アーキテクチャに対応。 複数の Google Cloud プロジェクトに分散した AI エージェントを、中央の管理プロジェクト (ハブ) から一元的に統制できるようになりました。

Resource Manager で AGENT_MANAGEMENT ケーパビリティを持つ管理境界 (management boundary) を構成すると、 中央の Agent Registry が全メンバープロジェクトのエージェントをランタイム ID (principal://...) を保持したまま自動検出。 管理プロジェクトに単一の Agent Gateway とポリシーエンジンを置くだけで、自然言語制約 (NLC) によるツール呼び出しの許可 / 拒否判定を組織全体に適用できます。

❌ Before: プロジェクトごとの重複管理

  • 単一プロジェクト内の統制が前提で、プロジェクトごとに Agent Gateway とポリシーエンジンをプロビジョニングする必要があった
  • 同じビジネスルールを各プロジェクトで重複して作成・保守
  • エージェントの可視化には各プロジェクトを個別に照会

✅ After: ハブからの一元統制

  • 管理プロジェクトの単一の Gateway + ポリシーエンジンで境界内の全エージェントを統制
  • 中央で作成したポリシーがバインド済みの全エージェントに適用、メンバー側のプロビジョニング不要
  • Agent Registry の自動検出でプロジェクト横断の一覧・検索 (クエリロールアップ) が可能

中央の管理プロジェクト (ハブ) に配置した Agent Registry・Agent Gateway・ポリシーエンジンが、各メンバープロジェクト (スポーク) のエージェントを自動検出し、 すべてのモデル / ツール呼び出しを単一のポリシー適用ポイントで統制するハブ & スポーク構成です。

⚡ 主要機能

1️⃣ 管理境界によるクロスプロジェクト自動検出

  • Resource Manager の BoundaryConfig / Boundary / CapabilityConfig で管理境界を構成し、AGENT_MANAGEMENT (gcloud: agent-management) ケーパビリティを有効化
  • Agent Registry が全メンバープロジェクトの Agent Runtime エージェント (Reasoning Engine)、Cloud Run サービス、GKE デプロイメントなどを自動検出し、ランタイム ID (principal://...) を保持したまま集約
  • CapabilityConfig 作成時に agentregistry.googleapis.com が自動的に有効化

2️⃣ 単一 Agent Gateway + ポリシーエンジンによる集中統制

  • 管理プロジェクトに Gateway とポリシーエンジンを 1 セットだけプロビジョニングすれば、同一リージョン内のメンバープロジェクトのエージェントをまとめて統制
  • 管理プロジェクトで定義したポリシーが、そのゲートウェイにバインドされた全メンバープロジェクトのエージェントに適用
  • メンバープロジェクト側でのエンジンのプロビジョニングやポリシー作成は不要

3️⃣ ランタイムでのセマンティック評価 (従来機能の拡張)

  • Agent Gateway がエージェント ⇔ モデル間、エージェント ⇔ ツール間の通信をインターセプトし、提案されたツール呼び出しをポリシーエンジン (PDP) に送信
  • ユーザー意図・会話履歴・自然言語制約に照らしてセマンティック分析を行い、ALLOW / DENY を判定
  • 判定結果は Cloud Logging に構造化ログ (verdict、rationale、token_usage) として記録、Cloud Trace によるトレースにも対応

🛠️ 設定方法

💡 前提条件:
  • 管理プロジェクトで必要な API を有効化 (aiplatform.googleapis.com、agentregistry.googleapis.com、networkservices.googleapis.com、networksecurity.googleapis.com、compute.googleapis.com、dns.googleapis.com)
  • 管理プロジェクトに Agent Gateway をセットアップ済み (サービス ID と必要な IAM ロールを含む)
  • Google 管理バインディングを使う場合、Gemini Enterprise Agent Platform サービスアカウント (P4SA) に roles/compute.networkAdmin と roles/dns.admin を付与
1

管理境界を構成する

組織またはフォルダに AGENT_MANAGEMENT ケーパビリティ付きの管理境界 (Boundary + CapabilityConfig) を構成し、中央ガバナンスプロジェクトを管理プロジェクト、エージェントワークロードのプロジェクトをメンバープロジェクトとして指定。これにより管理プロジェクトの Agent Registry が、全メンバーのエージェントをランタイム ID を保持したまま自動検出します。

2

クロスプロジェクトのゲートウェイアクセスを付与する

管理プロジェクトで、各メンバープロジェクトの Agent Runtime サービスエージェントに networkservices.agentGateways.get と networkservices.operations.get を付与 (カスタムロール ar_agw_cross_project_sa の利用例がドキュメントに記載)。

3

メンバープロジェクトのエージェントを中央ゲートウェイにバインドする

各エージェントを identity_type=AGENT_IDENTITY でデプロイし、agent_to_anywhere_config.agent_gateway に管理プロジェクトの Agent Gateway リソースを指定。

Text Agent Gateway リソース指定 
projects/MANAGEMENT_PROJECT_ID/locations/LOCATION/agentGateways/GATEWAY_NAME
4

管理プロジェクトでポリシーエンジンをプロビジョニングしポリシーを作成する

セマンティックガバナンスポリシーエンジンをプロビジョニング (通常 2〜3 分、最大 20 分) し、Agent Gateway に接続した上で、自然言語制約によるポリシーを作成します。

Bash ポリシーエンジンのプロビジョニング (Google 管理バインディングの例) 
# ポリシーエンジンのプロビジョニング (Google 管理バインディングの例)
gcloud beta ai semantic-governance-policy-engine update \
  --location=LOCATION \
  --project=MANAGEMENT_PROJECT_ID \
  --gateway-config="name='GATEWAY_NAME',network=NETWORK_NAME,subnetwork=SUBNETWORK_NAME,dns-zone-name=DNS_NAME"

# ポリシーの作成は Google Cloud コンソールの
# [Semantic governance policies] ページ、または
# gcloud beta ai semantic-governance-policies create で実施
✅ ベストプラクティス: ポリシーエンジンの LLM は誤判定の可能性があるため、本番適用前にドライランモードを有効にし、 Logs Explorer で判定結果 (logName="projects/PROJECT_ID/logs/semantic-governance-policy") を確認してから適用することが推奨されています。

🎯 メリット

💼 ビジネス面

✓ガバナンスの一元化: 調達ルールや金額上限などのビジネスルールを管理プロジェクトで一度定義すれば、組織内の全エージェントに一貫して適用でき、コンプライアンス統制が容易に
✓チームの自律性と統制の両立: 各チームは自プロジェクトで自由に開発・デプロイしつつ、ガバナンスチームは他プロジェクトへの直接アクセスなしに統一的な可視性と統制を維持 (マルチテナント分離)
✓運用コストの削減: プロジェクトごとのエンジン運用・ポリシー重複管理が不要になり、ポリシー変更もコード再デプロイなしに自然言語で即時反映

⚙️ 技術面

✓自動検出とランタイム ID の保持: attested RuntimeIdentity (principal://...) 付きで自動検出され、ID ベースの統制がプロジェクト境界を越えて機能
✓単一の適用ポイント: Agent Gateway でユーザー意図との整合性検証、コンテキストポイズニング対策、不正アクション (rogue action) 防止を集中実施
✓可観測性: verdict・rationale・トークン消費量を Cloud Logging に記録、Cloud Trace でレイテンシとポリシー適用を追跡。トポロジーグラフでクロスプロジェクトのエージェント関係と VPC Service Controls 境界の遵守も可視化

⚠️ デメリット・制約事項

制限事項

✗クロスプロジェクト管理境界 (Agent Registry の boundaries) は Preview 段階で、Pre-GA 利用規約が適用される
✗管理プロジェクトとメンバープロジェクトのエージェントは同一リージョンに存在する必要がある
✗ポリシーエンジンの対応リージョンは限定的 (Americas 4 + Europe 4 リージョン)
✗ストリーミングレスポンス非対応。ストリーミングで返されたツール呼び出しはブロックされない可能性がある
✗identity_type と agent_gateway_config はイミュータブルのため、要件を満たさない既存エージェントは再デプロイが必要
✗1 プロジェクトは親フォルダ / 組織ごとに最大 1 つの境界にしか所属できない

考慮すべき点

  • 判定は LLM に基づくため誤判定の可能性があり、ドライランモードでの事前検証が推奨される
  • 制約やパラメータは拒否理由 (rationale) としてエンドユーザーに表示され得るため、機密情報を制約文に含めない
  • IAM・レート制限・Model Armor などの既存セキュリティ機構を置き換えるものではなく補完するレイヤーとして設計する
  • ポリシー評価のたびにエンジン側の LLM トークンを消費する (消費量は Cloud Logging で確認可能)

💡 ユースケース

🧾 ユースケース 1: 組織全体のエージェント支出統制

シナリオ: 複数の部門がそれぞれのプロジェクトで調達・経費精算エージェントを運用しており、全社共通の承認ルール (「1,000 ドルを超える発注は承認確認なしに実行しない」など) を一貫して適用したい。

Text 自然言語制約の実装例 
管理プロジェクトのセマンティックガバナンスポリシー (自然言語制約):
- 「金額が 1,000 ドルを超える発注ツールの呼び出しは、
   会話内で承認者の確認が明示されていない限り拒否する」
対象: 全エージェント (Apply constraints to all tools)

効果: 各部門のプロジェクトにポリシーを個別配布することなく、中央の 1 つのポリシーで全部門のエージェントの発注アクションを統制。ルール変更時もエージェントの再デプロイは不要。

🏢 ユースケース 2: マルチテナント型エージェントプラットフォームの運営

シナリオ: プラットフォームチームが社内向けのエージェント基盤を提供し、各開発チームは自チームのメンバープロジェクトでエージェントを開発・デプロイ。プラットフォームチームは他チームのプロジェクトへ直接アクセスせずに、全エージェントのインベントリ管理とガードレール適用を行いたい。

効果: Agent Registry のクエリロールアップで全エージェントを一元的に検索・可視化しつつ、単一の Agent Gateway + ポリシーエンジンでコンテキストポイズニングや不正アクションを一括防御。チームごとの分離 (メンバープロジェクト間の相互アクセス不要) も維持される。

📋 Agent Registry: 管理境界内のエージェント・MCP サーバー・ツールを自動検出し、管理プロジェクトへ集約 (クエリロールアップ)。今回のクロスプロジェクトガバナンスの基盤
🚪 Agent Gateway: エージェント ⇔ モデル / ツール間通信のランタイム適用ポイント。ポリシーエンジンの判定に基づきツール呼び出しを許可 / 除去
🏢 Resource Manager (管理境界とケーパビリティ): BoundaryConfig / Boundary / CapabilityConfig リソースでプロジェクトのグルーピングと AGENT_MANAGEMENT ケーパビリティの有効化を行う

🛡️ Model Armor / IAM / VPC Service Controls: セマンティックガバナンスポリシーと組み合わせる多層防御 (プロンプトスキャン、アクセス制御、ネットワーク境界) を構成

📝 まとめ

今回のアップデートにより、セマンティックガバナンスポリシーが単一プロジェクトの枠を越え、ハブ & スポーク型のエンタープライズアーキテクチャで組織全体の AI エージェントを一元統制できるようになりました。 複数チーム・複数プロジェクトでエージェントを運用する組織は、Resource Manager の管理境界と AGENT_MANAGEMENT ケーパビリティの構成を検討し、 まずドライランモードでポリシー判定を検証した上で中央集権型ガバナンスへの移行を進めることを推奨します。
