🌐 Agent Gateway for cross-cloud

EKS / AKS / OpenShift / ベアメタル上のエージェントを Google Cloud から一元ガバナンス
Gemini Enterprise Agent Platform Limited Preview AI エージェント
📅 リリース日: 2026-11-11

📋 概要

Agent Platform のガバナンス機能を Google Cloud 外の CNCF 準拠 Kubernetes クラスタ (Amazon EKS、Azure AKS、Red Hat OpenShift、ベアメタル) 上のエージェントにまで拡張する機能が Limited Preview になりました。

最大の特徴は「エージェントは今の場所で動かし続けながら、ガバナンスは 1 か所 (Google Cloud) から行う」こと。 各エージェントに検証可能なアイデンティティを付与し、エージェントと MCP サーバーを Agent Registry に登録。 LLM / MCP / A2A トラフィックをローカルの Agent Gateway プロキシ (Envoy ベース) 経由でルーティングし、 アクセス制御と Model Armor 安全性ポリシーを適用、ログ / トレースを Cloud Logging / Cloud Trace に送信します。

❌ Before: アップデート前の課題

  • Agent Gateway は Google Cloud 上のランタイム (Agent Runtime、Gemini Enterprise) 向けのみ。Google Cloud 外のエージェントはガバナンス対象外
  • EKS / AKS / OpenShift / ベアメタルに分散したエージェントに、クラウドごとの個別実装が必要でポリシーの一貫性維持が困難
  • 外部エージェントのログ / トレースを Cloud Logging / Cloud Trace に集約する標準手段がなく、統一的な可視化が困難

✅ After: アップデート後の改善

  • CNCF 準拠 Kubernetes クラスタなら Google Cloud 外のエージェントもガバナンス対象に
  • Workload Identity Federation で K8s 認証情報を Agent Identity と交換し、検証可能なアイデンティティを付与
  • 中央定義したアクセスポリシー + Model Armor をローカルの Envoy ベースプロキシが適用
  • ログ / トレースを Cloud Logging / Cloud Trace に送信し、Agent Registry / Observability を全エージェントに拡張
🎯 主な対象: マルチクラウドや自社データセンターでエージェントを運用しつつ、 1 つのガバナンスポリシー・1 つのレジストリ・1 つの可観測性ビューで統制したい エンタープライズのプラットフォームチーム / セキュリティチーム。利用には アクセス申請フォーム からのリクエストが必要です。

Google Cloud 側の管理プレーンでアイデンティティ・レジストリ・ポリシーを一元管理し、 外部クラスタ内にデプロイした Envoy ベースの Agent Gateway プロキシがローカルでポリシーを適用します。 エージェントのトラフィック自体は外部環境内に留まり、 Model Armor スクリーニングなど設定したポリシーチェックのみが Google Cloud に送信されます。

⚡ 主要機能

1️⃣ CNCF 準拠 Kubernetes クラスタへのガバナンス拡張

→Amazon EKS、Azure AKS、Red Hat OpenShift、自社データセンターのベアメタルクラスタなど、Google Cloud 外の Kubernetes クラスタ上のエージェントが対象
→エージェントの稼働場所を変えずに、Google Cloud からガバナンスを一元管理
→軽量な Envoy ベースのプロキシと関連コンポーネントを自身のクラスタにデプロイする自己管理型プロキシモデル

2️⃣ 検証可能なエージェントアイデンティティ

→Workload Identity Federation を通じて Kubernetes ワークロード認証情報を Agent Identity 認証情報と交換
→各エージェントに検証可能なアイデンティティを付与し、アイデンティティベースのアクセス制御を実現

3️⃣ Agent Registry への登録と Agent-to-Anywhere トラフィックのガバナンス

→外部クラスタ上のエージェントと MCP サーバーを Agent Registry に登録
→LLM、MCP、A2A トラフィックを既存のサービスメッシュ / ネットワークスタックでローカルの Agent Gateway プロキシへルーティング
→中央で定義したアクセスポリシーと Model Armor 安全性ポリシーをプロキシが適用

4️⃣ Agent Observability の拡張

→アクセスログを Cloud Logging へ、エージェントトレースを Cloud Trace へ送信
→マルチクラウドに分散したエージェント活動を Google Cloud 上で統一的に可視化

📡 サポートされるプロトコル

Agent Gateway は、すべてのデプロイモデルで標準的な HTTP ベースのエージェント通信プロトコルをサポートします。

プロトコル内容
MCP (Model Context Protocol)SSE または HTTP POST によるアウトバウンド / インバウンドの MCP ツール呼び出しをガバナンス。JSON-RPC リクエストを検査してツール名とメソッド属性を抽出し、ツール単位の細かなアクセスポリシーを適用可能
A2A (Agent-to-Agent)エージェント間のタスク委譲・実行 API をガバナンス
REST / gRPCHTTP/1.1 および HTTP/2 (gRPC) トラフィックをサポート
⚠️ 制限事項 (Agent Gateway 全般): Agent Gateway インスタンス 1 つにつき、Agent Registry に登録されたリソースを最大 5,000 までガバナンス可能。

🛠️ 設定方法

✅ 前提条件

✓Limited Preview のため、アクセス申請フォームからリクエストして承認を受けていること
✓CNCF 準拠の Kubernetes クラスタ (EKS / AKS / OpenShift / ベアメタルなど) でエージェントが稼働していること
✓Workload Identity Federation を構成する権限 (roles/iam.workloadIdentityPoolAdmin、roles/iam.serviceAccountAdmin など) があること
✓エージェントトラフィックをローカルプロキシへルーティングできるネットワーク構成 (既存のサービスメッシュ等) があること

ステップ 1: Workload Identity Federation の構成

Bash 外部クラスタを OIDC プロバイダとして登録 
# 例: EKS クラスタの OIDC issuer URL を確認
aws eks describe-cluster --name CLUSTER_NAME \
  --query "cluster.identity.oidc.issuer" --output text

# Workload Identity Pool を作成
gcloud iam workload-identity-pools create POOL_ID \
  --location="global" \
  --display-name="DISPLAY_NAME"

# 外部クラスタを OIDC プロバイダとして追加
gcloud iam workload-identity-pools providers create-oidc PROVIDER_ID \
  --location="global" \
  --workload-identity-pool="POOL_ID" \
  --issuer-uri="ISSUER_URL" \
  --attribute-mapping="MAPPINGS"

外部クラスタの Kubernetes ServiceAccount トークンを Google Cloud の認証情報と交換できるようにし、エージェントに検証可能な Agent Identity を付与します (AKS の場合は OIDC issuer 機能の有効化が必要)。

ステップ 2: Agent Registry への登録とゲートウェイの構成

Bash Agent Gateway 管理コマンド 
# Agent Gateway の管理には gcloud network-services agent-gateways を使用
gcloud network-services agent-gateways --help

Google Cloud 側の管理プロジェクトでエージェントと MCP サーバーを Agent Registry に登録し、アクセスポリシーや Model Armor テンプレートを定義します。

ステップ 3: ローカルプロキシのデプロイとトラフィックルーティング

軽量な Envoy ベースの Agent Gateway プロキシと関連コンポーネントを外部クラスタにデプロイし、既存のサービスメッシュ / ネットワークスタックを使ってエージェントの LLM / MCP / A2A トラフィックをプロキシ経由にルーティングします。

💡 メリット

💼 ビジネス面

✓マルチクラウド戦略とガバナンスの両立: エージェントを EKS / AKS / オンプレミスなど最適な場所で運用し続けながら、セキュリティ・コンプライアンス統制は Google Cloud に一元化
✓移行不要でガバナンスを導入: エージェントの再配置やアプリケーションコードの変更を前提とせず、既存のクラスタ環境にガバナンスレイヤーを追加
✓Limited Preview 期間中は無償: 本機能自体は無料で利用でき、低リスクで評価を開始可能

⚙️ 技術面

✓単一のポリシー・レジストリ・可観測性ビュー: 全クラウドのエージェントに 1 つのガバナンスポリシー、1 つの Agent Registry、Cloud Logging / Cloud Trace による 1 つの可視化基盤を適用
✓データ主権への配慮: エージェントトラフィック自体は自環境内に留まり、設定したポリシーチェックのみが Google Cloud へ送信
✓プロトコルレベルの細かな制御: MCP の JSON-RPC 検査によりツール名・メソッド属性ベースの認可を適用。A2A / REST / gRPC にも対応
✓標準技術ベース: Envoy プロキシ + Workload Identity Federation という実績ある標準技術の組み合わせで、既存サービスメッシュと統合可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Limited Preview のため、アクセス申請フォームによるリクエストと承認が必要
✗対象は CNCF 準拠の Kubernetes クラスタに限定
✗Agent Gateway インスタンス 1 つあたり、Agent Registry 登録リソースは最大 5,000 まで
✗Preview 段階の機能であり、機能や提供時期は変更される可能性がある

🤔 考慮すべき点

⚠️外部クラスタ内のプロキシインフラは自己管理であり、デプロイ・運用・アップグレードの責任はユーザー側
⚠️エージェントトラフィックをゲートウェイへルーティングするクラスタネットワーキング設計 (サービスメッシュ等) はユーザーの責任範囲
⚠️Model Armor、Cloud Logging、Cloud Trace など組み合わせるサービスは各サービスの標準料金で課金
⚠️ポリシーチェックは Google Cloud への呼び出しを伴うため、外部クラスタから Google Cloud API へのネットワーク到達性とレイテンシを考慮

🎯 ユースケース

🏢 ユースケース 1: マルチクラウド企業におけるエージェントガバナンスの一元化

シナリオ: AWS (EKS) と Azure (AKS) の両方で LLM エージェントを運用している企業が、クラウドごとにバラバラだったエージェントのアクセス制御・プロンプト安全性対策・監査ログを統一したい。

Text 実装例 
1. Google Cloud に管理プロジェクトを用意し、Workload Identity Federation で
   EKS / AKS の各クラスタを OIDC プロバイダとして登録
2. 各クラスタのエージェントと MCP サーバーを Agent Registry に登録
3. アクセスポリシーと Model Armor テンプレートを管理プロジェクトで一元定義
4. 各クラスタに Envoy ベースの Agent Gateway プロキシをデプロイし、
   LLM / MCP / A2A トラフィックをプロキシ経由にルーティング

効果: クラウドごとの個別実装を排除し、全エージェントに一貫した最小権限ポリシーと Model Armor による安全性スクリーニングを適用。監査ログとトレースは Cloud Logging / Cloud Trace に集約され、監査対応が簡素化される。

🏭 ユースケース 2: オンプレミス (OpenShift / ベアメタル) エージェントの可視化と統制

シナリオ: データ主権要件により自社データセンターの OpenShift クラスタでエージェントを稼働させているが、エージェントがどのツール (MCP サーバー) をいつ呼び出しているかを可視化し、未承認ツールへのアクセスを防ぎたい。

効果: エージェントトラフィックはデータセンター内に留めたまま、MCP の JSON-RPC 検査によるツール単位のアクセス制御を適用。アクセスログとトレースのみを Cloud Logging / Cloud Trace に送信し、データ主権を維持しながらエージェント活動を可視化できる。

🔗 関連サービス・機能

📒 Agent Registry
エージェントと MCP サーバーを登録する中央レジストリ。本機能により Google Cloud 外のエージェントも登録対象に拡張される。
🔑 Agent Identity / Workload Identity Federation
Kubernetes ワークロード認証情報を Google Cloud の検証可能なアイデンティティと交換する基盤。
🛡️ Model Armor
プロンプト / レスポンスの安全性スクリーニング。中央で定義したテンプレートをローカルプロキシが適用する。
📊 Cloud Logging / Cloud Trace
外部クラスタ上のエージェントのアクセスログとトレースの集約先 (Agent Observability)。
🚪 Agent Gateway on Google Cloud
Agent Runtime / Gemini Enterprise 向けの Google 管理型ゲートウェイ。GKE / Cloud Run 向けの自己管理型デプロイモデルも順次提供予定で、本機能はそのクロスクラウド版に相当する。
🧭 セマンティックガバナンスポリシー
前日 (2026-11-10) に発表されたクロスプロジェクトガバナンスと組み合わせることで、マルチプロジェクト + マルチクラウドの統合ガバナンスが視野に入る。

📌 まとめ

Agent Gateway for cross-cloud は、Google Cloud のエージェントガバナンス (Agent Identity、Agent Registry、ポリシー適用、可観測性) を EKS / AKS / OpenShift / ベアメタルといった Google Cloud 外の Kubernetes 環境へ拡張する戦略的なアップデートです。

マルチクラウドやオンプレミスでエージェントを運用する組織は、エージェントを移行することなく統一ガバナンスを導入できます。 Limited Preview 中は無償のため、該当環境を持つプラットフォーム / セキュリティチームはアクセス申請のうえ、 Workload Identity Federation とローカルプロキシ構成の検証から始めることを推奨します。
