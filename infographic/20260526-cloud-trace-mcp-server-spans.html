📋 概要

リモート MCP (Model Context Protocol) サーバーが tools/call オペレーションに対してトレーススパンを自動生成する機能がリリースされました。エージェント型 AI アプリケーションが MCP サーバーを介して Google Cloud サービスを呼び出す際の動作を Cloud Trace で可視化・分析できるようになります。

BigQuery と Cloud SQL の MCP サーバーがこのトレーススパン生成をサポートし、アプリケーション側で W3C Trace Context 標準に準拠したトレースコンテキストを MCP リクエストの _meta フィールドに含めることで、MCP サーバー側でスパンが生成され、Cloud Trace に送信されます。

❌ Before (アップデート前)

  • MCP サーバー経由のツール呼び出し内部がブラックボックス
  • レイテンシの原因特定が困難
  • エージェント失敗原因の切り分け情報不足
  • MCP クライアント/ネットワーク/サーバー間のレイテンシ判別不可

✅ After (アップデート後)

  • tools/call スパン自動生成で Cloud Trace Explorer に可視化
  • W3C Trace Context によるエンドツーエンド分散トレーシング
  • OpenTelemetry Semantic Conventions 準拠のスパン命名
  • フィルタリング・分析が容易

⚡ 主要機能

1. tools/call スパン自動生成

→ リモート MCP サーバーが tools/call オペレーション受信時に自動的にトレーススパンを生成
→ スパン名は OpenTelemetry Semantic Conventions 準拠: tools/call NAME 形式
→ 認証済み・認可済みリクエストに対してのみスパン生成

2. W3C Trace Context による分散トレーシング

→ MCP リクエストの params._meta に traceparent を含めてコンテキスト伝播
→ HTTP ヘッダーの traceparent でもコンテキスト伝播が可能
→ エージェントアプリのスパンと MCP サーバーのスパンが同一トレース内で関連付け

3. 豊富なスパン属性

→ gen_ai.tool.name: 呼び出された MCP ツール名
→ mcp.method.name: MCP オペレーション名
→ mcp.protocol.version: MCP プロトコルバージョン
→ error.message / error.type: エラー発生時の詳細
→ gcp.mcp.server.id: MCP サーバーの URN

トレースコンテキストの形式

JSON MCP リクエストに traceparent を含める例 
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "execute_sql_readonly",
    "arguments": {
      "project_id": "my-project",
      "sql": "SELECT * FROM dataset.table LIMIT 10"
    },
    "_meta": {
      "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
      "tracestate": "gcp=project:my-project"
    }
  },
  "id": 1
}

🛠️ 設定方法

前提条件:
  • Cloud Trace API が有効化されていること
  • 対象の MCP サーバー API (BigQuery API / Cloud SQL Admin API) が有効
  • OpenTelemetry SDK または ADK を使用していること

Step 1: OpenTelemetry SDK のセットアップ

Python TracerProvider の設定 
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

# TracerProvider の設定
provider = TracerProvider()
processor = BatchSpanProcessor(
    OTLPSpanExporter(endpoint="https://telemetry.googleapis.com")
)
provider.add_span_processor(processor)
trace.set_tracer_provider(provider)

Step 2: MCP クライアントでのトレースコンテキスト伝播

Python トレースコンテキストを MCP リクエストに付与 
from opentelemetry import trace
from opentelemetry.trace.propagation.tracecontext import TraceContextTextMapPropagator

tracer = trace.get_tracer("my-agent-app")

with tracer.start_as_current_span("agent-tool-call") as span:
    # トレースコンテキストを抽出
    carrier = {}
    TraceContextTextMapPropagator().inject(carrier)

    # MCP リクエストに _meta フィールドとしてコンテキストを付与
    mcp_request = {
        "jsonrpc": "2.0",
        "method": "tools/call",
        "params": {
            "name": "execute_sql_readonly",
            "arguments": {"project_id": "my-project", "sql": "SELECT 1"},
            "_meta": {
                "traceparent": carrier.get("traceparent")
            }
        },
        "id": 1
    }

Step 3: ADK を使用する場合

💡 ADK (Agent Development Kit) を使用している場合: OpenTelemetry 統合が内蔵されているため、設定するだけでトレースコンテキストが自動的に伝播されます。詳細は ADK ドキュメントを参照してください。

✅ メリット

ビジネス面

🎯 本番運用信頼性向上: MCP ツール呼び出しの成功率やレイテンシを定量的に測定・監視でき、SLA/SLO の設定と維持が容易に
⏱️ 障害対応時間の短縮: ツール呼び出しの失敗原因を即座に特定でき、MTTR を大幅に削減
💰 コスト最適化: レイテンシの高いツール呼び出しを特定し、クエリの最適化やアーキテクチャの改善に活用

技術面

🔍 エンドツーエンドの可視性: エージェントアプリから MCP サーバーまでの完全な分散トレース
📐 標準規格準拠: W3C Trace Context + OpenTelemetry Semantic Conventions for MCP に準拠
⚙️ 自動インストルメンテーション: MCP サーバー側のスパン生成は自動、サーバー側のコード変更不要

⚠️ 制限事項・注意点

  • tools/call オペレーションのみがスパンを生成 (他の MCP オペレーションは対象外)
  • MCP サーバーは単一のスパンのみ生成 (子スパンなし、内部処理フロー追跡不可)
  • W3C Trace Context 標準のみサポート (X-Cloud-Trace-Context ヘッダー非サポート)
  • sampled フラグが 1 の場合のみスパン生成
  • 認証・認可チェック失敗時はスパン未生成の場合あり
  • スパン取り込み量増加により Cloud Trace 費用増加の可能性 (サンプリング戦略の検討が必要)

🔧 ユースケース 2: エラーの根本原因分析

シナリオ: Cloud SQL ツール呼び出しの断続的な失敗の原因切り分け。

効果: error.type と error.message 属性により、接続プール枯渇が原因と特定。max_connections 調整で解決。

効果: 単一トレース ID で両サービスのスパンが関連付けられ、ウォーターフォールビューで SLO 遵守を継続監視。
