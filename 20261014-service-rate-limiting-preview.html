📏 サービスレートリミットポリシー (Preview)

リリース日: 2026-10-14
☁️ Cloud Load Balancing 🛡️ Google Cloud Armor 🌐 Secure Web Proxy Preview
信頼できるクライアントの過剰消費を抑え、重要トラフィックの可用性を最大化する新しいサービスレベルのレート制御

📝 概要

Google Cloud は サービスレートリミットポリシー (Service rate limiting policies) を Preview として発表。リージョン内部アプリケーションロードバランサと Secure Web Proxy の 2 つのターゲットで利用でき、Cloud Armor もサービスレートリミットをサポートします。

従来の Cloud Armor レートリミットが「ネットワークエッジで信頼できないクライアントによる DDoS 攻撃を防ぐ」ことを主眼としていたのに対し、サービスレートリミットは「信頼できるが行儀の悪い (misbehaving) クライアントを管理し、重要なトラフィックの可用性を最大化する」仕組みです。しきい値を超えたクライアントのみをスロットリングし、過負荷時にも重要なクライアントトラフィックを優先します。

🎯 対象ユーザー: マイクロサービス間の内部通信でリソース枯渇を防ぎたいプラットフォームチーム、Secure Web Proxy 経由のアウトバウンド通信 (LLM API 呼び出しなど) のコストと流量を制御したいセキュリティ・ネットワーク管理者

❌ Before: アップデート前の課題

  • Cloud Armor のレートリミットは外部向け LB のエッジでの不正クライアント対策が中心で、内部 ALB を通る「信頼できる内部クライアント」同士の公平なリソース配分を制御する仕組みがなかった
  • Secure Web Proxy でアウトバウンドトラフィックへのクライアント別・サービス全体のレート制限ができず、LLM プロバイダ等への大量呼び出しによるコスト増・外部先過負荷のリスクがあった
  • 過負荷時に重要クライアントを優先しつつ過剰消費クライアントのみを抑制するサービスレベルの優先制御が利用できなかった

✅ After: アップデート後の改善

  • リージョン内部 ALB の転送ルールにポリシーをアタッチし、しきい値超過クライアントをスロットリングして重要トラフィックを優先できる
  • Secure Web Proxy のゲートウェイにポリシーをアタッチし、アウトバウンドの過負荷防止とコスト管理 (例: LLM トークンコスト) が可能に。認可ポリシー / ゲートウェイセキュリティポリシーのどちらのゲートウェイでも利用可
  • Cloud Armor セキュリティポリシーと組み合わせた多層的なレート制御を実現
  • mTLS クライアント証明書 Common Name や送信元 IP などのクライアント識別子単位でリクエスト数ベースの制限を設定可能

サービスレートリミットポリシーは、リージョン内部アプリケーションロードバランサの転送ルールまたは Secure Web Proxy のゲートウェイにアタッチします。しきい値を超えたクライアントのリクエストはスロットリングされ、重要なトラフィックの可用性が維持されます。

⚡ 主要機能

1️⃣ リージョン内部アプリケーションロードバランサでのサービスレートリミット Preview

→ポリシーを転送ルールにアタッチし、過剰にリソースを消費する信頼済みクライアントをスロットリング
→サービス過負荷時に重要なクライアントトラフィックを優先し、サービス可用性を維持
→リクエストに適用されるフィルタの 1 種として、他のフィルタと所定の順序で評価される

2️⃣ Secure Web Proxy でのサービスレートリミット Preview

→アウトバウンド Web トラフィックにクライアント別・サービス全体のレート制限を適用し、外部宛先の過負荷防止とコスト管理を実現
→認可ポリシー、ゲートウェイセキュリティポリシーのいずれを使用するゲートウェイにもアタッチ可能
→mTLS プリンシパル (クライアント証明書 Common Name) や送信元 IP アドレスなどのクライアント識別子に基づく、リクエスト/分単位の制限を設定可能

3️⃣ Cloud Armor によるサービスレートリミットのサポート Preview

→Cloud Armor レートリミット (エッジでの DDoS・不正クライアント対策) とサービスレートリミット (信頼クライアントの管理) を使い分け・併用可能
→セキュリティポリシーで不正クライアントを明示的に遮断しつつ、サービスレートリミットで信頼クライアントの過剰消費を抑制する多層防御を構成できる

ステップ 1: API の有効化

BashAPI の有効化
gcloud services enable \
    networksecurity.googleapis.com \
    networkservices.googleapis.com

ステップ 2: ポリシーを YAML で定義

LLM プロバイダ (foo.com) への送信を、クライアント証明書の Common Name で識別したエージェントごとに毎分 100 リクエストに制限する例です。

YAMLmy-rate-limit-policy.yaml
name: "projects/PROJECT_ID/locations/LOCATION/rateLimitPolicies/test-policy"
description: "Simple agent for LLM rate limiting."
httpRules:
  - to:
      destination:
        hosts:
          - exact: "foo.com"
    rateLimitActions:
      - rateLimitBucket: "rl_default_rpm_limit"
rateLimitBuckets:
  - name: "rl_default_rpm_limit"
    keys:
      - keyType: PRINCIPAL
        principalType: CLIENT_CERT_COMMON_NAME
    defaultLimit:
      countLimit:
        count: 100
        interval: 1
        intervalUnit: MINUTES
targets:
  - resource: "projects/PROJECT_ID/locations/LOCATION/gateways/GATEWAY_NAME"

ステップ 3: ポリシーのインポート

Bashポリシーのインポート (gcloud alpha)
gcloud alpha network-security rate-limit-policies import test-policy \
    --source=my-rate-limit-policy.yaml \
    --location=LOCATION

YAML をインポートすると、targets に指定した Secure Web Proxy ゲートウェイにポリシーが適用されます。

💡 メリット

💼 ビジネス面

✓サービス可用性の維持: 一部クライアントによる過剰なリソース消費時にも、重要なクライアントのトラフィックを優先してサービス全体の停止を防げる
✓アウトバウンドコストの管理: Secure Web Proxy 経由の外部 API 呼び出し (LLM トークンコストなど) に上限を設け、予期しないコスト増を抑制できる

⚙️ 技術面

✓信頼クライアント向けのきめ細かな制御: mTLS プリンシパルや送信元 IP などのクライアント識別子単位で制限を設定でき、エージェントやワークロードごとの公平なリソース配分が可能
✓多層的なレート制御: Cloud Armor セキュリティポリシー (エッジでの不正クライアント遮断) とサービスレートリミット (サービスレベルでの信頼クライアント管理) を組み合わせられる
✓運用の可観測性: Cloud Logging にスロットリング結果が記録され、ログベースアラートで検知できる

⚠️ デメリット・制約事項

🚧 制限事項

✗Preview 段階の機能であり、Pre-GA Offerings Terms が適用される。サポートが限定される可能性があり、本番環境での利用は慎重に判断する必要がある
✗対応ターゲットはリージョン内部アプリケーションロードバランサと Secure Web Proxy に限定される
✗転送ルール/ゲートウェイごとにアタッチできるポリシーは 1 つ、ポリシーごとの HTTP ルールは 5 つまでなど、各種上限がある (技術仕様の表を参照)
✗Secure Web Proxy のポリシーインポートは gcloud alpha コマンドで提供される
⚠️ 考慮すべき点:
  • サービスレートリミットは「信頼できるクライアントの管理」用。不正クライアントや DDoS 対策には従来どおり Cloud Armor セキュリティポリシー / レートリミットを使用する
  • クライアント証明書ベースの識別 (CLIENT_CERT_COMMON_NAME) を使う場合は、事前にフロントエンド mTLS の構成が必要
  • レートリミットの適用は近似的な動作となる場合があるため、厳密なクォータやライセンス制御ではなく、過負荷防止・可用性維持の用途で使用することが推奨される

🎯 ユースケース

🏢 ユースケース 1: 内部マイクロサービスにおける重要トラフィックの優先

シナリオ: 複数の内部クライアント (バッチ処理、分析ジョブ、オンライン API) が同一のバックエンドサービスをリージョン内部 ALB 経由で呼び出している。バッチ処理が大量のリクエストを発行すると、オンライン API のレイテンシが悪化する。

実装例: ポリシーを内部 ALB の転送ルールにアタッチし、クライアント識別子ごとにしきい値を設定。しきい値を超えたバッチ処理クライアントのみスロットリングする。

効果: サービス過負荷時でもオンライン API などの重要トラフィックが優先され、サービス全体の可用性が維持される。

🤖 ユースケース 2: AI エージェントの LLM API 呼び出しコスト制御

シナリオ: 多数の AI エージェントが Secure Web Proxy 経由で外部 LLM プロバイダの API を呼び出しており、特定エージェントの暴走によるトークンコストの急増や、外部 API のクォータ枯渇が懸念される。

実装例: クライアント証明書の Common Name でエージェントを識別し、エージェントごとに毎分 100 リクエストの上限を設定したポリシーを Secure Web Proxy ゲートウェイにアタッチする (設定方法のステップ 2 参照)。

効果: エージェント単位で外部 API 呼び出しが制限され、暴走時のコスト増と外部サービスへの過負荷を防止。スロットリング発生はログベースアラートで検知できる。

✨ まとめ

サービスレートリミットポリシーの Preview 提供により、エッジでの DDoS 対策 (Cloud Armor) に加えて、内部アプリケーションロードバランサと Secure Web Proxy という「サービスレベル」での信頼クライアント管理が可能になりました。特に AI エージェントからの LLM API 呼び出しコスト制御や、内部マイクロサービスの公平なリソース配分といった現代的な課題に直接応える機能です。Preview 段階のため本番適用は慎重に判断しつつ、まずは検証環境でポリシー設計とログベースアラートの構成を試すことをお勧めします。
