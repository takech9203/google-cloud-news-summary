🔄 継続的クエリで SQL UDF がサポート

リアルタイム変換ロジックをカプセル化し、バッチとストリーミングで再利用
📅 リリース日: 2026-11-03

📝 概要

BigQuery の継続的クエリ (Continuous Queries) で、永続 (persistent) および一時 (temporary) の SQL ユーザー定義関数 (UDF) が利用可能になりました。 リアルタイムデータ処理におけるカスタム変換ロジックを UDF としてカプセル化し、複数の継続的クエリ間で再利用できます。

継続的クエリは、BigQuery テーブルに到着するデータを継続的に処理し、結果を BigQuery テーブル、Pub/Sub、Bigtable、Spanner などへリアルタイムに出力する機能です。 従来はクエリ本文に変換ロジックを直接記述する必要がありましたが、SQL UDF でロジックを部品化し、ストリーミングパイプラインの保守性と再利用性を高められるようになりました。

⚠️ 注意: 継続的クエリでサポートされるのは SQL UDF のみです。JavaScript UDF や Python UDF は引き続き利用できません。

❌ Before: アップデート前の課題

  • 継続的クエリでは UDF が非サポートで、ドキュメント上も明示的に非サポートの SQL 機能として記載されていた
  • カスタム変換ロジック (クレンジング、正規化、マスキングなど) をクエリごとに本文へ直接記述し、重複記述が発生
  • UDF を参照するビューも対象外のため、既存のバッチクエリ資産をリアルタイム処理に流用しづらかった

✅ After: アップデート後の改善

  • CREATE FUNCTION で作成した永続 SQL UDF を継続的クエリから呼び出し、バッチ / リアルタイムの両方で共通ロジックを再利用可能に
  • CREATE TEMP FUNCTION による一時 SQL UDF で、単一クエリ内の複雑な式を関数として整理可能に
  • ロジック変更時の修正箇所が UDF 定義のみで済み、ストリーミングパイプラインの保守性が向上

継続的クエリが BigQuery テーブルへの新着データをリアルタイムに処理する際、SQL UDF にカプセル化した変換ロジックを呼び出し、結果を BigQuery / Pub/Sub / Bigtable / Spanner へ出力する構成です。

⚙️ 主要機能

1️⃣ 永続 SQL UDF のサポート

→CREATE FUNCTION dataset.function_name(...) で作成した SQL UDF を継続的クエリから呼び出し可能
→データセット単位で UDF を管理し、複数の継続的クエリや通常のバッチクエリ間でロジックを共有
→UDF 定義を更新するだけでロジックを一元的に変更可能 (実行中ジョブへの反映にはジョブの再起動が必要)

2️⃣ 一時 SQL UDF のサポート

→CREATE TEMP FUNCTION を継続的クエリの SQL 内で定義して利用可能
→単一クエリ内に閉じた複雑な式の整理や、デプロイ単位を自己完結させたい場合に有効

3️⃣ SQL UDF のみサポート (スコープの明確化)

✓継続的クエリでサポートされるのは SQL 式で定義された UDF のみ
✗JavaScript UDF は継続的クエリでは利用不可

💻 SQL UDF の例 (継続的クエリでの利用イメージ)

SQL 永続 UDF の定義と継続的クエリからの呼び出し 
-- 永続 SQL UDF: 共通の変換ロジックをデータセットに定義
CREATE OR REPLACE FUNCTION mydataset.mask_email(email STRING)
RETURNS STRING
AS (
  CONCAT(SUBSTR(email, 1, 2), '***@', SPLIT(email, '@')[SAFE_OFFSET(1)])
);

-- 継続的クエリから永続 UDF を呼び出してリアルタイム変換
INSERT INTO mydataset.masked_events (event_id, masked_email, event_time)
SELECT
  event_id,
  mydataset.mask_email(email) AS masked_email,
  event_time
FROM mydataset.raw_events;

📋 前提条件

✓Enterprise または Enterprise Plus エディションで、CONTINUOUS 割り当てタイプの予約 (Reservation) を作成済みであること
✓継続的クエリを長時間 (最大 150 日) 実行する場合はサービスアカウントでの実行を構成すること (ユーザーアカウントでは最大 2 日)
✓永続 UDF を使う場合、クエリ対象データと同じリージョンのデータセットに UDF を作成しておくこと

ステップ 1: 永続 SQL UDF を作成する

SQL 変換ロジックをデータセットに登録 
CREATE OR REPLACE FUNCTION mydataset.normalize_amount(amount NUMERIC, currency STRING)
RETURNS NUMERIC
AS (
  CASE currency
    WHEN 'JPY' THEN amount
    WHEN 'USD' THEN amount * 150
    ELSE NULL
  END
);

ステップ 2: 継続的クエリから UDF を呼び出す

Bash --continuous=true で継続的クエリとして実行 
bq query --use_legacy_sql=false \
  --job_timeout_ms=0 \
  --continuous=true \
  'INSERT INTO mydataset.normalized_sales (id, amount_jpy, ts)
   SELECT id, mydataset.normalize_amount(amount, currency), ts
   FROM mydataset.raw_sales'

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓開発・保守コストの削減: 変換ロジックを UDF として一元管理し、仕様変更時の修正箇所を最小化、変更リードタイムを短縮
✓バッチとリアルタイムのロジック統一: 既存バッチクエリの SQL UDF をリアルタイム処理でも共有し、集計結果の不整合リスクを低減

🔬 技術面のメリット

✓ロジックのカプセル化と再利用: 複雑な変換式を関数化し、クエリの可読性が向上
✓ガバナンスの向上: 永続 UDF はデータセット単位で権限管理・共有でき、標準化された変換ロジックをチーム横断で提供

🚧 制限事項

✗SQL UDF のみ利用可能で、JavaScript UDF は利用不可
✗Enterprise / Enterprise Plus エディションの予約 (CONTINUOUS) が必須。オンデマンド課金では実行不可
✗CONTINUOUS 割り当ての予約は最大 500 スロット (上限緩和は問い合わせが必要)
✗実行中の継続的クエリの SQL は変更不可。UDF 更新の反映にはジョブの再起動が必要

🤔 考慮すべき点

⚠️永続 UDF はクエリ実行リージョンごとに作成・維持が必要 (クロスリージョンのデータセットレプリケーションで同期する方法もある)
⚠️一時的な障害時の自動再処理で重複データが発生する可能性があるため、下流システムは冪等に設計する
⚠️UDF に複雑なロジックを詰め込みすぎるとスループットやスロット消費に影響するため、処理内容はシンプルに保つ

🎯 ユースケース

🔒 ユースケース 1: PII マスキングの標準化によるリアルタイムデータ共有

シナリオ: EC サイトのイベントストリームを BigQuery に取り込み、個人情報 (メールアドレス、電話番号) をマスキングした上で分析用テーブルと Pub/Sub 経由の下流システムにリアルタイム配信。マスキングルールは全社共通で管理。

SQL 全社共通の永続 SQL UDF を呼び出し 
INSERT INTO analytics.masked_events (event_id, masked_email, event_time)
SELECT
  event_id,
  security_ds.mask_email(email),  -- 全社共通の永続 SQL UDF
  event_time
FROM raw.events;

効果: マスキングロジックを security_ds データセットの UDF に集約することで、ルール変更時も UDF の更新 (+ ジョブ再起動) だけで全パイプラインに適用でき、コンプライアンス対応が容易になる。

📈 ユースケース 2: バッチとリアルタイムで共通の KPI 変換ロジックを利用

シナリオ: 日次バッチ集計で使用している売上正規化 UDF (通貨換算、税抜処理など) を、リアルタイムダッシュボード向けの継続的クエリでも使用し、バッチとリアルタイムで数値の定義を一致させる。

効果: 同一の SQL UDF を両方のパイプラインで参照することで、集計定義の二重管理を排除し、ダッシュボードと日次レポートの数値不整合を防止できる。

💰 料金

SQL UDF の利用自体に追加料金はありません。継続的クエリは容量ベース課金 (BigQuery Editions) のみに対応しており、Enterprise または Enterprise Plus エディションの予約で消費したスロットに対して課金されます。オンデマンド課金 (スキャン量ベース) は利用できません。

🌏 利用可能リージョン

継続的クエリがサポートされるリージョンについては、BigQuery のロケーション (continuous query locations) を参照してください。

🔗 関連サービス・機能

→📨 Pub/Sub: 継続的クエリの EXPORT DATA 先。UDF で変換したデータをリアルタイムに下流アプリケーションへ配信
→⚡ Bigtable / Spanner: 継続的クエリの出力先として、低レイテンシなサービングレイヤー (リバース ETL) を構築
→🎟️ BigQuery Reservations (Editions): 継続的クエリの実行に必須の CONTINUOUS 割り当てタイプの予約を管理
→🤖 BigQuery ML / 生成 AI 関数: 継続的クエリでは AI.GENERATE や ML.TRANSLATE などもサポートされており、SQL UDF と組み合わせたリアルタイム AI パイプラインを構築可能

✨ まとめ

継続的クエリで SQL UDF が利用可能になり、これまでクエリごとに重複記述していたリアルタイム変換ロジックをカプセル化・再利用できるようになりました。バッチとストリーミングで変換定義を統一できるため、BigQuery 上でストリーミングパイプラインを運用しているチームは、共通ロジックの UDF 化によるパイプラインの整理を検討することを推奨します。JavaScript UDF は対象外である点にのみ注意が必要です。
