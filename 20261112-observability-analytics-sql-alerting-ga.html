🚨 SQL ベースのアラートポリシーが GA

Observability Analytics の SQL クエリ結果を Cloud Monitoring で監視
Cloud Monitoring Cloud Logging Cloud Trace GA (一般提供)
📅 リリース日: 2026-11-12

📋 概要

Observability Analytics の SQL クエリ結果を直接アラート条件にできる「SQL ベースのアラートポリシー」が GA (一般提供) になりました。Google Cloud コンソールまたは Cloud Monitoring API から作成でき、Cloud Monitoring / Cloud Logging / Cloud Trace の各リリースノートで同時に発表されています。

ポリシーは SQL クエリ + 評価条件 (condition) + 実行スケジュール (schedule) で構成されます。指定した間隔 (例: 60 分ごと) でクエリが実行され、ルックバックウィンドウ内のデータを集計・分析し、条件を満たすと Cloud Monitoring がアラートを作成して通知チャネル経由で通知します。

💡 ポイント: 複数のログエントリにまたがる集計値 (エラー率、件数など) を正確に評価したい場合に最も効果的な方式です。個々のログエントリを評価したい場合は、従来のログベースのアラートポリシーが引き続き推奨されます。

🔄 Before / After

❌ アップデート前の課題

  • 複数のログエントリにまたがる集計分析 (例: エラー率 25% 超) を SQL で直接評価してアラートする手段が GA として提供されていなかった
  • ログベースの指標は発生件数が少ないイベントの監視には不向きで、SQL の柔軟な集計・結合ロジックを条件に使えなかった
  • トレースデータ (スパン) の集計分析結果に基づいてアラートを作成する標準的な方法がなかった

✅ アップデート後の改善

  • SQL クエリ結果 (行数しきい値または boolean 列) を条件としてアラートを作成でき、GA として本番環境で利用可能に
  • コンソールと Cloud Monitoring API (alertPolicies.create の conditionSql / SqlCondition) の両方で作成・管理が可能に
  • ログに加え、トレースデータ (_Trace バケットの _AllSpans ビュー) にも SQL ベースのアラートを構成可能に

⚡ 主要機能

1️⃣ SQL クエリ結果に基づくアラート条件 (GA)

Observability Analytics の SQL クエリの結果テーブルを条件として評価し、アラートを作成。複数のログエントリにまたがる正確な集計値 (件数、割合など) の評価に最適。1 つのポリシーに設定できる条件は 1 つ。

2️⃣ 2 種類の評価タイプ

行数しきい値 (Row count threshold): クエリ結果の行数がしきい値より大きい/等しい/小さい場合に条件成立 (例: severity > 200 のログが 50 件を超えたら通知)。
Boolean: クエリ結果の特定の boolean 列に true の行が含まれる場合に条件成立 (例: ERROR の割合が 25% を超えたら notify 列に true を書き込み通知)。

3️⃣ スケジュールとルックバックウィンドウ

スケジュールでクエリの実行頻度を定義 (分・時間・日単位の periodicity)。ルックバックウィンドウは前回評価以降に受信したデータのみを選択するフィルタ (例: スケジュール 60 分なら直近 60 分のデータが対象)。

4️⃣ コンソールと API の両方をサポート

Google Cloud コンソールから作成できるほか、Cloud Monitoring API の alertPolicies.create メソッドで条件タイプ conditionSql (SqlCondition) を指定してプログラマティックに作成可能。

5️⃣ トレースデータへの対応 (Cloud Trace)

_Trace という Observability バケット上の _AllSpans ビューに SQL クエリを実行し、トレースデータの集計分析結果に基づいてアラートを作成可能。

ステップ 1: SQL 条件を含むアラートポリシーを定義

alertPolicies.create メソッドで、条件タイプに conditionSql (SqlCondition) を指定します。スケジュールは minutes / hours / days のいずれかに periodicity を設定し、条件は boolean_test (boolean 列に true が含まれる場合に成立) または row_count_test (結果行数がしきい値を満たす場合に成立) を設定します。

ステップ 2: 通知チャネルを設定

アラートポリシーに通知チャネルのリストを設定します。条件が成立すると Cloud Monitoring がアラートを作成し、これらのチャネル経由で通知します。

💡 トラブルシューティング: コンソールのアラート詳細ページでは、クエリ実行履歴や結果テーブル、BigQuery のスキャン推定バイト数・スロット消費時間 (直近 7 日間のクエリに基づく) を確認できます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓集計ベースの SLO/品質監視: エラー率などビジネス上意味のある集計値を直接アラート条件にでき、ノイズの少ない通知運用が可能
✓GA による本番適用: 一般提供となり、本番環境の監視基盤として安心して採用できる

🔧 技術面のメリット

✓SQL の表現力: 複雑な集計・比率計算・複数エントリにまたがる評価を SQL で柔軟に記述できる
✓ログとトレースの統一的な監視: _AllSpans ビューへのクエリでトレースデータも同じ仕組みで監視
✓API による自動化: SqlCondition を使った API 経由で IaC やスクリプトによる一括管理が可能
✓データ複製不要: リンクされた BigQuery データセットは読み取り専用ポインタのため、データ複製や追加の BigQuery ストレージ料金なしで構成できる

🚧 制限事項

✗1 ポリシーにつき条件は 1 つのみ
✗アナリティクスビューに対するクエリは不可
✗クエリ実行時間は 5 分以内 (超過すると失敗)
✗アラート作成まで最大 7 分 + 実行時間の遅延があり、リアルタイム性が求められる検知には不向き

🤔 考慮すべき点

→クエリは BigQuery エンジン上で実行されるため、オンデマンドスロット (またはスロット予約) の料金が発生。スキャン量の大きいクエリを短い間隔で実行するとコスト増
→個々のログエントリ (セキュリティイベントなど) の検知には、引き続きログベースのアラートポリシーが適する
→リンクされた BigQuery データセットへのクエリは BigQuery の権限レイヤで評価されるため、データセットへのアクセス権を持つプリンシパルはすべてのビューをクエリ可能な点に注意
→Monitoring サービスアカウントの権限が失われるとクエリが失敗するため、失敗ログを検知するログベースのアラートの併用が望ましい

🎯 ユースケース

📊 ユースケース 1: エラーログ割合のしきい値監視

シナリオ: アプリケーションのログ全体に対する severity が ERROR のログの割合が 25% を超えた場合にオンコール担当者へ通知したい。

手順 Boolean 評価タイプの実装例 
1. ルックバックウィンドウ内のログエントリのうち ERROR の割合を計算する SQL クエリを作成
2. 割合が 25% を超えた場合に notify 列へ true を書き込むようにクエリを構成
3. 評価タイプ Boolean で notify 列を監視する条件を作成し、通知チャネルを設定

効果: 単発のエラーではなく「エラー率」という集計値で判定するため、ノイズを抑えつつサービス品質の劣化を検知できる。

🔢 ユースケース 2: 高 severity ログの件数監視

シナリオ: ルックバックウィンドウ内に severity が 200 (INFO) を超えるログエントリが 50 件を超えたら通知したい。

効果: 評価タイプ「行数しきい値」を使い、該当ログを返すクエリの結果行数をしきい値 50 で判定するだけで、ログベースの指標を別途作成せずに件数ベースの監視を実現できる。

🔍 ユースケース 3: トレースデータの集計分析に基づくアラート

シナリオ: Cloud Trace に取り込まれたスパンの集計分析結果 (特定条件のスパンの傾向など) に基づいて通知を受けたい。

効果: _Trace バケットの _AllSpans ビューに対する SQL クエリを条件にアラートポリシーを作成でき、トレースデータについてもログと同じ仕組みで集計ベースの監視ができる。

💰 料金

SQL ベースのアラートポリシーのクエリは BigQuery エンジン上で実行され、デフォルトではオンデマンドスロットが使用されます (スロット予約の構成も可能)。

  • 💳 BigQuery の料金
  • 💳 Google Cloud Observability の料金 (Cloud Logging / Cloud Monitoring のセクション)
💡 コストの可視化: コンソールのアラート詳細ページでは、直近 7 日間のクエリに基づくスキャン推定バイト数とスロット消費時間を確認できます。

🔗 関連サービス・機能

🪵 Cloud Logging (Observability Analytics)

SQL クエリの実行基盤。ログバケットのアップグレードとリンクされた BigQuery データセットの作成が前提。

📈 Cloud Monitoring

アラートポリシーの作成・評価・アラート管理と通知を担当。alertPolicies.create API で SqlCondition をサポート。

🔍 Cloud Trace

_Trace Observability バケットの _AllSpans ビューを介してトレースデータへの SQL ベースのアラートを提供。

🗄️ BigQuery

リンクされたデータセットを通じてクエリを実行するエンジン。スロット予約によるコスト管理も可能。

📑 ログベースのアラートポリシー / ログベースの指標

個別ログエントリの検知やログの傾向監視に適した代替・補完手段。
