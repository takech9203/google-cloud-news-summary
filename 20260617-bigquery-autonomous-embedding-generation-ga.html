BigQuery: Autonomous Embedding Generation

BigQuery GA AI/ML
2026-06-17

📋 概要

BigQuery の Autonomous Embedding Generation が一般提供 (GA) となりました。CREATE TABLE または ALTER TABLE ステートメントを使用してテーブルを作成・変更する際に、自律的なエンベディング生成を有効化できます。

BigQuery がソースカラムに基づいてエンベディングカラムを自動的に維持し、ソースカラムのデータが追加・変更されると、対応するエンベディングも自動的に生成・更新されます。

🤖 対象ユーザー: BigQuery でベクトル検索やセマンティック検索を活用したいデータエンジニア、ML エンジニア、およびアプリケーション開発者

⚡ 主要機能

📝 DDL ベースの自動エンベディング生成

CREATE TABLE / ALTER TABLE ADD COLUMN で宣言的にエンベディングカラムを定義。GENERATED ALWAYS AS 句と AI.EMBED 関数を使用。

🔄 自動同期メカニズム

ソースカラムへのデータ追加・変更を BigQuery がバックグラウンドで自動検知し、DML ジョブとしてエンベディングを生成・更新。進捗は SQL で確認可能。

🧠 複数エンベディングモデルのサポート

Agent Platform エンドポイント (text-embedding-005, gemini-embedding-001 等) とビルトインモデル (embeddinggemma-300m) から選択可能。

🔍 AI.SEARCH との統合

エンベディング列を意識せず、ソースカラム名を指定するだけでセマンティック検索が可能。ベクトルインデックスと自動連携。

✅ メリット

ビジネス面

💰運用コストの削減 - エンベディング生成パイプラインの構築・維持が不要、インフラ運用の負担が大幅に軽減
🔄データ鮮度の向上 - ソースデータ更新と同時にエンベディングが更新、検索結果が常に最新
🚀Time to Market の短縮 - DDL のみで RAG アプリケーションの開発サイクルが短縮

技術面

📝宣言的な定義 - SQL DDL でエンベディング生成を定義、ETL パイプラインのコード不要
📈自動スケーリング - BigQuery のバックグラウンドジョブとしてデータ量に応じた自動スケール
🔀モデル選択の柔軟性 - Agent Platform (高精度) とビルトイン (低コスト・データローカリティ) を選択可能
🔗エコシステム統合 - Vector Index、AI.SEARCH、VECTOR_SEARCH とのシームレスな統合

⚠️ デメリット・制約事項

制限事項:
  • テーブルあたり自動生成エンベディングカラムは 最大 1 つ のみ
  • ソースカラムは STRING 型のみ 対応 (他のデータ型は不可)
  • エンベディングカラムへの直接書き込み (DML、ストリーミング、bq insert) は不可
  • テーブルのコピー・クローン・スナップショットでは生成設定がコピーされない
  • パーティション付きベクトルインデックスは作成不可
  • カラムレベルのセキュリティポリシー (ポリシータグ等) は非対応
考慮すべき点:
  • 並行 DML 操作はエンベディング生成の遅延や一時的な失敗を引き起こす可能性あり (バッチ投入推奨)
  • BigQuery Storage Write API 使用時はエンベディング生成開始までに遅延が発生する場合あり
  • エンベディング生成カラムの存在は Google Cloud コンソール、bq show、INFORMATION_SCHEMA.TABLES からは確認不可
  • スナップショットからのテーブル復元では、エンベディング生成設定は復元されない
  • エンベディングカラム作成後はソースカラムの削除・リネームが不可

🎯 ユースケース

🛒 ユースケース 1: EC サイトの商品セマンティック検索

シナリオ: 大規模 EC サイトで数百万件の商品説明テキストに対して、自然言語でのセマンティック検索を実装。商品情報は日々更新され、新商品も頻繁に追加される。

SQL EC サイト実装例 
-- 商品テーブルの作成
CREATE TABLE ecommerce.products (
  product_id STRING,
  name STRING,
  description STRING,
  description_embedding STRUCT<result ARRAY<FLOAT64>, status STRING>
    GENERATED ALWAYS AS (
      AI.EMBED(description,
        connection_id => 'us.my_connection',
        endpoint => 'text-multilingual-embedding-002')
    ) STORED OPTIONS(asynchronous = TRUE)
);

-- ベクトルインデックスの作成
CREATE VECTOR INDEX product_search_idx
ON ecommerce.products(description_embedding)
OPTIONS(index_type = 'IVF');

-- セマンティック検索の実行
SELECT * FROM AI.SEARCH(
  TABLE ecommerce.products,
  'description',
  '防水で軽量なランニングシューズ',
  top_k => 20
);

効果: 新商品追加や商品説明の更新時に自動的にエンベディングが更新され、検索結果に即座に反映。パイプライン管理のオーバーヘッドがゼロ。

📚 ユースケース 2: 社内ナレッジベースの RAG システム

シナリオ: 社内ドキュメントを BigQuery に蓄積し、RAG パターンで社内チャットボットのコンテキストとして活用。

SQL ナレッジベース実装例 (ビルトインモデル) 
-- ナレッジベーステーブルの作成 (ビルトインモデル使用)
CREATE TABLE knowledge.documents (
  doc_id STRING,
  title STRING,
  content STRING,
  content_embedding STRUCT<result ARRAY<FLOAT64>, status STRING>
    GENERATED ALWAYS AS (
      AI.EMBED(content, model => 'embeddinggemma-300m')
    ) STORED OPTIONS(asynchronous = TRUE)
);

-- 関連ドキュメントの検索
SELECT base.title, base.content, distance
FROM AI.SEARCH(
  TABLE knowledge.documents,
  'content',
  'クラウド移行のベストプラクティス',
  top_k => 5
);

効果: ビルトインモデルでデータが BigQuery 外に送信されず、データガバナンスを維持しつつ Agent Platform の追加コストなしにセマンティック検索を実現。

🎫 ユースケース 3: カスタマーサポートチケットの類似検索

シナリオ: 新規サポートチケットに対して過去の類似チケットを自動検索し、解決策の提案を行いたい。

効果: チケット登録と同時にエンベディングが生成されるため、リアルタイムに近い形で類似チケット検索が可能になり、初回応答時間の短縮に貢献。

  • ビルトインモデル: embeddinggemma-300m を使用すれば Agent Platform 料金不要
  • バッチ投入: データを小刻みに DML するのではなくバッチで投入し、バックグラウンドジョブの効率を向上
  • BACKGROUND 予約: 予測可能なパフォーマンスとコストが必要な場合は job_type = BACKGROUND の予約を作成

📌 まとめ

BigQuery Autonomous Embedding Generation の GA リリースにより、エンベディングの生成・管理が完全に BigQuery に統合され、外部パイプラインなしでセマンティック検索や RAG アプリケーションを構築できるようになりました。


特にビルトインモデル (embeddinggemma-300m) を使用すれば、データの外部送信なしに BigQuery スロットのみでエンベディング生成が可能であり、データガバナンスとコスト効率の両面で優れた選択肢です。


本番ワークロードで活用するために、まずは小規模なテーブルでの検証から開始し、ベクトルインデックスとの組み合わせによる検索パフォーマンスを評価することを推奨します。
