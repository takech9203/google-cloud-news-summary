📚 Knowledge Catalog: Governance Workflows

Knowledge Catalog (Dataplex) Preview
2026-07-24

📋 概要

Knowledge Catalog (旧 Dataplex) に、データプロダクトへのアクセス管理を自動化するためのGovernance Workflows機能が Preview として追加されました。データプロダクトへのアクセスに対してリクエスト-レビュー (承認/拒否) のメカニズムを提供し、組織のデータガバナンスを強化します。

承認後は IAM ロールやグループメンバーシップが自動的に付与されるため、手動での管理オーバーヘッドが大幅に削減されます。すべてのリクエスト、承認/拒否の判断、タイムスタンプが監査証跡として記録されます。

🏗️ アーキテクチャ図

Governance Workflows は、データコンシューマーからのアクセスリクエストを受け付け、データプロダクトオーナーによるレビューを経て、承認時に IAM ロールとグループメンバーシップを自動的にプロビジョニングします。

sequenceDiagram
    participant Consumer as データコンシューマー
    participant KC as Knowledge Catalog
    participant Workflow as Governance Workflows
    participant Owner as データプロダクトオーナー
    participant IAM as Cloud IAM
    participant Group as Google Groups

    Consumer->>KC: データプロダクトを検索・発見
    Consumer->>Workflow: アクセスリクエスト送信
    Workflow->>Owner: メール通知
    Owner->>Workflow: レビュー 承認/拒否
    alt 承認の場合
        Workflow->>IAM: IAM ロール自動付与
        Workflow->>Group: グループメンバーシップ追加
        Workflow->>Consumer: 承認通知
    else 拒否の場合
        Workflow->>Consumer: 拒否通知 理由付き
    end
    Note over Workflow: 監査証跡を自動記録

⚡ 主要機能

📨 アクセスリクエストの送信

→データプロダクトページから直接リクエスト可能
→アクセスグループ、プリンシパルタイプ、理由を指定
→REST API (dataProducts:requestAccess) でプログラマティック操作

✅ 一元的なレビュー・承認管理

→「Pending Approvals」タブで複数リクエストを一括管理
→個別データプロダクトからの承認/拒否も可能
→REST API (changeRequests:approve/reject) 対応

🔐 自動アクセスプロビジョニング

→ユーザー承認時: Google Group にメンバー自動追加
→SA 承認時: impersonation 権限を自動付与
→Approval log タブで処理済みリクエストの履歴確認

📊 リクエストステータス追跡

→「My requests」タブで全リクエストを一覧表示
→ステータス: New / Approved / Rejected
→ステータス更新時にメール通知を送信

🔧 技術仕様: IAM ロールと権限

ロール 用途
roles/dataplex.catalogViewer データプロダクトの検索
roles/dataplex.dataProductsConsumer データアセット検索とアクセスリクエスト送信
roles/dataplex.dataProductsViewer データプロダクトの定義・メタデータの読み取り専用
roles/dataplex.dataProductsEditor アクセスリクエストの承認
roles/dataplex.dataProductsAdmin データプロダクトの完全な管理権限
roles/dataplex.workflowApprover ワークフローでのリクエスト承認専用ロール
roles/dataplex.workflowAdmin Governance Workflows の管理

🛠️ 設定方法・コードサンプル

前提条件

✓Dataplex API が有効化されていること
✓承認者に適切な IAM ロールが付与されていること
✓データプロダクトが作成済みで、アクセスグループが設定されていること

Step 1: API の有効化

Bash 
gcloud services enable dataplex.googleapis.com --project=PROJECT_ID

Step 2: IAM ロールの付与

Bash 
# 承認者にワークフロー承認者ロールを付与
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="user:approver@example.com" \
  --role="roles/dataplex.workflowApprover"

# コンシューマーにデータプロダクトコンシューマーロールを付与
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="user:consumer@example.com" \
  --role="roles/dataplex.dataProductsConsumer"

Step 3: アクセスリクエストの送信 (REST API)

Bash 
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -d '{
    "parent": "projects/PROJECT_ID/locations/LOCATION/dataProducts/DATA_PRODUCT_ID",
    "change_request": {
      "justification": "JUSTIFICATION_TEXT",
      "data_product_access_request": {
        "parent": "projects/PROJECT_ID/locations/LOCATION/dataProducts/DATA_PRODUCT_ID",
        "access_group_id": "DATA_PRODUCT_ACCESS_GROUP_ID"
      }
    }
  }' \
  "https://dataplex.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/dataProducts/DATA_PRODUCT_ID:requestAccess"

Step 4: リクエストの承認 (REST API)

Bash 
# 保留中のリクエスト一覧取得
curl -X GET \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://dataplex.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/changeRequests:listReviewable"

# リクエストの承認
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://dataplex.googleapis.com/v1/projects/PROJECT_ID/locations/LOCATION/changeRequests/CHANGE_REQUEST_ID:approve"

💡 メリット

ビジネス面

✓コンプライアンス強化: 全アクセスリクエストと承認判断の監査証跡が自動記録
✓時間短縮: 手動チケットプロセス排除、承認後即座にアクセスプロビジョニング

✓管理オーバーヘッド削減: IAM ロール付与とグループ管理の自動化
✓API 対応: REST API で既存ワークフローとの統合が容易
✓一元管理: 複数データプロダクトのアクセスリクエストを単一画面で管理

⚠️ 制約事項・注意点

制限事項

!Preview 段階のため「Pre-GA Offerings Terms」が適用 (SLA 保証なし)
!REST API 経由での承認時は Group メンバーシップ/SA impersonation を手動設定が必要
!ビジネス用語集へのメタデータ変更リクエストは Private Preview (別途申請必要)

考慮すべき点

!アクセスグループの設計と Google Groups マッピングの事前計画が必要
!既存 ITSM ツール/チケットシステムからの移行計画が必要
!大規模組織では承認者の負荷集中を考慮した権限委譲設計が必要

🎯 ユースケース

🛒 小売業: マーケティングチームのデータアクセス

シナリオ: マーケティングマネージャーが顧客行動分析のために、リージョン別売上データプロダクトへのアクセスを申請

Bash 
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -d '{
    "parent": "projects/retail-analytics/locations/us-central1/dataProducts/regional-sales",
    "change_request": {
      "justification": "Q3 ターゲティング広告キャンペーンの顧客行動分析のため",
      "data_product_access_request": {
        "access_group_id": "marketing-analysts"
      }
    }
  }' \
  "https://dataplex.googleapis.com/v1/projects/retail-analytics/locations/us-central1/dataProducts/regional-sales:requestAccess"

効果: サポートチケット発行から承認・アクセス付与までの期間が数日から数分に短縮

🏦 金融業: リスク分析チームのコンプライアンス対応

シナリオ: リスクアナリストが不正検知モデル構築のために取引履歴データプロダクトへのアクセスを申請。承認フローの記録がコンプライアンス監査に活用。

効果: 全アクセスリクエストと承認判断が自動記録。監査対応時のエビデンス収集が効率化され、アクセス権付与の正当性を証明可能。

🏥 ヘルスケア: 研究データへの制御されたアクセス

シナリオ: 臨床研究アナリストが匿名化された患者アウトカムデータへのアクセスを申請。データプロダクトオーナーが研究目的とアクセスの必要性をレビュー。

効果: 機密医療データへのアクセスが適切に制御され、HIPAA 等の規制要件への準拠を証明する監査証跡が自動生成。

📝 まとめ

Knowledge Catalog の Governance Workflows は、データプロダクトへのアクセス管理をチケットベースの手動プロセスからセルフサービス型の自動化ワークフローに変革する重要な機能です。

承認後の IAM ロール自動付与と完全な監査証跡により、セキュリティとコンプライアンスを維持しながらデータ活用までの時間を大幅に短縮できます。

現在 Preview 段階のため、本番環境への適用前に機能の検証を行い、アクセスグループの設計と承認者の配置を計画することを推奨します。
