🔄 Firestore Pipeline DML オペレーションが GA

クエリ結果への挿入・更新・削除をサーバーサイドの 1 パイプラインで完結 — 新ステージ insert() / upsert() 追加

📋 概要

Firestore の Pipeline オペレーションにおける Data Manipulation Language (DML) が 一般提供 (GA) になりました。あわせて新しい出力ステージ insert() と upsert() が追加され、Pipeline クエリの末尾に DML ステージを接続して、 クエリ結果に対して直接サーバーサイドでドキュメントの挿入・更新・削除を実行できます。

Pipeline は Firestore Enterprise エディションの中核機能で、ステージベースの合成可能な構文により 集計・結合・複雑なフィルタリングなど高度なクエリを実現します。今回の GA により Pipeline は 「読み取り」だけでなく「書き込み」までを 1 本で完結でき、バックフィル・データ移行・条件付き一括削除 といった運用タスクをクエリ 1 本で記述できます。

😣 Before: アップデート前の課題

  • Pipeline はクエリ (読み取り) 中心。結果に基づく書き換えはクライアントで受け取り、ドキュメント API で個別書き込みが必要
  • 一括更新・移行は「読み取り → アプリ側で変換 → 書き込み」の往復が発生し、コードが複雑化
  • クエリ結果の別コレクションへの挿入や upsert を、サーバーサイドで宣言的に表現する手段がなかった

😊 After: アップデート後の改善

  • DML ステージ (insert() / upsert() / update() / delete()) が GA となり本番利用が可能に
  • insert() と upsert() の追加で、クエリ結果をそのまま別コレクションへ書き込む移行・コピーが 1 パイプラインで完結
  • DML をトランザクション内で実行可能。atomic オプションで自動実行・自動コミットも
  • トランザクション内なら where / addFields / union / findNearest / 集計サブクエリなど他ステージとの組み合わせに制限なし
🎯 対象ユーザー: Firestore Enterprise エディションを利用し、大量ドキュメントの一括変更・移行・クリーンアップを効率化したいアプリケーション開発者・データ運用担当者

Pipeline の末尾に DML ステージを接続することで、クエリ・変換・書き込みをサーバーサイドの 1 つのパイプラインとして実行できます。 insert() と upsert() は原則としてトランザクション内 (または atomic オプション付き) での実行が必要です。

⚡ 主要機能

1️⃣ insert() ステージ 新規追加

→クエリ結果やリテラル値を新規ドキュメントとして Firestore に追加する DML ステージ
→引数パターン: insert(collectionName, documentIdExpression) (式で ID 決定) / insert(collectionName) (ID 自動生成) / insert() (入力の __name__ で宛先と ID を決定)
→users/u1/posts のようなフルパス指定でサブコレクションへの直接挿入も可能
→挿入先に同一ドキュメントが既に存在する場合は ALREADY_EXISTS エラーで失敗
→パイプラインの最終ステージである必要があり、後続ステージは追加不可

2️⃣ upsert() ステージ 新規追加

→既存ドキュメントがあれば更新、なければ新規挿入する DML ステージ
→引数パターン: upsert(collectionName, documentIdExpression, ...transformations) / upsert(collectionName, ...transformations) / upsert(...transformations) (後者 2 つは入力の __name__ で ID / 宛先を決定)
→前段ステージが同一ドキュメント ID を複数生成した場合は「後勝ち (last one wins)」セマンティクスで順次処理

3️⃣ update() / delete() ステージ GA

→update(): クエリで絞り込んだドキュメントにフィールドの追加・変更を適用。入力に __name__ フィールドが必要で、対象が存在しない場合は失敗
→delete(): クエリ条件に一致するドキュメントを削除。誤削除防止のため少なくとも 1 つの where() を含めることを推奨

4️⃣ トランザクション実行と atomic オプション 🔒

→明示的な read-write トランザクション内で DML パイプラインを実行可能
→atomic オプション (Java では withAtomic(true)) で新しいトランザクション内で自動実行し、成功時に自動コミット
→insert() と upsert() はほとんどのケースでトランザクション内での実行が必要

🔧 技術仕様

📊 DML ステージの比較

ステージ 動作 同一 ID が複数回対象になった場合
insert() 新規ドキュメントを追加 (既存なら ALREADY_EXISTS エラー) 最初の試行で作成、以降は ALREADY_EXISTS で失敗
upsert() 既存なら更新、なければ挿入 後勝ち (last one wins)
update() 既存ドキュメントを変更 (存在しなければ失敗) 後勝ち (last one wins)
delete() ドキュメントを削除 最初の試行で削除、以降は no-op

⚖️ 実行モードによる挙動の違い

項目 🔒 トランザクション内 🔓 トランザクション外
原子性 トランザクションとして原子的にコミット ドキュメントごとに独立して書き込み (ドキュメント間の原子性なし)。最初のエラーで停止し、部分的成功が発生しうる
利用できるステージ 制限なし (where、addFields、union、findNearest、集計サブクエリなども利用可) 高度なマルチクエリステージ (aggregate、distinct、unnest、find_nearest、union、join、サブクエリ) は非対応
制約 Enterprise エディションのトランザクション上限に従う。書き込み後の読み取りは不可 (FAILED_PRECONDITION エラー) —

📨 レスポンス

DML ステージは変更したドキュメント数のサマリーを 1 ドキュメントとして返します。

JSON DML レスポンス例 
{ "documents_modified": 3 }

ステップ 1: クエリ結果を別コレクションへ upsert する

JavaScript Node.js — トランザクション内で upsert 
// users コレクションから age >= 25 のドキュメントを抽出し、
// processed フィールドを付与して new_users へ upsert (トランザクション内)
const results = await db.runTransaction(async (transaction) => {
  return transaction.execute(
    db.pipeline()
      .collection("users")
      .where(field("age").greaterThanOrEqual(25))
      .addFields(constant(true).as("processed"))
      .upsert({ collection: "new_users", documentId: field("name") })
  );
});
✅ ポイント: クエリ・変換・書き込みが 1 つのパイプラインで完結します。

ステップ 2: リテラル値から新規ドキュメントを insert する

JavaScript Node.js — ID を指定して insert 
// ID を指定して新規ドキュメントを挿入
const results = await db.pipeline()
  .literals([
    { foo: "bar", id: "doc1" },
    { foo: "baz", id: "doc2" }
  ])
  .insert({ collection: "users", documentId: field("id") })
  .execute();
💡 ヒント: insert({ collection: "users" }) のように ID 式を省略すると、ドキュメント ID は自動生成されます。

ステップ 3: atomic オプションで自動トランザクション実行する

JavaScript Node.js — atomic オプションで update 
// atomic オプションで新しいトランザクション内で実行し、成功時に自動コミット
const results = await db.pipeline()
  .collection("users")
  .where(field("active").equal(false))
  .addFields(constant("inactive").as("status"))
  .update()
  .execute({ atomic: true });
✅ ポイント: 明示的なトランザクション管理コードを書かずに、原子的な DML 実行が可能です。

💪 メリット

💼 ビジネス面

✓運用タスクの省力化: データモデル変更のバックフィルやコレクション間移行をパイプライン 1 本で記述でき、専用のバッチ処理コードの開発・運用コストを削減
✓GA による本番適用: 一般提供となったことで、本番ワークロードでの採用判断がしやすくなった

⚙️ 技術面

✓サーバーサイドでの読み書き完結: クライアントへの読み取り結果の往復が不要。クエリ結果に対する書き込みをサーバーサイドで宣言的に表現できる
✓高度なクエリとの組み合わせ: トランザクション内であれば search や findNearest などの高度なクエリステージの結果をそのまま書き込みに接続できる
✓原子的実行の選択肢: 明示的トランザクションと atomic オプションの 2 通りで原子的な実行を選択できる

⚠️ デメリット・制約事項

🚧 制限事項

✗Firestore Enterprise エディションが必要 (Standard エディションでは利用不可)
✗DML ステージはパイプラインの末尾に配置する必要がある
✗insert() と upsert() はほとんどのケースでトランザクション内での実行が必要
✗トランザクションでは最初の書き込み以降の読み取り不可。1 トランザクション内で DML パイプラインを複数回呼び出したり、DML 実行後にドキュメントを読み取ったりできない (FAILED_PRECONDITION エラー)
✗トランザクション外では書き込みがドキュメント間で原子的でなく、最初のエラーで停止するため部分的成功が発生しうる。aggregate / distinct / unnest / find_nearest / union / join / サブクエリなどの高度なステージも利用不可

🤔 考慮すべき点

⚠️ Firebase Security Rules: ドキュメントのバッチごとにルールが再評価される。ルールで get() / exists() を使っている場合、約 200 ドキュメントの書き込みでグローバルな 20 ルックアップ上限に達し PERMISSION_DENIED で失敗するため、Custom Claims の利用が推奨される。
⚠️ delete() の安全策: 誤った一括削除を防ぐため、delete() を使うパイプラインには少なくとも 1 つの where() ステージを含めるべき。
💡 重複 ID のセマンティクス: 前段ステージが同一ドキュメント ID を複数生成した場合の挙動 (upsert / update は後勝ち、insert は 2 回目以降エラー、delete は 2 回目以降 no-op) を理解して設計すること。

🎯 ユースケース

📝 ユースケース 1: データモデル変更のバックフィル

シナリオ: users コレクショングループの全ドキュメントに新しいフィールド preferences.color を追加するスキーマ変更を行い、既存ドキュメントをバックフィルしたい。

JavaScript バックフィル実装例 
const snapshot = await db.pipeline()
  .collectionGroup("users")
  .where(not(exists(field("preferences.color"))))
  .addFields(constant(null).as("preferences.color"))
  .removeFields("color")
  .update()
  .execute();

✨ 効果: 対象ドキュメントの抽出・変換・更新がサーバーサイドの 1 パイプラインで完結し、専用のバッチ処理コードが不要になる。

🚚 ユースケース 2: 条件に基づくコレクション間のデータ移行

シナリオ: source_coll のアクティブなドキュメントにフィールドを付与して target_coll へコピーしたい。

JavaScript データ移行実装例 
const results = await db.runTransaction(async (transaction) => {
  return transaction.execute(
    db.pipeline()
      .collection("source_coll")
      .where(field("active").equal(true))
      .addFields(constant("val").as("new_field"))
      .insert({ collection: "target_coll" })
  );
});

✨ 効果: 読み取り・変換・別コレクションへの書き込みがトランザクション内で原子的に実行され、移行処理の信頼性が向上する。

🧹 ユースケース 3: 古いデータの定期クリーンアップ

シナリオ: 作成から 10 日以上経過した特定条件のドキュメントを削除したい。

JavaScript クリーンアップ実装例 
const pipeline = db.pipeline()
  .collectionGroup("users")
  .where(field("address.country").equal("USA"))
  .where(field("__create_time__").timestampAdd("day", 10).lessThan(currentTimestamp()))
  .delete();
await pipeline.execute();

✨ 効果: クライアント側で対象を列挙して個別削除する処理が不要になり、クリーンアップ処理をクエリとして宣言的に管理できる。
