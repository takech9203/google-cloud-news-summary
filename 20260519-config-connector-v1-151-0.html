7 つの新規 Alpha リソース追加とフィールド拡張

Config Connector Alpha

📋 概要

Config Connector v1.151.0 がリリースされました。Direct Reconciler を使用する 7 つの新規 Alpha リソースが追加され、Cloud Deploy、Compute Engine、GKE Hub、Network Services、Vertex AI など幅広いサービスの Kubernetes ネイティブ管理が可能になりました。

さらに、MemorystoreInstance リソースに自動バックアップ設定とクロスインスタンスレプリケーション設定を含む複数の新フィールドが追加されています。

💡 Config Connector とは: Kubernetes の Custom Resource Definition (CRD) を通じて Google Cloud リソースを管理するオープンソースのアドオン。GitOps ワークフローやインフラストラクチャのコード化 (IaC) を実践するチームにとって重要なツール。

🔄 Before / After

❌ Before (v1.150.x 以前)

  • Cloud Deploy Automation を Config Connector で管理不可
  • Compute Future Reservation の宣言的管理不可
  • GKE Hub のフリート管理リソース非対応
  • Network Services WasmPlugin 非対応
  • Vertex AI DataLabelingJob 非対応
  • Memorystore の自動バックアップ/レプリケーション設定不可
  • gcloud CLI や Terraform など別ツールの併用が必要

✅ After (v1.151.0)

  • 7 リソースを Kubernetes から一元管理可能
  • CI/CD パイプライン自動化を宣言的に定義
  • キャパシティプランニングをコードで管理
  • フリート管理を Kubernetes マニフェストで制御
  • Wasm プラグインを GitOps で管理
  • バックアップとレプリケーションを宣言的に定義
  • Direct Reconciler による信頼性向上

📈 MemorystoreInstance 新規フィールド

フィールド 種別 説明
spec.automatedBackupConfig spec 自動バックアップ設定 (モード、保持期間 1-365 日、スケジュール)
spec.crossInstanceReplicationConfig spec レプリケーションロール (none / primary / secondary)

status.observedState.availableMaintenanceVersions status 利用可能なメンテナンスバージョン一覧

📝 設定方法

ステップ 1: Config Connector のアップグレード

Bash 
# GKE アドオンを使用している場合は自動更新
# Operator を使用している場合は手動アップグレード
kubectl apply -f https://raw.githubusercontent.com/GoogleCloudPlatform/k8s-config-connector/v1.151.0/operator-system/configconnector-operator.yaml

ステップ 2: Direct Reconciler のオプトイン

YAML 
apiVersion: memorystore.cnrm.cloud.google.com/v1alpha1
kind: MemorystoreInstance
metadata:
  name: my-memorystore-instance
  annotations:
    alpha.cnrm.cloud.google.com/reconciler: direct
spec:
  automatedBackupConfig:
    mode: enabled
    retention: "2592000s"  # 30 days
  crossInstanceReplicationConfig:
    role: primary

ステップ 3: 新規 Alpha リソースの使用例

YAML 
# CloudDeployAutomation の例
apiVersion: clouddeploy.cnrm.cloud.google.com/v1alpha1
kind: CloudDeployAutomation
metadata:
  name: promote-to-staging
  annotations:
    alpha.cnrm.cloud.google.com/reconciler: direct
spec:
  deliveryPipelineRef:
    name: my-pipeline
  serviceAccount: "deploy-sa@project.iam.gserviceaccount.com"
  selector:
    targets:
      - id: dev
  rules:
    - promoteReleaseRule:
        id: "promote-release"
        wait: "60s"
        destinationTargetId: "@next"
⚠️ 注意: Alpha リソースを使用するには alpha.cnrm.cloud.google.com/reconciler: direct アノテーションを必ず付与してください。

✅ メリット

💼 ビジネス面

✓ 運用統一化 - Kubernetes マニフェストで Google Cloud リソースを一元管理、ツール分散による運用コストを削減
✓ GitOps 対応強化 - 7 リソースが GitOps ワークフローに組み込み可能、変更追跡とレビューが容易に
✓ マルチサービス連携の自動化 - Cloud Deploy の自動化やフリート管理を Kubernetes から制御

⚡ 技術面

✓ Direct Reconciler - API との直接通信による正確な状態同期を実現
✓ 宣言的なデータ保護 - バックアップとレプリケーションのドリフト検出と自動修復が可能
✓ Eventual Consistency - リコンシリエーションループにより desired state に自動収束

⚠️ デメリット・制約事項

⚠ 新規 Alpha リソースは Alpha ステータスであり、API やフィールドが将来変更される可能性がある
⚠ Direct Reconciler の使用にはアノテーションの明示的な付与が必要
⚠ Alpha リソースは本番環境での使用は推奨されない
⚠ Alpha から Beta/GA への昇格時に CRD スキーマの変更が発生する可能性 - マイグレーション計画が必要
⚠ 既存リソースへの Direct Reconciler 適用には注意が必要

💡 ユースケース

🚀 ユースケース 1: GitOps によるデプロイパイプライン全体の管理

シナリオ: Cloud Deploy のデリバリーパイプラインと自動化ルール (自動プロモーション、自動ロールアウト進行) を、アプリケーションのマニフェストと同じ Git リポジトリで管理したい。

効果: デプロイの自動化ルールがコードとして管理され、変更履歴の追跡、コードレビュー、ロールバックが容易になる。
