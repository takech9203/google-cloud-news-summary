Gemini Enterprise Agent Platform Changed (推奨構成の変更)
📅 リリース日: 2026-10-28

🏛️ Gemini Enterprise アプリ向けに
単一のリージョナル Agent Registry の使用を推奨

Agent Gateway と Agent Registry の推奨構成が「同一プロジェクト・同一リージョンの単一リージョナルレジストリ」に明確化

📋 概要

Google Cloud は、Gemini Enterprise アプリにおける Agent Gateway と Agent Registry の推奨構成を更新しました。各 Agent Gateway を、ゲートウェイと同一プロジェクト・同一リージョンにある単一のリージョナル Agent Registry インスタンスに関連付けることが推奨されます。global / us ロケーションのアプリには us-central1、eu ロケーションのアプリには europe-west1 のレジストリを使用します。

Agent Registry は A2A エージェント・エンドポイント・MCP サーバーを発見・追跡・管理する一元的なカタログ、Agent Gateway はエージェントトラフィックを制御・統制するリージョナルなネットワーキングコンポーネントです。アプリ・ゲートウェイ・レジストリの 3 コンポーネントはリージョン的に整合している必要があり、今回の推奨事項はその構成指針をシンプルにします。

💡 ポイント: この更新は 2026 年 9 月 9 日のリリースノートエントリを更新するものです。エージェントガバナンスを設計・運用する管理者・アーキテクトは、レジストリの配置方針を見直すべき重要なアップデートです。

🔄 Before / After

❌ Before (アップデート前の課題)

  • ゲートウェイには最大 2 つのレジストリ (グローバル 1 + リージョナル/マルチリージョナル 1) を関連付け可能で、構成の選択判断が複雑だった
  • 複数レジストリに同一インターフェース URL のエントリがあると、宛先 URL 解決時の優先順位を考慮する必要があった
  • マルチリージョン (us, eu) レジストリは手動登録をサポートせず、登録先の選択で混乱が生じやすかった

✅ After (アップデート後の改善)

  • 「ゲートウェイと同一プロジェクト・同一リージョンの単一リージョナルレジストリ」というシンプルで明確な構成指針
  • global / us アプリ → us-central1、eu アプリ → europe-west1 という具体的なマッピングを明示
  • 単一レジストリ構成でエントリ解決の競合や登録先の迷いを回避

⚙️ 主要機能

1️⃣ 単一リージョナルレジストリの推奨

Gemini Enterprise アプリでは、各 Agent Gateway をゲートウェイと同一プロジェクト・同一リージョンにある単一のリージョナル Agent Registry インスタンスに関連付けることが推奨されます。エージェント、エンドポイント、MCP サーバーは、ゲートウェイに関連付けられたレジストリに登録する必要があります。

2️⃣ アプリロケーションとレジストリリージョンの明確なマッピング

✓global / us ロケーションのアプリ: us-central1 のレジストリを使用
✓eu ロケーションのアプリ: europe-west1 のレジストリを使用

3️⃣ データレジデンシー整合の強制

Agent Registry と Agent Gateway はいずれもプロジェクト・リージョン固有のリソースであり、Gemini Enterprise アプリの運用リージョンと互換性のあるリージョンで整合させる必要があります。アプリ・ゲートウェイ・レジストリの 3 コンポーネントのリージョン整合は、バインドプロセスを通じて厳密に強制されます。

📒 レジストリ関連付けの仕様

項目 詳細
ゲートウェイあたりのレジストリ数 最大 2 つ (グローバル 1 つ + リージョナルまたはマルチリージョナル 1 つ) まで関連付け可能。ただし Gemini Enterprise アプリでは単一のリージョナルレジストリを推奨
リージョナルレジストリの URI 形式 //agentregistry.googleapis.com/projects/PROJECT_ID/locations/REGION
エントリ解決の優先順位 リージョナル / マルチリージョナルのエントリがグローバルのエントリより優先される
マルチリージョン (us, eu) レジストリの制約 エージェント、エンドポイント、MCP サーバーの手動登録をサポートしない
Gemini Enterprise での Agent Gateway モード Agent-to-Anywhere (Egress) のみサポート (Ingress は非サポート)

📝 Agent Gateway の定義例 (gcloud / YAML)

YAML 
name: AGENT_GATEWAY_NAME
protocols:
  - MCP
googleManaged:
  governedAccessPath: AGENT_TO_ANYWHERE
  registries:
    - //agentregistry.googleapis.com/projects/PROJECT_ID/locations/us-central1
Bash 
gcloud network-services agent-gateways import AGENT_GATEWAY_NAME \
  --source="my-agent-gateway-egress.yaml" \
  --location=us-central1

1ロケーションとレジストリのマッピングを計画する

Gemini Enterprise アプリのロケーション (global / us / eu) に対応する Agent Gateway のリージョン (us-central1 または europe-west1) を確認し、同一プロジェクト・同一リージョンのリージョナル Agent Registry を使用するように計画します。

2Agent Gateway を作成し、単一のリージョナルレジストリを関連付ける

Bash 
# YAML でゲートウェイを定義し、リージョナルレジストリを 1 つ指定してインポート
gcloud network-services agent-gateways import my-ge-gateway \
  --source="my-agent-gateway-egress.yaml" \
  --location=us-central1

3エージェントと宛先リソースを登録する

ゲートウェイに関連付けたリージョナル Agent Registry に、A2A エージェント、MCP サーバー、エンドポイントを登録します。エージェントがアクセスする宛先には、エージェント ID に対して iap.resources.egressViaIAP 権限を付与する IAM アクセスポリシーが必要です。

💪 メリット

💼 ビジネス面

✓データレジデンシー遵守: アプリ・ゲートウェイ・レジストリをリージョン的に整合させることで、データ所在地要件への準拠を確保できる
✓運用の簡素化: 単一レジストリという明確な指針により、構成判断にかかる時間とミスのリスクを削減できる

🔧 技術面

✓エントリ解決の競合回避: 複数レジストリ間で同一インターフェース URL のエントリが競合する問題を単一レジストリ構成で回避できる
✓手動登録の確実性: マルチリージョン (us, eu) レジストリでは手動登録がサポートされないのに対し、リージョナルレジストリでは手動登録が可能

⚠️ デメリット・制約事項

🚧 制限事項

✗Gemini Enterprise では Agent Gateway は Agent-to-Anywhere (Egress) モードのみサポートし、Ingress トラフィックはサポートされない
✗Gemini Enterprise アプリ向けの Agent Gateway は、アプリのロケーションに対応する特定リージョン (us-central1 または europe-west1) にデプロイする必要がある
✗クロスプロジェクトガバナンスは Runtime エージェント (Agent-to-Anywhere モード) のみサポートされ、Gemini Enterprise はサポート対象外

🤔 考慮すべき点

⚡既存環境でグローバルレジストリやマルチリージョナルレジストリを Gemini Enterprise アプリ向けゲートウェイに関連付けている場合は、今回の推奨構成への移行を検討する必要がある
⚡識別されないエージェントからのトラフィックはデフォルトでブロックされるため、各エージェントに一意の Agent Identity (SPIFFE ID) が必要

🧩 関連サービス・機能

📒 Agent Registry

A2A エージェント、エンドポイント、MCP サーバーを発見・追跡・管理する一元的なカタログ。今回の推奨構成の中核となるリソース。

🚪 Agent Gateway

エージェントトラフィックの制御とランタイムポリシー適用を行うリージョナルなマネージドネットワーキングコンポーネント。

⚡ Agent Runtime

エージェントのデプロイ先ランタイム。リージョナルリソースであり、デプロイリージョンに対応するリージョナルレジストリに登録される。

🔐 Identity-Aware Proxy (IAP)

エージェントから宛先へのアクセスには iap.resources.egressViaIAP 権限を付与する IAM アクセスポリシーが必要。

🛡️ Model Armor

Agent Gateway と組み合わせて AI モデルとのやり取りを保護するテンプレートを適用可能。

📝 まとめ

Gemini Enterprise アプリにおける Agent Gateway の推奨構成が「同一プロジェクト・同一リージョンの単一リージョナル Agent Registry」に明確化されました (global/us アプリは us-central1、eu アプリは europe-west1)。これは 2026 年 9 月 9 日のエントリを更新するものであり、既にグローバルやマルチリージョナルのレジストリを Gemini Enterprise アプリ向けゲートウェイに関連付けている場合は、推奨構成への見直しを検討してください。
